## Objective

Make every write to the ledger feel the same in the hand. Today exactly one of them does — saving a budget — and the four most common writes are silent.

## Context

- `src/screens/add-budget-screen/add-budget-screen.tsx:236` is the only `notificationAsync(Success)` in the app.
- Silent today: saving a transaction (`add-transaction-next-screen.tsx:262-266`), saving a split (`multi-postings-transaction-screen.tsx:428-429`), editing a transaction (`edit-transaction-screen.tsx:146`), deleting a transaction (`transaction-detail-screen.tsx:197`), and the receipt parse completing (`receipt-capture-screen.tsx:105-122`).
- There is **no** `Warning` or `Error` notification haptic anywhere, so a failed save feels identical to a successful one.
- t001 factors the four flows onto one shared confirmation helper — hang the haptic off that helper so a fifth write site cannot forget it.
- Other write sites that should be considered: opening an account (`src/screens/open-account-screen/use-open-account.ts`, from `w1/m16`), and ledger file save/delete in `src/screens/ledger-file-editor-screen/index.tsx` and `src/screens/ledger-file-browser-screen/index.tsx`.
- `w1/m19` centralised what a write invalidates; this is the same idea for what a write _feels_ like.

## Steps

1. Fire `success()` from the t002 wrapper on every successful ledger write, from inside t001's shared confirmation helper rather than at each call site.
2. Fire `error()` on the failure branch of the same helper, so a rejected save is distinguishable without reading the toast.
3. Cover the file-editor and file-browser write paths, and the open-account path, even though they do not route through the transaction helper.
4. Fire exactly one haptic per user-initiated write — no double-fire when a flow both toasts and navigates.
5. Do not add a haptic to non-write confirmations (copy-to-clipboard, navigation, filter changes); this milestone is about ledger writes.
