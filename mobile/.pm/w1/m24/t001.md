## Objective

Fix the defect at the token layer: light mode has **no** token that gives a control boundary at the 3:1 non-text minimum. Either re-tune the light ramp so `black40` clears 3:1, or add an explicit paired control token (fill + boundary) that every control uses.

## Context

- Tokens live in `src/common/theme/`; the measured table is in the milestone README.
- The trade-off to decide deliberately: re-tuning `black40` moves a token ~24 surfaces already use (wide blast radius, no new concepts); adding a paired token leaves the ramp alone but means two ways to reach a boundary until adoption finishes.
- Dark mode is already fine (`black40` vs `white` = 4.07). Do not regress it.
- Related in the same root cause: light `black60` is 1.62:1 on a `black10` field and is what nine screens pass as `placeholderTextColor`.

## Steps

1. Pick the approach and write the reason into the token file — the next person needs to know why the ramp is shaped this way.
2. Implement, keeping dark values unchanged unless a measurement says otherwise.
3. Compute the resulting contrast for every affected pair, in **both** themes, and record the numbers.
4. Decide the placeholder token in the same pass; a placeholder nobody can read is the same bug wearing a different hat.

## Files

- `src/common/theme/` (the token definitions)

## Acceptance criteria

- [ ] A named token pair gives ≥3:1 boundary-vs-surface in light mode, verified by computed contrast
- [ ] Dark-mode values are unchanged or improved, verified the same way
- [ ] The placeholder color clears its contrast bar on the control fill
- [ ] The reasoning is written down next to the tokens

## Out of scope

- Adopting the token at call sites (t002).
