## Objective

When the user switches 1M → 1Y, morph the existing series into the new one instead of swapping the path in a single frame. This is the object-constancy win: the user tracks what changed rather than re-reading a chart that teleported.

## Context

- Range state and re-render paths, all currently instant swaps:
  - Home: `src/screens/home-screen/components/account-charts-card.tsx:64` (`useState<TimeRange>("6M")`), `setRange` at :127 re-runs `filterBalanceSeriesByRange` + `seriesToChartArray` for all three pages (:92-106), the chart's `useMemo` (`interactive-line-chart.tsx:147-180`) regenerates the path strings, and the SVG `d` swaps in one frame.
  - Account detail: `src/components/balance-chart-card/index.tsx:47` local state, `filterBalanceSeriesByRange` at :57-60 — slices client-side, no refetch.
  - Reports: `src/screens/reports-screen/reports-screen.tsx:54` state, `handleRangeChange` :68-71, chart rebuild `useMemo` :89-100.
- `TIME_RANGES = ["1M","3M","6M","YTD","1Y","ALL"]` in `src/common/series-util.ts:17`.
- Point counts differ per range, so the two series have different lengths — a naive index lerp is wrong.
- **Reanimated 4.5.1 ships native C++ SVG path morphing**, enabled by default since 4.4 (`EXPERIMENTAL_CSS_ANIMATIONS_FOR_SVG_COMPONENTS`). `SVGPath::interpolate` pads mismatched command counts via `splitCubic`, and the docs state iOS and Android morph freely (only Web requires matching command structure). Its one documented caveat: colliding control points get nudged, which "can cause an unpleasant 'jump'".

## Steps

1. **Spike the native route first** — `transitionProperty: 'd'` on the animated `Path`. It is by far the cheapest implementation and most published guidance predates it. Time-box the spike; judge it on whether the morph is smooth for a 1M ↔ ALL switch on a real device in both directions.
2. If the native morph jumps or misbehaves, fall back to: resample both series to a fixed N on the JS thread (keep d3 there — it cannot cross to the UI thread), lerp the two plain `number[]` arrays inside a worklet, and rebuild the `d` string in `useAnimatedProps`.
3. Use the ease-in-out easing token from t001, not the entrance easing — a morph is a transition, not an entrance.
4. Morph the gradient area `Path` with the line so the fill never detaches from the stroke.
5. Cancel and retarget cleanly if the user taps another range mid-morph; never queue two morphs.
6. Suppress the t002 draw-in on a range change — the series is transitioning, not arriving.
7. Bar charts: cross-fade or re-grow rather than morphing `Rect` geometry across a changed bar count. Keep it cheap and do not fight a changing column count.
8. Record the chosen approach (native vs. resample-and-lerp) in the milestone README's design decisions.

## Acceptance criteria

- [ ] Switching between any two ranges on Home and account detail morphs the line and its area fill rather than swapping in one frame.
- [ ] Series of different lengths morph without a visible jump or a flash of a malformed path.
- [ ] Tapping a third range mid-morph retargets smoothly; no queued or overlapping animations.
- [ ] The first-paint draw-in does not replay on a range change.
- [ ] With reduce-motion on, the new range renders immediately.
- [ ] The Reports range switch still auto-scrolls to the newest month, unchanged.
- [ ] The chosen approach and why is written into the milestone README.

## Out of scope

- Refetching on range change — every range is currently sliced client-side; keep it that way.
- Morphing across a chart-type change (no chart-type toggle exists).
