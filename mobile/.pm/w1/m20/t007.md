## Objective

Stop pull-to-refresh from destroying a rendered chart, and soften the first-load handoff so the pulsing skeleton crossfades into content instead of hard-cutting mid-pulse. This is a defect fix, not polish: the current behavior contradicts a documented rule in `mobile/CLAUDE.md`.

## Context

**The defect.** `mobile/CLAUDE.md` states: _"Skeletons are for first loads only; pull-to-refresh keeps current content visible under the `RefreshControl` spinner (`refreshing` must track only the user's pull, not query loading)."_ Two screens do the inverse — they feed the user's pull into the skeleton:

- `src/screens/home-screen/home-screen.tsx:77` — `const isLoading = balanceSheetLoading || refreshing;`, passed as `loading` to the charts card at :139.
- `src/screens/account-detail-screen/account-detail-screen.tsx:254` — `loading={reportLoading || refreshing}`.

So every pull blanks a perfectly good chart to a pulsing tile and re-runs its entrance animation once t002/t004 land — which would make the regression worse, not better.

**The crossfade.** Every skeleton in the app is a bare ternary — `{isLoading ? <Skeleton/> : <Real/>}` — so a pulsing tile hard-cuts to real content at whatever opacity the pulse happened to reach. `src/components/loading-tile/index.tsx:44-61` pulses opacity 1 → 0.5 → 1 on a 600ms cycle with no easing. The team has already pixel-matched skeleton to content in several places (comments at `src/screens/multi-postings-transaction/list-item.tsx:52`, `src/screens/account-picker-screen/account-picker-screen.tsx:212`, `src/components/text-input-screen/index.tsx:93`, `src/screens/budget-screen/budget-screen.tsx:192`), so a crossfade has nothing to shift.

Good precedent already in the tree: `src/screens/add-transaction-screen/quick-add-accounts-selector.tsx:150-152`, `src/screens/home-screen/components/budget-card.tsx:82` and `src/common/hooks/use-ledger-meta.ts:9` all suppress the skeleton on refetch and show it only on first load.

## Steps

1. Split first-load from refresh on both screens: `loading` must mean "no data yet", never "the user pulled". Follow the `quick-add-accounts-selector.tsx:150-152` pattern.
2. Verify the `RefreshControl` spinner still appears and `refreshing` still tracks only the pull, so the gesture keeps its feedback.
3. Confirm the entrance animations from t002/t004 fire on first load only and never on a refresh.
4. Add `entering={FadeIn}` (duration from the t001 tokens) to the loaded branch of the chart surfaces in this milestone's blast radius: `account-charts-card.tsx:68-79`, `spending-card.tsx:83`, `balance-chart-card/index.tsx:52`, `reports-screen.tsx:139-141`, `budget-group-card.tsx:249-250`.
5. While in these files, fix the skeleton/content height mismatches so the crossfade has nothing to shift: spending card skeleton is 200 against a 220 chart; `balance-chart-card` is 240 against ~305 loaded; the Reports chart skeleton omits the legend row height.
6. Give `LoadingTile`'s pulse an easing token and slow the 600ms cycle to something that reads as a breath rather than a throb.
7. `LoadingTile`'s pulse is a `withRepeat` loop, which Reanimated's `ReduceMotion.System` default does **not** stop — gate it on `useReduceMotion()` from t001 and render a static tile when reduce-motion is on.
