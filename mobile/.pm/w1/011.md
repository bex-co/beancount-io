# Light neutral ramp gives no usable control boundary

The account-picker polish (w1/m17) exposed a token problem rather than a screen problem: `theme.black10` — the fill under search fields, chips, cards and drawers — is effectively the same value as the `theme.white` surface it sits on, so those controls read as smudges. Measured contrast against the surface token:

| pair                 | light    | dark |
| -------------------- | -------- | ---- |
| `black10` vs `white` | 1.10     | 1.21 |
| `black20` vs `white` | 1.18     | 2.50 |
| `black40` vs `white` | **1.34** | 4.07 |
| `black60` vs `white` | 1.78     | —    |
| `black80` vs `white` | 5.22     | —    |

The light ramp is compressed: the first four steps all land within 1.1–1.35 of the surface, then it jumps straight to secondary-text darkness. So there is **no token that gives a light-mode control boundary at the 3:1 non-text minimum** — the picker's new `black40` border clears it in dark (4.07) but not in light (1.34), where it is only marginally better than the fill it was added to rescue.

Scope: ~24 `backgroundColor: theme.black10` surfaces, including both other search fields (`transactions-header.tsx`, `journal-header.tsx`, neither of which has a border), `dashboard-card` (which already reaches for a `black20` hairline for exactly this reason), `picker`, `menu-button`, `ledger-drawer`, `text-input-screen`, `progress-bar`. Related and same root cause: light `black60` — documented as "placeholders / disabled" — is 1.62:1 on a `black10` field, and nine screens pass `placeholderTextColor={theme.black60}`. Dark is 5.21, so this is a light-only defect.

Fix at the token layer, not per screen: either add a paired control token (fill + boundary) or re-tune the light neutral ramp so `black40` clears 3:1 — then delete the per-screen borders the picker added. Doing it screen by screen leaves the app with search fields that look different from each other and the underlying token still broken.
