## Objective

Prove that canonical files and App Store Connect agree, then release the already-staged version through the existing tag-anchored workflow without losing localized assets.

## Context

- A metadata pull is the authoritative parity check after application.
- Generated screenshots are gitignored, so verification must cover the remote resource list as well as reproducibility from tracked inputs.
- The milestone's adoption outcome is not real until the localized version reaches distribution; closeout must wait for that observable state.

## Steps

1. Pull the applied version into `mobile/tmp/` and diff it against canonical app-info and version JSON without overwriting approved local work.
2. List remote screenshot sets and verify locale, display type, count, dimensions, processing state, and explicit order.
3. Push the already-staged version change through the normal release workflow and monitor build, submit, App Review, and distribution state.
4. After release, spot-check representative storefronts and both fallback languages, then record privacy-safe baseline metrics for the later 28-day comparison.

## Files

- `mobile/metadata/**`
- `mobile/tmp/` for ignored pull/diff output.
- `.github/workflows/deploy.yml` only if verification exposes an ordering defect.

## Acceptance criteria

- [ ] Canonical and pulled remote metadata match for all target localizations.
- [ ] Every remote screenshot set is processed and ordered as declared by the manifest.
- [ ] The release pipeline submits only after localized listing assets are present and reaches `READY_FOR_DISTRIBUTION`.
- [ ] Bulgarian and Persian storefront checks receive the documented primary fallback while their installed app UI remains localized.

## Out of scope

- Drawing a conversion conclusion before the planned post-release measurement window.
