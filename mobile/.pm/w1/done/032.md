# Merchants beyond parity — parked follow-ons from the 2026-08-19 research

Each is real value from the Monarch Merchants research that m35–m37 deliberately
do not attempt, parked on a named blocker:

- **Rename / merge merchants** — Monarch's merge is "rename into a name
  collision." For us a rename means rewriting the payee across ledger source
  files (the app can write files, but a multi-file text rewrite of production
  ledgers needs bean-check gating and its own design + owner sign-off).
  Cheap 80% first: display-only case-insensitive grouping in the directory
  ("Burger king" + "Burger King" as one row), which needs no writes.
- **Ledger-native persistence for recurring marks** — m37 stores overrides
  device-local. The beancount-idiomatic durable home is a
  `custom "recurring" "<payee>" "<cadence>"` directive (syncs everywhere,
  round-trips as plain text). Blocked on an owner decision about writing
  non-transaction directives from the app and the directive's shape.
- **Recurring calendar screen** — Monarch's month calendar with the
  paid / different-amount / upcoming / missed color language. Needs m37's
  forecast data to exist first, then a design pass; a list ships most of the
  value earlier.
- **Pre-charge reminders** ("expected in 3 days") — needs server-side push
  scheduling; nothing in the mobile schema supports it today.

---

**Triage — 2026-09-07.** The one unblocked item shipped; the rest stay parked
where their blockers live.

**Shipped: display-only case-insensitive grouping.** `aggregatePayees` now
folds rollup rows whose payee differs only by case into one directory row —
counts sum, the date span merges, and the row displays the variant with the
most transactions (ties: more recently used, then lexicographic). Unit-tested
(fold, casing winner, order independence, tie-break, and the negative case —
"Burger Kings" does not fold into "Burger King"). Known, accepted seam:
tapping the row opens merchant detail for the shown casing only, so a grouped
row's count can exceed the detail's — making detail variant-aware needs the
BQL statements and recurrence keying to take a variant set, which is the same
scope as real rename/merge and stays behind that blocker.

**Still parked, blockers unchanged:** rename/merge (multi-file ledger rewrite;
bean-check gating + owner sign-off), ledger-native `custom "recurring"`
persistence (owner decision on writing non-transaction directives), the
recurring calendar screen (design pass on m37's forecast data), pre-charge
reminders (server-side push). Each is re-raisable via `/pm-brainstorm` when
its blocker clears; this note in `done/` is the source for that scoping.
