## Objective

`app/(app)/(tabs)/_layout.tsx:49` sets `lazy: false`, so all five tabs mount — and issue their queries — before the user has visited any of them. Mount lazily, and make sure the first visit to each tab still looks right.

## Context

- Five tabs today: Home, Accounts, Reports, Transactions, Ledger.
- The risk is the first paint of a tab that now mounts on demand: `mobile/CLAUDE.md` requires background colors on loading states, and a missing one caused dark-mode flicker on the account picker before.
- `83bddba` ("unify nav bar position and eliminate tab-switch flicker") is the behavior not to regress.
- Every tab's first-load skeleton is in place after `w1/m20/t007`, so there is something to show while a lazily-mounted tab fetches.

## Steps

1. Flip to lazy mounting (globally, or per screen if any tab genuinely needs to be warm).
2. Cold-start and confirm only the first tab's queries fire; then visit each tab and confirm its skeleton renders with a background color, in light **and** dark.
3. Re-check the `83bddba` flicker fix and the drawer gesture on first mount.
4. Update `w1/m23/t004`, whose cost argument assumes every tab is already mounted.

## Files

- `app/(app)/(tabs)/_layout.tsx`

## Acceptance criteria

- [ ] Cold start issues queries for the first tab only
- [ ] Each tab's first visit renders a themed skeleton with no flicker in light and dark
- [ ] Tab-switch position/flicker behavior from `83bddba` is unchanged

## Out of scope

- Prefetching strategies; changing any tab's queries.

## Outcome

`lazy: true`, with the reasoning in a comment above it. Verified by cold-starting the dev build: Home renders and fetches; Accounts, Transactions, Reports and Files each mount on first visit and show their own themed skeleton.

The `83bddba` concern was checked and is unfounded — that commit fixed tab-switch flicker by lifting the single `SafeAreaView` into this layout and by evening out nav-bar heights; neither depends on eager mounting, and the inset is computed here once regardless. `lazy: false` turned out to predate the monorepo move (`182a07f`) with no rationale recorded anywhere.
