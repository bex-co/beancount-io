## Objective

Replace the browser's self-only `refetch()` with the `file` scope, and close the stale-sha hole: the browser hands `entry.sha` from its cached directory listing to `deleteLedgerFile`, but a save in the pushed editor advances that sha and the browser never refetches.

## Context

- `handleCreate` (`src/screens/ledger-file-browser-screen/index.tsx:371`) and `confirmDelete` (`:409`) call the screen's own `refetch()` — correct for the listing, but they also change ledger content and invalidate nothing else.
- `confirmDelete` passes `entry.sha` (`:398`), sourced from `getLedgerDirContent`.
- The stale path: the Files tab renders `LedgerFileBrowserScreen` via `LedgerScreen` (`app/(app)/(tabs)/ledger.tsx`), and `/(app)/ledger-file-editor` is pushed on the `(app)` stack **above** the tab navigator. The tab stays mounted underneath, `cache-and-network` does not re-run without a remount, and there is no focus refetch. So after save → back → delete, the sha is pre-save. t002's leave-time `file` invalidation is what actually fixes this, since `GetLedgerDirContentDocument` is in that scope; this task confirms it end-to-end.
- Whether the backend rejects a stale sha on **delete** the way it does on update is not verifiable from this repo (the update path has `isConflictError` handling at `index.tsx:362`). Verify against a real ledger; if delete does not enforce the lock, the fix is still correct — the listing's size/`lastCommitSha` were stale regardless.

## Steps

1. Swap the create and delete paths onto `invalidateLedgerData(client, "file")`, keeping the local `refetch()` only if it still buys an earlier repaint.
2. Reproduce the stale-sha path on a real ledger: open a file, save, go back, delete it.
3. Confirm the fix, and record in the milestone README whether the backend enforced the lock on delete.
