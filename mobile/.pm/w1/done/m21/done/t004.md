## Objective

Give the AI receipt flow a payoff. Right now the highest-magic action in the app — point a camera at a receipt and have the fields extracted — ends with a silent screen swap, so the user never sees that anything was understood.

## Context

- `src/screens/receipt-capture-screen/receipt-capture-screen.tsx:105-122` — on `phase.kind === "parsed"` it calls `analytics.track("receipt_parsed", …)` and then `router.replace()` straight into `/(app)/add-transaction` with `prefillDate`, `prefillPayee`, `prefillNarration`, `prefillSourceAccount`, `prefillTargetAccount`, `prefillAmount`. **No toast, no haptic, no reveal.**
- The `replace` (not `push`) is deliberate and documented at :102-104: it drops the camera from the stack so the form's own `router.back()` after saving returns to where the scan started. **Preserve that.**
- Workflow phases: `idle → uploading → parsing → parsed | error` (`src/screens/receipt-capture-screen/use-receipt-workflow.ts:18-23`).
- During upload/parse the screen shows a full-screen `ActivityIndicator` over a scrim (`preview-view.tsx:39-41,128`); the comment at :39-40 explains the deliberate choice of spinner over skeleton there. Leave that decision alone.
- Amount is normalised with `Math.abs(...).toFixed(2)` because receipts are expenses and the model's sign is unreliable — keep that.
- Pillar 2 in `.pm/GOAL.md` is explicit that **AI proposes, the user confirms**. A reveal that shows what was extracted before handing to the editable form serves that directly; it must not imply anything was written to the ledger. Nothing is saved at this point.
- `w1/m10` shipped this capture flow; this task finishes its last beat.

## Steps

1. Between `parsed` and the `router.replace`, show a brief reveal of what was extracted — payee, amount, date at minimum — so the user sees the app understood the receipt.
2. Keep it short. The motion budget is under 500ms for the transition; the reveal must not become a step the user has to dismiss on every scan.
3. Fire the success haptic from the t002 wrapper as the reveal lands.
4. Make the wording clearly a proposal, not a record — this is pre-confirmation, and nothing has been written to the ledger. All strings go in the English base under `src/translations/` and render via `useTranslations()`.
5. Preserve `router.replace` semantics exactly, including the stack behavior the comment at :102-104 describes, and all six prefill params plus the `Math.abs` normalisation.
6. Handle the `error` phase with the same care: an error haptic and an honest message, never a silent fallback.
7. Gate the reveal's motion on reduce-motion if `w1/m20/t001` has landed; otherwise rely on Reanimated's `ReduceMotion.System` default.
8. Keep the existing `receipt_parsed` analytics event, and consider one for the reveal being seen.

## Acceptance criteria

- [ ] A parsed receipt shows the extracted payee, amount and date before the form takes over.
- [ ] The reveal is brief and self-dismissing — it never requires a tap and never adds a step to a repeat scan.
- [ ] A success haptic fires as it lands; the error phase produces an error haptic and an honest message.
- [ ] The form still receives all six prefill params, amount still normalised via `Math.abs`.
- [ ] `router.back()` from the form after saving still returns to where the scan started (the camera is not in the stack).
- [ ] Copy makes clear this is a proposal awaiting confirmation, not something already recorded.
- [ ] All new strings in the English base, rendered via `useTranslations()`; correct in light **and** dark.

## Out of scope

- Changing the parse itself, the workflow phases, or the upload/parse spinner.
- Letting the user edit fields inside the reveal — the add-transaction form is where confirmation happens.
