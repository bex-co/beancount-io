## Objective

Remove the two hard-coded two-second waits that sit between a successful save and the user getting their screen back, and give all four write flows one consistent confirmation path.

## Context

Two flows deliberately stall for two seconds after a successful save so the success toast is visible before the screen unmounts:

- `src/screens/add-transaction-screen/add-transaction-next-screen.tsx:267-274` — `setTimeout(async () => { … await callback(); … router.back(); }, 2000)`.
- `src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:430-437` — the identical block.

The `AddTransactionCallback` refetch is **inside** the timeout, so the previous screen also stays stale for those two seconds.

A third flow does it differently:

- `src/screens/edit-transaction-screen/edit-transaction-screen.tsx:129-152` — loading toast → success toast → `router.back()` immediately (:147).

And a fourth:

- `src/screens/transaction-detail-screen/transaction-detail-screen.tsx:182-205` — `Alert.alert` confirm → success toast → immediate `router.back()` (:197-198).

The toast provider (`src/common/providers/toast-provider/index.tsx`) renders a centre-screen pill over the whole app, mounted app-wide in `src/common/providers/providers.tsx:22`, with `FadeIn`/`FadeOut` at 300ms (:63-64) and a 2000ms default dwell (:88). Because it is mounted above the navigator, **a toast shown just before `router.back()` survives the transition** — which is exactly why the stall is unnecessary.

This also relates to `w1/m19`, which centralised ledger invalidation: the callback here should not be racing a timer.

## Steps

1. Delete both `setTimeout(…, 2000)` blocks. Run the `AddTransactionCallback` and `router.back()` immediately on success.
2. Confirm the success toast survives the navigation — the provider sits above the navigator, so it should. Verify on device rather than assuming.
3. Factor the four flows' shared shape (show loading → branch on `result.data?.addEntries?.success` → confirm → return) into one helper so quick-add, split, edit and delete cannot drift apart again.
4. Preserve the payload-branching comment and behavior at `multi-postings-transaction-screen.tsx:424-429` — the hook's `error` field is a render behind, so a server-rejected split must branch on what the server actually returned, not on `error`.
5. Keep failure behavior exactly as it is: error toast, stay on the screen, do not navigate.
6. Do not change what the toast says; reuse `t("saveSuccess")` / `t("saveFailed")`.

## Acceptance criteria

- [ ] Saving a transaction returns to the previous screen immediately; measured wall-clock from tap to previous screen drops by ~2s.
- [ ] Saving a split behaves identically to saving a single transaction.
- [ ] The success toast is still readable after the transition on a real device.
- [ ] The caller's refetch fires immediately, so the previous screen is never stale for two seconds.
- [ ] A server-rejected save still shows the error toast and does not navigate — verified for the split path specifically.
- [ ] No `setTimeout` remains in any save path.
