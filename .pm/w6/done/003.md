# Count BQL result rows rather than physical lines in MCP text summaries

**Severity:** minor. **Estimate:** 45–60 minutes for the adapter and regression coverage; promote if trustworthy count metadata requires a broader wire change. **Owner:** backend-v2. **A1 — Agent-native accounting:** the row count an agent uses to check its query must agree with the actual result, including multiline cells and directive output.

## Live reproduction

Observed 2026-10-09 on `https://beancount.io/api-gateway/mcp`, Node 24.16.0, `main` at `94948115`; initially `a7c5d4ef`. `initialize` reports `beancount-mcp` 1.0.0, protocol `2025-11-25`. Deployed SHA and equality with HEAD remain unverified. Credential: designated QA `bcio_` API key, scopes `ledger.read ledger.write ledger.admin`, unpinned. Only the existing synthetic MCP evaluation ledger was read.

On any populated synthetic ledger, send this JSON-RPC request; `\n` in the JSON string becomes a newline inside the BQL string literal:

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"runBqlQuery","arguments":{"ledger":"qa-owner/qa-book","query":"SELECT 'qa\nline' AS qa_text LIMIT 1"}}}
```

Equivalent bundled-helper command from the repo root:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env call runBqlQuery "{\"ledger\":\"qa-owner/qa-book\",\"query\":\"SELECT 'qa\\nline' AS qa_text LIMIT 1\"}"
```

Two fresh requests return HTTP 200, `Content-Type: text/event-stream`, `ok:true`, and:

```json
{"content":[{"type":"text","text":"2 rows\nqa_text\n-------\nqa\nline"}],"structuredContent":{"ok":true,"result":"qa_text\n-------\nqa\nline\n"}}
```

Expected first line: `1 row`. The result is one cell containing a newline, not two result rows. `runBqlQueryStructured` for the identical query returns `rowCount:1`, `truncated:false`, and `table.rows:[["qa\nline"]]`, on both fresh requests.

The same cause affects ordinary directive output: `PRINT` on the existing synthetic fixture reports **63 rows** in `runBqlQuery` twice, while the structured query returns **29** table rows. Counts only are public here; no fixture/account contents are needed to reproduce the literal-cell case.

It also miscounts ordinary short results without embedded newlines. `SELECT COUNT(*) AS qa_count` returns a single value, `34`, in one typed row, but the text summary says `3 rows` on two fresh calls (`qa\n--\n34\n` is the raw table). `SELECT 1 AS qa_count LIMIT 1` likewise reports `3 rows` versus one typed row. An empty-string cell reports `2 rows` versus one typed row.

## Controls and root cause

- REST `POST /api-gateway/v1/ledgers/qa-owner/qa-book/query` with `{ "query": "SELECT 'qa\nline' AS qa_text LIMIT 1", "format": "json" }` returns one typed row. It was repeated with the same result.
- GraphQL `queryShell` returns the same one-row table; `queryShellText` returns the same raw multiline table as MCP's string payload. Its valid response is HTTP 200. The producer is not duplicating result rows.
- A literal backslash-plus-`n` control (`SELECT 'qa\\nline' AS qa_text LIMIT 1`) correctly reports `1 row`; an empty-result query correctly reports `0 rows — no postings matched`.
- `src/features/ai-agent/api/mcp-result-text.ts:53–71` computes the count by splitting rendered text on newlines, dropping blank lines, locating a dashed separator, and counting every subsequent physical line. A multiline cell therefore becomes several purported rows. A rendered directive includes its posting lines, producing the `PRINT` overcount.
- The separator regex requires at least three dashes. The actual text producer (`backend-cluster/ledger/src/features/ledger/service/ledger-shell-mappers.ts:260–289`) legitimately permits a column width of one or two characters, giving `-` or `--`. Those tables take the no-separator fallback, which counts their header and rule as extra rows; dropping blank data lines adds a further miscount for empty cells. This producer was source-traced only; no ledger-package change is proposed merely to force its valid tables into the heuristic.
- `src/server/api/composition-root.ts:1026` calls this formatter for successful tool responses. Its `structuredContent` remains the correct raw string. `src/features/ai-agent/tools/bql-query-tool.ts:145` computes the structured tool's count from `table.rows`, explaining the working control.

Caller search finds one production caller of `renderToolText`, the registry result wrapper. The physical-line heuristic is specific to `runBqlQuery`; the structured tool's numeric summary is separate. The ledger's text serializer legitimately preserves multiline cells; flattening or deleting cell content to make this heuristic pass is not the requested repair.

## Fix and acceptance

Derive the summary count from trustworthy row metadata associated with the same query result, not rendered line boundaries. Keep the public `runBqlQuery` string payload and readable text, including embedded newlines, and preserve the typed tool's rows, decimal/date types, cap, and truncation behavior. Do not add an independent second query that can observe a different ledger revision merely to count rows. If a canonical producer contract must carry count metadata, identify that dependency explicitly and follow its owning-package guidance; do not introduce cross-package imports or duplicate an upstream query engine.

Regression coverage must exercise the registry/text envelope for the one-row multiline literal, the literal-backslash control, empty results, one- and two-character columns, blank cells, an ordinary count aggregation, ordinary tables, and a multiline directive result. Assert counts against the canonical typed result and preserve REST/GraphQL raw/typed values. All eligible API surfaces must retain the same underlying query behavior; this reproduced discrepancy is in MCP's added summary. Run backend-v2 typecheck, tests, and OpenAPI drift generation when implementing.
