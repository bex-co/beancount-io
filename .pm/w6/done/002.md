# Distinguish invalid JSON-RPC envelopes from malformed JSON

**Severity:** minor. **Estimate:** 40–50 minutes, including socket-level regression coverage. **Owner:** backend-v2. **A1 — Agent-native accounting:** a client should be told whether its JSON syntax or its request envelope needs correction.

## Live reproduction

Production `https://beancount.io/api-gateway/mcp`, 2026-10-09; Node 24.16.0; `main` at `3ee1cbf9`. `initialize` reports `beancount-mcp` 1.0.0 and protocol `2025-11-25`. Deployed SHA and equality with HEAD remain unverified. Credential: designated QA `bcio_` API key, scopes `ledger.read ledger.write ledger.admin`, no ledger pin. No ledger is needed.

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env raw --body '{}'
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env raw --body '{"jsonrpc":"1.0","id":1,"method":"tools/list"}'
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env raw --body '{"jsonrpc":"2.0","id":1}'
```

The empty object and wrong-version object were repeated in fresh requests. All three syntactically valid JSON objects return HTTP 400, `Content-Type: application/json`, and:

```json
{"jsonrpc":"2.0","error":{"code":-32700,"message":"Parse error: Invalid JSON-RPC message"},"id":null}
```

Expected: HTTP 400 and JSON-RPC `-32600` (Invalid Request), retaining `id:null`. The [JSON-RPC 2.0 error definitions](https://www.jsonrpc.org/specification#response_object) distinguish invalid JSON text (`-32700`) from a JSON value that is not a valid Request object (`-32600`); `jsonrpc` must be exactly `"2.0"` and `method` is required. No support for JSON-RPC 1.0 or new batch behavior is requested.

## Controls and root cause

- Posting syntactically malformed `{` correctly returns HTTP 400 and `-32700` with `Parse error: the body is not valid JSON`.
- Posting `{"jsonrpc":"2.0","id":1,"method":"ping"}` succeeds with HTTP 200. Authentication and transport are working.
- `src/server/middleware/body-parser-middleware.ts:53` translates errors only when Koa cannot parse the body. A valid object passes through.
- `src/features/ai-agent/api/mcp-route.ts:140` passes the already parsed body directly to `transport.handleRequest` without classifying an invalid JSON-RPC envelope.
- Installed MCP SDK 1.30.0 `dist/cjs/server/webStandardStreamableHttp.js:503–511` validates `JSONRPCMessageSchema` after obtaining parsed JSON, but returns `-32700` for its schema failures. The JSON text is already parsed at this point. The application inherits that incorrect classification.

This affects envelope-invalid authenticated POSTs before method dispatch, independently of a tool, prompt, ledger, or resource. Authentication policy, successful notifications, and ordinary domain errors are not implicated. REST and GraphQL do not accept JSON-RPC envelopes, so they have no equivalent error-code operation to change; the live controls are the valid MCP request and malformed-JSON request. No domain work or mutation was requested.

## Fix and acceptance

Classify a valid JSON value with an invalid JSON-RPC envelope at the owned MCP transport boundary as `-32600`, without changing the SDK privately or replacing its transport. Preserve existing authentication order, HTTP media-type/Accept/protocol refusals, successful requests and notifications, body limits, and the existing `-32700` response for malformed JSON text. Preserve currently supported batch behavior rather than adding support in this repair.

Socket-level tests should post the three reproduced objects and malformed JSON, drain every response, and assert status, content type, error code, and null id. Include valid ping/initialize and notification controls, ensuring an invalid request reaches no registry handler. Run backend-v2 typecheck, tests, and OpenAPI drift generation when implementing.

---

**Resolved 2026-10-10** — The owned MCP HTTP boundary classifies parsed invalid JSON-RPC envelopes as HTTP 400 / `-32600` with JSON content and `id:null`, while malformed JSON remains `-32700`. Authentication, media-header precedence, protocol validation, empty/unparsed bodies, duplicate Content-Type refusals, body limits, notifications and current batch behavior are preserved. Invalid envelopes reach no registry factory or handler. Shipped in `62bc5b6f` (`backend-v2`).

The 21-case real-socket regression suite drains all responses under finite deadlines. Reverting only the route fix makes five classification cases fail and leaves sixteen controls passing; the source is restored byte-exact afterward. All 305 backend suites (5,177 tests), typecheck, lint/dead-code detection, build and OpenAPI generation pass without snapshot drift. REST and GraphQL accept no JSON-RPC envelopes; no domain operation, eligibility or credential policy changes. Tests mock only identity and use the actual parser, route and SDK transport; production deployment and billed agent sessions remain unverified.
