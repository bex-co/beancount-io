# Opening Edit Transaction overwrites the detail screen's cached entry context and drops `generated_from`, which logs Apollo's "Cache data may be lost" and costs a redundant refetch

**Trivial · mobile · 15–25m · A2.** Native mobile QA, 2026-11-10, repository HEAD `59f13b939`, development build `io.beancount.ios` 1.20261002.50 on iPhone 17e / iOS 27.0, English, signed in as the QA account on its synthetic `example` ledger. Read-only: Edit Transaction was opened and left untouched. **No user-visible symptom was observed** (the detail screen stayed correct in every frame captured); this is a verified cache-design defect with a log signature and one redundant request per open, filed because the fix is tiny and a third selection set would turn it into real data loss.

## Repro (log signature, counted exactly)

1. Note the number of lines in the dev server log that contain Apollo's error `15` for `getLedgerEntryContext` (`https://go.apollo.dev/c/err#…"message":15,"args":["getLedgerEntryContext","Query",…`; the URL decodes to "Cache data may be lost when replacing the getLedgerEntryContext field of a Query object … either ensure all objects of type EntryContext have an ID or a custom merge function").
2. In the app, open the **Transactions** tab and open one entry's detail. The count does not change (3 → 3).
3. From that detail, tap the **pencil** (Edit Transaction). The count rises by one (3 → 4). Leaving back to the list adds none.

**Expected:** two screens that read the same entry's context do not discard each other's fields, and Edit does not trigger a data-loss warning.
**Actual:** each Edit open logs the warning once, and the detail screen underneath is sent back to the network for data it already had.

## Root cause (verified in Node with the app's real documents and defaults)

Two GraphQL documents select the same root field with the same variables, and the cache has no `typePolicies` (`mobile/src/common/apollo/cache.ts` is a bare `InMemoryCache`; `invalidate-ledger.ts:5` says so on purpose):

- `GetLedgerTransactionContext` (`src/common/graphql/queries/getLedgerTransactionContext.graphql`) selects `generated_from` besides the five common fields. Transaction detail reads it through `useTransactionContext` (`transaction-detail-screen/use-transaction-context.ts:19`).
- `GetLedgerEntryContext` (`getLedgerEntryContext.graphql`) omits `generated_from`, because a server older than 2026-10-21 rejects the field (`w21/508`). Edit Transaction reads it with `fetchPolicy: "network-only"` (`edit-transaction-screen.tsx:167-175`).

`EntryContext` has no id, so Apollo stores one object per `getLedgerEntryContext({entryHash, ledgerId})` and the second write **replaces** the first. When Edit's smaller object lands, the detail document is incomplete (`generated_from` missing).

- **Cache probe** (`InMemoryCache` plus both real `.graphql` files): after the full document is written, `cache.diff` of it is complete; after the basic document is written it is **incomplete**; after a refetch of the full document it is complete again. Apollo prints error 15 at the second write, matching the log.
Rerun the cache probe from `mobile/` (plain Node, nothing is installed or written):

```js
const fs = require("fs");
const { InMemoryCache, gql } = require("@apollo/client/core");
const doc = (f) => gql(fs.readFileSync(`src/common/graphql/queries/${f}`, "utf8"));
const FULL = doc("getLedgerTransactionContext.graphql"), BASIC = doc("getLedgerEntryContext.graphql");
const variables = { entryHash: "h1", ledgerId: "example/ledger" };
const ctx = (more) => ({ getLedgerEntryContext: { __typename: "EntryContext", slice: "s", sha256sum: "a", entry: {}, balances_before: [], balances_after: [], ...more } });
const cache = new InMemoryCache();
const complete = (query) => cache.diff({ query, variables, returnPartialData: true, optimistic: false }).complete;
cache.writeQuery({ query: FULL, variables, data: ctx({ generated_from: null }) });
console.log(complete(FULL));                                  // true
cache.writeQuery({ query: BASIC, variables, data: ctx({}) }); // prints Apollo error 15
console.log(complete(FULL));                                  // false
```

- **Request count** (a real `ApolloClient` with the app's `APOLLO_DEFAULT_OPTIONS`, both documents watched, a link recording operation names): one screen's worth of watching sends `GetLedgerTransactionContext`, `GetLedgerEntryContext`, then `GetLedgerTransactionContext` **again**. The third request exists only to restore `generated_from`; the watcher's result never showed "no data" in between, which is why no flash was seen on the device.

## Fix

Smallest: give the field a merge policy, `typePolicies: { Query: { fields: { getLedgerEntryContext: { merge: true } } } }` in `cache.ts`, so the two selections accumulate instead of replacing each other. Check it against two deliberate choices: `invalidate-ledger.ts:93` leaves `getLedgerEntryContext` out of its eviction lists (evicting it after a delete would send the still-mounted detail screen back for an entry that no longer exists), so a merge policy changes nothing there; and Edit's `network-only` read, which must keep returning the fresh slice and checksum (a merge of equal field names takes the newer values; confirm that a field the server stops sending, such as a `generated_from` that becomes null, is overwritten and not kept). Alternative: have Edit read `GetLedgerTransactionContext` too, falling back to the basic document only for a server that rejects the field, as the detail hook does. Add a unit test that writes both documents into the app's cache and asserts the full one stays complete (the probe above is the test body), then confirm the device log count stays at 0 across an Edit open. Mobile only; no API surface.

## Blast radius

The basic document has two other readers: the Entry Context card (`transactions-screen/entry-context/index.tsx:198`, skipped when the screen already supplies the context) and the budget entry delete (`budget-screen/hooks/use-delete-budget-entry.ts:46`, `network-only`). The guest client allowlists both documents (`guest-client.ts:46`, `:63`); the guest path was not exercised. Only the Edit-over-detail order was observed on the device.

**Audit of every other root field (2026-11-10, a script over `src/common/graphql/queries/*.graphql` and `src/generated-graphql/schema.graphql`; 43 root fields, 54 root selections):** six are selected by two or more operations, and this is the only one that conflicts.

- `getLedger`, `listLedgers`, `userProfile` return types with an `id`, so Apollo normalizes them and different selections merge by entity: safe. (`DiscoveryIdentity(userId)` selects no `id`, but it is keyed by its own `userId` argument, so it never shares an entry with the others.)
- `getLedgerBalanceSheet`: `BalanceSheet` (`conversion: "at_value"`, no `time`) and the three aliases of `BalanceSheetBasis` (`"at_cost"`, `"units"`, `"units_by_cost"`) differ by the **value** of `conversion`, so their cache keys differ: safe (`use-balance-sheet.ts:14`, `use-balance-sheet-basis.ts:14`, `balance-util.ts:20`, `:33`). A tool that compares argument names alone flags it falsely.
- `getLedgerErrors`: the basic document runs only after the full one is rejected by an older server (`use-ledger-errors.ts:25-28`, `ledger-errors-read.ts:42`), and a rejected document writes nothing, so the two never overwrite each other: safe.

The audit also shows the one-line guard worth adding to the fix: a unit test that, for every root field selected by two operations whose return type has no `id`, asserts the two selection sets are equal or the field has a merge policy.

## Adjacent states

An Edit save (its returned slice legitimately changes the entry, `w21/692`, `w21/906`), a generated copy (the pad and plugin copies for which `generated_from` is set; per `w21/508` Edit is withheld on them, so the order was not exercised on the device), and a guest.

## Dedupe

Searched `.pm/**` (including `done/`) for "may be lost", "custom merge", "merge: true", `typePolicies`, `go.apollo.dev` and `GetLedgerTransactionContext`. `w21/done/508` introduced the second document and `w21/done/867` fixed its guest allowlist; neither considers the shared cache key. The earlier QA note that the Apollo `onError` deprecation (message 103) is a dev-only non-finding stays true; this one differs because it changes what the cache holds and what the app requests.

## Unverified

A user-visible effect (none seen), whether the redundant request is slow enough to matter on a poor network, a real older server (not available), and Android.
