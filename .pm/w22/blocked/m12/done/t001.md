## Objective

Choose what `bea cloud git credential` hands Git as the password, and how `bea cloud git setup` finds the host to register for, then record the decision where the next tasks and later readers will find it.

## Context

- The Git proxy accepts HTTP Basic with a `bcio_` token (authorized like REST: `ledger.read` to clone and fetch, `ledger.write` to push, a ledger pin respected) or a password (`git-proxy-handler.ts`, `gitCredentialKind`, `authenticateToken`).
- Recommended option (a): at `setup`, `bea` mints a personal access token for itself through `POST /api-gateway/v1/api-keys`, named after the device (`bea git on <hostname>`), with `ledger.read` and `ledger.write` and an expiry, and keeps it in its own credentials file beside the login. No backend change; the user sees it in Settings → Personal access tokens and can revoke it there.
- Option (b): the Git proxy accepts the credential `bea cloud login` stores. That is a backend change to a transport that currently takes only tokens and passwords, and it hands Git a credential broader than ledger read/write.
- Precondition for (a): the credential `bea cloud login` stores may call `apikeys.create` (op class `admin`, action `USER_CREDENTIALS_CREATE`), and minting passes `ApiKeyService`'s paid-plan rule, which self-hosted accounts (Enterprise, no plan limits) meet. Verify both against the code and a running stack before choosing.
- The Git host can differ from the API address `bea` talks to (`GIT_PUBLIC_URL`, a custom domain). Each ledger's `httpUrl` carries it; an account with no ledger yet has none to read. If a deployment-level field is needed, it is an API change and takes REST, GraphQL and MCP together (root `AGENTS.md`, parity rule).

## Steps

1. Check the precondition for (a); choose (a) unless it fails.
2. Decide the token's expiry and what happens when it lapses (re-mint on the next `get` while the login is valid).
3. Decide the host source: a ledger's `httpUrl`, or a deployment field added on all three surfaces.
4. Write the decision into this task under `## Decision`, and in `cli/docs/USAGE.md` beside the new commands when t002 lands. If it needs backend work, add it with `/pm add-task w22/m12`.

## Decision

Recorded 2026-11-18. The same text, for users, is in `cli/docs/USAGE.md` under "Cloud: Git sign-in on a self-hosted server".

- **Credential: option (a), a personal access token `bea` mints for itself.** `bea cloud git setup` calls `POST /api-gateway/v1/api-keys` with the login and gets a token named `bea git on <hostname>` with `ledger.read` and `ledger.write`. It is kept in `git-credential.json` beside `credentials.json` (0600, in the 0700 configuration directory) and is listed under Settings → Personal access tokens. The login is never given to Git, and the Git proxy is unchanged.
- **Precondition, from the code:** the credential `bea cloud login` stores is a CLI *session* (`cli-auth-routes.ts`: "a 30-day CLI session credential"). `USER_CREDENTIALS_CREATE` admits the `session` and `oauth` methods at `admin` capability and refuses only an API key (`authorization-service.ts`), so the login may mint. `ApiKeyService.mint` then asks `isPremium`, which is true for any tier but Free, and a self-hosted stack reports Enterprise for every account (`get-user-tier.ts`). A running stack confirms both in t006.
- **Expiry: 90 days.** When the token has lapsed (or will within five minutes), the next `bea cloud git credential get` mints a new one while the login is valid, and revokes the one it replaces. With no valid login it answers nothing, prints one line on stderr, and Git prompts. When Git reports the token refused (`erase`), `bea` forgets it and the next `get` mints another.
- **Git address: a ledger's `httpUrl`**, taken from the first ledger the account can reach (`GET /api-gateway/v1/ledgers?limit=1`) and cut down to scheme, host and port. On bex the API and Git share a host, but `GIT_PUBLIC_URL` and a custom domain can separate them, so the address is read, not derived from `BEA_API_URL`. An account with no ledger is told to create one first. No deployment-level address field was added: every ledger on a stack has the same one, and a person with no ledger has nothing to clone.
- **Self-hosted or not: one new field.** `bea` speaks the v1 REST contract, and `deploymentInfo.selfHost` is GraphQL-only by design (browser sign-up ceremony). The existing public configuration read (`GET /api-gateway/v1/feature-flags`, GraphQL `featureFlags`, MCP `beancount://configuration/feature-flags`) already carries one deployment fact, so it gains `selfHost` on all three surfaces: [t012](./t012.md). A server that does not send the field is refused, the same as the managed service.
- **Not chosen, option (b):** the Git proxy accepting the login. It changes a transport that takes only tokens and passwords, and hands Git a credential that can do everything the account can.
