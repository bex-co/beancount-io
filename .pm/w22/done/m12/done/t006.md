## Objective

Prove the whole flow on a real self-hosted stack, from a profile with no Git or `bea` state, then delete the stack.

## Context

- Create the stack from the root Blueprint; it takes about half an hour. Delete every resource afterwards and confirm each answers 404.
- Isolate the client: an empty `BEA_CONFIG_DIR`, and `GIT_CONFIG_GLOBAL` pointing at an empty file, so no Keychain entry or old helper answers instead.

## Steps

1. Sign up, create a ledger, `bea cloud login`, `bea cloud git setup`.
2. `git clone`, commit, `git push`, `git pull`: no prompt at any step.
3. Check the token in Settings → Personal access tokens (if t001 chose one).
4. `bea cloud logout`; the next `git fetch` is refused.
5. Against the managed service, `bea cloud git setup` refuses and writes nothing.
6. Delete the stack.

## Result (2026-11-20)

Every step passed. The stack came from the root Blueprint at `main` `d61546262` (it contains `5c9a3da1d` and the 0.5.0 release commit `cb395229b`) and was live 27 minutes after it was created. The client was `bea` 0.5.0 installed from PyPI into a fresh virtual environment, on macOS with Apple Git 2.54.0, whose built-in configuration turns on the Keychain helper (`osxkeychain`) for every host. `BEA_CONFIG_DIR` was an empty directory, `GIT_CONFIG_GLOBAL` an empty file, and `GIT_TERMINAL_PROMPT=0` made any prompt fail instead of wait.

1. Sign-up made the first account (sign-up then reported closed), with the sample ledger. `bea cloud login` signed in through the browser. `bea cloud git setup` wrote exactly two values under `credential.https://<api address>.helper`, an empty reset and `!<absolute path to bea> cloud git credential`, and minted the token `bea git on <hostname>`. No token went into the Git config.
2. Two clones over HTTPS, a commit and `git push` from one, `git pull` into the other: no prompt at any step. The remote URL holds no token, and the Keychain stored nothing for the Git address, so the empty reset kept Apple Git's own helper out.
3. Settings → Personal access tokens lists `bea git on <hostname>` as Active, with `ledger.read` and `ledger.write`, for all ledgers, expiring in 90 days. The same token reads ledgers over REST (200) and is refused for listing or minting tokens (403).
4. `bea cloud logout`: Settings shows the token Revoked, `git-credential.json` keeps only the two addresses, and the next `git fetch` is refused (exit 128) after the helper's stderr line "Not signed in, so Git gets no password from bea. Run 'bea cloud login' and try again." After the next `bea cloud login`, `git fetch` and `git pull` worked again with a newly minted token and no second `setup`. `bea cloud git setup --undo` then left the global Git config empty, removed the state file and revoked that token.
5. Against the managed service, with a read-only token through `BEA_TOKEN`, `setup` exited 1 with "'bea cloud git setup' is for self-hosted servers, and https://api.v3.beancount.io is the managed service, where Git signs in with an SSH key. Nothing was changed." and the SSH-key hint. The global Git config stayed empty and the configuration directory stayed empty.
6. The Blueprint, four services, Postgres, Key Value and the Gitea disk were deleted; each answers 404, as do both public addresses. Nothing else in the workspace was touched.

Nothing to fix. Two things behaved as designed: the device page continues by itself once the whole code is entered, and `bea cloud login` refuses to run without a terminal (`BEA_TOKEN` is the unattended route).
