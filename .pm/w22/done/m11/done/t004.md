## Objective

Make the two tools people actually run against a deployment say which revision they observed, so every evaluation record carries it without anyone having to remember.

## Context

- `scripts/mcp-conformance.ts` prints per-check lines only. It only observes, so it is safe against production, and a check that needs something it lacks skips rather than fails; `unknown` must not fail it.
- The QA contract replay (`.agents/skills/qa-shared/scripts/qa-contract-replay.mjs`) already prints `server: <serverInfo.name> <serverInfo.version>`, which will carry the build metadata once t002 ships. Add an explicit `revision:` line beside it so the record does not depend on parsing the version string.
- The two documents can disagree (a stale manifest cache, a proxy in front); flag a disagreement between `/.well-known/mcp.json` `revision` and the `initialize` build metadata rather than choosing one silently.
- Output helpers are unit-tested: `backend-cluster/backend-v2/scripts/__tests__/` and `.agents/skills/qa-shared/scripts/*.test.mjs`.

## Steps

1. Print `revision: <value>` from the conformance script, read from the manifest and `initialize`, with a clear line when they disagree.
2. Print `revision: <value>` in the replay output.
3. Unit tests: a known revision is printed; `unknown` prints and does not fail; a disagreement is flagged; the replay line is present.
4. Run the backend script tests and `node --test .agents/skills/qa-shared/scripts/qa-login.test.mjs .agents/skills/qa-shared/scripts/qa-mcp.test.mjs .agents/skills/qa-shared/scripts/qa-contract-replay.test.mjs`.

## Notes

- **Conformance** prints `revision: …` right after its header and before the checks. It is information, not a check, so it never changes the exit code. `observeRevision` reads the public `/.well-known/mcp.json`, and the `initialize` answer's build suffix only when a credential is supplied (`initialize` needs one); `describeRevision` turns the two into the lines: they agree; they disagree (a `WARNING:` line saying a cache or a proxy in front may serve an older build); `unknown`; the handshake alone; or not reported (an older deployment or an unreachable document). It never throws.
- **The replay** prints `revision: <build> (from serverInfo.version)` on the line after `server:`, or `revision: unknown (…)` when the version names no build, via an exported `revisionLine`. It does not read the manifest: it already holds the handshake, and the conformance run is the one that can cross-check the two.
- Tests: 17 new in `scripts/__tests__/mcp-conformance.test.ts` (the eight outputs of `describeRevision`, and `observeRevision` against a fake deployment over real HTTP: manifest only without a credential, the `Authorization` header and the build suffix with one, SSE and plain JSON answers, a 404 / non-JSON / missing-field / non-string manifest, a 401 handshake, and nothing listening) and 2 in `qa-contract-replay.test.mjs` (the record carries the line beside `server:`, and `revisionLine`'s accepted and refused forms).
- Mutations that fail them, each compiling: a disagreement never flagged; no credential sent with `initialize`; `initialize` asked without a credential; the build suffix never read; `unknown` beside a named build raising no warning; a six-character build accepted; the replay line not printed; the plus sign kept in the build.
- Not run: either tool against production, which rides the next owner deploy; until then a deployed `revision` can only read `unknown` or `not reported`.
- Gate: backend `yarn format:check`, `yarn typecheck`, `yarn lint:deadcode`, `yarn test` (481 suites, 10735 tests); the qa-shared node tests (29); `python3 scripts/check-agent-guidance.py`, `python3 scripts/skills/ci-check.py`, and `python3 scripts/skills/test_ci_check.py` exit 0.
