## Objective

Remove every hard-coded `*.onbex.co` address from `bex.yaml` and `dashboard/.env.production`, so the same Blueprint works for any workspace.

## Context

- bex builds a service's public host from its name, and on a cross-workspace collision it becomes `<name>-<suffix>`; a second deployer of this Blueprint would therefore get different hosts than the ones now written in `SERVER_URL`, `DASHBOARD_URL`, `AUTH_COOKIE_DOMAIN`, `EXTRA_ALLOWED_ORIGINS` and `VITE_API_URL`.
- The dashboard already forwards `/api-gateway/*` to the API (`API_PROXY_URL`, w22/m8-era work), so the browser needs one origin. bex injects `RENDER_EXTERNAL_URL` into each web service for its own host.
- Decide first, in writing, between: (A) the API learns its public origin per request from the forwarded host the dashboard proxy already sets, with a host-only cookie; (B) a first-deploy prompt for one public URL, then a sync; (C) making the API a private service behind the dashboard. The OAuth issuer and `/.well-known/*` must still resolve on the public host. Pick the option that keeps the managed service unchanged.

## Steps

1. Write the decision and its trade-offs in `deploy/bex/README.md`.
2. Implement it behind an unset-by-default switch (host-only cookie needs a sentinel; blank `AUTH_COOKIE_DOMAIN` already means the `.beancount.io` default and must not change).
3. Make `VITE_API_URL` independent of the host, or prove the client factory is never used during server rendering before using a relative path.
4. Add tests for the derivation and for the unchanged default.

## Done

**Decision (also in `deploy/bex/README.md`):** option D, the API learns its public address at start from the dashboard (`scripts/resolve-public-url.js` against `/_internal/public-url`). Per-request derivation was rejected (the OAuth issuer is fixed at boot and a request header must not set it) and a post-deploy prompt was rejected (defeats one click).

**Shipped:** the resolver and its tests (13, two guarantees mutation-checked), the dashboard endpoint, a relative `VITE_API_URL`, Gitea deriving its own `ROOT_URL`/`DOMAIN`, and `fromService` references with URLs composed in the start commands. Gates: backend 440 suites / 9428 tests, dashboard full suite and build, `bex blueprints validate` valid.

**Found by deploying into a clean second workspace**, where the names were already taken so every hostname carried a suffix, and fixed here:

- bex builds a service's *internal* address from its slug, not its name (`beancount-dashboard-496p:3000`), so every literal internal address in `bex.yaml` failed there. They are now `fromService` references. This only ever worked on the first deployer, which is why the canary hid it.
- Gitea's schema in the shared Postgres had been created by hand on the canary. `migrate-deploy.js` now creates the schemas in `ENSURE_SCHEMAS` (validated lowercase identifiers).
- Also removed an unused export that knip flagged (`authCookieDomain`).

**Verified:** the dashboard serves its own suffixed address in that workspace; the canary, on the final manifest, passes the browser flow (one `SignUp`, no verification page, signed in, four ledgers) and a healthy deep `/healthz`.
