## Objective

Shrink the Blueprint's `sync:false` prompts from 15 to the few a newcomer actually has to decide, generating the rest.

## Context

- Previewing `bex.yaml` in a clean workspace lists 15 `sync:false` variables: `ADMIN_TOKEN`, `BACKEND_V2_ADMIN_TOKEN` (must equal `ADMIN_TOKEN`), `OAUTH_JWKS`, `FAVA_API_ADMIN_PASSWORD`, `BLOCKEDEN_ACCESS_KEY`, the two model providers and their model names, and six S3 values.
- bex accepts copying a sibling's generated value through `fromService.envVarKey` (checked with `bex blueprints validate` on 2026-11-07; the comment in `bex.yaml` saying it cannot is out of date). So one generated token can feed both services, and the Gitea admin password can be generated and shared.
- `OAUTH_JWKS` is a private signing key document, not a random string: decide whether the API can mint and persist its own on first boot for self-hosters, or whether it stays a prompt with a one-line generator command.
- Optional integrations (model providers, S3, price feed) must not block a first deploy; the app has to run with them blank and say so.

## Steps

1. Replace the duplicated token prompts with `generateValue` plus `fromService` copies; generate the Gitea admin password the same way.
2. Decide the signing-key approach and implement it.
3. Remove the optional integrations from the prompt list (defaults blank, documented as post-deploy settings).
4. Check a clean-workspace preview and re-deploy over the existing canary to prove a sync keeps the values.

## Files

- `bex.yaml`, `deploy/bex/README.md`, possibly `backend-cluster/backend-v2/src/features/oauth/`

## Acceptance criteria

- [x] A clean-workspace preview lists nothing: `syncFalseVars` is empty (it was 15), the Blueprint is valid, and the estimate is unchanged.
- [x] Both services see the same generated values: the API's `ADMIN_TOKEN` and the ledger's `BACKEND_V2_ADMIN_TOKEN`, and Gitea's and the API's `FAVA_API_ADMIN_PASSWORD`, hash identically on the canary after the sync that introduced them and the redeploys that followed. A second, identical sync was not run separately.
- [x] The README lists each skipped integration and what it enables, and says to add it in the dashboard after the first deploy.

## Out of scope

- Changing the managed service's behavior: every new switch is off unless set.

## Done

- **Generated and copied, not typed:** `ADMIN_TOKEN` is generated on the API and copied into the ledger (`fromService.envVarKey`); Gitea generates the admin password and the API copies it. bex accepts copying a generated value (checked with `bex blueprints validate`), so the comment claiming otherwise is gone.
- **Signing key derived, not asked for:** `scripts/derive-oauth-jwks.js` derives the OAuth ES256 key from `AUTH_SECRET` (HKDF, so it is stable across restarts and adds no secret to store), only when `OAUTH_JWKS_FROM_AUTH_SECRET=true` and `OAUTH_JWKS` is unset. Tests (11) check it with the backend's own production parser, sign and verify with it, and that it differs per secret; a mutation that ignores the secret fails two of them. On the canary, with the hand-set key deleted, the published JWKS carries the derived key id and no private part.
- **Optional integrations no longer declared:** model providers, asset storage and the model-proxy key are not prompted for; the backend treats each as optional (LLM "not configured" is a quiet state; storage settings default to blank). The two required S3 regions stay.
- **Found while checking OAuth:** the dashboard's same-origin proxy forwarded only `/api-gateway/*`, so the OAuth and MCP discovery documents (the issuer is the dashboard host) answered 404. It now forwards `/.well-known/*` as the docker deployment's Caddyfile does; the handlers' path rules are tested (13) and a mutation of each is caught.
- Verified on the canary after redeploy: discovery 200 on the dashboard host, deep health `healthy`, and the browser flow (one `SignUp`, no verification page, signed in, four ledgers).
- Not exercised in a clean workspace (see t001 and t004): the derivation on a deployment that never had a hand-set key beyond this canary, because the second clean deploy could not finish on the platform side.
