# In Persian, Merchants counts print Latin digits beside Persian-digit dates: "71 تراکنش" under a row dated "۷ سپتامبر ۲۰۱۷"

**Trivial to minor (fa) · mobile · 20–30m · A3.** Native mobile QA, 2026-11-10, repository HEAD `6183533d9`, development build `io.beancount.ios` 1.20261002.50 on iPhone 17e / iOS 27.0, light, app language Persian after the layout restart, signed in as the QA account on an authenticated ledger. Read-only pass. This is the native confirmation of the Merchants strings that `w21/1020`'s "Wider sweep" listed from source and marked "still to be confirmed natively"; no follow-up was filed for them.

## Repro (reproduced in two Persian sessions)

1. Switch the app to **فارسی** (Settings → Language → Restart now).
2. Drawer → **Merchants** (پذیرندگان).
3. The search field reads `جستجوی 37 پذیرنده…` with a Latin "37". Every row's second line reads `71 تراکنش`, `47 تراکنش`, `34 تراکنش`… with Latin digits, while the date at the row's other end reads `۷ سپتامبر ۲۰۱۷`, `۲ اکتبر ۲۰۲۶` in Persian digits. Opening a merchant shows the same count in its header.
4. Control, same session: **Accounts** reads `۱۰ خارج از جمع` and `۶ قیمت از ۸ سپتامبر ۲۰۱۷ به‌روز نشده` entirely in Persian digits (the `w21/885` and `w21/1020` fixes), as do the Transactions date headers and the amounts.

**Expected:** one digit system on a screen, following the rule `localizeDigits` states (a language renders its own digits): `۷۱ تراکنش`, `جستجوی ۳۷ پذیرنده…`.
**Actual:** Latin counts in the same row and field as Persian-digit dates.

Local evidence: `.tmp/qa-20261110/fa2/merchants.png` (list, search field and row counts), `accounts.png` (the control).

## Root cause

`useTranslations().t` is a bare `i18n.t(key, params)` (`w21/1020`'s sweep), which prints `count` in Latin digits, and only call sites that wrap the sentence in `localizeDigits(…, locale)` get the language's digits. The Merchants sites do not:

- `mobile/src/screens/merchants-screen/merchant-row-text.ts:40-42` — `t("merchantsTransactionCount", { count })` for every row.
- `mobile/src/screens/merchants-screen/merchants-screen.tsx:280-282` — `t("merchantsSearchPlaceholder", { count })`.
- `mobile/src/screens/merchant-detail-screen/merchant-detail-screen.tsx:612` — the same row-count key in the detail header (not seen in Persian in this run; same call).

Working control: `mobile/src/common/valuation.ts:446-456` wraps `t("notInTotalCount", …)` in `localizeDigits(…, locale)`.

## Fix

Target: in Persian, the three Merchants strings read in Persian digits; the other twelve languages are unchanged (`localizeDigits` is a no-op where digits are Latin). `w21/1020` already recommends making this once, in the place the strings are filled (a count formatter in `useTranslations`), instead of per call site, and lists the other `{{count}}` strings it found from source (`postingNumber`, the budget and income/expense chart summaries, the error and "N items" counts); decide that here and keep one unit case per string family beside `valuation.test.ts`'s "counts in the language's digits". Mobile only; no API surface.

## Blast radius

Not re-listed: the strings in `w21/1020`'s sweep that were not on screen in this run. Observed in the same session, same class, not separately traced: the Commit detail stats read `+1 −1` in Latin digits under a Persian-digit date (`commit-detail-fa.png`); whether those are meant to stay Latin like diff output is the owner's call.

## Dedupe

Searched `.pm/**` (including `done/`) for `merchantsSearchPlaceholder`, `merchantsTransactionCount`, `localizeDigits`, "Persian digit" and merchants. `w21/884`, `885` and `1020` fixed the chart and budget labels, the stale-price sentence and the not-in-total/at-cost counts, and `1020`'s sweep named these Merchants strings as unconfirmed; `w21/248` and `898` concern plural rules and an empty-state placeholder. So this is a residual of `w21/885`/`1020`, not a regression.
