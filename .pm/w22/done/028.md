# Opening a file in the editor shows a blank white body, with no skeleton, until the embedded editor has booted

**Minor · mobile · 30–40m · A2.** Native mobile QA, 2026-11-10, repository HEAD `59f13b939`, development build `io.beancount.ios` 1.20261002.50 on iPhone 17e / iOS 27.0, light, English, signed in as the QA account on its synthetic `example` ledger. Read-only pass: both files were opened and left with the Back button, nothing was typed and `Save` was never enabled. This turns the earlier unreproduced sighting (a blank body "for more than 5 s" on a 6.5K-line `main.bean`) into a reproduced one with its cause.

## Repro (reproduced on two files, three opens of the larger one)

1. Terminate and relaunch the app at `large`, dismiss the dev toast, open the **Files** tab.
2. Tap `README.md`, and capture screenshots back to back (`xcrun simctl io <udid> screenshot`, about 2 per second), reading each file's size: a blank body is about 92 KB, a loaded one about 325–377 KB.
3. Go back, tap `main.bean` (6.5K lines) and capture again. Repeat the larger file twice.

**Expected:** from the moment the screen is pushed until the document is drawn, the body shows the skeleton the loading branch already has (`LoadingTile` bars), as `mobile/AGENTS.md` asks of every content area that waits ("Loading states — skeleton preloaders, not spinners").
**Actual:** the header shows the file name and a greyed `Save`, and the body is plain white: no tiles, no text. `README.md` (small): the first frame after the cold open is blank (92,318 B) and the next is loaded (377,082 B); a third, warm open is loaded in its first frame. `main.bean`: the first frame after every open, cold or warm, is blank (91,520 B, then 92,149 B) and the next is loaded (324,956 B, then 325,599 B). The capture loop shows the blank frame is replaced within about 2 s; it was not timed more finely here, because this machine adds about 5 s to each automation tap and shares its CPU. The earlier run saw more than 5 s on the large file.

Evidence is local only (`.tmp/qa-20261110/w22d/`): `21-readme-t1.png` (blank, header only) and `21-readme-t2.png`…, `23-main-t1.png`…`23-main-t14.png`, `24-main-warm-t1.png`…, `25-readme-warm-t1.png`.

## Root cause

The skeleton is shown only while `editorState === "loading"` (`mobile/src/screens/ledger-file-editor-screen/index.tsx:1193-1199`). `selectLedgerFileEditorState` returns `content` as soon as an editor session is `initialized` (`select-editor-state.ts`, the first branch), and with the persisted Apollo cache the session is seeded at once. The `content` branch (`:1241-1262`) mounts `CodeEditor`, which is an Expo DOM component (`"use dom"`, `src/components/code-editor/code-editor.tsx:1`), a WKWebView that must boot and run CodeMirror before it draws anything, inside a `FadeInView`. The editor says it is ready through `onReady`, whose handler `handleEditorReady` (`:676-688`) only then calls `setDocumentSpec`, so the document is not even handed over until then. Between `content` and that moment nothing is drawn: the skeleton is gone and the editor is not up. A larger document takes longer to boot and parse, which matches the large file being blank every time and the small one only when cold. `FadeInView`'s own comment describes the intended pattern, a crossfade "for the loaded branch of a skeleton swap", and here the swap happens before the loaded content exists.

## Fix

Keep the skeleton on screen until the editor has signalled ready, then crossfade it out. Concretely: add a `ready` input to `selectLedgerFileEditorState` (or an `editorReady` state set in `handleEditorReady`), keep `CodeEditor` mounted (it has to mount to boot) but under the skeleton while it is not ready, and let `FadeInView` hand off when `documentSpec` is set. No change to the error, unavailable or save paths. Add cases to the selector's tests (`initialized` but not ready stays on the skeleton; ready shows the editor; an error or an unavailable file still win), then verify natively by repeating the frame capture above on the 6.5K-line file: no blank frame between the header and the loaded body. Mobile only; no API surface.

## Blast radius

The one file editor, for every file the user opens, and the cold-link route that opens it at a source line (`jumpToLine`). The read-only notice and the `Save` state do not change. The Files list, which has its own skeleton, is not affected.

## Adjacent states

A genuinely empty file (a real document with `""`, which must still end on the editor, not the skeleton), a file that fails to load (the error branch) and a missing one (`w3/done/179`'s unavailable branch).

## Dedupe

Searched `.pm/**` (including `done/`) for `ledger-file-editor`, "file editor", `CodeEditor`, `onReady`, blank, skeleton. `w3/done/179` shows a missing-file state when the query returns null, a different branch with a different cause; `w3/done/214` and `w4/done/040` concern the keyboard. Nothing covers the blank interval before the editor is ready.

## Unverified

The exact blank duration (not timed here), the same screen in dark mode, the effect of a cleared Apollo cache (this run kept the persisted cache), a slow network, Android (the editor is the same DOM component).

**Resolved 2026-11-11** — opening a file now shows the skeleton over the editor from the moment the screen is pushed until the embedded editor has booted and says so through `onReady`, then fades it out; the editor stays mounted under it (mounting is what boots it). A new `coversEditorWithSkeleton(state, editorReady)` decides: `content` and not ready; `loading` keeps its own skeleton, and an error or an unavailable file never gets one; the save, error and unavailable paths are unchanged. Shipped in `e4222e20e` (`mobile`). Tests: selector cases (covered until ready, uncovered once ready, a genuinely empty file still ends on the editor, error and unavailable never covered) and source pins on the screen in `editor-boot-skeleton.test.ts` (the editor stays mounted in `content`, the cover sits after it and fades out, `onReady` lifts it first thing; two fail with the screen change reverted). Verified natively on iPhone 17e / iOS 27.0, light, from a cold launch of the fixed bundle, with the note's frame capture (about 2 frames per second): `README.md` and the 6.5K-line `main.bean` both go from the Files list to the skeleton tiles (two to three frames, about 95 KB each) to the loaded document (about 325–372 KB) with no blank frame (about 92 KB) in between, and the editor is fully drawn afterwards; nothing was typed or saved. One correction to the note's cause: the first `onReady` does nothing (`ready()` returns null the first time), and the document reaches the editor as its initial prop, so `onReady` is the signal that the page is drawn, not what hands the document over. Not checked: the exact length of the interval (not timed), dark mode, a cleared Apollo cache, a slow network, Android.
