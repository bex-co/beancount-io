# In Persian the Budget screen's history toggle reads "2 مورد" with a Latin 2, under Persian-digit amounts

**Severity:** trivial to minor (fa; consistency). **Estimate:** 15 minutes. Owner: mobile. A3: the native confirmation of one string from `w21/1020`'s "Wider sweep" (the "N items" count), the same way `w22/012` confirmed the Merchants strings; the rest of that sweep is still unconfirmed and untracked.

Environment: `main` at `48c785130` (`origin/main` identical, nothing under `mobile/` ahead), dev build `io.beancount.ios` on iPhone 17e / iOS 27.0, light, large text, app language Persian after the layout restart, QA account on the hosted server, its synthetic `example` ledger. Read-only: nothing was applied, and the history rows were not expanded.

## Repro

1. Settings → Language → **فارسی** → Restart now.
2. Home → the Budget card's **دیدن همه** (see all) opens the Budget screen.
3. Under each budget card's chart, the collapsed history row reads **`2 مورد`**: a Latin `2`. Everything else on the card is in Persian digits: the amounts (`$۱۲۲٫۰۰`, `$۰٫۰۰`), the axis ticks (`$۱۲۰`, `$۱۰۰`) and the month labels.

**Expected:** `۲ مورد`, the one digit system per screen that `localizeDigits` states as the rule (a language renders its own digits).
**Actual:** the count is the only Latin number on the card. English and the other Latin-digit languages are unaffected.

## Evidence

Local, gitignored capture `.tmp/qa-20261112/loop68/07-fa-budget.png` (the first card, the toggle at its foot; its second card has the same row).

## Root cause

- `mobile/src/screens/budget-screen/components/budget-history-rows.tsx:180` (the accessibility label) and `:184` (the visible text) call `t("budgetHistoryCount", { count: rows.length })`.
- `useTranslations().t` (`common/hooks/use-translations.ts`) is a bare `i18n.t(key, params)`, so a bare `{{count}}` prints in Latin digits unless the call site wraps the sentence in `localizeDigits(…, locale)`, as `valuation.ts` does and, since `w22/012`, the Merchants strings do. `fa.ts:704-707` holds the string; the file already has `locale` from the same hook (`:123`).

## Fix

Wrap both calls in `localizeDigits(t("budgetHistoryCount", { count: rows.length }), locale)` (a no-op in the Latin-digit languages), and add a Persian case plus a Latin-language control; revert the fix and watch the Persian case fail. This follows `w22/012`'s recorded decision: each family of app-written counts opts in at its call site, one test per family, and the count is not moved into `t()` (its output also carries payee names, file names and amounts whose digits must stay as written).
