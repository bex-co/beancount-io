# The shared `Button` has no disabled look, so Transactions Filters' Apply reads as available while it does nothing

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: a primary action that is dead but looks live gives a sighted user no cue that something is wrong, and the app already knows this (Profile patches it by hand).

Environment: `main` at `729d03708` (`origin/main` was 10 commits ahead, none under `mobile/`), dev build `io.beancount.ios` on iPhone 17e / iOS 27.0, light, English, default text size, QA account on the hosted server, its synthetic `example` ledger. Read-only: nothing was applied.

## Repro

1. Transactions tab → the filter icon at the right of the search field → Date range **Custom** (START 2026-11-01 and END 2026-11-11 are seeded).
2. Tap the START row → move the month wheel to December → **Confirm**. START is now 2026-12-01, after END.
3. The red line "End date must be on or after the start date." appears. The validation itself is right.
4. Look at **Apply**, then tap it.
5. **Cancel**, reopen the sheet and repeat 1–4: same result both times.

## Expected / Actual

Expected: Apply reads as unavailable, the way the app's other unavailable actions do (opacity 0.4: Profile Save, Edit Transaction's Save header action, Browse ledgers' star button while its request is pending; 0.35 on the file browser's disabled row action).

Actual: Apply is pixel-identical in the valid Custom range and in the reversed one: fill `#2f7d03`, label `#fffff7` (5.15:1), probed in both screenshots. Tapping it does nothing: the sheet stays open and no filter is applied. There is no press feedback either, because `Button` sets `pointerEvents="none"` when disabled. Only the inline error line says why.

## Evidence

Local, gitignored captures under `.tmp/qa-20261111/loop1/`: `03-custom.png` (valid range), `06-reversed.png` and `11-reversed-again.png` (reversed), `07-after-apply-tap.png` (after tapping Apply). The pixel values above come from those four.

## Root cause

- `mobile/src/components/button/index.tsx:43-75` defines `buttonPrimary`, `buttonOutline` and their pressed styles but no disabled style. `:130-141` hands `disabled` only to `PressableScale`, to `accessibilityState.disabled` and to `pointerEvents`, so the pixels never change.
- `mobile/src/screens/transaction-filters-screen/transaction-filters-screen.tsx:434-440` passes `disabled={!isRangeValid}` and relies on the Button to show it.
- The one caller that noticed patched it by hand: `mobile/src/screens/profile/profile-screen.tsx:147-149` says "The shared Button has no disabled look; here it matters" and `:204` wraps the Button in a `View` with `opacity: 0.4`.

## Fix

Give `Button` the look itself: when `disabled` and not `loading`, apply `opacity: 0.4` (the app's convention, see Expected / Actual); keep a `loading` button at full strength with its spinner (the busy cue, and what Profile's `!canSave && !isSubmitting` already does). Then delete Profile's `saveDisabled` wrapper so the two do not compound to 0.16. Test: render `Button` with the vm harness `live-font-scale-remeasure.test.ts` already uses for it and assert the disabled style is present for `disabled`, absent for enabled and for `loading`; revert the fix and watch it fail. Keep the existing `accessibilityState.disabled` (w3/212, `109d95ae`).

## Blast radius

13 files import `Button`. Callers that pass `disabled`: Filters Apply (the persistent state, reproduced here); Profile Save (hand-dimmed); Server settings Test connection and Save (each is `disabled` while the other runs, so the idle one stays full colour next to the spinner); Welcome Sign in, Sign up and Try example (`disabled={busy}` while one sign-in is pending). The last two are transient and were read from source, not observed.

## Adjacent states

VoiceOver already hears "dimmed" (`accessibilityState.disabled`), so this is the sighted cue only. Loading: spinner unchanged. Dark theme: opacity applies equally, not captured.

## Dedupe

Searched `.pm/**` including `done/` for the reversed-range message, `isDateRangeValid`, `saveDisabled`, "no disabled look" and Apply with disabled. w3/212 (shipped `109d95ae`) saw the same reversed-range Apply and recorded it as `Disabled` in the accessibility tree, but fixed only the missing button role and said the range validation "is not part of this finding". w21/026 (duplicate key in the message) and w21/307 (a 9999 end date) are about validation, not the look of Apply. No item covers the visual disabled state. `button/index.tsx` history ends at `a6a95ef7b` (w22/029, keys the label only).

## Unverified

Dark theme; the transient disabled states on Server settings and Welcome (not reachable without signing out or typing on this simulator); Android; Profile Save's double dimming after the fix is derived from reading the code.

---

**Resolved 2026-11-12** — the shared `Button` now dims itself when it is `disabled` and not `loading` (opacity 0.4, the strength the app's other unavailable controls use), so Transactions Filters' Apply reads as unavailable while the Custom range is reversed, and the transient disabled states on Server settings and Welcome follow. A loading button keeps full strength and its spinner. Profile's hand-made `saveDisabled` wrapper is gone so the two cannot compound to 0.16; its Save dims exactly as before because the Button now owns the look. Tests: a "Button disabled look" block in `src/__tests__/live-font-scale-remeasure.test.ts` (dimmed for primary and outline, full strength when enabled and when loading, `accessibilityState` unchanged); with the fix reverted the dimming case fails. Verified natively on iPhone 17e / iOS 27.0: in a reversed Custom range Apply draws as the pale disabled green, in the valid range at full strength. Not rechecked on a simulator: Profile Save after the wrapper's removal (the same 0.4 by construction), the transient Server settings and Welcome states, the dark theme and Android. Shipped in the commit that moves this note (`mobile`).
