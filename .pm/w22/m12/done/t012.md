## Objective

Give `bea` a way to ask a server whether it is self-hosted, so `bea cloud git setup` can refuse on the managed service. Added by t001's decision.

## Context

- `deploymentInfo.selfHost` exists only on GraphQL, as part of the browser sign-up ceremony; `bea` speaks the v1 REST contract.
- The public configuration read (`readFeatureFlags`) is already shared by `GET /api-gateway/v1/feature-flags`, GraphQL `featureFlags` and the MCP resource `beancount://configuration/feature-flags`, and already carries one deployment fact (`emailDelivery`).

## Steps

1. Add `selfHost` to the shared read and to the REST response schema.
2. Regenerate the v1 OpenAPI document, re-pin it in `cli/`, and regenerate the CLI client.
3. Test that the three surfaces agree, on and off.

## Files

- `backend-cluster/backend-v2/src/features/healthz/`
- `backend-cluster/backend-v2/docs/openapi/v1.json`, `backend-cluster/backend-v2/docs/mcp.md`
- `cli/openapi/v1.json`, `cli/src/cli/api/rest_client/`

## Acceptance criteria

- [x] REST, GraphQL and MCP return the same `selfHost` value, true on a self-hosted stack and false otherwise.
- [x] The backend parity suite and `make check-all` in `cli/` pass.

## Out of scope

- A deployment-level Git address; t001 reads it from a ledger.

## Done

**Shipped 2026-11-18.** `readFeatureFlags` returns `selfHost` (the deployment's `SELF_HOST` setting), so `GET /api-gateway/v1/feature-flags`, GraphQL `featureFlags` and the MCP resource `beancount://configuration/feature-flags` all carry it; the REST schema, `docs/openapi/v1.json`, `docs/mcp.md`, the CLI's pinned spec and its generated client were updated in the same change. `configuration-parity.test.ts` reads all three surfaces with the setting on and off.
