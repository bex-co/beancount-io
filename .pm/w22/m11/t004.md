## Objective

Make the two tools people actually run against a deployment say which revision they observed, so every evaluation record carries it without anyone having to remember.

## Context

- `scripts/mcp-conformance.ts` prints per-check lines only. It only observes, so it is safe against production, and a check that needs something it lacks skips rather than fails; `unknown` must not fail it.
- The QA contract replay (`.agents/skills/qa-shared/scripts/qa-contract-replay.mjs`) already prints `server: <serverInfo.name> <serverInfo.version>`, which will carry the build metadata once t002 ships. Add an explicit `revision:` line beside it so the record does not depend on parsing the version string.
- The two documents can disagree (a stale manifest cache, a proxy in front); flag a disagreement between `/.well-known/mcp.json` `revision` and the `initialize` build metadata rather than choosing one silently.
- Output helpers are unit-tested: `backend-cluster/backend-v2/scripts/__tests__/` and `.agents/skills/qa-shared/scripts/*.test.mjs`.

## Steps

1. Print `revision: <value>` from the conformance script, read from the manifest and `initialize`, with a clear line when they disagree.
2. Print `revision: <value>` in the replay output.
3. Unit tests: a known revision is printed; `unknown` prints and does not fail; a disagreement is flagged; the replay line is present.
4. Run the backend script tests and `node --test .agents/skills/qa-shared/scripts/qa-login.test.mjs .agents/skills/qa-shared/scripts/qa-mcp.test.mjs .agents/skills/qa-shared/scripts/qa-contract-replay.test.mjs`.

## Files

- `backend-cluster/backend-v2/scripts/mcp-conformance.ts` and its tests
- `.agents/skills/qa-shared/scripts/qa-contract-replay.mjs` and its test

## Acceptance criteria

- [ ] Both tools print the observed revision.
- [ ] `unknown` does not fail the conformance run.
- [ ] A disagreement between the two sources is flagged in the output.

## Out of scope

- Running either tool against production (that rides the next owner deploy).
