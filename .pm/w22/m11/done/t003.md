## Objective

Make it one command to build a local or self-hosted image that knows its commit, and state plainly that on bex the runtime variable is the path, so nobody ships an image that reports `unknown` without knowing why.

## Context

- `bex.yaml` records that Docker builds on bex get no build arguments, so the primary source is a runtime variable (`RENDER_GIT_COMMIT` where the platform sets it, otherwise `BEANCOUNT_REVISION` set on the service). A build argument only serves `docker compose build`.
- `backend-cluster/backend-v2/Dockerfile` has no `ARG`s today. Add `ARG REVISION=unknown` and `ENV BEANCOUNT_REVISION=$REVISION`; t001's parser treats the literal `unknown` as unset, so a platform variable is not shadowed.
- `deploy/docker/docker-compose.yml` and `deploy/docker-mac/docker-compose.yml` build the backend image; pass `REVISION: ${BEANCOUNT_REVISION:-unknown}` under `build.args`.
- The ledger service is out of scope.
- `scripts/check-bex-blueprint.py` keeps the Blueprint hostname- and workspace-neutral: any `bex.yaml` comment must not add a hostname, an internal address, or an input.

## Steps

1. Edit the Dockerfile and both compose files.
2. Add one sentence to each deployment README: `BEANCOUNT_REVISION=$(git rev-parse HEAD) docker compose build`.
3. In `deploy/bex/README.md` and as a comment in `bex.yaml`, state that bex builds take no build arguments and name the two runtime variables.
4. Run `python3 scripts/check-bex-blueprint.py` and `python3 -m unittest scripts/test_check_bex_blueprint.py` (or its documented runner), and validate each compose file with `docker compose config` where Docker is available.

## Notes

- **Scope grew by two targets.** Four deployment targets build the backend image, not the two this task named: `deploy/docker`, `deploy/docker-single-psql`, `deploy/docker-mac`, and `deploy/dev-sandbox`. All four now pass `REVISION: ${BEANCOUNT_REVISION:-unknown}` as a build argument, document it in their `.env.example` (as a commented placeholder, like `BEANCOUNT_IMAGE_TAG`) and in their README, and leaving two of them out would have made them quietly produce images that report `unknown`. No compose file uses `env_file`, so the variable in `.env` is read only for build-argument interpolation and is never passed into the container, where an empty value would have overridden the baked one.
- The backend `Dockerfile` has `ARG REVISION=unknown` and `ENV BEANCOUNT_REVISION=$REVISION`, declared last so a new commit invalidates no earlier layer. `parseRevision` treats the literal `unknown` as unset, so a platform's `RENDER_GIT_COMMIT` is not shadowed.
- `deploy/bex/README.md` gained "Which commit is running": a bex build takes no build arguments, so the commit has to arrive at runtime, `RENDER_GIT_COMMIT` where the platform sets it and `BEANCOUNT_REVISION` otherwise. It says plainly that this repository cannot show that bex sets `RENDER_GIT_COMMIT`, and tells the operator to set `BEANCOUNT_REVISION` on `beancount-api` if a fresh deploy reports `unknown`. `bex.yaml` has a matching comment on that service.
- **Verified:** the four compose files parse and each carries `build.args.REVISION: ${BEANCOUNT_REVISION:-unknown}` (checked with the repository's `yaml` package, resolving the shared anchor); the `ARG`/`ENV` lines were lifted verbatim out of the real Dockerfile onto `alpine:3` and built four ways: no build argument gives `unknown`, `--build-arg REVISION=2144cdbb2e6f` bakes it, `-e BEANCOUNT_REVISION=…` overrides the baked value, and a baked `unknown` reaches the process beside a platform `RENDER_GIT_COMMIT`. `python3 scripts/check-bex-blueprint.py` and `python3 -m unittest scripts.test_check_bex_blueprint` exit 0.
- **Not run here, so not claimed:** `docker compose config --quiet` (this machine's Docker has no `compose` plugin; the `${VAR:-default}` form is already used throughout these files) and a full backend image build (about 4.5 GB of dependencies). The end-to-end "compose build bakes it" is therefore shown by its two halves, not in one run.
