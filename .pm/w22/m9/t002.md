## Objective

Shrink the Blueprint's `sync:false` prompts from 15 to the few a newcomer actually has to decide, generating the rest.

## Context

- Previewing `bex.yaml` in a clean workspace lists 15 `sync:false` variables: `ADMIN_TOKEN`, `BACKEND_V2_ADMIN_TOKEN` (must equal `ADMIN_TOKEN`), `OAUTH_JWKS`, `FAVA_API_ADMIN_PASSWORD`, `BLOCKEDEN_ACCESS_KEY`, the two model providers and their model names, and six S3 values.
- bex accepts copying a sibling's generated value through `fromService.envVarKey` (checked with `bex blueprints validate` on 2026-11-07; the comment in `bex.yaml` saying it cannot is out of date). So one generated token can feed both services, and the Gitea admin password can be generated and shared.
- `OAUTH_JWKS` is a private signing key document, not a random string: decide whether the API can mint and persist its own on first boot for self-hosters, or whether it stays a prompt with a one-line generator command.
- Optional integrations (model providers, S3, price feed) must not block a first deploy; the app has to run with them blank and say so.

## Steps

1. Replace the duplicated token prompts with `generateValue` plus `fromService` copies; generate the Gitea admin password the same way.
2. Decide the signing-key approach and implement it.
3. Remove the optional integrations from the prompt list (defaults blank, documented as post-deploy settings).
4. Check a clean-workspace preview and re-deploy over the existing canary to prove a sync keeps the values.

## Files

- `bex.yaml`, `deploy/bex/README.md`, possibly `backend-cluster/backend-v2/src/features/oauth/`

## Acceptance criteria

- [ ] A clean-workspace preview lists no more than the signing key (or none) and no optional integration as a required input.
- [ ] Both services see the same generated admin token after deploy and after a second sync.
- [ ] The README says what each skipped integration disables.

## Out of scope

- Changing the managed service's behavior: every new switch is off unless set.
