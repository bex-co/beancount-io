## Objective

Remove every hard-coded `*.onbex.co` address from `bex.yaml` and `dashboard/.env.production`, so the same Blueprint works for any workspace.

## Context

- bex builds a service's public host from its name, and on a cross-workspace collision it becomes `<name>-<suffix>`; a second deployer of this Blueprint would therefore get different hosts than the ones now written in `SERVER_URL`, `DASHBOARD_URL`, `AUTH_COOKIE_DOMAIN`, `EXTRA_ALLOWED_ORIGINS` and `VITE_API_URL`.
- The dashboard already forwards `/api-gateway/*` to the API (`API_PROXY_URL`, w22/m8-era work), so the browser needs one origin. bex injects `RENDER_EXTERNAL_URL` into each web service for its own host.
- Decide first, in writing, between: (A) the API learns its public origin per request from the forwarded host the dashboard proxy already sets, with a host-only cookie; (B) a first-deploy prompt for one public URL, then a sync; (C) making the API a private service behind the dashboard. The OAuth issuer and `/.well-known/*` must still resolve on the public host. Pick the option that keeps the managed service unchanged.

## Steps

1. Write the decision and its trade-offs in `deploy/bex/README.md`.
2. Implement it behind an unset-by-default switch (host-only cookie needs a sentinel; blank `AUTH_COOKIE_DOMAIN` already means the `.beancount.io` default and must not change).
3. Make `VITE_API_URL` independent of the host, or prove the client factory is never used during server rendering before using a relative path.
4. Add tests for the derivation and for the unchanged default.

## Files

- `bex.yaml`, `dashboard/.env.production`, `dashboard/src/config/`, `backend-cluster/backend-v2/src/config/`, `src/shared/cookie-utils.ts`, `deploy/bex/README.md`

- [ ] `bex.yaml` and `dashboard/.env.production` contain no `onbex.co` host.

## Out of scope
