# A leading UTF-8 BOM hides line 1 from the backend-v2 text scanners: `appendLedgerText` puts a new entry inside a first-line `pushtag` scope (the entry is stored with a tag nobody wrote) and out of date order, and `renameAccount` and the long-number check misread a first-line comment, on MCP, REST and GraphQL

**Minor · backend-v2 (`src/features/ledger/utils/`) · 30–45m · A1.** The hosted engine loads a file that starts with a byte-order mark as if the mark were not there. The ledger service decodes with `TextDecoder`, which drops it, and its own commit path strips it before editing and writes it back (w21/368, `backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts:170-176`). backend-v2 decodes file bytes with `Buffer.toString("utf-8")` (`src/shared/file-content.ts:18`, through `ledger-repo-service.ts:331`). That keeps U+FEFF as the first character of line 1. Every line-anchored scanner then reads line 1 as something other than what the engine reads. The w31/015 and w31/099 fixes do not hold on that line.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). Also reproduced on local HEAD `5096eca03`, which already carries the w31/099 fix. The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), the fixture files were deleted, and the check showed 0 errors.

## Repro (live)

1. Fixtures (QA commits `72613b5f` and `3bb5b085`). `createLedgerFiles` made two files that are identical except for the first three bytes. `qa-bom.bean` starts with `EF BB BF`; `qa-control.bean` does not. Both are included from `main.bean`:

   ```beancount
   pushtag #qa-trip
   2026-09-02 * "qa payee" "scoped A"
     Expenses:Food:Coffee   3.00 USD
     Assets:Cash

   2026-09-05 * "qa payee" "scoped B"
     Expenses:Food:Coffee   4.00 USD
     Assets:Cash
   poptag #qa-trip
   ```

   `checkLedger` is clean. BQL `SELECT date, narration, tags` shows A and B tagged `qa-trip` in **both** files, so the engine applies the first-line `pushtag` despite the BOM. `readLedgerFiles` returns `qa-bom.bean` with first code unit `0xFEFF`.
2. `appendLedgerText {path: "qa-control.bean", dry_run: true, text: "2026-09-03 * \"qa payee\" \"appended\"\n  Expenses:Food:Coffee 1.00 USD\n  Assets:Cash\n"}` gives the control result. The diff wraps the entry in `poptag #qa-trip` … `pushtag #qa-trip` (the w31/015 fix).
3. The same call with `path: "qa-bom.bean"` gives a diff that inserts the entry bare between A and B, inside the scope. The result is `valid: true` and "No new bean-check errors". REST `POST /api-gateway/v1/ledgers/{owner}/{name}/directives/text` with `dryRun: true` and GraphQL `appendLedgerText(…, dryRun: true)` return the same diff.
4. Commit both appends (`6b57aa67` and `f3d32cae`), then compare. BQL and `listLedgerEntries {filter: "#qa-trip"}` show the BOM file's appended entry (hash `975ffd11…`) stored **with** `tags: ["qa-trip"]`. The control file's appended entry has no tag. The caller's text had none.
5. Date order. In a BOM file whose line 1 is `2026-09-10 * …`, followed by a `2026-09-20` entry, a `dry_run` append of a `2026-09-08` entry lands after the 09-10 entry. `appendedUnsorted` is `[]`, although the tool promises "inserts it in date order".

## The same cause in the other scanners (HEAD, run under tsx)

Each row compares the same text without and with a leading U+FEFF:

| Scanner | Without BOM | With BOM |
| --- | --- | --- |
| `renameAccountInText` on `# Assets:Cash is the petty cash box` + an `open` | renames only the `open` | also rewrites the `#` comment (the w31/099 symptom) |
| `textAmountLiterals` on `# ref 123456789012345678901234567890 USD` | `[]` | flags the number, so `updateLedgerFiles` refuses a valid file |
| `extractSingleBudgetAccount` after `# a "q` | `Expenses:Nope` | `undefined`: the budget check loses the budget |
| `scanIncludeLines` on `# a "q` then `include "a.bean"` | finds the include | misses it, so deletes and renames do not see the includer |

`scanIncludeLines` on a bare first-line `include` still works, but only by accident: JavaScript `\s` matches U+FEFF.

## Cause

- `directive-text.ts`:
  - `readStackStatement` (`:88`) matches `/^(pushtag|poptag|pushmeta|popmeta)\b/`.
  - `DATE_LINE` (`:288`) and the undated-keyword test in `directiveHead` (`:299`) are anchored at `^`.
  - With the BOM in front, `openPushes` (`:651`) never sees the first-line push. `insertionPoint` (`:554`) never sees the first-line entry.
- `isSkippedLine` (`skipped-line.ts:10`, `/^[*#:!&?%]/`) is false for `﻿#…`. All of its callers inherit that:
  - `account-rename.ts:55`
  - `engine-decimal.ts:302`
  - `budget-account-check.ts:31`
  - `include-target.ts:52`
  - `directive-text.ts:536`

## Fix

Read a file's text the way the engine reads it. Before scanning, drop a leading U+FEFF from the text that `getFilesContent` hands these scanners. Write it back unchanged on every rewrite, as `commit-ledger-files.ts` already does for the ledger service's own edits (w21/368). The alternative is to make each line-1 test BOM-aware.

The file must keep its bytes either way: the BOM stays, and no other byte changes. These workflows serve MCP, REST and GraphQL, so all three change together, with no response shape change:

- `appendLedgerText` (MCP) / `POST …/directives/text` (REST) / `appendLedgerText` (GraphQL)
- `renameAccount` / `POST …/rename-account` / the GraphQL rename mutation
- `updateLedgerFiles` and `createLedgerFiles` / `PUT …/files/{path}` / the GraphQL file writes, for the long-number check
- `deleteLedgerFiles` and `renameLedgerFile`, for the include scan
- the budget check in `appendLedgerText` and `updateEntrySource`
