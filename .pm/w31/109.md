# `appendLedgerText` reads only `YYYY-MM-DD` dates: a new entry lands above an existing `2026/08/25` or `2026-8-26` entry it should follow, and an unpadded date is called "not a Beancount directive" with no hint, on MCP, REST and GraphQL (gap in w31/106)

**Minor · backend-v2 (`src/features/ledger/utils/directive-text.ts`) · 20–30m · A1.** Stock Beancount's lexer reads `2026/08/25`, `2026-8-26` and `2026/9/1` as dates. The hosted engine loads them, and since w31/106 and w31/107 the ledger service slices and checks them too. `updateLedgerFiles` writes them, and a ledger converted from ledger-cli is full of them. The append tool's line classifier still recognizes only `^\d{4}-\d{2}-\d{2}` (`DATE_LINE`, `directive-text.ts:289`). That shows up twice:

1. **Order.** `insertDirectives` finds the file's entries with `directiveHead` (`:477`, `:572`), so an existing slash-dated or unpadded entry is not an entry to it. The tool promises to insert "in date order rather than at the end" (REST description). Instead, a new entry goes right after the last dash-dated entry on or before its date, which is above any such neighbour dated earlier. The stored file is left out of date order, and `appendedUnsorted` stays `false`. Nothing is split: the neighbour's header stops `endOfBlock`.
2. **Refusal text.** w23/240 decided that the tool refuses a `YYYY/MM/DD` date, and gave that refusal a hint naming the way out. That hint matches only a two-digit month and day (`/^\d{4}\/\d{2}\/\d{2}[ \t]/`, `:321`). `2026-9-1`, `2026/9/1` and `2026-09-1` get "line 1: not a Beancount directive", which is false, plus the generic hint "Fix the named argument and call again". Nothing tells the agent that dashes and two digits would work.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26.

## Fix

In `directive-text.ts`:

1. Recognize an existing entry's header by the lexer's date, `\d{4}[-/]\d{1,2}[-/]\d{1,2}`. That is the ledger service's `SOURCE_DATE` from w31/106. The packages share no code, so restate it here. Compare dates normalized to `YYYY-MM-DD` in `heads`, `sorted` and `insertionPoint`, so `2026/08/25` sorts as `2026-08-25` and `2026-8-26` as `2026-08-26`. This changes only where new text goes; existing lines stay as written.
2. New text keeps the w23/240 rule: it is refused unless it is written `YYYY-MM-DD`. Widen `notADirectiveHint` to every spelling the lexer reads, and have the hint name the exact rewrite ("write 2026-9-1 as 2026-09-01").

`appendLedgerText` is the only caller of `insertDirectives` and `parseDirectiveText`, and MCP, REST and GraphQL share it, so all three change together. No response shape changes.
