# `updateEntrySource` refuses an entry dated `2026/08/25` or `2026-8-25` with "must be one dated directive" and no hint, even when sent its own unchanged text, so the dashboard and the app tell the user to indent postings that are already indented (gap in w31/106 and w31/109)

**Minor · ledger (`src/features/ledger/utils/entry-tokens.ts`), plus the dashboard and mobile refusal maps · 30–45m · A1.** Stock Beancount's lexer reads `2026/08/25`, `2026-8-25` and `2026/8/25` as dates. A ledger converted from ledger-cli is full of them. Since w31/106 (`d5e0d2bdd`), the ledger service slices such an entry, so `getEntryContext` serves its text as written, starting with `2026/08/25`. Every client that edits an entry starts from that text: the dashboard's Entry Context panel loads `data.slice` into its editor (`entry-context-panel.tsx:224`) and sends the edit back as `newContent` (`:681`), and the app's edit screen does the same (`edit-transaction-screen.tsx:220,430`).

`updateSourceSlice` runs `assertSingleEntryText` first (`ledger-journal-service.ts:1581`), before it locates the slice. That check takes only `^\d{4}-\d{2}-\d{2}\s` (`entry-tokens.ts:348`). For a slash-dated or unpadded entry, that has three effects:

1. **Its own text is refused.** If the entry's slice is sent back byte for byte, the tool answers `BAD_USER_INPUT`. `docs/mcp.md` § Update or delete entry source promises `unchanged: true` with a `No change` message for exactly that call.
2. **Any edit that keeps the date is refused with a false message.** The message is "newContent must be one dated directive: 2026/08/25 * …", but the text is one dated directive. The error carries no hint, only `{field: "newContent"}`, and MCP adds its generic "Fix the named argument and call again". w23/240's YYYY/MM/DD hint and w31/109's rewrite hint ("write 2026-9-1 as 2026-09-01") are in backend-v2's `directive-text.ts`, which this ledger check never reaches.
3. **Both clients give the wrong advice.** The dashboard's `single-entry-refusal.ts:31` maps `must be one dated directive:` to `journal.entryRefusal.indentPostings`, "Indent each posting under its date line." The app's `ledger-refusal.ts:231` maps it to `ledgerEntryIndent`, "Indent postings under the date line." The postings are already indented, and nothing says the date spelling is what failed.

w31/106 decided that "an edit may therefore rewrite `2026/08/30` as `2026-08-30`, which loads the same." That decision stands. This note covers what it missed: the message, the missing hint, the unchanged case, and the client copy.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26.

## Fix

- **Ledger (`entry-tokens.ts`).** In `assertSingleEntryText`, a header that `SOURCE_DATE` (`src/foundation/rustledger/source-date.ts`) reads but that is not `YYYY-MM-DD` gets its own refusal. Name the rewrite, the way w31/109 words it for `appendLedgerText`: "`newContent` dates its entry 2026/08/25; this tool takes YYYY-MM-DD: write 2026/08/25 as 2026-08-25", with a hint saying the dashed date loads the same. Keep refusing the spelling, though. backend-v2's checks on `newContent` read dashes only (`budget-account-check.ts:19-21`, the engine-decimal scan), so accepting it would let a slash-dated budget or long amount skip them.
- **The unchanged case.** Text that equals the located slice byte for byte answers `unchanged: true`, as documented. That means either comparing against the slice before the date rule applies, or running the date rule after `locateSlice`.
- **Clients.** In the dashboard, match the new message ahead of the `must be one dated directive:` pattern (`single-entry-refusal.ts`), with a locale key in every `src/features/journal/locales/*.ts` ("Write the date as YYYY-MM-DD, for example 2026-08-25."). Do the same in the app (`src/common/ledger-refusal.ts`, `src/translations/*.ts`). Keep the indent advice for a line that really has no date.
- **Surfaces.** One ledger path serves MCP `updateEntrySource`, the REST entry-source update route and the GraphQL source mutation. They change together, with no change to the response shape. The client copy is separate dashboard and mobile commits, per the one-package rule.
- **Tests.** In `entry-tokens.test.ts`, one case per spelling (`2026/08/25`, `2026-8-25`, `2026/8/25`, `2026-08/25`). In `update-source-slice-hash.test.ts`, a slash-dated slice resent unchanged gives `unchanged: true` and an edited one gives the new message. Add cases to the dashboard's `single-entry-refusal` test and the app's `ledger-refusal.test.ts`.

## Blast radius

- `assertSingleEntryText` has one caller, `updateSourceSlice`. `deleteEntrySource(s)` and `moveEntrySources` take no new text, and w31/106's tests cover them on slash-dated entries.
- `appendLedgerText` already refuses these spellings, with the rewrite hint at HEAD (w31/109). `addLedgerEntries` takes structured ISO dates.
- Callers of the clients' maps: the dashboard's Entry Context panel and the app's edit-transaction screen.
