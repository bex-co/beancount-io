# Two option spellings stock `bean-check` accepts read as errors: a scalar option written twice (`E7003` "set more than once; the last value wins") and a boolean option spelled `yes`, `no` or `on` (`E7002` "expected TRUE, FALSE, 1 or 0"); `infer_tolerance_from_cost "on"` also leaves the flag off, so a buy stock balances reads unbalanced, on MCP, REST and GraphQL

**Minor · ledger (`src/foundation/rustledger/option-validation.ts`, `parseable-files.ts`) · 45–60m · A1.** The hosted check flags two `option` forms that `bean-check` 3.2.3, `bea check` and Fava load without a word. `@rustledger/wasm` 0.24.0 raises both as errors, and `reconcileOptionErrors` (`option-validation.ts:31`) passes them through. So `checkLedger`, the `errors` resource, REST `GET …/errors` and GraphQL `getLedgerErrors` call the ledger red, and a file write that adds either form previews `valid: false` and is refused `VALIDATION_FAILED` unless `allow_invalid` is set. GraphQL's own description of `getLedgerErrors` reads "what bean-check fails on"; bean-check fails on neither.

- **A scalar option written twice.** `option "title" "A"` and later `option "title" "B"`, or two `option "booking_method"` lines, or two `name_income` lines. Stock keeps the last value and reports nothing (`beancount/parser/grammar.py` `option()` simply overwrites a scalar). The engine keeps the last value too, then adds `E7003` "Option "title" is set more than once; the last value wins" at the later line. The service's own option reader already says the same: "Later `option` directives win over earlier ones (Beancount applies them in source order)" (`beancount-options.ts:197`). List and map options (`operating_currency`, `inferred_tolerance_default`, `documents`) are not flagged.
- **A boolean option outside `TRUE`/`FALSE`/`1`/`0`.** Stock never refuses a boolean option value. `render_commas` goes through `options_validate_boolean` (`beancount/parser/options.py:92`), which reads `1`, `true` and `yes` (any case) as true and everything else as false. `infer_tolerance_from_cost` has no converter, so `grammar.py` `option()` (`:424`–`:428`) reads `true` and `on` (any case) and `1` as true and everything else as false. The engine raises `E7002` "Invalid value "yes" for option "render_commas": expected TRUE, FALSE, 1 or 0" for `yes`, `no`, `on` or any other word. The service already reads `render_commas "yes"` as true (`parseBoolean`, `beancount-options.ts:75`), so there only the check disagrees.
- **`on` also changes the books.** With `option "infer_tolerance_from_cost" "on"`, stock turns the flag on and the engine leaves it off. A buy of `10.0 VTI {1.0001 USD}` paid `-10.03 USD` balances in stock (the cost widens the tolerance to about 0.05 USD) and reads `E3001` "Transaction does not balance: residual -0.02900 USD" on the hosted preview, beside the `E7002`. So dropping the error is not enough for that spelling: the engine has to read `on` as true.

This is the same direction as w31/138: the engine refuses what stock accepts. A ledger brought in from bean-check or Fava with a repeated `option "title"` reads red here and nowhere else, and the `close-month` prompt stops on a red ledger ("a ledger that starts red must be fixed before a close means anything").

## Fix

In `reconcileOptionErrors` (`option-validation.ts:31`), next to the existing `E7002` invalid-leaf and `E7007` rules:

- Keep `[E7003] Option "…" is set more than once; the last value wins` as a warning, as the `E7007` compatibility notice already is. Warnings stay off the check surfaces (w21/188), and the engine already applies the last value, as stock does.
- Drop `[E7002] Invalid value "…" for option "render_commas"` and `… "infer_tolerance_from_cost"` with "expected TRUE, FALSE, 1 or 0". Stock reads any value for these two without error. Every other `E7002` (a bad booking method, a bad decimal, an invalid leaf that is not a valid component) is unchanged.
- Before the engine parses, rewrite an `infer_tolerance_from_cost` value to `TRUE` when stock reads it as true (`true`/`on` in any case, or `1`) and to `FALSE` otherwise, in the copy the engine reads (`parseable-files.ts` already rewrites text for the engine this way, `withLeadingZeros`). Without it, `on` keeps the false `E3001`.

`locateOptionErrors` runs after this, so placement is unaffected. Every surface reads the shared snapshot, so `checkLedger`, the `errors` resource, REST and GraphQL error lists and every write preview's `valid` change together, with no API shape change. Add the fixtures to `verify:rustledger`, so the rule can go once the engine matches stock.
