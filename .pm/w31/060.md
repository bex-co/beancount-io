# `capital-gains` (`resolveGainsBounds` / `parseBound`) refuses valid Beancount ISO dates in years `0001`–`0099` across MCP, REST, and GraphQL (`Date.UTC` 1900-offset bug)

**Minor · backend-v2 (`resolveGainsBounds` in `src/features/ledger/utils/gains.ts`) · 20–30m · A1.** `parseBound` (`src/features/ledger/utils/gains.ts:77-90`) validates `fromDate` and `toDate` using `new Date(Date.UTC(Number(match[1]), Number(match[2]) - 1, Number(match[3]))).toISOString().slice(0, 10) === value`. Because JavaScript's `Date.UTC` maps years `0`–`99` to `1900`–`1999`, `Date.UTC(50, 0, 1)` produces `"1950-01-01"` instead of `"0050-01-01"` and fails the round-trip equality check. Every valid Beancount calendar date in years `0001`–`0099` (`0001-01-01`, `0050-01-01`, `0050-12-31`, `0099-12-31`) is therefore refused with `BAD_USER_INPUT: Invalid from-date '...'` / `Invalid to-date '...'` across MCP, REST, and GraphQL — the exact `Date.UTC` bug already fixed in `parseDirectiveDate` (`w4/m38`, `directive-date.ts:18-28`) and `isCalendarDate` (`w21/548`, `build-ledger.ts:95-105`), while `0100-01-01` and later succeed. ## Root cause

Not deployment lag — present at HEAD `d9290667e`:

`backend-cluster/backend-v2/src/features/ledger/utils/gains.ts:77-90`:

```ts
function parseBound(value: string, name: "from-date" | "to-date"): string {
  const match = ISO_DATE.exec(value);
  // The round trip rejects rollovers (`2024-13-01`, `2024-02-30`):
  // `Date.UTC` never yields NaN for four/two/two-digit inputs.
  const valid =
    match !== null &&
    new Date(Date.UTC(Number(match[1]), Number(match[2]) - 1, Number(match[3])))
      .toISOString()
      .slice(0, 10) === value;
  if (!valid) {
    throw new BadUserInputError(`Invalid ${name} '${value}'. Use YYYY-MM-DD.`);
  }
  return value;
}
```

`Date.UTC(year, month - 1, day)` maps `0 <= year <= 99` to `1900 + year`, so `toISOString().slice(0, 10)` yields `"1950-01-01"` for `"0050-01-01"`, failing `=== value`. Meanwhile `heldDays` (`:112-118`, using `Date.parse(`${d}T00:00:00Z`)`) and `heldLong` (`:126-130`, using padded 4-digit year string arithmetic) already preserve years `0001`–`0099`.
