# A `coherent_cost` or `unique_prices` error the ledger already has reads as new once a write moves it to another file: an unrelated USD entry written above a price line, or deleting the first of two uncosted VTI holdings, previews `valid: false` with `errorsBefore` equal to `errorsAfter` and is refused `VALIDATION_FAILED` (the twin of w31/127's `onecommodity` file move)

**Minor · backend-v2 (`src/features/ledger/utils/bean-check-errors.ts`) and ledger (`src/features/ledger/utils/new-ledger-errors.ts`) · 30–45m · A1.** Both copies of the "which errors are new" rule match an error on its message and its file. Only `onecommodity`'s error is matched in any file (`new-ledger-errors.ts:111`, `bean-check-errors.ts:296`). Two other plugin errors are issued once per thing and placed by a rule that reads entries across files, the same way stock Beancount places them:

- `Currency 'VTI' is used both with and without cost` (`coherent_cost`, or `pedantic`). It is issued once per currency, on the first transaction by date that holds the currency without a cost (`coherent-cost.ts:33`).
- `Disagreeing price entries` (`unique_prices`, or `pedantic`). It is issued once per pair and day, on the price that comes first when the day's prices are sorted by line number, ignoring the file (`unique-prices.ts:94-99`).

A write in one file can therefore move the error into another file without adding one. Stock `bean-check` 3.2.3 reports the same single error before and after, at the new place. The ledger keys the moved error on its new file, so it reads as new: the preview answers `valid: false` with `errorsBefore` equal to `errorsAfter`, and the commit is refused `VALIDATION_FAILED` unless `allowInvalid` is passed. `docs/mcp.md` (the preview rule) promises that "an error the write merely moves is not new" and that "Errors the ledger already had never block".

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`; `mcp:conformance` 19/19 and the contract replay were clean). The credential was an unpinned read/write `bcio_` key on the QA account. Writes went only to the designated disposable QA ledger `<qa-owner>/mcp-agent-eval`. There were five setup commits (`0656997d`, `146c29c8`, `1c4fa572`, `e8dcf898`, `8b3d1530`) and two restore commits (`c3b7f35e`, `8a6edd95`). `main.bean` is back byte for byte (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), the second file is deleted, and `checkLedger` shows no errors. Local HEAD `d8abefc82` has the same two functions.

## Fix

- In both copies of the rule, match `Currency '<currency>' is used both with and without cost` on its currency in any file. Beancount issues that error once per currency, so the currency is its identity. The file holding the first uncosted use is not part of it.
- Match `Disagreeing price entries` in any file. The message does not name its pair or day. If the error carries its location, key it on the date and pair of the price line it cites, read from the text before and after the write. Otherwise match it in any file on the message alone. Keep the per-message count in either case, so a second disagreeing pair or day still counts as new.
- Check the other errors the ledger places by a rule that reads across files (`sell-gains.ts`, `noduplicates.ts`, `pad-*.ts`) for the same move. Key any error that can move this way on what it is about.
- Tests:
  - `bean-check-errors.test.ts` and the ledger's `new-ledger-errors.test.ts`: a moved `coherent_cost` or `unique_prices` error matches. A second currency, or a second disagreeing day, does not.
  - A parity case on MCP, REST and GraphQL over a fixture like the setup: steps 1–3 preview `valid: true`, and their commits land without `allowInvalid`.
  - A live-engine case in `scripts/known-commodity-errors.ts` (or a sibling script run by `yarn verify:rustledger`).
  - Revert the fix and watch the tests fail.
- `docs/mcp.md` (the preview rule): state how these two errors match.

## Done when

On a fixture like the setup, each of steps 1–3 previews `valid: true` with `newErrors: []` on `appendLedgerText`, `addLedgerEntries`, `deleteEntrySource` and `updateLedgerFiles`, and on REST and GraphQL. Each commit lands without `allowInvalid`. A second currency held both ways, or a second disagreeing day, still previews `valid: false`.
