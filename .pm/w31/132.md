# An `updateLedgerFiles` exact-text edit that loses a race re-applies itself to the winner's content and commits it unchecked: a change bean-check would refuse lands without `allow_invalid`, and the call answers `ok: true`

**Major · backend-v2 (`src/features/ai-agent/tools/edit-ledger-files-tool.ts`) · 30–45m · A1.** w23/017 taught `updateLedgerFiles` to survive a lost race. When the commit answers `CONFLICT`, the tool re-reads the files, re-applies each `old_string` → `new_string` edit (and each create) to the new content, and commits again. The re-applied commit skips the checks the first attempt ran: the service dry run and `gateFileWrite`'s bean-check over the projected files. An edit that was valid on the file it read, but breaks the file it lands on, therefore commits without `allow_invalid`. The tool description and `docs/mcp.md` promise that "A commit that adds bean-check errors is refused with VALIDATION_FAILED". The call reports the new error in `validation` after committing it.

`appendLedgerText` and `addLedgerEntries` re-run the whole write, bean-check included, on a lost race (w31/007). The exact-text edit is MCP-only: REST `PUT …/files/{path}` and GraphQL `updateLedgerFile` take whole content and do not re-apply, so there is no REST/GraphQL twin to change.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The deployment predates local HEAD `634566e8f`, which has the same code at the lines below. The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval` with `qa-20261127-` probes. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check showed 0 errors.

## Repro (live)

Setup: the ledger's last `Assets:Cash` assertion is `2026-08-29 balance Assets:Cash 49.75 USD`. Append one probe transaction:

```beancount
2026-08-30 * "qa-20261127-race" "qa-20261127 race probe"
  Assets:Cash               -1.00 USD
  Expenses:Food:Coffee       1.00 USD
```

The two writes:

- **A:** `appendLedgerText {"path": "main.bean", "text": "2026-08-31 balance Assets:Cash  48.75 USD\n"}`.
- **B:** `updateLedgerFiles {"description": "qa-20261127 race edit", "files": [{"path": "main.bean", "old_string": "\"qa-20261127 race probe\"\n  Assets:Cash               -1.00 USD\n  Expenses:Food:Coffee       1.00 USD", "new_string": "\"qa-20261127 race probe\"\n  Assets:Cash               -2.00 USD\n  Expenses:Food:Coffee       2.00 USD"}]}`.

1. **Sequential control.** Land A, then send B. B is refused `VALIDATION_FAILED`: "commit failed: Validation failed for files: this file change would introduce 1 new bean-check error: Balance failed for Assets:Cash: expected 48.75 USD, got 47.75 USD (main.bean:93)". This is correct.
2. **Race.** Reset to the setup. Start A, and 1.0 s later send B. A answers at about 2.2–2.9 s and commits. B answers at 3.5–4.1 s. Its check passed, so it read `main.bean` before A landed. Yet the committed file holds both A's assertion and B's edit. So B's first commit, which carried the `sha` it read, lost, and the re-applied edit is what landed. B returns `ok: true`: "Committed 1 change(s) to main.bean. 1 new bean-check error: Balance failed for Assets:Cash: expected 48.75 USD, got 47.75 USD (main.bean:93)". Its `validation` is `{errorsBefore: 0, errorsAfter: 1, valid: false}`, and it carries a `commit`. `checkLedger` shows the error. This reproduced 2 of 2.

No `allow_invalid` was sent.

## Cause

- `executeEditLedgerFiles` (`edit-ledger-files-tool.ts`):
  - It checks the first attempt's projection: `changeFiles({dryRun: true})`, then `gateFileWrite(…, allowInvalid, …)` at `:633`.
  - Its commit loop (`:654-672`) catches a `ConflictError` on a retryable call (`:536`, exact-text edits and creates) and sets `attempt = (await prepare()).operations` (`:669`).
  - It then commits again without calling `changeFiles({dryRun: true})` or `gateFileWrite` on the new projection. `droppedLines`, `edits` and `notLoaded` are also not recomputed.
- `prepare()` still runs `foldOperations`, so the 28-digit amount check and the `old_string` must-match-once rule do apply to the fresh content. The bean-check gate is the only check that is skipped.

## Fix

- **Target behavior.** A re-applied exact-text edit or create is checked exactly like a first attempt, against the content it is about to commit:
  - the service dry run;
  - `gateFileWrite` with the re-applied overlays and edits.
- **Outcomes:**
  - Without `allow_invalid`, a re-applied edit that adds bean-check errors is refused `VALIDATION_FAILED` and nothing is committed. The winner's commit stays.
  - With `allow_invalid`, it commits as today.
  - `notLoaded` and the summary describe the attempt that committed.
- **Shape of the change.** Move the check into the loop, or have `prepare()` return what the gate needs and gate each attempt before its commit.
- **Docs.** Where `docs/mcp.md` says "An `old_string` edit is guarded by its own text, which must still match" (around line 850), add that a re-applied edit is checked again against what landed.
- **Tests.**
  - A case beside the w23/017 tests in `mcp-tools.test.ts`, or a parity-style test on a fake ledger that versions files by content. A rival write lands between the first read and the commit and makes the edit introduce an error. Assert `VALIDATION_FAILED`, no second commit, and the rival's content intact.
  - With `allow_invalid`, the edit commits on top of the rival.
  - The existing "both edits land" case still passes.
  - Revert the fix and watch the refusal assertion fail.

## Blast radius and controls

- **Same loop:** `createLedgerFiles` creations are also re-applied (`:536`), so a create that loses a ref race skips the gate the same way. It was not raced live.
- **Not affected:** whole-file `content` writes and deletes surface the `CONFLICT` instead of re-applying.
- **Sibling with a separate cause:** the ledger's source-slice writes re-apply in `commitLedgerFiles` and are filed as w31/131.
