# Production `/.well-known/mcp.json` reports `revision: "unknown"`

Source: `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`), run 2026-11-14.

- `GET https://beancount.io/.well-known/mcp.json` returns `"revision": "unknown"`, with `cf-cache-status: DYNAMIC`, so this is not a cached copy.
- The build is recent enough to carry the field, and `listStagedBankTransactions` takes `page`/`limit`, so production includes `a2ae7dbac` and `e195dfe96`.
- `src/config/revision.ts` reads `BEANCOUNT_REVISION`, then `RENDER_GIT_COMMIT`, and looks correct. Neither variable reaches the production API service.
- Effect: the "with the deployed revision" checks in `w1/m43` t006, `w1/m45` t005 and `w23/m44` t001 cannot be done.
- Paths: `backend-cluster/backend-v2/docs/mcp.md` ("Which build a deployment runs"), `deploy/bex/README.md` ("Which commit is running"), `deploy/docker/README.md`.

**Done when:** the owner sets `BEANCOUNT_REVISION` to the deployed commit on the production API service (or passes it at build time) and redeploys. Then `.well-known/mcp.json` `revision` is a 40-hex commit, and `git merge-base --is-ancestor a2ae7dbac <revision>` exits 0. The fix needs production deploy access, which only the owner has.

**Blocked 2026-11-14** — Triage at `1144a2e2e` reproduces it: `GET https://beancount.io/.well-known/mcp.json` still returns `"revision": "unknown"` with `cf-cache-status: DYNAMIC`. An anonymous MCP `initialize` returns 401, so `serverInfo.version` cannot be read without a key. Nothing in the repository is missing. `w22/m11` shipped the whole in-repo path: `parseRevision(process.env)` in `src/config/config.ts`, `publishedRevision` in `src/features/well-known/api/well-known-route.ts`, the `REVISION` build argument on every compose target, and the runtime path for bex. The operator docs already say to set `BEANCOUNT_REVISION` when a deploy reports `unknown` (`deploy/bex/README.md` "Which commit is running", `deploy/docker/README.md`, `backend-cluster/backend-v2/docs/mcp.md` "Which build a deployment runs"). That milestone left the production setting to the owner's next deploy, and the value is still unset. Not a duplicate: `w1/m43`, `w1/m45` and `w23/m44` are blocked on other conditions, and this one is an extra precondition for their "with the deployed revision" steps. One caution for the fix: a `BEANCOUNT_REVISION` set once by hand goes stale on the next deploy and then names the wrong build, which is worse than `unknown`. Set it from the commit on every deploy (the build argument or the deploy step), or rely on a platform `RENDER_GIT_COMMIT`.

**Unblock:** the owner gives the production API service the commit it runs on every deploy, either `BEANCOUNT_REVISION=$(git rev-parse HEAD)` at build time or a runtime `BEANCOUNT_REVISION` or `RENDER_GIT_COMMIT` that the deploy updates, and then redeploys. Only the owner can clear this, because it needs production deploy access.
