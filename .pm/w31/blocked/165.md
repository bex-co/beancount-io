# BQL `date_bin` calendar bins are still wrong, and no upstream report exists: choose a report or a refusal

**Minor · ledger (`src/foundation/rustledger/`), with backend-v2 parity · 30–45m once decided · A1.** Follow-up from routine `mcp-qa` (2026-11-28). `w6/031` and `w6/032` have been blocked since 2026-10-15 waiting for an upstream rustledger fix, but nobody has reported the bug upstream. Upstream `main` (`c1ebb168`) still has the same `date_bin_on_values` in `crates/rustledger-query/src/executor/functions/date.rs`. npm `latest` is still `@rustledger/wasm` 0.24.0, and no rustledger issue or PR covers it. The wrong bins are live on MCP, REST and GraphQL.

Repro (synthetic QA ledger, read-only):

```
SELECT date_bin('1 year', date, 2025-07-01) AS fy, sum(number) AS spent
WHERE account ~ '^Expenses' GROUP BY fy
```

The service returns one row, `2026-07-01 4091.49`. Stock returns two, `2025-07-01 15.49` and `2026-07-01 4076.00`. The cases `w6/032` lists (before the origin, quarter strides, a grouped total) reproduce on the live service and on the native engine.

**Owner decision (needed first).** Pick one:

1. **Report it upstream.** Approve a rustledger issue built from the repro text in `w6/031` and `w6/032`.
2. **Refuse it here.** `w6/032` forbids rewriting the query, not refusing it. A guard in `backend-cluster/ledger/src/foundation/rustledger/` would refuse `date_bin` with a month, quarter or year stride whose literal origin is not the first of a month, and `backend-cluster/ledger/README.md` would say so.

**Done when:** the upstream issue is filed and linked from `w6/032`, or the refusal ships with a `scripts/bql-oracle` case and the same refusal on MCP, REST and GraphQL. `w6/031` and `w6/032` stay blocked on the upstream release either way.

**Blocked 2026-11-28** — Triaged by `/loopx w31`. Nothing landed and nothing was sent upstream, because both options need the owner first.

- **Report upstream.** The blocked table in `.pm/w6/README.md` says an outward upstream request needs explicit authorization. Nothing on the board, in an ADR or in a commit grants it for this bug. w31/163 also left its upstream report for the owner to file.
- **Refuse it here.** The guard proposed above would not refuse this note's own repro. In `date_bin('1 year', date, 2025-07-01)` the origin is the first of a month. The year arm takes the bin's year from the year fields alone and keeps the origin's month and day (w6/032), so every 2026 expense lands in `2026-07-01`. A source before the origin also gets the wrong bin when the origin is the first of a month: `date_bin('3 months', 2026-01-01, 2026-02-01)`, `date_bin('1 month', 2026-02-10, 2027-03-01)` and w6/031's day strides. When the source is a column, that depends on the row's date, so a check of the query text cannot find it. Every scope therefore either refuses queries that answer correctly today or keeps serving some wrong bins. That is a product call:
  - **Narrow:** refuse a month or quarter stride whose literal origin is not day 1, and a year stride whose literal origin is not January 1. This covers the repro above and w6/032's cases at or after the origin. It still serves wrong bins for sources before the origin, which the README would have to say.
  - **Broad:** refuse every month, quarter and year `date_bin`. This also refuses origins on day 1 (or January 1) at or before every source, which answer as stock does today. The guards here so far avoid that (`date-arithmetic-guard.ts`: "never steals a working query").
  - **Per row:** run the query, then refuse when a source falls before the origin. The source would have to be evaluated as a hidden column, as the `balances.discrepancy` enrichment does. That is more work than this note's estimate.

**Unblock:** the owner chooses one or both options. (1) Authorize a rustledger issue built from the repro text in w6/031 and w6/032. A worker then dedupes, files it, and links it from w6/032. (2) Approve a refusal and pick its scope from the three above. A worker then ships the guard in `backend-cluster/ledger/src/foundation/rustledger/` with a `README.md` section, a `scripts/bql-oracle` case, a `verify:rustledger` pin on the raw engine, and the same refusal on MCP, REST and GraphQL. w6/031 and w6/032 stay blocked on an upstream release either way. Only the repository owner can clear this.
