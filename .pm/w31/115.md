# A lot error the ledger already has reads as new once a write changes the lots before it: "available 5" becomes "available 7", "2 lots match" becomes "3 lots match", and a valid buy is refused on every entry and file write (the lot-booking twin of w31/113)

**Minor · backend-v2 (`src/features/ledger/utils/bean-check-errors.ts`) and ledger (`src/features/ledger/utils/new-ledger-errors.ts`) · 30–45m · A1.** Both copies of the "which errors are new" rule match errors by message and file. Each copy strips the entry tag `(date, "narration")` (w21/367) and a failed balance assertion's "got" figure (w21/618, w31/113). The engine's two lot-booking errors also quote a figure that comes from the ledger's state, not from the failing entry:

- `Not enough units in Assets:Broker: requested 10, available 5; not enough to reduce (…)`
- `Ambiguous lot match for HOOL: 2 lots match in Assets:Broker (…)`

A write that adds a lot before the failing reduction changes that figure. The error the ledger already had then reads as new. The preview answers `valid: false` and the commit is refused `VALIDATION_FAILED` unless `allowInvalid` is passed. `docs/mcp.md` promises that "Errors the ledger already had never block". The usual way into this state is a sale whose buy history is incomplete. The usual way out is to import the missing buys one batch at a time, and every partial batch is refused.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The credential was an unpinned read/write `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`: setup commit `9763cc98`, then restore commit `26cab6e5`. `main.bean` was restored byte for byte (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check then showed 0 errors. Local HEAD `86bfaac78` has the same two functions. The messages above come from `@rustledger/wasm` 0.24.0, the version the ledger service pins; a local `validateSource` run gives the same text.

3. The same `appendLedgerText` without `dry_run` is refused `VALIDATION_FAILED`: "appending it would introduce 1 new bean-check error: Not enough units … available 7 …". Nothing is written.
4. The STRICT account behaves the same way. A one-unit buy, `2026-02-15 … Assets:QA20261127:Strict 1 QAHOOL {12.00 USD}`, previews `valid: false` with `Ambiguous lot match for QAHOOL: 3 lots match in Assets:QA20261127:Strict …`.

Control: the same buy dated `2026-04-15`, after the sale, previews `valid: true` with `newErrors: []` on `appendLedgerText` and `addLedgerEntries`. The count is 2 before and 2 after in every case.

## Fix

- In both `withoutEntryTag` copies, trim the state figures as w31/113 trims "got":
  - `Not enough units in <account>: requested <n>, available <m>; …` keys on the account and `requested <n>`.
  - `Ambiguous lot match for <currency>: <k> lots match in <account>` keys without `<k>`.
  - The engine also carries an `Insufficient units of <currency>: requested <n>, available <m>` wording. It was not seen live; trim it the same way.
- Keep the per-message count. A second failing reduction, a changed requested amount, and a reduction that newly fails all still count as new.
- Tests:
  - `bean-check-errors.test.ts` and the ledger's `new-ledger-errors` tests: a changed `available` and a changed lot count match. A changed `requested` and a second copy do not.
  - A parity case on MCP, REST and GraphQL over the fixture above: `appendLedgerText` and `addLedgerEntries` preview `valid: true`, and the commit lands without `allowInvalid`.
  - Revert the fix and watch the tests fail.
- `docs/mcp.md`: next to the balance rule, state that a lot error is matched without its available figure or lot count.

## Done when

On the fixture above, the `2026-02-15` buy previews `valid: true` with `newErrors: []` on `appendLedgerText`, `addLedgerEntries` and `updateLedgerFiles`, and on REST and GraphQL. Its commit lands without `allowInvalid`. `checkLedger` then shows the same reduction error with `available 7`. A buy that makes the sale succeed removes the error.
