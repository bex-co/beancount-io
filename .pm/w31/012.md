# Ledger search without `limit` returns the host's default page (20 rows with `q`, 30 without) and reports `hasMore: false` on MCP, REST and GraphQL

**Minor · backend-v2 (catalog page signal) · 30–45m · A1.** Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`), 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). Credential: an unpinned `bcio_` key on the QA account. Read-only, on the public `open_ledger/*` catalog.

- **Repro.**
  - MCP `resources/read` `beancount://catalog/ledgers/search?q=open_ledger` returns 20 ledgers (`open_ledger/3m` … `open_ledger/american-express`). Its `_meta.page` and second content item say `{"returned":20,"page":1,"hasMore":false}`.
  - The same read with `&page=1` answers the same way.
  - `beancount://catalog/ledgers/search` with no parameters returns 30 ledgers with `hasMore: false`.
  - REST `GET /api-gateway/v1/ledgers/search` returns 30 rows with `X-Has-More: false` and no `Link`.
  - GraphQL `{ s: searchLedgers { fullName } }` returns 30 rows with `extensions.page.s.hasMore: false`.
- **Truth.** Paging `q=open_ledger` with `limit=50` returns 263 distinct ledgers over six pages. The fifth page reports `hasMore: true`, and the sixth returns 13 rows with `hasMore: false`.
- **Controls.**
  - `q=open_ledger&limit=20` returns the same 20 rows with `hasMore: true, nextPage: 2`.
  - `limit=75` and `limit=100` (pages 1 and 2) match the truth exactly on all three surfaces.
  - A `page` past the first with no `limit` carries no signal, as `docs/mcp.md` "Pagination" says.
- **Effect.** An agent that searches the catalog with a query, as the template allows (`limit` is optional), reads the first 20 matches as the complete result. Nothing tells it that 243 more exist.
- **Cause.**
  - `src/server/api/page-signals.ts:103` registers `searchLedgers: numberedArray()` with no default limit.
  - `numberedPage` (`src/shared/page-info.ts:57-61`) reads a missing `limit` as "a read that returns everything".
  - That holds for `accessibleLedgers` and `ownedLedgers`, whose unpaged call returns every ledger (w2/m34, `catalogWindow`). It does not hold for search. `searchLedgers` (`src/features/ledger/workflow/ledger-workflow.ts:2158-2189`) forwards `page` and `limit` as given, so the host applies its own default page size.
  - `page-signals.test.ts:150` pins the complete-read reading only for `accessibleLedgers`.
- **Same class (code reading, not reproduced live):**
  - `listLedgers` and `listUserOwnedLedgers` called with `page: 1` and no `limit`: `catalogWindow` returns `null` when `limit` is missing (`ledger-workflow.ts:487`). The call is a single host page of 30, signalled `hasMore: false`. The QA account has 6 ledgers, so this was not observable.
  - REST and GraphQL `listPublicKeys` (`ledgerPublicKeys: numberedArray()`) have an optional `limit` that is forwarded to the host.

**Done when:**

- With no `limit`, `searchLedgers` sends an explicit, documented default page size upstream, and its signal uses the same default. A full default page then reads `hasMore: true, nextPage: 2` on MCP (`_meta.page` and the second content item), REST (`X-Has-More`, `Link`) and GraphQL (`extensions.page`).
- `page: 1` without `limit` on the three ledger lists and on public keys reports a signal that matches what was returned, or carries no signal, as a later page already does.
- `docs/mcp.md` "Pagination" states the search default.
- `page-signals.test.ts` and `catalog-parity.test.ts` cover an unpaged search over a fake host that serves more than one default page. The tests fail with the fix reverted.
- Package: `backend-cluster/backend-v2`.
