# Reading the permission of an existing user who is not a collaborator is an `INTERNAL_SERVER_ERROR` on MCP, REST and GraphQL; the doc promises `NOT_FOUND`

**Minor · backend-v2 (collaborator workflow) · 30–45m · A1.** Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`), 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). Credential: an unpinned read/write/admin `bcio_` key on the QA account. Only reads were sent, all on the designated QA ledger `<qa-owner>/mcp-agent-eval`, whose collaborator list is empty.

- **Repro.** Read `beancount://<qa-owner>/mcp-agent-eval/collaborators/permission?collaborator=open_ledger`. `open_ledger` is an existing account (the public example ledger's owner, `beancount://social/profile?username=open_ledger` reads it) and is not a collaborator. The answer is JSON-RPC `-32000`, `data.code: INTERNAL_SERVER_ERROR`, "Internal server error". REST `GET /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/collaborators/permission?collaborator=open_ledger` answers 500 `INTERNAL_SERVER_ERROR`. GraphQL `getLedgerCollaboratorPermission(ledgerId, collaborator: "open_ledger")` answers `INTERNAL_SERVER_ERROR` with `data: null`. Three fresh requests, and the `Open_Ledger` spelling, gave the same result.
- **Controls.**
  - The owner's own name reads its permission, and MCP equals REST.
  - A name no account has (`qa-20261115-nobody-zz`) answers `BAD_USER_INPUT` "No such user: qa-20261115-nobody-zz" on all three surfaces.
  - `setLedgerCollaborator` and `removeLedgerCollaborator` previews for both names succeed with `current: null`.
- **The contract.** `backend-cluster/backend-v2/docs/mcp.md` "Resources" (line 1288) says `collaborator` "must be the owner or a collaborator; any other name, whether or not the account exists, answers `NOT_FOUND` with the same message". `c921babd6` (2026-10-22) wrote that sentence and added the ledger service's membership check. Today the two cases answer differently, and neither answers `NOT_FOUND`.
- **Cause (from source; the production ledger service's revision is unknown).** At HEAD, `backend-cluster/ledger/src/api/collaborators.ts:44-61` checks membership first and answers 404 `Collaborator '<name>' not found` for a non-collaborator. backend-v2's `getCollaboratorPermission` (`src/features/ledger/workflow/ledger-collaborators-workflow.ts:544-577`) calls the generated client directly, not through `unwrapFavaResponse`. Its catch (line 572) only rewrites "user does not exist" through `translateUnknownUser` (line 40, added by w5/026), and rethrows every other `FavaApiError` raw, the 404 included. A raw upstream error is masked as `INTERNAL_SERVER_ERROR` on every surface. A name no account has fails Gitea's membership check with "user does not exist", which becomes `BAD_USER_INPUT` "No such user" (w5/026, which predates the doc sentence).
- **Effect.** An agent asking "what access does X have?" about someone who is not on the ledger gets an internal error with the hint "Retry once. If it persists the failure is server-side and changing the request will not help." It cannot tell that from an outage, and a monitor counts it as a server fault. The fourth fresh request, made to capture the hint, gave the same answer.

**Done when:** on MCP, REST and GraphQL, a permission read for an existing non-collaborator and for a name no account has both answer `NOT_FOUND` with the same message, and a hint that names `beancount://{owner}/{name}/collaborators`. Other upstream failures go through `favaApiErrorToDomainError`, so a 5xx is `SERVICE_UNAVAILABLE`, not a masked 500. The owner's and a collaborator's reads are unchanged. The w5/026 expectation in `src/features/ledger/workflow/__tests__/ledger-collaborators-workflow.test.ts` is updated. A case in `src/features/ai-agent/api/__tests__/collaborator-parity.test.ts` reads a non-collaborator through all three surfaces, and it fails with the fix reverted. Package: `backend-cluster/backend-v2`. One workflow serves all three adapters.
