# A routing option written with a leading `./` (`custom "beancountio-option" "transaction_file" "./main.bean"`) refuses every routed write of that kind with "Invalid file path", and the hint tells the agent to fix an argument it never sent, on MCP, REST and GraphQL

**Minor · backend-v2 (`src/features/ledger/utils/entry-file-resolver.ts`), ledger (`src/shared/safe-repo-path.ts`) · 30–45m · A1.** A ledger's `custom "beancountio-option"` lines name the file each kind of entry goes to, as a path from the ledger root. Beancount reads `./main.bean` and `main.bean` as the same file, and so does an `include`, so `./txns/{year}.bean` is a natural way to write the option. The router uses the value as written, and the repository-path check then refuses the `.` part. Every transaction written through `appendLedgerText` or `addLedgerEntries` fails, both preview and commit, while the ledger itself checks clean. The refusal blames the call: MCP's hint says "Fix the named argument and call again", and REST and GraphQL name `field: "paths[0]"`. Neither the agent nor the user sent a path, and nothing names the option that produced it.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27.

- **Target:** `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`), the same run as w31/151. Production's backend-v2 is older than w31/137, so it still says only "Invalid file path". At local HEAD `a872b7db3` the same check (`safe-repo-path.ts:39`) quotes the path and says `has a "." or ".." part: write it relative to the ledger root`, but it still names `paths[0]` and not the option. So this is not deployment lag.
- **Credential:** an unpinned read/write `bcio_` key on the QA account.
- **Writes:** only to the designated QA ledger `<qa-owner>/mcp-agent-eval`: option commit `01c40913`, restore `86ed5023`. `main.bean` was restored byte for byte (sha256 `77c3a591efd311e0`), and the check showed 0 errors afterwards.

## Repro (live)

1. `updateLedgerFiles` on `main.bean`: after `option "operating_currency" "USD"`, add `2000-01-01 custom "beancountio-option" "transaction_file" "./main.bean"`. The result is `valid: true`.
2. `appendLedgerText {dry_run: true, text: "2026-09-02 * \"CAFE\" \"coffee\"\n  Expenses:Food:Coffee   4.50 USD\n  Assets:Cash"}` is refused `BAD_USER_INPUT` "Invalid file path", with hint "Fix the named argument and call again; `tools/list` publishes each tool's input schema." REST `POST …/directives/text {dryRun: true}` answers `400` `{"code":"BAD_USER_INPUT","message":"Invalid file path","metadata":{"field":"paths[0]"}}`, and GraphQL `appendLedgerText(dryRun: true)` gives the same error with `extensions.field: "paths[0]"`.
3. `addLedgerEntries {dry_run: true}` with the same transaction as a typed entry is refused `BAD_USER_INPUT` "Invalid file path: ./main.bean", with the same hint.

Control: in the same ledger, an `addLedgerEntries` `note` previews cleanly ("Would add 1 entry. No new bean-check errors."), because notes are not routed through the option. Stock `bean-check` accepts `include "./x.bean"` as `include "x.bean"`.

## Cause

`resolveEntryFile` (`entry-file-resolver.ts:71`–`72`) returns the option's template with its date fields filled in and nothing else changed. In backend-v2, `appendLedgerText` hands that target to `getFilesContent`, which checks each path with `assertSafeRepoPath` under the field name `paths[<index>]` (`ledger-repo-service.ts:326`). That check refuses any `.` or `..` part (`safe-repo-path.ts:38`–`39`). `addLedgerEntries` passes it to the ledger service as each entry's `filename`, and that service's own check (`backend-cluster/ledger/src/shared/safe-repo-path.ts:36`–`40`) refuses it there. Neither check knows that the path came from the ledger's option and not from the caller.

## Fix

Normalize a routed path before it is used. Resolve the interpolated template against the entry point's folder the way Beancount resolves an include (`posix.normalize` of the join, as `resolveIncludeTarget` does), so `./txns/2026.bean` routes to `txns/2026.bean`. Then the existing-file lookup, the include check and the include line all see the path the ledger loads. A value that still points outside the ledger after that (`../x.bean`, `/x.bean`), or breaks another path rule, is refused `BAD_USER_INPUT`. The message names the option and its value, for example ``the ledger's `transaction_file` option routes this entry to "../x.bean", which is outside the ledger``, and the hint says to fix that `custom "beancountio-option"` line, or to pass `path` on `appendLedgerText`. It must not point at the call's arguments. Both write tools route through `resolveEntryFile`, and the receipt workflow uses it for `document_file`, so all of them pick this up. The MCP tools, REST `POST …/directives/text` and `…/entries`, and GraphQL `appendLedgerText` and the entry mutations change together.

Done when, on a ledger whose `transaction_file` is `./txns/{year}.bean`, an `appendLedgerText` and an `addLedgerEntries` transaction dated 2026 land in `txns/2026.bean` on MCP, REST and GraphQL, preview and commit alike, and an existing `txns/2026.bean` is updated, not created a second time or included twice. A `../x.bean` option is refused with a message that names the option. Tests cover both cases and fail with the fix reverted.
