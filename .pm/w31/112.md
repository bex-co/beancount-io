# The MCP streaming archive route charges a `bcio_` key two archive-budget tokens per download, so the documented 30 downloads a minute stops at 15

**Minor · backend-v2 (`src/features/ai-agent/api/mcp-archive-route.ts`, `src/server/api/composition-root.ts`, `src/server/rest/identity-middleware.ts`) · 40–60m · A1.** `docs/mcp.md` § Asset and archive URL discovery says the MCP archive blob, the streaming URL and both REST spellings "share the existing 30-downloads-per-minute credential bucket", and that "a refused read still spends one". `GET /api-gateway/mcp/archive/{owner}/{name}/{archive}` is the URL `beancount://{owner}/{name}/archive-download-url` hands an MCP caller. With a personal API key, each fetch on it spends two tokens of that bucket, so the 16th fetch in a minute is refused `429`. Because the bucket is shared, those 15 fetches also exhaust the MCP blob read and the v1 download for the rest of the minute.

## Environment

- **Target:** `https://beancount.io`, `beancount-mcp 1.0.0`, protocol `2025-11-25`. `yarn mcp:conformance` 19/19 and `qa-contract-replay.mjs --commit-probes` 17 probes, 0 mismatches, in the same run.
- **Credential:** an unpinned `bcio_` API key with `ledger.read ledger.write ledger.admin` on the designated QA account. Ledger `<qa-owner>/mcp-agent-eval`, read only; no writes.
- **Local HEAD:** `930518f53`, with the same code as cited below, so this is not deployment lag.

## Repro

Run each loop in a fresh minute (wait 61 s between them). Pace them at one request a second, which stays below 60 a minute and has nothing to do with the write budgets.

1. **Streaming route:** `GET /api-gateway/mcp/archive/<qa-owner>/mcp-agent-eval/main.zip` with `Authorization: Bearer <key>`, 20 times. Fetches 1–15 return `200` with 1127 bytes. Fetches 16–20 return `429`, and the first refusal reads `retry-after: 44` at 16.5 s into the loop. That dates the window to the loop's own first fetch, so no other traffic shared it.
2. **Control, MCP blob:** `resources/read` `beancount://<qa-owner>/mcp-agent-eval/archive/main.zip`, 20 times. All 20 succeed.
3. **Control, v1 REST:** `GET /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/archive/main.zip`, 20 times. All 20 return `200`.

An unpaced mix found it first. Ten MCP blob reads and ten streaming fetches, alternating, were refused `RATE_LIMITED` (`retryAfter: 49`) on the 21st request. That is 10 × 1 + 10 × 2 = 30 tokens.

## Root cause

- `assembleRestRouter` mounts `restIdentityMiddleware` and `restRateLimitMiddleware` on every route of the shared router (`composition-root.ts:418,420`), "outside"-gate routes included. That covers the MCP transport (`:346`) and this archive route (`:359`).
- For a `bcio_` key, `resolveIdentity(ctx, …)` in the identity middleware succeeds (`identity-middleware.ts:30`). So `restRateLimitMiddleware` charges the matched op, `REST GET /api-gateway/mcp/archive/{owner}/{name}/{archive}` (`rate-limit-middleware.ts:32`). That op is in the archive bucket (`rate-limit.ts:186`).
- The handler then resolves the identity again with the MCP audience (`mcp-archive-route.ts:39`). It calls `enforceRateLimit` with the same op id (`:54`), which charges the same `usr:`/`tok:` keys a second time.
- The v1 route and the MCP blob are charged once each, which is why they are the working controls. v1 has no charge in its handler. The blob's JSON-RPC POST spends the transport op, a different bucket, before `gateMcpCall` charges the archive bucket once.
- `mcp-archive-route.test.ts` mounts the route on a bare `Router` with `enforceRateLimit` mocked (`:6`, `:70`). The rate-limit aliasing test calls `consume` directly. No test runs a download through the assembled router's middleware, so neither sees the second charge.

## Same cause, source-traced only (not exercised: this run had no MCP OAuth token)

An MCP-audience OAuth token is what claude.ai, ChatGPT, Cursor and other hosted connectors hold. The identity middleware resolves it against the application audience only, which refuses the MCP audience by design (w23/023), so it gets no identity. `restRateLimitMiddleware` then takes its anonymous branch (`rate-limit-middleware.ts:44`) and charges `anon:default:<client ip>`, 120 a minute (`rate-limit.ts:247`). That has two effects:

- On this archive route, an OAuth download spends the archive bucket once (in the handler, correct) and also spends one request of the caller's anonymous IP budget.
- On `POST /api-gateway/mcp`, every JSON-RPC request from an OAuth token is charged to that IP-wide anonymous bucket, handshake included. The per-credential transport (300 a minute) and handshake (1200 a minute) budgets (`rate-limit.ts:156,161`) never apply. `docs/mcp.md` § Results and failures says the limiter "counts calls per credential and operation", with a per-credential transport budget and a larger handshake bucket. If every user of a hosted connector shares a few egress IPs, they share 120 requests a minute between them.

Confirm this case with a test through the assembled router (an MCP-audience JWT on both mounts) before changing it. A connected OAuth session would also confirm it live.

## Fix

Target behavior: one download spends exactly one archive-budget token for every credential kind (API key, MCP OAuth token, application OAuth token). An MCP-audience request is charged to its credential, never to the caller's IP.

- Have the shared middleware resolve identity on the two MCP mounts (`/api-gateway/mcp` and `/api-gateway/mcp/archive/…`) with the MCP OAuth resource, which those mounts already accept. Then its charge lands on the credential, and the archive handler drops its own `enforceRateLimit`. The middleware already sets `Retry-After`. Keep the handler's session refusal and read-capability check.
- Alternatively, keep the handler's charge and skip the middleware's charge for this mount. Either way, a download is charged once.
- One mount, no response-shape change. REST and GraphQL archive reads are unaffected, and GraphQL serves no archive bytes.

## Tests

- Through the real middleware stack (`restIdentityMiddleware` + `restRateLimitMiddleware` + `setMcpArchiveRoute`, limiter not mocked), with a `bcio_` key: 30 streaming fetches succeed and the 31st is `429`. 15 streaming fetches plus 15 MCP blob or v1 reads in one window also fit, with the next one refused.
- The same test with an MCP-audience token charges `usr:`/`tok:` keys and never an `anon:` key, on both mounts.
