# `renameAccount` refuses an account with a non-Latin leaf (`Expenses:Food:日本`) that the ledger, stock Beancount and `addLedgerEntries` all accept, on MCP, REST and GraphQL

**Minor · backend-v2 (account rename gate) · 30–45m · A1.** Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`), 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). Credential: an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. `main.bean` was restored byte for byte afterwards (blob `f1a0b83c`), and the check is clean.

- **Repro.**
  1. `appendLedgerText` commits `2026-08-30 open Assets:Qa20261115:Caisse USD`, `2026-08-30 open Expenses:Qa20261115:日本 USD`, and a balanced transaction between the two accounts. The answer is "No new bean-check errors", and `checkLedger` reports `errors: []`.
  2. `listLedgerEntries {account: "Expenses:Qa20261115:日本"}` and the `register/{account}` resource both read the new account.
  3. `renameAccount {from: "Expenses:Qa20261115:日本", to: "Expenses:Qa20261115:Japan", dry_run: true}` answers `BAD_USER_INPUT` "from "Expenses:Qa20261115:日本" is not a valid account name (Root:Component, each component starting with a capital letter or digit)."
  4. REST `POST …/rename-account` with `dryRun: true` answers 400 with the same refusal. So does GraphQL `renameLedgerAccount(dryRun: true)`.
  5. `to: "Assets:Qa20261115:現金"` is refused the same way.
- **Controls.**
  - An ASCII rename of the same new account (`…:Caisse` → `…:Caisse2`) previews "2 lines in 1 file".
  - `to: "Expenses:Food:Café"` previews fine, because `é` does not start a component.
  - `addLedgerEntries` and `appendLedgerText` previews of `open Expenses:Food:日本` both report `valid: true`.
  - Stock beancount 3.2.3 `loader.load_string` loads `Expenses:Food:日本` and `Expenses:Qa20261115:日本` with no error, though `account.is_valid` is `False` for both. The grammar checks an account with an unanchored prefix match.
  - Stock does report "Invalid account name" for `Expenses:日本`, whose first component is non-Latin. The hosted engine accepts that one too.
- **Effect.** A ledger that uses non-Latin leaf names, which is common for Chinese and Japanese Beancount users, can be written by every entry tool. Its accounts can never be renamed, in or out. An agent asked to rename one gets an input error for a name it read from the ledger itself.
- **Cause.**
  - `assertRenamable` (`src/features/ledger/workflow/account-rename-workflow.ts:223-233`) gates both names on `isValidAccountName` (`src/features/ledger/utils/account-matcher.ts:40`). That is stock's strict `account.is_valid` full match.
  - The rename scanner itself already handles non-ASCII names (w1/m43 t008).
  - The same module already approximates loader acceptance in `loadsAsAccount` (`:58`, `ACCOUNT_PREFIX_RE`).

**Done when:**

- On MCP, REST and GraphQL, `renameAccount` accepts as `from` and `to` every name the loader accepts. That means a valid first component followed by non-Latin components, such as `Expenses:Food:日本` → `Expenses:Food:食品`. The rename rewrites those names, and its preview reports `valid: true`.
- A name the loader refuses is still `BAD_USER_INPUT`, with a message that states the actual rule. Examples: a lowercase ASCII start (`Expenses:Food:coffee`), or a non-Latin first component as `to`.
- `account-rename-workflow.test.ts` and `rename-account-parity.test.ts` cover a non-Latin leaf through all three surfaces, and fail with the fix reverted.
- `docs/mcp.md` "Renaming an account" says which names are accepted.
- Package: `backend-cluster/backend-v2`. One workflow serves all three adapters.
