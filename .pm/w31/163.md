# The BQL `cost` column that `runBqlQuery` advertises drops the sign of a sale: `-5 GLD {197.06 USD}` reads `985.30 USD`, so `sum(cost)` gives 10710.40 USD where the cost basis is 4559.80, on MCP, REST and GraphQL

**Major · ledger (BQL results of the pinned `@rustledger/wasm` 0.24.0, served by `src/features/ledger/service/ledger-shell-service.ts`), backend-v2 (`src/features/ai-agent/tools/bql-query-tool.ts`) · 30–45m in this repo, plus an upstream report · A1.** Found by `/loopx w31` routine `mcp-qa` on 2026-11-28, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`), with an unpinned read/write QA key, read-only, on the QA account's synthetic example ledger (the generated `bean-example` file). Reproduced at HEAD `27a68409e` through `LedgerShellService` and on the raw engine with the ledger below.

## What an agent sees

The `runBqlQuery` description lists the columns an agent can select: `date, year, month, flag, payee, narration, account, number, currency, cost, weight, balance, position, tags, links, meta`. Stock beanquery 0.2.0 has no `cost` column (`column "cost" not found in table "postings"`). The engine has one, and `backend-cluster/ledger/scripts/bql-oracle/allowlist.json` accepts it as superset behavior (`cost-column`, from w23/022). Its value was only ever checked on a purchase (w23/022 it.299). On a reduction it is the lot's cost with the sign dropped, while `cost(position)` and `weight` keep the sign.

So `SELECT account, sum(cost)` adds every sale to the basis instead of taking it off. On the example ledger, the `Assets:US:ETrade:GLD` account bought 32 GLD and sold 15, and holds 17. The query reports a basis of 10710.40 USD. The real figure is 4559.80 USD, which `sum(cost(position))`, `sum(weight)` and stock all give. Nothing marks the figure as wrong.

2026-01-05 * "Buy VTI"

  Assets:Broker:VTI   -2 VTI {100.00 USD} @ 110.00 USD

`SELECT date, number, cost, cost(position), weight WHERE account = 'Assets:Broker:VTI'`:

| date | number | `cost` (actual) | `cost(position)` | `weight` |
| --- | --- | --- | --- | --- |
| 2026-01-05 | 5 | 500.00 USD | 500.00 USD | 500.00 USD |
| 2026-02-05 | -2 | **200.00 USD** | -200.00 USD | -200.00 USD |

`SELECT sum(cost), sum(cost(position)) WHERE account = 'Assets:Broker:VTI'` gives `700.00 USD` and `300.00 USD`. Stock beanquery refuses the first column and gives `300.00 USD` for the second. A short opening (`-3 VTI {100.00 USD}` on a liability) reads `cost` `300.00 USD` against `cost(position)` `-300.00 USD`, so the sign is dropped whatever the direction.

Production, the same shape on the example ledger, `runBqlQueryStructured` `SELECT date, number, cost, cost(position), weight WHERE account = 'Assets:US:ETrade:GLD' AND number < 0` gives `["2015-11-18","-5",{"USD":"985.30"},{"USD":"-985.30"},{"USD":"-985.30"}]` and `["2017-02-15","-10",{"USD":"2090.00"},{"USD":"-2090.00"},{"USD":"-2090.00"}]`. REST `POST /api-gateway/v1/ledgers/{owner}/{name}/query` and GraphQL `queryShell` return the same rows, since all three call `LedgerShellService`. The `runBqlQuery` text table shows the same values.

## Root cause

`@rustledger/wasm` 0.24.0 (the newest release) computes the `cost` column as the unsigned total cost: `query(source, "SELECT number, cost, cost(position) …")` on the raw engine returns `{"number":"200.00","currency":"USD"}` for the `-2 VTI` posting. The ledger service passes it through unchanged (`normalizeBqlQueryForEngine` has no stage for it; `ledger-shell-mappers.ts` only types it `Amount`). `bql-query-tool.ts:15` advertises the column to every MCP client. The oracle entry `cost-column` excuses only the outcome difference (stock refuses), so no check ever compared its values with `cost(position)`.

## Fix

- In `backend-cluster/ledger`, make the column agree with `cost(position)`: a bare `cost` column (an identifier `cost` not followed by `(`, not quoted, outside strings) is rewritten in `normalizeBqlQueryForEngine` to `cost(position)`, keeping `cost` as the column header (as `withSourceHeaders` keeps source text). Then `cost` is signed per posting, and `sum(cost)` equals `sum(cost(position))`. An alias named `cost` and the references to it are left alone: `skills/beancount-trade/references/realized-gains.md` selects `-number * cost_number AS cost`. If that rewrite is not sound everywhere the column can appear (`WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, nested `FROM`), refuse the bare column instead, as stock does, with a message naming `cost(position)`. Never serve the unsigned figure.
- In `backend-cluster/backend-v2`, the `runBqlQuery` description either keeps `cost` with its fixed meaning, or lists `cost(position)` in its place if the column is refused. Update `docs/marketplace-submissions/lobehub/lhm.plugin.json` the same way.
- Add oracle and service coverage: a reduction and a short opening, comparing `cost` with `cost(position)` per row and `sum(cost)` with `sum(cost(position))`, plus the `verify:rustledger` pin that the raw engine still drops the sign (it fails once a fixed engine ships, as the w23/022 pins do).
- Report the unsigned column upstream with the reproducer above.

REST, GraphQL and MCP share the service, so the ledger change covers all three. The description is MCP-only text.

## Blast radius

`grep` for a bare `cost` column in this repository finds no product query that relies on it: the dashboard, the CLI (`bea query` runs stock beanquery, which refuses it) and the skills use `cost(position)`, `cost_number` or `number * cost_number` (the realized-gains guide names that product `cost` with `AS`). Working controls are `cost(position)`, `weight` and `sum(position)` on every surface. `account_balance`, the other superset column, reads the same running units as `balance` on the same account.

## Dedupe

Searched `.pm/**` for `cost column`, `` `cost` column ``, `sum(cost)` and `SELECT cost`. w23/022 (done) records the column as superset with its value checked on a purchase only. w23/169 (done) gave it the `Amount` dtype. w23/012 (done) is `cost()` of a multi-currency inventory, a different function and a different defect. No item covers the sign. Not deployment lag: HEAD `27a68409e` and the newest engine release behave the same.
