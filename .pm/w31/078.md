# `previewLedgerSetup` and `createLedger` skip the 28-significant-digit engine decimal limit on `setup.accounts[].amount`, silently rounding 29–30+ digit opening balances (`validation.ok: true`) and cascading parse errors on wider numbers across MCP, REST, and GraphQL (gap in `w21/997`, `w23/081`)

**Major · backend-v2 (`src/features/ledger/setup/build-ledger.ts`, `src/features/ledger/utils/engine-decimal.ts`) · 30–45m · A1/A2.** The ledger engine's `Decimal` holds at most 28 significant digits (and 28 fractional digits): `w21/997` enforces this limit on structured entries (`addLedgerEntries` / `POST .../entries` / GraphQL `upsertEntry`) and `w23/081` enforces it on every raw ledger text write (`appendLedgerText`, file writes, `updateSourceSlice`). Ledger setup (`previewLedgerSetup` and `createLedger`) still validates `setup.accounts[].amount` only against `AMOUNT_PATTERN = /^[+-]?\d+(\.\d+)?$/` (`src/features/ledger/setup/build-ledger.ts:44, 300-304`) and never checks the 28-digit engine decimal bound. As a result, across MCP, REST, and GraphQL:

1. **Silent precision loss (`validation.ok: true`):** 29–30+ digit amounts that rustledger rounds rather than failing to parse — e.g. `1.0000000000000000000000000001` (29 significant digits, 28 fraction digits), `1.00000000000000000000000000001` (30 significant digits), `0.000000000000000000000000000001` (30 fraction digits), or `10000000000000000000000000000` (29 integer digits) — return HTTP `200` with `validation: { ok: true, errors: [] }` on `previewLedgerSetup`, and `createLedger` commits a silently rounded opening balance and matching `balance` assertion into `main.bean`.
2. **Unfiltered 5-error cascade on wider overflows:** 34-digit amounts such as `9999999999999999999999999999999999` bypass setup validation, hit the ledger-service `bean-check` subprocess, and return HTTP `200` with `validation.ok: false` and five noisy parser/interpolation errors instead of an upfront `VALIDATION_FAILED` on `setup`.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-24 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, verified at HEAD `d5a22712d`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger for control probes: `<qa-owner>/mcp-agent-eval` (read-only / dry-run / preview probes only; no files or ledgers were created or modified).

## Repro (live)

Reproduced identically across MCP, REST, and GraphQL against `https://beancount.io`:

1. **Silent rounding (`validation.ok: true`)** with `setup: { preset: "personal@1", accounts: [{ name: "Assets:Bank", openingState: "known", amount: "1.0000000000000000000000000001" }] }` (also reproduced with `"1.00000000000000000000000000001"`, `"0.000000000000000000000000000001"`, and `"10000000000000000000000000000"`):
   - **MCP `tools/call previewLedgerSetup`:** HTTP `200`, `isError` unset, `ok: true`, `validation: { ok: true, errors: [] }`; generated `main.bean` contains `Assets:Bank 1.0000000000000000000000000001 USD` and `balance Assets:Bank 1.0000000000000000000000000001 USD`.
   - **REST `POST /api-gateway/v1/ledgers/preview`:** HTTP `200`, `validation: { ok: true, errors: [] }`.
   - **GraphQL `previewLedgerSetup(setup: { preset: PERSONAL, accounts: [{ name: "Assets:Bank", openingState: KNOWN, amount: "1.0000000000000000000000000001" }] })`:** HTTP `200`, `data.previewLedgerSetup.validation: { ok: true, errors: [] }`.
2. **Overflow cascade** with `amount: "9999999999999999999999999999999999"` (34 digits):
   - **MCP `previewLedgerSetup`, REST `POST /api-gateway/v1/ledgers/preview`, and GraphQL `previewLedgerSetup`:** all return HTTP `200` (not `VALIDATION_FAILED` on `setup`) with `validation: { ok: false, errors: [...] }` containing 5 cascading errors (`Transaction has multiple postings with missing amounts in the same currency (2 in USD)`, `interpolation failed`, `parse error: invalid number in amount (likely exceeds 28-digit Decimal precision)` × 2, `parse error: unexpected input`).
3. **Working controls (same credential, same deployment):**
   - `addLedgerEntries` with `amount: { number: "1.0000000000000000000000000001", currency: "USD" }`, `dry_run: true` → `isError: true`, `BAD_USER_INPUT`: `entry 0: amount.number "1.0000000000000000000000000001" has more than 28 significant digits`.
   - `appendLedgerText` with `2026-01-02 balance Assets:Bank:Checking 9999999999999999999999999999999999 USD`, `dry_run: true` → `isError: true`, `BAD_USER_INPUT`: `amount 9999999999999999999999999999999999 has more than 28 significant digits; the engine would read it back rounded`.
   - `previewLedgerSetup` with 28-digit boundary `"1234567890123456789012345678"` → HTTP `200`, `ok: true`, `validation: { ok: true, errors: [] }`.

## Expected

`previewLedgerSetup` and `createLedger` refuse any `setup.accounts[].amount` exceeding the engine's 28-significant-digit / 28-fraction-digit `Decimal` bound upfront with `ValidationError("setup", ...)` (`VALIDATION_FAILED` on MCP, HTTP `400` on REST, `VALIDATION_FAILED` on GraphQL) before building files, invoking the ledger-service check, or creating a repository. Boundary 28-digit amounts (including leading-zero inputs like `00001.23`) remain accepted.

## Root cause

Not deployment lag — present at HEAD `d5a22712d`:

- `backend-cluster/backend-v2/src/features/ledger/setup/build-ledger.ts:44, 300-304`: `AMOUNT_PATTERN = /^[+-]?\d+(\.\d+)?$/` checks decimal syntax only. Both `previewLedgerSetup` (`ledger-workflow.ts:918`) and `createLedger` (`ledger-workflow.ts:768`, via `buildLedgerFiles`) route through `build-ledger.ts`, which never calls the engine-decimal check.
- `backend-cluster/backend-v2/src/features/ledger/utils/engine-decimal.ts:34-46`: `textLiteralFitsEngine(literal)` already implements the exact 28-significant-digit and 28-fraction-digit rule (stripping sign/commas/leading integer zeros), but is currently private to `engine-decimal.ts` and only invoked on raw Beancount text writes (`w23/081`).

## Fix

In `backend-cluster/backend-v2`:

1. Export `textLiteralFitsEngine` (or a clearly named helper such as `fitsEngineDecimal`) and `MAX_DECIMAL_DIGITS` from `src/features/ledger/utils/engine-decimal.ts`.
2. In `src/features/ledger/setup/build-ledger.ts:300-304` (inside `if (openingState === "known")`), after verifying `AMOUNT_PATTERN.test(selection.amount)`, check `!fitsEngineDecimal(selection.amount)` and call `fail(...)` (`ValidationError("setup", ...)`, matching every other setup refusal, e.g. naming the account, literal — truncated safely if very long — and the 28-significant-digit limit).
3. Add unit tests in `src/features/ledger/setup/__tests__/build-ledger.test.ts` covering:
   - 29-digit integer (`10000000000000000000000000000`),
   - 29-significant-digit fraction (`1.0000000000000000000000000001`),
   - 30-fraction-digit small decimal (`0.000000000000000000000000000001`),
   - 34-digit overflow (`9999999999999999999999999999999999`),
   - signed and leading-zero controls (`-1234567890123456789012345678`, `00000000000000000000000000001.23`, `1234567890123456789012345678` all still accepted).
4. Add 3-surface parity tests in `src/features/ledger/setup/__tests__/setup-surfaces.test.ts` asserting MCP `previewLedgerSetup`, REST `POST /api-gateway/v1/ledgers/preview`, and GraphQL `previewLedgerSetup` (plus `createLedger` before calling `checkSetupFiles` or creating a repo) all reject oversized setup amounts with `VALIDATION_FAILED` on `setup`.
