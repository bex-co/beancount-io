# A `PIVOT BY` whose pivot column has exactly two values labels both value columns with the SELECT expressions: `month(date)` and `sum(number)` where stock prints `7` and `8`, on MCP, REST and GraphQL

**Minor · ledger (`src/features/ledger/service/ledger-shell-service.ts`, `bql-select-aliases.ts`) · 20–30m · A1.** Found by `/loopx w31` routine `mcp-qa` on 2026-11-27, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`), with an unpinned read/write QA key on the synthetic `mcp-agent-eval` ledger (its text is `backend-cluster/backend-v2/evals/mcp-agent/fixtures/main.bean`). Reproduced at HEAD `035866c23` through `LedgerShellService` on the same text. Read-only.

A pivot is how an agent compares periods side by side, and two periods (this month and last, this year and last) is the commonest case. With two pivot values, the hosted answer drops which column is which period.

**Repro.** `runBqlQuery`, `runBqlQueryStructured`, REST `POST /api-gateway/v1/ledgers/{owner}/{name}/query` and GraphQL `queryShell` all answer alike:

```sql
SELECT account, month(date), sum(number) WHERE account ~ '^Expenses:Food' GROUP BY 1, 2 PIVOT BY 1, 2
```

| | columns |
| --- | --- |
| hosted | `account/month(date)`, `month(date)`, `sum(number)` |
| stock beanquery 0.2.0, `bea query` | `account/month(date)`, `7`, `8` |

The values are right (Groceries 120.40 in July, 180.85 in August). Only the headers are wrong.

- With the bare column `month` instead of `month(date)`, the headers read `account/month`, `7`, `sum(number)`: the last value column loses its label.
- **Controls.** The same query with `sum(number) AS total` reads `7`, `8`. Widened to `^Expenses`, the pivot has three months and reads `2`, `7`, `8`. The raw engine (`@rustledger/wasm` 0.24.0) names the columns correctly in every case.

**Cause.** `withSourceHeaders` (`ledger-shell-service.ts:88`, from w23/216, `442fadd72`) renames each unaliased expression column after its SELECT-list text, by position. Its comment says a PIVOT keeps the engine's names, but the only guard is `headers.length !== result.columns.length`. A pivot over N items has 1 + (distinct pivot values) columns, so with N − 1 values the counts match and the rename runs. `sourceSelectHeaders` (`bql-select-aliases.ts:81`) gives up only on `*` or a statement with no SELECT list.

**Fix.** A statement with a top-level `PIVOT BY` keeps the engine's column names. Either `sourceSelectHeaders` returns `undefined` when a depth-0 `pivot` word follows the list (it already finds clause words), or `withSourceHeaders` checks for it. The non-pivot renames of w23/216 stay as they are. Add a `bql-source-select-headers.test.ts` case and a shell-service case for the two-value pivot, with an alias and a three-value control. Revert the fix and watch them fail.

**Blast radius.** One producer feeds every surface: MCP text and structured results, REST JSON and `text/plain`, GraphQL `queryShell` and `queryShellText`, so the dashboard's Query page shows the same headers. No backend-v2 change is needed.

**Dedupe.** Searched `.pm/**` for `PIVOT`, `withSourceHeaders` and `sourceSelectHeaders`. w23/216 introduced the rename, and nothing tests it under PIVOT. w23/022 records two other pivot differences (the engine leaves pivot keys and rows unsorted, and applies LIMIT after pivoting) as upstream portability notes. Those are separate and out of scope here.
