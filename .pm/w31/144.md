# The `tags` and `links` vocabularies leave out a note's tags and links: `#dispute` on a `note` matches the journal filter but never appears in `tags`, `attributes` or `getLedgerContext`, on MCP, REST and GraphQL

**Minor · ledger (`src/foundation/rustledger/directives-report.ts`) · 15–25m · A1.** Beancount 3 notes carry tags and links: `2026-03-05 note Assets:Cash "dispute filed" #dispute ^case-42`. w21/655 restored them in the ledger service, because `@rustledger/wasm` 0.24.0 drops them, so the journal filters `#dispute`, `^case-42`, `tag:` and `link:` match the note. The vocabulary reads do not. `beancount://{owner}/{name}/tags`, `…/links` and `…/attributes`, `getLedgerContext`'s `attributes`, REST `GET …/tags` / `…/links` / `…/attributes`, and GraphQL `getLedgerTags` / `getLedgerLinks` / `getLedgerAttributes` list the tags and links of transactions and documents only. An agent that asks the ledger which tags it uses, so it can tag a new entry the same way or build a filter, never learns that `#dispute` exists. Yet the filter it would write with that tag works. The dashboard's tag and link suggestions come from the same lists. Fava 1.31 lists every tag and link on any entry that carries them.

## Repro (synthetic)

Append to a clean ledger whose existing entries carry no tags or links:

```beancount
2026-01-02 open Assets:Qa:Wallet USD
2026-02-01 * "qa" "fund" #qa-trip ^qa-link
  Assets:Qa:Wallet       50.00 USD
  Assets:Bank:Checking  -50.00 USD
2026-03-05 note Assets:Qa:Wallet "qa note" #qa-notetag ^qa-notelink
```

1. `resources/read beancount://<owner>/<name>/tags` → `["qa-trip"]`. `…/links` → `["qa-link"]`.
2. `…/attributes` and `getLedgerContext` → `attributes.tags: ["qa-trip"]`, `attributes.links: ["qa-link"]`.
3. REST `GET /api-gateway/v1/ledgers/<owner>/<name>/tags` and `…/links` return the same bodies, and so do GraphQL `getLedgerTags(ledgerId:)` and `getLedgerLinks(ledgerId:)`.
4. Control, same ledger: `listLedgerEntries` with `filter: "#qa-notetag"`, `"^qa-notelink"` or `"tag:qa-notetag"` → `total: 1`, the note. `getEntryContext` on it returns a `slice` that shows both tokens.
5. Control, same text: `bean-check` (Beancount 3.2.3) passes, and the loaded `Note` has `tags={'qa-notetag'}` and `links={'qa-notelink'}`. Fava 1.31's `/api/ledger_data` lists `tags: ["qa-notetag", "qa-trip"]` and `links: ["qa-link", "qa-notelink"]`.

## Root cause

`collectAttributes` (`backend-cluster/ledger/src/foundation/rustledger/directives-report.ts:98`) builds the tag and link sets in a `switch` over the directive type. It reads `transaction` (`:113`) and `document` (`:132`), and every other type falls to `default` (`:137`). A note's tags and links are on the directive: `mergeSourceSyntax` (`engine.ts:457`, called at `:792`) puts them there from the source, as w21/655 did. They are simply never read. The journal filter reads them through `directiveStringList` (`directive-filter.ts:726`), which covers `transaction`, `document` and `note`. `loadAttributes` (`ledger-data-service.ts:261`) feeds every vocabulary read, and REST, GraphQL and MCP all reach it through the ledger service. So one change fixes all three surfaces.

## Fix

In `collectAttributes`, read a note's tags and links the way a document's are read. Use the `SourceSyntax` fields `mergeSourceSyntax` sets, as `directiveStringList` does, or call that helper itself so the filter and the vocabulary share one rule for which directives carry tags. Sorting and de-duplication stay as they are.

## Done when

- With the repro ledger, `tags` reads `["qa-notetag", "qa-trip"]` and `links` reads `["qa-link", "qa-notelink"]` on the MCP resources, REST, GraphQL and `getLedgerContext.attributes`, matching Fava 1.31's ledger data.
- A tag that only `pushtag` puts on a note (`pushtag #qa-pushed` … note … `poptag #qa-pushed`) is listed too, as Beancount 3.2.3 applies it.
- A ledger test (`directives-report.test.ts`, or a real-engine case beside w21/655's in `scripts/verify-rustledger.ts`) asserts both cases and fails with the change reverted.

## Adjacent, not in scope

The journal's note row (`journal-serialize.ts:438`, `JournalNotePublic` in `idl/beancount-ledger.openapi.json`) has no `tags` or `links` fields. So `listLedgerEntries` with `#qa-notetag` returns a note that shows no tag. w21/655 left that out on purpose, as a contract change across `idl`, ledger and backend-v2, and it is not part of this fix.
