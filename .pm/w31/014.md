# A pad's padding leg is never checked: a pad whose source sits in the padded account's own subtree passes a failing balance, and a padding amount outside the source account's currencies passes, on every surface

**Major · ledger (pad validation) · 45–60m · A1.** A balance assertion that fails reads as passing, which is the same class as w21/675 and w21/720. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. `main.bean` was restored byte for byte afterwards (blob `f1a0b83c`), and the check is clean.

Each fixture below is appended to a ledger that opens its accounts on 2026-09-01. Each one passes the hosted check and fails stock Beancount 3.2.3 `bean-check`:

| Fixture | Hosted (`newErrors`, `checkLedger`) | `bean-check` 3.2.3 |
| --- | --- | --- |
| `2026-09-03 pad Assets:A Assets:A` then `2026-09-04 balance Assets:A 100 USD` | none | `Balance failed for 'Assets:A': expected 100 USD != accumulated 0 USD` |
| `pad Assets:A Assets:A:Sub` (source is a child) then `balance Assets:A 100 USD` | none | `Balance failed … accumulated 0 USD` |
| `pad Assets:A Assets:B` and `pad Assets:B Assets:A` on one day, then `balance Assets:A 100 USD` and `balance Assets:B 50 USD` | none | two `Balance failed` errors |
| `open Equity:Opening-Balances USD`, `open Assets:EurBank EUR`, `pad Assets:EurBank Equity:Opening-Balances`, `balance Assets:EurBank 250.00 EUR` | none | `Invalid currency EUR for account 'Equity:Opening-Balances'` |
| `open Equity:Eur EUR`, `pad Assets:A Equity:Eur`, `balance Assets:A 100 USD` | none | `Invalid currency USD for account 'Equity:Eur'` |

- **Repro (live).**
  1. `appendLedgerText` and `addLedgerEntries` with `dry_run: true` answer `valid: true`, "No new bean-check errors", for every row above. So do REST `POST …/directives/text` and `POST …/entries` with `dryRun: true`.
  2. Committing the self-pad row (`addLedgerEntries`, commit `3f93e407`, later reverted) leaves `checkLedger` and the `errors` resource at `[]`.
  3. On that committed ledger, BQL `SELECT date, flag, account, position, balance WHERE account = 'Assets:QA20261115:PadSelf'` returns the padding as `+100 USD` and `-100 USD` on the same account. The running balance is `{}`.
  4. `register/Assets:QA20261115:PadSelf` and `trial-balance` show the account at zero, next to the balance row asserting 100 USD.
  5. So the ledger reports itself clean while it contradicts its own assertion, and `bea check` or `bean-check` on the downloaded file fails.
- **Controls.** Ordinary pads match stock: a pad from another account, an unused pad (E2003), and a pad and balance on the same day (E2001 plus E2003). An ordinary transaction posting EUR to a USD-only account is refused ("Invalid currency EUR not allowed in account …"). Only the generated padding transaction escapes both checks.
- **Not deployment lag.** HEAD's engine gives the same result. `parseLedgerFilesInProcess` (`backend-cluster/ledger`, `@rustledger/wasm` 0.24.0, run under ts-node in `node:22-bookworm-slim`) returns no errors for all five fixtures. Raw `ledger.getErrors()` returns none either. `expandPads()` does generate the padding, for example `Assets:A 100 USD | Assets:A -100 USD` and `Assets:EurBank 250.00 EUR | Equity:Opening-Balances -250.00 EUR`.
- **Cause.**
  - rustledger checks a balance that follows a pad as if the pad filled the account to the asserted amount. It never sums the padding's source leg, which can land in the same subtree. It also never validates that leg against the source account's `open` currencies.
  - The service takes the engine's verdict as it is. `engine.ts:226` calls `expandPads()`, `:864` calls `dropPaddingWithinTolerance`, and `:873` calls `errorsHiddenByUnusedPads`. After that, `:902` merges the padding into the stream that BQL and every report read. `pad-tolerance.ts` and `pad-recheck.ts` handle tolerance and unused pads, but neither handles where the padding lands.
- **Fix.** In `backend-cluster/ledger`, once the kept padding is final:
  - Check each padding posting against its account's `open` currencies, and report stock's `Invalid currency <C> for account '<source>'` at the pad's file and line.
  - When a padding transaction posts both legs into the subtree of a balance assertion it serves, re-check that assertion against the merged stream, as stock runs `balance.check` after the pad plugin. This covers a source equal to the account, a descendant source, and mutual pads that later move the account.
  - Every surface reads the shared snapshot, so REST, GraphQL and MCP (`checkLedger`, the `errors` resource, and every write preview's `valid`) change together. No API shape changes.

**Done when:**

- All five fixtures report the errors `bean-check` 3.2.3 reports, at the pad or balance line, through `parseLedgerFiles`.
- The same fixtures, appended with `dry_run`, answer `valid: false` on MCP and REST, and their commits are refused `VALIDATION_FAILED` unless `allowInvalid`.
- The controls above keep their results, and w21/135, w21/675, w21/705 and w21/720's fixtures keep theirs.
- A `pad-*.test.ts` case and a `yarn verify:rustledger` check cover the self pad and the currency case, and fail with the fix reverted.
