# `moveEntrySources` reads an error the moved entry already carries as new: the preview says `valid: false` with `errorsBefore: 1, errorsAfter: 1`, and the commit is refused `VALIDATION_FAILED`, so the split-by-year recipe stops on any ledger whose entries have an error (the entry-move twin of w1/236 and w31/114)

**Minor · ledger (`src/features/ledger/service/ledger-journal-service.ts`) and backend-v2 (`src/features/ai-agent/api/mcp-source-slices.ts`) · 30–45m · A1.** `docs/mcp.md` promises that "Errors the ledger already had never block". Both copies of the "which errors are new" rule match an error on its message and its file. A file rename carries a `FileRenames` map so that its errors go with it (w1/236). An account rename carries its account mapping (w31/114). An entry move carries neither. So when an entry that already has an error moves to `toPath`, the same error now names `toPath` instead of the file it came from. It reads as new.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), `qa-20261127-move.bean` is gone, and the check shows 0 errors. Read against HEAD `158bc2656`: the code below is unchanged there, so this is not deployment lag.

## Repro

1. On a ledger whose `main.bean` holds `2026-01-01 open Assets:Cash USD`, add an entry that posts to an account the ledger never opens. Use `allowInvalid` so it commits:

   ```beancount
   2026-08-30 * "qa-move" "posting to an unopened account"
     Expenses:Qa:Unopened   5.00 USD
     Assets:Cash           -5.00 USD
   ```

   `checkLedger` now reports one error, `Account Expenses:Qa:Unopened was never opened` (`E1001`), at the entry's line in `main.bean` (line 90 on the QA ledger).
2. Follow the split recipe in `docs/mcp.md` ("Recipe: split a ledger by year"). `listLedgerEntries` with `time: "2026-08-30"`, `directiveTypes: ["Transaction"]` and `include_source: true` gives the entry's `entry_hash` and `source.sha256sum`. Then call `moveEntrySources` with those, `toPath: "qa-move.bean"`, `includeFrom: "main.bean"` and `dry_run: true`.

## Expected

The preview reports `valid: true` with `newErrors: []`. The commit goes through without `allowInvalid`, and afterwards the ledger has the same one error, at its line in `qa-move.bean`. That is what the move contract (w1/m45: "The ledger's balances and errors are exactly what they were") and the preview rule both say.

## Actual

| call | result |
| --- | --- |
| MCP `moveEntrySources` `dry_run: true` | `valid: false`, `errorsBefore: 1`, `errorsAfter: 1`, `newErrors: [{message: "Account Expenses:Qa:Unopened was never opened", source: "qa-move.bean:1", code: "E1001"}]`; summary "1 new bean-check error" |
| REST `POST …/entries/move` `dryRun: true` | `200`, the same `errorsBefore: 1`, `errorsAfter: 1`, one `newErrors` item, `valid: false` |
| GraphQL `moveLedgerEntrySources` `dryRun: true` | the same, `valid: false` |
| MCP commit, no `allowInvalid` | `VALIDATION_FAILED`: "moving these entries would introduce 1 new bean-check error … (qa-move.bean:1)". The hint says the move "would break the ledger". Nothing is written. |
| MCP commit with `allowInvalid: true` | commits, but its result again says "1 new bean-check error", with `errorsBefore: 1, errorsAfter: 1` |
| `revertCommit` on that move, preview and commit | "1 new bean-check error … (main.bean:90)": the undo reports the same error as new, moving back |

Controls, in the same window: moving a clean entry (`FARMERS MARKET`, 2026-08-28) to the same `toPath` previews `valid: true` with `newErrors: []`, while the error stays in `main.bean`. `deleteEntrySource` on the broken entry previews `errorsAfter: 0`, `valid: true`. Moving both entries together previews the broken one's error as new at `qa-move.bean:5`.

The error count never changes, yet `newErrors` holds one item. An agent that follows the recipe ("go on only when `validation.valid` is `true`") and the prompts' ground rule ("never pass allowInvalid") cannot move a year that holds any entry with an error. The errors include an unbalanced or unbookable transaction, a posting to an unopened or closed account, and a lot error. Those are often the ledgers someone is reorganising to clean up.

## Root cause

- **ledger.** `moveSourceSlices` (`ledger-journal-service.ts:1429`) gates through `projectWriteErrors` (`:741`, called at `:1531`). That diffs the projection with `newLedgerErrors` (`new-ledger-errors.ts:62`), which keys each error on `withoutEntryTag(message)` plus `source.filename` (`:66`). Nothing maps a baseline error inside a moved slice to `toPath`. `projectWriteErrors` already receives each file's cuts as `edits`, so it knows which lines left which file.
- **backend-v2.** For a commit, MCP re-checks with `withPostWriteValidation` (`mcp-source-slices.ts:159`). That diffs by message and file through `diffBeanCheckErrors` and passes no `renames`, although the function takes them (`write-validation.ts:72`, `FileRenames` in `bean-check-errors.ts:163`). So a forced move's result reports the moved error as new too. `revertLedgerCommit` (`ledger-workflow.ts:1729`) projects an undo without a file map, so undoing a move reports the same error as new in the other direction.

## Fix

A baseline error located inside a moved entry is the same error once it moves. Before the diff, re-key it from its source file to `toPath`.

- In the ledger, map each `before` error whose `source` falls inside a moved slice's line range (its file, `startLine`–`endLine`) to `toPath`, and then call `newLedgerErrors`. The per-message count stays as it is, so an error the move really adds still counts: a second broken entry, or an error outside the moved slices.
- In backend-v2, have MCP's move commit report the ledger's own verdict for the commit, or pass the same mapping to `withPostWriteValidation`. Then the preview and the commit result agree.
- For a revert, map in reverse when the reverted commit is a move. Otherwise, write down in `docs/mcp.md` that a revert's verdict can name a moved error.
- MCP, REST and GraphQL all relay the ledger's projection, so the ledger fix covers all three previews and refusals. Parity: no input or output shape changes.

## Done when

On the repro ledger, `moveEntrySources` with `dry_run: true` returns `valid: true` and `newErrors: []` on MCP, REST and GraphQL. The same call without `dry_run` or `allowInvalid` commits once. `checkLedger` afterwards shows the same single error at `qa-move.bean`, and MCP's commit result says "No new bean-check errors". A move that adds a second broken entry, or a move that breaks a balance assertion elsewhere, is still refused. A ledger unit case in `move-source-slices.test.ts` covers the known error moving with its entry, and fails with the fix reverted.
