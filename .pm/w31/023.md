# Rename and delete guards ignore includes written in a non-`.bean` file, so `updateIncludes` and `removeIncludes` cannot fix them, and a moved `.txt` keeps its relative includes

**Trivial · backend-v2 (include guards) · 20–30m · A1.** Found in the same run as `w31/022`, on the same ledger and with the same fixture. Here the fixture was committed with `allow_invalid`, so `main.bean` includes `qa/list.txt`, which includes `y.bean` relative to its folder. Every call below was a `dry_run`, and the probe files were deleted afterwards. This is independent of `w31/022`: here the include really does dangle, so the gate's error is true. The gap is that the guards meant to handle it never see it.

- **Repro.**
  - `renameLedgerFile {oldPath: "qa/y.bean", newPath: "qa/z.bean"}`, with or without `updateIncludes: true`. It is not refused, `updatedIncludes` is `[]`, and the preview reports `newErrors` `Included file not found: y.bean` (`qa/list.txt:1`). The commit would be `VALIDATION_FAILED`. The tool's description says it "refuses when oldPath is still included unless updateIncludes rewrites those lines".
  - `deleteLedgerFiles {files: [{path: "qa/y.bean"}]}`, with or without `remove_includes: true`, gives the same error. It never gives the guard's `BAD_USER_INPUT` naming the includer, and the include line stays.
  - `renameLedgerFile {oldPath: "qa/list.txt", newPath: "qa/sub/list.txt", updateIncludes: true}` rewrites the line in `main.bean`. The moved file's own `include "y.bean"` is not rewritten to `../y.bean`, so the preview reports `Included file not found: y.bean` (`qa/sub/list.txt:1`).
  - **Control:** renaming `qa/list.txt`, whose includer `main.bean` is a `.bean` file, is refused naming `main.bean`. With `updateIncludes: true` the rename rewrites that line and previews `valid: true`.
- **Cause.**
  - `scanLedgerBeanFiles` (`backend-cluster/backend-v2/src/features/ledger/utils/include-references.ts:91`) collects only `.bean`/`.beancount` files as includers. Rename and both delete paths use it.
  - `movedIncludesContent` (`src/features/ledger/workflow/ledger-workflow.ts:1862`) skips a moved file that is not `.bean`, because `w23/056` scoped itself to `.bean` files.
  - The ledger loads any file an include reaches, whatever its extension (`backend-cluster/ledger/src/foundation/rustledger/file-map-loader.ts:566`).
- **Fix.** Treat as includers the ledger's source files, meaning the include closure `getLedgerContext` already lists, rather than matching an extension. Do the same for the moved-file rewrite. Scanning every text file would not do: a README line `include "y.bean"` would then refuse renames. The workflow is shared, so REST, GraphQL and MCP change together.
- **Done when:** each of the three repros either refuses with the guard's message or, under `updateIncludes`/`removeIncludes`, rewrites or drops the `.txt` include line and previews `valid: true`. Cases in `rename-parity` and `ledger-repo-service` tests fail with the fix reverted.
- **Dedupe:** `w23/029`, `w23/056` and `w23/m4` built these guards for `.bean` includers, and none of them mentions other extensions. Searched `.pm/**` for "non-`.bean`", `scanLedgerBeanFiles` and "includer".
