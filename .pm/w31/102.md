# A file delete with `removeIncludes` gives a new error in the including file at its line after the include is dropped, in both the preview and the commit refusal, so `main.bean:89` names a blank line, on MCP and REST

**Minor · backend-v2 (`src/features/ledger/utils/`) · 30–45m · A1.** `deleteLedgerFiles` with `remove_includes` (REST `DELETE …/files/{path}` with `removeIncludes`) rewrites each file that includes the deleted one, dropping its `include` line. That shifts every later line of that including file up by one. When the delete adds a bean-check error further down that file, both the `dry_run` preview and the commit refusal give the error's line from the rewritten file. The caller only has the file as it stands. w5/1202 settled that a delete refusal names the entry that still uses the account at its current location, and its resolution says "Delete refusals map diagnostics to the current file". That holds for entry deletes, not for file deletes.

## Repro (live)

1. Build the fixture with two QA commits:
   - `95b07597`: `createLedgerFiles` makes `qa-20261126-incl.bean` holding `2026-01-01 open Assets:Qa-20261126-Incl USD`.
   - `a6de3ef5`: `updateLedgerFiles` puts `include "qa-20261126-incl.bean"` at `main.bean` line 7 and `2026-08-31 balance Assets:Qa-20261126-Incl 0.00 USD` at line 90, with line 89 blank.

   `checkLedger` is clean.
2. `deleteLedgerFiles {files: [{path: "qa-20261126-incl.bean"}], remove_includes: true, dry_run: true}` returns `validation.valid: false`, `newErrors: [{message: "Account Assets:Qa-20261126-Incl was never opened", source: "main.bean:89", code: "E1001"}]`.
   - REST `DELETE /api-gateway/v1/ledgers/{owner}/{name}/files/qa-20261126-incl.bean` with `{removeIncludes: true, dryRun: true}` returns the same `source`.
3. The same call without `dry_run` is refused `VALIDATION_FAILED`: "… was never opened (main.bean:89)". In `main.bean` as it stands, line 89 is blank. The `balance` is at line 90.

GraphQL `deleteLedgerFile` has no preview and no bean-check gate (w1/210, blocked on an owner decision), so it has nothing to compare here.

## Cause

- `stripIncludeLines` (`backend-cluster/backend-v2/src/features/ledger/utils/include-references.ts:245-261`) drops the include lines and does not record which lines went.
- `planIncludeRemovals` (`:275`) hands the rewritten text to the MCP tool (`src/features/ai-agent/tools/edit-ledger-files-tool.ts:451-467`) and the REST handler (`src/features/ledger/api/rest/v1/files-handler.ts:341-381`) as a whole-file `replace`/`update`.
- `gateFileWrite` (`src/features/ledger/utils/file-write-gate.ts:80-125`) reports the errors bean-check finds in that rewritten text as they are. `toWriteValidation` already maps paths back for renames (`renames`), but nothing maps line numbers back for removed lines.

## Fix

Have the include removal report the lines it dropped from each including file (1-based, in the current file). Map each new error in that file back the way the ledger service's `deletedLines` does for entry deletes (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:743-756`). Apply it to the preview and to the refusal alike.

A committed `allow_invalid` delete may keep the post-delete line, because after the commit that is where the error lives.

MCP `deleteLedgerFiles` and REST `DELETE …/files/{path}` change together, and no response shape changes. GraphQL follows when w1/210 adds its gate.
