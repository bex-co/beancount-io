# A dry run with a `requestId` that already committed a different write answers `valid: true`, and the same call with `dry_run: false` is refused `VALIDATION_FAILED`, on MCP, REST and GraphQL (gap in w1/195)

**Minor · backend-v2 (`src/features/ledger/utils/entry-write-idempotency.ts`) · 30–45m · A1.** `docs/mcp.md` "Retry-safe entry writes" promises that a dry run "refuses an id outside 1–200 characters exactly as the commit does, so a `valid: true` preview never carries an id its commit would reject (w1/195)". "The preview rule" tells an agent to approve a preview only when `valid` is `true`, then send the identical call with `dry_run: false`. A preview does not check whether its `requestId` is already taken. If the id committed a different write in the last 24 hours, the preview says `valid: true` and the commit is refused `VALIDATION_FAILED` "requestId was already used with a different write request". If the id committed the same write, the preview says "Would add 1 directive", but the commit writes nothing and replays the first result.

`runIdempotentEntryWrite` checks the id's format and then returns `write()` for a preview (`entry-write-idempotency.ts:101`), before it builds the key or reads the store. The fingerprint comparison that refuses the commit (`:121`) never runs for a preview. Both callers pass the preview flag: `addBulkEntries` (`ledger-entry-service.ts:524`–`531`) and `appendDirectiveText` (`:559`–`566`). The fingerprint already leaves `dryRun` out, so a preview and its commit hash the same. The key is `userId` + `ledgerId` + `requestId`, and the operation is part of the hash, so an `addLedgerEntries` preview that reuses an `appendLedgerText` id fails the same way.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27. Target: `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). Credential: an unpinned read/write `bcio_` key on the QA account. Writes went only to the QA ledger `<qa-owner>/mcp-agent-eval`, and `main.bean` was restored byte for byte afterwards (sha256 checked, `checkLedger` clean). `entry-write-idempotency.ts` has not changed since `7e7f9caf1` (w31/044), so production runs this code.

## Repro (synthetic, any ledger the key can write)

Let `R` be a fresh id, `A` one valid transaction text and `B` another (for example the same posting with a different narration).

1. `appendLedgerText {text: A, requestId: R}` commits: `ok: true`, "Added 1 directive to main.bean", with a commit sha.
2. `appendLedgerText {text: B, requestId: R, dry_run: true}` returns `ok: true`, "Would add 1 directive to main.bean. No new bean-check errors.", `validation.valid: true`.
3. `appendLedgerText {text: B, requestId: R}` (step 2's call without `dry_run`) returns `isError: true`, `VALIDATION_FAILED` "Validation failed for requestId: requestId was already used with a different write request". Nothing is written.
4. `addLedgerEntries {entries: [<any valid transaction>], requestId: R, dry_run: true}` also returns `valid: true`. Its commit would be refused the same way, because the id is keyed without the operation.
5. `appendLedgerText {text: A, requestId: R, dry_run: true}` (step 1's call as a preview) says "Would add 1 directive", a second copy. `appendLedgerText {text: A, requestId: R}` then writes nothing and returns step 1's result with step 1's commit sha.

## Controls

- **REST.** `POST /api-gateway/v1/ledgers/{owner}/{name}/directives/text` `{text: B, requestId: R, dryRun: true}` returns `200` "Would add 1 directive to main.bean" with a diff. The same body without `dryRun` returns `400 VALIDATION_FAILED` with the same message.
- **GraphQL.** `appendLedgerText(ledgerId, text: B, requestId: R, dryRun: true) { message valid }` returns `valid: true`. With `dryRun: false` it returns a `VALIDATION_FAILED` error with the same message and `data: null`.
- **Format bounds (w1/195).** A preview with `requestId: ""` or 201 characters is already refused exactly as its commit is.

## Fix

Have a preview look up its id without claiming it. Add a read-only `peek(key)` to `IdempotencyStore` (a Redis `GET`; `undefined` when the store is down, like the other methods), and call it in the `preview` branch after `assertRequestId`:

1. A record with a different `requestHash`: throw the same `ValidationError("requestId", "requestId was already used with a different write request")` the commit throws.
2. A `done` record with the same hash: the commit would replay it, so the preview should say so instead of projecting a second copy. Either return the stored result marked as a replay, or keep the projection and add a summary line such as "requestId … already wrote this request; the commit returns that result and writes nothing".
3. An `in-progress` record or an unavailable store: run the preview as today. The first case is transient, and the second fails open as the commit does.

This keeps "a dry run is never deduplicated": the preview still records nothing. One helper serves `addLedgerEntries`, `appendLedgerText` and their REST (`POST …/entries`, `POST …/directives/text`) and GraphQL (`bulkEntries`, `appendLedgerText`) twins, so all six change together. `insertReceiptTransaction` has no preview and is unaffected. Update the w1/195 sentence in `docs/mcp.md` "Retry-safe entry writes" to say the preview also refuses an id already used for another write.

## Done when

- Step 5's preview says the commit would replay the first result, and does not claim it would add the directive again.
- A preview still stores nothing: a preview with a fresh id followed by its commit writes once, and the commit is not replayed from the preview.
- `entry-write-request-id.test.ts` covers a preview after a committed different request, a preview after a committed identical request, and a preview while the store is down. The first two fail with the fix reverted.
