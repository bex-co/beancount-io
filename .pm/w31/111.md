# `docs/mcp.md` still says a client connected only through MCP OAuth "cannot fetch an archive larger than the cap", which w23/026's streaming route made untrue

**Minor · backend-v2 docs (`docs/mcp.md` § Asset and archive URL discovery) · 10–15m · A1.** w23/026 (`df1101ace`, 2026-11-01) added `GET /api-gateway/mcp/archive/{owner}/{name}/{archive}`. It streams an archive of any size to the credential an MCP client already holds. ADR 0007's 2026-10-31 amendment records the owner's choice of this route over "use an API key". The commit rewrote the first paragraph of the section, which now says `archive-download-url` gives MCP callers `{issuer}/api-gateway/mcp/archive/{owner}/{name}/main.zip`, fetched "with `Authorization: Bearer` and the same MCP credential … or a personal API key, at any archive size", and that a browser session is refused there.

The cap paragraph below it (`docs/mcp.md:993-996`) still has the w23/023 wording:

> The URL that resource returns streams at any size, but only with a personal API key or browser session, as above; a client connected only through MCP OAuth cannot fetch an archive larger than the cap.

That sentence contradicts the section's own first paragraph, the ADR amendment, and what the server tells agents. A host connected only through MCP OAuth, such as Claude, ChatGPT or Cursor, reads it and concludes it cannot download a ledger above 8 MiB. It can.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26.

## Evidence (live, `https://beancount.io`, `beancount-mcp 1.0.0`, protocol `2025-11-25`)

- `resources/read beancount://<qa-owner>/mcp-agent-eval/archive-download-url` returns `{"downloadUrl":"https://beancount.io/api-gateway/mcp/archive/<qa-owner>/mcp-agent-eval/main.zip"}`.
- A `GET` of that URL with `Authorization: Bearer <the same bcio_ key>` returns `200` `application/octet-stream`, `cache-control: private, no-store`, 1127 bytes starting `PK`. Anonymous, it returns `401` with `WWW-Authenticate: Bearer resource_metadata="https://beancount.io/.well-known/oauth-protected-resource"`.
- The served `archive/{archive}` template description says: "A larger archive is refused; read `beancount://{owner}/{name}/archive-download-url` for an HTTP URL that streams it at any size with the same MCP credential." Its over-cap hint (`mcp-resources.ts:154`) says the same.
- No MCP OAuth token was available to this run, so the OAuth fetch itself is unverified live. The route accepts the MCP audience by design (`df1101ace`, ADR 0007 amendment), and the API key's `200` above uses the same route.

## Fix

Rewrite the cap paragraph's last sentence to match the route. The URL `archive-download-url` returns to an MCP caller streams at any size with the caller's MCP credential, OAuth or API key, while a browser session is refused there. The 8 MiB cap applies only to the `archive/{archive}` blob. Docs only, with no code or response change. Grep for any other copy of "cannot fetch an archive" first. Today `docs/mcp.md` has the only one. The public website may quote the guide; per the root `AGENTS.md`, that copy is the website owner's to follow.

## Dedupe

w23/023 (resolved 2026-10-20, `ba1e497aa`) wrote the sentence when the fallback really was REST-only. w23/026 (`df1101ace`) shipped the streaming route and updated the paragraph above, but not this one. Searched `.pm/**` for "cannot fetch an archive", "only through MCP OAuth" and "personal API key or browser session": only those two done items match. No open item covers it.
