# `appendLedgerText` refuses valid text that pushes one `pushmeta` key twice: "`popmeta k:` has no matching pushmeta", on MCP, REST and GraphQL

**Trivial · backend-v2 (directive text stack) · 20–30m · A1.** Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`, run 23, the post-deploy regression sweep of the w31 fixes) on 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`), with an unpinned read/write `bcio_` key. Dry runs only, on the designated QA ledger `<qa-owner>/mcp-agent-eval`.

## Repro (live)

`appendLedgerText {path: "main.bean", dry_run: true, text}` with:

```beancount
pushmeta qa-k: "outer"
pushmeta qa-k: "inner"
2026-09-10 * "T1A" "inner scope"
  Expenses:Food:Coffee   1.00 USD
  Assets:Cash
popmeta qa-k:
2026-09-11 * "T1B" "outer scope"
  Expenses:Food:Coffee   1.00 USD
  Assets:Cash
popmeta qa-k:
```

The answer is `BAD_USER_INPUT` "line 10: `popmeta qa-k:` has no matching pushmeta: popmeta qa-k:". REST `POST …/directives/text` with `dryRun: true` answers 400 with the same message. GraphQL `appendLedgerText(dryRun: true)` answers the same, with `extensions.code: BAD_USER_INPUT`. The same refusal comes back when an entry sits between the two pushes.

**Controls:**

- Stock Beancount 3.2.3 `bean-check` is clean on this text. `bean-query` gives `T1A` `qa-k: "inner"` and `T1B` `qa-k: "outer"`.
- The hosted engine reads the same block, committed into a file, the same way.
- In the same text, nested `pushtag #t` twice, two different tags, two different keys, and an entry's own key inside a `pushmeta` of that key all expand correctly.
- The file-scope side handles same-key nesting already. `w31/015`'s append closes it with two `popmeta` lines and re-pushes `"outer"` then `"inner"`. `w31/016`'s move writes `"inner"`.

## Cause

`TagStack` in `backend-cluster/backend-v2/src/features/ledger/utils/directive-text.ts` keeps one value per key (`private readonly meta = new Map<string, { value; line }>()`, `:134`). A second `pushmeta` of the key overwrites the first (`:159`). The first `popmeta` deletes the key outright (`:160`), so the entries after it lose the outer value, and the second `popmeta` throws (`:161`). Beancount keeps a stack of values per key and pops the latest. So do `openPushes` (`directive-text.ts:600`) and the ledger's `PushScopes` (`source-slice.ts:172`). The map dates from `w23/041`.

## Fix

Keep a list of values per key in `TagStack`. `pushmeta` appends, `popmeta` pops the latest and refuses only when the key has no value left, and `annotate` writes the latest value. Line numbers stay as they are for the never-popped refusal. The one parser serves MCP, REST and GraphQL `appendLedgerText`, so all three change together. No response shape changes.

**Done when:** the repro previews `valid: true`, with `T1A` carrying `qa-k: "inner"` and `T1B` carrying `qa-k: "outer"`, on all three surfaces. A `popmeta` with no value left is still refused. A `directive-text.test.ts` case covers nested same-key pushes and fails with the fix reverted.

Dedupe: searched `.pm/**`, done and blocked included, for `TagStack`, same key, nested pushmeta and "has no matching pushmeta". `w23/041` built the stack. `w31/018` changed only `annotate`. `w31/015` and `w31/016` handle same-key nesting in files, not in appended text.
