# `previewLedgerSetup` and `createLedger` emit invalid year-`0000` directives (`0000-12-31`) when `historyStart: "0001-01-01"` has a `known` opening balance (missing `w5/889` parity across MCP, REST, and GraphQL)

**Minor · backend-v2 (`previewLedgerSetup` / `buildLedgerFiles` in `src/features/ledger/setup/build-ledger.ts`) · 25–35m · A1/A2.** `build-ledger.ts:95-105` (`w21/548`) explicitly accepts `historyStart: "0001-01-01"` and states `// Year 0000 is not a Beancount date and stays refused.` However, when any account in the setup has `openingState: "known"` (whether nonzero like `"100"` or `"0"`), `build-ledger.ts:329` and `:388` compute `dayBefore(historyStart)` (`:60-64`), which subtracts one UTC day from `"0001-01-01"` and returns `"0000-12-31"`. `previewLedgerSetup` emits `0000-12-31 open ...` and `0000-12-31 * "Opening balance"` and reports `validation: { ok: true, errors: [] }` (because `@rustledger/wasm` accepts proleptic year `0000`), and `createLedger` (`ledger-workflow.ts:775-786`) relies on the same builder and `checkSetupFiles`, so it creates a ledger containing year-`0000` directives that stock Beancount / `bean-check` / `bea check` refuse (`year 0 is out of range`) and that backend-v2's own `parseDirectiveDate` / `addLedgerEntries` / `appendLedgerText` reject. CLI `bea init --preset` already fixed this exact boundary in `w5/889` (`.pm/w5/done/889.md`). ## Working controls

- `historyStart: "0001-01-01"` with `openingState: "unknown"` → `isError: false`, `validation: { ok: true, errors: [] }`, opens accounts on `0001-01-01` (valid Beancount).
- `historyStart: "0001-01-02"` with `openingState: "known", amount: "100"` → `isError: false`, `validation: { ok: true, errors: [] }`, opens accounts and posts opening balance on `0001-01-01`, balance assertion on `0001-01-02` (valid Beancount).
- `historyStart: "0000-01-01"` → refused with `VALIDATION_FAILED` (`Invalid history start "0000-01-01"`).

## Root cause

Not deployment lag — present at HEAD `d9290667e`:

`backend-cluster/backend-v2/src/features/ledger/setup/build-ledger.ts:60-64`, `:326-329`, and `:388`:

```ts
const dayBefore = (date: string): string => {
  const parsed = new Date(`${date}T00:00:00Z`);
  parsed.setUTCDate(parsed.getUTCDate() - 1);
  return parsed.toISOString().slice(0, 10);
};
...
const hasKnownOpening = [...selected.values()].some(
  (account) => account.openingState === "known",
);
const openDate = hasKnownOpening ? dayBefore(historyStart) : historyStart;
```

`isCalendarDate("0001-01-01")` returns `true` (`year >= 1`), and when `hasKnownOpening` is `true`, `dayBefore("0001-01-01")` underflows to `"0000-12-31"` without checking that the prior day is still a valid Beancount date (`year >= 1`).

## Fix

In `backend-cluster/backend-v2`:

1. In `previewLedgerSetup` (`src/features/ledger/setup/build-ledger.ts`):
   - When `hasKnownOpening` is `true` and `historyStart === "0001-01-01"` (or `dayBefore(historyStart)` is not a valid calendar date with `year >= 1`), call `fail(...)` (`ValidationError("setup", ...)`) explaining that known opening balances post on the day before `historyStart` and therefore require `historyStart` to be `0001-01-02` or later (and that accounts without a known opening balance can still start on `0001-01-01`).
   - Keep `unknown` and `zero` opening states on `0001-01-01` working unchanged, and keep `0001-01-02` with `known` opening balances opening/posting on `0001-01-01`.
2. Add unit and 3-surface parity regression tests:
   - In `src/features/ledger/setup/__tests__/build-ledger.test.ts`: assert `previewLedgerSetup` and `buildLedgerFiles` refuse `historyStart: "0001-01-01"` with `openingState: "known"` (both nonzero and `"0"`), while accepting `0001-01-01` with `unknown`/`zero` and `0001-01-02` with `known`.
   - In `src/features/ledger/setup/__tests__/setup-surfaces.test.ts` (or `setup-modules-surfaces.test.ts`): verify MCP `previewLedgerSetup`, REST `POST /api-gateway/v1/ledgers/preview`, and GraphQL `Query.previewLedgerSetup` refuse `0001-01-01` + `known` with `VALIDATION_FAILED` and that `LedgerWorkflow.createLedger` refuses it before creating any ledger.
