# `renameAccount` and `renameLedgerFile` lose a race with any concurrent write and answer `CONFLICT` with a hint about an argument they do not take: "retry the write with that `sha`" and "`getEntryContext` returns the entry's current `sha256sum`" (the rename twin of w31/007)

**Minor · backend-v2 (`src/foundation/fava/error-to-domain.ts`, `src/features/ai-agent/api/mcp-errors.ts`, `src/features/ledger/workflow/account-rename-workflow.ts`, `ledger-workflow.ts`) and docs · 30–45m · A1.** w31/007 fixed this for `appendLedgerText` and `addLedgerEntries`. They now re-run on a lost race, and when every attempt loses, the hint names no `sha`. The two rename tools still commit once, with the per-file `sha` they read at the start. Any write that lands on a file they touch in the meantime refuses the whole rename with `CONFLICT`. Even an unrelated `note` on another account does it. The w1/m43 contract (`.pm/w1/blocked/m43/done/t001.md:65`) chose `CONFLICT` for this case. The hint is the bug: it tells the agent to pass an argument the tool does not have. Neither tool takes a file `sha` or an entry `sha256sum`.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The deployment predates `166902dc3` (w31/101), and local HEAD `4e0e5146e` has the same code on every path named below. The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`, and every probe was prefixed `qa-20261127-`. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), the probe file was deleted, and the check showed 0 errors.

## Repro (live)

Setup: append an `open Assets:Qa20261127:Probe3 USD` and two transactions that post to it.

1. Start `appendLedgerText {"text": "2026-08-31 note Assets:Cash \"qa-20261127 note f\"\n"}`. About 600 ms later, before it answers, send `renameAccount {"from": "Assets:Qa20261127:Probe3", "to": "Assets:Qa20261127:Probe4"}`.
   - The append commits.
   - The rename returns `isError: true`, `CONFLICT` "Ledger resource conflict: Ledger file conflict: the ledger changed under a concurrent write; re-read it and retry", with hint "Re-read the file to get its current `sha`, then retry the write with that `sha`."
   - It reproduced 2 of 2 times on MCP. The second time, the concurrent append posted to the account being renamed.
2. Do what the hint says: `renameAccount {…, "sha": "<main.bean blob sha>", "dry_run": true}` returns `BAD_USER_INPUT` "Unrecognized key: \"sha\"".
3. The same race on the other two surfaces gives the same hint:
   - REST `POST /api-gateway/v1/ledgers/{owner}/{name}/rename-account` `{from, to}` returns `409` with `error.metadata.hint` set to the same text.
   - GraphQL `renameLedgerAccount(ledgerId, from, to)` puts the same text in `extensions.hint`.
4. Sending the same rename again on its own commits, and the check stays clean.
5. `renameLedgerFile {"oldPath": "qa-20261127-move.bean", "newPath": "qa-20261127-move2.bean", "updateIncludes": true}`, sent while an append to `main.bean` (its includer) is in flight, returns `CONFLICT` "Ledger resource conflict: the ledger changed under a concurrent write; re-read it and retry". Its hint is the generic entry one: "`getEntryContext` returns the entry's current `sha256sum`, and `listLedgerEntries` with `include_source` returns a page of them." Nothing was renamed. This was raced on MCP only (1 of 1).

Controls on the same ledger. Each concurrent pair below landed both writes, because these tools re-read and re-apply on a lost race:

- two `updateEntrySource` calls on different entries;
- `moveEntrySources` racing an append;
- `appendLedgerText` racing `appendLedgerText` (w31/007).

`revertCommit` gives its own `CONFLICT` hint, which fits ("revert only a commit whose files nothing has changed since").

## Cause

- `AccountRenameWorkflow` (`account-rename-workflow.ts:166-176`) commits through `changeGeneratedFiles` with each file's `sha` and does not retry. The ledger service reports the lost race as `Ledger file conflict: …` (`backend-cluster/ledger/src/api/files.ts:224-227`). `toDomainError` then attaches the hint meant for a stale caller-supplied file `sha` (`error-to-domain.ts:278-281`, w23/178). REST and GraphQL carry that hint as well.
- `renameLedgerFile` (`ledger-workflow.ts:1706`) commits through `changeLedgerFiles`. The ledger's error middleware words that conflict without the `Ledger file conflict:` prefix (`backend-cluster/ledger/src/server/error-middleware.ts:59`). It gets no specific hint, so MCP falls back to the `CONFLICT` category hint, which is about entries (`mcp-errors.ts:98-99`).
- `docs/mcp.md` lists `renameAccount`'s refusals (around line 648) without `CONFLICT`. The `CONFLICT` row of the failure-code table (around line 1923) says to resend a fresh `sha256sum`, which neither tool takes.

## Fix

- Target: when either rename tool loses a race, it answers `CONFLICT` on MCP, REST and GraphQL, and writes nothing. The hint says that another write changed a file the rename touches, and that sending the same call again re-reads the files. It names no `sha`, `sha256sum` or `getEntryContext`.
- A server-side re-run on fresh content, the way `retryLostEntryWriteRace` (`src/features/ledger/utils/entry-write-race.ts:34`) does for entry writes, is also acceptable. If you add it, the exhausted case keeps the hint above.
- Keep the file-`sha` hint for the writes that take a caller `sha`: `updateLedgerFiles` and `deleteLedgerFiles`.
- `docs/mcp.md`:
  - Add this `CONFLICT` to the `renameAccount` refusals, and to the `renameLedgerFile` section.
  - Make the `CONFLICT` failure-code row cover the two renames.
- Tests:
  - A parity case on all three surfaces in which a rival write lands between the rename's read and its commit, for both tools. Assert the code, that no commit was made, and the hint text.
  - Revert the fix and watch the hint assertions fail.

Dedupe: searched `.pm/**` (open, done, blocked) for `renameAccount`/`rename-account`/`renameLedgerAccount` together with `conflict`/`race`/`concurrent`, and for "retry the write with that". w31/007 covers only the two entry writes, and its resolution says "the file-`sha` hint stays on the file writes it fits". w1/m43/t009 tests that a rename is refused, not what the hint says. `git log -S"then retry the write with that"` finds only `8107de3b8` (w23/178).

**Resolved 2026-11-27** — Both renames now commit through `commitRename` (`backend-cluster/backend-v2/src/features/ledger/utils/rename-write-race.ts`): `AccountRenameWorkflow` around `changeGeneratedFiles`, and `LedgerWorkflow.moveLedgerFile` around `changeLedgerFiles`. When the ledger refuses the commit as a lost race, in either of its wordings, the rename answers `CONFLICT` with the message "another write changed a file this rename touches after the rename read it; nothing was renamed". Its hint says to send the same call again, which re-reads the files, and names no `sha`, `sha256sum` or `getEntryContext`. REST (`error.metadata.hint`), GraphQL (`extensions.hint`) and MCP all carry it, since they share the workflows. The w1/m43 contract keeps `CONFLICT`: the rename does not retry by itself. A create over a path that another write took first is still the `File` conflict with its own message and hint. The file-`sha` hint (w23/178) stays on `updateLedgerFiles` and `deleteLedgerFiles`. `rename-write-race-parity.test.ts` drives the real adapters, workflows and repository service over a fake ledger that versions files by content. It lands a rival `note` between the read and the commit, for both tools on all three surfaces and in both of the ledger's lost-race wordings, and asserts `CONFLICT`, no commit, and the hint text. It then resends the call and checks that the rename commits on top of the rival. With the fix reverted, all 12 race cases fail on the hint. Three more cases pin the occupied-target refusal. `docs/mcp.md` adds the `CONFLICT` to the `renameAccount` refusals and to the `renameLedgerFile` section, and the `CONFLICT` failure-code row now covers both renames. Gates in `backend-cluster/backend-v2` on Node 22.22.0: `yarn typecheck`, `yarn test` (507 suites / 13,410 tests), `yarn lint:deadcode`, `yarn format:check`, ESLint on the changed files, and an OpenAPI regeneration with no drift. Production keeps the old hint until backend-v2 is redeployed. Shipped in this commit (`backend-v2`).
