# `revertCommit` (`POST /revert-commit`, `revertLedgerCommit`) returns `INTERNAL_SERVER_ERROR` on every commit; sibling PR merge limit check fails open (missing `{ format: "json" }`)

**Major · backend-v2 (Gitea client reads) · 30–45m · A1.** Every call to undo a real commit — preview or commit, across MCP, REST, and GraphQL — fails with a masked `INTERNAL_SERVER_ERROR`. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, checked against HEAD `86c4abf04`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval` (restored byte-for-byte to pre-run `main.bean` sha256 `77c3a591efd3`, 0 bean-check errors).

## Repro (live)

Reproduced in fresh requests across all three surfaces against `<qa-owner>/mcp-agent-eval`:

1. **MCP `revertCommit` (`dry_run: true`)**:
   ```sh
   node .agents/skills/qa-shared/scripts/qa-mcp.mjs call revertCommit '{"ledger":"<qa-owner>/mcp-agent-eval","sha":"main","dry_run":true}'
   ```
   Actual: HTTP `200`, `isError: true`, `structuredContent`:
   `{"ok":false,"error":{"code":"INTERNAL_SERVER_ERROR","message":"Internal server error","hint":"Retry once. If it persists the failure is server-side and changing the request will not help."}}`
2. **REST `POST /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/revert-commit`** with `{"sha":"main","dryRun":true}`:
   Actual: HTTP `500`, `{"ok":false,"error":{"code":"INTERNAL_SERVER_ERROR","message":"Internal server error"}}`.
3. **GraphQL `revertLedgerCommit(ledgerId: "<qa-owner>/mcp-agent-eval", sha: "main", dryRun: true)`**:
   Actual: `errors[0].extensions.code: "INTERNAL_SERVER_ERROR"`, `message: "Internal server error"`.
4. **All four commit kinds reproduce identically**: tested fresh synthetic commits on `<qa-owner>/mcp-agent-eval` that added a file (`createLedgerFiles`), modified a file (`updateLedgerFiles`), renamed a file (`renameLedgerFile`, both standalone and with `updateIncludes: true`), and deleted a file (`deleteLedgerFiles`). Every single one returned `INTERNAL_SERVER_ERROR` on `revertCommit` with `dry_run: true`.

Expected: `dry_run: true` returns `{ ok: true, result: { sha, subject, message, files, dryRun: true, validation } }` listing the inverse file operations; `dry_run: false` commits the revert on `main` (or returns `CONFLICT` when a later commit modified a touched file).

## Working controls

- `revertCommit` with an unknown SHA (`0000000000000000000000000000000000000000`) returns `NOT_FOUND` cleanly (throws in `findCommit` before reaching `blobAt`).
- `beancount://<qa-owner>/mcp-agent-eval/commit-details?sha=main` returns `200 OK` with metadata, files, and diff (`findCommit` passes `{ format: "json" }` at `commits-service.ts:69`).

## Root cause

Not deployment lag — present at HEAD `86c4abf04`:

1. `backend-cluster/backend-v2/src/features/gitea/client/gitea-api.ts:3096-3102`: the generated `swagger-typescript-api` client initializes `r.data = null` and parses the response body **only** when `format` is supplied (`const responseFormat = format || requestParams.format; const data = !responseFormat ? r : await responseToParse[responseFormat]()...`).
2. `backend-cluster/backend-v2/src/features/gitea/service/gitea-client-factory.ts:14-21`: `createGiteaClient` sets no default `format` in `baseApiParams`. Every other Gitea read in `backend-v2` passes `{ format: "json" }` explicitly (see `ssh-authenticator.ts:70-75`, `pull-request-service.ts:322-327`, `commits-service.ts:69`).
3. `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts:1776-1782`: `undoLedgerCommit`'s `blobAt` calls:
   ```ts
   const found = await gitea.repos.repoGetContents(
     ledgerOwner,
     ledgerName,
     encoded(path),
     { ref },
   );
   const { sha: blobSha, content } = found.data;
   ```
   without `{ format: "json" }`. On every real 200 response from Gitea, `found.data` is `null`, so destructuring throws `TypeError: Cannot destructure property 'sha' of 'found.data' as it is null`, which the transport masks as `INTERNAL_SERVER_ERROR` on MCP, REST, and GraphQL.
4. **Why unit tests missed it**: `backend-cluster/backend-v2/src/features/ai-agent/api/__tests__/fake-ledger.ts:262-278` (used by `revert-commit-parity.test.ts`) ignores the 5th `params` argument of `repoGetContents` and returns `{ data: { sha, content, encoding } }` even when `format` is omitted.

## Blast radius (sibling defect from full caller audit)

Audited every Gitea client call across `backend-cluster/backend-v2/src/` (excluding tests and generated `gitea-api.ts`). Exactly one other call reads `.data` without `{ format: "json" }`:

- `backend-cluster/backend-v2/src/features/gitea/pull-request/service/pull-request-service.ts:663-669` (`assertMergeWithinDirectiveLimit`): calls `client.repos.repoGetPullRequest(owner, repo, prNumber)` without `{ format: "json" }` (unlike `getPRDetails` at line 548, which passes `{ format: "json" }`). `pr` is always `null`, `pr.head?.sha` throws `TypeError`, caught at line 687 (`verdict = { decision: "unknown" }`), so the free-tier directive-limit gate silently fails open on every PR merge.

Every other Gitea client call in `backend-v2` that reads `.data` already passes `{ format: "json" }` or `{ format: "text" }`.

## Fix

In `backend-cluster/backend-v2`:

1. Pass `{ format: "json" }` as the 5th argument to `gitea.repos.repoGetContents` in `src/features/ledger/workflow/ledger-workflow.ts:1776-1781` (and guard `!found.data` -> `null`).
2. Pass `{ format: "json" }` as the 4th argument to `client.repos.repoGetPullRequest` in `src/features/gitea/pull-request/service/pull-request-service.ts:663-667`.
3. Update `src/features/ai-agent/api/__tests__/fake-ledger.ts` (`repoGetContents` and `repoGetAllCommits`) and `pull-request-service.test.ts` to mimic real `gitea-api.ts` behavior: return `{ data: null }` when `params?.format !== "json"`, so the existing `revert-commit-parity.test.ts` and merge directive-limit tests fail if `{ format: "json" }` is ever omitted.
4. Because `LedgerWorkflow.revertLedgerCommit` is shared by MCP `revertCommit`, REST `POST /api-gateway/v1/ledgers/{owner}/{name}/revert-commit`, and GraphQL `revertLedgerCommit`, fixing the workflow restores all three surfaces together with no OpenAPI/schema change.

**Done when:**

- `repoGetContents` in `ledger-workflow.ts` and `repoGetPullRequest` in `pull-request-service.ts` both pass `{ format: "json" }`.
- `fake-ledger.ts` returns `{ data: null }` when `format !== "json"`, and `revert-commit-parity.test.ts` plus a `pull-request-service.test.ts` merge-limit case fail with the `{ format: "json" }` arguments removed and pass with them present.
- `yarn typecheck`, `yarn lint:deadcode`, `yarn format:check`, `yarn test`, and `yarn generate-v1-openapi` pass in `backend-cluster/backend-v2/`.

Dedupe: searched `.pm/**` (open, done, blocked) for `revertCommit`, `revertLedgerCommit`, `repoGetContents`, `repoGetPullRequest`, and `format: "json"`. `w23/done/m42` shipped `revertCommit` with the permissive `fake-ledger.ts` stub; no open or blocked item tracks this defect.
