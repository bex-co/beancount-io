# An entry edit, delete or move that a concurrent write overtakes is checked against the ledger it read and committed onto the one it did not: `updateEntrySource` commits a change bean-check would refuse, skips `VALIDATION_FAILED`, and REST and GraphQL answer `valid: true` for a ledger that is now red, on MCP, REST and GraphQL

**Major · ledger (`src/features/ledger/service/ledger-journal-service.ts`, `src/features/ledger/operations/commit-ledger-files.ts`) · 45–60m · A1.** The four source-slice writes (`updateEntrySource`, `deleteEntrySource`, `deleteEntrySources`, `moveEntrySources`) refuse a change that adds bean-check errors (w21/m1, the preview rule in `backend-cluster/backend-v2/docs/mcp.md`). That check runs on the files as the write loaded them. The commit then reads each file again and applies the same edit to whatever it holds now. A write that lands between the two is never checked against. So an edit that is valid on the ledger it read, but breaks the ledger it lands on, commits without `allowInvalid`. REST and GraphQL then report the stale check, `errorsAfter: 0, newErrors: [], valid: true`, and the ledger is red. MCP re-reads after the write, so it reports the new error, but only after it has committed.

`appendLedgerText` and `addLedgerEntries` already get this right: on a lost race they re-run the whole write, bean-check included, against what landed (w31/007, `retryLostEntryWriteRace`). The renames commit against the shas they read and surface `CONFLICT` (w31/130).

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The deployment predates local HEAD `634566e8f`, which has the same code on every path named below. The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`, and every probe was prefixed `qa-20261127-`. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check showed 0 errors.

## Repro (live)

Setup: the ledger's last `Assets:Cash` assertion is `2026-08-29 balance Assets:Cash 49.75 USD`. Append one probe transaction:

```beancount
2026-08-30 * "qa-20261127-race" "qa-20261127 race probe"
  Assets:Cash               -1.00 USD
  Expenses:Food:Coffee       1.00 USD
```

Each of the two writes below is valid on its own. Together they break the ledger:

- **A:** `appendLedgerText {"path": "main.bean", "text": "2026-08-31 balance Assets:Cash  48.75 USD\n"}`.
- **B:** the probe edited to `-2.00 USD` / `2.00 USD`, sent with the probe's `entryHash` and `sha256sum`.

1. **Sequential control.** Land A, then send B. B is refused `VALIDATION_FAILED`: "this edit would introduce 1 new bean-check error: Balance failed for Assets:Cash: expected 48.75 USD, got 47.75 USD (main.bean:93)". This is correct.
2. **Race.** Reset to the setup. Start A, and 1.0 s later, before A answers (A takes about 2.2–2.8 s), send B. A commits. Then B commits too:
   - **MCP** `updateEntrySource {entryHash, sha256sum, newContent}` returns `ok: true`, "Updated entry … 1 new bean-check error: Balance failed for Assets:Cash: expected 48.75 USD, got 47.75 USD (main.bean:93)", `validation: {errorsBefore: 0, errorsAfter: 1, valid: false}`, and a `commit`.
   - **REST** `PUT /api-gateway/v1/ledgers/{owner}/{name}/entry-source` `{entryHash, sha256sum, newContent}` returns `200` with a `commit` and `"errorsBefore":0,"errorsAfter":0,"newErrors":[],"valid":true`.
   - **GraphQL** `updateLedgerEntrySourceSlice(ledgerId, input: {entryHash, sha256sum, newContent})` returns `errorsBefore: 0, errorsAfter: 0, valid: true, newErrors: []`.
   - After each race, `checkLedger` reports `Balance failed for Assets:Cash: expected 48.75 USD, got 47.75 USD` at `main.bean:93`. Each surface reproduced 1 of 1.

No `allowInvalid` was sent at any point.

## Cause

- Each of the four writes runs `projectWriteErrors(loaded, transforms, …)` over the file map `loadFileMap` returned. That is the refusal and the reported `validation`. The write then calls `commitTransforms(…, transforms, …)`. Line numbers:
  - `deleteSourceSlice`: `ledger-journal-service.ts:1273` and `:1282`.
  - `deleteMultiSourceSlices`: `:1324` and `:1333`.
  - `moveSourceSlices`: `:1538` and `:1553`.
  - `updateSourceSlice`: `:1650` and `:1659`.
- `commitLedgerFiles` (`commit-ledger-files.ts:237-242`) re-reads each file at the start of every attempt, the first one included. It applies the transform to that fresh content and commits with the fresh blob sha. Nothing between the read and the commit runs bean-check. The doc comment at `ledger-journal-service.ts:731-732` says this outright: "the commit re-applies them to fresh content under CAS." So the CAS protects the file version the commit read, not the one the check read.
- In backend-v2, REST and GraphQL pass the ledger's projection through (`toReportedProjection(data)`, `src/features/ledger/service/ledger-journal-service.ts:525,578,659,752`). MCP's `validated` wraps the commit in `withPostWriteValidation` (`src/features/ai-agent/api/mcp-source-slices.ts:141-166`). That is why only MCP shows the error after the fact.

## Fix

- **Target behavior.** The new-error check for these four writes judges the exact content the commit writes:
  - When a concurrent write changed a touched file after the check read it, the write is checked again against the fresh content before it commits.
  - Without `allowInvalid`, a write that now adds errors is refused `VALIDATION_FAILED`, or `UNBALANCED` where that rule applies, and nothing is committed.
  - With `allowInvalid`, the commit lands, and `errorsBefore`, `errorsAfter`, `newErrors` and `valid` describe the ledger it landed on, on REST, GraphQL and MCP alike.
- **One way to get there:** commit against the blob shas the check read, so any change in between is a lost race. On a lost race, re-run the whole write (load, locate, check, commit), bounded the way `retryLostEntryWriteRace` bounds entry writes. If every attempt loses, answer `CONFLICT` with a hint to send the same call again, since these writes hold no file `sha`. Keep the same-entry rules of w23/m1: one winner, and the loser gets `CONFLICT` or `NOT_FOUND`.
- **Docs.** `docs/mcp.md` gets one sentence where the preview rule and the entry-source tools are described: a write that a concurrent write overtakes is checked again against what landed.
- **Tests.**
  - A ledger-package test with a fake Gitea that lands a rival change between `loadFileMap` and the commit read, for update, delete, delete-many and move. Assert the refusal, no commit, and the `allowInvalid` path's reported projection.
  - A backend-v2 parity case for `updateEntrySource` on REST, GraphQL and MCP. `entry-write-race-parity.test.ts` and `rename-write-race-parity.test.ts` show the pattern.
  - Revert the fix and watch the refusal assertions fail.

## Blast radius and controls

- **Same mechanism, traced but not raced live:** `deleteEntrySource` and `deleteEntrySources` (deleting an `open` while a concurrent append posts to that account) and `moveEntrySources`.
- **Not affected:**
  - `appendLedgerText` and `addLedgerEntries` re-run the write, bean-check included (w31/007). The ledger's bulk route commits once, against the shas it checked (`src/api/entries.ts:456-520`).
  - `renameAccount` and `renameLedgerFile` commit against the shas they read and answer `CONFLICT` (w31/130).
  - Whole-file `updateLedgerFiles` `content` writes and deletes are not re-applied.
- **Separate path:** `updateLedgerFiles` exact-text edits re-apply after a lost race in backend-v2's own loop. That is a different cause, filed as w31/132.
- **Open question for the fix:** a concurrent write to a file this write does not touch is outside any per-file CAS. Note in the fix whether that case is covered, or stays out of scope.

**Resolved 2026-11-27** — The four source-slice writes in the ledger service (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts`) now commit only onto the content their check judged. `commitLedgerFiles` takes that content as `checked`. A touched file that holds anything else when the commit reads it, including on the re-read after Gitea refuses a stale sha, is a `LostWriteRaceError`, and nothing is applied or committed. `rerunLostRace` then runs the whole write again (load, locate, check, commit), up to 3 attempts, the bound the entry writes use (w31/007). A `VALIDATION_FAILED` or `UNBALANCED` refusal therefore applies to what landed, and an `allowInvalid` commit reports `errorsBefore`, `errorsAfter` and `newErrors` for the ledger it landed on. When every attempt loses, the write is `CONFLICT` "concurrent writes changed the files this write touches before each of 3 attempts could commit; nothing was written". backend-v2's `src/foundation/fava/error-to-domain.ts` maps that wording to a hint to send the same call again, on REST, GraphQL and MCP alike. A `LocationFence` keeps the w23/m1 rules on a re-run: each entry must be found again in the same file, among as many identical twins, and an entry the other write changed or removed is the stale-entry `CONFLICT`, not `NOT_FOUND`. A move into a `toPath` or `includeFrom` the loader could not decode as text is now refused `BAD_USER_INPUT` up front, since that content could never match. The open question stays out of scope: a concurrent write to a file the write does not touch is not checked against, as for the entry writes and the renames, because Gitea's change-files API has no whole-tree compare-and-swap. `source-slice-write-race.test.ts` (ledger) runs the real service and `commitLedgerFiles` over a fake Gitea that versions files by content, with a rival landing after the load or before the commit. It covers update, delete, delete-many and move: the refusal with no commit, the `allowInvalid` projection, a harmless rival the write lands beside, exhaustion after 3 loads, a dry run that runs once, and the three same-entry fences. With the fix reverted, 15 of its 23 cases fail; with the fence disabled, its three fence cases and two existing w23/m1 twin cases fail. `commit-ledger-files-concurrent-write.test.ts` adds 5 `checked` cases. `entry-source-write-race-parity.test.ts` (backend-v2) drives `updateEntrySource` on REST, GraphQL and MCP: the refusal on what landed, an `allowInvalid` commit reporting `errorsAfter: 1, valid: false` on all three, and the `CONFLICT` hint, whose 3 cases fail with the mapping reverted. `docs/mcp.md` describes the re-run under "Update or delete entry source", lists the move's two new refusals, and extends the `CONFLICT` failure-code row and the edit-one-entry step.
