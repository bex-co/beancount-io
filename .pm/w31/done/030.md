# `mcp:conformance` check 2 reports a skip and blames check 1 when its own discovery request fails

Source: follow-up from the `/loopx w31` routine `mcp-qa`, run 57, 2026-11-16.

- One conformance pass against `https://beancount.io` printed `PASS 1 endpoint-401 … points at https://beancount.io/.well-known/oauth-protected-resource`. It then printed `SKIP 2 discovery-resolves — check 1 produced no pointer to follow` and exited 0 with "17 passed, 0 failed, 1 skipped". A re-run straight after passed all 18 checks.
- Cause: in `backend-cluster/backend-v2/scripts/mcp-conformance.ts`, `checkDiscovery` sends its own anonymous POST through `discoverPointer`. When that request errors, or comes back without a pointer, the error and status are discarded. The failure then shows up as a skip that names check 1, the wrong check. `hostMetadata` handles errors the same way.
- A transient server error is therefore reported as a passing run with a misleading skip, rather than as a failure.

**Done when:** a test in `backend-cluster/backend-v2/scripts/__tests__/mcp-conformance.test.ts` uses a server that returns the pointer on the first anonymous POST and a 503 on the second. In that test, check 2 fails and reports the 503, the same way check 1 reports a probe error, instead of skipping with "check 1 produced no pointer". `hostMetadata` reports its own request failures the same way.

---

**Resolved 2026-11-16**: in `mcp:conformance`, a check that sends its own discovery request now reports that request's failure itself, instead of skipping and blaming check 1. `discoverPointer` (`backend-cluster/backend-v2/scripts/mcp-conformance.ts`) now says why its anonymous POST yielded no pointer: the request errored, or it got a status other than 401. Check 2 fails with that reason and the URL, for example "an anonymous POST to …/api-gateway/mcp returned 503, not 401". It skips only when a 401 arrived without a pointer, which is check 1's own finding. `hostMetadata` (checks 11–16) does the same for each of its three requests. A failed POST, protected-resource document or authorization-server metadata request is now a failure that names the address and the error or status. When neither metadata address serves a document, the failure lists what each one returned. That case used to be a skip, which exited 0 even though every OAuth host refuses that deployment. A document that arrived but is invalid JSON is still a skip naming check 2, and a document naming no `authorization_servers` is still a skip.

- **Repro, local only.** A stub server answers the first anonymous POST with the pointer and the second with a 503. Against it, the script at `ae5ff036f` printed `PASS 1` and then `SKIP 2 … check 1 produced no pointer to follow`. With the fix, it prints `FAIL 2 … returned 503, not 401`. No live calls were made, and no credential was read.
- **Tests.** In `scripts/__tests__/mcp-conformance.test.ts`, the flapping stub is the note's own case: check 1 passes, then check 2 and check 11 fail naming the 503. A closed port makes check 2 fail with the address. A 401 with no pointer still skips, naming check 1. A 503 on each of the three requests `hostMetadata` sends makes checks 11–16 fail naming the status. With the fix reverted, 5 of these fail as skips.
- **Gates.** Run in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, `yarn lint:deadcode`, `yarn format:check`, ESLint and Prettier on the changed files, and `yarn generate-v1-openapi` with no drift. `yarn test` passes 487 of 488 suites. The other one, `git-proxy-real-git.test.ts`, fails with or without this change because the slim image has no `git`. It passes (8/8) in `node:22-bookworm`.
