# Two entry writes at once: the loser gets `CONFLICT` and a hint to retry "with that `sha`", an argument `appendLedgerText` and `addLedgerEntries` do not take

**Minor · backend-v2 (entry writes, error mapping) · ~1h · A1.** Found in the same run and against the same target as `w31/006`. The writes ran on the designated QA ledger `<qa-owner>/mcp-agent-eval`, with every probe prefixed `qa-20261115-`. Afterwards `main.bean` was restored byte for byte (blob `f1a0b83c`), and the ledger check is clean.

- **Repro.** Send two `appendLedgerText` calls at the same moment, with no `requestId`. Each carries one valid, balanced transaction, and the two texts differ. One call commits. The other returns `isError: true` with `CONFLICT` "Ledger resource conflict: Ledger file conflict: the ledger changed under a concurrent write; re-read it and retry" and the hint "Re-read the file to get its current `sha`, then retry the write with that `sha`." This happened in 2 of 2 rounds. Two concurrent `addLedgerEntries` calls behave the same way (1 of 1). No data was lost: the file holds exactly the winner's entry.
- **The hint is wrong for these tools.** Neither tool takes a `sha`. The hint comes from the 409 mapping that `w23/178` added for stale file `sha`s (`backend-cluster/backend-v2/src/foundation/fava/error-to-domain.ts`, the `LEDGER_FILE_CONFLICT` branch). That branch also matches the ledger service's lost-race wording, and that is the error these generated writes get. The `docs/mcp.md` failure-codes row for `CONFLICT` is no better a fit: it says to re-read with `getEntryContext` and resend the fresh `sha256sum`.
- **Concurrent edits combine, appends do not.** Two concurrent `updateLedgerFiles` `old_string` edits on different lines of one file both landed, thanks to the re-read-and-re-apply loop that `w23/017` added. The entry writes have no such loop. `appendDirectiveText` (`src/features/ledger/workflow/directive-append-workflow.ts`) reads the target, projects bean-check, then commits once with the `sha` it read, through `changeGeneratedFiles`. The ledger service's bulk route (`backend-cluster/ledger/src/api/entries.ts`, `addBulkEntries`) also commits once and does not retry. Yet `commitLedgerFiles` in the same service documents that "concurrent appends/edits compose instead of clobbering".
- **Controls that hold.**
  - The same `requestId` sent twice at once makes one commit. The other call gets `CONFLICT` with the documented in-progress hint. A later repeat replays the first commit, and the text lands once.
  - Two whole-file `content` writes with one base `sha` make one commit. The other gets `CONFLICT` with the file-`sha` hint, which is correct there.
  - Two `updateEntrySource` calls with one `sha256sum` make one commit. The other gets `CONFLICT` with the entry hint.

**Done when:**
- An `appendLedgerText` or `addLedgerEntries` call that loses the race re-reads the file and re-runs bean-check and the balance check against the fresh content. It then commits again, up to the edit path's 3 attempts. Two concurrent appends of valid text both land, and an `UNBALANCED` or `VALIDATION_FAILED` refusal still applies to the fresh content.
- When the attempts run out, the `CONFLICT` hint says to send the same call again (with its `requestId`) and names no `sha`.
- REST and GraphQL share the change.
- Tests drive a lost race through each tool, and they fail with the retry reverted.

Packages: `backend-cluster/backend-v2`, plus `backend-cluster/ledger` if the bulk route keeps its single commit.

---

**Resolved 2026-11-15** — `LedgerEntryService` (`backend-cluster/backend-v2/src/features/ledger/service/ledger-entry-service.ts`) now runs the commit of `appendLedgerText` and `addLedgerEntries` through `retryLostEntryWriteRace` (`src/features/ledger/utils/entry-write-race.ts`). REST, GraphQL and MCP all call that service, and so does the legacy `addEntries`. When the ledger refuses a commit as a lost race (`CONFLICT`), the whole write runs again, up to the edit path's 3 attempts. Each run re-reads the target files and re-runs bean-check and the balance check against the content that landed: the append workflow's projection, and the ledger service's bulk route, which reads and checks on every call. So the ledger package keeps its single commit. Two concurrent appends of valid text both land, and an `UNBALANCED` or `VALIDATION_FAILED` refusal applies to the fresh content. The retry runs inside the `requestId` claim, so a retry is the same write, not a second one. A dry run is never retried. When every attempt loses, the call is `CONFLICT` with a new hint: none of its directives were committed, send the same call again, and keep its `requestId`. The hint names no `sha`. The file-`sha` hint stays on the file writes it fits. `entry-write-race-parity.test.ts` lands a rival write between the read and the commit, on a fake ledger that versions files by content. It covers both tools on all three surfaces: a lost race that commits on top of the winner, a duplicate `open` refused on the fresh content, exhaustion after exactly 3 attempts with the new hint, and a resend with the same `requestId` that writes once. With the retry reverted, all 24 cases fail. `docs/mcp.md` describes the behavior under "Insert structured directives" and in the `CONFLICT` failure-code row, and `mcp-doc-claims.test.ts` pins the 3 attempts. Before the deploy, the repro still held on `https://beancount.io`, 1 of 1 for each tool on `<qa-owner>/mcp-agent-eval`. `main.bean` was then restored byte for byte (blob `f1a0b83c`). Gates in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, `yarn test` (483 suites), `yarn lint:deadcode`, `yarn format:check`, ESLint on the changed files, and an OpenAPI regeneration with no drift. `w31/008` is a separate path (the `createLedgerFiles` error mapping) and stays open. Shipped in this commit (`backend-v2`).
