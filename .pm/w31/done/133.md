# A file rename or entry move to another folder leaves each relative `document` path pointing at the old folder: `renameLedgerFile` with `updateIncludes: true` commits a red ledger, and `moveEntrySources` cannot move a document entry at all

**Minor · backend-v2 (`renameLedgerFile`) and ledger (`moveEntrySources`) · 45–60m · A1.** Beancount resolves a relative `document` path against the directory of the file that declares it, the same rule it uses for `include`. The hosted engine does too (`backend-cluster/ledger/src/foundation/rustledger/document-validation.ts:84` `resolveDocumentPath`). w23/056 taught `renameLedgerFile` to rewrite a moved file's own relative includes. It does not do the same for the moved file's relative `document` paths, and `moveEntrySources` moves an entry's text unchanged. So a move to another folder makes every relative `document` name a file that does not exist.

This is the shape the product writes itself. Since w31/019, a receipt routed to `books/docs.bean` is written as `document … "../documents/…"` (`ledger-receipt-workflow.ts:113` `documentPathFrom`). Reorganizing such a ledger (moving `books/docs.bean` up a level, or moving receipt entries into a year file in another folder) breaks every receipt link.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27. Target: `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The probe files were deleted afterwards, `main.bean` is byte-identical to its snapshot (blob `f1a0b83c`), and the check is clean. `movedIncludesContent` and the move's text assembly are unchanged at HEAD `8b434fd75`, so this is not deployment lag.

## Repro (live)

1. `createLedgerFiles`:
   - `qa-books/docs.bean` containing `2026-08-30 document Assets:Cash "receipt.txt"`
   - `qa-books/receipt.txt`
2. `updateLedgerFiles`: add `include "qa-books/docs.bean"` to `main.bean`. The commit is clean. The `documents` resource lists `qa-books/receipt.txt`, and `checkLedger` returns `[]`.
3. `renameLedgerFile` with `{oldPath: "qa-books/docs.bean", newPath: "docs.bean", updateIncludes: true, dry_run: true}`:
   - The include in `main.bean` is rewritten.
   - `validation` returns `valid: false`, `errorsBefore: 0`, `errorsAfter: 1`, `newErrors: [{code: "E8001", message: "Document file not found: receipt.txt", source: "docs.bean:1"}]`.
   - A move one folder deeper (`qa-books/sub/docs.bean`) gives the same result.
   - REST `POST /v1/ledgers/{owner}/{name}/rename-file` with `dryRun: true` and GraphQL `renameLedgerFile(dryRun: true)` return the same verdict.
4. Run the same rename without `dry_run`. It is not refused, as `docs/mcp.md:490` says renames never are: "Renamed … 1 new bean-check error: Document file not found". After the commit, `beancount://…/errors` returns that E8001, and `documents` lists `receipt.txt` at the root.
5. `moveEntrySources` of the document entry to `main.bean` with `dry_run: true` (MCP, and REST `POST …/entries/move`) gives the same E8001, at `main.bean:90`. The commit would be refused `VALIDATION_FAILED`, so the entry cannot be moved without breaking it.

**Control:** stock Beancount 3.2.3 `bean-check` passes the step-2 layout. With `docs.bean` moved to the root and its line unchanged, it fails with `File does not exist: …/receipt.txt`. It passes again once the line reads `"qa-books/receipt.txt"`. A rename within the same folder needs no rewrite.

## Cause

- `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts:1993` `movedIncludesContent` re-anchors only what `scanIncludeLines` finds (`:2004`). A `document` line is copied byte for byte.
- `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:1660`: the move appends each slice as `slicesWithPushScopes` returns it. Only the push scope is applied; the relative path is not re-anchored for `toPath`'s folder.

## Fix

When a file changes folder, treat a relative `document` path like a relative include: resolve it from the old location, then write it relative to the new one so it names the same repository file. Do this in both operations.

- **`renameLedgerFile`:** in `movedIncludesContent`, rewrite each `document` directive in the moved file whose resolved target would change, under the same `updateIncludes` rule. Without the flag, refuse naming the paths. With it, rewrite them and list them in `preview`.
  - Leave absolute and URL paths alone.
  - Read every date form the line scanners accept (w31/106–110), skip what Beancount skips (w31/097–100), and escape the rewritten string as w31/093 does.
- **`moveEntrySources`:** when `toPath` is in another folder, rewrite a moved `document` entry's relative filename for `toPath`, so it resolves to the same file. The hash covers the directive's path (`entry-hash.ts:283`), so if the rewrite changes it, report the new hash in `movedHashes` and `entryHashes`, as w31/016 does for a push-scoped entry.
- **Surfaces:** REST, GraphQL and MCP share the workflow and the ledger service, so they change together.
- **Docs:** state the rule in `docs/mcp.md` next to "The moved file's own relative includes" (`:2347`) and in the `moveEntrySources` description.

**Resolved 2026-11-27** — A file rename and an entry move now rewrite each relative `document` filename that changes folder, so it still names the same repository file. Both commands and every surface use the same rule: the filename resolves from the old folder and is written relative to the new one. A leading `./` is kept and the new string is escaped. Root-anchored and URL filenames are left alone, and so are a filename that resolves the same from both folders and one that names no file in the repository. Same-folder renames and moves stay byte-identical.

- **`renameLedgerFile` (backend-v2).** `scanIncludeLines` (`src/features/ledger/utils/include-target.ts`) now also reads `document` headers. It accepts every date form the lexer reads (w31/106), skips lines that start inside a string or that Beancount skips (w31/097–099), and keeps a line-1 byte-order mark (w31/100). `movedIncludesContent` uses the include rule for these lines. Without `updateIncludes`, the move is refused `BAD_USER_INPUT` with "`qa-books/docs.bean` names the document "receipt.txt" relative to its folder; pass updateIncludes: true …". With the flag, the line is rewritten and listed in `preview`. In the note's layout, the moved line now reads `"qa-books/receipt.txt"`; one folder deeper it reads `"../receipt.txt"`. REST, GraphQL and MCP share the workflow.
- **`moveEntrySources` (ledger).** The new `withDocumentPathFor` (`src/foundation/rustledger/moved-document-path.ts`) runs on each slice after `slicesWithPushScopes`. A document's filename is part of its hash (`entry-hash.ts`), so a rewritten entry's `movedHashes` entry is its new hash, read from the files the move leaves. That projection is also what the commit lands (w31/131). MCP `entryHashes` relays it. Every other entry keeps its hash. The post-write hash resolver now takes several ranges, and `updateSourceSlice` uses it too.
- **Descriptions and docs.** The shared `MOVE_ENTRIES_DESCRIPTION` states the rule. It was kept short so MCP `tools/list` stays inside its 134 KiB budget. `docs/mcp.md` states it under "Moving entries to another file" and next to "The moved file's own relative includes". The hand-maintained ledger IDL `moveSourceSlices` and `moved_hashes` descriptions match. The following were regenerated: backend-v2 `Api.ts` (`yarn generate-fava-client`), `docs/openapi/v1.json` (`yarn generate-v1-openapi`), and the CLI pin and REST client (`make spec-sync && make codegen`). The dashboard and mobile GraphQL copies of the description were not regenerated. They are doc comments only, and no gate reads them.
