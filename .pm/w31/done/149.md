# `renameAccount` leaves an account's `option "documents"` folder under the old name, so every statement filed there drops out of the ledger without a word: the preview says "1 line in 1 file. No new bean-check errors.", and afterwards `documents`, `listLedgerEntries` and `entries-count` show none, on MCP, REST and GraphQL (the account-rename twin of w31/133)

**Minor · backend-v2 (`src/features/ledger/workflow/account-rename-workflow.ts`, `src/features/ledger/utils/account-rename.ts`) and docs · 45–60m · A1.** Beancount's `option "documents"` names a folder whose subfolders are named for accounts. Each file in `<root>/Assets/Bank/Checking/` named `YYYY-MM-DD.<anything>` is a `document` of `Assets:Bank:Checking`, but only while some entry names that account. That is how Fava files an uploaded statement, and the hosted engine discovers documents the same way (`backend-cluster/ledger/src/foundation/rustledger/document-discovery.ts`, w21/738). `renameAccount` rewrites account tokens in the loaded `.bean` files and moves bank mappings, but it never moves the account's folder. After the rename, the folder names an account no entry uses, so discovery skips every file in it, as stock does. The account's statements disappear from the ledger. No preview, summary or error says so, and the ledger checks clean.

The tool says it renames the account "across the ledger" and that "Bank mappings move with it". `docs/mcp.md` "Renaming an account" lists what moves and what stays, and does not mention document folders. w31/133 fixed the same loss for a file rename or entry move, where a relative `document` path stopped naming its file.

## Cause

`AccountRenameWorkflow.renameAccount` (`account-rename-workflow.ts:88`–`176`) reads only the files the ledger loads (`projectedSourceFiles`), and rewrites account tokens in them. It commits one `update` operation per changed file (`changeGeneratedFiles`, `:168`). The repository's other paths are never listed, so a folder under a documents root that spells the account never becomes a move operation. Discovery then skips that folder silently, because no entry names its account (`document-discovery.ts:109`, `!accounts.has(account)`). Stock Beancount's `find_documents` does the same.

## Fix

In the same commit, for each `option "documents"` root in `main.bean` (resolved against its directory, as `discoverDocuments` does): move every repository file under `<root>/<from as folders>/`, descendants included, to the same relative path under `<root>/<to as folders>/`. Use a delete and a create per file, or the repo service's move, so the rename stays one atomic commit. List each move in the result, for example `documents: [{from, to}]` beside `files`, so the preview shows it. Count the moves in the summary ("1 line in 1 file, 1 document moved"). Refuse with `BAD_USER_INPUT`, and write nothing, when a target path already exists, so two folders never merge silently. A root with no folder for the account changes nothing.

`renameAccount` (MCP), `POST /api-gateway/v1/ledgers/{owner}/{name}/rename-account` (REST) and `renameLedgerAccount` (GraphQL) all call `AccountRenameWorkflow`, so one change covers all three. Add the result field to each surface's schema in the same change: the MCP output schema, the OpenAPI snapshot via `yarn generate-v1-openapi`, and the GraphQL type. Update `docs/mcp.md` "Renaming an account" to say that document folders move. `revertCommit` already restores the folder, because a rename commit's moves are ordinary adds and removes.

**Resolved 2026-11-27** — `renameAccount` (MCP), REST `POST …/rename-account` and GraphQL `renameLedgerAccount` now move the account's documents folders in the rename's commit. For each `option "documents"` root that `main.bean` declares, read with the hosted engine's pattern and resolved from the entry point's folder, every file under `<root>/<from as folders>/` moves to the same relative path under `<root>/<to as folders>/`, descendants' folders included. Each file moves with its bytes unchanged, so PDFs survive. In the note's layout, the statement lands at `qa-20261127-r19-docs/Assets/Qa20261127r19/Statements/2026-08-15.qa-20261127-r19-statement.txt`.

- **Workflow (backend-v2).** `AccountRenameWorkflow.documentMoves` lists each source folder through `listDirContent`; a missing folder means nothing to move. A file the ledger loads stays put, because an `include` names it where it is. When the target folder already holds a file, the rename is refused `BAD_USER_INPUT` on both the preview and the commit, naming that file, and nothing is written. A ledger with no documents option, or no folder for the account, makes no listing call and renames exactly as before.
- **Repo service (backend-v2).** `changeGeneratedFiles` takes a `move` operation (`path`, `from_path`, `sha`). It reads the source as base64 and commits a create carrying those bytes plus a delete at the listed sha, beside the text updates, in one commit. A source that is gone or changed since it was listed refuses the batch as a lost race (`CONFLICT`, "send the same call again"). Moving `main.bean` is refused. `revertCommit` restores the files, as it does for any added and removed pair.
- **Result.** A new `documents: [{from, to}]` sits beside `files` on all three surfaces: the MCP output schema, the regenerated `docs/openapi/v1.json`, and the GraphQL `AccountRenameDocument` type. The message counts the moves, for example "…: 2 lines in 2 files, 2 documents moved". MCP `wrote` lists both ends of each move. The tool, route and mutation descriptions and `docs/mcp.md` "Renaming an account" say that document folders move, along with the new refusal.
- **Tests.** `rename-account-parity.test.ts` covers four cases on MCP, REST and GraphQL: the preview and the commit of a folder move, a renamed parent moving its descendants' folders, the refusal when the target folder is occupied, and a root with no folder for the account. With the moves disabled, the first three fail on all three surfaces (9 cases). Repo-service unit tests cover the byte-for-byte create and delete (and fail when the bytes are re-encoded), stale and missing sources, and the entry-point refusal. A workflow test shows a loaded file staying put, and `document-folders.test.ts` covers how roots are read.

Gates: `backend-cluster/backend-v2`: `yarn typecheck`, `yarn test` (510 suites), `yarn lint:deadcode` and `yarn format:check` pass. `yarn generate-v1-openapi` changes only the rename-account description and the new `documents` field.
