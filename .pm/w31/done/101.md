# An entry-delete preview puts its new error on the line it will have after the delete, often the `open` line being deleted; the same delete's commit refusal gives the current line (w5/1202 fixed only the refusal), on MCP, REST and GraphQL

**Minor · ledger (`src/features/ledger/service/ledger-journal-service.ts`) · 30–45m · A1.** w5/1202 made a refused entry delete name the error at its line in the file as it stands. The refusal used to give the line from the file as it would be after the delete, so it named a line the reader could not find. Only the refusal changed. The `dry_run` preview of the same delete still reports `newErrors[].source` from the post-delete file. The preview rule (`backend-cluster/backend-v2/docs/mcp.md`, "The preview rule") tells an agent to preview first. So the first location an agent sees is the wrong one, and it disagrees with the commit refusal for the same call.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26.

- **Target:** `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). It already serves the w5/1202 refusal mapping. Local HEAD `c0b8ff708` has the same code.
- **Credential:** an unpinned read/write `bcio_` key on the QA account.
- **Writes:** only to the designated QA ledger `<qa-owner>/mcp-agent-eval`.
- **Cleanup:** `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check showed 0 errors.

## Repro (live)

1. Append the w5/1202 shape to the end of `main.bean` with `updateLedgerFiles` (QA commit `bce607d4`). Lines 89–91 then read:

   ```beancount
   2026-08-30 open Assets:Qa-20261126-Probe USD

   2026-08-31 balance Assets:Qa-20261126-Probe 0.00 USD
   ```

2. Get the `open` entry: `beancount://<qa-owner>/mcp-agent-eval/account-directives` gives its `entryHash`, and `getEntryContext` gives `sha256sum` and `meta.lineno: 89`.
3. `deleteEntrySource {entryHash, sha256sum, dry_run: true}` returns `valid: false` with `newErrors: [{message: "Account Assets:Qa-20261126-Probe was never opened", source: "main.bean:89", code: "E1001"}]`. Line 89 is the `open` line this call deletes.
   - REST `POST /api-gateway/v1/ledgers/{owner}/{name}/entry-source/delete` with `dryRun: true` returns the same `source`.
   - GraphQL `deleteLedgerEntrySourceSlice(input: {…, dryRun: true})` returns the same `source`.
   - `deleteEntrySources` with the one entry and `dry_run: true` returns the same `source`.
4. The same `deleteEntrySource` without `dry_run` is refused `VALIDATION_FAILED`: "… was never opened (main.bean:91)". Line 91 is the `balance` that still names the account, which is right.

A second case needs no fixture. Dry-run deleting `2026-01-01 open Expenses:Food:Coffee USD` (line 15) reports `main.bean:66`, a blank line. The refusal on MCP, REST and `deleteEntrySources` reports `main.bean:67`, the `BLUE BOTTLE` transaction.

## Cause

- `projectWriteErrors` (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:722-760`) maps each new error back through the deleted line ranges (`deletedLines`) only inside `if (!allowInvalid)`, and only to build the refusal. It returns the unmapped `projection`, which becomes the result's `validation`.
- backend-v2 sends every preview to the ledger service with `allowInvalid: true` (`backend-cluster/backend-v2/src/features/ledger/service/ledger-journal-service.ts:510` for `deleteSourceSlice` and `:563` for `deleteMultiSourceSlices`), so that a preview reports errors instead of refusing. A preview therefore never reaches the mapping.
- The w5/1202 test pins the refusal's line. The preview tests in `backend-cluster/ledger/src/features/ledger/service/__tests__/source-slice-new-errors.test.ts` do not check `newErrors[].source`.

## Fix

When a delete commits nothing (`dryRun`), return the mapped `newErrors`, the same locations the refusal names. One way is to pass `dryRun` into `projectWriteErrors` and map before both refusing and returning.

A committed `allowInvalid` delete should keep the post-delete line, because after the commit that is where the error lives.

MCP `deleteEntrySource`/`deleteEntrySources`, REST `entry-source/delete`/`delete-many` and GraphQL `deleteLedgerEntrySourceSlice`/`deleteMultipleLedgerEntrySourceSlices` all delegate to this ledger method. They change together, and no response shape changes.

## Done when

- In the repro, the preview on all three surfaces reports `source: "main.bean:91"`, the same line as the commit refusal.
- In the Coffee case, the preview reports `main.bean:67`.
- A ledger unit test pins the preview's `newErrors[0].source.lineno` to the refusal's line for `deleteSourceSlice` and `deleteMultiSourceSlices`, including a cut that takes the separating blank line.
- A test shows an `allowInvalid` commit keeps the post-delete line.
- The new cases fail with the fix reverted.

---

**Resolved 2026-11-26** — A delete that commits nothing now names each new error at its line in the file as it stands, so the preview agrees with the refusal for the same call. `projectWriteErrors` (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts`) takes `dryRun`, maps the new errors back through the cut line ranges once, refuses from that mapping, and returns it when `dryRun` is set. A committed `allowInvalid` delete still reports the line after the cut, where the error now lives. `deleteSourceSlice` and `deleteMultiSourceSlices` serve MCP `deleteEntrySource`/`deleteEntrySources`, REST `entry-source/delete`/`delete-many` and GraphQL `deleteLedgerEntrySourceSlice`/`deleteMultipleLedgerEntrySourceSlices`, so all three surfaces changed together. No response shape changed, and backend-v2 needed no change.
