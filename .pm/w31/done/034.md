# `commit-details` with an empty `sha` (`?sha=` / `sha: ""`) silently returns HEAD instead of `BAD_USER_INPUT` on MCP, REST, and GraphQL

**Minor · backend-v2 (commit lookup validation) · 20–30m · A1.** Passing an empty `sha` to `commit-details` succeeds and returns the default branch's latest commit on all three surfaces, contradicting the documented requirement that `sha` is required and diverging from `revertCommit` (which refuses `sha: ""` with `BAD_USER_INPUT`). Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, checked against HEAD `86c4abf04`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval`.

## Repro (live)

Reproduced in fresh read-only requests across all three surfaces:

1. **MCP resource `beancount://<qa-owner>/mcp-agent-eval/commit-details?sha=`**:
   ```sh
   node .agents/skills/qa-shared/scripts/qa-mcp.mjs read 'beancount://<qa-owner>/mcp-agent-eval/commit-details?sha='
   ```
   Actual: HTTP `200`, returns the latest commit on `main` (`{"sha":"caa97152...","message":...}`).
2. **REST `GET /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/commit-details?sha=`**:
   Actual: HTTP `200`, returns the latest commit on `main`.
3. **GraphQL `getCommitDetails(ledgerId: "<qa-owner>/mcp-agent-eval", sha: "")`**:
   Actual: HTTP `200`, `{"data":{"getCommitDetails":{"sha":"caa97152..."}}}`.

Expected: refused with `BAD_USER_INPUT` (`sha is required`, hint naming `commits`), identically on MCP, REST, and GraphQL — matching what omitting `sha` and `revertCommit({ sha: "" })` already do.

## Working controls

- Omitting `sha` on MCP (`beancount://<qa-owner>/mcp-agent-eval/commit-details`) returns JSON-RPC `-32602` `BAD_USER_INPUT: sha is required`.
- Omitting `sha` on REST (`GET /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/commit-details`) returns HTTP `400` `VALIDATION_FAILED` (`Validation failed for query.sha: sha is required`).
- `commit-details?sha=%09` returns `NOT_FOUND` on all three surfaces.
- `revertCommit({ sha: "" })` refuses with `BAD_USER_INPUT: sha is required` before contacting Gitea (`ledger-workflow.ts:1735-1742`).

## Root cause

Not deployment lag — present at HEAD `86c4abf04`:

- `backend-cluster/backend-v2/src/features/gitea/commits/api/commit-reads.ts:70`: `ledgerCommitDetails` defines `query: z.object({ sha: z.string() }).strict()` with no non-empty check.
- `backend-cluster/backend-v2/src/features/gitea/commits/service/commits-service.ts:55-77` (`findCommit`, called by `CommitsService.getCommitDetails` at `:382`): calls `assertCommitRef(sha, "sha")` (`src/shared/commit-ref.ts:23-34`, which only checks for spaces, not empty string), then calls `client.repos.repoGetAllCommits(owner, repo, { sha: "", limit: 1, files: true, stat }, { format: "json" })`. Gitea treats an empty `sha` query parameter as "default branch HEAD", so `listed.data[0]` returns the latest commit instead of refusing.
- `ledger-workflow.ts:1735-1742` already guards `input.sha.trim() === ""` before calling `findCommit`, which is why `revertCommit` refuses empty `sha` while `getCommitDetails` does not.

## Fix

In `backend-cluster/backend-v2`:

1. Guard `sha.trim() === ""` in `findCommit` (`src/features/gitea/commits/service/commits-service.ts:55-63`), throwing `new BadUserInputError("sha is required", "sha", COMMIT_NOT_FOUND_HINT)` (matching `ledger-workflow.ts:1735-1742`, which can then rely on `findCommit` or keep its early pre-Gitea check).
2. Add `.min(1, "sha is required")` on `commit-reads.ts:70` if helpful for OpenAPI documentation, while keeping the service-layer guard in `findCommit` so GraphQL `getCommitDetails(ledgerId, sha: "")` enforces the exact same refusal.
3. All three surfaces (`beancount://{owner}/{name}/commit-details`, `GET /api-gateway/v1/ledgers/{owner}/{name}/commit-details`, and GraphQL `getCommitDetails`) delegate to `CommitsService.getCommitDetails` → `findCommit` and change together.
