# `docs/mcp.md` says BQL has "no query-length ceiling", but the server refuses a query over 262144 bytes

**Trivial · docs · backend-v2 · 15m · A1.** Found in the same run as `w31/006`. Only reads were sent, all to the public `open_ledger/example`.

- **Repro.** Send `runBqlQuery` a query of about 1.9 MB, which is inside the 2 MiB body cap. The answer is `BAD_USER_INPUT` "BQL query is 1992306 bytes, over the limit of 262144.", with the hint "Split the query into smaller ones."
- **The doc.** In `backend-cluster/backend-v2/docs/mcp.md` "Results and failures", the paragraph before "The result envelope" says "There is no query-length ceiling to write around". It adds that long literals "run as written on every surface" and that `x IN (…)` "has no such limit". `aab0ac7d3` wrote that on 2026-10-25. On 2026-11-01, `0dbe35519` added `MAX_BQL_QUERY_BYTES = 256 * 1024` in `src/features/ledger/utils/bql-query-size-limit.ts`, applied at the point REST, GraphQL and MCP share. That commit updated the tool and OpenAPI descriptions ("up to 262144 bytes") but not this paragraph. "Argument limits" does not mention the cap either.
- **Controls that match the doc** (MCP, REST and GraphQL agree):
  - An `OR` list of 501 comparisons runs. One of 502 is refused: "chains 501 operators, over the limit of 500".
  - A query may hold up to 2,000 operators, and comparisons count toward that total.
  - `runBqlQuery` truncates as documented. The lead line reads `3209 rows (output truncated; …)`. The text is cut at 1,002 lines or 100 KB, and its last line, `[truncated: showing the first N of M lines (B of T bytes) …]`, agrees with the full REST and GraphQL text.
  - `runBqlQueryStructured` returns 1,000 rows with `truncated: true`. `LIMIT 1000` is not truncated, and `LIMIT 1001` is.

**Done when:**
- The paragraph states the 262,144-byte (256 KiB of UTF-8) query cap and its `BAD_USER_INPUT` refusal.
- It says `x IN (…)` is exempt from the operator limit, but not from the byte cap.
- A docs check pins that number to `MAX_BQL_QUERY_BYTES` and fails on the old sentence, for example in `mcp-doc-claims.test.ts`.

---

**Resolved 2026-11-15** — The BQL paragraph under "The result envelope" in `backend-cluster/backend-v2/docs/mcp.md` now says what the server enforces. The POST body removes the URL-length ceiling, and a query is capped at 262144 bytes (256 KiB of UTF-8). A longer query is refused with `BAD_USER_INPUT` ("BQL query is N bytes, over the limit of 262144.", hint "Split the query into smaller ones."), before authorization, the same way on REST, GraphQL and MCP. The paragraph also says `x IN (…)` is exempt from both operator limits, because its members are not operators, but not from the byte cap. "Argument limits" gains a bullet for the BQL `query` cap. `mcp-doc-claims.test.ts` adds the claim "a BQL query is at most 262144 bytes". It holds only while `MAX_BQL_QUERY_BYTES` is 262144 and the served `runBqlQuery` and `runBqlQueryStructured` descriptions state `up to 262144 bytes`. The old sentence "There is no query-length ceiling to write around" is now a stale phrase. With the previous doc text, both checks fail. Nothing was sent to production; the refusal itself is already covered on all three surfaces by `bql-parity.test.ts` ("refuses an over-cap query on every surface before domain work"). Gates run in `node:22-bookworm-slim`: `yarn typecheck`, `yarn test` (483 suites), `yarn lint:deadcode` and `yarn format:check`. Shipped in this commit (`backend-v2`).
