**Minor · ledger (`src/foundation/rustledger/stock-syntax-errors.ts`, `parseable-files.ts`) · 30–45m · A1.** Stock `bean-check` 3.2.3 refuses each spelling below as a syntax error and drops the directive. The hosted ledger reads each one as something else and reports nothing. The preview says `valid: true` with `newErrors: []`, the commit goes through without `allow_invalid`, and every error surface reads clean. The same file fails `bea check` and stock `bean-check`, and Fava will not load it, so the hosted balances disagree with every local tool.

The last row is deliberate today, and its reason is wrong. w21/969 (done, `ac8f20640`) found that the engine read `.5` as `5` and fixed it by rewriting `.5` to `0.5` before parsing (`withLeadingZeros`, `parseable-files.ts:54`). Its note and the function's comment (`:48`) say "Beancount's lexer reads `.5` as 0.5". Beancount 3.2.3's number rule is `([0-9]+|[0-9][0-9,]+[0-9])(\.[0-9]*)?` (`beancount/parser/lexer.l:282`), which needs a leading digit, and `bean-check` answers `Invalid token: '.50'`. Keep the rewrite, so the figure is never ten times too large, and add the error stock reports.

## Cause

`@rustledger/wasm` 0.24.0 reads `Assets:Cash:` as `Assets:Cash` and a flagless dated header with strings as a `*` transaction, with no error (checked directly with `validateSource` and `parse` under Node). The ledger service's own stock-rejection rules (`stockSyntaxErrors`, `stock-syntax-errors.ts:152`, wired at `engine.ts:855`) do not cover either. For `.5`, the ledger rewrites the text before the engine sees it (`parseableFiles` → `withLeadingZeros`, `parseable-files.ts:83`), so nothing is left to report.

## Fix

Add three rules beside the existing ones, each reported at its line with stock's wording, abstaining on doubt and tracking strings and `;` comments as the other rules do:

- an account token followed directly by `:` (`Assets:Cash:`), on any directive or posting line: `syntax error, unexpected COLON`;
- a dated line whose next token is a string, not a flag, `txn` or directive keyword: `syntax error, unexpected STRING`;
- a number with no leading digit, the exact tokens `withLeadingZeros` rewrites: `Invalid token: '.50'`. Keep the rewrite so the amount stays right.

Read the date with the shared `SOURCE_DATE` (w31/107), so `2026/09/01 "x"` is caught too. Correct the `parseable-files.ts:48` comment. No response shape changes; every surface reads these errors from the one ledger path.

**Resolved 2026-11-27** — The ledger service now reports all three spellings with stock's message at the line where stock reports it. Each preview answers `valid: false`, a commit without `allow_invalid` is refused `VALIDATION_FAILED`, and `checkLedger`, the `errors` resource, REST and GraphQL all list the error.

- **Trailing colon.** `stock-syntax-errors.ts` reports an account written with a colon after it (`Assets:Cash:`) as `syntax error, unexpected COLON, …` with the tokens stock 3.2.3 says it expected there. That is `expecting end of file or EOL or ATAT or AT` on a posting, `expecting end of file or EOL` on `open`, `close`, the second `pad` account and a metadata value, `expecting ACCOUNT` on the first `pad` account, `expecting PLUS or MINUS or LPAREN or NUMBER` on `balance`, `expecting STRING` on `note` and `document`, and no list on a `custom` value. The message then adds `: the account "Assets:Cash:" ends with a colon`, as the bare-booking rule adds its own explanation. A colon before a space, a comment, a quote, a `-` or the line's end counts. A colon before a capital, a digit or a non-ASCII letter continues the account. The engine already refuses a lowercase letter or a second colon there, so those are left alone. So is a dot there, where stock also reports an invalid token.
- **Flagless header.** A dated line whose next token is a string (`2026-09-02 "x"`, any date spelling `SOURCE_DATE` reads, with or without a space) gets `syntax error, unexpected STRING: a transaction has a flag (* or !) or txn after its date`.
- **Leading dot.** `Invalid token: '.50'` is reported at every dot `withLeadingZeros` rewrites. Both read the same offsets through the new `leadingDotOffsets` (`parseable-files.ts`). The token runs to the next whitespace, as stock's lexer reads it, so `(.5+1)` is `.5+1)`. The rewrite stays, so the figure stays 0.50. The `withLeadingZeros` comment now says stock refuses `.5`.
- **Stock's error recovery.** Stock drops a directive at its first syntax error, so the scan reports only that one. It also drops what stock would have reported after it: a repeated key on the transaction, a posting error below the bad line, and a duplicate of a commodity that was dropped. Lexer errors are reported wherever they occur. Stock's parser stays quiet until it has read three tokens after an error, so a flagless header on the line right after a failed directive is not reported. With one blank or comment line between them, it is.
- **Code.** All three use the engine's parse-error code `P0012`, so backend-v2's refusal hint says the text is not valid Beancount rather than "valid but would break the ledger". No response shape changed. `posting-syntax-errors.ts` now exports its stock account pattern (`STOCK_ACCOUNT`) for reuse.
- **Checked against stock.** Compared with bean-check 3.2.3 on about 14,500 random ledgers and on the 126 tracked ledger fixtures, with no difference. A 200,000-line ledger scans in about 85 ms, against 76 ms before.
- **Controls.** These stay clean: `Assets:Cash-`, `Assets:9Cash`, `0.50`, `1.`, `1,000.00`, `txn` and a `P` flag, a `key:` line, a colon inside a string or a `;` comment, an org-mode `:` line, and `Assets:Cash:Sub`.
- **Tests.** `stock-syntax-errors.test.ts` has new cases for each context, each control and each recovery rule. 38 fail with the fix reverted, and disabling any single rule fails at least one test. `verify-rustledger.ts` asserts that the raw engine still loads each repro clean, so the rules are load-bearing. It also asserts that the service reports each one at its line with code `P0012`, and that the controls stay valid.
- **Gates.** `backend-cluster/ledger`: `yarn lint`, `yarn typecheck`, `yarn build`, `yarn test` (234 suites, 4,018 tests) and `yarn verify:rustledger` pass. The hosted repro against `beancount.io` waits for the next ledger deploy.
