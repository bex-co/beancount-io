# A write that adds lines names a new error below them at its line after the write, in the preview and in the refusal: `appendLedgerText` cites `main.bean:91` in an 87-line file, and a one-line-longer `updateEntrySource` cites `main.bean:88`, where `addLedgerEntries` names line 87 (the insert-side twin of w31/101 and w31/102)

**Minor · backend-v2 (`src/features/ledger/workflow/directive-append-workflow.ts`) and ledger (`src/features/ledger/service/ledger-journal-service.ts`) · 45–60m · A1.** Two earlier fixes settled where a new error points when a write is previewed or refused. w5/1202 and w31/101 cover entry deletes, and w31/102 covers the include lines a file delete drops. In each case nothing is committed, so the error is named at its line in the file as it stands. Both packages map back only the lines a write removes (`deletedLines` in `projectWriteErrors`, `droppedLines` in `gateFileWrite`). Lines a write adds are not mapped.

- `appendLedgerText` inserts the text in date order, and adds an `include` line when it routes to a new file. It then diffs the projected errors as they come back (`diffBeanCheckErrors(baseline, projected)`, `directive-append-workflow.ts:261`) and refuses from them (`:278`). So every error below the insertion point is named that many lines lower.
- `updateEntrySource` replaces an entry's lines through `projectWriteErrors` (`ledger-journal-service.ts:1634`) with no line map. An edit that makes an entry longer or shorter therefore shifts every error below it.

`addLedgerEntries` appends at the end of the file, which shifts nothing, so it names the same error at its real line. An agent that follows the refusal to `main.bean:91` reads past the end of the file. In a longer file it reads a different entry.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The credential was an unpinned read/write `bcio_` key on the QA account. The QA ledger `<qa-owner>/mcp-agent-eval` was at its pristine `main.bean` (git blob `f1a0b83c`, 87 lines, `2026-08-29 balance Assets:Cash 49.75 USD` on line 87). Every call below is a dry run or a refused commit, so nothing was written, and the check stayed at 0 errors. Local HEAD `86bfaac78` has the same code.

   - The same call without `dry_run` is refused `VALIDATION_FAILED` "… got 48.75 USD (main.bean:91)".
   - REST `POST …/directives/text` gives `main.bean:91` in the `dryRun` preview and in the `400` refusal. GraphQL `appendLedgerText(dryRun: true)` gives the same line.
2. `addLedgerEntries` with the same transaction and `dry_run` returns the same error at `main.bean:87`.
3. Make the `2026-08-28 "FARMERS MARKET"` entry (line 83) one posting longer: `-24.50 USD` cash, `23.50` groceries, `1.00` coffee. `updateEntrySource {entryHash, sha256sum, newContent, dry_run: true}` returns the same balance error at `main.bean:88`, and so does REST `PUT …/entry-source` with `dryRun`. The refusal without `dry_run` also says "(main.bean:88)".
   - Control: an edit that keeps the entry at three lines (`-24.50` / `24.50`) names `main.bean:87`.

When the ledger already carries errors the effect is worse. With the w31/115 fixture appended above the balance, the `appendLedgerText` refusal for a lot buy named `main.bean:53`. In the file as it stood, line 53 was the header of a different failing sale.

## Fix

- backend-v2, `directive-append-workflow.ts`:
  - Record the lines the write inserts in each target file: each directive's block from `insertDirectives`, and the include lines from `addIncludeLines`.
  - For the refusal and for `dryRun`, map each new error outside those lines back to its current line. This is the inverse of `atCurrentLines`: subtract the inserted lines above the error.
  - An error inside the inserted text has no current line. It keeps its line after the write, which the preview's diff shows.
  - A committed `allowInvalid` write keeps the post-write line, as in w31/102.
- ledger, `projectWriteErrors`:
  - Generalize the `deletedLines` cuts into replacements (`start`, `end`, new length). `updateSourceSlice` should record its replaced range, so an error below the edit is mapped by the size difference. An error inside the edited entry keeps its post-edit line.
  - `moveEntrySources` (`:1531`) passes no map for its source-file cuts or its added include. This was not exercised live. Check it, and fix it in the same change if it has the gap.
- Tests:
  - `appendLedgerText` and `updateEntrySource` parity cases on MCP, REST and GraphQL. The preview and the refusal name the assertion at line 87. An error in the new text keeps its post-write line. The committed `allowInvalid` line is unchanged.
  - Revert the fix and watch the tests fail.

**Resolved 2026-11-27** — A write that adds lines now names each new error at its line in the file as it stands, in the preview and in the refusal. A committed `allowInvalid` write still reports the line after the write, and an error inside the written text keeps the line the preview shows.

- **backend-v2.** `insertDirectives` (`directive-text.ts`) reports every block it writes as an insertion (`insertions`), and `addIncludeLines` (`include-target.ts`) reports where its include lines go. `atLinesBeforeInserts` (`bean-check-errors.ts`) undoes them, last first. `appendLedgerText` (`directive-append-workflow.ts`) refuses from the mapped errors and returns them when `dryRun` is set. MCP, REST and GraphQL all append through that workflow.
- **ledger.** `projectWriteErrors` takes the edits each transform made, `{start, end, lines}` per file in the order they ran, and maps through them with `atLinesBeforeEdits` (`new-ledger-errors.ts`). A delete's cuts are edits with no lines, so w31/101's mapping is the same rule. `updateSourceSlice` records its replaced range and now passes `dryRun`. `moveSourceSlices` had the gap the note suspected: it recorded no cuts and no include line. It now records both and passes `dryRun`. The bulk route behind `addLedgerEntries` (`src/api/entries.ts`) had the same gap when routing added an include line to `main.bean`, and it maps that line now too. backend-v2 relays the ledger's errors for update, move and add, so all three surfaces changed together. No response shape changed.
