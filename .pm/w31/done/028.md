# An open `pushmeta` overrides an entry's own value for the same key on every hosted read; stock Beancount keeps the entry's value, and `moveEntrySources` silently flips it

**Minor · ledger (engine metadata) · 30–45m · A1.** BQL `entry_meta`, entry listings and entry context give a different value from stock `bean-query` for the same file. The `w31/016` move writes stock's reading, so moving such an entry changes its hosted metadata under the same hash with "No new bean-check errors". Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`, run 23, the post-deploy regression sweep of the w31 fixes) on 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`, which was restored byte for byte afterwards (blob `f1a0b83c`), and the check is clean.

## Fixture

```beancount
pushmeta qa-c: "pushed"
2026-09-26 * "PAYEE-C1" "own key"
  qa-c: "own"
  Expenses:Food:Coffee   1.00 USD
  Assets:Cash
popmeta qa-c:
```

## Repro (live)

1. Commit the fixture. `checkLedger` is `[]`, and stock Beancount 3.2.3 `bean-check` is clean.
2. Every hosted read gives `qa-c: "pushed"`:
   - MCP `listLedgerEntries` `meta`
   - MCP `getEntryContext` `meta`
   - MCP `runBqlQueryStructured` `SELECT payee, entry_meta('qa-c')`
   - REST `POST …/query` and `GET …/entry-context?entry_hash=…`
   - GraphQL `queryShellText`
3. Stock `bean-query` 3.2.3 on the same downloaded file gives `qa-c: "own"`. Its grammar sets the pushed values first, then updates them with the entry's explicit metadata.
4. `moveEntrySources` of `PAYEE-C1` to another file previews and commits the text with `qa-c: "own"` only. It skips the pushed key "since its own value wins" (`backend-cluster/ledger/src/foundation/rustledger/source-slice.ts:1020`, `:1068`). After the commit, `movedHashes` resolve and the hash is unchanged, but every hosted read now says `qa-c: "own"`. The answer was "No new bean-check errors".

**Controls:** without a collision, the engine agrees with stock on every case in the same fixture. That covers nested and same-key nested `pushmeta`, a crossing `pushtag`/`pushmeta`, and scopes that do not reach an included file. The `w31/015` append and `w31/016` move keep the hosted reading for all of them.

## Cause

`@rustledger/wasm` 0.24.0 applies the `pushmeta` stack after the entry's own metadata, so the pushed value wins. The ledger service passes that through. It already corrects the engine from the source for note tags (w21/655, `engine.ts`), but not for this.

## Fix

Make the hosted reading match stock: an entry's own key keeps its value inside a `pushmeta` scope. Do it in the ledger service's post-parse pass from the source text, as w21/655 does for note tags, or upstream in rustledger with a pinned bump. The fix must not reimplement the parser. Every read surface uses the shared snapshot, so MCP, REST and GraphQL change together. The `w31/016` move needs no change once the reading is stock's. Note that the hosted engine also gives `pushmeta` to non-transaction directives, where stock does not. That is a known, separate divergence (`w31/016`) and stays out of scope.

**Done when:** on the fixture, MCP `listLedgerEntries`, BQL `entry_meta('qa-c')`, REST `query` and GraphQL `queryShellText` all read `qa-c: "own"`, before and after a `moveEntrySources`. An entry without its own key still reads the pushed value. A `verify:rustledger` or unit case covers the collision and fails with the fix reverted.

Dedupe: searched `.pm/**`, done and blocked included, for pushmeta with own, explicit, wins, precedence and collide. `w31/016` and `w31/018` assume stock's precedence. `w23/041` covers the appended text's stack. `w21/655` covers note tags. None reports the engine's precedence.

---

**Resolved 2026-11-15** — Inside a `pushmeta` scope, an entry that writes the pushed key itself now keeps its own value on every hosted read, as stock Beancount 3.2.3 does. Shipped in the commit carrying this note (`backend-cluster/ledger`).

- **Where the override happens.** It happens in the engine, not in this repository. `@rustledger/wasm` 0.24.0's parser (`apply_inherited_state` in `crates/rustledger-parser/src/cst/convert.rs`) inserts the pushed values after the entry's own metadata. At HEAD `dee333e55`, the raw `getDirectives()`, `parseLedgerFilesInProcess` and BQL `entry_meta('qa-c')` all gave `"pushed"` for `PAYEE-C1`, while `bean-query` 3.2.3 gave `"own"`. The ledger service passed the engine's value through. backend-v2's appended-text stack (w23/041, w31/018) and the w31/016 move already keep the entry's key. Upstream fixed the parser in rustledger `593b7d46` ("let a directive's own key win", #2853, merged 2026-11-04). No published release contains it yet: npm `latest` is 0.24.0, and `v0.24.0` is upstream's newest tag.
- **What changed here.** `pushed-meta.ts` corrects the engine's output from its own second parse. It does not reimplement the parser, the same approach w21/655 takes for note tags. The correction runs only when a file pushes a key that one of its indented lines also writes. In that case the files are parsed a second time with their `pushmeta`/`popmeta` statements blanked, line for line. Each entry then takes the values of the keys it writes from that second parse. Entries are matched by entry ID, which excludes metadata. On such a ledger, BQL runs over the corrected, materialized stream, as it already does for pads. Every read surface uses the shared snapshot or that one BQL entry point, so MCP, REST and GraphQL change together. The w31/016 move needed no change: it writes the entry's own key, which is now also what the hosted reading shows, so a move no longer flips the reading.
- **Results.** The fixture reads `qa-c: "own"` on the journal, the entry context and BQL, both before and after a move, and the hash does not change. An entry that does not write the key still reads `"pushed"`. Inside a nested push of the same key, an entry that writes the key keeps its own value, and an entry that does not reads `"inner"`. Stock `bean-query` 3.2.3 gives the same four readings. A note that writes the key now keeps its own value too, as it does in stock. The engine still gives pushed keys to non-transaction directives that do not write them. That is the separate divergence the note names, and it stays out of scope here.
- **Cost.** A 20,000-entry ledger with one collision takes about 300 ms more to parse, and the snapshot is cached by content. A ledger with no collision makes no second parse. Once a bump brings in `593b7d46`, the two parses agree, and the pass can be removed.
- **Tests.** `pushed-meta.test.ts` covers the collision check, line-for-line blanking (CRLF, and a `pushmeta` inside a multi-line string), and the merge (own value wins, pushed value kept, identical entries matched by order). `engine-pushed-meta.test.ts` checks that the stubbed engine's parse keeps the entry's value, and that BQL runs on the corrected stream only when an entry writes a pushed key. `yarn verify:rustledger` (`verifyOwnKeyUnderPushmeta`, `scripts/entry-move.ts`) runs the fixture and a nested push through the live engine, before and after a move. With the fix reverted, four unit cases fail, and the live check stops on "the journal reads PAYEE-C1 pushed". With only the BQL wiring reverted, it stops on BQL `entry_meta`.
- **Not observable yet.** Production keeps the old reading until the ledger service is redeployed. No live write was made for this change.
- **Gates.** Run in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, ESLint, `yarn lint:deadcode`, Prettier on the changed files, `yarn test` (223 suites, 3457 tests), `yarn verify:rustledger` and `yarn build`.
