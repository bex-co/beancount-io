# A `./`-prefixed `receipt_base_folder` is not normalized before the receipt path is built (w31/152 sibling)

**Minor · backend-v2 (receipt workflow) · 20–30m · A1.** The `w31/152` worker flagged this as a follow-up outside its item. `w31/152` (`db4949816`) normalizes the routing options (`resolveEntryFile`), so a `./`-prefixed `default_file`, budget file, or similar option no longer refuses every routed write. `receipt_base_folder` goes down another path. `src/features/ledger/workflow/ledger-receipt-workflow.ts` reads it as `bcioData.receipt_base_folder || "documents"` and passes it to `buildReceiptPath` unchanged. The path that comes out is sent to `createLedgerFile` as the repository path.

- Expected, not yet run (the worker confirms it first): with `receipt_base_folder` set to `./receipts`, attaching a receipt builds `./receipts/…`. The file write then refuses it as an invalid path, or stores it under a name the `document` directive does not resolve to. It would be the same refusal `w31/152` fixed for the routing options.
- Fix as `w31/152` did: normalize the folder through the same safe-path rule before the path is built. If the option names an unsafe path (`..`, absolute), refuse with a hint that names the option, not the caller's arguments.
- Done when a receipt attach with `./receipts` (and with `receipts/`) stores the file at `receipts/…`, the `document` directive resolves to it, and an unsafe value is refused with the option named. A test covers it and fails with the fix reverted, on every surface that attaches receipts.

---

**Resolved 2026-11-27**: a git-stored receipt now goes to the folder Beancount reads when `receipt_base_folder` is written with a leading `./` or a trailing `/`. Before the fix, the workflow built `./receipts/…` or `receipts//…`. The ledger's create-file check refuses both, and the workflow then reported the refusal as a `500` "Failed to store receipt in ledger repository", after the entry had already passed its check. With `./receipts`, `receipts/` or `.//receipts/2026/`, `insertReceiptTransaction` on MCP, REST `POST …/import/insert-receipt` and GraphQL `insertReceiptTransaction` stores the file at `receipts/…`. The `document` directive names the file relative to the file it is routed to, so it reads `receipts/…` from `main.bean` and `../receipts/…` from `books/docs.bean`. `./` stores receipts at the ledger root. A folder outside the ledger (`../x`, `./receipts/../../x`, `/receipts`) is refused `BAD_USER_INPUT` before anything is checked, downloaded or stored, and so is one a new file can't be stored under (`.git`, `:`, a part ending in a dot, a Windows device name). The message names the option and the folder, for example ``The ledger's `receipt_base_folder` option ("./receipts/../../x") stores receipts in "../x", which is outside the ledger``. The refusal carries no `field`, and its hint says to fix the `custom "beancountio-option" "receipt_base_folder"` line. The in-app assistant's receipt tool calls the same workflow, so it gets the same fix.

- **Fix (backend-v2).** A new `resolveReceiptFolder` in `entry-file-resolver.ts` normalizes the folder with the same rule `w31/152` gave the routing options. `routedPath` and `resolveReceiptFolder` now share that rule as `fromLedgerRoot`. The folder is checked against `unsafeRepoPathRule` and against a new `unportableRepoPathRule`, which is the rule body of `assertPortableRepoPath` (`safe-repo-path.ts`), now readable on its own. `LedgerReceiptWorkflow.gitStrategy` resolves the folder before its entry check. `docs/mcp.md` (`insertReceiptTransaction`) states the rule.
- **Tests.** `receipt-insert-parity.test.ts` stores a receipt under five spellings on REST, GraphQL and MCP and checks the stored path and the document directive's `filename`. It also refuses five unsafe folders on all three surfaces, with the option named, no `field`, no "named argument" hint, and no write, download or stored file. `entry-file-resolver.test.ts` pins the normalization and ten refusals. With the fix reverted, 27 of these cases fail.

Gates: `backend-cluster/backend-v2`: `yarn typecheck`, `yarn test` (510 suites, 13,697 tests), `yarn lint:deadcode`, `yarn format:check` and ESLint on the changed files pass. `yarn generate-v1-openapi` produces no drift.

**Not observable yet.** Production keeps refusing these receipts until backend-v2 is redeployed.

Shipped in the commit carrying this note (`backend-v2`).
