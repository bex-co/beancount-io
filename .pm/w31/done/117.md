# A hosted BQL division answers with 29 significant digits where Beancount and `bea query` answer with 28: `number / 3` on 10000.00 reads `3333.3333333333333333333333333`, not `3333.333333333333333333333333`

**Minor · ledger (`src/features/ledger/service/ledger-shell-mappers.ts`) · 30–45m · A1.** Stock beanquery runs BQL arithmetic in Python's default `Decimal` context: 28 significant digits, rounded half-even. The hosted engine (`@rustledger/wasm` 0.24.0) divides in `rust_decimal`, which keeps up to 29 significant digits when the mantissa fits in 96 bits. The ledger service passes a Decimal cell through as the engine renders it: `toShellCell` (`ledger-shell-mappers.ts:282`) returns any string cell unchanged, and the text table prints it the same way. So every non-terminating quotient of 1 or more carries one digit that stock Beancount and local `bea query` never print. The structured result, the text table, REST and GraphQL all go through `LedgerShellService`, so all of them show it.

The ledger already rounds its own report math to that context. `decimal-context.ts` has `roundWithPythonDecimalContext` and `divideWithPythonDecimalContext`, used for prices, total costs, running balances and lot inventories (#261, #262). BQL results are the one numeric path that skips it. An agent that compares a hosted figure with `bea query` output, or with a value it computed in Python, sees two different numbers for the same average or ratio.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The credential was an unpinned read/write `bcio_` key on the QA account. The QA ledger `<qa-owner>/mcp-agent-eval` was at its pristine `main.bean` (git blob `f1a0b83c`, 87 lines). Every call was a read, so nothing was written. Local HEAD `dda807b0d` has the same mapper.

- MCP `runBqlQueryStructured` returns the hosted value in `table.rows`, and `runBqlQuery` prints it in the text table.
- REST `POST /api-gateway/v1/ledgers/{owner}/{name}/query` and GraphQL `queryShell` / `queryShellText` return the same digits.
- Controls: a quotient below 1 already has 28 significant digits on both sides, because the scale caps at 28 places. `-60.00 / 7` has 28 digits on both sides, because its 29-digit mantissa does not fit in 96 bits. Multiplication of the fixture's amounts (`number * 2`) agrees.
- The oracle is the checkout's own managed engine: `cli/.venv` (beancount 3.2.3, beanquery 0.2.0) with `query.run_query`, and `bea -f main.bean --json query …`, on a copy of the fixture.

## Fix

- ledger, `ledger-shell-mappers.ts`: give a Decimal cell (a string that `isDecimalString` accepts) more than 28 significant digits a pass through `roundWithPythonDecimalContext`. Do it in `toShellCell` and in the text-table formatter, and also for the numbers inside Inventory and Amount cells (`unitsToCurrencyMap`). A value that already fits passes through unchanged, and ledger amounts are refused past 28 digits (w23/081), so only engine arithmetic changes.
- That matches stock for one operation, which is the common case (`sum(x) / n`, `number / 3`). A chained expression such as `number / 3 * 3` rounds every intermediate result in stock. Rounding only the output cannot match it. Leave that to the upstream engine report (rustledger/rustledger#2831 batch, w23/022), and name the residual there.
- Tests: mapper unit cases for the table above (structured and text), plus a live `verify:rustledger` check that runs `number / 3` on `@rustledger/wasm` and expects 28 digits. Revert the fix and watch them fail.

**Resolved 2026-11-27** — A hosted BQL result now prints Python `Decimal`'s 28 significant digits where the engine kept 29. On the note's fixture shape, `number / 3` reads `3333.333333333333333333333333` and `166.6666666666666666666666667`, `SELECT 5/3` reads `1.666666666666666666666666667`, and `SELECT 1/3` still reads `0.3333333333333333333333333333`.

- **ledger.** `decimalTextWithPythonContext` (`decimal-context.ts`) rounds decimal text past 28 significant digits half-even to exactly 28, the way `Decimal` spells an operation's result. Text that already fits passes through unchanged. `ledger-shell-mappers.ts` applies it before both renderers: to every cell of a `Decimal` column, and to the numbers inside Amount, Position and Inventory cells (`convert(position, 'GBP')` at 3 USD per GBP read `33.333333333333333333333333330 GBP`, and a `{{100.00 USD}}` lot over 3 units read a 29-digit cost). An inventory's summed lots round like one more addition. A `str` column is never rounded, however numeric it looks. MCP `runBqlQueryStructured` and `runBqlQuery`, REST `/query`, and GraphQL `queryShell` and `queryShellText` all read `LedgerShellService`, so all of them changed together. backend-v2 passes the cells through and needed no change.
- **Residuals, upstream.** Stock rounds every intermediate result, so a chain such as `1000.00 / 3 * 3` reads `999.9999999999999999999999999` on stock and `1000.000000000000000000000000` hosted. The engine also rounds some exact products to its own 29 digits first, so a false tie can round the other way (`-45.20 USD` at `1/1.20` reads `…666 EUR`, stock `…667`). Rounding the output cannot fix either. Only an engine that computes in the 28-digit context can. Both are recorded as `cells` deviations in `scripts/bql-oracle/allowlist.json` (`decimal-context-chained`, `decimal-context-double-rounding`), so the gate flags them once the engine matches.
- **Tests.** `ledger-shell-decimal-context.test.ts` covers the note's quotients in the structured result and the text table, values that already fit, a trailing-zero extra digit, half-even ties, a carry across a power of ten, Amount, Position and Inventory numbers, summed lots, and a numeric `str` cell. With the fix reverted, 6 of its 8 cases fail. The 2 that pass are the controls. The BQL oracle gains six `main.bean` queries with stock beanquery 0.2.0's answers: a quotient per posting, integer literals, a grouped sum quotient, a dated conversion, and the two residuals. With the fix reverted, `verify:rustledger` fails on the first four. A live check in `verify-rustledger.ts` runs `number / 3` on `@rustledger/wasm`, confirms the engine's 29 digits, and expects 28 in the text table.
- **Checks.** `backend-cluster/ledger`: `yarn typecheck`, `yarn lint:deadcode`, ESLint and Prettier on the changed files, `yarn build`, `yarn test` (233 suites, 3,879 tests) and `yarn verify:rustledger` (88 oracle queries, 43 documented deviations).
- **Not observable yet.** Production keeps the 29-digit answers until the ledger service is redeployed. After that, the note's repro against the QA ledger is the live check.
