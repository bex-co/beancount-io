# `getUserProfile` (`beancount://social/profile`) compares `currentGiteaUsername === username` case-sensitively, dropping all private repositories and activities on mixed-case self-views across MCP, REST, and GraphQL

**Minor · backend-v2 (`UserProfileService.getUserProfile`, `UserProfileService.followUser`) · 25–35m · A1.** Gitea usernames are case-insensitive (`userGet("ALICE")` returns `alice`), and `UserProfileService.getUserStarredRepos` (`ownGiteaClientFor`, `user-profile-service.ts:486`) and `ensureFollowing` (`:299`) already match the caller's username case-insensitively with `.toLowerCase()`. `UserProfileService.getUserProfile` still checks `currentGiteaUsername === username` with strict equality (`user-profile-service.ts:149,193`), so an authenticated caller reading their own profile with any uppercase letter silently loses the authenticated self-view and receives `activities: []` and zero private repositories (`repositories` drops every private ledger) across MCP, REST, and GraphQL. `followUser` (`:257`) has the same case-sensitive self-follow check (`currentUser?.ledger_username === username`). Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, verified at HEAD `b311b440b`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval` (read-only for this finding; disposable write round-trip restored `main.bean` byte-for-byte, blob `f1a0b83c`, sha256 `77c3a591efd311e0`, 0 bean-check errors).

## Repro (live)

Send fresh authenticated requests for the signed-in account's own username in lowercase vs uppercase (`<qa-owner>` vs `<QA-OWNER>`) across MCP, REST, and GraphQL:

1. **MCP (`beancount://social/profile{?username}`):**
   ```sh
   node .agents/skills/qa-shared/scripts/qa-mcp.mjs read 'beancount://social/profile?username=<qa-owner>'

   ```
   - Lowercase `<qa-owner>`: HTTP `200`, `profile.username: "<qa-owner>"`, `repositories: 6` (6 private), `activities: 20`.
   - Uppercase `<QA-OWNER>`: HTTP `200`, `profile.username: "<qa-owner>"`, `repositories: 0` (0 private), `activities: 0`.

2. **REST (`GET /api-gateway/v1/social/profile?username=...`):**
   - Lowercase `<qa-owner>`: HTTP `200`, `repositories: 6` (6 private), `activities: 20`.
   - Uppercase `<QA-OWNER>`: HTTP `200`, `repositories: 0` (0 private), `activities: 0`.

3. **GraphQL (`Query.getUserProfile`):**
   ```graphql
   query { getUserProfile(username: "<QA-OWNER>") { profile { username } activities { id } repositories { name isPrivate } } }
   ```
   - Lowercase `<qa-owner>`: `profile.username: "<qa-owner>"`, `repositories: 6` (6 private), `activities: 20`.
   - Uppercase `<QA-OWNER>`: `profile.username: "<qa-owner>"`, `repositories: 0` (0 private), `activities: 0`.

Expected:

- Reading the authenticated caller's own profile with any casing (`<qa-owner>`, `<QA-OWNER>`, mixed case) resolves `isViewingOwnProfile = true` and returns the same private repositories and activity feed as lowercase `<qa-owner>` on MCP, REST, and GraphQL.
- `followUser` refuses self-follow regardless of casing, matching `ensureFollowing`.

## Working controls

- `beancount://social/profile?username=<qa-owner>` (exact lowercase) returns all 6 private repositories and 20 activities on MCP, REST, and GraphQL.
- `beancount://social/starred-repositories?username=<QA-OWNER>` uses `ownGiteaClientFor` (`user-profile-service.ts:486`), which compares `me.data?.login?.toLowerCase() === username.toLowerCase()`.
- `beancount://<qa-owner>/mcp-agent-eval/collaborators/permission?collaborator=<QA-OWNER>` returns identical `permission: "owner"` output for both `<qa-owner>` and `<QA-OWNER>`.

## Root cause

Not deployment lag — present at HEAD `b311b440b`:

1. `backend-cluster/backend-v2/src/features/gitea/user-profile/service/user-profile-service.ts:148-150` and `:192-194` (`UserProfileService.getUserProfile`):
   ```ts
   const currentGiteaUsername = await this.getCurrentGiteaUsername(userId);
   const isViewingOwnProfile = !!userId && currentGiteaUsername === username;
   ```
   Strict `===` fails whenever `username` differs in case from `user.ledger_username` (and `getCurrentGiteaUsername` is also fetched twice in the same call). When `isViewingOwnProfile` evaluates to `false`, both `userListActivityFeeds` and `userListRepos` fall through to the anonymous Gitea client, which returns no activities and omits all private repositories.
2. `backend-cluster/backend-v2/src/features/gitea/user-profile/service/user-profile-service.ts:257` (`UserProfileService.followUser`):
   ```ts
   if (currentUser?.ledger_username === username) {
   ```
   Strict `===` misses case-differing self-follows, unlike `ensureFollowing` at `:299` (`currentUser?.ledger_username.toLowerCase() === username.toLowerCase()`).

## Fix

In `backend-cluster/backend-v2`:

1. In `UserProfileService.getUserProfile` (`src/features/gitea/user-profile/service/user-profile-service.ts:146-225`):
   - Compute `currentGiteaUsername` once and compare case-insensitively:
     `const isViewingOwnProfile = !!userId && !!currentGiteaUsername && currentGiteaUsername.toLowerCase() === username.toLowerCase();`
   - Also pass the canonical login (`user.login || username`, or the existing `username` which Gitea accepts case-insensitively — verify both match Gitea's `userListActivityFeeds` / `userListRepos` behavior) using the authenticated `authClient` when `isViewingOwnProfile` is true.
2. In `UserProfileService.followUser` (`src/features/gitea/user-profile/service/user-profile-service.ts:257`):
   - Compare case-insensitively (`currentUser?.ledger_username?.toLowerCase() === username.toLowerCase()`), matching `ensureFollowing` at `:299`.
3. Add unit and 3-surface parity tests:
   - In `src/features/gitea/user-profile/api/__tests__/public-profile-parity.test.ts`: assert that an authenticated caller querying `"ADA"` (mixed/upper case of their own `"ada"` login) gets the same private repositories and activities as `"ada"` across MCP (`beancount://social/profile?username=ADA`), REST (`GET /api-gateway/v1/social/profile?username=ADA`), and GraphQL (`getUserProfile(username: "ADA")`), while another user querying `"ADA"` still receives only the public view.
   - In `src/features/gitea/user-profile/service/__tests__/user-profile-service.test.ts`: cover case-insensitive self-view in `getUserProfile` and case-insensitive self-follow refusal in `followUser`.
