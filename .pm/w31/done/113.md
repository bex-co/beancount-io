# A balance assertion that is already failing reads as a new error once a write changes its "got" figure: `appendLedgerText` and the file writes refuse a valid entry that `addLedgerEntries` accepts, and MCP's `addLedgerEntries` commit reports "1 new bean-check error" after a clean preview (w21/618 fixed only the ledger service)

**Minor · backend-v2 (`src/features/ledger/utils/bean-check-errors.ts`) · 20–30m · A1.** `docs/mcp.md` says of every write: "Errors the ledger already had never block." The ledger service keeps that promise for a failing balance assertion. Its `newLedgerErrors` (`backend-cluster/ledger/src/features/ledger/utils/new-ledger-errors.ts:33`) matches `Balance failed for A: expected X, got Y` and `Balance exceeds explicit tolerance for A: expected X ~ T, got Y (difference: D)` on the account and the expected amount, and ignores the figure the account reached (w21/618, w21/681). backend-v2 has its own copy of that rule, `diffBeanCheckErrors` (`bean-check-errors.ts:176`). Its comment says it restates the ledger service's rule, but its `withoutEntryTag` (`:131`) strips only the `(2026-08-30, "Groceries")` entry tag. It never got the w21/618 or w21/681 trim.

So, while an assertion is off, any write that adds or changes a posting above it changes "got". backend-v2 then reads the same assertion as a new error. That diff decides the outcome for:

- `appendLedgerText` on MCP, REST and GraphQL (`directive-append-workflow.ts:261`): the preview answers `valid: false`, and the commit is refused `VALIDATION_FAILED`.
- `createLedgerFiles`, `updateLedgerFiles` and `deleteLedgerFiles`, REST `PUT`/`DELETE …/files/{path}`, and `renameAccount` (`file-write-gate.ts:134`): the same preview and refusal.
- The result an MCP commit returns. `withPostWriteValidation` (`write-validation.ts:83`) re-diffs the ledger after the write for `addLedgerEntries`, `updateEntrySource`, `deleteEntrySource(s)`, `moveEntrySources`, the file writes and `insertReceiptTransaction` (`mcp-tools.ts:518`, `:597`, `mcp-source-slices.ts:159`, `edit-ledger-files-tool.ts:624`). Those commits go through, but their result reports a new error that the preview did not.

The structured writes are judged by the ledger service instead, so they disagree with the text writes on the same entry. This is the reconcile case the `reconcile-account` prompt drives: an account is off, and the agent adds the missing transactions one at a time.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check shows 0 errors. The diff is reproduced on local HEAD `d5557bf6d`.

## Repro

The ledger is the eval fixture: `2026-08-29 balance Assets:Cash 49.75 USD` passes.

1. Make one assertion fail. `appendLedgerText {"text": "2026-08-30 balance Assets:Cash 40.00 USD", "allowInvalid": true}` commits with `errorsAfter: 1`: `Balance failed for Assets:Cash: expected 40.00 USD, got 49.75 USD (main.bean:89)`, code `E2001`.
2. Preview the same balanced entry two ways. The entry is dated `2026-08-29`, with `Assets:Cash -5.00 USD` and `Expenses:Food:Coffee 5.00 USD`, so "got" becomes 44.75.
   - `addLedgerEntries` with `dry_run: true` answers "Would add 1 entry. No new bean-check errors." with `validation: {errorsBefore: 1, errorsAfter: 1, newErrors: [], valid: true}`. REST `POST …/entries` with `dryRun` answers the same.
   - `appendLedgerText` with the same entry as text and `dry_run: true` answers "1 new bean-check error: Balance failed for Assets:Cash: expected 40.00 USD, got 44.75 USD (main.bean:93)" with `{errorsBefore: 1, errorsAfter: 1, newErrors: [that], valid: false}`. REST `POST …/directives/text` with `dryRun` and GraphQL `appendLedgerText(dryRun: true)` return the same `valid: false`.
   - `updateLedgerFiles` with `dry_run`, inserting the same text above the assertion through `old_string`/`new_string`, also answers `valid: false`, with the same error.
3. Commit the append (no `allowInvalid`). It is refused `VALIDATION_FAILED`: "appending it would introduce 1 new bean-check error: Balance failed for Assets:Cash: expected 40.00 USD, got 44.75 USD (main.bean:93)". Nothing is written.
4. Commit the entry through MCP `addLedgerEntries` (no `dry_run`). It commits, but the result says "Added 1 entry to main.bean. 1 new bean-check error: Balance failed … got 44.75 USD (main.bean:89)" with `valid: false`. The preview of that exact call said `valid: true`.

`errorsBefore` equals `errorsAfter` in every case. The "new" error is the assertion the ledger already had. On HEAD, `diffBeanCheckErrors([{message: "Balance failed for Assets:Cash: expected 40.00 USD, got 49.75 USD"}], [{message: "…got 44.75 USD"}])` returns the second error as new. The explicit-tolerance wording behaves the same way.

## Fix

- In backend-v2's `withoutEntryTag`, apply the ledger service's second replacement too: `^(Balance (?:failed|exceeds explicit tolerance) for [^:]+:.*?expected [^,]*), got .*$` → `$1`. Keep the per-message count, so a second failing assertion still counts as new. The packages share no code, so restate the rule and pin it with the same cases as `new-ledger-errors.test.ts`.
- Tests:
  - `bean-check-errors.test.ts`: a changed "got" for both wordings is not new; a second failing assertion on the same account is new; an assertion whose expected amount changes is new.
  - A parity case in `directive-text-parity.test.ts`: the preview and commit of `appendLedgerText` on MCP, REST and GraphQL over a baseline with a failing assertion.
  - A case for MCP's `addLedgerEntries` commit result.
  - Revert the fix and watch them fail.

## Done when

With an assertion already failing, the four calls above all agree: `appendLedgerText`, `updateLedgerFiles` and `addLedgerEntries` each preview `valid: true` with `newErrors: []`. The append commits without `allowInvalid`. MCP's `addLedgerEntries` commit reports "No new bean-check errors". A write that makes a passing assertion fail is still reported as new.
