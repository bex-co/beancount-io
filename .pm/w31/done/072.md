# `listStagedBankTransactions` and `bank-transactions/unsynced` silently ignore `page` when `limit` is omitted and drop the pagination signal for `page > 1`

**Minor · backend-v2 (`PlaidItemService.getUnsyncedTransactions`, `page-signals.ts`) · 30–45m · A1.** When a caller passes `page` without `limit` to staged bank transactions (`listStagedBankTransactions`, `beancount://{owner}/{name}/bank-transactions/unsynced`, REST `GET /api-gateway/v1/ledgers/{owner}/{name}/bank-transactions/unsynced`, or GraphQL `getUnsyncedPlaidTransactions`), `pageOf` (`plaid-item-service.ts:153-157`) checks `if (limit === undefined || limit === null) return rows;` and silently ignores `page` — returning every staged row from page 1 even when `page: 2` was requested. At the same time, `page-signals.ts:49,111-112` registers both reads with bare `numberedArray()` (no default limit), so `page > 1` without `limit` drops the pagination signal altogether on all four surfaces (no `structuredContent.page` on the MCP tool, no `_meta.page` or second content item on the MCP resource, no `X-Has-More` header on REST, and no `extensions.page` on GraphQL), while `page: 1` without `limit` reports `hasMore: false`. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, verified at HEAD `69d4680b6`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval` (read-only for this finding; disposable write round-trip restored `main.bean` byte-for-byte, sha256 `77c3a591efd311e0`, 0 bean-check errors).

# 2. MCP resource with page=2 and no limit -> 1 content item, no _meta.page or second page item

REST and GraphQL controls (same credential, repeated in fresh requests):
- `GET /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/bank-transactions/unsynced?page=2` → `200 OK []` with **no** `X-Has-More` header (`x-has-more: null`).
- GraphQL `query { getUnsyncedPlaidTransactions(ledgerId: "<qa-owner>/mcp-agent-eval", page: 2) { transactionId } }` → `{"data":{"getUnsyncedPlaidTransactions":[]}}` with **no** `extensions.page`.

Controls (same ledger, same credential):
- Omitted `page`/`limit` or `page: 1` returns `page: {"returned":0,"page":1,"hasMore":false}` on MCP tool, 2 content items with `_meta.page` on MCP resource, `X-Has-More: false` on REST, and `extensions.page` on GraphQL.
- `page: 2, limit: 10` returns `page: {"returned":0,"limit":10,"page":2,"hasMore":false}` on MCP tool, `_meta.page` + second item on MCP resource, `X-Has-More: false` on REST, and `extensions.page` on GraphQL.
- Working sibling control (`w31/012`): `listLedgers({ page: 2 })`, `beancount://catalog/ledgers?page=2`, and GraphQL `listLedgers(page: 2)` all apply the documented default page size (`30`) and emit `{"returned":0,"limit":30,"page":2,"hasMore":false}` across every surface.

Expected:
- Omitting both `page` and `limit` continues to return every staged row with `{ returned, page: 1, hasMore: false }` (preserving the dashboard Bank Sync table's full-list read).
- Passing `page` without `limit` slices with a documented default page size (`HOST_DEFAULT_LIMIT` = 30, matching `listLedgers` and `ownedLedgers` from `w31/012`) instead of silently returning all rows from page 1, and emits the matching `{ returned, limit: 30, page, hasMore, nextPage? }` signal on MCP tool, MCP resource (`_meta.page` and second content item), REST (`X-Has-More` and `Link`), and GraphQL (`extensions.page`).

## Root cause

Not deployment lag — present at HEAD `69d4680b6`:

- `backend-cluster/backend-v2/src/features/plaid/service/plaid-item-service.ts:153-157`: `pageOf` returns `rows` unpaged whenever `limit === undefined || limit === null`, ignoring an explicit `page` parameter. On a ledger with staged rows (e.g. 50 rows), requesting `page: 2` without `limit` returns all 50 rows from page 1 again.
- `backend-cluster/backend-v2/src/server/api/page-signals.ts:49,111-112`: `listStagedBankTransactions` and `bankUnsyncedTransactions` use `numberedArray()` with no default limit (unlike `catalogArray` at lines 58-63), so `page > 1 && limit === undefined` returns `undefined` and omits the page signal everywhere.
- `backend-cluster/backend-v2/src/features/ai-agent/api/mcp-list-tools.ts:73-86` documents `page` as `"1-based page number, defaults to 1."` and `limit` as optional, giving callers no indication that `page` is ignored unless `limit` is supplied.

In `backend-cluster/backend-v2`:

Update `pageOf` in `src/features/plaid/service/plaid-item-service.ts` so that when both `page` and `limit` are nullish it returns all rows (preserving the dashboard's full-list read), and when `page` is provided without `limit` it slices using `HOST_DEFAULT_LIMIT` (30), matching `listLedgers` / `ownedLedgers`.
