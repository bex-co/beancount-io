# backend-v2 `TagStack` does not apply pushed tags to `note` and `document` entries

Source: follow-up from `w31/016` (`71c06b859`), 2026-11-15.

- The hosted engine gives an open `pushtag`'s tags to every directive. It also gives `pushmeta`'s metadata to every directive, where stock Beancount gives it only to transactions.
- backend-v2's `TagStack` (its `annotate` rules) does not tag `note` or `document` entries. The `w31/015` append fix (`96adc02e4`) relies on these rules, so a note or document written inside, or next to, a `pushtag` scope may be described differently from how the engine reads it.
- First confirm whether this changes any result a client sees: write a `note` and a `document` inside a `pushtag`/`pushmeta` scope on the QA ledger, and compare what the tools report with what the engine reads back. Restore the ledger byte for byte afterwards.

**Done when:** backend-v2 tags `note` and `document` entries exactly as the hosted engine does, a test pins that behaviour, or the note is closed with evidence that no client-visible result differs.

---

**Resolved 2026-11-15** — `appendLedgerText` now writes a `pushtag` in its own text onto the enclosed notes and documents, as well as onto transactions. Before, the tag was dropped from them, and the write still read "No new bean-check errors". Stock Beancount 3.2.3 tags all three from the stack, and the hosted engine does too, since the ledger service restores note and document tags (w21/655). MCP, REST `POST …/directives/text` and GraphQL `appendLedgerText` share `parseDirectiveText` (`backend-cluster/backend-v2/src/features/ledger/utils/directive-text.ts`), so all three changed together, and no response shape changed. Metadata was already right: `pushmeta` goes under every enclosed directive, which is how the engine reads it. Three adjacent `TagStack.annotate` gaps that changed what was stored are also fixed:
- A header whose string runs onto an indented line gets the tag after the closing quote, and the metadata under that line. Before, both landed inside the string.
- A `#tag` inside a narration or a note's comment no longer counts as one the entry writes, so the pushed tag is still added.
- A key set on a posting no longer stops the pushed key from going on the entry.

The file-scope side, `w31/015`'s `outsideScopes`, already handles every directive kind the same way, so nothing changed there. `docs/mcp.md` "Writing directives as Beancount text" states the rule.

Client-visible before the fix: on the QA ledger `<qa-owner>/mcp-agent-eval`, the deployed `appendLedgerText` dry run of `pushtag #t` / `pushmeta k: "v"` around a note, a document and a transaction previewed the note and document without `#t`, and only the transaction with it. Hosted engine check, with writes made through the file tools: three copies of that block were committed through `updateLedgerFiles`. The first was the text itself, written in place. The second was what HEAD's append writes, and the third was what the fixed append writes. `listLedgerEntries {filter: "#t"}` returned the note, document and transaction of the in-place copy and of the fixed copy, but only the transaction of HEAD's copy. Every note and document carried `k: "v"` in `meta`, including the in-place ones, which confirms the engine reads `pushmeta` on every directive. Stock Beancount 3.2.3, loading the same file, agrees on the tags. `main.bean` was restored byte for byte (blob `f1a0b83c`), and `checkLedger` is clean.

Tests:
- `directive-text.test.ts`: w23/041's case now expects the enclosed note and document to be tagged, and a `balance` not to be. New cases cover a header that runs onto an indented line, a tag inside a string, and a body tag line with a posting's key.
- `directive-text-parity.test.ts`: appends a scoped note and document through REST, GraphQL and MCP, and checks the preview diff, the committed file and `wrote`.

With the fix reverted, 7 of these fail. Gates, run in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, `yarn lint:deadcode`, `yarn format:check`, ESLint on the changed files, `yarn test` (484 suites, all passing), and `yarn generate-v1-openapi` with no drift. Shipped in the commit carrying this note (`backend-v2`).
