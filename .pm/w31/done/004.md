# `tools/list` declares `ledger.write` on `parseFile`, `parseReceipt` and `generateTempAssetUploadUrl`, but a `ledger.read` credential may call all three

**Minor · backend-v2 (MCP `securitySchemes`, docs) · 30–45m · A1.** Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`), 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). Credentials: an unpinned `bcio_` key with `ledger.read` only, and an unpinned read/write key as the control, both on the QA account. Nothing was written.

- **Repro.** Send `generateTempAssetUploadUrl { filename: "qa.csv", mimeType: "text/csv" }` with the `ledger.read` key. The call succeeds and returns `uploadUrl`, `objectKey`, `expiresIn: 300` and `uploadHeaders`. REST `POST /api-gateway/v1/temp-assets/upload-url` answers 200 to the same key, and so does GraphQL `generateTempAssetUploadUrl`. The same `tools/list` gives this tool `securitySchemes: [{ type: "oauth2", scopes: ["ledger.write"] }]`, and it does the same for `parseFile` and `parseReceipt`.
- **The server accepts the read key on purpose.** `ASSISTED_FILE_PARSE`, `ASSISTED_RECEIPT_PARSE` and `TEMP_ASSET_UPLOAD_CREATE` require `capability: "read"` (`src/server/api/authorization/authorization-service.ts:550`, `:559`, `:587`). The `VERB_TABLE` comment at `src/server/api/op-class.ts:1701` says "the operation class is not a credential ceiling". `docs/mcp.md` agrees: "The existing policy requires read capability for both operations, including URL creation" (line 2070), and `parseFile` / `parseReceipt` "allow read capability" (lines 2092, 2116).
- **The declaration is where they differ.** `mcpToolSecuritySchemes` (`src/server/api/op-class.ts:2265`) maps each verb's op `class` through `SCOPE_FOR_CLASS`. These three verbs keep `class: "write"` for their rate budget, so the tools declare `ledger.write`. That follows ADR 019 D2 to the letter ("the scope the tool's op class requires", `docs/adrs/ADR019-backend-v2-mcp-host-compatibility.md:95`). But `docs/mcp.md:369` says each tool declares "the scope its most privileged operation needs", and for these three that scope is `ledger.read`. The Tools table (`docs/mcp.md:347`–`349`) also lists them as `Write`, which contradicts their own sections.
- **Why it matters.** Per ADR 019 D2, ChatGPT uses this declaration to decide when to ask the user for a broader scope. A user who linked with `ledger.read` would be asked for `ledger.write` before they could parse a statement or receipt, even though the server accepts the read grant. A broader grant than needed is the cost.
- **Completeness.** I joined every MCP tool's `VERB_TABLE` class with its PDP credential capability, and checked it live: the `ledger.read` key called all 47 tools with previews or made-up ids. Only these three tools differ. Every other tool declared `ledger.write` or `ledger.admin` refuses the read key with `FORBIDDEN`. Every tool declared `ledger.read` accepts it. `previewLedgerSetup` and `listBankConnections` declare `ledger.admin` and require it. `parseFile` and `parseReceipt` were not run on a real upload, because that spends AI quota. Their read capability is taken from the policy table and the docs.

**Done when:** `tools/list` declares `ledger.read` for `parseFile`, `parseReceipt` and `generateTempAssetUploadUrl`, while their write-class rate budgets stay the same. The declared scope comes from the strictest credential capability the tool's verbs' PDP actions require, falling back to the op class for verbs without an action. A case in `src/server/api/__tests__/mcp-tool-list.test.ts` asserts that rule for every tool, and it fails with the fix reverted. In `docs/mcp.md`, the Tools table shows these three as needing read authority with a write rate budget. ADR 019 D2 gets an amendment saying the declaration follows the credential requirement. If the owner would rather require `ledger.write` for these operations, that is a decision for the owner, since `docs/mcp.md` documents read capability as existing policy on all three surfaces. Package: `backend-cluster/backend-v2`. The REST and GraphQL behavior does not change.

---

**Resolved 2026-11-15** — `mcpToolSecuritySchemes` (`backend-cluster/backend-v2/src/server/api/op-class.ts`) now takes each verb's scope from the capability its PDP action's credential requirement checks, read through the new `authorizationActionCredentialCapability` (`src/server/api/authorization/authorization-service.ts`). An action that checks no capability declares OAuth without a scope, and only a verb with no action falls back to its op class. `parseFile`, `parseReceipt` and `generateTempAssetUploadUrl` now declare `ledger.read` on `tools/list`. Their `VERB_TABLE` class stays `write`, so their rate budgets are unchanged, and REST and GraphQL behavior does not change. In `src/server/api/__tests__/mcp-tool-list.test.ts`, one case derives the expected scope for every tool on the wire from that rule, and it fails with the fix reverted, naming exactly these three tools. Another case pins the three tools at `ledger.read` while they keep the `write` class. A third covers an action that checks no capability. `docs/mcp.md` marks the three as **Read, write budget** in its Tools table and states the rule beside `securitySchemes`. ADR 019 D2 has a 2026-11-15 amendment. Before the change, the live repro against `https://beancount.io` with the unpinned `ledger.read` QA key still showed `ledger.write` on all three tools, and the key still got an upload URL. Production declares `ledger.read` after the next backend deploy. Gates in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, `yarn test` (482 suites, 10782 tests), `yarn lint:deadcode`, `yarn format:check`, and an OpenAPI regeneration with no drift. Shipped in this commit (`backend-v2`).
