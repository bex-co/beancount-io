# An entry dated `2026/08/30` or `2026-8-30` is listed with `source: null`, and every entry-hash tool answers `NOT_FOUND` for the hash `listLedgerEntries` just returned, on MCP, REST and GraphQL

**Minor · ledger (`src/foundation/rustledger/source-slice.ts`) · 30–45m · A1.** Stock Beancount's lexer reads a date as `[0-9]{4,}[\-/][0-9]+[\-/][0-9]+` (`beancount/parser/lexer.l:267`), so `2026/08/30` and `2026-8-30` are valid dates. The hosted engine (`@rustledger/wasm` 0.24.0) loads both. `bean-check` 3.2.3 and `checkLedger` both report the ledger clean. `updateLedgerFiles` writes such an entry, and w23/240 names it as the tool for slash dates. But the ledger service finds an entry's source only in a block whose first line starts `YYYY-MM-DD`. A valid entry with any other spelling of its date therefore has no source.

- `listLedgerEntries` with `include_source` returns `source: null` for it. The tool description says `null` means "a plugin's or a pad's copy, a managed price line", not an entry the user wrote in `main.bean`.
- `getEntryContext`, `updateEntrySource`, `deleteEntrySource`, `deleteEntrySources` and `moveEntrySources` all refuse its hash with `NOT_FOUND` "Entry with ID '…' not found". A correct `sha256sum` does not help, and `dry_run` gets the same answer.
- The hint says "Entry hashes change when an entry is edited…; read fresh ones with `listLedgerEntries`". That call returns the same hash, so an agent that follows the hint loops.
- A ledger converted from ledger-cli, which writes `2026/08/30`, has every entry in this state.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26.

- **Target:** `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). Local HEAD `2e8f71586` has the same code.
- **Credential:** an unpinned read/write `bcio_` key on the QA account.
- **Writes:** only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. The QA commits were `ad06bfd2` (slash-dated probe), `2aa7cb0e` (unpadded probe) and `654c73e2` (restore).
- **Cleanup:** `main.bean` was restored byte for byte (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check showed 0 errors.

## Cause

- `backend-cluster/ledger/src/foundation/rustledger/source-slice.ts:135`: `DATE_PREFIX = /^\d{4}-\d{2}-\d{2}\b/`.
  - `isTopLevelStart` (`:343`) uses it, so a line starting `2026/08/30` or `2026-8-30` opens no block, and `splitIntoBlocks` (`:387`) skips the entry's header and postings.
  - `isDated` (`:419`) uses it too.
  - `buildSourceDetailsProbe` (`:435`) marks only dated blocks, so the entry carries no source details: it gets `source: null` and no filename or line.
  - `indexDatedBlocks` (`:568`), which the entry reads and edits look hashes up in, never holds the entry, so every lookup by hash is `NOT_FOUND`.
- Checked in-process at HEAD: `splitIntoBlocks` on the balance line followed by a `2026/08/30` and a `2026-8-31` transaction returns the balance block alone.
- `DATED_HEADER_RE` (`:965`) and the document/note pattern (`:825`) in the same file have the same `\d{4}-\d{2}-\d{2}` shape.

## Fix

Have the source slicer accept every date the lexer accepts: four digits, then `-` or `/`, a one- or two-digit month, `-` or `/`, and a one- or two-digit day. `managed-price-overlay.ts:79` already matches dates this way (w1/163).

- Use one shared pattern for `DATE_PREFIX`, `DATED_HEADER_RE` and the `:825` pattern, so a slash-dated or unpadded entry is a dated block with its own slice and `sha256sum`.
- The slice stays the text as written. Its checksum is the hash of those bytes.
- `updateEntrySource`'s `newContent` check (`entry-tokens.ts:348`) and `appendLedgerText` (w23/240) still take dashes only. An edit may therefore rewrite `2026/08/30` as `2026-08-30`, which loads the same.

All four surfaces reach this one ledger code path: the MCP tools and the `entry-context` resource, REST `entry-context` and the entry-source routes, and GraphQL `getLedgerEntryContext` and the source mutations. They change together, and no response shape changes.

## Blast radius

The same `^\d{4}-\d{2}-\d{2}` dated-header pattern is in other ledger-service shims that make engine output match stock Beancount. Their effect on a slash-dated entry was not checked; decide each one or list it as a known gap. They are:

- `entry-sort-order.ts:26`: the same-day order, keyed `date|type`. It needs the date normalized as well as matched.
- `block-index.ts:38-39`, `pre-open-uses.ts:11`, `generated-closes.ts:139`, `pad-tolerance.ts:61`, `balance-error-dates.ts:7`, `meta-order.ts:11`, `one-commodity.ts:12`, `book-errors.ts:18`, `noduplicates.ts:68`, `unique-prices.ts:14`, `stock-syntax-errors.ts:33-39`, `parse-errors.ts:67`, `balance-tolerance-syntax.ts:27`, and `engine.ts:491,502,517`.

Not affected:

- backend-v2's `insertDirectives`: a local run put a `2026-09-01` append before an existing `2026/09/15` entry, as it should.
- BQL `filename`/`lineno`: they are empty for dash-dated entries too, which is the known gap in w23/022.

**Resolved 2026-11-26** — The ledger service's source slicer now reads every date the lexer reads: four digits, `-` or `/`, a one- or two-digit month, `-` or `/`, and a one- or two-digit day. One pattern, `SOURCE_DATE` in `backend-cluster/ledger/src/foundation/rustledger/source-date.ts`, now drives `DATE_PREFIX`, `DATED_HEADER_RE` and the document/note pattern in `source-slice.ts`. A `2026/08/30` or `2026-8-30` entry is a dated block again, with its own slice and the `sha256sum` of its bytes as written. That gives it a `source` on `listLedgerEntries`, and `getEntryContext`, `updateEntrySource`, `deleteEntrySource(s)` and `moveEntrySources` all resolve it on every surface, since they share this one ledger path. No response shape changes. Shipped in the commit carrying this note (`backend-cluster/ledger`).

- **Blast radius, fixed.** `entry-sort-order.ts` keys a slash-dated or unpadded header on the engine's `YYYY-MM-DD`, so same-day order follows the source. `block-index.ts` reads such opens and closes, and `entryLocator` matches such headers. Before, `generated-closes.ts` took a written `2026/04/01 close` for close_tree's and repeated the engine's inactive-account error, and the locator left errors on slash-dated transactions without a line.
- **Blast radius, known gap.** These shims still match only `YYYY-MM-DD`: `pre-open-uses.ts:11`, `generated-closes.ts:139` (pad), `pad-tolerance.ts:61`, `balance-error-dates.ts:7`, `meta-order.ts:11`, `one-commodity.ts:12`, `book-errors.ts:18`, `noduplicates.ts:48,68`, `unique-prices.ts:14,114`, `stock-syntax-errors.ts:33-39`, `parse-errors.ts:67`, `balance-tolerance-syntax.ts:27` and `engine.ts:491,502,517`. For a slash-dated or unpadded entry, each one leaves the engine's own result in place, exactly as before this change. Each consumer reaches the newly visible blocks only through its own dash-only pattern or an ISO-date prefix test, so none of them regresses. Moving each one to `SOURCE_DATE` and `sourceDateOf` is the follow-up, with a test per shim.
- **Tests.** `source-slice.test.ts` covers five date spellings: `splitIntoBlocks`, `indexDatedBlocks` and the CAS re-location treat `2026/08/30`, `2026-8-30`, `2026/8/30` and `2026-08/30` like `2026-08-30`.
