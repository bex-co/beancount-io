# Four v1 REST request body schemas omit `.strict()`, silently stripping misspelled safety/preview flags (`dryrun`, `allowinvalid`, `remove_include`, `sourceAccout`) — breaking parity with MCP (`w5/039`, `w23/057`)

**Major · backend-v2 + cli (`files-handler.ts`, `banks-handler.ts`, `query-handler.ts`, OpenAPI snapshot + CLI pin) · 30–45m · A1.** On MCP, `refusingUnknownArguments` (`src/server/api/composition-root.ts:1048-1096`) rejects unknown keys at both root and nested object levels so a misspelled preview flag (`dryrun: true`) never silently commits a write (`w5/039`) and a misspelled bank submission key (`source_account` / `sourceAccout`) never silently books against the default bank mapping (`w23/057`). Four v1 REST request body schemas still use plain `z.object(...)` without `.strict()`:

1. `PUT /api-gateway/v1/ledgers/{owner}/{name}/files/{*path}` (`putBodySchema`, `files-handler.ts:69-94`) — a misspelled `dryrun: true` or `allowinvalid: true` is silently stripped and **commits the file write immediately**.
2. `DELETE /api-gateway/v1/ledgers/{owner}/{name}/files/{*path}` (`deleteBodySchema`, `files-handler.ts:96-109`) — a misspelled `dryrun: true` or `remove_include: true` is silently stripped and **permanently deletes the file**.
3. `POST /api-gateway/v1/ledgers/{owner}/{name}/bank-transactions/submit` (`transactions[]` item schema, `banks-handler.ts:251-265`) — outer body has `.strict()`, but the nested item schema omits `.strict()`, so a misspelled `sourceAccout` or pasted MCP snake-case `source_account` is silently stripped and books against the default bank mapping (contradicting `w23/done/175`, which noted *"a pasted snake key dies in strict validation"*).
4. `POST /api-gateway/v1/ledgers/{owner}/{name}/query` (`queryBodySchema`, `query-handler.ts:6-15`) — silently strips unknown body keys, while MCP `runBqlQuery` / `runBqlQueryStructured` refuse them with `BAD_USER_INPUT`.

## Repro

1. `PUT /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/files/qa-nonexistent.bean` with `{"content":"; test\n","message":"test","dryRun":true,"dryrun":false}` (or `bogusKey: 1`):
   - **Actual:** HTTP `200` `{"ok":true,"path":"qa-nonexistent.bean","dryRun":true,"valid":true,"newErrors":[],"notLoaded":["qa-nonexistent.bean"]}` — unknown key silently stripped (sending `"dryrun": true` alone would strip it and commit).
   - **MCP control (`createLedgerFiles` / `updateLedgerFiles`):** `isError: true`, `BAD_USER_INPUT`: `Unrecognized key: "dryrun"`.
2. `DELETE /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/files/qa-nonexistent.bean` with `{"message":"test","dryRun":true,"bogusKey":1}`:
   - **Actual:** HTTP `200` — unknown key silently stripped.
   - **MCP control (`deleteLedgerFiles`):** `isError: true`, `BAD_USER_INPUT`: `Unrecognized key: "bogusKey"`.
3. `POST /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/bank-transactions/submit?dry_run=true` with `{"transactions":[{"transactionId":"ptxn_nonexistent","targetAccount":"Expenses:Food:Coffee","sourceAccout":"Assets:Cash"}]}`:
   - **Actual:** HTTP `400` `BAD_USER_INPUT`: `"Some transactions not found in database"` — `sourceAccout` was silently stripped and the request proceeded into `PlaidSyncService.submitTransactionsToLedger` / DB lookup.
   - **MCP control (`importStagedBankTransactions`):** `isError: true`, `BAD_USER_INPUT`: `"transactions.0: Unrecognized key: \"sourceAccout\""` (refused before any service/DB call).
4. `POST /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/query` with `{"query":"BALANCES","bogusKey":1}`:
   - **Actual:** HTTP `200` returning the `BALANCES` table — unknown key silently stripped.
   - **MCP control (`runBqlQuery`):** `isError: true`, `BAD_USER_INPUT`: `Unrecognized key: "bogusKey"`.
5. Working REST controls on the same deployment: every other v1 JSON body (`POST .../entries`, `POST .../directives/text`, `POST .../rename-file`, `POST .../rename-account`, `POST .../revert-commit`, `POST .../entry-source/*`, `POST .../pull-requests`, `POST/PUT/DELETE .../ledgers`, `PUT/DELETE .../collaborators`, `POST .../temp-assets/upload-url`, `POST .../import/parse-file`, `POST .../import/insert-receipt`, `POST .../import/suggest-categories`) already uses `.strict()` / `z.strictObject(...)`, and `v1Route` already rejects unknown query params on all v1 routes (`GET .../files/main.bean?bogusQuery=1` → HTTP `400 VALIDATION_FAILED`).

## Expected

All four v1 REST body schemas reject unknown keys at HTTP `400 VALIDATION_FAILED` naming the unrecognized key before calling any service or database, matching MCP and GraphQL strict-input behavior. (`POST /api-gateway/v1/token/introspect` is intentionally left non-strict per RFC 7662 extension parameters.)

## Root cause

Four Zod object schemas were declared with `z.object(...)` instead of `.strict()` / `z.strictObject(...)`:

- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/files-handler.ts:69-94` (`putBodySchema`)
- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/files-handler.ts:96-109` (`deleteBodySchema`)
- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/banks-handler.ts:251-265` (element schema inside `BankTransactionSubmission.transactions`)
- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/query-handler.ts:6-15` (`queryBodySchema`)

## Fix

1. Add `.strict()` to:
   - `putBodySchema` and `deleteBodySchema` in `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/files-handler.ts`,
   - the `transactions` array item object in `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/banks-handler.ts`,
   - `queryBodySchema` in `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/query-handler.ts`.
2. Regenerate the OpenAPI snapshot (`yarn generate-v1-openapi` in `backend-cluster/backend-v2/`) and re-pin/regenerate the CLI client in the same change (`make spec-sync && make codegen` in `cli/`) per `backend-cluster/backend-v2/AGENTS.md` (since `additionalProperties: false` appears in `docs/openapi/v1.json`).
3. Add a parameterized contract/schema guard test (in `src/server/api/__tests__/` or `src/features/ledger/api/rest/v1/__tests__/`) asserting that every v1 REST JSON request body schema (and nested object schemas inside it, with an explicit allowlist for RFC 7662 `/token/introspect` if kept non-strict) rejects unknown keys, plus HTTP adapter tests for the four fixed routes.

## Blast radius

- Owning packages: `backend-cluster/backend-v2` (schema + tests + `docs/openapi/v1.json`) and `cli` (`openapi/v1.json` + generated client via `make spec-sync && make codegen`).
- Audit of all `paths` in `backend-cluster/backend-v2/docs/openapi/v1.json` confirmed these four routes (plus RFC 7662 `POST /api-gateway/v1/token/introspect`) are the only v1 REST JSON request bodies with non-strict object schemas.
- MCP (`refusingUnknownArguments`) and GraphQL (typed schema validation) already reject unknown keys on all four operations.
- Adjacent states: valid requests (including all documented aliases: `message`/`description`, `dryRun`/`dry_run`, `allowInvalid`/`allow_invalid`, `removeIncludes`/`remove_includes`) stay accepted; unauthenticated or forbidden callers still fail at auth/scope middleware before body validation.

- `PUT /api-gateway/v1/ledgers/{owner}/{name}/files/{*path}`, `DELETE /api-gateway/v1/ledgers/{owner}/{name}/files/{*path}`, `POST /api-gateway/v1/ledgers/{owner}/{name}/bank-transactions/submit` (nested `transactions[]` item), and `POST /api-gateway/v1/ledgers/{owner}/{name}/query` all return HTTP `400 VALIDATION_FAILED` naming the unrecognized key when given an unknown field (such as `dryrun`, `allowinvalid`, `remove_include`, `sourceAccout`, `source_account`, or `bogusKey`), without invoking any service or writing to the repository.
- A guard test prevents future non-strict v1 REST JSON request body schemas (root or nested).
