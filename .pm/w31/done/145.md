# A `query` directive is listed as a `Custom` entry: `listLedgerEntries`, the journal and `getEntryContext` give it `directive_type: "Custom"`, `type: <name>` and `values: [<query>]`, `directiveTypes: ["Query"]` is refused, and `entries-count` counts it as `Query`, on MCP, REST and GraphQL

**Minor · ledger (`src/foundation/rustledger/journal-serialize.ts`) + idl + backend-v2 · 45–60m · A1.** Beancount stores a named query as `2026-01-05 query "<name>" "<BQL>"`. Fava shows it in the journal as a `Query` entry with `name` and `query_string`. The hosted journal relabels it. `listLedgerEntries`, `beancount://{owner}/{name}/journal`, REST `GET …/journal` and GraphQL `getLedgerJournal` return it as `{"directive_type": "Custom", "type": "<name>", "values": ["<BQL>"]}`, and `getEntryContext` says `directive_type: "Custom"` beside a `slice` that reads `query`. An agent reading the journal sees a custom directive named after the query. When it filters, `directiveTypes: ["Custom"]` returns the query, and `directiveTypes: ["Query"]` is refused `BAD_USER_INPUT`, "Unknown directiveTypes value \"Query\"". Meanwhile `entries-count` reports `Query: 1, Custom: 0` for the same ledger, and `docs/mcp.md` says `checkLedger`'s `entriesCount` is the same report. `docs/mcp.md` says every type there except `Price` agrees with `listLedgerEntries`.

## Repro (synthetic)

Append to a clean ledger:

```beancount
2026-01-05 query "qa-q" "SELECT account WHERE account ~ 'Cash'"
```

1. `listLedgerEntries { time: "2026-01-05" }` returns, among the context `open`s, `{"directive_type": "Custom", "date": "2026-01-05", "type": "qa-q", "values": ["SELECT account WHERE account ~ 'Cash'"]}`. `resources/read beancount://<owner>/<name>/journal?time=2026-01-05` returns the same row.
2. `listLedgerEntries { directiveTypes: ["Custom"] }` gives `total: 1`, the query. `{ directiveTypes: ["Query"] }` is refused: `BAD_USER_INPUT` "Unknown directiveTypes value \"Query\"", with the hint "Use any of Transaction, Balance, Commodity, Close, Custom, Document, Event, Note, Open, Pad, Price".
3. REST `GET /api-gateway/v1/ledgers/<owner>/<name>/journal?directiveTypes=["Custom"]` (URL-encoded) returns the same row. `["Query"]` is a `400` with the same message. GraphQL `getLedgerJournal(ledgerId:, query: {directiveTypes: ["Custom"]}) { total data }` returns the same row, and `["Query"]` gives the same `BAD_USER_INPUT`.
4. `getEntryContext` on that row's `entry_hash` returns `entry.directive_type: "Custom"`, `type: "qa-q"`, and a `slice` of `2026-01-05 query "qa-q" "…"`.
5. Control, same ledger: `beancount://<owner>/<name>/entries-count` (and REST) lists `{"type": "Query", "number": 1}` and `{"type": "Custom", "number": 0}`.
6. Control, same text: `bean-check` (Beancount 3.2.3) passes and loads a `Query` entry. Fava 1.31's `/api/journal` lists it as `{"t": "Query", "name": "qa-q", "query_string": "SELECT account WHERE account ~ 'Cash'"}`, with no `Custom` entry.

## Root cause

`DIRECTIVE_TYPE_BY_TAG` (`backend-cluster/ledger/src/foundation/rustledger/journal-serialize.ts:98`) maps the engine's `query` tag to `"Custom"`. `serializeDirective` (`:476`) then writes the query's `name` as `type` and its `query_string` as `values[0]`. The doc comment at `:348` says a query "is not emitted by `getJournal`", so the mapping only "keeps the union exhaustive". That premise is false: `getJournal` emits every directive, and the query reaches every journal read. `DirectiveType` in `ledger/src/foundation/ledger-api-types/index.ts:89` (and the IDL's journal item union) has no `Query` member. That is also why `normalizeJournalKinds` (`backend-v2/src/features/ledger/utils/journal-kinds.ts:19`) refuses `"Query"`. Two other mappings in the same package already say `Query`: the entries count (`features/ledger/service/ledger-data-mappers.ts:100`) and the legacy journal (`features/ledger/service/ledger-legacy-journal.ts:37`).

## Fix

- Add `Query` to `DirectiveType` and a `JournalQueryPublic` item `{entry_hash, directive_type: "Query", date, meta, name, query_string}` in `backend-cluster/idl/beancount-ledger.openapi.json`, then regenerate the ledger and backend-v2 types the way the IDL scope says.
- Map `query` to `"Query"` in `journal-serialize.ts`, serialize `name` and `query_string`, and correct the `:348` comment.
- Accept `Query` in `directiveTypes` on MCP, REST and GraphQL. It goes through the shared `JOURNAL_KINDS`, so one list covers all three. Add `Query` to the tool's `directiveTypes` enum and description, and to the GraphQL field description.
- In `docs/mcp.md`, list `Query` among the journal's directive types, next to the `entries-count` agreement passage.

**Resolved 2026-11-27** — A stored query is now a `Query` entry on every journal read. ledger (`journal-serialize.ts`): `serializeDirective` maps the engine's `query` tag to `"Query"` and writes `{entry_hash, directive_type: "Query", date, meta, name, query_string}`, and the doc comment that said `getJournal` never emits one is corrected. idl: `DirectiveType` gains `Query` and `JournalQueryPublic` joins the journal, account-journal and entry-context unions; the ledger's DTO types and backend-v2's generated ledger client (`yarn generate-fava-client`) follow. backend-v2: `JOURNAL_KINDS` reads the regenerated enum, so `directiveTypes: ["Query"]` (any case) is accepted on `listLedgerEntries`, the journal and account-journal resources, REST `GET …/journal` and `…/account-journal`, and GraphQL `getLedgerJournal` and `getLedgerAccountJournal`, and `listLedgerEntries`' published enum lists it. Both GraphQL `directiveTypes` fields gain a description naming the kinds from that same list, and the tool's description names `["Query"]`. `getEntryContext` passes the ledger's entry through, so it says `Query` too. `docs/mcp.md` lists `Query` among the kinds and says a stored query is never a `Custom`. v1 OpenAPI regenerated (the REST parameter description), CLI pin and client re-synced (docstrings only). dashboard: the Journal renders a `Query` entry with its name and BQL (it would otherwise fall to "Unknown directive type" now that it is no longer a `Custom`), the entry's accessible label carries both, and the filter bar gains Fava's Query chip, using the existing `journal.query` key in all 15 locales.
