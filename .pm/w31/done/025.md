# GraphQL's public-capable ledger reads answer a rejected credential with "Authentication required", the no-credential wording that w23/070 replaced; so does REST `archive-download-url`

**Minor · backend-v2 (authentication refusals) · 30–45m · A1.** Send an expired, revoked or malformed key to GraphQL `getLedgerYears` and the answer is the one you get with no key at all. An MCP-audience OAuth token takes the same code path. That case was traced in source, not run live, because this run minted no OAuth token. An agent told "Authentication required" after sending a credential retries the same credential instead of replacing it, which is the failure `w23/070` fixed on REST and on GraphQL's `@Authenticated` fields. `docs/mcp.md` ("The reverse holds too", line 131) promises that an MCP token sent to GraphQL is refused with "This token was issued for the MCP endpoint (`/api-gateway/mcp`) and is not accepted here". On GraphQL's ledger reads it is not. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). Every request was a read on the QA account's private disposable ledger, sent either with no credential, with a made-up one, or with the QA account's own unpinned `bcio_` key as a control.

## Repro (live, reads only)

`POST /api-gateway/` with `query($l:String!){ getLedgerYears(ledgerId:$l) }` and `l` set to a private ledger `<owner>/<name>`:

| credential sent | GraphQL `getLedgerYears` (also `getLedger`, `getLedgerOptions`, `getLedgerJournal`, `listCommits`, `getLatestLedgerCommit`) | GraphQL `apiKeys` / `getFeed` (`@Authenticated`) | REST `GET /api-gateway/v1/ledgers/<owner>/<name>/years` |
| --- | --- | --- | --- |
| none | `UNAUTHENTICATED` "Authentication required" | "Access denied! Please login to continue!" | 401 "This endpoint requires a credential: …" |
| `Authorization: Bearer qa-garbage` | `UNAUTHENTICATED` "Authentication required" | "The credential sent was not accepted: it is expired, revoked, malformed, or issued for another resource. …" | 401 "The credential sent was not accepted: …", `error="invalid_token"` |
| `Authorization: Bearer bcio_000…0` (key-shaped, unknown: the answer an expired or revoked key gets) | `UNAUTHENTICATED` "Authentication required" | "The credential sent was not accepted: …" | 401 "The credential sent was not accepted: …" |
| `x-api-key: qa-garbage` | `UNAUTHENTICATED` "Authentication required" | "The credential sent was not accepted: …" | 401 "The credential sent was not accepted: …" |
| the owner's valid key (control) | data | data | 200 |

REST `GET /api-gateway/v1/ledgers/<owner>/<name>/archive-download-url` has the same gap: 401 `UNAUTHENTICATED` "Authentication required" for both no credential and a garbage bearer. Its `WWW-Authenticate` header does add `error="invalid_token"` in the second case, but the message does not change. MCP is not affected: a rejected credential is refused with 401 before any tool or resource runs.

## Cause

- The GraphQL context works out the rejection (`backend-cluster/backend-v2/src/server/graphql/context.ts:76-79`), but only `getCurrentIdentity`/`getCurrentUserId` (`:95`, `:102`) and `@Authenticated` (`src/server/graphql/authenticated.ts:19`) read it. REST's `requireIdentity` (`src/server/rest/v1-route.ts:159`) uses it too.
- The ~45 `@AllowAnonymous` ledger and commit reads (`src/features/ledger/api/resolvers/*.query.ts`, `src/features/gitea/commits/api/commits-resolver.ts`) accept a missing identity because public ledgers are readable anonymously. Their services then substitute the anonymous principal: `identity ?? anonymousPrincipal()` at `src/features/ledger/utils/authorize-ledger.ts:27`, `src/features/gitea/commits/service/commits-service.ts:281` and `:371`, and `src/features/ledger/workflow/ledger-workflow.ts:604`. REST `anonymousV1Route`s, such as `archive-download-url` in `src/features/ledger/api/rest/v1/asset-url-handler.ts`, get an undefined identity the same way (`v1-route.ts:250-254`).
- On a private ledger, `authorizeOrThrow` (`src/server/api/authorization/authorization-service.ts:1388-1389`) throws a fixed `UnauthenticatedError("Authentication required")` for the anonymous principal. It cannot tell "nothing was sent" from "something was sent and refused".
- `w23/070`'s tests (`src/server/api/__tests__/credential-rejection.test.ts`) cover REST `…/years` and GraphQL's `getCurrentIdentity` and `@Authenticated` paths, not an `@AllowAnonymous` read, which is why this path was missed.

## Fix

When a request sent `Authorization` or `x-api-key` and it resolved to no identity, every `UNAUTHENTICATED` refusal on that request must carry `credentialRejection`'s wording. That includes the one `authorizeOrThrow` raises for the anonymous principal, and the MCP-audience variant when the token verifies for the MCP resource. A request with no credential keeps "Authentication required". A public ledger read that succeeds anonymously stays a success; this changes only refusals. One way to do it: carry the rejection on the request (the async context, or the anonymous principal) and use it in `authorizeOrThrow`. Mapping the error at the GraphQL `formatError` and REST error-middleware boundaries would also work. Either way, every anonymous-capable path changes at once on GraphQL and REST. MCP needs no change.

**Done when:** on a private ledger, GraphQL `getLedgerYears` and `listCommits` and REST `archive-download-url` answer a garbage bearer, an unknown `bcio_` key and a garbage `x-api-key` with "The credential sent was not accepted: …". An MCP-audience token gets "This token was issued for the MCP endpoint …". No credential still gets "Authentication required". `credential-rejection.test.ts` covers an `@AllowAnonymous` GraphQL read and the REST anonymous route for each case, and fails with the fix reverted.

## Dedupe

- `w23/070` (done, `bf8e10937`) is the same contract for REST's `requireIdentity` and GraphQL's `getCurrentIdentity`/`@Authenticated`. This is the anonymous-capable path it did not reach, not a regression of what it shipped: those paths still answer correctly in production (table above).
- `w1/206` and `w1/222` (done) are the `WWW-Authenticate` challenge, which is correct here.
- Searched `.pm/**` for `Authentication required`, `credentialRejection`, `not accepted here` and `anonymousPrincipal`, and `git log -S credentialRejection`. No other item covers it and no fix exists on `main`.

---

**Resolved 2026-11-15** — On a private ledger, the reads a public ledger serves anonymously now tell a request whose credential was refused that it was refused. They no longer ask it for a credential. Shipped in the commit carrying this note (`backend-cluster/backend-v2`).

- **What changed.**
  - The transport that knows a credential was sent now records `credentialRejection`'s wording on the request's async context (`credentialRejection` in `src/shared/async-context.ts`). GraphQL does this in `createContext`, for every field. REST does it in the `anonymousV1Route` branch of `registerV1Route` (`optionalIdentity`). The anonymous principal's refusal in `authorizeOrThrow` uses that wording, and so does `unusableRepoIdError` (GraphQL `getLedgerAssetDownloadUrl`). A request with no credential, or only a browser cookie, still gets "Authentication required". An MCP-audience token is named as one, as `w23/070` set up.
  - No authorization decision changed. A public ledger still answers a refused credential anonymously. The text depends only on the request's headers, never on the ledger. A private ledger and a missing one therefore still read the same wherever they read the same before. GraphQL `getLedgerYears`, for example, answers both the same way, and `getLedgerAssetDownloadUrl` gives a missing repository ID and a private one the same refusal. MCP is unchanged, because it refuses a rejected credential with 401 before any tool runs.
  - `docs/mcp.md` ("The reverse holds too") now covers these reads.
- **Evidence.**
  - Live repro first, reads only, on `https://beancount.io` against a QA private ledger. A garbage bearer and a garbage `x-api-key` got `UNAUTHENTICATED` "Authentication required" from GraphQL `getLedgerYears` and from REST `archive-download-url`. So did no credential.
  - `credential-rejection.test.ts` now covers these refusals through the real `AuthorizationService`. On GraphQL it covers `getLedgerYears`, `listCommits` and `getLedgerArchiveDownloadUrl`, run through `createContext` and the scope middleware in a request context. On REST it covers `archive-download-url` over the v1 test server. Each is checked with no credential, an MCP-audience token, an expired token, a malformed bearer, an unknown key sent as `x-api-key` or as a bearer, and a garbage `x-api-key`. Two more cases check that a public ledger still serves a refused credential, and that `getLedgerAssetDownloadUrl` answers a missing repository ID the same as a private one. With the fix reverted, the 3 GraphQL cases and the REST case fail. With only the `unusableRepoIdError` change reverted, the asset case fails. The v1 test server now mounts `asyncContextMiddleware`, as `start-server.ts` does in production.
  - Not changed: REST `archive-download-url` answers a missing ledger 404 before it authorizes, and a private one 401. That difference already existed, and this fix keeps it as it was.
- **Gates.** Run in `node:22-bookworm-slim` (v22.23.4) from `backend-cluster/backend-v2`: `yarn typecheck`, ESLint on the changed files, `yarn lint:deadcode`, `yarn format:check`, `yarn test` (485 suites, 11034 tests passing, 1 skipped), and `yarn generate-v1-openapi` (no drift). The live behavior changes after the next backend-v2 deploy.
