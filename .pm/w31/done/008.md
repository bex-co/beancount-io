# A `createLedgerFiles` call that loses a race to a create of the same path gets the entry `sha256sum` hint

**Trivial · backend-v2 (error mapping) · 20m · A1.** Found in the same run and on the same ledger as `w31/007`. The probe files were deleted afterwards.

- **Repro.** Send two `createLedgerFiles {files: [{path: "qa-…-race2.bean", content: …}]}` calls at the same moment. One commits. The other gets `CONFLICT` "commit failed: Ledger resource conflict: qa-…-race2.bean already exists; update it with its sha, or choose another path". It carries the category's fallback hint: "`getEntryContext` returns the entry's current `sha256sum`, and `listLedgerEntries` with `include_source` returns a page of them". An entry lookup cannot satisfy a file create.
- **Control.** A sequential create over an existing path is refused earlier, by the pre-check in `src/features/ledger/service/ledger-repo-service.ts`. That refusal carries `FILE_EXISTS_HINT`: "Creating is for a new file. To overwrite this one deliberately, update it: …".
- **Cause.** A create that loses the race fails at commit time instead. The ledger service's error middleware (`backend-cluster/ledger/src/server/error-middleware.ts`, `conflictMessage`) then answers 409 "`<path>` already exists; update it with its sha, or choose another path". backend-v2's 409 mapping (`src/foundation/fava/error-to-domain.ts`) attaches a hint only to messages that start with `Ledger file conflict:`. This one therefore gets the entry fallback, which `w23/147` and `w23/178` already removed from the other file conflicts.

**Done when:** the commit-time "already exists" 409 maps to `CONFLICT` with `FILE_EXISTS_HINT`, or an equivalent file hint, on MCP, REST and GraphQL. A mapping test pins the ledger service's wording and fails with the change reverted.

---

**Resolved 2026-11-15** — The 409 mapping in `backend-cluster/backend-v2/src/foundation/fava/error-to-domain.ts` now reads the ledger service's commit-time wording ("`<path>` already exists; update it with its sha, or choose another path") as `fileExistsConflict(path)`. That is the same refusal the pre-check in `ledger-repo-service.ts` throws: `CONFLICT` "File conflict: `<path>` already exists" with `FILE_EXISTS_HINT`, which moved beside it. So a create that loses a race reads exactly as a create over a file already there. REST `PUT` and MCP `createLedgerFiles` reach it through `/change-files`. GraphQL `createLedgerFile` has no pre-check, so every create it sends over an existing file reaches it, and those creates now get the hint too (before, they had none). `unwrap-response.test.ts` maps the wording and pins it against `backend-cluster/ledger/src/server/error-middleware.ts`. `write-conflict-parity.test.ts` drives the lost race through MCP, REST and GraphQL (executed), and checks that MCP and REST answer the race and the sequential create identically. With the mapping reverted, 6 cases fail. `mcp-reference-resolution.test.ts` now scans `src/foundation` for hints, so the moved hint's tool names stay checked. Before the fix, the repro held on `https://beancount.io`, 1 of 1 on `<qa-owner>/mcp-agent-eval` with two different contents. When both calls sent the same content, the loser settled as landed. The probe files were deleted afterwards. Gates in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, `yarn test` (483 suites), `yarn lint:deadcode`, `yarn format:check`, ESLint on the changed files, and an OpenAPI regeneration with no drift. Shipped in this commit (`backend-v2`).
