# `addLedgerEntries` / `POST .../entries` / GraphQL `bulkEntries` accept non-ASCII component starts (`Assets:Bank:épargne`, `Assets:Bank:€`, `Assets:Bank:😀`) past `assertEntryTokens`, producing opaque parse errors or writing unparseable syntax under `allowInvalid`

**Major · ledger (`src/features/ledger/utils/entry-tokens.ts`) · 25–35m · A1.** `assertEntryTokens` (`backend-cluster/ledger/src/features/ledger/utils/entry-tokens.ts:15-20, 47, 158-182`) validates every unquoted account token in structured entry writes (`addLedgerEntries` on MCP, `POST /api-gateway/v1/ledgers/{owner}/{name}/entries` on REST, `bulkEntries` on GraphQL) before rendering Beancount text. Its `ACCOUNT` regex places `NON_ASCII = "[^\\x00-\\x7F]"` in the **component-start** position, matching **any** non-ASCII code point — including lowercase non-ASCII letters (`Ll`, e.g. French `Assets:Bank:épargne` or `Assets:épargne`), currency symbols (`Sc`, `Assets:Bank:€`), emojis (`So`, `Assets:Bank:😀`), non-ASCII punctuation (`Pd`/`Ps`, `Assets:Bank:—`), modifier letters (`Lm`), and non-decimal numbers (`Nl`/`No`). Live rustledger only accepts `[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]` at a component start and fails on all of those with `parse error: unexpected input` (`P0012`). Consequently, instead of refusing upfront with `BAD_USER_INPUT: entry 0: account "..." is not a valid account` (as it does for ASCII lowercase `Assets:Bank:epargne`), `dry_run: true` returns `ok: true` with `valid: false` and an opaque `parse error: unexpected input`, a commit without `allowInvalid` fails late as `VALIDATION_FAILED` (`parse error: unexpected input`), and a commit with `allowInvalid: true` writes unparseable Beancount syntax into the ledger. Companion `backend-cluster/backend-v2` fix is tracked in `w31/081`.

## Expected

`assertEntryTokens` rejects any account whose root does not start with `[\p{Lu}\p{Lt}\p{Lo}]` or whose sub-component does not start with `[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]` upfront with `BAD_USER_INPUT` (`entry <idx>: <field> "..." is not a valid account`) on MCP, REST, and GraphQL alike — on previews, commits, and `allowInvalid: true` calls alike — while continuing to accept all valid Unicode account names rustledger parses (including `Café`, `Épargne`, `日本`, `خانه‌ها` with ZWNJ/ZWJ, and `١`).

## Root cause

Not deployment lag — reproduced identically at local HEAD `439cf6ae9`:

- `backend-cluster/ledger/src/features/ledger/utils/entry-tokens.ts:15-20`:
  ```ts
  const NON_ASCII = "[^\\x00-\\x7F]";
  const ACCOUNT = new RegExp(
    `^(?:[A-Z]|${NON_ASCII})(?:[A-Za-z0-9-]|${NON_ASCII})*` +
      `(?::(?:[A-Z0-9]|${NON_ASCII})(?:[A-Za-z0-9-]|${NON_ASCII})*)+$`,
    "u",
  );
  ```
  Placing `${NON_ASCII}` in the root-start and component-start positions accepts any non-ASCII code point (including `Ll` lowercase letters like `é`, `Sc` symbols like `€`, `So` emoji like `😀`, `Pd`/`Ps` punctuation like `—`/`「`, `Lm`, `Nl`, `No`, and `Mn` combining marks), even though rustledger only lexes `[\p{Lu}\p{Lt}\p{Lo}]` at root start and `[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]` at sub-component start.
- Called from `backend-cluster/ledger/src/api/entries.ts:239` for all bulk structured entry writes (covering `transaction` postings, `open`, `close`, `pad` `account`/`sourceAccount`, `balance`, `note`, `document`, and `budget`/`custom` account values) behind MCP `addLedgerEntries`, REST `POST /api-gateway/v1/ledgers/{owner}/{name}/entries`, and GraphQL `bulkEntries`.
