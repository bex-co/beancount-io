# Statement summaries round any amount past a double's ~16 significant digits: 0.123456789012345678 of an 18-decimal token reads `0.12345678901234568` in the balance sheet's, overview's and interval totals' `otherCurrencies`, on MCP and REST; the code says only "a magnitude past 2^53 rounds"

**Minor · backend-v2 (`src/features/ledger/utils/report-summaries.ts`) + docs · 30–45m · A1.** By default (`shape=summary`), the MCP statement resources and their REST twins return amounts as JSON numbers: `netWorth`, `assets`, `byAccount[].balance`, each interval's `total`, and every `otherCurrencies` value. The design comment (`report-summaries.ts:31`) accepts the cost on the premise that it "is real and bounded: a magnitude past 2^53 rounds". That bound is wrong. A double holds about 15–17 significant digits at any magnitude, so a small amount with many decimals rounds too. Crypto ledgers hit this routinely: an ETH-style token written to 18 decimals, or a balance such as `90071992547409.93 USD`, which would read back as `…09.94`. The ledger, BQL, holdings and `shape=fava` all give the exact decimal. The summary, which is the shape agents are steered to for totals, gives a different number with no sign that it rounded. `docs/mcp.md`'s statement section does not say the summary amounts are doubles at all.

## Repro (synthetic)

Append to a USD ledger:

```beancount
2026-01-02 open Assets:Qa:Wallet QAETH
2026-01-02 open Equity:Qa:Opening
2026-01-03 * "qa" "wallet"
  Assets:Qa:Wallet  0.123456789012345678 QAETH
  Equity:Qa:Opening
```

1. `resources/read beancount://<owner>/<name>/statements/balance-sheet`, with or without `conversion=units`, gives `"otherCurrencies": {"QAETH": 0.12345678901234568, …}`. `…/overview` gives the same value. `…/interval-totals?interval=year&conversion=units&accountName=Assets` gives it in the interval's `otherCurrencies`. REST `GET /api-gateway/v1/ledgers/<owner>/<name>/statements/balance-sheet` returns a byte-identical body.
2. Control, same ledger: `…/statements/balance-sheet?shape=fava` gives `"QAETH": "0.123456789012345678"`. `runBqlQueryStructured` `SELECT account, sum(position) … GROUP BY account` gives `{"QAETH": "0.123456789012345678"}`. `…/holdings` gives `units.number: "0.123456789012345678"`.
3. Control, by arithmetic: in Node, `Number("90071992547409.93")` is `90071992547409.94`, while `Number("12345678901234.56")` round-trips. So a USD figure in the tens of trillions loses its cents long before 2^53.

## Root cause

`amount()` (`backend-cluster/backend-v2/src/features/ledger/utils/report-summaries.ts:194`) returns `Number(raw)`. `otherCurrencies()` (`:205`) adds in `BigNumber` and then calls `.toNumber()` (`:221`). `sum()` (`:340`) does the same. The ledger service sends exact decimal strings, and these lines are where the digits are lost. The comment at `:31` sets the bound by magnitude (2^53) when the real limit is significant digits.

## Fix

The owner picks one of two:

- **(a) Keep numbers and state the limit.** Correct the `:31` comment to "about 15 significant digits". Say in `docs/mcp.md`'s statement section, and in the statement, overview and interval-totals resource descriptions, that summary amounts are JSON numbers exact to 15 significant digits, and that `shape=fava`, holdings or `runBqlQueryStructured` give the exact decimal. Optionally also mark a rounded value, for example with a `rounded: true` beside `otherCurrencies` when some value fails `String(Number(raw)) === raw` after normalizing.
- **(b) Send exact values.** Make `otherCurrencies` values (the commodity side, where long-decimal tokens live) decimal strings, as holdings already does. This changes the REST/MCP contract and needs an OpenAPI change and a parity note.

Either way, MCP and REST change together (the summaries are shared). GraphQL returns the chart payload with decimal strings and is already exact.

## Done when

- With (a): the docs and the descriptions state the 15-digit limit and name the exact alternatives. The comment no longer says "past 2^53". With the repro ledger, a test that reads the summary of an 18-decimal amount shows the documented behavior (and the `rounded` flag, if added).
- With (b): the repro reads `"QAETH": "0.123456789012345678"` in `otherCurrencies` on MCP and REST, the OpenAPI snapshot shows the type change, and a test fails with the change reverted.

## Dedupe

Searched `.pm/**` (including `done/` and `blocked/`) for `otherCurrencies` together with round, precision or digits, "18 decimals", `2^53`, `toNumber`, and `report-summaries`. w21/594 fixed the same 18-decimal loss in the mobile app's formatting. w23/013 fixed float noise in summary sums (`906.5799999999999`). w23/133 covers BQL integer literals past 2^53. **Resolved 2026-11-27** — took fix (a), keeping the recorded w2/m28:t002 design: summary amounts stay JSON numbers that an agent can compare without parsing. The limit is now stated where callers read it. The design comment in `backend-cluster/backend-v2/src/features/ledger/utils/report-summaries.ts` sets the bound by significant digits, not 2^53: up to 15 digits is exact, and a longer amount reads as the nearest double. The `sum()` comment stops claiming that `String(n)` is always exact. A shared `SUMMARY_PRECISION_DESCRIPTION` states the limit, and names `shape=fava`, holdings and BQL as the exact alternatives, on the REST statement, overview and interval-totals routes and on the four MCP resources (balance sheet, income statement, overview, interval totals). The `shape` parameter says the same. `docs/mcp.md`'s statement section lists the numeric fields, gives this note's two examples, and names `shape=fava`, holdings and `runBqlQueryStructured`. The OpenAPI snapshot and the CLI's pinned copy and generated client were regenerated, with description text the only change. Pinned by `report-summaries.test.ts` ("summary amounts are doubles, exact to 15 significant digits": the repro's `0.123456789012345678 QAETH` reads `0.12345678901234568` in the balance sheet's, overview's and interval totals' `otherCurrencies`, `1234567890123.45` comes back exact, and `90071992547409.93` reads `…09.94`) and by `served-description-claims.test.ts`, which fails with the description removed.
