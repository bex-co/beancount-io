# `deleteEntrySources` (`POST .../entry-source/delete-many`, `deleteMultipleLedgerEntrySourceSlices`) accepts empty `entries: []`, runs full ledger load/check, and returns `200 OK` with a malformed trailing-colon message (`"Would delete 0 entries: "`) instead of `BAD_USER_INPUT`

**Minor · backend-v2 + ledger (batch entry-source delete validation) · 25–35m · A1.** Passing `entries: []` to batch entry deletion succeeds with `200 OK` on MCP, REST, and GraphQL — on both `dry_run: true` and `dry_run: false` — loading the full ledger and running bean-check for a zero-entry batch and returning a malformed message ending in a dangling colon (`"Would delete 0 entries: "` / `"Deleted 0 entries: "`), instead of refusing with `BAD_USER_INPUT` as direct sibling `moveEntrySources` and every other batch write tool do. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, checked against HEAD `ffb9f6270`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval` (snapshot verified unchanged byte-for-byte after run: `main.bean` sha256 `77c3a591efd3`, 0 bean-check errors).

## Repro (live)

Reproduced in fresh requests across all three surfaces against `<qa-owner>/mcp-agent-eval`:

1. **MCP `deleteEntrySources` (`dry_run: true` and `dry_run: false`)**:
   ```sh
   node .agents/skills/qa-shared/scripts/qa-mcp.mjs call deleteEntrySources '{"ledger":"<qa-owner>/mcp-agent-eval","entries":[],"dry_run":true}'
   ```
   Actual (`dry_run: true`): HTTP `200`, `isError` absent, `ok: true`, `result.summary: "Would delete 0 entries. No new bean-check errors."`, `result.message: "Would delete 0 entries: "`, `result.deletedCount: 0`.
   Actual (`dry_run: false`): HTTP `200`, `isError` absent, `ok: true`, `result.message: "Deleted 0 entries: "`, `result.deletedCount: 0`, `result.wrote: []`.
2. **REST `POST /api-gateway/v1/ledgers/<qa-owner>/mcp-agent-eval/entry-source/delete-many`** with `{"entries":[],"dryRun":true}`:
   Actual: HTTP `200`, `{"message":"Would delete 0 entries: ","dryRun":true,"deletedCount":0,"preview":[],"errorsBefore":0,"errorsAfter":0,"newErrors":[],"valid":true}`.
3. **GraphQL `deleteMultipleLedgerEntrySourceSlices(ledgerId: "<qa-owner>/mcp-agent-eval", input: { entries: [], dryRun: true })`**:
   Actual: HTTP `200`, `{"data":{"deleteMultipleLedgerEntrySourceSlices":{"message":"Would delete 0 entries: ","deletedCount":0,"dryRun":true}}}`.

Expected: refused with `BAD_USER_INPUT` (`entries must name at least one entry`, field `entries`) on MCP, REST, and GraphQL without loading the ledger or contacting Gitea.

## Working controls

- Direct sibling `moveEntrySources` with `entries: []` returns `BAD_USER_INPUT: entries must name at least one entry` (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:1392-1397`, tested in `move-source-slices.test.ts:274`).
- Every other batch write tool refuses an empty batch with `BAD_USER_INPUT`: `createLedgerFiles`, `updateLedgerFiles`, `deleteLedgerFiles` (`files: Too small: expected array to have >=1 items`), `importStagedBankTransactions`, `discardStagedBankTransactions`, and `createPullRequest`.

## Root cause

Not deployment lag — present at HEAD `ffb9f6270`:

- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/source-slice-handler.ts:61-65`: `deleteSlicesInput` defines `entries: z.array(sliceRef).max(MAX_BULK_ENTRIES, ...)` with no `.min(1)`.
- `backend-cluster/backend-v2/src/features/ledger/service/ledger-journal-service.ts:516-544` (`LedgerJournalService.deleteMultiSourceSlices`): checks only `assertBulkEntriesSize(entries, "deleted")` (upper cap of 1,000), never `entries.length === 0`, so GraphQL (which does not use the Zod schema) also forwards empty arrays to the ledger service.
- `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:1248-1294` (`deleteMultiSourceSlices`): unlike `moveSourceSlices` directly below it (`:1392-1397`), has no `if (entries.length === 0)` guard; `backend-cluster/ledger/src/api/journal.ts:207-209` unconditionally joins hashes after `": "`, emitting `"Would delete 0 entries: "` / `"Deleted 0 entries: "`.

## Fix

In `backend-cluster/backend-v2` and `backend-cluster/ledger`:

1. In `backend-cluster/backend-v2/src/features/ledger/service/ledger-journal-service.ts:523` (`LedgerJournalService.deleteMultiSourceSlices`), guard `if (entries.length === 0)` throwing `new BadUserInputError("entries must name at least one entry", "entries")` before calling the ledger service (matching `moveSourceSlices`'s wording), so MCP, REST, and GraphQL all refuse identically without an upstream call. (Note: update the existing mock-failure unit test at `ledger-journal-service.test.ts:524-528` that passes `entries: []` as a dummy fixture to pass a 1-element entry.)
2. In `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:1257` (`deleteMultiSourceSlices`), add the same `if (entries.length === 0) throw new BadUserInputError("entries must name at least one entry", "entries")` guard that `moveSourceSlices` already has at `:1392-1397`.
3. Optionally add `.min(1, { message: "entries must name at least one entry" })` to `deleteSlicesInput` (`source-slice-handler.ts:63`) — note `moveSlicesInput` extends `deleteSlicesInput`, so if added, regenerate `docs/openapi/v1.json` and sync `cli/openapi/v1.json` (`make spec-sync && make codegen` in `cli/`) in the same change.
4. Add unit tests in both `backend-v2` and `ledger`, plus 3-surface adapter tests in `source-slice-parity.test.ts` covering `entries: []` for both preview (`dryRun: true`) and commit (`dryRun: false`) across MCP `deleteEntrySources`, REST `POST .../entry-source/delete-many`, and GraphQL `deleteMultipleLedgerEntrySourceSlices`.
