# `updateLedgerFiles` `old_string`/`new_string` edits cite post-write lines in preview and refusal when the edit changes the line count

**Minor · ledger + backend-v2 (write error lines) · 30–45m · A1.** Last open sibling of `w31/101` (entry delete) and `w31/116` (`appendLedgerText`, `updateEntrySource`, `moveEntrySources`, routed `addLedgerEntries`). Those fixes map a write's new errors back to the lines of the file as it stands now. `updateLedgerFiles` with `old_string`/`new_string` edits still reports the line numbers of the file after the edit. Whenever a replacement adds or removes lines, an error below it then points at the wrong current line, in the `dry_run` preview and in the commit refusal alike. Flagged as not done in `w31/116`'s resolution (`done/116.md`).

- Expected repro (not yet run; the worker confirms it first): on a scratch ledger, replace a one-line `old_string` with a three-line `new_string` above an entry that the edit makes fail. Preview and refusal should cite that entry's line + 2, while its line in the current file is 2 lower.
- Fix where `w31/116` did: map edit spans through the same line mapping before error lines are reported, on MCP, REST and GraphQL alike.
- Done when: preview and refusal name the current line for an edit that grows, shrinks or keeps the line count. A parity test covers all three surfaces, and a `yarn verify:rustledger` live check sits next to `scripts/edit-error-lines.ts`. The live repro on `beancount.io` waits for both services to deploy.

**Resolved 2026-11-27** — An `updateLedgerFiles` `old_string`/`new_string` edit now names each new error at its line in the file as it stands, in the `dry_run` preview and in the refusal, when the edit grows, shrinks or keeps the line count. An error inside the edit's new text keeps the line the preview's diff shows. A committed `allow_invalid` edit still reports the line after the write.

- **Repro, before the fix.** On the live engine (`@rustledger/wasm`, `checkProjectedErrors`), growing the FARMERS MARKET groceries posting into three lines put the assertion from current line 14 at `main.bean:16`. In-process, MCP `updateLedgerFiles` that grew line 2 into three lines previewed and refused the stranded assertion at `main.bean:8`; it is on line 6. A three-into-one edit named line 4, and two chained edits named line 7.
- **backend-v2.** `foldOperations` (`edit-ledger-files-tool.ts`) records the lines each exact-text edit replaced, in the order the edits chain, for every file the batch changes only by exact-text edits. `gateFileWrite` (`file-write-gate.ts`) takes them as `edits` and maps each new error back with `atLinesBeforeEdits` (`bean-check-errors.ts`). That is w31/116's insertion mapper generalized to replacements: `LineInsertion` is now `LineEdit`, with an optional `replaced` count. A file written whole with `content` is all written text, so it is not mapped. No response shape changed.
- **Surfaces.** Only MCP takes an exact-text edit. REST `PUT …/files/{path}` and GraphQL `updateLedgerFile` take the whole content, and GraphQL file writes have no gate yet (w1/210, blocked). The parity suite therefore drives MCP for the edits. For whole-file writes it pins MCP `content` and REST `PUT` to the same written line.
- **Tests.** `file-edit-lines-parity.test.ts` runs the preview, the refusal and the forced commit on the shared fake ledger: an edit that grows, one that shrinks, one that keeps the count, chained edits, an error inside the new text, and the whole-file controls. It is registered as an `updateLedgerFiles` proof in `write-preview-matrix.test.ts`. `edit-ledger-files-gate.test.ts` adds a table of line-break shapes: merges, whole-line cuts, a break cut from a line's start, mid-word splits, CRLF, chained edits, an edit below the error, and a batch that also writes the file whole. `bean-check-errors.test.ts` covers replacements in `atLinesBeforeEdits`. With the gate's mapping off, 19 cases fail; with `replaced` ignored, 4 mapper cases fail. The keep-the-count, below-the-error, forced-commit and whole-file cases pass either way, as intended. The ledger's `verifyProjectedEditLines` (`scripts/edit-error-lines.ts`, run by `verify:rustledger`) checks on the live engine what the mapping depends on: the projected check names the assertion at its line in the edited text. The packages share no code, so the mapping itself is tested in backend-v2. `docs/mcp.md` now lists the exact-text edit among the writes that map lines.
- **Checks.** `backend-cluster/backend-v2`: `yarn typecheck`, `yarn format:check`, `yarn lint:deadcode`, ESLint on the changed files, `yarn test` (505 suites, 13,329 tests), and `yarn generate-v1-openapi` with no drift. `backend-cluster/ledger`: `yarn typecheck`, `yarn lint:deadcode`, `yarn test` (233 suites, 3,879 tests) and `yarn verify:rustledger`.
- **Not done here.** The live `beancount.io` repro waits for backend-v2 and the ledger service to deploy.
