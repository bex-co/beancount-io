# A negative posting price (`10 EUR @ -1.10 USD`), a merge cost `{*}`, and a cost with two dates, two labels or two amounts all read clean and commit, though stock `bean-check` 3.2.3 refuses each; the negative price is booked as a negative weight, on MCP, REST and GraphQL

**Minor · ledger (`src/foundation/rustledger/engine.ts`, `stock-syntax-errors.ts`) · 30–45m · A1.** `@rustledger/wasm` 0.24.0 loads five posting constructs that Beancount's parser refuses. The ledger service adds no error for any of them. Each one previews `valid: true` with `newErrors: []`, commits without `allow_invalid`, and reads clean on every error surface. The same file fails `bea check` and stock `bean-check`, and Fava will not load it.

The negative price is the one that changes figures. A sign typo on a currency exchange reads as "received 10 EUR and also received 11 USD", and every balance, BQL `weight` and report built on it follows. That path already refuses a malformed account (`"Assets:Cash:" is not a valid account`, `BAD_USER_INPUT`), so the refusal machinery is there.

## Repro (live)

1. Send `updateLedgerFiles` with `dry_run: true`, giving `main.bean`'s whole content with one case appended at a time. For example:

   ```beancount
   2026-09-01 open Assets:Broker
   2026-09-01 * "buy"
     Assets:Broker  10 HOOL {5 USD, 2026-01-01}
     Assets:Bank:Checking  -50.00 USD
   2026-09-01 * "buy2"
     Assets:Broker  10 HOOL {7 USD, 2026-01-02}
     Assets:Bank:Checking  -70.00 USD
   2026-09-02 * "sell"
     Assets:Broker  -5 HOOL {*}
     Assets:Bank:Checking  30.00 USD
   ```

   Every row of the table answers `valid: true`, `newErrors: []`. Stock `bean-check` on the same file gives the error in the table.
2. Commit with `appendLedgerText` (no `allow_invalid`):

   ```beancount
   2026-09-01 open Assets:Qa20261127Wallet

   2026-09-01 * "qa-20261127-negprice" "negative price"
     Assets:Qa20261127Wallet  10 EUR @ -1.10 USD
     Assets:Bank:Checking  11.00 USD
   ```

   The result is `Added … No new bean-check errors.` with `validation.valid: true`. REST `POST …/directives/text` and GraphQL `appendLedgerText` with `dryRun: true` give the same verdict.
3. Read the errors. MCP `checkLedger` returns `errors: []`. `resources/read beancount://<qa-owner>/mcp-agent-eval/errors` returns `[]`. REST `GET …/errors` returns `200 []`. GraphQL `getLedgerErrors` returns `[]`.
4. `runBqlQueryStructured` `SELECT date, account, position, price, weight WHERE payee ~ 'qa-20261127'` gives `price {"USD": "-1.10"}` and `weight {"USD": "-11.00"}` on the wallet posting.
5. Control: `bea --file <the committed main.bean> check` exits 1 with `Negative prices are not allowed: -1.10 USD` and `Transaction does not balance: (22.00 USD)`.

## Cause

The engine accepts all five; checked directly against `@rustledger/wasm` 0.24.0 under Node (`validateSource` reports no error, `parse` keeps the price `-1.10`, the first date, label and amount, and an empty cost for `{*}`). The ledger service backs stock's other parser refusals with its own rules: `stockSyntaxErrors` (`stock-syntax-errors.ts:152`, wired at `engine.ts:855`), `midCurrencyToleranceErrors`, `coherentCostErrors`. None of them covers a posting's price sign or a cost spec's repeated components.

## Fix

Report each construct as an error at the posting's transaction line, with stock's wording, the way `stockSyntaxErrors` reports a bare booking method:

- a negative per-unit or total price. The parsed directives carry the price, so this can read `posting.price` in `engine.ts`, or a text rule can read the line. Do not also fold the sign the way stock does; the error is enough, and the entry must not count as clean;
- `{*}`: `Cost merging is not supported yet`;
- a second date, label or per-unit/total amount in one `{…}`: `Duplicate date`, `Duplicate label`, `Duplicate cost`. Track strings so a `"a, b"` label is one label.

Structured `addLedgerEntries` should refuse a negative `price`/`totalPrice` number up front with `BAD_USER_INPUT` naming the posting, beside its account check. If that check lives in backend-v2, the ledger error above already makes the preview `valid: false` and the commit `VALIDATION_FAILED`, so this part can be its own commit.

No response shape changes. Every surface reads these errors from the one ledger path: the MCP tools and `errors` resource, the REST `errors` route and write previews, and GraphQL `getLedgerErrors` and the write mutations.

**Resolved 2026-11-27** — The ledger service now reports each of the five constructs with stock's wording, on the posting's own line, so the entry no longer reads clean and a commit without `allow_invalid` is refused. Every stock message in the table matches bean-check 3.2.3 byte for byte, line included.

- **ledger, text rule.** `posting-syntax-errors.ts` reads a transaction's posting lines with stock's lexer rules (a `1,000.00` number, a `2026/1/5` date, a `"a, b"` label is one label, `\"` stays inside it) and its posting grammar (units, an optional `{…}` or `{{…}}`, an optional `@` or `@@`). It reports `Negative prices are not allowed: -1.10 USD (see …)` (`NEGATIVE_PRICE`), `Cost merging is not supported yet` and `Duplicate merge-cost spec` (`COST_MERGE`), and `Duplicate cost: 'CompoundAmount(…)'.`, `Duplicate date: '2026-01-05'.` and `Duplicate label: 'b'.` (`DUPLICATE_COST_COMPONENT`). A price or cost expression is evaluated the way Python's `Decimal` evaluates it, so `@ (1-2.1) USD` reads `-1.1 USD`, `@ -10/0.5 USD` reads `-20 USD` and `{5 USD, 1 / 7 USD}` prints stock's 28 digits. `stockSyntaxErrors` runs it on every posting line it already walks for duplicate keys, and the engine's error assembly in `engine.ts` is unchanged otherwise. The sign is not folded, as the note asked.
- **Deviation from the note.** The note asked for the error at the transaction's line. Stock 3.2.3 puts all five on the posting's line (for example, `case.bean:7` for a posting under a header on line 6), so the service does too.
- **ledger, structured writes.** `POST /entries/{owner}/{repo}/bulk` (`src/api/entries.ts`) refuses a negative `price.number` or `totalPrice.number` before it reads a file: `entry 1: postings[0].price.number "-1.10" is negative; Beancount allows no negative price, …`, `BAD_USER_INPUT`. `0` and `-0` still write. backend-v2's `addLedgerEntries` reaches this route on MCP, REST and GraphQL, so it needed no change, and no response shape changed.
- **Controls.** `10 EUR @ 1.10 USD`, `@ 0 USD`, `@ -0 USD`, `@@ -0 USD`, `{5 USD, 2026-01-01, "lot1"}`, `{5 # 1 USD}` and `{}` stay clean. A line stock refuses as a syntax error (an unclosed `{`, a `#tag` inside a cost, two cost specs), or a label that spans lines, is left alone.
- **Checked against stock.** Compared with bean-check 3.2.3 on 1,808 random posting lines, 541 of which stock flags, and on the 126 tracked ledger fixtures. There was no difference. 192 further random lines that stock refuses as syntax errors were skipped, and the rule raised nothing stock does not on them.
- **Tests.** `posting-syntax-errors.test.ts` covers each construct, each spelling and each control, and the rule abstaining on syntax errors. `entries-amount-syntax.test.ts` covers the up-front refusal and the zero prices. With the fix reverted, 50 of the new tests fail. `scripts/verify-rustledger.ts` asserts that the raw engine still loads all six cases clean, so the rule is load-bearing, and that the service reports each at line 10, `valid: false`, and keeps the controls valid.
- **Gates.** `backend-cluster/ledger`: `yarn lint`, `yarn typecheck`, `yarn build`, `yarn test` (234 suites, 3,958 tests) and `yarn verify:rustledger` pass. The hosted repro against `beancount.io` waits for the next ledger deploy.
