# `renameAccount` is refused while any existing error names the account: the error's message now names the new account, so the rename's own preview and commit count it as new, though it is the same error under its new name (the account-rename twin of w1/236)

**Minor · backend-v2 (`src/features/ledger/workflow/account-rename-workflow.ts`, `src/features/ledger/utils/bean-check-errors.ts`) · 20–30m · A1.** `renameAccount` rewrites every account token at or under `from` and gates the result with `gateFileWrite` (`account-rename-workflow.ts:139`). That compares the ledger's errors before and after by message and file (`diffBeanCheckErrors`, `bean-check-errors.ts:176`). Many bean-check messages name an account, for example `Balance failed for Assets:Cash: …`. After the rename, an error the ledger already had names `to` instead of `from`, so it no longer matches its own baseline. It is reported as new. The preview answers `valid: false`, and the commit is refused `VALIDATION_FAILED` unless `allowInvalid`.

`docs/mcp.md` promises that "Errors the ledger already had never block." It also describes the file-rename case: "the moved file's own errors go with it to its new path, so renaming a file that carries errors reports none as new" (w1/236, `FileRenames` in `diffBeanCheckErrors`). The account rename has no such mapping. So the tool cannot rename an account while the account has any error. That is often when a ledger is being cleaned up, and the clean-up is exactly what an agent uses this tool for.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). The credential was an unpinned read/write/admin `bcio_` key on the QA account. Writes went only to the designated QA ledger `<qa-owner>/mcp-agent-eval`. `main.bean` was restored byte for byte afterwards (git blob `f1a0b83c`, sha256 `77c3a591efd311e0`), and the check shows 0 errors. HEAD `d5557bf6d` has the same code path.

## Repro

1. Make one assertion fail. `appendLedgerText {"text": "2026-08-30 balance Assets:Cash 40.00 USD", "allowInvalid": true}` commits with one error: `Balance failed for Assets:Cash: expected 40.00 USD, got 49.75 USD (main.bean:89)`.
2. Preview the rename: `renameAccount {"from": "Assets:Cash", "to": "Assets:Wallet", "dry_run": true}`. It answers "Would rename Assets:Cash to Assets:Wallet: 8 lines in 1 file. 1 new bean-check error: Balance failed for Assets:Wallet: expected 40.00 USD, got 49.75 USD (main.bean:89)" with `validation: {errorsBefore: 1, errorsAfter: 1, newErrors: [that], valid: false}`.
3. Commit the rename (no `allowInvalid`). It is refused `VALIDATION_FAILED`: "this file change would introduce 1 new bean-check error: Balance failed for Assets:Wallet: …". The hint then says "Fix the file contents", which does not apply to a rename. Nothing is written.

The figures are unchanged (expected 40.00, got 49.75), and so are the line and the count. Only the account name in the message moved with the rename. With a passing baseline (`checkLedger` clean), the same rename previews `valid: true`, which is the control. REST `POST …/rename-account` and GraphQL `renameLedgerAccount` go through the same workflow.

## Fix

- Let the rename carry its account mapping into the diff, as file moves carry `FileRenames`. Before keying, rewrite each baseline error's message with the workflow's own `accountTokenOffsets` / `renameAccountAt` (`from` → `to`, whole names only, children included). A `before` error then matches its renamed `after` copy. An error the rename really adds still counts, for example a collision with an existing `open` or a renamed account used before its `open`.
- Apply the same mapping in the commit's post-write validation.
- Tests:
  - `account-rename-workflow.test.ts`: a baseline error naming `from`, and one naming a child, are not new after the rename.
  - `rename-parity.test.ts`: the same preview and commit on MCP, REST and GraphQL.
  - Keep a case where the rename does add an error.
  - Revert the fix and watch them fail.
- Independent of w31/113. With both fixed, renaming an account whose assertion is off also survives a changed "got" figure.

## Done when

With an assertion on `Assets:Cash` already failing, `renameAccount Assets:Cash → Assets:Wallet` previews `valid: true` with `newErrors: []` on MCP, REST and GraphQL. It commits without `allowInvalid` and reports "No new bean-check errors". `checkLedger` then shows the same single assertion error, now naming `Assets:Wallet`.

---

**Resolved 2026-11-27** — The account rename now carries its account mapping into the error diff, as a file move carries `FileRenames`. `AccountRenameWorkflow` passes `{ account: { from, to } }` to `gateFileWrite`, which hands it through `toWriteValidation` to `diffBeanCheckErrors`. Before keying, that diff reads every message, before and after, through the new `renameAccountInMessage` (`src/features/ledger/utils/account-rename.ts`): `from` becomes `to`, on whole names only, with children included. A quoted narration that keeps the old name still matches. An error the ledger already had that names the account therefore matches its copy under the new name, and an error the rename adds still counts. The rename has no post-write read: its commit verdict is this same gate, so the preview and the commit on MCP, REST and GraphQL all get the fix. Tests:
- `account-rename.test.ts`: the message rename covers the colon after a name, children, quoted names, longer names, suffixes and parents.
- `bean-check-errors.test.ts`: a renamed account's error and its child's are not new. An added error, a second copy and a prefix-only name still count, and a narration that keeps the old name matches.
- `account-rename-workflow.test.ts`: over a failing assertion and a child's error, the preview is `valid: true` and the commit lands without `allowInvalid`. An error added beside them is still refused.
- `rename-account-parity.test.ts`: on REST, GraphQL and MCP, over a failing assertion, the preview gives `valid: true` and `newErrors: []`. The commit then lands without `allowInvalid`, and MCP reports "No new bean-check errors". An added error is still refused and named alone.

With the fix set aside, 12 of these cases fail. `docs/mcp.md` now states the rule. backend-v2 gates passed: `yarn typecheck`, `yarn format:check`, ESLint, `yarn lint:deadcode`, `yarn test` (504 suites / 13,248 tests), and the OpenAPI snapshot shows no drift. The parity case is in `rename-account-parity.test.ts`, not in `rename-parity.test.ts` (the file-rename suite) as the note said. Shipped in the commit carrying this note (`backend-cluster/backend-v2`).
