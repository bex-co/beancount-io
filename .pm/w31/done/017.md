# `moveEntrySources` description still says the move is "byte for byte"

Source: follow-up from `w31/016` (`71c06b859`), 2026-11-15.

- Since `w31/016`, a moved entry keeps its source file's `pushtag`/`pushmeta` scope. The ledger service now writes those tags or metadata onto the entry at its destination, so the text that arrives is no longer an exact copy of the text that left.
- The shared tool description still promises a "byte for byte" move. Copies of that description live in the CLI's OpenAPI client and in the dashboard as well as in backend-v2.
- Paths: start from backend-v2's `moveEntrySources` description, then the generated or copied text under `cli/` (OpenAPI) and `dashboard/`. Regenerate generated copies instead of hand-editing them.

**Done when:** every copy of the `moveEntrySources` description says how scoped entries move: they keep their pushed tags and metadata, which are written onto the entry. No copy claims a byte-for-byte move any more, and each package's own checks pass.

**Resolved 2026-11-15** — The shared `moveEntrySources` description (`MOVE_ENTRIES_DESCRIPTION`, `backend-cluster/backend-v2/src/features/ledger/utils/move-entries.ts`) no longer says the source text leaves its file "byte for byte". It now says: "An entry inside its file's pushtag or pushmeta scope keeps that scope's tags and metadata, written onto the entry, so its hash stays but its text and sha256sum change; any other entry's text moves unchanged." MCP `moveEntrySources`, REST `POST …/entries/move` and GraphQL `moveLedgerEntrySources` all build their descriptions from it. The `preview` field now reads "Each moved entry's text as toPath receives it, with the file it leaves", because a scoped entry's preview is the text with its scope written on (w31/016). The ledger IDL's `moveSourceSlices` description (`backend-cluster/idl/beancount-ledger.openapi.json`, which is maintained by hand) says the same thing. `docs/mcp.md` "Moving entries to another file" and `docs/api-parity.md` now match.

The copies were regenerated, not edited by hand:
- backend-v2 `src/foundation/fava/Api.ts`: `yarn generate-fava-client`.
- backend-v2 `docs/openapi/v1.json`: `yarn generate-v1-openapi`.
- The CLI's pinned `cli/openapi/v1.json` and its REST client: `make spec-sync && make codegen`.
- dashboard `src/graphql/definitions.ts`: `yarn codegen`, run against the SDL printed from backend-v2's `buildGraphqlSchema`. This also picked up the holdings fields that `849766134` (w1/255) added to the schema without regenerating the dashboard. No dashboard document reads those fields.

A new test in `move-entry-sources-parity.test.ts` ("moveEntrySources description (w31/017)") reads the description from MCP `tools/list`, the live v1 OpenAPI document and the GraphQL schema. It requires the scope sentence and rejects "byte for byte". It fails against the old text.
