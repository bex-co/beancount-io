# A malformed file path is refused `BAD_USER_INPUT` "Invalid file path" on every MCP file tool, naming neither the argument nor the rule, while REST and GraphQL name the field; `listLedgerFiles` also refuses `dir_path: "Reports/"`

**Minor · backend-v2 (`src/features/ledger/utils/safe-repo-path.ts`, `src/features/ai-agent/utils/run-tool.ts`, `src/features/ai-agent/tools/agent-repo-path.ts`) · 30–45m · A1.** `assertSafeRepoPath` (`safe-repo-path.ts:10`) refuses an empty segment (`a//b.bean`, a trailing `/`), a `.` or `..` segment, or a backslash with the bare message `Invalid file path`, and puts the argument only in `metadata.field`. REST returns that field (`"metadata":{"field":"newPath"}`) and GraphQL returns it (`extensions.field`). MCP drops it: `carrierFields` (`run-tool.ts:68`) is an allowlist of `retryAfter`, `newLedgerErrors` and `limitOwner`, so a tool refusal carries `code`, `message` and the fallback hint only. That hint reads "Fix the named argument and call again", but no argument is named. An agent that sent `oldPath` and `newPath`, `toPath` and `includeFrom`, or three `files[]` paths cannot tell which one is wrong, or what is wrong with it. `docs/mcp.md` "Argument limits" promises that a refused value is `BAD_USER_INPUT` "naming the parameter".

The commonest trigger is a directory written with a trailing slash, as `ls` prints it. `listLedgerFiles {dir_path: "Reports/"}` is refused `Invalid file path` before any lookup (`"nope/"` gives `BAD_USER_INPUT`, while `"nope"` gives `NOT_FOUND`). The QA ledger has no folder, so the refusal was seen on a missing name; the validator runs before the listing, so an existing folder is refused the same way. `normalizeAgentDirPath` (`agent-repo-path.ts:19`) already rewrites the other shell spellings `.` and `./` for MCP (w31/064, w31/067), but not a trailing `/`.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-27. Target: `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`). Credential: an unpinned read/write `bcio_` key on the QA account. Only reads and dry runs were used, on the QA ledger `<qa-owner>/mcp-agent-eval`. HEAD has the same `safe-repo-path.ts`, `carrierFields` and `normalizeAgentDirPath`, so this is not deployment lag.

## Repro (synthetic, any ledger the key can write)

Each call returns `isError: true`, `BAD_USER_INPUT`, the message below and the hint "Fix the named argument and call again; `tools/list` publishes each tool's input schema."

1. `renameLedgerFile {oldPath: "main.bean", newPath: "x//y.bean", dry_run: true}`: `Invalid file path`.
2. `renameLedgerFile {oldPath: "main.bean/", newPath: "y.bean", dry_run: true}`: `Invalid file path`. This is the same text as step 1, though the other argument is the wrong one.
3. `moveEntrySources {…, toPath: "dir/", dry_run: true}` and `moveEntrySources {…, toPath: "m.bean", includeFrom: "main.bean/", dry_run: true}`: `Invalid file path` both times.
4. `createLedgerFiles {files: [{path: "a.bean", …}, {path: "b.bean", …}, {path: "dir/", …}], dry_run: true}`: `preview refused: Invalid file path`. No index is given. `updateLedgerFiles` (`qa/./main.bean`), `deleteLedgerFiles` (`qa/../main.bean`), `readLedgerFiles` (`a//b.bean`) and `appendLedgerText {path: "qa//x.bean"}` behave the same way.
5. `listLedgerFiles {dir_path: "nope/"}`: `Invalid file path`. `listLedgerFiles {dir_path: "nope"}` answers `NOT_FOUND` "Directory 'nope' not found", so the trailing slash is refused before any lookup, whether or not the directory exists (`safe-repo-path.ts:21` refuses the empty last segment).

## Controls

- **REST.** `POST /api-gateway/v1/ledgers/{owner}/{name}/rename-file` with step 1's or step 2's body gives `400 BAD_USER_INPUT` "Invalid file path" with `"metadata":{"field":"newPath"}` or `{"field":"oldPath"}`. `POST …/entries/move` names `toPath` or `includeFrom`. `GET …/files?dir=nope/` names `dirPath`.
- **GraphQL.** `getLedgerDirContent(ledgerId, dirPath: "nope/")` gives `BAD_USER_INPUT` "Invalid file path" with `extensions.field: "dirPath"`.
- **MCP, other refusals.** A NUL in a path is caught earlier and named (`files[].path must not contain a NUL (U+0000) character`). A malformed `ledger` names the slug rule. A missing directory gets a hint saying names are case-sensitive. Only this helper's refusals lose the argument.
- **Scope.** A scan of `new BadUserInputError(message, field)` in `backend-v2/src` finds 109 calls with a field. In 14 of them the message omits the field: four in `safe-repo-path.ts`, two in `ledger-asset-service.ts`, one each in `blob-sha.ts`, `safe-archive-name.ts`, `plaid-sync-service.ts`, `assert-bank-account.ts` and `domain-errors.ts`, and three `ledgerId` checks in `shared/str.ts`. The path checks are the ones every MCP file tool reaches.

## Fix

1. In `assertSafeRepoPath`, put the value and the broken rule in the message. Every surface then reads it, and REST and GraphQL keep `field` as now. For example: `File path "x//y.bean" has an empty part: remove the doubled or trailing "/"`, `File path "qa/../main.bean" has a "." or ".." part: write it relative to the ledger root`, and `File path "a\b.bean" uses "\": separate folders with "/"`. The echo is bounded by the `DomainError` constructor as usual (w1/225). "File path must not be empty" stays as it is, since there is no value to quote. Give the `.git` refusal the value too.
2. In `normalizeAgentDirPath`, also drop one trailing `/` from `dir_path`, so `"Reports/"` lists `Reports`. This is the MCP-only shell-spelling rule that `./` already follows (w31/064, w23/084). REST `dir` and GraphQL `dirPath` stay strict, but they now get the clearer message from step 1.
3. Optionally, MCP could add `field` to `carrierFields`. The service field names (`dirPath`, `operations[2].path`, `paths[1]`) are not the MCP argument names (`dir_path`, `files[2].path`), though, so quoting the value is what identifies the argument.

## Done when

- Repro steps 1–4 give `BAD_USER_INPUT` with a message that quotes the offending path and states the rule, so steps 1 and 2 read differently. The same calls on REST and GraphQL carry the same message and keep their `field`.
- `listLedgerFiles {dir_path: "<existing dir>/"}` lists that directory, as `"<existing dir>"` does.
- `safe-repo-path.test.ts` asserts the message for each rule, and `agent-repo-path.test.ts` covers the trailing slash. A rename parity test asserts that MCP, REST and GraphQL name the wrong one of `oldPath` and `newPath`. With the change reverted, the new cases fail.

**Resolved 2026-11-27** — Every `assertSafeRepoPath` refusal now quotes the path and names the rule it broke, so a call with several paths shows which one is wrong: `File path "x//y.bean" has an empty part: remove the doubled "/"`, `File path "main.bean/" ends with "/": remove the trailing "/"`, `File path "/main.bean" starts with "/": write it relative to the ledger root`, `File path "qa/../main.bean" has a "." or ".." part: write it relative to the ledger root`, `File path "a\\b.bean" uses "\": separate folders with "/"`, `File path "…" contains a NUL (U+0000) character`, and `File path ".git/config" is inside .git, which can't be read or written`. "File path must not be empty" is unchanged. REST and GraphQL keep their `field`. The refusals reach every MCP file tool through the same helper. MCP `listLedgerFiles` also drops one trailing `/` from `dir_path`, so `Reports/` lists `Reports` and `Imports/` answers `NOT_FOUND` like `Imports`. A bare `/`, a doubled `//`, and a trailing `/` after `.` or `..` are still refused. REST `dir` and GraphQL `dirPath` stay strict but get the clearer message. `docs/mcp.md` documents the path rules under "Argument limits" and the trailing `/` in the `listLedgerFiles` row. Fix step 3, adding `field` to MCP `carrierFields`, was not done: the service field names (`dirPath`, `operations[2].path`) are not the MCP argument names, so the quoted value is what identifies the argument.
