# `insertReceiptTransaction` (`POST .../import/insert-receipt`, GraphQL `insertReceiptTransaction`) accepts blank/malformed `documentAccount` and empty `postings: []` instead of refusing upfront with `BAD_USER_INPUT`

**Minor · backend-v2 (`LedgerReceiptWorkflow.insertReceiptTransaction`) · 30–45m · A1.** Passing a blank or syntactically invalid Beancount account name for `input.documentAccount` (`""`, `"   "`, `"not-an-account"`) or an empty `input.postings: []` array passes validation across MCP, REST, and GraphQL, proceeding past the pre-flight entry dry run (`writeBulkEntries(..., dryRun: true)`) to fetch `bcio` options, resolve ledger metadata, and promote/download the temporary S3 asset. When a receipt has been uploaded, S3 storage (`s3Strategy`) silently commits with `200 OK` (accepting a garbage `documentAccount` or a zero-posting transaction and deleting the temp upload), while Git storage (`gitStrategy`) downloads the receipt from S3 and **commits the receipt file to Git** before `writeBulkEntries([document, transaction])` finally rejects the invalid `documentAccount`, forcing a second cleanup Git commit that litters history on every bad call (the same class `w23/058` fixed for transaction postings, and a direct sibling of `w31/052`). Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, checked against HEAD `42378939e`). Credential: unpinned read/write/admin `bcio_` key on `<qa-owner>/mcp-agent-eval`; probes used a freshly minted, unuploaded `objectKey` from `generateTempAssetUploadUrl` (no bytes uploaded to S3, no ledger mutations).

## Working controls

- On the exact same operation and unuploaded `<key>` across MCP, REST, and GraphQL, passing `postings[0].account: "not-an-account"` (with valid `documentAccount: "Assets:Cash"`) is refused before S3 with `BAD_USER_INPUT`: `'entry 0: postings[0].account "not-an-account" is not a valid account'`.
- Passing `date: "not-a-date"` or `postings[0].amountNumber: "abc"` is likewise refused before S3 with `BAD_USER_INPUT`.
- Passing `receiptObjectKey: ""` is refused before authorization or S3 with `BAD_USER_INPUT` (`assertTempAssetKey`, `w5/054`).
- Sibling `PlaidSyncService.submitTransactionsToLedger` (`w31/052`, commit `42378939e`) validates Beancount account names with `lexesAsAccount` (`@/features/ledger/utils/account-matcher`) upfront before authorization or I/O.

## Root cause

Not deployment lag — present at HEAD `42378939e`:

- `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-receipt-workflow.ts:154-188` (`LedgerReceiptWorkflow.insertReceiptTransaction`):
  - Only calls `assertTempAssetKey(receiptObjectKey, "receiptObjectKey")` at `:166`, then authorizes and calls `runIdempotentEntryWrite` -> `insertAuthorized`.
  - Never checks `lexesAsAccount(input.documentAccount)` or `input.postings.length === 0`.
  - In `gitStrategy` (`:250-258`), the pre-flight dry run checks only `[transaction]` — never `input.documentAccount` — because the receipt file does not exist yet. So an invalid `documentAccount` downloads the receipt (`:280`), commits it to Git (`:291`), fails at `:317` when building the `document` directive, and creates a second cleanup commit (`:339`).
  - In `s3Strategy` (`:369-430`), `input.documentAccount` is never validated or referenced at all, so any blank or invalid string silently succeeds.
  - Because Beancount treats a zero-posting transaction as a warning rather than an error, `input.postings: []` also passes the `:250`/`:381` dry run and reaches S3 promotion.
- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/receipt-insert-handler.ts:32-42` (`receiptInsertInput`): declares `postings: z.array(receiptPostingSchema)` without `.min(1)` and `documentAccount: z.string()` without validation; GraphQL `InsertReceiptTransactionInput` (`src/features/ledger/api/resolvers/ledger-receipt-resolver.ts:33-48`) has no input constraints.

## Fix

In `backend-cluster/backend-v2`:

1. At the entry of `LedgerReceiptWorkflow.insertReceiptTransaction` (`src/features/ledger/workflow/ledger-receipt-workflow.ts:166`, alongside `assertTempAssetKey` and before `authorizeOrThrow` / `runIdempotentEntryWrite`, or right after `authorizeOrThrow` if keeping auth-before-input-details — note that `assertTempAssetKey` runs before `authorizeOrThrow` here, and `w31/052` checks syntax before auth while preserving `FORBIDDEN` for read-only callers with valid inputs):
   - Refuse `input.postings.length === 0` with `BadUserInputError("postings must contain at least one posting", "postings")`.
   - Validate `input.documentAccount` with `lexesAsAccount(input.documentAccount)` (from `@/features/ledger/utils/account-matcher`); refuse blank, whitespace-only, or malformed values with `BadUserInputError(\`documentAccount ${JSON.stringify(input.documentAccount)} is not a valid Beancount account name\`, "documentAccount", 'Pass a colon-separated Beancount account name such as "Expenses:Food:Dining" or "Assets:Bank:Checking".')`.
2. Verify whether `receiptInsertInput` (`src/features/ledger/api/rest/v1/receipt-insert-handler.ts:37`) should stay workflow-validated (no OpenAPI diff) or also tighten `postings` to `.min(1)` (if `receipt-insert-handler.ts` changes, run `yarn generate-v1-openapi` and sync `cli/openapi/v1.json` via `make spec-sync && make codegen` in `cli/`). Keeping the guard in `LedgerReceiptWorkflow.insertReceiptTransaction` enforces identical behavior across MCP, REST, GraphQL, and the in-product chat tool (`src/features/ai-agent/tools/insert-receipt-transaction-tool.ts`).
3.
