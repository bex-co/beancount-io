# Account-name validators in `backend-v2` accept non-ASCII component starts (`Assets:Bank:épargne`, `Assets:Bank:€`, `Assets:Bank:😀`) that the ledger engine cannot parse, while disagreeing on Unicode format characters (`U+200B`, ZWNJ/ZWJ)

**Major · backend-v2 (`src/features/ledger/utils/account-matcher.ts`, `src/features/ledger/setup/build-ledger.ts`) · 35–45m · A1/A2.** Five account-writing workflows in `backend-v2` — `previewLedgerSetup`/`createLedger` (`build-ledger.ts`), `renameAccount` (`account-rename-workflow.ts`), `insertReceiptTransaction` (`receipt-insert-validation.ts`), `mapBankAccount`, and `importStagedBankTransactions` (`assert-bank-account.ts`) — validate account names before rendering or delegating to the ledger engine, across MCP, REST, and GraphQL. Both underlying regexes (`ACCOUNT_PATTERN` in `build-ledger.ts:57-58` and `ACCOUNT_TOKEN_RE` in `account-matcher.ts:39-52`) allow **any** non-ASCII code point (`\P{ASCII}` / `[^\p{ASCII}\s\p{Cc}]`) at the **start** of an account component. However, the live rustledger engine only accepts Unicode categories `Lu`, `Lt`, `Lo`, and `Nd` (`[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]`) at a component start — it rejects lowercase non-ASCII letters (`Ll`, e.g. French `Assets:Bank:épargne`, `Assets:épargne`), currency symbols (`Sc`, `Assets:Bank:€`), emojis (`So`, `Assets:Bank:😀`), non-ASCII punctuation (`Pd`/`Ps`, `Assets:Bank:—`, `Assets:Bank:「Foo」`), modifier letters (`Lm`), and non-decimal numbers (`Nl`/`No`). In addition, the two validators disagree on Unicode format characters (`\p{Cf}`): `account-matcher.ts` (`REFUSED` / `WIDE`) accepts invisible zero-width spaces (`Assets:Bank:Foo\u200BBar`) that `build-ledger.ts` and `entry-tokens.ts` refuse, while `build-ledger.ts` (`NOT_IN_A_NAME = /[\s\p{C}]/u`) refuses Persian/Indic ZWNJ/ZWJ (`Assets:Bank:خانه‌ها`) that the ledger engine, `addLedgerEntries`, and `renameAccount` all accept (`w21/649`, `w31/013`). Companion `backend-cluster/ledger` fix is tracked in `w31/082`.

## Expected

- Every account-name validator in `backend-v2` rejects account components whose leading character is not in `[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]` (e.g. `Assets:Bank:épargne`, `Assets:épargne`, `Assets:Bank:€`, `Assets:Bank:😀`, `Assets:Bank:—`) upfront with its existing input-validation error (`VALIDATION_FAILED` on `setup` in `previewLedgerSetup`/`createLedger`; `BAD_USER_INPUT` in `renameAccount`, `insertReceiptTransaction`, `mapBankAccount`, and `importStagedBankTransactions`), identically across MCP, REST, and GraphQL.
- Format/control rejection is consistent across validators: reject all `\s` and `\p{C}` except Persian/Indic ZWNJ (`\u200C`) and ZWJ (`\u200D`) in non-leading positions (matching `entry-tokens.ts:25`, `w21/649`), so `Assets:Bank:Foo\u200BBar` is refused everywhere and `Assets:Bank:خانه‌ها` is accepted in `previewLedgerSetup`/`createLedger` as in `addLedgerEntries`/`renameAccount`.

## Root cause

Not deployment lag — reproduced identically at local HEAD `439cf6ae9`:

- `backend-cluster/backend-v2/src/features/ledger/setup/build-ledger.ts:57-59`: `ACCOUNT_PATTERN` uses `[\p{Lu}\p{N}\P{ASCII}]` as the component-start character class. `\P{ASCII}` matches every non-ASCII code point (including `\p{Ll}`, `\p{S}`, `\p{P}`, `\p{Nl}`, `\p{No}`), contradicting the comment on `:52-55` ("an uppercase letter, a digit, or a non-ASCII letter"). Meanwhile `NOT_IN_A_NAME = /[\s\p{C}]/u` rejects `\u200C`/`\u200D` (ZWNJ/ZWJ).
- `backend-cluster/backend-v2/src/features/ledger/utils/account-matcher.ts:31-52`: `WIDE = "[^\\p{ASCII}\\s\\p{Cc}]"` is used in both component-start and continuation positions of `ACCOUNT_TOKEN_RE`, so `lexesAsAccount` (and therefore `loadsAsAccount` whenever the first component is valid, such as `Assets:Bank:épargne` or `Assets:Bank:😀`) accepts any non-ASCII code point at component start, and `REFUSED` (`:31-33`) omits `\p{Cf}` characters other than bidi overrides (allowing `U+200B` ZWSP, `U+00AD` soft hyphen, etc.).

## Fix

In `backend-cluster/backend-v2`:

1. In `src/features/ledger/utils/account-matcher.ts`:
   - Narrow the component-start class in `ACCOUNT_TOKEN_RE` (for both root and sub-components) from `(?:[A-Z]|${WIDE})` / `(?:[A-Z0-9]|${WIDE})` to match what rustledger actually lexes at a component start: `[\p{Lu}\p{Lt}\p{Lo}]` for root start and `[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]` for component start (with continuation characters remaining `[A-Za-z0-9-]|${WIDE}`).
   - Align `REFUSED` / `WIDE` with `entry-tokens.ts:25` (`(?![\u200c\u200d])[\s\p{C}]`) so `\p{Cf}` format characters like `U+200B` (ZWSP) and `U+00AD` are refused while ZWNJ (`\u200C`) and ZWJ (`\u200D`) remain allowed inside a component (never at component start). Keep `ACCOUNT_CHAR` consistent for `account-rename.ts`.
   - Update `ACCOUNT_NAME_RULE` in `src/features/ledger/workflow/account-rename-workflow.ts:226-227` if its prose ("each later component starts with a capital letter, a digit or a non-ASCII character") would misstate the narrowed rule.
2. In `src/features/ledger/setup/build-ledger.ts:57-59`:
   - Narrow `ACCOUNT_PATTERN`'s component-start class from `[\p{Lu}\p{N}\P{ASCII}]` to `[\p{Lu}\p{Lt}\p{Lo}\p{Nd}]` (keeping valid continuation chars including non-ASCII letters/digits/marks/dashes/ZWNJ/ZWJ) and update `NOT_IN_A_NAME` to `/(?![\u200c\u200d])[\s\p{C}]/u`.
   - Update the error message on `:281` if needed so it states the actual rule clearly.
3. Add regression tests in:
   - `src/features/ledger/utils/__tests__/account-matcher.test.ts` (`Assets:Bank:épargne`, `Assets:épargne`, `Assets:Bank:€`, `Assets:Bank:😀`, `Assets:Bank:—`, `Assets:Bank:Foo\u200BBar` rejected; `Assets:Bank:Épargne`, `Assets:Bank:Café`, `Assets:Bank:日本`, `Assets:Bank:خانه‌ها`, `Assets:Bank:١` accepted).
   - `src/features/ledger/setup/__tests__/build-ledger.test.ts` (same refused/accepted cases on `blank@1`).
   - `src/features/ledger/api/rest/v1/__tests__/rename-account-parity.test.ts` and `setup-surfaces.test.ts` (MCP, REST, GraphQL all refuse `Assets:Bank:épargne` upfront with `BAD_USER_INPUT` / `VALIDATION_FAILED` before any ledger write or projection).
   - Verify `receipt-insert-validation.test.ts` and `assert-bank-account.test.ts` cover `Assets:Bank:épargne` refusal via `lexesAsAccount`.
