# `revertCommit` on a `renameAccount` commit restores the files but leaves the moved bank mappings on the new name

**Minor · backend-v2 (ledger workflow, bank mappings) · 45–60m · A1.** Follow-up from `/loopx w31` routine `mcp-qa`, 2026-11-27. Found by reading the source; not reproduced live, because the QA account has no bank connection and linking one is outside the standing write authorization.

`backend-cluster/backend-v2/docs/mcp.md` § "Renaming an account" says a rename's commit can be undone: "`revertCommit` on that sha undoes it". It also says bank-account mappings that name the renamed account move with it, "otherwise the next sync would post to an account that no longer exists". The move is made by `bankMappings.remap(…)` in `src/features/ledger/workflow/account-rename-workflow.ts`, which is the only caller of `remap`. `undoLedgerCommit` in `src/features/ledger/workflow/ledger-workflow.ts` restores only the git files, through `changeLedgerFiles`, and never touches mappings. So after the revert the files open the old account again, every moved mapping still names the new one, and the next sync posts to an account that no ledger file opens.

- Fix: either revert the mappings with the files, or say plainly what the revert does not do. To revert them, the rename commit has to record which mappings it moved, from what to what, so the undo can move them back. The preview should list them in `bankMappings` the way a rename's preview does. To keep the revert files-only instead, have the preview and the result name the mappings left on the new account, and change the docs so they do not promise a full undo.
- Done when `revertCommit` on a rename commit with a moved mapping, both preview and commit, either restores that mapping or reports it, the same way on MCP, REST and GraphQL. A fake-repo parity test covers it and fails with the fix reverted, and `docs/mcp.md` describes the behavior that ships.

---

**Resolved 2026-11-27**: `revertCommit` (MCP), REST `POST …/revert-commit` and GraphQL `revertLedgerCommit` now move a rename's bank mappings back when they revert a `renameAccount` commit. The fix takes the note's first option: the mappings revert along with the files.

- **Which commit counts (backend-v2).** The rename commit already records its pair in its subject, `Rename <from> to <to>`. `accountsRenamedByCommit` reads that subject, or git's default `Revert "…"` of it, and then checks the diff: every file the commit modified must be exactly that rename of its parent, in either direction. A commit that only carries the message moves nothing. Each mapping, every member's, that names an account the commit renamed goes back to its name before. A mapping on an account the rename never touched stays where it is, such as one opened under the new name later. Reverting the revert renames them again. The mappings are read only after their own `ledger.files.write` decision, and only for a commit that passes the check.
- **Result.** A `bankMappings` field sits beside `files`, in the rename's shape (`plaidAccount`, `from`, `to`, `updated`), on all three surfaces: the MCP output schema, the regenerated `docs/openapi/v1.json`, and the GraphQL `RevertLedgerCommitResponse`. A preview lists the moves with `updated: false` and moves nothing. A commit moves them after the files commit. If that update fails, the revert stands, each mapping says `updated: false`, and the MCP `summary` names each mapping still on the new name, to fix with `mapBankAccount`. Any other commit returns `bankMappings: []`. `docs/mcp.md` describes this under "Renaming an account", in the `revertCommit` row and in the undo paragraph. The REST and GraphQL descriptions say it too.
- **Tests.** `revert-commit-parity.test.ts` now runs the real rename workflow over the fake repository, with mappings held in memory. On MCP, REST and GraphQL it covers four cases: the preview and then the commit of a rename's revert, a revert of that revert, a failed mapping update, and a commit whose subject names a rename its diff does not make. The existing revert cases now pin `bankMappings: []`. With the move after the commit disabled, 9 cases fail. With the diff check reduced to the subject alone, the forged-subject case fails on all three surfaces. Unit tests cover the detector (`account-rename.test.ts`) and the workflow's authorization and remap outcomes (`account-rename-workflow.test.ts`).

The `tools/list` budget in `mcp-tool-list.test.ts` went from 135 KB to 136 KB, with a measured note: the list grew from 138,050 to 138,621 bytes, and the list had 190 bytes of headroom. Nearly all of the 571 bytes is the shared mapping item schema. The tool description adds no prose.

Gates: `backend-cluster/backend-v2`: `yarn typecheck`, `yarn test` (510 suites), `yarn lint:deadcode` and `yarn format:check` pass. `yarn generate-v1-openapi` changes only the revert route's description and the new `bankMappings` field. The CLI pin `cli/openapi/v1.json` and its REST client were regenerated with `make spec-sync && make codegen`, and `cli`: `make check-all` passes.

**Not observable yet.** Production keeps the old behaviour until backend-v2 is redeployed. The QA account has no bank connection, so no live revert was made.
