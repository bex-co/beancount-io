# Task-augmented MCP requests (`params.task: {}` / `{ ttl }`) answer uncoded JSON-RPC `-32603` with no `error.data` or hint across every MCP method and bypass `w31/079`'s `assertNoNulDeep` check

**Minor · backend-v2 (`src/server/api/composition-root.ts`) · 25–35m · A1.** Every MCP protocol-level parameter refusal in `backend-cluster/backend-v2/src/server/api/composition-root.ts` is shaped into this server's coded `McpRequestFailure` envelope (`-32602` with `data: { code: "BAD_USER_INPUT", message, hint }`, single `MCP error` prefix) so an agent never mistakes a client error for an internal server fault (`w1/036`, `w4/070`, `w5/041`, `w5/045`, `w6/001`, `w23/118`, `w23/208`, `w31/079`). However, when a client sends a task-augmented MCP request carrying a valid `params.task` object (such as `task: {}`, `task: { ttl: 60000 }`, or `task: { extra: "\u0000" }`) on **any** registered MCP method (`tools/call`, `resources/read`, `prompts/get`, `initialize`, `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list`, `ping`), `@modelcontextprotocol/sdk`'s `Protocol._onrequest` invokes `this.assertTaskHandlerCapability(request.method)` **before** any registered handler runs. Because this stateless endpoint advertises no `tasks` capability, the SDK throws a plain `Error` (`Server does not support task creation (required for <method>)`) with no numeric JSON-RPC code and no `data`, which `Protocol._onrequest` serializes as uncoded JSON-RPC **`-32603`** (`InternalError`) with **no `error.data` (`code`, `message`, `hint`)** — misleading retry logic into treating an unsupported client parameter as a server crash, and bypassing `w31/079`'s `assertMcpToolOuterParams` / `assertMcpParams` `assertNoNulDeep` check when `params.task` carries a NUL byte or unpaired surrogate in an extra property.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-24 against `https://beancount.io` (`beancount-mcp 1.0.0`, negotiated protocol `2025-11-25`, verified still present at local HEAD `e78cf822a` via `assembleMcpRegistry` + MCP SDK `Client` over `InMemoryTransport`). Credential: unpinned read/write/admin `bcio_` API key on the QA account (read-only key also exercised for boundary sweeps). Synthetic ledger: `<qa-owner>/mcp-agent-eval` (read-only protocol probes for this finding; separate disposable write round-trip restored `main.bean` byte-for-byte, sha256 `77c3a591efd311e0`, 0 bean-check errors).

## Expected

Sending `params.task` on any MCP request to this stateless server is refused in the server's single coded JSON-RPC error envelope — never uncoded `-32603` without `error.data`:

- JSON-RPC code `-32602` with `data: { code: "BAD_USER_INPUT", message: ..., hint: ... }` (and formatted message `BAD_USER_INPUT: ...\nHint: ...`, single `MCP error` prefix on SDK `Client`), stating that task-augmented requests (`params.task`) are not supported by this stateless endpoint and hinting to omit `params.task` and send the request directly.
- No domain work executes.

## Root cause

Not deployment lag — reproduced identically at local HEAD `e78cf822a`:

- `@modelcontextprotocol/sdk/dist/cjs/shared/protocol.js:344, 394-397`: `Protocol._onrequest` checks `isTaskAugmentedRequestParams(request.params)` (`dist/cjs/types.js:115`, which accepts any object whose optional `task` matches `TaskMetadataSchema` — a loose object with optional numeric `ttl`, so `{}`, `{ ttl: 60000 }`, and `{ extra: "\u0000" }` all match). When `taskCreationParams` is truthy, `Protocol._onrequest` runs `this.assertTaskHandlerCapability(request.method)` **before** invoking the registered handler.
- `@modelcontextprotocol/sdk/dist/cjs/server/index.js:254-261` delegates to `assertToolsCallTaskCapability(this._capabilities.tasks?.requests, method, "Server")` (`dist/cjs/experimental/tasks/helpers.js:22-25`), which throws a plain `new Error("Server does not support task creation (required for <method>)")` because `this._capabilities.tasks` is `undefined`.
- `protocol.js:426-434` catches that plain `Error`, sees `!Number.isSafeInteger(error['code'])`, and emits JSON-RPC `-32603` (`ErrorCode.InternalError`) with no `data` field.
- `backend-cluster/backend-v2/src/server/api/composition-root.ts` overrides every request handler (`tools/call`, `resources/read`, `prompts/get`, `initialize`, `*/list`, `ping`) to shape parameter failures into `McpRequestFailure`, and `mcp-request-parameters.test.ts:178-185` only tested a malformed `task: { ttl: "later" }` (where `isTaskAugmentedRequestParams` is `false`), so valid `params.task` objects slipped into the SDK's pre-handler `assertTaskHandlerCapability` throw.
- Additionally, `composition-root.ts:675-685` retains a dead `parsed.data.params.task ? CreateTaskResultSchema : CallToolResultSchema` validation branch (and `CreateTaskResultSchema` import at `:31`) that would throw a raw `McpError` with a Zod dump if a task-augmented `tools/call` ever reached `dispatchTool`.

## Fix

In `backend-cluster/backend-v2/src/server/api/composition-root.ts` (`assembleMcpRegistry`):

1. Override `assertTaskHandlerCapability` on `server.server` (following the existing structural-cast precedent at `:926` and `:1025`) so any task-augmented request throws a coded `McpRequestFailure` (via `refuseMcpParameters` / `envelopeFromThrown(new BadUserInputError(...))`, JSON-RPC `-32602`, `data.code: "BAD_USER_INPUT"`, clear message naming `params.task` and `method`, and actionable hint explaining that this stateless MCP endpoint does not support tasks and to omit `params.task`).
2. Remove the dead `parsed.data.params.task ? CreateTaskResultSchema : CallToolResultSchema` branch at `:675-685` (and the unused `CreateTaskResultSchema` import at `:31`), keeping `CallToolResultSchema` validation.
3. Add regression tests in `src/server/api/__tests__/mcp-request-parameters.test.ts` covering `params.task: {}`, `params.task: { ttl: 60000 }`, and `params.task: { extra: "\u0000" }` across `tools/call`, `resources/read`, `prompts/get`, `initialize`, `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list`, and `ping` — proving `-32602` with `data.code: "BAD_USER_INPUT"`, non-empty `hint`, single `MCP error` prefix on SDK `Client`, and zero domain calls.
