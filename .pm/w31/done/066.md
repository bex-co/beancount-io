# File writes skip blob `sha` format validation: REST `DELETE` with `sha: ""` silently drops the optimistic lock, REST `PUT` with `sha: ""` silently switches to `create`, and malformed `sha` values answer misleading `CONFLICT` across MCP, REST, and GraphQL

**Major · backend-v2 (`files-handler.ts`, `ledger-repo-service.ts`, `edit-ledger-files-tool.ts`, `ledger-workflow.ts`) · 40–50m · A1.** Direct file-write sibling of `w31/054` (`sha256sum` validation on entry-source writes). Passing an explicit empty (`""`), blank (`"   "`), or malformed (`"not-a-sha"`) Git blob `sha` to file write/delete operations is never validated upfront as `BAD_USER_INPUT`, causing silent safety-lock bypasses on REST and misleading `CONFLICT` errors across all three surfaces:
1. **REST `DELETE /api-gateway/v1/ledgers/{owner}/{name}/files/{*path}` (`files-handler.ts:339`)** uses `...(body.sha ? { sha: body.sha } : {})`, so an explicit `sha: ""` silently **drops the optimistic lock** and succeeds (`200 OK`, deleting the file unconditionally without checking its current SHA).
2. **REST `PUT /api-gateway/v1/ledgers/{owner}/{name}/files/{*path}` (`files-handler.ts:252,255`)** uses `body.sha ? "update" : "create"`, so an explicit `sha: ""` silently **switches from update to create** — returning `200 OK` (creating a new file) when the path does not exist, and `409 CONFLICT: "<path> already exists"` ("Creating is for a new file") when it exists.
3. **MCP `updateLedgerFiles` / `deleteLedgerFiles`, REST `PUT` / `DELETE`, and GraphQL `updateLedgerFile` / `deleteLedgerFile`** skip blob `sha` format validation for `"   "` and `"not-a-sha"` (and `""` on MCP), hitting Gitea and returning misleading `CONFLICT` (`"changed since you read it; re-read it and retry"`) — or leaking Gitea's raw `"[SHA]: Required"` on GraphQL `sha: ""` — instead of refusing immediately with `BAD_USER_INPUT` naming `sha`.

Expected:

- Across MCP (`updateLedgerFiles`, `deleteLedgerFiles`), REST (`PUT`/`DELETE …/files/{path}`), and GraphQL (`updateLedgerFile`, `deleteLedgerFile`), any explicitly provided `sha` (`sha !== undefined`) that is not a valid Git blob SHA (40 or 64 lowercase hex digits, `/^(?:[0-9a-f]{40}|[0-9a-f]{64})$/`) is refused upfront with `BAD_USER_INPUT` (`field: "sha"`, REST HTTP `400`) naming the expected hex Git blob SHA format and pointing at `readLedgerFiles` / `GET …/files/{path}` — without calling Gitea or silently dropping/reinterpreting `sha`.
- Omitting `sha` (`undefined`) keeps its documented meaning (unconditional overwrite/delete on MCP, create on REST `PUT`, unconditional delete on REST `DELETE`).

## Working controls

- Valid 40-lowercase-hex blob SHA that does not match the current file (e.g. `"0".repeat(40)`): returns `CONFLICT` (`"changed since you read it; re-read it and retry"`) across MCP, REST, and GraphQL.
- Matching 40-lowercase-hex blob SHA from `readLedgerFiles` / `GET …/files/{path}`: succeeds on preview and commit.
- Omitted `sha` on REST `PUT` creates a new file (and conflicts if it exists); omitted `sha` on MCP `updateLedgerFiles`/`deleteLedgerFiles` and REST `DELETE` updates/deletes without optimistic lock.

## Root cause

Not deployment lag — present at HEAD `f0fbe3d005991525f3bc1dfbcedce32b83d2a9bc`:

1. `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/files-handler.ts`:
   - `:252,255,262` (`PUT`): checks truthiness `body.sha ? "update" : "create"` instead of `body.sha !== undefined`, so `sha: ""` silently flips an update into a create.
   - `:339` (`DELETE`): checks truthiness `...(body.sha ? { sha: body.sha } : {})`, so `sha: ""` silently omits `sha` and deletes without optimistic-lock verification.
2. `backend-cluster/backend-v2/src/features/ledger/service/ledger-repo-service.ts:531,555` (`changeFiles`): checks truthiness `operation.sha` (`:531`, silently skipping `sha: ""` in dry-run version checks!) and never validates blob `sha` format before calling `getLedgerFilesContent` / `changeLedgerFiles`.
3. `backend-cluster/backend-v2/src/features/ai-agent/tools/edit-ledger-files-tool.ts:73,253-258`: `baseSha` is bare `z.string().optional()` and `applyOperations` compares `f.sha !== fileCache.get(f.path)?.sha` after fetching from Gitea, turning `""`, `"   "`, and `"not-a-sha"` into `staleFileConflict` (`CONFLICT`).
4. `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts:1214-1223,1308-1315` (`updateLedgerFile`, `deleteLedgerFile`): forwards `input.sha` straight to `favaApiClient` with no format validation.

## Fix

In `backend-cluster/backend-v2`:

1. Add a shared helper `assertBlobShaFormat(sha: string, field = "sha"): void` (e.g. in `src/features/ledger/utils/stale-file-conflict.ts` or a dedicated `src/features/ledger/utils/blob-sha.ts`) enforcing `/^(?:[0-9a-f]{40}|[0-9a-f]{64})$/` (Git SHA-1 40-hex or SHA-256 64-hex, lowercase) and throwing `BadUserInputError("sha must be a 40- or 64-character lowercase hex Git blob SHA from readLedgerFiles or GET …/files/{path}", field, "Read the file's current `sha` (MCP `readLedgerFiles`, or REST `GET` on the file) and pass it verbatim, or omit `sha` where optional.")`.
2. Wire `assertBlobShaFormat` into every file-write entry point (after authorization, before any Gitea/Fava file read or commit):
   - `files-handler.ts:252,255,262,339`: check `body.sha !== undefined` (never truthiness) and pass `sha: body.sha` through when present (so `sha: ""` never flips `PUT` to `create` or drops `sha` on `DELETE`).
   - `LedgerRepoService.changeFiles` (`ledger-repo-service.ts`): validate `operation.sha` with `assertBlobShaFormat` whenever `operation.sha !== undefined` (on `update` and `delete`), and check `operation.sha !== undefined` at `:531`.
   - `executeEditLedgerFiles` (`edit-ledger-files-tool.ts`): validate `f.sha` with `assertBlobShaFormat` whenever `f.sha !== undefined` before fetching files in `fileCache` (after authorization or via `changeFiles` dry-run / upfront guard so a read-only token still receives `FORBIDDEN`).
   - `LedgerWorkflow.updateLedgerFile` (`:1214`) and `deleteLedgerFile` (`:1308`): call `assertBlobShaFormat(input.sha)` after authorization and before `favaApiClient`.
3. Update any existing unit or parity tests that pass placeholder non-40-hex `sha` fixtures (e.g. `"abc"`, `"sha1"`, `"old-sha"`) as valid blob SHAs to use 40 lowercase hex digits (e.g. `"a".repeat(40)`), mirroring `w31/046` and `w31/054`.
4. Add unit tests and 3-surface parity tests (MCP `updateLedgerFiles`/`deleteLedgerFiles`, REST `PUT`/`DELETE …/files/{path}`, GraphQL `updateLedgerFile`/`deleteLedgerFile`) covering `""`, `"   "`, `"not-a-sha"`, uppercase 40-hex, valid mismatched 40-hex (`CONFLICT`), valid matching 40-hex (success), and omitted `sha` (`undefined`). Verify REST `DELETE` with `sha: ""` refuses `400 BAD_USER_INPUT` and never deletes; REST `PUT` with `sha: ""` on both existing and nonexistent paths refuses `400 BAD_USER_INPUT` and never creates.
