# A transaction whose only posting has no amount reads as an error (`BOOK` "interpolation failed: cannot infer currency") on every surface, though stock `bean-check` 3.2.3 accepts it and drops the empty posting

**Minor · ledger (engine adapter, `src/foundation/rustledger/engine.ts`, `book-errors.ts`) · 30–45m · A1.** The hosted check flags a file that `bean-check` and `bea check` pass. Stock Beancount's interpolation fills an elided posting from the transaction's residual. When the elided posting is the only one, there is no residual, so stock drops the posting and reports nothing: the loaded entry has no postings, and `bean-query` returns no row for it. rustledger 0.24.0 reports the error `BOOK` "interpolation failed: cannot infer currency for posting to account Assets:Cash (2026-09-07, "…")", plus a hidden warning `E3004` "Transaction has only one posting". So `checkLedger`, the `errors` resource, REST `GET …/errors` and every write preview's `valid` call the ledger red. The `close-month` prompt tells an agent that "a ledger that starts red must be fixed before a close means anything; surface the errors and stop", so a close can stall on an error `bean-check` does not report. A one-posting stub is easy to produce: a half-typed entry, or an import row whose counter posting was dropped.

This is the reverse of w31/120 and w31/121, which made the engine refuse what stock refuses. Here the engine refuses what stock accepts.

No code at HEAD treats this case.

## Repro (synthetic, any ledger the key can write)

Fixture, appended to a ledger that opens `Assets:Cash USD`:

```beancount
2026-09-07 * "qa" "single elided posting"
  Assets:Cash
```

1. `appendLedgerText {text: <fixture>, dry_run: true}` returns `validation.valid: false`, with `newErrors: [{code: "BOOK", message: "interpolation failed: cannot infer currency for posting to account Assets:Cash (2026-09-07, \"single elided posting\")", source: "main.bean:89"}]`. `addLedgerEntries` with one posting `{account: "Assets:Cash"}` (the schema allows one posting to omit its amount) previews the same.
2. Commit it with `allowInvalid: true`. `checkLedger`, `beancount://{owner}/{name}/errors` and REST `GET /api-gateway/v1/ledgers/{owner}/{name}/errors` then each list that one `BOOK` error with `severity: "error"` at `main.bean:89`.
3. Download the same file and run stock `bean-check` 3.2.3 on it: no output, exit 0. The Python loader keeps the entry with zero postings. `bean-query "SELECT date, account, position WHERE payee = 'qa'"` returns no rows. Hosted `runBqlQueryStructured` returns no rows too, so the reports agree and only the check differs.

## Controls

| Fixture | Hosted | `bean-check` 3.2.3 |
| --- | --- | --- |
| Elided `Assets:Cash` alone | `BOOK` error | clean (posting dropped) |
| Elided `Assets:Cash` plus `Expenses:Food:Coffee 0 USD` | clean | clean (elided posting dropped) |
| Elided `Assets:Bank:Checking` after two postings that already balance | clean | clean |
| A transaction with no postings | clean | clean |
| Two elided postings | `E3002` and `BOOK` | "You may not have more than one auto-posting per currency" |

Only the lone elided posting differs in kind. (The two-elided row reports two errors where stock reports one; that count difference is out of scope here.)

## Fix

In the ledger engine adapter, where the `BOOK` errors are collected (`engine.ts`, near `:1189`) and attached to their transactions (`book-errors.ts`), treat this case as stock does. When every posting of a transaction lacks units and there is no residual to interpolate from, drop the `BOOK` error and leave those postings out of the booked entry. That is the case for a transaction whose only posting is elided. The hidden `E3004` warning can stay. Any other `BOOK` error is unchanged, the two-elided case included. Every surface reads the shared snapshot, so `checkLedger`, the `errors` resource, REST and GraphQL error lists, and every write preview's `valid` change together, with no API shape change. Add the case to `verify:rustledger`, so the adapter rule can go once the engine matches stock.

**Resolved 2026-11-27** — A transaction whose only posting has no amount, cost or price now checks clean and is booked with no postings, as stock `bean-check` 3.2.3 loads it. `loneElidedTransactions` (`book-errors.ts`) pairs the engine's `BOOK` "interpolation failed: cannot infer currency for posting to account …" with its transaction by date, narration and account, only when they are as many. `engine.ts` then drops that error and books the entry with `postings: []` before plugins run, so `checkLedger`, the `errors` resource, REST and GraphQL error lists and every write preview's `valid` change together, with no API shape change. The entry keeps the ID its source text hashes to (source IDs are seeded first), so the journal still opens it. The hidden `E3004` warning stays. The controls behave as stock: two elided postings (`E3002` and `BOOK`) and a lone posting with a price or a cost are still errors, and an elided posting beside `0 USD` stays clean. One difference is left: a lone elided posting to an account that was never opened keeps the engine's `E1001`, where stock drops the posting and reports nothing. BQL is unchanged: the transaction is still left out of the query source, so `SELECT` returns no row as `bean-query` does. A `PRINT` still omits it, where stock prints it with no postings. The ledger `README.md` documents the rule.

- **Tests:** `book-errors.test.ts` covers the pairing: a narrationless entry, an escaped quote, two elided postings, a price, a cost, another account, and twins whose counts differ. `engine-lone-elided-posting.test.ts` checks, through the snapshot, that the entry is clean with no postings and not unbooked, that its source ID is the hash of the written entry, and that the two-elided control stays red and unbooked. With the `engine.ts` change reverted, the two lone-posting cases fail. `yarn verify:rustledger` runs the note's fixtures through the real engine. It checks that the raw engine still reports `BOOK`, so the rule is still needed and can go once the engine matches stock. It also checks that the snapshot is clean with no postings, that the journal's entry hash opens the written text, that BQL returns no row, and the four controls. With the fix reverted it fails.
