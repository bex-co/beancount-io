# `addLedgerEntries` (`POST /v1/ledgers/{owner}/{name}/entries`, GraphQL `bulkEntries`) accepts empty `entries: []`, runs upstream ledger checks, caches `requestId`, and returns `200 OK` (`Added 0 entries successfully`) instead of `BAD_USER_INPUT`

**Minor · backend-v2 + ledger (bulk entry write validation) · 25–35m · A1.** Passing `entries: []` to structured entry creation succeeds with `200 OK` on MCP, REST, and GraphQL — on both `dry_run: true` and `dry_run: false` — fetching `bcio` options, calling the ledger service (which loads the ledger to count errors), caching `requestId` in Redis for 24 hours on a 0-entry no-op commit, running post-write `checkLedger` on MCP, and returning `Added 0 entries successfully`, instead of refusing with `BAD_USER_INPUT` as its own contract (`"One or more directives to add to the ledger"`) and every sibling batch write operation do (direct twin of `w31/042` for `deleteEntrySources`). Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, checked against HEAD `686cdff7b`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval` (restored byte-for-byte after run: `main.bean` sha256 `77c3a591efd311e0`, 0 bean-check errors).

## Working controls

- Direct sibling `deleteEntrySources` (`w31/042`) and `moveEntrySources` both refuse `entries: []` with `BAD_USER_INPUT` (`entries must name at least one entry`).
- Every other batch write refuses an empty batch with `BAD_USER_INPUT`: `createLedgerFiles`, `updateLedgerFiles`, `deleteLedgerFiles` (`files: Too small: expected array to have >=1 items`), `createPullRequest` (`changes must not be empty`), `importStagedBankTransactions`, `discardStagedBankTransactions`, and `appendLedgerText` (empty text -> `BAD_USER_INPUT`).
- `entriesBodySchema` (`entries-handler.ts:283,373`) and GraphQL `bulkEntries` (`ledger-entry-resolver.mutation.ts:588`) already document `"One or more directives to add to the ledger"` / `"Add one or more entries to a specific ledger (atomic)"`.

## Root cause

Not deployment lag — present at HEAD `686cdff7b`:

- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/entries-handler.ts:256-263`: `entriesBodySchema` defines `entries: z.array(entrySchema).max(MAX_BULK_ENTRIES, ...)` with no `.min(1)`.
- `backend-cluster/backend-v2/src/features/ledger/service/ledger-entry-service.ts:474-517` (`LedgerEntryService.addBulkEntries`): validates only `assertBulkEntriesSize(inputs, "added")` (upper cap `> 1000` in `bulk-entries-cap.ts:17`), never `inputs.length === 0`. After authorization, `runIdempotentEntryWrite` claims and caches any `requestId` for 24 hours (`committed: (result) => result.success` returns `true`), `writeBulkEntries` calls `getLedgerBcioOptions` and `favaApiClient.entries.addBulkEntries` with `entries: []`, and on MCP `dry_run: false` `withPostWriteValidation` calls `getLedgerErrors` again.
- `backend-cluster/ledger/src/api/entries.ts:232,493-503` (`POST /entries/:owner/:repo_name/bulk`): accepts `entries: []` and runs `data.getErrors(...)` over the ledger to return a 0-entry success response.

## Fix

In `backend-cluster/backend-v2` and `backend-cluster/ledger`:

1. In `backend-cluster/backend-v2/src/features/ledger/service/ledger-entry-service.ts:493` (`LedgerEntryService.addBulkEntries`), guard `if (inputs.length === 0)` throwing `new BadUserInputError("entries must contain at least one entry", "entries")` right after authorization and before `assertBulkEntriesSize` / `runIdempotentEntryWrite` (matching `w31/042`'s placement in `deleteMultiSourceSlices`), so MCP `addLedgerEntries`, REST `POST .../entries`, GraphQL `bulkEntries`, and legacy GraphQL `addEntries` (`legacy-entry-workflow.ts:70`) all refuse identically without touching Redis or calling the ledger service.
2. In `backend-cluster/ledger/src/api/entries.ts:232` (`POST /entries/:owner/:repo_name/bulk`), guard `if (rows.length === 0)` throwing `new BadUserInputError("entries must contain at least one entry", "entries")` before contacting Gitea or loading ledger errors (and verify whether `LedgerEntryService.addBulkEntries` in `backend-cluster/ledger/src/features/ledger/service/ledger-entry-service.ts:164` should also reject `inputs.length === 0 && attachments.length === 0`).
3. If `.min(1)` is also added to `entriesBodySchema` (`entries-handler.ts:256`), regenerate `docs/openapi/v1.json` and re-pin `cli/openapi/v1.json` (`make spec-sync && make codegen` in `cli/`) in the same change.
4. Add unit tests in `backend-v2` and `ledger` plus 3-surface adapter parity tests in `structured-entry-parity.test.ts` covering `entries: []` for both `dryRun: true` and `dryRun: false` across MCP `addLedgerEntries`, REST `POST .../entries`, and GraphQL `bulkEntries` (and asserting `requestId` is not cached and upstream ledger calls are not made).
