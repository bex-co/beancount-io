# A write that adds `include "accounts.txt"` (any non-`.bean` file) is refused "Included file not found", though the file exists, bean-check accepts it, and the committed ledger loads it

**Minor · ledger (write-gate projection) · 30–45m · A1.** The preview and the commit gate both report a bean-check error that does not exist, so splitting a ledger into `.txt`, `.ldg` or extensionless files cannot be done without `allow_invalid`. That flag then commits a ledger that loads clean. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-15, against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, `revision: unknown`, see `w31/002`). The credential was an unpinned read/write/admin `bcio_` key on the QA account, and writes went only to the QA ledger `<qa-owner>/mcp-agent-eval`. The probe files were deleted and `main.bean` was restored byte for byte afterwards (blob `f1a0b83c`), and the check is clean.

## Repro (live)

The run's folder was `qa-20261115-r9`, and this note shortens it to `qa`.

1. `createLedgerFiles` with `qa/list.txt` = `include "y.bean"` and `qa/y.bean` = one balanced transaction. The commit lands, `valid: true`.
2. `updateLedgerFiles` with `dry_run: true`, appending `include "qa/list.txt"` to `main.bean`. It answers `valid: false` with `newErrors` `Included file not found: qa/list.txt` (`main.bean:135`, code `LOAD`). REST `PUT …/files/main.bean` with `dryRun: true` answers the same. `include "./qa/list.txt"` behaves the same way. Without `dry_run`, the commit is refused `VALIDATION_FAILED` with the same message.
3. The same happens with `qa/extra.ldg`, a file that holds one transaction. `include "qa/extra.ldg"` gives "Included file not found", and the glob `include "qa/*.ldg"` gives `include pattern "qa/*.ldg" does not match any files`, on both MCP and REST.
4. **Control:** `include "qa/y.bean"` previews `valid: true`.
5. **The committed ledger is fine.** Step 2 committed with `allow_invalid: true` reports `errorsAfter: 0` and "No new bean-check errors". After it, `checkLedger` returns `[]`, `listLedgerEntries` finds the transaction from `y.bean`, and `getLedgerContext` lists `main.bean`, `qa/list.txt` and `qa/y.bean` as source files. Once the file is included, an unrelated edit previews `valid: true`.
6. Stock Beancount 3.2.3 `bean-check` passes the same files for both the plain and the glob include, and `bean-query` reads both transactions.

GraphQL file writes have no gate (`w1/blocked/210`), so only MCP and REST show this.

## Cause

- The committed load fetches every `.bean`/`.beancount` file. It then walks the `include` lines and fetches the non-`.bean` files they reach, transitively and through globs (`backend-cluster/ledger/src/foundation/rustledger/file-map-loader.ts:566-625`).
- The write gate's projection is `projectFileMap` (`backend-cluster/ledger/src/features/ledger/service/ledger-data-service.ts:544`). It starts from that cached committed map (`:567-575`) and applies the overlays, but it never walks the includes the overlays add.
- So a non-`.bean` file the committed ledger did not reach is in the repository (`repoPaths`) but not in the projected map, and the engine reports it missing. `repoPaths` reaches `parseLedgerFiles` only for document reconciliation.
- The managed-price include had the same gap, and it was fixed in the same function (`w1/221`, `8017e066c`).
- Every projection reader inherits the gap: `checkProjectedErrors` (the preview rule and the commit gate of every file and entry write), `projectedEntryIds` and `projectedSourceFiles`.

## Fix

After the overlays are applied, run the loader's include walk over the projected map. From the same ref, fetch every repository blob the walk reaches that the map lacks, and keep a path an overlay deleted deleted. Share the walk with `file-map-loader.ts` rather than restating it, and keep its byte and file caps. The projection is shared, so MCP and REST change together.

**Done when:**

- The previews in repro steps 2 and 3 answer `valid: true`, and their commits land without `allow_invalid`.
- An include of a non-`.bean` path that does not exist still reports `Included file not found`, and a glob that matches no file still says so.
- A projection test that adds an include of an existing, unreached `.txt` file, and a glob over `.ldg` files, fails with the fix reverted.

Dedupe: searched `.pm/**`, done and blocked included, for "Included file not found", "non-`.bean`", `accounts.txt`, `projectFileMap` and "extensionless". `w21/189` and `w21/772` cover the message for a file that is really missing. `w21/771` is mobile's file browser. `w23/035` is `appendLedgerText` writing to a file outside the include closure. `w1/221` is the managed-price precedent. None of them reports this.

---

**Resolved 2026-11-15** — A write that adds an include of a committed file the load never reached (`include "qa/list.txt"`, `include "qa/extra.ldg"`, the glob `include "qa/*.ldg"`) now previews `valid: true`, and its commit lands without `allow_invalid`. Shipped in the commit carrying this note (`backend-cluster/ledger`).

- **Where the gate lives.** In this repository, not upstream. `@rustledger/wasm` has no filesystem and resolves includes only against the FileMap the service hands it. The write gate's projection (`projectFileMap`, `ledger-data-service.ts`) built that map from the committed load and the overlays, and never fetched the files the overlays' new includes reach.
- **What changed.**
  - `file-map-loader.ts` now holds the include walk once. `fetchReachedIncludes` does the transitive and glob walk. `RepoFileReader` reads blobs under the loader's per-file, byte and file-count caps. `fetchBeanFileMap` and the new `fetchProjectedIncludes` both use them.
  - After the overlays are applied, the projection runs the walk from the files the write changed. It reads each repository file they reach that the map lacks, at the commit the load read (`ref`, now on `LoadedLedger`). A path the write deletes stays deleted. Committed files were walked already by the load, so they are not scanned again.
  - Every projection reader gets the fix together: `checkProjectedErrors` (the preview and the commit gate), `projectedEntryIds` and `projectedSourceFiles`. MCP and REST call the same endpoint, so they change together. GraphQL file writes still have no gate (`w1/blocked/210`).
- **Unchanged.** An include of a file the repository lacks still reports `Included file not found`. So does an include of a file the same write deletes. A glob that matches nothing still reports `include pattern "…" does not match any files`.
- **Evidence.**
  - Live repro first, on `https://beancount.io` against the QA ledger. Three probe files were committed, the three previews answered "Included file not found" or "does not match any files", and the `.bean` control previewed clean. The probe files were then deleted. `main.bean` is unchanged (blob `f1a0b83c`), and `checkLedger` is clean.
  - Six new cases in `check-projected-errors.test.ts` cover a `.txt` read at the load's commit, a glob over `.ldg`, a transitive include, a missing target, a deleted target and `projectedSourceFiles`. With the fix reverted, 4 of them fail. The deleted-target case fails when the exclusion is dropped.
  - `yarn verify:rustledger` (`scripts/projected-includes.ts`) drives the real projection and engine. It checks that the four includes preview clean and load their files, and that a missing file, a deleted file and an unmatched glob keep their errors. With the fix reverted, it stops on `Included file not found: qa/list.txt`.
- **For `w31/023`.** backend-v2 cannot import ledger code, so no shared helper crosses into it. Its includer scan can instead use the ledger's include closure. Committed, that is `getSourceFiles`, which already lists non-`.bean` includers such as `qa/list.txt`. Projected, it is `POST /reports/{o}/{r}/source-files`, which now also lists the non-`.bean` files a write's new includes reach.
- **Gates.** Run in `node:22-bookworm-slim` (v22.23.4): `yarn typecheck`, `yarn lint` (ESLint and Knip), Prettier on the changed files, `yarn test` (221 suites, 3440 tests, all passing), `yarn verify:rustledger` and `yarn build`.
