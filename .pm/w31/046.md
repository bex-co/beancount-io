# Entry-source writes (`updateEntrySource`, `deleteEntrySource`, `deleteEntrySources`, `moveEntrySources`) skip `assertEntryHashFormat`, loading the full ledger and answering `NOT_FOUND` instead of `BAD_USER_INPUT` on MCP, REST, and GraphQL

**Minor · backend-v2 (entry-source hash validation) · 30–45m · A1.** Passing an empty (`""`), blank (`"   "`), or malformed (`"not-a-hash"`) `entryHash` / `entry_hash` to any of the four entry-source write operations bypasses input validation, sends the value upstream to the ledger service (which loads the full repository from Gitea and parses it with rustledger), and fails with `NOT_FOUND` instead of `BAD_USER_INPUT` — and for `""`, drops the entry-specific hint and falls back to the generic `Ledger resource` hint. Direct sibling `getEntryContext` validates `entryHash` with `assertEntryHashFormat` before calling the ledger service. Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 SHIP=1`) on 2026-11-23 against `https://beancount.io` (`beancount-mcp 1.0.0`, protocol `2025-11-25`, checked against HEAD `8714e21cb`). Credential: unpinned read/write/admin `bcio_` key on the QA account. Synthetic ledger: `<qa-owner>/mcp-agent-eval` (restored byte-for-byte after run: `main.bean` sha256 `77c3a591efd311e0`, 0 bean-check errors).

   - `POST .../entry-source/delete-many` and `POST .../entries/move` (`toPath: "main.bean"`) with `entryHash: ""` → identical HTTP `404` `NOT_FOUND` (`"Entry not found"`).

Expected: refused immediately with `BAD_USER_INPUT` (`entryHash must be an entry_hash from list output: 32 lowercase hex digits, with a :<n> suffix on a repeated entry`) on MCP, REST, and GraphQL without loading the ledger from Gitea or calling the ledger service.

## Working controls

- `getEntryContext` (MCP tool), `beancount://{owner}/{name}/entry-context/{entryHash}` (MCP resource), REST `GET /api-gateway/v1/ledgers/{owner}/{name}/entry-context`, and GraphQL `getLedgerEntryContext` all call `assertEntryHashFormat(entryHash)` at `backend-cluster/backend-v2/src/features/ledger/service/ledger-journal-service.ts:364` and refuse `""`, `"   "`, and `"not-a-hash"` with `BAD_USER_INPUT` before calling the ledger service.
- A valid 32-hex hash of a non-existent or edited entry still reaches the ledger service and answers `NOT_FOUND` with the entry-specific hint.

## Root cause

Not deployment lag — present at HEAD `8714e21cb`:

- `backend-cluster/backend-v2/src/features/ledger/utils/entry-hash-alias.ts:38-52` defines `assertEntryHashFormat(entryHash)` (added in `8a2e14649`), enforcing `/^[0-9a-f]{32}(?::[1-9][0-9]*)?$/`.
- `backend-cluster/backend-v2/src/features/ledger/service/ledger-journal-service.ts` calls `assertEntryHashFormat` only in `getContext` (`:364`). All four write methods omit it:
  - `deleteSourceSlice` (`:477-514`)
  - `deleteMultiSourceSlices` (`:516-563`)
  - `moveSourceSlices` (`:565-617`)
  - `updateSourceSlice` (`:619-695`)
- `resolveEntryHash` (`entry-hash-alias.ts:10-31`) only checks `undefined` and camel/snake disagreement, so empty/blank/malformed strings pass straight to `favaApiClient.journal.*`, triggering a full ledger load/parse and returning `NOT_FOUND`. For `""`, the empty ID triggers the generic `NotFoundError("Ledger resource")` branch, losing the entry-specific hint.

## Fix

In `backend-cluster/backend-v2`:

1. Call `assertEntryHashFormat(entryHash)` in `LedgerJournalService.deleteSourceSlice` (`ledger-journal-service.ts:487`) and `LedgerJournalService.updateSourceSlice` (`:639`), and validate every entry's `entryHash` with `assertEntryHashFormat` in `LedgerJournalService.deleteMultiSourceSlices` (`:538`, after `entries.length === 0` and `assertBulkEntriesSize`) and `LedgerJournalService.moveSourceSlices` (`:588`, after `assertBulkEntriesSize` — and keep empty-array check first if applicable), before invoking `favaApiClient`.
2. Update any existing unit or parity tests that pass short placeholder hashes (e.g. `"abc"`, `"h1"`) as valid fixtures to use 32 lowercase hex digits (e.g. `"a".repeat(32)`).
3. Add unit tests in `ledger-journal-service.test.ts` and 3-surface adapter tests in `source-slice-parity.test.ts` covering `""`, `"   "`, and `"not-a-hash"` on all four operations across MCP, REST, and GraphQL, asserting `BAD_USER_INPUT` and zero upstream ledger-service calls.
