# The 28-digit amount check misses three written forms: a posting amount with no currency, an amount written flush against its currency (`1.00USD`), and a `custom` value under an unpadded date; each commits and reads back rounded, on MCP, REST and GraphQL (gap in w31/095)

**Minor · backend-v2 (`src/features/ledger/utils/engine-decimal.ts`) · 30–45m · A1.** The hosted engine holds 28 significant digits. A literal past that is read back rounded while bean-check stays clean. So every raw-text write refuses one with `BAD_USER_INPUT` "amount … has more than 28 significant digits; the engine would read it back rounded" (w23/081, w31/095). The writes that check are `appendLedgerText`, `createLedgerFiles`, `updateLedgerFiles` and `updateEntrySource`, plus REST `POST …/directives/text`, `PUT …/files/{path}` and `PUT …/entry-source` and their GraphQL twins. Three valid ways of writing an amount get past the scanner. Each one commits with `valid: true` and is stored rounded:

1. **A posting amount with no currency.** Beancount infers the currency, so `Assets:Cash  -1.0000000000000000000000000000001` is legal. The amount scanner only counts a number as an amount when a currency, a `~`, a cost brace or a metadata key surrounds it, and a bare posting number has none of these.
2. **An amount written flush against its currency.** Beancount's lexer reads `1.0000000000000000000000000000001USD` as a number and then a currency (stock 3.2.3 loads `price EUR 1.0…01USD` as `1.0000000000000000000000000000001 USD`). In `tokenizeCode`, a digit run followed by a letter becomes one word (`engine-decimal.ts:176`), so no number is seen. This bypasses the check on postings, `price` directives and amount-valued metadata.
3. **A `custom` value under an unpadded date.** A bare number in a `custom` directive counts as an amount only when the line starts with `CUSTOM_DIRECTIVE_START` (`:33`), and that pattern wants a two-digit month and day (`\d{4}[-/]\d{2}[-/]\d{2}`). Stock's lexer, and the ledger service since w31/106 and w31/107, also read `2026-9-1` and `2026/9/1` as dates. `2026-09-01 custom "x" 1.0…01` is refused, and `2026-9-1 custom "x" 1.0…01` commits. Stock keeps `Decimal('1.0000000000000000000000000000001')`, and the hosted engine reads `1.0000000000000000000000000000`.

Found by `/loopx w31` routine `mcp-qa` (`/qa-find-bugs-mcp w31 LAND=1`) on 2026-11-26.

The refusal is the hosted rule, though, and it already refuses the same posting when the currency follows it. The `price`, metadata and `custom` values are kept exactly by stock.

## Cause

`lineAmountLiterals` (`engine-decimal.ts:237-283`) decides which numbers are amounts from their neighbours (`isAmountContext`, `:265`):

- A posting's units are the expression right after its account. Nothing in `isAmountContext` treats that position as an amount. The only position after an account that counts is inside braces (`seenAccountOutsideBraces`).
- `tokenizeCode` (`:176`) turns `1.00USD` into one `word` token, because a digit run followed by `[A-Za-z_.]` is taken to be a word such as `2026abc`.
- `DATE_TOKEN` (`:20`) and `CUSTOM_DIRECTIVE_START` (`:33`) want `\d{2}` months and days.

## Fix

In `engine-decimal.ts`:

1. Count the first expression after an account outside braces, on an indented line, as an amount, with or without a currency after it. That covers posting units like `Assets:Cash -BIG`, `Assets:Cash -BIG {…}` and `Assets:Cash -BIG @ …`.
2. When a digit run is followed directly by an uppercase letter, emit the number and let the rest be tokenized as the currency word, as Beancount's lexer does. Keep the word reading for a lowercase letter, `_` or `.`.
3. Accept the date the lexer reads, `\d{4}[-/]\d{1,2}[-/]\d{1,2}`, in `DATE_TOKEN` and `CUSTOM_DIRECTIVE_START`. That is the ledger service's `SOURCE_DATE` from w31/106. The packages share no code, so restate it here.

The one function serves every caller, so MCP, REST and GraphQL change together and no response shape changes:

- `directive-append-workflow.ts:114`
- `edit-ledger-files-tool.ts:366,442`
- `ledger-journal-service.ts:700`
- `ledger-workflow.ts:575`
- `files-handler.ts:245`

- The three bypass texts above are refused `BAD_USER_INPUT` "amount … has more than 28 significant digits" on `appendLedgerText`, `updateLedgerFiles` and `updateEntrySource`, on MCP, REST and GraphQL, in preview and commit alike.

  - an account component with digits, such as `Assets:Bank2`;

  - a number inside a string or after `;`.
