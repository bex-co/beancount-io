# `updateLedgerFiles` `old_string`/`new_string` edits cite post-write lines in preview and refusal when the edit changes the line count

**Minor · ledger + backend-v2 (write error lines) · 30–45m · A1.** Last open sibling of `w31/101` (entry delete) and `w31/116` (`appendLedgerText`, `updateEntrySource`, `moveEntrySources`, routed `addLedgerEntries`). Those fixes map a write's new errors back to the lines of the file as it stands now. `updateLedgerFiles` with `old_string`/`new_string` edits still reports the line numbers of the file after the edit. Whenever a replacement adds or removes lines, an error below it then points at the wrong current line, in the `dry_run` preview and in the commit refusal alike. Flagged as not done in `w31/116`'s resolution (`done/116.md`).

- Expected repro (not yet run; the worker confirms it first): on a scratch ledger, replace a one-line `old_string` with a three-line `new_string` above an entry that the edit makes fail. Preview and refusal should cite that entry's line + 2, while its line in the current file is 2 lower.
- Fix where `w31/116` did: map edit spans through the same line mapping before error lines are reported, on MCP, REST and GraphQL alike.
- Done when: preview and refusal name the current line for an edit that grows, shrinks or keeps the line count. A parity test covers all three surfaces, and a `yarn verify:rustledger` live check sits next to `scripts/edit-error-lines.ts`. The live repro on `beancount.io` waits for both services to deploy.
