# Hosted BQL `getprice()` and `convert()` of a plain amount chain prices through a third currency: `getprice('VTI', 'EUR')` reads `104.16666666666666666666666666` and `convert(units(sum(position)), 'EUR')` reads `1145.8333333333333333333333333 EUR`, where stock `bean-query` and `bea query` answer NULL and `11 VTI`

**Minor · ledger (BQL results of the pinned `@rustledger/wasm` 0.24.0, served by `src/features/ledger/service/ledger-shell-service.ts`) · 45–60m, cause in the engine · A1.** Stock beanquery 0.2.0 reads a price only from the pair itself or its inverse. `getprice(base, quote)` calls `prices.get_price(price_map, (base, quote), date)` (`beanquery/query_env.py:520`), and `convert(<amount>, currency)` calls `convert.convert_amount` with no `via` currencies (`query_env.py:480`). Beancount derives a rate through another currency only when given `via` (`beancount/core/convert.py:190`–`224`). The one stock function that passes `via` is `convert(<position>, …)`, through the position's own cost currency. The hosted engine also routes `getprice` and the conversion of a plain amount through a third currency. A ledger that quotes VTI in USD and EUR in USD therefore gets a VTI price in EUR that it never recorded, and `runBqlQuery` disagrees with `bea query` on the same file. An agent that cross-checks a figure locally, or compares it with a value it computed in Python, gets two different answers. The ledger README's BQL section, and the other BQL reconciliations under `src/features/ledger/service/bql-*.ts`, do not mention this.

## Repro (synthetic, any ledger the key can write)

A ledger with `option "operating_currency" "USD"` that holds 11 VTI at cost in USD, with these two prices and no others:

```beancount
2026-08-15 price VTI 125.00 USD
2026-08-20 price EUR 1.20 USD
```

| Query | hosted (`runBqlQuery`) | `bean-query` / `bea query` |
| --- | --- | --- |
| `SELECT getprice('VTI', 'EUR') AS p, getprice('EUR', 'VTI') AS q LIMIT 1` | `104.16666666666666666666666666`, `0.00960` | NULL, NULL |
| `SELECT account, convert(units(sum(position)), 'EUR') AS e WHERE account ~ 'Broker' GROUP BY account` | `1145.8333333333333333333333333 EUR` | `11 VTI` |
| `SELECT convert(units(position), 'EUR', 2026-08-25) AS e WHERE account ~ 'Broker'` | `1041.6666666666666666666666666 EUR`, … | `10 VTI`, … |

Controls that agree on both: `convert(position, 'EUR')` for a lot at cost converts through its cost currency (`1041.67 EUR`). `getprice('USD', 'EUR')` is the recorded pair's inverse, `0.8333333333333333333333333333`. `getprice('EUR', 'EUR')` is `1`. `getprice('GBP', 'EUR')` with no GBP price is NULL. The hosted reports are not affected: the balance sheet, holdings and the statements value from the ledger's own price map (`docs/mcp.md`, "Prices come from the ledger's `price` directives alone").

## Root cause

The pinned engine's BQL price lookup falls back to a path through another currency for `getprice` and for converting an `Amount`. The ledger service passes those cells through unchanged (`ledger-shell-mappers.ts`). Nothing in `src/` touches `getprice` or `convert` except the mixed-currency comparison guard (`mixed-comparison-guard.ts:134`). The engine's price code ships only as WebAssembly, so the exact chaining rule is unverified: which currencies it routes through, and whether it chains more than one step.

## Fix

Target behavior: on MCP `runBqlQuery`/`runBqlQueryStructured`, REST `query` and GraphQL `queryShell`, `getprice(base, quote[, date])` answers NULL, and `convert(<amount>, currency[, date])` leaves the amount in its own currency, whenever the ledger has neither the pair nor its inverse by that date, as beanquery 0.2.0 does. `convert(<position>, …)` keeps converting through the position's cost currency. Find out whether `@rustledger/wasm` offers stock lookup (a newer release or an option), and adopt it if so. If it does not, and the service cannot correct the cells after the fact, block this note on that engine change. In that case, list the difference with this example in the ledger README's BQL section and in the `runBqlQuery` description, so an agent knows hosted `convert` and `getprice` can chain prices.

## Done when

- The three repro queries return NULL, NULL, `11 VTI` and the units rows on MCP. A REST `query` parity test asserts the same.
- A ledger test (unit, or `verify:rustledger` when the engine is the fix) pins the `getprice` and `convert(units(…))` results for a two-hop fixture, and the controls above still hold. With the change reverted, the test fails.
- Otherwise the note is blocked, the README states the difference, and the block names the engine change.
