# Keep loaded commit details through cache refresh

**Severity:** minor. **Estimate:** 45–60 minutes. **Owner:** dashboard. **A2:** a reader reviewing an already-loaded commit should keep its diff and expanded file list when refreshing, including when the new read fails.

## Reproduction and controls

Production `https://beancount.io`, owned isolated headless Chromium156.0.8078.47, authenticated QA owner, designated disposable synthetic ledger, English/light/UTC. Desktop1440×1000 and an independent fresh390×844 reader reproduce. The selected immutable commit **46df57e2d38ecf88148e30418a128dead3897387** creates one91-byte QA text file. That file has already been deleted; its historical diff correctly remains readable.

1. Open the loaded Commit Details, expand **Files Changed**, and activate that file's link. The exact filename, two added lines, encoded fragment and native target are correct. Keep the selected SHA unchanged.
2. Let a genuine later ledger commit expose **Out of date — click to refresh**, then activate it. Hold only this selected commit's `GetCommitDetails` before transport.
3. The connected file list is removed, the diff target count becomes0, and four skeletons replace the loaded details. Abort the read. Only connection guidance and Try Again remain; the previously readable diff/file list stay absent.
4. Retry, hold and abort again. The action is replaced by the skeleton during the attempt. Manually focus the new Try Again and retry with healthy transport: a genuine HTTP200 returns the same SHA, filename and two added lines. The diff returns, but **Files Changed is now collapsed**.

The desktop reader uses an actual out-of-date notice retained through native SPA navigation after an earlier owned file create/delete. The fresh narrow reader first loads the healthy commit with no notice; creating/deleting a separate35-byte QA trigger file then lets its genuine30-second latest-commit poll expose the notice. Both trigger files are removed before final verification. There are no substituted responses or synthetic out-of-date values.

A third control reuses the desktop reader, expands Files Changed, and holds then **continues** a real healthy refresh to HTTP200. The old file list/diff are still removed while pending; success recreates the same content with the disclosure collapsed. An outage is not needed to lose that view state. The narrow error screenshot was visually inspected.

Seven observed detail reads comprise four pre-transport aborts and three genuine successes. All use the same ledger/SHA. Zero reader mutations or page exceptions. The four setup writes are the two small owned file create/delete pairs; exact original file bytes and zero ledger errors are verified afterward. The fresh narrow reader, both fixture contexts and an additional source-observation context close; the original owned root remains. All gates and this probe's handlers are removed.

Retry focus is supporting context, not another finding: its old button disconnects and focus reaches BODY, but the next Tab immediately reaches the new Try Again. Repeated/unfocused Enter adds no duplicate request, and ordinary manual retry succeeds. No permanent trap or unhandled rejection is claimed.

## Cause and bounded repair

`dashboard/src/features/git/commits/components/commit-detail.tsx:62–72` owns this query. At:109 it renders loading skeletons unconditionally; at:124 it renders metadata, CommitFileList and DiffViewer only under `!loading && !error && commit`. Thus revalidation unmounts the shown reader and its native disclosure, and a refresh error suppresses all prior content. `CommitFileList` creates a closed-by-default native details element at `commit-file-list.tsx:22`. The bare refetch action at:100 repeats that replacement lifecycle.

The actual header action calls `useApolloCacheClear`; that hook evicts ROOT_QUERY, causing observed query revalidation. The selected scope never changes: the parent already keys CommitDetail by ledger and SHA at `commits-split-view.tsx:236`. This is an inner reader branch, not the layout unmount repaired by246 or a new-commit transition.

Retain the last successful details for the same ledger/SHA and keep their mounted file list/diff through refresh and failure. Show truthful refreshing/failure feedback alongside them, with an in-place single-flight retry using the existing query-retry pattern. Preserve disclosure/scroll/fragment state and useful focus without resurrecting an abandoned reader. Cold reads may still show loading/terminal errors; selecting another commit must continue to withhold the previous SHA's diff. Keep missing/denied classifications, the large-diff gate, history paging/drawer behavior and encoded filename targets. No API, dependency or global cache-policy change is needed.

Acceptance: real CommitDetail/Apollo interactions load a known commit, expand its list, then refresh through pending → failure → failed retry → success and through pending → healthy success. The same reader nodes and disclosure state remain, with the selected SHA and content unchanged; retry requests only that query and ignores repeat activation. Cover scope departure, cold errors and the large-diff gate as compatibility, then repeat both widths and run dashboard gates.
