# `pushtag` and `poptag` are the only Beancount directives the editor doesn't highlight

**Severity:** trivial — cosmetic highlighting only. **Estimate:** 10 minutes including the test. Owner: mobile. A2: the in-app editor is where a newcomer reads their own ledger, and two standard directives render as plain text beside their highlighted siblings, which reads as "the app doesn't know what this is".

Environment: branch `main`, HEAD `038faeeb`. Verified by running the production tokenizer; no device interaction.

## The defect

`src/components/code-editor/beancount-language.ts:56-57` lists the directives to highlight:

```ts
const DIRECTIVE_PATTERN =
  /^(txn|balance|open|close|pad|note|price|document|custom|option|include|plugin|pushmeta|popmeta|event|query|commodity)\b/;
```

`pushmeta` and `popmeta` are there. **`pushtag` and `poptag` are not** — and they are the only Beancount directives missing from the list. Neither appears anywhere in `mobile/src/`.

Driving the production `tokenizeBeancount` over a line stream (the same harness the existing tests use), reporting the first non-null token:

| line | first token |
| --- | --- |
| `pushtag #travel` | **`tagName`** — the `#travel`, because `pushtag` produced nothing |
| `poptag #travel` | **`tagName`** |
| `pushmeta k: 1` | `keyword` ✔ |
| `popmeta k:` | `keyword` ✔ |
| `option "title" "x"` | `keyword` ✔ |
| `open Assets:Cash` | `keyword` ✔ |

So the directive word itself falls through every rule — it starts lowercase, so neither `ACCOUNT_PATTERN` (uppercase/`\p{Lo}`/digit start) nor `CURRENCY_PATTERN` (`\p{Lu}` start) claims it — and is consumed character by character as plain text. The tag on the same line is still coloured, which makes the unstyled directive beside it more conspicuous, not less.

`pushtag`/`poptag` are the standard way to tag a block of transactions (a trip, a project), so this is ordinary ledger content rather than an exotic corner.

## Fix

Add both to the alternation:

```ts
/^(txn|balance|open|close|pad|note|price|document|custom|option|include|plugin|pushtag|poptag|pushmeta|popmeta|event|query|commodity)\b/
```

Order within the alternation does not matter here — every entry is a distinct whole word terminated by `\b`, and no entry is a prefix of another (`pushtag` vs `pushmeta` diverge at the fifth character).

**Acceptance:** `tokenizeBeancount` returns `keyword` as the first token for `pushtag #travel` and `poptag #travel`; every directive currently returning `keyword` still does. Add both to the directive list in `src/components/code-editor/__tests__/beancount-language.test.ts:125-128`, which already drives the production tokenizer through its own `LineStream` — this is a real test file, not one of the nine in `w4/026`.

## Blast radius

One regex, used only for editor highlighting. No parsing, saving or validation depends on it — an unhighlighted directive still saves and still checks correctly. Not exercised: whether the rustledger/backend parser accepts `pushtag` (out of scope here; this note is only about colouring).

## Adjacent states

The rest of the grammar is careful and should not be disturbed: rule order is documented and correct (directives and accounts run before the currency rule so neither `open` nor `USD` is stolen); `ACCOUNT_PATTERN` requires two segments, which is precisely what keeps a bare `USD` falling through to the currency rule; CJK account segments are supported via `\p{Lo}`; and `consumeStringBody` carries `state.inStr` across lines and treats `\"` as non-terminating, so a multi-line string stays a string.

**A second, lesser issue found in the same pass and deliberately not filed separately:** a metadata key whose name collides with a directive highlights as a keyword, because `\b` matches before the colon.

```
note: "x"            → keyword("note")
price: 3             → keyword("price")
document: "a.pdf"    → keyword("document")
query: 1             → keyword("query")
statement: "x"       → not a directive ✔
```

`note`, `price`, `document` and `query` are all plausible metadata keys. Fixing it properly means knowing whether the token is at line start or indented inside a directive body, which the current stateless-per-token design does not track — a real change, not a one-liner, and cosmetic in both directions. Worth deciding alongside the fix above rather than separately; if it is left alone, say so in a comment so the next reader knows it was considered.
