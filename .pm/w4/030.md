# `::1` is in the localhost allowlist but can never match, so IPv6 loopback is rejected as insecure

**Severity:** trivial. **Estimate:** 10–15 minutes including the test. Owner: mobile. A2: a self-hoster pointing a development build at `http://[::1]:4104` is told their server is **insecure** and to use https — wrong advice for loopback, and `::1` is sitting right there in the allowlist, so this is plainly not what anyone intended.

Environment: branch `main`, HEAD `038faeeb`. Static, verified by running the shipped function; no device interaction.

## The defect

`src/common/server-url-validation.ts:11` allows three loopback names:

```ts
const localhostNames = new Set(["localhost", "127.0.0.1", "::1"]);
function isLocalhost(hostname: string): boolean {
  return localhostNames.has(hostname.toLowerCase());
}
```

But the WHATWG URL spec brackets IPv6 literals in `hostname`, so the lookup can never hit the third entry:

```
new URL("http://[::1]:8081/").hostname  →  "[::1]"     // not "::1"
new URL("http://localhost:8081/").hostname  →  "localhost"
new URL("http://127.0.0.1:8081/").hostname  →  "127.0.0.1"
```

Running the shipped `validateServerUrl` with `allowInsecureLocalhost: true`:

| input | result |
| --- | --- |
| `http://localhost:8081` | `{ ok: true, url: "http://localhost:8081/" }` |
| `http://127.0.0.1:8081` | `{ ok: true, url: "http://127.0.0.1:8081/" }` |
| `http://[::1]:8081` | **`{ ok: false, code: "insecure" }`** |

So the two IPv4 spellings of loopback work and the IPv6 spelling does not, despite being explicitly allowlisted.

## Fix

Strip the brackets before the lookup, rather than adding a second spelling to the set — the set should stay a list of host *names*, not of URL serializations:

```ts
function isLocalhost(hostname: string): boolean {
  const host = hostname.toLowerCase().replace(/^\[(.+)\]$/u, "$1");
  return localhostNames.has(host);
}
```

Leave the rest of the rules alone; they are correct and deliberately strict (see Adjacent states).

**Acceptance:** `validateServerUrl("http://[::1]:4104/", { allowInsecureLocalhost: true })` returns `{ ok: true, url: "http://[::1]:4104/" }`; `localhost` and `127.0.0.1` are unchanged; with `allowInsecureLocalhost: false` all three are still `"insecure"`; and a non-loopback IPv6 literal such as `http://[2001:db8::1]/` stays `"insecure"`.

## Why nothing caught it

`src/common/__tests__/server-url.test.ts` is a **real** test — it imports the module under test, unlike the nine files in `w4/026` — but its two localhost cases are:

```ts
validateServerUrl("http://localhost:4104/",  { allowInsecureLocalhost: true  })  // → ok
validateServerUrl("http://127.0.0.1:4104/",  { allowInsecureLocalhost: false })  // → insecure
```

The second exercises the **flag**, not the host. So `127.0.0.1` is never tested with the flag on, and **`::1` is never tested at all** — the one allowlist entry with no coverage is the one that is broken. Add all three hosts under both flag states.

## Blast radius

One predicate, used only by `validateServerUrl`. No effect on the `https` path, which is what every non-self-hosted user is on. Limited further by `allowsInsecureLocalhost()` returning `__DEV__`, so http loopback is only ever accepted in a development build — a release build rejects all three spellings equally and is unaffected.

**Not verified on-device:** the bracket behaviour above is from Node's WHATWG `URL`. React Native resolves `URL` through its own polyfill; bracketing is spec-mandated so it should be identical, but I did not run this inside the app, and the server field was deliberately left untouched — changing the selected server risks the authenticated session this QA run depends on.

## Adjacent states

The rest of `server-url-validation.ts` is **sound and worth not disturbing**: it rejects a URL carrying `username`/`password` with its own `credentials` code (so `https://user:pass@host` cannot be pasted in), rejects any `search` or `hash`, rejects non-http(s) schemes, requires a hostname, and normalizes the trailing slash **while preserving a path prefix** (`https://host/proxy/prefix` → `https://host/proxy/prefix/`), which is what makes reverse-proxy self-hosting work. Gating http on `__DEV__` rather than shipping a user-visible "allow insecure" switch is the right default.

One naming nit, deliberately **not** filed: `parsed.search || parsed.hash` both return the code `"query"`, so a URL rejected for its fragment reports a query error. Whether that matters depends on the user-facing string, which I did not trace.

`endpointFor(serverUrl, path)` strips leading slashes before `new URL(path, serverUrl)`. That is safe for the app's uses because every caller passes a constant (`getEndpoint("api-gateway/")`), but note it would resolve an absolute URL against nothing if a caller ever passed one through — worth a comment if that function ever takes input.
