# Keep signed market values in Holdings gain percentages

**Major · 45–60m · dashboard · A2.** A valid negative quote makes every Holdings grouping report a gain when the position has lost more than its cost. The market-value column is correct; the derived gain percentage and its CSV are wrong. This is a new calculation finding, separate from percentage formatting or valuation dates.

QA on October 23, 2026 UTC, production `https://beancount.io`, owned isolated headless Chromium 156.0.8078.47, English/light/UTC, anonymous public stock-example shell, fresh 390×844 and 1440×1000 contexts. **These are explicitly modeled QueryShell reads:** execute the exact production query templates against the valid local fixtures with the current ledger WASM and actual `queryResultToShellResult`; clone genuine successful HTTP 200 envelopes and substitute those results. Other reads remain genuine. No hosted ledger is changed, and no existing public holding is claimed to have this quote.

Expected: signed profit is `−20 − 10 = −30 USD`; relative to the 10 USD basis, the percentage is **−300%**, displayed/exported as **−300.00** under the existing rounding policy. Actual: taking absolute values before subtraction gives `(20 − 10) / 10 × 100 = +100%`, reversing a loss into a gain by 400 percentage points.

Working controls use the same source except for the quote: **0.00 USD** yields **−100.00**, and **20.00 USD** yields **100.00**, in every grouping and native CSV at both widths. The zero-price position remains present. No price fallback or lossless quantity/value formatting failure is inferred.

## Cause and bounded repair

`dashboard/src/features/ledger-data/holdings/holdings-statement.ts` repeats the same numerator in all four exported templates, at lines 21, 32, 44 and 54:

```sql
abs(sum(number(value(position, today())))) - abs(sum(number(cost(position))))
```

The absolute values discard market-value direction before calculating the gain. The ledger faithfully returns the requested expression and the UI/CSV format that result. Its separate signed market-value column is already correct.

Use signed market minus signed book value, with an absolute cost denominator where nonzero, consistently in all four templates. A read-only alternate BQL control using `safediv(sum(number(value(position, today()))) - sum(number(cost(position))), abs(sum(number(cost(position))))) * 100` returns **−300** for this fixture in every grouping, with zero query errors. This is a verified repair direction, not an implemented product fix.

Retain the existing `safediv` zero-basis behavior, grouping/account selection, dated `today()` valuations, exact units/cost/price/book/market strings, filtering and two-decimal percentage formatting. Independent valid local controls for ordinary short positions—−1 unit at 10 USD cost, quotes 5 and 20 USD—retain their existing **+50%** and **−100%** results with the signed expression. A zero-cost position retains the current zero-division result. Those three additional profiles are local engine controls, not browser reproductions. The owning change is dashboard-generated BQL; the general REST/GraphQL/MCP query capability needs no behavior change.

Acceptance: execute all four actual templates on the negative, zero and positive quote fixtures; their results must be −300, −100 and +100 respectively. Meaningful query-result regressions must also preserve ordinary short-position and zero-cost controls. Verify native desktop/narrow grouping and CSV agree with the corrected results, with other row cells unchanged. Preserve current read-retry/download-failure behavior and run dashboard gates when implementing. Do not add the WASM engine to the dashboard/browser dependency graph merely to test these queries.
