# A delayed relative navigation in the journal can still produce `/ledger/undefined`

Severity: minor navigation defect with a timing-dependent trigger, same class as w4/m17. Package: dashboard. Estimate: ~30m.

w4/m17 repaired the public profile search, where a debounced write used `to: "."` and the router resolved it against a pending ledger destination whose params carry `ledgerOwner`/`ledgerName` rather than `username`, interpolating `$username` as undefined. The standing `/simplify` review censused the rest of the codebase for the same hazard. The mechanism was confirmed in the installed `@tanstack/router-core`: a navigation's `fromParams` and `fromSearch` are both taken from `pendingBuiltLocation ?? latestLocation`, so any navigation relying on implicit inheritance resolves against the in-flight destination.

Nine non-test `to: "."` call sites exist across six files. Seven are synchronous user gestures that cannot outlive their route, or sit between sibling ledger routes that share param names. Two were genuinely at risk; one — `user-profile-tabs.tsx` — was fixed in w4/m17/t004 because it is the same route and feature. The other is recorded here.

## The remaining site

`dashboard/src/features/journal/pages/journal-page.tsx` (around line 140) resets the offset with a relative navigation, and it is reached from `NewDirectiveDialog`'s success callback, which fires after an awaited mutation (`new-directive-dialog/transaction-form.tsx`). That await is the delay: if the reader has started toward `/ledger/$username` or `/ledger` while the entry is being created, the journal's params no longer exist on the destination and the write can resolve to `/ledger/undefined/undefined/journal`. Both `ledgerOwner` and `ledgerName` are already in scope at the call site, so addressing it explicitly is a small change.

## Deliberately not proposed

A lint rule banning `to: "."` was considered and rejected during the m17 review: it would flag nine sites to catch two, and it targets the wrong invariant — the hazard is implicit param inheritance during a pending navigation, not the literal. Every absolute `$param` navigation already in the repo passes explicit params, so the convention is enforced by practice; the two at-risk sites are worth fixing individually rather than building enforcement machinery.

## Related gap in the m17 repair itself

The departure flush that preserves an uncommitted profile search is bound to the results grid, so it covers leaving via a ledger card. Leaving the profile another way — the tab triggers, the profile header, any link outside that grid — still drops a query typed inside the 250ms window. The guard that prevents a stale write is generic, but the compensating flush is not, so the two have to be kept in sync by hand. Worth deciding whether the flush should move to a seam that covers every departure, bearing in mind that `useBlocker` and `onBeforeNavigate` both fire after the history-entry decision and so cannot write into the entry being left.
