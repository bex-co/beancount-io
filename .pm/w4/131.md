# Preserve visible tab selection in forced-colors mode

Severity: minor. Estimate: 60m, dashboard. A2: users browsing example reports with a high-contrast palette can identify their selected view. Repeated dashboard QA, 2026-09-18.

Environment: production https://beancount.io, anonymous public open_ledger/example, English/light, isolated headless Chromium149.0.7827.55 at1440×1000. Browser forced-colors emulation, not a physical Windows high-contrast session. HEAD26d54a9d, fetched origin/mainbd5d1d31, deployed main-BIr0jJni.js; exact deployment SHA unverified.

Reproduce: enable forced-colors:active, open `/ledger/open_ledger/example/income-statement?time=2016-02`, and wait for the report to settle. Net Profit is selected, but all five tabs have the same visible black text, white background and1px black border. Select Income, then move focus outside the tablist and wait for transitions: the panel correctly changes to Income, but the tab strip still has no visible selected marker. Fresh reload reproduces; repeating with reduced-motion:no-preference excludes the initial reduced-motion setting as the cause. `aria-selected` remains correct; this is not an inaccessible-state or failed-navigation claim.

Measured selected and unselected tabs: font-weight500, color black, border1px solid black, box-shadow none, no outline. Selected background white versus unselected transparent over the white tablist produces the same visible fill. In normal colors, the selected tab has a white fill and shadow against the muted list. At390×844, the responsive View combobox explicitly displays Net Profit, then Expenses after selection, and remains usable: that is a passing control.

Root: `dashboard/src/common/components/ui/tabs.tsx:63–71` uses background and shadow as the default variant's only persistent active-state cues; its transparent borders become visible for every tab and the shadow disappears under forced colors. `common/components/responsive-tab-trigger-list/index.tsx:53–59` uses that default variant. No forced-colors override exists. [W3C's tabs example](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/examples/tabs-manual/#accessibility-features) explains preserving separately perceivable selection and keyboard focus under high contrast; use that principle rather than copying its example implementation.

The profile underline variant reproduces the same lost selection at1440 and fresh390: `/ledger/open_ledger?tab=starred` has correct Starred selection and empty-state content, but every tab receives the same2px black bottom border. The selected underline merges into one continuous line. `tabs.tsx:74–80` varies only border/text color; forced colors removes that distinction too.

Fix both shared tab variants with a persistent selected indicator that survives forced colors, using system colors and/or a distinct border/underline geometry. Preserve a separately visible keyboard-focus indicator, layout dimensions, normal light/dark appearance, Radix selection/keyboard behavior and narrow Select fallback. Do not disable forced color adjustment globally or add a dependency.

Blast radius: the responsive helper serves Income Statement, Balance Sheet, Cash Flow, Trial Balance, Account and Holdings. Other default-variant consumers are New Entry directive tabs and the file Clone menu. Profile uses the separate underline variant and was also reproduced live at both widths. Income Statement, its narrow fallback and profile tabs were exercised; the other listed consumers are source-derived regression scope. No API or data change is needed; loading, denied and network-error behavior are outside this presentation defect.

Dedupe: searched all open/done/blocked board records for forced colors, high contrast and selected tabs, plus deleted-history searches. Existing086 concerns missing semantic state on Net Worth's plain Chart/Table buttons;116 concerns low-contrast canvas legends; neither owns this tab styling defect. Shared tabs source originates inaf5339de with no later repair in targeted history.
