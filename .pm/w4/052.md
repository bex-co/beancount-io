# The accessibility-label guardrail doesn't scan the app's own button primitive, so an icon-only `Button` would ship green

**Severity:** trivial — **no live violation exists**; this is a hole in a check, not a defect on screen. **Estimate:** 15–20 minutes. Owner: mobile. A2: `mobile/CLAUDE.md` tells contributors the unit suite catches this class of mistake, and for the most likely way to make it, it doesn't.

Environment: branch `main`, HEAD `038faeeb`; static analysis of the repository at that commit. No device interaction.

## The promise

`mobile/CLAUDE.md`, under **Accessibility — label icon-only controls**:

> *"The guardrail `src/__tests__/accessibility-labels.test.ts` fails the unit suite when a new unlabeled icon-only control appears; add an allowlist entry only with a written reason."*

The guardrail is real and well built — it scans `src/screens`, `src/components` **and** the `app/` router tree, it parses JSX opening tags properly (brace/paren/string aware rather than regex-to-`>`), and it has a second test asserting the `app/` root is actually reached so a wrong path cannot make the scan silently cover a third of the tree while looking green. **The allowlist is `[]`** — nothing has been waved through.

## The hole

`accessibility-labels.test.ts:36`:

```ts
const OPEN_TAG = /<(TouchableOpacity|Pressable)\b/g;
```

`\b` after `Pressable` does not match `<PressableScale`, because `e` and `S` are both word characters — there is no boundary between them. And `PressableScale` is not an obscure wrapper: it is what **`src/components/button/index.tsx:119`** renders, i.e. the app's general-purpose `Button`. It is also used directly in four more places (`server-settings-screen.tsx:281`, `welcome/index.tsx:98`, `account-charts-card.tsx:109`, `dashboard-card/index.tsx:101`).

So the guardrail covers the two raw RN primitives and misses the component most contributors would actually reach for. An icon-only `<Button><Ionicons name="trash" /></Button>` with no `accessibilityLabel` passes the suite.

Two narrower limits of the same heuristic, worth knowing but not worth changing:

- It requires `Ionicons` or `<Image` in the 400 characters after the tag, so a control whose glyph comes from a custom component (`AccountTypeIcon`, `ReferralGiftIcon`, `getRootIcon`) or from a variable is not recognised as icon-only.
- `TouchableHighlight` / `TouchableWithoutFeedback` are not in the pattern either — currently unused for controls, so this is theoretical.

## Verified: nothing is broken right now

Three complementary scans over `src/screens`, `src/components` and `app/`, all at HEAD:

| scan | population | icon-only **and** unlabeled |
| --- | --- | --- |
| wrappers `OPEN_TAG` never matches (`PressableScale`, `TouchableHighlight`, …) | 6 | **0** |
| higher-level tappables (`Button`, `DashboardCard`, `SecondaryButton`, `ListItemHorizontal`) | 33 | **0** |
| `TouchableOpacity`/`Pressable` that are unlabeled and textless but *don't* trip the `Ionicons`/`<Image` heuristic | 5 | **0** (all five are row wrappers whose `<Text>` sits beyond the 400-character window, so their accessible name comes from their children) |

This is a preventive fix, not a repair.

## Fix

Widen the pattern to the components the app actually uses as controls:

```ts
const OPEN_TAG = /<(TouchableOpacity|Pressable(?:Scale)?|Button)\b/g;
```

`Button` needs care: it takes `children`, so the existing "no `<Text` nearby" test still works, but its call sites often pass a `<Text>` child and would be excluded correctly. Run it and expect zero new violations — per the table above there are none — then keep it.

Consider also asserting that the pattern covers `PressableScale` explicitly, in the spirit of the existing "scans the Expo Router app tree, not only src" test: that test exists precisely because a silently-narrowed scan is the failure mode this file is prone to, and a component-name pattern is the other place it can narrow.

**Acceptance:** adding an icon-only `<Button><Ionicons name="trash" /></Button>` with no `accessibilityLabel` fails `yarn test:unit`; adding the same with a label passes; the existing suite still reports zero violations and the allowlist stays `[]`.

## Blast radius

One regex in one test file, plus optionally one new assertion. No product code changes, no behaviour change. If widening the pattern does surface violations in future work, each is a real missing label rather than a false positive — the heuristic errs toward silence, not noise.

Not exercised: VoiceOver itself, which the Simulator does not offer (`w4/002`), so none of this is a substitute for hearing the app read out.

## Adjacent states

One thing found by the scan and deliberately **not** filed as a defect, because it cannot be judged without VoiceOver: `ledger-drawer.tsx:847-851` renders the drawer's backdrop as a full-screen `Pressable` with `testID="ledger-drawer-backdrop"`, `StyleSheet.absoluteFill`, `onPress={onClose}` and **no label or accessibility opt-out**. The sibling content view does carry `importantForAccessibility={open ? "no-hide-descendants" : "auto"}`, so the hiding logic was thought about — just not for the scrim. Whether an assistive technology announces an unlabeled full-screen button here, or ignores it, needs a real device with VoiceOver; guessing either way would be speculation. Worth checking off in the same sitting as `w4/002`.

The rest of the accessibility surface has held up well across this run and is worth recording: every icon-only control I inspected on device carried a label (`w4/049`'s discovery tabs, `w4/050`'s picker rows, `w4/047`'s Done button), status is never colour-only (the picker swaps chevron for checkmark, the account table uses weight as well as colour), and validation messages use `accessibilityRole="alert"` or `accessibilityLiveRegion="polite"`.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for accessibility, label, guardrail, VoiceOver and allowlist terms. **`w4/done/m7`** is the milestone that built this guardrail (the test's own comment says "matches w4/m7"), and this note extends it rather than reopening it. **`w4/002`** is the VoiceOver/Accessibility-Inspector residual that milestone left behind — the backdrop question above belongs with it. `w4/013` and `w4/014` are Dynamic Type on specific rows. `w4/025`, `w4/026` and `w4/046` are the same *family* — a detector that looks green because of what it doesn't look at — and should be cross-referenced when any of them is picked up. No item covers this scan's coverage.

Reproducible from `mobile/` at HEAD `038faeeb`: the three scans in the table re-run the guardrail's own tag parser over widened component sets. Counts are 6, 33 and 5 occurrences respectively, zero violations in each.
