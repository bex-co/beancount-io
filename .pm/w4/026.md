# 178 unit tests — 10% of the suite — never reference the code they claim to test

**Severity:** minor as a defect (nothing user-facing is broken) but high signal: these tests cannot fail, so the suite overstates what is protected. **Estimate:** well over an hour across nine independent files; **`/pm promote` to a milestone** rather than treating it as one note. Owner: mobile. A2: `yarn test:unit` reporting **1769 passed** is the main safety signal an agent has before changing this package, and one case in ten of that number is inert.

Environment: branch `main`, HEAD `038faeeb`. Found by static analysis of every `*.test.ts`/`*.test.tsx` under `src/`; `yarn test:unit` passes (1769) and `yarn lint:deadcode` passes clean.

## What was measured

Every test file was checked for any relative import or `require` of app code (`from "./…"`, `from "../…"`, `require("../…")`). Nine files have **none**, and do not read source off disk either:

**178 cases, 10.1% of the reported 1769.**

Each file instead re-declares the logic inline and asserts against its own copy. The headers say so plainly — *"Test business logic extracted from ContactRow component"*, *"mirrors hook implementation"*, *"tests the business logic without requiring actual Sentry SDK"*. In practice that collapses to testing the language:

```ts
// bar-chart-d3.test.ts — the largest of the nine, and it imports d3-scale but never the chart
const numbers = [10, 25, 15, 30, 20];
const maxValue = Math.max(...numbers, 1);
expect(maxValue).toBe(30);

// contact-row-utils.test.ts
const iconName = `radio-button-${selected ? "" : "un"}checked`;
expect(iconName).toBe("radio-button-checked");

// use-user-profile.test.ts
const variables = { userId: "user-123" };
expect(variables.userId).toBe("user-123");
```

If `bar-chart-d3.tsx` changed its domain calculation tomorrow, all 42 of its cases would still pass.

## Why it happened — and why it no longer has to

The package runs a custom lightweight runner (`scripts/jest-lite-runner.js`), and a module that imports `react-native` cannot simply be required into it. That is a real constraint and it explains the hook and provider files: re-declaring the logic was the only way to assert anything at the time. `src/common/date-format.ts` documents the other half of the same trade-off from the source side — *"Import-free, so the unit-test runner can require it and assert real formatted output rather than mocking a formatter."*

But the capability now exists. `src/common/__tests__/fixtures/mock-react-native.ts` models the native surface, and its own comment is explicit that the model is *"deliberately faithful on the one point that matters"*. It has exactly **one** consumer — `src/common/__tests__/rtl.test.ts` — which imports the real `rtl.ts` and tests shipped behaviour through the mock. That file is the worked example for all nine.

## Fix

Not one change; sort the nine into three piles.

1. **Delete outright** — `use-user-profile.test.ts` and `contact-row-utils.test.ts`. Their subjects do not exist, so there is nothing to point them at. Remove `src/screens/setting/hooks/` entirely (it contains only `__tests__/`). This is the same deletion `w4/025` §2 asks for; **do that one here** rather than twice.
2. **Rewire through the mock fixture** — the hook and provider tests (`use-session`, `use-theme-style`, `use-translations`, `toast-provider`). Import the real module, extend `mock-react-native.ts` where a new native surface is needed, and keep the mock faithful on the points that matter, as `rtl.test.ts` does. Expect some assertions to turn red; each one that does was a real gap.
3. **Extract, then import** — `bar-chart-d3` and `use-add-entries-to-remote`. The logic worth testing (scale domain, entry assembly) should move into an import-free sibling selector, which the component then uses and the test imports. That is exactly the shape `transaction-display-utils.ts`, `select-filter-query.ts` and `budget-dates.ts` already have, and their tests import the real thing.

`sentry.test.ts` needs a judgement call: decide whether `src/common/sentry/capture.ts` has logic worth testing and rewire, or delete the file. Do not leave it asserting `if ("https://…") initialized = true`.

**Do not** fix this by lowering the bar — deleting all nine files without replacing the coverage in pile 2 and 3 would trade fake protection for none. And do not add a lint rule that bans importless tests: three legitimate guardrails (`accessibility-labels.test.ts`, `apollo/cache-persist.test.ts`, `apollo/fetch-policies.test.ts`) import nothing on purpose and scan source off disk instead. They are correct and must keep passing.

**Acceptance:** every remaining test file either imports the module it names or deliberately reads source from disk; the nine files above are deleted or rewired; `yarn test:unit` passes with a count that has *dropped*, and the drop is documented. A mutation check is the real proof — change the domain calculation in `bar-chart-d3.tsx` or the icon-name expression in `ContactRow`, and a test must fail.

## Blast radius

Test-only. No runtime code changes except the selector extractions in pile 3, which are behaviour-preserving moves. The visible outcome is a **smaller** passing count, which is the point: the number becomes true. Not exercised: whether any of the nine hides a real defect that a rewired test would catch — likely for the hooks, since none of their shipped code is currently asserted at all.

## Adjacent states

`.agents/skills/pm/SKILL.md` already carries the governing rule for every milestone's standing test task — *"Tests must assert real behavior and failure modes; never game coverage with trivial, tautological, or snapshot-everything tests"* — so this needs no new policy, only enforcement on files that predate it.

Two findings from this run are instances of the same underlying problem and should be read together: `w4/024`, where `it("handles boundary values")` pins `shortNumber(999999) === "1000.0K"` — a real test of real code that asserts the *wrong* answer — and `w4/025` §2. This note covers tests that assert nothing; `w4/024` covers a test that asserts a bug. Both make the suite a worse signal than its count suggests.

The wider suite is in good shape and should not be tarred with this: the selector tests (`transaction-display-utils`, `select-filter-query`, `budget-dates`, `drawer-ledgers`, `wheel-position`, `beancount-language`) all import their subjects and assert real behaviour, and `rtl.test.ts` is a model for testing native-dependent code honestly.
