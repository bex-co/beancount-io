Severity: major. Estimate: 60 minutes for the truthful unresolved-period fallback described below. Package: dashboard. A3: exported financial statements must not claim a period their numbers do not cover.

Environment: production beancount.io, public `open_ledger/apple`, signed out, English/light, isolated headless Chromium149.0.7827.55, fresh390×844 and1440×1000. Root: `dashboard/src/features/reports/export/reporting-period.ts:239–271` treats a null parseConcreteTimeFilter result as an absent selection. The concrete parser intentionally does not resolve relative tokens. Consequently a nonempty, backend-accepted year-1 falls through to implicitThroughDate and the generation day, with inferredStartDate from the chart buckets. Backend `ledger/src/foundation/rustledger/directive-filter.ts:1050–1068` substitutes year-1 before parsing; the producer returns correctly filtered2025 data. Export model.ts278 forwards the raw time filter but has no authoritative resolved-bound fields in this report response. Markdown, CSV, print and filenames all consume the wrong common reportingPeriod.

Scoped fix: distinguish an empty time filter from a nonempty selection whose exact bounds the export cannot resolve. Apply the existing generation-day/future-bucket policy only to genuinely unfiltered statements. For an unresolved selected filter, leave start/end/as-of dates unknown, retain the exact raw selection, use the existing unavailable-date/internal-draft notices and period-unresolved filename fallback, and expose that raw time selection in Markdown/print scope as CSV already does. Reuse an appropriate existing localized Time label where possible. Do not claim all available activity or manufacture bounds from partial chart buckets. If a later implementation supplies authoritative resolved bounds, year-1 here must resolve toJanuary1–December31,2025; this note does not require a second relative-date parser or backend/schema expansion. Preserve report numbers, units and filters.
