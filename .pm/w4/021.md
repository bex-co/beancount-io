# `beancount:///auth/welcome` shows a signed-in user the sign-in screen, with no way back

**Severity:** minor — recoverable by force-quitting, and it takes a URL to reach. **Estimate:** 20–30 minutes. Owner: mobile. A2: a signed-in newcomer who hits this link sees "Sign In / Sign Up" and has no visible route back into the app, which reads as a lost session.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, authenticated production session at `https://beancount.io`, ledger `open_ledger/alphabet`. Report-only QA; no ledger mutation and **Sign In was never tapped** (see Unverified).

## Repro

1. With the app signed in and showing Home, fire `xcrun simctl openurl <udid> 'beancount:///auth/welcome'`.
2. The **signed-out Welcome screen** renders: app logo, a settings gear top-right, and `Sign In` / `Sign Up` buttons at the bottom. The authenticated session is still perfectly valid.
3. There is **no back affordance** — no chevron, no header. Tapping where a back button would sit does nothing; the screen stays.
4. The only escape is terminating the app. Relaunching recovers cleanly: Home, session intact, `open_ledger/alphabet` still selected.

**Working control, same mechanism:** `beancount:///(app)/agent` is also a URL-reachable route that should not be shown, and it *is* guarded — it redirects to the tabs and no agent UI appears.

**Second control — the app already has the recovery pattern.** Firing a route that does not exist (`beancount:///(app)/this-route-does-not-exist`) lands on `+not-found`, which reads **"Page not found / That link doesn't lead anywhere in the app."** with a **Go to Home** button that works. So an unknown route is handled gracefully with a way out; `auth/welcome` is worse off precisely because it *is* a known route, so it renders rather than falling through to that screen. Neither of the two established patterns — the `/agent` guard or the `+not-found` escape — is applied here.

## Root cause

`app/auth/welcome.tsx` renders the screen unconditionally:

```tsx
export default function Auth() {
  return <WelcomeScreen />;
}
```

There is no session check in the route, in `src/screens/welcome/index.tsx`, or in the root layout. And `app/auth/_layout.tsx` sets `screenOptions={{ headerShown: false }}`, so nothing supplies a back control — correct for a genuine signed-out launch, and a dead end when the screen is reached with a live session.

`app/(app)/agent.tsx` already establishes the pattern and the reasoning, in its own comment:

> *"Gating the Home card alone would leave `beancount:///(app)/agent` open to anything that can fire a URL scheme, so the route is the real switch and the card is only the visible half of it."*

The identical argument applies to `auth/welcome`: whatever normally keeps a signed-in user away from it, the route is the real switch, and it doesn't have one.

`app/+native-intent.tsx` is **not** the right place for this — it only rewrites incoming Universal/App Link paths to in-app routes before Expo Router matches them, and explicitly runs before app providers, so session state is not reliably available there.

## Fix

Guard the route the way `agent.tsx` does: when a session exists, `return <Redirect href="/(app)/(tabs)" />` instead of rendering `<WelcomeScreen />`. That single change removes the dead end, because the user never lands on the screen at all.

Keep the genuine signed-out path untouched — a cold launch with no session must still show Welcome, and `headerShown: false` is right there. Do not add a back button to the auth stack as the fix: it would put a "back to where?" control on the real sign-in screen, where there is nothing behind it.

Consider the same audit for the other `auth/` route: `beancount:///auth/server` renders the server settings screen with no back control either (observed earlier in this session). That one is at least reachable from Settings by normal navigation, so it is a weaker case, but it shares the shape.

**Re-checked later in the run, with a detail that sharpens it.** Unlike `welcome`, the server screen *does* opt a header in — `server-settings-screen.tsx:208-209` sets `{ headerShown: true, title: t("serverSettings") }` over the auth layout's `headerShown: false`. It still renders with **no back chevron** when deep-linked, because a header only gets one when there is a previous route in that stack, and a deep link makes this the stack's only entry. So the header is present and empty on the left, which reads as more broken than `welcome`'s headerless screen, not less.

The screen's only programmatic exit is `router.back()` inside `onSave` (`:188`) — reached by saving a server URL. I did not fire it: it would write a `serverUrlOverrideVar` this run is meant to leave untouched, and whether `back()` can escape to `(app)` from a deep-linked `auth/` route is therefore **unverified**. A session guard on this route, as proposed above for `welcome`, sidesteps the question entirely.

**Acceptance:** with a live session, `beancount:///auth/welcome` lands on the tabs and never shows Sign In / Sign Up; with no session, a cold launch still shows Welcome and sign-in still completes; `beancount:///(app)/agent` is unchanged.

## Blast radius

One route. Reachable by anything that can fire the custom scheme — another app, a web page, a QR code, or a stale link. Not exercised: the same URL as an **https** Universal Link (blocked by `w4/018`: the well-known files are 404, so https links do not reach the app at all), and Android.

## Adjacent states

Relaunch fully recovers — the session survives, so this is a navigation dead end rather than a session or data problem, which is why it is rated minor. The signed-out flow itself was not disturbed. The `w3/191` worklet error is unrelated and did not fire here.

**Unverified, deliberately:** I did not tap **Sign In** from this screen while already authenticated. Doing so starts the OAuth/PKCE flow in a web view that this tooling cannot drive, and a failure would have cost the session for the rest of the QA run. What a second sign-in does to an existing session — replace it, duplicate it, or error — is therefore unknown and worth checking when the fix is made.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for auth/welcome, welcome screen, deep-link guards, stranded and redirect terms. **`w3/203.md` (open)** is the nearest — "Give cold native detail links a working return destination" — but its subject is a *legitimate* destination (a shared transaction detail) lacking a way onward into the ledger; the fix there is a return path. Here the screen is the *wrong destination entirely* for an authenticated user and the fix is a session guard. Same family, different cause, different fix — read them together. `w4/018` covers why the https form of this URL cannot currently reach the app at all. No item covers this route.
