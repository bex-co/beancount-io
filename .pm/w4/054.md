# The Cash flow chart reads its totals to VoiceOver as bare 12-digit integers, and omits Savings — the two charts beside it get this right

**Severity:** minor. **Estimate:** 15–20 minutes. Owner: mobile. A2: no value is drawn anywhere on this chart, so its `accessibilityLabel` is the **only** way a screen-reader user learns any magnitude from it — and it is the one summary of three that is unformatted.

Environment: branch `main`, HEAD `038faeeb`; source trace, plus the chart exercised on device (`open_ledger/alphabet`, Reports, all four ranges, light appearance). **VoiceOver itself was not used** — it does not start on this Simulator (`w4/002`), so what is confirmed is the string that gets built, not how it sounds.

## The three summaries, side by side

The app builds an accessibility summary for each of its three charts. Two format money; one does not.

| chart | code | produces |
| --- | --- | --- |
| Income/expense bars (Reports) | `income-expense-bar-chart.tsx:158` — `` `${currencySymbol}${shortNumber(total)}` `` | `$305.0B` |
| Budget bars (Budget) | `budget-labels.ts:145-146` — the same `` `${currencySymbol}${shortNumber(...)}` `` helper | `$122` |
| **Cash flow Sankey (Reports)** | `cash-flow-sankey.tsx:288-291` — `String(Math.round(incomeTotal))` | **`305000000000`** |

```ts
accessibilityLabel={t("cashFlowChartSummary", {
  income: String(Math.round(incomeTotal)),
  expenses: String(Math.round(expenseTotal)),
})}
```

No currency symbol, no separators, no abbreviation. On `open_ledger/alphabet` a screen-reader user swiping down Reports hears the income/expense chart announce *"Income $305.0B, expenses $190.0B, net …"* and then, in the very next card, *"Income 305000000000, expenses 190000000000."* A twelve-digit integer read aloud is not a quantity anyone can hold.

It is worse on a non-USD ledger: with no symbol at all, `open_ledger/minimax`'s figures are announced as unitless numbers, and that ledger's whole point is that its currency is **MUSD** rather than dollars.

## Savings is missing from the summary

`cashFlowChartSummary` (`en.ts:337`) names two of the chart's three roles:

> *"Cash flow from income to expenses. Income {{income}}, expenses {{expenses}}."*

But the chart has a third. `cash-flow-sankey.tsx:369-371` renders a **Savings** legend item whenever `data.nodes.some((node) => node.role === "savings")`, and on `open_ledger/alphabet` at 6M the blue Savings band is the largest single destination on the expense side — visually about a third of the flow. A sighted user sees three colours in the legend; the summary describes two.

Compare `incomeExpenseChartSummary`, which does include a third term (`net`). The Sankey's has no equivalent.

## Fix

Everything needed is already in scope at the call site. `reports-screen.tsx:69` computes `currencySymbol` and passes it to the income/expense chart at `:170` — it just is not passed to the Sankey at `:185`:

```tsx
<CashFlowSankey income={income.tree} expenses={expense.tree} currencySymbol={currencySymbol} />
```

Then format the same way the sibling charts do, and add the third term:

```ts
const money = (v: number) => `${currencySymbol}${shortNumber(v)}`;
```

with `cashFlowChartSummary` extended to `"… Income {{income}}, expenses {{expenses}}, savings {{savings}}."` — and the savings term omitted (or the existing two-term string used) when there is no savings node, matching the condition the legend already uses. Adding a key is the right move here rather than reusing one: the other twelve locales extend `en`, so an untranslated new key falls back cleanly.

**Both precedents cited above are themselves incomplete** (added September 14). `w4/060` shows that the `` `${currencySymbol}${shortNumber(…)}` `` idiom at `income-expense-bar-chart.tsx:158` and `budget-labels.ts:145-146` puts the minus on the wrong side of the symbol and drops the currency entirely when it has no symbol. Copying the idiom verbatim here would inherit both faults. Copy the *intent* — `shortNumber` plus a currency — but take it from `w4/060`'s `formatShortMoneyWithCurrency` helper, which routes through `annotateCurrency` and gets the sign and the symbol-less fallback right. That makes this a three-site fix in one sitting rather than a fourth hand-rolled formatter.

**`shortNumber` has an open defect of its own** (`w4/024`: it renders a whole zero as `$0.0` and rounds past its own suffix). Use it anyway — consistency with the other two summaries matters more than avoiding a bug those two already share, and `w4/024`'s fix then improves all three at once. Do not hand-roll a third formatter here.

**Acceptance:** the Cash flow chart's `accessibilityLabel` on `open_ledger/alphabet` contains `$305.0B`-style figures rather than raw integers, matching the income/expense chart directly above it; it names savings when a savings node exists and omits that clause when none does; on `open_ledger/minimax` the figures carry the ledger's currency. Add a unit test over the summary string for the three cases — with savings, without savings, and non-USD. `cash-flow-sankey` has tests for `truncateSankeyLabel` and the layout selectors but none over the accessibility label.

## Blast radius

One component's label, one prop, one translation key. **No visual change** — the Sankey draws no values today and this does not add any; it only changes what assistive technology is told. The other two summaries are untouched.

**This is the only instance in the app.** A sweep of `src/` and `app/` for `accessibilityLabel` / `accessibilityValue` / `accessibilityHint` / `*ChartSummary` whose interpolated parameters are built with `String(…)`, `Math.round(…)`, `.toFixed(…)`, `.toString()` or `Number(…)` returns four lines: the two in `cash-flow-sankey.tsx` above, and two false positives in `income-expense-bar-chart.tsx` where the match is the `Number` inside `shortNumber`. So the defect is isolated rather than a pattern — worth stating, because it means the fix is genuinely local and no follow-up sweep is owed.

Not exercised: VoiceOver (`w4/002` — unavailable on this Simulator), so the *audible* result is inferred from the constructed string; Android; and whether a savings node can ever be absent on a real ledger (the conditional legend implies yes, but I did not find a ledger without one).

## Adjacent states

The rest of the Cash flow card is **well built**, which is why the label stands out:

- The whole plot is one `accessible` view with a single summary, rather than exposing every SVG node — exactly what `mobile/CLAUDE.md` asks for ("Charts need a summarizing `accessibilityLabel` instead of exposing SVG nodes").
- Node labels use an explicit `truncateSankeyLabel` with proper boundary handling (`maxChars <= 0` → `""`, `=== 1` → `"…"`), because SVG text cannot ellipsize natively. This is deliberate, not the accidental tail-truncation of `w4/050`.
- A node too short to host a line of text is skipped rather than overprinted, with a comment saying so.
- There is a real empty state (`cashFlowEmpty`: "No cash flow in this range").
- The card recomputes correctly on every range change — verified on device across 1M, 6M, YTD and ALL, where the source node ordering visibly changes with the window.

**A hypothesis I checked and dropped:** I had flagged the previous iteration that the Sankey might be a "chart with no magnitudes at all" defect, since no band carries a value and every node label is truncated. That is not right — the magnitudes *are* published, through the accessibility summary, and the truncation is deliberate. Reading the component settled both questions and turned the finding into the narrower one above.

## Dedupe

`grep -rli "cashFlowChartSummary\|Sankey\|chart summary\|accessibilityLabel" --include='*.md' .` over the whole board including `done/`, plus VoiceOver and cash-flow terms.

**Two closed notes are the precedent for this fix, and both argue for it.** **`w3/done/128`** ("Expandable mobile report categories omit accessible amounts") added amounts to an accessibility label on the Reports category breakdown — *one card below this one on the same screen*, and it did not reach the Sankey. **`w3/done/149`** ("Name the native posting amount fields and expose their signed values") did the equivalent for the entry form's amount inputs, and is why `multi-postings-transaction-screen.tsx:347-348` carries `accessibilityLabel` plus `accessibilityValue` today. So "a number a sighted user can see must be available to assistive tech, formatted" is settled practice here; this is the one chart that formats it as a bare integer.

`w3/188` (the merchant Recurring switch announcing the wrong state) is a different control and a state bug rather than a value bug. `w4/024` is `shortNumber`'s formatting, discussed above. `w4/002` is the VoiceOver residual that makes this unverifiable here. `w4/052` is the label guardrail, which only checks that a label *exists* — it has nothing to say about whether a label is useful, which is worth noting on both. No item covers this.
