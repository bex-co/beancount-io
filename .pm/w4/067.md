# A failed query on Home reads as an empty ledger — "No transactions yet", "Quick add to show charts" — because three of its five queries throw `error` away

**Severity:** minor — it takes a request failure to bite, but when it does the app makes an affirmative, false claim about the user's data on its primary screen. **Estimate:** 30–45 minutes across the sites below. Owner: mobile. A2: a newcomer whose first launch hits a flaky network is told their ledger is empty and invited to "Quick add" data they already have.

**Read this first: the defect is established from source, not observed on screen.** This QA environment has no way to fail a single GraphQL request — there is no network shaping, and the one lever available (pointing the app at a bad server) rewrites `serverUrlOverrideVar` and the session scope, which this run is not authorized to touch. What is shown below is the code path, step by step; the step I could not execute is the failure itself. Treat the rendering claims as strongly implied rather than photographed.

Environment: branch `main`, HEAD `038faeeb`; source trace at that commit, with the live screens inspected in their healthy state on the native build on iPhone 17e / iOS 26.5.

## The app already has the right machinery, and it is good

`src/common/apollo/stale-data.ts` is a small, well-documented, unit-tested decision:

```ts
/**
 * Pure decision for "cached data is on screen but the latest refetch failed."
 * - cache + error → stale (show indicator)
 * - cache + ok    → fresh (hide indicator)
 * - no cache + error → first-load failure (existing error UI, not the indicator)
 * - no cache + ok → loading / empty (not stale)
 */
```

`isShowingStaleDataFromQueries(queries)` aggregates it across a screen, and `StaleDataBanner` renders it. Three screens use it — Home, Accounts, Reports.

**The problem is what each screen passes in.** Every one of them aggregates exactly two queries:

| screen | queries wired into the banner |
| --- | --- |
| `home-screen.tsx:91-94` | `balanceSheet`, `ledgerMeta` |
| `accounts-screen.tsx:113-116` | `accountData`, `ledgerMeta` |
| `reports-screen.tsx:142-145` | `incomeData`, `ledgerMeta` |

Home renders **five** queries. The other three run inside its cards, and each card discards `error` at the call site.

## The path, for Home's Recent Transactions

1. `home-screen/components/recent-transactions-card.tsx:44` —
   `const { data, loading, refetch } = useGetLedgerJournalQuery({…})`. No `error`.
2. The card derives `entries` from `data?…` and renders at `:72-77`:

   ```tsx
   {loading && entries.length === 0 ? <Skeleton/> : (
     entries.length === 0 ? <Text style={styles.empty}>{t("recentTransactionsEmpty")}</Text> : …
   ```
3. On a **cold** failure (`error` set, no cache) Apollo leaves `data` undefined and `loading` false. So `entries` is `[]`, the skeleton is skipped, and the card renders `recentTransactionsEmpty` — **"No transactions yet"**.
4. Because the card never surfaced `error`, `isShowingStaleDataFromQueries` at `home-screen.tsx:91` cannot see it. No banner.

The net-worth chart above, driven by the separately-wired `balanceSheet`, may well have succeeded — so the user sees a correct billion-dollar chart sitting directly above "No transactions yet", with nothing to reconcile the two.

## Fix

Two changes, in this order:

1. **Surface `error` from the card queries and feed it into the existing aggregate.** The cards already return `refetch` to their parent; returning `error` the same way, and adding the three entries to `home-screen.tsx:91`, makes the banner honest with no new mechanism. Do the same for `account-transactions-card` on Reports.
2. **Do not let an empty state be rendered from a failed query.** The stale banner only covers the *cache + error* quadrant; the quadrant this note is about is *no cache + error*, which `stale-data.ts` explicitly hands to "existing error UI". Those cards have no error UI — so give each one a failure branch distinct from its empty branch. The minimum honest version is the empty container plus a short "Couldn't load" line and a retry, reusing whatever the team settles on; the one thing that must stop is a positive claim.

`useLedgerErrors` needs both: `w4/042` already asks it to expose `refetch`, and it should expose `error` in the same edit — today it returns `{ errors, count, loading }` and collapses `data?.getLedgerErrors ?? []`, so the screen *cannot* distinguish "no errors" from "the check failed" even if it wanted to.

**Do not** fix this by switching to `errorPolicy: "all"` globally to keep partial data on screen. That changes behaviour for every mutation and query in the app, including the receipt flow, which has two comments (`receipt-utils.ts:28`, `use-receipt-workflow.ts:80`) reasoning explicitly about Apollo's *default* policy.

**Acceptance:** with `getLedgerJournal` failing and `balanceSheet` succeeding, Home shows the stale banner or a per-card failure state — never "No transactions yet"; with both succeeding, Home is pixel-identical to today; a genuinely empty ledger still shows "No transactions yet" and "Quick add to show charts"; Notifications distinguishes "no recent changes" from "couldn't fetch changes"; and `useLedgerErrors` can tell the two apart. Add unit tests over each card's branch selection for the four `stale-data.ts` quadrants — the pure helper is tested, but **nothing tests that a screen passes its queries into it**, which is exactly the gap this note reports.

## Blast radius

Seven query call sites; the three Home cards are the ones that matter. No change to `stale-data.ts` itself (it is correct), to `StaleDataBanner`, or to the Apollo client configuration.

**Not exercised, and this is the note's main limitation:** the failure itself. I could not induce a per-query error, so the rendering in the table above is inferred from the branch conditions rather than seen. The inference is short — `data` undefined → `?? []` → `length === 0` → the empty branch — and each link is quoted above, but it is inference. Anyone fixing this can confirm it in seconds by forcing one query to reject in a dev build; that is worth doing first, because it also tells you whether `cache-and-network` leaves a prior result in place often enough to mask the cold case in practice.

Also not exercised: Android, and whether any of these queries would in practice be served from persisted cache (`restoreApolloCache` runs at startup), which would move the failure into the *cache + error* quadrant the banner already covers — on a first launch, or after a ledger switch evicts the scope, there is no such cache.

## Adjacent states

The queries that **do** carry `error` are wired correctly and are the pattern to copy: `use-balance-sheet.ts:14`, `use-trial-balance.ts:15`, `use-account-report.ts:20`, `use-income-statement.ts:14`, `use-budget-groups.ts:34`, `use-budget-actuals.ts:61`, `use-ledger-access.ts:8`, `use-ledger-meta.ts:23`, plus the three detail screens (`transaction-detail-screen.tsx:273`, `entry-context/index.tsx:191`, `ledger-file-browser-screen/index.tsx:312`). So the codebase's default habit is right; this is a set of card-level queries that drifted from it.

Home's `chartError` at `home-screen.tsx:90` is also worth noting as a correct example in the same file — `Boolean(balanceSheetError) && !balanceSheet` keeps the chart skeleton on a first-load failure instead of drawing an empty chart, with the reasoning in a comment directly above. That is precisely the treatment the three cards lack.

## Dedupe

`grep -rn 'StaleDataBanner\|stale-data\|isShowingStaleData\|errorPolicy' .pm --include='*.md'` over the whole board including `done/` returns **nothing**. A broader `-i 'stale'` returns six lines, all about stale *URLs* or stale *paths* (`w4/051`, `w3/129`, `w3/m35/t008`, `w3/done/m15`, `w3/done/m21`) or explicitly ruling stale data out (`w3/219`). No item covers the banner's coverage or discarded query errors.

**`w4/042`** is the one real neighbour and they should be fixed together. It reports two symptoms on Notifications — pull-to-refresh not re-checking the ledger errors, and "Ledger is healthy" rendering while the error query is still loading. This is a **third symptom on the same screen with a different cause**: its commits query discards `error`, so a failed `listCommits` renders "No recent changes." `w4/042`'s symptom 2 is *loading*-shaped (an affirmative claim on data that has not arrived); this one is *error*-shaped (an affirmative claim on data that will never arrive). Its fix already touches `useLedgerErrors`, which is where this note's sixth row lives, so the two overlap in exactly one file and should be one sitting.

`w4/008` concerns the same screen's refresh behaviour and is cross-referenced from `w4/042`.
