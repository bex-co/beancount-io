# Auth hand-rolls field-error association that `ui/form.tsx` already provides, and five fields still lack it

Severity: minor accessibility defect plus a structural duplication. Package: dashboard. Estimate: ~2h — a primitive repair, five form migrations and a guard, so this is a milestone candidate rather than a note.

w4/m15 repaired sign-in, recovery and registration by hand-writing `aria-invalid`, `aria-describedby`, error ids and `role="alert"` on each field. That was the correct call for the reported defect, but the standing `/simplify` review found the repo already owns the mechanism: `dashboard/src/common/components/ui/form.tsx` emits `aria-invalid` and `aria-describedby` from form context (`FormControl`, ~line 107) and renders the error paragraph with a `useId()`-scoped id (`FormMessage`, line 139). Roughly a dozen feature forms already consume it — ledger-form, api-key-create-dialog, ssh key-create-dialog, receipt-review-form, open-account-dialog, add-budget-dialog, the four new-directive-dialog forms and the importer configure forms — and `api-key-create-dialog.tsx:134` already ships `<FormMessage role="alert" />`. The `auth` feature is the sole outlier.

## The primitive needs two fixes before anything migrates

Verified on `main` at `1221d4c8`:

- `FormControl` always includes `formDescriptionId` in `aria-describedby`, even when no `FormDescription` is rendered, so most fields would gain a dangling idref.
- `FormMessage` sets no `role="alert"`, so migrating the auth forms as they stand would silently lose the announcement w4/m15 just added.

Fix those first, then migrate; a straight swap today is a regression.

## Fields still carrying the defect

Inside auth, out of w4/m15's stated scope:

- `dashboard/src/features/auth/pages/reset-password-page/index.tsx` — `newPassword` (~326) and `confirmPassword` (~344) inputs unassociated; their error paragraphs bare. This is the reset-token form, which w4/m15/t001 explicitly excluded.
- `dashboard/src/features/auth/components/otp-form/index.tsx` — the `InputOTP` (~136) has no invalid state or description; its error paragraph (~153) has no id or role.

Outside auth, the one other genuine react-hook-form/Zod cluster:

- `dashboard/src/features/importer/components/steps/preview/editable-cell.tsx` — the `Input` branch (~165) takes an `error` prop but uses it only for border colour; the error paragraph (~187) has no id or role. The sibling `Textarea` branch points `aria-describedby` at the multiline hint only, so the error is never referenced. The collapsed `Button` branch (~237) repeats the unassociated text. Errors come from `editable-preview-row.tsx` (date, payee, description, amount).
- `dashboard/src/features/importer/components/steps/preview/editable-preview-row.tsx` (~200) — the error summary row duplicates every field error with no association and no live region.

Already correct, do not re-report: every `ui/form` consumer listed above, registration's Username, and `ledger-editor/create-file`. Server and status messages in `plaid/bank-item.tsx`, `ledger-clone-url-menu.tsx` and `user-profile-tabs.tsx` are a different class.

## Why nothing caught it

`dashboard/eslint.config.js` has no `eslint-plugin-jsx-a11y`, and adding it would not help — the plugin has no rule for field-error association. The repo's actual mechanism for cross-cutting invariants is source-scanning tests under `dashboard/src/test/`: `no-raw-error-message.test.ts` and `no-untranslated-user-facing-strings.test.ts`, each walking `src/` with an `ALLOWLIST` of justified exceptions. There is no accessibility counterpart, so a guard belongs there: flag JSX that renders `errors.<field>.message` whose control lacks `aria-describedby`. `git log -S'aria-describedby' -- dashboard/src` shows this has been repaired one field at a time across roughly eight commits; a guard is what stops the series.

Also worth one line: `register-form` lacks the `noValidate` that `login-form` sets. Exercised live during w4/m15/t004 — a malformed address still produces the correct association and alert, so this is a consistency question, not a defect, and changing it alters submission behaviour.
