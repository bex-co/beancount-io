# Keep the pending Close Account date equal to its request

**Severity:** minor confirmation accuracy. **Estimate:** 25–40 minutes, dashboard. **A2:** an in-flight bookkeeping confirmation should describe the date its prepared request actually contains.

Controlled reproduction on production `https://beancount.io`, 2026-10-24, owned isolated headless Chromium156.0.8078.47, English/light/UTC, signed-in designated disposable-ledger owner. This is a browser-local clock/fixture check, not an observed physical-midnight incident or a claim that an incorrect date was committed. Every CLOSE request is held and aborted before transport.

The account-read fixture appends only the exact zero-entry, empty-balance account record returned by the earlier real native create journey in [1083](./1083.md). That account was already removed and the original ledger restored before this check; other account rows and permissions remain genuine. Playwright `Page.clock.setFixedTime` controls Date only in each isolated context; the computer and original browser clock are untouched.

## Reproduce and controls

1. Fix the owned page's Date to **2026-10-25T23:59:59Z**, load Accounts, then use the empty asset account's **Actions → Close**. The confirmation says it will add a close directive **on2026-10-25**.
2. Move the owned Date to **2026-10-26T00:00:01Z** while the confirmation stays open. Immediately before activation, its text still offers October25.
3. Focus **Close Account**, press Enter and hold BulkEntries before transport. The prepared CLOSE date is **2026-10-25**, agreeing with the text the user acted on.
4. The mutation's loading render nevertheless changes the busy confirmation to **on2026-10-26**, while the held request still contains October25. The action is disabled. Abort it, then Cancel without writing anything.

Both widths and an independent fresh narrow repeat reproduce this sequence; the narrow busy-confirmation screenshot was visually inspected. In each context, same-day opening/submission keeps both copy and payload on October25. A fresh opening on October26 correctly uses October26 in both. Preserve these controls: fixing the pending copy must not freeze every later opening to an earlier day.

Three retained fresh native contexts contain three cases each, three explicit partial account reads and nine prepared CLOSE requests, all aborted before transport. Real file content, git SHA, byte size, last commit and zero ledger errors remain unchanged. There are no hosted writes or page exceptions; console errors are the expected aborted-resource messages. An earlier unknown-balance account correctly lacked Close and is excluded. Those four contexts and one separate unmocked asset-observation context close, leaving the owned root context.

## Cause and bounded repair

`dashboard/src/features/ledger-data/accounts/close-account-dialog.tsx:47` computes `closeDate = format(new Date(), "yyyy-MM-dd")` on every render. `handleConfirm` at:55–70 prepares the mutation using the date captured by the render whose button was activated. The `useMutation` loading update renders the component again; its description at:109–114 reads a newly computed date, while the already-prepared request retains the captured one. The clock change is correct; the two parts of one pending action use different date snapshots.

Keep the date shown for an in-flight submission tied to that submission's actual prepared date. Preserve the offered date/request relationship and the existing fresh-opening/current-day behavior; let ordinary failure recovery remain truthful about the next available action. Keep canonical local civil dates, account identity, pending duplicate refusal, error feedback and dialog-closing focus. No global clock, timer, storage feature, API or dependency change is needed.

Acceptance: with the real CloseAccountDialog and mutation boundary, open before midnight, move Date past midnight, activate and hold the request; the busy text's date must equal the prepared input date throughout that attempt. Retain the same-day and fresh-next-day controls above, plus failure/retry and dismissal behavior. Repeat both widths and run dashboard gates when implementing. Successful hosted closure, non-UTC/DST transitions, other engines and repaired code remain unverified.
