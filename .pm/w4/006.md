# Merchant detail rows don't add up to the merchant total — negative entries render unsigned

**Severity:** major. **Estimate:** 35–50 minutes. Owner: mobile. A2/A3: Merchants is a drill-down whose whole promise is that the rows explain the total, and on a public example ledger they visibly don't.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, public `open_ledger/alphabet`. Report-only QA; no ledger mutation, and the "Mark as recurring" switch was left off.

## Repro

1. Open `beancount:///ledger/open_ledger/alphabet`, terminate and relaunch the app.
2. Ledger drawer (hamburger) → **Merchants** → tap **Q1 2026 Revenue** (5th row, `Mar 31, 2026`).
3. Header reads `Q1 2026 Revenue`, `7 transactions`, **$109,896,000,000.00**, `Mar 31, 2026 – Mar 31, 2026`.
4. The seven rows under `March 31, 2026` read, top to bottom:
   `$180,000,000.00` (no sign, neutral), `+$411,000,000.00`, `+$20,028,000,000.00`, `+$12,384,000,000.00`, `+$6,971,000,000.00`, `+$9,883,000,000.00`, `+$60,399,000,000.00`.
5. Add the visible row amounts: **$110,256,000,000.00**. The header says **$109,896,000,000.00**. The gap is `$360,000,000.00` — exactly twice the first row.
6. Tap the first row. Its detail hero reads **-$180,000,000.00**, narration `Hedging losses`, with Money flow `FROM Assets:Cu…uivalents -$180,000,000.00` / `TO Income:He…ns-Losses +$180,000,000.00`.
7. Relaunch and repeat steps 2–5. The same header, the same unsigned row, the same gap.

**Expected:** the row for a negative entry shows that it is negative, and the rows the screen displays reconcile with the total the same screen displays.
**Actual:** the only negative entry in the set renders as an unsigned magnitude indistinguishable from the six positive ones, so the rows over-count the total by twice that entry, and nothing on screen explains the discrepancy.

## Root cause

`mobile/src/screens/transactions-screen/entry-row/index.tsx:143-152` renders `amountStr` with a `+` prefix and the positive color only when `isPositive` (`value > 0`, line 108); every other value falls through to `styles.amountNeutral` with **no sign**. `amountStr` is `EntryAmount.text`, which `formatAmount` (`src/screens/transactions-screen/utils/transaction-display-utils.ts:49`) produced through `Math.abs(value)`. So a negative entry and a positive one of the same magnitude render identically apart from color, and the sign the selector correctly computed is discarded at the row.

The header total is correct: `merchant-detail-screen.tsx:470` renders `stats.totalsByCurrency`, which `buildMerchantCurrencyTotalsBql` (`selectors/merchant-stats.ts:48-55`) gets from `SELECT currency, sum(number) … WHERE payee = … AND (account ~ '^Expenses' OR account ~ '^Income')` — a **signed** sum. The transaction detail hero is correct too: `transaction-detail-screen.tsx:412` re-applies `-` when `hero.isPositive === false`. The row is the only surface in the chain that loses the sign, which is why it disagrees with both its own header and the detail it opens.

## Fix

In `EntryRow`, render the sign for negative amounts — `` `-${amountStr}` `` when `amount.value < 0` — so the row agrees with the detail hero it navigates to. Keep the existing color mapping (`amountPositive` for credits, `amountNeutral` otherwise) and keep zero unsigned. `formatAmount` stays unsigned and shared; the sign belongs at the presentation site, as it already does in the detail screen. Do not fix this by taking the absolute value of the merchant total instead — that would make the total agree with a set of rows that are themselves wrong.

This changes every `EntryRow` surface, and that is the point: today a `-$102.00` expense shows as `$102.00` in the list and `-$102.00` on its detail. If the team wants list expenses to stay unsigned as a deliberate convention, the alternative is to keep the row unsigned **and** make the merchant header render the same unsigned convention plus an explicit "includes N negative entries" affordance — but state that choice in the code, because nothing documents it today and no test asserts it.

**Acceptance:** on a fresh iPhone 17e launch, `open_ledger/alphabet` → Merchants → `Q1 2026 Revenue` shows `-$180,000,000.00` on the first row, and the seven visible rows sum to the displayed `$109,896,000,000.00`. The six positive rows keep their `+` and color. Add regression coverage over the row's presentation for a negative amount, a positive amount, a zero amount, and a non-USD commodity, asserting the rendered string — selector-level tests cannot catch a sign dropped in the component.

## Blast radius

`EntryRow` is rendered by `home-screen/components/recent-transactions-card.tsx:80`, `transactions-screen/transactions-screen.tsx:238`, `reports-screen/components/account-transactions-card.tsx:118`, and `merchant-detail-screen/merchant-detail-screen.tsx:575`. Reproduced on the merchant detail (reconciliation gap) and on the Transactions list (`Anthropic` → `$102.00` in the list vs `-$102.00` on its detail, `puncsky/example`). Not independently reproduced: the Reports account-transactions card. `account-detail-screen/components/account-entry-row.tsx` is a different component and already signs its amounts correctly.

## Adjacent states

Loading and empty states are unaffected — the unsigned row only appears on settled data. The header itself goes through `formatMoneyWithCurrency`, whose `groupThousands` takes `Math.abs` (`common/number-utils.ts`), and the BQL sum over credit-normal Income legs is negative — so this header displays the right magnitude only because the sign is stripped. That formatter is already owned by the open `w3/216.md`; it is called out here so a fix there does not accidentally flip this header to `-$109,896,000,000.00` while the rows stay unsigned. Not exercised: Android, VoiceOver speech of the row amount, enlarged Dynamic Type, and dark mode.

**Header sign-stripping confirmed — this was "traced but not independently reproduced" and now is reproduced**, on a second ledger (`puncsky/example`), with the exact query the app issues:

| merchant | kind | `sum(number)` over Expenses/Income legs | header shows |
| --- | --- | --- | --- |
| `Hoogle` | employer (income) | **`USD -182014.14`**, `IRAUSD 54500.00`, **`VACHR -360`** | `$182,014.14`, `54,500.00 IRAUSD`, `360.00 VACHR` |
| `Cafe Modagor` | restaurant (expense) | `USD 1536.16` | `$1,536.16` |

So money **received from** an employer and money **spent at** a restaurant render as the same bare positive figure in the same style — the header cannot express direction at all. The sign loss is not USD-specific: `VACHR -360` renders `360.00 VACHR` through the same formatter. Note the mismatch is internal to one file — `selectors/merchant-stats.ts:45-46` documents the query as producing "Per-currency **signed** totals", and `merchant-detail-screen.tsx:470` then passes them to a formatter whose own doc comment says it is "An **unsigned** money string … where the sign is not shown", with no comment at the call site reconciling the two. Whichever way the fix goes, one of those two comments is currently wrong.

The rows on those same two screens *do* carry direction (Hoogle's rows are green `+$2,550.60`; Cafe Modagor's are neutral `$34.71`), so header and rows disagree about whether direction is expressible — which is the same inconsistency this note reports, seen from the other side.

Also now exercised: a merchant carrying **both** commodity kinds. `Hoogle` nets Income legs in three currencies at once, and the per-currency split handles that correctly — it is only the sign that is lost.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for merchant totals, reconcile, unsigned, negative/minus sign, and `EntryRow`. `w3/216.md` (open) is the Reports `CategoryBreakdown` losing signs inside `formatMoneyWithCurrency` — a different component, a different formatter, and a different fix site; the two are related in theme only and this one is independently evidenced above. `w3/done/109.md` is crypto-scale rounding, fixed. `w4/004.md` (filed this session) is the zero-net transfer in `selectTransactionAmount` — that selector produces a correct signed value here, so the two do not share a cause. `git log -S` on the entry-row amount rendering shows no prior sign repair. Not deployment lag.
