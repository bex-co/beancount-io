# Keep cached Activity cards when returning to Dashboard cannot refresh them

**Severity:** minor. **Estimate:** 40–55 minutes. **Owner:** dashboard. **A2:** a failed background update should leave already loaded commit links available, with an explicit refresh retry.

## Reproduction and controls

Production `https://beancount.io`,2026-10-22; authenticated QA, isolated owned headless Chromium155.0.8059.85, English/light. Fresh390×844 and1440×1000 reproduce independently. All feed/commit content and successful reads are real; only the selected offset0 refresh read is held and then aborted before transport. No feed item contents, private destinations or account identity are included in this report.

1. Open Dashboard `/ledger`; wait for ten Activity articles and their ten Changes links. Open the first Changes link natively and wait for its actual Commit destination to settle.
2. Before browser Back, hold only GetFeed with `source:"LEDGER_RSS",offset:0,limit:10,locale:"en"`. Back to Dashboard displays **ten cached cards and ten Changes links while the refresh is pending**, at both widths.
3. Abort that refresh. Activity becomes **Failed to load feed / Retry**, with **zero articles and zero Changes links**. Existing content disappears even though it was available moments earlier.
4. In a second narrow repeat, inspect the real existing Apollo observable read-only: before/pending/failure/recovered all contain `data.getFeed.items.length=10`, with a complete ten-item cache. On failure, loading=false, networkStatus=8 and error=true. The page discards available data; this is not an empty feed or a cache eviction.
5. Let the next read through and use Retry. Genuine HTTP200 offset0 responses have ten items and no GraphQL errors; cards and links return. Recovery was checked after the actual response settled, not just when cached cards first reappeared.

Fresh desktop no-data control: abort the first feed read before any feed result is loaded. The existing terminal Failed to load feed/Retry with zero cards is appropriate; allowing Retry restores ten. Keep that behavior. Healthy Changes/Back and successful revalidation remain usable. All retained runs have zero mutation attempts, route errors and page exceptions. The failure is explicitly injected, not a claimed production outage.

## Cause and bounded repair

`dashboard/src/features/ledger-list/components/activity-feed.tsx:58–73` deliberately uses cache-and-network so returning to Dashboard refreshes activity. Its loading branch at:112 preserves data, but the error branch at:137 unconditionally returns the terminal error view whenever error exists, even with the ten cached items still present. The real query-state diagnostic above confirms the rendered boundary.

Use a terminal error view only when no usable feed data exists. Keep cached cards mounted/readable on revalidation failure and show localized, accessible refresh-failure feedback with an in-place retry for this same offset0 query. Keep the feedback honest about stale content and preserve retry focus/busy state. Do not silently hide the failure, replace retained cards with a spinner, reload the document or refetch unrelated dashboard sections. Preserve initial loading/no-data error/empty states, locale lifetime, actual query variables, Show More pagination and the completed overlap dedupe. No API, dependency or backend change is needed.

Acceptance: drive a real Apollo cache-and-network ActivityFeed through a successful ten-item load, route leave/return, held replacement read, failure and successful retry. Assert cached card/link nodes remain through the failed refresh and useful retry feedback appears; the successful read clears it. Keep the no-data first-read error/retry and existing pagination/overlap/locale regressions, then verify both widths and dashboard gates. Empty cached feeds, other locales/engines and the repaired deployment remain unverified.
