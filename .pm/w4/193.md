# Respect read-only ledger access before starting Smart Import

Severity: **minor** — a reader can prepare an import the ledger does not permit. This is a misleading write workflow, not evidence of an authorization bypass.

Estimate: **45–60 minutes**, dashboard only. A2 — newcomers exploring a public example should see its read-only state before spending time configuring an import.

## Reproduce

Production, 2026-10-08 America/Los_Angeles; QA-owned headless Chromium with an isolated context, English/light, initially 1440×1000 and independently repeated at 390×1000. Source inspected at main `96aa0048`; production loaded `main-GcCTaQbi.js`. The deployed commit is unknown and is not assumed to match local HEAD. Browser API origin is `https://beancount.io/api-gateway/`.

1. Sign in as an ordinary account that can read, but cannot write, `open_ledger/example`.
2. Open `/ledger/open_ledger/example/import` directly.
3. Select this synthetic CSV; parsing is local:

   ```csv
   Date,Payee,Description,Amount
   2026-10-08,QA Synthetic,Preview only,-1.00
   ```

4. Click **Continue to Configure**. Observe enabled **Import 1 Transaction** and **AI Fill**, with account-mapping controls and no read-only explanation. Do not submit or invoke AI Fill.
5. Reload and repeat. The same state occurs at both viewport widths.

Expected: resolve ledger write access before offering a workflow that promises to add transactions. A denied reader gets an accessible read-only explanation and useful read navigation; upload/configuration/submission and AI Fill are unavailable. Pending or failed access must not provisionally expose write controls.

Actual: the direct route renders the full import wizard and enabled write controls regardless of access. The missing-target-account alert concerns form validation and never explains that this user cannot write this ledger.

## Evidence and control

The authenticated GraphQL read returns HTTP 200:

```json
{"data":{"getLedger":{"permissions":{"pull":true,"push":false,"admin":false}}}}
```

Both fresh repeats report `importEnabled: true` and `aiEnabled: true`. No browser exception or failed HTTP request occurred. A browser request guard blocked mutations if attempted; none were attempted by the preview/configuration checks. No uploaded server asset, transaction, or test resource was created.

Working control: `/ledger/open_ledger/example/journal` exposes no Add Entry/Transaction action for this account. `features/journal/pages/journal-page.tsx:73,273,339` uses `useLedgerPermission` to guard both its action and its new-entry dialog.

Verified local evidence under `dashboard/tmp/qa-20261008-loop/`: `import-readonly-1440.txt`, `import-readonly-390.txt`, corresponding `.png` screenshots, and `import-readonly-results.json`. These ignored artifacts supplement the public text reproducer and contain only the public example plus the synthetic row.

## Cause and repair

- `dashboard/src/features/importer/pages/import-page.tsx:18,37` reads the ledger display name and mounts `ImportWorkflowContainer` unconditionally. The route wrapper has no write gate.
- `components/import-workflow-container.tsx:31,58` mounts workflow/submit hooks and configuration without an access check.
- `components/steps/configure/transaction-config-form.tsx:282–284` disables Import only for zero selected rows or an in-progress submission.
- `hooks/use-import-submit.ts:66` sends `BulkEntriesDocument` without a client permission guard. This write was source-traced only; no live submission was sent.
- Reuse the existing `common/hooks/use-ledger-permission.ts` semantics (`permissions.push || permissions.admin` for an authenticated user). Guard the page before mounting the interactive workflow and preserve an explicit non-writing state while access is unresolved or fails. Review the submit boundary so a permission change cannot leave a previously mounted workflow actionable.

Blast radius: the route and page are the only application callers of this workflow container; covers direct links and navigation into this ledger's Import route. Receipt's separate direct route also renders an upload control for this reader, but its later workflow was not exercised and is not included as a proven submission defect here. No backend/API contract change or cross-package import is required by this finding. Server authorization behavior is unverified by this run and must remain intact.

Acceptance: a rendered read-only route cannot enter configuration or invoke import/AI operations; write-authorized users retain CSV preview/configuration and normal submission. Cover loading, access-read failure, permission loss and a write-authorized control with meaningful behavior assertions. Recheck both viewport widths and run the dashboard's normal gates when implementing.

Dedupe: searched all `.pm` states and open milestones for import/receipt combined with permission, read-only, public, wizard and non-owner terms. The mobile permission work in `w4/done/m4` concerns a different client; importer draft/preview repairs do not establish dashboard write access. Targeted history of the import page/container and `git log -S useLedgerPermission` show no current importer guard. This is not a source fix already on main awaiting deployment.

Unverified: actual import rejection/success, AI Fill, server asset uploads, anonymous import, permission changes during a live wizard, screen readers, and native file dialogs. No product code was changed.
