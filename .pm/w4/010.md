# Capitalize the account picker's "Create" prefill so the form it opens is valid

**Severity:** minor. **Estimate:** 30–40 minutes. Owner: mobile. A2: opening your first account is an onboarding step, and the app currently offers an action it already knows it will reject.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA — **no account was created**; both forms were dismissed with Back and Home is unchanged at `$106,723.05`.

## Repro

1. Terminate and relaunch the app with `puncsky/example` selected. Header **+** (Quick Add) → **Enter new transaction** → tap the first posting's account row to open **Account Picker**.
2. Tap the search field and type `groceryboxw` — all lowercase, which is what search invites: typing `vanguard` earlier matched `Assets:US:Vanguard`, `…:Cash`, `…:RGAGX`, `…:VBMPX`, so the field is case-insensitive.
3. No account matches. The list shows `No matching accounts` and a green **Create "groceryboxw"** row.
4. Tap it. **Open Account** opens with root `Assets:` and name `groceryboxw`, and immediately shows the red error **"Each account component must start with an uppercase letter or a number."** with **Done** disabled.

**Working control, same session:** back out, clear the search, type `Groceryboxw` (identical except the leading capital), tap **Create "Groceryboxw"**. Open Account opens with **no error** and **Done enabled**.

**Expected:** the affirmative "Create X" action leads to a form that can be submitted, or at minimum does not open pre-failed.
**Actual:** every lowercase-led query — the natural thing to type into a case-insensitive search — lands on an invalid form the user must edit before the action they just chose can proceed.

## Root cause

`mobile/src/screens/account-picker-screen/account-picker-screen.tsx:435-450` — `onCreate` calls `pushOpenAccount(router, { prefill: trimmedQuery, prefillRoot: … })`, passing the raw search text through unchanged. The destination validates it with `src/screens/open-account-screen/account-name.ts:100-101`: `if (!/^[A-Z]/.test(components[0])) return { ok: false, reason: "componentMustStartUppercase" }`, mapped to the visible string at `open-account-screen.tsx:54` → `openAccountUppercaseComponent` (`translations/en.ts:280`). The picker therefore hands the form a value its own validator is guaranteed to reject.

Note the validator's deliberate scope (`account-name.ts:63-67`): the initial-character rule is not a bare `\p{Lu}` test, because Han and Kana are `\p{Lo}` and have no distinct uppercase form. Any fix has to respect that — this is about the Latin case the picker can safely fix, not about tightening the grammar.

## Fix

In `onCreate`, normalize the prefill before pushing: upper-case the first character of each `:`-separated component **only when that character has a distinct uppercase form and the component is Latin-led**, leaving Han/Kana/other caseless scripts untouched so the existing `account-name.ts` allowances still hold. Leave the rest of the name exactly as typed — do not title-case the whole string, and do not strip or substitute characters the validator would reject for other reasons (those must still surface as errors on the form). The user can still edit the prefilled name; this only changes where the form starts.

Do not fix this by relaxing `account-name.ts` — the uppercase rule is Beancount's, and the form's validation must keep rejecting a genuinely invalid name typed by hand.

**Acceptance:** on a fresh iPhone 17e launch, searching `groceryboxw` and tapping Create opens Open Account with `Groceryboxw`, no error, Done enabled; `Groceryboxw` still behaves as it does today; a caseless-script query (e.g. Japanese) is passed through unchanged and still validates exactly as it does now; a query that is invalid for a different reason (leading digit-and-symbol mix, empty after trim) still shows its own error. Add regression coverage over the prefill normalization for: lowercase Latin, already-capitalized Latin, a multi-component `foo:bar` query, a caseless-script query, and a whitespace-only query.

## Blast radius

`onCreate` has one caller — the `account-picker-create-row` in the same screen — and one destination, `pushOpenAccount`. The create row appears in every account picker: transaction postings (reproduced), and the `to`/`from` variants which choose `Expenses` vs `Assets` as `prefillRoot` (`account-picker-screen.tsx:443-445`); only the `Assets`-rooted source picker was exercised. `canWrite` correctly gates `onCreate` (lines 436-440), and the row does not appear on a read-only ledger. Not exercised: Android, VoiceOver, dark mode, enlarged Dynamic Type, and actually completing the creation (that is a production write and was deliberately not performed).

## Adjacent states

The picker itself behaves correctly elsewhere: search is case-insensitive and matches parents as well as leaves; the caller's current account is checkmarked; the root chips (`All/Assets/Liabilities/Income/Expenses/…`) are hidden while searching, which `account-picker-screen.tsx:489` does deliberately because search spans all roots; `No matching accounts` is an honest empty state. Open Account's `Currency USD` and `Open date 2026-09-13` defaults are correct, and Done is properly disabled while invalid.
