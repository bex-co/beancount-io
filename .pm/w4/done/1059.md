## Cause and repair

The [Unicode currency-symbol chart](https://www.unicode.org/charts/PDF/U20A0.pdf) identifies U+20BF as **BITCOIN SIGN**. The runtime also classifies it as Unicode Sc. `dashboard/src/features/importer/utils/csv-validator.ts` uses that broad Sc category in `splitAmountSign`, accepting/removing this symbol before normalization, but its finite `SYMBOL_CURRENCIES` table omits ₿. Consequently `amountCurrencySymbols('-₿4.50')` returns an empty array and `lib/import-currency-conflicts.ts` cannot distinguish USD from BTC. The exact original token is retained; this is not a CSV decoding failure.

Executing the actual current parser and guard offline confirms both Bitcoin cases return valid amount−4.5, exact decimal **-4.50**, and no conflicts. The euro/USD control returns its expected EUR conflict; euro/EUR, deselected euro/USD and the ambiguous-dollar control stay clear. `transaction-config-form.tsx:handleSubmit` checks that same conflict list before mapping each selected row's normalized decimal to the global Currency. Native submission remains unverified.

The same finite table omits ₭ and ៛. Fresh execution of the actual parser and guard accepts exact decimals **-1250.00 / -2500.00**, but returns no symbol evidence or conflict for either USD or the matching LAK/KHR choice. The parser strips both symbols, then the existing Configure mapping and submit hook write the chosen global Currency. Four whole served modules, offline execution and native prepared batches agree. Independent Beancount3.2.3 controls accept both balanced LAK/KHR transactions without errors; this is not a request to invent currency codes.

Include **₿→BTC, ₭→LAK and ៛→KHR** in the source-unit consent policy so USD cannot silently replace those explicit units. Preserve matching behavior. If additional Bitcoin aliases are intended, establish their policy explicitly rather than treating every arbitrary custom commodity as equivalent. No alias acceptance claim was established by this QA. Retain ambiguous $/¥ and shared £/₩ exceptions, selected-row scoping, all-symbol checks, exact normalization and existing draft/pending behavior. Keep this dashboard change independent of the CLI; no FX, dependency, backend/API or cross-package import is needed.

Acceptance: selected ₿, ₭ and ៛ amounts under USD expose actionable source-unit guidance and cannot prepare an import; choosing respectively BTC, LAK and KHR clears that conflict. Deselecting the row clears it, and euro/matching/ambiguous controls remain correct. Cover the native two-fiat-row preparation case, real parser/guard and rendered Configure when implementing, then run dashboard gates. QA authored no product fix or formal tests.
