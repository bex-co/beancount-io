## Objective

Repair the independently reproduced registration email, password and confirmation fields.

## Context

See [FINDINGS.md](./FINDINGS.md) and the milestone DoD. This schedules dashboard work; it does not authorize real credential submissions, recovery emails or account creation.

## Steps

Apply the field/error pattern to the three affected controls. Preserve the already-correct username-hint and username-error behavior, generated/hidden Username paths, optional names, confirmation validation and safe next navigation. Audit the three consent wrappers for prop compatibility without claiming live signed-in coverage.

## Files

dashboard/src/features/auth/components/register-form/index.tsx; existing registration tests and source-traced consent consumers

## Acceptance criteria

- [x] Empty registration submission exposes all three current errors accessibly; correcting a field clears only its error; Username hint/error and hidden mode remain correct; no account is created.

## Out of scope

Authentication policy/schema changes, reset-token workflows, new dependencies, production mutations and unrelated form redesign.

## Implementation and verification

Completed 2026-09-19. Registration's email, password and confirmation inputs now carry `aria-invalid` and a conditional `aria-describedby`, and their error paragraphs carry `id="email-error"`, `id="password-error"` and `id="confirmPassword-error"` with `role="alert"` — the same treatment t001 applied to sign-in and recovery, and the same pattern Username already used in this file, so no new abstraction was introduced to carry three attributes.

Username's existing behaviour is preserved exactly: its `aria-describedby` still starts as the persistent `username-hint` and appends `username-error` only while that error exists, so the public-name hint survives a failed submit rather than being replaced by the error.

Verified by rendering the real `RegisterForm`: before submission none of the three fields is marked invalid and Username already points at its hint. After activating Create account on an empty form, all three fields read `aria-invalid="true"` and each `aria-describedby` resolves to a `role="alert"` paragraph carrying the actual current message; the submit handler is never invoked, so no registration mutation fires and no account or email is created. Username still points at its hint. Typing a valid address clears both attributes on the email field with no stale association. The scaffolding was removed after confirming the behaviour; t005 owns the durable suite.

Validation rules, the generated and hidden username behaviour, optional first/last name semantics, the password confirmation rule, visibility toggles, submit blocking and safe next links are untouched, and no dependency was added.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn build` and `yarn test` all pass at 375 files and 4,223 tests with the one pre-existing skip. Actual screen-reader speech and the consent wrappers' runtime flows remain unverified, as FINDINGS records.
