## Simplify review

Completed 2026-09-19. Ran `/simplify` over the three forms this milestone changed. The efficiency angle was verified directly rather than dispatched, because the whole diff is JSX attributes and markup — filtering it for anything that is not an attribute, an error paragraph or its closing tag leaves nothing, so there is no new computation, state, effect, import or dependency to weigh. The reuse, simplification and altitude angles were reviewed in depth.

**Fixed.** `firstName` and `lastName` in `register-form/index.tsx` were left unassociated while the four other fields in the same file were repaired — no `aria-invalid`, no `aria-describedby`, and error paragraphs with no `id` or `role`. Both reviews flagged it independently as the clearest inconsistency the milestone would otherwise ship: a reader who trips the 50-character limit hears nothing, and the next reader of the file cannot tell whether the omission was deliberate scoping or oversight. Both now follow the same pattern. They sit outside the milestone's definition of done, which names only email, password and confirmation, but completing the file they live in is the smaller and safer change than leaving four fields done and two not.

**Confirmed correct, so deliberately unchanged.** The `errors.x ? true : undefined` shape is load-bearing rather than stylistic: `common/components/ui/input.tsx:13` styles `aria-invalid:border-destructive`, which matches `[aria-invalid="true"]` only, so the more obvious `aria-invalid={!!errors.x}` would emit `aria-invalid="false"` on every valid field. The literal error ids are safe across every consumer — `login-page`, `forgot-password-page`, the register flow's early return, and the OAuth, mobile and identity consent pages, which are all step machines whose login, forgot-password and register branches are mutually exclusive — and they add no constraint the pre-existing `id="email"` / `id="password"` inputs did not already carry.

**Checked and dismissed.** One review noted that `register-form` lacks the `noValidate` that `login-form` has, so a malformed `type="email"` value could let the browser's native bubble preempt the new announcement. Exercised live rather than assumed: submitting `not-an-email` with valid passwords still yields `aria-invalid="true"`, `aria-describedby="email-error"` and the alert "Please enter a valid email address". The inconsistency is real but does not reduce what this milestone delivers, and adding `noValidate` would change submission behaviour outside the definition of done. Recorded, not changed. The singular `getByRole("alert")` in `register-form.test.tsx:83` is likewise latent rather than broken — that test leaves every other field valid, so exactly one alert exists — and rewriting a passing assertion that already checks the right thing is churn.

**Recorded as follow-up, because it is the right depth but cannot be done safely today.** Both reviews independently found that `common/components/ui/form.tsx` already emits `aria-invalid` and `aria-describedby` automatically and is used by roughly a dozen feature forms, making `auth` the sole outlier that hand-rolls the attributes. Migrating auth onto it is the structural fix. It cannot land as part of this milestone: `FormControl` always includes `formDescriptionId` in `aria-describedby` even when no description is rendered, which would introduce a dangling reference, and `FormMessage` sets no `role="alert"`, so a straight swap would lose the announcement this milestone just added. The primitive has to be repaired first. That, the remaining unassociated auth fields, the importer cluster and a repo-wide guard following the existing `src/test/` scanners are captured in [140](../../140.md).

Gates from `dashboard/` after the fix: `yarn format:check`, `yarn lint`, `yarn build` and `yarn test` all pass at 375 files and 4,223 tests with the one pre-existing skip.
