# Retry a failed initial Version History read in place

**Severity:** minor follow-up to [M50](./done/m50/README.md)'s read-recovery contract. **Estimate:** 45–60 minutes, dashboard. **A2:** a reader should be able to recover file history from the displayed connection error without reloading the document.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-23; dedicated QA owner of the designated synthetic ledger, isolated headless Chromium156.0.8078.47, English/UTC/light, fresh1440×1000 and390×844 contexts. Only the browser's initial ListCommits read is aborted; no server outage or fabricated response is claimed.

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/files/tree/main?lang=en`. The Files directory and main.bean are visible. Focus **Version History** and press Enter.
2. Abort the first ListCommits with `ledgerId:<that-ledger>,branch:main,page:1,limit:30`. The destination `/commits` settles with **Connection problem. Please check your internet connection and try again.**, **zero Try Again/Retry buttons** and no history navigation/list. Both fresh widths reproduce. At narrow width this initial failure is inline; the history drawer is used only after a commit is selected.
3. Remove the interceptor and reload. Genuine HTTP200 ListCommits reads return30 distinct SHAs. The existing first-load behavior selects the newest commit, and a genuine GetCommitDetails returns that same SHA with no GraphQL errors. The desktop list and reopened narrow **Version History** drawer each contain30 links with the selected commit marked aria-current=page.
4. Close the narrow drawer normally and use browser Back. Both cases return to the original Files URL, with main.bean visible again. Files and commit-detail reads are usable; the unrecoverable-in-place state belongs to the initial list observer.

Reload is a verified workaround, not the requested repair. Its normal route/observer transitions produce two successful page1 ListCommits reads and one GetCommitDetails in each retained case; this report does not claim only one recovery request. Each failed case has exactly one aborted ListCommits with the recorded variables. Zero mutation attempts, hosted writes, route errors or page exceptions; no commit/file content or credentials are published in this report.

## Cause and bounded repair

`dashboard/src/features/git/commits/components/commits-split-view.tsx:79–96` owns the ListCommits observer but destructures data/loading/error/fetchMore without refetch. Its commitsList renderer passes the error into CommitsList. `components/commits-list.tsx:42–48` returns a bare Alert/AlertDescription for that error. The existing continuation control only retries a later page through onLoadMore; it cannot recover the missing first page.

Keep this observer's refetch and use the existing scoped query-retry lifecycle. Pass an initial-error retry and busy state through CommitsList, retaining its failure view/action while a retry is pending and returning focus after another rejection. Retry `branch:main,page:1,limit:30` for the current ledger. Do **not** wire the initial action to loadOlder/fetchMore, which would start at page2, or use document reload/router invalidation to repeat unrelated reads.

Preserve the loaded-page/cursor/selection contract from [246](./done/246.md), its truthful detail-pending state, normal newest-commit auto-selection after a first successful list, successful-empty wording, SHA deduplication, ledger-switch/abandoned-request guards and working continuation focus. A list retry must not re-read or discard an independently healthy selected diff. The same list is rendered in the wide aside and the narrow history drawer: target the action the reader actually activated, and do not reopen a dismissed drawer or focus a hidden counterpart after a late failure. No API, backend or dependency change is needed.

Acceptance: actual owner/query integration covers cold first-page failure → keyboard retry with retained busy error/action → repeated failure/focus handback → successful real-shaped list and successful empty list. Verify exact variables, repeat activation, both responsive presentations, closing the drawer/leaving the ledger during a retry, existing loaded-page selection and later-page retry behavior. Repeat the native Files/History/Back control and run dashboard gates. Those pending-retry/abandonment states are implementation regression scope, not already exercised live: the current initial-error view has no action to activate.

**Resolved 2026-10-23** — The Version History owner (`git/commits/components/commits-split-view.tsx`) now keeps the ListCommits `refetch` and runs it through `useQueryRetry`. Try Again re-reads this ledger's `branch:main,page:1,limit:30`, never page 2 through `fetchMore`, and never reloads the document or invalidates the router. `CommitsList` shows the localized error with that Try Again, busy while the retry runs, so a second activation sends nothing. Another rejection returns focus to the button actually pressed. A history drawer closed during a retry stays closed, focus stays on its Version History trigger, and the selected commit's detail is never re-read. Loaded-page cursor and selection (246), newest-commit auto-selection after a first good list, empty wording, SHA deduplication, unmount guards and the continuation control are unchanged.

`commits-initial-retry.test.tsx` runs the real split view, router and Apollo observer. It covers:
- a cold failure, then a keyboard retry with the busy error and action retained and a second Enter sending nothing;
- another failure that keeps focus on Try Again;
- recovery to the list with the newest commit auto-selected, with every request equal to the first page;
- a retried empty history saying "No commits";
- a direct commit page whose drawer is closed during a pending retry: it stays closed, the trigger keeps focus, and the detail is unchanged.
