# Activity “Show More” silently ignores a failed page read

Severity: **minor**. Estimate: **30–45 minutes**, dashboard only. A2 — a reader loading more ledger activity should know that a read failed and can retry, rather than seeing a button apparently do nothing.

## Reproduction and controls

Authenticated dashboard `/ledger`, fresh page loads at 1440×1000 and 390×1000. Wait for the initial ten activity cards and **Show More** to settle. In the owned headless browser, abort only the next GraphQL `GetFeed` request whose variables have `offset: 10`. This is a **QA-injected network failure**, not a reported production outage. No ledger/account writes or activity-item details were captured.

Click **Show More**. Exactly one matching read is aborted at each width. Ten activity cards remain; **Show More** becomes enabled again. There is no visible `Failed to load feed` message, no Retry button, and no explanation of the failure. Browser errors include the injected resource `ERR_FAILED` and `Failed to fetch`.

Remove the route guard and click the same button again. The real request still uses offset 10, and the list grows from 10 to 20 cards at both widths. Offset preservation and retry mechanics work; the defect is missing failure feedback and an unhandled rejected handler promise. Existing cards should remain available on failure.

Independent control: an injected `ListLedgers` read failure on the same dashboard shows `Failed to Load Ledgers` and Retry at both widths; removing that guard and choosing Retry restores the list without overflow. The missing feedback is specific to activity pagination.

## Cause and bounded repair

`dashboard/src/features/ledger-list/components/activity-feed.tsx:60–87`: `handleShowMore` awaits `fetchMore` in a `try/finally`, clears the busy state, and advances offset only on success. It has no catch or local page-error state. The component's initial-read `useQuery.error` branch at lines 111–127 does not become active for this failed `fetchMore`, as the live reproduction demonstrates.

Catch the pagination rejection, preserve cards and offset, and show localized accessible failure guidance beside Show More. Reuse the existing localized feed-error text when appropriate; let Show More retry the failed page, and clear the page error after a successful retry. Keep initial-read error behavior and duplicate-click protection. No backend, credential policy, feed payload or other collection pagination changes are needed.

Acceptance: a failed offset-10 read retains the original ten cards and produces accessible visible failure guidance with a usable retry; a successful retry requests offset 10, appends exactly ten cards once, and clears the error. Exercise the actual asynchronous handler rejection and successful retry with meaningful component coverage; verify desktop/narrow behavior and run the dashboard's native checks when implementing.

Dedupe: searched all `.pm` states for activity-feed, handleShowMore, fetchMore, feed pagination/failure and Show More failure. `w4/done/m25/t003` covers translated wording, not rejected page reads. Other feed items concern authorization, avatars or managed price feeds. Source history attributes this handler to `a19044d1`; fetched main `b548b3be` still has the uncaught branch. Deployed full SHA is unverified; live behavior and current source agree.

Ignored reproduction scripts: `dashboard/tmp/qa-20261008-loop/feed-more-failure-repeat.js` records card counts, matching failure count, and successful retry offsets without item contents; `dashboard-list-error.js` records the working list-error control. No product fix is part of this filing.
