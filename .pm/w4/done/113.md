# Expose the actual highlighted filter suggestion to assistive technology

Severity: major. Estimate: 60 minutes. Package: dashboard. A2: keyboard and assistive-technology users can identify which report period Enter will apply.

Environment: production beancount.io, signed out, public example ledger, English/light, isolated headless Chromium149.0.7827.55; fresh390×844 and1440×1000 loads. Observed client main-BIr0jJni.js; exact deployment SHA unavailable. LocalHEAD26d54a9d, origin/main358ba4dc; no newer source repair identified.

Repro: open `/ledger/open_ledger/example/income-statement?lang=en` without a Time filter. At390 open Filters; at1440 use the inline header. Focus Time and press ArrowDown twice. The visible highlight is2016, DOM focus remains on Time, but2017 has `aria-selected=true` and2016 has `aria-selected=false`. Chromium's native accessibility tree reports those same selected states. The input has neither `aria-controls` nor `aria-activedescendant`; its native node has no corresponding relationship. Enter nevertheless applies `time=2016`. Both fresh widths repeat this exact mismatch.

Expected: the input references its own suggestions list and, while a suggestion is highlighted, that option; the visual highlight, accessible selected state and Enter target agree. The [WAI-ARIA combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) describes retaining DOM focus on the input while exposing the active option through aria-activedescendant. This finding verifies native browser metadata, not physical screen-reader speech.

Root: `dashboard/src/common/components/ui/combobox.tsx:132–170` maintains a custom highlightedIndex and uses it for Enter. Input at214–236 does not expose the list/active-option relationships. CommandItem at294–310 only applies CSS for that index and explicitly hides cmdk's competing selected styling. Installed cmdk1.1.1 owns a separate selected value and supplies its normal input relationships through Command.Input, but this component uses a separate plain Input outside Command. The two selection models diverge. This is integration behavior, not evidence that cmdk itself is defective.

Fix the shared Combobox with one coherent active-option state, stable per-instance list/option IDs and correct input relationships. Synchronize cmdk's selected state with the actual keyboard/pointer highlight, or use a suitable single listbox implementation without duplicating keyboard state. Do not merely add an active-descendant pointing at an option that still reports unselected. Clear obsolete references when filtering removes an option or the popup closes; preserve manual custom-value entry, pointer selection, form identity props, hierarchy indentation, popup sizing and the existing skipBlurCommitRef protection. Coordinate with095's separate Escape repair without expanding this into a global Command rewrite.

**Resolved 2026-09-19** — Reproduced against a local build at both widths: two
ArrowDowns on the Time filter highlighted 2016 and Enter applied `time=2016`,
while 2017 carried `aria-selected="true"` in the DOM and in Chromium's native
accessibility tree, and the input had neither `aria-controls` nor
`aria-activedescendant`.

The component already filters its own options (`shouldFilter={false}`) and owns
its own keyboard handling, so cmdk contributed nothing here but a second,
competing notion of which item is selected — which is exactly the divergence
this note traced. Rather than syncing two models, the suggestions are now a
plain listbox whose option ids, `aria-selected` and visible highlight all come
from the single `highlightedIndex` that Enter already used, and the input
points at its own list and at the active option while one is highlighted. Both
references clear when filtering removes every match and when the popup closes.
The first attempt — feeding cmdk a controlled `value` — was abandoned because
`CommandItem` overrides the `id` needed for `aria-activedescendant` and its
`onValueChange` fed back into the index; that is recorded here because it
rules out the smaller-looking fix.

Focus stays on the input throughout. Pointer selection, custom Enter values,
ordinary blur commits, the `skipBlurCommitRef` protection, the Escape repair
from `w4/095` (`d49766ee`), form identity props, hierarchy indentation and the
popover sizing are unchanged; the existing sizing test now selects the listbox
rather than `[cmdk-list]`, with its assertions intact.

Verified in a real browser at 1440px and 390px, 10/10: the active option, the
only `aria-selected` option, the visible highlight and the applied `time=2016`
all name 2016, and the native accessibility tree reports exactly one selected
option, `2016`. ArrowUp moves it to 2017, Escape drops both references, a
no-match filter leaves no active option, and with six comboboxes on the page
only the open one claims a relationship, resolving inside its own list. Pointer
selection still applies `time=2015` and a typed `2016-03` still commits.

Eight rendered cases in `ui/__tests__/combobox-active-option.test.tsx` cover
the same ground with a real focused input; seven fail without this change while
the pointer/custom-value control keeps passing. Gates from `dashboard/`:
`yarn format:check`, `yarn lint`, `yarn test` (400 files, 4482 passed, 1
pre-existing skip) and `yarn build` all pass. Other engines, actual screen
readers, loading/failure transitions and authenticated consumers remain
unverified. Shipped in `46a595a9` (`dashboard`).
