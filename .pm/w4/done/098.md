A2: visitors using landmark navigation should be able to locate registration, password-recovery and dashboard not-found content as they can the sign-in form. The repair remains a bounded page-shell markup change, approximately one hour including existing state fixtures.

**Resolved 2026-09-19** — Reproduced against a local build: `/auth/sign-up`,
`/auth/forgot-password`, the tokenless `/auth/reset-password` state and the
ledger not-found screen each exposed zero `main` elements and zero non-ignored
`main` landmarks in the native Chromium accessibility tree at 1440px and 390px,
while `/auth/login` exposed exactly one through `AuthPageLayout`.

Each standalone shell now marks its primary form or status as `main`:
`register.tsx` (whose promotional column became the complementary `aside` it
already was), `register-otp.tsx` (form and expired-session shells),
`forgot-password-page`, all five `reset-password-page` branches,
`root-route/not-found-page.tsx`, and the shared
`ledger-layout/ledger-layout-error.tsx` used by both `LedgerLayout` and
`LedgerRouteError`. Nothing was added inside `AuthPageLayout` consumers, no new
layout abstraction was introduced, and the desktop promotional layout,
headings, field associations, validation timing, pending/error/success content,
focus, continuation links, the HTTP 404, `noindex`, the error classification
and the retry are all unchanged.

Verified in a real browser, 13/13: sign-up, forgot password, the tokenless
reset state, the not-found screen and the ledger error state each expose
exactly one `main` in both the DOM and the native accessibility tree, with no
nesting and — for the non-`AuthPageLayout` pages — every visible actionable
control inside it. Sign-in still exposes exactly one, and a recovered ledger
overview does too. The ledger error state was reached the way this note
describes, by aborting only the browser's `GetLedger` reads and navigating from
the public profile, since a direct load is served by SSR.
