# Home reports "+1863.27%" when net worth crosses from negative to positive — percent change is undefined across a sign flip

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A3: this is the headline figure on the app's first screen, on a **public showcase ledger**. A percentage that reads as an eighteen-fold gain is describing a book that went from −76 to +1,347 — a real and good change, but not that one.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`, public `open_ledger/minimax` (operating currency **MUSD**). Report-only QA; no ledger mutation.

## Repro

1. Select `open_ledger/minimax` and let Home settle. The hero reads **Net Worth 1,346.68 MUSD**.
2. With the default **6M** pill, the change line reads:

   > **+3,994.87 MUSD (+150.85%)**

3. Tap **ALL**:

   > **+1,423.06 MUSD (+1863.27%)**

Both are internally consistent, which is what makes them worth reporting rather than dismissing as a glitch — the numbers give away the baseline:

| range | shown value | change | implied baseline | stated % | check |
| --- | --- | --- | --- | --- | --- |
| 6M | 1,346.68 | +3,994.87 | **−2,648.19** | +150.85% | 3994.87 ÷ 2648.19 = 1.5085 ✓ |
| ALL | 1,346.68 | +1,423.06 | **−76.38** | +1863.27% | 1423.06 ÷ 76.38 = 18.632 ✓ |

So in both cases the window **starts at a negative net worth and ends positive**, and the app divides the change by the absolute value of that negative start.

## Root cause

`src/common/d3/interactive-line-chart.tsx:356-358`:

```ts
const baseline = numbers[0] ?? 0;
const change = shownValue - baseline;
const changePct = baseline !== 0 ? (change / Math.abs(baseline)) * 100 : 0;
```

The `Math.abs` is **deliberate and half-right**: without it, a negative baseline would invert the sign, and a book recovering from −2,648 to +1,347 would be reported as a *decrease*. That would be worse. But taking the magnitude does not make the quantity meaningful — percent change is simply undefined when the start and end have opposite signs. There is no denominator that makes "how much did −76 grow to reach +1,347" a percentage.

`baseline !== 0` is the only guard, and it guards the wrong case: division by zero is handled, division by a *negative* is not.

The absolute change (`+3,994.87 MUSD`, `+1,423.06 MUSD`) is **correct and meaningful** in both rows. Only the parenthesised percentage is not.

## Fix

Suppress the percentage when it cannot be computed, rather than computing something:

```ts
const meaningfulPct = baseline > 0 && shownValue > 0;
const changeText = meaningfulPct
  ? `${formatSignedMoneyWithCurrency(change, currency, true)} (${change >= 0 ? "+" : ""}${changePct.toFixed(2)}%)`
  : formatSignedMoneyWithCurrency(change, currency, true);
```

An absolute change with no percentage is honest and still tells the user what happened. Note `baseline > 0` also subsumes the existing `baseline !== 0` check, so the zero case stops needing its own `0` percentage — which today renders a flat, false `(+0.00%)` whenever a window starts at exactly zero.

Two things **not** to do:

- Do not drop the `Math.abs` in place of this. That reintroduces the sign inversion it was added to prevent, and would make a recovery read as a loss.
- Do not substitute a different denominator (final value, midpoint, absolute mean). Each produces a number, none produces *percent change*, and inventing one here would be harder to spot than the current figure because it would look plausible.

Whether a suppressed percentage should show something in its place (an em dash, "n/a") is a copy decision; showing nothing is the safe default.

**Acceptance:** on `open_ledger/minimax`, Home's 6M and ALL rows show `+3,994.87 MUSD` and `+1,423.06 MUSD` with **no percentage**; a window that starts and ends positive (`open_ledger/alphabet`, any range) still shows its percentage unchanged — `+$225,215,000,000.00 (+54.23%)` today; a window starting at exactly zero shows no percentage rather than `(+0.00%)`; and a genuine decline between two positive values still shows a negative percentage. Add unit tests for the four sign combinations of `(baseline, shownValue)` — there is no test over `changePct` at all today, which is why both `Math.abs` and the zero case went unexamined.

## Adjacent states

- Three-decimal amounts (`357.997`) render without truncation or rounding to two.
- The absolute change matches the implied baseline exactly at both ranges, so the underlying series arithmetic is sound; only the ratio is wrong.

Two things checked and **not** filed. Beancount `pad`-generated entries appear in Recent Transactions as `(Padding inserted for B…` — they are real transactions and showing them is defensible; whether a synthetic directive belongs in a "recent activity" list is a product question, not a defect. ## Tooling note worth keeping

My first three taps on the range pills silently did nothing, and I nearly recorded "Home's range pills are unresponsive" as a finding. They are not. The coordinate rule in earlier notes — *logical = displayed × 0.4258* — applies to the **resized** screenshot (924 px wide), and I had been applying it after also scaling to the original 960 px, i.e. double-converting by a factor of 1.04. Large targets absorbed the error; a 40 pt pill did not. The correct mapping for this capture size is `logical = displayed × 0.4253` with **no** intermediate step. Worth adding beside the existing coordinate guidance in `mobile/CLAUDE.md`.

**Resolved 2026-09-14** in `fix(mobile): drop the percentage when a balance change has none`.

**The rule.** A new pure `changePercent(baseline, value)` (`src/common/d3/change-percent.ts`) returns null when no percentage means anything: a zero start, or a start and end on opposite sides of zero. Otherwise it divides by the baseline's magnitude, which gives:
- a liability improving from −1,000 to −500: +50%
- a positive balance falling: a negative percentage
- a balance reaching zero: −100%, or +100% from a negative start

`InteractiveLineChartD3`'s change row always shows the amount and adds the percentage only when there is one, so `open_ledger/minimax` reads `+3,994.87 MUSD` with no rate. The `Math.abs` sign-inversion guard is kept, as the note directed. Both chart consumers (the Home card and the account balance card) share the row.

**Tests.** `src/common/__tests__/change-percent.test.ts` covers every sign combination: positive pairs, negative pairs, sign flips and zero starts. It also checks, from the chart's source, that the row goes through `changePercent`. With the chart reverted, the source check fails. With the sign check removed, the sign-flip test fails. The mobile gate passes: `format:check`, `lint`, `typecheck`, and `test:unit` (1877 passed).

**Left to `w4/036`.** Which point the baseline is taken from. That note's `Assets:Bank:Mercury:Checking` repro still shows the first active month's change, now without the bogus rate.

**Not exercised.** The Home card on device.
