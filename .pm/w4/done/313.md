# Let an unlimited ledger allowance advance the creation wizard

**Severity:** minor, conditional client-contract defect. **Estimate:** 40–60 minutes, dashboard. **A2:** the creation wizard must accept the documented unlimited allowance instead of treating it as an exhausted negative cap.

2026-10-21, owned isolated headless Chromium155.0.8059.85, English/UTC. Deployed dashboard at https://beancount.io; **browser-local successful-response simulation**, not an actual Enterprise account or production subscription failure. Fresh1440×1000 and390×844 cases, plus another fresh desktop repeat, use the real Create Ledger dialog. No account, subscription, profile or ledger is changed.

## Reproduction and result

1. The real GetAllTierQuotas read returns HTTP200 with Enterprise maxLedgers=-1. Backend-v2's current create-ledger operation explicitly exempts this sentinel from its finite-cap comparison.
2. In a fresh authenticated browser context, intercept only GetCurrentUser. Obtain its genuine successful response and clone it, replacing tier with ENTERPRISE and limits.ledgersUsed/ledgersMax with0/-1. Keep the remaining schema/data intact. Block all mutations before transport.
3. Open `/ledger`, activate Create Ledger, and wait for the fixture response to render. The real dialog shows **Ledger Limit Reached**, **0 / -1 ledgers**, Step1of3 and a disabled **Next**. Starter template selection is otherwise normal. Both widths and a fresh desktop repeat reproduce; no creation request occurs.
4. Passing fresh desktop controls use the same interception with GROWTH and0/20: Next is enabled, and native Enter advances to Step2of3. With20/20, the limit warning and disabled Next are correct. Dismiss every dialog and close the contexts.

Expected: a known unlimited allowance does not exhaust at any nonnegative owned-ledger count. Creation can advance through its normal validation/review; finite caps continue to block at and above the cap. An unlimited indicator must not display a negative denominator or reached-limit warning.

The simulation proves the deployed client's handling of a valid documented wire value. It does not prove that a current customer holds Enterprise, that production assigns it today, or that an actual Enterprise create request fails. No server mutation was attempted.

## Cause and bounded repair

`dashboard/src/common/hooks/use-user-limits.ts:32–34` computes isAtLedgerLimit as `ledgersUsed >= ledgersMax`, so0>=-1 is true. Its sole production consumer, LedgerForm, disables Next and the final create submit on that boolean at:762/770. `common/components/limit-indicator.tsx` separately repeats `used >= max` and renders the raw max, explaining the false warning and negative denominator.

Honor the -1 unlimited sentinel in the hook's finite-cap predicate and the shared indicator. Reuse localized unlimited presentation or omit a finite-limit warning for unlimited allowances. Preserve finite below/exact/over-cap behavior, the intentional zero-cap policy, pending/error handling, ordinary wizard validation and server enforcement. No API, tier assignment, quota configuration, billing or dependency change is indicated.

Acceptance: exercise the real hook/form integration for unlimited allowances with0 and several owned ledgers; Next advances and review is reachable without sending a write. Keep finite below/exact/over-cap and zero controls. Verify the shared indicator never invents an exhausted unlimited quota. LimitIndicator also serves Collaborators settings: audit that binding and preserve its finite behavior, but this note claims no independent live collaborator failure. Run dashboard format:check, lint, test and build on implementation.
