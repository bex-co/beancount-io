## Objective

Repair the overview aggregation to retain direct balances and descendants once per unit at every supported depth. See FINDINGS.md for the exact tax reconciliation.

See [FINDINGS.md](./FINDINGS.md) for evidence, source and limits.

## Acceptance criteria

- [x] Parent and child direct balances survive, including empty children and ancestors above the grouping depth.
- [x] Unlike units never enter the same scalar sum; retain every unit for the presentation layer.

- [x] Resolve each actual account before grouping: exclude nested Cash/Checking contributions under Assets:US, preserve declared activity overrides and fixed Income/Equity vocabulary.

## Outcome

Reproduced all three losses live at HEAD before changing anything, by hovering
the real chart and reading ECharts' own tooltips:

- `Cash Flow → Expenses:Taxes 42,116.2 USD` — the exact figure FINDINGS
  derived, `52,047.35 − 295.23 − 27,635.92 + 18,000`;
- `Cash Flow → Assets:US 80,174.807 USD` — every asset leaf including the cash
  ones and the 25 VACHR;
- `Income:Revenue → Cash Flow 7,054 USD` on Synopsys, whose API returns MUSD.

`sankey-data-transformer.ts` now carries amounts as a `UnitAmounts` map
(`unit → amount`) from the response to the presentation layer, and nothing sums
across keys. Three separate repairs, all in the aggregation:

1. **A node's own postings count.** `aggregateHierarchyBalance` reads
   `balance` at every level and then recurses, instead of summing only
   children from zero. The producer stores direct postings on the account and
   rolls them into each ancestor's `balanceChildren`, so nothing is
   double-counted — and the old base case dropped a parent's money even when
   the child that triggered the recursion was empty, which is exactly the
   `Y2015/Y2016:US:Federal` case.
2. **Every unit survives.** `readBalance` keeps every key rather than
   `balance["USD"] ?? Object.values(balance)[0]`, so IRAUSD, VACHR and MUSD
   stay themselves instead of becoming USD or being silently dropped.
3. **Every descendant resolves its own role.** The recursion skips a child that
   resolves to `exclude` or to the `cash` role, so a Checking or Cash leaf no
   longer reaches the investing bucket on its parent's authority. A declared
   activity role still keeps such an account, because `isExcludedAccount` is
   what decides.

An ancestor above the grouping depth now contributes its own postings to its
own depth key before the traversal descends, so direct balances above depth are
not lost either.

`transformToSankeyData` then chooses **one** unit for the whole diagram — the
one the most accounts are denominated in, ties broken by magnitude then
alphabetically so the choice is stable across renders — and projects every node
to it. A Sankey adds its links into node totals, the centre and Savings, so it
can only be truthful in a single unit; totals and Savings are computed inside
that unit alone. `SankeyData` now carries `unit` and the full `units` list so
the presentation layer can label and disclose scope, which is t002's work.

Verified live after the change, and cross-checked against the real API rather
than assumed:

| Link | Before | After |
| --- | --- | --- |
| `Expenses:Taxes` | 42,116.2 | **52,047.35** |
| `Assets:US` | 80,174.807 | **73,386.297** |
| `Income:US` | 148,104.58 | **129,974.58** |

The income change is the clearest proof the unit split is right: the API's
`Income:US.balanceChildren` is `{ USD: -129974.58, IRAUSD: -18000, VACHR: -130 }`,
and 129,974.58 + 18,000 + 130 is precisely the old 148,104.58. The chart was
adding dollars, retirement dollars and vacation hours into one number.

Synopsys still reads 7,054 — the correct MUSD amount — and is still labelled
USD, because the literal suffix lives in `cash-flow-sankey.tsx` and belongs to
t002. The single-currency crypto ledger renders unchanged, as the control.

Tests: the three existing aggregation cases keep their expected values (5000,
6500, 1000) and now read them from the unit map, which shows the repair did not
disturb them — all three fixtures had `balance: null` parents, which is why they
never caught this. Four cases were added for exactly what this task repairs: a
parent's postings surviving an empty child, unlike units staying apart, every
unit of a single mixed leaf, and cash descendants staying out of an investing
ancestor. The broader matrix belongs to t006.

files, 4282 passed, 1 pre-existing skip) and `yarn build` all pass.
