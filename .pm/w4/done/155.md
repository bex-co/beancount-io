# Seven OAuth consent strings ship untranslated in all fourteen non-English locales

Severity: minor localization gap. Estimate: ~40m, dashboard. A2/A3: the OAuth
consent screen is where a third-party app asks for access to someone's ledger,
so it is a trust moment, and it is in English for every non-English reader.

Found while repairing the Ukrainian `auth` catalog for `w4/m24/t001`. These
seven keys are byte-identical to `en.ts` in every one of `bg ca de es fa fr ja
ko nl pt ru sk uk zh`:

- `auth.oauthSignInToContinue` — "Sign in to continue"
- `auth.oauthRegisterToContinue` — "Create an account to continue"
- `auth.oauthVerifyEmailToContinue` — "Verify your email to continue"
- `auth.oauthAppWantsAccess` — "An app wants to access your Beancount ledger."
- `auth.oauthChooseLedger` — "Choose a ledger"
- `auth.oauthSelectLedger` — "Select which ledger to grant access to."
- `auth.oauthApproveAccess` — "Approve access"

This is a different defect from the one `w4/m24` and `w4/153` own. Those are
half-translated messages, where a find/replace swapped a leading token and left
the rest — the result is a word in neither language. These are simply keys that
were added to English and never translated anywhere, so the count being 14 out
of 14 is the signal: no locale was ever updated, rather than one being behind.

Scope: translate the seven in all fourteen locales. `Beancount` stays as the
brand name in `oauthAppWantsAccess`. Preserve every key and any
`{placeholder}`.

Acceptance: none of the seven is byte-identical to `en.ts` in any of the
fourteen; English is unchanged; the dashboard gates pass, including the
translation suites. Native-speaker review is welcome; no phrasing is mandated.

Worth checking while here, but not in scope to fix: whether the repo has a
guard that would have caught a new English key never reaching the other
catalogs. `dashboard/src/test/translations.test.ts` compares placeholder sets
rather than translation coverage, and a coverage assertion would be noisy given
the ca 200 legitimately-identical entries per locale (brand names, notation,
symbols) counted in `w4/149`. If a guard is wanted it needs that allowlist
first, which makes it its own piece of work.

---

**Resolved 2026-09-20** — translated all seven keys in all fourteen
non-English locales, 98 strings, in `features/auth/locales/*.ts`. Shipped in
the commit above (`dashboard`).

Each locale uses the word for "ledger" its own catalogs already use, read from
`common.ledgerSettings` and `common.failedToLoadLedger`. Notably *not* from the
dashboard delete label: the German, Spanish and Portuguese ones are themselves
half-translated (`Löschen Ledger`, `Eliminar Ledger`, `Excluir Ledger`), so
copying them would have spread the very defect `w4/157` exists to fix.

`Beancount` stays as the brand name. Key counts and English are unchanged, and
the all-locale guard still passes.

Not verified on screen: `/oauth/consent` returns 500 without a real
authorization request, and originating one needs a registered client. The
strings were checked against the catalogs and the guard only.

On the open question this note raised — whether a guard should catch a new
English key never reaching the other catalogs — the answer is still "not
cheaply". A byte-identical-to-English assertion would fire on the ca 200
legitimately identical entries per locale counted in `w4/149`, so it needs the
allowlist first. `w4/157` proposes the en-comparison machinery that would make
it affordable; this is worth revisiting once that exists.
