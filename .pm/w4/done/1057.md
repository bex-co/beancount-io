## Cause and concrete correction

`dashboard/src/features/journal/locales/de.ts:62–65` and `nl.ts` localize the amount example to `100,00`; `fa.ts:64–67` localizes its digits to `۱۰۰.۰۰`. The other12 journal catalogs already use ASCII100.00. The sole production key consumers are Transaction at `new-directive-dialog/transaction-form.tsx:544` and Balance at `balance-form.tsx:219`.

These are native number fields, rather than the importer's bank-format text parser. Their supplied examples disagree with the recorded browser entry behavior. The current actual parseDecimalNumber control also rejects literal `100,00` and `۱۰۰.۰۰`, accepts `100.00` unchanged, and accepts the browser-filtered `10000` unchanged. Main's shared ExactAmountInput preserves native typing/validity and does not normalize those locale examples.

Use the accepted **ASCII100.00** example in these three journal.amountPlaceholder messages, retaining each surrounding translation. Explain in the translation descriptions that this example denotes the amount field's input syntax and its digits/decimal point must stay invariant. Preserve the already-valid examples in the remaining catalogs and the exact numeric input behavior. No broader localized-number parser, CSV grammar change, display-format change, API change or dependency is needed for this guidance correction.

Acceptance: following the actual rendered German, Dutch and Persian examples enters raw `100.00` and numeric100 in Transaction and Balance, without badInput. Repeat German narrow/desktop and the working English/point controls. Add a meaningful catalog/example regression against the accepted decimal grammar, retain existing form/input tests and run dashboard format, lint, test and build when implementing.
