# Preserve small nonzero values in chart axis labels

**Severity:** minor. **Estimate:** 45 minutes. **Owner:** dashboard. **A2/A3:** readers should be able to distinguish the scale of a fractional holding without every tick claiming zero.

Production `https://beancount.io`, signed out, English/light, isolated headless Chromium149.0.7827.55. Local HEAD26d54a9d; fetched main bd5d1d31 retains this code. Asset `main-BIr0jJni.js`; exact deployed SHA unknown.

The API and chart model retain the real values. The formatter dates to af5339de and has no subsequent repair.

Bounded fix: make the shared formatter preserve meaningful precision for fractional magnitudes, so nonzero ticks are not rendered as zero and the reproduced adjacent ticks remain distinguishable. Preserve signs, actual zero, string-number inputs, existing large-value abbreviations, plotted data and full tooltip values. Use the existing formatting dependency or standard number formatting; do not round ledger data, force all charts to cents, or change axis domains to conceal the problem. Scientific notation for extremely small values is acceptable if it remains readable and unambiguous. This is not a request to remove `.0` from ordinary zero ticks or redesign all number presentation.

**Resolved 2026-09-19** — Confirmed by exercising the installed formatter:
`formatYAxisNumber` returned `"0.0"` for 0.003, 0.006, 0.009, 0.012, 0.015,
0.018 and for 0.01 through 0.044, exactly as this note records, while 1000 gave
`"1.0k"`.

`common/lib/chart/chart.ts` now keeps two significant digits for a tick below
one — enough to tell 0.003 from 0.006 and 0.019 from 0.020 — while an actual
zero still reads `"0.0"` and everything from one upward is untouched, including
the k/m/b abbreviations, signs and string inputs. Below 1e-4, where two digits
would be unreadable inline, the label falls back to exponential notation, which
this note allows. No ledger data is rounded, no axis domain changes, the
Commodities price formatter (`w3/012`) and the BQL chart path are untouched,
and no dependency changed.

Verified through the chart option the Account Balance and Balance Sheet views
actually install: a new case renders `LineChart` with the reproduced BTC series
and runs the option's own `yAxis.axisLabel.formatter` over the ticks, yielding
`0.0, 0.01, 0.02, 0.03, 0.04` — one zero instead of five — while a 4,500 USD
axis still yields `0.0, 1.0k, 4.5k`. Eleven formatter cases cover both
reproduced tick series, small negatives, fractional strings, the exponential
threshold and the unchanged abbreviation boundaries; six of the new cases fail
without this change.

Reported honestly: the axis labels are painted into the canvas rather than the
DOM, and the page does not expose the ECharts instance, so the rendered glyphs
could not be read in the browser. A pixel-signature proxy was tried and
discarded — it returned identical numbers with and without the fix, so it was
measuring the wrong region and proves nothing. The verification therefore rests
on the option-level and formatter tests above. All five formatter consumers —
the BTC account, Balance Sheet, Overview, Budget and Income Statement — were
re-loaded at 1440px and render with no page errors and no zero-width canvases.
