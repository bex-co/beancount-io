# Make the one-shot BQL statement guard understand block comments

Severity: **minor**. Package: **cli**. Estimate: **35–50m**. Source: continuous CLI QA. **A1**: documented queries should run, and a rejected multi-query script must not become a silent partial success because its comment contains an apostrophe.

Main `390568c2`, checkout `cli/.venv/bin/bea` 0.3.0, Python 3.13.3, macOS arm64. Isolated config/cache, closed stdin, piped stdout/stderr, synthetic ledgers only. Reproduced both failures twice in fresh processes; source hashes unchanged.

Create `/scratch/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Equity:OpeningBalances USD
2024-01-02 * "Start"
  Assets:Cash 1000 USD
  Equity:OpeningBalances
```

1. Run `bea --json --file /scratch/main.bean query 'SELECT /* accounts; audit */ account LIMIT 1'`. Actual: exit 2, stdout empty, usage error on stderr saying `One BQL statement per invocation; got 2`. Human mode also exits 2. This is one valid SELECT; native `bea query --source /scratch/main.bean 'SELECT /* accounts; audit */ account LIMIT 1'` returns the Assets:Cash row, exit 0.
2. Run `bea --json --file /scratch/main.bean query "/* customer's accounts */ SELECT account LIMIT 1; SELECT number LIMIT 1"`. Actual: exit 0, empty stderr, JSON contains only the first SELECT's `account` column/Assets:Cash row. The second SELECT is silently discarded. Removing the comment correctly returns exit 2 for this same two-statement input.

Controls: a block comment without punctuation and a quoted literal containing a semicolon both return the expected row. A leading block comment containing a semicolon is also falsely rejected; the inline-comment case above supplies the decisive working upstream control, since the native upstream shell has separate leading-comment rendering limitations.

Expected: punctuation within a block comment must not affect top-level statement count or string quoting. Single statements run; genuine multiple statements receive the existing explicit usage refusal. This follows BQL's installed block-comment grammar and completed w3/282/w1/m23/t005's no-silent-tail contract. No expansion to multi-result support is requested.

Root: `cli/src/cli/commands/query.py:67–108`, `_split_statements`, tracks only quotes and backslash escapes, not `/* ... */`. It splits comment semicolons as statement boundaries and treats a comment apostrophe as the start of an unclosed string, hiding subsequent real boundaries. The sole production caller is `_refuse_multi_statement`, reached by the managed one-shot path at line 210, including stdin queries. The engine then executes only the first statement, as the original guard was intended to prevent.

Repair the guard to respect the supported BQL comment/quote grammar without altering the query sent to the engine. Prefer an existing parser/tokenizer boundary if available; keep frontend/engine architectural constraints. Preserve literal semicolons, escaped quotes, a trailing terminator, malformed-query diagnostics, and the separate dot-command handling. Cover both reproduced failure directions in real command tests, human and JSON, plus the nearby controls. Run CLI checks.

Dedupe: searched all board states for query comments/semicolons and read completed w3/282 and w1/m23/t005 in full. `15629c14` introduced this guard and still supplies its only definition. Completed w1/026 fixed leading-comment rendering engine-side; that fix remains effective for ordinary comments, and did not make this later frontend splitter comment-aware. No overlapping open item found. Native output alias protection (w4/181) is independent.

Evidence: `cli/tmp/qa-20260921-cli-loop/cycle15.py`, `cycle15.log`, and captures `cycle15-*-inline-semicolon-*`, `cycle15-*-comment-quote-bypass-*`, and controls, with exact argv, streams, exit status and before/after hashes. Interactive query behavior, other platforms and patched behavior are unverified. No product changes or shipping.

**Resolved 2026-09-23** — Already fixed on `main` before this triage by `5a5463f0` (w3/402, `cli`): `_split_statements` skips `/* … */` comments and doubled-quote literals when counting top-level semicolons, matching the engine's `_code_mask`. Re-ran both repros at HEAD. `SELECT /* accounts; audit */ account LIMIT 1` returns the `Assets:Cash` row with exit 0. `/* customer's accounts */ SELECT …; SELECT …` exits 2 with "One BQL statement per invocation; got 2", no longer a silent partial success. `cli/tests/test_query_statement_comments.py` (26 passing) covers both directions and pins frontend/engine agreement. No code changed.
