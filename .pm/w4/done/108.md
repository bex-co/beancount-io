# Keep file metadata visible when the source editor viewport shrinks

Severity: minor. Estimate: 50 minutes, dashboard. A2: readers should retain the file size and last-change date after resizing a source view.

Environment: production https://beancount.io, September17 local / September18 UTC2026, isolated headless Chromium149.0.7827.55, English/light, signed out, public open_ledger/example main.bean. Local26d54a9d, fetchedorigin358ba4dc; no newer dashboard repair. Deployed main-BIr0jJni.js, exact deployment SHA unverified. These are Playwright viewport changes, not a physical-device orientation test.

Reproduce:

1. Fresh-load `/ledger/open_ledger/example/files/blob/main/main.bean?lang=en&lineNumber=1` at844×390. The editor is195px tall, with the last-change date fully visible at y341–357.
2. Resize to390×320 and let layout settle. The editor remains195px high; the date moves to y325–341, below the viewport and the clipping container. File size at y301–317 is partly clipped. A fresh load at390×320 instead gives a157px editor with file size y263–279 and date y287–303, both visible.
3. A separate fresh-context sequence starts390×320, grows844×390 and shrinks390×320: the same195-vs157px mismatch repeats without Find open.

Border clientHeight228 / scrollHeight261 / scrollTop0 with overflow:hidden. Reloading at844×390 restores the195px editor and visible date.

Find remains usable: Cmd+F2017-09-07 reaches the source-backed line5544 in the shortened view, and Escape closes Find. Do not claim lost source data, an invisible active line, or physical keyboard overlap. Initial short-viewport checks looked usable until the metadata clipping was inspected; the positive control applies to a fresh load only.

Source boundary: `dashboard/src/features/ledger-editor/file-editor/components/ledger-file-view/text-file-view.tsx:202–216` puts TextEditor and its metadata footer together in an overflow-hidden flex column. `text-editor.tsx:228–242` gives the editor inner div h-full but no sizing constraints for the library's outer wrapper; automaticLayout is already enabled at208. Installed @monaco-editor/react's container renders a section with default height100%, followed here by a footer. Live computed outer section has flex0 1 auto/min-height:auto and retains the wrong allocation after resizing; it is195px when only157px remains for the editor. This traces the app/library sizing boundary; an exact CSS patch has not been validated. The structure dates to af5339de and is unchanged by subsequent permission, draft and save fixes.

Fix: allocate the remaining flex height to a shrinkable editor wrapper while reserving the metadata footer's actual responsive height. Let Monaco observe that correctly sized container; preserve the persistent editor/model rather than remounting it on resize or forcing a reload. Keep narrow two-line and wider one-line metadata, the readonly guard, draft/selection/Find state and editor scrolling. Avoid global CSS changes to every Monaco user unless independently required. No dependency/API change.

Acceptance: both resize sequences keep file size and date fully visible, with editor bounds matching the space left by header/footer; a fresh load and resized state at the same size agree. Add a real browser layout regression: a mocked editor or jsdom zero rectangles cannot prove this. Retain successful Find/selection and the existing persistent editor lifecycle. Writer draft preservation is a regression requirement, not a production write exercised here.

**Resolved 2026-09-19** — Reproduced against a local build, both sequences.
Resizing from 390×844 to 844×390 left the editor filling all 228px of the
clipped box, with the file size and last-change date at y365–398 — below the
clip bottom at 366 and below the 390px viewport — and the box reporting
`scrollHeight 261` against `clientHeight 228` with `overflow: hidden`, so
nothing could bring them back. A fresh load at the same size gave a 195px
editor with the metadata visible at y332–365, so the resized and fresh states
disagreed. The 844×390 → 390×320 sequence clipped it the same way.

`text-file-view.tsx` placed `TextEditor` and the metadata bar directly inside
one `overflow-hidden` flex column. The library's wrapper is 100% height and
does not shrink, so it kept the allocation it was first given. The editor now
sits in its own `min-h-0 flex-1` child with the metadata bar as a `shrink-0`
sibling, so Monaco's already-enabled `automaticLayout` observes a container
sized to the space that is actually left. No dependency, API or global Monaco
CSS change, and `text-editor.tsx` is untouched.

After the fix both sequences keep the metadata fully inside the clip and the
viewport, and the resized state matches the fresh load exactly: 157px editor at
390×320 and 195px at 844×390 either way, with `scrollHeight` no longer
exceeding `clientHeight`. The persistent editor survives — the same
`.monaco-editor` node is present after the resize rather than a remount — an
open Find keeps its `2017-09-07` query and its match count across it, and
Escape still closes it. 4/4 on those checks plus the four layout measurements.

Reported honestly: the note asks for a real browser layout regression, and
`dashboard/` has no browser test harness to add one to — its suite is jsdom
only, and introducing Playwright would be the dependency and CI change this
note rules out. The verification above therefore lives in the QA script rather
than in CI, and no jsdom test was added, since the note correctly says a mocked
editor cannot prove this. Other engines, authenticated editing and physical
device rotation remain unverified. Shipped in `fa9578cb` (`dashboard`).
