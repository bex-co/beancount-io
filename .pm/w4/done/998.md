# Keep the Income Statement bar mode when Time changes

**Severity:** minor residual of [142](./142.md) and [M16](./m16/README.md). **Estimate:** 45–60 minutes. **Owner:** dashboard. **A2:** selecting a new period should retain the bar presentation the reader chose.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-22; owned isolated headless Chromium 155.0.8059.85, anonymous public `open_ledger/example`, English/light, fresh 1440×1000 and 390×844 contexts. Genuine reads only; no response fixtures, writes or artificial delay.

1. Open `/ledger/open_ledger/example/income-statement?time=2016&view=income`; repeat independently with `view=expenses`. Choose **Single Bars** with the named **Select chart mode** control.
2. Passing control: change Monthly to an uncached **Yearly** interval. The real GetLedgerIncomeStatement returns HTTP 200 and Single Bars remains selected. Return to Monthly; it still remains Single Bars. This preserves M16's completed inner-query lifetime behavior.
3. Change shared **Time** from 2016 to **2016-11** and press Enter. On narrow screens use the actual Report filters sheet, then close it normally after the read. The new scoped query succeeds with HTTP 200, monthly interval, no GraphQL errors and one period.
4. The selected Income/Expenses view and its `view=` bookmark correctly survive, but **Select chart mode becomes Stacked Bars**. Both views repeat at both fresh widths, producing four retained failures.
5. Explicitly choose Single Bars again. It works immediately and starts no additional Income Statement read, so the failure is lost view state rather than bad report data or an unavailable chart mode.

A separate settled desktop Expenses repeat captures the same Single → Stacked change after chart animations finish. Monthly remains Monthly during the failing Time edit; the earlier Yearly control was restored first to isolate bar mode. Other shared account/advanced-filter edits are source-traced aliases, not independently failed here.

## Cause and bounded repair

`dashboard/src/features/reports/income-statement/index.tsx:61–66` keeps selectedTab in useUrlView but still declares `useState<ChartMode>("stacked")` for chartMode. `common/components/ledger-layout/index.tsx:51–81,180–193` intentionally replaces Outlet while the shared account/filter/time scope changes. That outer boundary unmounts the whole report page, so the local bar mode initializes to stacked again. In contrast, the Yearly/Monthly query branch only replaces report content, leaving the page-owned mode alive.

[142](./142.md) already made the product decision that a chosen chart is a view preference that survives a scope edit, and adopted the validated URL pattern compatible with M16's report/ledger lifetime. Its tab choice now works; the second choice, chartMode, was omitted. M16's [t004](./m16/done/t004.md) explicitly lifted that same mode, and [t005](./m16/done/t005.md) records its lifetime test gap.

Keep bar mode in a validated page-scoped home that survives the outer scope boundary, following the existing URL preference contract alongside the selected chart view. Preserve current stacked default, clean default URLs, valid Single/Stacked choices and behavior across the Income/Expenses views. Do not add a global cookie/localStorage preference or weaken the intentional pending-data guard. Preserve shared filters, conversion/interval behavior, exact report results, exports, existing tab bookmarks and named selectors. No API, dependency or backend behavior change is needed.

Acceptance: drive a real page/router lifecycle with Income and Expenses in Single mode, perform an uncached Time scope replacement, and assert Single and the selected view remain after the remount with the new query/results. Include native desktop/narrow checks, the working uncached interval control, explicit mode recovery, initial/default/invalid URL values and ordinary reload/bookmark behavior. Keep M16's inner pending behavior and 142's tab retention healthy; run dashboard gates when implementing. Other engines/locales, account/filter aliases and repaired behavior remain unverified.

**Resolved 2026-10-22** — The Income Statement's Single/Stacked bar mode now lives in the URL as `?mode=`, beside `?view=` (from 142). The route schema validates it the same way: an unknown value is the default, and the default leaves the URL clean. A shared Time, account or filter edit, which remounts the page, keeps it. `useUrlView` takes the parameter name, and `ChartMode` derives from the new `CHART_MODES`. Interval and conversion changes still keep the mode, and Stacked stays the default. Regressions in `index.test.tsx` and the new `search.test.ts`: a Single choice survives a full page remount with its view, a return to Stacked clears the param, an unknown mode falls back, and the schema handles valid, unknown and malformed values. The remount case fails against the old code.

Local browser check: Income and Expenses at 1440×1000 (header Time) and 390×844 (Filters sheet). After choosing Single Bars and changing Time from 2016 to 2016-11, both views kept Single Bars with `?mode=single` and their `view=`. The 2016-11 read was answered with the real 2016 response, since only the preference was under test. Shipped in `5c36ab719` (`dashboard`).
