# The app ships 13 languages and iOS is told it has one — a Chinese device gets an English app on first launch

**Severity:** major. **Estimate:** 20–30 minutes for the config fix, plus a release-build verification. Owner: mobile. A2/A3: twelve complete translations are paid for and shipped in the JS bundle, and no iOS user ever sees one without going to find it by hand — through the language wheel that **`w4/009`** shows cannot be tapped. The App Store product page's "Languages" section is derived from the same missing bundle metadata, so the app also advertises itself as English-only.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, **simulator fully shut down and rebooted** after setting the device language, authenticated production session at `https://beancount.io`, `open_ledger/alphabet`. Report-only QA; no ledger mutation. Device and app preferences were changed locally and restored (see Restore).

## Repro — a three-arm experiment on one device

Device set to Chinese and rebooted so the change is genuinely in effect:

```
$ xcrun simctl spawn <udid> defaults read -g AppleLanguages
( "zh-Hans-US", "en-US" )
$ xcrun simctl spawn <udid> defaults read -g AppleLocale
zh_Hans_US
```

| arm | persisted `locale` in AsyncStorage | app renders |
| --- | --- | --- |
| A (baseline) | `"en"` | English |
| **B — the defect** | **key absent** (a first launch) | **English** |
| C (control) | `"zh"` | **Chinese** — 首页 / 净资产 / 最近交易 / 近6月, tab bar 首页·账户·交易记录·报表·文件 |

Arm C matters: it proves the Chinese translation is complete and correct and that `setLocale` works. The only thing that fails is **detection**. Arm B is a faithful first launch — `loadLocale()` returns `null` when the key is absent, which is exactly the state a new install is in.

`zh` is in `SUPPORTED_LOCALES` (`src/translations/index.ts:14-38` registers all 13), so if `Localization.getLocales()` had reported `zh` at all, arm B would have rendered arm C's screen.

## Root cause

The JS side is correct and is not the problem. `src/translations/index.ts:42-54`:

```ts
const getLocale = () => {
  const locales = Localization.getLocales();
  for (let i = 0; i < locales.length; i++) {
    const locale = locales[i];
    if (locale.languageCode && SUPPORTED_LOCALES.includes(locale.languageCode)) {
      return locale.languageCode;
    }
  }
  return "en";
};
```

and `splash-provider.tsx` applies a persisted choice only when there is one, with the intent spelled out in its own comment:

> *"`loadLocale()` returns null when nothing is persisted, in which case `i18n.locale` already holds the device-derived choice from `src/translations/index.ts` — so a Persian device flips on its very first launch, not only after the user visits Settings."*

**That is the intent, and it does not happen.** The reason is one level down, in what the native bundle declares. On the installed app:

```
$ plutil -extract CFBundleLocalizations json -o - .../Beancount.app/Info.plist
  → No value at that key path
$ plutil -extract CFBundleDevelopmentRegion raw -o - .../Beancount.app/Info.plist
  → en
$ ls -d .../Beancount.app/*.lproj
  → no matches
```

iOS resolves an app's language by intersecting the user's preferred languages with the localizations the bundle declares, falling back to `CFBundleDevelopmentRegion`. This bundle declares none, so the app's language resolution can only ever land on `en`, and that is what `expo-localization` reports back to `getLocale()`.

**This is not a dev-build artifact.** The bundle metadata comes from config, and the config has nothing to say: `app.json` has **no `expo.locales`** key (the Expo field whose whole job is to generate `.lproj` directories and `CFBundleLocalizations`), and `ios.infoPlist` — which does carry eleven deliberate entries — has no `CFBundleLocalizations`. The `expo-localization` plugin is listed, but it only links the native module; it does not declare supported languages. A release EAS build from this config produces the same `Info.plist`.

## Fix

Declare the languages the app actually ships. In `app.json`, add the twelve non-English locales alongside `en` so the bundle advertises them:

```jsonc
"ios": {
  "infoPlist": {
    "CFBundleLocalizations": [
      "en", "zh", "bg", "ca", "de", "es", "fa", "fr", "nl", "pt", "ru", "sk", "uk"
    ],
    …
  }
}
```

The list must stay in step with `SUPPORTED_LOCALES` in `src/translations/index.ts`, which is the actual source of truth — **add a check that the two agree**, because a translation added to the JS map and not to the plist would silently fail to be detectable, which is precisely the failure this note reports.

Prefer `ios.infoPlist.CFBundleLocalizations` over Expo's `locales` field unless localized *store/permission* strings are also wanted: `expo.locales` maps locale → a strings file and is aimed at localizing `Info.plist` values such as the camera and photo-library usage descriptions. Those are currently English-only too (`app.json` `ios.infoPlist.NSCameraUsageDescription`: *"Beancount uses the camera to scan receipts."*), so doing both in one pass is defensible — but they are separate problems and the detection fix does not require the second.

Android should be checked in the same sitting and is **not** covered by this note; its language resolution differs and was not exercised.

**Do not** fix this by making `getLocale()` read a region or a raw preference list to work around the bundle. The bundle metadata is load-bearing for the App Store listing and for iOS's own language-per-app setting, and working around it leaves both wrong.

**Acceptance:** on a device set to Chinese, German or Persian, a **fresh install** comes up in that language with nothing persisted; a device set to a language the app does not ship still comes up in English; an existing user's persisted choice still wins over the device language; the Persian case still flips layout direction on first launch (the `applyLayoutDirection` path in `splash-provider.tsx`, which today can only run after a manual selection); `CFBundleLocalizations` matches `SUPPORTED_LOCALES`; and the App Store product page lists the shipped languages. Add a unit test that the plist list and `SUPPORTED_LOCALES` are equal sets — that is the regression that will otherwise recur.

## Blast radius

One config key, but it changes what every non-English user sees on first launch, and it interacts with three things:

- **`w4/009`** — the language wheel's options cannot be tapped, only dragged. Today that is the *only* route to a translated app on iOS. Fixing this note removes the need for most users to find that control at all; fixing `w4/009` makes the fallback usable. **They compound, and this one should go first.**
- **RTL.** `splash-provider.tsx` calls `applyLayoutDirection` and reloads the app when the flag moves, with the comment "a Persian device flips on its very first launch". That path is currently unreachable from a fresh install, so **first-launch RTL has never actually run in the wild** — worth saying out loud, because fixing this note is what will first exercise it, and `w4/056`'s RTL caveats become live at the same moment.
- **App Store metadata.** `mobile/CLAUDE.md` documents 14 store localizations and says the app "ships Bulgarian and Persian". The binary agrees with none of it.

Not exercised: **Android**; a release (non-dev) build, though the config argument above says it must behave identically; a physical device; and whether iOS's per-app Language setting appears in system Settings once localizations are declared (it should, and is worth confirming as part of acceptance).

## A correction to my own earlier conclusion

An earlier pass in this QA run examined `getLocale()` and `splash-provider.tsx`, found both correct, and **recorded device-locale detection as working**. That conclusion was drawn from source alone and was wrong: the JS is correct, and the layer beneath it makes the JS unreachable. This note supersedes it. The general lesson is worth keeping — a correct-looking detection path proves nothing about detection until something is actually detected.

## Adjacent states

Translation quality is not in question and arm C is the evidence: every string on Home rendered in Chinese, including the range pills (`近1月` … `全部`), which are generated labels rather than static copy. `w4/046`'s dead-key finding is unaffected — those keys are dead in all 13 locales equally.

Also confirmed while establishing the baseline: the only writer of `localeVar` is `src/screens/setting/main-content.tsx:228`, and `createPersistentVar` does **not** write its default on load (`loadFromStorage` returns `null` and writes nothing when the key is absent). So arm B is genuinely reachable — an install that never visits Settings never has the key. This also means arm A's `"en"` came from a real selection in an earlier session, not from the app seeding itself, which is what made arm B necessary to run at all.

## Dedupe

`grep -rln 'CFBundleLocalizations\|getLocales\|device locale\|device language\|expo.locales\|lproj\|preferredLanguages' .pm --include='*.md'` over the whole board including `done/` → exactly **one** file, `w4/056`.

**`w4/056`** ("Every date picker pinned to `en_US` → English month names") is a different defect with a different fix site (`date-picker-modal.tsx:60-61`), and the two do not overlap — but **it asserts this note's defect as a fact in its severity line**: *"the app detects the device language and comes up translated on first launch."* That premise is false on iOS and is corrected there. Its estimate and reasoning survive intact; if anything this note strengthens it, because `w4/056` currently cannot bite anyone (nobody reaches a non-English locale) and will begin to the moment this is fixed. **Fix this one first, then `w4/056`.** `w4/056` also records that it could not change the app's language to verify its own repro; the AsyncStorage route used here (arm C) is the method that unblocks it.

`w4/046` (35 dead translation keys) and `w4/043` (three hardcoded English strings in Settings) are about translation *content*; this is about whether any translation is ever selected. No item covers bundle localizations.

## Restore

All local state was returned to its starting values after the run: AsyncStorage `locale` restored to `"en"` from a backup taken before the first edit, device `AppleLanguages` restored to `("en-US", "zh-Hans-US")` and `AppleLocale` to `en_US`, and the simulator rebooted so the restore is in effect. No production data was touched at any point — every change was to the simulator's own preferences and the app's local container.

**The change.** `app.json`'s `ios.infoPlist` now declares `CFBundleLocalizations`: `en`, `zh`, `bg`, `ca`, `de`, `es`, `fa`, `fr`, `nl`, `pt`, `ru`, `sk`, `uk`.
