# The transaction list shows only the payee, so seven rows read alike and search returns matches on text that is never displayed

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A3: `open_ledger/alphabet` is the app's showcase public ledger, and its Transactions tab is a column of identical labels distinguished only by amount. A2: searching it returns rows that visibly do not contain the search term, which reads as a broken search rather than a hidden field.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / **default** text size, light, authenticated production session at `https://beancount.io`, public `open_ledger/alphabet`. Report-only QA; no ledger mutation, and the search box was cleared afterwards.

## Repro

**A — the list.** Open the Transactions tab on `open_ledger/alphabet`. Nine rows are visible under `June 30, 2026`:

| name shown | amount |
| --- | --- |
| Q2 2026 Expenses | $26,560,000,000.00 |
| Q2 2026 Other I… | +$97,983,000,000.00 |
| Q2 2026 Expenses | $6,461,000,000.00 |
| Q2 2026 Expenses | $8,403,000,000.00 |
| Q2 2026 Expenses | $18,219,000,000.00 |
| Q2 2026 Expenses | $29,764,000,000.00 |
| Q2 2026 Expenses | $16,179,000,000.00 |
| Q2 2026 Revenue | +$106,000,000.00 |
| Q2 2026 Revenue | +$382,000,000.00 |

Five consecutive rows carry the same label. The only thing separating them is the figure on the right.

**B — the search.** Type `revenue` into the search field. Among the results is a row labelled **`Q2 2026 Expenses`**. Tapping it shows why: its **narration** is *"Other cost of revenue"* — a legitimate match on a field the list never renders. Two more `… Expenses` rows appear for the same reason.

**Working control:** the same list on `puncsky/example` reads `Anthropic`, `Cafe Medager`, `AMEX EPAYMENT; ACH PM…`, `STRIPE; TRANSFER; TIAN P…` — distinct rows, because that ledger's payees are per-merchant. The defect is a function of payee granularity, not of the list.

## Root cause

`transactions-screen/entry-row/index.tsx:101` picks exactly one string and renders it on one line:

```ts
const name = entry.payee || entry.narration || entry.directive_type;
```

```tsx
<Text style={styles.name} numberOfLines={1}>{name}</Text>
```

There is no second line. When `payee` is present it wins unconditionally, so the narration — often the only thing distinguishing two entries — has nowhere to appear. On a ledger built from quarterly filings (or from a bank import that stamps a batch name into the payee) every entry in a quarter shares a payee, and the list collapses.

Search, meanwhile, runs server-side through `getLedgerJournal`'s `filter`. The client's own matcher documents what that is expected to cover — `groupToSections` (`utils/transaction-display-utils.ts:170-181`) filters on `payee`, `narration`, **and** each posting's `account`:

```ts
entry.payee?.toLowerCase().includes(q) ||
entry.narration?.toLowerCase().includes(q) ||
entry.postings.some((p) => p.account.toLowerCase().includes(q))
```

Two of those three are invisible in the row. (That client-side matcher is itself dead — both call sites pass `""` for `searchQuery`, deliberately, because the server filter is what keeps paging consistent with the query. It is quoted here as a statement of intended match semantics, not as live code.)

So the search is **correct**; the row is what makes it look wrong.

## Fix

Render the narration as a second line when it differs from the payee:

```tsx
<Text style={styles.name} numberOfLines={1}>{name}</Text>
{secondary ? <Text style={styles.secondary} numberOfLines={1}>{secondary}</Text> : null}
```

where `secondary` is `entry.narration` when a payee was used for `name` and the narration is non-empty and not equal to it. That fixes both halves at once: the rows become distinguishable, and a `revenue` result labelled `Q2 2026 Expenses` visibly carries *"Other cost of revenue"* underneath.

Two things to be careful about, neither of which should block it:

- **Row height.** This list pages 30 at a time and is the app's primary browse surface, so a second line has a real layout cost. Keep it `numberOfLines={1}` at a smaller size, and mirror the change in `transactions-list-skeleton.tsx` so the skeleton still matches the loaded layout to the pixel — `mobile/CLAUDE.md` makes that an explicit convention.
- **`w4/013`** reports that at `accessibility-medium` this row's name is already truncated to two or three characters while the amount keeps full width. A second line will be squeezed the same way. **`w4/013` should be fixed first**, or at least designed together with this, since both are about the middle column losing to the amount column.

Highlighting the matched substring would be a further improvement and is a bigger change (the server does not report which field matched); the second line is enough to make the result explicable.

**Acceptance:** on `open_ledger/alphabet` the nine June 30 rows show distinct secondary text; searching `revenue` shows *"Other cost of revenue"* on the `Q2 2026 Expenses` result; `puncsky/example` rows with no narration, or whose narration equals the payee, render exactly as they do today with no extra blank line; the skeleton's row height still matches a loaded row; and Home and Reports, which mount the same row, are checked too. Add a unit test for the four cases — payee only, narration only, both and equal, both and different. `getDisplayInfo` is module-private today and has no test at all, so this means exporting it (it is a pure function of one entry, so that is the cheap option) rather than reaching it through the component.

## Blast radius

One row component and its skeleton — but `EntryRow` is **shared across four surfaces**, which makes the fix land wider than the Transactions tab and is why the same repeated labels appear elsewhere:

| surface | import |
| --- | --- |
| Transactions tab | `transactions-screen` |
| **Home → Recent Transactions** | `home-screen/components/recent-transactions-card.tsx:12` |
| **Reports → account transactions card** | `reports-screen/components/account-transactions-card.tsx:12` |
| **Merchant detail → transaction list** | `merchant-detail-screen/merchant-detail-screen.tsx:41` (used at `:575`) |

That is a point in the fix's favour — one change fixes all four. It is also the reason to size the second line conservatively: two of them are cards inside a scroll view rather than a full-height list, so extra row height costs visible rows on Home. Check all four after changing it.

**Merchant detail is the worst of the four**, and was found later in this run: on `open_ledger/alphabet`, `Q1 2022 Revenue` lists **seven rows all captioned `Q1 2022 Revenue`**, separated only by amount and a brand logo. The narrations that distinguish them (`Google Search`, `YouTube ads`, `Google Cloud`, …, legible in `2026/Q1.bean` through the file editor) are exactly what a user opens a merchant to see, and none of them is rendered. Where the Transactions tab at least mixes payees, this screen is by construction a list of one payee — so the payee is the one field guaranteed to be redundant there, and it is the only field shown.

An earlier version of this note said three surfaces. That was a miscount: the grep that produced it was truncated by `head` and dropped the merchant-detail import.

The Merchants list has its own row (`merchants-screen/merchant-row.tsx`), as does Account detail (`AccountEntryRow`); neither is affected.

Not exercised: enlarged Dynamic Type (deliberately — that is `w4/013`, and this was measured at the default size to keep the two findings separate), dark mode, Android, and whether any ledger has a narration long enough to make the second line unhelpful.

## Adjacent states

The rest of the transactions journey was exercised natively and is **correct**:

- Search is debounced into the server query rather than filtering a page client-side, and the comment explains why — *"they narrow the query itself, so paging stays consistent with the filter"*.
- Search is case-insensitive (`revenue` matched `Revenue`).
- The search term **survives navigating into a transaction detail and back**, which is the right behaviour and not a given.
- A non-matching query (`zzqq`) shows a centred empty state reading *"No transactions match your search or filters."* — copy that correctly names both inputs rather than blaming the search alone.
- Clearing the search restores the full list exactly, in the same order, with no duplicated rows.
- The Filters sheet opens with `Cancel` / `Reset`, `ALL` preselected under Date Range and `All accounts` under Account; `Cancel` restores the prior state. `selectFiltersForLedger` scopes the stored filter to its ledger so an account restriction cannot follow the user into a different book — with a comment explaining that too.

Two things checked and **not** filed. The hero amount on the `$29,764,000,000.00` detail splits its minus onto its own line — that is `w4/005`, a second instance of an already-reported defect on a different entry, and it is already generalised there. And the Filters sheet's `Apply` button sits behind the development LogBox banner, which was mistaken for a missing control earlier in this run; it is dev chrome, not product.

The transactions header has **no `testID` on the search field, the clear button or the filter button**, so all three had to be driven by coordinate. That is `w4/020`'s subject, recorded here as another instance rather than filed again.

---

**Resolved 2026-09-14** in `feat(mobile): show a transaction's narration under a repeated payee`.

**The row.** `EntryRow` renders a second line whenever the payee is the name shown and the narration says something else, so a `revenue` search result labelled `Q2 2026 Expenses` carries "Other cost of revenue".
- The line comes from a new pure `entryRowSecondaryText` (`entry-row/entry-row-secondary.ts`).
- It is set in `fontSizes.sm` in `black60`: one line at default text size, wrapping like the name once the row stacks at enlarged sizes.
- Rows with no narration, a narration equal to the payee, or no payee render as before, with no blank line.

**The skeleton.** `TransactionsListSkeleton` mirrors the line on alternate rows.

**Surfaces.** `EntryRow` is shared, so Transactions, Home's Recent Transactions, Reports' account transactions card and merchant detail all gain the line.

**Tests.** `entry-row/__tests__/entry-row-secondary.test.ts` covers payee only, narration only, payee equal to narration, and payee different from narration, plus a check that the row renders the helper's line. With the row reverted, that check fails. The existing Dynamic Type guardrail still passes. The mobile gate passes, with 1877 unit tests.

**Not exercised.** Row heights on the four surfaces on device, and highlighting the matched field, which the note calls a bigger change.
