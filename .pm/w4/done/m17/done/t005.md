## Outcome

`ledger-collection.test.tsx` now carries 14 cases on a real router whose ledger
route holds its loader (`defaultPendingMs: Infinity`), so the destination really
sits in `pendingMatches` while the debounce is outstanding. Five of them cover
departure:

- never rewrites the destination while a ledger read is in flight
- never writes to another profile after the reader moves on
- drops an uncommitted query when leaving outside the results grid
- commits a cleared search when the reader opens a card
- keeps sort and show while committing a fast-typed query

The second case found a real gap in t001's guard: `hasLeftProfile()` compared
only `routeId`, and `/ledger/alice` → `/ledger/bob` is the same route with a
different param, so a stale draft could be written onto another reader's profile
URL. The guard now also compares the destination's `username`. Proved
load-bearing — reverting to the plain route-id check fails that case (1 failed |
13 passed) and restoring it passes 14/14.

`user-profile-tabs.test.tsx`'s router mock gained the matching
`params: { username: "testuser" }` so its matches describe this profile rather
than an anonymous one; its reveal/sort assertions already expected the explicit
`to: "/ledger/$username"` + `params` form from t001.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (376
files, 4247 passed, 1 pre-existing skip; baseline 375/4246 before the new cases)
and `yarn build` all pass.
