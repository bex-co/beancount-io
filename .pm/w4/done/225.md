# Restore changed-files keyboard focus in forced colors

Severity: **minor**, dashboard. Estimate: **25–40 minutes**. A2 — keyboard readers should be able to see which commit-history control they are about to activate.

Production `https://beancount.io`, 2026-10-09, dedicated QA login, public synthetic `open_ledger/crypto-example`, English/light, isolated headless Chromium 149.0.7827.55. Browser forced-colors emulation, not a physical Windows session. Source rechecked on main **2469e5ab**; exact deployed SHA is unverified.

## Reproduce

1. With forced colors active, open `/ledger/open_ledger/crypto-example/commit/0d023f5e1c7029c4977fe11004fee0551caa147c?lang=en` at 390×1000 or 1440×1000. Wait for Commit Details and the Load Large Diff gate. Move the pointer away from controls.
2. Use native Tab until the **files changed** summary receives focus: eight Tabs in the fresh narrow layout, 26 in desktop. Both `activeElement` and `:focus-visible` confirm focus. Before/after screenshots of the summary, including surrounding padding, are byte-identical.
3. Press Enter to open the native disclosure. Capture its first file link before focus, then press Tab. The real link receives focus and matches `:focus-visible`, but its before/after screenshots are also byte-identical.
4. Both focused controls have `outline-style:none`, zero-width border and `box-shadow:none`. Foreground and background do not distinguish focus. Visually inspected focused screenshots at both widths confirm the missing cue.
5. Independent fresh forced-colors contexts at both widths repeat both identical-image results. Enter still expands the disclosure and activates the first file link with its correct encoded URL fragment. This is a visual focus failure, not a disabled control or failed navigation.
6. With forced colors disabled, the same native sequences at both widths show a visible green inset ring on both controls, and before/after screenshots differ. Those focused screenshots were also visually inspected.

The first returned filename can differ between loads; the check follows the actual first link, not a guessed filename. No Load Large Diff, Undo, Compare, source edit, clipboard or server mutation was needed. Fresh contexts were closed and the original QA page was untouched.

## Cause and bounded repair

`dashboard/src/features/git/commits/components/commit-file-list.tsx` owns the summary and file-link styles. Both combine `focus-visible:outline-none` with an inset box-shadow ring. Forced colors removes the shadow, leaving no visible cue. These are native summary/anchor elements and do not consume the shared Button; **w4/223** therefore cannot repair them through Button styling alone. The baseline outline in `dashboard/src/style.css` is overridden by these component utilities.

Add an explicit forced-colors keyboard-focus outline using a system color to both owning elements. Preserve the ordinary ring, disclosure dimensions, native Tab/Enter behavior, accessible names, file counts and change statistics, link/hash navigation, repeated-file activation, and the existing deferred large-diff gate. Do not globally disable forced-color adjustment or change dependencies/APIs.

Acceptance: native keyboard focus visibly distinguishes both the collapsed summary and an expanded file link under forced colors at desktop and narrow widths; Enter still opens the disclosure and selects the correct file fragment. Repeat the ordinary-color controls. Add meaningful coverage compiling the actual component's emitted focus CSS, plus browser geometry/visual verification; class-name assertions alone cannot establish a visible cue. Run dashboard gates when implementing.
