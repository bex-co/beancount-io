# The profile search's departure flush covers one exit, and broadening it naively regresses the page's own controls

Severity: minor. Package: dashboard. Estimate: ~45m — the cheap version is already known not to work, so this needs a design decision first.

Raised by w4/143 and confirmed by attempting it. `features/user-profile/components/ledger-collection.tsx` debounces the search query into the URL by 250ms, and compensates by flushing the pending write on the way out. That flush is bound to the results grid:

```
onPointerDownCapture={commitQuery}
onKeyDownCapture={(event) => { if (event.key === "Enter") commitQuery(); }}
```

So it covers leaving via a ledger card, and nothing else. A query typed inside the window is still dropped when the reader leaves by a tab trigger, the profile header, or any other link. The guard that prevents a stale write is generic; only the compensating flush is not, so the two have to be kept in sync by hand.

## What was tried, and why it was reverted

Moving the flush to a document-level capture listener for `pointerdown` and `keydown` — the same idea, one seam wider. It covers every departure, and it breaks the page:

- `keydown` fires on every character, so the flush defeated the debounce outright; `q` reached the URL as `hueod` mid-word.
- Narrowing `keydown` to Enter/Space fixed that, but `pointerdown` then still fires on the page's own controls. Clicking **Clear search** flushes the very text the click is about to clear, and the "reveals all remaining ledgers and resets the visible page after a search is cleared" case fails on it.

Excluding the component's own controls one by one would work, but it is the same hand-maintained list the current grid binding already is — inverted, and longer.

## What the next attempt should weigh

- The router's own seams do not help: `useBlocker` and `onBeforeNavigate` both run after the history entry has been decided, so neither can write into the entry being left. That is what forced a gesture-phase flush in the first place.
- A pointerdown alone does not say whether the gesture will leave the page, which is the real missing predicate.
- Worth considering instead: shorten or drop the debounce (writes already use `replace: true`, so history churn may not be the cost it was assumed to be), or commit on the field's own `blur`, which is a genuine "done editing" signal and fires before any link activation that follows.

The `blur` option looks cheapest and is not yet tested; it would make the flush intrinsic to the input rather than to whatever happens to surround it.

---

**Resolved 2026-09-20** — moved the flush onto the search input's own `blur`
and removed the grid binding, in
`features/user-profile/components/ledger-collection.tsx`. Shipped in `69cc1759`
(`dashboard`).

The `blur` option this note nominated as cheapest does not work on its own, and
failing it was the useful part. Clicking **Clear search** blurs the field
first, so the flush writes the very text the click is about to remove;
`updateSearch` resolves a tick later, and the sync-from-URL block then reads
that echo as an external navigation and restores the cleared text. Two existing
tests caught it immediately.

Rather than the exception list this note anticipated — and rejected — the fix
is at the seam that actually cannot tell the two cases apart. The component now
records the value it last wrote and declines to adopt its own echo, so an edit
made between the write and its arrival survives. Back/Forward still sync
normally, because those values were not written here. The flush then needs no
knowledge of what surrounds it, which is what the note was asking for.

Coverage: the test that recorded the gap as expected ("drops an uncommitted
query when leaving outside the results grid") is replaced by one proving it
closed, plus one for the clear-beats-flush race. Removing `onBlur` fails 4 of
the 15; removing the echo tracking fails 3, including the two pre-existing
clear-search cases. Verified live as well — typing then blurring inside the
250ms window writes `q` at 30ms, and type-then-Clear leaves no `q` with the
full list restored.

One departure is still lossy, for a reason outside this note and filed as
`w4/154`: the profile tab triggers navigate with `search: { tab }`, replacing
the whole search object, so leaving by a tab discards `q` after the flush has
written it — along with `sort`, `show` and `lang`.
