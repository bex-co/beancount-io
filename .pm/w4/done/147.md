# Radix keyboard navigation ignores the document's RTL direction

Reproduced while verifying w4/076, against the code at `a4e59cab`.

w4/076 gave the document its reading direction: `?lang=fa` now renders
`<html dir="rtl">` and the page lays out right-to-left. Radix primitives do not
follow it.

`@radix-ui/react-direction`'s `useDirection(localDir)` returns
`localDir || globalDir || "ltr"`, where `globalDir` comes from a
`DirectionProvider` context. The dashboard renders no `DirectionProvider`, and
`common/components/ui/tabs.tsx` passes no `dir`, so every Radix component
resolves to `ltr` no matter what the document says.

Reproduced at 1440×1000 on `/ledger/open_ledger/example/balance-sheet?lang=fa&time=2017`:

- the document is `dir=rtl` and the tab list renders right-to-left;
- focusing the first tab and pressing **ArrowRight** moves to the _next_ tab in
  DOM order — the same as in English — so the focus ring travels leftward,
  against the visual order.

The same page in English behaves correctly, which is the control.

Likely fix: render Radix's `DirectionProvider` with `i18n.dir()` at the root,
beside where the document direction is already set, so every Radix primitive
inherits the one source of truth rather than each call site passing `dir`.
Check the other Radix primitives in use at the same time — tabs, dropdown
menus, sliders, toggle groups and anything else reading `useDirection`.

Scope note: this is keyboard behaviour, not layout. w4/076 deliberately did not
expand into it, and no broader RTL layout audit is claimed here — only that
arrow-key order disagrees with the rendered order in right-to-left locales.

---

**Resolved 2026-09-20** — Fixed as the note proposed: a `DirectionProvider` fed by `i18n.dir()` now sits in `LocalizationProvider`, so every Radix primitive inherits the one source of truth instead of each call site passing `dir`. One correction to the reported symptom, from reproducing it at the exact URL: the tab list was **not** rendering right-to-left. Radix writes its resolved direction back onto its own root, so with `useDirection()` falling back to `ltr` the list computed `direction: ltr` inside a `dir="rtl"` document — its layout and its arrow keys agreed with each other and disagreed with the page. ArrowRight did move to the next DOM tab, but that tab was visually to the right, so the focus ring did not travel against the rendered order. The diagnosis in the note is exactly right; only the visible consequence differs, and it is a layout inconsistency as well as a keyboard one. After the change, measured on the same Persian balance sheet: the tablist computes `rtl`, the first DOM tab is now the rightmost, and ArrowLeft moves leftward — the visual reading order. English is unchanged (`ltr`, first tab leftmost), and on a Persian journal page no element carries a `dir` attribute overriding the document any more, which covers the other primitives the note asked about — dropdown menus included — since they all read the same context. `i18n/__tests__/radix-direction.test.tsx` adds four cases rendering a real `Tabs` inside the real provider: `useDirection()` reporting rtl for Persian, that direction reaching the tab list Radix renders, ltr still reported for English, and the direction following a language change rather than being fixed at mount. Three fail without the provider; the English control passes either way. One consequence worth recording: the shared test stub in `src/test/setup.ts` had no `dir()` on its mock i18n, so three unrelated suites broke the moment anything read it. The stub now implements `dir()` the way real i18next does rather than the component guarding against a missing one. Not done: no broader RTL layout audit, which the note explicitly does not claim. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 425 files, 4777 passed, 1 pre-existing skip — and `yarn build`). Shipped in `108e78b7` (`dashboard`).
