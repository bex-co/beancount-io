# A failed account deletion tells the user nothing at all, and its only two messages are the app's only hardcoded English strings

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: deleting an account is the most consequential thing a user can do in this app, and it is the one action whose outcome is not reported in their language — or, when it fails, reported at all. A user who types `sudo delete my account`, taps a destructive confirm, and lands back on an unchanged Settings screen has no way to tell whether their account is gone.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`. Report-only QA. **The mutation was never fired** — this is a source trace of `src/screens/setting/main-content.tsx:82-113`, reached by opening the Settings screen and reading the code behind its Delete Account row. Confirming it by experiment would mean deleting a real account.

## The two defects

`main-content.tsx:82-105`:

```ts
const handleDeleteAccount = async () => {
  try {
    const result = await deleteAccountMutation();
    if (result.data?.deleteAccount) {
      toast.showToast({ message: "Account deleted successfully", type: "success" });
      await actionLogout(session);
      router.replace("/auth/welcome");
    } else {
      toast.showToast({ message: "Failed to delete account", type: "error" });
    }
  } catch (error) {
    console.error("Delete account error:", error);
    toast.showToast({ message: "Failed to delete account", type: "error" });
  }
};
```

### 1. On failure, the screen does nothing observable

Both failure branches produce exactly one effect: a toast. No navigation, no inline message, no state change, no disabled row. The modal has already closed (`handleDeleteAccountConfirm` closes it before calling this), so the user is returned to an unchanged Settings screen.

That would be thin feedback under any circumstances. It is **no** feedback here, because **`w4/029` establishes that toasts do not render in this app at all** — confirmed on three independent call sites, in three sessions, with a pasteboard control proving the handlers ran. So today, a failed account deletion is visually identical to having never tapped the button.

The success path survives this only by accident: `actionLogout` + `router.replace("/auth/welcome")` is itself a loud, unmistakable signal. Failure has no such accident to fall back on.

The `catch` branch adds `console.error`, which reaches no user and — per `w4/028` — no crash reporter either, since Sentry is never initialized.

### 2. Three hardcoded English strings, and they are the only ones in the app

`"Account deleted successfully"` and `"Failed to delete account"` (twice) are string literals, not `t()` calls, in an app that ships **13 locales**. A Ukrainian or Persian user deleting their account gets English, if they get anything.

This is not a general i18n gap — it is a single exception in an otherwise complete discipline. A sweep of `src/` for user-facing literals found **exactly three**, all of them these:

```
$ grep -rn 'message: "[A-Z]' src/ --include='*.ts*' | grep -v __tests__
src/screens/setting/main-content.tsx:87:   message: "Account deleted successfully",
src/screens/setting/main-content.tsx:94:   message: "Failed to delete account",
src/screens/setting/main-content.tsx:101:  message: "Failed to delete account",
```

and `Alert.alert` with a literal first argument returns nothing anywhere in the tree. Every other string on this very screen — the alert body, both alert buttons, the modal title, message, placeholder and both button labels — goes through `t()`.

## Fix

1. Add `deleteAccountSuccess` / `deleteAccountFailed` to `src/translations/en.ts` beside the existing `deleteAccount*` block and call them through `t()`. The other twelve locales extend `en`, so they fall back safely until translated.
2. Give the failure path something that survives a broken toast. The cheapest honest option is an `Alert.alert` — this flow already uses one for the first confirmation, it is native chrome that cannot fail to render, and a failed deletion is exactly the kind of thing that warrants stopping the user. Do this **independently of `w4/029`**: a destructive action should not depend on the app's most fragile presentation layer for its only error report.
3. Surface `deleteAccountLoading`. It is already destructured from the mutation and used only to early-return from `onPress` (`:166`), so during the request the row looks completely idle — no spinner, no disabled styling. The guard prevents a second tap but tells the user nothing about why the first one appears to have done nothing.

**Acceptance:** with the mutation forced to return a falsy `deleteAccount`, the user sees a localized failure message that does not depend on the toast layer; the same holds for a thrown error; the success path is unchanged; and no literal user-facing string remains in `main-content.tsx`. Add a test that `handleDeleteAccount` reports on all three outcomes and that the success path calls `actionLogout` before navigating — the mutation is mocked, so this needs no real account.

Consider adding the literal-string sweep above as a lint rule while this is open; it found the only three offenders in the codebase, so the rule would start green.

## Blast radius

One screen, one handler, three strings, two new translation keys. No change to the mutation, the confirmation flow, or `actionLogout`. The suggested `Alert.alert` swap affects only the failure path — the success path must keep navigating rather than blocking on an alert the user has to dismiss.

**Not exercised, and deliberately so:** the deletion itself, in either direction. Everything above is read from source. Also not exercised: dark mode, enlarged Dynamic Type, Android, and whether the server's `deleteAccount` can return falsy in practice at all (if it only ever throws, defect 1 narrows to the `catch` branch — it does not go away).

## Adjacent states

The rest of this flow is **unusually careful** and should be recorded as verified, because it makes the gap above the exception rather than the pattern:

- Deletion is **two-step**: a native `Alert` with `cancelable: false` and a `destructive`-styled confirm, then a `TextInputModal` requiring the user to type `sudo delete my account` verbatim. `isConfirmDisabled` (`text-input-modal/index.tsx:187`) keeps the confirm button disabled until the phrase matches, and `handleConfirm` (`:181`) re-checks it. `handleDeleteAccountConfirm`'s own phrase check is therefore belt-and-braces — unreachable, but harmless, and I would leave it.
- **The confirmation phrase is correctly English in all 13 locales.** Every `deleteAccountConfirmPhrase` is the literal `sudo delete my account`, and every locale's `deleteAccountConfirmMessage` quotes that exact string inside its own translated sentence (checked in all thirteen files). Translating the phrase would have made it impossible to keep the message and the validator in sync; keeping it fixed is the right call and it was made consistently.
- The `Delete Account` row and the `Sign Out` button are both gated on `session &&`, so neither renders signed-out.
- The theme picker was exercised natively and behaves correctly, including the case I expected to fail: `onSelect` early-returns when the chosen value equals the current one (`:274`), but `Picker.handleDone` calls `hideModal()` after `onSelect` regardless (`picker/index.tsx:254-257`), so confirming an unchanged selection still closes the sheet. **Predicted a stuck modal here and was wrong** — verified on screen (`w4l88-02`, `w4l88-03`).

One thing checked and deliberately **not** filed here: the version row reads `1.20260906.47` while `main` is at `1.20260912.48`. That is a stale dev binary on the simulator, not a product defect.
