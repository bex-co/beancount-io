# Commit the print generation timestamp before native capture

**Minor · dashboard · 40 minutes.** A3: a shared statement's “Generated” footer should identify when it was printed. Production beancount.io, 2026-10-20 America/Los_Angeles (2026-10-21 UTC), owned isolated headless Chromium 155, English/System theme, fresh 1440×1000 and 390×844 guest contexts on public open_ledger/example Balance Sheet. Local main `670b592ae`; deployed main-D9qWGMxD.js, full deployment revision unverified.

## Reproduction and controls

1. Set only the page's Date/Date.now to 2026-10-20T17:00:00Z (10:00 AM PDT), load the report, and wait for the hydrated Export control and settled reads. The printable footer correctly says Oct 20, 2026, 10:00 AM.
2. Advance that browser-only fixed date to 17:30:00Z, leaving timers and the host clock running normally. Invoke Chromium's native headless A4 PDF pipeline directly, without opening Export or emulating print media first.
3. The first actual PDF still says 10:00 AM. Its beforeprint event sees the current 10:30 AM clock but the old footer DOM. After PDF capture, React commits the footer to 10:30 AM.
4. Print again without another clock change: the second actual PDF now says 10:30 AM. This same-day 390px repeat isolates event timing from date-boundary/report-period policy.

An independent 1440px run advances Oct 20 10:00 AM to Oct 21 10:30 AM: direct native PDF still prints Oct 20 10:00 AM. A fresh Export → Print / Save as PDF control prints Oct 21 10:30 AM correctly. That control uses the app action with a memory-only window.print stub, then the same headless PDF pipeline. All four three-page PDFs have extracted footer text; their final pages were rendered and visually inspected. Physical OS print dialogs/drivers and other browser engines remain unverified.

The report's As of October 20 snapshot and financial values remain unchanged in both paths, as intended. This finding concerns only generatedAt; do not redate the report period or refresh financial data at print time. No ledger writes or persistent browser preferences were changed. Extra contexts closed; the original QA tab and history were preserved.

## Cause and repair

`dashboard/src/features/reports/export/statement-export-menu.tsx:78–89` registers native beforeprint with a plain setPrintGeneratedAt. React batches the update, so capture can finish before it reaches the printable portal. The menu's handlePrint path at :154–164 already gives React a frame before window.print, explaining the passing control. `model.ts:441–448` refreshes only generatedAt.

Synchronously commit the generation timestamp at the native beforeprint boundary, keeping the scope bounded to this browser integration. React's [official beforeprint example](https://react.dev/reference/react-dom/flushSync) describes this batching failure and a flushSync integration. Preserve ready/loading guards, live document props, period/filter/amount snapshot semantics, and the existing menu path. No API, dependency or ledger-engine change is needed.

Add a meaningful regression that observes the printable DOM when beforeprint returns, before React act flushes pending work. The existing test at statement-export-menu.test.tsx:325 wraps dispatch in async act and checks only later prop updates; it cannot catch this capture race. Cover first native print after an idle clock advance, a second print, the menu control, later report props and pending-data portal removal. Verify the first actual headless PDF footer, then run dashboard format/lint/test/build.
