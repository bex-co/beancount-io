# In Persian the Accounts magnitude bars stay pinned to the physical left, under the balances instead of the labels — and indent backwards

**Severity:** minor. **Estimate:** 10–15 minutes. Owner: mobile. A3: Persian is the app's one right-to-left locale and the rest of its RTL work is unusually thorough — this is the one place the mirror fails, and it fails on the screen whose whole job is to show hierarchy.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, light, default text size, authenticated production session at `https://beancount.io`, `open_ledger/alphabet`. App locale forced to `fa` via the persisted `locale` key (method in `w4/063`) and restored afterwards. Report-only QA; no ledger mutation.

## Repro

1. Set the app to فارسی. The layout flips to RTL (see Adjacent states — it does this well).
2. Accounts tab (`حساب‌ها`). Rows render mirrored: account name on the **right**, balance on the **left**.
3. The green magnitude bars under `NonCurrent` and `Current` **stay on the physical left**, under the *balance* column.

Side by side, same ledger, same rows:

| | account label | magnitude bar |
| --- | --- | --- |
| `de` (LTR) | left | left, **directly under the label** ✓ |
| `fa` (RTL) | **right** | left, **under the balance** ✗ |

The bar's own style comment states the intent it no longer meets:

> `barTrack` — *"Magnitude bar, **aligned under the row's own label**."*
> and at the call site: *"**Under the label**, not the chevron: one more step past the indent."*

**The indentation also reads backwards.** The offset is derived from depth, so on the left edge a deeper row is pushed *further from the left* — `NonCurrent`'s bar begins about 24 pt in and `Current`'s about 41 pt in. In an RTL tree the deeper row should be further from the **right**. So the bars do not merely sit on the wrong side; their relative indentation inverts the hierarchy they exist to show.

## Root cause

`src/components/account-table/account-table.tsx:259-266`:

```tsx
{row.share > 0 && (
  <View
    style={[
      styles.barTrack,
      // Under the label, not the chevron: one more step past the indent.
      { left: GUTTER + (row.depth + 1) * INDENT_STEP },
    ]}
  >
    <View style={[styles.bar, { width: `${row.share * 100}%` }]} />
  </View>
)}
```

`left` is a **physical** edge. Everything around it is logical and therefore mirrors: the row is `{ paddingStart: GUTTER }` (`:275`), and the label's indentation is spacer views of `width: INDENT_STEP` inside a `flexDirection: "row"` row (`:94,104,107`), which React Native mirrors on its own. So the label moves and the bar does not.

**This is precisely the class of bug the codebase's own RTL decision was meant to expose.** `src/common/rtl.ts:75-87` turns React Native's `doLeftAndRightSwapInRTL` **off**, and explains why:

> *"That is the wrong default for this codebase now that the sites which mean leading and trailing say `start` / `end` outright: with the swap on, the sites that are deliberately physical get mirrored too, and those are exactly the ones coupled to geometry React Native does not mirror — `translateX`, an `onLayout` x, a `shadowOffset`."*

The rule that follows is: a site that *means* leading must say `start`. This one means leading — it wants to sit under the label — and says `left`. With the swap disabled, nothing rescues it.

## Fix

```tsx
{ start: GUTTER + (row.depth + 1) * INDENT_STEP },
```

One word. `start` resolves to the physical left in LTR and the physical right in RTL, which is exactly the bar's intent, and it makes the depth offset indent in the reading direction so the hierarchy reads correctly again.

**Check the fill direction in the same pass.** `barTrack` is `flexDirection: "row"`, which *does* mirror, so the `bar` child already grows from the track's leading edge. Once the track itself is anchored with `start`, track and fill should agree — but that combination has not been seen on screen and should be confirmed rather than assumed, since today's capture has a mirroring fill inside a non-mirroring track.

**Do not** fix it by re-enabling `doLeftAndRightSwapInRTL`. `rtl.ts` documents a real defect that caused (the time-range pills' sliding fill leaving the screen), and the pills still rely on the flag being off.

**Acceptance:** in فارسی, each magnitude bar sits under its own account label on the right-hand side, and a deeper row's bar is further from the right edge than its parent's; in English and every LTR locale the bars are pixel-identical to today; the fill still grows from the label side; and a row with `share === 0` still draws no bar. Add a render test asserting the track uses `start` — `flatten-rows.ts` has tests for `share` but nothing covers the row's layout.

## Blast radius

One style property in one component. `AccountTable` has a single production caller (`accounts-screen.tsx`), so the change cannot reach another screen.

**A sweep for the same mistake elsewhere found no second instance.** `grep -rn 'left:\|right:' src/ --include='*.tsx' --include='*.ts'` outside tests and generated code returns 28 lines; every one was read:

| shape | sites | verdict |
| --- | --- | --- |
| paired `left: 0, right: 0` (full-width stretch) | ledger-file-editor, edit-transaction, welcome ×2, receipt-capture ×3, picker ×2 | direction-neutral — fine |
| symmetric insets (`left: 16, right: 16`) | camera-view, preview-view | fine |
| `hitSlop` with all four edges | account-table:235 | fine |
| deliberately physical, documented | `time-range-pills:127` (`left: 0` paired with a measured `translateX`; the file explains it at length) | fine |
| explicitly branched on direction | `ledger-drawer:92-93` — `isRtlLayout() ? { right: 0 } : { left: 0 }` | **correct by construction** |
| physical `right` computed from a physical measurement | `menu-button:125,139` — `right: screen.width - (x + width)` from `measureInWindow` | **self-consistent**: the measurement and the position are both physical, so the menu tracks its anchor wherever the anchor is. Not a defect. |
| **physical `left` against logical siblings** | **`account-table:264`** | **this note** |

So the RTL discipline holds everywhere else and this is a single miss, not a pattern.

Not exercised: Android; enlarged Dynamic Type in `fa` (which grows the row and may change how visible the misplacement is, but not whether it happens); and an account tree deeper than two levels, where the inverted indent would be more pronounced.

## Adjacent states

**The RTL implementation is otherwise excellent and this note should not read as doubt about it.** Verified on device in Persian, first run of this locale in the QA session:

- The whole chrome mirrors: header title with bell and hamburger on the right, tab bar reversed (`خانه` rightmost), list rows with icon-right / amount-left, and the `دیدن همه` link carrying a correctly mirrored **left-pointing** chevron via `directionalIcon`.
- The Home range pills mirror **and the sliding selection fill lands on the right pill** (`6م`) — i.e. the `left: 0` + `translateX` arrangement that `rtl.ts` describes as having broken once is working.
- All three Home chart tabs fit in Persian, which matches the width audit in `w4/064` (`fa` is among the shortest locales).
- Persian strings render with correct shaping and the `ی`/`ه` ligatures intact throughout.

**The charts are deliberately *not* mirrored, and that is correct.** `rtl.ts:142-153` exports `LTR_PLOT` and explains: *"Time on a financial axis runs earliest-to-latest left-to-right in Persian interfaces as in every other, so mirroring one would invert the meaning of every trend line."* It is applied in the shared `chart-chrome.tsx:40`, so every chart inherits it while its header and legend mirror as text. On screen the Reports bar chart has its value axis on the left and `ژان…ژون` running left-to-right inside a fully mirrored card — which is the documented intent, **not** a defect, and is recorded here so a later pass does not file it as one.

**A second Persian pass (September 14) widened the survey and found no further RTL defect.** Transactions (`تراکنش‌ها`) mirrors completely — search magnifier on the right, filter icon on the left, Latin entry names pinned to the right/leading edge by `LEADING_TEXT_ALIGN`, amounts at the trailing edge, and the date header localized to Persian numerals (`۳۰ ژوئن ۲۰۲۶`). Transaction detail mirrors, including the Money flow card's `به` / `از` captions and its mirrored chevrons. The one fault seen there is **`w4/005`** reproducing in RTL, which is an existing open note and is amended there rather than refiled.

Three source-level RTL detectors were also run at HEAD `038faeeb` and each came back clean, which is why this note claims a single miss rather than a pattern:

| detector | result |
| --- | --- |
| directional Ionicons used raw instead of through `directionalIcon()` | **0 of 19** — every site is wrapped |
| `marginLeft` / `marginRight` / `paddingLeft` / `paddingRight` | **1** (`agent-screen/message-bubble.tsx:106`, a bubble inset on a disabled feature) |
| hardcoded `textAlign: "right"` | 8 sites, **all correct** — RN's `textAlign` is direction-aware on iOS, so `"right"` means the trailing edge in both directions; `rtl.ts:118-140` documents this and warns specifically against "fixing" it with an `isRtlLayout()` branch |

`LEADING_TEXT_ALIGN` itself is applied at roughly 110 sites across 30-odd files, covering every screen that renders ledger data in a `Text` wider than its content — the rule its own doc comment states.
