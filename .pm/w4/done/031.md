# Delta Dental gets the Delta Air Lines logo — one-word brand keys match any payee containing that word

**Severity:** minor — cosmetic, no data is wrong. **Estimate:** 40–60 minutes, most of it deciding the matching rule. Owner: mobile. A2/A3: the wrong company's mark appears beside a real payee in a finance app, and the three clearest cases (a dental insurer, a health insurer, a retirement fund) are among the most common entries in a US personal ledger.

Environment: branch `main`, HEAD `038faeeb`. Verified by running the shipped `matchBrand` over realistic payee strings; the account-glyph fallback was checked against real ledger data on `puncsky/example`.

## The defect

`matchBrand` (`src/common/brand-matcher/index.ts:185-207`) first tries an exact map hit, then falls back to a **substring search with word boundaries** — "Starbucks #1234" must match `starbucks`, which is the right motivating case. But 51 of the 132 curated keys are six characters or fewer, and several are ordinary English words or shared corporate names. A boundary-respecting substring match cannot tell which company a shared word belongs to.

Running the shipped logic:

| payee | resolves to | should be |
| --- | --- | --- |
| `Delta Dental` | **delta.com** (Delta Air Lines) | no logo |
| `United Healthcare` | **united.com** (United Airlines) | no logo |
| `Target Date 2040 Fund` | **target.com** (Target retail) | no logo |
| `United Way` | **united.com** | no logo |
| `Apple Farm Market` | **apple.com** | no logo |
| `Shell Company Filing` | **shell.com** | no logo |
| `Chase the Dream Cafe` | **chase.com** | no logo |
| `The Gap Between` | **gap.com** | no logo |

Delta Dental and UnitedHealthcare are two of the largest US insurers, and a target-date fund is the default retirement holding — these are not contrived. The same map is applied to **account leaf names** as well as payees (`resolveBrandDomain`), so `Assets:Retirement:Target Date 2040` is exposed the same way.

## Why the existing guard doesn't cover it

The word-boundary check is correct and does its job — verified, and the tests pin it:

```
matchBrand("targeted ads inc")  → null      // "target" followed by "e"
matchBrand("UnitedHealthcare")  → null      // no boundary after "united"
matchBrand("gapping expenses")  → null      // tested in the suite
matchBrand("nbp energy corp")   → null      // tested in the suite
```

So the sub-word case is handled. What is unhandled is the **adjacent-word** case: `Delta Dental` puts a real boundary after `delta`, so the guard passes and the wrong brand wins. `brand-matcher.test.ts` has 14 cases and every negative one is a sub-word collision (`gapping`, `nbp`); none is a legitimate two-word payee whose first word is a brand. The author clearly considered `gap` — they wrote `gapping expenses` — and stopped one case short.

## Fix — decide the rule, then apply it

The safest default is to **require the match to consume the whole payee after stripping transaction noise** rather than to match any token:

1. Normalize: lowercase, strip store/reference numbers (`#1234`, `*AB12345`), common processor prefixes (`SQ *`, `TST*`), and trailing punctuation.
2. Look the remainder up exactly. `STARBUCKS #1234` → `starbucks` → hit. `AMAZON.COM*AB12345` → `amazon.com` → hit. `Delta Dental` → `delta dental` → **miss**, which is correct.
3. Keep the current substring pass only for keys that are **multi-word or unambiguous** (`uber eats`, `whole foods`, `chick-fil-a`), where a shared-word collision is implausible.

That preserves every case the suite already pins while removing the whole adjacent-word class. If instead the substring pass is kept for single-word keys, the alternative is a curated negative list (`delta dental`, `united healthcare`, `united way`, `target date`, …) — workable but open-ended, and it will be wrong again for the next insurer.

Do not fix it by deleting the generic keys: `target`, `apple`, `chase` and `shell` are real merchants a user will have, and dropping them trades a wrong logo for a missing one.

**Acceptance:** `matchBrand("Delta Dental")`, `("United Healthcare")`, `("Target Date 2040 Fund")` and `("United Way")` all return `null`; `("STARBUCKS #1234")`, `("AMAZON.COM*AB12345")`, `("Spotify USA")`, `("Uber Eats")` and `("Uber")` are unchanged; `resolveBrandDomain` behaves the same way for an account leaf. Add the adjacent-word cases to `brand-matcher.test.ts` — that is the class with zero coverage today.

## Blast radius

Every row that shows a logo: the Transactions list, Home's Recent Transactions, the Merchants directory and merchant detail, and account rows via `resolveBrandDomain`'s leaf-name pass. Cosmetic only — no amount, account or date is affected, which is why this is minor despite being very visible.

**Not reproduced on-device against a live payee**, because none of the ledgers reachable from this session contains one of the colliding names; the table above is the shipped function run over realistic strings, which is sound for a pure function but is not the same as a screenshot. Worth confirming against a ledger that has a real `Delta Dental` entry.

## Adjacent states

The rest of the module is **well built and should not be disturbed**: keys are sorted longest-first so `uber eats` beats `uber`; the exact-match fast path runs before the substring pass; matching happens entirely on-device with a comment saying so; and `buildLogoUrl` points at the app's own proxy (`config.logoProxyUrl`) rather than logo.dev directly, so a payee name is never handed to a third party. `resolveBrandDomain` tries the payee first and then accounts in target-account priority order, which is the right precedence.

The account-glyph fallback was checked and is **correct**: the `Anthropic` row on `puncsky/example` renders a house, which looked wrong until BQL showed the transaction posts to `Expenses:Home:Internet` — the ledger files a Claude subscription under Home, and the glyph follows the account. No brand key matches `Anthropic`, `Internet` or `Checking`, so the fallback is doing exactly what it should.
