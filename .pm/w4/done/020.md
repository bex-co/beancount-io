# Below-fold Home and Reports surfaces carry no testID, so documented automation cannot verify them

**Severity:** minor (testability, not user-facing). **Estimate:** 25–40 minutes. Owner: mobile. A1/A2: `mobile/CLAUDE.md` tells agents to verify UI changes with expo-mcp "rather than asking someone to check by hand" — and for several screens that is currently impossible.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, expo-mcp automation. Report-only QA; no ledger mutation.

## The constraint, established empirically

**1. There is no scroll tool.** `tools/list` on the pinned expo-mcp returns exactly `expo_router_sitemap`, `open_devtools`, `collect_app_logs`, `automation_tap`, `automation_take_screenshot`, `automation_find_view`. `mobile/CLAUDE.md` says the same: *"Scrolling has no equivalent, so anything below the fold has to be reached by deep link rather than by swiping."*

**2. `automation_find_view` *can* see below-fold elements.** `picker-item-fa` resolves with `frame: {x:0, y:960, w:390, h:50}` and `is_hittable: false` on an 852pt-tall screen — off-screen, still reported.

**3. But it matches the accessibility *identifier* only, never the label.** Verified A/B on `puncsky/example`:

```
find_view {"testID":"home-add-menu-button"}  → FOUND,     label: 'Quick Add'
find_view {"testID":"Quick Add"}             → not found
```

The label is *returned* but is not a lookup key.

**Therefore: below-fold content is verifiable if and only if it carries a `testID`.** The app uses testIDs widely (94 occurrences across `src/` and `app/`), so the convention exists — it just stops short of these surfaces.

## What this blocks

These render only below the fold and have `accessibilityLabel` but **no** `testID`, so they can be neither tapped nor inspected:

| Surface | Source | Consequence |
| --- | --- | --- |
| Reports **Income/Expenses category breakdown** | `reports-screen/components/category-breakdown.tsx:248,328` — `accessibilityLabel={node.name}`, no testID | **Blocks verifying open `w3/216`**, whose entire subject is sign loss in this component |
| Home **Budget card** rows | `home-screen/components/budget-card.tsx:94` — `accessibilityLabel={row.account}`, no testID | Budget progress never verified on Home |
| Home **Spending card** | `home-screen/components/spending-card.tsx` — no testID, no label | Could not confirm the expected `$0.00` / `$102.00` for last/this month, which BQL says the ledger contains |
| Reports **account-transactions card** | `reports-screen/components/account-transactions-card.tsx:118` (an `EntryRow` caller) | Listed as "not independently reproduced" in `w4/013`'s blast radius for that exact reason |
| Discovery **`discovery-load-more`** | has a testID, but sits below the fold and needs a scroll to trigger naturally | `w4/done/m4`'s "pagination" DoD bullet stayed unverified |

Workarounds attempted this run and rejected on evidence: shrinking text to `content_size extra-small` (the chart cards are fixed-height — no extra rows appear), and choosing a near-empty time range so the Cash flow Sankey would collapse (it renders full height regardless).

## Fix

Add `testID`s to the below-fold rows and containers listed above, following the existing convention (`merchant-row`, `picker-item-…`, `discovery-open-…`): a stable identifier on each row, ideally keyed by the data it shows (`category-row-${node.name}`, `budget-row-${row.account}`, `spending-card`). Keep the existing `accessibilityLabel`s exactly as they are — they are the user-facing accessible names and must not be replaced by identifiers.

This does not make the content *reachable* by tap — that still needs a scroll gesture the tooling lacks — but it makes it **inspectable**, which is what verification actually requires: `automation_find_view` returns each row's label and frame, so an agent can assert the rendered values without seeing them.

Do not add testIDs indiscriminately across the app; the five surfaces above are the ones that have demonstrably blocked verification.

**Acceptance:** with the app on `puncsky/example`, `automation_find_view` resolves a Reports category row, a Home budget row and the Spending card without scrolling, each returning its accessible label; `w3/216`'s sign-loss claim becomes checkable from a QA session. Existing accessible names are unchanged, and `src/__tests__/accessibility-labels.test.ts` still passes.

## Blast radius

Test-only identifiers on five components. No user-visible change, no behaviour change. Not exercised: whether adding `testID` to a `FlatList`/`SectionList` row affects recycling (it should not — `merchant-row` already does this).

## Adjacent states

`automation_find_view` correctly reports `exists: false` for a control that is genuinely absent rather than merely off-screen — `home-add-menu-button` is not found on the read-only `open_ledger/alphabet` and is found on `puncsky/example`, which is the write-permission gating working, not a tooling failure. Distinguishing those two cases is why the A/B above was run on a ledger where the control exists.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for testID, testability, automation, scroll and expo-mcp terms. Nothing covers this. `w3/220.md` (open) asks for an accessibility **role and name** on `EntryRow` — a user-facing accessibility fix, not a test identifier, and on a different component. `w4/done/m7` added accessible labels app-wide but no identifiers. No overlap.

---

**Resolved 2026-09-14** in `fix(mobile): give below-fold Home and Reports surfaces test identifiers`. The accessible labels are unchanged.

- **Reports category breakdown.** Every row now carries `category-row-<account>`: top and child rows, expandable or not. The row is keyed by its full account rather than `node.name`, because leaf names repeat under different parents and the account is already the row's React key.
- **Home budget card.** Rows carry `budget-row-<account>-<currency>`, because a budget row is per account and currency, matching its key.
- **Cards.** `DashboardCard` forwards an optional `testID` to its root view. The Home spending card uses `spending-card`, and the Reports account-transactions card uses `account-transactions-card`.
- **`discovery-load-more`.** Not changed: it already carries a testID, and `automation_find_view` reports off-screen views. Triggering it still needs a scroll gesture the tooling lacks, as the note says.
- **Guardrail.** `src/__tests__/below-fold-test-ids.test.ts` checks every identifier above and that the existing labels are still present. With the identifiers reverted, its 4 tests fail. The mobile gate passes: `format:check`, `lint`, `test:unit` (1828 passed), and `typecheck`.
- **Not exercised in this session.** The live `automation_find_view` lookups on `puncsky/example` named in the acceptance, and `w3/216`'s sign-loss check that they unblock.
