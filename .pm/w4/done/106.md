# Show initial social-list failures instead of claiming an empty profile

Severity: minor. Estimate: 60 minutes, dashboard. A2/A3: public visitors should distinguish unavailable community data from an empty community and recover without reloading the whole profile.

Environment: production https://beancount.io, September17 local / September18 UTC2026; isolated headless Chromium149.0.7827.55, English/light, signed out, public synthetic open_ledger profile. Fresh390×844 and1440×1000 contexts. LocalHEAD26d54a9d; fetchedorigin358ba4dc has no dashboard differences. Deployed main-BIr0jJni.js; exact deployment SHA unverified.

Reproduce:

1. Open `/ledger/open_ledger?lang=en` in a fresh context. Intercept only the browser POST `/api-gateway/` whose GraphQL operation is GetUserFollowers, and abort it with a network failure. Keep GetUserProfile and all other reads live.
2. Choose Followers. The request variables are username=open_ledger, page=1, limit=20.
3. After loading settles, the panel says **No followers yet**, with zero retry buttons; the separate successful profile read still gives **Followers (142)**. Reproduced from fresh desktop and narrow sessions.
4. In the desktop context, independently abort the first GetUserFollowing and GetUserStarredRepos reads and select each tab. They settle to **Not following anyone yet** and **No starred repositories**, respectively, with no failure state.

These are deliberately induced client transport failures, not a claim that production had an outage. No payload was replaced with a synthetic empty success. Controls: removing the interceptor and reloading Followers returns20 cards and Show more; Following returns1 card; successful Starred legitimately stays empty. Counts can grow over time. Earlier live page-two failure checks in this run retained the first20 followers and exposed retry correctly.

Root: `dashboard/src/features/user-profile/hooks/use-paginated-social-list.ts:83` reads Apollo error; :157 returns it, and all three wrapper hooks expose error. `components/user-profile-tabs.tsx:116–143` discards those initial errors while consuming loadMoreError. Its empty branches at217,254,291 check only loading and array length, so failed first reads are treated as successful empty reads. Wrappers also omit the common hook's refetch. All three hooks have this one production component consumer. Original empty branches date to af5339de; 96fa94b2 added continuation/error handling for later pages but retained this omission.

Fix: consume each first-page error and show an accessible localized failure with a working retry, exposing the existing refetch through wrappers as needed. Only show the empty message after a successful empty result. Retry must use the current username/tab and avoid duplicate requests; preserve lazy loading, pagination identities, existing loaded rows and continuation retry behavior. Use existing shared error/retry translations where appropriate. No backend or REST/GraphQL/MCP contract change is needed for this reproduced transport failure.

Add meaningful UI tests for initial failure → retry → nonempty success and successful empty success, covering all three branches, plus preserve existing continuation failure behavior. Verify keyboard retry and both viewport sizes. Keep profile counts independent of the list's returned page size.

Producer boundary: query documents are `dashboard/src/graphql/query/user-profile.graphql:35,47,59`. Backend resolver delegates to user-profile/service/user-profile-service.ts:355,387,419. Those service methods have a separate catch-to-empty behavior for upstream Gitea failures; no upstream outage was induced or reproduced here, and changing that behavior is outside this dashboard-only note. Do not claim the frontend can detect an error that the server serializes as a successful empty result.

Dedupe: searched all queues including done/blocked for followers, following, starred, initial social errors and first-page failures. Completed w3/m21 owns pagination and later-page failures; this initial-read omission remains in current source. w3/done/104 and107 own social-write/navigation behavior; w4/m17 owns profile search navigation. No overlapping open repair found, and origin has no pending source fix.

Evidence: `dashboard/tmp/qa-20260917/profile-initial-read-failure.json` contains sanitized operation names/variables, failure panel text and recovery counts; `profile-initial-followers-failure-390.png` was visually inspected. No follower identities, cookies or credentials saved in these artifacts. Authenticated profiles, live server GraphQL-error responses and upstream Gitea failures remain unverified. No follow/star mutation or product-code edit performed.

**Resolved 2026-09-19** — `use-paginated-social-list.ts` already returned both
`error` and `refetch`, but the three wrapper hooks dropped `refetch` and
`user-profile-tabs.tsx` consumed only `loadMoreError`. Its empty branches
checked just `loading` and array length, so a failed first read rendered "No
followers yet" — beside a `Followers (142)` count from the separate, still
successful profile read — with no retry short of reloading the page. Following
and Starred behaved identically.

Each panel now renders an accessible failure with a retry when its first read
fails, and keeps its empty message only for a read that genuinely succeeded
with no rows. The retry calls the paginated hook's own `refetch`, which already
carries the current username and page 1, so it cannot duplicate or mistarget
the request; the wrappers now expose it. Lazy loading, pagination identities,
already-loaded rows and the continuation failure path from `96fa94b2` are
unchanged, as are the profile counts, which come from a different read. The
first-page message is a new key rather than the continuation's "Could not load
more results.", translated across all fifteen catalogs, and the retry reuses
`common.tryAgain`. Nothing changes in the resolver or its catch-to-empty
behaviour for upstream Gitea failures, which the frontend cannot detect.

Fifteen cases in
`user-profile/components/__tests__/social-list-initial-error.test.tsx` cover all
three branches: the failure replacing the empty message, retry followed by a
non-empty success, a genuinely empty success, a keyboard retry through the
rendered button, and a continuation failure still reported separately. Nine
fail without this change while the empty-state and continuation controls keep
passing. Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test`
(397 files, 4455 passed, 1 pre-existing skip) and `yarn build` all pass.
