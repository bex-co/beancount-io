# `amount-step-precision` loses focus intermittently under full-suite load

Severity: minor test-infrastructure flake. Package: dashboard. Estimate: ~40m — reproduce under load, fix the real nondeterminism, confirm with repeated runs.

`dashboard/src/features/journal/components/new-directive-dialog/__tests__/amount-step-precision.test.tsx`, the case "accepts Transaction 0.001/-0.001 on Enter while a posting amount stays focused", intermittently fails at its `expect(amounts[1]).toHaveFocus()` assertion (around line 132). The posting amount input is expected to hold focus after `user.click`, but focus is observed on the Payee input instead.

Observed 2026-09-19 while running the w4/m16 gates, and confirmed nondeterministic rather than caused by that work:

- One full `yarn test` run reported it as the only failure, 375 of 376 files passing.
- The same file passes in isolation.
- The clean tree at `479cc1f6` passed 376/376.
- A second full run of the identical working tree passed 376 files and 4,238 tests.

Same code passing and failing across runs is nondeterminism. The w4/m16 change that was in the tree touches only `features/reports/cash-flow/`, which shares no module with the journal directive dialog, so the coupling is scheduling and timing under parallel load rather than behaviour.

Likely shape: a focus assertion racing an async state settle or an autofocus effect in the dialog, which only loses the race when the worker is contended. Worth reproducing with repeated runs under load rather than in isolation, fixing the actual race — awaiting the settle the dialog performs, rather than adding a sleep — and confirming with a run of consecutive green passes.

This is recorded because an intermittent failure in the shared gate will eventually block an unrelated ship, and because the next person to see it should not have to re-derive that it is unrelated to whatever they were changing.

**Resolved 2026-09-20** — Fixed the race rather than papering over it. The transaction form focuses Payee on a 150ms timer after mount (`transaction-form.tsx`); the case clicked a posting amount and asserted focus synchronously straight afterwards, so whenever that timer was still pending it fired between the click and the assertion and pulled focus to Payee. The test now waits for the mount focus to land on Payee before taking focus, which is the settle the dialog itself performs — no sleep, no fake timers, no change to the component. The mechanism was demonstrated rather than assumed, after a first model of it proved wrong: simply lengthening the timer does not reproduce the failure, because a later timer just moves the steal past the assertion. What does reproduce it is a pending timer allowed to fire after the click — with that, the pre-fix test fails on exactly the reported assertion and the fixed test passes, since no timer is left pending. Three consecutive full runs are green (4753 passed, 1 pre-existing skip). Checked and not affected: the Balance case in the same file asserts focus too, but `balance-form.tsx` has no mount focus timer, and `transaction-form.tsx` is the only directive form that sets one. Not done: no attempt was made to reproduce the original low-rate failure by running the whole suite repeatedly under contention — the deterministic pending-timer reproduction above is the evidence, and the three clean runs are a confirmation rather than a proof of absence. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` and `yarn build`). Shipped in `485eb9d3` (`dashboard`).
