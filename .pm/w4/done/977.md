# Let the shared Dialog hold dismissal while a write is pending

**Severity:** maintenance, no customer-visible defect. **Estimate:** 45–60 minutes, dashboard. **A2:** dialogs that save should behave the same way while a save is pending.

Six dialogs now copy the same one-line guard that ignores `onOpenChange(false)` while a write is pending:
- `new-directive-dialog/index.tsx` (w4/m33);
- `open-account-dialog.tsx` and `add-budget-dialog.tsx` (w4/m42);
- `api-key-create-dialog.tsx`;
- the Change Name and Change Username dialogs in `user-profile-section.tsx` (w4/m47).

They handle the Close (X) button differently. `api-key-create-dialog.tsx` hides it with `showCloseButton={!loading}`. The others leave it enabled, so it does nothing while Cancel shows as disabled. `dashboard/AGENTS.md` now states the guard as a convention, which suggests the primitive should own it.

Proposal: give the shared wrapper in `dashboard/src/common/components/ui/dialog.tsx` a `busy`/`dismissible` prop. It would drop `onOpenChange(false)` and disable the X button, whose class already carries `disabled:pointer-events-none`. Then migrate the six callers and shorten the AGENTS.md bullet. Precedent: w4/292 put the composing-Escape guard in the same wrapper.

Acceptance:
- Every caller keeps its pending behavior: Escape, outside click and Close all wait, while idle dismissal and focus restore still work.
- The X button presents as unavailable while a write is pending.
- Existing pending suites pass: New Entry, Open Account, Add Budget, profile, API key.
- Run the dashboard format:check, lint, test and build gates.

Source: the w4/m47 `/simplify` altitude review (see [m47 t004](./m47/done/t004.md)), skipped there as out of the bounded scope.

**Resolved 2026-10-22** — `DialogContent` (`common/components/ui/dialog.tsx`) takes `busy`. While it is set, Escape, a pointer press or focus outside, and the close button all wait, and the X is disabled and presents as unavailable. The composing-Escape guard is kept. Six dialogs pass `busy={pending}` and drop their copied `onOpenChange(false)` guards: New Entry, Open Account, Add Budget, Create API Key (whose X is now disabled rather than hidden), Change Name and Change Username. Their Cancel buttons already lock with their fields, and the dashboard AGENTS.md write-lock rule names the prop. `dialog-busy.test.tsx` checks that Escape, an outside press and the disabled X dismiss nothing while busy, and that each closes once idle; the busy case fails on the old wrapper. New Entry's two m33 focus tests now assert the unavailable X and the dialog's focus trap in place of a focusable inert one. The existing New Entry, Open Account, Add Budget, profile and API key suites pass. Native checks against the local fixture API held the write in New Entry (Note) at 1440 and 390 and in Add Budget at 1440. During each hold the X was disabled and Escape, an outside click and a forced X click left the dialog open. After the failed write, the X was enabled and Escape closed the dialog. No page errors, and every write was aborted before transport. Shipped in `8a6067001` (`dashboard`).
