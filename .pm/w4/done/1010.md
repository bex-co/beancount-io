# Keep keyboard position when removing a transaction posting

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** dashboard, `features/journal/components/new-directive-dialog/transaction-form.tsx`. **A2:** a person removing an extra posting should continue editing the remaining postings without traversing the entry dialog again. Treat this as a remaining keyboard-continuation case of [967](./967.md), not another historical finding group.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-22 America/Los_Angeles; owned isolated headless Chromium155.0.8059.85, English/light, UTC browser clock, QA owner of its designated disposable synthetic ledger. Fresh1440×1000 and390×844 New Entry → Transaction dialogs reproduce. Only unsaved local drafts were edited; zero mutation attempts or hosted writes.

1. In Journal → New Entry → Transaction, leave the accounts blank and enter Posting1 amount **−12.50** and Posting2 amount **0**. Activate **Add posting** once, then enter Posting3 amount **12.50**. This is an unfinished draft, not an accepted transaction.
2. Focus the named **Remove posting2** button and press Enter. The correct middle row disappears; the remaining amounts are exactly **−12.50 /12.50**, now labelled Posting1/Posting2.
3. Focus is on the **DIV role=dialog**, not a surviving posting control. The next native Tab reaches **Transaction**, the first tab at the top of the dialog. Both fresh widths reproduce. The screenshot shows this restart; no amount loss is alleged.
4. An independent fresh desktop control removes the **last** of three rows. It preserves the other amounts **−12.50 /0** but again focuses the dialog container. Manually focus Posting2 amount, select its contents with Cmd+A and type **12.75**: the exact value is accepted and remains focused. The remaining controls work after a manual return.

## Cause and bounded repair

`transaction-form.tsx:369–373` defines removePosting as only a length check plus `remove(index)`. The field.id-keyed rows and the button around593–604 remove the focused node without selecting a surviving target. The installed Radix focus-scope1.1.7 mutation observer (`dist/index.js:88–93`) explains the observed fallback: removing the active node leaves body focused, so the trapped scope focuses its container. Repair the form's own removal handoff; do not change Radix or the global Dialog policy.

After an explicit removal, focus an appropriate surviving posting field, preferring the row that moves into the removed position and falling back to the previous row for a last-row removal. Wait for the remaining field-array DOM and numbering to settle. Keep the handoff scoped to the removal action. Preserve remaining accounts/amounts/currencies, exact auto-balance, the minimum of two visible rows, pending-submit locking, automatic blank-row addition and967's explicit Add focus repair. No persistence, confirmation dialog, new dependency, API or backend change is needed.

Acceptance: real owning-form keyboard removal of first/middle/last rows, including3→2 and a longer list, retains all other field values and focuses the intended surviving posting. Immediate typing edits that field; Tab continues within the posting workflow rather than restarting at Transaction. Cover pointer removal and ordinary native traversal as controls, repeat desktop/narrow, and run the dashboard gates when implementing. No product code or tests were authored by QA.
