# Browse ledgers throws away the search query when you switch tabs — at exactly the moment you switch to widen the search

**Severity:** minor. **Estimate:** 10–15 minutes (a two-line deletion, then verify). Owner: mobile. A3: finding a public ledger is how a newcomer first sees what Beancount.io holds. The commonest reason to move from **Your ledgers** to **Explore** is "it isn't here, look wider", and that is the one action that discards what was typed.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`. Report-only QA; **no star was toggled** and no ledger selection was changed.

## Repro

1. Open `beancount:///(app)/ledger-selection`. **Your ledgers** is selected; the search field sits **below** the tab row, so it reads as belonging to the screen rather than to one tab.
2. Type `alpha`. The list empties to *"No ledgers match your search."* — correct; neither owned ledger matches.
3. Tap **Explore**.
4. The field is **empty**, showing its `Search ledgers` placeholder, and the unfiltered Explore list renders (`adobe`, `adyen`, `airbnb`, `alphabet`, `amazon`, …).
5. Retype `alpha`. `open_ledger/alphabet` is found immediately, with its description and a `Public · Current` badge.

So the ledger the user was looking for **was** one tab away, and the app made them type the query twice to find out.

## Root cause

`ledger-selection/index.tsx:201-204` — the tab `Pressable` clears both the query and its debounced copy:

```tsx
onPress={() => {
  setTab(value);
  setQuery("");
  setDebounced("");
}}
```

There is **one** `TextInput` (`:213`) bound to **one** `query` state, rendered once outside the tab content. Nothing about the layout suggests the field is per-tab, and it isn't — it is shared state that is deliberately reset.

## Fix

Delete the two resets. The existing wiring already carries a query across tabs correctly, so nothing else has to change:

```ts
const remoteQuery = tab === "explore" ? debounced : "";
useEffect(() => { void store.load(tab, remoteQuery); }, [store, tab, remoteQuery]);
```

- **Yours/Starred → Explore** with `debounced === "alpha"`: `remoteQuery` becomes `"alpha"`, the effect's dependency changes, and the server search fires for it. `waitingForSearch` is already false (the debounce settled on the previous tab), so the list does not sit in a skeleton waiting for a timer that will not fire.
- **Explore → Yours/Starred**: `remoteQuery` becomes `""`, the tab reloads unfiltered, and `filterLedgers(state.items, query)` applies the carried query locally. Also correct.

Both directions work because the local and remote paths already read the same `query`. I checked this against the code rather than assuming it; it is the reason this is a deletion rather than a rewrite.

While in here, note that the tab is changed in **two** places with different behaviour: the tab bar (above, clearing) and the Starred empty state's "Explore" link (`:334`), which calls `setTab("explore")` bare. They agree today only because that link renders solely when `!query.trim()`. After the fix they agree unconditionally, which is one fewer invariant to hold.

**Acceptance:** typing `alpha` on Your ledgers and tapping Explore shows `open_ledger/alphabet` without retyping; the field still shows `alpha`; tapping back to Your ledgers shows "No ledgers match your search." with `alpha` still present; the `✕` still clears; an empty query on any tab still lists that tab in full. Add a test that the tab handler preserves `query` — `ledger-selection` has no test for its tab/query interaction today.

If clearing turns out to be intended (nothing in the code says so — there is no comment, and this screen is otherwise well commented), then the field should move *inside* each tab's content, or gain a per-tab placeholder, so the reset stops looking like data loss.

## Blast radius

One screen, two deleted lines. No change to `useDiscovery`, the store, the debounce, or `filterLedgers`. The three tabs use two different search mechanisms — Explore queries the server with the debounced term, Yours/Starred filter the loaded list client-side — and the fix respects both rather than unifying them.

Not exercised: starring from this screen (needs write authorization and would have to be restored), the Starred tab's populated state (this account has none), dark mode, enlarged Dynamic Type, and Android.

## Adjacent states

Verified correct in the same pass, and several of these are things that are commonly wrong:

- **No stale-result flash.** `ListEmptyComponent` renders the skeleton while `state.loading || waitingForSearch`, and `items` is forced to `[]` during `waitingForSearch`, so the previous tab's results never show under a new query.
- Search is case-insensitive and matches on the ledger id.
- The empty states are distinct and correct: `discoveryNoMatches` when a query is present, `discoveryEmpty_<tab>` when it is not, and `discoveryLoadError` on failure — each with its own icon (`search-outline`, `star-outline`, `cloud-offline-outline`).
- The currently selected ledger is marked `Public · Current` in the Explore list, which is genuinely useful on a long list.
- `accessibilityRole="tab"` with `accessibilityState={{ selected }}` on each tab; `accessibilityLabel` on both the field and the clear button.
- **This screen carries `testID`s** — `discovery-tab-yours|starred|explore` and `discovery-search` — which is worth recording next to `w4/020`, since the Transactions header (`w4/048`) has none at all. The good pattern already exists in the codebase.

Confirmed here as a **second instance** of the open `w4/007`: rows whose ledger has no description render a blank line where it would go, so `puncsky/example`, `adobe`, `adyen`, `airbnb` and `amazon` each show a gap between the id and `Public`/`Private`, while `alphabet` and `minimax` fill it. Not re-filed.
