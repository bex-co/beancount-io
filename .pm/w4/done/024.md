# `shortNumber` formats the zero tick as "$0.0" and rounds past its own suffix ("1000.0K")

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: one of the two defects is visible on every chart axis in the app; the other is frozen in place by a test that asserts the wrong answer.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, dark appearance, `open_ledger/alphabet`, Reports at 6M. Verified on screen, by running the shipped `shortNumber` logic directly, and by `yarn test:unit` (**1769 passed**, so the expectation below is live, not stale).

## Defect 1 — the zero tick reads "$0.0" while every other tick has no decimal

Reports → 6M on `open_ledger/alphabet`, income/expense chart. The Y axis reads, top to bottom:

```
$200B   $150B   $100B   $50B   $0.0
```

`shortNumber` drops the decimal for whole values at or above 1000 (`1e3 → "1K"`, `5e10 → "50B"`) but always applies `toFixed(1)` below it (`number-utils.ts:16-18`), so the zero tick alone carries a `.0`. Zero is a whole number and should render `"0"`.

Fix: apply the same "whole numbers lose the decimal" rule below 1000 that the suffix branch already applies above it. Both branches then agree, and the axis reads `$0`.

This is the manifestation that is actually **seen**: axis ticks come from `scale.ticks()` and are drawn by `scrollable-axis-chart.tsx:78` and `bar-chart-d3.tsx:89`.

## Defect 2 — rounding past the suffix

`src/common/number-utils.ts:28-39` selects the suffix from the raw magnitude and *then* rounds, so a value just under the next threshold rounds up past the suffix it was chosen for:

```
      999949  →  999.9K     ✓
      999950  →  1000.0K    ← should be 1.0M
      999999  →  1000.0K
     1000000  →  1M         ✓
   999999999  →  1000.0M
999999999999  →  1000.0B
     -999999  →  -1000.0K
```

The window is `[999_950, 999_999.99]` at each magnitude — values whose one-decimal rounding reaches 1000.

## The test is the real problem

`src/common/__tests__/number-utils.test.ts:81-85`:

```ts
it("handles boundary values", () => {
  expect(shortNumber(999)).toBe("999.0");
  expect(shortNumber(999999)).toBe("1000.0K");
  expect(shortNumber(999999999)).toBe("1000.0M");
});
```

Every neighbouring case in the file is a "formats X correctly" assertion with an obviously right expectation (`1000 → "1K"`, `1500000 → "1.5M"`). This one is pure characterization: it asserts what the code happens to do, with no comment claiming the output is intended, and "1000.0K" is not an output anyone would choose. A correct fix makes the suite fail, which is backwards.

## Fix

Round first, then pick the suffix — or promote when the rounded value reaches 1000:

```ts
const shortNum = absNum / value;
if (shortNum >= 999.95 && i < suffixes.length - 1) continue; // let the next suffix take it
```

Cleaner: compute the rounded string, and if it starts `1000`, re-run against the next suffix up. Either way, keep the existing "drop the decimal when whole" rule (`1000 → "1K"`, not `"1.0K"`), which the other tests correctly pin.

Then **rewrite** `handles boundary values` to assert the right answers (`999999 → "1.0M"`, `999999999 → "1.0B"`) rather than deleting it — the boundary is exactly the case worth testing. Add the largest suffix's own edge: above `1e15` there is nothing to promote to, so `999999999999999999` must stay `"1000.0Q"` and not fall through.

**Acceptance:** the Reports 6M axis on `open_ledger/alphabet` reads `$0` rather than `$0.0` with the other ticks unchanged; `shortNumber(999999)` is `"1.0M"`, `shortNumber(999999999)` is `"1.0B"`, `shortNumber(-999999)` is `"-1.0M"`; every existing non-boundary expectation is unchanged, and `yarn test:unit` passes.

Note that `handles zero correctly` (line 39) and `handles very small positive numbers` currently assert `shortNumber(0) === "0.0"` and `shortNumber(0.01) === "0.0"`; fixing defect 1 changes the first to `"0"` and leaves the second, since `0.01` is not whole. Update them deliberately rather than preserving `"0.0"` to keep the suite green.

## Blast radius

Callers split into two groups, and the two defects land in different ones:

- **Axis ticks** — `src/common/d3/scrollable-axis-chart.tsx:78`, `bar-chart-d3.tsx:89`. Drawn on screen. Tick values come from d3's `scale.ticks()`, which emits round numbers, so these **cannot** reach defect 2's window — but they always include zero, so they hit **defect 1 on every chart in the app**.

These format **real data**, so they can reach defect 2's window — and they are announced by VoiceOver rather than drawn.

**Resolved 2026-09-14** in `fix(mobile): drop whole-number decimals and promote rounded short numbers`.

**Rule.** `shortNumber` now picks the suffix the magnitude reaches, then promotes it when one-decimal rounding would show 1000 of it. Whole values lose the decimal at every magnitude, below 1000 as well as above.

**Axis labels.** Ticks read `$0`, `$50` and `$200B`.

**Boundaries.**

| input | output |
| --- | --- |
| `999999` | `1.0M` |
| `999999999` | `1.0B` |
| `-999999` | `-1.0M` |
| `999.96` | `1.0K` |
| `999949` | `999.9K` |

Non-whole small values keep their decimal: `0.01` is `0.0`, `-0.01` is `-0.0`, and `999.4` is `999.4`.

**Deviation.** The note expected `999999999999999999` to stay `1000.0Q`. As a double that literal is exactly `1e18`, a whole 1000 Q, so it reads `1000Q`. The test pins `1e18 → 1000Q` and `1234.5e15 → 1234.5Q`: the largest suffix never promotes or falls through.

**Tests updated deliberately.** The whole-number expectations in `number-utils.test.ts`, `utilities.test.ts` (`12` rather than `12.0`) and `budget-labels.test.ts` (`Actual $400 of $500`) changed, the characterization in `handles boundary values` was rewritten, and promotion and largest-suffix cases were added. With the old function restored, 6 `shortNumber` tests fail. The mobile gate passes, with 1831 unit tests.
