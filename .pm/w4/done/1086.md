# Translate existing import errors when the language changes

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** dashboard. **A2:** a customer choosing German should receive existing import-configuration guidance in German, without submitting the same invalid form again.

## Reproduction and controls

Production `https://beancount.io`, owned isolated headless Chromium156.0.8078.47, authenticated QA owner, disposable synthetic ledger, English/light/UTC initially. Two independent fresh1440×1000 runs reproduce this journey using actual local CSV parsing and healthy API reads, with no modeled response:

1. Smart Import → upload the two-row synthetic Date/Payee/Description/Amount fixture. In Preview, edit row1's amount to `oops`; it correctly shows **Amount must be a valid number**. Continue with the valid2.50 companion row.
2. Configure: retain USD, assign `Assets:Bank:Checking` as the companion's target, leave Source Account empty, and activate **Import1Transaction**. Validation correctly refuses it. Source is `aria-invalid=true`, and its description resolves to **Source account is required**.
3. Through the desktop User menu, choose Dark, then Language → Deutsch. The URL becomes `?lang=de`, document language is de, and the same connected source control is labeled **Quellkonto**. The rest of Configure is German, but its visible alert and associated description still say **Source account is required** after800ms.
4. Activate **1Transaktion importieren** while source remains empty. Only then does the same error become **Quellkonto ist erforderlich**. Both rejected submissions make zero mutation attempts.

A third fresh390×844 draft reproduces the retained English error after the same language choice: widen only to1440 to access the desktop menu, then return390 before inspecting it. The narrow screenshot was visually inspected. This is responsive-crossover coverage; the mobile avatar navigates to Settings and is not claimed to provide that in-place menu.

Working controls in all three contexts: Dark and German preserve the same source node, empty source, USD, target account and row eligibility. The error's ARIA relationship remains intact. Back returns to both original rows, including unchanged `oops` and `2.50`; Preview's corresponding amount diagnostic correctly reads **Betrag muss eine gültige Zahl sein**. The German catalog and subsequent validation therefore work. No accepted invalid import, draft loss or parsing defect is claimed.

All three contexts closed. Zero mutations, AI calls, hosted writes, modeled responses, page exceptions or console errors. No final valid Import is activated.

## Cause and bounded repair

`dashboard/src/features/importer/components/steps/configure/transaction-config-form.tsx:69–114` resolves catalog keys into translated strings when building its Zod schema. `useForm` at:135–138 receives that resolver, but the already-stored error is not refreshed on language changes. `common/components/ui/form.tsx:169–187` renders `String(error.message)` directly. The Source Account FormMessage is correctly present at:302; its error text is simply from the earlier validation.

The actual served react-hook-form module matches installed `dist/index.esm.mjs` byte-for-byte. Its resolver execution at:1620–1638 and submit path at:2176–2178 replace stored errors on validation; its options setter at:2453–2458 only updates options. Replacing a schema on render does not translate an error already stored. In contrast, Preview's schema stores validation keys and `editable-preview-row.tsx:82–83` translates the displayed message with the current locale, matching the passing native control.

Keep displayed Configure errors synchronized with the current language while retaining values, error identities and focus. Store translation identities until presentation, or quietly refresh only exposed validation messages on a locale change. Do not reset/remount the import draft or demand another submit. Keep untouched fields quiet, existing field associations, invalid-submit refusal and target/selection retention. The existing15 catalogs already contain the required key; no new dependency or API behavior is needed. ConfigureStep is this form's sole production caller. Other Configure constraints are compatibility scope; other forms and shared FormMessage consumers are audit context, not additional reproduced bugs.

Acceptance: render the real Configure form with real localization, trigger its required-source error, change language, and observe the translated existing message without editing/resubmitting or losing source/currency/targets/selection. Preserve successful new-language validation, repair/error removal, Preview's translated-key control and idle appearance changes. Repeat the desktop journey and documented narrow crossover; run dashboard gates when implementing.
