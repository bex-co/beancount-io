# Live GraphQL queries select fields nothing reads — including two unused time-series per account

**Severity:** trivial. **Estimate:** 30–45 minutes for the sweep (delete selections, re-run `yarn codegen`, confirm the suite). Owner: mobile. A2: several of these sit on hot paths — app start, every ledger switch, every account opened — and the server has to compute them before they are thrown away.

Environment: branch `main`, HEAD `038faeeb`. Static; no device interaction.

## The sweep

Every selected field across all 42 `.graphql` documents (194 distinct names) was matched against every reference in `src/` and `app/`, excluding `src/generated-graphql/` and the documents themselves. Excluding the seven wholly-unused operations already filed as `w4/025`, these fields are selected by **live** queries and referenced nowhere:

| document | selected but never read |
| --- | --- |
| `accountReport.graphql` | **`accountBalanceData`**, and **`intervalTotalsData`** (see below) |
| `getLedger.graphql` | `options { nameAssets, nameEquity, nameExpenses, nameIncome, nameLiabilities, operatingCurrency }`, `httpUrl`, `sshUrl`, `updatedAt` |
| `listLedgers.graphql` | `httpUrl`, `sshUrl`, `updatedAt` |
| `createLedger.graphql` | `httpUrl`, `sshUrl`, `updatedAt` |
| `getLedgerDirContent.graphql` | `lastAuthorDate` |
| `getLedgerJournal.graphql` | `is_empty` |
| `getFeed.graphql` | `authorAvatar` |
| `queryShell.graphql` | `resultType` |

**The sharpest one is `accountReport`.** It selects three parallel `{ date, balance }` series — `linechartData`, `intervalTotalsData`, `accountBalanceData` — and the app reads **one**. `linechartData` is consumed at `select-account-balance-series.ts:18`; `intervalTotalsData` appears only inside a doc comment (`use-account-report.ts:9`, describing it as "the per-interval change") and is never read; `accountBalanceData` has no mention anywhere, not even a comment. This query runs every time an account is opened, and two-thirds of what it asks for is discarded.

`httpUrl` / `sshUrl` / `updatedAt` repeat across all three ledger queries, which reads as one selection block copied three times. `sshUrl` is a git remote the mobile app has no way to use.

## Methodology, and its limits

The match is word-boundary on the raw field name across all app source. That direction of error is **under**-reporting, not over-reporting: a field referenced only in a comment still counts as "used", which is exactly what happened to `intervalTotalsData` — it escaped the automated list and was caught by hand. So the table is a floor.

It cannot see a field consumed by spreading an object into a component and reading it generically. **Confirm each row before deleting it**; the reason `accountBalanceData` is called out above rather than merely listed is that it was checked by hand against its two siblings in the same selection.

Root-field names of mutations were excluded from the table — they appear unreferenced simply because callers use the generated hook rather than the field name, which is not a finding.

## The original instance, in detail

`src/common/graphql/queries/getLedger.graphql:19-26` selects:

```graphql
options {
  nameAssets
  nameEquity
  nameExpenses
  nameIncome
  nameLiabilities
  operatingCurrency
}
```

`GetLedger` has **seven** consumers — `splash-provider.tsx`, `use-ledger-access.ts`, `ledger-drawer.tsx`, `ledger-selection/index.tsx`, `open-app-link.ts`, `use-agent-chat.ts`, and one test. **None of them reads `options`.** Grepping each for `.options` returns a single hit, and it is a comment about Lottie animation options in `splash-provider.tsx:29`.

So every ledger load asks the server to resolve six ledger-option values — which on the backend means parsing the ledger's `option` directives — and then discards them.

## Not to be confused with the options the app *does* use

There are two option types in the schema and the app uses the other one:

| type | shape | used by |
| --- | --- | --- |
| `LedgerOptions` (`schema.graphql:746`) | camelCase — `nameAssets`, `operatingCurrency` | `getLedger` only, and read by nobody |
| `Options` (`types.ts:1351`) | snake_case — `name_assets`, `operating_currency` | `LedgerMeta.options`, read by `ledger-meta-utils.ts` and `add-transaction-next-screen.tsx` |

Different `__typename`s, so they occupy separate cache entries and removing one cannot starve the other. I checked specifically because `ledger-meta-utils.ts` reading `name_assets` against a schema that advertises `nameAssets` looked like a bug — it is not; it reads `Options`, and every field there is non-nullable.

## Fix

Confirm each row against its consumers, then delete the confirmed selections and re-run `yarn codegen`. Do not hand-edit `src/generated-graphql/` (root `CLAUDE.md`).

Some rows may be intentional — a field kept for a consumer not yet written, or one that moved elsewhere. Where that is the case, leave it and **say so in the query**; an unexplained selection is what made the whole sweep necessary.

**Acceptance:** no live document selects a field no consumer reads, or every remaining exception carries a comment saying why; `yarn test` passes; opening an account still renders its balance chart from `linechartData`; and the account-type ordering (which reads `LedgerMeta.options` from a *different* query) is unaffected.

## Blast radius

Eight query documents. No UI change in any of them — every listed field is already discarded. The saving is smaller responses and less server-side work on three hot paths: app start and ledger switch (`getLedger`, `listLedgers`) and opening an account (`accountReport`). Not measured: actual payload or latency, which needs a network capture this session's tooling cannot take (`collect_app_logs` cannot reach the JS console here, per `w4/019`).

## Adjacent states

`ledger-meta-utils.ts` was audited in the same pass and is sound: `getAccountsAndCurrency` builds its from/to orderings from the ledger's own option names rather than hardcoded English roots, and `groupAccountsByRoot` documents that it preserves caller ordering both across and within roots — which holds, since `Array.sort` is stable on Hermes and the comparator returns 0 within a root.

One latent sharp edge there, **not filed** because it needs a contrived ledger to trigger: `createOrderGetter` matches with `name.startsWith(accountType)` rather than on the root segment, so if a ledger configured one root name as a prefix of another (`name_income = "In"` alongside a root `Inventory`), ordering would mis-assign. The five default names are mutually non-prefixing, so this cannot happen out of the box.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for over-fetch, `getLedger`, unused field and selection-set terms. **`w4/025`** (open, filed this run) is the same family at the level of whole unused *operations*; this is unused *fields inside live operations*, which its detector (match each document against its generated hook) cannot catch. The two should be fixed together, and the gate `w4/025` proposes should check selection sets as well as operations — this note's sweep is a working prototype of that check. No other item touches query shape.
