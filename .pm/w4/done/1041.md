# Keep failed first-page social retries mounted and focused

**Severity:** minor follow-up to [106](./done/106.md). **Estimate:** 40–55 minutes, dashboard. **A2/A3:** a visitor should be able to retry an unavailable community list again from the keyboard without losing the recovery control.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-23; owned isolated headless Chromium156.0.8078.47, anonymous public `open_ledger` profile, English/UTC/light. Four fresh retained cases: Followers at1440×1000 and390×844, Following and Starred at390×844. These are browser-local failed/held reads, not a claim of a production outage; every recovery uses the real service response.

1. Load `/ledger/open_ledger?lang=en&tab=followers`. Abort only the initial GetUserFollowers request. The independent GetUserProfile succeeds and the selected tab still says **Followers (473)**. The panel correctly displays **Could not load this list.** and **Try Again**, preserving106's repair.
2. Focus Try Again and press Enter. Hold that query's second request before aborting it. While it is pending, the error and retry control are both absent (`alertCount:0,retryButtons:0`), the spinner replaces them, and native focus is **BODY**. Enter while pending sends no third request because the focused recovery control has disappeared.
3. Release the held request as a network failure. The same error and Try Again return, but settled focus remains **BODY**, not the new Try Again. Both Followers widths repeat this result.
4. Focus the returned Try Again and press Enter after allowing reads through. The third request is genuine HTTP200, no GraphQL errors, and20 follower cards appear. All three attempts retain `username:open_ledger,page:1,limit:20` and the Followers URL/tab.
5. Fresh narrow cases repeat the pending replacement and failed-retry focus loss for GetUserFollowing and GetUserStarredRepos. Their genuine third reads recover respectively **one followed-user card** and the truthful **No starred ledgers** empty state, matching their independently loaded tab counts1/0. Do not replace failed reads with those empty messages.

Working adjacent control: a separate fresh narrow Followers context reads real pages1/2 (`limit:20`), expands20→40 cards, and keeps native focus on **Show more**. Thus the existing continuation control from [W3/491](../w3/done/491.md) works; the failing control is the initial-read retry.

No follower/star mutation, hosted write, AI action, route error or page exception occurred. The four retained cases each have exactly two local aborts followed by one successful scoped read. No failure or success payload was fabricated.

## Cause and bounded repair

`dashboard/src/features/user-profile/components/user-profile-tabs.tsx:43–55` renders SocialListError with a bare onRetry button and no pending ownership. The Followers branch at:251–258 renders its spinner on followersLoading and the error only when !followersLoading. Following:293–300 and Starred:335–342 repeat that ordering. Each retry calls the corresponding wrapper's raw refetch.

`hooks/use-paginated-social-list.ts:79–91` owns useQuery/error/refetch, and:154 returns loading when the enabled first-page query is pending with no rows. Refetch therefore removes the error owner/button; a failed completion mounts a new one without restoring focus. The three wrapper hooks expose that refetch and have one production consumer, UserProfileTabs. Its sole page owner is `pages/user-profile-page.tsx:246`, shared by `/ledger/$username` profiles. Only the public profile was exercised here.

Use the existing query-retry lifecycle for each first-page observer: retain its error view and focusable busy Try Again while retrying, allow one request, and return focus to that control after another rejection. Render the retained failure before the ordinary loading branch, since Apollo clears error while refetching. Retry only the current list/username/page1 with its existing limit. Keep genuine empty and nonempty success separate, lazy tabs, selected tab and collection URL state, identity deduplication, cached rows and the working continuation/error path. A changed tab/profile or later completion must not pull focus away from the reader. No API, backend, dependency or global Button/dialog repair is required.

Acceptance: through the real owner/query integration, cover initial failure → held keyboard retry with visible busy error/action → repeated failure with focus restored → genuine empty/nonempty success. Cover all three lists, scoped variables, repeat activation and leaving the tab/profile while pending; preserve later-page retries and existing healthy controls. Run dashboard gates when implementing. Abandonment, GraphQL error envelopes and another authenticated profile were not independently tested live.

**Resolved 2026-10-23** — The shared `usePaginatedSocialList` (`user-profile/hooks/use-paginated-social-list.ts`) now passes its first page through `useQueryRetry`. A failed first page keeps its error, and `loading` stays false while that failure is held, so the spinner no longer replaces the error and its button during a retry. The new `retry` runs one attempt at a time and returns focus to Try Again after another rejection. A retry still pending when the profile changes never shows its failure on the new profile.

The three wrappers expose `retry`/`retrying` in place of the raw `refetch`. `SocialListError` shows a busy Try Again. Variables (username, page 1, limit 20), lazy tabs, selected tab and URL, identity deduplication, cached rows, genuine empty versus nonempty success, and the continuation path are unchanged.

`social-first-page-retry.test.tsx` runs the real tabs, wrapper hooks and Apollo observers for Followers, Following and Starred. It covers:
- initial failure;
- a held keyboard retry with a busy error and action, where a second Enter sends nothing;
- a rejected retry with focus restored;
- recovery: rows, or Starred's genuine empty state;
- identical scoped variables;
- a profile change during a pending retry, which never shows the old failure.

The retry cases fail on the old hook, and the profile cases fail if only the profile gate is removed. The 106 suite now mocks `retry`.

Native check on the built repaired client (local fixture SSR, public `open_ledger` profile, genuine recorded reads; the first read aborted, the retry held then aborted, the next let through), for Followers at 1440×1000 and 390×844 and Following and Starred at 390×844:
- while the retry is held, the error and a busy Try Again stay, and a second Enter sends nothing;
- after the failure, focus is on Try Again;
- Enter recovers 20 follower cards, one followed user, and the truthful "No starred" state;
- all three reads sent `{"username":"open_ledger","page":1,"limit":20}`, and the URL and tab are retained.

Zero mutations or page errors, and no horizontal scroll. Dashboard gates pass. Not verified: GraphQL error envelopes, another signed-in profile, other engines and locales, screen-reader speech, and the deployed client. Shipped in the commit that moved this note (`dashboard`).
