# Format exact commit timestamps in the active app language

Severity: **minor**, dashboard. Estimate: **25–40 minutes**. A2 — changing the dashboard language should also change generated exact-date text and its accessible name.

Production `https://beancount.io`, 2026-10-09, dedicated QA login, public synthetic `open_ledger/real-estate-example`, isolated headless Chromium 149.0.7827.55. Browser locale **en-US**, application German/English, fresh 1440×1000 and 390×1000 contexts in UTC and Pacific/Kiritimati. Source rechecked on main **982a8f59**, unchanged after pulling; exact deployed SHA is unverified.

## Reproduce

1. Open `/ledger/open_ledger/real-estate-example/commit/20f7f9482a06d4f1857613b286bf43da5a79d1be?lang=de` with an English browser preference. The document language is `de`, surrounding controls are German, and the commit relative time is **vor 7 Monaten** on the observation date.
2. Focus the metadata time element. Its visible tooltip and `aria-label` both say **Feb 27, 2026, 4:18:24 AM UTC** in UTC. Active-language Intl formatting of the identical instant is **27.02.2026, 04:18:24 UTC**.
3. Repeat in Pacific/Kiritimati. The actual tooltip/name correctly changes to **Feb 27, 2026, 6:18:24 PM GMT+14**, but remains English; the German reference is **27.02.2026, 18:18:24 GMT+14**. Both widths reproduce in both time zones.
4. Fresh English controls at both widths/zones match the active-language formatter. All eight genuine public API reads succeed HTTP 200; the rendered `datetime` is exactly the API author-date string, and every tooltip equals its accessible name. This is a locale-selection defect, not a wrong instant or time-zone conversion.
5. Independent fresh German/UTC contexts at both widths repeat the metadata result; their tooltip screenshots were visually inspected. The selected commit's history-list time also has an English browser-formatted native `title` rather than the German equivalent. At narrow width, open the actual **Versionsverlauf** dialog and inspect its visible selected entry; do not use the hidden desktop copy. Its relative label remains German. The list-title claim concerns the actual title attribute, not a captured operating-system tooltip.

No clipboard, source edit or account/ledger mutation was performed. All fresh contexts were closed and the original QA page was untouched.

## Cause and bounded repair

`dashboard/src/features/git/commits/components/commit-metadata.tsx` uses the active-language `useFormatRelativeTime` hook for the visible duration, but builds `exactTime` with `new Intl.DateTimeFormat(undefined, ...)`. That selects the browser locale. `commit-list-item.tsx` likewise calls `toLocaleString()` with no language for its exact-time title. These two generated strings bypass the application language even though the surrounding timestamp UI is correctly localized.

Use the existing active application language for both exact-time formatters and re-render on language changes. Preserve each consumer's formatting options, actual browser time zone, timestamp identity, `datetime`, tooltip keyboard access, accessible name, relative-time behavior and history selection/navigation. Do not hardcode UTC, add date dependencies, translate commit messages or alter APIs.

Acceptance: an English browser with the application set to German renders the actual exact tooltip, accessible name and history title in German; switching application language to English updates them without changing the underlying instant. Cover mismatched browser/app locales, both exercised time zones, desktop and narrow history, and ordinary matching-locale controls. Assert the strings produced by the real consumers and real Intl formatting; mocking a formatter to echo a language does not establish integration. Run dashboard gates when implementing.
