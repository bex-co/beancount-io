## Outcome

t001 and t002 made the forms safe. This task is about the other half of the
acceptance — that a user is not left in a **misleading usable state** — and
that gap was real: with JavaScript unavailable the fields still accepted
typing while the submit button was dead and unexplained. Safe, but baffling.

Both forms now render a `<noscript>` notice in place of a working button:
*"Sign-in needs JavaScript. Please enable it and reload this page."* New key
`auth.scriptRequired`, written in all fifteen locales as real translations —
the suite rejects placeholders in non-English catalogs. `<noscript>` is the
right mechanism here because it needs no hydration to appear, which is exactly
the state it describes.

Verified live at 1440x1000:

| Page | JavaScript | Notice | Submit |
| --- | --- | --- | --- |
| login | off | shown | disabled |
| login | on | hidden | enabled |
| sign-up | off | shown | disabled |
| sign-up | on | hidden | enabled |

and `?lang=de` renders the German string, so the notice is not English-only for
the readers most likely to hit it.

That completes the criterion: without scripts the reader is told why they
cannot proceed rather than being shown a form that silently does nothing, and
no path submits credentials through a native GET — pre-hydration there is now
no submission at all.

**Documentation.** `dashboard/README.md` mentions `/login` and `/sign-up` only
as SEO/acquisition paths and describes the OAuth `postMessage` bridge; the root
`README.md` mentions authentication only for the CLI. Nothing documents form
submission mechanics or promises a non-JavaScript fallback, so nothing drifted
and nothing needed correcting. No skill, package table entry or authentication
stack was added — the change is one attribute, one hook and one notice.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (384
files, 4331 passed, 1 pre-existing skip) and `yarn build` all pass.
