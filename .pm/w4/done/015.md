# The Merchants sort button is named for the sort it already applied — and w3/188 cites it as the opposite

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: a VoiceOver user must be able to tell what a button will do before activating it.

**Also corrects an open item.** `w3/188.md` ("The merchant Recurring switch announces the opposite of its own state") uses this control as its precedent, stating: *"inspected live, it reports `label: "Sort alphabetically"` while showing the `Aa` icon, and after a tap it reports `label: "Sort by transaction count"` with the `⇅` icon — icon and label both describe the next action."* The label/icon pairing it records is right; the conclusion is not. Both describe the **current** sort. Anyone implementing `w3/188` by copying this button would copy a state-labelled control believing it is action-labelled.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, public `open_ledger/alphabet`. Report-only QA; the sort is component-local state and was returned to its default.

## Repro — a single A/B, list order checked against the label each time

1. Terminate and relaunch. Ledger drawer → **Merchants**.
2. **State A (default).** `automation_find_view {"testID":"merchants-sort"}` → `label: "Sort by transaction count"`. Icon is `⇅`. The list reads `Q1 2022 Revenue`, `Q1 2023 Revenue`, `Q1 2024 Revenue`, `Q1 2025 Revenue`, `Q1 2026 Revenue`, `Q2 2022 Revenue`, … — **every visible row has `7 transactions`**, i.e. the list is already sorted by transaction count, descending.
3. Tap the button once.
4. **State B.** `label: "Sort alphabetically"`. Icon is `Aa`. The list reads `Opening Balance` (1), `Q1 2022 Expenses` (6), `Q1 2022 Other Income (Ex…` (1), `Q1 2022 Revenue` (7), `Q1 2023 Expenses` (6), … — **alphabetical**, counts in no order.
5. Tap again → `label: "Sort by transaction count"`, count order restored.

So in State A a button named "Sort by transaction count" sits on a count-sorted list and activating it sorts alphabetically; in State B a button named "Sort alphabetically" sits on an alphabetical list and activating it sorts by count. The name always describes what has already happened, and activating it always does the other thing.

## Root cause

`mobile/src/screens/merchants-screen/merchants-screen.tsx:232-235`:

```js
const sortLabel =
  sort === "count"
    ? t("merchantsSortByCount")        // "Sort by transaction count"
    : t("merchantsSortAlphabetical");  // "Sort alphabetically"
```

That value is passed as `accessibilityLabel` on a `<TouchableOpacity accessibilityRole="button" onPress={onToggleSort}>` (lines 337-347). The icon is keyed the same way — `sort === "count" ? "swap-vertical-outline" : "text-outline"` (line 350) — so both the glyph and the accessible name track state, not action. `sort` defaults to `"count"` (line 145), which is why a fresh launch lands in State A.

## Fix

An icon-only button's accessible name must say what activating it does. Invert the ternary so the label names the **other** mode:

```js
const sortLabel =
  sort === "count"
    ? t("merchantsSortAlphabetical")
    : t("merchantsSortByCount");
```

The existing strings already read as actions and need no change. Leave the icon keyed to current state if that is the intended visual convention — but then say so in a comment, because the icon and the name will deliberately disagree. The alternative, if the team wants the control to *announce* its state, is to keep the current label and add `accessibilityValue`/`accessibilityHint` describing the action; pick one and record the choice, because `w3/188` turns on exactly this distinction.

Do not change the sort behaviour, the default (`"count"`), the tie-breaking within a count group, or the `Aa`/`⇅` glyphs.

**Acceptance:** on a fresh iPhone 17e launch, `merchants-sort` reports `label: "Sort alphabetically"` while the list is count-ordered, and `label: "Sort by transaction count"` while it is alphabetical; tapping still toggles and the visible order still matches what the previous label promised. Add a regression test asserting the rendered `accessibilityLabel` for both `sort` values — the current code would pass a test that only checks "a label exists".

---

**Resolved 2026-09-14** — fixed in `mobile` by `fix(mobile): name the Merchants sort button for the order it switches to`. Triage confirmed the root cause at HEAD before the fix: `merchants-screen.tsx` derived the button's `accessibilityLabel` from the current `sort`, so a count-ordered list offered "Sort by transaction count" and tapping it sorted alphabetically. The note was not stale.

`mobile/src/screens/merchants-screen/sort-button-label.ts` returns the translation key for the other order. While the list is sorted by count, the button reads "Sort alphabetically", and while it is alphabetical, it reads "Sort by transaction count". The icon still shows the order already applied, and a comment at the call site records that the icon and the name deliberately differ. The sort behaviour, the default (`count`), and the `⇅` / `Aa` glyphs are unchanged, as are the existing strings. The corrected precedent is recorded on `w3/188`.

Regression tests in `mobile/src/screens/merchants-screen/__tests__/sort-button-label.test.ts` cover the helper for both sort values; both tests fail when the helper names the current order. A source guardrail checks that the button's label comes from the helper while the icon stays keyed to the applied order, and it fails with the screen change reverted. The unit runner cannot render the screen, so the `automation_find_view` labels and VoiceOver speech were not re-checked in this run.
