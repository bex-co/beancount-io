# Recover when the browser blocks a delayed ZIP-download popup

Severity: minor. Estimate: 50m, dashboard. A2: public readers should receive their requested archive or a usable explanation and download action. Repeated dashboard QA, 2026-09-18–19 UTC (fresh keyboard repeat after the user resumed the loop).

Environment: production beancount.io, anonymous public `open_ledger/crypto-example`, English/light. Owned headless installed Chrome153.0.8010.52 with Playwright's `--disable-popup-blocking` default argument removed; otherwise normal isolated profile. Fresh1440×1000 and768×1024 contexts. Local HEAD26d54a9d, fetched origin/mainbd5d1d31, served main-BIr0jJni.js; exact deployed commit unknown.

## Reproduction

1. Open `/ledger/open_ledger/crypto-example/files/tree/main`, then Git Clone.
2. Hold only the real GetLedgerArchiveDownloadUrl request. Click Download ZIP; in the fresh768 repeat, focus the button and press Enter.
3. Let transient activation expire (the keyboard repeat held the request for at least6500ms). Release the request unchanged and await its response: HTTP200 with a nonempty downloadUrl.
4. Both widths return to an enabled Download ZIP button, with no alert, no fallback link, no popup and no archive request. The real window.open call returns null with navigator.userActivation.isActive=false.
5. On the768 page, retry without delaying the real lookup: window.open returns a window with activation=true; one popup and one archive request follow. No error remains.

This is a controlled slow-network case, not a claim that every ZIP click fails. Popup-blocking automation defaults would hide it. A transparent observation wrapper forwards the original window.open arguments, receiver and return value unchanged and records activation/result only. CDP Runtime.evaluate used userGesture:false for inspection while the request was held, avoiding accidental activation renewal. The real response and URL were not fabricated. Held routes were released, finished and removed; all extra contexts/popups/browser and CDP sessions were closed. No clipboard, auth or ledger mutation.

## Cause and repair

`dashboard/src/features/ledger-editor/directory-browse/components/ledger-clone-url-menu.tsx:115–136` awaits archive discovery before calling `window.open(downloadUrl, "_blank")` at127. The browser can legitimately return null without throwing. The handler ignores that return, catches only exceptions, and clears downloading in finally, so the existing error UI never renders. This is the sole window.open call in ledger-editor and the only archive action in this component.

Keep successful archive discovery usable when automatic opening is blocked: retain the returned URL and offer a clearly labelled native link/button requiring a fresh user gesture, with localized accessible feedback. Alternatively start navigation within the original activation and explicitly clean up any reserved window on lookup failure; do not leave blank tabs. Never ask users to globally disable popup protection. Preserve quick downloads, keyboard activation, pending-click disabling, lookup rejection/missing-URL feedback and retry. Keep the fix in dashboard; no backend/API, permission, dependency or archive-content change is needed.

Working failure control: aborting only archive discovery shows the translated connection error and re-enables the action; removing the abort and retrying opens its download. This confirms completed w3/117's lookup-rejection fix still works. The new failure occurs after a successful lookup. Completed w4/m1/t004's same-window report printing is a different action and deliberately avoids this failure class. w4/132 concerns popover/textbox naming. All current/done/blocked board states and targeted history were checked; window.open originates inaf5339de and fetched main still ignores its return.

Acceptance: with normal popup blocking and an actual delayed successful lookup, the reader gets an archive or an explicit usable download link. Verify prompt success, null-return fallback, keyboard retry, lookup rejection and no orphan blank window. A test that merely mocks window.open to return a window misses this failure; include the blocked/null case and a real browser activation-delay check. Run dashboard's normal gates when implementing. Narrower-than640 Git Clone is intentionally hidden; Safari/Firefox, authenticated readers and native browser chrome indicators remain unverified.

Evidence: `dashboard/tmp/qa-20260917/zip-popup-blocked-1440.json`, `zip-popup-blocked-768.json`, `zip-popup-prompt-retry-control.json`, and `zip-lookup-recovery-control.json` in the same directory. `dashboard/tmp/qa-20260917/zip-popup-blocked-1440.png` was visually inspected and shows the unchanged popover without feedback. No product fix, commit or push.

Post-resume source refresh, 2026-09-19: fetched origin/main04f274d2 still contains the same unguarded window.open; served main-BIr0jJni.js remains unchanged. The intervening source change only updates guidance references.

---

**Resolved 2026-09-19** — `handleDownloadZip` now checks what `window.open` returned. When the browser refuses, the URL the lookup already found is kept and offered as a plain `<a download>` link under a localized `role="status"` explanation, so the reader can start the archive with a fresh gesture. No window is reserved ahead of the lookup, so there is no blank tab to clean up, and nothing asks the reader to weaken popup protection. One new key, `ledgerEditor.downloadZipBlocked`, was added to all fifteen locales; the link reuses the existing `ledgerEditor.downloadZip` label. Reproducing this required the installed Chrome channel with Playwright's `--disable-popup-blocking` default removed — bundled headless Chromium opened the popup anyway, with `blocked: false`, so an early probe of mine showed nothing. Under installed Chrome, holding only `GetLedgerArchiveDownloadUrl` past the activation window reproduced the note exactly at 1440×1000 (click) and 768×1024 (keyboard Enter): `window.open` returned null with `navigator.userActivation.isActive` false, zero popups opened, and the popover showed no alert, no status and no link while the button silently re-enabled. After the change the same runs show "Your browser blocked the download. Use the link below to start it." with a Download ZIP link whose `href` is the discovered archive URL, at both widths and for both activation methods. Controls in the same harness are unchanged: a prompt lookup still opens the archive directly with one popup and no fallback; a rejected lookup still shows the translated connection error with no link, since no URL was discovered; and retrying after that rejection clears the error and opens the download. Exactly one window is opened in each successful case, so no orphan blank window is left. `__tests__/zip-download-blocked.test.tsx` adds six cases driving the null return — which is precisely what a blocked popup looks like to the page — covering the explanation, the link's `href` and `download` attributes, the button staying usable, the fallback clearing on a retry that succeeds, the unblocked path offering no fallback, and a failed discovery offering no link. Four of the six fail when the guard is removed; the unblocked and discovery-failure cases pass either way and stand as controls. Not verified: Safari and Firefox, authenticated readers, native browser chrome indicators, and the archive actually downloading — the link's target was checked against the discovered URL rather than followed. Git Clone stays hidden below 640px, so no narrow case is claimed. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 421 files, 4744 passed, 1 pre-existing skip — and `yarn build`). Shipped in `217775f3` (`dashboard`).
