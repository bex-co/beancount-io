# Lock the open calendar during transaction submission

**Minor · dashboard · 45–60m · A2.** Residual of [m33](./done/m33/README.md)'s pending-form contract: a calendar already open when Transaction submits can still change the date while the form is locked. No successful hosted write or late-success draft loss is claimed.

## Reproduce and controls

Production `https://beancount.io`,2026-10-24 UTC; owned isolated headless Chromium156.0.8078.47, English/light/UTC, designated disposable-ledger owner. Fresh390×844 and1440×1000 repeats, actual native keyboard/pointer actions. Hold and subsequently abort every BulkEntries request **before transport** to expose the pending window without booking anything.

1. Open Journal → New Entry → Transaction. Set Date **10/01/2026**, a prefixed QA payee, and two existing open accounts with balanced **-12.50 USD /+12.50 USD** postings.
2. Open **Select date**, focus the selected October1 day button, and press **Cmd+Enter**. Exactly one prepared TRANSACTION has canonical date **2026-10-01**.
3. While that request is held, the date input and submit button are natively disabled and the parent remains in its pending state. The already-open calendar remains visible; October2's day button is still natively enabled.
4. Click October2. The disabled date field changes to **10/02/2026**, and the popup closes, while the submit button remains disabled and the held payload still names October1. Both widths reproduce.
5. Abort the held request. The form remains open and re-enables with October2 retained. Explicitly close the unsaved draft. This failure recovery works; the defect is accepting another date during the pending lock.

Expected: after submission starts, neither the field nor its already-open calendar/Today/month controls can publish another date until the save settles. Ordinary calendar selection remains available before submission and after failure. The original selected October1 agrees with the prepared canonical payload; duplicate submissions and ordinary field disabling remain intact.

The final narrow observer independently confirms the enabled day button has **no form or fieldset DOM ancestor**, while the date input is disabled. Before/after screenshots show the open calendar during the lock and the changed disabled field beside the busy submit control; the narrow after image was visually inspected.

## Cause and bounded repair

`dashboard/src/features/journal/components/new-directive-dialog/transaction-form.tsx:321–340` handles Cmd/Ctrl+Enter through the form's native requestSubmit path even when focus is in the calendar. At:378 the pending lock is a disabled fieldset. The DatePicker at:393 receives value/onChange but no pending/disabled state.

`common/components/ui/date-picker.tsx` has no disabled prop. Its open state and calendar/Today selection callbacks remain active; the Calendar receives no pending restriction. `common/components/ui/popover.tsx:35` renders content through a Portal, outside the native fieldset. The existing usePendingSubmit/usePendingAction guard correctly holds the write and disables the ordinary form, but fieldset inheritance cannot lock that portaled calendar. Complete current sources and actual DOM ownership agree with the native result.

Propagate the pending state into DatePicker and ensure an already-open popup cannot change its value during it. Closing the popup or rendering a disabled calendar must also prevent selection callbacks during its exit window. Preserve canonical civil dates, strict localized input, ordinary selection/failure recovery, popup focus/scroll behavior, the single-submit guard and dialog completion ownership. No backend/API, dependency or cross-package change is needed.

Seven production DatePicker callers were audited: Transaction, Balance, Note and New Entry Account; Accounts Open Account; Add Budget; Receipt Review. They share this primitive. Only Transaction's native shortcut path was reproduced; do not claim the other six can submit with an open popup from this evidence. Carry compatible pending state through the actual owning callers as needed, without an AI/receipt operation.

Acceptance: a meaningful real Transaction/DatePicker regression starts a held write from the open calendar and proves day/Today selection cannot change the submitted draft. Keep native field locks, duplicate-submit refusal, failure retention/retry and ordinary calendar selection. Repeat both widths and run dashboard gates when implementing. QA authored no product fix or formal tests.
