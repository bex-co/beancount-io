# Retry a failed BQL history query without replacing the current editor

**Severity:** minor. **Estimate:** 35–50 minutes. **Owner:** dashboard. **A2:** a failed history card's “try again” guidance needs an action for that query, while preserving the newer query the reader is editing.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-22; owned isolated headless Chromium 155.0.8059.85, anonymous public `open_ledger/example`, English/light, fresh 390×844 and 1440×1000 contexts. Browser-local transport fault, not a production outage. No response-body fixtures, mutations or hosted writes.

1. Open Query with A: `SELECT 'qa-20261022-retry-A' AS label LIMIT 1`. Hold only this first QueryShell before transport. Wait for the actual writable editor, replace its text with the B variant, and execute B with Cmd+Enter. B completes and displays a table while A remains pending.
2. Abort the held A request before transport; remove that one-shot fault. A's older card shows **Connection problem. Please check your internet connection and try again.** Its only button is **Delete query**: there is no Try Again/Retry/Run action. The editor and bookmark correctly remain B.
3. Close and reopen A with its native summary and Enter. The summary keeps focus, but no QueryShell is sent and the same error remains. Both fresh widths repeat.
4. Activate the main **Execute Query** button. It sends B again, HTTP 200, and leaves A's error unchanged. Thus the existing global action cannot retry the failed card without replacing the newer editor text.
5. Working workaround: retype A in the editor and activate Execute Query. The unblocked genuine read returns HTTP 200 with `[["qa-20261022-retry-A"]]`; A's table returns and its alert clears. The editor/bookmark now become A. This proves a transient read failure and a usable backend, rather than invalid BQL or an unavailable service.

Recorded QueryShell request totals are **2 after A/B submission, 2 after A's disclosure toggles, 3 after the global B run, 4 after the explicit A workaround** at each width. There is no failed-card retry attempt because no such control exists. No query-result corruption or lost ledger data is claimed.

## Cause and bounded repair

`dashboard/src/features/bql/components/query-result-card.tsx:295–300` executes an opened history item only when it has no result, no error and no pending read. An errored item is explicitly excluded. At approximately :356–363 its error branch renders only Alert/AlertDescription. Its actions are Delete and, for a successful settled table, CSV; neither retries a read.

The existing `onExecute(query)` callback already carries the correct query. `pages/index.tsx:217–219` invokes executeQueryAndCache for that history query without rewriting editor text or URL. The global button instead submits the current editor text. The page is this card's sole production owner; getQueryErrorFeedback correctly classifies the injected connection failure and is not the missing action.

Expose a localized keyboard retry on the failed card, bound to its own query through the existing execution path. Keep the newer editor draft and bookmark intact, keep pending/repeated-failure feedback coherent, prevent competing retry activations, and replace only that card's error with its successful result/export. Preserve successful cached disclosure toggles without extra reads, per-query result ownership, history order and card identity, classified BQL errors, current network-only execution, pending export guards and cross-ledger isolation. Do not automatically replay every failed query, require a reload, or make the reader overwrite the editor to recover. No API, dependency or backend behavior change is needed.

Acceptance: through the real page/history/card integration, fail A while B succeeds, keep a newer editor draft, retry A from its card, and assert an A request/result with the draft/bookmark/B result unchanged. Cover a held retry, repeated transport failure, successful recovery and normal cached toggles. Verify keyboard focus/busy behavior and desktop/narrow, then run dashboard gates when implementing. Other engines/locales, syntax-error recovery actions and repaired behavior remain unverified.
