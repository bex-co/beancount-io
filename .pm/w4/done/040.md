# The file editor stacks two keyboard accessory bars, and the lower one is the WebView's default

**Severity:** minor. **Estimate:** 10–20 minutes (one prop, then re-measure). Owner: mobile. A2: the two bars together take roughly a fifth of the screen above the keyboard on an editing surface, and the lower one is redundant — it offers form-field navigation on a screen with one field.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA; **nothing was saved** — `Save` stayed disabled and no text was entered.

## Repro

1. Select `puncsky/example`, open Files → `main.bean` (or `beancount:///(app)/ledger-file-editor?path=main.bean`).
2. Make the software keyboard visible. On the Simulator this needs **⌘K** — see "How to see this at all" below.
3. Tap into the editor text.

Two bars appear stacked between the content and the keyboard:

- **Upper — the app's own** `KeyboardAccessoryBar`: beancount insert chips `2026-09-13`, `*`, `!`, `""`, `:`, `USD`, `→|`, scrolling horizontally. This is deliberate and useful.
- **Lower — the WebView's default**: a translucent pill with `∧` `∨` and `✓`. Editor text shows *through* it (`export: "IGNORE"` and `name: "US 401k and IRA Contributions"` are legible behind it in the capture).

## Cause

The editor is an Expo DOM component, so it runs in a `WKWebView`, and the web view supplies its own input accessory view whenever a field inside it has focus. The app never suppresses it — `ledger-file-editor-screen/index.tsx:654` passes exactly one DOM prop:

```tsx
dom={{ style: { flex: 1 } }}
```

`hideKeyboardAccessoryView` is not set anywhere in `code-editor.tsx` or the editor screen.

The lower bar is not just duplicative, it is **meaningless here**: `∧`/`∨` step between form fields, and the editor is a single field, so they have nothing to move between. Its `✓` does do something the app's bar does not — dismiss the keyboard — which is worth preserving in the app's own bar if the system one goes.

## Fix

Suppress the WebView accessory and, if the dismiss affordance is wanted, add it to `KeyboardAccessoryBar`:

```tsx
dom={{ style: { flex: 1 }, hideKeyboardAccessoryView: true }}
```

**Verify rather than assume this prop reaches the web view.** `hideKeyboardAccessoryView` is a `react-native-webview` iOS prop and Expo's `dom` prop forwards `WebViewProps`, so it should apply — but I could not test it without editing the working tree, and this run is report-only. If it does not forward, the fallback is the same suppression applied where the DOM component is configured.

**Acceptance:** focusing the editor shows only the app's insert bar above the keyboard; the beancount chips still insert; the keyboard can still be dismissed without leaving the screen; and the number of editor lines visible with the keyboard up increases by roughly the height of the removed bar.

## Blast radius

**Two** DOM/WebView surfaces, not one: the file editor and the **Edit Transaction** screen, which mounts the same `CodeEditor` and passes the same single DOM prop (`edit-transaction-screen.tsx:445` — `dom={{ style: { flex: 1 } }}`, no `hideKeyboardAccessoryView`). The fix applies identically to both call sites. No effect on the native text inputs (payee, narration, amount), which get ordinary native keyboards.

The Edit Transaction case matters more per screen-inch: it edits raw beancount source for one transaction in a much smaller document, so chrome above the keyboard eats a larger share of what there is to see.

Not exercised: whether removing the bar changes anything on iPad or in landscape, and Android (where WebView accessory behaviour differs entirely).

## Relationship to `w3/214`

`w3/214` ("Keep the code editor's active line above the native keyboard") is the open, more serious defect on this same surface: with the keyboard up the caret can sit behind the chrome, and it measures visibility against "the quick-insert bar" — the app's bar. It does not mention the second, system bar.

These compound. Removing the redundant bar recovers vertical space and so directly reduces the occlusion `w3/214` describes, without being a fix for it — the caret-scrolling behaviour that note reports would still need addressing. **Fix this one first**, then re-measure `w3/214` against the shorter chrome, because its "only lines 43–57 are above the quick-insert bar" measurement was taken with both bars present and will change.

## How to see this at all — a tooling note worth keeping

The software keyboard never appears on this Simulator by default, because the hardware keyboard is connected (which is precisely what makes the `osascript` typing technique in `mobile/CLAUDE.md` work). Every earlier QA pass in this run therefore saw these screens **without** a keyboard, and recorded keyboard behaviour as unverified.

Two things that do **not** work: `defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false` (read at Simulator launch, so it has no effect on a running instance), and any `xcrun simctl` subcommand.

What works is sending **⌘K** to the Simulator:

```sh
osascript -e 'tell application "Simulator" to activate' \
          -e 'tell application "System Events" to keystroke "k" using command down'
```

That toggles the software keyboard at runtime and leaves hardware typing working. Worth adding to `mobile/CLAUDE.md` beside the existing `osascript` typing note — it is the difference between the keyboard journey being testable and not.

## Adjacent states

Verified correct in the same pass, with the keyboard finally visible: the amount field on **New Transaction** gets a **decimal pad** (digits, `.`, backspace) rather than a full QWERTY, which is the right `keyboardType` for a money field; and on that screen the form content sits entirely above the keyboard, so nothing is occluded there.

The app's own `KeyboardAccessoryBar` is a genuinely good feature — inserting a date, flags, quotes, a colon and the operating currency is exactly what a beancount editor on a phone needs.

**Resolved 2026-09-14** in `fix(mobile): show one keyboard accessory bar in the code editors`.

**Suppressing the system bar.** Both `CodeEditor` call sites, the file editor and Edit Transaction, pass `hideKeyboardAccessoryView: true` in their `dom` props. Expo's `DOMProps` extends the `react-native-webview` props, which declare it, and typecheck accepts it.

**Replacing its dismiss.** The system bar's ✓ was the only way to dismiss the keyboard.
- `KeyboardAccessoryBar` now takes an optional `onDismiss` and renders a trailing chevron-down button labelled "Hide keyboard".
- The new key is translated in all 13 locales, so the locale-integrity suite passes without a known gap.
- Both screens wire it to a new `CodeEditorRef.blur()`, which blurs CodeMirror's content element.

**Tests.** `src/components/keyboard-accessory-bar/__tests__/editor-keyboard-chrome.test.ts` checks that both screens hide the web view's bar and wire the dismiss, that the editor exposes `blur`, and that the bar calls `onDismiss`. With either screen reverted, its test fails. The mobile gate passes, with 1850 unit tests.

**Not exercised on device.**
- That the prop reaches the WKWebView.
- That `blur()` hides the keyboard.
- The recovered editor height, and a re-measurement of `w3/214`.

The note's suggestion to add the ⌘K software-keyboard tip to `mobile/CLAUDE.md` was not taken up here.
