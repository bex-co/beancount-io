# Keep route-error retries single-flight and restore focus after another failure

**Severity:** minor residual of [264](./done/264.md)'s child-loader recovery. **Estimate:** 55–60 minutes, dashboard. **A2:** a keyboard reader should be able to retry a failed section again without finding the action anew or accidentally queuing another attempt.

## Live reproduction and controls

Production `https://beancount.io`, October23 local / October24 UTC2026; dedicated QA owner and disposable synthetic ledger, isolated headless Chromium156.0.8078.47, English/UTC/light. Fresh1440×1000 and390×844 contexts reproduce. These are local browser request aborts/holds, not a natural service outage or a substituted response.

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/files/tree/main?lang=en`. Activate **Version History** by keyboard. Abort only GetCommitDetails for the real commit selected by that navigation. The section displays **Something went wrong / This section couldn't be displayed. The rest of the page should still work. / Try Again**.
2. Focus Try Again and press Enter. Hold this retry's GetCommitDetails before transport. The original action remains focused, but stays **enabled**, has no `aria-busy`, and still says Try Again. Press Enter again while that same request is held.
3. Reject the held read, wait for its actual requestfailed event and the resulting UI to settle. At both widths the error action returns, but **focus is BODY**, rather than Try Again. The repeated Enter also produces **one additional detail read after the held rejection**: three local failed attempts in total, including the initial one. There were only two while the request was held.
4. A third fresh390px case uses **one Enter** during the held retry. It still loses focus to BODY after rejection, but has only two failed attempts: initial + retry. This separates the focus defect from the extra activation.
5. Remove the fault, manually focus the visible Try Again and press Enter. All three cases recover the real Commit Details region at the same selected commit URL. Each obtains one genuine HTTP200 GetCommitDetails response, without GraphQL errors, whose SHA/variables match that case's failed reads.

264's original loader-recovery repair therefore works in production. This item covers its remaining pending/rejection lifecycle. No permanent trap, missing retry action, wrong commit, unbounded request storm or ledger mutation is claimed. Selected commits differed between fresh cases because the shared QA history advanced; identity is compared within each case.

## Cause and bounded repair

`dashboard/src/common/components/error-boundary-fallback.tsx:65–67` directly invokes onRetry from a button without pending state or an activation guard. `error-boundary.tsx:66–78` awaits its recovery callback but unconditionally clears the caught error in finally. Its fallback callback at:89 discards that promise with `void`. In the ledger layout at:187–193, recovery is `router.invalidate()` and resetKey is the pathname.

Installed TanStack Router1.167.0 `router-core/src/router.ts:2686–2710` clears failed match status/error and calls load for every invalidation. After the repeated loader failure, `react-router/src/Match.tsx:275–297` throws the failed client match again. Clearing/re-catching the boundary replaces the action and loses its native focus. Without an owning pending guard, a second Enter can invoke another invalidation; the live single-Enter comparison confirms the extra read is activation-dependent. No extra read from a single Enter is alleged.

Carry the awaited retry lifecycle through the existing default fallback: guard one recovery at a time, expose its pending state accessibly while preserving the initiating control's focus, and keep or restore that action after another failure. Do not clear the failure in a way that leaves keyboard focus on the document body. A success must still release the boundary and show the selected loader result. Retain router invalidation from264; resetting React state alone would reintroduce the original bug.

Preserve resetKey navigation behavior: leaving this route while pending must not refocus or resurrect the abandoned fallback. Keep immediate ordinary panel retries when no asynchronous onRetry is provided, custom fallback rendering, safe Error Details, and the stale-chunk **Reload page** path. The other production ErrorBoundary owners are Overview widgets/README (ordinary default fallback) and ReactECharts (custom fallback); those are compatibility scope, not separately reproduced failures. The root route's different error-page implementation is outside this repair. No backend, API, dependency or global query policy change is needed.

Acceptance: real router/loader integration covers initial failure → held keyboard retry → repeat Enter → repeated failure, with one accepted recovery, accessible pending feedback and focus on its action after rejection; then successful recovery. Include the single-Enter control and leaving the route while pending. Preserve ordinary synchronous/default and custom-fallback callers, then repeat desktop/narrow and run dashboard gates. Do not settle for a source assertion or a mock synchronous retry: it would miss the actual replacement after a failed loader.

**Resolved 2026-10-23** — `ErrorBoundary` (`common/components/error-boundary.tsx`) now carries an awaited recovery through its default fallback. While `onRetry` (the ledger layout's `router.invalidate()`) runs, the same Try Again stays mounted, busy and disabled, and a second activation is refused, so no extra read is queued.

When the recovery settles, the boundary clears as before so the real loader result renders. If the loader failed again, the re-thrown error mounts a new fallback, and the first commit after settling hands focus to its Try Again. That only happens when focus had been dropped to the page, never when the reader moved it.

If the reader leaves the route while the recovery runs (`resetKey` changes), the abandoned attempt neither clears nor focuses anything. A plain panel retry with no `onRetry` stays immediate. Custom fallbacks, Error Details and the stale-chunk Reload page path are unchanged.

`error-boundary-retry-lifecycle.test.tsx` runs 264's real router and loader harness with loads settled by hand. It covers:
- a held keyboard retry with a busy action, where a repeated Enter queues no load;
- a rejection with focus on Try Again and exactly two loads;
- recovery to the commit;
- the single-Enter control;
- leaving the route mid-recovery, after which the route stays as it is with no fallback or focus move.

The two retry cases fail on the old boundary; the abandoned-route control passes on both. 264's own suite still passes.

Native check on the built repaired client (local fixture SSR, public example ledger, genuine recorded reads). Files, then keyboard Version History, then the selected newest commit with its `GetCommitDetails` aborted, at 1440×1000 with two Enters, 390×844 with two Enters, and 390×844 with one Enter:
- the section shows its error and Try Again;
- the retry, while held, is busy and disabled;
- a repeated Enter adds no read (two reads after the failure, where the report saw three);
- focus is on Try Again after the rejection;
- the next Enter recovers the Commit Details region at the same commit URL, with all reads' variables identical.

Zero mutations or page errors, and no horizontal scroll. Dashboard gates pass. Not verified: Overview widget and README boundaries natively, other engines and locales, screen-reader speech, and the deployed client. Shipped in the commit that moved this note (`dashboard`).
