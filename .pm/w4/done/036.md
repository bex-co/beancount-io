# A "6M" balance change is measured from the account's first *active* month, not from the start of the range

**Severity:** minor. **Estimate:** 40–60 minutes. Owner: mobile. A2: the headline change and percentage sit directly under the balance on Home and on every account drill-down, and on a dormant-then-funded account both numbers are wrong — a $0 → $5,317.06 gain reads as **+$6,829.48 (+451.56%)**. It is **data-dependent**: the same code produces correct figures whenever the first active month in the window nets to zero (verified — see Blast radius), which is why it has survived.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA; no ledger mutation. BQL below is read-only through the MCP credential pinned to that ledger.

## Repro

1. Select `puncsky/example`, open `Assets:Bank:Mercury:Checking` (Accounts → Assets, or `beancount:///(app)/account-detail?account=Assets%3ABank%3AMercury%3AChecking`).
2. The card, at its default **6M**, reads:

   > **Balance $5,317.06** · **+$6,829.48 (+451.56%)**

3. The account's entire history, via BQL — two activity dates, nothing earlier:

   | date | delta | running |
   | --- | --- | --- |
   | 2026-08-31 | −1,512.42 | −1,512.42 |
   | 2026-09-01 | +6,829.48 | **+5,317.06** |

With "today" at 2026-09-13, the 6M window opens on ~2026-03-13, when the balance was **$0.00** — the first posting is five months later. So over the range actually selected the account went from `$0.00` to `$5,317.06`: a change of **+$5,317.06**, and a percentage that is undefined rather than 451.56%.

The figure shown, `+$6,829.48`, is the change since **2026-08-31** — the first month in the series that has a point.

## Every range reports the same wrong number, including ALL

Switching the range pill changes nothing. **Directly observed: 1M, 6M, YTD and ALL all render `+$6,829.48 (+451.56%)` above an identical two-point plot** — four of the six, captured one after another on the same screen (September 14 for 1M and YTD; `w4l133-03-ytd.jpg`, `w4l133-04-x77.jpg`, `w4l133-04-x311.jpg`). Only 3M and 1Y remain inferred, and the inference is tight: the series holds exactly two monthly points (2026-08, 2026-09), so every window contains both and none can contain anything earlier.

**The user-visible form of this is that the range control is inert.** A reader tapping through six pills on this account gets one answer six times — same balance, same change, same percentage, same plot. That is worth stating separately from the arithmetic, because it is what someone would actually notice and report, and because this journey's contract is specifically that "period and account controls change summaries."

**ALL is the important one.** Its change should be measured from the account's inception, where the balance was `$0.00` — the transactions list shows the account opening on `September 12, 2017` at `Balance: $0.00`, and BQL confirms **no postings at all** before 2026-08-31. So the true all-time change is `+$5,317.06`, not `+$6,829.48`.

That rules out "sub-range filtering" as the whole story: `linechartData` never contains the account's opening zero, or any of the dormant years, so *no* range — not even the unfiltered one — has a correct baseline available to it. A fix that only corrects windowed ranges would leave ALL wrong.

A prediction this note made that did **not** hold, recorded so nobody chases it: I expected ALL to expose the `baseline === 0 → +0.00%` branch by including the 2017 zero point. It does not, because the 2017 row is an `open` **directive** rather than a posting, and the series is built from postings. The `+0.00%` branch remains real but still unobserved.

## Root cause

`src/common/d3/interactive-line-chart.tsx:356-358`:

```ts
const baseline = numbers[0] ?? 0;
const change = shownValue - baseline;
const changePct = baseline !== 0 ? (change / Math.abs(baseline)) * 100 : 0;
```

`numbers` comes from `seriesToChartArray(filterBalanceSeriesByRange(series, range))`, and the series is **monthly and sparse** — `pointsToMonthlySeries` emits one point per month *that has data*. A range filter over a sparse series cannot produce a point for a month the account was dormant, so `numbers[0]` is the first **active** month inside the window, not the window's start. Here that is August at −1,512.42, which is exactly the observed arithmetic: `5317.06 − (−1512.42) = 6829.48`, and `6829.48 / 1512.42 = 451.56%`.

`filterBalanceSeriesByRange` documents the intended contract — *"the window's first point is the baseline the change is measured from"* — and it is implemented faithfully. The gap is that "the window's first point" and "the balance when the window opened" are only the same thing when the series is dense.

**Stated precisely, because it decides when this bites:** a monthly balance point carries the balance *after* that month's postings. So using the first in-window point as the baseline silently **excludes everything that happened during that month** from the reported change. The defect appears exactly when the first active month inside the window has a non-zero net change — and it is invisible when that month nets to zero.

That is why it is data-dependent rather than always wrong, and it yields a one-line test: *does the range change equal (closing balance − balance immediately before the window opened)?*

**Two further consequences of the same three lines:**

- `Math.abs(baseline)` makes the percentage's sign follow the change rather than the base. For a liability improving from −1,000 to −500 that is the sensible reading. For a **sign flip** — owing $1,512 to holding $5,317 — "+451.56%" is not a meaningful rate in either direction.
- `baseline !== 0 ? … : 0` means a window that genuinely opens at zero renders a real gain as **"+$5,000.00 (+0.00%)"** — a non-zero change beside a zero rate. That is precisely the dormant-then-funded case, so fixing the baseline without fixing this would swap one wrong number for another. **Not observed on screen** — it needs a window whose first point is exactly `0` — but it is a direct read of the line above.

## Fix

1. **Carry the baseline explicitly.** The balance at the window's start is a real quantity even when no posting occurred that month; it is the running balance carried forward — and before the first posting it is `0`. Either have the series include a point at the window start (carrying the prior balance forward through dormant months), or pass the opening balance alongside the series so the header does not have to infer it from `numbers[0]`. **This must cover `ALL` too**, whose baseline is the account's opening zero and which is wrong today for the same reason.
2. **Say "no rate" instead of inventing one.** When the opening balance is `0`, or when the sign flips between opening and closing, render the change amount with no percentage rather than `+0.00%` or a rate against `Math.abs`. A missing percentage is honest; a wrong one is not.
3. Keep `Math.abs` for the ordinary same-sign case — it is right for liabilities and is not what is broken here.

Do not fix this by making the chart hide ranges with sparse data: the plot itself is fine, and `filterBalanceSeriesByRange`'s existing "borrow the point just before the window" rule for 1M shows the codebase already has a notion of reaching outside the window for a baseline. This is the same idea applied to every range.

**Acceptance:** on `puncsky/example`, `Assets:Bank:Mercury:Checking` shows a change of **+$5,317.06** measured from a `$0.00` opening balance, with no percentage (or an explicit "—"), at **every** range including ALL; at 1M it still reads as the month-over-month change; an account whose balance moves within the window keeps its current, correct figures; and a liability improving from −1,000 to −500 still shows +50%. Add coverage for a dormant-then-funded account, a sign flip, and a zero opening balance — `series-util`'s tests cover the range filtering but nothing asserts the header's change or rate.

**Resolved 2026-09-14** in `fix(mobile): measure a balance change from the balance when the range opened`.

**The baseline.** A new `balanceSeriesBaseline(series, range)` in `series-util.ts` returns the closing balance of the month before the window, or zero before a series' first point. The balance series start at the ledger's first data: neither `useBalanceSheet` nor `useAccountReport` sends a time filter. `InteractiveLineChartD3` takes it as an optional `baseline` prop, and both the change row and the trend colour measure from it. Home's account charts card and the account balance card pass it.

**Results.**
- **`Assets:Bank:Mercury:Checking`** now reads `+$5,317.06` at 6M, YTD and ALL, with no percentage, because `w4/053`'s `changePercent` suppresses one from a zero start.
- **1M** still reads last month to this month: its baseline is the same earlier point the one-month window borrows to draw its line.
- **Same-sign liabilities** keep their percentage.

**Behaviour changes to know about.**
- **ALL** now measures from the ledger's opening zero everywhere, so `open_ledger/alphabet`'s Home card at ALL shows its whole balance as the change, with no percentage, instead of `+154.53%`.
- **The dashed "period start" line** in the plot still sits at the first plotted point; only the figures and colour moved.
