# The file editor never says a ledger is read-only — it just quietly drops Save and lets the caret move

**Severity:** trivial. **Estimate:** 10–15 minutes. Owner: mobile. A2/A3: every public `open_ledger/*` ledger is read-only, so this is the state a newcomer evaluating the app is in when they open a `.bean` file. Tapping a line moves the active-line highlight exactly as an editable editor would, and nothing on the screen explains why the keyboard never comes.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, public `open_ledger/alphabet`. Report-only QA; **no write was attempted and none is possible** — the screen is read-only, which is the subject.

## Repro

1. On `open_ledger/alphabet`, **Files** → `2026` → `Q2.bean`.
2. The editor opens with line numbers, beancount syntax highlighting, and an active-line highlight on line 1. The header carries the filename and a back chevron — **and nothing else**.
3. Tap any line of code (line 16 here). The **active-line highlight moves to that line** and its line number highlights, exactly as it would in an editable file.
4. No keyboard appears. No toast, no banner, no badge, no disabled Save button. There is no statement anywhere on the screen that this ledger cannot be edited.

The two captures are identical apart from which line is shaded, which is the whole point: the screen responds to the tap like an editor and then does nothing.

## Root cause

`src/screens/ledger-file-editor-screen/index.tsx` branches on `canWrite` in exactly two places, and **both are subtractions**:

```tsx
// :582
headerRight: canWrite ? headerRight : undefined,
```

```tsx
// :645
<CodeEditor readOnly={!canWrite} … />
```

So the read-only build of the screen is the editable one minus its Save button. Nothing is substituted for it. `selectLedgerFileEditorState` (`:573-579`) resolves `loading` / `error` / `unavailable` / `content` and has no notion of write access at all, so the read-only case is simply `content`.

**The app has the right sentence already, fully translated.** `src/translations/en.ts:25-26`:

> `ledgerReadOnly: "This ledger is read-only. Choose a ledger you can edit to make changes."`

`grep -c ledgerReadOnly src/translations/*.ts` returns **13 of 13 locales**, so the fix needs no new translation work. Its single consumer today is `src/components/ledger-write-guard.tsx:34`.

## Why the guard cannot simply be added here

This is the part that makes it a real gap rather than an oversight to copy-paste past. `LedgerWriteGuard` wraps **seven** routes — `add-transaction`, `add-transaction-legacy`, `add-transaction-next`, `edit-transaction`, `add-budget`, `open-account`, `receipt-capture` — and it works by *replacing* the screen with the message plus a `Browse ledgers` link. That is correct for those seven: a transaction form on a ledger you cannot write to has nothing to show.

The file editor is different and is deliberately **not** in that list (a fact `w4/034` also records): reading a ledger's source on a public example is a legitimate, valuable thing to do, and the guard would block it. So the editor cannot adopt the guard — it needs the *message* without the *replacement*, and that variant does not exist.

## Fix

Render an inline, non-blocking read-only indicator when `!canWrite`. The screen already has the right slot and the right component shape: `ErrorBanner` sits directly above the editor (`:589-594`) and is conditional in exactly the same way. A quiet sibling banner carrying `t("ledgerReadOnly")` — or, more proportionate to a trivial severity, a small `headerRight` label reading the equivalent of "Read-only" where Save would be — puts the answer where the missing affordance is.

Prefer the header label: it costs one line, it is exactly where a user looks for Save, and it avoids stacking a second banner above a file that may already be showing `ErrorBanner`. If the fuller sentence is wanted, the banner variant should collapse when `fileErrors.length > 0` so the two never stack.

**Do not** fix it by disabling the tap/caret. The active-line highlight is a genuine reading aid on a long file, and `readOnly` is already doing its job correctly — the editor refuses input, which is right. The gap is the explanation, not the behaviour.

**Acceptance:** opening any file on `open_ledger/alphabet` shows a read-only indicator using the existing `ledgerReadOnly` string or a short equivalent; the same file on `puncsky/example` still shows the Save button and no indicator; Save's existing disabled-until-dirty behaviour is unchanged; the indicator does not stack with `ErrorBanner`; and the editor remains fully readable and scrollable in the read-only state. Add a render test asserting the indicator appears when `canWrite` is false and the Save control when it is true — `selectLedgerFileEditorState` has tests, but write access is not one of its inputs, so nothing covers this branch today.

## Blast radius

One screen, one conditional. No change to `canWrite` resolution, to `LedgerWriteGuard`, to the seven guarded routes, or to the editor's `readOnly` behaviour. The `ledgerReadOnly` key gains a second consumer.

Not exercised: dark mode, enlarged Dynamic Type against a new header label's width (`w3/204` is the standing concern about action-label sizing in this exact header), RTL, and Android. **Also not exercised: how the read-only state reads to assistive technology.** `CodeEditor` is an expo-dom component (`dom={{ style: { flex: 1 } }}`), so its contents are a webview rather than native views; whether `readOnly` surfaces to VoiceOver at all is a separate question this run cannot answer (`w4/002` — VoiceOver does not start on this Simulator).

## Adjacent states

**The rest of the read-only story is handled well, which is why this stands out.** Verified in the same pass on `open_ledger/alphabet`:

- The file browser hides its entire write surface — no `+` in the header, no per-row trash icon — matching what `w4/051` recorded.
- The editor's `readOnly` genuinely prevents input: the tap moved the caret and the keyboard never appeared, so no edit can be started and then rejected.
- Directory navigation works: root → `2026` renders `Q1.bean` / `Q2.bean` / `year.bean` under a `< 2026` breadcrumb, and the syntax highlighting, line numbers and gutter all render correctly.

Also re-confirmed rather than refiled: `uv.lock` is dimmed, loses its chevron, and carries `accessibilityState={{ disabled: true }}` because `lock` is not in `TEXT_EXTENSIONS`. **`w4/022` already records this and concludes it is conservative-allowlist behaviour rather than a defect** — noted here only so a later pass does not rediscover it as new. The same note owns the horizontal-wrap problem visible in these captures (every posting's amount is off-canvas to the right), so that is not refiled either.

## Dedupe

`grep -rn 'This ledger is read-only\|LedgerWriteGuard\|canWrite' .pm --include='*.md'` over the whole board including `done/` → 18 lines across 13 files, every one read.

- **`w4/022`** ("Beancount files never wrap in the mobile editor") is the same screen and its Adjacent states already verifies the Files journey's `canWrite` gating in the **browser**. It does not touch the editor's own read-only presentation. Same sitting, different defect.
- **`w4/051`** documents that the browser correctly hides create/delete on a read-only ledger — the positive control cited above, not this gap.
- **`w4/034`** records that the file editor is *not* behind `LedgerWriteGuard` while `edit-transaction` is, and quotes the guard's message. That observation is the premise of this note; the note is the missing half.
- **`w3/done/114`** (closed) is the account picker's Create row routing a read-only user into a guarded dead end — the opposite failure: there an affordance existed and led nowhere, here no affordance exists and nothing says why.
- **`w3/m41`** and **`w3/done/140`** concern hiding Delete and Share from read-only users on the transaction detail — same principle (subtract the control), different screen, and neither adds a message either. Worth deciding the convention once.

No item covers the editor's read-only indication.

**Resolved 2026-09-14** in `fix(mobile): tell the file editor's reader when a ledger is read-only`.

**The banner.** When `canWrite` is false and the file has loaded, the file editor shows a quiet banner above the editor: a lock icon and the existing `ledgerReadOnly` string, already translated in all 13 locales. It gives way to the error banner when the file has errors, so the two never stack. Save stays hidden, and the editor stays readable and scrollable with its caret behaviour unchanged.

**Deviation.** The note preferred a short header label. That would have needed a new key in all 13 locales and would compete with the header's width concern (`w3/204`). The note also allows this banner variant, which reuses a translated sentence.

**Tests.** `ledger-file-editor-screen/__tests__/read-only-banner.test.ts` checks the source for the banner and for Save still hidden. With the screen reverted, the banner test fails. The mobile gate passes, with 1888 unit tests.
