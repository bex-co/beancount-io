# Report charts ignore a saved hidden preference on load

Severity: minor state/accessibility defect. Estimate: 40m, dashboard. A2: a
reader who hides report charts should find them hidden on their next visit, and
a collapsed section's controls should stay out of the tab order.

Environment: local build of current `main` at `23416828`, served through the QA
SSR server, anonymous public `open_ledger/example`, isolated headless
Chromium 149.0.7827.55, English, 320x800 light. Found while verifying `w4/090`,
whose own repro this defect masks.

Repro: open `/ledger/open_ledger/example/cash-flow?lang=en&time=2016-01`, press
Hide charts (the section correctly becomes `hidden` and `inert`, and the cookie
`beancount.chartsVisible.cashFlow=false` is written), then reload. The toggle
button correctly reports `aria-expanded="false"` and is labelled "Show charts",
but the section renders expanded: its wrapper keeps `grid-rows-[1fr]`, the
region is 430px tall with the charts on screen, and it carries neither `hidden`
nor `inert` — 8 focusable controls remain reachable inside it. Pressing the
button then hides them, so the saved preference costs an extra click every
visit. Reproduced identically with the cookie set before the first paint, so it
is not a timing artefact of the toggle.

Expected: a report loaded with charts saved-hidden renders the section
collapsed, `hidden` and `inert`, matching what the toggle says.

Root: the server cannot read the request cookie —
`curl --cookie beancount.chartsVisible.cashFlow=false` returns
`grid-rows-[1fr]` in the SSR HTML, the same as with the cookie set to `true`.
`common/hooks/use-cookie-storage-state/use-cookie-storage-state.ts` reads the
cookie in `useState(readValue)`, so the client's first render disagrees with
the server's. The toggle button recovers, because its `aria-label` text differs
and React re-renders that subtree, but the section's wrapper has no text
mismatch and keeps the server's `className`. `reports/components/
collapsible-charts-section.tsx` then never settles: `collapseSettled` only
flips on `onTransitionEnd`, and no transition runs, so `hidden` and `inert` are
never applied.

Fix in the report pages' visibility source or the section, not in zrender and
not by removing `hidden`/`inert`: make the server render the saved preference,
or make the section derive its collapsed state without depending on a
transition that may never fire. Preserve the `w3/127` repair that keeps a
collapsed section's controls out of keyboard navigation, the 300ms animation
for an interactive collapse, and the chart instances staying mounted.

Blast radius: every report page using `useChartsVisibility` — Balance Sheet,
Income Statement, Trial Balance, Cash Flow. Cash Flow was live-reproduced;
the others share the hook and wrapper and are source-traced.

Dedupe/history: `.pm` searched including `done/` and `blocked/` for charts
visibility, hidden/inert, cookie state and hydration. Completed `w3/127`
introduced the hidden/inert wrapper; this defect defeats it on a saved-hidden
load rather than replacing it. Completed `w4/090` concerns chart canvas
measurement and is closed; this is the separate defect that masked its repro.

Acceptance: with the preference saved as hidden, a fresh load renders the
section collapsed with `hidden` and `inert` applied and no focusable control
inside it reachable by keyboard, on narrow and desktop; the toggle still
animates on an interactive collapse and expand; chart instances still survive
collapsing. Add a regression test for the saved-hidden mount. Run dashboard
gates.

Evidence: reproduced live at `23416828`; the SSR HTML comparison above was
taken with `curl` against the same build. No product changes were made for this
note.

---

**Resolved 2026-09-20** — The defect does not reproduce, and the acceptance criteria already hold; what was genuinely missing is the regression test the note asks for, which is now in place. Evidence against the reported behaviour, gathered against a production build of current `main`: SSR honours the request cookie, contrary to the note's root cause — `curl --cookie beancount.chartsVisible.cashFlow=false` returns `grid-rows-[0fr]` with `inert=""` and `hidden=""` on the section, while `=true` returns `grid-rows-[1fr]` and neither attribute. In a real browser at 320×800, pressing Hide charts writes the cookie and collapses the section, and a reload renders it collapsed: `hidden`, `inert`, height 0, wrapper `grid-rows-[0fr]`, toggle labelled "Show charts" with `aria-expanded="false"`. Eight controls remain mounted inside — charts keep their instances by design — and none is focusable: focusing each in turn leaves `document.activeElement` unchanged, so `inert` is doing its job and the w3/127 repair is intact. On the source: `collapsible-charts-section.tsx`, `use-charts-visibility.ts` and `use-cookie-storage-state/` have **no commits** between `23416828` and HEAD, so the code the note describes is byte-identical to the code that now behaves correctly. The component already derives its settled state from the preference (`useState(!chartsVisible)`), so a collapsed-from-first-render section never needs a transition. Since nothing changed and the behaviour differs, the likeliest explanation is that the reported evidence came from a stale `.output` — the QA SSR server serves a build, and `yarn build` overwrites it, a trap this workstream has hit repeatedly. That is an inference, not something proven. What was real: none of the five existing cases in `__tests__/collapsible-charts-section.test.tsx` started from a saved preference — they all begin expanded and toggle — so breaking that initialisation left every one of them green. Four cases now cover the saved-hidden mount: collapsed without waiting for a transition, agreeing with what the toggle reports, staying out of the tab order, and still expanding on the first interaction. Two fail when the settled state stops deriving from the preference. Not verified: only Cash Flow was exercised live, as in the original note; Balance Sheet, Income Statement and Trial Balance share the same hook and wrapper and are covered by the component-level tests rather than individually in a browser. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 425 files, 4781 passed, 1 pre-existing skip — and `yarn build`). Shipped in `e00a943e` (`dashboard`).
