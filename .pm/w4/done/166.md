# Bulk JSON bypasses the zero-net inference guard and writes a posting that disappears on read

Severity: **minor**. Package: **cli**. Estimate: **30–45m**. Source: continuous
CLI QA for w4. **A1:** single and bulk additions must preserve the same observable
posting contract, including input reused by agents as JSON.

Environment: 2026-09-21, main `390568c220bfbdb0df1c9decb8436c64dfa3c9ca`,
checkout `cli/.venv/bin/bea` 0.3.0, Python 3.13.3, Darwin arm64.
All commands ran as fresh subprocesses under isolated
`cli/tmp/qa-20260921-cli-loop/`, with absolute ledger paths, closed stdin
(except the explicitly piped JSON), captured stdout/stderr, and 25-second
limits. Child-only `BEA_CONFIG_DIR`, `XDG_CACHE_HOME`, and `XDG_DATA_HOME`
pointed inside that directory; `BEA_NO_UPDATE_NOTIFIER=1`; inherited
`BEA_FILE` and `BEA_TOKEN` were removed. No hosted account was used.

## Reproducer and observed result

Use a pristine ledger:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Pipe this JSON to `bea --json --file /absolute/main.bean add transactions --from -`:

```json
[{"date":"2024-03-01","narration":"Zero","postings":[{"account":"Expenses:Food","amount":"0 USD"},{"account":"Assets:Cash"}]}]
```

The command exits 0 with `data: {"written": 1, "rejected": []}` and empty stderr.
Disk contains both the `Expenses:Food 0 USD` and bare `Assets:Cash` lines.
A fresh `bea --json --file /absolute/main.bean list transaction` contains only
one posting, `Expenses:Food 0 USD`; the Cash leg is absent. Check is valid,
which demonstrates the upstream inference behavior rather than a parse error.
Repeated on two pristine fixtures and a third minimal fixture.

Working controls: equivalent single `add transaction Zero --date 2024-03-01
-p 'Expenses:Food 0 USD' -p 'Assets:Cash'` correctly exits 2 without writing,
explaining the disappeared leg and asking for an explicit zero. Bulk JSON
with `"amount":"0 USD"` on Cash succeeds and lists both postings.

Expected: apply the deliberate zero-inference refusal consistently to bulk
input (normal row-validation/partial semantics), or otherwise preserve every
explicit input leg on read. Do not create a silent success that single-add
already rejects for this reason.

## Cause, scope, and repair

`cli/src/bea_engine/ledger/adding.py:696–782` validates bulk rows as
`TransactionDirective`, then formats and appends them. It bypasses the
single `_transaction` inference guard at lines 543–561. Upstream booking
drops an inferred zero; `ledger/reader.py:148` serializes booked postings,
so listing is reflecting the engine correctly. This is an input-validation
gap, not a request to fork upstream inference or synthesize read-only legs.

Put the actual lost-leg validation at a point both write paths use, retaining
bulk row numbers and atomic/partial handling. Keep cost-aware, nonzero inference
valid: the separate cost-lot guard false positive needs that distinction.
Caller search covers `commands/add.py:add_transaction/add_transactions`, both
engine handlers, `writer.format_transaction/write_transactions`, and listing.
No REST, GraphQL or MCP change is needed for these local-only commands.

- [ ] The shown bulk row is refused before atomic writes, with a useful row
      diagnostic and explicit-zero remedy; the original ledger stays byte-identical.
- [ ] With `--partial`, valid companion rows can write while this row is
      reported rejected and the command exits nonzero, following the existing contract.
- [ ] Explicit zero/zero and valid nonzero inference preserve both/all postings
      in a fresh list/query; meaningful regressions cover the shared guard.

Dedupe: all queues, completed records and open milestones searched for zero-net
inference and bulk lost postings. Completed w3/339 and commit `a60e560f` fix only
single-add; its full DoD and tests were reviewed and its controls still pass.
`git log` shows no later bulk extension. No overlapping open item; retain this
as the missing bulk path, distinct from raw-unit cancellation rejecting valid
cost-lot inference.

Evidence: verified `cli/tmp/qa-20260921-cli-loop/captures/cycle2-*-zero-*.json`,
`minimal-zero-*.json` and corresponding fixtures. Exact JSON is above; captures
retain arguments, streams, exit statuses and file hashes. No product fix or
shipping. Unverified: partial application for this specific candidate (acceptance
for the fix), other operating systems and hosted commands.

---

**Resolved 2026-09-23** — `add transactions --from` now runs each row through the same weight-based zero-inferred-leg guard as a single add (shared `_inferred_leg_is_zero`, applied to the text the row would be written as, with `price_total` kept as the exact `@@` total). The note's row is rejected as `Row N: Refusing a zero-net transaction …` with the explicit-zero remedy. Atomic mode leaves the ledger byte-identical; `--partial` writes the other rows and exits nonzero with `rejected_rows`. Explicit zero/zero rows and cost-aware nonzero inference still write every posting. Regressions are in `cli/tests/test_add_refuses_zero_net_inferred.py` (both refusal tests fail without the fix). The atomic-mode header now says "failed validation" instead of "failed schema validation", since it also covers this check. `make spec-check` was red from unrelated w2/m32 work; every other gate passed. Shipped in `660d937b` (`cli`).
