# `beancount:///oauth/callback` with no params shows "Sign In / loading…" forever — a fake progress state with no way out

**Severity:** minor — recoverable by force-quitting, and it takes a URL to reach. **Estimate:** 10–15 minutes. Owner: mobile. A2: this is the third route in the app that strands a user with no affordance, and it is the worst of the three, because the other two at least tell the truth about what they are. This one claims a sign-in is in progress that will never finish.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`, ledger `open_ledger/alphabet`. Report-only QA; **no OAuth exchange was attempted** — with no params the route never calls the completer, which is exactly why this state exists (see Root cause). Session and ledger were intact afterwards.

## Repro

1. With the app running and signed in, fire `xcrun simctl openurl <udid> 'beancount:///oauth/callback'` — no query string.
2. A full-screen card appears:

   > **Sign In**
   > loading…

3. It never changes. Two captures **8 seconds apart are byte-identical** (74,814 bytes each).
4. There is **no back affordance** — no header, no chevron, no button — and tapping where one would sit does not navigate.
5. Terminating and relaunching recovers completely: Home, `open_ledger/alphabet`, session intact, 6M pill unchanged.

## Root cause

The screen has exactly two states, and the "nothing to do" case falls into the wrong one.

`src/common/oauth/callback-url.ts` returns `null` when there are no params, and it is **right** to:

```ts
return any ? url.toString() : null;
```

Its header explains the design — the completer validates a full URL against the pending request ("exact redirect URI, one `state`, one `iss`, no tokens in the query"), and params are replayed verbatim "so the single-value checks still fail closed". Failing closed on an empty callback is correct security behaviour and should not change.

`app/oauth/callback.tsx` then does:

```tsx
useEffect(() => {
  if (!callbackUrl || startedFor.current === callbackUrl) return;   // ← returns here
  ...
  void completeOAuthAuthorization(callbackUrl).catch(...)           // never runs
}, [callbackUrl]);
```

so `failed` stays `false`, and the render picks the optimistic branch:

```tsx
<Text style={styles.title}>{failed ? t("journalError") : t("signIn")}</Text>
{!failed ? <Text style={styles.message}>{t("loading")}</Text> : null}
{failed ? <Button …>{t("backToSignIn")}</Button> : null}
```

The escape hatch — **"Back to Sign in"**, which calls `router.replace("/auth/welcome")` — already exists and is gated on the one state that cannot be reached from here. And there is **no `app/oauth/_layout.tsx`**, so the route inherits the root `<Slot />` with no header and no back button.

## Fix

Treat "no callback URL" as a failure, since that is what it is — there is no authorization to complete:

```ts
const [failed, setFailed] = useState(false);
...
useEffect(() => {
  if (!callbackUrl) { setFailed(true); return; }
  ...
```

That alone turns the dead end into the existing **Error / Back to Sign in** card, using machinery already on the screen.

**Better, if the session is consulted:** a signed-in user who lands here should go back into the app, not to the sign-in screen — sending them to `/auth/welcome` drops them into **`w4/021`**'s trap instead. `app/(app)/_layout.tsx` already redirects to `/auth/welcome` when there is no session, so the inverse check is available; prefer `router.replace("/(app)/(tabs)")` when a session exists and `/auth/welcome` when it does not. Decide this together with `w4/021`, since both are about where a stranded user should be sent.

While here: the card reads **"Sign In"** over **"loading..."** — title case over lowercase, with an ASCII ellipsis (`en.ts:222`, `loading: "loading..."`). Whatever the state ends up being, those two lines should agree in style.

**Acceptance:** `beancount:///oauth/callback` with no params shows an error card with a working button rather than a permanent "loading…"; a *real* callback with valid params still completes sign-in unchanged; a cancelled authorization still lands on `/auth/welcome` via the existing `error.cancelled` branch; and the fail-closed validation in `callback-url.ts` is untouched. Add a test that `callbackUrlFromParams(uri, {})` is `null` **and** that the route renders its failed state for that input — the URL builder's behaviour is the documented part, the screen's reaction to it is what is missing.

## Blast radius

One route file, one effect branch. No change to the OAuth completer, the redirect-URI builder, the PKCE flow, or the validation rules — all of which are correct and deliberately strict. The only behaviour that moves is what a paramless visit renders.

Not exercised: a callback with **partial or malformed** params (e.g. `?state=x` with no `code`), which *does* build a URL and so reaches `completeOAuthAuthorization` — that path would surface the real failure UI, but firing it means invoking the completer against a live session, which this run has no authorization for. Also not exercised: Android, and the cold-launch variant where the app is not already running.

## Adjacent states

The OAuth plumbing around this is **careful**, and the note should not read as doubt about it: `callback-url.ts` rebuilds the URL from parsed params precisely because `Linking.useURL()` is null on a cold launch, replays repeated params verbatim so single-value checks fail closed, and `startedFor` guards against a re-render restarting a completion. The cancelled-authorization branch already routes somewhere sensible. This note is about the one input that reaches none of it.

## Dedupe

`grep -rli "oauth/callback\|callbackUrlFromParams\|oauth callback" --include='*.md' .` over the whole board including `done/` → seven files: `w4/done/m5/done/t002.md` and `t004.md` (the app-links milestone, closed, about `/ledger/...` link resolution), `w3/done/182` (the filter Apply button — an unrelated string match), and four older closed `w1`/`w2` items. None covers this route's paramless state.

**`w4/021`** ("`beancount:///auth/welcome` shows a signed-in user the sign-in screen, with no way back") is the same **family** and should be fixed alongside: same trap, same custom-scheme reachability argument, same question of where to send the user. It is not the same defect — that one renders a real screen with working buttons for the wrong audience; this one renders a state that is untrue for anybody.

`w4/021` now carries the **complete inventory** of this family, enumerated structurally rather than discovered one at a time: it is exactly three screens — `auth/welcome`, `auth/server` and this one — all of them outside `(app)/`. Everything under `(app)/` is fine, because `app/(app)/_layout.tsx:56` mounts a `Stack` that supplies a back control to every pushed route. And `app/+not-found.tsx`, the fourth non-`(app)` screen, already does the right thing with a `Go to Home` button — it is the pattern to copy, and it sits in the same directory.

`w4/034` is the sibling failure mode — two routes that *crash* when reached without their params, where these instead render something misleading.

**Resolved 2026-09-14** in `fix(mobile): stop the bare OAuth callback route showing a sign-in that never finishes`.

**With no authorization response,** `app/oauth/callback.tsx` no longer shows the permanent "Sign In / loading…" card:
- A signed-in arrival goes back into the app. It uses `useSignedInOnArrival` from `w4/021`, so it follows the same arrival rule as the other auth routes.
- Anyone else gets the existing failure card with its "Back to Sign in" button.

**A real callback** with params still completes as before. The cancelled branch and the fail-closed `callbackUrlFromParams` are untouched, and that function keeps its existing tests in `common/oauth/__tests__/callback-url.test.ts`.

**Tests.** `src/__tests__/oauth-callback-route.test.ts` checks the source for the redirect and for the failure state when there is no callback URL. With the route reverted, both tests fail. The mobile gate passes, with 1888 unit tests.

**Not done.** The "Sign In" / "loading…" capitalization mismatch the note mentions in passing.

**Not exercised.** The deep link on device, and a real sign-in.
