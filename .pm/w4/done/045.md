# Edit Transaction has no concurrent-edit handling, though its message is already written and translated into all 13 locales

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: the sibling editor on the same optimistic-lock scheme handles this case properly, with a named recovery action. Edit Transaction shows a raw error and leaves the user with a draft it will keep refusing to save, and no hint that reloading is what unsticks it.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA; **nothing was saved**, so the conflict itself was not induced — see "What was and was not observed".

## The gap

Both editors save against a `sha256sum` optimistic lock and both can be rejected because the entry moved underneath them. They handle that rejection completely differently.

**The file editor** (`ledger-file-editor-screen/index.tsx:440-458`) classifies the error and offers a way out:

```ts
const msg = err instanceof Error ? err.message : String(err);
if (isConflictError(msg)) {
  Alert.alert(t("ledgerEditorConflictTitle"), t("ledgerEditorConflictMessage"), [
    { text: t("ledgerEditorKeepEditing"), style: "cancel" },
    { text: t("ledgerEditorReload"), style: "destructive", onPress: handleReload },
  ]);
} else {
  Alert.alert(t("ledgerEditorSaveFailed"), msg);
}
```

`isConflictError` (`ledger-file-editor-screen/utils.ts:1-4`) matches `sha`, `conflict` or `409` in the message. The user gets **File Changed**, and a choice between *Keep Editing* and *Reload*.

**Edit Transaction** (`edit-transaction-screen.tsx:258-265`) does none of it:

```ts
if (!outcome.ok) {
  // The toast says "couldn't save"; the inline message says why.
  setSaveError(
    outcome.error instanceof Error ? outcome.error.message : outcome.message,
  );
  return false;
}
```

Every failure is the same failure. A stale checksum renders whatever the server said, inline, in red — no classification, no reload action, and no way to recover other than backing out and losing the draft (the unsaved-changes guard will ask first, so the exit is at least not silent).

This is despite the screen's own help text telling the user in advance that this exact thing can happen:

> *"Edit raw beancount source below. A stale checksum or invalid beancount will be rejected with an error."*

## The string already exists, in every locale

`src/translations/en.ts:376`:

```ts
editConflict: "Transaction was modified elsewhere. Reload and try again.",
```

That is precisely the message for this case — including the instruction — and it is **referenced nowhere**. A sweep of `src/` and `app/` (excluding `src/translations/`) for `editConflict` returns no hits, and no code constructs it dynamically. All thirteen locale files define it, so it has been translated twelve times over for a code path that was never wired up.

Whoever wrote this screen's copy planned the behaviour; the handler never grew it.

## Root cause

Not a bug in a line so much as a missing branch. `handleSave` funnels everything through `confirmWrite`'s generic `failureMessage: t("editFailed")` and then surfaces `outcome.error.message` verbatim. Nothing in that path distinguishes a **409 / checksum** rejection from **invalid beancount**, which are the two failures the screen's own help text names and which need opposite responses:

- invalid beancount → keep the draft, the user should fix the text;
- stale checksum → the draft can never be saved as-is; the entry must be re-read.

The second is the one the app currently cannot express.

## Fix

Reuse the classifier rather than writing a second one. `isConflictError` is already a standalone pure function in `ledger-file-editor-screen/utils.ts` — move it somewhere both editors can import (`src/common/` is where the other shared editor helpers live) and branch in `handleSave`:

```ts
if (!outcome.ok) {
  const msg = outcome.error instanceof Error ? outcome.error.message : outcome.message;
  if (isConflictError(msg)) {
    setSaveError(t("editConflict"));
    // …and offer the reload, see below
  } else {
    setSaveError(msg);
  }
  return false;
}
```

The message alone is an improvement, but `editConflict` says *"Reload and try again"*, so give the user the reload. This screen has no `handleReload` equivalent — it seeds the editor once per opened entry and deliberately refuses to let a refetch replace an active draft (`:159-169`, and the comment is right to do so). Reloading therefore means resetting `initialized` and bumping `documentEpochRef`, which is the same move that effect already performs. Do it behind the same two-button Alert the file editor uses, so a draft is never discarded without a confirmation.

**Do not** change `getLedgerEntryContext`'s `fetchPolicy` or the "don't clobber an active draft" rule while fixing this — both carry comments explaining why they are the way they are, and both are correct.

**Acceptance:** with the mutation forced to reject on the checksum, Edit Transaction shows `editConflict` rather than a raw server message and offers *Reload* / *Keep Editing*; *Reload* re-reads the entry and clears the dirty flag; invalid-beancount rejections still show the server's own explanation, because that text is the useful part there; the file editor is unchanged. Add a unit test for the shared `isConflictError` against both screens' error shapes, and one asserting the transaction editor picks the conflict branch — the mutation is mocked, so neither needs a real write.

## What was and was not observed

The **gap** is confirmed: both handlers were read at HEAD, and the `editConflict` sweep is reproducible (`grep -rn editConflict src/ app/ | grep -v src/translations/` → empty; `grep -c editConflict src/translations/*.ts` → 1 in each of the thirteen locale files).

The **failure itself** was not induced. Producing a real checksum conflict means writing to `puncsky/example` twice — once to move the entry, once to attempt the stale save — which is outside this run's authorization. So what the raw server message actually reads like on screen is unknown; it may be anything from `409` to a stack-ish string. That uncertainty does not affect the finding, since the point is that no branch exists to improve on it, but it does mean the *severity* could be worse than minor if the raw text is unintelligible.

## Blast radius

One handler on one screen, plus moving one pure function to a shared location. No change to the mutation, the lock scheme, the seeding rule, or the file editor. The suggested reload is new behaviour on this screen and is the only part that needs care, because it discards a draft.

Not exercised: the conflict path on either editor, dark mode, enlarged Dynamic Type, Android. The file editor's conflict handling is likewise read-only verification — it too would need two concurrent writers to demonstrate.

## Adjacent states

The rest of Edit Transaction's save path is **careful and correct**, which is what makes the missing branch stand out:

- `entryHashRef` moves to the hash the server reports after a save, because the entry's identity is content-derived, so a second save from the same screen targets the entry as it now exists.
- Edits typed *while* a save is in flight are tracked separately (`markRevisionsSaved`), and the screen stays put with an accurate dirty flag rather than navigating away over an uncovered edit.
- On success it pops back with `router.dismissTo` and **replaced params**, because the detail screen behind is holding a now-dead `entryHash`; when the server reports no usable new identity it falls back to `router.dismiss(2)` onto the journal rather than a detail screen that could only error.
- `getLedgerEntryContext` is deliberately excluded from `invalidateLedgerData`'s eviction list, with a comment explaining that evicting it after a delete would send the mounted detail screen after an entry that no longer exists.

A broader sweep for unused translation keys suggested a cluster of roughly thirty more. The first attempt used a prefix heuristic and was wrong — `discoveryEmpty_*` and `budgetInterval*` are built dynamically — so it was not filed. Re-done by enumerating all 41 non-literal `t()` call sites and resolving each one's key space, it now stands as **`w4/046`**: 35 dead keys, 455 definitions across 13 locale files. `editConflict` is one of them, and is the one that should be **wired up rather than deleted** — `w4/046` says so explicitly and defers to this note.

---

**Resolved 2026-09-14** in `fix(mobile): offer a reload when Edit Transaction saves against a stale checksum`.

**Shared classifier.** `isConflictError` moved to `src/common/ledger-conflict.ts`, and the file editor and `ledger-m15.test.ts` now import it from there. Edit Transaction classifies a rejected save through a new pure `selectSaveFailure` (`edit-transaction-screen/save-failure.ts`).

**A stale checksum or conflict.**
- The editor shows `editConflict` inline, plus an alert offering *Keep Editing* and *Reload*. Those two labels reuse the file editor's translated strings.
- *Reload* re-reads the entry under its current identity (`entryHashRef`) and reseeds the editor: a new document epoch, a reset revision tracker, the fresh checksum, and a clean dirty flag. It mirrors the seeding effect.
- A draft is never discarded without that choice.

**Any other rejection.** Invalid Beancount still shows the server's own message. The `network-only` fetch policy and the "never clobber an active draft" seeding rule are untouched.

**Tests.** `save-failure.test.ts` covers checksum and 409 messages against other rejections, plus a source guardrail that the screen uses `editConflict` and offers Reload. With the screen reverted, the guardrail fails. The existing `isConflictError` tests still pass from the new location. The mobile gate passes, with 1877 unit tests.

**Not exercised.** A real checksum conflict (two production writes), and the alert on device.
