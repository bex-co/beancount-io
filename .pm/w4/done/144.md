# Three login continuations still drop the destination

Found while reviewing w4/m19 (which fixed the fragment delimiter in the three
producers FINDINGS scoped). These three were verified by reading the code at
`05bc84d3` but were deliberately left out of that milestone.

Each builds a login `next` from the pathname alone — no query, no fragment —
and none passes it through `getSafeRedirectPath`:

- `dashboard/src/common/components/ledger-layout/ledger-route-error.tsx:16-27`
  — `useRouterState({ select: (state) => state.location.pathname })`, then
  `navigate({ to: "/auth/login", search: { next: pathname } })`.
- `dashboard/src/common/root-route/error-page.tsx:30,41-44` — the same shape.
- `dashboard/src/common/apollo/links/auth-error-link.ts:88` —
  `window.location.pathname + window.location.search`, so it keeps the query
  but drops the fragment. This one is window-based, not router-based, so it
  cannot use `getSafeReturnPath` as it stands.

Why it matters: `ledger-route-error.tsx` is the `errorComponent` of
`/ledger/$ledgerOwner/$ledgerName`, whose loader w4/m19/t002 changed. That one
route now has two continuation producers that disagree about how much of the
destination survives — the loader keeps path, query and fragment, the error
component keeps only the path. A reader sent to login from the error component
loses their time filter and their anchor.

Likely shape of the fix: point the two router-based producers at
`getSafeReturnPath(location)` from `common/lib/auth/auth.ts`, which already
serializes and validates. The Apollo link needs its own decision, since it has
a native `window.location` (where `hash` keeps its `#`) rather than a parsed
router location.

Not yet reproduced in a browser — the error components need an unauthenticated
error against a readable route to fire, which the public instance does not
offer anonymously. Confirm the repro before implementing.

---

**Resolved 2026-09-20** — All three now carry the whole destination. `ledger-route-error.tsx` and `root-route/error-page.tsx` use `useLoginNextPath()`, the hook that already wraps `getSafeReturnPath` for guest actions, so the shape the note proposed was available without writing anything new. `auth-error-link.ts` keeps its own assembly, because the note is right that it cannot use `getSafeReturnPath`: it holds a native `Location`, whose `hash` still carries its `#`, rather than a router location whose parsed `hash` has had the delimiter sliced off. It now appends that hash and passes the result through `getSafeRedirectPath`, so it is validated like every other `next` and falls back to `/` rather than being repaired if it does not come out relative. That assembly moved into an exported `locationAsNext`, alongside `buildUnauthenticatedLoginHref`, which the module already exports for the same testing reason. The note's caution about reproduction stands and was respected: the two error components need an unauthenticated error against a readable route, which the public instance does not offer anonymously, so this was **not** verified in a browser. It was verified by test instead. The ledger error component's existing case had been asserting the path-only contract against a fixture location that carried only `pathname`; its fixture now carries a real `href` with a query and a fragment, and the case asserts the full `/ledger/alice/books/commits?time=2016#entry-7` reaches login — it fails when the component is put back on `state.location.pathname`. Five new cases cover `locationAsNext`: a query, a fragment with its delimiter intact, a fragment arriving without a query, a bare path, and two hostile candidates falling back to the root. The two fragment cases fail when the hash is dropped from the assembly. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 424 files, 4768 passed, 1 pre-existing skip — and `yarn build`). Shipped in `f8d0de23` (`dashboard`).
