# Overview drops transaction amounts for a valid account component filter

Severity: minor. Estimate: 50m. Package: dashboard. A2: account search should retain usable transaction summaries for accepted filter inputs. Source: repeated dashboard QA, 2026-09-17.

Environment: production https://beancount.io, anonymous public synthetic `open_ledger/example`, QA-owned isolated headless Chromium 131, English/light, 1440×1000 and 390×844. Local main `26d54a9db7d33c31a549bd12a0454a1c01f3f038`; deployed main asset `main-BIr0jJni.js`, exact deployed commit unverified.

Repro: open `/ledger/open_ledger/example`; type `Checking` into Account and press Enter. The URL becomes `?account=Checking`. Wait for loading to settle and scroll to Recent activity: Hoogle Payroll, BANK FEES and every returned row show a dash instead of their amount; desktop additionally says Multiple postings, even on the two-posting bank fee. Repeat from a fresh direct load at 390px: BANK FEES again shows a dash. Expected: the matching Checking posting still supplies the selected-account amount, e.g. bank fee **-4 USD**, payroll **2550.60 USD**.

Working control: `?account=Assets%3AUS%3ABofA%3AChecking` shows the payroll amount 2550.60 USD. Both filter values produce HTTP 200 GetLedgerJournal responses, total 275 and the same ordered first eight entry hashes. BANK FEES hash `b87655bf8c041110e7b6162278ffeb8c` has Checking -4 USD / Expenses:Financial:Fees +4 USD; payroll hash `c94ed5271c6df2e9a494015d1dcb6121` has Checking +2550.60 USD. The backend does not omit postings or return different transactions.

Root: `dashboard/src/features/reports/overview/lib/transaction-summary.ts:21` uses exact equality or `startsWith(root + ':')`. The active-account branch at 72 filters selected postings with this predicate, so component `Checking` matches no full account and amounts becomes empty. RecentActivityCard renders that as Multiple postings / dash. The UI accepts typed values (`common/components/ledger-search-controls/index.tsx:193`), while the ledger filter's `foundation/rustledger/directive-filter.ts:230` accepts a whole account component or case-insensitive pattern search. That producer behavior is confirmed by the identical live responses. No backend fix is warranted.

Fix: selected-posting matching must honor the accepted account-filter semantics, including the reproduced component-name form, instead of silently interpreting all filter strings as a full account root. Reuse a suitable dashboard matcher if one exists; otherwise keep a small documented browser-owned matcher with the required regex/fallback behavior, without a cross-package import or bundling the ledger engine. Preserve exact subtree selection and match each posting once. Do not choose all postings (which would net transactions to zero) or treat valid filters as no-data states.

Acceptance: `Checking` and its full path give the same Checking summary amounts at both widths. Cover component, full path/subtree, accepted case-insensitive pattern, invalid-pattern fallback and genuinely unmatched selection using meaningful posting fixtures; verify no unrelated posting enters the total. Preserve transaction ordering, units, loading/empty/error state and entry-context navigation. Run dashboard native gates when implementing.

Blast radius/dedupe: summarizeTransaction has one production caller, RecentActivityCard; overview and its redirect alias share it. Other report/Journal totals are not claimed broken. Searched all .pm queues including done/blocked for account regex/component, Checking summaries, Multiple postings and selected-posting mismatches; no duplicate found. `w4/074` touches the same helper but owns the separate **unfiltered mixed-income/expense precedence** branch; coordinate edits and retain both regression cases. Completed w3/m30 concerns applying account filters in producers/other reports, and the producer here already works. `git log -S summarizeTransaction` and path history show only original import `af5339de`, with no later repair.

Verified evidence: `dashboard/tmp/qa-20260917/account-filter-summary.json` contains sanitized public response controls; `account-substring-summary.png` captures the fresh narrow failure; `payroll-summary.json` records the full-path control. Authenticated roles, other browsers, actual screen-reader speech, regex variants beyond the reproduced component, and patched behavior remain unverified. No product fix, production mutation or shipping performed.

**Resolved 2026-09-19** — the summary's selected-posting test now mirrors what
the ledger's own account filter accepts: a whole account component, or a
case-insensitive unanchored regex, falling back to literal equality when the
pattern will not compile. It had used a plain exact-or-subtree test, so typing
`Checking` returned the right transactions but matched none of their postings
and every row lost its amount. Deliberately a small local matcher rather than a
cross-package import. Verified live at 1440×1000 and 390×844: `?account=Checking`
now shows the bank fee as `-4 USD` and the payroll as `2,550.6 USD`, identical
to the full-path control. Seven regressions cover the component form, full path
and subtree, a case-insensitive pattern, the invalid-pattern fallback, a
genuinely unmatched selection, and that no unrelated posting joins the total
(which would net the transaction to zero); reverting the matcher fails three.
w4/074's mixed-entry branch in the same helper is preserved and re-verified.
Shipped in `670864c2` (`dashboard`).
