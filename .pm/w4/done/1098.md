# Run only the requested BQL bookmark on startup

**Severity:** minor. **Owner:** dashboard. **Estimate:** 45–60 minutes. **A2:** opening a shared or saved query should execute that requested query without also replaying an unrelated query from this device's history. One residual of [W3/m12](../w3/done/m12/README.md)'s intended-query startup contract, not another historical finding group.

## Reproduction and controls

Production `https://beancount.io`,2026-10-25 America/Los_Angeles; owned isolated headless Chromium156.0.8078.47, anonymous public synthetic `open_ledger/example`, English/light/UTC. Fresh1440×1000 and390×844 complete cases plus an earlier independent390 discovery reproduce. All inputs, bookmarks and history are created through the real UI; **no local-storage injection, response substitution, delayed request or failure**.

1. Open Query with bookmark A: `SELECT 'qa-20261025-bookmark-A' AS marker LIMIT 1`. It executes once and shows its one correct row.
2. In Monaco, type B: `SELECT 'qa-20261025-bookmark-B' AS marker LIMIT 1`. Activate **Execute Query** by Enter. Save the resulting `?query=` URL as bookmark B. It sends B once, with B's correct result and history order `[B,A]`.
3. Execute A again through the editor/toolbar. It sends A once and leaves native saved history `[A,B]`.
4. Open the saved **B URL directly**. Although the address bar and editor contain B, the fresh document sends **two QueryShell requests**, one A and one B. Both return genuine HTTP200 and their correct literal rows. Both cards are expanded, with unrelated **A above B**, and stored history is `[A,B]` again. The request order varies between repeats; the extra A request does not.
5. Working control: explicitly execute B, making history `[B,A]`, then reload that unchanged B URL. It sends **only B once**; B opens with the correct row and A remains collapsed/unread.

Each complete case uses seven real queries: three setup executions, two on the mismatched-history bookmark load, one explicit B control and one matching-history reload. Fourteen retained queries plus five discovery queries all return the exact single marker column/row independently checked against the submitted literals. Both widths reproduce one unintended query per mismatched bookmark opening. No mutations, hosted writes, page exceptions or console errors. Screenshots at both widths visibly show editor B and the unexpected expanded A result above the correct B result. The bookmarked query itself is neither lost nor calculated incorrectly.

## Cause and bounded repair

`dashboard/src/features/bql/pages/index.tsx:206–220` correctly auto-executes the URL query. Independently, its history map at:412 gives **the first stored item** `isInitiallyOpen={index === 0}`, even when that item differs from the requested URL query. `components/query-result-card.tsx:307–313` opens that mounted card; its real details toggle at:315–319 sees no result/error/loading and calls onExecute for that different query. `use-query-history.ts` restores `[A,B]` from ordinary browser storage. The URL execution marker prevents repeating the page's own submitted query, but cannot coordinate this separate **different-query** startup action. Neither backend execution nor the per-query result cache is wrong.

Make initial result opening/execution honor the explicit normalized URL query before any default newest-history auto-open. An older requested bookmark must be the only startup query; other stored cards remain available without running until explicitly opened. Keep the current no-query/default-history behavior, normal manual older-card execution, fresh explicit reruns, and new toolbar/shortcut submissions opening their own results. Do not just disable every history auto-open, deduplicate A against B, stop adding history, or restore cache-first queries. Preserve per-query loading/errors/retries/exports, exact current editor text, own-URL acknowledgement, history identity/order, collapsed choices on deletion and ledger isolation. No API, dependency, storage migration or new global state is needed.

Acceptance: real page/router/history/card integration first saves distinct A/B through normal executions, retains most-recent A, and loads older bookmark B. Exactly one B request/result appears; A stays saved, collapsed and unexecuted until the reader opens it. Cover matching-top and empty history, no-query startup, manual older-card opening, a new toolbar submission while URL navigation settles, and the existing deletion/late-draft safeguards. Exercise the native details toggle path rather than mocking QueryResultCard away. Repeat desktop/narrow, then run dashboard format:check, lint, test and build on implementation. The no-query/manual-uncached compatibility cases above are required follow-up, not newly verified by this cycle.
