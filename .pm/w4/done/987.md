# Explain file-download generation failures and keep retry usable

**Severity:** minor. **Estimate:** 35–50 minutes. **Owner:** dashboard. **A2:** a reader choosing Files → More actions → Download should know when the file could not be generated, while keeping the file available to retry.

## Reproduction and controls

Production `https://beancount.io`,2026-10-22; owned isolated headless Chromium155.0.8059.85, anonymous public `/ledger/open_ledger/example/files/blob/main/main.bean`, English/light, fresh390×844 and1440×1000. All file/ledger responses are real. **Only the owned page's URL.createObjectURL is temporarily made to throw** `qa-controlled-file-download-generation`; this is a modeled browser API failure, not an observed disk, network or production outage.

1. Wait for the actual read-only Monaco editor and file actions. Native More actions → Download succeeds once at each width, yielding main.bean.
2. Save the original browser API, install the scoped throw, then activate the same Download menu item with Enter at390 or Space at1440.
3. Each case makes exactly one object-URL attempt, emits one uncaught Error matching the injected marker and produces **zero additional downloads**. There is no toast or nonempty alert. The menu remains open with its enabled Download item focused, so the action appears to have done nothing.
4. Restore the original API and activate the same still-open menu item. A second genuine download succeeds with no further exception, the menu closes normally and focus returns to More actions.

Both baseline/retry pairs are byte-identical across both widths: **318015 bytes**, SHA-256 **673efbe1493cac4f09b50d2bfabf2acf4439c5b5dc19c68d57fea823ee6cc3ba**. That independently matches the decoded real GetLedgerFile content, HTTP200 with the same size and no GraphQL errors. The existing file and its bytes are available throughout; the failure occurs while generating the local download. All actions are read-only.

## Cause and bounded repair

`dashboard/src/features/ledger-editor/file-editor/components/ledger-file-view/file-view-mode.tsx:26–30` obtains the available content and calls downloadFile without handling its exception. `shared/lib/utils.ts:331–359` decodes the actual base64 into a Blob, then calls URL.createObjectURL. Its errors propagate to the shared `FileActionButtons` menu in `file-editor/components/non-text-file-views.tsx:175–181`, which binds onClick directly to onDownload. The thrown callback prevents normal menu-item completion and produces no user-facing failure feedback.

Handle download-generation errors at the owning file action boundary using localized file/common notification conventions. Keep the file, exact bytes, enabled manual retry and usable keyboard focus; let normal menu dismissal/focus behavior remain coherent. Do not claim a completed download on failure, swallow arbitrary errors globally or automatically repeat the action. Preserve filenames, byte/MIME handling, cleanup, read-only access and the260 distinction between known size0 content and unavailable positive-size content. No API, dependency or backend change is needed.

Acceptance: the real menu and download helper with a failing object-URL call produce localized visible failure feedback, no uncaught exception and no download. After API restoration, one native retry downloads the same bytes/name and leaves useful focus. Retain nonempty/empty text and unavailable-content controls, plus ordinary image/PDF/unknown download behavior. FileActionButtons is also used by those three views; their failure paths were not exercised live. Run dashboard gates when implementing. Actual native save-dialog/disk failures, other engines/locales and the repaired deployment remain unverified.
