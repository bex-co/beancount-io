# Reader-chosen view state still resets at the outer layout boundary, and on the overview card

Severity: minor interaction regression, same class as w4/m16. Package: dashboard. Estimate: ~45m.

w4/m16 moved the chart selection of the four statement reports from their content components to their pages, because the report's own Apollo pending branch unmounts the content. The standing `/simplify` review found the class is not fully closed. Verified on `main` at `4825ac71`.

## The second unmount boundary

`common/components/ledger-layout/index.tsx` replaces the whole `Outlet` with a loading state when `isRoutePending` — true whenever the shared `account`, `filter` or `time` scope changes. That unmounts the _page_, so the selection w4/m16 just moved into the page still resets on a shared-filter edit. The reader-visible symptom is the same one m16 fixed, from a boundary m16 deliberately did not own: its own coordination note assigns the outer router-pending boundary to m13, which keeps unmounting on genuine scope changes on purpose.

So this needs a decision rather than a reflex fix. Either a chart choice is view preference that should outlive a scope change — in which case it needs a home that survives both boundaries, such as the URL (the `ledger-data/holdings` page already does this with a validated `?view=` and `replace: true`) or per-report cookie state next to `useChartsVisibility` — or it is scoped to the data being viewed and resetting is correct. m16's definition of done explicitly forbids a global preference store and requires the state to stay scoped to the report/ledger lifetime, which is why a cookie was not adopted there; the URL option is compatible with that constraint and has repo precedent.

## Same class, outside m16's four reports

`features/reports/overview/components/net-worth-card.tsx` owns `const [view, setView] = useState<"chart" | "table">("chart")`. Its parent `overview/index.tsx` returns a spinner unconditionally while loading, with a comment stating it must not keep prior cards, so a shared-filter change flips the reader's chart/table choice back to chart.

## Verified clean, do not re-fix

`reports/account/index.tsx` already keeps `selectedTab` at page level. `AccountJournalTable`'s filters, `showMetadata`, `showPostings` and `offset` return their loading state from inside the owning component, so React preserves them. The `ledger-data` pages using `QueryView` (events, errors, documents, accounts, budget) all declare their view state above it. `journal-page.tsx`'s loading state is a ternary inside the owner, gated on an empty result. `ledger-data/holdings` is URL-backed and immune by construction.

## Smaller items

`reports/trial-balance/__tests__/trial-balance-content.test.tsx` renders the component inline with a fourteen-prop list duplicating what `Harness` already builds, so every new prop is a two-site edit; giving `Harness` an optional data override removes it. And three of the four m16 fixes are pinned only by the Cash Flow page test — w4/m16/t005 owns extending that coverage to the other three.

One note for whoever picks this up: `reports/account/index.tsx` uses `isLoading && !accountReportData` with a `previousData` fallback, so it deliberately shows stale data while loading, unlike the statement pages' `selectSettledReportData` contract. That asymmetry looks intentional and is documented per-page rather than globally, but it is worth confirming rather than assuming while touching this area.

**Resolved 2026-09-20** — The decision this note asks for was made rather than deferred: a chart choice is **view preference that should outlive a scope change**, on the precedent the repo already set. `ledger-data/holdings` keeps its grouping in a validated `?view=` written with `replace: true`, for the same reason and with a documented rationale; that option is the one the note names as compatible with w4/m16's constraint against a global preference store, since the value stays scoped to the page rather than to a reader. Flagging the judgement plainly: this adds `?view=` to four report URLs and the overview, so a shared link can now carry a view the sender picked. If that is unwanted, the alternative the note offers — accepting the reset as correct — is a one-line revert per page. The symptom was reproduced first at HEAD: selecting "By Activity" on Cash Flow and then editing the shared Time filter to 2016 in-app reset the page to "Net Cash Flow", exactly as described. Rather than five copies of the Holdings block, `common/lib/navigation/view-search.ts` and `common/hooks/use-url-view.ts` hold the contract once, and each page contributes a small `search.ts` naming its own views. Wired: the four statement reports and `net-worth-card.tsx`, whose parent returns a spinner and keeps no prior cards. After the change, verified live, "By Activity" survives the same time-filter edit and the URL reads `view=byActivity`; returning to the default drops the param, so an untouched page has a clean URL; and an injected `?view=<script>` is stripped with the default selected and the page rendering normally. Two adjustments the note did not anticipate: the schema leaves `view` optional in its output, because a required one would force every `Link` to these routes to name a view it does not care about; and the five affected test suites needed a router mock that actually notifies, since their pages now read the URL — the mock subscribes readers and re-renders on navigation, the way a real navigation does. Coverage: `common/lib/navigation/__tests__/view-search.test.ts` pins the parse contract across ten hostile values, and the Cash Flow suite gains three cases — selection surviving a full unmount and remount of the page, the default with no param, and an unrecognised value falling back. The unmount case fails with page-local `useState` while m16's own "uncached read" case still passes, which is the evidence that this is a different boundary rather than a re-fix. The note's smaller item is done too: the trial-balance content harness takes an optional data override, so its fourteen-prop list is no longer duplicated. Left alone as the note directs: extending m16's coverage to the other three reports belongs to w4/m16/t005, and `reports/account/index.tsx`'s deliberate `previousData` fallback was read and not changed — it does differ from the statement pages' `selectSettledReportData` contract, and that asymmetry is still documented per page rather than reconciled. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 424 files, 4762 passed, 1 pre-existing skip — and `yarn build`). Shipped in `a0940b82` (`dashboard`).
