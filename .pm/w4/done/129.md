# Preserve selected files before resetting the upload input

Severity: minor. Estimate: 50m, dashboard. A2: selecting another local file should reliably extend the upload queue. Repeated production dashboard QA, 2026-09-18.

Environment: https://beancount.io, anonymous public open_ledger/freelancer-invoicing, English/light, isolated headless Chromium149.0.7827.55; fresh390×844 and1440×1000. Local HEAD26d54a9d, fetched origin/mainbd5d1d31, deployed main-BIr0jJni.js; exact deployed commit unverified.

Reproduce at `/ledger/open_ledger/freelancer-invoicing/files/upload/main/transactions`:

1. Choose your files → select a real local `qa-native-first.txt` containing `first local fixture` (19bytes). Selected files (1) and its row appear.
2. After rendering settles, choose a different `qa-native-second.txt` containing `second local fixture` (20bytes). Only the first row remains. Fresh desktop and narrow loads reproduce it.
3. Both selections deliver trusted native input/change events with their correct filenames and sizes. This also reproduces with actual disk paths through Playwright's file-chooser API, not just injected buffer payloads. Upload is never submitted.
4. Desktop removal of the first row followed by selecting that same file leaves the queue empty. A capture listener retains the FileList reference: before the handler it contains the selected filename; after the event/render settles that same reference is empty. Initial selection after reload is the working control.

Expected: each selection snapshots its File objects and appends them once to the staged queue; removal followed by same-file selection works without reload. Actual: subsequent choices silently disappear. Neither Save nor Upload was activated; no remote file was created. Authenticated writers and actual submission remain unverified; this is the shared form's local selection handler. Coordinate with128's separate permission gating without treating that gate as a fix for writer selection.

Root: `dashboard/src/features/ledger-editor/upload-files/index.tsx:152–160` captures `event.target.files`, reads `Array.from(files)` inside the functional state updater, then immediately clears `event.target.value`. The updater may consume the live FileList after reset has emptied it. The deployed handler has the same ordering. Copy the File objects synchronously before scheduling the updater, then append that immutable snapshot and preserve native-input reset. Do not remove the reset, remount the page, or replace the existing queue.

Blast radius: the shared UploadFilesPage serves root/nested canonical upload routes and the compatibility redirect. Drag/drop uses a separate event path and was not exercised. No API, dependency or server authorization change is needed.

Dedupe/history: all current/done/blocked board records and targeted history checked. Commit61854497 repaired historical w3/071's absent native change event on same-file reselection, but introduced this reset after a deferred FileList read. That older note explicitly called for copying File objects before resetting. Here trusted change events arrive and the UI still loses the selection: a regression, not deployment lag.128 concerns permissions; historical649c6eb3 concerns remove-button names. Neither owns this state-ordering defect.

Acceptance: real browser selection of first then different second file retains both rows at desktop/narrow sizes; remove/reselect retains exactly one intended row; selecting multiple files together and canceling a later chooser preserve the queue. Cover the deferred updater ordering rather than a mock that always evaluates it synchronously. Preserve removal, input reset and drag/drop behavior. Run dashboard format/lint/tests/build when implementing. Do not upload to production for verification.

Evidence under `dashboard/tmp/qa-20260917/`: `upload-native-selection-390.json`, `upload-native-selection-1440.json` contain the trusted event traces and rendered one-file lists; matching `.png` screenshots (narrow visually inspected); `upload-live-filelist-control.json` records the retained reference becoming empty and empty queue after remove/reselect. Synthetic disk fixtures are retained locally. No product changes, commits or pushes.

**Resolved 2026-09-19** — `handleFileSelect` now copies the `File` objects synchronously, then resets the input, then appends that snapshot. The reset stays, so the same path can still be chosen again; nothing was remounted and the queue shape is unchanged. Mechanism confirmed: React evaluates the _first_ functional update eagerly at dispatch time, which is why the first selection read the still-live FileList and stuck while every later one was deferred past `event.target.value = ""` and read the emptied list — exactly the reported pattern of the first row appearing and subsequent choices vanishing. Verification note: because w4/128 shipped first and now gates these routes, the anonymous repro path is closed, so write access was forced **locally and temporarily** in `use-ledger-permission.ts` to exercise the writer flow in the browser; that edit was reverted before committing and the hook is byte-identical to `main`. With the fix, real disk files selected through the native file chooser behave correctly at 1440×1000 and 390×844: choosing `qa-native-first.txt` then a different `qa-native-second.txt` leaves **Selected files (2)** with both rows; removing the first row and re-choosing that same file restores it to two; choosing both files together in one chooser stages both; and cancelling a later chooser leaves the queue at two. One honest discrepancy with the original report: in my pre-fix browser run the _first_ selection also failed to appear, rather than appearing and then being replaced. Both are the same defect — a deferred read of an emptied FileList — and the boundary depends on React's eager-update optimization; the unit evidence below pins the reported boundary exactly. `features/ledger-editor/upload-files/__tests__/upload-file-selection.test.tsx` adds five cases with a fake input that empties its own FileList the moment `value` is assigned, exactly as a browser does, so a handler that defers the read fails rather than passing against a mock that always evaluates synchronously. Two of the five fail on the old ordering — the second different choice and the remove-then-reselect case, precisely the reported symptoms — while the first-choice, multi-select and cancel cases pass either way and stand as controls. Not verified: authenticated writers against the live API, actual submission (nothing was uploaded), and drag/drop, which uses a separate event path and was left untouched. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 412 files, 4627 passed, 1 pre-existing skip — and `yarn build`). Shipped in `1bcf41c0` (`dashboard`).
