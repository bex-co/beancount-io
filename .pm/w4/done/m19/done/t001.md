## Objective

Repair the shared hook using actual TanStack location semantics; preserve path, query, fragment and safe redirect validation.

## Context

See [FINDINGS.md](./FINDINGS.md) for reproduction, source and evidence limits.

## Acceptance criteria

- [x] Public Star and Follow produce the original relative URL with a single fragment delimiter, with and without a query.

## Out of scope

Backend/API changes, authentication policy changes, new dependencies and unrelated login defects.

## Outcome

Confirmed the router semantics FINDINGS names, in the installed source rather
than by assumption: `@tanstack/router-core`'s `router.js` builds its own `href`
from the raw hash and only then exposes `hash: decodePath(hash.slice(1)).path`,
so the parsed field has lost its `#` while `searchStr` keeps its `?`. Gluing the
three parts together therefore appends the fragment to the query — or to the
path when there is no query.

Added `toRelativeLocation` beside `RequireAuthLocation` in
`common/lib/auth/auth.ts`, the type those producers already share, and used it
in `use-login-next-path.ts`. It inserts the delimiter only when a fragment is
present, so plain paths are unchanged. `getSafeRedirectPath` still does the
validating and the encoding — it already normalises through `new URL` and
returns `pathname + search + hash` — so the unsafe-next rejection from w3/170
is untouched.

Reproduced first on the built unfixed code, at 1440 and 390, signed out:

- Star on `/ledger/open_ledger/example?lang=en&time=2016#overview-recent-activity-heading`
  emitted `next=/ledger/open_ledger/example?lang=en&time=2016overview-recent-activity-heading`
  — the fragment swallowed into the time filter;
- Follow on `/ledger/open_ledger?lang=en#ledger-collection-heading` emitted
  `next=/ledger/open_ledger?lang=enledger-collection-heading`.

After the change, 12/12 live checks at both widths:

- query-plus-fragment and fragment-only continuations come back exactly as
  entered, with one `#`;
- replaying each emitted continuation loads the intended page, with none of the
  "Error loading data / invalid information" the malformed target produced;
- the plain-path control and a query-only destination are unchanged.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (377
files, 4253 passed, 1 pre-existing skip) and `yarn build` all pass.

The two guarded producers — `requireAuth` in `auth.ts` and the ledger route —
still build the string by hand; aligning them is t002.
