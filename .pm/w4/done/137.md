# Keep signup initialization from replacing an already typed username

Severity: minor. Estimate: 60m, dashboard. A2: a newcomer on a slow initial load should not have their chosen public username silently replaced when the form becomes interactive. Repeated dashboard QA, 2026-09-18.

No signup submission, email/password entry or account creation.

Root: `dashboard/src/features/auth/hooks/use-register-form.ts:38` creates a default username in a state initializer. `pages/register/register.tsx:67–72` supplies it to RegisterForm. `components/register-form/index.tsx:78–81` initializes react-hook-form with `defaultValues: { username: defaultUsername }`, while the visible input at161–173 has no server-rendered value or readiness gate. Installed react-hook-form7.71.0 `dist/index.esm.mjs:1535–1543,2132` applies that non-undefined default when the input ref registers; `setFieldValue` at1701–1742 assigns the DOM value. First Name lacks that default and therefore adopts the existing input value instead. This explains the same-node overwrite without a React hydration exception.

Fix the registration integration so initialization cannot replace text already accepted by the visible Username field. Preserve pre-hydration input when applying the generated default; if the form cannot safely adopt it, keep that field non-interactive until its initial value and handlers are ready rather than presenting an editable field whose value will be discarded. Retain the generated default for an untouched form and for hidden-username consent flows, and preserve later custom edits, validation, focus and error associations. Do not patch react-hook-form, remove SSR from the whole app, change username rules or alter backend signup behavior.

Blast radius: RegisterForm has the standalone registration page plus OAuth/mobile/identity consent consumers. Only the standalone SSR journey was reproduced. Hidden generated usernames remain required by the existing consent flow (w1/done/m6/done/t004); they must not become empty as a side effect of this repair. No backend, dependency or API surface change is needed.

**Resolved 2026-09-19** — The visible Username input now goes through a ref wrapper that reads the field before handing it to react-hook-form and restores anything already typed, updating the form state to match. The library is not patched, SSR is not removed, username rules and backend behavior are untouched, and the generated default still applies whenever the field is empty at registration — which is the untouched case, since the server renders it blank. The hidden-username consent flows bind the raw field and are unaffected. Reproducing this needed the production build: in the dev server the form arrives with a username already filled in, so the overwrite never appears, and an early dev-server probe of mine showed no difference between the fixed and unfixed code. Against `yarn build` output served locally, with the `/lgassets/main-*.js` entry script held, the note's conditions appear exactly — the Username field is served **blank**, enabled and writable. Without the fix, typing `qa_hydration_reader` and then releasing the script left the field reading `un_rp9vqhtrvh4g` at 390×844 and `un_sdvikmawnqjw` at 1440×1000, on the same DOM node, while First Name's `QA Reader` survived. With the fix, both widths keep `qa_hydration_reader` on that same node; editing afterwards to `qa_after_hydration` still works with no validation error; and a form nobody touches still hydrates to a generated `un_…` name. `__tests__/register-form-hydration.test.tsx` adds six cases that render the component's real server markup with `renderToString`, simulate the reader typing into it, then hydrate over that container with the real react-hook-form — not a mock asserting `defaultValues`. Three cover preservation (the value survives, it stays on the node that was typed into, and it is not the generated default) and three cover what must not change (an untouched field, an emptied field, and the hidden-username consent flow still getting the generated name). The three preservation cases fail when the wrapper is removed; the other three pass either way and stand as controls. Not verified: the actual signup and OTP flow, autofill and password managers, other engines, and the OAuth, mobile-consent and identity-consent consumers, of which only the standalone journey was exercised. No signup was submitted and no account created. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 420 files, 4738 passed, 1 pre-existing skip — and `yarn build`). Shipped in `126d90f6` (`dashboard`).
