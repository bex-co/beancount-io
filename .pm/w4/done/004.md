# Mobile shows $0.00 for every transfer between two cash/liability accounts

**Severity:** major. **Estimate:** 40–55 minutes. Owner: mobile. A2/A3: a newcomer's first native list is the transactions list, and the most ordinary entries in it — a credit-card payment, a bank-to-bank transfer — read as if no money moved.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA; no ledger mutation.

## Repro

1. Select `puncsky/example` from the ledger drawer and wait for Home to settle.
2. Home → Recent Transactions: `STRIPE; TRANSFER; TIAN PAN; …` reads **$0.00** and `AMEX EPAYMENT; ACH PMT; TI…` reads **$0.00**. `Anthropic` in the same card reads `$102.00`.
3. Tap the Stripe row. Transaction detail's hero amount is **$0.00**, while its own Money flow rows below read `TO Assets:Bank:…ury:Checking +$6,931.48` and `FROM Liabilities:…:Chase:Slate -$6,931.48`.
4. Tab bar → Transactions. Both rows show **$0.00** again (September 1 and August 31, 2026), next to working controls `Cafe Modagor $34.71`, `Hoogle +$2,550.60`, `Farmer Fresh $86.31`.
5. Terminate and relaunch the app. All three zeros reproduce.

**Expected:** a transfer shows the amount that moved — `$6,931.48` — in the list row and in the detail hero.
**Actual:** `$0.00` everywhere the headline amount is derived, while the postings on the very same screen show ±6,931.48.

## Root cause

`mobile/src/screens/transactions-screen/utils/transaction-display-utils.ts:86` `selectTransactionAmount` buckets every `Assets:`/`Liabilities:` posting by currency and **sums within the bucket** (lines 100–113), then formats that sum. Its doc comment (lines 69–82) states the intent — "netting Assets/Liabilities postings answers 'what moved in or out'" — and the degenerate case is unhandled: when both legs of the transaction are cash/liability accounts in the same currency, the bucket sums to exactly `0` and the transaction is rendered `$0.00`. A single-cash-leg entry (expense, income) nets to the leg itself, which is why `Anthropic` and `Hoogle` are correct.

**The netting computes the right quantity for the wrong question.** Verified against source: over the last six months this ledger's only net-worth-affecting activity is the `-102.00 USD` Anthropic expense — the AMEX and Stripe transfers each net to exactly zero — and Home's 6M change reads `-$102.00 (-0.10%)`, which is correct. So "net effect on net worth" is a real, useful quantity, and the selector calculates it faithfully. But a **transaction row** is not a net-worth delta; it answers "how much moved", and for a transfer that is `$6,931.48`, not nothing. The fix is to stop conflating the two in a per-transaction amount, not to change the netting wherever a net-worth delta is genuinely wanted.

The detail hero adds nothing: `transaction-detail-screen.tsx:402` calls `selectHeroAmount` → `select-transaction-detail.ts:34` → the same selector; `hero.isPositive` is `null` at value `0`, so no sign is applied either.

## Blast radius

All five `selectTransactionAmount` consumers show the zero:

- `home-screen/components/recent-transactions-card.tsx:80` (via `EntryRow`) — reproduced
- `transactions-screen/transactions-screen.tsx:238` — reproduced
- `transaction-detail-screen/selectors/select-transaction-detail.ts:35` — reproduced
- `reports-screen/components/account-transactions-card.tsx:118` — not independently reproduced
- `merchant-detail-screen/merchant-detail-screen.tsx:575` — not independently reproduced

`account-detail-screen/components/account-entry-row.tsx` uses a different, per-account amount and is correct — the account journal shows the real signed delta for the same entries, which proves the API data is intact and the loss is in this selector.

## Fix

In `selectTransactionAmount`, when the picked bucket's net is zero **and** the bucket holds more than one posting, fall back to the transfer's magnitude instead of its net: use the largest absolute leg in that bucket (equivalently, half the sum of absolute leg values for a two-leg transfer). Keep the existing behavior for every other shape — single cash leg, cross-currency bucketing by `moneyCurrencyOf`, the non-cash fallback at lines 135–153, and the recorded decimal scale from `amountScale`. Decide and document the sign: a transfer has no in/out direction at the transaction level, so `value` should stay `0`-signed (unsigned display, no `+`/`-`), matching how the list already renders sign-neutral rows. Do not change `formatAmount`, and do not special-case account-name prefixes beyond the `Assets:`/`Liabilities:` test already there. No backend, API, or cross-package change is needed.

**Acceptance:** on a fresh iPhone 17e launch with `puncsky/example` selected, the Stripe and AMEX rows read `$6,931.48` and their real amount respectively in Home, Transactions, and the detail hero; `Anthropic`, `Hoogle`, `Cafe Modagor` keep their current values and signs. Add regression coverage in `mobile/src/screens/transactions-screen/utils/` for: a two-leg same-currency Assets↔Liabilities transfer, an Assets↔Assets transfer, a single-cash-leg expense and income (unchanged), a cross-currency trade (unchanged bucket pick), and a genuinely zero-amount entry with one cash posting (still `$0.00`).

**Resolved 2026-09-14** — fixed in `mobile` by `fix(mobile): show how much moved in a transfer between cash accounts`. Triage confirmed the root cause at HEAD before the fix: `selectTransactionAmount` summed every same-currency `Assets:`/`Liabilities:` posting, so a two-leg transfer between cash or liability accounts netted to exactly zero and rendered `$0.00`. The note was not stale.

`mobile/src/screens/transactions-screen/utils/transaction-display-utils.ts` now tracks each currency bucket's leg count and largest leg. When a bucket with more than one posting nets to zero at its recorded precision, the entry reports the largest leg's size (`$6,931.48` for the Stripe transfer) with `value` 0. A transfer has no in/out direction at the transaction level, so it renders unsigned in the list row and the detail hero. Single-cash-leg expenses and income, the cross-currency bucket pick, the non-cash fallback, and the recorded decimal scale are unchanged, and a genuinely zero single-cash entry still reads `$0.00`. Only two callers read the result — the transaction detail hero and `EntryRow`, which Home, Transactions, Reports, and Merchants all render — and neither sums `value`, so no other surface changes. A device re-check on iPhone was not repeated in this run; the behavior is covered at the selector level.

Regression tests in `mobile/src/screens/transactions-screen/utils/__tests__/transaction-display-utils.test.ts`: an Assets↔Liabilities transfer, an Assets↔Assets transfer, a high-precision BTC transfer keeping its scale, and a genuinely zero single-cash entry. The existing expense, income, multi-posting, and cross-currency cases still pass.
