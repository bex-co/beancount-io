# Restore visible sidebar-button keyboard focus in forced colors

Severity: **minor**. Package: **dashboard**. Estimate: **35–50m**. Source:
continuous dashboard QA. **A2**: keyboard users must be able to see when the
navigation toggle is focused before opening or collapsing the sidebar.

Production `https://beancount.io`, public synthetic `open_ledger/real-estate-example`,
owned headless Chromium149.0.7827.55, English/light. Browser forced-colors
emulation, not a physical Windows session. Initial local main `bd2dab98`;
fetched main `76424c58` leaves the relevant Button, Sidebar and stylesheet
unchanged. Exact served revision unverified. No ledger writes.

1. Open `/ledger/open_ledger/real-estate-example/files/tree/main/transactions`
   at390×1000 with forced-colors active. Move the pointer away from controls.
2. Press Tab until Toggle Sidebar is focused (two native Tab presses in this
   layout). Both `activeElement` and `:focus-visible` confirm the real button.
3. There is no visible change: surrounding crops with8px padding before and
   after focus are byte-identical PNGs. The focused button has
   `outline-style:none`, zero-width border and `box-shadow:none`; its icon,
   foreground, transparent background and opacity are unchanged.
4. Fresh1440×1000 repeats the same result after18 native Tabs. Independent
   fresh repeats at both widths again produce byte-identical crops.
5. With forced colors disabled, the same native keyboard sequence produces a
   visible3px green ring and different before/after screenshots at both widths.
   These images were visually inspected alongside the forced-colors images.
6. Activation works: Enter on desktop collapses the sidebar (`aria-expanded`
   true→false). Narrow Enter opens the named Sidebar dialog; Escape closes it
   and returns focus to the toggle. The defect is invisible keyboard focus,
   not a disabled control or broken focus restoration.

Cause: `dashboard/src/common/components/ui/sidebar.tsx:388–396` uses the shared
Button's ghost variant. `common/components/ui/button.tsx:8` removes outlines
with `outline-none` and supplies its focus indicator through a ring shadow.
Forced colors removes that shadow, and changing a zero-width border's color
cannot draw an indicator. The base-layer `:focus-visible` outline in
`src/style.css:202` still supplies width/color/offset, but the Button utility
keeps the computed outline style `none`. Its promised baseline therefore does
not protect this consumer.

Give the shared Button an explicit forced-colors focus outline using system
colors, as the existing Tabs focus treatment already does. Scope it to
keyboard focus in that media mode; preserve ordinary light/dark styling,
button variants, pressed indicators, dimensions, disabled states, accessible
names and activation. Other shared Button consumers are source-derived repair
scope, not separately reproduced defects. Do not change API behavior or add a
new focus abstraction/dependency.

Acceptance: native Tab gives Toggle Sidebar a visible indicator at390/1440 in
forced colors, independent of pointer hover. Preserve the working Enter/Escape
behavior and ordinary ring. Include meaningful shared-Button coverage of the
emitted forced-colors outline and check its ghost/outline/default variants;
verify actual browser pixels/focus, not only a class name. Run dashboard gates
when implementing.

Dedupe: done `w4/131` repairs Tabs focus and selection; done `w4/133` repairs
Journal filter selection with local styles. Neither repairs this shared Button
consumer. Done `w4/130` reveals Markdown Copy buttons on focus, a different
opacity issue. No matching open/done/blocked sidebar forced-colors focus repair
was found. Initial directory-toolbar samples at desktop landed on the Clone
control, so those unfocused samples are excluded from the proof above.

Ignored evidence under `dashboard/tmp/qa-20261008-loop/`:
`sidebar-trigger-forced-colors-focus-repro-result.json` records the four
forced/ordinary native-focus comparisons;
`sidebar-trigger-forced-colors-focus-repeat-result.json` records independent
forced-colors repeats and activation. `sidebar-focus-<width>-<mode>-before.png`
and `-after.png` include surrounding focus-ring space; repeat screenshots use
`sidebar-focus-repeat-`. Forced before/after bytes are identical at both widths;
ordinary focused screenshots visibly show the ring.

Ordinary rings, variants and behavior retain their existing rules. Fresh local before-fix native Tab checks at 390/1440 pixels reproduced identical forced-color focus/unfocused crops, outline style none and no shadow. Eight final browser contexts (both widths, light/dark, forced/ordinary) expose real keyboard focus: forced colors paints a black or white solid outline with distinct focus pixels; ordinary mode retains its three-pixel ring, and the toggle stays 28 by 28 pixels. Forced light/narrow and dark/desktop crops were visually inspected. Desktop Enter collapses/reopens the sidebar; narrow Enter opens the Sidebar dialog and Escape closes it with focus returned to the toggle. Additional actual default Git Clone and outline Version History consumers show the same native forced-color outline and changed focus pixels; Clone Enter/Escape retains popup and focus behavior. Removing only the four forced-color classes fails four style regressions while 11 controls pass; byte-exact restoration passes all 15 focused tests. Checks use Chromium forced-colors emulation, local synthetic reader authentication and read-only public-ledger responses; a physical Windows session, production deployment and additional reproduced consumer defects are not claimed.
