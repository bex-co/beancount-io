# Every date picker is pinned to `en_US`, so a German or Chinese user gets English month names inside an otherwise fully translated app

**Severity:** minor. **Estimate:** 15–25 minutes. Owner: mobile. A3: the app is fully translated into 13 languages — the work to localize it has already been done and paid for. The date picker is the one control that opts out, and it opts out of more than its comment claims.

> **Premise corrected, September 14.** This note originally opened *"the app detects the device language and comes up translated **on first launch**"*, taken from the source. On iOS it does not: the bundle declares no `CFBundleLocalizations`, so `Localization.getLocales()` can only ever report `en` and a fresh install is English whatever the device is set to. That is filed as **`w4/063`**, proven with a three-arm experiment (no persisted locale → English; `locale="zh"` → fully Chinese). Nothing else here changes — the `en_US` pin is real and the fix is the same — but **`w4/063` should land first**, because until it does no user reaches a non-English locale and this defect cannot bite anyone. Afterwards it bites everyone who is not American.

Environment: branch `main`, HEAD `038faeeb`; source trace at that commit. The app's own locale could not be changed on device — see "Why this is not verified on screen".

## The pin

`src/components/date-picker-modal/date-picker-modal.tsx:60-61`:

```tsx
<RNDateTimePickerModal
  locale="en_US"
  ...
```

with this rationale, twelve lines above:

> *"`locale="en_US"` pins the spinner columns to Month → Day → Year. Without a locale the native iOS picker follows the device region and can flip to Day → Month → Year. (Stored dates are ISO `YYYY-MM-DD`, so this is purely the wheel column order.)"*

The parenthetical is where it goes wrong. The prop is forwarded to `UIDatePicker`, whose locale governs **column order and the localized month names together** — they are not separable. Pinning `en_US` therefore also forces `January … December`, in an app that ships **13 languages**.

All three callers use `mode="date"` with no `display` override — `multi-postings-transaction-screen.tsx:642-644` (transaction date), `add-budget-screen.tsx:333-335` (budget start date), `open-account-screen.tsx:431-433` (account open date) — and both iOS presentations for that mode show month names: the spinner as a column, the inline calendar in its header. So all three are affected.

The second half of the rationale is also worth questioning on its own terms: for a German or Spanish user, **Day → Month → Year is the correct order**, not a flaw to be pinned away. The comment treats the American order as the right answer rather than as one locale's answer.

**The board has already decided that question, in the other direction, for the other package.** The open **`w3/m42`** — *"Accept dates in the user's own date order"*, rated **major** — exists because *"Every date text input in the app displays and parses US month-first order only, in all 15 languages… A French user typing `12/09/2026` for 9 December gets a silently accepted 12 September."* That milestone is scoped **dashboard** and concerns typed text that a parser must disambiguate, so it is not this defect. But it settles the principle: pinning US date order on a localized surface is something this project treats as a bug, not a convenience.

Mobile's picker is the gentler case — a wheel cannot be misread the way `12/09/2026` can, because the month is spelled out — which is exactly why the **month names** matter more here than the column order does.

## Why this is guaranteed, not hypothetical

The app resolves the device language at startup and uses it when the user has never chosen one. `src/translations/index.ts:42-53` walks `Localization.getLocales()` for the first supported `languageCode`, and `splash-provider.tsx:86-93` applies the persisted choice only when there is one, with the reasoning spelled out:

> *"`loadLocale()` returns null when nothing is persisted, in which case `i18n.locale` already holds the device-derived choice from `src/translations/index.ts` — so a Persian device flips on its very first launch, not only after the user visits Settings."*

That is good behaviour and it is what makes this a real mismatch: a German user installs the app, sees German everywhere, opens New Transaction, taps the date, and reads `September`.

## Fix

Feed the picker the app's locale instead of a constant:

```tsx
const locale = useReactiveVar(localeVar);
...
<RNDateTimePickerModal locale={locale} ... />
```

`DatePickerModal` already calls `useTheme()` and already spreads `{...props}` after its defaults, so a caller can still override — the shape does not change. `localeVar` holds a bare language code (`de`, `zh`), which `UIDatePicker` accepts; pass a region-qualified tag only if a specific column order is wanted for a given language, and if so say which and why.

**Rewrite the comment in the same edit.** Whoever fixes this should not have to re-derive that the prop does two things; the current text would talk them out of the change. If pinning the column order is genuinely wanted, that is a product decision that needs stating as one — and it cannot be had without also pinning the month names, which is the trade the comment currently hides.

**Acceptance:** with the app language set to Deutsch, the transaction date picker shows German month names; with 中文, Chinese ones; with English, the picker is unchanged from today; the budget and open-account pickers follow; and the dark-mode card/cancel-button theming this component exists to provide still applies. Add a test that `DatePickerModal` passes the current `localeVar` through — there is no test over this component today.

## Now verified on screen — and the component leaks English in **two** ways, not one

September 14, HEAD `038faeeb`, iPhone 17e / iOS 26.5, app locale forced to `zh` by the method below, `open_ledger/alphabet`. Transactions → filter → **自定义** (Custom) → **开始**:

The sheet around it is fully Chinese — `筛选`, `状态`, `日期范围`, `开始` / `结束`, `账户` — and inside the picker:

```
April   May   June   July   [ August  14  2026 ]   September   October   November
                          Confirm
```

1. **The month names are English**, exactly as this note predicted from source. Confirmed, not inferred.
2. **So is the button.** It reads **`Confirm`**, not `确认`. That is a *second* untranslated surface on the same component, and it has a different cause: `react-native-modal-datetime-picker` renders its own English defaults unless given `confirmTextIOS` / `cancelTextIOS`, and `grep -rn 'confirmTextIOS\|cancelTextIOS' src/` returns **nothing** — `DatePickerModal` does not set them and none of its three call sites (`transaction-filters-screen.tsx:367`, `add-transaction-next-screen.tsx:348`, `add-budget-screen.tsx:332`) passes them either.

**The app localizes month names correctly everywhere else**, which rules out a missing capability and leaves the `en_US` pin as the whole cause (September 14, German): the Transactions date header renders `30. Juni 2026` and the Reports month axis renders `JAN FEB MÄR APR MAI JUN`. Only `UIDatePicker` shows English months. Recorded in `w4/065`'s adjacent states.

So fix both in `date-picker-modal.tsx` in one edit: pass `locale` from `localeVar` **and** `confirmTextIOS={t("confirm")}` / `cancelTextIOS={t("cancel")}`. Both keys already exist and are translated in all 13 locales. Extend the acceptance criterion accordingly: with 中文, the picker shows Chinese month names **and** a Chinese confirm button.

Note the contrast that makes this look like an oversight rather than a decision: the app's *other* wheel, the in-house `Picker`, is passed translated button text by every one of its callers (`open-account-screen.tsx:417-418`, `add-budget-screen.tsx:363-364`, `setting/main-content.tsx:266-267`). Its own defaults are the hardcoded `confirmButtonText = "Done"` / `cancelButtonText = "Cancel"` (`components/picker/index.tsx:175-176`), which are latent today because no caller omits them — worth replacing with translated defaults while in the area, but not a live defect.

## Why this was not verified on screen (superseded above)

I could not change the app's language on the device, and the reason is itself already on the board: the language picker is the wheel from **`w4/009`**, whose options cannot be tapped, and the pinned Expo MCP has no scroll or drag tool (**`w4/020`**), so the wheel cannot be moved to reach `Deutsch`. The list is alphabetical-by-native-name with English first, so every other locale is below the fold.

I considered changing the **simulator's** language instead and decided against it after checking: `localeVar` is a *persisted* var (`vars/locale.ts`) and this device has `en` stored from earlier in the run, so `splash-provider` would apply the persisted value and the device change would do nothing — while still leaving a modified simulator to restore. The claim above therefore rests on the source and on documented `UIDatePicker` behaviour, not on a capture.

**That reasoning was right, and there is now a way through it** (September 14). Changing the simulator language was tried and, exactly as predicted, did nothing — the persisted `"en"` won. The route that works is to set the persisted value directly, which needs no scrolling and no device language change at all:

```
xcrun simctl terminate <udid> io.beancount.ios
# .../Library/Application Support/io.beancount.ios/RCTAsyncLocalStorage_V1/manifest.json
# back the file up, then set:  "locale": "\"zh\""
xcrun simctl launch <udid> io.beancount.ios
```

Verified to work: the app came up fully in Chinese (首页 / 净资产 / 最近交易, range pills 近1月…全部), and the repro **was** then captured — see the section above. It is a local preference edit, fully reversible by restoring the backup, and touches no ledger. Evidence and the full method are in **`w4/063`**.

Evidence for the on-screen verification, under gitignored `mobile/tmp/qa-2026-09-14/`: `w4l126-08-filters-zh.jpg` (the Chinese filter sheet), `w4l126-09-custom.jpg` (自定义 selected, 开始/结束 rows) and `w4l126-10-datepicker.jpg` (**the picker: English months and an English `Confirm` inside a Chinese sheet**).

## Blast radius

One prop in one wrapper, reaching all three date pickers. No change to stored values: dates round-trip as ISO `YYYY-MM-DD` through `getFormatDate` / `parseFormatDate` regardless of picker locale, so this is presentation only and cannot alter what is written to a ledger.

Not exercised: any non-English locale on device (blocked above), Android's picker (which localizes through a different mechanism), and RTL locales, where the column order question interacts with layout direction and deserves its own look.

## Adjacent states

The date handling around this is **correct and carefully reasoned**, which is worth recording since off-by-one date bugs are the norm in this area:

- `format-util.ts:1-17` uses local-time getters for `getFormatDate` and appends `T00:00:00` in `parseFormatDate`, with a comment naming the exact trap — *"`new Date("YYYY-MM-DD")` is UTC midnight and shifts the calendar day west of Greenwich"*. The transaction screen uses `parseFormatDate(date)` when seeding the picker, so the round-trip lands on the day the ledger names.
- `DatePickerModal` exists to fix a real theming defect (the library paints its cancel button `#0E0E0E` in dark mode, invisible against the app's charcoal page) and drives dark mode from `themeVar` rather than the OS, so an in-app theme override cannot desync the picker.
- Its themed cancel button carries `accessibilityRole` and `accessibilityLabel`.
