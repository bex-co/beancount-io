## Cause and bounded remediation

The client Google tag's automatic Site Search detection processes the real URL's query parameter independently of the app's sanitized dispatcher. No dashboard source manually emits view_search_results/search_term. The current bootstrap in `common/analytics/google-analytics.tsx` disables automatic page_view and provides origin-only location/referrer; `track.ts:57–69` and analytics-provider.tsx correctly publish route patterns. Those measures are present and working, but do not stop this other automatic event.

Google documents that automatic Site Search reads URL parameters including query and sends search_term, and that individual enhanced-measurement options are configured in the stream/tag settings. Editing those settings requires an Editor or higher property role. [Google Enhanced Measurement documentation](https://support.google.com/analytics/answer/9216061?hl=en). The effective detector is observed here; its administrator UI and exact connected-tag configuration were not inspected.

Disable automatic Site Search for the production stream/connected Google tag that emits these events, and check every other enabled environment stream. If automatic public-search measurement is deliberately retained, its supported detection configuration must exclude BQL's query parameter and any financial-input parameter; raw BQL must never be used as a search term. Also enforce the already documented requirement to disable automatic browser-history page views, so only the app's sanitized page_view events remain. Google's linked documentation describes that history-based option separately from the default initial page view. Preserve the app's intentional bare BQL count and sanitized page/route metrics. Keep the existing bookmark/query URL contract and origin-only auth/referrer protection.

Update `dashboard/docs/event-taxonomy.md`'s per-stream setup checklist and the GoogleAnalytics bootstrap guidance to cover automatic Site Search, rather than only Enhanced Measurement page views. Verification must observe the real tag's generated collector payload with harmless markers blocked locally. The existing jsdom dataLayer tests can stay green while the external tag emits the raw term, so a passing stub-only test does not close this issue. Do not add undocumented gtag options, filter only the app's custom-event wrapper, or assert that changing page_location repairs search_term.

**External completion dependency:** a maintainer with authorized Editor-or-higher access to the affected GA4 property/Google tag must change and verify the effective setting. Repo guidance/check work can proceed first; closure requires that actual stream-level outcome. No GA4 settings or analytics account data were accessed or changed during QA.

Acceptance: fresh guest/public and owner/synthetic-private bookmarked BQL loads and reloads emit no query text in search_term or any other collector field. Wait for the tag to be ready, execute through the actual UI and observe delayed collector requests as well: no page_location may include the resulting query URL. Private Files tree→blob navigation emits no raw ledger/file location and no duplicate automatic page view; actual UI execution still produces the intended bare engagement metric and sanitized page/route telemetry. Repeat after effective settings settle, record the applicable environment/stream without publishing identifiers, and preserve existing reset/callback protections. No backend/API or new dependency is required.
