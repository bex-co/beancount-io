# Warn before discarding a New Transaction draft, like every other editor already does

**Severity:** minor. **Estimate:** 25–35 minutes. Owner: mobile. A2: entering a transaction is the app's primary write flow for a newcomer, and it is the one editor where a stray Back throws the work away without asking.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA — **nothing was saved**: Done was never pressed, the file edit was dismissed with Discard, and Home is unchanged.

## Repro

1. Terminate and relaunch with `puncsky/example` selected. Header **+** (Quick Add) → **Enter new transaction**.
2. Tap the first posting's amount and type `4321`. The draft is now dirty **and valid**: `Assets:Ban…ry:Checking + 4321`, auto counter-posting `Expenses…:Internet − 4321.00`, `Remainder ✓ $0.00`, and **Done is enabled**.
3. Tap **Back**.
4. The screen closes straight to Home. **No prompt.** The draft is gone; Recent Transactions is unchanged (`STRIPE…`, `Anthropic $102.00`, `AMEX EPAYMENT…`), so nothing was written either.

**Working control, same session, same device:** Files → `README.md` → tap into the body → type a **single character** → Back. An alert appears: **"Unsaved Changes / Discard your changes?"** with **Cancel** and a destructive **Discard**. Cancel returns to the editor with the edit intact; Discard leaves the file untouched.

**Expected:** abandoning a dirty transaction draft asks first, the same way abandoning a dirty file or a dirty transaction *edit* does.
**Actual:** a complete draft — date, payee, narration and any number of postings — is destroyed by one Back tap, with no confirmation and no undo.

## Root cause

The guard simply isn't wired on this screen. Two sibling screens already have it, with identical shape and shared strings:

- `mobile/src/screens/ledger-file-editor-screen/index.tsx:467-487` — `navigation.addListener("beforeRemove", …)`, `e.preventDefault()`, `Alert.alert(t("ledgerEditorUnsavedTitle"), t("ledgerEditorUnsavedMessage"), [cancel, destructive discard → navigation.dispatch(e.data.action)])`.
- `mobile/src/screens/edit-transaction-screen/edit-transaction-screen.tsx:319-336` — the same listener, plus a `savedOutRef` check so a successful save's own navigation is not mistaken for a discard.

`mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx` — the screen behind `/add-transaction` (`app/(app)/add-transaction.tsx` renders `MultiPostingsTransactionScreen` inside `LedgerWriteGuard`) — has no `beforeRemove` listener and no dirty-state tracking at all. So editing an existing transaction is protected and creating a new one is not.

## Fix

Add the same `beforeRemove` guard to `MultiPostingsTransactionScreen`, reusing `ledgerEditorUnsavedTitle` / `ledgerEditorUnsavedMessage` / `ledgerEditorDiscardChanges` rather than adding new strings — they are already translated and already describe this exact decision.

Dirtiness must be judged against the screen's **initial** state, not against emptiness: the form opens pre-seeded with a date, two suggested accounts and zero amounts (and `createPrefilledPostings` can seed more from a route prefill or the receipt handoff). An untouched draft must close silently, or the guard becomes an alert on every cancelled tap. Follow `edit-transaction-screen`'s `savedOutRef` pattern so a successful Done — which navigates back itself — does not raise the prompt.

Do not solve this by blocking Back, and do not auto-save the draft: the ledger is production data and a silent write is worse than a lost draft.

**Acceptance:** on a fresh iPhone 17e launch, a New Transaction draft with a typed amount prompts "Unsaved Changes / Discard your changes?" on Back; Cancel returns with the amount, payee, narration and postings intact; Discard closes without writing. An untouched draft closes with no prompt. A successful Done still closes silently and creates exactly one transaction. Add regression coverage for: untouched draft (no prompt), amount-only dirty, payee/narration-only dirty, added/removed posting, and the post-save path (no prompt).

## Blast radius

One screen and its two entry points — Home → Quick Add → Enter new transaction (reproduced), and the Transactions tab's **+**, which routes to the same `/add-transaction`. The receipt handoff also lands on this screen with prefilled postings, which is exactly why the dirty check must compare against the seeded state; that path was not exercised (the simulator has no camera). `/add-transaction-legacy` and `/add-transaction-next` are separate implementations and were not tested. Not exercised: Android, the hardware/edge-swipe back gesture (`expo-mcp` has no swipe tool — a swipe-back would hit the same `beforeRemove` listener, but that is unverified), VoiceOver, and enlarged Dynamic Type.

## Adjacent states

The rest of the flow is sound and should not change: `LedgerWriteGuard` correctly gates the route, Done is disabled while `validatePostings` fails and its handler refuses to write anyway (`multi-postings-transaction-screen.tsx:464-474`), the auto counter-posting and remainder update live, and the file editor's Save is correctly disabled until dirty. Note this finding is about the **discard prompt only** — the draft's amount arithmetic is a separate, already-open problem tracked by `w3/m34`.

---

**Resolved 2026-09-14** — fixed in `mobile` by `fix(mobile): ask before discarding a New Transaction draft`. Triage confirmed the gap at HEAD before the fix: `multi-postings-transaction-screen.tsx` had no `beforeRemove` listener and no dirty tracking, while the file editor and Edit Transaction both asked. The note was not stale.

`mobile/src/screens/multi-postings-transaction/draft-dirty.ts` compares the draft's date, payee, narration, and each posting's account and amount with how the form opened. That snapshot follows the seeding effect, so an untouched draft — including an untouched receipt-prefilled one — closes without asking. The screen registers the same `beforeRemove` guard as Edit Transaction and reuses `ledgerEditorUnsavedTitle`, `ledgerEditorUnsavedMessage`, and `ledgerEditorDiscardChanges`: Cancel keeps the draft, Discard leaves without writing. Save now passes `goBackOnSuccess: false`, marks the draft saved, and calls `router.back()` itself. Otherwise `runLedgerWrite` navigates away inside the write, before any flag could be set, so a successful Done would raise the prompt. Nothing is auto-saved and Back is never blocked.

Regression tests in `mobile/src/screens/multi-postings-transaction/__tests__/draft-dirty.test.ts` cover an untouched draft and edits to the amount, payee, narration, and date. They also cover added, removed, and re-accounted postings. A source guardrail checks that the listener is gated by the saved flag and the dirty check, and that the flag is set before `router.back()`. The dirty-check cases fail when the helper always returns false, and the guardrail tests fail with the screen changes reverted. The unit runner cannot render the screen or perform a back gesture, so the alert and the swipe-back path were not exercised, and no device re-check was done in this run.
