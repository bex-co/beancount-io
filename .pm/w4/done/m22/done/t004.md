## Outcome

The milestone's whole implementation is one file — 45 lines in
`common/components/monaco-editor/index.tsx` — so this ran as a direct review
rather than a four-way agent fan-out, which would have been disproportionate.
Recorded here rather than implied.

Against this task's own criteria, the shape was already right: **one policy in
one place**, not repeated DOM mutations or a new wrapper. All five consumers
already routed through this component, so nothing needed a per-call-site patch,
and no writer gate, draft lifetime or browser API was touched — the repair is
one ARIA attribute plus one defaulted Monaco option.

Two real improvements applied:

- **The options object was rebuilt on every render.** `withDomReadOnly` returns
  a new object whenever a consumer sets `readOnly`, and `@monaco-editor/react`
  re-applies options when that prop's identity changes — so every parent render
  pushed a fresh options object into the editor. It is now memoized on the
  caller's own options.
- **The re-apply was gated too narrowly.** It only listened for the `readOnly`
  option changing, which misses Monaco rebuilding its input surface for any
  other reason. It now re-applies on any configuration change; `apply` is a
  `querySelector` plus a `setAttribute`, so the broader trigger costs nothing
  and removes the `hasChanged` branch along with it.

Comment prose came down from 24 lines to 14 — enough to explain the
non-obvious Monaco internals (which surface gets which attribute, and why
`domReadOnly` matters) without restating the finding.

Kept: `Parameters<OnMount>[0]`/`[1]` for the editor and monaco types. It is
slightly indirect, but it avoids a type-only import of the full monaco-editor
package into a component that otherwise has none.

Verified unchanged after the refactor: 20/20 read-only state checks and 9/9
reader-affordance checks, identical to before.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (383
files, 4319 passed, 1 pre-existing skip) and `yarn build` all pass.
