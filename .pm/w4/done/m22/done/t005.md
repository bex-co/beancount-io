## Objective

Verify real Monaco native accessibility state and meaningful permission/mode regressions, then dashboard gates.

See [FINDINGS.md](./FINDINGS.md) for evidence, source and limits.

## Acceptance criteria

- [x] Cover native EditContext and textarea fallback, reader/writer transitions, Entry Context and source-derived previews.
- [x] A mock that merely echoes options is insufficient; retain key-rejection, Find, line navigation and draft/selection controls.

## Outcome

Coverage lands in two places, because the acceptance needs both and neither
alone is sufficient.

**Real Monaco, in a browser (the accessibility proof).** 20 state checks and 9
affordance checks over CDP against a production build, covering both public
reader journeys — file source and journal Entry Context — in **both supported
input modes** at 1440x1000 and 390x844:

- native AX `readonly=true` everywhere it should be, where the EditContext
  surface previously reported `false`;
- the textarea fallback reached by deleting `window.EditContext` in a
  separately labelled diagnostic context, never in product code;
- **key rejection** proved by comparing the *complete* Monaco model before and
  after a typed `x` — 318,015 characters byte-identical. Rendered-text
  comparison is worthless here because focusing changes the virtualized
  viewport, and my first attempt fell into exactly that trap and reported a
  phantom edit;
- **Find** (`2017-09-07` → "1 of 1"), **Escape** returning focus to
  `Editor content`, **selection** of the whole model, **line navigation** to
  `main.bean:595` and **Back** retaining `offset=60`;
- the **editable control**: the public BQL editor still reports
  `readonly=false` and accepts a typed character.

**12 committed cases (`monaco-editor.test.tsx`)** pin the integration logic
that browser run exercises. FINDINGS rules out "a mock that merely echoes
options", so the double here is not an echo: it builds the DOM Monaco builds —
a `.native-edit-context` div or a `textarea.inputarea`, already carrying
Monaco's own `role="textbox"` and `aria-multiline` and pointedly *not*
`aria-readonly` — and implements the option lookup and the
configuration/dispose events. The cases cover both surfaces read-only and
editable, a **reader→writer→reader transition** through configuration changes,
listener disposal, Monaco's own attributes being left intact, the four
`domReadOnly` policy branches (defaulted true, defaulted false, an explicit
override respected, and an editor that never mentions `readOnly` left alone),
and the consumer's own `onMount` still running.

Both halves proved load-bearing by removal: dropping the `aria-readonly` sync
fails 7 cases, dropping the `domReadOnly` default fails 2, and restoring them
passes 12/12.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (384
files, 4331 passed, 1 pre-existing skip) and `yarn build` all pass. `gitleaks`
reports no leaks in `dashboard/src`.

Recorded honestly: the committed cases verify **this integration's** logic, not
Monaco itself — Monaco needs real layout and cannot run in JSDOM, and no
browser-test harness exists in `dashboard/` to commit one into without adding
the dependency this milestone rules out. The accessibility claim rests on the
browser runs above. The two account-deletion previews are covered by the shared
`domReadOnly` policy and its tests rather than by a production reproduction,
since they sit behind a writer-only dialog.
