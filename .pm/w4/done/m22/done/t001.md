## Objective

Use supported Monaco options/integration so a read-only editor exposes native readonly=true in both native EditContext and textarea modes. Preserve editable defaults and explicit caller behavior.

See [FINDINGS.md](./FINDINGS.md) for evidence, source and limits.

## Acceptance criteria

- [x] Real source-viewer AX state agrees with rejected keypress behavior; no global window.EditContext deletion or static contradictory label.
- [x] Preserve persistent models, drafts, selection, Find and source positioning.

## Outcome

Confirmed the cause in the installed Monaco 0.55.1 rather than inferring it.
`editContext/native/screenReaderSupport.js` gives the native input surface
`role="textbox"`, `aria-required`, `aria-multiline`, `aria-autocomplete`,
`aria-roledescription` and `aria-label` — and never `aria-readonly`. The
textarea path (`textAreaEditContext.js`) sets a native `readonly` only when
`domReadOnly` **and** `readOnly` are both true. So the same read-only viewer
reports two different states depending on which input surface the browser
supports.

Reproduced over CDP on the anonymous `example/main.bean` viewer, at 1440x1000
and 390x844, in both supported modes:

| Mode | Before | After |
| --- | --- | --- |
| native EditContext | AX `readonly=false`, no `aria-readonly` | **`readonly=true`** |
| textarea fallback | AX `readonly=true` (already correct) | `readonly=true` |

The fix lives in the shared `common/components/monaco-editor/index.tsx`, which
all five Monaco consumers already route through. On mount it sets
`aria-readonly` on whichever input surface exists, and re-applies it when the
`readOnly` option changes, so a view-mode switch under the reader stays
correct. It disables nothing, removes no browser API, adds no dependency, and
does not touch the permission checks that actually reject the keystroke.

Controls, all passing — 12/12:

- **Editing still rejected.** The complete model is byte-identical after
  pressing `x` in every mode and width: 318,015 characters unchanged. This is a
  full-model comparison on purpose — FINDINGS warns that comparing rendered
  text is worthless here, because focusing the editor changes the virtualized
  viewport, and my first version of the check fell into exactly that trap and
  reported a phantom edit.
- **Editable editors stay editable.** The public BQL query editor still reports
  `readonly=false`, carries `aria-readonly="false"`, and accepts a typed
  character. Without this control the repair could have silently made a
  writable surface read-only.
- The textarea fallback is reached by deleting `window.EditContext` before load
  in a **separately labelled diagnostic context only** — never product
  behaviour.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (383
files, 4319 passed, 1 pre-existing skip) and `yarn build` all pass.

Not claimed: no screen reader was exercised, and Firefox and WebKit were not
tested. This is native accessibility-tree state and DOM attributes in Chromium.

Entry Context still passes `readOnly` without `domReadOnly`, so its textarea
fallback remains wrong; that and the two deletion previews are t002.
