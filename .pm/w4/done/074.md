# Overview presents payroll's deductions as the transaction amount

Severity: minor (misleading summary; underlying postings are correct). Estimate: 50m. Owning package: dashboard. A2: a newcomer should not read a salary receipt as a payment of its deductions. Source: repeated dashboard QA, 2026-09-17.

Environment: production https://beancount.io; anonymous public synthetic `open_ledger/example`; QA-owned isolated headless Chromium 131, English/light, fresh 1440×844 and 390×844 loads. Local main `26d54a9db7d33c31a549bd12a0454a1c01f3f038`; deployed main asset `main-BIr0jJni.js`, exact deployed commit unverified. No later source repair exists for the traced function.

Reproduction: open `/ledger/open_ledger/example`, scroll to Recent activity, inspect Hoogle / Payroll dated Sep 7, 2017. At both widths the row shows `-2,089.1 USD` alongside Checking / Salary. Open the row: Entry Context points to `main.bean:5544`. The public source file and GraphQL entry contain Checking **+2550.60 USD**, Income **-4639.70 USD** and Expenses **+2089.10 USD**, plus +5/-5 VACHR. The displayed negative amount is only the expenses, without a deductions label; it is neither gross income nor net cash received.

Expected: a mixed income/expense transaction must not be presented as an ordinary expense with one unexplained signed subtotal. Use the existing mixed/multiple-postings summary for this ambiguous case, with a visible accessible indication at narrow width, and let entry details explain the postings. Preserve the exact selected-account summary when an account filter is active. Do not simply give income precedence instead: that would select another unlabeled subtotal.

Control: `/ledger/open_ledger/example?account=Assets%3AUS%3ABofA%3AChecking` correctly shows the same Hoogle payroll as `2,550.6 USD`. The ordinary Cafe Modagor expense remains `-33.71 USD`. Browser `GetLedgerJournal` returns HTTP 200 and payroll hash `c94ed5271c6df2e9a494015d1dcb6121`, with all 16 postings. Independent Decimal summation of downloaded `main.bean` yields the totals above. No API/serializer discrepancy or mutation is involved.

Root: `dashboard/src/features/reports/overview/lib/transaction-summary.ts:86–98` returns kind expense whenever any expense posting exists, before looking for income at 101. `recent-activity-card.tsx:123` is its sole production caller; at 286 it renders the resulting amount without disclosing that only expense postings were selected. Existing tests cover simple expense, simple income, account subtree, transfer and ambiguous FX, but omit mixed payroll. The fallback `kind: mixed` / no singular amount already exists, and desktop has a translated Multiple postings label at 282; make the mixed meaning understandable on narrow layouts too.

Fix/acceptance: classify entries containing both income and expense postings before choosing a simple category. The reproduced payroll becomes explicitly mixed, never an unlabeled negative deductions total. Account-filtered Checking keeps 2550.60 USD; pure expense and pure income signs stay unchanged; simple same-currency transfers and ambiguous multi-unit entries keep their semantics. Add a meaningful payroll regression with balancing postings and a narrow rendered-summary assertion. Preserve honest loading/empty/error states and entry-context navigation. Run the dashboard's native gates. No backend/API or dependency changes.

Blast radius/dedupe: sole helper consumer is RecentActivityCard in overview; the `/overview` alias redirects to the same overview route. Reports and Journal amounts use separate renderers and are not claimed broken. All .pm queues including done/blocked searched for payroll, deductions, expense precedence, summarizeTransaction and recent-activity amount/sign. No overlap found; w3/done/130 and 144 concern different date/filter defects, w4/done/004 is mobile transfer netting. Targeted git history contains only original import `af5339de` for this helper. No intentional mixed-payroll expense-only presentation is documented in its tests or guidance.

Verified evidence: `dashboard/tmp/qa-20260917/payroll-summary.json`, `payroll-summary-1440.png`, `payroll-summary-390.png`, and `main.bean`. Public text and exact amounts above make the ignored evidence independently reproducible. Authenticated roles, actual screen-reader speech, other browsers, failure injection and patched behavior remain unverified. No fixes or shipping performed.

Additional corroboration, September 17 (Chromium 149.0.7827.55): public synthetic `/ledger/open_ledger/stock-example` shows the April 17, 2026 “Sell 40 ACME from the 2025 lot — short-term gain” as **-4.95 USD**, including a fresh 390×844 load. HTTP-200 GetLedgerJournal, hash `a5460d0ee5a71f00d021fd857f0ba12c`, has -40 ACME at 84.60 USD cost, cash +3670.00/-4.95 USD, commission expense +4.95 USD, and capital-gain income -286.00 USD. Thus the same expense-before-income branch selects only commission. The account-filtered control `?account=Assets%3ABrokerage%3ACash` correctly shows **3,665.05 USD**. Include this mixed income/expense trade as a regression alongside payroll; do not replace the commission with another unexplained subtotal. `dashboard/tmp/qa-20260917/stock-expense-summary.json` retains settled narrow text, the complete public entry, and the cash-filter control. This extends the existing cause and scope; it is not a separate issue or an API discrepancy.

**Resolved 2026-09-19** — `summarizeTransaction` now classifies an entry
carrying both income and expense postings as `mixed` before either simple
category, so the Hoogle payroll reads "Multiple postings" instead of
`-2,089.1 USD` and the stock-example sale is no longer reduced to its `-4.95`
commission. The label moved into the amount's place so it is visible at narrow
widths, where the column carrying it is hidden. Verified live at 1440×844 and
390×844: the account-filtered Checking control still shows `2,550.6 USD` and
the ordinary Cafe Modagor expense is unchanged at `-33.71 USD`. Five
regressions cover the payroll (with its balancing VACHR postings), the sale,
both account-filter controls and pure income/expense entries; removing the new
branch fails two of them. Shipped in `f06b4398` (`dashboard`).
