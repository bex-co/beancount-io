# "YTD" on a stale account reports a year that ended nine years ago

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: every other range pill is a rolling window and survives the app's stale-ledger rule, but "year to date" is calendar-anchored by definition — relabelling it to a past year makes the pill say something untrue rather than something approximate.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`, "today" = 2026-09-13. Report-only QA; no ledger mutation. BQL is read-only through the MCP credential pinned to that ledger.

## Repro

1. Select `puncsky/example`, open `Assets:US:BofA:Checking`. Its **last posting is 2017-09-07** — there is no 2026 activity at all (`max(date)` via BQL confirms it).
2. Tap **YTD**. The card reads:

   > **Balance $2,754.06** · **−$3,130.61 (−53.20%)**

Year-to-date 2026 for this account is **$0.00** — nothing has happened in 2026. The figure shown is the change across **2017**.

## Cause — and what is *not* the cause

`series-util.ts:95-99` states the anchoring rule and its reason plainly:

> *"The window is anchored to the **latest data point** (not 'today') so a stale ledger still shows history instead of an empty chart."*

**That rule is sound and should stay.** For `1M/3M/6M/1Y` it means "the last N months of this account's life", which is a reasonable thing to show instead of a blank plot — the pill is a rolling window and stays approximately honest.

The problem is that `rangeStartMonth` applies the same anchor to `YTD` (`series-util.ts:81-83`):

```ts
const [year, month] = referenceYearMonth.split("-").map(Number);
if (range === "YTD") {
  return `${year}-01`;
}
```

`year` comes from the **reference month**, so on this account `YTD` resolves to `2017-01`. Unlike the rolling ranges, there is no reading under which "year to date" means "the year ending at the last data point" — that is just another 1Y. The label asserts a relationship to today that the computation does not have.

**The number is wrong even for the year it is actually showing.** The baseline is the first monthly point *inside* the window — end of January 2017 — not the year's opening balance:

| quantity | value |
| --- | --- |
| balance at 2016-12-31 (true YTD-2017 opening) | `$6,377.23` |
| balance at 2017-01-31 (what the card uses) | **`$5,884.67`** |
| closing balance | `$2,754.06` |

`2754.06 − 5884.67 = −3130.61` and `3130.61 / 5884.67 = 53.20%` — matching the screen to the cent, and confirming the baseline defect filed as **`w4/036`** is compounding here. The true 2017 change would be `−$3,623.17`.

## Fix

Anchor `YTD` to the **current** year while leaving the rolling ranges anchored to the latest data point:

```ts
if (range === "YTD") {
  return `${currentYear}-01`;   // from the caller's "today", not the reference month
}
```

`rangeStartMonth` takes only a reference month today, so this needs today's year threaded in (the codebase already prefers passing "now" explicitly — `detect-recurrence.ts` documents "never read the clock here").

Then decide what `YTD` shows when the current year has no data. An empty plot is the honest answer and the one the anchoring rule was written to avoid, so the better options are to render `$0.00` change with a "no activity this year" empty state, or to hide/disable the `YTD` pill when the series has no point in the current year. **Do not** resolve it by leaving the label and quietly showing a different year.

Fixing `w4/036` alongside this is what makes the resulting number right rather than merely right-labelled.

**Acceptance:** with "today" in 2026, `Assets:US:BofA:Checking` at YTD shows a `$0.00` change (or an explicit empty state) rather than 2017's; `Assets:Bank:Mercury:Checking`, which does have 2026 activity, shows its real year-to-date change; Reports at YTD on a ledger whose newest data is 2025 no longer plots 2025 months; `1M/3M/6M/1Y/ALL` are unchanged everywhere, still anchored to the latest data point. Add a test with a series whose last point is in a prior year, asserting `YTD` resolves to the current year's January — `series-util`'s tests cover `rangeStartMonth`'s month arithmetic but none pins its behaviour against a stale reference.

## Blast radius

`rangeStartMonth` is shared: its own comment notes it is used "so the Spending chart and its transaction list apply the same window", and `filterSeriesByRange`/`filterBalanceSeriesByRange` sit on both the account drill-down and Home's Net Worth / Assets / Liabilities card. Any surface offering a YTD pill over a series whose latest point is in a prior year is affected.

Only bites a **stale** account or ledger — on one with current activity the reference year *is* the current year and YTD is correct.

**Confirmed on Home as well, so the shared-surface claim is observed rather than inferred.** On public `open_ledger/crypto-example`, whose newest transaction is **2025-02-10** (verified from the Transactions list; there is no 2026 activity), Home's Net Worth card at **YTD** reads `$114,581.88` with **`+$5,535.30 (+5.08%)`** and plots a two-point Jan→Feb 2025 line. Year-to-date 2026 for that ledger is `$0.00`. The same card at 6M reads `+$5,530.46 (+5.07%)` — close but not equal, which is itself evidence the two windows resolve differently (6M ≈ Sep 2024–Feb 2025, YTD = Jan–Feb 2025) and that both are anchored to February 2025.

**Also confirmed on Reports — a third surface, and the worst-presented of the three.** On the same stale `open_ledger/crypto-example`, the Reports income/expense chart at **YTD** plots exactly two bars labelled **`JAN`** and **`FEB`** — January and February **2025** — on 2026-09-13. At 6M the same chart shows `SEP OCT NOV DEC JAN FEB`, which is the intended rolling-window behaviour and is *not* a defect.

What makes the Reports instance sharper than the two card instances: `seriesToChartArray` labels months with `point.date.slice(5, 7)`, so the axis reads **month-only, with no year**. A card at least shows a single figure a reader might question; here the chart presents a confident two-month "year to date" with nothing on screen indicating the year is not the current one. Any fix should consider showing the year on the axis when the series is not in the current year, or the label change alone will leave this reading the same way.

Reproduced on one account (`Assets:US:BofA:Checking`, `puncsky/example`), one Home card and one Reports chart (both `open_ledger/crypto-example`). Not exercised: the Spending chart's YTD (below the fold and unreachable, per `w4/020`), the Reports transaction list that `rangeStartMonth`'s comment says shares this window, dark mode, and Android. The crypto-example figures could not be reconciled against BQL — the MCP credential for this run is pinned to `puncsky/example` — so that arm rests on the on-screen values and the ledger's visible date range.

That is **not** filed as a defect: per the documented rule it means "the six months ending at the last data point", which is the intended stale-ledger behaviour. It is listed here so a reader who notices it knows it was considered.

**Resolved 2026-09-14** in `fix(mobile): anchor YTD to the current year on stale ledgers`.

**The change.** `rangeStartMonth` resolves `YTD` to January of the current year. The year is an optional `currentYear` that defaults to the clock, following the `today` default in `budget-labels.ts`. It no longer uses the reference month's year. `1M`/`3M`/`6M`/`1Y`/`ALL` stay anchored to the latest data point, as the note required. `filterSeriesByRange`, `filterBalanceSeriesByRange` and `selectAccountTransactions` pass the year through, so tests are deterministic.

**On a stale ledger.**
- The flow charts (Reports income/expense) have no year-to-date points and render their placeholder.
- The balance cards hold the last balance, so the change reads zero.
- The account transactions list is empty.
