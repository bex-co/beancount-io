# Omit empty journal detail rows when Metadata has nothing to display

**Severity:** minor. **Estimate:** 45 minutes. **Owner:** dashboard. **A2:** newcomers using table navigation should encounter transactions and their available details, without an empty row after every transaction.

Environment: production `https://beancount.io`, signed out, English/light, isolated headless Chromium 149.0.7827.55. Local HEAD `26d54a9d`; production asset `main-BIr0jJni.js`, exact deployed SHA unknown. Fetched main `bd5d1d31` adds importer test mocks only; the affected renderer is unchanged.

## Reproduction and evidence

1. Open `/ledger/open_ledger/example/journal?offset=1020&lang=en`. Select Transaction only, Metadata on, Postings off, and leave every individual posting disclosure collapsed.
2. Results correctly says `1021–1044 / 1044`, representing 24 transactions.
3. Inspect the DOM and Chromium accessibility tree. Both expose 49 rows: one header, 24 transaction rows, and 24 empty detail rows. Each extra row contains a single unignored, unnamed cell with no children; the DOM is `<tr><td colspan="5"></td></tr>` with a one-pixel border-height row.
4. Fresh reloads at 390×844 and 1440×1000 reproduce it. Turn Metadata off: 25 rows and zero empty detail cells. Restore Metadata and expand the first transaction's postings: its detail row becomes populated, while the other 23 empty rows remain.

The shared account journal also reproduces at 390×844: `/ledger/open_ledger/example/account/Assets%3AUS%3ABofA%3AChecking?lang=en`, with the same display settings, exposes 41 rows for 20 entries plus 20 empty details and a header. This is native accessibility-tree evidence, not a claim about actual screen-reader speech or keyboard Tab stops.

Real `GetLedgerJournal` HTTP 200, query `{directiveTypes:["Transaction"],offset:1020,limit:60,time:"",account:"",filter:""}`, returns total 1044 and exactly 24 entries, all with `meta:null`. It does not return additional empty records. First entry hash `836bfe4fa9a39d4db0d7b8dfd6e62d02`, date 2015-01-19, narration “Investing 60% of cash in RGAGX”, has two valid postings.

Verified artifacts: `dashboard/tmp/qa-20260917/journal-empty-detail-rows.json` (fresh-width cases, controls, account corroboration, request/response) and `dashboard/tmp/qa-20260917/journal-empty-detail-1440.png` (viewed). The counts and markup above stand independently of ignored artifacts.

## Cause and scoped fix

`dashboard/src/features/journal/components/journal-table.tsx:434–476` sets `detailVisible = (isTransaction && postingsVisible) || showMetadata`. The global Metadata preference therefore creates a detail row even when its children render nothing. `journal-metadata.tsx:12–28` correctly returns null for absent metadata or metadata containing only excluded internal keys; `journal-postings.tsx:18–19` correctly returns null when postings are hidden or absent. The wrapper never accounts for those conditions.

The API's nullable metadata is valid (`common/types/journal.ts:49`); Journal maps the returned directives directly at `pages/journal-page.tsx:205–219`, and Account Journal does likewise at `features/reports/account/index.tsx:238–247`. Both production consumers use this renderer. No API, authorization, or REST/GraphQL/MCP behavior change is needed.

Render the detail row only when it has visible postings or displayable metadata. Reuse one metadata-filtering calculation so the wrapper and metadata content agree about `__*`, `filename*`, and `lineno*` exclusions. Preserve real metadata, per-entry expansion, the global Postings preference, semantic headers/cells, date-button actions, and account amounts. Do not hide populated details with `aria-hidden` or disable Metadata globally.

Acceptance: both live reproductions expose one row per entry plus the header while details are empty; expanding postings or showing actual metadata adds the appropriate populated row, and collapsing removes an otherwise empty row. Add focused renderer coverage for null/empty/internal-only metadata, visible custom metadata, and visible/hidden postings in both journal modes. Preserve existing table semantics and meaningful details. Other browsers, authenticated roles, network failures, and a patched implementation remain unverified.

Dedupe: all board states searched for empty/blank journal rows, detail cells and metadata rows. This is a consequence of the table rewrite in `398e67e3` (`w3/done/m40`), whose semantic-table improvement must remain. Later `87d3c63b` makes Entry Context keyboard reachable and does not repair this condition. Existing w4/110 concerns generated-entry dialogs; m20 concerns table names. Neither owns empty detail rows. No product changes or production mutations made.

Preserve these populated rows while omitting empty ones. Evidence: `dashboard/tmp/qa-20260917/journal-populated-metadata-control.json`. This extends the working control, not the issue count or scope.

**Resolved 2026-09-19** — Reproduced against a local build: the 24-transaction
journal page exposed 49 rows — a header, 24 transactions and 24 empty detail
rows — at 1440px and 390px, and the crypto journal showed 49 empty rows beside
its 11 real `pool: slushpool` ones.

`journal-table.tsx` set `detailVisible` from the global Metadata preference
alone, so the row existed whether or not its children would render anything.
It now renders only when there are visible postings or metadata that will
actually be displayed. The filtering — the `__*`, `filename*` and `lineno*`
exclusions — moved into one small module (`journal-metadata-entries.ts`) that
both the wrapper and `JournalMetadata` read, so the two cannot disagree about
whether a directive has something to show.

Real metadata, per-entry expansion, the global Postings preference, the
semantic table from `w3/m40`, the date-button actions and the account amounts
are unchanged; nothing is hidden with `aria-hidden` and Metadata still works.
No API, authorization or contract change.

Verified in a real browser: the same page is now 25 rows with zero empty detail
rows at both widths; expanding one transaction's postings adds exactly one
populated row (26 rows) and collapsing removes it; and the crypto journal keeps
all 11 metadata rows through a Metadata off-and-on cycle — 72 rows with, 61
without, 72 again — with no empty rows at any point. The account journal was
re-checked and shows no empty detail rows either.

Eight renderer cases in `journal/components/__tests__/empty-detail-rows.test.tsx`
cover null, empty and internal-only metadata under Metadata on, real metadata,
a mixed page, visible and hidden postings, a transaction with no postings, and
the per-entry toggle; six fail without this change. Gates from `dashboard/`:
`yarn format:check`, `yarn lint`, `yarn test` (401 files, 4501 passed, 1
pre-existing skip) and `yarn build` all pass. Other browsers, authenticated
roles and network failures remain unverified. Shipped in `71624f3d`
(`dashboard`).
