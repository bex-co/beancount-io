# Let Receipt Record accept the exact decimal the review permits

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** dashboard. **A2:** a receipt reader must be able to correct a more precise amount instead of being forced to round it to cents. This is a remaining native-form boundary of completed [W1/028](../../w1/done/028.md), whose exact receipt serializer still passes; retain it as a residual follow-up, not another count of that historical group.

## Reproduction and controls

Production `https://beancount.io`,2026-10-22, isolated owned headless Chromium155.0.8059.85, English/light, authenticated designated synthetic ledger,390×844 and1440×1000. Upload URL, PUT and ParseReceipt are modeled before transport; no actual upload, AI action or quota use. All Record requests are intercepted and aborted before transport.

1. Reach the actual Receipt review using a locally parsed12.50 fixture and existing expense/payment accounts. Enter Amount **12.345**; choose the supported free-entry Currency **KWD** and keep other required fields populated.
2. Preview preserves12.345/-12.345KWD. The amount input exposes `aria-invalid=false`, but native `validity.stepMismatch=true`, `validity.valid=false`, with **Please enter a valid value. The two nearest valid values are 12.34 and 12.35.**
3. Native Enter on Record Transaction focuses Amount and produces **zero** InsertReceiptTransaction attempts at both widths. The fixed-cent HTML constraint blocks the submit event before the exact schema/workflow can run.
4. Change only Amount to **12.34**. Record now prepares one input with exact12.34/-12.34KWD and the same accounts/date; each control request is aborted before transport. A separate USD12.345 probe has the same native step refusal, so this is not a suggestion lookup or KWD-specific API failure.
5. Reload each page and locally supply ParseReceipt amount **12.345**. The existing deliberate prefill default displays **12.35**. Select KWD and correct it back to12.345: the native step refusal and zero requests repeat independently after reload.

This proves client reachability and input preservation only. It does not prove these particular accounts permit KWD postings or that the backend accepted a transaction. The ordinary12.50 fixture and two-decimal controls work. Positive-number/date/account validation and exact typed-amount serialization must stay intact.

## Cause and bounded repair

`dashboard/src/features/receipt/components/receipt-review-form.tsx:219–224` uses `type="number" step="0.01" min="0"`, imposing cents regardless of the selected currency. Its Zod schema at:76–83 accepts exact positive decimals, and `use-receipt-workflow.ts:57–62,149–170` normalizes/negates their strings exactly. These layers disagree before the mutation boundary. The existing helper test explicitly covers1.005,123.456 and0.00000001, but cannot see browser constraint validation.

Remove the universal two-decimal native step restriction, using a control/step compatible with the existing supported exact-decimal grammar. Keep a useful numeric input experience, positive/nonzero validation, exact text, localized required errors, selected currency, pending guard and failure recovery. Do not repair this by rounding the user's edit or weakening valid-number validation. W1/028 explicitly left the two-place parsed prefill as an editable default; changing that policy or the parser response type is not required here. The demonstrated bug is that the promised correction cannot be submitted.

Acceptance: in the actual browser review,12.345KWD and the existing supported fractional-amount controls reach the mutation boundary once with exact positive/negative strings;12.34 and12.50 remain exact. Zero, negative and invalid input still fail appropriately. Include native constraint-validation coverage; a workflow-helper test alone misses this. Run dashboard gates when implementing. Actual OCR, server booking, currency/account eligibility, other engines and the repaired deployment are unverified. No API, dependency or backend change is established as necessary.
