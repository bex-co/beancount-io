# Expose the sidebar’s actual size and expanded state

**Severity:** minor. **Estimate:** 60 minutes. **Owner:** dashboard. **A2:** keyboard and assistive-technology users should receive the current pane size and expanded state when collapsing or restoring the sidebar.

Production beancount.io, signed out, English/light, owned headless Chromium149.0.7827.55. Public stock-example Commodities; HEAD26d54a9d/main bd5d1d31; deployed main-BIr0jJni.js, exact deploy SHA unknown.

At1440×1000, focus the separator named Toggle Sidebar and press Enter. The expanded256px sidebar collapses to its48px icon rail, but the separator's aria-valuenow remains256, aria-valuemin192 and aria-valuemax384. Chromium's native accessibility tree also reports value256 and empty valuetext after settlement. The interior sidebar element measures47px excluding its border; this is not a one-pixel discrepancy. A fresh collapsed reload repeats the incorrect value, and a fresh1024×844 reload does too. Pressing Enter to expand and ArrowRight once correctly updates the value to272 alongside the271px interior: ordinary resizing works, while collapsed-state reporting does not.

Root: `dashboard/src/common/components/ui/sidebar.tsx:515–518` always publishes the remembered expanded width and expanded minimum, independent of open. The collapsed layout uses SIDEBAR_WIDTH_ICON=3rem while preserving that width for later restoration. Retaining the preference is correct; exposing it as the present splitter position is not. Introduced by4652596f. The [WAI window-splitter guidance](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/) describes the value as the current separator position/primary-pane size, with Enter collapsing and restoring it. This report relies on actual native AX state, not a claim about a particular screen reader's speech.

Derive a coherent accessible value/range from the effective open/collapsed pane state while retaining the stored expanded width. A suitable localized value description may clarify the collapsed state if needed; do not change the saved preference to the icon width, break restoring it, or add unsupported ARIA solely to announce a toggle. Preserve keyboard arrows, Enter/Space, pointer drag/clamps, SSR-safe cookies, focus, and the ordinary expanded-width values. The mobile sheet below the rail breakpoint is a separate control and is not part of this bug.

Acceptance: expanded → collapsed → expanded exposes values describing each actual state; a collapsed reload does likewise; keyboard resizing still changes values and width together, and collapse/reopen restores the preferred expanded width. Verify1440 and1024 and an ordinary nondefault expanded width, with meaningful tests through the existing SidebarProvider/rail state behavior. Run dashboard gates when implementing.

**Resolved 2026-09-19** — Both halves of this note are fixed. The rail now reports the pane's present size — `aria-valuenow` is the icon-rail width while collapsed and the stored width while expanded, and `aria-valuemin` moves with it so the reported position is never outside its own range — while the remembered expanded width stays untouched as the value to restore to. `SidebarTrigger` gains `aria-expanded` taken from whichever sidebar it governs, so the desktop rail's open state is exposed on the disclosure control without adding dialog ARIA. `SIDEBAR_WIDTH_ICON_PX` in `sidebar-state.ts` now backs both the CSS length and the reported value, so the two cannot drift. Both defects were reproduced first at HEAD at 1440×1000 on the public stock-example Commodities page: collapsing the 256px sidebar to its 47px interior left `aria-valuenow` at 256 with `aria-valuemin` 192, and the trigger had no `aria-expanded` in either state. After the change, measured live in the same browser: expanded reports 256/192/384 with `aria-expanded="true"` beside a 255px pane; collapsed reports 48/48/384 with `aria-expanded="false"` beside a 47px pane; a fresh collapsed reload reports the same; and the whole cycle behaves identically at 1024×844. The nondefault-width path was exercised too — ArrowRight took the value to 272 alongside a 271px pane, collapsing reported 48 while keeping 272 as the preference, and reopening restored 272. The sidebar preference was left at 256px/open, as found. `common/components/ui/__tests__/sidebar-state-exposure.test.tsx` adds eleven cases driving the real `SidebarProvider`/`SidebarRail`/`SidebarTrigger` composition with cookie persistence: expanded and collapsed reporting, the collapsed minimum, the value staying inside its range, a collapsed first render, the nondefault-width round trip, keyboard resizing still moving value and width together, and the trigger's state through collapse, reopen, a collapsed first render and a click. Seven of the eleven fail when the two attributes are reverted; the four that still pass are the expanded-state and keyboard-resize controls, which were already correct and are there to catch a regression in the working path. Not verified: real assistive-technology speech, other browser engines, and pointer-drag announcements. The mobile sheet was left alone as the note directs, beyond the trigger reporting the sheet's own state when it governs one. Dashboard gates all pass (`yarn format:check`, `yarn lint`, `yarn test` — 407 files, 4586 passed, 1 pre-existing skip — and `yarn build`). Shipped in `535f8d09` (`dashboard`).
