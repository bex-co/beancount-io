## Objective

Keep guest browsing read-only and make the transition into the existing authentication flow preserve the visitor's intended view.

## Context

- `mobile/src/common/oauth/oauth-sign-in-finalizer.ts` selects a ledger after login and handles pending app links.
- The native sign-in runner already distinguishes cancellation and failures.
- `useLedgerAccess()` and route-level write guards remain the authority for edit availability after sign-in.

## Steps

1. Inspect actions reachable from the three guest views and route protected actions through the existing authentication entry; keep direct protected routes guarded.
2. Retain a bounded continuation containing the guest server, example, and supported view during sign-in.
3. On cancellation or failure, restore the guest view. On success, recheck access before restoring it and reconcile the continuation with existing pending-link behavior.
4. Discard stale continuations on server changes, logout, or a different session completing the flow.

## Files

- `mobile/src/screens/welcome/use-native-sign-in.ts` and related flow code.
- `mobile/src/common/oauth/oauth-sign-in-finalizer.ts`
- `mobile/src/common/app-links/` — existing continuation integration if needed.
- Guest navigation and existing ledger-access/write guards.

## Acceptance criteria

- [x] Guest navigation triggers no ledger mutation or authenticated-only query; direct protected routes retain their guard.
- [x] Canceling or failing authentication restores the original guest example and view.
- [x] Successful sign-in rechecks current access before restoring the view; missing access has a recoverable result.
- [x] A server change, logout, or competing authentication completion cannot restore a stale guest continuation or private cache.
- [x] Existing signed-in navigation across all five tabs and pending app-link continuation still work.

## Out of scope

Changes to OAuth protocol behavior, credential policy, server-side rate limits, archive downloads, or SSH requirements.
