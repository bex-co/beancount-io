# Keep the minus sign attached to the transaction detail's hero amount

**Severity:** major. **Estimate:** 25–40 minutes. Owner: mobile. A2/A3: the public open ledgers are the app's shop window, and on the largest of them a debit's headline reads as a credit.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, public `open_ledger/alphabet`. Report-only QA; no ledger mutation.

## Repro

1. Open `beancount:///ledger/open_ledger/alphabet`, terminate and relaunch the app, and wait for Home to settle.
2. Home → Recent Transactions → tap the first row, `Q2 2026 Exp… $26,560,000,000.00`.
3. The Transaction detail hero renders on **two lines**: a lone `-` on the first line, flush to the screen's leading edge, and `$26,560,000,000.00` centred on the second. Money flow below reads `TO Expense…ome-Tax +$26,560,000,000.00` / `FROM Assets:…valents -$26,560,000,000.00`.
4. Relaunching and reopening the entry reproduces the split exactly.

**Working control:** `puncsky/example` → `Anthropic`. The hero reads `-$102.00` on one centred line with the sign attached, from the same code path.

**Expected:** the hero amount stays one visual unit — the sign never separates from its digits, and the number never scales or wraps out of the sign's reach.
**Actual:** the sign is orphaned on its own line and left-aligned, so the amount a user reads is an unsigned `$26,560,000,000.00`.

## Root cause

`mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:412` builds the string as `` `-${hero.text}` `` and renders it through `AmountText` with `styles.heroAmount` (lines 100–104: `fontSize: fontSizes.heroSm`, no `numberOfLines`, no `adjustsFontSizeToFit`, no `minimumFontScale`). At `heroSm`, `-$26,560,000,000.00` is wider than the hero container, and the leading hyphen is a legal line-break opportunity, so the text engine breaks after it. The orphaned line is then left-aligned rather than centred because `AmountText` (`mobile/src/components/amount-text/amount-text.tsx`) deliberately layers `textAlign: LEADING_TEXT_ALIGN` under the caller's style, and `heroAmount` never overrides it — the single-line control looks centred only because the line fills the width.

## Reproduced in right-to-left, which independently confirms the diagnosis (added September 14)

Same entry, same build, app locale forced to **فارسی** (method in `w4/063`), `open_ledger/alphabet`. The hero splits identically — a lone `−` on its own line, then `$26,560,000,000.00` below — **except that the orphaned sign now sits at the screen's *right* edge.**

That is exactly what the root cause above predicts and is worth recording as corroboration rather than as a second defect. `AmountText` layers `textAlign: LEADING_TEXT_ALIGN`, and `LEADING_TEXT_ALIGN` is documented (`common/rtl.ts:118-140`) as "the **layout's** leading edge rather than its own content's direction" — left in LTR, right in RTL. The sign follows the leading edge in both directions, so the diagnosis is confirmed from a second angle: this is an alignment inherited from `AmountText`, not a stray left-alignment somewhere in the hero.

It also **adds one acceptance criterion**: the proposed `textAlign: "center"` on `heroAmount` must be checked in RTL too. Centring is direction-neutral, so it should hold — but the whole reason this note exists is that the centring was only apparent, so it should be seen rather than assumed. Evidence: `mobile/tmp/qa-2026-09-14/w4l130-02-fa-detail.jpg`.

Noted in the same pass and **not** a defect: the Money flow rows render their direction caption (`به` / `از`) stacked above the account name in Persian. That is the normal layout in every locale — `posting-row.tsx` puts `direction` and `account` in a column with `marginBottom: 3` — not an RTL wrap.

## Fix

Make the hero amount unbreakable and self-fitting at the call site:

- Add `numberOfLines={1}` plus `adjustsFontSizeToFit` with a `minimumFontScale` low enough for a 21-character amount, so long values shrink instead of wrapping. Amounts must not ellipsize — a truncated figure lies — so the shrink floor has to cover the widest realistic string, not merely most of them.
- Give `heroAmount` an explicit `textAlign: "center"` so it agrees with the centred `hero` container in every case, not only when the line happens to be full.

Keep `AmountText`'s `LEADING_TEXT_ALIGN` default and its `maxFontSizeMultiplier` cap as they are — both are deliberate and shared. Do not solve this by replacing the hyphen-minus with U+2212 alone: that hides this instance without bounding the width, and the amount would still wrap on a narrower device or at a larger Dynamic Type setting. No backend, API, or cross-package change is needed.

**Acceptance:** on a fresh iPhone 17e launch, the `open_ledger/alphabet` Q2 2026 income-tax entry shows `-$26,560,000,000.00` on one centred line, with the minus adjacent to the `$`; `puncsky/example` → `Anthropic` still shows `-$102.00` unchanged at full size. Add regression coverage that a hero amount string wider than its container renders single-line (assert the props the screen passes — `numberOfLines`, the shrink floor, the centred alignment — through the presentation path, not the selector). Re-check at the largest Dynamic Type setting supported by `amountMaxFontSizeMultiplier` and in dark mode.

## The Home net-worth headline does the same thing, and it is not the minus sign (added September 14)

This note's blast radius listed the Home net-worth headline as *"not independently reproduced."* It now is — and in a way that sharpens the fix.

German at **AX1** (`xcrun simctl ui … content_size accessibility-medium`), `open_ledger/alphabet`, Home. The hero splits across two lines **in the middle of a thousands group**:

```
$640,480,000,00
0.00
```

The first line is a complete-looking, wrong figure. There is **no sign at all** on this value — it is positive — so the break opportunity was the comma after a digit group, not the leading hyphen.

Same shape, same omission. `interactive-line-chart.tsx:253-256`:

```ts
headline: {
  fontSize: fontSizes.display,
  fontWeight: fontWeights.medium,
  color: theme.text01,
},
```

No `numberOfLines`, no `adjustsFontSizeToFit`, no `minimumFontScale` — rendered through `AnimatedAmount` at `:374-381`, the same family as the transaction-detail hero's `AmountText`.

**What this changes about the fix:** this note already rejects swapping the hyphen for U+2212 on the grounds that it "hides this instance without bounding the width". The Home case is the proof — an amount with no sign whatsoever still wraps, so any sign-focused remedy cannot be sufficient. The real requirement is the one stated above: bound the width and shrink, at every hero-sized amount.

Add `interactive-line-chart.tsx`'s `headline` to the fix and to the acceptance criteria. It has **two** consumers — `home-screen/components/account-charts-card.tsx` (Home) and `components/balance-chart-card/index.tsx` (the account drill-down) — so one style covers both of the remaining hero surfaces this note listed as unreproduced, leaving only Android and VoiceOver outstanding.

Evidence: `mobile/tmp/qa-2026-09-14/w4l131-01-de-ax1-home.jpg`.

**Related but separate, and deliberately not folded in:** `w4/012` reports amounts *clipped* mid-number at the screen edge on the Accounts tab at enlarged text (`$921,983,000.6` for ~$922 billion). Same class of harm — a number that reads as a different number — but a different mechanism (clipping, not wrapping) and a different component. Read the two together when sizing the work; the underlying policy question, "what should an amount too wide for its box do", is one decision that ought to be made once for the whole app.

## Blast radius

`styles.heroAmount` is used only at `transaction-detail-screen.tsx:502`. `AmountText` itself is shared — the change stays at the call site so no other amount's alignment or wrapping behavior moves. Not independently reproduced: the same overflow shape on other hero-sized amounts (account detail header, Home net-worth headline), Android, and VoiceOver, which reads the string and is likely unaffected.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for minus/negative sign, "wraps", "orphan", hero amount and truncation terms. `w3/216.md` is an open, distinct finding — Reports category amounts lose the sign in `formatMoneyWithCurrency` before rendering; here the sign is present and correctly produced, and only the layout detaches it. No overlapping open item; not deployment lag.
