# Disclose the public profile's capped ledger preview in its count and search

Severity: **minor**. Package: **dashboard**. Estimate: **45–60m**. Source:
continuous dashboard QA for w4. **A2/A3**: public example discovery should not
tell a newcomer that an existing example is absent from the collection.

## Reproduction

Production `https://beancount.io`, anonymous public `open_ledger`, owned isolated
headless Chromium 149.0.7827.55, English/light, 1440×1000 and 390×844. Local
main `390568c2`; deployed entry `main-d5j4FX-V.js`, exact deployed SHA unverified.

1. Open `/ledger/open_ledger`. Its heading is **Ledgers 50**.
2. Repeatedly choose **Show more ledgers**. It stops at **Showing 50 of 50
   ledgers**, with exactly 50 cards and no continuation control.
3. Search for `stock-example`. The page says **No ledgers match your search.
   Try another name or keyword.** and **Showing 0 of 0 ledgers**.
4. On that same profile, **Committed to stock-example** in Recent Activity
   opens `/ledger/open_ledger/stock-example`, whose overview successfully loads
   with the `stock-example` heading. This is an accessible public ledger.
5. Fresh-load `/ledger/open_ledger?q=stock-example`; the empty search repeats at
   both widths. Searching `example` is a working control: it returns the three
   examples included in the preview, including the ordinary `example` ledger.

Real GraphQL `getUserProfile(username: "open_ledger")` and REST
`GET /api-gateway/v1/social/profile?username=open_ledger` both return HTTP 200,
50 repositories, ordinary `example` present and `stock-example` absent.
GraphQL's 50 entries are all public. No response was mocked. This is not caused
by access denial, a failed request, or the local 12-card Show more slice.

## Cause and bounded fix

The server cap is **intentional**:
`backend-cluster/backend-v2/src/features/gitea/user-profile/service/user-profile-service.ts:177–212`
documents a 50-repository performance limit and requests one page in both
self-view and public branches. `api/public-profile-route.ts:46–48` documents
that limit in the public contract. Do not remove or raise that cap for this fix.

The dashboard treats that preview as complete. Its
`features/user-profile/hooks/use-user-profile.ts:27` passes the array through;
`components/ledger-collection.tsx:136–158` filters/sorts only that array,
`:175–180` presents its length without qualification, and `:259–288` presents
global-sounding empty results and a complete-looking denominator. The same
component's Show more control reveals already-fetched cards only.

Make the preview scope visible and accessible when the response reaches the
documented cap: the heading/count must describe *loaded/shown* ledgers and
explain that more may exist; search and no-match guidance must explicitly refer
to that preview. Do not infer that there are exactly 50 total repositories, nor
claim a 51st repository exists merely because an array has length 50. Preserve
the existing API limit and local Show more behavior. Server-backed continuation
and whole-profile search are a separate product/API change, not a requirement
of this bounded truthfulness fix.

- [ ] On the live profile, the exhausted 50-card view no longer claims it is the
      complete ledger inventory; the cap/possible additional ledgers are clear.
- [ ] Searching `stock-example` explains that it has no match in the loaded
      preview, without claiming the account has no matching public ledger.
- [ ] Search, clear, ordering, Show more, opening a matching ledger, and restored
      `q`/`sort`/`show` URLs retain their existing behavior.
- [ ] Test a capped response, a response below the cap, and a no-match search;
      do not assert a fabricated overall total. Localize the new guidance and
      run dashboard gates. Verify desktop/narrow accessible text.
