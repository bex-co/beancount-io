# Persian localization leaves the document direction left-to-right

Severity: minor. Estimate: 50m for document direction and focused regression checks; broader component layout work is separate. Package: dashboard. A2/A3: the advertised Persian locale should establish the correct reading direction. Source: repeated dashboard QA, 2026-09-17.

Repro/environment: QA-owned isolated headless Chromium 131, narrow 390×844, anonymous, production https://beancount.io. Open `/ledger/open_ledger/example?lang=fa`, then independently load `/auth/login?lang=fa`. Both display Persian translations and `<html lang="fa">`, but no `dir` attribute; `getComputedStyle(document.body).direction` is `ltr`. Overview's translated descriptions and headings remain aligned to the left/start of an LTR container. Screenshot visually inspected. Reloaded sign-in independently confirms the same result without credential entry. English/German controls earlier in the run correctly used LTR.

Expected: the shell declares RTL for Persian from the first rendered document and keeps direction synchronized with the selected locale; returning to English/German restores LTR. Preserve intentional LTR isolation for ledger source code, identifiers and other machine syntax where appropriate. This note does not claim all translated text is unreadable or that the entire application has received an RTL audit.

Root: `dashboard/src/common/root-route/shell-component.tsx:13` emits `<html lang={i18n.language}>` with no direction. There is no direction synchronization in RootProvider/LanguageSync. Installed i18next `dist/esm/i18next.js:2107–2120` already exposes `i18n.dir(...)` and includes `fa` in RTL languages, so no new dependency or locale table is necessary. Path history: original `af5339de`, then language-loading change `7b7b35ed`; neither establishes direction. Local main `26d54a9db7d33c31a549bd12a0454a1c01f3f038`; production asset `main-BIr0jJni.js`, exact deployed SHA unverified. The missing attribute is live-confirmed, not merely inferred from source.

Fix/acceptance: derive document direction from the resolved i18n instance beside its language in the shell; ensure SSR and hydrated locale transitions agree. Fresh fa overview and sign-in use RTL, then en/de use LTR without a stale direction or hydration mismatch. Verify visible punctuation/alignment in the exercised screens and keep code/ledger identifiers legible. Add a meaningful rendered locale-switch regression. Audit existing direction-sensitive primitive configuration when verifying: shared Tabs currently supplies no dir, and installed Radix tabs reads useDirection; do not assume setting HTML direction proves its keyboard behavior. File any independently reproduced component-specific work separately instead of silently expanding this note into a full layout rewrite. Run dashboard native gates when implementing.

Blast radius: ShellComponent wraps dashboard routes, including public ledgers and auth. Only Persian Overview/sign-in are independently reproduced here; owner/member screens, native mobile and actual screen-reader speech are unverified. Backend/API responses are not involved: locale text renders successfully and the defect is in document markup.

Dedupe: searched every queue including done/blocked for Persian, RTL, right-to-left, html dir and document direction, plus all open milestone titles. Existing w4/done/063 and 066 concern **mobile** locale selection and magnitude bars; no dashboard shell-direction task found. No product code, production data, credential or user browser state changed.

Verified local evidence: `dashboard/tmp/qa-20260917/fa-overview.png` and `fa-login.png`; live DOM results were `{lang:"fa",dir:null,direction:"ltr"}` on both pages. No fixes or shipping performed.

---

**Resolved 2026-09-19** — the shell now emits `dir={i18n.dir()}` beside
`lang`, using i18next's own right-to-left table, so the direction is in the
server markup rather than applied after hydration. Verified live at 390×844 and
1440×1000: `?lang=fa` on the public overview and `/auth/login` went from no
`dir` and computed `ltr` to `dir="rtl"` and computed `rtl`, present in the
server response, with no hydration warning; English and German are now
explicitly `ltr`. Eight regressions drive the real i18next table (fa/ar/he as
rtl, en/de/ja as ltr, a language change not leaving a stale direction, and the
attribute being on the document element) and all fail without the fix. Shipped
in `a4e59cab` (`dashboard`).

The direction-sensitive component audit this note asked for did find a gap, and
it is filed as **w4/147** rather than folded in: Radix reads its direction from
a `DirectionProvider` rather than from the document, and the shared `Tabs`
passes no `dir`, so under `dir=rtl` ArrowRight still moves to the next tab
instead of following the visual order. Reproduced on the Persian balance-sheet
page.
