# A range row can render with *nothing* selected — the selected pill's only background is an indicator that starts invisible and has no fallback

**Severity:** minor. **Estimate:** 15–25 minutes. Owner: mobile. A2: observed on the Home net-worth card, where the row is the primary control — for over a minute the chart showed six months of data while the pill row showed no selection at all, and the active label was a washed-out ghost rather than the missing green pill.

**Read the caveat first: observed once, explained from source, and *not* reproduced on demand.** One subsequent attempt at the same ledger-switch sequence rendered correctly. What follows separates the two captures I have from the code argument, which stands on its own.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`. Report-only QA; no ledger mutation — only the selected ledger and the range pill were touched.

## What was observed

After switching the selected ledger from `puncsky/example` to `open_ledger/alphabet` (Browse ledgers → Explore → `open_ledger/alphabet`) and returning to Home:

- The net-worth card showed `$640,480,000,000.00`, `+$225,215,000,000.00 (+54.23%)` and the six-month curve — **correct 6M data**.
- The pill row read `1M  3M  6M  YTD  1Y  ALL` with **no green pill anywhere**, and `6M` rendered *lighter* than its five neighbours.
- This persisted across two captures **60 seconds apart** (`w4l125-05`, `w4l125-06`), so it is a settled state, not a frame caught mid-animation.
- Tapping `3M` fixed it instantly: solid green pill, delta recomputed to `+$161,734,000,000.00 (+33.78%)`. Tapping back to `6M` restored a solid green `6M` with the delta identical to the broken capture (`w4l125-08`), confirming the *data* had been 6M all along and only the chrome was wrong.

So the selection state was correct throughout; only its rendering was absent.

## Root cause

`src/components/time-range-pills/index.tsx`. The selected pill **has no background of its own** — this is deliberate and the file says so:

> *"The selected pill's fill is the sliding indicator below, not a style on the pill itself — otherwise the fill would teleport while the indicator travelled."*

The indicator is one absolutely-positioned `Animated.View` whose opacity starts hidden:

```ts
// Hidden until measured — otherwise a zero-width pill flashes at the origin
// on first mount.
const opacity = useSharedValue(0);
```

and the **only** place opacity is raised is inside `moveTo`, *after* an early return:

```ts
const moveTo = useCallback((key: T, animate: boolean) => {
  const layout = layouts.current[layoutKey(key)];
  if (!layout) {
    return;                    // ← opacity stays 0, and nothing retries
  }
  y.value = layout.y;
  height.value = layout.height;
  opacity.value = 1;
  …
```

`layouts` is a `useRef({})` populated only by each pill's `onLayout`. The mount-time `useEffect` calls `moveTo(value, …)` while that record is still empty, so it early-returns by design; the indicator is then expected to appear when the **active** pill reports its layout:

```ts
const handleLayout = (key: T) => (event: LayoutChangeEvent) => {
  layouts.current[layoutKey(key)] = event.nativeEvent.layout;
  if (key === value) { moveTo(key, placedRef.current); revealSelected(); }
};
```

That is the whole recovery path. If the active key's `onLayout` does not fire again after the ref is reset — React Native does not re-emit `onLayout` for a view whose layout is unchanged — there is no second chance, and the row stays with `opacity: 0`.

**And the label has already committed to being selected.** `styles.labelActive` is `{ color: theme.white }`, applied purely from `option.key === value`, independently of whether the indicator ever appeared. So the failure renders as **white text on the card's cream surface** — which is exactly the "dimmer than its neighbours" appearance in the capture, not a missing pill with normal text.

That is the defect worth fixing regardless of how often the trigger fires: **the two halves of "selected" are decided independently, and one of them can fail silently while the other proceeds.**

## What I could not establish

I could not pin the trigger. The same switch sequence (`puncsky/example` → Explore → `open_ledger/alphabet` → Home) rendered a correct solid `6M` on the next attempt (`w4l125-10`), as did the same shape of switch in an earlier session pass. Candidate explanations I did **not** confirm and am not asserting: a remount that resets `layouts`/`opacity` while React Native suppresses a redundant `onLayout`; an `onLayout` arriving with a zero box during a cross-fade; or an ordering race between the mount effect and the layout pass under load. Whoever fixes this should treat the trigger as unknown and make the failure unreachable rather than chase the repro.

## Fix

Make the selected state impossible to render half-way. Two changes, both small:

1. **Do not gate opacity on the layout lookup.** Move `opacity.value = 1` before the `if (!layout) return`, or better, derive the indicator's visibility from `width.value > 0` in `indicatorStyle` so it is a function of measured state rather than a flag someone must remember to set:

   ```ts
   const indicatorStyle = useAnimatedStyle(() => ({
     opacity: width.value > 0 ? 1 : 0,
     …
   ```

   This preserves the "no zero-width flash on first mount" behaviour the comment asks for, because width is still 0 until measured — but it removes the state where width is known and opacity is not.

2. **Tie `labelActive` to the same condition as the fill.** A white label is only legible over the indicator, so it should not be applied when the indicator is not shown. Failing gracefully to an *unhighlighted but legible* row is strictly better than an invisible one.

Optionally, as belt and braces: re-run `moveTo` when `layouts.current` has the active key but the indicator is unplaced — but that is a patch on the symptom, and (1) makes it unnecessary.

**Do not** fix it by giving the pill its own background colour. The file's comment explains why that was rejected (the fill would teleport while the indicator slides), and that reasoning is still right.

**Acceptance:** the Home net-worth pill row never renders with no pill filled while a range is selected; the active label is never white unless the fill is behind it; the first-mount behaviour is unchanged (no zero-width flash, no slide-in from the left edge); the account picker's `null`-keyed "All" chip still highlights on open; and tapping between ranges still slides rather than teleports. Add a test that the indicator is hidden before any layout is reported and shown once the active pill's layout arrives, and a render assertion that `labelActive` and the fill are applied under the same condition — the component has no tests today.

## Blast radius

One component — but it is shared by **six** surfaces, so the same failure is possible on all of them:

| consumer | row |
| --- | --- |
| `home-screen/components/account-charts-card.tsx:190` | net-worth / assets / liabilities ranges — **the one observed** |
| `reports-screen/reports-screen.tsx:151` | Reports ranges |
| `budget-screen/budget-screen.tsx:182` | Budget time spans |
| `components/balance-chart-card/index.tsx:88` | account drill-down balance ranges |
| `account-picker-screen/account-picker-screen.tsx:491` | the root-category chips (`scrollable`, `null` "All" key) |

The account-picker case deserves a second look during the fix: its default selection is the `null` "All" chip, so a user who sees no chip highlighted has no way to tell whether a filter is applied — arguably worse than a chart whose numbers still say which range they cover.

Not exercised: dark mode (where `theme.white` on a dark card would be *high* contrast, so the failure would likely look different and possibly invisible in the other direction), enlarged Dynamic Type, RTL — where the file's `left: 0` / `translateX` reasoning is load-bearing and worth re-reading alongside any change — and Android.

## Adjacent states

The component is otherwise carefully built and the note should not read as doubt about it: positions are measured with `onLayout` rather than assumed *because* "YTD"/"ALL" differ in width across the app's 13 locales; `revealSelected` scrolls an off-screen selection into view exactly once and no-ops when the pill already fits; `NULL_KEY` uses a NUL sentinel so a real key cannot collide; `moveTo` is called on press rather than waiting for `value` to round-trip; and the `left: 0` inset is documented as physical-not-logical with the RTL reasoning spelled out. The bug is one early return in an otherwise thorough file.

Verified working in the same pass, on both ledgers: tapping a pill changes the delta and redraws the curve (6M `+54.23%` → 3M `+33.78%` on `open_ledger/alphabet`), and the selection survives a ledger switch as *state* even when it fails to render.
