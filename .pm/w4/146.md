# Overview charts could pick their unit from the ledger's operating currency

Found while writing w4/m21/t006's tests, against the code at `73829285`.

`overview/lib/unit-amounts.ts`'s `chooseDisplayUnit` decides which unit an
overview chart is drawn in by reading the accounts: most accounts wins, ties
break on total magnitude, then alphabetically. That is truthful and stable, and
it gets every public fixture right — USD for the example ledger, MUSD for
Synopsys, EUR for Adyen.

It can still pick an odd unit on a thin ledger. With exactly one account on
each side, the count tier ties and magnitude decides, so a single large
retirement account denominated in `IRAUSD` beats a single smaller `USD`
account and the whole diagram is drawn in IRAUSD — with a correct note saying
USD is not included. Nothing is misstated, but the chart is less useful than it
could be. `overview/lib/__tests__/../cash-flow-sankey-units.test.tsx` documents
this in "follows the units the accounts use, not the largest number".

The ledger already declares a stronger signal. The net-worth and account cards
read the operating currency (that is how Adyen's cards show EUR), and
`buildAccountBalanceRows` takes a `preferredCurrency` for exactly this purpose.
Threading the same value into `chooseDisplayUnit` as a first tier — prefer the
declared operating currency when the accounts actually hold it, otherwise fall
back to today's account-count heuristic — would make the choice match what the
rest of the page already shows.

Scope: `chooseDisplayUnit`'s signature plus its three callers (the Sankey
transformer, `buildDistributionData`, the income/expenses bar chart), and the
`preferredCurrency`/`primaryCurrency` the overview page already has in hand.
Keep the existing tie-breaks as the fallback, and keep the disclosure note —
the point is a better first choice, not a different contract.

Not a correctness defect: no amount is misreported today, and every omitted
unit is disclosed. This is a quality-of-choice improvement.
