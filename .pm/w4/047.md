# Open Account green-lights a half-typed name, and Return creates the account it was normalized into

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: opening accounts is among the first things a newcomer does to a fresh ledger. Mid-way through typing `Investments:Brokerage` the form declares the name valid, and the keyboard's **Return** key creates an account — `Assets:Investments`, not what is on screen — with no confirmation and no undo on this screen.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`, today = 2026-09-13. Report-only QA; **no account was created** — `Done` was never tapped and **Return was never pressed** (see below for why that matters).

## Repro

1. Select `puncsky/example`, open `beancount:///(app)/open-account`. Root defaults to `Assets:`, the field is empty, `Done` is disabled. Correct.
2. Type `Investments:` — an ordinary intermediate state on the way to `Investments:Brokerage`.
3. **`Done` turns green.** No message. The name the form would submit is `Assets:Investments`.
4. `Bank::Checking` behaves the same way: `Done` green, no message, submits `Assets:Bank:Checking`.

**Control, and it works properly:** type `Bank:checking`. The form shows *"Each account component must start with an uppercase letter or a number."* in red with `accessibilityLiveRegion="polite"`, and `Done` returns to grey. The validation surface is real and correctly wired; the problem is upstream of it.

## Mechanism

`open-account-screen.tsx:230-231` validates the **composed** name, not the typed one:

```ts
const account = composeAccountName(rootPrefix, subPath);
const validation = validateAccountName(account);
```

and `composeAccountName` (`account-name.ts:23-33`) normalizes first — `split(":")`, `trim()`, `filter(Boolean)` — so empty and whitespace-only components are gone before the validator runs. `Investments:` becomes `Assets:Investments`, which is valid, so `canSubmit` is true.

**This normalization is deliberate, not an oversight.** `src/__tests__/open-account-name.test.ts:34-39` asserts it by name:

```ts
it("trims the entered components and collapses stray separators", () => {
  expect(composeAccountName("Assets", " :Bank:: Checking: ")).toBe("Assets:Bank:Checking");
```

Tolerating messy separators in a free-text field is a defensible choice, and this note does **not** argue it should be reverted. The defect is what the form then claims and what it lets happen.

## The two things that are wrong regardless

**1. The form asserts validity about a string the user cannot see.** There is no preview of the composed name anywhere on screen. The field reads `Investments:`; the account created reads `Assets:Investments`. A user who wanted `Assets:Investments:Brokerage` gets a stray parent account with no signal that anything was reinterpreted.

**2. Return submits, and it is one key away.** `onSubmitEditing={handleSubmit}` with `returnKeyType="done"` runs the create directly — no sheet, no confirmation — and `handleSubmit` gates only on `canSubmit`, which is the same over-permissive validation. So "type `Investments:`, reach for the next character, hit Return" writes to a real ledger. On a hardware keyboard Return sits beside the letters being typed. This screen offers no delete, so removing a stray `open` directive means going to the file editor.

The data that lands is not corrupt — `Assets:Investments` is a well-formed beancount account — which is why this is minor rather than major. And it is why the repro stops at step 4: every remaining step is a production write this run has no authorization for.

## A contradiction worth resolving in the same sitting

Because the composition strips exactly the components the validator would reject, **two of the five validation reasons cannot fire from the UI at all** — and `validateAccountName` has exactly one call site in the app.

| reason | message | reachable from the screen? |
| --- | --- | --- |
| `emptyComponent` | "Account components cannot be empty." | **no** — `filter(Boolean)` removed them |
| `invalidRoot` | "Choose a valid account type." | **no** — the root comes from a `Picker` over `ACCOUNT_ROOT_PREFIXES` |
| `tooFewComponents` | "Enter at least one account name component." | yes (empty field) |
| `componentMustStartUppercase` | "Each account component must start with an uppercase letter or a number." | yes — verified on device |
| `invalidCharacters` | "Use only letters, numbers, and hyphens in account names." | yes |

So the repository holds both positions at once: a test that says empty components should be silently collapsed, and a string — translated into all 13 locales — that says they should be reported. `invalidRoot` is different and fine: it guards `validateAccountName` as a library function against callers other than this screen, and should stay.

Pick one for `emptyComponent`: either reject it (and the string becomes reachable) or accept it (and the string should go, per `w4/046`'s sweep — note it is *not* currently on that list, because `VALIDATION_KEYS` references it as a literal, which is exactly the blind spot a key-usage detector cannot see through).

## Fix

The narrow fix addresses both problems without touching the normalization:

1. **Gate `canSubmit` on the typed string being complete**, not just on the normalized one validating. The minimum useful rule is that `subPath` must not end in a separator and must not be empty after the root:

   ```ts
   const typedIsComplete = subPath.trim().length > 0 && !subPath.trimEnd().endsWith(":");
   const canSubmit = validation.ok && typedIsComplete && !loading;
   ```

   That alone stops the mid-typing submit, which is the part with a write behind it.

2. **Show the composed name** under the field, the way `create-ledger-screen` shows "Will be created as …" — so when normalization does reinterpret the input, the user sees the result before committing. (That hint has its own defect, `w4/041`; don't copy it verbatim.)

Leave `autoCapitalize="words"` alone — it suits beancount components and it is *not* masking anything, since `Bank:checking` still fails (word-capitalization does not trigger after a colon; confirmed on device).

**Acceptance:** with `Investments:` in the field, `Done` is disabled and Return does nothing; `Investments:Brokerage` is accepted and creates `Assets:Investments:Brokerage`; the composed name is visible before submitting; `Bank:checking` still reports the uppercase rule; an empty field still reports "Enter at least one account name component."; the `composeAccountName` normalization tests still pass unchanged. Add a test over `canSubmit` for the trailing-separator and empty-component inputs **as the screen composes them** — the existing 20 cases test the validator on hand-written strings and the composer on its own, and nothing joins the two the way the screen does, which is why this went unnoticed.

## Blast radius

One screen, one boolean, plus an optional preview line. `composeAccountName` and `validateAccountName` have no other callers, so nothing else can regress, and the proposed fix changes neither. The account picker's **Create** prefill reaches this screen through `splitPrefillAccountName` and is unaffected — its own defect is `w4/010`.

Not exercised, deliberately: creating an account in any state, `Done`, and Return. Also not exercised: dark mode, enlarged Dynamic Type (the red message already wraps to two lines at the default size), Android, and non-Latin components (`Assets:日本:貯金`), which `startsSubcomponent` is explicitly written to allow but which this tooling cannot type.

## Adjacent states

The rest of the screen is **good**, and parts of it are better than they needed to be:

- `startsSubcomponent` (`account-name.ts:70-76`) accepts a caseless-script initial (Han, Kana, Arabic) as well as `\p{Lu}` and `\p{N}`, with a comment explaining that a plain uppercase-only test would reject names the Beancount grammar allows. The test file records this as a past fix ("the validator applied ASCII-only rules to every component"), so it is a deliberately maintained property.
- The validation message uses `accessibilityLiveRegion="polite"`, so it is announced rather than silently appearing; `Done` carries `accessibilityState={{ disabled, busy }}`.
- A cancelled create cleans up after itself — `useEffect(() => () => AccountCreated.deleteFn(), [])` — so a registration cannot leak into a later visit.
- On success the screen pops **only its own frame** before invoking the callback, with a comment noting the picker pops its own; no screen pops a frame it does not own.
- Currency defaults to the ledger's first operating currency and offers an explicit "no currency" option rather than forcing one.
