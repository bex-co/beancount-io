# Name valuation details and preserve keyboard access to its holdings

Severity: **minor**, dashboard accessibility. Estimate: **45–60 minutes** for both local omissions and focused regressions. A2 — readers should be able to identify the valuation explanation, navigate its holdings, and return to the report with the keyboard.

## Reproduce

Production `https://beancount.io`, 2026-10-08 America/Los_Angeles; QA-owned isolated headless Chromium, English, System theme. Authenticated reader of the public stock example; no ledger/account writes. Source rechecked after pulling main `408b2690`; production module `main-GcCTaQbi.js`, deployed commit unknown.

1. Fresh-load `/ledger/open_ledger/stock-example?time=2026-05` at 1440×1000 and wait for the financial-position card to settle.
2. Focus **At market value. Valuation details** and press Enter. Wait for the popover's opening animation to finish.
3. Chromium's native accessibility tree exposes an unignored `dialog` with `name: ""`. The content has `role="dialog"`, with neither `aria-label` nor `aria-labelledby`, despite its visible **Valuation details** title.
4. Escape closes it and returns focus to the correctly named trigger. Repeat from a fresh load at 390×1000: the same unnamed dialog appears; close/focus return still work, with no horizontal page overflow.

Expected: the dialog itself has the localized **Valuation details** name. [WAI-ARIA's dialog role](https://www.w3.org/TR/wai-aria-1.2/#dialog) requires an accessible name for nonmodal as well as modal dialogs. Naming the trigger does not name its dialog.

Actual: the title remains plain content, so assistive technology receives no programmatic window identity. The listed holdings and **Update prices** link are readable; this finding does not claim that price data is missing or keyboard access is broken.

Screenshots `valuation-name-1440.png` and `valuation-name-390.png` show the visible title; the narrow screenshot was inspected. No new browser exception occurred. This is a caller omission, independent of API results.

Associate that visible title with the PopoverContent using a stable unique ID and `aria-labelledby`, or use the existing localized title as its explicit name. Keep the trigger's separate label, per-holding prices/statuses, selected time/account filters, Update prices destination, responsive placement and Escape/focus return. Do not assign a global default name to every Popover or alter valuation calculations. NetWorthCard has one application caller, `features/reports/overview/index.tsx:274`; other ledgers reuse it but were not independently exercised for this defect.

Acceptance: settled valuation details is discoverable as a named dialog at both widths; a real-component role-and-name assertion fails when the association is removed. Preserve opening/closing/focus controls and existing price-state tests. No new translation, API, dependency or cross-package change is needed; run normal dashboard gates when implementing.

## Additional reproduced defect: holdings omitted from the Tab loop

Fresh production `/ledger/open_ledger/crypto-example?lang=en`, the same authenticated read-only headless Chromium **149.0.7827.55**, English/System, at **1440×1000 and 390×844**:

1. Wait for the overview to settle, focus the valuation trigger and press Enter. Initial focus is the popover's DIV. The actual list has **13 holdings**, with `clientHeight: 288`, `scrollHeight: 688`, no explicit tabindex and DOM `tabIndex: -1`.
2. Press **Tab**: Chromium focuses the UL. **End** scrolls it to **400**, making the final **WETH** holding visible. **Home** returns to **0**. This is a working keyboard-scroll control: the list can be reached initially.
3. Press **Tab** to **Update prices**. Press **Shift+Tab**, **Tab**, then **Shift+Tab** again. Each leaves the same link focused; none returns to the list. The reader must close and reopen the popover to regain that initial keyboard route to the holdings.
4. Escape still closes the popover and restores trigger focus. Both fresh widths repeat with no new console errors. A third fresh narrow load reproduces the link loop and supplies the inspected screenshot.

Independent `getLedgerBalanceSheet` Units control returns HTTP **200** and thirteen non-USD holdings, including WETH. This is a real overflowing public fixture, not substituted content or a scrollbar inferred from CSS. The failure concerns returning to the list after the link, not an inability to read or scroll it on the first visit.

Root: the UL at `dashboard/src/features/reports/overview/components/net-worth-card.tsx:151` relies on Chromium's implicit scroll-container focusability. The shared Popover forwards to Radix unchanged. Installed `@radix-ui/react-popover` **1.1.15**, `dist/index.mjs:225`, supplies `loop: true`; `@radix-ui/react-focus-scope` **1.1.7**, `dist/index.mjs:143–149`, gathers only nodes with `tabIndex >= 0`. Its first/last edge handling at lines 110–120 therefore sees the link as both edges and intercepts both directions to focus that same link. Native Tab can initially reach the UL from the DIV, but the library's loop excludes it. This installed-source mechanism agrees with the observed DOM and focus behavior; the deployed library version itself is unverified.

Give this overflowing holdings list explicit keyboard focusability so it participates in the existing focus loop, with a visible focus indicator. Keep the repair local to NetWorthValuationNote and combine it with the dialog naming repair above. Preserve native End/Home scrolling, list semantics and quantities, price statuses, Update prices navigation, selected filters and Escape/focus return. Do not disable looping globally, make every holding a button, or alter generic Popover/FocusScope behavior.

Extend acceptance with the real overflowing disclosure: keyboard entry reaches the list, End shows its last holding, Tab reaches Update prices, Shift+Tab returns to the list, and forward wrapping also includes it. Check both widths in a real browser with the actual Radix primitive; asserting a tabindex class/attribute alone does not prove the loop. Retain the named-dialog regression and the initial-scroll and Escape controls. Other engines and actual screen-reader speech remain unverified.
