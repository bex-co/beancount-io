# Honor a return to the current view during pending navigation

**Severity:** minor report selection. **Estimate:** 45–60 minutes. **Owner:** dashboard (`common/hooks/use-url-view.ts` and the equivalent Holdings selection owner). **A2:** URL-backed view preferences should retain the reader's latest choice, including a return to the currently rendered view before another choice finishes. Residual of [142](./done/142.md)'s view-preference contract, with the equivalent Holdings path from [W3/160](../w3/done/160.md); count one residual, not another historical finding group.

## Genuine pending-read reproduction

Production `https://beancount.io`, 2026-10-22, owned isolated anonymous Chromium 155.0.8059.85, English/light/UTC. Five fresh contexts: two desktop Holdings failures, one desktop Income Statement failure, one narrow Holdings failure and one narrow third-choice control. Each holds one genuine navigation GetCurrentUser response after HTTP200 completion, then returns its same 30 bytes unchanged. No query-result, clock, CPU or React-state fixture and no hosted write.

1. Open `/ledger/open_ledger/stock-example/holdings?lang=en&view=holdings` at 1440×1000. Wait for **Holdings**, seven rows and real hydration. Focus that tab and press ArrowRight to **Holdings by Account**. Wait until the next tab actually receives focus; hold the navigation read described above.
2. The address bar already reads `view=by-account`, but the still-rendered selected tab is **Holdings**, with seven rows. Press ArrowLeft and wait for actual focus back on **Holdings**. In the independent second desktop run, also press Enter to explicitly reaffirm that choice.
3. Release the unchanged successful response. Both runs settle on **Holdings by Account**, five rows and `view=by-account`, despite the newer return to Holdings. Focus remains on Holdings while a different tab is selected. Enter after settlement recovers the intended seven-row Holdings view normally.
4. At 390×844, choose By Account through the real **View** list, then reopen it while that read is held and explicitly choose **Holdings**. The trigger still displays Holdings during the pending route; after release it changes to **Holdings by Account** and five rows. The newer explicit choice was ignored. Selecting Holdings after settlement recovers seven rows and its URL.
5. A fresh desktop Income Statement at `?time=2016&lang=en` repeats **Net Profit → Income pending → ArrowLeft to Net Profit → Enter**. Release selects **Income**, with focus still on Net Profit; Enter after settlement restores Net Profit and the clean default URL, preserving Time 2016.

Working control: in another fresh narrow Holdings context, **Holdings → By Account pending → By Currency** is accepted. Its URL immediately becomes `view=by-currency`, and releasing the earlier response retains By Currency and its four rows. Returning to Holdings after settlement also works. Thus ordinary newer navigation supersedes the older one; the failure specifically concerns the choice equal to stale rendered selection. The genuine all-four-view/CSV controls in `holdings-all-view-native-export-complete-controls.json` also pass. No financial-data, API-result, generic request-ordering or universal rapid-tab failure is claimed.

## Cause and bounded repair

useUrlView derives `selected` from the resolved match's useSearch, then rejects `next === selected`. During the pending route, location.search already contains B while resolved selected remains A. A newer explicit A is incorrectly treated as a no-op. Holdings duplicates the same guard as `nextTab === selectedTab`. The controlled Radix Select also still considers A selected, so reselecting it can produce no value-change notification; desktop automatic focus uses that same stale selection. Simply changing the page's equality check does not cover the narrow case.

Keep the URL-backed view owner aware of the latest pending choice for this route, so its controlled selection and no-op decision agree with the current navigation intent. A later A must supersede pending B. Reuse the existing view/navigation contract and remove the duplicated stale-selection behavior in Holdings where appropriate; avoid a second preference store or a timer. Preserve validation, per-page defaults, Holdings' canonical view behavior, default-param omission in the shared hook, replace-history semantics, Back/reload, shared-filter retention and settled-data guards. Do not alter Radix globally or change request data/API behavior.

Acceptance: a real router lifecycle delays a genuine successful navigation read and drives **A → B pending → A**, including native desktop ArrowLeft/Enter and narrow explicit reselect. Final selection, URL and content must represent A after release. Preserve the passing **A → B → C** order, ordinary settled return, valid/invalid view handling, clean defaults and existing persistence/focus regressions. Check cancellation/failure settlement so an optimistic choice cannot remain stuck. Run dashboard gates when implementing. No product implementation or formal test was authored during QA.
