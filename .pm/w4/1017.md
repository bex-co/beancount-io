## Cause and bounded repair

`dashboard/src/features/journal/components/new-directive-dialog/transaction-form.tsx:543–544` and `balance-form.tsx:219–220` expose the exact string draft through native `type="number" step="any"` inputs. The shared `common/components/ui/input.tsx` forwards those attributes and field handlers unchanged. The native input event contains the changed string before the application processes it. `parseDecimalNumber` and BigInt inference then correctly normalize that already changed value; they are not the source of this loss. The browser's internal stepping algorithm was not traced.

Give these exact-decimal fields an entry/control policy that cannot silently round supported drafts. If increment/decrement controls remain, their changes must preserve the exact decimal and intended increment. Otherwise remove the unsupported step affordance and retain an appropriately labelled decimal text-entry surface. Merely formatting the changed value afterward cannot restore its digits. Do not restrict all amounts to safe integers, relax numeric/server validation, replace the correct decimal helpers with doubles or patch Chromium.

Preserve exact typed digits, supported exponent normalization, negative/fractional values, blank inference, account checks, pending guards, composition and failed-write recovery. Coordinate [1014](./done/1014.md)'s independent native-invalid shortcut gate: these stepped values remain **valid**, so a validity check alone does not address this issue. Receipt Review and Add Budget are the other two production `type="number"` amount callers; audit their validation before sharing a policy, but their native stepping was not independently exercised here. Avoid a global Input change that widens another form's accepted grammar.

Acceptance: native desktop/narrow amount editing never turns an increment into a reduction or precision loss. Transaction's prepared posting and inferred counterpart, and Balance's draft, retain the chosen exact-value contract. Keep the manual/ordinary controls, small quantities, negative values and retry behavior. Add meaningful control-boundary regressions that fail the old integration, plus native ArrowUp/ArrowDown checks; parser-only or jsdom change-event tests already pass the manual control and do not reproduce browser stepping. Run dashboard gates when implementing. QA authored no product fix or formal tests.
