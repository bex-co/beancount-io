## Cause and bounded repair

`dashboard/src/features/importer/utils/csv-validator.ts:222–252`: separatorVote receives the raw core from splitAmountSign. Its three-fractional-digit rule requires `^\d+,\d{3}$`; a grouping filler prevents that vote. With no other evidence, resolveDecimalConvention selects point decimals. normalizeBankAmount at257–285 subsequently removes THOUSAND_FILLER, sees `1234,567`, refuses that invalid comma-grouping shape and leaves the row invalid. Inference and parsing therefore see different representations of the same supported spelling. The same separatorVote also lacks the CLI's strong vote for a nonzero-led whole part with two or more valid dot groups (`1.234.567`); without that column evidence it treats the companion `1.250` as a point decimal.

Normalize the already-supported grouping fillers consistently before recognizing decimal-convention evidence, and recognize unambiguous two-or-more dot thousands groups using the current CLI's established rule. A valid whole-column dot-group vote must also interpret its single-dot companion correctly. Retain the original token for editing/diagnostics. Keep ambiguous `1,234` as grouping, genuine mixed-column refusals, exact-decimal/unsupported-precision checks, currency-symbol consistency and existing per-row convention propagation. Do not guess a convention separately for each row, loosen malformed grouping, add a dependency or change backend/API behavior.

The sole production resolveDecimalConvention caller is `hooks/use-csv-parser.ts:265–295`, which chooses the file's convention and passes it to buildParsedRow. Preview inline validation, `utils/row-edit-schema.ts`, `lib/import-config-draft.ts` and Configure consume that stored convention. Preserve their coherent behavior and exact normalized submission strings; this finding requires a dashboard inference repair only.
