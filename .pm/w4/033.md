# `/add-transaction-next` is two deep-link hops off every UI path, and nothing says whether that's intended

**Severity:** trivial — nothing is broken. **Estimate:** 10 minutes if the answer is "document it"; longer if the answer is "remove it". Owner: mobile. A2: an agent reading the QA journey table's **entry** row will go looking for the add/edit flow and can land on the wrong screen, or try to verify suggestion chips that no user can reach.

**This is a request for one comment or one decision, not a deletion.** The screen may be deliberate in-progress work; the problem is that the repository does not say.

Environment: branch `main`, HEAD `038faeeb`. Static reachability analysis; no device interaction.

## What the routing actually is

Three add-transaction routes are registered, all wrapped in `LedgerWriteGuard`:

| route | mounts | reached from |
| --- | --- | --- |
| `/add-transaction` | `MultiPostingsTransactionScreen` | Home `+` (`home-screen.tsx:127`), Transactions `+` (`transactions-screen.tsx:230`), receipt capture (`receipt-capture-screen.tsx:135`) |
| `/add-transaction-legacy` | `AddTransactionScreen` (keypad / quick-add) | **nothing** |
| `/add-transaction-next` | `AddTransactionNextScreen` | **only** `add-transaction-screen.tsx:212`, i.e. only from the screen above |

`add-transaction-legacy.tsx` is explicit and correct about its own status:

> *"Parked keypad flow, kept registered but off every UI path. Superseded by `/add-transaction`, which now renders the multi-posting screen. Reachable only via `beancount://add-transaction-legacy`."*

So `/add-transaction-next` is reachable only *through* a screen that documents itself as off every UI path — two deep-link hops from anywhere a user can go. **It carries no equivalent comment**, and its name reads as the intended successor rather than as parked work.

Reachability was checked by grepping every `router.navigate` / `router.push` / `router.replace` in `src/`; there is no computed or dynamic route string that could reach either screen, and the only inbound edge is the one `router.replace` above.

## What rides on it

`AddTransactionNextScreen` is the sole consumer of the payee/account suggestion engine. Splitting `src/common/suggestion-utils.ts` (380 lines, 33 test cases) by who uses it:

- **Live** — `multi-postings-transaction/payee-input-screen.tsx` imports exactly `twoPostingPayees` and the `JournalEntryLike` type.
- **Parked-only** — `deriveSuggestions`, `rankLlmSuggestions`, `splitAccountsBySide`, `classifyAccount`, `deriveTwoPostingSuggestions`, `buildLlmTransaction`, `MAX_SUGGESTIONS`, plus `SuggestionChips`, `QuickAddAccountsSelector`, `use-payee-account-suggestions` and `use-two-posting-suggestions`.

So most of that module, and its tests, protect behaviour no user can currently see. **The module is not dead** — do not delete it on the strength of this note; the live payee input depends on part of it.

## Why no gate catches it

`knip.jsonc:5` lists `app/**/*.{ts,tsx}` as entry points, which is correct — Expo Router loads route modules by filesystem convention, so a route file has no importer by design. The consequence is that an **unreachable route** is invisible to `lint:deadcode`, and everything it transitively pulls in looks used. Same blind-spot family as `w4/025`, different mechanism: that note is about unreferenced GraphQL documents, this is about unreferenced routes.

## Fix — pick one

1. **If `next` is in-progress:** give it the same comment `add-transaction-legacy.tsx` already has, naming what it is waiting on. One comment, and the ambiguity is gone.
2. **If `next` superseded nothing and is not going anywhere:** decide whether it and the parked-only half of the suggestion engine should go, and record that decision. Removing it would also remove 33 tests, so it is a real call, not cleanup.

Either way, note in `mobile/CLAUDE.md` or the route file which of the three is the live entry flow. Right now the only way to know is to grep three route files and follow a `router.replace`.

**Acceptance:** each of the three add-transaction routes states its status in a comment, and the live one is identifiable without tracing navigation calls.

## Blast radius

Documentation or deletion only; no behaviour change in either direction.

**Now exercised, and the answer sharpens this note: it does not work when deep-linked.** `w4/034` (filed straight after this one) records a hard render crash — `Cannot read property 'split' of undefined` at `add-transaction-next-screen.tsx:255` — because the screen dereferences a route param that only its parked predecessor supplies. So the screen is not merely unreachable; entering it the one way that *is* possible fails immediately. If the decision below is "remove it", `w4/034` is moot; if it is "promote it", `w4/034` must be fixed first.

Still not exercised: its suggestion behaviour, which would mean composing a transaction on a production ledger — this run has no write authorization.

## Adjacent states

`suggestion-utils.ts` was read in the same pass and the parts I could follow are sound: `dedupeAccounts` preserves first-seen order; `rankByFrequency` relies on `Array.sort` stability for ties, which holds on Hermes (ES2019+); and `extractTwoPostingPair` derives direction from the **sign** of each posting, so it handles an income transaction (`Income:Salary` negative → from, `Assets:Checking` positive → to) as naturally as an expense.

A concern I formed and then disproved, worth recording so nobody re-raises it: `classifyAccount` splits on the account root, which looked like it would break for non-English ledgers. It does not — `add-transaction-next-screen.tsx:130-139` builds the prefixes from the **ledger's own options** (`name_assets`, `name_liabilities`, `name_expenses`), so localized roots work correctly.

One real asymmetry in that same code, left unfiled because it only affects the unreachable screen: `toPrefixes` is built from `name_expenses` alone, with **no `name_income`**. So on that screen an income transaction's `Income:` leg classifies as neither side and is dropped, even though `extractTwoPostingPair` handles it correctly one function away. If `next` is ever promoted, that is the first thing to check.
