# The "Copied" toast never appears, though the copy itself works — every toast in the app is suspect

**Severity:** minor. **Estimate:** 30–45 minutes, most of it confirming the mechanism. Owner: mobile. A2: toasts are the app's only confirmation for several actions, so a user who taps **Copy** gets no feedback at all and cannot tell whether anything happened — the clipboard is the only evidence, and it is invisible.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`. Report-only QA; no ledger mutation — the only side effect was writing the app's own referral URL to the simulator pasteboard.

## Repro, with a control that proves the handler ran

1. Fire `beancount:///(app)/referral`. **Dismiss the development LogBox banner** — it covers the bottom of this screen (see Adjacent states).
2. Set the pasteboard to a sentinel: `xcrun simctl pbcopy <udid>` with `CLEARED`.
3. Tap **Copy** next to the referral link.
4. Screenshot immediately, repeatedly.
5. Read the pasteboard back: `xcrun simctl pbpaste <udid>`.

**The clipboard is correct** — `https://beancount.io/auth/sign-up?src=ios&by=<24-char account id>`, 69 characters, matching `buildReferralUrl(Platform.OS, userId)` exactly. So the sentinel was replaced and execution reached past `await Clipboard.setStringAsync(shareLink)`.

**No toast renders.** `referral-screen.tsx:107-114` calls `toast.showToast({ message: t("copied"), type: "text" })` on the very next line, and `toast-provider/index.tsx:86-88` holds a message for `message.duration || 2000` ms behind a 300 ms `FadeIn`. Five samples across two app sessions, taken inside that 2.3 s window, show nothing.

**This resolves a question left open twice earlier in this QA run.** On previous screens a missing confirmation toast could not be separated from a tap that simply missed its `Pressable`. The pasteboard is the control that separates them: the handler runs, and the toast does not appear.

## Cause — narrowed, not confirmed

Stated plainly because the remaining candidate is untested. Eliminated by experiment:

| Candidate | Ruled out by |
| --- | --- |
| Tap missed the control | Pasteboard sentinel replaced with the correct URL |
| Toast expired before capture | Frames sampled from ~1 s after tap, inside the 2000 ms + 300 ms window; three consecutive frames were byte-identical |
| Runtime degraded by this session's earlier worklet errors (`w3/191`) | Reproduces identically after terminate + relaunch |
| `ToastProvider` not mounted | `app/_layout.tsx:7-10` wraps `<Slot />` in `Providers`, and `providers.tsx:22` mounts `ToastProvider` above it, so every route is inside it |
| Toast layer has no layout box | `SplashProvider` renders `<View style={{flex: 1}}>` (`splash-provider.tsx:38-39,161`), and the toast layer is `position: "absolute"` with all four insets `0` inside it, so it should fill the screen and centre its pill |

**Reanimated `FadeIn` was this note's first hypothesis and it is now RULED OUT.** The pill is wrapped in `<Animated.View entering={FadeIn.duration(300)}>` (`toast-provider/index.tsx:60-64`), and a failing entering animation would leave it present-but-invisible. But `FadeInView` (`src/components/crossfade/index.tsx:36-44`) uses the **identical** `Animated.View entering={FadeIn.duration(...)}` from the same package, and it wraps the loaded branch on ~24 screens — Notifications, Accounts, Transactions, Merchants, the file browser, the file editor and the commit detail among them — every one of which was watched rendering its content during this run. Reanimated entering animations work in this app.

**Where the evidence now points: the toast is probably never *called*, not rendered invisibly.** A second call site reproduces it, on a different screen, through different code:

- Drawer → `•••` on a ledger row → **Copy link** (`ledger-drawer.tsx:571-577`). Clipboard receives `https://beancount.io/ledger/open_ledger/alphabet`; two frames show no toast.
- That handler runs `onClose()` **synchronously before** the copy, and **the drawer visibly closed** — so the synchronous half of the handler definitely executed and only the continuation produced nothing.

Both paths funnel through a promise continuation: `referral-screen.tsx` does `await Clipboard.setStringAsync(...)` then `showToast`, and `ledger-url-actions.ts:9-11` does `Clipboard.setStringAsync(url).then(onCopied)`. In both, the pasteboard is written (the native side ran) while the code after the promise shows no effect. **The first thing to check is therefore whether `Clipboard.setStringAsync` settles at all** — log or instrument the continuation, rather than assuming it runs. If it does settle, the investigation moves back to the provider.

Two objections worth foreclosing: the LogBox banner cannot be hiding this, because the toast layer is a full-screen absolute view with `justifyContent: "center"` (`toast-provider/index.tsx:109-120`) so the pill renders **centred**, not at the bottom where the banner sits; and the layer is the last child of the context provider, so it is not behind `{children}`.

## A second, independent defect in the same file

`toast-provider/index.tsx:31-41`:

```ts
const ToastContext = createContext<ToastContextType>({
  showToast: () => () => {},           // non-null default; showToast is a no-op
});

export const useToast = () => {
  const context = useContext(ToastContext);
  if (!context) {                       // can never be true
    throw new Error("useToast must be used within a ToastProvider");
  }
  return context;
};
```

Because the context default is a non-null object, `useContext` never returns a falsy value, so the guard is dead code. A component rendered outside `ToastProvider` does not get the intended error — it silently receives a `showToast` that does nothing.

That is **not** the cause of the defect above (the provider is mounted), but it is the same failure *shape*, it lives in the same file, and it is why a future regression of this kind would also be silent. Fix it in the same sitting: default the context to `null`, type it `ToastContextType | null`, and keep the throw — which then actually fires.

## Fix

1. **Establish whether `showToast` is reached**, by instrumenting the continuation on either copy path. That single answer splits the work: if it is never reached, the defect is in the clipboard promise and both copy call sites need restructuring; if it is reached, the defect is in the provider's rendering and the investigation continues there. Do not change anything before this is known — the first hypothesis this note carried was wrong, and guessing twice is worse than measuring once.
2. Fix whichever half it turns out to be. Do not "fix" it by lengthening the duration; a toast that never appears shown for longer still never appears.
3. Repair the dead `useToast` guard as above.
4. Give the toast pill a `testID` so this is verifiable from automation at all. It currently has none, so `automation_find_view` cannot confirm presence or absence — this note rests on screenshots alone, which is exactly the gap `w4/020` describes. That is also why step 1 needs instrumentation rather than another QA pass.

**Acceptance:** tapping **Copy** on the referral screen shows the "Copied" pill for ~2 s on a fresh launch; `automation_find_view` resolves the pill by `testID` while it is up and reports it absent afterwards; a component rendered outside `ToastProvider` throws rather than silently no-opping. Add coverage that `showToast` inserts a message, that it is removed after its duration, and that the default context throws — noting that `toast-provider/__tests__/index.test.ts` is one of the nine files in `w4/026` that never import the module they name, so the existing 21 cases there prove nothing about this.

## Blast radius

Reproduced a **third** time later in this run, in a third app session: referral **Copy**, six consecutive frames, all byte-identical at 124,161 bytes, with the pasteboard again holding the correct 69-character URL. Nothing about the sampling or the session state changes the result (`w4l87-copy-1..6.jpg`).

Every toast in the app, not just this one — the provider is global. Reproduced on **two** independent copy actions (referral **Copy**, and the drawer's ledger **Copy link**), which are the confirmations whose side effect is externally observable; the remaining toasts (ledger writes, file saves, discovery errors) need write authorization or an induced failure to trigger and were not exercised. **No toast was observed rendering anywhere during this QA run**, which is consistent with a global failure but is not the same as having tested every path. Not exercised: dark mode, enlarged Dynamic Type, Android, VoiceOver announcement of the toast, and whether a `type` other than `"text"` (which renders an icon) behaves differently.

## Adjacent states

The rest of the referral journey is **correct** and was verified in the same pass: `buildReferralUrl` (`src/common/referral-url.ts`) pins the hosted sign-up URL deliberately and documents why it does not go through `getEndpoint()`; the copied link carries `src=ios` from `Platform.OS` and an opaque 24-character account identifier — **not an email or any personal data**; and `app/(app)/_layout.tsx:43-45` redirects to `/auth/welcome` when there is no session, so `useSession()`'s unconditional throw in `ReferralScreen` is unreachable from a signed-out state. (That guard is also the asymmetry `w4/021` reports from the other side: `(app)` is session-gated, `auth/welcome` is not.)

The link preview is `<Text numberOfLines={1}>` (`referral-screen.tsx:101`), so it always reads `https://beancount.io/auth/sign-u…` and no user can see their own referral code. Deliberately **not filed**: Copy and Share both carry the full URL, so it is a one-line preview rather than a defect, and I could not establish that showing the code was intended.

**The LogBox banner covers the bottom of this screen**, including the `Share` button — the same dev-chrome occlusion that hid the Filters sheet's `Apply` button earlier in this run. Not a product issue; recorded so the next agent dismisses it before concluding a control is missing.

## Blocked

**Blocked 2026-09-14 by `/loop-worker w4` after a partial on-device investigation; no code change was shipped.** The note says not to change anything until one question is answered: is `showToast` reached? That measurement could not be completed reliably here. The note's two code-hygiene items (the dead `useToast` guard and a toast `testID`) are not the reported defect, and wait with it.

**Measured** (iPhone 17 Pro simulator, JS served from Metro, a temporary probe that was never committed):
- **The toast layer renders.** A probe calling `showToast({ message: "TOAST PROBE", duration: 15000 })` from `ToastProvider` shortly after mount showed the centred pill over the Welcome screen at about 20 s, and it was gone by 30 s. That rules out the provider's rendering and layer placement: its position in `providers.tsx` and its `Animated.View` `FadeIn`.
- **A clipboard probe was inconclusive.** A probe calling `Clipboard.setStringAsync("toast probe").then(showToast…, showToast…)` showed neither its resolved nor its rejected toast, and the simulator pasteboard still read the sentinel after 20 s. But a follow-up that added a toast immediately *before* the call showed nothing either, and Metro reported no rebuild for it. So these runs cannot tell a hanging `setStringAsync` apart from a bundle that did not reload.

**Not done.** Tapping Copy on the referral screen or the drawer's Copy link in an instrumented build: the simulator session was signed out, and signing in was not attempted.

**Unblock with** an instrumented run whose bundle is confirmed current: for example, a marker toast visible on launch plus the clipboard probe, or the Copy button on a signed-in dev build with the debugger attached. If `setStringAsync` never settles, restructure both copy call sites (`referral-screen.tsx`, `ledger-url-actions.ts`) so the confirmation does not wait on it. If it does settle, the rendering half is already cleared, so look at the calling screens' toast context. Then move this back to `.pm/w4/029.md`.
