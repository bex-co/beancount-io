# Verify and repair redundant login history after a protected client query is rejected

Candidate severity: minor navigation friction; native-toolbar impact unverified. Estimate: 55m, dashboard. A2: a visitor who declines to sign in should be able to return to the public ledger they were browsing.

Environment: production https://beancount.io, signed out, isolated headless Chromium149.0.7827.55, English/light, fresh1440×1000 and390×844. Local/fetched main26d54a9db7d33c31a549bd12a0454a1c01f3f038; deployed main-BIr0jJni.js, exact deployed SHA unverified.

Reproduction: open `/ledger/open_ledger/example/query?query=SELECT%20date%20LIMIT%202`, wait for the two-row result, and click the Related Pages Import link. It reaches `/auth/login?next=%2Fledger%2Fopen_ledger%2Fexample%2Fimport`. Invoke Playwright page.goBack() once. The browser revisits Import, repeats the protected read, and returns to the same login page rather than the original public query. Fresh desktop and narrow repeats agree; the initial stock-example query also reproduces. Recorded history remains public Query → Import → Login. This is a Back-triggered redirect cycle, not an autonomous page reload loop.

Producer/control: Import mounts AiCfoUpgradePanel, which calls useAiCfoUsage. Real GetAiCfoUsage returns HTTP200 with `UNAUTHENTICATED`, message “Access denied! Please login to continue!”, data null. Backend-v2 `features/feature-usage/api/ai-cfo-usage-resolver.ts:20` deliberately marks aiCfoUsage authenticated. Preserve that policy. No file input is reached, no file was uploaded, and no import or authentication mutation was attempted. Direct header Log In / Sign Up → automated history traversal is a passing control, restoring the public bookmarked query and its two rows.

Cause: `dashboard/src/common/apollo/links/auth-error-link.ts:81–90` handles the expected denial with `window.location.assign(...)`. This adds a history entry after the rejected client route. A new document resets the module-level redirecting flag, so revisiting that route starts the same redirect again. The full-page navigation is intentional to clear Apollo/React state; changing its history behavior can preserve that reset. The original assign behavior survives af5339de, the optional-identity correction2f982c52 and first-time guest copy correction1f5ed3af. Existing auth-error-link tests cover operation eligibility and the URL string, not actual navigation history.

Bounded repair: replace the rejected route's history entry during this automatic auth redirect while preserving its intended next target, full-page state reset, optional-identity/auth-flow exclusions and safe continuation policy. Do not enable anonymous usage reads, disable authentication, attach a false expired-session reason, or change every ordinary user-initiated login navigation. Other protected client operations share the link; Import and Version History were live-reproduced; other entry points remain source-traced.

Acceptance: fresh desktop/narrow Query → Import → Login → one automated history traversal restores the original public query URL and results without another Import usage request or return to login. Files → Version History → Login → Back likewise restores Files. The login URL still carries the intended Import or Commits continuation. Test the real link's navigation/history behavior and preserve concurrent-error deduplication, optional identity probes, expected auth-flow failures and non-auth errors. Run dashboard native gates. Authenticated completion, actually expired sessions, other engines and patched behavior remain unverified.

Dedupe: all .pm including done/blocked searched for auth-error-link, assign/replace, login history and Back loops. Completed w3/104 covers missing Star/Follow continuations (and their passing Back behavior); completed w3/170 covers unsafe-next normalization. w4/m19 owns fragment serialization, not history insertion. w4/093 and m17 affect different public navigation state. No matching active repair found.

**Blocked 2026-09-17** — The automated history traversal is reproducible, but it does not yet establish the claimed native-toolbar navigation trap. Chromium can skip redirect-created entries for toolbar navigation while raw history traversal revisits them. A delayed local A → B → C redirect calibration confirmed a marked-skippable B entry; CDP side-button input and an isolated headless extension tabs.goBack() both revisited B and returned to C. Neither harness established toolbar equivalence. Do not implement the proposed repair solely on this evidence. **Unblock:** reproduce the production Query → Import → Login sequence using actual browser toolbar Back in an isolated headed browser, recording whether the first and subsequent Back actions restore Query, and compare against direct header login. A repository QA worker with that browser harness can clear this blocker; credentials are not required. No repair has shipped.
