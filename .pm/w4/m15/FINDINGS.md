# Authentication validation errors lack field associations

Severity: minor accessibility defect. Dashboard. Scheduling: 70m implementation plus 70m closing work in this milestone. A2: a keyboard or assistive-technology user should be able to identify and correct a rejected sign-in field. Source: repeated dashboard QA, 2026-09-17.

Environment: production https://beancount.io, signed out; QA-owned isolated headless Chromium 149.0.7827.55, English, browser-emulated dark appearance. Desktop 1440×1000 and fresh 390×844 reload. Local main `26d54a9db7d33c31a549bd12a0454a1c01f3f038`; deployed main-BIr0jJni.js, exact deployed commit unverified. No credentials were entered and no SignIn request was sent.

Repro: open `/auth/login`, leave both inputs empty, and activate Sign In. “Email is required” and “Password is required” appear, and focus moves to Email address. However, both inputs still have no `aria-invalid` and no `aria-describedby`; the error paragraphs have no IDs, alert role or live-region semantics. Chromium's native accessibility tree has no error description on either textbox. Reload at 390×844 and repeat: identical.

Expected: each invalid input exposes its invalid state and the matching visible validation error as an accessible description, with an appropriate announcement when validation changes. Actual: the required error is separate static text, so focusing the field does not expose its explanation or invalid state. This records browser metadata, not an actual screen-reader speech session. Visual messages and submit blocking work correctly.

Working control: follow Sign Up, replace the generated Username with `qa invalid name`, and blur it without submitting. That field exposes `aria-invalid="true"`, `aria-describedby="username-hint username-error"`, and an error paragraph with `id="username-error" role="alert"`. No account was created or email sent. The sign-in fields themselves have correct labels; the defect is their validation state/error association.

Root: `dashboard/src/features/auth/components/login-form/index.tsx:70–80` and `:89–95` register the email and password inputs without accessibility error props. Error paragraphs at `:81–83` and `:120–122` render only text/classes. The form explicitly disables native validation and uses react-hook-form/Zod, so browser constraint validation does not supply a replacement description. PasswordInput forwards standard input props at `password-input/index.tsx:30–34`; it needs no fork to accept the missing attributes. Registration's username implementation at `register-form/index.tsx:171–184` already provides a repository-local pattern.

Fix: give each login error a stable, collision-safe ID, associate it with its input only while present, expose invalid state, and announce validation changes without duplicate messages. Preserve initial clean state, on-blur/submit timing, first-invalid-field focus, correction recovery, password visibility, server-error alert, loading/submit blocking and continuation links. Add meaningful rendered tests for empty submit, invalid email, correction and password failure, asserting actual message associations rather than only visible strings. Run dashboard's normal gates. Do not change authentication validation or add dependencies.

Blast radius: LoginForm has four production consumers: login-page, OAuth consent, mobile-consent, and identity-consent. The three consent wrappers are source-traced, not exercised live here. Other authentication forms except recovery and registration verified below, authenticated/session-expiry behavior, real credential submission, other engines/locales and actual screen-reader announcements remain unverified. The local empty-form path makes no network request and does not depend on API failure classification.

Dedupe: searched all `.pm` including done/blocked for login/auth validation, aria-describedby, field-error association and invalid-state announcements. Existing native accessibility work is a separate implementation; completed login continuation fixes concern navigation. No overlapping open item. `git log -S 'errors.email'` traces this markup to `af5339de`; subsequent login-form commits change consent/continuation behavior, with no later error-association repair on current main.

Verified ignored evidence: `dashboard/tmp/qa-20260917/login-validation.json` records desktop/fresh narrow input attributes, Chromium textbox metadata, and the registration control; `login-validation.png` is the visually inspected narrow empty-form screenshot. No product fix, production mutation, commit or push.
