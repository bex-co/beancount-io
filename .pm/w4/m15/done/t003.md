Completed 2026-09-19. All three public authentication forms were exercised live against a local production build of the current HEAD, signed out, with no credentials entered: 38 checks in fresh isolated headless Chromium contexts at 1440x1000 and 390x844, all passing.

Each form's association was read the way assistive technology resolves it — following `aria-describedby` to the element it names and reading that element's role and text — rather than checking that a string is visible somewhere.

- **Sign in:** clean before submission. After an empty Sign In, email reads `aria-invalid="true"` with `aria-describedby="email-error"` resolving to a `role="alert"` paragraph reading "Email is required", and password likewise resolves to "Password is required". Focus lands on email, the first invalid field. Correcting the address clears both attributes with no stale association. Forgot Password? and Sign Up remain reachable.
- **Recovery:** focusing the empty field and tabbing away exposes `aria-invalid="true"` and a `role="alert"` description reading "Please enter a valid email address". Send reset link stays disabled, correction clears the association, and Back to Sign in is present with the encoded `next` destination intact.
- **Registration:** Username points at its persistent `username-hint` before submission. After an empty Create account, email, password and confirmation each read `aria-invalid="true"` with descriptions resolving to "Email is required", "Password is required" and "Please confirm your password"; Username still points at its hint, so the public-name guidance is not replaced by an error. Correction clears the association.
