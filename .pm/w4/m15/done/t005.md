## Implementation and verification

Completed 2026-09-19. Added `dashboard/src/features/auth/components/__tests__/field-error-association.test.tsx`, 13 cases rendering the three real form components with their real Zod resolvers.

The suite resolves associations the way assistive technology does rather than asserting a string is visible somewhere, which is exactly what let this defect ship: a shared helper follows `aria-describedby` to the elements it names, requires every referenced id to resolve so a dangling reference cannot pass, requires one of them to carry `role="alert"`, and matches the resolved text. A second helper asserts the absence of both attributes for clean and corrected states.

Coverage per the milestone: initial clean state with no invalid attributes and no alert; empty Sign In submit associating both fields without invoking the submit handler; an invalid email resolving to its own distinct message rather than the required one; correction clearing the association while the still-empty password keeps its own; attribute forwarding through `PasswordInput` reaching the real `input`; and the visibility toggle still switching the field to text while the error stands. Recovery covers on-blur association and stale-message clearing, both asserting the `SendForgotPasswordLink` mutation is never called. Registration covers all three empty-submit associations without invoking submit, Username's persistent hint surviving a failed submit with every referenced id resolving, a mismatched confirmation, the optional name fields when a length rule trips, and correction clearing.

Proved real rather than assumed: restoring the three components to their pre-repair state (`524bc682~1`) fails 12 of the 13 cases — the survivor is the clean-initial-state case, which passes either way by construction. Restoring the repair passes all 13.

The suite resolves `t` to the message key, so assertions name keys such as `emailInvalid` and `confirmPasswordRequired`. That distinguishes required from invalid per field and stays robust to copy changes, which is what these tests are about; the user-visible English text was verified live in t003 instead.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn build` and `yarn test` all pass — 376 files and 4,236 tests, up from 375 and 4,223, with the one pre-existing skip. gitleaks reports no leaks in the changed tree.

Treated honestly: no real credential, recovery email or account creation is involved anywhere. Desktop and narrow browser accessibility metadata was captured in t003 rather than here, and this suite makes no browser claim. Actual screen-reader speech remains unverified, and the reset-token and OTP forms stay out of scope, recorded in [140](../../140.md).
