## Objective

Expose invalid states and current error descriptions in LoginForm and ForgotPasswordForm without changing validation or requests.

## Context

See [FINDINGS.md](./FINDINGS.md) and the milestone DoD. This schedules dashboard work; it does not authorize real credential submissions, recovery emails or account creation.

## Steps

Read FINDINGS.md. Give each error a stable collision-safe ID; associate it conditionally with its field, preserve hints, and announce changes without duplicate messages. Keep initial clean state, first-invalid focus, onTouched/submit timing, recovery disabled state and continuation callbacks.

## Files

dashboard/src/features/auth/components/login-form/index.tsx; dashboard/src/features/auth/components/forgot-password-form/index.tsx; shared PasswordInput only if its existing forwarding needs adjustment

## Acceptance criteria

- [x] Empty login submit and empty recovery blur expose their exact messages through the field and invalid state; correction removes stale associations; no auth mutation occurs.

## Out of scope

Authentication policy/schema changes, reset-token workflows, new dependencies, production mutations and unrelated form redesign.

## Implementation and verification

Completed 2026-09-19. Both forms now expose invalid state and an accessible description that resolves to the visible validation error, following the pattern registration's Username already established at `register-form/index.tsx:171-180` rather than inventing a second one.

`login-form/index.tsx` gives the email and password inputs `aria-invalid` and an `aria-describedby` that points at the matching error only while that error exists, and their paragraphs now carry `id="email-error"` / `id="password-error"` with `role="alert"` so a change in validation is announced once. `forgot-password-form/index.tsx` gets the same treatment with `id="forgot-password-email-error"`, matching its existing `forgot-password-email` input id.

Error ids are stable and collision-safe in practice: the inputs already use fixed ids that the labels reference, and the OAuth, mobile and identity consent wrappers render LoginForm and RegisterForm as separate steps, so the two never mount together. `PasswordInput` needed no change — it spreads `...props` onto the underlying Input at `password-input/index.tsx:30-34`, so the new attributes forward unmodified.

Verified by rendering both real components: on an empty Sign In submit, the email and password inputs both read `aria-invalid="true"`, each `aria-describedby` resolves to a `role="alert"` paragraph carrying the actual current message, and the submit handler is never invoked, so no authentication mutation occurs. Typing a valid address and blurring clears both `aria-invalid` and `aria-describedby`, leaving no stale association. On the recovery form, focusing the empty email and tabbing away exposes the invalid state and its description without sending a reset link. That scaffolding was removed after confirming the behaviour; the durable suite belongs to t005, which owns the rendered coverage.

Validation rules, onBlur/onTouched timing, first-invalid focus, password visibility, the server-error alert, the recovery form's disabled-until-valid button and every continuation link are untouched. No dependency was added and no form abstraction introduced.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn build` and `yarn test` all pass at 375 files and 4,223 tests with the one pre-existing skip. gitleaks reports no leaks in the changed tree. Actual screen-reader speech and the three consent wrappers' runtime flows remain unverified, as FINDINGS records.
