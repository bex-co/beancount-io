# m7 follow-up: picker options can't be tapped and expose no selected state

Severity: **major** residual failure in completed **w4/m7** ("Screen-reader pass on the mobile core journeys"); retain that existing finding group rather than counting this as unrelated discovery. **Estimate:** 45–60 minutes; promote to a milestone if adding the scroll-to-index animation and its tests exceeds an hour. Owner: mobile. A3: m7's definition of done states a screen-reader user "changes the theme … without visual interaction", and that is not achievable on the shipped control.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`, public `open_ledger/alphabet`. Report-only QA; no preference was changed — every picker was dismissed with Cancel.

## Repro

### A — tapping an option does nothing

1. Terminate and relaunch the app. Drawer (hamburger) → **Settings** → **Theme**. The sheet shows `Light` / `Dark` / `System` with **System** selected (green, enlarged, in the indicator band).
2. Tap `Dark` at its inspected bounds. `automation_tap {"testID":"picker-item-dark"}` returns `{"tapped":true,"success":true}` and `automation_find_view` reports that row `is_hittable: true`, frame `{x:0,y:610,w:390,h:50}`.
3. The selection does not move. **System** is still the highlighted option.
4. Same on the Language picker: six taps on the `中文` row by coordinate, then one by `testID`, all reported as successful taps; `English` stayed selected through all seven.

Only dragging the wheel changes the selection. The sheet renders as three stacked, tappable-looking rows, so the first interaction most users try is inert.

### B — no selected state or label on the option rows

`automation_find_view` on the theme picker, with **System** visibly selected:

| testID | `label` | `is_selected` | `is_hittable` |
| --- | --- | --- | --- |
| `picker-item-light` | `''` | `false` | `true` |
| `picker-item-dark` | `''` | `false` | `true` |
| `picker-item-system` | `''` | `false` | `true` |

The language picker reports the same for `picker-item-en` (visibly selected), `picker-item-zh` and `picker-item-bg`. No row distinguishes itself as selected in the accessibility tree; selection is carried only by font size and color.

**Working control:** the trigger row is correct — `automation_find_view {"testID":"setting-theme"}` returns `label: "Theme, System"`, `element_type: 9` (button). That is exactly what m7/t004 shipped ("label theme and language pickers with their current value"), and it labelled the row that *opens* the picker, not the options inside it.

## Root cause

`mobile/src/components/picker/index.tsx`, `renderItem`: each option is a plain `<View testID={...} style={styles.wheelItem}>` wrapping an `<Text>`. There is no `Pressable`/`onPress`, no `accessibilityRole`, and no `accessibilityState={{ selected }}`. Selection is derived exclusively from scroll offset — `scrollHandler` → `wheelIndexAtOffset` → `setPendingIndex`, and `handleDone` re-reads `wheelIndexAtOffset(scrollY.value, …)`. A tap changes no offset, so it changes nothing.

The component's own `src/components/picker/README.md` claims under Technical Details: "**Accessibility**: Proper touch targets and keyboard navigation support". Neither holds — the rows are not touch targets at all and there is no key handling. That line is what a reviewer would have trusted.

## Fix

In `renderItem`, wrap each option in a `Pressable` that scrolls the wheel to that index (reuse the existing `wheel-position` module for the offset, so tap and drag land on one code path and `handleDone` keeps reading a single source of truth). Add `accessibilityRole="button"` and `accessibilityState={{ selected: index === pendingIndex }}` so the current choice is announced. Keep the confirm-on-`Confirm` model — a tap should move the selection, not dismiss the sheet, so Cancel still means cancel.

Do not "fix" this by making a tap call `onSelect` directly: that would bypass `handleDone` and re-introduce the class of bug `7538fb0d` fixed (an untouched picker confirming the wrong option). Do not remove the wheel; dragging must keep working unchanged. Correct or delete the README's accessibility claim in the same change.

**Acceptance:** on a fresh iPhone 17e launch, Settings → Theme → tapping `Dark` moves the highlight to Dark without dismissing the sheet, `Confirm` then applies Dark, and `Cancel` leaves the previous value; the same holds for Language, Open Account root/currency and Add Budget interval/currency, which share this picker. `automation_find_view` reports `is_selected: true` for exactly the highlighted row. m7/t008's outstanding checklist item — "picker value labels are covered by a test that asserts the rendered accessibility props" — is satisfied for the option rows, not just the trigger: add tests for the selected row's `accessibilityState`, the unselected rows', and that a tap updates the pending index without calling `onSelect`.

## Blast radius

One shared component, four known callers: Settings language and theme, Open Account root/currency, Add Budget interval/currency (the same set `7538fb0d` names). Reproduced natively on the theme and language pickers. Not independently reproduced: Open Account and Add Budget (both need an owned ledger and, for Add Budget, write scope), dark mode, enlarged Dynamic Type, and Android.

## Adjacent states

`Cancel` correctly discards (verified: selecting nothing and cancelling leaves Theme at System, Language at English). The trigger rows announce their current value correctly. An option scrolled out of the 5-item window reports `is_hittable: false` (`picker-item-fa`, frame y 960) — expected for a wheel, but it means a tap-to-select fix must still rely on scrolling for distant options, which is why the fix scrolls rather than selecting in place.

**Unverified:** this was inspected through the accessibility tree, not with VoiceOver running. The inner `Text` nodes remain their own accessibility elements, so a VoiceOver user would likely still *hear* "Light", "Dark", "System" — what is missing is which one is current and any way to activate one. m7's closeout already records that an end-to-end VoiceOver journey was not captured; confirming the speech output on a device is the remaining step.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for picker, `picker-item`, wheel, and selected-state terms. `w4/done/m7/done/t004.md` covers labelling the picker **trigger** with its current value — shipped and still working, and it is the reason this is filed as an m7 residual rather than new discovery. `w4/done/m7/done/t008.md` left "picker value labels … covered by a test that asserts the rendered accessibility props" as its own checklist line, which this closes for the option rows. `git log -- mobile/src/components/picker/` shows `7538fb0d`, which fixed a **different** picker defect (w3/101: `handleDone` read an unseeded `scrollY`, so an untouched picker confirmed the first option) — that fix is on `main` and is not this. No open item overlaps; not deployment lag.
