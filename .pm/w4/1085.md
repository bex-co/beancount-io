# Keep late account-close results with their confirmation

**Severity:** minor. **Estimate:** 35–50 minutes. **Owner:** dashboard. **A2:** closing one account must not put its error into another account's confirmation or dismiss that later confirmation.

## Reproduction and controls

Fresh390×844 and1440×1000 contexts reproduce both settlements below. Only the genuine `GetLedgerAccountDirectives` HTTP200 is partially modeled: append two unused empty Asset accounts produced by the current parser and unmodified `LedgerAccountService.getAccountDirectives`. Independent Beancount loading validates both Open directives, identities and absence of postings. The hosted file never contains those additions.

1. On Accounts, open **Close** for synthetic account A. Focus **Close Account**, press Enter and hold its one real prepared `BulkEntries` request before transport. It targets A. The submit button is disabled, but Cancel and Close remain enabled.
2. Press Escape. The pending confirmation closes. Open **Close** for account B. Its description correctly names B, there is no error, and its submit is disabled by A's still-pending mutation. Do not submit B.
3. Abort A's request before transport. The B confirmation acquires the connection error from A and enables its own Close Account button. There has been exactly one request, naming A; B has never failed or submitted.
4. In separate fresh contexts, repeat steps1–2 and settle A with a clearly labeled **browser-only successful GraphQL acknowledgement**. The success toast correctly names A, but B's already-open confirmation disappears. This is client lifecycle evidence, not a successful hosted closure or persistence claim.

Both widths repeat the wrong-target failure and the modeled-success dismissal. The narrow failure screenshot was visually inspected. Idle B opens enabled without error and cancels normally; both failure cases return to B's row. Preserve those controls.

All five native contexts closed. Five held attempts consist of three pre-transport aborts and two synthetic acknowledgements; **zero hosted writes**. Seven partial account reads, zero unhandled page errors, three expected aborted-request console messages. ## Cause and bounded repair

`dashboard/src/features/ledger-data/accounts/close-account-dialog.tsx:43` consumes mutation loading only for the submit button at:119. `DialogContent` at:83 receives no pending/busy integration; `handleOpenChange` at:47 and Cancel at:116 permit dismissal during the request. The same component stays mounted for the page's changing `closeTarget`. The awaited handler at:67–77 then sets its shared error or unconditionally calls the parent's success/close callbacks, without checking which opening is current. Accounts' single caller at `accounts/index.tsx` replaces that target directly.

Give this confirmation the existing pending-action ownership contract: one in-flight action, pending dismissal held across Escape/Close/outside/Cancel, and completion scoped to its submitted opening and account. Use the established `usePendingAction`/`DialogContent busy` pattern, including useful focus after failure; preserve deliberate focus movement and successful row/search handoff. The API already supplies the required inputs and outcomes. Coordinate [1084](./1084.md)'s separate pending-date snapshot; do not use its date correction as a substitute for target ownership.

Acceptance: real Accounts/CloseAccountDialog interactions hold A, attempt each dismissal, and settle failure/success without changing a later B confirmation. If a legitimate lifetime change is permitted, obsolete completion must leave B's state alone. Preserve one attempt across repeated Enter, same-opening error/retry, idle cancellation, row focus and the date/request relationship. Repeat both widths and run dashboard gates on implementation. `DeleteAccountDialog` has an independent handler and is source-audit scope only here.
