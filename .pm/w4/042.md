# Pull-to-refresh on Notifications never re-checks the ledger errors — and the errors section's skeleton is gated on the *commits* query

**Severity:** minor. **Estimate:** 20–30 minutes. Owner: mobile. A2: Notifications is the app's only dedicated view of "is my ledger broken?", and the refresh gesture a user reaches for there refreshes the other half of the screen. On the ledger I tested, the single error is a **failed remote fetch** — exactly the kind that clears by itself and that a user would pull down to re-check.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA; nothing was written.

## Two symptoms, one cause: the errors half is subordinated to the commits half

`notifications-screen.tsx` runs two independent queries — `useLedgerErrors()` (`getLedgerErrors`) and `useListCommitsQuery` (`listCommits`) — and then wires the screen so the commits query drives both sections.

### 1. The refresh gesture refreshes only Recent Changes

`:213-220`:

```ts
const onRefresh = async () => {
  setRefreshing(true);
  try {
    await refetchCommits();
  } finally {
    setRefreshing(false);
  }
};
```

`refetchCommits` is the only thing awaited, and `useLedgerErrors` (`src/common/hooks/use-ledger-errors.ts`) **does not expose a `refetch` at all** — it returns `{ errors, count, loading }`. So there is no way for this screen to re-run the error check, by gesture or otherwise. The spinner spins, the `LEDGER ERRORS` section is untouched, and the user has no signal that half the screen did not refresh.

In-app writes are fine and should not be confused with this: `invalidateLedgerData` evicts `getLedgerErrors` in every scope (`errors` ⊂ `entries` ⊂ `file`), and `cache-and-network` refetches on remount. The gap is specifically **changes that did not originate in this app** — a fix made from the dashboard, the CLI, a collaborator, or a transient server-side condition.

That last case is not hypothetical. The one error on `puncsky/example` reads:

> `failed to read file https:/beancount.io/prices/BTCUSD: file not found in virtual filesystem: https:/beancount.io/prices/BTCUSD`

A remote price include that failed to fetch is transient by construction. Pulling to refresh is the obvious user response, and it cannot work. (The mangled `https:/` in that message is the separate open **`w4/017`**; this note is about the refresh, not the string.)

### 2. "Ledger is healthy" can render while the error query is still loading

`:211`:

```ts
const isFirstLoad = (errorsLoading || commitsLoading) && !commitsData;
```

One flag gates **both** sections (`:243` and `:274`), and its data term names only `commitsData`. The consequences are asymmetric:

- Errors still loading, commits landed → `isFirstLoad` is **false**, so the errors branch runs with `errorCount === 0` and renders the green check and *"Ledger is healthy — no errors."* — an affirmative, reassuring claim made about data that has not arrived.
- Commits still loading, errors landed → the commits section shows a skeleton. Harmless; a skeleton claims nothing.

The correct term for the errors section is its own query's data, not another query's. Note that `errorCount === 0` is genuinely indistinguishable from "no data yet" here, because `useLedgerErrors` collapses `data?.getLedgerErrors ?? []` before the screen sees it — the screen cannot tell an empty result from an absent one even if it wanted to.

**Symptom 2 was not observed on screen.** Fourteen back-to-back frames from a cold launch straight into `beancount:///(app)/notifications` all showed the error already rendered — `getLedgerErrors` resolved before `listCommits` on this ledger and network, which is the benign ordering. The claim is a source reading, and the ordering it depends on is a race I could not force without network shaping. Symptom 1 needs no such qualification: it is unconditional.

### 3. A failed commits query renders as "No recent changes." (added September 14)

The same screen has a third symptom, filed as **`w4/067`** because it is one instance of an app-wide pattern, but recorded here because it lands in this file and shares this note's fix.

`:199-204` destructures `{ data: commitsData, loading: commitsLoading, refetch: refetchCommits }` from `useListCommitsQuery` — **no `error`**. On a cold failure Apollo leaves `commitsData` undefined and `commitsLoading` false, so `commits` is `[]`, `isFirstLoad` is false, and `:277-282` renders `notificationsNoChanges` — *"No recent changes."*

That is the same class of harm as symptom 2 above with the opposite cause: symptom 2 makes an affirmative claim about data that **has not arrived yet**, this one about data that **will never arrive**. Both end in the app asserting something about the ledger that it does not know.

It also sharpens fix step 1: `useLedgerErrors` should expose **`error` as well as `refetch`**. Today it returns `{ errors, count, loading }` and collapses `data?.getLedgerErrors ?? []`, so — as symptom 2 already notes — the screen cannot tell an empty result from an absent one. Adding `refetch` without `error` would leave it unable to tell a *failed* re-check from a clean one, which is the same blindness one step later.

## Fix

1. Return `refetch` **and `error`** from `useLedgerErrors`, and await both refetches in `onRefresh`:

   ```ts
   await Promise.all([refetchCommits(), refetchErrors()]);
   ```

   `Promise.all` rather than sequential awaits, so one slow half does not hold the spinner for the sum of both. Consider whether a rejected error refetch should surface anything — today a failed refresh is silent on this screen either way, which is a separate question.

2. Give each section its own first-load term. The narrow version:

   ```ts
   const errorsFirstLoad = errorsLoading && !errorsData;
   const commitsFirstLoad = commitsLoading && !commitsData;
   ```

   which needs `useLedgerErrors` to report whether `data` exists (a `loaded` boolean is enough, and does not leak the query shape). Until it does, the errors section must not make an affirmative "healthy" claim.

**Acceptance:** introducing a ledger error outside the app (edit the file from the dashboard or the CLI) and then pulling to refresh on Notifications shows it without leaving the screen; removing it the same way clears it on a pull; the `LEDGER ERRORS` section shows a skeleton until its own query resolves, never the green "healthy" row; and Recent Changes refreshes exactly as it does today. Add a unit test that `onRefresh` calls both refetches — there is currently **no test file for this screen at all**, only `notifications-screen/formatting.ts`'s helpers are covered indirectly.

## Blast radius

One screen and one hook. `useLedgerErrors` has one other consumer — the Home header's bell badge — which is read-only and unaffected by adding a `refetch` to the hook's return. No change to the queries, the cache, or `invalidateLedgerData`, whose scope table is correct as it stands and should be left alone.

Not exercised: the pull gesture itself (the pinned Expo MCP has no drag tool — `w4/020`), so symptom 1 is established from source and from the absence of any refetch path, not from watching a pull. Also not exercised: dark mode, enlarged Dynamic Type, Android, and the behaviour when the errors query *fails* rather than returning an empty list.

## Adjacent states

The rest of the screen is **correct** and worth recording, since much of it is the kind of thing that is usually wrong:

- `contentContainerStyle={{ flexGrow: 1 }}` with `alwaysBounceVertical` is deliberate and documented — it keeps a short page (healthy ledger, no commits) pull-refreshable over its whole area rather than only over the rows.
- `refreshing` tracks only the user's pull, never query loading, which is the convention `mobile/CLAUDE.md` sets out for skeletons vs. `RefreshControl`.
- `SkeletonRows` mirrors the real row layout (a title tile plus a 60%-width meta tile) with varied widths, again per the documented convention.
- `ErrorRow` degrades honestly: with no `filename` it renders as plain text with no chevron and no `open-outline` icon rather than offering a tap that could not work. That is precisely the state the error above is in, and it renders correctly.
- Rows are keyed by `commit.sha`; the divider is suppressed after the last row rather than drawn and hidden.
- `LedgerGuard` wraps the screen, so it cannot mount without a selected ledger.

One thing checked and **not** filed: the error rows use `key={i}` (`:260`) while the commit rows use `key={commit.sha}`. The errors array is replaced wholesale on every fetch and its rows hold no state, so the index key is harmless today; calling it a defect would be a style opinion.
