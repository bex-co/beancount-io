# Commodity accounts are shown as an unlabelled USD cost basis — and a commodity with no cost renders as $0.00

**Promoted to [w4/m11](./blocked/m11/README.md) on 2026-09-15**, with [w4/027](./027.md) folded in. The user approved the display rule recorded in that milestone, which settles the decision this note was blocked on. The milestone is the sole implementation queue and estimate; this note retains the original evidence and is dropped when m11 closes.

**Severity:** major. **Estimate:** 50–70 minutes. Owner: mobile. A2/A3: an account named `…:RGAGX` whose every figure is an unlabelled dollar amount misrepresents what the ledger records — and where the commodity has no cost currency, a real balance is displayed as `$0.00`, indistinguishable from an empty account (Repro C). The public crypto example is a shop-window ledger.

**Severity raised from minor after Repro C:** unlabelled conversion is a clarity problem; showing a non-empty account as `$0.00` and silently dropping it from the net-worth total is a correctness one.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light / default text size, authenticated production session at `https://beancount.io`. Reproduced on public `open_ledger/crypto-example` and on own `puncsky/example`. Report-only QA; no ledger mutation. **BQL evidence below is read-only, from the MCP credential pinned to `puncsky/example`.**

## Repro A — the arithmetic, on a ledger whose source I can query

1. Select `puncsky/example`. Accounts → expand `Assets` → `US` → `Vanguard` → open **`RGAGX`**.
2. Header reads **`Balance $49,049.67`**. The `August 14, 2017` section reads `+$150.02` (running `Balance: $49,049.67`) and `+$299.96` (`Balance: $48,899.65`); `July 31, 2017` reads `+$360.02` and `+$719.96`.
3. The recorded postings for that account, via BQL:

   | date | position |
   | --- | --- |
   | 2017-08-14 | `1.843 RGAGX {81.40 USD}` |
   | 2017-08-14 | `3.685 RGAGX {81.40 USD}` |
   | 2017-07-31 | `4.322 RGAGX {83.30 USD}` |
   | 2017-07-31 | `8.643 RGAGX {83.30 USD}` |

   and `SELECT sum(position), sum(cost(position))` → **`597.748 RGAGX`** / **`49049.66613 USD`**.

Every displayed figure is `units × cost`, rounded to cents: `1.843 × 81.40 = 150.0202` → `$150.02`; `3.685 × 81.40 = 299.959` → `$299.96`; `4.322 × 83.30 = 360.0226` → `$360.02`; `8.643 × 83.30 = 719.9619` → `$719.96`; and `49049.66613` → `$49,049.67`.

**The screen never shows a single RGAGX figure**, and nothing marks the dollars as a cost-basis conversion. In the same column of the Accounts tree they sit beside genuinely USD-denominated accounts (`BofA:Checking $2,754.06`, `Bank:Mercury:Checking $5,317.06`), indistinguishable from them.

## Repro C — a commodity with no cost currency disappears

On `puncsky/example`, Accounts → `Assets` → `US` shows two rows reading exactly `$0.00`:

| Row | `sum(position)` via BQL | Shown |
| --- | --- | --- |
| `Federal:PreTax401k` | `{}` — genuinely empty | `$0.00` ✔ correct |
| `Hoogle:Vacation` | **`-8 VACHR`** | `$0.00` ✘ **not empty** |

`VACHR` (vacation hours) is a bare commodity with no cost currency, so `cost(position)` contributes nothing and the row collapses to zero. A real holding is rendered identically to an empty account, with nothing to distinguish them.

This is not one stray leaf. `SELECT root(account, 1), sum(cost(position)) GROUP BY root` over the whole ledger returns:

| Root | Source | Shown in Accounts |
| --- | --- | --- |
| Assets | `USD 114846.39944`, **`VACHR -8`** | `$114,846.40` |
| Liabilities | `USD -8123.35` | `-$8,123.35` |
| Equity | `USD -3490.52` | `-$3,490.52` |
| Income | `USD -357944.58`, **`VACHR -360`**, **`IRAUSD -54500`** | `-$357,944.58` |
| Expenses | `USD 254712.05`, **`VACHR 368`**, **`IRAUSD 54500.00`** | `$254,712.05` |

**Every USD figure is exactly right.** But three of the five roots carry commodities the tree never mentions, across two commodities — and both are complete, balanced sub-ledgers (`VACHR: -360 + 368 - 8 = 0`; `IRAUSD: 54500 - 54500 = 0`). Home's net worth is the same story: `{USD: 106723.04944, VACHR: -8}` at source, `$106,723.05` on screen.

The omission survives all the way down the hierarchy. In the app, `Expenses` → `Taxes` → `Y2015:US` reads **`$53,758.01`**. Its children at source:

```
Expenses:Taxes:Y2015:US:CityNYC             USD  4722.84
Expenses:Taxes:Y2015:US:Federal             USD 28994.07
Expenses:Taxes:Y2015:US:Federal:PreTax401k  IRAUSD 18000.00   ← no USD
Expenses:Taxes:Y2015:US:Medicare            USD  2878.74
Expenses:Taxes:Y2015:US:SDI                 USD    30.24
Expenses:Taxes:Y2015:US:SocSec              USD  7000.04
Expenses:Taxes:Y2015:US:State               USD 10132.08
```

The six USD siblings sum to exactly `53,758.01`, so the displayed subtotal is arithmetically right — and an **18,000-unit pre-tax 401(k) contribution is simply absent** from a figure presented as that year's complete US tax total. This is not an obscure corner: it is a retirement contribution inside a tax subtotal.

**Expected:** a commodity account either shows its units, or labels the converted figure as a valuation and keeps the units reachable; an account with a non-zero balance never reads as `$0.00`; a total that omits a commodity says so.
**Actual:** units are unavailable on the account journal, the conversion is unmarked, and a commodity with no cost basis is silently rendered and summed as nothing.

## Cause

**Traced for the displayed value:** the amount is `cost(position)` in the operating currency, rounded to cents — confirmed by the exact arithmetic above against the ledger's own postings.

**Still open:** whether the server returns these USD figures to the app or the client converts. The BQL above is the ledger's source of truth, not a capture of the app's GraphQL response, so it proves *what the number is* without proving *who computed it*. Decide that before implementing — it determines whether the change is mobile-only or also backend.

Showing cost basis is a defensible default for a balance sheet, so the defect is not the conversion itself: it is that the conversion is unlabelled, the units are absent from the one screen dedicated to that account, and the Transactions list states the same posting differently.

## Fix

Pick one rule for commodity accounts and apply it to the account journal and the Accounts tree together:

- Mark converted figures as valuations wherever they appear — journal rows, running balance, and the header's change/percentage — so `$49,049.67` cannot be read as a dollar holding;
- make the recorded units reachable on the account journal (alongside the converted value, or as the primary figure with the conversion secondary); and
- **never render a non-empty account as `$0.00`.** A commodity with no cost currency must show its units (`-8 VACHR`) rather than a zero, and a total that cannot express a commodity in the operating currency must disclose the omission instead of dropping it. Distinguish "empty" (`Federal:PreTax401k`, genuinely `{}`) from "not expressible here" (`Hoogle:Vacation`, `-8 VACHR`).

Do not fix this by converting the Transactions list to USD — that would discard the recorded scale `w3/done/109` restored (`+0.005 STETH`, `+0.004 ETH`, verified still working this session). Do not change the Accounts tree's operating-currency **totals**, which are correct and reconcile exactly (`597.748 RGAGX` at cost is genuinely `$49,049.67`; the crypto tree's trial balance nets to zero). Do not relabel or convert commodities in the ledger.

**Acceptance:** on a fresh iPhone 17e launch, `Assets:US:Vanguard:RGAGX` conveys `597.748 RGAGX` as well as its `$49,049.67` cost basis, with the dollar figure visibly a conversion; `Assets:US:Hoogle:Vacation` conveys `-8 VACHR` and is distinguishable from the genuinely empty `Assets:US:Federal:PreTax401k`; the `crypto-example` Lido entry presents consistently between the Transactions list and the `Lido:STETH` journal; a plain USD account (`BofA:Checking`) is unchanged. Add coverage for a commodity held at cost, a multi-lot holding at different costs, a commodity with **no** cost currency, an empty account, and a same-currency control.

## Blocked

**Blocked 2026-09-14 by `/loop-worker w4` triage; no implementation started.** Still reproduces at HEAD. Triage answered the open cause question: the server converts because the app asks it to. `mobile/src/common/balance-util.ts` sets `BALANCE_CONVERSION = "at_cost"`, which the Accounts tree (`use-account-report`, `use-trial-balance`) passes as `conversion`. The account journal then takes the primary-currency figure from the converted inventory (`resolveCurrencyBalance(item.change, currency)` in `select-account-journal.ts`). So the change can be mobile-only.

It is not a sub-hour fix, and it needs a display decision the note leaves open. For commodity accounts:

- Are the recorded units the primary figure, with the cost basis secondary? Or does the cost basis stay primary, labelled as a valuation, with units reachable?
- How does the tree show a commodity with no cost currency (`-8 VACHR`) so it reads differently from a genuinely empty account?
- How does a root or subtotal disclose commodities it cannot express in the operating currency?

The rule has to cover the tree, the journal rows, the running balance, and the header's change and percentage together, and it probably needs a second query for units.

**Unblock with a user decision:** choose the display rule. The merchant header's one-line-per-currency layout is one existing candidate. The work is likely milestone-sized once chosen, so promote it with `/pm promote`, or move this note back to `.pm/w4/016.md`.
