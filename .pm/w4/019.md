# Track UIScene adoption before a future iOS turns it into a launch assert

**Severity:** minor — nothing is broken today. **Estimate:** 20–30 minutes to confirm and record the upstream status; the fix itself is an Expo SDK upgrade, not work in this repo. Owner: mobile (tracking) / upstream Expo (implementation). A3: the app ships to the App Store, and this is the class of issue that is free to watch now and a launch failure later.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, `expo ~57.0.4`, `react-native 0.86.0`. Report-only QA; no ledger mutation.

## What was observed

Every cold launch emits one UIKit runtime issue at **fault** level against this app:

```
[fault] com.apple.runtime-issues:UIKit App Config UIKitCore
        `UIScene` lifecycle will soon be required.
        Failure to adopt will result in an assert in the future.
```

Captured with `collect_app_logs` (`sources: ["js_console","native_ios"]`, `appId: io.beancount.ios`) across a terminate-and-relaunch: one occurrence per launch, in 4,748 log lines. `mobile/app.json`'s `ios.infoPlist` declares no `UIApplicationSceneManifest`, and no such key exists anywhere in the repo.

Apple's wording is explicit that this becomes an **assert** — i.e. a launch crash — in a future iOS release, not merely a warning.

## Why this is a tracking item, not a fix here

Adopting the `UIScene` lifecycle is the responsibility of the Expo / React Native app template, which owns the `AppDelegate` and the generated `Info.plist`. `.pm/DO_NOT_DO.md` says not to re-implement what upstream does — hand-rolling a scene manifest or patching the native project would fork the template and break on the next `expo prebuild`.

The actionable work is therefore:

1. Check whether the installed Expo SDK (or a newer one) adopts `UIScene`, and record the finding — including any upstream issue or release note that names the SDK version where it lands.
2. Add the check to the pre-release routine: `/mobile-release` should confirm the fault is gone, or that the shipped iOS version still tolerates it, before a store build.
3. Re-verify after each Expo SDK upgrade; the fault disappearing from a cold-launch log capture is the signal.

Do **not** hand-write `UIApplicationSceneManifest` into `app.json` as a workaround: declaring scene support without the corresponding `AppDelegate` adoption produces a worse failure than the current warning, and it would be silently reverted by a prebuild.

**Acceptance:** the upstream status is recorded on this note with a concrete SDK version or upstream link, and the pre-release check exists. When the supporting SDK ships, a cold-launch `collect_app_logs` capture on iPhone 17e contains no `UIScene lifecycle will soon be required` fault.

## Blast radius

Whole-app: the fault is about application lifecycle, not any screen. Not exercised: Android (unaffected — this is UIKit), a physical device, and whether any current iOS version already asserts rather than warns.

## Adjacent states

The rest of the native log is dev-infrastructure noise, explicitly **not** product issues: `getpwuid_r did not find a match for uid 501` (simulator user lookup), and repeated `Connection refused` / `NSURLErrorDomain -1004` against `localhost:8083` and `localhost:8097`, which are the Expo dev-tools and React DevTools ports that are not running. No product network failure appears in the capture.

Also worth recording for future QA runs: **`collect_app_logs` cannot capture JS console output on this setup.** Its `cdp` collector reports `"webSocketDebuggerUrl": ""`, so `sources: ["js_console"]` returns empty — which is why every earlier bounded capture this session came back with nothing, despite the LogBox banner continuously reporting warnings. That is an instrumentation limit, not evidence that no warnings exist. Native logs (`native_ios`) do capture correctly, and `durationMs` is capped at 10000.

Searched `.pm/**`, `mobile/CLAUDE.md` and `docs/` for `UIScene`, "scene lifecycle" and `SceneManifest` — no hits. No open or done item tracks it. `w3/191.md` is an unrelated JS worklet error surfaced through LogBox.
