# The zero-net add guard rejects valid cost-lot transactions with an inferred gain

Severity: **minor**. Package: **cli**. Estimate: **35–50m**. Source: continuous
CLI QA for w4. **A1:** agents must be able to use documented native cost syntax
and an inferred balancing posting together; this valid write has an explicit-amount workaround.

Environment: 2026-09-21, main `390568c220bfbdb0df1c9decb8436c64dfa3c9ca`,
checkout `cli/.venv/bin/bea` 0.3.0, Python 3.13.3, Darwin arm64.
All commands ran as fresh subprocesses under isolated
`cli/tmp/qa-20260921-cli-loop/`, with absolute ledger paths, closed stdin
(except the explicitly piped JSON), captured stdout/stderr, and 25-second
limits. Child-only `BEA_CONFIG_DIR`, `XDG_CACHE_HOME`, and `XDG_DATA_HOME`
pointed inside that directory; `BEA_NO_UPDATE_NOTIFIER=1`; inherited

## Reproducer and observed result

Create `main.bean`:

```beancount
2024-01-01 open Assets:Broker HOOL
2024-01-01 open Assets:Cash USD
2024-01-01 open Income:Gains USD
2024-01-02 * "Buy"
  Assets:Broker 1 HOOL {50 USD}
  Assets:Cash -50 USD
```

Check succeeds. With an absolute `--file` path, run:

```sh
bea --json --file main.bean add transaction "Sell and repurchase"   --date 2024-03-01   -p 'Assets:Broker -1 HOOL {50 USD} @ 60 USD'   -p 'Assets:Broker 1 HOOL {60 USD}' -p 'Income:Gains'
```

Exit 2; stdout empty, stderr has one usage error:
`Refusing a zero-net transaction with an inferred balancing posting; Beancount
drops that leg from list/query.` The ledger is byte-identical. This is not
zero weight: `-1 * 50 + 1 * 60 = 10 USD`, so the inferred gain is `-10 USD`.

Working controls: change only the final posting to `Income:Gains -10 USD` and
single-add succeeds with check valid. Alternatively, on a pristine copy,
`add transactions --from -` accepts this exact JSON and a fresh list contains
all three postings, including `Income:Gains -10 USD`; check succeeds:

```json
[{"date":"2024-03-01","narration":"Sell and repurchase","postings":[{"account":"Assets:Broker","amount":"-1 HOOL {50 USD} @ 60 USD"},{"account":"Assets:Broker","amount":"1 HOOL {60 USD}"},{"account":"Income:Gains"}]}]
```

The candidate and bulk control repeated on two fresh fixtures; the minimal
fixture above also reproduced the rejection and explicit-amount success.
Expected: preserve upstream weighted booking/inference for this valid transaction,
while retaining the deliberate refusal for a genuinely zero residual with a lost leg.

## Cause and bounded repair

`cli/src/bea_engine/ledger/adding.py:543–561` sums raw `units.number` by units
currency. `-1 HOOL + 1 HOOL` cancels, regardless of the two USD costs, so it
refuses before validation can infer the nonzero gain. `_transaction:453` is
called by the single-add engine dispatch; bulk `_transactions:696` is separate.
Use upstream cost/price-aware weights or validated booking results to decide
whether an inferred posting would actually disappear. Do not sum quantities as
if they were accounting weights, and do not weaken ordinary ledger validation.

- [ ] The exact single-add succeeds and fresh list/query returns the inferred
      `-10 USD` gain; `bea check` passes.
- [ ] Genuine zero-net inferred postings remain refused; explicit zero/zero
      and ordinary nonzero inference remain accepted.
- [ ] Add a regression around real cost booking, with cost/price cases supported
      by the same guard; run CLI checks when fixing.

Dedupe: all board files and open milestones searched for zero-net inference,
repurchase and cost-weight guards. This is a regression introduced by
`a60e560f` (completed w3/339). Its entire acceptance and current
`tests/test_add_refuses_zero_net_inferred.py` were reviewed: ordinary USD
controls pass but investment weights are absent. No open equivalent. The
separate bulk zero-leg omission is a missing-path problem, not evidence that
this valid investment should be blocked in bulk too.
