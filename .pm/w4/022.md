# Beancount files never wrap in the mobile editor, because wrapping shares a slot with the language mode

**Severity:** minor. **Estimate:** 15–25 minutes. Owner: mobile. A2: the file editor is where a newcomer reads their own ledger on a phone, and on a 393pt screen the right-hand half of most directives is off-canvas.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, authenticated production session at `https://beancount.io`, ledgers `open_ledger/alphabet` and `puncsky/example`. Report-only QA; **nothing was saved** — the Save button stayed disabled throughout.

## Repro

1. Select `puncsky/example`, open the **Files** tab, tap **main.bean**.
2. Long lines are clipped at the right edge with no wrap. Observed verbatim:

   | line | rendered as |
   | --- | --- |
   | 7 | `option "title" "Example Beancount file h` |
   | 10 | `include "https://beancount.io/prices/BTC` |
   | 14 | `2017-09-12 open Assets:Bank:Mercury:Chec` |

3. Go back and tap **README.md** in the same ledger. Its first heading and every paragraph **wrap** across multiple rows, with the line-number gutter correctly numbering the logical line once per wrapped block.

## The worse surface: Edit Transaction

The same defect lands hardest on `beancount:///(app)/edit-transaction`, which is a **raw beancount source editor for a single transaction** ("Edit raw beancount source below. A stale checksum or invalid beancount will be rejected with an error."). It passes `beancount` to the same component (`edit-transaction-screen.tsx:434-445`), so it takes the same non-wrapping branch.

Editing `Anthropic` on `puncsky/example`, the three lines render as:

```
1  2026-09-01 * "Anthropic" "ANTHROPIC* CLAUD      ← clipped mid-narration
2    Assets:Bank:Mercury:Checking
3    Expenses:Home:Internet
```

**The amounts are not on screen.** BQL confirms the postings carry `-102.00 USD` and `102.00 USD`, and the transaction detail renders them correctly — so on the one screen whose entire purpose is editing this transaction, the two numbers that matter most are past the right edge. A user can change an account or a payee while unable to see what they are balancing.

That the amounts are off-screen rather than absent is an inference from beancount's column-alignment convention (the same alignment `bea format` applies, and the reason a 30-character posting line still ends well short of its amount), corroborated by line 1 being visibly truncated mid-word. It was not confirmed by reading the raw file.

This raises the case for fixing the ternary: on the file browser, clipping is an inconvenience; here it hides the transaction's amounts during editing.

**Control on a second ledger:** `open_ledger/alphabet`'s `main.bean` clips identically (`2015-10-02 open Assets:Current:Cash-And-E`), so this is the file type, not the ledger.

So the same screen wraps a Markdown file and refuses to wrap a Beancount file. Beancount is the app's primary file type.

## Root cause

`mobile/src/components/code-editor/code-editor.tsx:160` (and the identical reconfigure at `:386`):

```ts
languageCompartment.of(
  beancount ? beancountStreamLanguage : EditorView.lineWrapping,
),
```

`beancount` comes from `isBeancountFile(path)` (`ledger-file-editor-screen/index.tsx:306`), so a `.bean`/`.beancount` file installs the language mode **and nothing else**, while every other file installs line wrapping **and no language**. Two unrelated concerns — how the text is highlighted and whether it wraps — are sharing one compartment slot, so you can never have both, and a Beancount file can never have wrapping.

This also explains the pairing seen in the repro: `main.bean` is syntax-coloured and unwrapped; `README.md` is plain black and wrapped. Neither file can be both.

**The clipped content is still reachable** — CodeMirror scrolls horizontally when wrapping is off — so this is a usability defect, not data loss, which is why it is rated minor.

## Fix

Give wrapping its own slot instead of borrowing the language one:

```ts
EditorView.lineWrapping,
languageCompartment.of(beancount ? beancountStreamLanguage : []),
```

Apply the same split at the `:386` reconfigure so a document swap does not reintroduce the coupling. `Compartment.of([])` is the normal way to express "no language here", and it keeps the compartment's name honest.

If unconditional wrapping turns out to be unwanted for Beancount specifically — column-aligned amounts do read better unwrapped on a wide screen — then make that an explicit, named decision (a `wrap` prop, or a viewport-width threshold), not a side effect of the language ternary. Either way the two concerns must stop sharing a slot: as written, a future change that adds a Markdown or JSON language to the `else` branch would **silently remove line wrapping from every non-Beancount file**, with no test to catch it.

Leave `highlightActiveLine()` / `highlightActiveLineGutter()` alone; they are a separate question (see Adjacent states).

**Acceptance:** opening `main.bean` on `puncsky/example` shows line 10's `include` directive in full across wrapped rows with no horizontal scroll, and it stays syntax-coloured; `README.md` still wraps; the gutter numbers each logical line once. Add a unit test under `src/components/code-editor/__tests__/` asserting that the built extension list contains `EditorView.lineWrapping` for **both** `beancount: true` and `beancount: false` — **no test currently covers wrapping at all**, which is why the coupling went unnoticed.

## Blast radius

One expression, used by **both** editor surfaces — the file editor (every file it opens, on read-only and writable ledgers) and the Edit Transaction screen above. Both pass `beancount`, so both lose wrapping. No change to saving, parsing, or the document model. Not exercised: dark theme (wrapping is theme-independent), iPad width, Android, and whether wrapping interacts with the `jumpToLine` scroll target used by the errors screen — worth a look, since jumping to a line is measured in visual rows once wrapping is on.

## Adjacent states

**One gap on this screen was found later and filed separately** (September 14): `w4/061` — on a read-only ledger the editor drops its Save button and says nothing, while the caret still follows taps. Same file, same sitting; it is a missing indicator rather than a wrapping problem, so it is not folded in here.

The rest of the Files journey behaved correctly on both ledgers and is worth recording as verified: the browser sorts directories before files; `main.bean` carries a lock icon and no delete action while every other file gets a trash icon, and both appear only when `canWrite` (absent entirely on read-only `open_ledger/alphabet`); non-openable files are dimmed, lose their chevron, get a `document-outline` instead of `code-slash-outline`, and correctly set `accessibilityState={{ disabled: true }}`. `uv.lock` is dimmed because `lock` is not in `TEXT_EXTENSIONS` (`src/common/ledger-file-types.ts`) — conservative-allowlist behaviour, not a defect, and arguably right given the repo-wide "never hand-edit a lockfile" rule.

One thing deliberately **not** filed: `highlightActiveLine()` is installed unconditionally, so line 1 carries an active-line background even in the read-only viewer on `open_ledger/alphabet`, where there is no cursor to be on it. It is cosmetic, I could not establish intent, and guessing would be speculation.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for wrapping, word/line wrap, horizontal scroll, CodeMirror, code-editor and file-editor terms. Four editor items exist and none touches wrapping: `w3/197` (unsaved-changes warning when there are none), `w3/214` (keep the active line above the keyboard), `w3/204` (header text limit in editors), `w3/done/100` (stale document after a ledger switch). `w4/017` is adjacent only in that the malformed `include` it reports is line 10 here — the very line this defect clips, which makes that error harder to diagnose from the phone. No overlap.
