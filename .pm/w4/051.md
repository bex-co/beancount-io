# Switching ledgers keeps the file browser inside the old ledger's folder, so a ledger with files reports "No files" — and offers to create one there

**Severity:** minor, at the top of that band — the display defect is recoverable in one tap, but the state it leaves behind aims a **write** at a directory the user never chose. **Estimate:** 20–30 minutes. Owner: mobile. A2/A3: the Files tab is how a newcomer inspects a ledger's source, and switching between a public ledger and their own is the most ordinary thing to do on the discovery path.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, English / System / light, authenticated production session at `https://beancount.io`, ledgers `open_ledger/alphabet` (read-only) and `puncsky/example` (owned, writable). Report-only QA; **no file was created or deleted** — `Create file` was never tapped, for the reason this note is about.

## Repro

1. Select `open_ledger/alphabet` and open the **Files** tab. Root lists `2022`–`2026`, `.gitignore`, `CLAUDE.md`, `main.bean`, `Makefile`, `pyproject.toml`, `README.md`, and a dimmed `uv.lock`.
2. Tap **2026**. It opens, showing `Q1.bean`, `Q2.bean`, `year.bean`, with a `‹ 2026` breadcrumb row.
3. **Without leaving the tab**, open the drawer and tap **puncsky › example**.
4. The drawer closes straight onto the Files tab. The breadcrumb still reads `‹ 2026`, and the screen shows:

   > 🗀 **No files**
   > Create a ledger file here, or pull down to refresh.
   > **[ + Create file ]**

5. Tap `‹`. The root listing appears correctly: `main.bean` (lock icon, no delete) and `README.md` (trash icon).

`puncsky/example` has **no `2026/` directory**. Its root is not empty — step 5 proves it. So the app states, of a ledger the user just selected, that it contains no files.

**Both switch paths were tried, and the drawer is the worse one.** Firing `beancount:///ledger/puncsky/example` also reproduces it, but that link navigates to Home first, so the user reaches the false empty state only by returning to the tab. The drawer — the normal way to change ledgers — dismisses onto the Files tab directly, putting the user on "No files / Create file" as the immediate result of choosing their own ledger.

## Why the editor is not affected

`w3/done/100` fixed the sibling case in the file *editor*, and the obvious question is whether its fix covers a path that does not exist in the new ledger at all. It does not need to: **that state is unreachable.** The editor is a pushed route with a back chevron and no drawer affordance, so the drawer cannot be opened from it; and the only other way to switch ledgers — the `beancount:///ledger/...` link — pops to Home and dismisses the editor. Verified on device: opening `2026/Q1.bean` on `open_ledger/alphabet` and then firing the link landed on Home with the editor gone.

The asymmetry is structural and worth stating, because it is the reason this bug exists where it does. On iOS **all five tabs mount once and stay mounted**, so a tab carries its local state across every ledger change; a pushed screen does not. Any per-ledger state living in a tab therefore needs an explicit reset — the transactions filters have one, the file browser does not.

*A stale comment to fix while you are here.* `(tabs)/_layout.tsx:172-176` sets `lazy: true`, with a comment explaining that native iOS tabs render eagerly anyway so the route components carry their own focus-once guard, and that the flag is there for Android's JS navigator. But `invalidate-ledger.ts`'s header still reasons from *"`(tabs)/_layout` sets `lazy: false`, so all five tabs mount once and stay mounted"*. The **behaviour** that comment depends on is still true on iOS, so nothing is broken — but the cited fact is not, and the next person to reason about mount lifetimes from it will be misled. It also means the Android side of this note is genuinely open rather than merely untested: under a lazy JS navigator the Files tab may unmount and remount, which could mask the defect there entirely.

## Root cause

`ledger-file-browser-screen/index.tsx:302-304`:

```ts
const [pathStack, setPathStack] = useState<string[]>([""]);
const currentPath = pathStack[pathStack.length - 1];
```

`pathStack` is plain local state seeded once. Nothing keys it to the ledger, and `ledgerId` (`:296`, from `useLedgerGuard()`) changes underneath it. The directory query at `:313` then runs with the **new** ledger and the **old** path:

```ts
variables: { ledgerId, dirPath: currentPath || undefined },
```

An empty result for `2026` in `puncsky/example` is the correct answer to that query. The screen renders its generic empty state over it, and the empty state is phrased as a statement about the ledger rather than about the folder.

## The part that makes this more than cosmetic

The empty state's primary action is **Create file**, and the create path is built from the stale directory (`:373`):

```ts
const filePath = buildLedgerFilePath(currentPath, filename);
```

So accepting the screen's own suggestion on a **writable** ledger creates `2026/<name>` in `puncsky/example` — materializing a directory that exists only in the ledger the user just left, in a repository where a stray top-level folder is not obvious afterwards.

**Not performed.** This is a production write and this run has no authorization for one; the path above is read from source at HEAD. What is confirmed on device is everything up to it: the stale breadcrumb, the false empty state, and the offered button.

Note the interaction with `canWrite`: on `open_ledger/alphabet` the browser correctly hides create/delete affordances, so the hazard only appears in the direction that matters — *away* from a read-only public ledger and *into* the user's own.

## Fix

Reset the stack when the ledger changes. The narrow version:

```ts
useEffect(() => {
  setPathStack([""]);
}, [ledgerId]);
```

The app already has the better-stated version of this idea one screen over, and it is worth copying the reasoning as well as the shape. `transactions-screen/filters/select-filter-query.ts` scopes the stored filter to its ledger, with:

> *"Every reader of `transactionFiltersVar` goes through here, so switching ledgers cannot carry an account restriction into the new ledger's journal — whether the transactions tab was mounted at the time or not."*

That is exactly the invariant the file browser lacks. If a remembered path per ledger is wanted later, store it keyed by `ledgerId` and resolve through one accessor, as the filters do — do not keep a bare stack.

Separately, **make the empty state honest about scope**. "No files" is right at the root and wrong in a subdirectory; in a folder it should say the folder is empty, and offer a way back as well as (or instead of) Create. That is a smaller change than the reset and guards the same class of confusion if a path is ever restored deliberately.

**Acceptance:** switching ledgers while inside `2026` lands on the new ledger's **root**, listing `main.bean` and `README.md`; the breadcrumb is gone; switching back to `open_ledger/alphabet` also shows root; navigating into a folder and back within one ledger is unchanged; and creating a file from an empty subdirectory writes to that subdirectory of the ledger currently selected. Add a test that `pathStack` resets on `ledgerId` change — the browser has tests for `pushPathStack`/`popPathStack` and `buildLedgerFilePath`, but nothing covers the ledger-change reset, which is why this survived.

## Blast radius

One screen's local state, one effect. No change to the query, the create/delete mutations, `LedgerGuard`, or the path helpers. The reset is observable — a user deliberately deep in a folder who switches ledgers loses their place — which is the correct trade and matches what the transactions filters already do.

**The rest of the tabs were audited and are clean** — the file browser is the only one. Transactions is protected deliberately (`selectFiltersForLedger`). Reports and Home hold only a range pill, which is a presentation preference and carries harmlessly. Accounts was the one I expected to fail and it does not, for a reason worth writing down:

`AccountTable` keeps its expand/collapse set in local `overrides` state (`account-table.tsx:344`) keyed by account name **and by category key** — and the five category keys (`assets`, `liabilities`, …) are identical in every ledger, so a collapsed `Assets` should follow the user across a switch. **It doesn't.** Collapsing `Assets` on `open_ledger/alphabet` and switching to `puncsky/example` via the drawer shows `Assets` expanded again (`w4l97-03`, `w4l97-04`).

The reason is incidental rather than designed: `accounts-screen.tsx:138-163` swaps `AccountTable` out for a skeleton while `accountsPending`, so the new ledger's load unmounts the table and `overrides` resets with it. Correct outcome, accidental mechanism — **a future change that keeps the previous table mounted during a refetch (a "don't flash a skeleton on refresh" improvement, say) would silently reintroduce the bug.** Worth an explicit reset keyed on `ledgerId` when this note's fix is made, so the behaviour stops depending on a loading branch.

Not exercised: the create itself (write authorization), dark mode, and Android.

## Adjacent states

The Files journey is otherwise **correct**, including several things that are easy to get wrong:

- Directory navigation and the `‹ <name>` breadcrumb work, and the breadcrumb recovers the correct listing for the *current* ledger — which is what makes this a stale-path bug rather than a stale-data bug.
- `canWrite` gates the whole write surface: on `open_ledger/alphabet` there is no `+` in the header and no per-row trash; on `puncsky/example` both appear, and `main.bean` still shows a **lock** instead of a trash icon while `README.md` gets one.
- Directories sort before files; non-openable files (`uv.lock`) are dimmed, lose their chevron, and take a `document-outline` icon.
- The root empty state, when genuinely empty, is well built — icon, explanation, pull-to-refresh hint and a primary action.

Recorded as a **capability finding, not a defect**: the journey's "branches" promise has no mobile surface at all. `listCommits` is the only branch-aware call and it hardcodes `branch: "main"` (`notifications-screen.tsx:205`) — which matches the GraphQL schema, where `listCommits(branch: String! = "main", …)` and `getLatestLedgerCommit(branchName: String! = "main", …)` are the only branch parameters and there is no `branches` query or `defaultBranch` field to build a picker from. So branch browsing is absent by construction on both sides, not broken on mobile. Worth a board decision rather than a bug.

## Dedupe

Searched all `.pm/**/*.md` including `done/` for ledger switch, stale state, file browser, path and empty-state terms. **`w3/done/100`** ("Mobile file editor retains the previous ledger's document after a link switch") is the closest and is **closed** — same class, one screen deeper: it is about the *editor* showing the old ledger's document, fixed by keying the editor session on ledgerId + path. This is the *browser's* directory stack, a separate piece of state that the same reasoning was never applied to. That the fix stopped at the editor is the story here. `w4/022`, `w4/023` and `w4/040` are other Files-journey defects on the editor and diff. No open item covers the browser's path.
