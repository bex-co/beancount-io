## Objective

Audit the LoginForm/RegisterForm consumers in ordinary login/signup and OAuth, mobile and identity consent. Preserve generated hidden usernames, next routing, validation and keyboard submission. Other auth forms need an explicit audit; source similarity alone is not a confirmed production finding.

## Context

See [FINDINGS.md](./FINDINGS.md) for reproduced behavior, source, controls and limits.

## Steps

1. Apply the objective within the dashboard package and verify the acceptance criteria.

## Files

- `dashboard/src/features/auth/`
- `dashboard/src/features/oauth/pages/` (shared consumer verification)
- Milestone board records for closeout only.

## Acceptance criteria

- [x] Shared consumers retain their existing contracts; every additional claimed affected route has evidence.

## Out of scope

- New dependencies, backend authentication replacement, real credential experiments or unrelated auth redesign.

## Outcome

**The shared consumers.** `oauth/pages/identity-consent.tsx` is the only
consent page that renders `LoginForm` and `RegisterForm`, so it inherits t001's
guard directly — same components, same props. The other consent forms were
never in this class: `consent.tsx` and `mobile-consent.tsx` already declare
`method="POST"` with an explicit `action`, and they carry a `decision` and a
`scope`, not credentials. They are unchanged.

Those routes need a valid OAuth `uid`, so they remain source-verified rather
than live — the same boundary FINDINGS drew, and no claim is widened beyond it.

**The sibling forms, audited by reproduction rather than by reading.** FINDINGS
warned specifically not to call these live password leaks from syntax alone.
Loading each route with JavaScript disabled settles it:

| Route | Server-rendered forms | Verdict |
| --- | --- | --- |
| `/auth/login` | 1, `method="post"`, submit disabled | fixed in t001 |
| `/auth/sign-up` | 1, `method="post"`, submit disabled | fixed in t001 |
| `/auth/forgot-password` | **none** | never exploitable |
| `/auth/reset-password` | **none** | never exploitable |
| `/auth/otp` | 404 at this path | not a route |
| `/auth/device` | 404 at this path | not a route |

So forgot-password, reset-password, the OTP form and the CLI code entry render
nothing without JavaScript: there is no native submission to serialize, and
**they were not affected**. That is the evidence this task asked for, and it is
the opposite of what source similarity alone would have suggested.

They still got `method="post"` — one attribute each, stated in their comments
as prophylactic rather than a fix. If any of them is ever server-rendered, the
native default would put its fields in the URL, and this closes that door in
advance without claiming a defect that did not exist.

**Existing contracts preserved.** 9/9 checks still pass: login and sign-up make
no pre-hydration submission at all and carry no `password` key, the submit
button enables after hydration at both widths, and an empty hydrated submit
still shows "Email is required" / "Password is required" with the
`next`-bearing route unchanged. The forgot-password page hydrates to its single
`method="post"` form with its email field and "Send reset link" button.

Not exercised, deliberately: the forgot-password form was **not submitted** —
doing so would send a real reset email, which this milestone's evidence rules
excluded. No credential, account, OTP or reset flow was run, and generated
hidden usernames were not touched (w4/137 stays open and independent).

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (384
files, 4331 passed, 1 pre-existing skip) and `yarn build` all pass.
