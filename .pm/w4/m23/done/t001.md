## Objective

Prevent native submission from putting credentials in a URL before React handlers attach. Use an SSR-safe readiness/submission guard and a non-GET defensive fallback; preserve the existing GraphQL authentication flow. Coordinate w4/137 so early input is not silently lost.

## Context

See [FINDINGS.md](./FINDINGS.md) for reproduced behavior, source, controls and limits.

## Steps

1. Apply the objective within the dashboard package and verify the acceptance criteria.

## Files

- `dashboard/src/features/auth/`
- `dashboard/src/features/oauth/pages/` (shared consumer verification)
- Milestone board records for closeout only.

## Acceptance criteria

- [x] LoginForm and RegisterForm cannot construct a credential-bearing GET with delayed or failed JavaScript; hydrated validation and submission still work.

## Out of scope

## Outcome

Reproduced first, on the built code, with JavaScript disabled so only the
server-rendered form existed and with every navigation aborted before
transmission. Login (click **and** Enter, at 1440x1000 and 390x844) and
registration all constructed a **GET** carrying a `password=` query key —
exactly what FINDINGS recorded. Synthetic non-credential fixtures throughout;
nothing left the browser.

Two layers, because neither alone is enough:

1. **`method="post"` on both forms.** This is defence in depth, not a working
   fallback — there is no non-JavaScript auth endpoint, and this milestone was
   explicitly not to invent one. It guarantees only that if the form is ever
   submitted natively, the fields land in a request body rather than in a URL,
   and so never in history, the referrer, or any log that records request
   lines.
2. **A hydration gate on the submit button.** `useHydrated` reports `false`
   while only server markup exists and `true` once React attaches. The submit
   button is disabled until then, which blocks the click path *and* the implicit
   Enter path — a form whose submit button is disabled is not submitted on
   Enter either.

`useHydrated` uses `useSyncExternalStore` with a server snapshot of `false`
rather than a `useState`/`useEffect` pair: the lint rule on synchronous
`setState` inside an effect rejects the latter, and this is the idiomatic
hydration signal anyway.

After the change, 9/9:

| Check | Result |
| --- | --- |
| login, click, 1440 / 390 | `method="post"`, **1 navigation** (the page load), no `password` key |
| login, Enter, 1440 / 390 | same |
| sign-up, 1440 | same |
| submit enabled after hydration | true at both widths |
| hydrated empty submit | route unchanged, "Email is required" / "Password is required" |

The strongest line is *1 navigation*: before, a second navigation carried the
credentials; now there is no submission at all before hydration. And the
hydrated control is exactly the one FINDINGS recorded as healthy — validation
shows and the `next`-bearing route is untouched.

Gates from `dashboard/`: `yarn format:check`, `yarn lint`, `yarn test` (384
files, 4331 passed, 1 pre-existing skip) and `yarn build` all pass.

Audited but not changed here, as FINDINGS asked — no claim is made about them
from syntax alone: `forgot-password-form`, `otp-form`, `reset-password-page`
and `device-auth-page/cli-auth-code-entry-view` are all `onSubmit`-only too,
and `oauth/pages/identity-consent.tsx` already sets `method="POST"`. They are
t002's scope, together with the consent consumers that share these two
components. w4/137 (signup defaults overwriting early input) is untouched and
stays open.

Not claimed: no real credential, account, email or authentication mutation was
exercised, and no server receipt occurred — every attempted navigation was
aborted in the browser.
