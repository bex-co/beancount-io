# An income budget needs a negative amount for its status badge to be right, and nothing on the form says so

**Severity:** minor. **Estimate:** 15–25 minutes (a line of help text, or derive the direction from the account). Owner: mobile. A2: the sign is load-bearing — it decides whether the budget reads as a spending cap or an earnings target — and it is documented only in a source comment, so a user who types the natural positive amount for an income budget gets its badge inverted.

Environment: branch `main`, HEAD `038faeeb`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5, authenticated production session at `https://beancount.io`, own ledger `puncsky/example`. Report-only QA; **nothing was saved** — the Add Budget form was opened and left, `Done` was never tapped.

## The convention, and where it is written down

`build-budget-entry.ts:11-16` states it plainly, and deliberately:

> *"Amount as typed. Kept a string all the way to the server so the ledger records exactly what the user entered, and because **a negative amount is meaningful: it declares an income target rather than a spending cap**."*

Everything downstream depends on it. `budget-selectors.ts:388-390`:

```ts
export function budgetDirection(budgetValue: number): 1 | -1 {
  return budgetValue < 0 ? -1 : 1;
}
```

and `isFavorableVariance` (`:410-418`) then treats `below` as good for `direction > 0` and `above` as good for `direction < 0`. That chain is **correct** — for a spending cap you want to come in under, for an earnings target you want to come in over. `select-budget-card-stats.ts` even flags this as the part "easiest to get subtly wrong (income budgets invert them)". It is not wrong; it is just entirely dependent on the sign.

## What the form shows

Opening `beancount:///(app)/add-budget` gives five rows — Date, Account, Interval, Amount, Currency — and one line of help:

> *"Budgets apply to one account. A newer entry for the same account and currency takes effect on its date."*

That is the whole of it. **No mention of the sign, of income targets, or of which account types a budget is for.** The `Amount` field is a plain numeric entry.

Meanwhile the account picker does offer income accounts: the budget picker uses `PICKER_ORDER.budget = "to"` (`push-account-picker.ts`), and `account-picker-screen.tsx:263` resolves `"to"` to the `expenses` list — which is `[...data.accounts]` sorted expenses-first, i.e. **every account**, income included, just ranked lower.

So the flow is: pick `Income:Salary`, type `5000` (the obvious thing), and the ledger records `+5000`. `budgetDirection(+5000)` returns `1`, the app treats it as a spending cap, and **earning less than the target renders as favourable** — green, "Below target" — while beating it reads as unfavourable.

**Traced, not observed.** Demonstrating the inverted badge requires creating an income budget, which is a production write this run has no authorization for. The chain above is read from source and each link is quoted; what has not been seen on screen is the resulting badge.

## Fix

Prefer removing the dependency on the user knowing the convention:

1. **Derive the direction from the account** — if the chosen account is under the ledger's `name_income` root, treat it as an earnings target regardless of the sign the user typed, and negate on write so the stored directive keeps the documented convention. `ledger-meta-utils.ts` already reads `name_income` from the ledger's own options, so this needs no new plumbing and works for non-English ledgers.
2. If the sign must stay the user's responsibility, **say so on the form** — one line under Amount, shown when an income account is selected ("Enter a negative amount for an income target"), plus the same in the field's accessible label.

Do **not** resolve it by hiding income accounts from the picker: budgeting an income target is a legitimate use and the data model plainly supports it.

**Acceptance:** choosing an income account and entering a positive amount produces a budget whose badge is favourable when actual **exceeds** the target; the existing expense behaviour is unchanged; a directive written by hand with a negative amount still reads as an income target. Add a test that an income-account budget entered positively ends up with `direction === -1` — `budget-selectors`' tests cover `isFavorableVariance` given a direction, but nothing covers how the direction is arrived at from the form.

## Blast radius

The Add Budget form and every surface that renders a budget's status: the Budget screen's cards and Home's budget panel (which shares `selectBudgetCardStats`, per `w4/038`). Only income budgets are affected — expense budgets, which are the common case and the only ones present on `puncsky/example`, are correct today.

Requires an **owned** ledger. Not exercised: actually creating an income budget (write authorization), the dashboard's equivalent form, dark mode, and Android.

## Adjacent states

The rest of the favorability chain was audited in the same pass and is **sound**: `varianceStatus` uses a documented half-cent epsilon (`VARIANCE_EPSILON = 0.005`) because "actuals and prorated budgets are both floating point, so an exact-zero variance never occurs in practice" — without it "on target" would be unreachable; `isFavorableVariance` returns true for `"on"` in both directions; and `selectPointFavorability` applies the same rule per charted point so, as its comment says, "a bar can't contradict the badge sitting above it".

`build-budget-entry.ts` also documents that there is no update mutation — "revising a budget means adding a newer-dated entry, which supersedes the previous one from its date" — which matches the form's help text exactly. That part is coherent.
