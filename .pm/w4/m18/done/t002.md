## Objective

Apply the presentation to both Inventory and str cells. Preserve PRINT newlines and exact amounts, with keyboard access and focus return for any disclosure. Keep shared formatters and CSV unchanged.

## Context

See [FINDINGS.md](./FINDINGS.md) and the milestone definition of done; preserve w3/m28/m37 behavior.

## Files

BQL cell rendering and any local full-value component

## Acceptance criteria

- [x] Opening PRINT transaction exposes all four lines and three postings, while Amount/Decimal/one-unit cases remain correct.

## Out of scope

Backend/API changes, Holdings layout changes, financial rounding policy, new dependencies and unrelated BQL copy fixes.

## Outcome

The result cell's `truncate` class was doing three things at once — flatten
(`white-space: nowrap`), clip (`overflow: hidden`) and ellipsize — so a printed
directive's newlines collapsed into a single clipped line and its posting
amounts could not be read. Cells now use `whitespace-pre-wrap break-words`:
pre-wrap keeps the source line structure and the postings' leading
indentation, break-words wraps a line too long for its column instead of
cutting it off, and t001's measured rows grow to fit. No disclosure control
was needed, so there is no new focus behaviour to manage.

The shared formatters (`common/lib/format/inventory-cell.ts`) and the CSV
export component are untouched, so inventory formatting, decimal precision and
CSV bytes are unchanged.

Live checks against a production build, 16/16 at 1440x1000 and 390x844:

- PRINT's Opening transaction renders all four source lines with their
  indentation preserved — `2026-01-01 * "Opening" "Starting balances"`,
  `Assets:Bank:Business 12000.00 USD`, `Assets:Bank:TaxReserve 4500.00 USD`,
  `Equity:Opening -16500.00 USD` — all three posting amounts readable, and the
  cell is clipped in neither axis (1100/1100 by 96/96 desktop, 338/338 by
  92/92 narrow). Before the change that cell was 338px wide over 1005px of
  content at 390px, on one flattened line.
- No cell anywhere in the 44-row PRINT result is clipped.
- The eight-unit Inventory still renders exactly
  `3609.87 USD, -13 VACHR, 193.442 VBMPX, 597.748 RGAGX, 36 VEA, 104 ITOT,
  64 VHT, 17 GLD` — same values, same order.
- A one-unit aggregate (`2754.06 USD`) stays a single compact line, 36px
  desktop / 32px narrow.
- The 1001-row control keeps `aria-rowcount` 1002, renders only 15–20 rows,
  and reaches row index 1002 without overlapping rows.

Recorded trade-offs, both measured rather than assumed:

- At 390px the 1001-row control's ordinary rows grew from 33px to 53px, because
  an account name too long for a 169px column now wraps to a second line
  instead of being ellipsized. Nothing is hidden any more; rows that fit are
  still one line, and desktop rows are unchanged at 37px.
- With measured heights the list re-estimates its scroll extent as rows are
  measured, so a programmatic jump straight to `scrollHeight` on the 1001-row
  result can land short once (row 999) and reaches the last row on the next
  pass. Incremental scrolling converges continuously; the last row is always
  reachable.
