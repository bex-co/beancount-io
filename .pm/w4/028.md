# Sentry is never initialized, so every error the app captures is silently dropped

**Severity:** minor as a user-facing defect — **nothing is broken for the user, and that is exactly the problem**: the app has no error reporting, so nothing tells anyone when something *is* broken for them. Rated minor rather than major only because no shipped behaviour is wrong; treat the operational impact as higher. **Estimate:** 20–30 minutes either way (wire it up, or remove it and correct the docs). Owner: mobile. A3: the app is in the App Store; today a crash or a failed receipt upload on a stranger's phone produces no signal at all.

Environment: branch `main`, HEAD `038faeeb`, `@sentry/react-native ~7.11.0`. Static verification over the whole `mobile/` package plus the installed SDK source; no device interaction needed.

## The chain

**1. The repo declares Sentry as the error-reporting stack.** `mobile/CLAUDE.md`'s tech-stack table says "**Errors**: Sentry (`@sentry/react-native`)". `package.json:41` depends on it. `app.json:124` lists `"@sentry/react-native"` in `expo.plugins`.

**2. `Sentry.init` is never called.** Grepping `Sentry` across the whole package (excluding `node_modules/` and `tmp/`) returns exactly two files: `src/common/sentry/capture.ts` and `src/common/__tests__/sentry.test.ts`. There is no `Sentry.init`, no `Sentry.wrap`, and **no DSN anywhere in the repository** — not in `app.json` (`extra` holds only the EAS project id), not in `eas.json`, not in `.env.example`.

The `app.json` plugin entry is a bare string with no options. The Expo config plugin prepares the native projects for symbol upload; it does not init the JS SDK and cannot supply a DSN that does not exist.

**3. Without init, the capture is dropped.** From the installed SDK, `node_modules/@sentry/core/build/cjs/scope.js`:

```js
captureException(exception, hint) {
  const eventId = hint?.event_id || uuid4();
  if (!this._client) {
    DEBUG_BUILD && debug.warn('No client configured on scope - will not capture exception!');
    return eventId;
  }
  ...
}
```

No `init` → no client on the scope → the exception is discarded. Note it still **returns a freshly minted event id**, so the call looks successful to any caller that checks, and the warning is `DEBUG_BUILD`-gated, so a release build says nothing.

**4. Production builds also disable symbol upload.** `eas.json`'s `build.production.env` sets `SENTRY_DISABLE_AUTO_UPLOAD: "true"`. So even the half that the plugin does own is off in the profile that ships.

**The app does call this.** `src/screens/receipt-capture-screen/use-receipt-workflow.ts:91,116` reports receipt parse and upload failures through `captureError`. Both are dropped.

## Why nothing catches it

`src/common/sentry/capture.ts`'s own comment says it is written so "a missing/uninitialised Sentry never turns error reporting into a crash of its own — capture failures are swallowed." That is good defensive design and it is also what makes this invisible: the uninitialised case is indistinguishable from the working one at every call site.

The only test on this path, `src/common/__tests__/sentry.test.ts`, opens with *"Test the sentry initialization logic / This tests the business logic without requiring actual Sentry SDK"* and includes `it("should accept valid Sentry DSN format")` — **19 cases asserting against an inline re-implementation of an initialization path that does not exist in the app.** It is one of the nine files in `w4/026`; fixing that note's pile-3 for this file means deciding what the real behaviour should be first, which is this note.

## Fix — decide which of two states is intended

- **If Sentry is wanted:** call `Sentry.init({ dsn })` once in `app/_layout.tsx` (and `Sentry.wrap` the root component, per the SDK's Expo guidance), source the DSN from configuration rather than a literal — **a DSN is not a secret but this is a public repo, so keep it in `app.json`'s `extra` or an EAS env var and document it in `.env.example`**. Then decide deliberately whether `SENTRY_DISABLE_AUTO_UPLOAD` should stay `true` in the production profile; without symbol upload the reports arrive unsymbolicated. Add a `beforeSend` scrub before enabling — `captureError` forwards its `context` straight into `extra` with no filtering, which is fine for today's two call sites (`phase`, `ledgerId`, `code`) but is the wrong default to grow into.
- **If Sentry is not wanted** (the same call the board already made for analytics in `w3/001`): remove the dependency, the `app.json` plugin entry, `src/common/sentry/`, the `SENTRY_DISABLE_AUTO_UPLOAD` env, and the two `captureError` call sites — and **correct `mobile/CLAUDE.md`, which currently tells every agent that errors go to Sentry.** Note the build command documented in `mobile/CLAUDE.md` and used across `.pm` tasks (`SENTRY_DISABLE_AUTO_UPLOAD=true npx expo run:ios`) would stop being necessary.

Do not resolve it by adding a DSN without the `beforeSend` scrub, and do not leave the third state the package is in now.

**Acceptance:** either a deliberate error thrown in a production-profile build appears in the Sentry project within minutes, with `captureError`'s context attached and no credential-bearing fields; or no Sentry reference remains in `mobile/` and `mobile/CLAUDE.md` no longer claims error reporting. Either way `src/common/__tests__/sentry.test.ts` is replaced by a test of real code or deleted.

## Blast radius

Whole-app error reporting. No runtime behaviour changes for the user in either direction — `captureError` is already a no-op, so wiring it up starts data flowing and removing it changes nothing observable. Not exercised: whether native crashes (as opposed to JS exceptions) are reported through some other path — the `@sentry/react-native` plugin can wire a native handler at build time, and I did not inspect a built binary's `Info.plist`, so a native-side DSN injected by a mechanism outside this repository cannot be fully ruled out. Confirm against a real build before deleting anything.

## Adjacent states

The OAuth module was audited in the same pass and is **exemplary — nothing to file, and worth saying so** given how often this is where apps go wrong:

- `pkce-encoding.ts` uses a 64-character alphabet precisely so `byte & 63` is an unbiased draw, and says why 66 would not be; `CODE_VERIFIER_LENGTH = 43` is RFC 7636 §4.1's minimum; base64url conversion strips padding per §4.2; a short entropy buffer is **rejected rather than cycled**.
- `pkce.ts` draws from `Crypto.getRandomBytes` (OS CSPRNG), uses S256 rather than `plain`, and draws `state` the same way.
- `authorization-result.ts`'s `validateAuthorizationRedirect` is stronger than most: it compares the full redirect origin and path, rejects a fragment, enforces both a clock-skew floor and an expiry, requires `state` to match, requires **`iss`** to match (RFC 9207 mix-up defence, routinely skipped), and rejects `access_token`/`id_token`/`token` appearing in an authorization-code callback. `singleParameter` **throws on duplicates**, which closes parameter pollution.
- No token, code or verifier is logged anywhere: the only `console.*` in the entire module is `oauth-sign-in-finalizer.ts:46`, which logs a ledger-load failure and no credential.
