# Non-UTF-8 formatter exports still emit a raw traceback under --json

Severity: **minor**. Package: **cli**. Estimate: **35–50m**. Source: continuous
CLI QA for w4. **A1:** every supported JSON command must give automation a
parseable error and identify the input that needs correction.

Environment: 2026-09-21, main `390568c220bfbdb0df1c9decb8436c64dfa3c9ca`,
checkout `cli/.venv/bin/bea` 0.3.0, Python 3.13.3, Darwin arm64. Fresh bounded
subprocesses, closed stdin, child-only config/cache/data beneath
`cli/tmp/qa-20260921-cli-loop/`, update notices disabled, BEA_FILE/BEA_TOKEN
removed. All fixture and export paths are disposable; no hosted session.

## Reproducer and observed result

Create an invalid-UTF-8 source in a disposable directory:

```python
from pathlib import Path
Path("bad.bean").write_bytes(b"2024-01-01 open Assets:Cash USD\n\xff\n")
Path("out.bean").write_text("SENTINEL\n")
```

Then run, substituting absolute paths:

```sh
bea --json format bad.bean --output out.bean
```

Exit 1; stdout is empty. Stderr is an upstream Python traceback, ending in:

```text
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 32: invalid start byte
```

`json.loads(stderr)` fails. `--debug` was not passed. The traceback names the
upstream executable/source, not the bad input file; there is no re-save hint.
Both source and existing export remain unchanged. Human `format bad.bean -o
out.bean` and plain `format bad.bean` emit the same traceback. Reproduced on two
fresh fixtures, in addition to the original export candidate.

Working control: `bea --json format bad.bean --check` exits 1 with one proper
JSON validation error naming `bad.bean`, byte 32, UTF-8 and the instruction to
re-save. A valid UTF-8 file exports successfully, and syntax-invalid but valid
UTF-8 text remains format-able in stdout/export mode as documented.

Expected: the normal JSON error object, empty stdout, input path/offset/encoding
and actionable hint; no raw traceback unless it is contained in the debug
field. Human mode should present the same useful diagnostic. This follows
`cli/docs/USAGE.md`'s JSON error and non-UTF-8 input contracts.

## Cause, scope, and repair

`cli/src/cli/commands/format.py:82,94,139–141` preflights text only for the
walking modes (`--check`, `--dry-run`, `--in-place`). File stdout/export calls
`launch.run_native("bean-format", ...)` directly and raises `typer.Exit(status)`.
`cli/src/cli/engine/launch.py:75–87` inherits native streams, so an upstream
decode exception reaches stderr before the CLI can render an envelope.
Installed `beancount/scripts/format.py:194` reads the input without catching
UnicodeDecodeError. The CLI's existing `_text` and `decode_error_message`
handling already supplies the better diagnostic on the working control.

Validate encoding on the file stdout/export paths, and route remaining native
failures through the existing structured-error boundary (`check_native`) where
appropriate. Keep upstream formatting and the documented syntax-invalid text
transformation behavior; do not turn export into an accounting-validity gate.
Caller search finds the single registered `format_beans` handler for both
`-o`/`--output` and stdout, separate from the captured in-place branch. The stdin
native branch also exists but invalid-byte stdin was not exercised here.

- [ ] The exact file-export repro produces one JSON error with the bad file,
      encoding, offset and re-save hint; both source and existing output stay intact.
- [ ] Human file stdout/export gives a concise diagnostic without a traceback;
      debug retains diagnostic detail within its documented shape.
- [ ] Valid UTF-8 and syntax-invalid-but-decodable export controls still work;
