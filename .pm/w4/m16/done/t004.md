## Simplify review

Completed 2026-09-19. Ran `/simplify` over the milestone's changed code. The efficiency angle was verified directly rather than dispatched — filtering the diff for anything that is not state plumbing, a comment or a test leaves nothing, so there is no new computation or dependency. Reuse, simplification and altitude were reviewed in depth, and the two reviews disagreed on the central question, which is recorded below.

**Fixed — a fifth instance of the same defect, in a file this milestone had already edited.** `income-statement-content.tsx` still owned `chartMode` (stacked vs single) with `useState`, in the same toolbar row as the tab list that was lifted. It has the identical problem: a reader on Income or Expenses who picks "single" is snapped back to "stacked" by any uncached read. It is now page-owned as `chartMode`/`onChartModeChange`. Leaving it would have meant fixing four instances and shipping the fifth from the same file.

**Fixed — four renders that silently tested a mode production no longer has.** `balance-sheet-content.test.tsx`, `report-wiring.test.tsx` (both components, via one shared props object) and `net-profit-summary.test.tsx` still rendered their content without the new required props. `tsconfig.app.json` excludes `**/*.test.tsx`, so `tsc -b` never saw it, and at runtime an undefined `value` flips Radix `Tabs` back to uncontrolled. All four now pass the controlled props.

**Fixed — smaller cleanups.** `defaultValue={selectedTab}` beside `value={selectedTab}` is dead once the prop is required and always supplied, so it was removed from all four content components; it wrongly suggested the component can run uncontrolled. The rationale had been stated nine times — `AGENTS.md`, a four-line comment in each page, and a prop JSDoc in each content file — and the wording had already drifted between copies, so the page comments are now one line each and the durable explanation lives in `AGENTS.md` and the caller-facing prop doc. The Cash Flow content harness owned state no test in that file exercises, so it now passes fixed props in the style the file already uses for `onConversionChange`, and the explanatory comment moved to the Trial Balance harness, which genuinely needs state for its narrow view-picker test. The second Cash Flow page case repeated an assertion the first already made; it now pins the pending state itself.

**Rejected, with the reasoning recorded.** The altitude review recommended replacing the lifted state and threaded props with a cookie-backed `useReportChartSelection` hook beside `useChartsVisibility`, arguing it would survive a second unmount boundary and cover `chartMode` and the overview card at once. It was not adopted, for two reasons. It conflicts with this milestone's own definition of done, which requires the state to be "scoped to the relevant report/ledger lifetime" and explicitly forbids adding a global preference store; a cookie outlives the session and the ledger. And the reuse review independently established that `account/index.tsx:320` already keeps exactly this as bare page-level `useState`, so a hook would make the four statement pages diverge from the account report rather than converge with it, while wrapping a single line of state — unlike `useReportConversion`, which exists because it carries real shared logic.

**Recorded rather than fixed**, in [142](../../142.md): the outer ledger-layout boundary also unmounts the page on a shared account/filter/time change, so the selection still resets there — that boundary belongs to m13 by this milestone's own coordination note; the overview `net-worth-card` chart/table choice has the same defect outside these four reports; and the Trial Balance content test still duplicates a fourteen-prop list that `Harness` already builds.

Gates from `dashboard/` after the fixes: `yarn format:check`, `yarn lint`, `yarn build` and `yarn test` pass at 376 files and 4,238 tests. The first lint run caught a missing `ChartMode` type import on the income-statement page, added before the rerun.
