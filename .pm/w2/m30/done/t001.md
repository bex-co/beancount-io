## Objective

One `POST parseFile` request with a failing LLM upstream crashed the production backend on 2026-09-08 (edge 502 for ~10 s until Compose health-gating restarted the container) — a one-request denial of service. Find the error path that escapes the request boundary, contain it so the request returns an ordinary 500 like `parseReceipt` does, and pin the fix with a regression test that proves the process survives.

## Context

- Incident: ADR 0011, Context section ("a sibling probe of `parseFile` escaped the request error boundary entirely").
- `parseReceipt` fails the same upstream the normal way (masked 500), so the escape is specific to the `parseFile` path — most likely an unhandled promise rejection in `extractTransactionsFromFile` or its file-download leg.
- Reproduce locally: unit-level (mock the LLM/model to reject at the right point) or docker-mac with no LLM key configured.

## Steps

1. Reproduce: drive `parseFile` with an upstream that rejects (bad credential, aborted fetch) and watch for `unhandledRejection` / process exit.
2. Trace the escape (likely a promise created outside the awaited chain) and contain it inside the request.
3. Add a regression test: `parseFile` with a rejecting model returns an error result and the process emits no `unhandledRejection`.
4. Audit `parseReceipt`'s parallel block (`Promise.all`) for the same shape while in the file.

## Acceptance criteria

- [ ] A failing-upstream `parseFile` request returns a 500 (or clearer domain error) with the process alive.
- [ ] Regression test fails on the pre-fix code (verified by reverting the fix locally) and passes after.
- [ ] No `unhandledRejection` warnings in the test run.
