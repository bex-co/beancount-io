# Signed in, a Gallery search for a common term takes 4–5 s per request, against under 1.2 s signed out, so each "Show more ledgers" waits 5–10 s

**Minor (performance) · backend-v2 (Gitea search as the user) · 1–2 hours to locate; fix size unknown.** A2: the Ledger Gallery is how people find the public example ledgers. w2/104 made it page past 50, and it works: the button shows a spinner and `aria-disabled` while a page loads. But for a signed-in reader every page of a broad search is slow.

Production https://beancount.io, 2026-11-12, `main-CuYafm8C.js`, isolated headless Chromium. Signed in as the QA account (GROWTH); controls signed out. Read only.

## Measurements

`searchLedgers` with `{ fullName }` only, fetched from the page; each figure is a single request.

| Request | Signed in | Signed out |
| --- | --- | --- |
| `q:"open_ledger", limit:50, page:1` | 3,869 ms | 1,104 ms (`curl`) |
| `q:"open_ledger", limit:50, page:2` | 4,298 / 5,252 ms | 900 ms (`curl`) |
| `q:"open_ledger", limit:10, page:2` | 4,629 ms | — |
| `q:"open_ledger", limit:1, page:2` | 5,147 ms | — |
| `q:"stock", limit:50` (1 match) | 765 ms | — |
| `listLedgers` (6 ledgers), control | 924 ms | — |

The dashboard's full `SearchLedgers` selection with `permissions { … }` signed out (`curl`): 363 ms for page 2 and 599 ms for page 3. Signed in, the same selection took 5,158 ms, so the extra fields are not the cost.

In the Gallery (`/ledger-gallery?q=open_ledger`, signed in), **Show more ledgers** took 5.2–9.7 s from click to rows across four timed clicks. One measured request ran 9,489 ms from send to finish. The rows arrive correctly (50 → 100 → 150, no duplicates), with the button busy throughout.

So the cost follows the signed-in identity and the number of matches, not the page size: `limit:1` is as slow as `limit:50`, and a one-match term is fast.

## Where it comes from

`backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts:2053–2101` (`searchLedgers`) passes the arguments to the Gitea repository search through `favaClientFactory.getApiContext(userId)`, that is, as the signed-in user. Gitea's repo search for a named user adds access conditions (owned, collaborations, teams), which likely scan every matching repository before applying the limit. Signed out there is no user to check access for. This was not traced into Gitea or its database here.

## Fix

- Confirm where the time goes (Gitea request log or SQL timing for `/repos/search` with and without a user).
- If it is the per-user access scan, consider answering public-catalog searches without the per-user scan and adding the reader's own private matches separately, or the index/configuration change Gitea needs.

**Acceptance:** a signed-in `searchLedgers` for `open_ledger` answers within about 1.5× its signed-out time.
