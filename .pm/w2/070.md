# Keep Explore paging usable when one ledger's star status is denied

**Severity:** minor. **Owner:** mobile. **Estimate:** 45–60 minutes, including a focused Apollo/result-boundary regression. A2/A3: a newcomer browsing public examples should reach later examples even when an optional favorite badge is unavailable. Native report-only QA,2026-10-09; no product fix or star/ledger mutation.

Environment: production `https://beancount.io/`; local development client on main `76424c58`, React Native0.86/Expo57, iPhone17e/iOS26.5,390×844 logical points, English/System/light/default large text. Existing native OAuth session, verified without retaining identity or credentials. Fresh QA sign-in is unverified because the designated credential file is absent. Initial selected synthetic ledger `open_ledger/example`; fresh-repeat process28040, earlier process21246.

## Reproduction and working controls

1. From Example Home, actually tap the drawer, **Browse ledgers**, then **Explore**. Leave search empty. The first page loads; bounded native scrolling reaches `open_ledger/conagra` and **Load more**.
2. Tap Load more and scroll to the next footer. Page two loads through `open_ledger/jabil`. Tap Load more again to request page three.
3. After settling, the list remains at Jabil with **Try again**. The native retry is an enabled48-point-high Button; an actual label-matched tap repeats the same state. Later examples cannot be reached by ordinary unfiltered paging.
4. Terminate/relaunch the client through the inspected public Example link, then repeat the actual drawer→Browse→Explore journey. Pages one/two succeed and page three plus actual retry fail again. The development warning banner was dismissed before the paging check and is excluded as a defect.
5. As a recovery control, type `stock-example` into the actual Explore search field. One public result appears. Tap its inspected `discovery-open-open_ledger/stock-example` action: Stock Home loads with its Broker transactions. A read-only native state check confirms selected ledger `open_ledger/stock-example`. No star control was pressed.

**Expected:** valid ledger records remain browsable; an unavailable optional star status stays unknown with its star action disabled. **Actual:** one optional field denial rejects all30 otherwise returned records and repeatedly blocks later pages. Exact search provides recovery, so this is minor rather than a loss of all ledger access.

## Real response control and root cause

Read-only controls used the app's **actual installed Apollo client and generated DiscoverLedgers document**, with its existing OAuth flow; no credential was copied and no response was fabricated. These are native API controls, **not interception of the UI's wire request**. Variables were `q:"",page:N,limit:30`; the generated operation also sets `isPrivate:false,includeDesc:true`.

- Exact generated pages1/2 with `errorPolicy:"all"`:30 records each, no GraphQL errors.
- Exact generated page3 with that inspection policy:30 records and one error `{code:"FORBIDDEN",message:"Authorization denied",path:["searchLedgers",21,"isStarred"]}`. That record is public, reports `permissions.pull:true`, and has `isStarred:null`. Its other-owner identity and payload were omitted. The page still contains23 public `open_ledger/` examples, including JPMorgan Chase, Meta, Microsoft and Nvidia.
- Exact generated page3 with the app's default policy: rejects with `ApolloError`, the same FORBIDDEN field path, and no network-error status.
- Preserve the generated selection except remove **only optional `isStarred`**: pages3/4 each return30 records with the default policy and no GraphQL errors. Page4 includes `open_ledger/stock-example`. This isolates star-status handling; it does not grant that field or prove patched UI behavior.

`mobile/src/common/graphql/queries/ledgerDiscovery.graphql:1–15` includes nullable `isStarred` in the shared fragment. `src/screens/ledger-selection/use-discovery.ts:32–42` queries Explore without an error policy or partial-result classification. The installed Apollo3.14 `core/QueryManager.js:841,793–818` defaults to `none` and rejects any GraphQL field error. `discovery-store.ts:117–143` correctly retains the failed page number and prior records, but therefore retries the same rejected page indefinitely. Footer retry wiring is `index.tsx:390–415`.

The backend nullable field is declared at `backend-cluster/backend-v2/src/features/ledger/api/resolvers/ledger-resolver.query.ts:170–181`; `workflow/ledger-workflow.ts:1524–1528` authorizes star-status reads through `LEDGER_SOCIAL_STAR_STATUS_READ` before Gitea work. **The exact relationship fact causing this one denial is unverified and is not claimed to be an authorization bug.** The reproduced mobile failure is its amplification to every record on a successful catalog page.

## Repair and acceptance

At the mobile Explore query/result boundary, retain valid catalog data when all returned errors are recognized denials of the nullable `searchLedgers[index].isStarred` field. Keep those statuses null/unknown. Validate the result and error paths; continue failing on root/catalog errors, missing required records, authentication errors, transport failures and unrecognized field/source errors. An explicit `all` policy plus narrow result classification is one bounded option; avoid a blanket `ignore` policy or inventing `isStarred:false`.

Preserve the current safeguards: `index.tsx:319–335` already dims/disables unknown-star controls, `discovery-store.ts:146–147` refuses their mutation, and `index.tsx:160–187` independently checks GetLedger readability before selection. Preserve true/false stars, pending serialization, featured ranking, deduplication, exact page/hasMore semantics, generation/abort guards, current items during refresh and retry after genuine failures. This is a mobile consumer change; backend REST/GraphQL/MCP credential and relationship policies remain in force.

Acceptance for implementation: the reproduced first two pages→third page→later page journey shows the permitted examples; unknown star status remains disabled; selecting Stock from paging and exact search reaches the correct ledger. A real Apollo/link plus production page-consumer regression should distinguish partial optional denial from root FORBIDDEN/UNAUTHENTICATED, missing data, network failure and ordinary complete success; verify unknown-star actions produce no mutation. Retain rapid-search/tab-switch and refresh/retry behavior. Run the mobile gates and native light/dark check when implementing.

Blast radius: one `useDiscovery` owner and authenticated `app/(app)/ledger-selection.tsx` route, reached through the drawer. MyDiscoveryLedgers shares the fragment and default rejection policy, so an analogous account-list issue is source-derived only. StarredDiscoveryLedgers maps repositories with known starred status and does not select this field. The guest chooser uses curated IDs rather than authenticated discovery. These other journeys were not exercised here.
