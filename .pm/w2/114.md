# A lowercase or malformed currency in New Entry is refused as "information provided is invalid"

**Minor · dashboard · 35–50 minutes.** A2: typing `usd` instead of `USD` is the most natural slip in a free-text currency field. The ledger names the bad value, but the form neither prevents the slip nor says which field is wrong. This is the dashboard counterpart of mobile's [w21/659](../w21/done/659.md), which maps the same w23/033 refusal.

Production https://beancount.io, 2026-11-10, English, isolated headless Chromium 156 at 1440×1000, signed in as the owner of the designated synthetic ledger. Every attempt was refused; main.bean stayed at blob `f1a0b83c`. Local main `0a223be1c`.

## Reproduce

Open `/ledger/<o>/<l>/journal?action=new-entry&directive=transaction`, enter a balanced two-posting transaction, set both currencies to the value below, then Create:

| Currency | `BulkEntries` response | Dialog shows |
| --- | --- | --- |
| `usd` | `BAD_USER_INPUT: entry 0: postings[0].units.currency "usd" is not a valid currency` | "Some of the information provided is invalid. Please check and try again." |
| `U$D` | `… "U$D" is not a valid currency` | same |
| `X` (well-formed, not allowed by the accounts' `open`) | `VALIDATION_FAILED: … Invalid currency X not allowed in account …` | "This would add an error to your ledger: Invalid currency X not allowed in account Expenses:Food:Coffee (main.bean:89); …" ✓ |

The Balance tab behaves the same way: `usd` returns `entry 0: amount.currency "usd" is not a valid currency`, and the dialog shows the generic text. The draft is kept in every case.

## Root cause

- The forms accept any trimmed string. For example, `features/journal/components/new-directive-dialog/transaction-form.tsx:113` has `currency: z.string().trim()`, so the syntax error is only found by the server.
- The refusal then goes through the shared `getErrorMessageKey` → `common.errors.badUserInput`. Mobile parses the same message with `TOKEN_REFUSAL` (`mobile/src/common/ledger-refusal.ts:153-162`; account, currency, tag, link, flag) and shows the value in the app's words. Packages stay independent, so the dashboard needs its own copy.

## Fix

1. **Prevent it.** Validate currency fields with Beancount's commodity syntax before submit: uppercase start, `A–Z 0–9 ' . _ -`, alphanumeric end, at most 24 characters. Message: "Currencies are written in capitals, e.g. USD". This applies to the Transaction posting currencies, Balance, and the Add Budget currency. Consider uppercasing automatically on blur when the only problem is case.
2. **Explain the refusal.** Add a dashboard matcher for `^entry \d+: \S+ ("…"|\S+) is not a valid (account|currency|tag|link|flag)`. Map it to localized copy naming the value: "“usd” isn't a valid currency". Never show the field path.

Add keys in all 15 locales. Add tests for `usd`, `U$D`, and a valid `USD` control in both forms.

## Blast radius

Currency inputs in `new-directive-dialog/transaction-form.tsx`, `balance-form.tsx`, `ledger-data/budget/add-budget-dialog.tsx`, `receipt/components/receipt-review-form.tsx` and the importer's `transaction-config-form.tsx`, all of which pass a typed currency to a ledger write. Only Transaction and Balance were exercised here; the other three need the same check confirmed. Account names are already validated client-side (w0/017) and are not affected.
