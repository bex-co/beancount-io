# Typing "4,50" in an amount field records 450, silently, wherever the decimal separator and the browser's language differ

**Major · dashboard · 50–70 minutes.** A2: a German, French, Dutch or Spanish speaker writes 4.50 as **4,50**. In an English-language browser, New Entry turns that into **450** and books it without a warning, a hundredfold error in the ledger. The reverse happens in a German-language browser: the ledger-style `4.50` becomes 450. The dashboard ships in 15 languages, nine of which use a decimal comma.

Production https://beancount.io, 2026-11-10, isolated headless Chromium 156 at 1440×1000, signed in as the owner of the designated synthetic ledger. The test entry was deleted and main.bean restored to blob `f1a0b83c`. Local main `520c67742`.

## Reproduce

1. Open `/ledger/<o>/<l>/journal?action=new-entry&directive=transaction` in a browser whose language is English (default en-US).
2. Narration `qa-comma`. Posting 1: `Expenses:Food:Coffee`, then type **`4,50`** in its amount. Posting 2: `Assets:Cash`, amount left blank. Click **Create Transaction Entry**.

**Actual:** while typing, the field changes to `450` (`value "450"`, `validity.valid: true`, `badInput: false`). "Entry created successfully" appears, and the ledger receives:

```
2026-11-10 * "qa-comma"
  Expenses:Food:Coffee                                  450 USD
  Assets:Cash                                          -450 USD
```

**Also:** in a context with locale `de-DE`, typing `1.234,56` yields `1.23456`, and `4,50` yields `450` in that headless run. Chromium's number-field separators follow the browser's UI language, which emulation may not fully reproduce; in a real German-UI Chrome, `4.50` is the input at risk.

**Expected:** an amount is never reinterpreted by the browser. Either the field accepts the decimal separator of the dashboard's language and shows exactly what will be booked ("Recorded as 4.50 USD"), or it refuses an ambiguous entry with a message. It must never silently store a different number.

## Root cause

`dashboard/src/common/components/exact-amount-input.tsx` renders a native `<input type="number" step="any">`. The browser parses the typed text with its own locale: in en-US `,` is a grouping separator, so `4,50` → `450`. The form only ever sees the sanitized `value`, so `transaction-form.tsx` (`parseDecimalNumber(posting.amount)`) cannot tell that anything was dropped. Every form sharing the component inherits this: New Entry (Transaction, Balance), Receipt Review and Add/Update Budget (w4/1021).

## Fix

- Switch `ExactAmountInput` to `type="text"` with `inputMode="decimal"`, keeping the exact-decimal ArrowUp/Down stepping and wheel guard it already implements.
- Parse the raw text with the importer's existing rules (`features/importer` `parseAmount` / `resolveDecimalConvention`: accounting signs, grouping, comma decimal only when unambiguous), copied into `common/` if needed.
- Use the active UI language's decimal separator as the tie-breaker. Refuse genuinely ambiguous input (`4,500` in a comma-decimal UI) with "Use 4500 or 4.5".
- Show the normalized value beside the field whenever it differs from what was typed.

Add tests: `4,50` → `4.50` under `de`; `4,50` → refused or `450` with a visible "Recorded as 450" under `en`; `1.234,56` → `1234.56` under `de`; and controls `-12.50` and `9007199254740993.01` unchanged.

## Blast radius

All `ExactAmountInput` users: `new-directive-dialog/transaction-form.tsx`, `balance-form.tsx`, `receipt/components/receipt-review-form.tsx` and `ledger-data/budget/add-budget-dialog.tsx`. The CSV importer already parses decimal commas (w4/164, w4/1054) and is not affected.
