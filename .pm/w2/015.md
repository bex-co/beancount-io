# Give the config an API public URL distinct from the OIDC issuer

From w2/m29:t002 review, deferred because it changes OAuth configuration.

`backend-v2`'s config has two URL fields — `dashboard.url` and `oauth.issuer` —
for three ideas: where the dashboard is, where the API gateway is, and what
identity the OIDC issuer claims. `config.ts` sets
`oauthIssuer = environment === "production" ? dashboardUrl : SERVER_URL`, and
`assertOAuthInteractionHost` refuses to boot when the issuer host differs from
`DASHBOARD_URL`'s.

Consequence, as shipped in m29: deriving the MCP manifest's `endpoint`,
`openapi`, and `auth` from the issuer is the real fix outside production —
`deploy/docker-mac` serves the dashboard on `:42600` and the API on `:42601`,
and the manifest now correctly names `:42601`. In production the two
expressions are the same string, so a production-mode deployment that genuinely
splits dashboard and API origins still advertises the dashboard origin, and has
no field in which to say otherwise.

Fix: add `AppConfig.api.publicUrl`, fed by `SERVER_URL` in every environment,
and derive the manifest, the 401's `WWW-Authenticate` pointer, and the OIDC
issuer from it. Then `assertOAuthInteractionHost` can keep guarding the cookie
requirement it actually exists for without forcing the API origin to equal the
dashboard's.

Until then, the manifest test fixture in `well-known-route.test.ts` exercises
`mcpManifest`'s own contract rather than a state the config module can build in
production — the comment there says so.
