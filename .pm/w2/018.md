# `bea add transactions` labels two different rows with the same row number

Found 2026-09-12 by a CLI QA sweep against HEAD `84231f9c`, bea 0.2.0, synthetic ledgers only. Sub-hour fix plus a regression test.

`bea add transactions --partial` builds its rejection list from two code paths that number rows differently, so a mixed batch reports two distinct input rows under the same label:

```
$ cat mixed.json
[
 {"date":"2024-03-01","narration":"schema-bad","postings":[{"account":"Expenses:Food","units":{"number":"1","currency":"USD"},"amount":"1 USD"},{"account":"Assets:Cash"}]},
 {"date":"2024-03-02","narration":"unbalanced","postings":[{"account":"Expenses:Food","units":{"number":"1","currency":"USD"}},{"account":"Assets:Cash","units":{"number":"5","currency":"USD"}}]},
 {"date":"2024-03-03","narration":"ok","postings":[{"account":"Expenses:Food","units":{"number":"2","currency":"USD"}},{"account":"Assets:Cash"}]}
]
$ bea --file main.bean add transactions --from mixed.json --partial
Error: Added 1 of 3 transactions; 2 rows were rejected.
  Row 1, postings.0: Value error, Use either amount or units for a posting, not both.
  Example posting: {"account":"Assets:Checking","amount":"-30 USD"}. Use bea add transactions --help for a complete row.
  row 1: .../main.bean:29: Transaction does not balance: (6 USD)
$ echo $?
1
```

Input row 1 (schema failure) prints as `Row 1` (1-based); input row 2 (accounting failure) prints as `row 1` (0-based). A single-failure batch shows it plainly too — a 2-row batch whose first row is unbalanced prints `row 0:`. An operator repairing "row 1" edits the wrong entry.

- Root cause: `cli/src/bea_engine/ledger/adding.py:419` formats schema rejections as `f"Row {index + 1}, {location}: ..."`; `adding.py:453` formats partial-recovery accounting rejections as `f"row {index}: ..."`. Both append to the same `details` list raised at `adding.py:466`.
- Fix: at `adding.py:453` use `index + 1` and the same `Row N:` prefix. Leave the JSON `result.written_rows` / `rejected_rows` zero-based — `cli/docs/USAGE.md:496-497` documents those as zero-based indexes and scripts consume them. Only the human `details` strings change.
- Blast radius: `adding.py:453` is the only 0-based human row string in the package. `cli/src/cli/commands/import_.py:403`, `bea_engine/importing.py:177,279` and `bea_engine/csv_mapper.py` already number rows from 1. Strict (no `--partial`) batches never reach `adding.py:453`, so they are already 1-based.
- Regression test: a `--partial` batch with one schema failure and one accounting failure must name two different row numbers, both 1-based.
- Dedupe: nothing on the board covers row numbering in `add transactions` (`w2/done/m24/done/t005.md` specified `--partial` without a numbering contract). `git log -S 'row {index}'` shows the string introduced by `a90b1706` (ADR014 engine split) and unchanged since — present on main, not deployment lag.
