# `bea engine status` reports "Provisioned: no" while the engine is serving every command

Found 2026-09-12 by a CLI QA sweep against HEAD `84231f9c`, bea 0.2.0, in an editable checkout. Sub-hour fix plus a docs line.

`bea engine status` reports only whether the *managed* engine directory is provisioned, never which of the launcher's three tiers is actually answering. In a checkout that reads as a broken install:

```
$ bea engine status
Engine 0.2.0 at /Users/you/.local/share/bea/engine/0.2.0
Provisioned: no
Optional features:
  beangulp: disabled, absent (GPL-2.0-only)
  beanprice: disabled, absent (GPL-2.0-only)

$ ls ~/.local/share/bea/engine/          # the named 0.2.0 path does not exist
0.1.0

$ bea --file main.bean check             # works fine anyway
$ echo $?
0

$ bea upgrade --check                    # this command *does* know
bea 0.2.0 (installed by: checkout)
```

So the one command a user runs when something engine-related looks wrong says the engine is not provisioned, names a directory that does not exist, and gives no hint that a checkout tier is serving the request. `bea upgrade --check` already resolves and prints the install channel in the same session.

- Root cause: `cli/src/cli/commands/engine.py:37` prints `Provisioned: {'yes' if status['provisioned'] else 'no'}` straight from `paths.is_provisioned(root)`. The launcher documents a three-tier resolution in `cli/src/cli/engine/launch.py:26-40` — an explicit `BEA_ENGINE_PYTHON`, a provisioned engine, then a checkout's `cli/src` via `paths.checkout_source_root()` (`launch.py:132-134`, `181-183`) — and `status` surfaces none of it.
- Fix: report the tier actually in use, not just provisioning. Add a line such as `Serving from: checkout (/path/to/cli/src)` / `managed engine` / `BEA_ENGINE_PYTHON override`, and mirror it in the `--json` envelope alongside the existing `provisioned` / `python_override` fields (`engine status --json` already carries `python_override`, so the shape is there). Reuse whatever `upgrade --check` uses to name the channel.
- Scope note: affects contributors and coding agents working in this repo, plus anyone who has set `BEA_ENGINE_PYTHON`. A Homebrew install (which sets `BEA_ENGINE_DIR`) and a provisioned PyPI install both report `yes` and are unaffected.
- Dedupe: `w1/done/m19/done/t002.md` covered the launcher handling provisioned and first-use paths — this is about `status` *reporting* the resolved tier, not about resolution itself, which works. `git log -S 'Provisioned:' -- cli/src/cli/commands/engine.py` shows the line added by `cc5ce3f9` (m20) and unchanged since; present on main, not deployment lag.

## Also found (docs, one line)

`cli/docs/USAGE.md:818-824` lists the environment variables bea honours — `BEA_CONFIG_DIR`, `XDG_DATA_HOME`, `BEA_API_URL`, `BEA_DASHBOARD_URL`, `BEA_NO_UPDATE_NOTIFIER`, `CI` — but omits `XDG_CACHE_HOME`, even though `USAGE.md:359-360` states that write locks live under `$XDG_CACHE_HOME/bea/locks`. Verified honoured: with `XDG_CACHE_HOME` pointed at a scratch directory, every lock file landed there and none in `~/.cache/bea` or beside the ledger. Add the row.
