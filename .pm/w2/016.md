# Publish MCP client setup from the manifest instead of hardcoding it twice

From w2/m29:t001 and t003 review. Cross-package duplication, so it is reported
rather than merged into a shared module.

The `claude mcp add --transport http beancount …` line and the `mcpServers`
JSON shape are now written independently in:

- `dashboard/src/features/user-settings/pages/api-keys/mcp-setup-config.ts`
- `cli/src/cli/commands/cloud/mcp.py`
- `README.md`, `backend-cluster/backend-v2/README.md`, and
  `backend-cluster/backend-v2/docs/mcp.md`

They have already diverged: the dashboard has a `curl` tab the CLI does not,
the CLI has a `json` client the dashboard does not, and `bcio_your_token` is
declared separately in both. The per-client config-file locations are hardcoded
in the CLI and, in the dashboard, live in `translations.ts` — where a file path
like `~/.cursor/mcp.json` is being translated into fifteen languages.

Both clients already fetch `/.well-known/mcp.json`. The natural single source is
a `setup` block there: per-client label, command template, and config-file
location by platform, with the key substituted client-side. That keeps client
knowledge in one deployable artifact instead of two packages and three
documents.

Smaller version if the manifest change is not wanted: lift the path table out of
i18n, keep one table per package, and stop translating file paths.
