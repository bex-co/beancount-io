# Flaky: `lazy-chart-error` fails intermittently under full-suite load

Observed while running the dashboard gate for w2/m29 on `main@26e71f59`.

`dashboard/src/common/components/react-echarts/__tests__/lazy-chart-error.test.tsx`
→ "contains a failed chart download in a stable panel with recovery" fails about
one run in three when the whole suite runs, and passes every time in isolation.

```
TestingLibraryElementError: Unable to find role="alert"
<div style="height: 320px;" />
```

The panel is still in its loading state when `findByRole("alert")` gives up, so
the lazy chart import has not rejected yet. Under full-suite load the dynamic
import is slow enough to outlast the default `findBy` timeout.

Not caused by that milestone — it touches no chart code — and the suite is green
on repeat runs, so it was not treated as a blocker. It is a real flake and will
eventually redden CI on an unrelated change.

`/routine-flaky-test-fixer` is the tool for this: root-cause the race (likely an
unawaited rejection or a timer the test does not control) rather than raising the
timeout.

---

**Resolved 2026-09-12** — root-caused rather than timed out, and the note's guess ("an
unawaited rejection or a timer the test does not control") was right on both counts: there
were two races, and fixing either one alone left the test flaky.

Measured first. The test passed on this machine but spent 686–763ms of `findByRole`'s hard
1000ms budget under full-suite load, against 375ms in isolation — the margin *was* the flake.
Instrumenting the phases showed the import cost 0.6ms and the render 10.8ms, while
`findByRole` waited 352ms. So it was never the chunk download. Polling the DOM every 40ms
showed the Suspense fallback (`ReactEChartsServer`, the bare `<div style="height: 320px">`
from the failure report) held for ~344ms before the error boundary appeared, and a tick
counter put that at ~240 macrotask yields — not one long timer.

Two false leads, checked and discarded: the mock factory does not re-run per retry (3 calls
total), and warming the global `use-translations` mock's async locale import costs 0ms.

The actual cause: when the lazy chunk rejects, React queues the retry on a low-priority lane
and keeps the Suspense fallback up until its concurrent scheduler works through it.
`findByRole` only polls the DOM — it never drives that scheduler — so the test was waiting
for React to make progress on its own. Those yields are budgeted in wall-clock time slices,
which is exactly why the wait scaled with contention and approached the 1s ceiling.

`await act(async () => {})` drains the queued work: ~13ms instead of ~300ms. But on its own
it still failed 5 of 20 runs, because of the *second* race — `index.tsx` prefetches the
client chunk at module scope without awaiting it, and `React.lazy` starts its own import on
first render, so sometimes React had no rejection to report yet when `act` flushed.

Fix is both: `await expect(import("../client")).rejects.toThrow()` settles the chunk before
rendering, then one `act` flush drains the retry. Nothing timing-dependent is left, and the
polling window is gone entirely — the test now uses `getByRole`, not `findByRole`.

Verification: 20 consecutive isolated runs green (the same 20 that failed 5 times with `act`
alone), 4 consecutive full-suite runs green (347 files, 3879 tests), and the test now takes
95ms under full-suite load versus 686–763ms before. `yarn format:check`, `yarn lint`, and
`yarn build` green.
