# Replace prose-matched error hints with typed metadata

From w2/m28:t007 (`/simplify`), deferred because it touches throw sites and the
ledger IDL.

Two places decide behavior by matching on an error's wording:

- `mcp-errors.ts` `MESSAGE_HINTS` picks an actionable hint by regex over the
  message. `envelopeFromThrown` already prefers `DomainError.metadata.hint` when
  present, so the table is a shadow copy of data the throw site could carry.
  `/scope/i` is broad enough to hijack any message containing "ledgerScope".
- `ledger-entry-service.ts` `unbalancedOrValidationError` decides `UNBALANCED` vs
  `VALIDATION_FAILED` with `/does not balance|residual/i` over bean-check output,
  and scrapes the residual amount with a second regex.

Cost: a reworded message silently degrades a hint or downgrades an error code, and
no test can catch it. It also inverts the repo rule that tests assert `category`
and `metadata`, not prose — here prose *produces* the category.

Fix: attach `hint` in `metadata` at the ~7 throw sites the audit named and delete
`MESSAGE_HINTS`, keeping `CATEGORY_HINTS` as the fallback; and have the ledger
service's projected-check response carry a typed error kind plus residual so the
classification reads a field.

---

**Resolved 2026-09-12** — both halves done, and one of them turned out to be a live bug
rather than only a fragility.

**`MESSAGE_HINTS` is gone.** The hint is now the throw site's to declare: `DomainError`
subclasses (`BadUserInputError`, `ForbiddenError`, `NotFoundError`, `ValidationError`,
`OperationNotAllowedError`) take an optional trailing `hint` folded into `metadata`, the way
`UnbalancedTransactionError` already did. The four refusals the table covered now carry
their own — ledger selection and the pin ceiling in `mcp-context.ts`, the missing-file read
in `mcp-resources.ts` (which was throwing a bare `Error`, so it is a real `NotFoundError`
now), and the rename include-refusal in `ledger-workflow.ts`. `CATEGORY_HINTS` stays as the
fallback. The "changed since it was loaded" entry needed no throw-site change: it is raised
in the ledger package and `CATEGORY_HINTS[CONFLICT]` already gives the same advice.

The `/scope/i` entry is deleted with the rest, and a test pins that a message containing
"ledgerScope" no longer hijacks the hint.

**Classification reads a field.** The ledger engine has been emitting a stable `code` all
along — verified against the WASM directly: an unbalanced transaction is `E3001`, a failed
balance assertion `E2001`, an unopened account `E1001`. `toBeancountErrorsPublic` was
dropping it, which is *why* backend-v2 had to regex the prose. The IDL's
`BeancountErrorPublic` now carries `code` and the engine's own `hint`, the ledger mapper
passes both through, the fava client is regenerated, and `unbalancedOrValidationError`
branches on `code === "E3001"`.

That fixed a real misclassification, not just a fragility: the old
`/does not balance|residual/i` also matched `"Balance failed for Assets:Cash: expected
999.00 USD, got residual -3.00 USD"`, reporting a failed balance assertion as an unbalanced
transaction. There is a test for exactly that message now.

Fallback preserved: an error with no `code` still classifies by wording, so a deployment
whose ledger service predates this degrades to the old behaviour rather than calling
everything a validation failure.

**Left as-is, deliberately:** the residual is still scraped from the message with a regex.
The engine emits no separate residual field — only the code and the prose — so there is
nothing typed to read. It is now scoped to messages already identified as `E3001` rather
than deciding the classification, which is the part that mattered.

`backend-v2`: `yarn typecheck`, `yarn test` (282 suites, 4417 tests), `yarn generate-v1-openapi`
(no diff), `yarn generate-fava-client` (10-line additive diff) green; `yarn lint` reports only
the pre-existing unused `AppLinksConfig`. `ledger`: `yarn typecheck`, `yarn lint`, `yarn test`
(65 suites, 908 tests) green.

Not verified live: unit and service-seam tests only.
