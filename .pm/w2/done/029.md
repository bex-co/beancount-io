# Report malformed OAuth discovery as a server problem before sign-in

**Severity:** minor. **Estimate:** 30–45 minutes. **Package:** mobile. **Goal:** A2 — self-hosted users get actionable server guidance instead of repeatedly retrying an authentication flow that never starts.

**Environment:** 2026-09-21, `main` at `98359325`, current Metro JavaScript; native `io.beancount.ios` 1.20260906.47 (47), iPhone 17e / iOS 26.5, English, ordinary text size, light appearance. Signed out. This is a controlled live-native failure test using an anonymous loopback HTTP responder, not evidence of a hosted-service outage. No credentials, ledger, fabricated session or authorization grant is involved.

## Repro

1. Run a loopback responder at `http://127.0.0.1:18473/`. For `POST /invalid-json/api-gateway/`, return HTTP 200 JSON `{"data":{"health":"OK"}}`. For `GET /.well-known/oauth-protected-resource/invalid-json/v1`, return HTTP 200, `Content-Type: text/html`, body `<html><body>QA reverse-proxy landing page</body></html>`. The second response models a proxy serving its HTML fallback at the metadata URL.
2. In the native development build, follow Welcome's gear to Server. Enter `http://127.0.0.1:18473/invalid-json/` and tap **Test connection**. It correctly reports **“This server does not expose the required Beancount.io API.”** Saving a valid URL despite an unsuccessful connection test is intentionally allowed.
3. Tap **Save**, then **Sign In**. No authorization browser opens. The only request is the anonymous protected-resource metadata GET above. Welcome instead says **“Could not complete sign-in. Please try again.”**
4. Terminate and relaunch the native app, dismiss the development packager warning, and tap Sign In again. The same generic retry message appears for the same response.

Expected: identify the selected server's incompatible discovery response and direct the user toward server configuration, using the existing server-error message. Actual: a discovery parsing failure becomes the generic rejected-sign-in outcome even though no credentials were requested or submitted. Retrying authentication cannot repair the metadata.

## Root cause and fix

`mobile/src/common/oauth/discovery.ts:94–110` wraps only the `fetcher()` rejection in `OAuthDiscoveryError`; the `response.json()` call at line 108 is outside that classification. HTML under HTTP 200 throws a plain `SyntaxError`. `start-authorization.ts:17` passes discovery directly into the launcher, which awaits it before creating the browser flow. `screens/welcome/native-sign-in-runner.ts:27–32` recognizes only typed discovery failures; every other exception becomes `rejected`. Welcome's `failureMessageKey` at `screens/welcome/index.tsx:75–85` therefore selects `signInFailed` instead of `serverConnectionIncompatible`.

Normalize malformed discovery payloads to `OAuthDiscoveryError("incompatible", ...)` at the discovery boundary, with sanitized details. Preserve genuine transport failures as unreachable, cancellation semantics, issuer/resource validation and the deliberate ability to save a valid offline server URL. Do not mask authentication/code-exchange failures as server-configuration errors. Inspect endpoint-validation exceptions in this same discovery boundary as adjacent cases; they were not separately reproduced here.

**Acceptance:** a 200 HTML or malformed-JSON metadata response produces the server-incompatible message on native Sign In, starts no browser or token exchange, and leaves the action available for retry after changing the server. Cover both protected-resource and authorization-server metadata parsing with the real discovery function and its outcome mapping. Preserve successful discovery, HTTP error handling, network failure and browser cancellation. Sign Up shares this runner and needs regression coverage too.

## Controls, dedupe and limits

The native Server screen is the working control for this exact response: `testServerConnection` catches the rejected discovery promise and reports an incompatible server. Earlier in this same run, the actual hosted server passed Test connection and native Sign In reached its browser consent page, which was cancelled. A diagnostic loading the unchanged discovery and native runner modules against the local responder additionally records: HTML → `SyntaxError` / `rejected`; HTTP 503 → typed `incompatible`; valid metadata → compatible. This diagnostic supports the traced cause; the screenshots establish the native behavior.

Searched every `.pm` queue, including completed and blocked work, for `OAuthDiscoveryError`, malformed/parsed metadata, discovery errors, incompatible sign-in and related terms; scanned open milestones. No overlapping item exists. Completed `w1/m4` and `w1/m6` require useful server-error guidance; the `321f870a` classification change still leaves this parse call outside its typed handling. `git log -S 'response.json()'` traces the parser to `7682c4e4`. Completed [w4/059](../w4/done/059.md) concerns a missing OAuth callback, a different stage. ADR013's proposed verified-HTTPS redirect migration does not change this pre-browser failure. This is current client behavior, not deployment lag.

Verified ignored evidence under `mobile/tmp/qa-20260921/`: `malformed-server-draft.json`, `malformed-connection-result-0.jpg`, `malformed-sign-in-result-0.jpg`, `malformed-sign-in-fresh-0.jpg`, `connection-probe.mjs`, `connection-probe.log`, `probe-malformed-body.html` and `discovery-cause-control.json`. The responder logs only method, path and timestamp. Only a signed-out local server preference was saved; the native Restore default action and subsequent field inspection confirmed `https://beancount.io/` was restored. No production ledger or account data changed. No fix or shipping performed.

Unverified: native Sign Up for this response, the second metadata endpoint, HTTPS proxy deployment, Android, physical hardware and release builds. Loopback HTTP is used only under the development build's existing localhost exception; that policy is outside this fix.

---

**Resolved 2026-09-23** — `fetchJson` now turns a body that fails to parse as JSON into `OAuthDiscoveryError("incompatible")`. Before, it escaped as a plain `SyntaxError`, which the runner reported as `rejected`. The adjacent endpoint checks (missing, malformed, or off-issuer `authorization/token/revocation_endpoint`) are classified the same way through `discoveredEndpoint`. So Welcome shows `serverConnectionIncompatible` for Sign In and Sign Up (one shared runner) and starts no browser. Transport failures stay `unreachable`. HTTP errors, issuer/resource validation and cancellation are unchanged. Two new discovery tests cover HTML-under-200 on both metadata documents and the three endpoint failures; both fail against the previous `discovery.ts`. Mobile format, lint, typecheck and 1878 unit tests pass. Not re-run on the native simulator. Shipped in `mobile`.
