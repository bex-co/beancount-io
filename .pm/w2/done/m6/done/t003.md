## Objective

Write `references/dedup.md`, the centerpiece convention: every imported entry carries `import-id: "<source>:<stable-id>"` transaction metadata — the source's native transaction ID when one exists (e.g. OFX FITID), else `sha256` of the normalized `date|amount|payee|source-account` — plus the two-layer dedup procedure that makes re-imports idempotent.

## Context

- Plain-text-native dedup must live **in the ledger itself** (metadata), not in a side database, so any tool — this skill, other importers, future integrations — can recognize already-imported entries.
- Layer 1: exact — scan existing entries' `import-id` metadata for the candidate's ID; match → skip, counted in the review table.
- Layer 2: fuzzy — for pre-existing manual entries without metadata: date-window + amount + payee similarity → flagged as *suspected* duplicates for the user to decide; never silently skipped, never silently double-entered.

## Steps

1. Specify the `import-id` grammar with examples (`ofx:<FITID>`, `csv:sha256:<hex>`), and the normalization rules feeding the hash.
2. Specify both dedup layers, the suspected-duplicates review flow, and the idempotency guarantee (re-importing the same file → zero new entries).
3. Note the convention is deliberately tool-agnostic so other beancount tooling can adopt it; keep the spec self-contained in this reference.
