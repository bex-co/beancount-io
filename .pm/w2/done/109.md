# A renamed file shows as an empty section in commit diffs

**Minor · dashboard · 30–40 minutes.** A1/A2: agents rename files through `renameLedgerFile` (MCP, REST and GraphQL all share `ledger-workflow.ts:~1392`, commit message `Rename <old> → <new>`), and the dashboard's Version History is where the owner reviews that change. It should say what happened to each file. A pure rename shows only the new name above an empty body, with no hint that it was a rename or what the old path was.

Production https://beancount.io, 2026-11-10, English, isolated headless Chromium 156 at 1440×1000, signed in as the owner of the designated synthetic ledger. Read-only (the commit was made by a sibling QA loop's rename probe). Local main `76738bba0`.

## Reproduce

1. On a ledger you can write to, rename a file through the MCP `renameLedgerFile` tool or the REST/GraphQL equivalent (for example `qa/r2.bean` → `qa/r.bean`) without editing it. The dashboard has no rename action.
2. Open the resulting commit, `/ledger/<o>/<l>/commit/<sha>` (observed: `1ef5997`, "Rename qa-20261110/r2.bean → qa-20261110/r.bean").

**Actual:** the header reads "2 files · +1 · −1". The `main.bean` section shows the include change. The second section shows only the heading **`qa-20261110/r.bean`** with nothing under it: no old path, no "renamed" label, no "no content changes" line. Its anchor `#diff-file-qa-20261110%2Fr.bean` jumps to that empty section.

**Control:** the `GetCommitDetails` response for the same commit carries the full rename:

```text
diff --git a/qa-20261110/r2.bean b/qa-20261110/r.bean
similarity index 100%
rename from qa-20261110/r2.bean
rename to qa-20261110/r.bean
```

`files[]` lists `{"filename":"qa-20261110/r.bean","additions":0,"deletions":0}`.

**Expected:** the section heading says `qa-20261110/r2.bean → qa-20261110/r.bean` (or carries a "Renamed from qa-20261110/r2.bean" line). A rename without content changes shows a short "File renamed without changes" body.

## Root cause

`dashboard/src/common/components/diff-viewer/diff-viewer.tsx` renders every file heading from `getDiffFilePath(file)` (new path first, lines ~54-55), in both the small view (~line 368) and the virtualized row (~line 303). `react-diff-view`'s `parseDiff` already returns `type: "rename"` and `oldPath` for this patch (w3/482 relies on that `oldPath` for focus aliases), but neither value is shown, and an empty `hunks` array renders as nothing.

## Fix

In both header renderers, when `file.type === "rename"` and `oldPath !== newPath`, show `oldPath → newPath`. Keep the section `id` on the new path so existing links and w3/482's canonical-first focus rules still hold. When `hunks.length === 0`, render a muted localized line: "File renamed without changes" for a rename, and an equivalent for a mode-only change. Add the keys in all 15 locales. Cover both views with the real parser in `common/components/diff-viewer/__tests__/`, using this exact patch text.

## Blast radius

`DiffViewer` is shared by commit detail and pull-request diffs (`features/git/pull-requests`). Both gain the label. The file list (`commit-file-list.tsx`) shows only `filename` and is out of scope.

## Dedupe

Searched `.pm/**` for rename together with diff/commit, `rename from`, and `oldPath`. w3/482 fixed rename *paths and focus* (and `/dev/null` headings); w4/263 fixed header tab separators. Neither displays the rename. No existing item.

---

**Resolved 2026-11-10** — shipped in this commit (`dashboard`). `DiffViewer`
headings name both sides of a rename, `qa-20261110/r2.bean →
qa-20261110/r.bean`, in the small view, the virtualized rows and the
virtualized view's current-file bar. The section id stays on the new path,
so existing links and w3/482's canonical-first focus rules are unchanged. A
file with no hunks gets a muted body line: "File renamed without changes"
for a rename, "No line changes to show" otherwise. Two new keys
(`commits.renamedWithoutChanges`, `commits.noLineChanges`) are in all 15
locales.

Deviation: rename detection keys on `oldPath !== newPath` (neither
`/dev/null`) rather than `type === "rename"`: the parser reports an edited
rename (`similarity index 90%`) as `type: "modify"`, and that heading should
name both paths too. The parser does not record a mode-only change, so it
shares the generic line with binary changes rather than a mode-specific
message.

Validation: four new cases in `diff-viewer.test.tsx` use the recorded patch
text (both views), a mode-only patch and an edited rename; the two existing
virtual rename-focus cases now expect the `old → new` heading with the id on
the new path. All six fail against the previous viewer. `yarn format:check`,
`yarn lint`, `yarn test` (773 files, 7711 passed, 1 existing skip) and
`yarn build` pass; secret scan clean. Not verified against production before
the next dashboard deploy.
