# Route `appendDirectiveText` through `LedgerRepoService`

From w2/m28:t007 (`/simplify`), deferred because it changes authorization semantics.

`LedgerEntryService.writeDirectiveText` drives the raw Fava client to read files,
bean-check a projection, and commit. `LedgerRepoService` already exposes all three
(`getFilesContent`, `checkProjectedFiles`, `changeFiles`) with per-operation
`assertSafeRepoPath` and a `dryRun` mode — and `editLedgerFiles` runs the identical
read → project → commit sequence through it.

Cost of leaving it: a second write path into the repository that repo-service guards
do not cover; auto-routed target paths skip the per-operation path assertion the
repo service applies.

Why it was not done in m28: delegating means the call also selects
`LEDGER_FILES_WRITE` alongside `LEDGER_ENTRIES_WRITE`, which narrows the credential
ceiling. That is a deliberate contract decision, not a refactor.

Shape: an append workflow (CLAUDE.md puts multi-step coordination in `workflow/`)
that parses and routes with the pure `directive-text` utils and calls
`ILedgerRepoService`; the service keeps its `authorizeLedger` + delegate. Confirm
first whether both actions resolve to the same ledger-writer relationship — if they
do, the ceiling does not actually narrow and this is behavior-preserving.

---

**Resolved 2026-09-12** — done, and the deferral's premise turned out not to hold.

The note asked to confirm first "whether both actions resolve to the same ledger-writer
relationship — if they do, the ceiling does not actually narrow." They do.
`authorization-service.ts` declares `LEDGER_FILES_WRITE` and `LEDGER_ENTRIES_WRITE`
identically: same relationship (`ledger` → `write_contents`), same
`LEDGER_CONTENT_WRITE_CREDENTIAL`, same `write` audit class. So delegating narrows nothing;
the only change is one more audit row per append, which is honest — the operation does
write files.

`DirectiveAppendWorkflow` (`workflow/directive-append-workflow.ts`) now owns the
coordination — parse, route, read, project, check, commit — and every repository step goes
through `ILedgerRepoService`. `LedgerEntryService.appendDirectiveText` keeps its
`authorizeLedger(LEDGER_ENTRIES_WRITE)` and delegates. `writeDirectiveText` is gone from the
`ILedgerEntryWriter` seam; the receipt workflow only ever used `writeBulkEntries`. Shared
vocabulary (`AppendDirectiveTextInput`/`Result`, `MAX_APPENDED_DIRECTIVES`,
`unbalancedOrValidationError`) moved to `utils/directive-text-contract.ts` so neither the
service nor the workflow imports the other.

The gap this closes: auto-routed targets are now asserted. `assertSafeRepoPath` previously
ran only on a caller-supplied `path`, so a target produced by the ledger's own
`resolveEntryFile` rules reached the commit unasserted. The repo service asserts every
operation it is handed, so routed and explicit paths are guarded the same way.

Two things found while doing it, both fixed rather than left:

- `changeFiles` did not translate pre-receive-hook failures (directive limit, push policy),
  which have no HTTP response to classify — they surfaced as generic internal errors. The
  entry service's own commit path always translated them, so routing appends through the
  repo service would have silently lost that. `changeFiles` now carries
  `operationNotAllowedFromCause`, which every other caller wanted too.
- The batched `getFilesContent` read replaces one `getLedgerFile` call per target. The ledger
  service's `files-content` endpoint filters missing files out of the result rather than
  erroring, which is how a `create` still tells itself apart from an `update`.

Tests: a new 9-case `directive-append-workflow.test.ts` covering the routed-target commit,
plain-text (not base64) hand-off, create-vs-update, projection-refusal and `allowInvalid`,
the dry-run stop, unsafe-path and batch-size refusals, and the single batched read. The
existing `directive-text-parity` suite now drives the real new path through a real
`LedgerRepoService` on all three surfaces and passes unchanged in intent.

`yarn typecheck` and `yarn test` (281 suites, 4408 tests) green; `yarn lint` reports only
the pre-existing unused `AppLinksConfig` export in `config.ts`; `yarn generate-v1-openapi`
produced no diff.

Not verified live: service-seam tests only, no docker-mac run.
