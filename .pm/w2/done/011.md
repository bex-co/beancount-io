# REST `PUT …/files/{path}` sends raw UTF-8 where the ledger service expects base64

Found during w2/m26 live verification (docker-mac): `PUT /api-gateway/v1/ledgers/{owner}/{name}/files/{path}`
with `{"content": "<utf-8 text>"}` fails with `BAD_USER_INPUT: illegal base64 data`,
because `LedgerRepoService.changeFiles` forwards `content` verbatim to the ledger
service's `change-files`, which passes it to Gitea as base64. The MCP
`editLedgerFiles` tool base64-encodes before the same call, so it works; only the
REST file-write path is broken. Pre-existing on main, out of m26's scope
(m26 covers the MCP write path; not in t001–t006).

Suggested fix (one place): base64-encode `body.content` in the REST files handler
or `LedgerRepoService.changeFiles`, plus a live roundtrip (PUT → GET bytes equal)
and a parity unit test. Keep the OpenAPI description ("full new content, as UTF-8
text") — the encoding stays an internal detail.

---

**Resolved 2026-09-12** — fixed in the one place the note suggested,
`LedgerRepoService.changeFiles`, which now base64-encodes `content` before the ledger
service call. Base64 is that service's wire encoding (it forwards to Gitea), not this
service's contract: `getFilesContent` already decodes and `checkProjectedFiles` already
encodes, so encoding here is what makes `content` mean plain UTF-8 text in both directions.
A caller that reads a file, edits the text, and writes it back no longer has to know.

The three `Buffer.from(...).toString("base64")` calls in the MCP `editLedgerFiles` tool are
gone with it — that tool was working only because it happened to encode first, and leaving
them would have double-encoded every agent write.

Tests: a REST-level regression on `PUT …/files/{path}` asserting the handler passes the
caller's UTF-8 text through, a service-level encode assertion with non-ASCII content, a
delete case (no content to encode), and a read → edit → write round-trip proving the bytes
survive. The OpenAPI description stays "full new content, as UTF-8 text" — it was always
the truth the code failed to honour.

`yarn typecheck` and `yarn test` (280 suites, 4399 tests) green; `yarn generate-v1-openapi`
produced no diff.

Not verified live: this was fixed and tested against the service seam, not re-run against a
docker-mac stack.
