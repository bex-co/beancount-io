# Import preview calls an impossible date a format error

**Minor · dashboard · 25–35 minutes.** A2: a reader fixing a CSV is told to use YYYY-MM-DD for a date that is already written in YYYY-MM-DD, so they look for the wrong mistake. This is the dashboard counterpart of the CLI's [w5/330](../w5/done/330.md).

Production https://beancount.io, 2026-11-10, English and zh, isolated headless Chromium 156, signed in as the owner of the designated synthetic ledger. Preview only. Local main `78b4cb37f`.

## Reproduce

Choose a CSV containing `2026-02-30,qa-g,bad date,-1.00` (`2026-04-31` and `2026-13-01` take the same code path; not exercised) on `/ledger/<owner>/<ledger>/import`.

**Actual:** the date cell and the diagnostic line say **"Invalid date format. Expected YYYY-MM-DD"** (zh: `日期格式无效。预计年-月-日`). A genuinely misformatted `09/07/2026` gets the same text.

**Expected:** a well-formed date that is not on the calendar says so, for example "2026-02-30 is not a calendar date". The format message stays for `09/07/2026`.

## Root cause

`dashboard/src/features/importer/utils/csv-validator.ts:35-57` `parseDate` already separates the cases ("Invalid date format…" vs "Invalid date value"). But `utils/row-edit-schema.ts:32-37` refines on `parseDate(val).valid` alone and always reports `importer.validation.invalidDateFormat`. No localized key exists for the value case.

## Fix

Return a structured reason from `parseDate` (`format` | `value`), in the same way `parseAmount` reports `AmountParseFailureReason`. Use `superRefine` in the schema to pick `invalidDateFormat` or a new `importer.validation.invalidDateValue` key, added to all 15 locales. Extend `utils/__tests__` / `editable-preview-row.test.tsx` with `2026-02-30` (value) and `09/07/2026` (format).

## Dedupe

w3/142 and w4/972 used `2026-02-30` as a control and recorded the format text without questioning it. w5/330 fixed the same wording in the CLI. No dashboard item exists.
