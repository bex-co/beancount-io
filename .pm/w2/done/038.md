# Keep transaction source and balance context available to mobile readers

Severity: **minor**. Estimate: **45–60 minutes**, mobile only. A2 — a newcomer exploring a public ledger should be able to inspect the source and balance changes behind an ordinary transaction without acquiring permission to edit it.

## Reproduce

2026-10-08; native `io.beancount.ios` development build `1.20260906.47`/47, current mobile JS `1.20261002.50` from local Metro, source HEAD `674a9f64` (mobile unchanged after pulling `39146e52`). Sole booted **iPhone 17e**, iOS 26.5, 390×844 logical points; English, System/light, default large text. Selected server `https://beancount.io/`, no local override. Existing authenticated session, public read-only `open_ledger/example`; the user-designated QA environment path was unavailable, so fresh dedicated-account OAuth authentication remains unverified. No account identity or private ledger data is needed for this reproducer.

1. Open the drawer → **Browse ledgers** → **Explore**, search `example`, and open `open_ledger/example`.
2. In Transactions, open **Cafe Modagor**, September 8, 2017, narration **Eating out with Julie**, amount **−$33.71**. Its real hash is `aff1ee23d8f70c970c137b006b4d8a62`.
3. Wait for detail to settle. The ordinary transaction and two Money flow postings render, followed by empty space. There is no **Entry Context** disclosure, source location, source text, or balances-before/after panel.
4. Terminate and relaunch the native app, then tap the same entry in Home's **Recent Transactions**. The same missing panel persists. Dismiss the development warning banner; its dismissal does not restore the panel.

Expected: source-backed transactions expose their read-only context to a reader; editing/deletion remain separately permission-gated. The mobile README promises inspection of postings and balance context (`mobile/README.md:53`). Generated transactions without source keep their existing generated-entry behavior.

Actual: the display-only context panel requires write access even though context is readable and the screen already requests it.

## Evidence and controls

An independent **anonymous**, real production GraphQL control returns HTTP 200 without errors for `getLedgerEntryContext` on this public ledger/hash:

```text
entry.flag: *
entry.meta: {filename: "main.bean", lineno: 3047}
slice: 2017-09-08 * "Cafe Modagor" "Eating out with Julie"
       Liabilities:US:Chase:Slate  -33.71 USD
       Expenses:Food:Restaurant    33.71 USD
balances_before: Restaurant 12050.12 USD; Slate -2669.58 USD
balances_after:  Restaurant 12083.83 USD; Slate -2703.29 USD
```

This is a read control, not the native authenticated response or injected data. The native transaction's postings and hero amount agree with it. Files → `main.bean` renders the explicit **This ledger is read-only** banner with no Save action. After rebuilding the native client and clearing Metro's stale cross-checkout DOM cache, its actual syntax-colored source renders correctly. The independent anonymous file response is HTTP 200, `type: file`, `encoding: base64`, `size: 318015`; this passing source-reader control does not restore the detail panel. The missing panel repeats on that clean bundle from Home → Cafe Modagor (`cafe-clean-bundle-context-0.png`). The initially blank file editor was a local bundler-cache issue and is discarded as a bug candidate.

## Cause and repair

- `mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:427` defines `entryHasEditableSource = canWrite && !isGenerated`; line 608 uses it to mount **EntryContext**.
- The ordinary-source query at lines 276–282 is already independent of write access. The panel at `screens/transactions-screen/entry-context/index.tsx:266` only expands read-only Text/source/balance content; it has no editing or deletion action.
- Separate source availability from permission to mutate. Render ordinary readable context with its existing loading/error/empty states; keep `showWriteActions`, edit/delete handlers, checksum requirements, and generated-source exclusions intact.

Blast radius: the shared detail screen serves `app/(app)/transaction-detail.tsx` and `app/examples/transaction-detail.tsx`; Home, Transactions, account detail, Reports, merchant detail, and entry links use that screen. Home and Transactions were exercised natively. Signed-out examples and the other entry points are source-derived scope, not independently confirmed failures. No REST/GraphQL/MCP contract, backend authorization, dependency, or cross-package import needs changing.

Acceptance: a native public reader can expand the ordinary Cafe entry's actual source and the two before/after balances, while its menu retains only authorized read actions. Add meaningful rendered coverage distinguishing source availability from reader/writer access, generated entries, context loading/read failure, and permission loss; preserve existing writer actions. Recheck light/dark and run mobile's normal gates when implementing.

Dedupe: searched every `.pm` state for Entry Context, balance context, readers, hidden panels, write permission, and `entryHasEditableSource`, and scanned open milestone scopes. `w4/done/m4` covers discovery/write gating and source-file viewing; `w4/done/058` fixes balance-row text layout; `w3/done/106` fixes the missing write-action-selector import; dashboard context milestones concern other code. None fixes this native panel gate. `221f5a4e` introduced the write restriction during discovery work, and `75d45df6` retained it while extending generated-entry handling. Current main still contains it; this is not deployment lag.

Unverified: fresh QA OAuth login, signed-out preview, writer UI, expired/denied/network-failure states, actual VoiceOver speech, enlarged text, Android, and physical hardware. No product fix or production mutation was performed.
