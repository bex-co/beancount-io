# New Entry accepts a 29-digit amount, then the ledger's refusal ("is not a decimal number") reaches the reader as "Some of the information provided is invalid"

**Minor · dashboard (+ ledger wording) · 25–35 minutes.** A2: a pasted account number or a slipped key can easily produce a 29-digit amount. Since w21/997 the ledger service refuses more than 28 significant digits, the most the engine's Decimal holds, so nothing wrong is written. The dashboard never says why: its amount fields accept the number, and the refusal comes back as the generic invalid-input toast. The server's own text is misleading too, because a 29-digit integer *is* a decimal number. Mobile refuses it in the form ([w21/997](../w21/done/997.md)); this is the dashboard counterpart.

Production https://beancount.io, 2026-11-10, English, isolated headless Chromium 156 at 1440×1000, signed in as the owner of the designated synthetic ledger. The write was refused, so nothing changed (main.bean blob `f1a0b83c`). Local main `656479913`, which includes the w2/120 amount-field rewrite.

## Reproduce

1. Journal → **New Entry** → Transaction. Narration `qa-29digits`. Posting 1: `Expenses:Food:Coffee`, amount `99999999999999999999999999999` (29 nines). Posting 2: `Assets:Cash`, amount blank.
2. **Create Transaction Entry**.

**Actual:** the form accepts the amount and submits. `BulkEntries` answers `BAD_USER_INPUT: entry 0: postings[0].units.number "99999999999999999999999999999" is not a decimal number`. The dialog stays open with the toast **"Some of the information provided is invalid. Please check and try again."** Nothing points at the amount, or at the 28-digit limit.

**Expected:** the amount field refuses more than 28 significant digits as it is typed: "Amounts can have at most 28 digits." The server's refusal, if it is ever reached, says the same thing.

## Root cause

- Dashboard: `ExactAmountInput` and its typed-amount parser (`common/components/exact-amount-input.tsx` and the w2/120 helper) and `parseDecimalNumber` (`common/lib/beancount/decimal-number.ts`) check only the number's shape, not its digit count. The same fields back Balance, Add/Update Budget and Receipt Review.
- `common/lib/errors/error-message.ts:199` (`INVALID_TOKEN`) recognizes `… is not a valid account|currency|tag|link|flag`, but not `… is not a decimal number`, so this refusal falls through to the generic key.
- Ledger: `backend-cluster/ledger/src/foundation/rustledger/entry-build.ts:51–70` (`fitsEngineDecimal`, called from `isDecimalNumber`) folds "too many digits" into the shape check, so the caller can only say "is not a decimal number".

## Fix

- **Dashboard:** in the typed-amount parser, refuse more than 28 significant digits (integer plus fraction, leading zeros ignored) with the form's inline error, as mobile's `parseExactAmount` does. Map `… units.number "…" is not a decimal number` (and the more specific message below) to "This amount can't be read: use at most 28 digits." Locale keys go in all 15 languages.
- **Ledger:** split the check, so too many digits answers `units.number "…" has more than 28 significant digits`. This is the same field and status, with a truthful reason. REST, GraphQL and MCP share it, so parity holds.
- Tests: 28 digits accepted, 29 refused, with and without a fraction (`999999999999999999999999999.99`), in New Entry and Add Budget. Add an error-message case for the server text.

## Blast radius

New Entry (Transaction, Balance), Add/Update Budget and Receipt Review amount fields. Smart Import already refuses inexact CSV amounts in Preview (`parseAmount`). Entry Context and the file editor send source text and were not checked here.

(`backend-cluster/ledger`, `729d03708`): a structured write's amount past 28
digits is refused as `entry 0: postings[0].units.number "…" has more than 28
significant digits` — same field, same 400 — instead of "is not a decimal
number"; `decimalNumberRefusal` in `entry-build.ts` replaces `isDecimalNumber`,
and REST, GraphQL and MCP pass the ledger's text through. Dashboard (this
commit): `exceedsLedgerDigits` in `common/lib/beancount/decimal-number.ts`
counts digits as the ledger does (leading zeros aside, every fraction digit),
and New Entry Transaction and Balance, Add/Update Budget and Receipt Review
refuse such an amount with "Amounts can have at most 28 digits." — as it is
typed in the three `onChange` forms, on submit in Receipt Review.
`error-message.ts` maps both server texts to `common.errors.amountTooLong` and
`common.errors.invalidAmount` ("“…” isn't an amount the ledger can read. Write
it as a number of at most 28 digits."), which also covers production's older
wording until the ledger deploys. Keys in all 15 locales. Deviation: the field
refuses through the form's validation message rather than inside
`ExactAmountInput`, so the message is not repeated. Tests: ledger
`entries-amount-syntax.test.ts` asserts the new text (three fail against the
