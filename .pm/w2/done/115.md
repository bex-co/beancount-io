# Most ledger pages have no h1 below 768px, so screen-reader heading navigation finds nothing

**Minor (accessibility) · dashboard · 15–25 minutes.** A2: on a phone browser, VoiceOver and TalkBack users jump between pages by heading, and from Journal, Accounts, every statement, Query, Statistics, Holdings, Settings and Import they land on no page heading at all. The first heading reachable is the footer's "Related Pages".

Production https://beancount.io, 2026-11-10, English, isolated headless Chromium 156, signed in. Read-only. Accessibility tree read with Playwright's `getByRole('heading', {level: 1})`. Local main `a4084b693`.

## Reproduce

At 390×844, open each route below on any ledger and list level-1 headings:

| Route | h1 at 390px | h1 at 1440px |
| --- | --- | --- |
| `/` (Overview), `/budget`, `/files/tree/main` | 1 | 1 |
| `/journal`, `/accounts`, `/income-statement`, `/balance-sheet`, `/trial-balance`, `/cash-flow`, `/query`, `/statistics`, `/holdings`, `/settings`, `/import` | **none** | 1 |

At 390px the Journal page's only heading in the accessibility tree is `h2 "Related Pages"` at the bottom. The page title "Journal" is not visible either, which is the deliberate narrow layout noted in [w4/228](../w4/done/228.md).

## Root cause

`dashboard/src/common/components/page-header/index.tsx:12` wraps the h1 and description in `hidden md:flex …`. `display:none` below `md` removes the h1 from the accessibility tree as well as from view. 25 feature files render `PageHeader`. Overview, Budget and Files render their own visible headings, which is why they pass.

## Fix

Keep the visual design that w4/228 asked to keep. Below `md`, render the title as `sr-only` instead of removing it. For example, always render the `<h1>`, and apply `sr-only md:not-sr-only` to it while the description keeps `hidden md:block`. Add a test that renders `PageHeader` and asserts one `heading` of level 1 with the title, independent of breakpoint classes (assert the class contract, since jsdom has no layout).

## Blast radius

Every page that uses the shared `PageHeader` (25 files under `features/`). Desktop rendering is unchanged.

## Dedupe

Searched `.pm/**` for `PageHeader`, `page-header`, and h1 / page heading together with narrow width:

- w4/228 (done) recorded the narrow hide as deliberate visual design and fixed table names instead.
- w3/469 (done) gave the Plaid pages a heading.

Neither restores a level-1 heading for assistive technology at narrow widths.

**Resolved 2026-11-10** — shipped in this commit (`dashboard`). The shared
`PageHeader` no longer uses `display: none` below `md`. Its wrapper is
`max-md:sr-only` there — visually hidden and out of flow, so the narrow
layout w4/228 designed is unchanged and no gap appears where it sat — and
its h1 stays in the accessibility tree; the description keeps
`max-md:hidden`. Desktop rendering is unchanged. Budget and Plaid passed
`className="flex …"` precisely to show their header on phones (which is why
Budget passed the audit); they now say so with a new `showOnMobile` prop
rather than relying on a display class overriding `hidden`.

Validation: `page-header/__tests__/page-header.test.tsx` compiles each
element's classes against the app stylesheet and asserts nothing on the path
to the h1 is `display: none` at any width, that the wrapper is visually
hidden only below `md`, and that `showOnMobile` hides nothing; both contract
cases fail against the previous component. `yarn format:check`, `yarn lint`,
`yarn test` (780 files, 7808 passed, 1 existing skip) and `yarn build` pass;
secret scan clean. Heading navigation was not re-run with a real screen
reader or against production before the next dashboard deploy.
