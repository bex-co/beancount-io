## Objective

Write down what makes this a distinct skill under ADR 020's gate: trigger, input contract, deliverable, and evaluation set. Confirm the name against routing evidence.

## Context

- [ADR 020](../../../../../docs/adrs/ADR020-skills-accounting-workflow-candidates.md) "Proposed decision": a new top-level skill needs a distinct trigger, input contract, deliverable, and evaluation set.
- `beancount-add` matches the `bea add` command family. m38's routing set and runner measure whether the name and description collide with siblings.

## Steps

1. Draft the scope and skip list, naming each sibling a request should go to instead.
2. Add positive and near-miss prompts for the skill to `skills/evals/routing.json`. Relabel the manual-entry prompts that were `none`.
3. Run the routing set with a draft description in a scratch install and record the result in `skills/docs/routing-rehearsal.md`.

## Files

- `skills/evals/routing.json`, `skills/docs/routing-rehearsal.md`

## Acceptance criteria

- [x] The scope note answers each of ADR 020's four criteria.
- [x] The draft routes its prompts correctly without pulling prompts away from siblings, on both clients.

## Out of scope

## Result

Scope note against [ADR 020](../../../../../docs/adrs/ADR020-skills-accounting-workflow-candidates.md)'s four criteria for a new top-level skill. **Trigger:** a single thing the user just did, described in words or pasted receipt text — a purchase, bill, paycheck, transfer between their own accounts, opening or closing one account, a price, or a note — in a local ledger. No sibling owns it: m38's runs route these prompts to no skill. **Input contract:** the user's description, plus the local root ledger; no export file, statement, or app history (those route to import, reconcile, migrate), and no options lifecycle event (options). **Deliverable:** the exact proposed directives and target file, written through `bea add` after an explicit yes, then a passing root check. Existing entries are never edited. **Evaluation set:** routing labels (9 positives, near-misses against import, options, reconcile, close, and edits) and behavior evals in t004. Name `beancount-add` matches the `bea add` family; measured with a draft description in a scratch suite (`skills/docs/routing-rehearsal.md`, "Draft beancount-add"): Claude Code 53/53 twice, Codex 53/53 and 52/53 (the known hosted miss), every manual-entry prompt to the draft, no sibling losing a prompt. Deviation: `ci-check.py` rejects labels naming a skill that does not exist yet, so the new `routing.json` labels land with the SKILL.md in t002; this task measured them on a scratch copy. `bea` behavior found while scoping (0.3.1): `add close` writes even when the account still holds a balance, with no warning, so the skill must read the balance first; a posting after the close date is refused; `add price` accepts an undeclared commodity and reports `written: 0` for an exact repeat.
