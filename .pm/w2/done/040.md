## Reproduce and controls

1. From a fresh native launch, open the valid public link `beancount:///ledger/open_ledger/example`. Wait for Example Home, then tap its actual **Cafe Modagor** recent transaction. Detail shows **−$33.71**, **September 8, 2017**, **Eating out with Julie**, and the Slate/Restaurant postings. Its real hash is `aff1ee23d8f70c970c137b006b4d8a62`.
2. While detail is open, open the valid public link `beancount:///ledger/open_ledger/crypto-example/account/Assets%3ACrypto%3ACoinbase%3ABTC`. Wait for Crypto's BTC account with **0.16 BTC**. This step uses an inspected App Link and proves its destination and ledger switch, rather than a drawer gesture.
3. Tap native **Back** once. Example's Cafe transaction reappears, including its old narration and postings, while the app's selected ledger is Crypto.
4. Tap **Expenses:Food:Restaurant** in the transaction. The native Restaurant account shows **$0.00**, **+$0.00 (+0.00%)**, **Not enough data to chart yet**, and **No entries**. It is reading Crypto, which has no such history, rather than Example's Restaurant account. Dismissing the development warning leaves the same settled failure.
5. Recovery: open the original valid entry link `beancount:///ledger/open_ledger/example/entry/aff1ee23d8f70c970c137b006b4d8a62`, then tap Restaurant. Balance returns to **$12,083.83**, with Cafe **+$33.71**, Uncle Boons and other real transactions.
6. Same-ledger control: Back to Cafe, open `beancount:///ledger/open_ledger/example/account/Assets%3AUS%3ABofA%3AChecking`, then Back to Cafe and tap Restaurant again. The correct **$12,083.83** balance and populated history remain. Preserve this working retained navigation.

The fresh repeat above reproduced an earlier independent actual Merchants journey: search **Dupar**, tap **Dupar's** (six transactions, **163.37 USD**), then its April 16, 2016 transaction **−$31.02**, hash `740de2cc7ecd8cafdd479fe4dd703fc0`. Opening the same Crypto BTC link, Back, and tapping Restaurant produces the same false zero/empty account. Both entries originate in Example.

Expected: a transaction's ledger identity survives Back, or an explicit unavailable/recovery state prevents an old transaction from being reinterpreted in another ledger. Actual: retained Example content remains actionable under Crypto, so a real posting opens an unrelated empty account. This is a navigation identity defect; it is not a claim of unauthorized access or an API arithmetic failure.

Real anonymous GraphQL controls at `/api-gateway/` independently return HTTP 200: `getLedgerEntryContext` for each hash under Example supplies the matching regular transaction and source slice; the same hash under Crypto returns GraphQL **NOT_FOUND**, **Ledger resource not found**, `data: null`. `getLedgerAccountReport` for Restaurant under Example ends at **2017-09-08, USD 12083.83**; `getLedgerAccountJournal` has **371** items and begins with Cafe **+33.71**, balance **12083.83**. Under Crypto those controls return an empty chart and journal **total 0**. These are separate real API controls; native request bodies were not captured.

## Cause, scope and repair

`mobile/src/screens/transaction-detail-screen/open-transaction-detail.ts:13` stores the last tapped transaction without ledger identity; 23–28 pushes only `entry_hash` and optional `origin_account`. In `transaction-detail-screen.tsx:260`, LedgerGuard supplies the current ambient ledger; 274 accepts a stash by hash alone. The context query at 279–282 is correctly keyed by the current ledger/hash, but 331–340 returns the stash before considering fetched context. A missing entry in Crypto therefore does not prevent Example's cached detail from rendering. The posting handler at 342–355 pushes `{ account, ledger: ledgerId }`, binding Example's posting to the new Crypto ledger. The current account route's own identity guard receives that wrong pair and cannot recover the originating transaction's ledger.

`src/common/app-links/open-app-link.ts:58` selects the incoming ledger and 68 replaces the current destination; older transaction stack entries survive, as the native Back reproduction demonstrates. `resolve-app-link.ts:152–162` likewise creates entry destinations with only a hash. The outer TransactionDetailScreen reads no ledger route param. Entry links at `transaction-detail-screen.tsx:363–373` are also built from the ambient ledger; incorrect Share/Copy output is source-derived risk only, and those actions were not exercised.

Bind the transaction route and its immediate-paint stash to the originating ledger. Before querying, rendering a retained record, or enabling posting/link/write actions, reconcile the route ledger with the selected ledger using the existing readable-ledger policy. Either retain a truthful unavailable/recovery state or deliberately restore the original ledger with access checks; do not silently query another ledger. Preserve same-ledger instant detail, cold public entry links, generated-entry handling, guest state isolation, and existing permission/checksum/write guards. Handle loading, missing, denied, expired-session and network-error states distinctly; mismatched cached content must not mask any of them. No backend contract, dependency or cross-package change is needed.

All five production `openTransactionDetail` callers were searched: Home recent transactions (`recent-transactions-card.tsx:120`), Transactions (`transactions-screen.tsx:224`), Account detail (`account-detail-screen.tsx:361`), Reports' account card (`account-transactions-card.tsx:136`), and Merchant detail (`merchant-detail-screen.tsx:418`). Home and Merchants are confirmed native starts; the remaining callers share the helper but were not independently repeated for this failure. Include authenticated `/transaction-detail`, `/examples/transaction-detail`, and entry App Link producers in the repair. Guest and writable routes remain unverified.

Acceptance: rerun both real Example transaction → Crypto BTC link → Back → Restaurant journeys without presenting Example data under Crypto or an unrelated false zero; explicit recovery restores Example's **$12,083.83** and populated history. Preserve the exercised same-ledger Checking/Back/posting control and fresh entry links. Add behavioral regression coverage for retained ledger switches, equal hashes in different ledgers, and late context responses; preserve missing/denied/loading behavior and guest isolation. Run the mobile package gates when implementing. No product fix implemented by this QA run.
