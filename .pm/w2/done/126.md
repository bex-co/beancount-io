# The Query page hides the engine's own fix for unsupported BQL ("use date_add(date, days)") behind "Some of the information provided is invalid"

**Minor · dashboard (+ ledger for a structured reason) · 60–90 minutes; may need promotion to a milestone.** A2: people arriving from Fava or bean-query write stock BQL, and this engine refuses about ten stock spellings it cannot run faithfully: `date + 1`, `'a' + 'b'`, `id`, `FROM … CLEAR`, `… AT value`, mixed-type comparisons and others. For each one, the ledger service writes a precise refusal that names the replacement. REST and MCP callers get that text. The dashboard's Query page, the only human BQL surface (mobile has none), replaces all of them with the generic **"Some of the information provided is invalid. Please check and try again."**

Production https://beancount.io, 2026-11-10, English, isolated headless Chromium 156 at 1440×1000, signed in. Queries ran against the public `open_ledger/example`. Local main `a5247ec21`, which includes the w2/111 fix (not yet deployed); the source analysis below is against that code.

## Reproduce

On `/ledger/open_ledger/example/query`, execute each query:

| Query | Page shows | API `message` (GraphQL `queryShell`, `BAD_USER_INPUT`) |
| --- | --- | --- |
| `SELECT date + 1` | generic | "Date arithmetic with + and - is not supported by this query engine: … Spell it with date_add(date, days) and date_diff(first, second) instead." |
| `SELECT 'a' + 'b'` | generic | "String concatenation with + is not supported by this query engine: … concatenate outside the query instead." |
| `SELECT id, date LIMIT 1` | generic | "The `id` column is not supported by this query engine: … Filter or join on entry attributes instead …" |
| `SELECT account, sum(position) FROM CLEAR GROUP BY account` | generic | the CLEAR refusal, naming the supported query |
| `SELECT account WHERE account ~ '('` | generic (production); on local HEAD, "A value has the wrong type for this comparison or function." | "type error: invalid regex: (" |

**Controls:** an unknown column, a syntax error and (on HEAD) an ungrouped column, unknown function or table, and argument count each get a specific localized message (w2/111). `extensions` carries only `{"code":"BAD_USER_INPUT"}`, so the client has nothing structured to map.

## Root cause

- `dashboard/src/features/bql/lib/query-error.ts` explains only messages it recognizes by regex and, by design, never shows raw server text. None of the ledger's guard refusals match, so they fall through to `getErrorMessageKey` → generic.
- The guards live in `backend-cluster/ledger/src/foundation/rustledger/*-guard.ts`: date-arithmetic, string-concat, id-column, clear-scope, at-value, mixed-comparison, composite-comparison, inventory-group-by, quoted-column and star-alias. Each throws English prose with no machine-readable reason.
- On HEAD, `TYPE_ERROR_PATTERN = /\btype error:/` also matches the engine's `type error: invalid regex: …`. A malformed regex would therefore be described as a wrong-typed value.

## Fix

**Preferred, structured:**
- Have each ledger guard attach a stable reason (`extensions.bqlRefusal: "dateArithmetic" | "stringConcat" | "idColumn" | "clearScope" | "atValue" | "mixedComparison" | …`). backend-v2 forwards it on GraphQL and REST. MCP already returns the full text, and per the root parity rule the REST/MCP payloads gain the same field.
- In the dashboard, map each reason to a localized message that keeps the code tokens as placeholders (`date_add(date, days)`, `date_diff(first, second)`), as w2/111 did.

**Minimum, dashboard only:** add patterns for the two most common refusals, date arithmetic and the `id` column, plus `type error: invalid regex:` → "The pattern after ~ is not a valid regular expression. Check its brackets and escapes." Place the regex pattern before the generic `type error:` match.

Tests: one rendering case per mapped refusal with the recorded production messages, and a check that a regex error no longer reads as a type error.

## Blast radius

Only the Query page's error card. Journal advanced filters have their own parser and messages (ADVANCED_FILTER_ERROR) and are not affected.

## Dedupe

Searched `.pm/**` for "not supported by this query engine", `date_add`, the guard file names, and Query page + generic error:

- w2/111 (done, not deployed) mapped five other engine diagnostics and the generic `type error:`.
- w23/188 and w23/193 (done) added server guards and never touched the dashboard.

No item routes the guard refusals to the Query page.

---

**Resolved 2026-11-11** — shipped in this commit (`dashboard`), the note's
dashboard-only minimum plus string concatenation. `query-error.ts` now
explains four of the ledger's refusals by their stable prefixes: date
arithmetic ("…Use date_add(date, days) to shift a date and
date_diff(first, second) to count the days between two", the function
spellings passed as untranslated placeholders), string concatenation with
`+`, the `id` column, and `type error: invalid regex:` ("The pattern after ~
isn't a valid regular expression…"), which is matched before the generic
`type error:` so a malformed pattern no longer reads as a wrong-typed value.
Four `bql.errors.*` keys in all 15 locales; Try Again stays hidden for them,
as for every `BAD_USER_INPUT` (w2/111). Raw server text is still never
shown.

Not done: the structured `extensions.bqlRefusal` reason from each ledger
guard (with backend-v2 forwarding and REST/MCP parity), which would let the
remaining refusals — `FROM … CLEAR`, `AT value`, mixed and composite
comparisons, inventory GROUP BY, quoted columns, star aliases — be mapped
without matching English prose. That spans the ledger service and the API
contract and is worth filing on its own if wanted.

Validation: `query-error.test.ts` gains the recorded production messages for
all four, and `query-result-card-engine-errors.test.tsx` renders three of
them with the real English catalog, including the regex case that read as a
type error; seven fail against the previous matcher. `yarn format:check`,
`yarn lint`, `yarn test` (793 files, 7938 passed, 1 existing skip) and
`yarn build` pass by exit code; secret scan clean. Not verified against
production before the next dashboard deploy.
