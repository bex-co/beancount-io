## Objective

Keep users with an already-issued valid Dashboard token signed in while making the compatibility path incapable of creating, extending, or renewing legacy authority.

## Context

- The authenticated identity check already understands the historical credential.
- The user requires this check to remain so deployment does not force a logout.
- Compatibility must be one-way and naturally shrinking; it cannot remain a hidden alternate login or rollback issuer.

## Steps

1. Isolate legacy-token verification as a read-only authenticated-check branch with explicit expiry and historical authority.
2. Preserve current protected Dashboard behavior for valid tokens and optionally upgrade them to OAuth without clearing the valid token on upgrade failure.
3. Reject issuance, renewal, rotation, refresh, or resurrection through every compatibility entry point and record a measurable removal condition after the last possible expiry.

## Files

- `backend-cluster/backend-v2/src/server/api/identity.ts`
- `backend-cluster/backend-v2/src/features/auth/**`
- `dashboard/src/features/oauth/dashboard-session-upgrade.ts`
- authentication compatibility tests

## Acceptance criteria

- [x] A valid pre-cutover token remains accepted without user reauthentication or loss of historical authority.
- [x] Expired, revoked, malformed, or wrong-user tokens fail closed.
- [x] No compatibility request can issue, renew, rotate, or extend a legacy token.
- [x] Failed silent OAuth upgrade preserves a still-valid legacy login and cannot leak another account's cache or credential.

## Out of scope

- Keeping legacy verification after every possible pre-cutover token has expired.
