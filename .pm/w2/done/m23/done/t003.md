## Objective

Authenticate password and magic-link users as part of the OAuth provider interaction and complete authorization directly without issuing a legacy Dashboard session.

## Context

- Credential verification and magic-link consumption are account-authentication operations and remain necessary.
- Their current success paths return or install a legacy session before m21 starts OAuth.
- OAuth interaction completion must preserve rate limits, one-time-link consumption, account blocking, audit, safe redirects, and actionable errors.

## Steps

1. Move or reuse password verification behind an OAuth interaction login operation that establishes the provider account context without creating an application session token.
2. Bind magic-link completion to the original/new OAuth interaction and consume it exactly once before completing the authorization grant.
3. Remove Dashboard dependencies on legacy login responses/cookies while preserving reset, blocking, rate-limit, and account-initialization behavior.

## Files

- `dashboard/src/features/auth/pages/login-page/**`
- `dashboard/src/features/auth/pages/auth-callback-page/**`
- `backend-cluster/backend-v2/src/features/auth/**`
- `backend-cluster/backend-v2/src/features/oauth/api/oidc-route.ts`

## Acceptance criteria

- [x] Password and magic-link success return through OAuth code + PKCE and write only the Dashboard OAuth credential.
- [x] Neither path creates a legacy session row/token or sets a legacy credential cookie.
- [x] Invalid, blocked, expired, replayed, and rate-limited attempts issue no OAuth code or other credential.
- [x] Password reset remains functional but cannot become an alternative session issuer.

## Out of scope

- Removing passwords or magic links as account-authentication methods.
