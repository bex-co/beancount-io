## Objective

Finish the migration in the codebase by deleting Dashboard-only session terminology, policy branches, handlers, and tests that no longer have a live issuer or consumer.

## Context

- Compatibility verification must remain narrow, but it should not keep unrelated legacy login orchestration alive.
- OAuth provider browser sessions and interaction cookies are required protocol state and must not be removed merely because they contain the word “session.”
- Shared auth code may have non-Dashboard consumers; deletion requires consumer evidence rather than name matching.

## Steps

1. Trace remaining session-only branches and classify them as existing-token verification, OAuth protocol state, non-Dashboard use, or dead Dashboard code.
2. Delete dead Dashboard resolvers, response fields, helpers, redirects, cookie writers, revocation paths, tests, and misleading authorization classifications.
3. Prove retained code has a named live consumer and that first-party authority comes from the exact Dashboard OAuth client for every new login.

## Files

- files changed by `w2/m23`
- `backend-cluster/backend-v2/src/server/api/**`
- Dashboard/backend authentication tests and generated contracts when affected

## Acceptance criteria

- [x] No dead Dashboard legacy-login/session branch remains outside the explicit existing-token verifier.
- [x] Every retained session-related component is documented as OAuth protocol state, a live non-Dashboard consumer, or verify-only compatibility.
- [x] Dashboard first-party authorization depends on the verified OAuth client for new credentials, never a caller-supplied marker.
- [x] Generated API artifacts are regenerated from source where contract removal requires it; no lockfile is hand-edited.

## Out of scope

- Deleting live non-Dashboard authentication or required OAuth provider state.
