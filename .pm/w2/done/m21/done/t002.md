## Objective

Represent the Dashboard as a static first-party OAuth client and make the requested 365-day access-token lifetime a client-specific policy rather than a global relaxation.

## Context

- `backend-cluster/backend-v2/src/features/oauth/data/config.ts` is the client/resource/lifetime catalog.
- `oidc-provider` currently reads one access-token TTL for every client.
- Redirect metadata must work for self-hosted and issuer-path deployments rather than embedding `beancount.io`.

## Steps

1. Add the Dashboard client metadata and materialize its deployment-derived redirect URI, API resource, scopes, public/confidential behavior, grant type, and PKCE requirement from the catalog.
2. Select access-token TTL by verified client ID: exactly 365 days for Dashboard and the existing one hour for Mobile, MCP/DCR, and identity clients.
3. Fail closed for unknown client/resource keys and preserve issuer/path normalization in discovery, authorization, code exchange, and verification.

## Files

- `backend-cluster/backend-v2/src/features/oauth/data/config.ts`
- `backend-cluster/backend-v2/src/features/oauth/api/oidc-route.ts`
- `backend-cluster/backend-v2/src/config/config.ts`
- focused OAuth configuration and route tests

## Acceptance criteria

- [ ] The static Dashboard client is generated from one catalog entry and uses `<issuer>/v1`.
- [ ] Only a token minted for the exact Dashboard client receives `365 * 24 * 60 * 60` seconds.
- [ ] Mobile, MCP/DCR, and Discourse access tokens retain the existing one-hour policy.
- [ ] Official, self-hosted, and path-prefixed redirect/discovery tests pass without a hardcoded production origin.

## Out of scope

- Changing authorization-code, interaction, grant, Mobile refresh-token, or provider browser-session TTLs.
