## Objective

Define the exact Dashboard OAuth protocol, trust boundary, migration sequence, and one-year bearer semantics before changing either package.

## Context

- Dashboard password, OTP, and magic-link paths currently mint a revocable session JWT and set `authSess:beancount.io`; CSR sends the cookie and SSR forwards it as a bearer.
- The OAuth catalog currently has static Mobile and Discourse clients plus an MCP DCR profile. Its one-hour access-token TTL is global.
- A self-contained 365-day access token cannot be cut short by logout or provider revocation after it has been copied.

## Steps

1. Inventory every Dashboard authentication entry point, callback, cookie reader, SSR/CSR/agent transport, logout path, OAuth-consent bootstrap, and legacy native bridge dependency.
2. Specify a stable Dashboard client ID, application API resource, scopes, authorization-code + S256 PKCE flow, path-aware callback, cookie boundaries, and whether any refresh credential is issued.
3. Record the staged cutover/rollback contract and the security consequences of the explicit 365-day access-token requirement, including compromise response and truthful logout semantics.

## Acceptance criteria

- [ ] Every current browser login and credential-consent path has an owner in the migration sequence.
- [ ] The Dashboard token contract names its client, audience, scopes, exact 365-day expiry, cookie storage, and callback validation.
- [ ] The design states that logout cannot revoke a copied self-contained access token and records the operational compromise response.
- [ ] Mobile `/v1`, MCP, Discourse, API-key, and legacy-session compatibility boundaries are explicitly outside the TTL broadening.

## Out of scope

- Renaming `/v1`, changing other clients' lifetimes, or implementing a reference-token/revocation service.
