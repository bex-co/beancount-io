## Objective

Let the exact first-party Dashboard OAuth identity perform interactive-browser operations without granting the same authority to delegated OAuth clients.

## Context

- Current consent approval calls `assertSessionIdentity`, and several PDP actions use a literal session-only credential list.
- OAuth identities already carry the signed `client_id`; transport headers or caller arguments must not classify first-party authority.
- After cutover the Dashboard must still approve Mobile, Discourse, and MCP authorization requests.

## Steps

1. Define one reviewed first-party-interactive credential predicate based on verified identity method plus the configured Dashboard OAuth client ID.
2. Apply it to OAuth consent/bootstrap and the PDP actions that genuinely require an interactive Dashboard user, preserving capability, exact-self, relationship, and audit requirements.
3. Prove DCR/MCP, Mobile, unknown OAuth clients, API keys, and forged client identifiers remain denied and perform no protected work.

## Acceptance criteria

- [ ] Dashboard OAuth can reach the operations previously intended for the signed-in Dashboard and can approve OAuth consent.
- [ ] Trust derives only from the verified token's configured client ID, never `x-app-id`, request input, cookie name, or scope alone.
- [ ] Mobile, DCR/MCP, API-key, and arbitrary OAuth credentials do not gain session-equivalent authority.
- [ ] Denials remain audited, actionable, and side-effect free; source failures keep their existing fail-closed behavior.

## Out of scope

- Broadening every OAuth token into a browser session or changing durable relationship semantics ceremonially.
