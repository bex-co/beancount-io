# Discard server connection results after the URL draft changes

**Severity:** minor. **Estimate:** 35–50 minutes. **Package:** mobile. **Goal:** A2 — a newcomer configuring a server can trust that the connection status belongs to the URL shown beside it.

**Environment:** 2026-09-21, `main` at `98359325` during reproduction (unrelated CLI work subsequently advanced HEAD to `e4da9d6e`; mobile source unchanged), native development build `io.beancount.ios` 1.20260906.47 (47) with current Metro JavaScript, iPhone 17e / iOS 26.5, English, light, ordinary text size. Signed out. Controlled anonymous loopback responses exercise latency; this is not a claimed production-server incident. The selected server remained `https://beancount.io/`; only unsaved drafts were edited.

## Repro

1. Open Server from Welcome's gear. Enter a loopback test server URL, `http://127.0.0.1:18473/slow/`. Its health endpoint returns `{"data":{"health":"OK"}}`, and both discovery documents satisfy the existing native OAuth contract. Delay the protected-resource metadata response by six seconds, below the connection test's eight-second timeout.
2. Tap **Test connection**. While it is pending, replace the field with `https://beancount.invalid/`. The field remains editable during the test. Do not tap Save or start a second test.
3. When the original request finishes, the screen shows `https://beancount.invalid/` together with green **“Connected to a compatible Beancount.io server.”** No connection test was made against the replacement URL.
4. Terminate and relaunch, open the inspected `/auth/server` route, and repeat. The same false association appears. This repeat proves the destination; the first pass used actual gear navigation.
5. As a working control, edit the URL after the test has settled. The status clears normally. An unchanged hosted URL also passed its earlier native connection test with the result attached to the correct field value.

Expected: changing a URL invalidates the previous URL's pending result; only a test of the current draft may publish a connection status. Actual: editing clears the current status, but completion of the old request puts it back under the new URL.

Native request and keyboard-helper timestamps establish the order independently of screenshots. First run: old metadata requested at `06:10:27.920Z`, replacement typing completed at `06:10:28.812Z`, old response completed at `06:10:33.923Z`. Fresh run: request `06:13:35.666Z`, edit finished `06:13:36.177Z`, old response completed `06:13:41.666Z`. The native screen was driven through Expo MCP; the helper used Simulator's hardware keyboard to enter ordinary synthetic text after observing the old request, without modifying React state or injecting a response into the app.

## Cause and fix

`mobile/src/screens/welcome/server-settings-screen.tsx:170–184` captures the validated URL, awaits `testServerConnection`, then unconditionally calls `setTesting(false)` and `setConnection(result)`. The `TextInput` at lines 233–250 stays editable. Its `onChangeText` clears `connection` immediately but does not invalidate the in-flight request, so that request later overwrites the cleared state. There is no request identity or tested-URL association at publication time.

Tie each result to the draft/test generation that initiated it. Invalidate that generation when the draft changes, and ignore late completion for obsolete generations; release any obsolete request resources where the existing API permits cancellation. Ensure obsolete requests cannot overwrite a newer request's loading or error state either. Preserve editing, the normal loading indication, the eight-second timeout and advisory save behavior. Do not make a successful network test mandatory for saving a syntactically valid offline server URL.

**Acceptance:** start a deferred connection test for A, edit to B, then resolve A with success or failure: no A status appears under B. A subsequent test of B can settle normally without being overwritten by A. Editing after a settled result still clears it; unchanged-URL success/failure/timeout and Restore default still work. Add a deferred-response regression that exercises the screen's draft/result transition, and repeat the native steps.

**Resolved 2026-09-23** — `ServerSettingsScreen` ties each connection test to a token from `createConnectionTestGate` (`src/screens/welcome/connection-test-gate.ts`). Editing the draft, restoring the default, or starting another test makes earlier tests obsolete: a late result, success or failure, is dropped instead of appearing under the new URL. Editing also ends the obsolete loading state, so B can be tested at once and A cannot overwrite B's state. Editing still works during a test. The eight-second timeout, advisory save and Restore default are unchanged.

`testServerConnection` exposes no external abort signal, so the obsolete request still runs to its own timeout and its result is ignored. No renderer is available to the unit runner, so `connection-test-gate.test.ts` covers the change in two parts:
- deferred A → edit → B sequences (late success, late failure, B settling while A finishes later, unchanged draft);
- the screen's wiring, which checks the result is published only after the token check and that edit/reset invalidate.

The wiring cases fail against the previous screen. Mobile format, lint, typecheck and 1884 unit tests pass. Not re-run on the native simulator. Shipped in `mobile`.
