# Add Budget stores a positive income target, so the web Budget card treats it as a spending cap

**Minor · dashboard · 30–40 minutes.** A2: typing the natural "3500" as a monthly salary target produces a card that calls a month of 4,000 income "Below target" and shows the actual as −4,000 beside a +3,500 target. This is the dashboard counterpart of mobile's [w4/039](../w4/done/039.md), which since 2026-09-14 derives the sign from the account.

Production https://beancount.io, 2026-11-10, English, isolated headless Chromium 156 at 1440×1000, signed in as the owner of the designated synthetic ledger. Both budgets below were written, then deleted, and main.bean was restored to blob `f1a0b83c`. Local main `a6c2d42c7`.

## Reproduce

1. `/ledger/<o>/<l>/budget` → **Add Budget**: Date 2026-07-01, Account `Income:Salary`, Interval Monthly, Amount `3500`, Currency USD → Add Budget. The ledger receives `2026-07-01 custom "budget" Income:Salary "monthly" 3500 USD`; the sign is stored as typed.
2. The Income:Salary card reads **Current budget 3,500.00 USD · Latest actual 0.00 USD · Variance: Below target −3,500.00 USD**. Its Period data rows read `2026-07-31 · 3,500.00 USD · −4,000.00 USD` and `2026-08-31 · 3,500.00 USD · −4,000.00 USD`. In both months the salary of 4,000 beat the target, yet the target and actual carry opposite signs and the card applies spending rules.

**Control:** an Expenses budget added the same way (`Expenses:Housing:Rent`, Quarterly, 5000) reads correctly: `2026-09-30 · 5,000.00 USD · 3,600.00 USD`, Below target. A directive written as `-3500 USD` for Income:Salary is read as an income target (`budgetGroupDirection`, `budget-utils.ts:~63`), so the card logic is right. Only the form's input is wrong.

## Root cause

- `dashboard/src/features/ledger-data/budget/add-budget-dialog.tsx` writes the amount as typed and has no income handling. Its help text ("Budgets apply to one account, e.g. Expenses:Food:Groceries…") never mentions sign.
- The card decides direction from the sign of the stored amount.
- Mobile resolved the same trap in w4/039 by recording income-root targets as negative (and hardened it in w21/303 and w21/878 while options load). The dashboard never received that change.

## Fix

- When the selected account is under the ledger's income root (`options.name_income`, not the literal "Income"), store the negated amount and show it unsigned in the form. Apply the same rule in Update Budget, which reuses this dialog.
- Do not write until the ledger options have loaded (the w21/303 and w21/878 lesson).
- Outside the income root, strip a typed sign and store the cap positive. Mobile does this since w21/302: "-500" or "+500" on an Expenses account saves 500, or the card would read a negative cap as an income target.
- Add a one-line hint under Amount for income accounts: "Income targets are stored as negative amounts, as in Beancount."
- Test both roots: Income:Salary 3500 → `-3500 USD`, and Expenses `5000` or `-5000` → `5000 USD`. Include a renamed income root.

## Blast radius

Add Budget and Update Budget in `features/ledger-data/budget/`. Existing positive income budgets in users' ledgers keep spending rules; a one-line notice on such cards ("This income target is positive; Update it to track income") is optional.

---

**Resolved 2026-11-10** — shipped in this commit (`dashboard`). Add Budget,
and Update Budget, which reuses the dialog, now take the stored sign from the
account (`budgetAmountForAccount`, `budget-utils.ts`): a target on the
ledger's income root — `options.nameIncome`, so a renamed root such as
`Revenue` counts, while `IncomeTax:Refund` does not — is stored negative, and
any other budget positive, whatever sign was typed; a zero stays unsigned.
`Income:Salary 3500` writes `-3500 USD`, and `Expenses:Housing:Rent -5000`
writes `5000 USD`. A hint under Amount appears only for an income account:
"Income targets are stored as negative amounts, as Beancount records
income." (`page.budget.budgetIncomeAmountHelp`, 15 locales). The w21/303 and
w21/878 loading lesson holds by construction here: both callers render
inside `LedgerProvider`, whose `ledgerData` is loaded before any ledger page
renders, so the root is known before a write. Not done: the optional notice
on existing positive income budgets.

Validation: `budgetAmountForAccount` cases (signs, the root itself, a
renamed root, the prefix case, an unknown root, zeros) and
`add-budget-income-sign.test.tsx` (both roots, typed signs, a renamed root,
the hint shown only for income) — four dialog cases fail against the
