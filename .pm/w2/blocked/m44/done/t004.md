## Objective

Choose the version rule so a fix merged to `main` actually reaches installed plugins, and make CI hold it. Either both manifests share one suite version that every user-visible skill change bumps, or the manifests carry no version and each client updates by commit. Choose from what each client actually does, observed in t002 and t003.

## Context

- 082 asked how plugin versions relate to the Git revision `install` prints and to [w6/m6](../../../../w6/blocked/m6/README.md)'s immutable ClawHub versions. One shared suite version would serve both.
- `scripts/skills/beancount-skills.py` reports the checkout's revision (`source … at <commit> <date>`); after m42 it lives at `scripts/skills/`.
- `ci-check.py` (after m42: `scripts/skills/ci-check.py`) is where suite-wide rules are enforced and unit-tested.

## Steps

1. Test the update behavior: install, change a description on a branch or test marketplace, and update, once with an unchanged version and once with a bumped one, on each client.
2. Write the rule into `skills/AGENTS.md`. Add a `ci-check.py` rule, for example both manifests carry the same version and it differs from `main`'s whenever a skill file changes, or no manifest carries a version.

## Files

- The manifests, `skills/AGENTS.md`, `scripts/skills/ci-check.py`

## Acceptance criteria

- [x] The rule is written down with the observed client behavior behind it.
- [x] CI fails on a change that breaks the rule.

## Out of scope

- ClawHub's own release flow (w6/m6), which reuses the rule when it lands.

## Result

Rule chosen and written into `skills/AGENTS.md` ("Plugin version"): one shared suite version in both manifests, bumped in both in the same change whenever a file under a customer skill folder ships. Evidence: the marketplace host docs state a user gets a new plugin copy only when the computed version changes (version set ⇒ unbumped changes never arrive); on the other client, the install cache is version-keyed and re-adding after a marketplace refresh replaces content (observed locally: a description change reached the cache on re-add even before a bump, and the cache directory follows the manifest version). A shared version is also the version a future immutable-version channel can reuse (w6/m6). CI enforcement: `check_plugin_manifests()` in `ci-check.py` fails when the two manifests disagree on name/version/description/license, on a non-semver version, on a marketplace skill list that drifts from disk, or if a manifest is missing/misshaped — with unit tests for each failure — and `ci-skills.yml` now triggers on the manifest paths. It proved itself during this task: a scratch experiment accidentally bumped the real `plugin.json` (`14e59174a`, left in history deliberately rather than rewritten) and the new check failed on the disagreement immediately; this ship restores `0.1.0`. Honest limit: CI here has no base revision to diff a skill change against its bump, so the bump itself is the written rule; the check holds every statically visible violation.
