## Contract (drafted 2026-10-19, awaiting owner confirmation)

**Name.** `beancount-edit`. No Beancount directive is named `edit`, so it avoids the collision class behind [m39](../m39/README.md). Routing confusables are `beancount-add` (new entries), `beancount-import` (statements not yet in the ledger), and `beancount-reconcile` (comparing against a statement).

**Triggers.** The user asks to change something that is already in their local ledger: fix, correct, recategorize, rename (an account), tag/link, or move entries. **Skips:** recording a new transaction (`beancount-add`); importing or reconciling a statement; answering questions (`beancount-ask`); hosted Beancount.io ledgers (the MCP hand-off every sibling carries); deleting entries or history (out of scope for the milestone); editing importer code (`beancount-importer-author`); reformatting files beyond the lines named.

**Supported requests.** Exactly the milestone's five: (1) fix one entry's payee, narration, amount, date, or account; (2) recategorize a matched set, optionally adding the matching rule to the user's import rules when they ask; (3) rename an account (two paths below); (4) add a tag or link to a set; (5) move entries to another file, keeping the `include` graph valid. Anything else is refused by name, not approximated.

**Locating entries.** Only from `bea --json list transaction --search … --on-disk` (and the matching `list` forms for other directives), which returns `source.filename` and `source.lineno` per entry and hides plugin-synthesized rows. Before any edit, the skill re-reads those exact lines and compares them with what the query reported; a mismatch (file changed under it) stops the run. Edits touch only the named lines, in the user's existing files and layout. There is no rewrite verb in `bea`; edits are text edits made safe by the rails below, per this task's Context.

**Preview.** The change is first applied to a temporary copy of the ledger (root file plus its includes) outside the ledger tree. The skill runs `bea check` on the copy and shows a unified diff of copy vs. real files. Nothing in the real ledger changes before the user's explicit yes. A yes must name the shown change; anything ambiguous is a no.

**Check rule.** `bea check` runs on the real root before the preview (baseline) and after the approved change. The change may only land when the after-error set contains no error that was not in the baseline set ("no errors that were not there before"); fixing a pre-existing error is allowed and reported. If the after-check adds an error, the skill restores the target files from Git and reports failure — it never commits a change that made the ledger worse. Amount changes that unbalance an entry are shown in the preview diff with both postings the user approved, never silently rebalanced.

**Commit and undo.** Each approved change-set is exactly one Git commit containing only the target files, message `beancount-edit: <imperative summary>` (for example `beancount-edit: recategorize 12 Starbucks charges from Dining to Coffee`). "Undo the last change" runs `git revert --no-edit` on that commit and re-runs `bea check`; if the revert conflicts (later edits touched the same lines), the skill stops and shows the conflict instead of forcing. `git reset --hard` is never used.

**Dirty tree and no Git.** Undo needs Git, so a ledger outside a Git repository is refused with that reason; the skill may offer `git init` plus an initial commit, and proceeds only on an explicit yes. In a dirty tree: if any target file has uncommitted changes, the skill stops and names them (its diff and restore guarantees would be ambiguous); unrelated dirty files do not block, and the commit names its paths explicitly so unrelated work is never swept in. No backup files are ever written into the ledger tree.

**Account renames — two paths, always the user's choice.** (a) *Rewrite history:* replace the account name on every located line (opens, closes, balances, postings) and in import-rules files the user names; history reads as if the account always had the new name. (b) *Close and transfer:* keep history, open the new account, move the balance with a dated transfer, and close the old one — the append-only path, through the shared `bea` recipes. When the account has any postings, the skill shows both outcomes and asks which; it defaults to neither. For an account with no postings (opened only), it may propose (a) and still needs the yes. A target name that already exists with postings is a merge, which this skill refuses in v1 and says so.
