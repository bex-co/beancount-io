## Objective

REST (`docs/openapi/v1.json`, "Page size, at most 100") and the MCP `listLedgers` tool both document a maximum `limit` of 100. A `limit` from 51 to 100 should return exactly that many ledgers per page, instead of silently returning 50, which reads as a final page. The workflow does this by stitching together the 50-item upstream pages that cover the requested window.

## Context

- Gitea clamps `limit` to 50 and does not say so. Every client here treats a short page as the end of the list (mobile's `ledger-directory.ts` and the workflow's own owned-ledger loop), so an agent that asks for 100 stops at 50.
- The requested window is items `[(page − 1) × limit, page × limit)`.
- GraphQL `ListLedgersArgs.limit` declares no maximum; the same stitching applies.

## Steps

1. Extend the t001 reader to read a window `(offset, count)`. It starts at upstream page `⌊offset / 50⌋ + 1` and drops the leading items of that first page.
2. `listLedgers` and `listUserOwnedLedgers`: `limit` > 50 reads the window; `limit` ≤ 50 or page-only calls keep today's single call.
3. On the window path only, normalize `page` and `limit` the way the ledger service parses them: drop any fraction, and treat a page below 1 as 1.
4. Tests:
   - `limit: 100, page: 1` returns all 91 fixture ledgers in 2 upstream calls;
   - `limit: 60, page: 2` returns fixture items 61–91;
   - `limit: 100, page: 2` returns an empty list;
   - a window that crosses an upstream page boundary keeps its order.

## Acceptance criteria

- [x] `limit: 100` returns all 91 ledgers of the 91-ledger fixture, where the old code returned 50.
- [x] `limit: 60, page: 2` returns exactly fixture items 61–91.
- [x] `limit` ≤ 50 still makes exactly one upstream call with the caller's arguments.
- [x] `yarn typecheck` and `yarn test` pass in `backend-cluster/backend-v2`.

## Out of scope

- Raising or lowering the documented maximum.
- A `hasMore` or total-count field, which would be a separate API-contract change.

## Result

- A `limit` above 50 is read as a window over 50-item upstream pages. The workflow suite proves it (`keeps page boundaries when one page spans upstream pages`: items 1–75, items 61–91, then an empty page), and so does `catalog-parity.test.ts`, through every adapter: `limit=100` returns exactly 100 of a 120-ledger fixture and page 2 returns the remaining 20. All of these fail on the previous implementation.
