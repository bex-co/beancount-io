## Objective

`listLedgers` and `listUserOwnedLedgers` called with neither `page` nor `limit` return the caller's complete catalog instead of the ledger service's first page. They do it by reading upstream pages of 50 until a short page, through one reader that `listUserOwnedLedgersWithDirectiveCounts` also uses.

## Context

- `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts`: `listLedgers` passes `{ page: args.page, limit: args.limit }` straight to the ledger service's `GET /ledgers` (`backend-cluster/ledger/src/api/ledgers.ts`), which relays Gitea `GET /user/repos`. `listUserOwnedLedgers` does the same through `GET /ledgers/users/{username}`, which relays `GET /users/{username}/repos`.
- Gitea 1.24 serves at most `API.MAX_RESPONSE_ITEMS` (50) per page, falls back to `API.DEFAULT_PAGING_NUM` (30) when `limit` is omitted, and orders by name. No deployment config in this repo overrides either value.
- The GraphQL query is described as "List all ledgers for the current user", the MCP tool as "List the ledgers this credential can reach" and REST `accessibleLedgers` as "List the caller's accessible ledgers". All three adapters call this workflow method (`api/rest/v1/catalog-reads.ts`, `ai-agent/tools/ledger-context-tools.ts`, `api/resolvers/ledger-resolver.query.ts`).
- The dashboard's callers send no paging arguments: the ledger switcher (`dashboard/src/common/components/ledger-layout/ledger-switcher.tsx`), the `/ledger` sidebar, the OAuth consent ledger picker (`dashboard/src/features/oauth/pages/consent.tsx`) and the create form's default-name check. Mobile pages explicitly (`DIRECTORY_PAGE_SIZE = 30` in `mobile/src/common/ledger-directory/ledger-directory.ts`) and is unaffected.
- `listUserOwnedLedgersWithDirectiveCounts` already loops `OWNED_LEDGERS_PAGE_SIZE = 50` pages until a short page. It is the same reader, written inline and without a bound.
- `restrictToPin` filters `listUserOwnedLedgers` after the read, so today a credential pinned to a ledger outside the first upstream page gets `[]`.

## Steps

1. Add one catalog reader to the workflow. It reads upstream pages of 50 until a page comes back shorter than 50. The page size is a named constant that states the Gitea rationale. The reader stops at a page cap and logs a warning when it hits it.
2. `listLedgers` (unpinned path) and `listUserOwnedLedgers`: when `args.page` and `args.limit` are both undefined, read through the reader; otherwise keep today's single call.
3. Replace the inline loop in `listUserOwnedLedgersWithDirectiveCounts` with the reader.
4. Write workflow tests over a fake ledger service that holds 91 ledgers and serves them in 50-item pages, or 30-item pages when `limit` is omitted:
   - unpaged reads return all 91 in order, in exactly 2 upstream calls;
   - an explicit `{ page, limit }` still makes one call with the same arguments;
   - a credential pinned to a ledger that sorts after the 50th is found by `listUserOwnedLedgers`.
