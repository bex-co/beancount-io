## Scope (decided 2026-10-19)

**Placement: a new skill, `beancount-trade`** — not widened `beancount-options`, not folded into `beancount-add`. Evidence: the three candidate prompts ("Record that I bought 10 shares of VTI at $250 in my Roth", "I sold some bitcoin, record the gain", "Record my RSU vest") run through `run-routing.py` at `3c8d5636e` against the linked suite — one client (2.1.289, `claude-opus-5-5[1m]`) opened **`beancount-add` for all three** (they read as "record a described entry"), and the second client (0.163.0, `gpt-6-luna`) returned its usage-limit error for all three and has not routed them. So today these requests land in a skill whose procedures have nothing about lots or cost basis. Widening `beancount-options` was rejected: it records *options* trades and lifecycle events, and its name and triggers would lie about a plain VTI purchase. Widening `beancount-add` was rejected: t002's procedure depth (lot selection, booking methods, split/transfer/vest handling) would bloat the everyday-entry skill every routing decision must read. A dedicated skill keeps all three triggers honest: options contracts → `beancount-options`, described securities/crypto investment events → `beancount-trade`, everything else one-off → `beancount-add`. No Beancount directive is named `trade`.

**Trigger.** The user asks to record a described investment event in a local ledger: buy, sell (with gain), cash or reinvested dividend, split, transfer of a position between their own accounts, or an RSU/ESPP vest — for stocks, funds (ETF/mutual fund), and crypto alike.

**Input contract (per event; ask for what is missing, print an explicit unknown rather than inventing).**

- *Buy:* account, date, commodity (ticker/asset), units, price per unit (or total), cash account, fees. Output: units at total cost as one lot, cash out including fees.
- *Sell:* account, date, commodity, units, proceeds (price or total), which lot (cost + acquisition date) when named, fees. Unnamed lot: the account's `open` booking method decides — the procedure names the lot the method selects, never picks silently. Gain is whatever the booking produces to the ledger's existing capital-gains income account; a gain is never typed in.
- *Cash dividend:* account, date, amount, paying commodity. *Reinvested:* the same plus units and price, recorded as income and a buy at that cost.
- *Split:* commodity, date, ratio. Total cost unchanged; units and per-unit cost change.
- *Transfer between own accounts:* source, destination, commodity, units, lot. Same units at the same cost and acquisition date on both sides.
- *RSU/ESPP vest:* account, date, units, fair-market value. Income at FMV and a lot at that cost; tax treatment stays the user's.

**Exclusions.** Options contracts and their lifecycle (`beancount-options`); broker statement files (`beancount-import`); comparing an account to a statement (`beancount-reconcile`); performance/return questions (`beancount-ask`); tax advice (the skill shows both sides of a vest, the user decides treatment); shorts, margin, and derivatives beyond options (refused by name); hosted Beancount.io ledgers (the sibling hand-off).

**Output contract.** The suite rails: proposal first with target file and exact entries (lot, cost basis, and booking-produced gain shown), explicit yes, existing accounts only (new account only on request), `--file`/`--into` on every write, passing root `bea check` before success. Write path is the shipped `bea add transaction` (`cost lots ({...}), total cost ({{...}}), @ / @@ prices`, verified against `bea 0.3.1 --help` 2026-10-19); no CLI growth is proposed by this milestone — booking methods beyond what `bea` accepts are t004's research question.

**Routing labels for t002/t005:** the three probes become `beancount-trade` positives; near-misses: an options open/roll (→ `beancount-options`), a broker CSV (→ `beancount-import`), "what has VTI returned?" (→ `beancount-ask`), a plain purchase (→ `beancount-add`). The both-clients routing verification lands with the text (t002) and its eval run (t005/t006) — the second client has not routed these prompts yet, and no description exists to route to until t002 writes it.
