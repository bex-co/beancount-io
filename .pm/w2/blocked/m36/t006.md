## Objective

Make the listing real: generate the signing key, serve its public record from production, store the private key for the workflow, publish version `1.0.0`, and verify it through the registry API. This task is the deployment operator's; it is the only step the repository cannot complete by itself.

## Context

- Ed25519 key generation needs OpenSSL 3 (`brew install openssl@3` on macOS; the system LibreSSL fails with "Algorithm Ed25519 not found"). The registry's documented commands: `openssl genpkey -algorithm Ed25519 -out key.pem`; public record `v=MCPv1; k=ed25519; p=$(openssl pkey -in key.pem -pubout -outform DER | tail -c 32 | base64)`; 64-hex private key `openssl pkey -in key.pem -noout -text | grep -A3 "priv:" | tail -n +2 | tr -d ' :\n'`.
- Which target serves `beancount.io` is not established in this repository (`w2/blocked/m35/t013.md`); establish it before setting the production value. Setting `MCP_REGISTRY_AUTH_PROOF` requires a backend-v2 deploy that includes t002.
- A probe on 2026-10-03 got `502` from `https://beancount.io/.well-known/mcp.json`; the registry does not probe the remote, but a listing that points at a dead endpoint is worse than no listing.
- `key.pem`, the hex key, and the record must stay out of the repository and the board (gitleaks gates every push; the record itself is public but is production-only configuration).

## Steps

1. Generate the key pair in `backend-cluster/backend-v2/tmp/` or a password manager; derive the record and the hex private key.
2. Set `MCP_REGISTRY_AUTH_PROOF` on the production backend, deploy, and confirm `curl -fsS https://beancount.io/.well-known/mcp-registry-auth` prints the record.
3. In GitHub, create environment `mcp-registry-publish` restricted to `main` (optionally with a required reviewer) and add `MCP_REGISTRY_PRIVATE_KEY`.
4. Re-check the endpoint: `yarn mcp:conformance https://beancount.io` from `backend-cluster/backend-v2/` must pass the unauthenticated-challenge and discovery checks.
5. Dispatch `Publish (mcp registry)` with `publish`, or run `mcp-publisher login http --domain beancount.io --private-key "$KEY"` and `mcp-publisher publish server.json` locally.
6. Verify `curl -fsS "https://registry.modelcontextprotocol.io/v0.1/servers/io.beancount%2Fbeancount/versions/latest"` shows status `active`, version `1.0.0`, and the remote URL; record the timestamp and version in the milestone README.

## Blocked

**Blocked 2026-10-03** — every prerequisite in this repository is shipped (t001–t005; backend `b4518048` serves the route when configured, workflow `d4449afc`), but the three remaining steps are the deployment operator's and cannot be done from here:

1. **The signing key.** Generating it is a one-line OpenSSL 3 command (`docs/mcp.md`, "Publishing the registry listing"), but it is a long-lived identity for the `io.beancount/*` namespace, so where the private half is kept is the operator's call, not this run's.
2. **The production proof.** `https://beancount.io/.well-known/mcp-registry-auth` answers 404 on 2026-10-03: production either predates `b4518048` or has no `MCP_REGISTRY_AUTH_PROOF`. Which target serves `beancount.io` is still not established in this repository (`w2/blocked/m35/t013.md`), and no production access is available here.
3. **The GitHub secret.** The `mcp-registry-publish` environment exists — GitHub auto-created it, unprotected, when the workflow's first push run reached the publish job — but `MCP_REGISTRY_PRIVATE_KEY` is not set and no deployment-branch rule or reviewer is configured.

Observed the same day: `https://beancount.io/.well-known/mcp.json` answers 200 and `POST /api-gateway/mcp` answers 401 with discovery, so the 502 seen on 2026-10-03 was transient; the registry has no `io.beancount/beancount` (404).

Steps 4–6 of this task then verify through the registry API.
