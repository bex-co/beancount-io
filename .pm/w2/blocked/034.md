# Ledger counts read from one upstream page

Found while fixing the public catalog in [m34](./m34/README.md). Three backend-v2
paths call the ledger service's `GET /ledgers` themselves instead of going
through the workflow, each with one page. Gitea caps a page at 50, so each of
these is wrong once a user can reach more ledgers than one page holds:

- `src/features/ledger/operations/create-ledger.ts` enforces the tier ledger
  limit by counting owned ledgers inside `page: 1, limit: 10` of the
  *accessible* catalog. The count tops out at 10, below the Growth (20) and
  Organization (100) limits. Collaborations that sort before the user's own
  ledgers push owned ones off the page, so the count can be low on any tier.
- `src/features/auth/service/account-service.ts` reports `limits.ledgersUsed`
  from `limit: 100`, which arrives as 50. The dashboard's `useUserLimits()`
  reads this number to decide whether to offer "Create ledger".
- `src/features/gitea/feed/service/feed-service.ts` builds the activity feed from
  `limit: MAX_REPOSITORIES` (100), so activity in ledgers past the 50th never
  appears.

Also latent: `TIER_LIMITS[ENTERPRISE].maxLedgers` is `-1` (unlimited), but
create-ledger compares with `>=`. Any user resolved to that tier would be refused
every create. No code path assigns the tier today.

Fix shape: count owned ledgers with the unpaged owned-catalog read m34 adds
(`listUserOwnedLedgers` with no `page`/`limit` reads `GET /users/{username}/repos`
in full, so collaborations are never mistaken for owned ledgers), and treat a
negative limit as unlimited.

Needs a product decision first. Counting correctly will refuse creates for
users who are already over their tier's limit because of the undercount.
Decide whether existing ledgers are grandfathered before this ships.


**Blocked 2026-10-02** — Confirmed on `main`: `create-ledger.ts` still counts owned ledgers within the first 10 accessible rows, `account-service.ts` requests one page of 100, and `feed-service.ts` requests one capped page. Correcting the count changes both server-side creation eligibility and the dashboard Create action for existing over-limit users. The note explicitly requires a product decision before these changes ship; no grandfathering policy is recorded.

**Unblock:** the repository owner decides how existing over-limit accounts are treated (enforce the accurate tier count for new creates, or specify a grandfathering allowance and its scope). Then implement the complete reads and unlimited-tier handling with regression and cross-surface checks. **Who can clear it:** the repository owner. No partial implementation was made.
