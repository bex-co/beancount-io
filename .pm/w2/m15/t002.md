## Objective

Route protected social reads and mutations through application-service PEPs while retaining Gitea as the current relationship source and leaving explicit public reads at their public boundary.

## Context

- Existing social operations are grouped under coarse session-only/read/write classes.

## Steps

1. Make each protected public service method accept the resolved `Identity` and call the PDP before Gitea/backend work; use workflows only for real orchestration.
2. Resolve current target visibility/relationship facts from stable IDs and authoritative data on every authorization call.
3. Keep operation IDs in AsyncLocalStorage; remove superseded authorization checks but preserve validation, public routing, and exact API error contracts.

## Files

- `backend-cluster/backend-v2/src/features/gitea/feed/**`
- ledger star/unstar workflow files
- authorization integration files

## Acceptance criteria

- [ ] Follow/unfollow and star/unstar authorize the authenticated user's own preference only.
- [ ] Public/private repository visibility is unchanged.
- [ ] Denied mutations make no Gitea write.
- [ ] Direct service calls cannot bypass authorization and audit under the canonical-action fallback.

## Out of scope

- General ledger-content authorization or an authorization-only workflow wrapper.
