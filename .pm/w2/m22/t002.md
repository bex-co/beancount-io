## Objective

Give interactive and workload clients durable, server-controlled authorization bounds from which OAuth tokens can safely be minted.

## Context

- A workload needs a stable user owner and authorization grant even when no user is present at token-exchange time.
- The OAuth catalog already centralizes static clients, resources, and lifetimes, while the PDP owns credential ceilings.

## Steps

1. Add one authoritative client-policy resolver for static, dynamically registered, interactive, and workload profiles, including allowed grants, resources, token authentication, and lifetime selection.
2. Persist a user-owned workload authorization with stable client/grant identity, allowed resources, scope ceiling, optional ledger pin, lifecycle state, and safe rotation metadata.
3. Enforce paid-plan creation, ownership, consent, no-self-replication, narrowing-only updates, and resource binding at client/grant creation rather than trusting token-request input.

## Files

- `backend-cluster/backend-v2/src/features/oauth/data/**`
- `backend-cluster/backend-v2/src/features/oauth/api/**`
- `backend-cluster/backend-v2/src/features/oauth/model/**`
- relevant migrations and authorization actions

## Acceptance criteria

- [ ] A token request can resolve one stable user owner and client/grant principal without accepting a caller-supplied user ID.
- [ ] Allowed audience, scopes, and ledger pin come from persisted/server-owned bounds and can only narrow.
- [ ] MCP-only dynamic clients cannot silently acquire application-API authority, and application clients cannot silently acquire MCP authority.
- [ ] Credentials and request context do not become FGA tuples or a second policy engine.

## Out of scope

- Implementing the client flows or storing private workload signing keys on the server.
