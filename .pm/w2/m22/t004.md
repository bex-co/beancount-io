## Objective

Allow CI and cron workloads to obtain narrow, short-lived OAuth access tokens without storing a reusable bearer API key.

## Context

- Unattended jobs cannot complete an interactive browser flow on every run.
- A symmetric client secret would reproduce much of the leakage and replay risk of the personal API key it replaces.

## Steps

1. Implement standards-based confidential workload authentication with `private_key_jwt`, and define an extension point for approved external workload federation/token exchange where available.
2. Bind the authenticated workload client to its user-owned grant and issue only the stored resource, scopes, ledger pin, subject, and one-hour access-token lifetime.
3. Support public-key registration/rotation, assertion audience/issuer/subject/time validation, replay prevention, revocation, and operationally safe bootstrap/recovery.

## Files

- `backend-cluster/backend-v2/src/features/oauth/**`
- workload client/grant persistence and management surfaces
- CI/cron setup examples and fixtures

## Acceptance criteria

- [ ] A workload exchanges a signed, short-lived assertion for a one-hour OAuth access token and never uses the assertion itself as an API bearer.
- [ ] The token's user, client/grant, audience, scopes, and ledger pin are server-derived and cannot be broadened by request parameters.
- [ ] Expired, replayed, wrong-audience, wrong-issuer, unknown-key, revoked, and rotated-key assertions fail closed.
- [ ] No private signing key, client secret, access token, or user data is committed, logged, or written to the public board.

## Out of scope

- Building a general-purpose cloud identity broker or migrating backend provider credentials such as Plaid.
