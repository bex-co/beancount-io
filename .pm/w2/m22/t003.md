## Objective

Let a human authorize a CLI or interactive agent without copying a permanent personal key.

## Context

- Local CLIs may open a browser callback; remote terminals and coding agents also need a headless-friendly standards path.
- Browser authorization must preserve consent, resource binding, PKCE, and safe redirect behavior.

## Steps

1. Add a standards-based device authorization flow, or authorization code + S256 PKCE where a verified loopback callback is available, using provider primitives rather than a parallel token protocol.
2. Bind authorization, consent, client, resource, scopes, ledger pin, device/user code, expiry, polling, and replay protection to one stored transaction/grant.
3. Add CLI/agent token acquisition, renewal, secure local storage, logout/revocation, and actionable expiry/denial behavior without logging credentials.

## Files

- `backend-cluster/backend-v2/src/features/oauth/**`
- supported CLI/agent OAuth client surfaces
- shared public discovery and setup documentation

## Acceptance criteria

- [ ] An interactive client obtains a one-hour application or MCP access token only after user authorization and exact resource/scope consent.
- [ ] Headless authorization does not require copying an access token, refresh token, authorization code, or password through chat or logs.
- [ ] PKCE/device codes are single-use, expiring, client-bound, and resistant to polling abuse and callback substitution.
- [ ] Denied, expired, cancelled, and revoked grants recover with actionable user-facing behavior.

## Out of scope

- Browserless password collection or inventing a proprietary long-lived bearer credential.
