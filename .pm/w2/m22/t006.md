## Objective

Move supported users and tools from personal-key creation and headers to the appropriate OAuth client/grant lifecycle.

## Context

- Dashboard settings currently manage API keys, OpenAPI advertises `x-api-key`, and public examples teach `bcio_` bearer values.
- Interactive and unattended clients need different onboarding even though both ultimately present OAuth access tokens.

## Steps

1. Replace Dashboard API-key management with OAuth client/grant creation, scope/resource/ledger-pin review, public-key rotation, revocation, and truthful token-lifetime status.
2. Update supported CLI, agent, MCP, GraphQL/REST, conformance, and self-hosted client paths to select interactive or workload OAuth setup and use standard bearer tokens.
3. Provide a migration view/instruction for any existing personal keys without displaying stored credentials or claiming they were converted in place.

## Files

- Dashboard credential-management feature
- CLI/agent/MCP client configuration and conformance scripts
- backend OAuth management API and generated/public API contracts

## Acceptance criteria

- [ ] An interactive user and an unattended workload can complete setup from the supported UI/docs and call only their approved resource.
- [ ] Dashboard clearly distinguishes delegated client access, workload public keys, active grants, expiry, and revocation effects.
- [ ] Supported clients no longer require users to copy a `bcio_` value or send `x-api-key` after migration.
- [ ] Existing Mobile, Dashboard, Discourse, and MCP OAuth behavior does not inherit workload-only authority.

## Out of scope

- Automatically exporting secrets or changing unrelated third-party integration settings.
