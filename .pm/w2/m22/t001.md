## Objective

Define the interactive, workload, compatibility, and retirement contracts before replacing the current personal API-key path.

## Context

- Personal `bcio_` keys currently cover CLI, agents, CI, cron, GraphQL, REST, and MCP and are looked up on every request for immediate revocation.
- OAuth access tokens are self-contained and short-lived; a client-credentials token alone does not establish which user or ledger authorized a workload.
- The current dynamic-registration profile is MCP-specific, so it cannot simply be reused as an unrestricted application-API client.

## Steps

1. Inventory issuance, storage, authentication, authorization, rate, audit, docs, Dashboard, CLI, MCP, OpenAPI, and deployed personal-key use; record only aggregate evidence on the public board.
2. Specify authorization code + S256 PKCE/device authorization for interactive clients and a user-owned asymmetric or federated workload profile for CI and cron.
3. Define resource, scope, ledger-pin, lifetime, revocation, migration, rollback, and dated sunset semantics, including the condition under which zero usage permits immediate retirement.

## Acceptance criteria

- [ ] Every supported personal API-key use case maps to an explicit interactive or unattended OAuth profile.
- [ ] The design does not treat a renamed long-lived bearer or shared client secret as the replacement.
- [ ] The sunset gate requires aggregate proof of zero live use or a dated compatibility window with an owner.
- [ ] Third-party provider keys, webhooks, email/observability tokens, OAuth client authentication, and deployment secrets are explicitly out of scope.

## Out of scope

- Changing the Dashboard's requested one-year token policy from m21 or migrating third-party service credentials.
