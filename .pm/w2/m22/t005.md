## Objective

Make OAuth presentation preserve every security and abuse-control property that personal API keys currently provide.

## Context

- API-key scopes, paid issuance, ledger pins, MCP eligibility, rate budgets, per-request lookup, and audit identity are independent constraints.
- Keying an OAuth rate budget by access-token `jti` would reset the budget whenever a token rotates.

## Steps

1. Map verified interactive/workload OAuth profiles into the centralized credential policy while preserving each operation's existing scope, relationship, paid-plan, and ledger-pin checks.
2. Derive rate and audit identity from stable client/grant claims, carry operation IDs safely, and retain the current operational classes and explicit budgets.
3. Define revocation so client/grant disablement stops new authorization and refresh immediately while documenting the bounded lifetime of already-issued access tokens.

## Files

- `backend-cluster/backend-v2/src/features/auth/**`
- `backend-cluster/backend-v2/src/features/authz/**`
- OAuth identity, rate-limit, audit, and MCP gate integrations

## Acceptance criteria

- [ ] Replacing an API-key identity with its OAuth workload equivalent neither grants nor removes any operation capability.
- [ ] Rotating access tokens preserves one continuous rate budget and stable, non-secret audit attribution.
- [ ] A revoked client/grant cannot mint or refresh; previously issued tokens expire within the standard one-hour TTL and docs make that distinction explicit.
- [ ] Source outages, malformed claims, unknown profiles, and missing client/grant records fail closed before domain side effects.

## Out of scope

- Expanding domain permissions, changing operational budgets, or adding a general token-introspection service.
