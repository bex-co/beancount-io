## Objective

Remove the user-facing API-key authentication system only after supported consumers have migrated or aggregate evidence proves none exist.

## Context

- The current assumption is that personal API keys have no users, but a public removal needs evidence rather than an unverified flag-day assertion.
- Historical database migrations should remain even when runtime models and endpoints retire.

## Steps

1. Measure active/accepted personal-key use with aggregate, non-identifying evidence and choose immediate retirement only if it is zero; otherwise run the dated compatibility and communication window from t001.
2. Disable creation first, then remove API-key verification, identity resolution, management operations, schema/security declarations, conformance acceptance, and persisted runtime model after the exit gate holds.
3. Remove obsolete `bcio_` and `x-api-key` paths from supported clients and docs while confirming similarly named infrastructure/provider secrets are untouched.

## Files

- `backend-cluster/backend-v2/src/features/apikeys/**`
- API-key branches in auth, authz, GraphQL, REST, MCP, rate, and audit code
- Dashboard management UI, OpenAPI security schemes, examples, and tests

## Acceptance criteria

- [ ] The acceptance cutoff is backed by aggregate zero-use evidence or completion of a published compatibility window.
- [ ] No new personal key can be issued before acceptance is removed, and unsupported keys fail with a clear terminal authentication error afterward.
- [ ] Runtime personal-key routes, schema, identity method, and docs are removed without deleting historical migrations or unrelated secrets.
- [ ] Rollback and incident steps do not require recovering or re-exposing plaintext keys.

## Out of scope

- Destructive deletion of audit history or third-party/infrastructure credentials.
