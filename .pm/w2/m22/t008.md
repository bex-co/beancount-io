## Objective

Make the OAuth-only credential model discoverable and usable for newcomers, agents, self-hosters, and automation operators.

## Context

- Current top-level and backend guidance prominently teaches personal API keys.
- OAuth terminology can hide the practical choice between a human-authorized tool and an unattended workload.

## Steps

1. Update root/backend/CLI/MCP/OpenAPI and self-hosted guidance with one interactive quick start and one workload quick start based on discovery.
2. Explain client, grant, resource/audience, scopes, ledger pin, one-hour token expiry, renewal, rotation, and revocation in user-facing language.
3. Add migration/troubleshooting guidance for terminal API-key rejection without publishing credentials, tenant data, or internal-only deployment details.

## Files

- `README.md`
- `backend-cluster/backend-v2/README.md`
- relevant CLI, MCP, OpenAPI, Dashboard, and deployment documentation

## Acceptance criteria

- [ ] A new interactive user can authorize a supported tool without first learning API-key internals.
- [ ] A self-hoster can configure a workload public key and obtain a narrow token without a beancount.io host constant.
- [ ] Examples use discovery, the correct resource, least scopes, and placeholders that cannot be mistaken for live secrets.
- [ ] Docs distinguish personal-key retirement from unchanged Plaid/provider/webhook/operational secrets.

## Out of scope

- Marketing claims that every external identity provider or CI platform is supported.
