# REST `PUT …/files/{path}` sends raw UTF-8 where the ledger service expects base64

Found during w2/m26 live verification (docker-mac): `PUT /api-gateway/v1/ledgers/{owner}/{name}/files/{path}`
with `{"content": "<utf-8 text>"}` fails with `BAD_USER_INPUT: illegal base64 data`,
because `LedgerRepoService.changeFiles` forwards `content` verbatim to the ledger
service's `change-files`, which passes it to Gitea as base64. The MCP
`editLedgerFiles` tool base64-encodes before the same call, so it works; only the
REST file-write path is broken. Pre-existing on main, out of m26's scope
(m26 covers the MCP write path; not in t001–t006).

Suggested fix (one place): base64-encode `body.content` in the REST files handler
or `LedgerRepoService.changeFiles`, plus a live roundtrip (PUT → GET bytes equal)
and a parity unit test. Keep the OpenAPI description ("full new content, as UTF-8
text") — the encoding stays an internal detail.
