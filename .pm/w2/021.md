# `bea query` silently drops `--output` and `--numberify` under `--json`, and `-f beancount` fails with a raw Python message

Found 2026-09-12 by a CLI QA sweep against HEAD `84231f9c`, bea 0.2.0. Two sub-hour fixes in the same command.

## 1. `--json` accepts `-o` / `-m` and discards them (exit 0, no warning)

```
$ bea --json --file main.bean query "SELECT date, account WHERE account ~ 'Food'" -o /tmp/q.out
{"bea": "0.2.0", "target": {...}, "data": {"columns": [...], "rows": [...]}, "truncated": false}
$ echo $?; test -f /tmp/q.out && echo exists || echo "no file"
0
no file
```

`-m/--numberify` is dropped the same way — the envelope is byte-identical with and without it. `cli/docs/REFERENCE.md:135-136` documents `--output, -o` as "Write the result to this file instead of stdout" and `--numberify, -m` as "Split amounts into one column per currency", with no `--json` exception anywhere. So a script running `bea --json query … -o results.csv` gets a clean exit and no file.

- Root cause: `cli/src/cli/commands/query.py:92-96` forwards `--output` and `--numberify` to the engine, but `cli/src/bea_engine/main.py:82-83` routes `format == "json"` to `bql.rows_answer(resolved, query_string, allow_errors=...)`, which takes neither parameter. Only the `else` branch (`main.py:85-92`, `bea_engine/query.py:74-105`) honours them.
- `-f/--format` is also ignored under `--json`, which is fine — JSON *is* the rendering. `-o` (a destination) and `-m` (a data shape) are different concerns.
- Precedent for the right behavior is in this same CLI: `bea format` raises a usage error rather than guessing when JSON mode and a destination conflict — "In --json mode, formatting needs an explicit destination: pass --in-place to rewrite the files, --output FILE, or --check/--dry-run to report instead." (`cli/src/cli/commands/format.py:82-85`, documented at `cli/docs/USAGE.md:232`).
- Fix: either honour `-o` under `--json` by writing the envelope to that path, or reject `-o`/`-m` with `--json` as a usage error (exit 2) the way `format` does. Pick one and document it in `USAGE.md`'s automation section. Silently dropping an explicitly named destination is the one option to avoid.

## 2. `-f beancount` on a column `SELECT` surfaces an internal Python message

```
$ bea --file main.bean query "SELECT date, account" -f beancount
Error: too many values to unpack (expected 1)          # exit 1, category "validation"
$ bea --file main.bean query "SELECT date" -f beancount
Error: 'datetime.date' object has no attribute 'meta'  # exit 1
$ bea --file main.bean query "PRINT" -f beancount      # works, exit 0
```

`beancount` is one of three names `cli/src/cli/commands/query.py:28` validates against (`bogus` is rejected with a good message: "Unknown query format 'bogus'. Choose one of: text, csv, beancount."), so bea owns this surface — but it validates the format *name* without checking that the query actually produces entries.

- Origin is upstream: `bean-query -f beancount main.bean "SELECT date, account"` raises the same `ValueError` from `beanquery/render/beancount.py:11` (`[entry for entry, in rows]`). bea catches it and maps it to `LedgerError`, which is already an improvement on upstream's traceback — but the resulting message tells a user nothing.
- Fix: keep the delegation and improve the mapping only — when `--format beancount` fails to unpack rows, say so in bea's own words, e.g. "`--format beancount` prints directives, so the query must return entries; use `PRINT`, or `--format text`/`csv` for a column result." Classify it `usage` (exit 2) rather than `validation` (exit 1): the ledger is fine, the flag/query combination is not. No reimplementation of upstream rendering.

Nothing on the board covers `bea query` output flags. `git log -S rows_answer -- cli/src/bea_engine/main.py` shows the split introduced by `a90b1706` (ADR014 engine split) and unchanged since — present on main, not deployment lag.
