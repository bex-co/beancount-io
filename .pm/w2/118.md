# Source views draw an account with a Persian or Arabic segment in the wrong order: the amount lands inside the account path

**Minor · dashboard · 45–60 minutes.** A2/A3: Persian is one of the dashboard's 15 locales, and an account such as `Assets:Bank:ملی` is valid Beancount. Wherever the dashboard shows ledger source, such a posting reads as a different account and amount. This is the dashboard counterpart of mobile's [w21/780](../w21/done/780.md) (commit diff) and [w21/865](../w21/done/865.md) (Entry Context source).

Production https://beancount.io, 2026-11-10, English UI, isolated headless Chromium 156 at 1440×1000, signed in as the owner of the designated synthetic ledger. Both test writes were deleted; main.bean was restored to blob `f1a0b83c`. Local main `022da3103`. Screenshots kept locally (`rtl-diff.png`, `rtl-entry-context.png`, `rtl-blob.png`, `rtl-journal.png`).

## Reproduce

1. Open Account `Assets:Qa:ملی`, then add a transaction: `Assets:Qa:ملی 1.00 USD` / `Assets:Cash -1.00 USD`. Stored text: `  Assets:Qa:ملی                               1.00 USD`.
2. Look at the posting in each view:

| View | Rendered |
| --- | --- |
| Commit diff (`/commit/<sha>`) | `Assets:Qa:1.00 ……… ملی USD` (the amount sits inside the path; the Persian segment sits beside the currency) |
| Entry Context source (Journal → open entry) | `Assets:Qa ……… ملی:1.00 USD` (the segment and its colon move next to the amount) |
| File view (`/files/blob/main/main.bean`) | the `open` line reads `open Assets:Qaملی:` (the colon is pushed to the end) |
| Journal table with Postings | `Assets:Qa:ملی` │ `1.00 USD` ✓ (account and amount in separate cells) |

Every view uses an English (LTR) interface, so this is not the Persian-UI case fixed in [w4/226](../w4/done/226.md).

## Root cause

w4/226 made each diff line `direction: ltr; unicode-bidi: isolate` (`common/components/diff-viewer/diff-viewer.css:13-14`). That fixes an RTL page around LTR source. It does not cover RTL letters inside an LTR line: under the Unicode bidi algorithm, the run `ملی` plus the following spaces and the number `1.00` are reordered as one right-to-left run. Mobile solved exactly this with `isolateSourceLine` (`mobile/src/common/bidi.ts`, w21/780), which isolates each string, comment and word that holds Hebrew or Arabic-script letters. The dashboard has no per-token isolation. Its Monaco views render tokens as spans with no bidi isolation.

## Fix

- **Diff viewer:** when rendering a change's text, wrap each token (word or string literal) that contains RTL letters in `<bdi>` or a span with `unicode-bidi: isolate`, the same tokenization rule as mobile's `isolateSourceLine`. Keep the line-level isolation from w4/226. Copy the rule locally; packages stay independent.
- **Monaco views** (Entry Context source and file view): give the Beancount tokenizer's account and string token classes `unicode-bidi: isolate` in the editor stylesheet, or add inline decorations with an isolating class on RTL-bearing tokens. Verify the caret still moves in logical order.
- **Tests:** add a regression for the diff viewer using the exact posting line above (assert that `1.00` follows the account in the DOM's isolated structure), plus a visual check in Persian and English UIs.

## Blast radius

Commit and pull-request diffs (`common/components/diff-viewer`), Entry Context and the entry page (Monaco), and the file view and editor (Monaco). Tables that put account and amount in separate cells are unaffected.
