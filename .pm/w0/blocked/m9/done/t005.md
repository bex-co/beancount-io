## Objective

Route the expired event to the recovery operation, behind the handler's existing verification.

## Context

- `backend-cluster/backend-v2/src/features/stripe/api/stripe-webhook-handler.ts` verifies the signature, drops test-mode events and a foreign `metadata.clientId`, and handles `checkout.session.completed` from `metadata.userId`. Its route description lists the handled events.

## Steps

1. Add `case "checkout.session.expired"` that calls the operation when `metadata.userId` is present, and returns `processed: true` only when an email was sent.
2. Update the route description to list the new event.

## Files

- backend-cluster/backend-v2/src/features/stripe/api/stripe-webhook-handler.ts

## Acceptance criteria

- [x] A test-mode expired event, or one without `metadata.userId`, is ignored before any Stripe or SendGrid call.
- [x] An operation failure surfaces as a non-2xx response, so Stripe redelivers.

## Out of scope

- Enabling the event on the live endpoint (t006).

## Outcome

- `case "checkout.session.expired"` calls `emailCheckoutRecovery` with the verified session, the shared Stripe service, the models, SendGrid, and `config.sendGrid.checkoutRecoveryGroupId`. `processed` is `true` only when an email went out. An ineligible session is acknowledged with `processed: false`. A failure reaches the handler's catch, which answers 400, so Stripe redelivers. The existing livemode and `clientId` checks run first, and a session without `metadata.userId` never reaches the operation.
- The route's OpenAPI description lists the new event. No generated snapshot contains it.
- Tests: 6 added to `stripe-webhook-handler.test.ts`, covering hand-off, ineligible ack, test mode, no user, failure → 400, and a recovered session binding through `checkout.session.completed`. Whether Stripe really copies `metadata` onto the recovered session can only be confirmed live (t006). backend-v2 `yarn typecheck`, `format:check`, `lint:deadcode`, and `yarn test` (9,502, all green) pass.
