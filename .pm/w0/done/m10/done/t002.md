## Objective

Show, on a backend-v2 container running with `NODE_ENV=production` and the environment the Docker targets now render, that OAuth works with only `AUTH_SECRET`, stays off without the flag, and prefers a supplied key.

## Context

- Production refuses the ephemeral development key, so `docker-mac`'s default run does not prove this. Use a local Compose override under `.internal/` that runs backend-v2 in production mode, or bring up `deploy/docker` locally with placeholder domains; whichever reaches the backend's own routes.
- Routes to check: `/.well-known/oauth-authorization-server` (and the protected-resource document), and the JWKS URI that document names.
- Unit coverage of the derivation already exists in `backend-cluster/backend-v2/src/config/jwks/index.test.ts`. This task proves the deployment wiring, not the derivation.

## Steps

1. Run backend-v2 in production mode with `AUTH_SECRET` set, `OAUTH_JWKS` empty and `OAUTH_JWKS_FROM_AUTH_SECRET=true`. Fetch the discovery document and the JWKS.
2. Restart with the flag unset and confirm `503 oauth_not_configured`.
3. Restart with a valid `OAUTH_JWKS` and the flag set, and confirm the served `kid` is the supplied one.
4. Restart twice with the same `AUTH_SECRET` and confirm the derived `kid` is stable.
5. Record versions, the commit, the date and the results in this task's text. Keep logs and scratch files in `.internal/`, never committed.

## Files

## Acceptance criteria

- [x] With only `AUTH_SECRET` and the flag: discovery answers 200 and the JWKS serves one ES256 key.
- [x] Without the flag and without `OAUTH_JWKS`: `503 oauth_not_configured`.
- [x] A supplied `OAUTH_JWKS` is served instead of the derived key.
- [x] The derived `kid` is the same across restarts.

## Out of scope

- A full mobile-app run against a Docker stack. The app's sign-in to a self-hosted stack was proven against bex on 2026-11-19 (PRFAQ006 question 5), and it reaches the same backend code.

## Result (2026-11-25)

Run on `deploy/docker` itself: its `docker-compose.yml` at `dcce9ef14` plus t001's change, brought up locally as project `m10-proof` from an `.env` made from `.env.example` with the `change-me` values replaced, `SELF_HOST=true`, and the names `books.localhost`, `api.books.localhost` and `git.books.localhost`, so Caddy served them with its internal CA. Every request went through Caddy on 443. Docker Engine 29.7.2 with Compose 5.4.0, Caddy 2.11.4, Gitea 1.24.7, PostgreSQL 16 (alpine), and backend-v2 built from `main` on 2026-11-22 (Node 22.23.4, `NODE_ENV=production`), which includes the derivation from `eadd4fb9e`.

- **Only `AUTH_SECRET` and the flag** (`OAUTH_JWKS` empty, `OAUTH_JWKS_FROM_AUTH_SECRET=true` as `.env.example` sets it): `https://books.localhost/.well-known/oauth-authorization-server` answered 200 with issuer `https://books.localhost` and `jwks_uri` `https://books.localhost/api-gateway/oauth/jwks`, which served one key: EC P-256, ES256, no private part. The app's own discovery request, `/.well-known/oauth-protected-resource/v1`, answered 200 with resource `https://books.localhost/v1` and authorization server `https://books.localhost`, which is what the app checks for the address `https://books.localhost`. `POST https://books.localhost/api-gateway/mcp` without a token answered 401 with `resource_metadata="https://books.localhost/.well-known/oauth-protected-resource"`, whose document names resource `https://books.localhost/api-gateway/mcp`, and a client registration like an MCP host's at `/api-gateway/oauth/reg` answered 201.
- **The `.env` without the new line** (an install from before this change): the backend's `OAUTH_JWKS_FROM_AUTH_SECRET` rendered empty, and the discovery document, the protected-resource document and the JWKS each answered `503 oauth_not_configured`.
- **A supplied `OAUTH_JWKS`**, with the flag still set: the JWKS served the supplied key (`kid` `operator-supplied-m10`) instead of the derived one.
- **Restarts:** the derived `kid` was `KxaMYBIYyN2Vs5O3KoXZyU` at first boot, after two `docker compose restart backend-v2` and after a forced recreate, all with the same `AUTH_SECRET`.

To reproduce: from `deploy/docker`, `docker compose -p <name> --env-file <your env> up -d`, then fetch the routes above; switch the `.env` and run `docker compose up -d backend-v2` between cases.
