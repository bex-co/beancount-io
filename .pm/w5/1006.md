# Use effective unit costs when recognizing total-cost short covers

**Major · cli · 30–45m · A1 · worker1.** A positive cover expressed as a
total or compound cost loses the existing short lot's exact label. The write
succeeds and checks valid, but leaves two offsetting positions and a following
`add close` fails: the units cancel but the lots do not. The economically
identical per-unit cover empties the inventory and closes correctly.
No product fix implemented.

The book holds one short HOOL at 100 USD with an exact multi-line label.

cost-lot identity; no plugin or malformed ledger is involved.

                         exit=r.returncode,stdout=r.stdout,stderr=r.stderr,duration=time.monotonic()-start,

The plain-label total-cost control likewise shows why the symptom requires
a label whose exact text changes during acquisition normalization.

Cause: `cli/src/bea_engine/ledger/writer.py:256`, `_cost_parts`, reads
`Cost.number` or `CostSpec.number_per`. `_covers_short` (:297) compares that
number directly with the held lot's booked unit cost. For an unbooked
`CostSpec`, it ignores `number_total` and posting quantity. The held lot's
number is correctly 100, while the incoming per field is 0 or 50. The new
predicate returns false even though native `booking_full.compute_cost_number`
returns 100. `normalize_entry_strings` (:334, :377) therefore applies ordinary
acquisition label normalization instead of preserving the exact cover selector.

`format_transaction` (:477, :499) intentionally represents a structured total
with null per as `CostSpec(0, total, ...)`, so that documented shape is affected
too. It must not be reinterpreted as an open or zero-price lot. In the two-unit
case, comparing the total 200 directly with held cost 100 would also be wrong:
the correct unit cost is `(total + per * abs(units)) / abs(units)` using native
booking semantics.
