# Overview switches to another month and back within a second of opening whenever the browser's date differs from the server's: "August 2017" → "September 2017" → "August 2017", with React error #418

**Severity:** minor. The page settles on the right month, but for about a second every card, chart and heading answers for the wrong one, React discards the server-rendered page, and four extra API reads go out. It happens on every Overview load from a browser whose calendar date differs from UTC's: in the Americas every evening (from 16:00 in California, 18:00 in Mexico City), and in Asia and Oceania every morning. **Owner:** `dashboard`. **Estimate:** 45–60 minutes including tests. **A2:** the Overview loader promises that the month it opens on "never changes under the reader"; a newcomer opening their books in the evening sees it change. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-26 local (2026-11-27 UTC) against `https://beancount.io`, production entry chunks `main-B-XRW1Dk.js` and `main-BBmi61Hs.js` (deployed during the run). QA-owned headless Chromium 158, fresh isolated contexts with Playwright `timezoneId`, 1440×1000, English. Reproduced signed out on the public ledger and signed in on two QA-owned ledgers. Read-only: no ledger writes. Local HEAD `78eb9e1da`.

## Repro

Public ledger, no sign-in needed. The browser's date must differ from UTC's when the page loads. A browser zone of `Pacific/Pago_Pago` (UTC−11) does that while UTC's hour is below 11, and `Pacific/Kiritimati` (UTC+14) while it is 10 or above.

1. At 19:57 in `America/Mexico_City` on 2026-11-26 (01:57 UTC on 2026-11-27), open `/ledger/open_ledger/example`.
2. The month dateline reads **August 2017** in the server-rendered page, **September 2017** about 200 ms after the scripts run, and **August 2017** again about one second later (sampled every 20 ms).
3. The console shows `Minified React error #418` (hydration text mismatch). A `data-` attribute set on `<main>` at `DOMContentLoaded` is gone afterwards: React replaced the server-rendered tree.
4. The client sends `GetLedgerOverview` for `time=2017-09` and `2017-08-31`, `GetLedgerOverviewValuation` for `2017-09`, then `GetLedgerOverview` for `2017-08` and `2017-07-31`. With the browser in UTC, only the last two (and one `GetLedgerJournal`) go out.

Controls at the same moment: `UTC` and `Pacific/Kiritimati` (both 2026-11-27 locally) show August 2017 throughout, no #418, and the server-rendered `<main>` is kept. A QA-owned ledger whose newest transaction is 2026-10-02 flips September 2026 → October 2026 → September 2026 in Mexico City and stays on September in UTC; its dormancy line also renders "Last entry 2026-10-02 (8 weeks ago)" on the server and "(7 weeks ago)" in the browser.

## Cause

- The server and the browser each take "today" from their own clock: `dashboard/src/features/reports/overview/loader.ts:30` and `features/reports/overview/index.tsx:220`, both `toLocalISODate(new Date())`. The server runs in UTC.
- `today` goes into the newest-transactions read as a date predicate (`features/reports/overview/lib/recent-transactions.ts:4-10`, `recentTransactionsVariables`), so the variables differ: the server caches `…|2026-11-2[0-6]|2026-11-27$` and the browser asks for `…|2026-11-2[0-5]|2026-11-26$`. The browser misses the cache the server filled.
- While that read is in flight, `useDataThrough` (`hooks/use-overview-month.ts:36-46`) gets no data, and `dataThroughOf(undefined, today)` falls back to today (`lib/overview-month.ts:25-31`, `lib/overview-utils.ts:585-590`). `openingMonth` then treats the ledger as running through today and picks its latest month, September 2017 instead of the settled August 2017. When the read lands, it picks August again.
- The first browser render therefore differs from the server's HTML ("September 2017" for "August 2017", and the weeks-ago text, `components/month-summary.tsx:71-75`), which is React error #418. React 19 recovers by rendering the whole root again in the browser.

## Fix

- The server render and the hydration render use the same `today`. For example, the Overview loader returns the date it used, as it already returns `readme`, and the page reads that until `useHydrated()` is true, then the browser's day. This is the hydration-stable pattern `useHydratedTime` (`common/hooks/use-date-locale.ts`) set for timestamps in w4/m36.
- When the browser's day differs and the newest-transactions read has to run again, the page keeps the data-through date it already has (Apollo `previousData`, or the server-day result) while that read is in flight, instead of falling back to today. The month then changes only if the browser-day answer itself moves it, for example an entry dated today in the browser but tomorrow in UTC (w5/1176's rule still holds).
- Do not change which month the page opens on when the dates agree, and keep the Time, account and filter handling, `?month=` and Back (w5/1148), and dormancy measured on the unfiltered ledger (w5/1149).
- Tests: a real server render with one `today` hydrated with the next day keeps the server's month and dormancy text, raises no hydration error, and never shows the other month while the browser-day read is pending; a control where both days agree is unchanged. The first fails on the current code.

## Definition of done

- With the browser's date one day behind and one day ahead of UTC's (for example `America/Mexico_City` in the evening and `Pacific/Kiritimati`), `/ledger/open_ledger/example` shows August 2017 from the first paint to settled, with no #418, the server-rendered `<main>` kept, and no `GetLedgerOverview` or `GetLedgerOverviewValuation` request for 2017-09.
- A same-date control (UTC) is unchanged. Dashboard gates pass.

## Blast radius

`today` is also the default in `components/net-worth-card.tsx:310`, `components/recent-activity-card.tsx:34` and `components/income-expenses-chart.tsx:43`, and feeds `financialPositionPeriod` (`lib/overview-month.ts:91-125`), whose current-month valuation range ends today. On a month boundary (the evening of the last day of a month west of UTC) the server and browser disagree on the month itself. That case was not reproduced. Journal, Accounts, Budget, the statements, Holdings, Statistics, Commodities, Documents, Events, Errors, Query and the account page showed no #418 in `America/Mexico_City` during the run.

## Dedupe

Searched `.pm/**`, including `done/` and `blocked/`, for hydration, `#418`, `toLocalISODate`, `recentTransactionsVariables`, server date or clock, and time zone. w4/m36 (done) made commit, activity and repository-card timestamps hydration-stable and scoped other consumers out. w4/done/317 and w21/done/436 and 856 concern the server's UTC date in Create Ledger, receipts and Ask AI. w5/done/1148 (Back loses the month), 1149 (dormancy from the filtered view) and 1176 (future-dated entries) changed how the month and "today" are chosen, not where "today" comes from during hydration. `main` still computes `today` from each runtime's own clock, so this is not deployment lag.

**Unverified:** the month-boundary case, the 390px layout, right-to-left locales.
