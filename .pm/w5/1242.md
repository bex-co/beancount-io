# A file link to a line (`?lineNumber=`) often opens with that line under the editor's sticky heading: Errors → source, Entry Context → Open source and shared line links land on a hidden line, and in edit mode the caret is in it

**Severity:** minor. Nothing is written by itself, but the page that exists to show one line hides that line. On a Beancount file organized under `* Section` headings, which is how `bean-example` and the public example ledgers are laid out, the target line is often scrolled to the very top of the editor, where Monaco's sticky heading covers it. The first line the reader can see is the next one. From the Errors page, or from Entry Context for a ledger they can write, the editor opens in edit mode with the caret at the end of the hidden line and keyboard focus in it. **Owner:** `dashboard`. **Estimate:** 30–45 minutes including tests. **A2:** a newcomer whose ledger has an error clicks the error's file on **Errors** to fix it. They are shown the line after the broken one and type into a line they cannot see. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English. Reproduced signed out on a public ledger, and signed in as the QA account on its disposable `qa-` ledger, read-only (edit mode was opened, nothing was typed or saved). Local HEAD `8757c3311`.

## Repro

Public ledger, no sign-in needed.

1. Open `/ledger/open_ledger/example/files/blob/main/main.bean?lineNumber=40` from a fresh page load. Repeat with `lineNumber=500`, `2000` and `12`.
2. Sometimes line 40 is centered in the 813px editor and highlighted, 407px below its top. Often it is instead at the very top (3px), and the sticky heading `13 * Commodities` (18px tall) is drawn over it. The first visible line is 41. Line 500 hides under `70 * Banking`, line 2000 under `833 * Credit-Cards`, and line 12 under `5 * Options`. In one fresh browser context, 5 of 8 consecutive loads hid the line. In another, 1 of 4 did.
3. Owner path: on a ledger with an error (here a disposable QA ledger whose `main.bean` includes two missing files), open **Errors** and click `main.bean` on the `Line 12` row. The URL becomes `/files/blob/main/main.bean?editMode=true&lineNumber=12`, line 12 sits under the sticky `7 * Options`, and the editor shows `13 include "./commodities.bean"` as its first line. A fresh load of `?editMode=true&lineNumber=200` on the same file also hid line 200 under `23 * Banking`. The focused caret was at 3px from the editor's top, under the 18px heading.
4. Control: some loads center the line correctly. Opening **Open source at main.bean:5745** from a Journal row's Entry Context centered it once and hid it on a later fresh load of the same URL.

## Cause

The reveal runs before Monaco knows the editor's height.

- `@monaco-editor/react` 4.7.0 creates the editor inside a container that is still 0px tall: its layout height is 5px. The dashboard passes `line={lineNumber}` (`dashboard/src/features/ledger-editor/file-editor/components/ledger-file-view/text-editor.tsx:262`), so the library calls `editor.revealLine(line)` at creation. That scrolls the line to the top of the 5px viewport.
- `handleEditorMount` then calls `editor.revealLineInCenter(lineNumber)` (`text-editor.tsx:181-201`). When `automaticLayout` has already resized the editor to 813px, the line is centered. When the resize has not yet happened, "center" of a 5px viewport is its top. The later resize keeps that scroll position, so the line stays at the top.
- Instrumenting `monaco.editor.create` on production showed both orders. Good loads ran `revealLine(500) layoutH=5`, then `layout h=813`, then `revealLineInCenter(500) layoutH=813`, ending at scrollTop 8575. Bad loads ran `revealLine(500) layoutH=5`, then `revealLineInCenter(500) layoutH=5 domH=813`, then `layout h=813`, ending at scrollTop 8979. In the bad order the container's DOM height was already 813px while Monaco's layout was still 5px.
- Monaco's sticky scroll is on by default and shows the enclosing fold region's first line (`* Commodities`) over the top line, which is why the top line is not just at the edge but covered.

## Fix

Owned by `dashboard`. No API change.

- Reveal the target line only once the editor has its real size. For example, call `editor.layout()` before `revealLineInCenter` in `handleEditorMount`, or reveal on the first `onDidLayoutChange` with a real height. Stop passing `line` to the library, so its early `revealLine` cannot leave the line at the top.
- Keep the rest of the deep-link behavior: the highlighted line, the caret at its end in edit mode, focus, the end-of-file default when no line is given (w3/465), and no re-reveal when toggling between view and edit mode (`text-file-view.tsx:97-103`).

## Definition of done

- On `/ledger/open_ledger/example/files/blob/main/main.bean?lineNumber=40`, `500` and `2000`, 10 of 10 fresh loads show the target line centered and fully below the sticky heading. Line 12 is visible below the heading on every load.
- On a ledger with an error, **Errors** → file opens edit mode with the error line visible and the caret in it, on every one of 10 tries. Entry Context → **Open source** does the same.
- A test of `TextEditor` mounts with a mocked editor whose layout height is 5px at mount and 813px after one layout event. It asserts that the line is revealed in the center after the editor has its real height, or that `layout()` runs before the reveal. It fails on the current code. Dashboard gates pass.

## Blast radius

Every route that opens a file at a line goes through this `TextEditor`. That includes `fileNavigate(…, { lineNumber })` from **Errors** (`dashboard/src/features/ledger-data/errors/index.tsx:39-40`, edit mode), Entry Context's **Open source** (`dashboard/src/features/journal/components/entry-context-panel.tsx:741-748`, edit mode for writers and view mode for readers), the legacy `files/content` route's handoff, and links pasted or shared from the app (w21/223 keeps `?lineNumber=` on those). The no-line case (scroll to the end, w3/465) was not seen to misplace the view.

## Dedupe

Searched `.pm/**`, including `done/` and `blocked/`, for `lineNumber=`, "sticky", `revealLine`, "error line", "target line" and `highlighted-line`. w3/465 (done) chose the end-of-file default. w4/1053 (done) made focus visible on the read-only editor and mentions the sticky heading only as a tab stop. w21/223, w21/152 and w21/340 (done) are the native app's file editor. w3/166 (done) made the Errors source a button. w3/630 (done) fixed malformed `?lineNumber=` values. No item covers a valid line landing hidden, and `main` still reveals at mount through both calls, so this is not deployment lag.
