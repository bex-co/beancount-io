# A refused Smart Import throws away the file and every account choice: "Import Failed" offers only Start Over, so one bad row means uploading and mapping the whole file again

**Severity:** major (a failed write discards the draft). **Owner:** `dashboard`. **Estimate:** 30–45 minutes including a rendered workflow test. **A2:** importing a first bank CSV is one of the first writes a newcomer makes. When the ledger refuses the batch (a typo in one target account, or one row dated before the account's `open`), the server's message names the exact fix, but the only button is **Start Over**. It returns to the empty upload box with the parsed rows, the source account and every per-row target gone. On a 200-row statement that is 200 choices to redo, for an error in one of them. Browser Back leaves the page entirely, because the wizard steps are not history entries. `dashboard/AGENTS.md` already states the rule this breaks: "A failed write keeps that draft mounted with its error beside the submit control; never swap it for a context-free error view (w4/m33, w4/m47, w4/m48, w4/m49, w4/977)." **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-28 against `https://beancount.io`, production entry chunk `main-BBmi61Hs.js`, local HEAD `8f66924bb`. Isolated headless Chromium 158 at 1440×1000, English, signed in as the QA owner on its designated disposable ledger `<qa-owner>/mcp-agent-eval` (`main.bean` is the synthetic fixture `backend-cluster/backend-v2/evals/mcp-agent/fixtures/main.bean`). Every import below was refused by the server, so nothing was written: `main.bean` stayed at blob `f1a0b83c` (last commit unchanged) and the ledger reports no errors.

## Repro

A CSV (`Date,Payee,Description,Amount`) with two rows, `2025-12-15,qa-20261128-r2 Cafe,Coffee,-4.50` and `2026-09-02,qa-20261128-r2 Market,Groceries,-45.67`. The fixture opens every account on 2026-01-01.

1. Open `/ledger/<owner>/<ledger>/import` and choose the CSV. Preview reads "2 Valid". Press **Continue to Configure**.
2. Pick every account from its list: Source **Assets:Bank:Checking**; targets **Expenses:Food:Coffee** and **Expenses:Food:Groceries**. No notice appears under any field and **Import 2 Transactions** is enabled.
3. Press **Import 2 Transactions**. `BulkEntries` answers `VALIDATION_FAILED`: "adding these entries would introduce 2 new bean-check errors: Account Assets:Bank:Checking used on 2025-12-15 but not opened until 2026-01-01 (main.bean:89); Account Expenses:Food:Coffee used on 2025-12-15 but not opened until 2026-01-01 (main.bean:89)".
4. The page now reads **Import Failed**, then that message, then **Error Details:** with the same message a second time. The only control is **Start Over**.
5. Press **Start Over**: the page is back at "Drop your file here". The file, the rows and all three account choices are gone. Fixing the one early row means uploading again and re-picking every account.

Same result from a fresh page load with a three-row file where one target was typed as `Expenses:Food:Grocery` (not an account): "Account Expenses:Food:Grocery was never opened (main.bean:93)", then **Start Over** only.

## Cause

- `dashboard/src/features/importer/components/import-workflow-container.tsx:48-51`: `handleSubmit` awaits `submitImport` and then always calls `workflow.moveToFinish()`, success or failure. That unmounts the Configure form.
- `components/steps/finish/index.tsx:103-151`: the failure branch renders the message and a single **Start Over** button wired to `onImportMore`, which is `workflow.resetToUpload` (`hooks/use-import-workflow.ts:65-69`). That clears `parseResult` and `configDraft`. The draft is still intact in `useImportWorkflow` state until that button is pressed. Nothing returns to it.
- The message is shown twice because `hooks/use-import-submit.ts:127-141` puts the same `formatError(error)` in both `message` and `errors[0]`.

w4/280 froze the Configure fields while a batch is pending, and noted "they re-enable when a failed import settles". The form is never on screen when a failure settles, because the container has already moved to Finish.

## Fix

- On a failed `submitImport`, stay on Configure (or return to it) with the same `parseResult` and `configDraft`: source, currency, per-row targets and selection all as they were. Show the error beside **Import N Transactions** in the form's existing alert area, once. Focus goes back to the Import button (the `usePendingAction` / `usePendingSubmit` convention in `dashboard/AGENTS.md`).
- Keep the Finish step for success. **Start Over** may stay as a secondary action next to the error, but it must not be the only way forward.
- Show the server's message once, not twice.
- Do not resend automatically. The next **Import** sends a new attempt with the edited rows.

## Definition of done

On `/import`, with a CSV whose batch the ledger refuses (a row dated before its account opens, or a typed account that does not exist), pressing Import shows the refusal once beside the Import button while the Configure table still shows every row with its source and target. Correcting or deselecting the bad row and pressing Import again imports the rest without a new upload. A successful import still ends on the Finish step with View Journal and Import More. A rendered workflow test (container plus Configure, with `BulkEntries` mocked to fail and then succeed) asserts the draft survives the failure and the retry sends the corrected batch. It fails on current code. Dashboard gates pass.

## Blast radius

`FinishStep`'s failure branch is reached only from `ImportWorkflowContainer`, and `resetToUpload` is called only from there. The receipt review keeps its draft through a failure already (w4/m48) and is not changed by this. Bank Sync's submit was not exercised (it needs a linked bank). The CLI's `bea import` previews before writing (w3/276) and is unaffected.

## Dedupe

Searched `.pm/**` (open, `done/`, `blocked/`) for "Start Over", "Import Failed", `startOver`, `failedTitle`, `resetToUpload` and `FinishStep`. w4/280 (done) froze Configure during a pending batch and treated Start Over after an aborted request as a passing control. It did not look at a refusal the user can fix. w3/564 and w3/641 (done) fixed amount spellings that made every import fail. w5/1230 (open) is about the Out of date flag after a successful import. None keeps the draft after a refusal. `git log` on `import-workflow-container.tsx` shows `handleSubmit` unchanged since the dashboard was imported, so this is not deployment lag.

The narrow layout of the new error placement. Partial-success responses (`bulkEntries` is all-or-nothing today). A transport failure after the server committed (w4/280 left it out of scope too).
