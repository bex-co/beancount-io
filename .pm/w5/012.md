# A rejected `BEA_TOKEN` says "Run 'bea cloud login'", which cannot take effect while it is set

**Severity:** minor. **Estimate:** 25–40 minutes. **Owner:** cli. **A1:** an
unattended job or CI runner whose `BEA_TOKEN` was revoked is told to run an
interactive browser login — advice that neither applies to that environment nor
fixes the credential the CLI is actually using.

Found 2026-09-16 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with an isolated
`BEA_CONFIG_DIR`. Dummy non-credentials only — no real token was used and the
user's own credential store was never read or written.

## Repro

```sh
export BEA_CONFIG_DIR=$(mktemp -d) && chmod 700 "$BEA_CONFIG_DIR"
BEA_TOKEN=bea_qa_env_dummy_token_000 bea cloud status
```

```text
Error: Not authorized (the server does not recognize this environment
credential). Run 'bea cloud login'.
```

The diagnosis is precise and already source-aware — it says **environment**
credential. The remedy contradicts it: `bea cloud login` writes
`credentials.json`, and that file is never consulted while `BEA_TOKEN` is set.

The precedence is unconditional. `cli/src/cli/auth/credentials.py:81-90`:

```python
token = os.environ.get("BEA_TOKEN")
if token is not None:
    return Credentials(token=_validate_token(token), expire_at=None, source=ENVIRONMENT)
```

The environment is checked first and returns immediately, so a user who follows
the advice completes a browser login and then hits the identical error on the
next command.

Demonstrated directly — with a stored credential present *and* `BEA_TOKEN` set,
the environment one is the one that gets used and rejected:

| config | message |
| --- | --- |
| stored credential only | `…does not recognize this **file** credential). Run 'bea cloud login'.` |
| stored credential **and** `BEA_TOKEN` | `…does not recognize this **environment** credential). Run 'bea cloud login'.` |

The first row's advice is correct — replacing the stored file is exactly what
login does. Only the second row misdirects.

## Expected / actual

Expected, for an environment-sourced credential: name the variable and say what
to do with it — correct or unset `BEA_TOKEN`, or mint a new token — the way
`bea cloud logout` already does for the same situation.

Actual: both sources receive the same fixed suffix.

## Root cause

Two places, one hardcoded remedy.

`cli/src/cli/commands/cloud/app.py:88` composes the detail with the source
interpolated:

```python
raise error_from_status(401, f"the server does not recognize this {creds.source} credential")
```

`cli/src/cli/errors.py:113-114` then appends a suffix that cannot vary:

```python
if status in (401, 403):
    return AuthError(f"Not authorized ({detail}). Run 'bea cloud login'.", request_id=request_id)
```

So the CLI has the source in hand at the moment it builds the message and
discards it one call later. The source interpolation was added deliberately by
`14e9d543` ("report a revoked credential the same way on cloud status and
ledger commands"); that change made the *diagnosis* source-aware and left the
*remedy* fixed.

## The correct phrasing already exists 36 lines above

`cli/src/cli/commands/cloud/app.py:52-60` handles the same credential source in
`logout`, and gets it exactly right:

```python
if creds.source == ENVIRONMENT:
    output.success(
        "BEA_TOKEN is set in this shell; 'bea cloud logout' leaves it "
        "unchanged and does not revoke it. Unset BEA_TOKEN to stop using it."
    )
```

with a comment explaining that a shared unattended credential must not be
revoked by a routine command. The auth module is careful about this elsewhere
too: `credentials.py:49-53` deliberately declines to pre-expire an environment
token because "the server is the authority on it".

## Fix

Give the 401/403 path a source-aware remedy. Either pass the credential source
into `error_from_status`, or (simpler) let `app.py:88` and its siblings supply
the whole sentence and have `errors.py` stop appending a fixed one for that
status. For `source == ENVIRONMENT`, say that `BEA_TOKEN` is the credential in
use and that logging in will not change it — reuse the wording `logout` already
ships. Keep the current text for the stored-file case, where it is right. Add
coverage asserting the environment branch names `BEA_TOKEN` and does **not**
say "Run 'bea cloud login'", and that the file branch still does.

## Blast radius and adjacent states

Affects every hosted command when the active credential came from `BEA_TOKEN`
and the server rejects it — `cloud status`, `cloud ledger list/show/create/
clone/delete`, and `bea ask`, which authenticates through the same store.
Signed-out behaviour is correct and was exercised: with neither a token nor a
stored file, every one of those exits 3 with "Not logged in. Run 'bea cloud
login', or set BEA_TOKEN", which names both options accurately. An expired
*stored* credential correctly reports "Session expired. Run 'bea cloud login'
to re-authenticate", and that branch is unreachable for environment tokens by
design (`expire_at=None`, `is_expired()` returns False). Not exercised: a
genuinely revoked real token, and 403-as-opposed-to-401 responses.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for `BEA_TOKEN`, "Not
authorized", cloud-login advice and credential-source terms. Nothing covers
this; the hits are unrelated (`.pm/w4/done/067.md` is a mobile empty-state
defect, `.pm/w1/done/010.md`/`011.md` are BQL and cost-label issues).
`git log -S 'does not recognize this' -- cli/src` shows `14e9d543` as the only
touch. This is the same *class* as `.pm/w5/011.md` — a remedy that ignores the
source the CLI already identified — but a different subsystem
(`auth`/`cloud` rather than `engine`), different files, and a separable fix, so
it is filed apart rather than folded in. Reproduced at `b78efe7d`.

## Evidence and unverified areas

Captures under `cli/tmp/qa-20260915/run21/` hold both source variants of the
401 message, the expired-stored-credential control, and the precedence
demonstration. All tokens were obvious dummies in a throwaway
`BEA_CONFIG_DIR`; `~/.config/bea/credentials.json` was not read, written or
modified at any point. The "login will not help" consequence is reasoned from
the precedence code and the demonstrated precedence, not from performing a real
login.
