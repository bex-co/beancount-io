# A profile's "Recently updated" ledger list holds the 50 oldest-created ledgers, so open_ledger hides every ledger created after 2026-09-13, including the ones its own Recent Activity names

**Severity:** minor (discovery). **Owner:** `backend-v2` (the dashboard sorts what it receives). **Estimate:** 30–45 minutes including tests. **A3:** `/ledger/open_ledger` is the public showcase that the gallery and "Start with an example" lead to. Its Ledgers tab defaults to **Recently updated**, yet none of the ledgers published since mid-September appear: not h-and-r-block or rocket-lab, which the **Recent Activity** panel beside the list says were committed 17–18 days ago, and not stock-example. A visitor sorting by recency sees ledgers last touched in March before any of the new ones. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English. The profile was read anonymously over GraphQL and as the QA account in the browser. Local HEAD `d682554fb`. Read-only.

## Repro

1. Open `/ledger/open_ledger`. The Ledgers tab reads **Ledgers 50**, "Only the first 50 ledgers are loaded here", with **Recently updated** selected. Choose **Show more ledgers** until all 50 cards show.
2. The cards are sorted by update time: fedex (2026-11-10) … real-estate-example (2026-03-11). Neither h-and-r-block nor rocket-lab is among them, though **Recent Activity** on the same page lists "Committed to h-and-r-block" (2026-11-10T19:14Z) and "Committed to rocket-lab" (2026-11-09T21:37Z). Both are newer than every card after fedex.
3. Search `rocket`: "None of the 50 loaded ledgers match your search."
4. API control, anonymous: `getUserProfile(username: "open_ledger") { repositories { name createdAt updatedAt } activities { repoName createdAt } }` returns 50 repositories in **ascending `createdAt`** order: minimax 2025-12-22 first, synopsys 2026-09-13T17:52Z last. `updatedAt` is unordered, and the oldest `updatedAt` among them is 2026-03-11. The first activities are fedex, h-and-r-block ×2, rocket-lab ×2 and hims-hers. None but fedex is among the 50 repositories.

## Cause

`backend-cluster/backend-v2/src/features/gitea/user-profile/service/user-profile-service.ts:189-221` fetches repositories with `users.userListRepos(username, { limit: 50 })`, for both the self-view and the public branch. Gitea lists a user's repositories in creation (id) order, so the documented 50-repository cap keeps the **oldest** 50. The dashboard (`features/user-profile/components/ledger-collection.tsx:155-166`) sorts that slice by `updatedAt`. The default **Recently updated** order is right within the slice but can never include a ledger created after the 50th. w4/161 kept the cap deliberately and made the page say the list is partial. Which 50 it keeps was not in its scope.

## Fix

Owned by `backend-v2`. Keep the 50 cap and the response shape. Choose the 50 **most recently updated** repositories the viewer may see instead of the 50 oldest. Gitea's `repoSearch` (`GET /repos/search`) takes `uid`, `exclusive=true`, `sort=updated`, `order=desc`, `limit=50`. For the self-view, keep the authenticated client and its private repositories (`private`/`is_private` as today). Do this in the service, so the GraphQL `getUserProfile`, REST `GET /api-gateway/v1/social/profile` and MCP `beancount://social/profile` all change together. Update the route description at `public-profile-route.ts:48` if it describes the order. No dashboard change is required: its "loaded ledgers" disclosure stays accurate.

## Definition of done

- Anonymous `getUserProfile(username: "open_ledger")` returns 50 repositories whose `updatedAt` values are non-increasing, and that include the most recently updated public ledger (today fedex, then h-and-r-block and rocket-lab).
- On `/ledger/open_ledger`, **Recently updated** shows h-and-r-block and rocket-lab, and a search for `rocket` finds rocket-lab.
- The REST and MCP profile reads return the same repositories in the same order. A self-view still includes the owner's private ledgers.
- A backend-v2 test with a fake Gitea client fails on the current `userListRepos` call (oldest-first) and passes with the new selection. backend-v2 gates pass, including the parity suite.
