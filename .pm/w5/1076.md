# Preserve exact native magnitudes when clipping a closed lot's quantity

**Minor · cli · 25–40m · A1 · worker1.** Capital Gains overstates what a
posting actually closed by **2e−18 TOKEN**, because `abs()` rounds its native
accepted 29-digit operand before the quantity clamp. A partial short cover
leaves **−2e−18 TOKEN** natively, but reports a larger 28-digit closed
quantity. The same error occurs when a long sale crosses into a tiny short:
it counts the new short's two smallest units as part of the long lot closed.
JSON already has the wrong number; human output repeats it. All reads exit 0
with valid/complete metadata, and source files stay unchanged. No product fix.

## Reproduce a partial short cover

Create `main.bean` in a fresh directory:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Token TOKEN "NONE"
2024-01-01 open Equity:Opening USD
2024-01-01 open Assets:Cash USD
2024-01-01 open Income:Gains USD
2024-01-02 * "Open"
  Assets:Token -12345678901.12345678901234568 TOKEN {0 USD, 2024-01-02}
  Equity:Opening 0 USD
2024-01-03 * "Close or cover"
  Assets:Token 12345678901.123456789012345678 TOKEN {0 USD, 2024-01-02} @ 0 USD
  Assets:Cash 0 USD
  Income:Gains 0 USD
```

With the isolated environment above:

```sh
bea --json --no-input --offline --file /absolute/main.bean check
bea --json --no-input --offline --file /absolute/main.bean list transaction --details
bea --json --no-input --offline --file /absolute/main.bean report capital-gains
bea --no-input --offline --file /absolute/main.bean report capital-gains
```

Native inventory starts at **−12345678901.12345678901234568 TOKEN**.
The positive cover is exactly **12345678901.123456789012345678 TOKEN**,
and native inventory finishes at **−0.000000000000000002 TOKEN**.
The quantity actually closed is precisely the positive cover, including its
last `78`; the two smallest units remain short.

Actual report: `quantity.number: "12345678901.12345678901234568"`.
Human QTY is **12,345,678,901.123456789012345680 TOKEN**. It has counted
those last two still-short units as closed. This contradicts
[USAGE](../../cli/docs/USAGE.md#reports)'s rule and completed
[1035](./done/1035.md): a priced posting reports only the quantity it
actually reduced, even when it covers a short. Proceeds, basis and gain are
all zero in this precision-isolating fixture; monetary miscalculation is not
claimed here.

For the other direction, keep the same dated cost and `NONE` booking,
change the opening to **+12345678901.123456789012345678 TOKEN**, and make
the second posting **−12345678901.12345678901234568 TOKEN**. Native load
retains both exact quantities and ends at the same **−2e−18 TOKEN**.
Only the original 29-digit long holding closed; the extra two smallest units
opened the short. Capital Gains again reports the whole larger 28-digit
posting as closed instead of clipping to the exact original holding.

Controls in both directions: make both magnitudes the 28-digit number for a
genuine full close, or reduce/cover only `12345678901 TOKEN` for a whole-unit
partial close. Both are reported correctly and retain their actual native
remainder. No wide negative parsing, total-price division, quote conversion
or source rewrite explains the failing case.

## Cause and bounded repair

[`_capital_gains`](../../cli/src/bea_engine/report.py#L802) correctly tracks
the native inventory and identifies the priced reduction. Its clamp at :863,
`quantity = min(abs(before), abs(units.number))`, then changes the operands.
Decimal's `abs()` applies the active 28-digit context. In the long case,
`abs(before)` changes the original 29-digit holding to the larger 28-digit
sale amount; in the short case, `abs(units.number)` changes the positive
29-digit cover to the whole short holding's magnitude. `min` therefore no
longer chooses from the actual native amounts. Proceeds/basis and the row
receive that wrong quantity afterward; JSON serializes it faithfully and
the [frontend table](../../cli/src/cli/commands/report.py#L560) formats the same value.

An isolated existing-runtime operator probe confirms precision 28:
`abs(Decimal("12345678901.123456789012345678"))` yields
`12345678901.12345678901234568`; `copy_abs()` retains the full operand.
The 28-digit and whole-unit controls are unchanged by either operation.
This is a runtime arithmetic proof, counted separately from native ledger
loads; the actual report behavior is proven through real bea commands.
History `efca4dad5` introduced the clamp for 1035's directional reduction fix;
there is no later context-free magnitude correction.

Copy the two Decimal magnitudes without context rounding before selecting
the smaller one. Preserve the existing native inventory update, reduction
direction, price checks, date/account bounds, gain sign/buckets, and real
multiplication/subtraction arithmetic. A cover must report at most its exact
positive posting; a cross-zero sale must report at most the exact long lot
previously held. Keep a genuinely remaining tiny position. Do not raise
global precision, round stored quantities, change native booking, or hide the
difference in formatting. The sole producer feeds human/JSON and every
Capital Gains filter combination. CLI-local only, no dependency or API change.
Add real CLI regression cases and run `make check-all` inside `cli/` when fixing.
