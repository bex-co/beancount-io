# A commit link with a short SHA, an uppercase SHA or a branch name (`/commit/deb272d`, `/commit/main`) opens the commit, but Version History says "The selected commit is outside the loaded history" while listing it first, and the page is indexed under that alias (gap in w2/m9)

**Severity:** minor. Nothing is lost or written, but the history list contradicts itself, and a public commit is served under URLs that are not its own. **Owner:** `dashboard`. **Estimate:** 30–45 minutes including tests. **A2/A3:** every ledger is a git repository, and Version History shows each commit as a 7-character SHA (`deb272d`). Someone who types that SHA into the URL, or pastes one from `git log --oneline` in their clone, gets the right commit. Next to it, though, the list says the commit is outside the loaded history, highlights no row, and offers **Load older commits** as if it were further back. On a public ledger, every such spelling is also an indexable page that declares itself canonical. w2/m9 gave commit pages a stable canonical for search. That holds only for the full lowercase SHA. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000 and 390×844, English. Signed out on the public example ledger, and signed in as the QA account on the designated synthetic ledger. Read-only. Local HEAD `405eb456a`.

## Repro

Public ledger, no sign-in needed. Take the newest commit's 7-character SHA from `/ledger/open_ledger/example/commits` (on 2026-11-27, `deb272d`, full SHA `deb272d41ba8224c747dfb1f8f4f90ded16ddf49`).

1. Control: open `/ledger/open_ledger/example/commit/deb272d41ba8224c747dfb1f8f4f90ded16ddf49`. The detail loads, the first history row is the current one (`aria-current="page"`), no notice is shown, and `<link rel="canonical">` is the same URL.
2. Open `/ledger/open_ledger/example/commit/deb272d`. HTTP 200, and the same detail loads: heading `Add 2026-10-30 custom budget Expenses:Food:Restaurant`, `deb272d`, `1 file +3 -0`. Above the history, **The selected commit is outside the loaded history.** The first row is that same commit, but no row is marked as current. The canonical is `…/commit/deb272d`, and there is no `noindex`.
3. Open `/commit/DEB272D41BA8224C747DFB1F8F4F90DED16DDF49`. Same as step 2. The title is `Commit DEB272D - example`, and the canonical is the uppercase URL.
4. Open `/commit/main` and `/commit/HEAD`. Both load the newest commit, with the same notice and no current row. The titles are `Commit main - example` and `Commit HEAD - example`, and the description is "Changes in commit main for example". Each page is self-canonical and indexable, though its content will change with the next push. `/commit/main~1` loads the commit before it, and `/commit/deb27` (five characters) loads `deb272d`.
5. At 390×844, open **Version History** on `/commit/deb272d`. The sheet shows the same notice, and no row is current.
6. Signed in as the owner of a synthetic ledger, `/commit/<7-char sha>` and `/commit/<10-char uppercase sha>` of its second-newest commit behave the same way. The private ledger's page carries `noindex`, so only the list symptom applies there.

Repeated from a fresh load. The GraphQL control is direct: `getCommitDetails(ledgerId: "open_ledger/example", sha: …)` with `deb272d`, the uppercase SHA, `main`, `HEAD`, `main~1` or `deb27` returns `sha: "deb272d41ba8…"` (for `main~1`, `80260f14…`), never an error.

## Cause

The API resolves any git revision on purpose. `findCommit` (`backend-cluster/backend-v2/src/features/gitea/commits/service/commits-service.ts:50–77`) documents that it accepts "a sha, an abbreviated sha or a branch", and `assertCommitRef` (`src/shared/commit-ref.ts`) admits revision syntax such as `main@{1 day ago}` (w31/024, w31/061, w31/062). The dashboard, however, treats the URL segment as the commit's identity:

- `dashboard/src/features/git/commits/loaders/commit-loader.ts:15–24` checks only that the detail exists. It never compares the resolved `getCommitDetails.sha` with `params.commitSha`.
- `features/git/commits/components/commits-list.tsx:93–94` shows `commits.selectedOutsideHistory` when no row's `sha` equals the URL segment exactly, and `:106` marks a row current only on that same exact match.
- `common/lib/seo/ledger-head.ts:75` builds the title from `params.commitSha.slice(0, 7)`, and `:131–135` passes the segment to `getLedgerCommitCanonicalUrl` (`common/lib/seo/indexability.ts`).

## Fix

Owned by `dashboard`. No API change: the API's acceptance of revisions is deliberate and shared with REST and MCP.

- In `loadCommitRoute`, once the detail resolves, compare `data.getCommitDetails.sha` with `params.commitSha`. When they differ, `throw redirect(...)` to the same route with `commitSha` set to the resolved full SHA, keeping the search (`?lang=`, retained filters) and the `#diff-file-…` hash, with `replace: true`. Use a temporary status such as 302 or 307, not the 301 the ledger-slug redirect in `routes/ledger.$ledgerOwner.$ledgerName.tsx` uses, because `main` moves and an abbreviation can later become ambiguous.
- After the redirect, the existing exact comparisons, title and canonical are all correct, so `commits-list.tsx` and the SEO helpers need no change. Keep `notFound()` for a revision that resolves to nothing, keep the retry and error states (w4/1043, w21/297), and keep the full-SHA URL with no redirect.

## Definition of done

- On production, `/ledger/open_ledger/example/commit/<7-char sha>`, `/commit/<UPPERCASE full sha>` and `/commit/main` each end at `/commit/<full lowercase sha>`, keeping `?lang=` and any `#diff-file-…` hash. The newest commit's row is current, the "outside the loaded history" notice is absent, and the canonical and title use the full SHA. The same holds at 390×844 in the Version History sheet, and for a commit reached by clicking a history row (no redirect, no extra request).
- A loader test covers a short SHA, an uppercase SHA and `main`, each mocked as resolving to a full SHA: the loader throws a redirect to the full SHA with search and hash kept. It also asserts that the full SHA does not redirect and that a missing commit is still `notFound`. The redirect cases fail on the current code. Dashboard gates pass.

## Blast radius

The only route that takes a commit ref from the URL is `routes/ledger.$ledgerOwner.$ledgerName.commit.$commitSha.tsx`. In-app links already use the full SHA: `commit-list-item.tsx`, `commits-split-view.tsx:202` (the `/commits` redirect to the newest commit), and the dashboard's Activity card (`features/ledger-list/components/feed-card.tsx:131`, from the backend's `activity-transformer.ts:173` head SHA). Mobile's `build-ledger-url.ts:58` passes through whatever SHA it is given, so a fix here also covers an app link that carries a short one. The copy button beside the short SHA copies the full SHA, so the alias reaches the page only by hand or from git. `pull/$prNumber` already refuses anything that is not a positive integer (`pull-request-loader.ts`). `files/tree/$branch` and `files/blob/$branch` take a branch by design and are out of scope.

## Dedupe

Searched every board state for `outside the loaded history`, `selectedOutsideHistory`, `short SHA`, `abbreviated`, `commit/main`, `HEAD`, `canonical` with `commit`, and `getCommitDetails`. w2/m9 (done) added the commit page's canonical and short-hash title, assuming the URL carries the full SHA. w4/246 and w5/1160 reach the notice by paginating, where it is true. w31/034, w31/024, w31/061 and w31/062 hardened which refs the API accepts and kept revisions as valid input. w21/297 added the not-found state. None covers a resolvable alias in the URL. `git log` on the loader, `commits-list.tsx` and `ledger-head.ts` shows no change to the comparison since they were written, so this is not deployment lag.

## Unverified

Firefox and Safari, whether a search engine has indexed any alias, and the `entry/$entryHash` route, where a prefix lookup was not tried.
