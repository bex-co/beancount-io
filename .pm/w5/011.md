# Engine override diagnostics misdirect: one recommends deleting a working engine, the other reports a bare errno

**Severity:** minor. **Estimate:** 45–60 minutes (two related messages). **Owner:** cli. **A2:** the
one error a misconfigured install produces hands the user a destructive remedy
that removes a healthy managed engine and does not fix the problem, leaving them
worse off than before they read it.

Found 2026-09-16 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME`. Synthetic local fixture; **no engine
directory was modified** — the destructive advice was traced, not followed.

## Repro

Point the documented override at something that is not a Python environment —
a typo'd path, a stale virtualenv, a wrapper script:

```sh
printf 'option "operating_currency" "USD"\n2026-01-01 open Assets:Cash USD\n' > ok.bean
BEA_ENGINE_PYTHON=/bin/echo bea --file ok.bean check
```

```text
Error: The engine environment has no 'bean-check' (/bin). Remove
/Users/<you>/.local/share/bea/engine/0.2.0 and rerun to provision it again.
```

The diagnosis is right and the remedy is not. `/bin` is the override's bin
directory; `~/.local/share/bea/engine/0.2.0` is the **managed** engine, which
is a different installation, is intact, and is not the thing that failed.

Confirmed in-process under the same override:

```text
python_override()      : /bin/echo
bin dir of override    : /bin
engine_root() (remedy) : /Users/<you>/.local/share/bea/engine/0.2.0
remedy names the same place as the failure? False
```

and that engine is healthy — `~/.local/share/bea/engine/0.2.0/bin/bean-check`
exists and serves every command once the override is unset.

Following the advice therefore destroys a working engine **and leaves the error
in place**, because `BEA_ENGINE_PYTHON` still points at `/bin/echo`. The next
run re-provisions the managed engine it just deleted and fails identically.

## Expected / actual

Expected: the remedy addresses the cause the CLI already identified. When
`paths.python_override()` is set, say that the override points at an
environment without `bean-check` and tell the user to correct or unset
`BEA_ENGINE_PYTHON` — naming the variable, since `cli/docs/USAGE.md:874-877`
describes it as an advanced override for "tests and recovery tooling" that
ordinary installs never set. Reserve "Remove <engine root> and rerun" for the
case where the managed engine really is the broken one.

Actual: one message for both causes, whose remedy is only ever correct for the
second, and is destructive when applied to the first.

The CLI is not missing the information it needs. In the same failing session,
`bea --json engine status` reports `serving.tier: "override"` and
`serving.location: "/bin/echo"` — the tier reporting added by
`.pm/w2/done/022.md`. The error text simply does not consult it.

## Root cause

`cli/src/cli/engine/launch.py:176-197` (`native_command`). The loop over
`_candidate_bin_dirs()` fails to find the executable, then `:191` rebinds
`directory` to `paths.bin_dir_for(provision.ensure_engine())` — which under an
override resolves to the override's bin directory (`/bin`) — and `:194-197`
raises:

```python
raise BeaError(
    f"The engine environment has no '{name}' ({directory}). "
    f"Remove {paths.engine_root()} and rerun to provision it again."
)
```

`directory` and `paths.engine_root()` are independent: the first follows the
override, the second is always the managed engine root. When an override is
active they name different installations, and the sentence reads as though they
are the same one.

## Fix

Branch the message on `paths.python_override()` inside `native_command`:

- **override set** — "`BEA_ENGINE_PYTHON` points at `<path>`, whose environment
  has no `<name>`. Correct or unset `BEA_ENGINE_PYTHON`, or run
  `bea engine status` to see which engine would serve." No deletion advice.
- **no override** — keep the current text, which is correct there.

`require_feature` at `cli/src/cli/engine/launch.py:85-101` already takes exactly
this shape. Its override branch (`:93-99`) reads:

```python
override = paths.python_override()
if override is not None:
    raise UsageError(
        f"Engine feature '{name}' is not available in {paths.PYTHON_ENV}={override}. "
        f"Install it into that environment, or unset {paths.PYTHON_ENV} and run "
        f"'bea engine enable {name}'."
    )
```

It names the variable, tells the user to fix or unset it, and proposes nothing
destructive. `native_command` sits 80 lines below it in the same file and needs
the same branch, so this is applying an existing in-file pattern to its
neighbour, not inventing one. Add coverage for
both branches asserting that the override branch names the variable and does
**not** contain "Remove".

## Part 2 — `BEA_UV` is not validated the way `BEA_ENGINE_PYTHON` is

`cli/docs/USAGE.md:874-877` presents the two as siblings: "Advanced overrides
(`BEA_ENGINE_PYTHON`, `BEA_UV`) exist for tests and recovery tooling". They are
not handled alike.

`cli/src/cli/engine/paths.py:75-79` validates the first:

```python
python = Path(value).expanduser()
if not python.exists():
    raise BeaError(f"{PYTHON_ENV} points at '{python}', which does not exist.")
```

`cli/src/cli/engine/provision.py:356-367` (`_find_uv`) returns the second
verbatim, unchecked:

```python
override = os.environ.get(UV_ENV)
if override:
    return override
```

Confirmed in-process: `BEA_UV=/nonexistent/uv` returns `'/nonexistent/uv'` with
`exists=False`, and `BEA_UV=/bin/echo` is accepted as a uv. The bad path then
reaches `_run` (`:369-379`), which calls `subprocess.run` with no guard, so a
missing binary raises `FileNotFoundError` rather than returning a code.

Through the real CLI, against an isolated engine directory so nothing was
installed:

```sh
BEA_ENGINE_DIR=./isolated-engine BEA_UV=/nonexistent/uv bea engine enable beanprice
```

```text
Installing the Beancount engine 0.2.0 (one time) in ./isolated-engine...
Error: [Errno 2] No such file or directory: '/nonexistent/uv'
```

Exit 2, no traceback — the top-level handler contains it, which is right. But
the text is a raw Python `OSError` string: it never names `BEA_UV`, so a user
whose shell profile or CI image set that variable has no way to know where
`/nonexistent/uv` came from. `_find_uv` already owns a well-phrased message for
its *other* failure ("needs uv to install, and uv was not found on PATH.
Install it from https://docs.astral.sh/uv/ or set BEA_UV to its path") — it
simply never validates the override.

The two siblings also disagree on exit code for the identical situation, an
override naming a path that does not exist: `BEA_ENGINE_PYTHON` exits **1**,
`BEA_UV` exits **2**.

Fix: validate `BEA_UV` in `_find_uv` the way `paths.python_override()` already
validates `PYTHON_ENV` — name the variable, name the path, and pick one exit
code for the pair. Both parts of this note are one small change to the same
subsystem and should be worked together.

## Blast radius and adjacent states

Affects `native_command` only, so every `run_native` delegation
(`check`, `format`, `query --source`, `doctor`, `example`, `treeify`, and
optional `price`) shows this message when an override lacks the tool. The
neighbouring diagnostics are correct and were exercised:
`BEA_ENGINE_PYTHON=/nonexistent/python3` gives "points at '…', which does not
exist" with no deletion advice, and `BEA_ENGINE_DIR` aimed at an empty
directory correctly falls back to the checkout tier and exits 0. `bea engine enable` under an override is
also correct — `provision.py:163-167` refuses with "Cannot enable engine feature
'X' while BEA_ENGINE_PYTHON is set. Unset it to use the managed engine…",
naming the variable and proposing nothing destructive, which is a third
in-repo instance of the pattern `native_command` is missing. The
tier-reporting consistency documented after `w2/022` also holds — `engine
status` named `managed`, `checkout` and `override` respectively across those
three configurations, matching what `check` actually ran each time.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for `BEA_ENGINE_PYTHON`,
`engine_root`, "provision it again", and engine-environment terms.
`.pm/w2/done/022.md` is the same subsystem but a different, fixed defect
(`engine status` not reporting the serving tier); its fix is what makes it
provable here that the CLI knows an override is active. `.pm/w5/010.md` is the
other open engine-boundary note and concerns signal deaths inside a *working*
engine, not resolution of a missing one — no overlap. `git log -S 'provision it
again' -- cli/src` shows the message arriving with `a90b1706` (ADR014) and
unchanged since. Reproduced at `b78efe7d`, so not deployment lag.

## Evidence and unverified areas

Captures under `cli/tmp/qa-20260915/run19/` hold the three override
configurations with exit codes and full stderr, the in-process resolution dump
above, and the `engine status` tier comparison. The managed engine was read
only — never deleted, moved or modified — so the "following the advice" outcome
is reasoned from the resolution order rather than executed. The `BEA_UV` case ran with
`BEA_ENGINE_DIR` pointed at a scratch directory and failed before uv was ever
invoked, so nothing was downloaded or installed and
`~/.local/share/bea/engine/` was byte-identical before and after. Not
exercised: a genuinely corrupt managed engine (the case where the current
advice is right), Homebrew's `BEA_ENGINE_DIR` layout, and Windows.
