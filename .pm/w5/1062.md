December31 is silently closed February1 when its empty grandparent closes.

## Cause and bounded repair

Frontend `cli/src/cli/commands/add.py:258–272` sends the close request.
Engine `cli/src/bea_engine/ledger/adding.py:424–435` builds `_closed_with` from
the **already loaded** ledger: all descendant opens minus all closes, without
comparing dates or distinguishing previously generated closes. `_close:455`
therefore never checks the funded grandchild because the before-load already
contains its generated December31 close. This helper has one caller.

The installed upstream `beancount/plugins/close_tree.py:49–77` recomputes
closes from the source's explicit closes on each load. The newly added earlier
grandparent generates February1 for Checking before the later Branch close
is visited. That is intentional upstream behavior; native validation permits
closing a funded cash account. The CLI's stronger funded-close decision is
what this source-only set approximation misses. The original repair is
`b1ba52fcdb3c98050af1d8d5bd3e0430265665cf`.

Judge actual candidate close effects against the same source snapshot:
newly generated closes **and a generated effective close moved earlier** must
receive `_remaining_balance`'s existing units/lot/force policy at their new
date. Reuse existing candidate inspection (`write.validate_append` /
`validate_candidate`'s `inspect`) and validated-append/snapshot plumbing;
keep validation and write tied to that snapshot. Merely ignoring every old
generated close would wrongly reject the already-closed January15 control.
Keep explicit future closes, earlier unchanged generated closes, no-plugin
parent independence, drained children, `check_drained` and `--force` working.
No upstream fork, dependency, API, import-policy or historical-ledger repair.
