# The ledger switcher carries the old ledger's Journal page, Accounts search and Overview month to the new ledger: page 3 of A opens page 3 of B, "No account name contains “Mercury”", June 2025 instead of B's latest month (gap in w5/1209)

**Severity:** minor. Nothing is written or lost, but the other ledger opens somewhere the reader never chose for it: its Journal without its newest 120 entries, its chart of accounts empty, its Overview on an old month. **Owner:** `dashboard`. **Estimate:** 20–30 minutes including tests. **A2:** the switcher is how a reader with several ledgers (personal and business books) moves between them. w5/1209 made it clear "the current ledger's filters" so they do not leak, but it clears only `account`, `filter` and `time`, and the other per-ledger positions still travel. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, production entry chunk `main-BBmi61Hs.js`, which already contains the w5/1209 fix (from an account page the switch lands on Accounts with `time` dropped). QA-owned headless Chromium 158, isolated context, 1440×1000, English, signed in as the QA owner. Read-only: no ledger writes. Local HEAD `f4e13a733`.

## Repro

The QA owner has two synthetic ledgers with long histories: A (1,132 journal entries, latest entry 2026-10-02) and B (1,186 entries, latest 2025-10-11). Each step uses the sidebar's "<ledger> — switch ledger" combobox and picks the other ledger. Repeated from fresh loads.

1. **Journal.** Open A's Journal and click page "3" in the pager: the URL gets `?offset=120` and the status reads "Showing 121–180 of 1,132". Switch to B. The URL is `/ledger/<owner>/<B>/journal?offset=120`, the status reads "Showing 121–180 of 1,186", the pager marks page 3 as current, and the first row is dated 2025-07-07. B's own Journal opens on "Showing 1–60 of 1,186" with 2025-10-11 first. From A's last page (`?offset=1080`) the switch lands on "Showing 1,081–1,140 of 1,186", B's entries from 2023.
2. **Accounts.** Open A's Accounts and type "Mercury" in "Search accounts...": the URL gets `?search=Mercury` and the count reads "1 / 63". Switch to B. The URL is `/ledger/<owner>/<B>/accounts?search=Mercury`, the search box still holds "Mercury", every type reads 0, the count reads "0 / 63", and the page says "No accounts found — No account name contains “Mercury”." A search that does match B ("vanguard") opens B's Accounts showing only those 4 of its 63 accounts.
3. **Overview.** Open B's Overview (it opens on September 2025) and press "Previous" three times: June 2025, `?month=2025-06`. Switch to A. The URL is `/ledger/<owner>/<A>?month=2025-06` and A's Overview opens on "June 2025 … Financial position Jun 30, 2025", where A on its own opens on September 2026. When the carried month is outside the new ledger's months (A's `?month=2016-05` switched to a ledger that starts in 2026), the page falls back to its own month but the URL still says `month=2016-05`.

Controls on the same build: the Events page's "Search events..." text is cleared by the same switch (A "Boston", 1 / 9 → B, empty box, 7 / 7), and `time`, `account` and `filter` are dropped as w5/1209 intended.

## Cause

`dashboard/src/common/components/ledger-layout/ledger-switcher.tsx:154-196` (`handleSelectLedger`) navigates with `search: (prev) => ({ ...prev, account: undefined, filter: undefined, time: undefined, ...fileParams })` (`:180-190`). Every other search param of the page being left survives. Three of them are positions in the old ledger's data, and each destination route accepts them:

- Journal `offset` (`common/lib/ledger-action-search.ts:106`, `normalizeListSearchOffset`), which the Journal clamps only to the new ledger's last page.
- Accounts `search` (`ledger-action-search.ts`, `accountsActionSearchSchema`), the text in "Search accounts...".
- Overview `month` (`features/reports/overview/search.ts:36-44`, added by w5/1148), which `useUrlView(…, "month", { writeFallback: true })` in `features/reports/overview/hooks/use-overview-month.ts` honours whenever the new ledger has that month.

The Events search is component state, so it resets with the ledger; these three live in the URL and do not. The reducer is unchanged at HEAD since `3a6d6d4b0` (w5/1209), so this is not deployment lag.

## Fix

Owned by `dashboard`, in `handleSelectLedger` only. Also drop `offset`, `search` and `month` in the search reducer, so the new ledger opens its Journal on page 1, its Accounts unfiltered and its Overview on its own opening month. Keep the display choices that mean the same thing on any ledger and that the reducer keeps today: report and chart `view`, `interval`, `mode`, Overview `movement`, Holdings `view` and Accounts `type`. Keep the Query page's `query` too: a BQL query is the reader's own text, and running it on the other ledger is a reasonable reading of the switch. Update the comment at `:176` to name what is cleared and why.

## Definition of done

- On production, each of the three repros above lands on the new ledger's own default: Journal "Showing 1–60", Accounts with an empty search and every account listed, Overview on its latest month with no `month` in the URL.
- Switching from a report with `?view=…&interval=…` still keeps those, and the w5/1209 destinations (account → Accounts, entry → Journal, commit/pull → Commits, files → Files root) are unchanged.
- `common/components/ledger-layout/__tests__/ledger-switcher-journey.test.tsx` gains cases for `/journal?offset=120` → `/journal`, `/accounts?search=Mercury` → `/accounts` and `/?month=2025-06` → `/`, plus one case that keeps `view`. The three fail on the current code. Dashboard gates (`yarn format:check`, `yarn lint`, `yarn test`, `yarn build`) pass.

## Blast radius

The phone drawer calls the same `handleSelectLedger`, so it behaves the same way (not repeated at 390px). Other search params of ledger pages were read from their route schemas: report `view`/`interval`/`mode`, Overview `movement`, Holdings `view`, Accounts `type` and `action`, Journal `action`/`directive`, Query `query`, file params. `action` cannot be carried in practice, because the New Entry and Open Account dialogs are modal and cover the switcher.
