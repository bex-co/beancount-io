# Every added entry ends the file with a blank line, so the next add leaves two blank lines between entries: New Entry, Open Account and Close Account each commit `+` / `+<entry>` / `+` (gap in w23/203 and w23/055)

**Severity:** minor (ledger hygiene; no data change, the ledger check stays clean). **Owner:** `backend-cluster/ledger` (`src/features/ledger/utils/line-ending.ts` `appendBlock`, `src/foundation/rustledger/entry-build.ts` `entryInputToText`, called from `src/features/ledger/service/ledger-entry-service.ts`). It is the one append path behind GraphQL `bulkEntries`, REST and MCP `addLedgerEntries`, so every surface changes together. **Estimate:** 30–45 minutes with tests. **A1/A2:** a ledger kept through the web app, the app or an agent grows a doubled gap after every entry. The file stops looking like one a person wrote, `git diff --check` flags the blank line at the end of the file, and the bytes no longer match what Fava or `bea` would write for the same entries.

**Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, signed in as the QA owner on the designated synthetic ledger. Local HEAD `efcd0bb01`. The entries were deleted afterwards and `main.bean` is back to its starting blob `f1a0b83`, byte for byte.

## Repro

`main.bean` starts at blob `f1a0b83` and ends `…49.75 USD\n`, with one newline.

1. Accounts → **Open Account** `Assets:Qa-20261127-Dqa` (today). Commit `b6c0e26` ("Add 2026-11-27 open …") adds three lines: `+` (blank), `+2026-11-27 open Assets:Qa-20261127-Dqa`, `+` (blank). The file now ends `…Dqa\n\n`, with a blank last line.
2. **Actions → Close Account** on the same row. Commit `25cec53` again adds `+`, `+2026-11-27 close Assets:Qa-20261127-Dqa`, `+` after that blank line. Lines 89–92 read `open …`, blank, blank, `close …`.
3. A third add (`0c2bc11`, Open Account with a later date) repeats it. Every add after the first leaves two blank lines before its entry and one after it.

Deleting the entries (Accounts → Delete) returns the file to `f1a0b83`, so the delete normalization from w23/055 is right. Only the append side is off.

## Cause

- `entry-build.ts:360-363` `entryInputToText` returns `directiveToText(…) + "\n"`, so every block ends with a blank line (`…\n\n`). `ledger-entry-service.ts:207-215` joins a batch's blocks, which correctly gives one blank line between entries of the same batch.
- `line-ending.ts:19-22` `appendBlock` returns `current + eol + block` (the comment at `ledger-entry-service.ts:260-262` cites `current_contents + "\n" + format_entries`). It always adds a separator, even when `current` already ends with the blank line the previous add left. `appendBlock("", block)` also starts a new file with a blank line. `__tests__/line-ending.test.ts` pins both.
- Fava's `insert_entry` appends so that exactly one blank line separates entries and the file ends with a single newline. w23/203 fixed the same doubling for `appendLedgerText` (`insertDirectives` in backend-v2), but this structured path still has it.

## Fix

In `appendBlock` (or its one caller), trim the trailing line endings of both `current` (the existing `withoutTrailingNewlines` helper) and the block. Then write `current`, one blank line (none when `current` is empty) and the block, ending in a single line ending. Keep the file's own line ending (w21/673, w21/695). Leave the blank line between entries of one batch as it is.

## Definition of done

- Two consecutive single-entry adds to a file ending in one newline commit `\n<entry one>\n` and then `\n<entry two>\n`: one blank line between them and a single newline at the end of the file. Adding to a file that already ends with a blank line adds no second blank line. Adding to an empty file writes the block with no leading blank line.
- A two-entry batch still has one blank line between its entries. CRLF files stay CRLF.
- Add → delete still returns the file to its starting bytes (w23/055).
- Unit tests for `appendBlock` cover those cases and fail on the current code. One service-level test makes two sequential `addBulkEntries` calls and checks the committed text. The `backend-cluster/ledger` gates in its `AGENTS.md` pass.
