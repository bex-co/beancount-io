# A `/0` anywhere in a ledger crashes the engine; `bea check` then exits 139 in silence

**Severity:** minor. **Estimate:** 45–60 minutes. **Owner:** cli. **A2:** one
mistyped amount makes every command fail on that ledger, and the first one a
newcomer reaches for — `bea check` — prints *nothing at all* and exits with a
code outside the documented table.

Found 2026-09-16 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME`. Synthetic local fixtures only.

## Repro

`cli/docs/USAGE.md:360` documents native posting arithmetic — "native posting
arithmetic such as `84/2 EUR` works" — and it does. A zero divisor does not:

```sh
bea --file main.bean add transaction "dz" --date 2026-02-01 \
    -p "Expenses:X 100/0 EUR" -p "Assets:Cash"
```

```text
Error: The Beancount engine did not answer 'bea-engine add --file
/abs/main.bean --type transaction --request -' (exit -11).
```

Exit 1, stdout empty, ledger byte-identical. `exit -11` is SIGSEGV: the engine
child segfaulted.

The same expression saved in a ledger file poisons every read of it:

```sh
printf 'option "operating_currency" "EUR"
2026-01-01 open Assets:Cash EUR
2026-01-01 open Expenses:X EUR

2026-02-01 * "dz"
  Expenses:X   100/0 EUR
  Assets:Cash
' > dz.bean
```

| command | exit | stdout | stderr |
| --- | --- | --- | --- |
| `bea check` | **139** | 0 B | **0 B — completely silent** |
| `bea --json check` | 1 | 0 B | 221 B, well-formed JSON error |
| `bea list transaction` | 1 | 0 B | `…did not answer 'bea-engine list …' (exit -11)` |
| `bea balance` | 1 | 0 B | same, for `bea-engine balance` |
| `bea report trial-balance` | 1 | 0 B | same, for `bea-engine report` |

Two distinct problems. `bea check` in human mode is the sharp one: **exit 139
with no output on either stream**. 139 is `128 + SIGSEGV`, outside the exit
table at `cli/docs/USAGE.md:132-140`, which defines only 0–4. A user running
the one command whose whole job is reporting problems is told nothing, by
anything.

The rest exit 1 with a real message, but none of them names `dz.bean:6`, the
expression, or division by zero.

## The crash itself is upstream, and bea's containment is correct

Verified independently of bea, on the same file:

```sh
bean-check dz.bean                      # exit 139  (128 + SIGSEGV), no output
python -c "from beancount import loader; loader.load_file('dz.bean')"
                                        # exit 139, no output
```

So Beancount's parser segfaults on a zero divisor; that is not bea's bug and
should not be fixed by reimplementing the parser (`.pm/DO_NOT_DO.md`: don't
re-implement upstream).

**bea's handling of the crash is already right, and should not be "fixed" away.**
`cli/src/cli/engine/launch.py:265-273` catches the missing envelope and raises a
normal `BeaError`, so the frontend survives a child that dies mid-call: exit 1,
empty stdout, no traceback, the ledger untouched, and under `--json` a single
well-formed error object (`category: validation`). That containment is what
keeps a segfaulting child from becoming a segfaulting CLI.

## Expected / actual

What is missing is the diagnosis. Expected: the user learns that an amount
expression divides by zero, or at minimum that the engine died on a *signal*
while loading a specific file, with something searchable to act on. Actual: the
message is the generic "did not answer" text plus a raw `exit -11`, identical
for every command and for any other way the child might die.

## Root cause

**The silent `bea check`** comes from the delegation split.
`cli/src/cli/commands/check.py:20` runs human mode through
`launch.run_native("bean-check", …)`, which by design hands the child this
process's streams and returns its status untouched
(`cli/src/cli/engine/launch.py:71-82`). A segfaulting child writes nothing and
dies on a signal, so `bea` faithfully forwards silence and `subprocess`'s
128+N convention straight to the shell. `--json` escapes this because it goes
through `capture_native` instead, which reads the output and raises a
`BeaError` when it cannot parse one — which is why only that path produces an
envelope.

**The uninformative message on the other commands**:
`cli/src/cli/engine/launch.py:270-273` builds one message for every case where
no JSON envelope came back, interpolating `completed.returncode` directly. A
negative return code (killed by signal) and an ordinary nonzero exit are
reported the same way, and `details` carries the child's stderr — which for a
segfault is empty, so nothing survives to explain it.

bea already validates amount notation at the input boundary:
`cli/src/cli/commands/add.py:62-71` (`_check_decimal_notation`) rejects
scientific notation before anything reaches the engine, from three call sites
(`:52`, `:152`, `:224`). There is no equivalent guard for a zero divisor.

## Fix

Two independent pieces, both small:

1. **Guard the write path.** Extend the existing input-boundary check in
   `add.py` to reject a literal zero divisor in an amount expression with a
   usage error (exit 2) naming the posting, the way scientific notation is
   already rejected. That covers `add`, `add balance`/`add price`, and keeps a
   typo from ever reaching the engine.
2. **Never exit outside the documented table, and never exit silently.** Map a
   child that died on a signal onto the documented codes — exit 1
   (`validation`) with a message saying the engine was killed by signal N while
   loading the named file. This is the same gap `w5/005` describes for the
   other `run_native` callers, and a fix there should cover `check`'s human
   path too; the two notes should be worked together.

3. **Distinguish a signal death.** In `launch.py:270-273`, when
   `completed.returncode` is negative, say the engine was killed by signal N
   rather than printing `exit -11`, name the resolved ledger file, and add one
   hint that a division by zero in an amount expression is a known upstream
   cause worth grepping for. Keep the existing `details` passthrough for the
   cases where the child did print something.

A ledger file that already contains `x/0` cannot be pre-validated without
parsing it, so piece 2 is what that case gets. Add coverage for the rejected
`add`, and for the signal-death message shape using a stub engine that exits on
a signal rather than a real segfault.

## Blast radius and adjacent states

Affects any ledger containing a zero divisor in an amount expression, and the
`add` paths that would write one.

The silent-139 half is **not limited to `bea check`**. Every `run_native`
caller that makes upstream parse the ledger passes the signal exit straight
through, measured on the same `dz.bean`:

| command | exit | stdout | stderr |
| --- | --- | --- | --- |
| `bea check` | **139** | 0 B | **0 B** |
| `bea doctor context dz.bean 6` | **139** | 0 B | **0 B** |
| `bea query --source beancount://dz.bean "SELECT account"` | **139** | 0 B | **0 B** |
| `bea doctor lex dz.bean` | 0 | 844 B | 0 B |
| `bea format dz.bean` | 0 | 155 B | 0 B |

The last two are correct and should stay: the lexer never evaluates the
expression, and `format` is a regex text transformation that never parses
(`cli/docs/USAGE.md:231-247`).

Equally important, the `helper_json` commands are **already contained** and
need no change. A systematic sweep of the same crashing ledger across five
commands in both modes found exactly one anomaly:

| command | human | `--json` |
| --- | --- | --- |
| `check` | **139, silent** | 1, JSON envelope |
| `list transaction` | 1 | 1, JSON envelope |
| `balance` | 1 | 1, JSON envelope |
| `report trial-balance` | 1 | 1, JSON envelope |
| `query "SELECT account"` | 1 | 1, JSON envelope |

Every one of those keeps stdout empty on failure. So the guard is needed only
where a `run_native` caller parses the ledger — `check`'s human path, the
parsing `doctor` operations, and `query --source` — and not at the
`helper_json` boundary, which already does the right thing.

The same sweep over ordinary failure conditions (a missing file, a ledger with
loader errors) across those five commands in both modes produced **zero**
anomalies: every exit was inside the documented 0–4 table, stdout was empty on
every failure, and every JSON-mode failure put exactly one JSON object on
stderr. The exit-code discipline is sound everywhere except the crash path.

It is also not specific to division by zero, and that generalization is
measured rather than inferred: with `BEA_ENGINE_PYTHON` pointed at a stub whose
`bean-check` kills itself with `SIGTERM`, `bea check` on a perfectly valid
one-line ledger exits **143** (`128 + SIGTERM`) with 0 B on both streams. So
these commands report *any* engine death by signal the same way, which equally
covers a killed or OOM-terminated child. Other arithmetic is correct and was
exercised: `84/2 EUR` → `42`, `3*5 EUR` → `15`, `(2+3)*4 EUR` → `20`, and
`100/3 EUR` → `33.33333333333333333333333333` which balances against its
inferred counter-posting. `2**10 EUR` is rejected cleanly as unsupported
syntax. The generic "did not answer" path also covers a genuinely missing or
wrong engine binary, so its message must stay useful for those.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for segfault, SIGSEGV,
`exit -11`, "did not answer", division and divide terms. No item mentions an
engine crash or a signal exit; the term hits are unrelated
(`.pm/w2/done/002.md`, `003.md` are tax/equity scoping spikes, and
`.pm/w4/done/042.md`, `053.md`, `006.md` are mobile UI defects). The other w5
notes cover different surfaces; `w5/007` is the nearest for the input-boundary
guard, since it is also about amount-expression validation, and `w5/005` is the
nearest for the silent exit, since both come from `run_native` callers passing
upstream's behavior through unmapped. Neither subsumes this one, and the three
are best worked together. Reproduced at `b78efe7d`, so not deployment lag.

## Evidence and unverified areas

Captures under `cli/tmp/qa-20260915/run17/` include the arithmetic matrix, the
`add` failure with exit code and unchanged-file hash, the four-command blast
radius, the `--json` envelope proving containment, and the two upstream
controls at exit 139. Synthetic fixtures only. The failure matrix above was
re-measured from a clean directory with stdout and stderr captured separately;
an earlier draft of this note wrongly described `bea check` as producing the
"did not answer" message, which is what the `--json` path does. The
signal-passthrough generalization was then verified independently of the
segfault with a stub engine under `BEA_ENGINE_PYTHON` (SIGTERM → exit 143,
silent), so it does not rest on the upstream crash reproducing. Not exercised:
whether other expressions (modulo by zero, overflow) crash the same way, and
whether the segfault reproduces on Linux or on other Beancount versions.
