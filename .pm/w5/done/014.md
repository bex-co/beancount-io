# A `bea` write killed by PID leaves full-size `.bea-*.tmp` copies beside the ledger

**Severity:** minor. **Estimate:** 40–60 minutes. **Owner:** cli. **A1:** an
agent or CI job that times out a long `bea import` or `add transactions` with
`Popen.kill()` leaves a complete hidden copy of the candidate ledger next to the
user's books on every attempt, and they accumulate.

Found 2026-09-16 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME`. Synthetic local fixtures only.

## Repro

```sh
# an 8000-row batch, so the write takes long enough to interrupt
bea --file books.bean add transactions --from big.json &
PID=$!
sleep 0.9
kill -INT $PID          # signal the bea process, not its group
wait $PID; echo "exit=$?"
ls -a $(dirname books.bean) | grep '\.bea-'
```

```text
exit=130
.bea-_3n6vu58.tmp
.bea-qgpbd8zk.tmp
```

They are never removed. Each is a **complete candidate ledger** — 671 KB here,
the original plus all 8000 staged transactions. Permissions are correct
(`-rw-------`), so this is clutter and disk, not exposure.

**The leak is intermittent — retry if a single attempt leaves nothing.** It
only happens when the signal lands while a candidate file is open, i.e. between
`mkstemp` and the `finally`. Measured over 10 interrupted runs at five kill
timings, two runs each:

| strays left | runs |
| --- | --- |
| 0 | 6 |
| 1 | 2 |
| 2 | 2 |

So 4 of 10 attempts leaked, one or two files each. A reproducer that kills at a
single fixed offset can easily see zero and conclude the bug is absent; vary the
timing or repeat. An earlier draft of this note described it as "two files per
interrupted run", which was an artifact of the first few timings I happened to
try.

## What is and is not affected

The ledger itself is safe, which is the important half:

| interrupted at | exit | ledger unchanged | rows written |
| --- | --- | --- | --- |
| 0.6 s | 130 | yes | 0 |
| 1.0 s | 130 | yes | 0 |
| not interrupted | 0 | (written) | 8000 |

Atomicity holds, and a run that completes normally leaves **zero** stray files —
cleanup works on the success path.

Two further teardown properties were checked and are **correct**, so they need
no work:

- **No surprise write.** The orphaned child does not carry on and land the
  write later. After killing the frontend by PID, the ledger was still unchanged
  with zero rows at +2 s, +5 s, +10 s and +20 s — well past the ~1.5 s a full
  write takes — and no engine process remained alive.
- **The lock is released.** A normal write issued immediately after a killed one
  succeeded in 0.7 s with no blocking, and repeated cleanly. `flock` is released
  by the kernel on process death, so an interrupted write cannot wedge the
  ledger.

## Root cause — the cleanup is correct but never runs

`cli/src/bea_engine/ledger/write.py:162-177`:

```python
@contextmanager
def candidate_file(file: Path, content: str) -> Iterator[Path]:
    fd, name = tempfile.mkstemp(prefix=".bea-", suffix=".tmp", dir=file.parent)
    candidate = Path(name)
    try:
        ...
        yield candidate
    finally:
        candidate.unlink(missing_ok=True)
        Path(str(candidate) + ".picklecache").unlink(missing_ok=True)
```

The `finally` is right. It does not run because the **engine child process**
never receives the signal: the frontend dies on SIGINT, and the child is
orphaned and torn down without unwinding.

Demonstrated by changing only the signal target, everything else identical:

| signal sent to | frontend exit | stray files |
| --- | --- | --- |
| the `bea` process alone | 130 | **2** |
| the whole process group | 130 | **0** |

When the child does receive SIGINT it raises `KeyboardInterrupt`, the `finally`
runs, and nothing is left behind.

This means an interactive **Ctrl-C is fine** — a terminal delivers SIGINT to the
foreground process group, which is the clean row above. The leaking case is
programmatic termination by PID: `kill <pid>`, `Popen.terminate()`/`kill()`,
`timeout(1)` without `--foreground` group handling, a container stopping its
main PID, or a supervisor targeting the pid. That is precisely how an agent or
CI harness cancels a slow command, so the failing case is the automation one.

## Fix

Make the child's cleanup reachable regardless of how the frontend dies. Options,
roughly in order of directness:

1. Have the frontend forward SIGINT/SIGTERM to the engine child and wait briefly
   for it to unwind before exiting, so the existing `finally` does its job.
2. Start the child in its own process group and signal that group on frontend
   teardown, which is the inverse of the same idea.
3. Belt-and-braces: sweep stale `.bea-*.tmp` files in the ledger directory that
   are older than some threshold at the start of the next write, so an
   abrupt `SIGKILL` (which no handler can catch) still self-heals.

(1) or (2) fixes the common case; (3) is the only thing that covers SIGKILL, and
is worth having because the files are full-size. Add coverage that kills a write
by PID and asserts the ledger directory has no `.bea-*.tmp` afterwards.

## Blast radius and adjacent states

Affects every writer that stages through `candidate_file` — `bea add`, `bea add
transactions`, `bea import --apply`, and `bea ask`'s write tool — when the
process is terminated by PID mid-write. Larger ledgers mean larger leaks, since
each file is a full candidate copy. The related safety properties all hold and
were exercised in this sweep: the atomic write itself (`w5`, iteration 3), the
external-edit conflict guard (exit 4), the preview-token guard for AI writes,
and the persistent lock files, which live under `$XDG_CACHE_HOME/bea/locks` and
are correctly **not** written into the ledger directory. Not exercised: SIGKILL
(uncatchable by design, and the reason for fix option 3) and Windows.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for temp-file, SIGINT, Ctrl-C,
orphan and leftover terms. Nothing covers this; the hits are unrelated mobile
and dead-code items. `git log -S 'candidate_file' -- cli/src` shows the helper
arriving with `6036b606`, reworked by `790791ac` ("harden ledger workflows") and
moved engine-side by `a90b1706` (ADR014); none of those addressed child
teardown. This is distinct from `.pm/w5/010.md`, which is about the frontend
*reporting* a child that died on a signal — this one is about the child not
cleaning up when it does. They touch the same boundary and could be worked
together. Reproduced at `b78efe7d`.

---

**Resolved 2026-09-16** — Fixed with both mechanisms the note proposed, because they cover different failures. (1) `helper_json` now runs the engine child under a handler that passes SIGINT/SIGTERM/SIGHUP on and waits up to five seconds for it to unwind, then re-raises the signal with its default disposition so the status the shell reports is unchanged; handlers are installed only for the child's lifetime. (2) A write sweeps `.bea-*` files in the ledger directory older than an hour — the only thing that covers SIGKILL, which no handler can catch. Shipped in `7df6d57f` (`cli`).

Scope decision worth recording: (1) is deliberately applied to the `helper_json` path only, not to `run_native`/`run_engine_argv`. Those hand upstream the terminal, and `bea query`'s interactive shell already receives Ctrl-C through the foreground process group — forwarding a second signal there would change interactive behavior for no benefit, since those commands stage no candidate files. The note's option (2), putting the child in its own process group, was not taken for the same reason: it would stop the interactive shell hearing Ctrl-C at all.

Measurement. Reproducing the note required two corrections to its repro on this machine: a non-interactive shell sets SIGINT to `SIG_IGN` for background jobs, so the leak had to be driven with SIGTERM (which is the automation case the note names anyway — `Popen.terminate()`, container stop, supervisor), and `$!` under `uv run` is not bea's pid. With those fixed the note's finding reproduced closely: **7 of 14** interrupted runs leaked, 14 stray files, each a full candidate copy, while the ledger stayed byte-identical and the lock released cleanly — confirming the note's judgement that atomicity itself is sound. After (1), **0 of 42** runs leaked. A tail-focused sweep then found a residual leak reachable within ~0.1s of completion (2 of 20 runs at that offset), which is exactly what (2) is for. The honest summary is that (1) closes the bulk of the window and (2) guarantees the files do not accumulate.

Coverage in `cli/tests/test_candidate_cleanup.py`, 7 tests, all deterministic rather than timing-dependent: the sweep removes an abandoned candidate and its picklecache, keeps a fresh one that a concurrent write may still own, touches no other file or directory, and tolerates an unreadable directory; a real write clears an abandoned candidate beside the ledger while leaving a fresh one; and a subprocess test drives a stub engine to assert the frontend actually delivers SIGTERM to its child. Reverting only the forwarding change fails that last test; ten consecutive runs of the file pass, so it is not flaky. `make check-all` passes (873 tests).

Not exercised, as the note flagged: SIGKILL (uncatchable by design, and the reason the sweep exists) and Windows.
