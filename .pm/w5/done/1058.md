# Report the unchanged ledger's errors after a refused write

**Minor · cli · 20–35m · A1 · worker1.** An atomic `--json --allow-errors`
write that is refused can omit the real pre-existing error from
`error.ledger_warnings`, or describe an unwritten proposed balance as if it
were the current one. A backdated rejected payment would change an existing
assertion's computed Cash100 to80 or92. The ledger remains at100 with the
same failing80 assertion, but warnings disappear or say92. Single add,
bulk add and a configured import reproduce. Refusal/new-error diagnostics
and all source bytes remain correct; no product fix implemented.

A narrow follow-up to completed [461](./done/461.md). Its exact original
add/bulk/import fixtures still pass; their proposed entries occur after the
failed assertion, so the candidate never changes that earlier diagnostic.
The original completed record and DoD are retained unchanged.

## Minimal failure

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
2024-01-01 open Equity:Opening USD
2024-01-02 * "Capital"
  Assets:Cash 100 USD
  Equity:Opening -100 USD
2024-01-31 balance Assets:Cash 80 USD
```

Native loading and `bea check` report one BalanceError: expected80USD,
accumulated100USD,20 too much. With the isolated environment below, run:

```sh
bea --json --no-input --offline --file /absolute/main.bean add transaction 'Rejected payment' --date 2024-01-15 --posting 'Assets:Cash -20 USD' --posting 'Expenses:Nope 20 USD' --allow-errors
```

Actual: validation exit1, nothing written. The new unopened-account error
is correctly reported, but `error.ledger_warnings` is absent. Native
before/after loads still report the same Cash100/failed80 assertion, and
the file hash is identical. The proposal would have repaired that assertion
only if it had been written; its own unknown-account error prevented it.

For the second manifestation, use known `Expenses:Food 7 USD` and
`Assets:Cash -8 USD` on the same date. The new transaction is correctly
refused as unbalanced. Its warning nevertheless says **accumulated92USD /
12 too much**, although the unchanged real ledger still holds **100USD /
20 too much**. This92 comes from the discarded proposal.

Move the bad payment to2024-02-02, after the assertion, and warnings
correctly retain100. A `query --allow-errors 'SELECT no_such_column'`
failure on the same source also carries the correct100 warning. These
controls isolate diagnostic origin from error classification and source
mutation. The [documented error contract](../../cli/docs/USAGE.md) says
`error.ledger_warnings` carries loader errors tolerated before another
failure; completed461 explicitly requires that the caller learns the
ledger was already broken. A refused proposal must not erase that fact or
supply its hypothetical numbers as the existing ledger's warning.

## Cause, callers and bounded repair

`cli/src/bea_engine/ledger/write.py::validate_candidate:2389–2401` loads the
proposed ledger into `errors`; it separately loads `before_errors` at
`:2433–2436`. Its formatted `records` at`:2493–2497` describe candidate
errors. For a refused allowed-errors write,`:3015` selects nonblocking
candidate records as `tolerated_records`, and`:3021` sends those as
`CandidateRejected.ledger_errors`. A pre-existing assertion resolved in
the candidate has no such record, so it disappears; a changed residual
becomes an unqualified candidate92 warning. The real snapshot is already
available but is not the warning's source.

For an atomic validation refusal with nothing committed, report the
pre-existing errors from the actual original snapshot in `ledger_errors` /
`error.ledger_warnings`. Keep the candidate's newly introduced failures in
`error.details`. Preserve source-file/line mapping and existing new-error
classification. Do not tighten message-identity matching to reject a valid
partial repair: the same assertion legitimately changes100→93 while it is
being repaired. After a successful write, warnings must still describe the
persisted post-write state, and a real repair to80 must clear them. Keep
partial-write effects and their current-state diagnostics intact.

Single adds reach the shared validator through append; bulk add forwards
`batch_error.ledger_errors` at`ledger/adding.py:1999–2009`. Import copies
`exc.ledger_errors` at`importing.py:939` and forwards them at`:1069–1076`.
The frontend `cli/src/cli/engine/launch.py:608–612` passes that list into the
JSON warning envelope. Update's direct validator callers at
`ledger/updating.py:603,869,975` are traced but were not newly exercised.
Init calls the validator without `allow_errors`; no init defect is claimed.
One shared diagnostic-source correction, with no dependency/API changes.
