# Preserve valid bulk plans across existing balance assertions

**Major · cli · 45–60m · A1 · worker1.** A valid existing balance assertion
makes the bulk row builder unable to place intermediate prefixes. The CLI
falls back to moving both purchases before both sales, including an existing
LIFO/HIFO sale that should retain its earlier position. All four rows write
successfully and the ledger checks valid, but the sale uses a new 200 USD lot
instead of the old 100 USD lot: realized profit becomes **0 instead of 100**,
remaining basis **200 instead of 300**, cost worth **1000 instead of 1100**.
Cash remains 800 and share counts agree. An offsetting-gains variant instead
refuses the valid whole batch, or writes only the purchases under partial
recovery. No product fix implemented.

The book starts with two Existing shares at 100 USD, acquired January 2,
and Cash 800. A February 2 assertion states Cash 800. It is valid before the
batch and after either complete order, because the four February 1 rows move
net zero cash. The supplied rows are:

| Index | Row | Stock / Cash |
| --- | --- | --- |
| 0 | Existing sale | −1 Existing at 150 / +150 USD |
| 1 | New-account sale | −1 New at 150 / +150 USD |
| 2 | Existing purchase | +1 Existing at cost 200 / −200 USD |
| 3 | New-account purchase | inferred +1 New at cost 100 / −100 USD |

Only the New sale needs its purchase moved ahead. Whole order `[0,3,1,2]`
validates with the original assertion and retains the Old Existing sale.
The CLI chooses `[2,3,0,1]`; LIFO/HIFO then takes the newly purchased 200 lot.
Removing only the already-correct assertion restores the preserving result.
Stating row 3's quantity as 1, or supplying the preserving order directly,
also restores it while keeping the assertion. FIFO takes Old in either order
and is a working financial control.

Cause: `_built_booking_order` (`cli/src/bea_engine/ledger/adding.py:2132`)
tries each date's remaining rows one at a time, using `write.validate_append`
on every candidate prefix. A whole ledger's future assertion is not a prefix
constraint on an atomic batch. In the Cash case, Existing sale alone leaves
950, Existing buy alone 600 and inferred New buy alone 700, so the 800
assertion rejects all three. New sale alone has no purchased lot to resolve
its open cost and gain (native diagnostic: too many missing USD numbers).
Nothing can be placed and the builder returns None. The Stock assertion
permits the independent New pair, then stalls on the two mutually offsetting
Existing rows. A valid complete plan can therefore have no accepted next
prefix under this validator.

`_booking_order` (:2079, :2124–2128) then accepts the bookable eager order.
It still moves the independent Existing sale after its new purchase, producing
the lot change. Current runtime traces on the actual model rows/snapshot show:
input/rule order fails, each Cash singleton fails as above, builder result
`None`, eager `[2,3,0,1]` passes and is returned. A direct staged validation
of `[0,3,1,2]` on that same initial snapshot passes, without changing inputs.
The public native control then confirms the Old lot and correct financial
state. These are noncommitting helper observations around real validation,
not mocked validation results or a product patch.

The explicit-unit control lets the same-day rule form a preserving whole

can place a preserving prefix. FIFO keeps the earlier acquisition even under
the eager order, explaining its unchanged financial result. These controls
isolate whole-ledger prefix validation rather than invalid fixtures, missing
engine features, quantity inference itself or upstream lot booking.

**Resolved 2026-10-23** — fixed: the bulk row builder (`_built_booking_order` in `cli/src/bea_engine/ledger/adding.py`) no longer treats a prefix of the batch as unbookable just because an existing balance assertion is not yet met. It places rows one at a time against the ledger, so every prefix of a batch whose complete order nets to the asserted balance failed that assertion and the builder returned nothing, leaving the eager reorder to move the existing LIFO/HIFO sale behind its same-day purchase. A prefix refusal now counts as bookable when the only things refused are `Balance failed` errors and their advice lines (`_only_balance_failures`); any other error, such as the new-account sale having no lot yet, still rejects the placement, and the complete order is validated in full when it is written. The mixed LIFO/HIFO batch beside a February 2 Cash assertion therefore writes all four rows in the order that keeps the old sale on the old 100 USD lot (profit 100, `check` valid). Regression tests in `cli/tests/test_bulk_plan_across_balance_assertion.py` (LIFO and HIFO) fail without the fix; the 1002 tests still pass. Full suite green (10525 passed). Not exercised: the offsetting-gains variant, partial recovery with assertions.
