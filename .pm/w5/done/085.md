# Preserve every currency when exporting a partially retained pad

**Major · cli · 30–45m · A1 · worker1. Reopened 2026-10-24.** The original
padding fix suppresses all generated transactions whenever their pad is
selected. A period export can retain that pad and just one of its two
currency assertions. Reloading then regenerates only that currency:
**100 USD + 50 EUR becomes just 100 USD**, yet export, check and reports all
exit 0. With EUR at 2 USD, net worth falls from **200 USD to 100 USD** in
the exported copy. Swapping the assertion order loses USD instead. Source
ledger bytes stay unchanged. No product fix implemented.

Environment: clean main `4d4857a6824bc5965cc3dff841a3d319c6df2121`, with CLI
byte-identical to frozen `ee4b7702516da4535bb3b478e2efe9913b09481b`.
Checkout `bea 0.3.1`, frontend Python 3.13.3, managed Python 3.12.10 /
Beancount 3.2.3 / Beanquery 0.2.0, macOS 26.5.1 arm64. Fresh bounded
subprocesses, closed stdin/no TTY, absolute isolated config/cache and
notifier disabled. Synthetic local files only.

## Standalone reproduction

`python3 recipe.py /absolute/unused/book USD`. Repeat in another unused
directory with `EUR`. `single`, `explicit` and `plain` are healthy controls.

## Root cause and repair target

`cli/src/bea_engine/query.py:1814–1825`, `_render_beancount`, collects
selected Pad source locations, then removes **every** selected P transaction
at any of those locations. Both currency adjustments share the same pad
location. This test never checks whether the balance assertions needed to
regenerate each adjustment remain in the result. `14189e298` introduced
that condition to solve this item's original double-padding/Unused Pad
failure. It still solves the unfiltered original fixture, but is too broad
for a partially retained multi-currency pad.

Preserve selected adjustments that cannot be reconstructed from the
retained directives, while keeping the healthy full-pad and pad-free
exports reloadable. Retaining the appropriate explicit postings or
flattening an incomplete pad are possible approaches; simply printing all
P transactions beside their pad would restore the original bug. Preserve
the source-view currencies, amounts and dates. Update the export rule in
USAGE if its implementation changes. This belongs to the local CLI
renderer, without a dependency or API change.

The renderer is called by `PreciseShell.on_Select` (:1569); `on_Print`
(:1596) dispatches there through the native PRINT handler. `SELECT entry`
uses the renderer for posting rows, but the native `#entries` table does
not expose an `entry` column, so it cannot select this pad-plus-assertions
result. No SELECT-specific failure is claimed. Stored queries, interactive
exports, default-format PRINT, other operating systems and native
`--source` rendering were not separately exercised for this new gap.

## Original report and resolution (preserved)

# A `PRINT` export of a ledger with a pad does not pass `bea check`

**Minor · cli · 30m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. `bea query PRINT -f beancount` is the
documented way to export parseable directives. For a ledger containing a
`pad`, the export carries both the `pad` directive and the padding
transaction Beancount synthesized from it, so the exported file fails
validation. No product fix implemented.

Create disposable `/absolute/books/pad.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Equity:Open
2024-01-09 pad Assets:Cash Equity:Open
2024-01-10 balance Assets:Cash  42.00 USD
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, and an absolute `--file`.

```sh
bea -f /absolute/books/pad.bean check
bea -f /absolute/books/pad.bean query PRINT -f beancount -o /absolute/books/out.bean
bea -f /absolute/books/out.bean check
```

Actual: exits 0, 0, then 1 with `out.bean:4: Unused Pad entry`. The export
holds the `pad` line and a `2024-01-09 P "(Padding inserted for Balance of
42.00 USD …)"` transaction. Repeated twice.

Control: a ledger without a pad — cost lots, sales, labels, typed metadata,
multi-line strings — exports and reloads to the same entries once its option
lines are restored.

Expected: `docs/USAGE.md` calls `PRINT` output "parseable directives" and
says the Beancount format "preserves" values so an export can be reloaded. An
export of a valid ledger should itself pass `bea check`.

Cause: `cli/src/bea_engine/query.py:804-820` (`_render_beancount`) prints
every result row, including flag-`P` transactions whose source location is a
`pad` line. Upstream `bean-query` prints the same pair, but this renderer is
`bea`'s own and already departs from upstream to keep exports reloadable.

Fix: under `-f beancount`, omit a padding transaction when the `pad` that
generated it is in the same result, so the reloaded ledger derives it again.
Native `--source` rendering stays upstream's. No dependency or API change.

Dedupe: board search for Unused Pad, "Padding inserted" and `PRINT`
round-trips finds w3/224 and w1/116 (`add balance --pad-from`) and w3/457
(custom values in exports); none covers pads in exports.

Acceptance: the fixture's export passes `bea check` and holds one `pad` and
one `balance`; a filtered `PRINT` that selects the padding transaction
without its `pad` still prints it; the pad-free control is unchanged. Only
macOS and the checkout were exercised.
