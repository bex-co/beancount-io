# Keep native unit residuals in reports

**Minor · cli · 40–60m · A1 · worker1.** A valid token ledger and native BQL
hold `0.123456789012345678 SHIB`, while balance, trial-balance, register,
balance-sheet and overview report `0.12345678901234568`. The human register
prints `0.123456789012345680`, overstating the residual by two smallest
18-decimal units. JSON loses the same digits, so this is calculation rather
than display rounding. All reads exit 0 with valid/complete metadata; files
remain unchanged. No product fix implemented.

The error starts when the report's inventory adds its first position to an
artificial Decimal zero, rounding an accepted 29-digit positive quantity
before a later whole-token return. The final native residual has only
18 significant digits. This is distinct from legitimate upstream rounding
during an actual addition, and from upstream parsing of a wide negative
literal; neither requires changing here.

`9da8d91a4da248a8528b7eade60d047c99face11` (1674 fingerprints verified before
and after). Checkout bea 0.3.1/frontend Python 3.13.3, managed Python 3.12.10 /
Beancount 3.2.3 / Beanquery 0.2.0, macOS 26.5.1 arm64. Frontend's newer

## Reproduce against native inventory

Receive `12345678901.123456789012345678 SHIB` at a zero USD price, then return
`12345678901 SHIB`. The zero-weight postings balance exactly in USD; there is
no wide negative literal, inferred amount or currency conversion in the unit
comparison. Both the source and unwrapped native Beancount check valid:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Wallet SHIB
2024-01-01 open Equity:Opening USD
2024-01-02 * "Receive tokens"
  Assets:Wallet 12345678901.123456789012345678 SHIB @ 0 USD
  Equity:Opening 0 USD
2024-01-03 * "Return whole tokens"
  Assets:Wallet -12345678901 SHIB @ 0 USD
  Equity:Opening 0 USD
```

`query 'SELECT account,SUM(position) GROUP BY account ORDER BY account'`
returns Wallet units `0.123456789012345678`. The same engine's native
`Inventory.add_position` and `Inventory.reduce(get_cost)` return exactly
that residual, with default Decimal precision 28. `balance Assets:Wallet
--conversion units`, `report trial-balance --conversion units`,
`report register Assets:Wallet --conversion units`, balance-sheet and overview
all round it to `0.12345678901234568`. Matching January `--time` produces the
same result. The register's first row retains the full 29-digit movement in
`amount`, while its running `balance` is already rounded.

Put checkout `bea` on PATH, save this standalone recipe and run
`python3 recipe.py /absolute/new/book return-wide standard /absolute/engine/bin/python`.
Repeat in a fresh directory; `renamed` changes all five account roots.
The recipe adds an explicit zero market quote to exercise the nearby known-zero
valuation control, records exact argv/cwd, safe env overrides, streams, exits,
timing and unchanged hashes, and loads an independent native inventory without
Fava or checkout modules. Its other modes are controls described below.


| Mode | Native inventory / BQL | Unit reports |
| --- | --- | --- |
| `return-wide`: 29-digit receipt, whole-token return |0.123456789012345678|0.12345678901234568|
| `gift-wide`: receipt only |12345678901.123456789012345678|12345678901.12345678901234568|

The real addition in `add-wide` is intentionally evaluated in native precision
28: the correct expected result is the native rounded value ending in68,
not an arbitrarily widened algebraic result. Reports instead round the first
quantity early and then round again, ending in67. The boundary case retains
all 18 residual digits, showing that the report can represent that result.
With the explicit SHIB zero quote, the converted balance tree correctly
retains `USD:0` and complete valuation; its value is not a missing price.

## Root cause, callers and bounded repair

`cli/src/fava/core/inventory.py:114–116` (`CounterInventory.add`) computes
`number + self.get(key, ZERO)` even when no inventory position exists.
`SimpleCounterInventory.add` at lines50–52 uses the same pattern. The first 29-digit
positive number therefore encounters Decimal arithmetic and rounds to 28
before any genuine sum. The native Beancount 3.2.3
`core/inventory.py::Inventory.add_amount` (line402) creates `Position(units,
cost)` directly for an absent key; arithmetic happens only when augmenting
or reducing an existing position. Its first value is still exact when the
whole-token return reduces it to an ordinary 18-digit residual.

The register uses `CounterInventory` directly at
`cli/src/bea_engine/report.py:631/667`. Balance/trial/balance-sheet use the
same inventory through `fava/core/tree.py` and `FinancialStatementsModule`;
overview and balance-sheet series also use it in `fava/modules/chart.py`.
Simple inventory conversion and summary aggregation carry the rounded value
through to JSON and human rendering. Cash Flow's flow/closing inventories
also use this accumulator; the correctly bounded SHIB Cash closing in the
separate return pilot shows the same rounded residual. The costless fixture
has no Holdings row under that report's existing contract.

Make first-position initialization and no-op inventory reductions preserve
native amounts, reusing upstream inventory semantics where practical.
Keep native arithmetic for actual nonzero additions, reductions, cost and
price calculations; do not globally raise Decimal precision or rewrite the
source numbers. Preserve zero-removal and [908](./done/908.md)'s known-zero
conversion behavior. The fix belongs in the CLI's inventory/report layer;
no server input-policy or dependency change is needed.
