# Release batch targets when their update row is rejected during planning

**Minor · cli · 25–40m · A1 · worker1.** A rejected batch-update row
still reserves its source transaction, so a later valid row for that entry
is rejected as “already targeted.” The same valid edit previews successfully
on its own. An independent entry is correctly updated, but10USD remains in
the review queue rather than moving to Food. Reversing the rows, or making
the first failure a malformed flag instead of a bad account retarget, writes
both valid edits. No money disappears and the ledger remains valid; this
breaks the batch promise that rejected rows do not abort valid ones.
No product fix implemented.

## Reproduce

The fixture has capital100USD and two review transactions: R1 spends10USD,
R2 spends20USD, both on `Expenses:Uncategorized`. Each has an `import-id`
and a separate `ref` alias. Use this mapping:

```json
[
  {"id":"R1","account":"Expenses:Absent=Expenses:Food"},
  {"id":"R1","account":"Expenses:Food","flag":"*"},
  {"id":"R2","account":"Expenses:Food","flag":"*"}
]
```

Row1 correctly fails because R1 has no posting to Absent. Row2 is a valid
request to clear and categorize R1; it must not conflict with an earlier
row already rejected without a plan. Row3 independently categorizes R2.
`ref:Alias1` instead of R1 in row1 reproduces the same problem with different
ID strings resolving to the same written transaction.

Save the self-contained recipe below, put checkout `bea` on PATH, then run
`python3 recipe.py /absolute/new/book bad-first json json standard file /absolute/engine/bin/python`.
Use `alias-bad-first` for the ref-alias reproduction, `csv` for the mapping,
or `human renamed stdin` for EUR, renamed roots, human update output and
piped input. Every run needs a new directory. Other modes are controls.

## Cause and bounded repair

`cli/src/bea_engine/ledger/updating.py:516–575`, `_plan_rows`, resolves a row
to its `(filename,lineno)` key. At :562 it assigns `seen[key] = index`
**before** `_summarize` at :564. The invalid old account raises a
`UsageError`; :566–568 records a rejection and continues, but leaves `seen`
claiming that transaction. Row2 reaches :555 and is rejected as duplicate,
although no accepted plan for that key exists. `_summarize` uses
`_retarget_accounts` (:346–381) to detect the invalid source account; this
is a planning failure, not candidate-ledger validation or an ID lookup failure.

Reserve a source key only after that row has successfully produced an
accepted plan, including a legitimate no-op plan. A planning-rejected row
must leave no claim that prevents later valid rows. Preserve first-accepted
row ownership and the “merge them” refusal for a real second plan at the
same source transaction; do not implement last-row-wins. Unknown-ID and
schema failures already avoid the stale claim and are working controls.
This is a bounded `_plan_rows` ordering repair, not a redesign of selection
among candidate-ledger-invalid plans.

Callers: `_transactions` invokes this planner for preview and apply, including
the snapshot/revalidation flow. The frontend
`cli/src/cli/commands/update.py` routes JSON/CSV and `--from PATH/-` to that
same engine request, so all four transports are affected. Single update
does not use the reservation map and correctly accepts the valid request.
The map originated in `62c0e1910` (batch form); no current-source repair found.

Acceptance: the bad-first and alias-bad-first inputs reject only row1,
preview both valid edits, and apply2 at partial exit1 with original-index
`written_rows:[1,2]`, `rejected_rows:[0]`. Food becomes30USD/EUR,
Uncategorized0, both review flags clear, and native Cash remains70.
Retain JSON/human per-row diagnostics, preview0/no writes, whole-file
atomicity, independent valid rows and all working duplicate controls.
Add real CLI regressions for same-ID/ref-alias inputs and accepted-noop
ownership; run `make check-all` inside `cli/` when implementing. No new
dependency or eligible API change.
