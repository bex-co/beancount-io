# Keep funded-close checks when check_drained does not reject the actual holdings

**Minor · cli · 45–60m · A1 · worker1.** The shared remaining-balance helper
reports no money when `check_drained` will not reject the account's actual
holdings. A direct close succeeds without `--force`; native import preview
and apply omit their funded-close warning. The valid result still holds
100.00USD (125.50EUR with renamed roots), and later transfers are refused.
No amount is lost and no product fix is implemented.

Two nearby forms share that false coverage decision: `check_drained` before
`close_tree` sees no generated child close, so it creates no child assertion;
and a generated parent zero assertion passes because parent−100/child+100
cancel in its subtree, although the parent itself remains funded. The latter
needs no `close_tree`. Both reproduce twice in the public matrix.

statement/flow/split outcome set still passes in44fresh cases. Keep that
record and DoD untouched. This is independent of [1062](./1062.md): none of
these starting books has a Close, both closing accounts are selected, and
no existing date exclusion hides them. The failure is downstream, where
actual held amounts are discarded.

## Cause and bounded repair

`cli/src/bea_engine/ledger/adding.py:408–421` computes own-account holdings
correctly, then drops every currency returned by `_drained_checks:328–350`
whenever a plugin name ends in `check_drained`. That helper models the
plugin's account-type/currency/explicit-assertion rules, but does not establish
that the real candidate will contain an effective failing assertion for
that account's holdings.

The installed standard `beancount/plugins/check_drained.py:49–94` processes
the entries it receives and emits a zero assertion **the day after a Close**.
Before `close_tree`, it never sees the child's generated Close. Separately,
`beancount/ops/balance.py:138–151` intentionally sums the asserted account's
subtree; an offsetting child can make its zero check succeed despite a
nonzero own balance. Both are valid upstream semantics.

There are two production consumers of `_remaining_balance`: direct
`_close` at `adding.py:456` (frontend `commands/add.py:258`) and native
`_funded_close_advisories` at `importing.py:1118`, reached through candidate
inspection at:915. Both must retain their different refusal versus warning
policies when native validation will not protect the actual account holdings.
Reuse the real candidate/validation and snapshot plumbing; do not approximate
coverage from plugin presence, declared currencies, or a parent's zero total.
Preserve the genuine `check_drained` diagnostic where its assertion fails,
explicit force, drained/same-day cases, snapshot protection and import
acceptance. Do not reorder/fork upstream plugins or add an API/dependency.

Two supporting native processes independently load existing primary books
and call the actual helpers, with module hashes matching the frozen/current
source. In `before`, `_closed_with` selects Checking, `_held_through` returns
100.00USD and `_drained_checks` claimsUSD; `_remaining_balance` returns `{}`
both before and on the real candidate, which has no assertions. In the
no-tree cancellation, it similarly drops Bank−100.00USD while the native
parent zero assertion has `diff_amount=None` (passes). Calling the real import
advisory on those candidates with an empty prior-close set returns `[]`.
The prior state in this proof is parsed only, not loaded; the two actual
native loads are listed separately from the public matrix below.

**Resolved 2026-10-27** — funded-close checks no longer assume `check_drained` covers a currency just because the plugin is listed. `_drained_currencies` (`cli/src/bea_engine/ledger/adding.py`, replacing `_drained_checks`/`_plugin_currencies`) counts a currency as already refused only when the loaded candidate holds the plugin's zero assertion for that close (the day after, on the account or an ancestor, at the close's own file and line) and that assertion actually fails. With `check_drained` before `close_tree`, or a parent whose subtree zero passes despite its own nonzero balance, a direct unforced `add close` now refuses naming the money, and the import warns in preview and apply. Where the assertion really fails, the plugin's own refusal still appears; `--force`, drained children and the 910/913/888/1062 behaviours are unchanged. The direct route judges the requested account inside the same candidate inspection as its descendants. Tests: `cli/tests/test_close_drained_coverage.py` (20 cases, JSON/human, renamed roots/EUR); 12 fail with the fix reverted. `make check-all` passed. Only macOS was exercised. Shipped in this commit (`cli`).
