# Keep written transactions when native booking regroups their currencies

**Major · cli · 45–60m · A1 · worker1.** A valid written transaction has
interleaved USD/EUR postings. Native booking groups them by currency without
changing any fact or the posting count. When a plugin retains the original
and adds only a header-changed copy at its location, the CLI calls the real
source generated too. `--on-disk` loses it; import treats its unchanged
statement as new and writes another 10 USD and 20 EUR of expenses, even with
`--duplicates skip`. No product fix implemented.

Real local CLI QA, 2026-10-23, `bea 0.3.1`, macOS 26.5.1 arm64, frontend
Python 3.13.3, existing managed Python 3.12.10 / Beancount 3.2.3. Runtime
commands use an immutable public CLI archive at
`df8dc180e99ed36c31bf2f3f0f7d4043be4b4794`; all 1,613 tracked CLI file hashes
were checked before/after each batch. The current main package is byte-for-byte
identical before filing. Fresh synthetic directories, isolated child
config/cache, closed stdin/no TTY, bounded timeouts, separate streams and
file hashes. HOME and installed dependencies remain unchanged.

The four authored postings, in order, are Assets:USD -10 USD,
Expenses:EUR +20 EUR, Assets:EUR -20 EUR, Expenses:USD +10 USD. Native booking
returns the USD pair then the EUR pair. The plugin retains that booked source
and adds a differently narrated copy at the same date/location; all quantities
stay the same. The full calculated view is intentional. Native before/after
loads and queries on plugin-free snapshots isolate the authored write effect.

With this checkout's `bea` on PATH, replace the absolute directory below
with a fresh disposable path and run. Use another pristine directory for
each mode/repetition. `skip=True` selects explicit duplicate skipping;
`human=True` renders apply in human form, and human on-disk details are always
captured. The inspected plugin copies entries only in memory. The inspected
local importer parses the synthetic statement. Source, importer, plugin and
reference bytes are guarded; only successful apply/repeat may change main.

Observed twice per profile:

- `interleaved-copy`, `euro-first-copy` and `reverse-copy` all mark the
  unchanged source generated. Both ordinary and newest/limit-1 on-disk
  searches are empty, with no truncation; human details say no transactions.
  Changing which currency appears first or the plugin's return order does
  not recover the source.
- Preview calls the identical statement `new`. Apply exits 0 and writes one
  row. The default interleaved case does this in JSON and human output and
  with explicit `--duplicates skip`. Authored native transaction count rises
  one to two, USD Cash/Expense goes from -10/+10 to -20/+20, and EUR
  Cash/Expense goes from -20/+20 to -40/+40. Native checks stay valid. The next
  repeat recognizes the newly written hash and writes zero; no unbounded
  append is claimed.
- `grouped-copy` writes the same four source facts already grouped by
  currency; `same-currency-copy` keeps all four postings in USD. Both retain
  the one real source, preserve the existing `possible_duplicate` review,
  and default apply exits 4 without writing. Explicit grouped `skip` exits 0
  and writes zero. Thus an existing review/skip decision is bypassed in the
  interleaved case; this report does not require automatically recognizing
  an unkeyed manual transaction as an exact duplicate.
- `interleaved` omits the copying plugin. Unique-location listing retains
  the real source and import still warns/refuses rather than writing.
  `native-id-copy` keeps the listing defect but adds B1 to source/statement:
  the separate authored-ID fallback correctly recognizes it as a duplicate
  and writes zero. The financial failure here concerns the unkeyed manual
  source, not every native-ID path.

**Resolved 2026-10-23** — fixed: `_amounts_declared` in `cli/src/bea_engine/ledger/reader.py` compared a booked transaction with its source line posting by position, but Beancount's booking groups postings by currency, so a source with interleaved USD and EUR postings differed from its own booked copy and a plugin header copy at the same location made both generated. When the positional comparison fails, postings are now matched one for one regardless of order, through a new `_posting_declared` that also holds the account, units, cost, price and flag checks. The written source stays in `list --on-disk`, and a copy that changes an amount is still generated. Regression tests in `cli/tests/test_currency_regrouped_source.py` (on-disk, unchanged-statement import, changed-amount copy); the on-disk and changed-amount tests fail without the fix. Full suite green (10567 passed, 2 skipped). Not exercised: `--duplicates skip` and human apply as separate runs, and euro-first or reversed plugin orders. The unchanged-statement import test passes without the fix too, so it guards the behaviour but does not reproduce the reported double write.
