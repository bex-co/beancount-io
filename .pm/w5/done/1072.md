# Preserve native precision when Cash Flow merges cash accounts

**Minor · cli · 20–35m · A1 · worker1.** An exactly balanced, price-free
SHIB ledger is refused as unsupported priced FX solely because its larger
cash posting comes first. Reversing those two postings produces the same
native account inventories and works. In a quiet month the first ordering
exits 0 with `ledger_valid: true` / `valuation: complete`, but reports opening
and closing **0.12345678901234568 SHIB** instead of native
**0.123456789012345678 SHIB**. Its own per-account balance objects still keep
the exact inputs. Source bytes and ledger money do not change; this is an
order-dependent read/aggregation defect, two smallest SHIB units in this case.

Environment: 2026-10-27, immutable CLI source
`9ff5cc6184bc75cdaf4e5a8a79e7fc09089e95fa` (1734 tracked files), byte-identical
to reviewed main through `b58c6acafa87f8ed6499258f89dae77ff12d5662`.
Checkout bea 0.3.1, frontend Python 3.13.3, managed Python 3.12.10 /
Beancount 3.2.3 / Beanquery 0.2.0, macOS 26.5.1 arm64. Fresh synthetic books,
offline bounded commands, explicit local files, child-local config/cache,
notifier off, DEVNULL stdin/no TTY, separate streams/exits/timings and hashes;
HOME unchanged. No plugins, posting prices, lot costs, conversions or invalid

## Standalone reproduction

The essential book is:

```beancount
2024-01-01 commodity SHIB
2024-01-01 open Assets:Checking SHIB
2024-01-01 open Assets:Savings SHIB
2024-01-01 open Equity:Opening SHIB
2024-01-02 * "Two cash accounts"
  Assets:Checking 12345678901.123456789012345678 SHIB
  Assets:Savings -12345678901 SHIB
  Equity:Opening -0.123456789012345678 SHIB
```

`check`, native `Inventory.add_position`, BQL `SUM(position)` and the unit
balance sheet agree on total cash **0.123456789012345678 SHIB**.
January `report cash-flow` exits **2**, claiming “some transactions move cash
in SHIB by a price, not by cost”. Quiet February exits **0** but its opening
and closing both lose the last two units. Swap only Checking and Savings in
the transaction: January reports the correct movement, and February keeps
the exact native opening/closing. Reducing the first value to 28 significant
digits (`1234567890.123456789012345678`, with the matching whole withdrawal)
also works. None of these transactions needs a tolerance to balance.

Put checkout `bea` on PATH, save this as `recipe.py`, and run in a fresh path:

```sh
python3 recipe.py /absolute/unused/cash-sum wide-first standard root /absolute/managed-engine/bin/python
```

`small-first` and `boundary` are the working controls. `renamed included`
uses renamed roots and a split journal. Each recipe records 16 real CLI
calls and four uncached native loads, guards all four input files, and
compares the real source with an independently handwritten reverse-order
reference plus a full PRINT export. It tests human/JSON, `--time`, explicit
date bounds, `--allow-errors`, quiet-month output, native BQL and a sibling
unit report. The parent tree's `balance_children` is its aggregate; its
`balance` is only direct postings, so the control reads the former.

## Cause and bounded repair

[`_sum_amounts`](../../cli/src/bea_engine/report.py#L1214) initializes each
currency with `totals.get(currency, Decimal(0)) + total` (:1219). Decimal
addition is arithmetic even when adding zero: the first 29-digit amount
rounds to 28 **before** the offsetting whole quantity arrives. Native
`Inventory.add_position` stores a first position without arithmetic, then
subtracts the whole quantity exactly, leaving an 18-digit residual. The
current Fava inventory already follows that native behavior after
[1054](./done/1054.md), so each cash-account inventory is correct; this later
map fold rounds it again.

The four call sites are Cash Flow's activity totals (:1113), overall activity
net (:1114), selected cash movement (:1120) and closing total (:1138).
The new guard sees the artificially rounded movement disagree with the
18-digit activity net and refuses January. In quiet February both flows are
empty, so the guard passes; the closing fold still rounds, and the derived
opening inherits that false total. Source posting order controls the dict's
first amount. Frontend [`cash_flow`](../../cli/src/cli/commands/report.py#L620)
prints or emits the resulting payload unchanged. No sibling report, importer,
API adapter or upstream Decimal implementation needs changing.

Make a first value and a genuine zero/no-op preserve the incoming native
Decimal, as the fixed inventory does, while keeping explicit zero currency
keys. Actual nonzero additions must retain normal native arithmetic; do not
globally raise precision, round to display digits, change the source or
weaken the reconciliation guard. The report must use the exact combined cash
facts for opening/closing/movement and remain independent of posting order.
Cover first-wide cancellation, reversed order, 28-digit boundary, zero keys,
and real additions, with native inventories as the oracle. Keep native
rounded cost arithmetic and valid-FX refusal semantics. Run CLI checks when
implementing. This is a bounded shared-fold fix, not a precision-policy rewrite.
