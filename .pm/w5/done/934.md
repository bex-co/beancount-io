# Recognize native directive text when locating a leaf's root

**Major · cli · 45–60m · A1.** Valid unpadded or compact account-open dates,
or a UTF-8 BOM before its first open, hide a split ledger's root from leaf-write routing. A note is refused as an
unknown account, and its suggested `add open` succeeds at exit 0 in the leaf.
The previously valid whole ledger then fails check with a duplicate open.
No `--allow-errors` is involved. No product fix implemented.
A first-line BOM on a root-only operating-currency option also loses the
root's currency default, as verified below.

Real CLI QA, 2026-10-21, checkout `cb137da07` (initial journeys on
`ea8bb9c94`, CLI unchanged), `bea 0.3.1`, macOS 26.5.1 arm64, frontend
Python 3.13.3, existing managed Python 3.12.10. Separate subprocesses,
closed stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-1-1 open Assets:Cash USD
2024-1-1 open Equity:Opening USD
2024-01-02 * "Capital"
  Assets:Cash 1000.00 USD
  Equity:Opening -1000.00 USD
include "entries.bean"
```

`/abs/books/entries.bean`:

```beancount
option "operating_currency" "USD"
2024-01-03 note Assets:Cash "Original note"
```

From `/abs/books`, with the isolated child environment above:

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/entries.bean add note --date 2024-02-01 --account Assets:Cash --comment "Reviewed statement"
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/entries.bean add open --date 2024-01-01 --account Assets:Cash --currency USD
bea --json -f /abs/books/entries.bean check
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean list open --account Assets:Cash --allow-errors
```

Actual exits: **0, 1, 0, 0, 0, 1, 0**. The first note returns empty stdout
and a JSON validation error on stderr, including:

```text
Invalid reference to unknown account 'Assets:Cash' To create it, use bea --file entries.bean add open --account Assets:Cash --date YYYY-MM-DD.
```

It preserves both files. The next add uses that remedy with the account's
actual opening date. It returns `written: 1`, no warnings, and
`target.file` = `/abs/books/entries.bean`. It appends:

```beancount
2024-01-01 open Assets:Cash USD
```

The leaf now checks successfully in isolation. The root, which was valid
before the add, now reports `Duplicate open directive for Assets:Cash` at
the new leaf line and exits 1. The final listing returns two Cash opens.
The root file itself remains byte-identical; the invalid state is introduced
through its included leaf. The same date gap can also misclassify a plugin
overlay as the root and accept a false balance assertion; see the variant below.

Expected: recognize `main.bean` as the defining root, as the split-ledger
write contract promises. The note should be checked against that root and
written to the leaf. Reopening Cash must be refused without changing either
file, because that root already opens it. A direct read of the unmodified
leaf can still fail and point to the real root; creating a second open must
not be its remedy.

Twenty-two fresh journeys, each profile repeated twice:

- Eight initial journeys: padded ISO and padded slash controls route correctly;
  unpadded dates and `2024-01-01open` reproduce the refusal followed by a
  successful duplicate open. All roots initially pass check.
- Fourteen further journeys isolate the root's open lines while leaving its
  capital transaction in ordinary padded ISO. One-digit month, one-digit day,
  unpadded slash, compact ISO and compact slash all reproduce the invalidating
  open. Padded ISO and slash controls accept the note, reject the duplicate
  open and keep the root valid.
- In every failure, the modified leaf passes check and the root fails with
  exactly the duplicate Cash open; listing confirms two opens. Restoring the
  synthetic leaf and explicitly using `--file main.bean --into entries.bean`
  makes the note work and correctly refuses reopening Cash. Root bytes remain
  unchanged throughout. These private fixtures were restored before recovery;
  the public command sequence intentionally retains the invalid state as proof.

Cause: `cli/src/bea_engine/ledger/write.py:_OPEN_LINE` (:2051) requires
two-digit month/day and whitespace between the date and `open`. Both are
stricter than the native parser, as the successful initial checks prove.
`_defines_in` (:2104) therefore misses the external account opens. With the
operating-currency option already present in the leaf, no fresh option rescues
the classification. `defining_root` returns no root and `write_through_root`
(:2168–2189) leaves the write on the leaf. Final validation sees only that
leaf, where adding the missing open appears valid; the real root's duplicate
is outside the snapshot. The unknown-account hint has the same wrong scope.

Fix: recognize native date/token spellings when extracting root definitions
and keep the related dated predicates consistent: `_OPEN_ACCOUNT`,
`_DIRECTIVE_ACCOUNT`, `_PAD_ACCOUNTS` and `_ENTRY_LINE` (:2058–2074) use the
same narrow prefix for plugin-dependency and overlay decisions. Reuse native
lexing or existing compatible token handling rather than requiring a ledger
to be reformatted before a write is safe. Preserve explicit-root behavior,
pass-through includes, forecast-overlay exclusion and genuine two-root refusal.
Do not silence unknown-account/duplicate-open errors or weaken validation.

Shared root routing is called by engine `add`, `root` (frontend import-memory
lookup), `append` and `import` in `cli/src/bea_engine/main.py` (:286, :339,
:381, :579). Read and unknown-account hints use the same root predicates.
Runtime coverage here is add note/open and fresh check/list; import/raw append
impact is source-traced only. No dependency or backend/API change needed.

Dedupe: searched all board states for unpadded/compact root dates and the
dated root predicates; the same 46 active/blocked milestone scopes scanned
for w5/933 contain no matching repair. Completed w5/343–348 added leaf/root
validation; w5/774 (`c727a3623`) introduced these definition predicates and
w5/870 repairs case-variant filename suffixes, a different lookup boundary.
Completed w1/114 accepts compact tokens in listing provenance, and w1/163
accepts native dates in managed-price shadowing; neither changes root facts.
Open w5/933 is false ambiguity between recognized roots, not missing a root's
opens. Targeted predicate history shows no subsequent syntax repair.

Acceptance: all date spellings above route leaf writes through the same root;
the note succeeds and a duplicate open refuses with unchanged bytes and a
passing root check. Keep the padded controls, source locations and other
root-selection rules, including the overlay variant below. The seven public
commands were replayed twice. Only
macOS/checkout tested; repaired behavior unverified.

## Overlay variant of the same date scan

In a pristine copy of the first two fixtures, create `forecast.bean`:

```beancount
plugin "beancount.plugins.auto_accounts"
include "main.bean"
2024-03-01 * "Forecast withdrawal"
  Assets:Cash -7.00 USD
  Equity:Opening 7.00 USD
```

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/forecast.bean check
bea --json -f /abs/books/main.bean add balance --date 2024-03-02 --account Assets:Cash --amount "1000.00 USD"
bea --json -f /abs/books/main.bean add balance --date 2024-03-02 --account Assets:Cash --amount "993.00 USD"
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/forecast.bean check
```

Actual exits: **0, 0, 1, 0, 1, 0**. The real root holds 1,000 USD; its true
assertion refuses unchanged. The false 993 USD assertion writes 1 to main.bean
at exit 0 with `target.file` = forecast.bean. The root then fails its balance
check, while the overlay passes because its forecast accounts for the 7 USD
difference. The leaf and forecast stay byte-identical.

Six fresh journeys, twice across padded/unpadded/compact opens, verify this
variant. Padded opens ignore the unneeded overlay plugin and correctly accept
1,000 / refuse 993. Both native-date variants do the opposite. In another
pristine copy, explicit destination selection also keeps validation on the
working root even with unpadded opens:

```sh
bea --json -f /abs/books/main.bean add balance --date 2024-03-02 --account Assets:Cash --amount "1000.00 USD" --into main.bean
bea --json -f /abs/books/main.bean check
```

Both exit 0. All public variant/control sequences were replayed twice.

The related `_OPEN_ACCOUNT` predicate misses these already-written opens.
`_posts_unopened` therefore says the working root needs the overlay's fresh
auto-accounts plugin, although every account it uses is already open.
`_defines_in` (:2117–2119) promotes the overlay instead of stopping below it.
This independently verifies why the repair must cover the common dated
predicates, rather than only `_OPEN_LINE`. Completed w5/578/774's forecast
exclusion must also hold for native date spellings. No plugin or native
balance-assertion behavior needs changing.

## UTF-8 BOM before the first open

Additional real CLI QA on 2026-10-21, HEAD `dead69e3c` (CLI unchanged), finds
the same false root facts with an ordinary padded date preceded by a UTF-8
BOM. The native loader accepts it. In a disposable directory, create:

```python
from pathlib import Path
books = Path('/abs/books')
books.mkdir(parents=True, exist_ok=True)
(books / 'main.bean').write_text(
    '\ufeff2024-01-01 open Assets:Cash USD\n'
    'include "entries.bean"\n', encoding='utf-8')
(books / 'entries.bean').write_text(
    '2024-01-01 open Equity:Opening USD\n'
    '2024-02-01 * "Opening"\n'
    '  Assets:Cash 100.00 USD\n'
    '  Equity:Opening -100.00 USD\n', encoding='utf-8')
```

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/entries.bean add note --date 2024-02-02 --account Assets:Cash --comment "Statement reconciled"
bea --json -f /abs/books/entries.bean add open --date 2024-01-01 --account Assets:Cash --currency USD
bea --json -f /abs/books/main.bean check
```

Actual exits: **0, 1, 0, 1**. The note's refusal calls Cash unknown and advises
adding its open. That command reports `written: 1`, targets the leaf alone,
and writes the second Cash open; root check then reports `Duplicate open
directive`. The root bytes, including its BOM, stay unchanged. Expected:
the note routes through the root and succeeds, and the duplicate open is
refused with no append, leaving the root valid.

Six fresh books, two repetitions × plain/BOM-before-open/BOM-before-option,
verify the boundary. Plain and BOM-before-option controls both route the note
correctly, refuse the duplicate and preserve a valid root. In the latter,
the padded open follows the BOM-bearing option on the next line. Removing
only the BOM in a pristine copy is also a working public control. The four
public commands and that control were replayed twice.

The raw-byte `_OPEN_LINE` anchor is `^` followed immediately by the digit;
it misses the sole first-line open behind `EF BB BF`. This is the same
`_defines_in` false negative and leaf-only validation as the date variants.
Recognize the loader-supported BOM at a file's beginning when deriving
root facts, alongside the accepted date spellings; the related anchored
option/plugin predicates should retain the same native text handling.
Do not remove the BOM from the user's source merely to route a write.
Whole-board BOM/root searches find no overlapping open repair; the treeify
BOM decoder and Ask context issue w5/891 concern separate readers. This
extends this root-fact repair rather than adding another finding.

The `_OPTION_NAME` sibling is now runtime-confirmed too: four fresh books,
two repetitions × plain/BOM, use a root containing only
`'\ufeffoption "operating_currency" "USD"\ninclude "entries.bean"\n'`
and a leaf containing
`'2024-01-01 open Assets:Cash\n2024-01-01 open Expenses:Food\n'`.
Both roots pass check. Running
`bea --json --no-input -f /abs/books/entries.bean add transaction Coffee --date 2024-02-01 -p 'Expenses:Food 7.75' -p Assets:Cash`
on the BOM case refuses at exit 2 with `Currency is ambiguous for
Expenses:Food`, because it runs against the leaf alone and sees no default.
The plain case routes through the root and writes one in USD. On a pristine
BOM case, explicit `-f /abs/books/main.bean` with `--into entries.bean`
also writes one; query gives Cash -7.75 / Food 7.75 USD and check passes.
Root bytes stay unchanged and the false refusal preserves the leaf.
This corroborates applying the BOM handling to shared root facts, including
options, rather than special-casing only dated opens.

## Native account text in the same root facts

Additional real CLI QA on 2026-10-21, HEAD `e01a385d3`, confirms another
false negative in the same raw dependency scan: valid accented root names
hide an unopened account from `_posts_unopened`. The account's auto-open
plugin is then mistaken for an unneeded overlay, so a valid leaf write fails.

Create `/abs/books/main.bean`:

```beancount
plugin "beancount.plugins.auto_accounts"
include "entries.bean"
```

Create `/abs/books/entries.bean`:

```beancount
option "name_assets" "Áctivos"
2024-01-01 open Equity:Opening USD
2024-01-02 * "Opening"
  Áctivos:Cash 100 USD
  Equity:Opening -100 USD
```

In the same isolated subprocess environment, closed stdin/no TTY:

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/entries.bean add note --date 2024-02-01 --account Áctivos:Cash --comment "QA note"
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean add note --date 2024-02-01 --account Áctivos:Cash --comment "QA note" --into entries.bean
bea --json -f /abs/books/main.bean list note
bea --json -f /abs/books/main.bean query "SELECT account,sum(number) WHERE account='Áctivos:Cash' GROUP BY account"
bea --json -f /abs/books/main.bean check
```

Actual exits **0, 1, 0, 0, 0, 0, 0**. The leaf write says `Invalid reference
to unknown account 'Áctivos:Cash'` and preserves every byte, even though the
root already passes check. Explicit root plus `--into` writes one note,
the listing contains exactly that note, Cash remains 100 USD and the root
stays valid and byte-identical. Expected: the leaf write routes through the
root and succeeds too. Both recipes were replayed twice from pristine books.

Controls: the same split with ASCII `Activos` routes correctly and writes
through the root. `Actívos` also fails, proving this is not confined to the
first character. Leaving the default `Equity:Opening` unopened makes the
accented case work: that ASCII posting correctly triggers the plugin
dependency and rescues root selection. All four control variants ran twice;
each final root passes check and contains exactly one note.

`_POSTED_ACCOUNT` (`cli/src/bea_engine/ledger/write.py:2061`) accepts only
`[A-Z][A-Za-z0-9_-]*` before the first colon. It sees the already-open Equity
posting but neither accented asset root. `_posts_unopened` returns false,
then `_defines_in` rejects the fresh `auto_accounts` dependency. The same
predicate drives defining-root selection and read/write root hints. The
explicit-root control bypasses this false dependency decision.

Include native account tokens in the shared root-fact repair above, preserving
the existing exclusion of a genuinely unneeded overlay. This extends the
same open work item rather than creating another root-classification task.
Whole-board searches and active milestone scan found no separate Unicode
dependency repair; `c727a3623` introduced the ASCII posting predicate.
The source amount, plugin behavior and native account grammar need no change.
