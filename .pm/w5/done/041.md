# Unparseable resource URI skips the coded-error envelope

**Severity:** low. **Journey:** boundaries. **Owner:** backend-v2. Found by the MCP QA auth sweep on 2026-10-03 against production; live at repo HEAD `75819075`. No live board dupe.

Target: `https://beancount.io`, `POST /api-gateway/mcp` (production), observed 2026-10-03.
serverInfo `{"name":"beancount-mcp","version":"1.0.0"}`, protocolVersion `2025-11-25`.
Credential: `bcio_` API key (server kind `apikey`), scopes `ledger.read ledger.write ledger.admin`, ledger pin none (unpinned), no expiry. Value never recorded.
Helper: `node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file muse.env` from repo root.

## Repro (synthetic coords `qa-owner/qa-book`)

```sh
read not-a-uri
```

JSON-RPC sent:

```json
{"jsonrpc":"2.0","method":"resources/read","params":{"uri":"not-a-uri"},"id":1}
```

Observed: -32603 `Invalid URL` with NO `data` envelope, while other unmatched URIs get coded -32002 + `data.code` (the c86144b3 fix covers those, but not unparseable input).

## Control

None: MCP-protocol-only defect (in-SDK parse, no REST counterpart).

## Cause

- `backend-cluster/backend-v2/src/features/ai-agent/api/mcp-resource-template.ts`

`new URL(uri)` in `QueryResourceTemplate.match` (:40) throws TypeError outside any try/envelope, so the SDK reports it raw.

## Fix (parity: MCP)

Owning package `backend-cluster/backend-v2`; the fix must land on every eligible surface (MCP) in the same change. Wrap the parse in `refuseUri` with the coded envelope.

## Evidence

`.tmp/qa-2026-10-03-auth/r2-boundaries-account/03-resource-urishapes.txt` (gitignored bundle `.tmp/qa-2026-10-03-auth/`); finding brief `.tmp/qa-2026-10-03-auth/final/boundaries-account-invalid-uri-no-datacode.md`.

---

**Resolved 2026-10-03** — a `resources/read` for a string that is not a URI is now refused as `-32602` with `data.code: BAD_USER_INPUT` and a hint naming `resources/templates/list`, instead of the SDK's bare `-32603 Invalid URL`. Shipped in `83c13deb` (`backend-cluster/backend-v2`).

The cause was one layer above where the note points: the SDK's own dispatcher parses the URI before it consults any template, so wrapping the parse in `mcp-resource-template.ts` could not have caught it. `resources/read` is now answered at the server's own boundary, as `tools/call` already is, dispatching over the same templates in the same order. That also closes a neighbouring gap found on the way: a URI in another scheme matched no template — not even the `beancount://` catch-all — and got the SDK's uncoded "not found"; it is now a coded `NOT_FOUND`. Tests read `not-a-uri`, an empty string, a scheme-less string, a foreign-scheme URI and an oversized input through an MCP client; all fail with the fix reverted. Not re-run against the hosted endpoint: the fix reaches it with the next deploy.
