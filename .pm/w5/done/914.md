# Clarify the import lifecycle exceptions for notes and documents

**Trivial · cli docs · 10–15m · A1.** The importing guide says notes and
documents on an account closed before their date are blocked. They correctly
import: Beancount permits a final note or statement attachment after the
account closes. The guide should describe that supported workflow and the
actual opening-date checks. No product fix implemented.

Real CLI QA 2026-10-21, checkout `4a79feb7c`, `bea 0.3.1`, Darwin 25.5.0
arm64, frontend Python 3.13.3, managed Python 3.12 engine with existing
Beangulp. Two pristine repetitions of each of six cases (12 journeys),
bounded separate processes, closed stdin/no TTY, isolated absolute
BEA_CONFIG_DIR/XDG_CACHE_HOME, updater disabled, no inherited
BEA_FILE/BEA_TOKEN. No hosted data.

Create `/absolute/qa/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-31 close Assets:Cash
```

Create a synthetic `bank.txt`, an existing `receipt.pdf` fixture, and
`importers.py`:

```python
from beancount.parser import parser

class Imp:
    def identify(self, file):
        return str(file).endswith(".txt")
    def account(self, file):
        return "Assets:Cash"
    def extract(self, file, existing_entries=None):
        entries, errors, _ = parser.parse_string(
            '2024-02-01 note Assets:Cash "Final statement received"\n'
        )
        assert not errors, errors
        return entries

CONFIG = [Imp()]
```

```sh
bea --json -f /absolute/qa/main.bean import /absolute/qa/bank.txt --config /absolute/qa/importers.py
bea --json -f /absolute/qa/main.bean import /absolute/qa/bank.txt --config /absolute/qa/importers.py --apply
bea --json -f /absolute/qa/main.bean list note
bea --json -f /absolute/qa/main.bean check
```

Actual, twice: preview exits 0, `ready: 1`, `blocked: 0`, `invalid: 0`, row
status `new`; apply exits 0 and writes 1. Fresh listing retains the February 1
note, and check exits 0. Replacing the returned directive with
`2024-02-01 document Assets:Cash "receipt.pdf"` on fresh fixtures gives the
same result twice. Preview preserves ledger bytes.

Controls for each type, twice: an account first opened on March 1 makes the
February 1 annotation `invalid: 1`, apply exit 1, written 0 and unchanged
bytes, with the opening date/location in its reason. An account never opened
makes it `blocked: 1`, apply exit 4 and unchanged bytes, with the valid
`add open` remedy. The accepted post-close case is a native annotation
exception, not failed inactive-account protection.

Mismatch: `cli/docs/IMPORTING.md:186–200` groups an importer's balance,
note, document, pad and close together, then says rows whose account was
closed before their date are `blocked` and apply exits 4. It also overstates
that classification for pre-open notes/documents, which native validation
reports as invalid instead. `cli/src/bea_engine/importing.py:1969–1990`
explicitly leaves Note/Document out of the active-account check because they
may follow a close; `_inactive_reason` at 2176 is its only `active_only`
caller. Existence checks and final native validation remain active.

Fix: correct that paragraph to distinguish ordinary active-account
requirements from annotation rules. State that notes/documents may follow a
close, still need an opened account, and are refused as invalid when dated
before that opening. Keep the existing accepted/rejected states and exit
codes; no runtime or API change is needed.

**Resolved 2026-10-22** — `cli/docs/IMPORTING.md` no longer groups notes and documents with the rows an inactive account blocks: it now says they may follow the account's `close`, still need an account the ledger opened (never-opened is `blocked` with the `bea add open` line), and are refused as `invalid` when dated before the opening (`--apply` exits 1). The three states were retested against isolated fixtures (post-close: ready, apply exit 0; pre-open: invalid, exit 1; never-opened: blocked, exit 4); docs check green; prose only, no runtime change; shipped in the commit that moves this note (`cli`).
