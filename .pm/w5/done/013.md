# The importer dependency error tells you to fix the wrong environment, and cites the doc that says so

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** cli. **A1:** an
agent or author writing a custom importer that needs a third-party package is
told to change the environment it runs `bea` from — which the CLI's own
documentation states explicitly will not work — so the obvious next step is a
dead end.

Found 2026-09-16 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME`. Synthetic local fixtures only.

## Repro

```sh
bea --no-input init books --currency USD --date 2026-08-01
printf 'Date,Payee,Narration,Amount\n2026-08-02,Cafe,Coffee,-5.25\n' > bank.csv
cat > imp.py <<'PY'
import definitely_not_installed_module_xyz
CONFIG = []
PY
bea --file books/main.bean import bank.csv --config imp.py
```

```text
Error: Importer dependency is unavailable: No module named
'definitely_not_installed_module_xyz'. Run bea in an environment containing
your importer's dependencies; see docs/IMPORTING.md. Pass --debug before the
command for a traceback.
```

## The advice contradicts the document it points at

`cli/docs/IMPORTING.md:251-256` is explicit, and bolds the part that matters:

> No extra dependency is needed for the CSV mapper or the importer interface
> itself. Configurations that `import beangulp` (or other importer packages)
> need those packages in the **managed engine**, not the bea frontend

The docs are right. The importer configuration is executed by the engine
interpreter, not the frontend — measured by having the config record
`sys.executable` and `sys.prefix` as it loads:

```text
/Users/<you>/.local/share/bea/engine/0.2.0/bin/python
/Users/<you>/.local/share/bea/engine/0.2.0
```

against a frontend running from `cli/.venv/bin/python3`. So "run bea in an
environment containing your importer's dependencies" describes an action that
cannot help: installing the package into the shell, venv or `uvx --with …`
environment that launches `bea` leaves the engine interpreter unchanged, and
the next run fails identically. The message then cites the document that would
have told the user this, which is the only reason the situation is
recoverable at all.

## Expected / actual

Expected: name the environment that actually needs the package — the managed
engine — and give the user a way to locate it, the way the rest of the engine
diagnostics do. `bea engine status` already prints the engine root and is the
documented place to look (`IMPORTING.md:268`).

Actual: one sentence that points at the frontend, and a doc reference that
contradicts it.

## Root cause

`cli/src/bea_engine/importing.py:140-145`:

```python
except ImportError as exc:
    raise UsageError(
        f"Importer dependency is unavailable: {exc}. Run bea in an environment containing your importer's "
        "dependencies; see docs/IMPORTING.md.",
        traceback=_traceback(exc),
    ) from exc
```

The handler lives in `src/bea_engine/`, i.e. engine-side, so by construction the
`ImportError` it catches is the *engine* interpreter failing to import the
module. The wording predates or simply diverges from the guidance later written
into `IMPORTING.md`. `git log -S 'Run bea in an environment containing' --
cli/src` shows it arriving with `ff47e5c6` and carried through `a90b1706`
(ADR014), the change that established the frontend/engine split this sentence
now gets wrong.

## Fix

Reword to match the documentation and the architecture: say the package must be
available to the managed engine rather than the frontend, point at
`bea engine status` for its location, and keep the `docs/IMPORTING.md`
reference. Keep the `ImportError` branch distinct from the general
`Importer failed (…)` branch below it — that separation is useful and correct.
Add coverage asserting the message names the managed engine and does not tell
the user to change the environment running `bea`.

Worth deciding at the same time whether there is a supported way to satisfy
such a dependency: `bea engine enable` covers only the known optional features
(`beangulp`, `beanprice`), and `IMPORTING.md:269-272` currently says to add
third-party importer packages "the same way you would for any engine-side
dependency once Beangulp is enabled, or keep a separate project environment for
custom importer development". If that is the intended answer, the error message
should say it in one line; if not, the gap belongs on the board separately.

## Blast radius and adjacent states

Affects every `bea import --config` run whose configuration imports a module the
engine lacks. The neighbouring importer diagnostics are correct and were
exercised: a missing `CONFIG`, a non-list `CONFIG`, an empty `CONFIG`, a syntax
error, an import-time exception, an unknown `--importer` name, and a recognized
importer that rejects the file all produce distinct, accurate messages, and a
raising importer is contained cleanly with a `--debug` hint. `bea ingest` shares
the engine-side execution model and was not exercised for this message.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for importer-dependency,
managed-engine and engine-side-dependency terms. Nothing covers this message.
`.pm/w5/011.md` and `.pm/w5/012.md` are the same *class* — a remedy that names
the wrong target — but in the engine-resolution and auth subsystems
respectively; this one is in the importer path and is a one-sentence fix, so it
is filed apart. `.pm/w2/done/022.md` concerns `engine status` reporting and is
fixed. Reproduced at `b78efe7d`, so not deployment lag.

## Evidence and unverified areas

Captures under `cli/tmp/qa-20260915/run22/` hold the failing import, the

**Resolved 2026-09-16** — The message now names the environment that actually needs the package: "Importer configurations are executed by the managed engine, not the environment you run bea from, so the package has to be installed there; 'bea engine status' prints which engine serves and where it lives. See docs/IMPORTING.md." The `ImportError` branch stays distinct from the general `Importer failed (…)` branch, as the note asked. Shipped in `b2650f1f` (`cli`).

The note's interpreter split was re-measured independently rather than taken on trust: an importer configuration loads under `~/.local/share/bea/engine/0.2.0/bin/python` while the frontend runs from `cli/.venv/bin/python`, so the old advice was indeed a dead end. Coverage in `cli/tests/test_import.py` asserts the new message names the managed engine and `bea engine status`, keeps the `docs/IMPORTING.md` reference, and no longer says "Run bea in an environment"; a second test pins that an importer raising a non-`ImportError` still takes the other branch. Reverting the fix fails the first and leaves the second passing. `make check-all` passes (866 tests).

Left open deliberately: the note's question of whether there is a *supported* way to satisfy a third-party importer dependency. `bea engine enable` covers only the known optional features, and `IMPORTING.md` currently answers vaguely ("the same way you would for any engine-side dependency once Beangulp is enabled, or keep a separate project environment"). Naming `BEA_ENGINE_PYTHON` in this error would contradict `USAGE.md`, which frames it as an advanced override for tests and recovery tooling. That is a product decision rather than a wording fix, so it is filed as its own note ([w5/015](../blocked/015.md), blocked on that decision) rather than being invented here; this message points at the docs, which is correct regardless of how it is answered.
