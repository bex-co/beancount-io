## Fix (parity: MCP+REST)

Owning package `backend-cluster/backend-v2`; the fix must land on every eligible surface (MCP+REST) in the same change. `.int().positive()` on both schemas; regression: delete `1.5` -> BAD_USER_INPUT.

---

**Resolved 2026-10-02** — a key id that is not a positive integer is now refused as BAD_USER_INPUT before any upstream work. The check sits in the key service, so it also covers GraphQL, whose `keyId` argument is a Float; the REST path parameter and the delete schema the MCP tool parses carry the same constraint, and the v1 OpenAPI document publishes `keyId` as a required positive integer. Shipped in `2c012633` (`backend-cluster/backend-v2`).

Regression tests delete `1.5`, `0` and `-1` through REST, GraphQL and an MCP client and assert that nothing reaches the key store; they fail with the fix reverted. The advertised MCP tool schema is unchanged, because the integer bounds would have pushed `tools/list` past its 64 KB budget. Not re-run against the hosted endpoint: the fix reaches it with the next deploy.
