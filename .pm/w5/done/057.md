# Bulk posting fragments bypass the literal-zero-divisor guard and crash validation

**Minor · 30–45m · cli · A1 — Agent-native accounting.** A bad bulk row
crashes the engine instead of yielding the documented row rejection, and
--partial cannot append an unrelated valid row. Reject literal zero divisors
before parsing the fragment; preserve the existing batch validation contract.

Found 2026-10-08 at HEAD `96aa0048`, checkout `bea 0.3.1`, Python 3.13.3,
macOS/Darwin. Real bounded subprocesses, closed stdin/no TTY, isolated absolute
config/cache directories and disabled update notices. No network or hosted
credential is needed. Two pristine synthetic batch fixtures, each repeated
twice; source hashes and contents confirm no ledger changes after crashes.

## Reproduction

Create `/absolute/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

Create `/absolute/batch.json`:

```json
[
  {"date":"2026-02-01","narration":"valid","postings":[
    {"account":"Expenses:Food","amount":"1 USD"},
    {"account":"Assets:Cash"}]},
  {"date":"2026-02-02","narration":"bad","postings":[
    {"account":"Expenses:Food","amount":"100/0 USD @ 1 USD"},
    {"account":"Assets:Cash"}]}
]
```

Run from a disposable cwd:

```sh
bea --json --file /absolute/main.bean add transactions --from /absolute/batch.json
bea --json --file /absolute/main.bean add transactions --from /absolute/batch.json --partial
```

Both exit **4** with empty stdout. JSON stderr reports:

```text
The Beancount engine did not answer 'bea-engine add --file /absolute/main.bean --type transactions --request -' (exit -11); the outcome is unknown. Inspect the file before retrying.
```

The engine dies on SIGSEGV before row validation completes. Neither run writes
anything, including the valid first row under --partial. No row/field/zero
divisor is identified. Repeated twice per mode from reset fixtures.

Working controls: single `add transaction` with the exact same posting exits
**2**, explicitly naming division by zero and leaving the file unchanged.
Changing only the divisor from `0` to `0.5` in the bulk fragment writes both
rows, exits **0**, and a new-process `bea check` succeeds. A plain two-token
bulk amount `100/0 USD` also produces a normal row rejection rather than a
crash, because that branch checks Decimal before dispatching to the parser.

Expected: the literal-zero fragment becomes a row validation error before
Beancount parsing. Atomic mode exits 1, names the second row/posting, and writes
nothing. --partial exits 1, appends only the first row, and reports
`result.written = 1`, `written_rows = [0]`, `rejected_rows = [1]`, per USAGE's
Bulk transactions from JSON contract. Do not turn this into an attempt to
evaluate every arithmetic expression or solve upstream computed-divisor crashes.

## Cause, fix and dedupe

`cli/src/bea_engine/ledger/models.py:161,170–190` sends multi-token amount
shorthands to `_posting_fragment`, which calls `parser.parse_string` before
the model can validate its numbers. The equivalent flag path uses
`cli/src/cli/amounts.py:33–55` to reject a literal zero divisor first. The
bulk frontend (`cli/src/cli/commands/add.py:568–572`) forwards raw rows;
`bea_engine.ledger.adding._transactions` can collect ValidationError per row,
but it cannot catch a parser process crash during model validation.

Add the equivalent bounded literal-divisor check at the engine fragment input
boundary, respecting quoted labels/comments, raising a normal ValueError so
the row loop keeps --partial working. The engine cannot import the frontend;
use its own existing numeric validation module or a small engine-local check.
Keep safe divisors such as 0.5/10 and quoted zero-like text accepted. Run
meaningful real subprocess regressions, batch acceptance/preservation checks,
and `make check-all` inside cli when implementing. No dependency/API change.

Caller search found one `_posting_fragment` call, through the Posting
amount_shorthand model validator, reached by bulk TransactionDirective
validation. Scope: file/stdin bulk input, atomic and partial modes, including
--into; only file input and root writes were exercised. Existing structured
units do not carry arithmetic expressions. Other platforms, stdin, --into,
cost/price denominators and alternate zero spellings remain unverified.

Searched all board states for bulk zero divisors, shorthand/fragment crashes
and literal guards. Completed w5/010 deliberately leaves computed
`100/(2-2)` unsupported, but its literal-divisor protection predates the
fragment path added by `afc2af7e` (completed w3/272 / w1/m27/t005).
`git log -S '_posting_fragment'` traces that addition; current history has no
equivalent guard here. This is a missed adapter input path, not a request to
fork upstream arithmetic or reopen the accepted computed-divisor limitation.

Acceptance: the exact two-row fixture follows ordinary rejection/partial
semantics and names the bad row; no engine crash; positive divisor controls
still write and validate; atomic failures preserve every ledger byte.

Sanitized evidence under `cli/tmp/qa-20261008-cli/`:
`batch-repro-console.jsonl`, `batch_reproduce.py`, `batch_round2.py`, synthetic
batch files and `transcript.jsonl` with argv/cwd/environment, separate streams,
exits/durations and hashes. The public reproducer is self-contained. No
product fix or hosted mutation was performed.

---

**Resolved 2026-10-10** — the engine now refuses a literal zero divisor in a bulk amount fragment before handing it to Beancount's parser, with the same diagnostic the flag path gives. The exact two-row fixture exits 1 naming `Row 2, postings.0` in both modes: atomic writes nothing (`written: 0`, `rejected_rows: [1]`), and `--partial` appends only the first row (`written: 1`, `written_rows: [0]`, `rejected_rows: [1]`). Shipped in `50c1c6a4` (`cli`).

Real-command regression tests cover zero divisors in the units, a per-unit cost, a unit price and a total price, in the spellings `0`, `0.0`, `.0` and `00`; they assert the row is named, the ledger bytes are unchanged in atomic mode, and the partially written ledger passes `bea check`. Controls with divisors `0.5` and `10` and a cost label containing `1/0` still write and validate. Six of the seven tests fail with the fix reverted. `make check-all` passed. A computed zero divisor such as `100/(2-2)` is still not caught, as accepted in w5/010; stdin input, `--into` and other platforms were not exercised.
