# Arithmetic total-price inputs lose their exact @@ annotation

**Minor · 35–55m · cli · A1.** Accepted native arithmetic in a total-price
annotation silently becomes a repeating per-unit price. Preserve the evaluated
total and price_total JSON shape using upstream parsing, without adding an
independent arithmetic evaluator.

Found 2026-10-08 at HEAD `a4cd88ac`, checkout bea 0.3.1, Python 3.13.3,
macOS/Darwin. Real bounded subprocesses, closed stdin/no TTY, absolute isolated
config/cache, update notices disabled. No network or hosted credentials needed.

## Reproduce

Create `/absolute/main.bean`:

```beancount
2026-01-01 open Assets:Stock HOOL
2026-01-01 open Assets:Cash USD
```

Run:

```sh
bea --json --file /absolute/main.bean add transaction Total --date 2026-02-01 \
  -p 'Assets:Stock 3 HOOL @@ (40+60) USD' -p 'Assets:Cash -100.00 USD'
```

Exit **0**, no stderr. The written line is:

```beancount
  Assets:Stock  3 HOOL @ 33.33333333333333333333333333 USD
```

The add envelope reports price.number `33.33333333333333333333333333` and
price_total:null. The exact total 100 and the @@ annotation are lost. A fresh
check passes within the cash posting's ordinary cents tolerance; validity
therefore does not prove preservation of the requested total.

Repeated in a fresh ledger, and with `(100)` and `200/2` as the supplied total.
All accepted inputs become the same per-unit annotation. Working control:
change only `(40+60)` to `100` in a fresh ledger. It exits **0**, writes
`3 HOOL @@ 100 USD`, and reports price:null and price_total.number `100`.

The bulk shorthand path shares the failure. From a pristine ledger, pass this
file to `bea --json --file /absolute/main.bean add transactions --from FILE`:

```json
[{"date":"2026-02-01","postings":[
  {"account":"Assets:Stock","amount":"3 HOOL @@ (40+60) USD"},
  {"account":"Assets:Cash","amount":"-100.00 USD"}]}]
```

It exits **0** and writes the repeating @ line. A bulk `@@ 100 USD` control
preserves @@. All these successful files pass check. Initial probes with
`-100 USD` instead of `-100.00 USD` were refused by upstream's strict inferred
tolerance for the repeating valuation even for the literal control; that
upstream validation behavior is excluded from this finding.

Expected: valid native arithmetic in an @@ amount is evaluated once to its
total and remains `@@ 100 USD` with price_total:{number:"100",currency:"USD"}
in single-add JSON, so returned postings can be replayed as documented. USAGE's
Adding directives section supports native posting arithmetic; Investment
postings explicitly promises an exact @@ total, never its divided repeating
unit price. The bug concerns serialization after successful parsing, not
whether upstream stores a booked per-unit price internally.

## Cause, repair and dedupe

`cli/src/bea_engine/amounts.py:38–52` split_total_price recognizes only a
plain-decimal first token after @@. Arithmetic or parentheses return None.
`ledger/adding.py:822` then skips the total-price marker and serializes the
parser's divided unit price; `ledger/models.py:217` falls back the same way
for bulk amount shorthand. The helper's comment explicitly describes this
fallback, but it contradicts the supported input/output contract.

Extract the valid annotation's evaluated total through upstream Beancount
parsing before the quantity division, keeping the existing literal path and
quoted-label/comment handling. Reuse the engine's parser; do not implement
arithmetic independently or recover the total by multiplying the already
rounded unit price. Preserve the @@ marker and price_total response on both
callers. Keep malformed/missing prices and literal-zero-divisor protection.
Add real subprocess regressions for `(100)`, `(40+60)`, `200/2`, literal totals,
single-add JSON replay and bulk shorthand; run make check-all inside cli.
No dependency or backend/API change is needed.

Caller search found exactly the single-add _total_price and bulk
_posting_fragment users. Scope includes file/stdin bulk inputs and --into;
only root/file-input journeys were reproduced. Cost arithmetic, negative
units/totals, comments, stdin, --into and other platforms remain unverified.

Full-board/history dedupe: completed w3/309 preserves literal @@ annotations;
completed w1/093 corrects their single-add price_total answer. Neither covers
arithmetic totals. `git log -S split_total_price` traces the shared helper to
`afc2af7e` (w1/m27/t005); no current repair or matching open item was found.
This is a missed accepted spelling of the shipped guarantee, not an upstream
rounding fix. Keep normal booked listing normalization unchanged.

Acceptance: every reproduced expression writes the exact evaluated @@ total,
single-add output carries price_total and price:null, replay preserves that
annotation, bulk behaves likewise, and literal/malformed controls keep their
existing semantics. No successful write silently falls back to a divided
unit price just because the total was expressed with native arithmetic.

Sanitized evidence under `cli/tmp/qa-20261008-cli/`:
`total-price-expr-console.jsonl`, `total-price-repeat-console.jsonl`,
`total_price_expr_cents.py`, `total_price_repeat.py`, synthetic ledgers/batches
and transcript.jsonl with argv/cwd/environment, streams/exits and file hashes.
The public repro is self-contained. No product fix was implemented.

---

**Resolved 2026-10-10** — a total price written as native arithmetic now keeps its `@@` annotation. When the text after `@@` is not a plain decimal, the engine evaluates just that expression through Beancount's own parser (as a probe amount, so no arithmetic is implemented here) and records the result as the total. `3 HOOL @@ (40+60) USD`, `@@ (100) USD`, `@@ 200/2 USD` and `@@ 40 + 60 USD` each write `3 HOOL @@ 100 USD`, and single-add JSON answers `price: null` with `price_total: {"number": "100", "currency": "USD"}`. Shipped in `ad573aba` (`cli`).

Real-command regression tests cover those four expressions on the flag path — including replaying the JSON answer through `add transactions` to byte-identical text and a passing `bea check` — and on the bulk amount shorthand with a literal control; unit tests add a total beside a cost, a negated expression, a trailing comment and a quoted label containing `@@`, plus malformed expressions that still fall back. A zero divisor in the total is still refused with exit 2. Fifteen of the module's tests fail with the fix reverted. `make check-all` passed. While testing, a spaced expression exposed a misread in the existing literal path (`@@ 40 + 60 USD` took `+` as the currency); that is fixed in the same change. Arithmetic inside a cost, stdin input, `--into` and other platforms were not exercised.
