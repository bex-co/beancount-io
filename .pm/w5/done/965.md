`check` is valid. Raw ascending order is **num2, num10, text11**; explicit
text order is **num10, text11, num2**. Raw `LIMIT 1` therefore selects **num2**
instead of **num10**. Raw descending is **text11, num10, num2**, while the
text control gives **num2, text11, num10**. Human tables and CSV reproduce
the same raw order twice.

Two fresh repetitions of all six permutations of the three source rows give
**three different raw ascending results** for the same distinct values:
`num2/num10/text11`, `num10/text11/num2`, or `text11/num2/num10`.
The explicit `str()` control always gives `num10/text11/num2`; raw `LIMIT 1`
varies accordingly. This is a query result error, with no write or data-loss
claim. Numeric-only `2,10,11` sorts numerically, string-only `"2","10","11"`
sorts lexically, and missing metadata still sorts first ascending / last
descending; all controls pass in both repetitions.

**Cause and scope.** `cli/src/bea_engine/query.py:192–222`, `_Orderable`,
uses native comparison for each comparable pair, then text for each
incomparable pair. Thus `2 < 10` numerically, `10 < "11"` as text, and
`"11" < 2` as text are all true. This violates the ordering required by
Python's sort; it cannot become a consistent column order. Both `__eq__` and
`__lt__` catch only `TypeError`; upstream Amount's comparison methods assume
other Amounts and access `.number` / `.currency`, so a mixed Amount instead
leaks `AttributeError` before text fallback. Keep that upstream assumption;
the CLI adapter must choose compatible keys before comparing mixed values.
`_null_safe_ordering`
`:224–249` installs this key in Beanquery's `query_execute.nullitemgetter`;
installed Beanquery uses it in `rows.sort` at line 226.
The bad comparator is this CLI's adapter, not an upstream financial result.

`_native_shell` (`:490–503`), and `build_shell` (`:1320–1335`). JSON query,
one-shot human output, CSV and `LIMIT` are directly exercised here; an actual

**Resolved 2026-10-23** — fixed: `ORDER BY` now has one comparison rule per column (`_Column` and `_Orderable` in `cli/src/bea_engine/query.py`). The keys of a sort share a column record that is complete before the first comparison; a column whose non-null values are of different kinds (numbers beside text, an Amount beside a number or a string) is ordered as a whole by `str()`, which is `ORDER BY str(...)`'s order, and a uniform column keeps its native order, so numbers stay 2, 10, 11 and Amounts stay numeric. Every permutation of the three-row fixture now answers num10, text11, num2 (and `LIMIT 1` num10), descending and multi-key sorts keep their directions, null still sorts first ascending and last descending, and a mixed Amount no longer leaks `AttributeError`. Regression tests in `cli/tests/test_query_mixed_order_consistent.py` fail without the fix. Full suite green apart from the known `test_release` smoke timeout and a pseudo-terminal teardown flake, both of which pass alone. Shipped in this commit (`cli`).
