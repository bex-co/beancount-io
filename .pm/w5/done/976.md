# Honor shared-ID transfer reservations before skipping rows

**Major · cli · 30–45m · A1.** A shared-native-ID match bypasses the
whole-batch transfer reservations. One recorded transfer is offered to two
receiving-side rows, so `--duplicates skip` drops a genuine 100 USD gift.
Savings stays at **100 USD** and gift income/net worth at **0**, instead of
**200 / 100 / 100**. Both row orders fail. Changing only the gift's reference
or distance works. Follow-up to completed [882](./done/882.md);
no product fix implemented.

Real CLI QA, 2026-10-22, clean main `dbd9aa160` (initial reproduction on
`bba809727`; import code unchanged), checkout `bea 0.3.1`, frontend Python
3.13.3, managed Python 3.12.10 / Beancount 3.2.3 / Beanquery 0.2.0,
macOS 26.5.1 arm64. Fresh subprocesses, closed stdin/no TTY, isolated absolute
configuration/cache, notifier disabled and inherited file/token overrides
removed. Synthetic local CSVs and ledger only.

Use the checkout's `bea` on PATH and replace `/abs/case` with a fresh absolute
disposable directory. Checking records one 100 USD transfer. The receiving
statement has that transfer and a separate dated gift, whose source reference
is reused. The importer already supports repeated references on distinct
statement dates; they are not proof that two source rows are one payment.
The gift posts to `Income:Gift`, not Checking, and has its own date/description.

```python
import json, os, subprocess
from pathlib import Path
case = Path('/abs/case')
case.mkdir(parents=True)
ledger = case / 'main.bean'
ledger.write_text('''option "operating_currency" "USD"
2024-01-01 open Assets:Checking USD
2024-01-01 open Assets:Savings USD
2024-01-01 open Expenses:Uncategorized USD
2024-01-01 open Income:Gift USD
''')
unique_gift_ref = False
reverse_rows = False
head = 'Date,Description,Amount,Category,Reference\n'
checking = case / 'checking.csv'
savings = case / 'savings.csv'
checking.write_text(head + '2024-02-01,TRANSFER TO SAVINGS,-100.00,Assets:Savings,shared-ref\n')
gift_ref = 'gift-2' if unique_gift_ref else 'shared-ref'
rows = ['2024-02-06,TRANSFER FROM CHECKING,100.00,Assets:Checking,shared-ref\n',
        '2024-02-07,BIRTHDAY GIFT,100.00,Income:Gift,' + gift_ref + '\n']
savings.write_text(head + ''.join(reversed(rows) if reverse_rows else rows))
fixed = {p: p.read_bytes() for p in (checking, savings)}
env = os.environ.copy()
for key in ('BEA_FILE', 'BEA_TOKEN', 'BEANCOUNT_LOAD_CACHE_FILENAME',
            'BEA_ENGINE_PYTHON', 'BEA_ENGINE_DIR'):
    env.pop(key, None)
env.update(BEA_CONFIG_DIR=str(case / 'config'), XDG_CACHE_HOME=str(case / 'cache'),
           BEA_NO_UPDATE_NOTIFIER='1')
def run(tag, args, json_mode=True):
    argv = ['bea', *(['--json'] if json_mode else []), '--no-input', '-f', str(ledger), *map(str, args)]
    result = subprocess.run(argv, cwd=case, env=env, stdin=subprocess.DEVNULL,
                            capture_output=True, text=True, timeout=25)
    print(json.dumps(dict(tag=tag, args=argv, exit=result.returncode,
                         stdout=result.stdout, stderr=result.stderr)), flush=True)
map_spec = 'date=Date,narration=Description,amount=Amount,category=Category,id=Reference'
run('baseline-check', ['check'])
run('checking-apply', ['import', checking, '--csv', map_spec,
    '--account', 'Assets:Checking', '--apply'])
authored = ledger.read_bytes()
second = ['import', savings, '--csv', map_spec, '--account', 'Assets:Savings']
run('human-preview', second, json_mode=False)
run('preview', second)
assert ledger.read_bytes() == authored
run('default-apply', [*second, '--apply'])
run('skip-apply', [*second, '--duplicates', 'skip', '--apply'])
run('positions', ['query', 'SELECT account,sum(number) GROUP BY account ORDER BY account'])
run('transactions', ['list', 'transaction', '--sort', 'oldest', '--limit', '20'])
run('check', ['check'])
assert ledger.read_bytes().startswith(authored)
assert all(p.read_bytes() == content for p, content in fixed.items())
```

Cause: `answer` in `cli/src/bea_engine/importing.py:644–652` directly accepts
`_transfer_side(...)` as a possible duplicate without checking `paired(match)`
for that row. The later amount/date counterpart path consults reservations;
this native path does not. `_assign_counterparts` (`:1721–1764`) does reserve
the shared-reference transfer once, but that reservation is ignored when both
rows take the native-ID branch. With only shared-ID hits, the lazy `paired`
callback need not run at all.

Four direct controls on the actual two-row graphs confirm: the assignment
reserves the only transfer for row 1; `_transfer_side` still returns that same
entry for row 2, whose reservation is false, and actual preview marks both
possible duplicates. There is also an ordering guard for the repair: the
native-ID reservation loop currently assigns in input order. In reversed
input, it reserves the farther gift, not the nearer transfer. Simply checking
that current reservation would then write the original transfer again and
still skip the gift. Reserve eligible shared-ID claims by date proximity
before classifying rows, with the existing row-order tie break only for equal
distances.

Fix in `cli/`: use one-to-one whole-batch assignments consistently for both
shared-native-ID and amount/date matching. When several source rows share a
native reference, reserve its eligible recorded counterpart for the nearer
row, and let other rows follow normal new/duplicate/conflict handling.
Preserve the native seven-day and amount-only three-day windows, issuer
account scoping, changed-amount own-ID conflicts, exact duplicates, and
882's existing distinct-reference/deposit controls. Do not merely suppress
one row based on input order or downgrade all shared IDs to amount-only
matching. No dependency or API change indicated.

Caller scope: `answer` calls `_transfer_side` for classification; lazy `paired`
uses `_assign_counterparts`, which calls it for reservations too. The direct
native branch and native reservation pass must agree. CSV producer/consumer
and human/JSON flows were exercised. Python importers and FITID/custom native

**Resolved 2026-10-23** — fixed: import's whole-batch transfer reservations now govern a shared-reference match too. In `cli/src/bea_engine/importing.py`, rows sharing a recorded transfer's native reference compete for it in `_assign_counterparts` — the row that posts to the transfer's own source account first, then the nearer date, then the earlier row — and the preview offers the transfer (`_transfer_side(..., owns=...)`) only to the row the batch paired it with. A birthday gift that reuses the transfer's reference is therefore `new` instead of a second candidate for the same transfer, `--duplicates skip` no longer drops it (Savings 200, gift income −100), in both row orders; a gift with its own reference was never affected. Regression tests in `cli/tests/test_import_transfer_history_reused_reference.py` fail without the fix. Full suite green apart from one run of Beancount's randomized `bean-example` generator, which passes alone. Shipped in this commit (`cli`).
