# Commits list silently defaults limit=-1/page=0 instead of BAD_USER_INPUT

**Severity:** low. **Journey:** resources. **Owner:** backend-v2. Found by the MCP QA auth sweep on 2026-10-03 against production; live at repo HEAD `75819075`. No live board dupe.

Target: `https://beancount.io`, `POST /api-gateway/mcp` (production), observed 2026-10-03.
serverInfo `{"name":"beancount-mcp","version":"1.0.0"}`, protocolVersion `2025-11-25`.
Credential: `bcio_` API key (server kind `apikey`), scopes `ledger.read ledger.write ledger.admin`, ledger pin none (unpinned), no expiry. Value never recorded.
Helper: `node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file muse.env` from repo root.

## Repro (synthetic coords `qa-owner/qa-book`)

```sh
read beancount://qa-owner/qa-book/commits?limit=-1 (also page=0)
```

JSON-RPC sent:

```json
{"jsonrpc":"2.0","method":"resources/read","params":{"uri":"beancount://qa-owner/qa-book/commits?limit=-1"},"id":1}
```

Observed: 200 with a full list; `page=0` likewise accepted. Out-of-range paging silently takes effect as defaults.

## Control

REST shares the schema (commit-reads.ts:44-45); REST probe not in bundle (structural). Distinct from w2/m34 (unpaged completeness): this is range validation.

## Cause

- `backend-cluster/backend-v2/src/features/gitea/commits/api/commit-reads.ts`

`page`/`limit` are `z.coerce.number().int().default(...)` with no `.min()`; `-1`/`0` pass to Gitea, which applies its own defaults.

## Fix (parity: MCP+REST)

Owning package `backend-cluster/backend-v2`; the fix must land on every eligible surface (MCP+REST) in the same change. `.min(1)` (+ sane max) -> BAD_USER_INPUT.

## Evidence

`.tmp/qa-2026-10-03-auth/r6-reads-resources/q33-commits-limitneg.txt` (gitignored bundle `.tmp/qa-2026-10-03-auth/`); finding brief `.tmp/qa-2026-10-03-auth/final/resources-commits-paging-no-range-check.md`.

---

**Resolved 2026-10-03** — the commits list now refuses a `page` or `limit` that is not a positive integer as `BAD_USER_INPUT` on REST (400), the MCP resource (`-32602`) and GraphQL, before any upstream call, instead of passing it on and returning a default first page. The v1 OpenAPI document publishes `minimum: 1` for both. Shipped in `fb293d4e` (`backend-cluster/backend-v2`).

No maximum was added, though the note suggested one: clients already choose their own `limit`, the upstream caps page size itself, and a new ceiling could break a working caller for no finding. A regression test reads the list with `limit=-1`, `limit=0` and `page=0` through HTTP REST, GraphQL execution and an MCP client; it fails with the fix reverted. Not re-run against the hosted endpoint: the fix reaches it with the next deploy.
