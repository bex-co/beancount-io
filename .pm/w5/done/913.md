# Warn before a native import closes an account that still holds money

**Minor · cli · 35–55m · A1.** A Python importer's close row is shown ready
and applied without any warning while the account still holds 100 USD.
Later transactions cannot move that balance out after the close date. The
direct `add close` command already explains and refuses this situation;
native imports need the remaining balance made visible too. No product fix
implemented.

Real CLI QA 2026-10-21, checkout `47e6713bc` (`cli` unchanged from the
`29562700d` reproduction), `bea 0.3.1`, Darwin 25.5.0 arm64, frontend Python
3.13.3, existing managed Python 3.12 engine with Beangulp. Two pristine JSON
journeys and two fresh human-output journeys, separate bounded processes,
closed stdin/no TTY, isolated absolute configuration/cache paths, updater
disabled, no inherited BEA_FILE/BEA_TOKEN.

Create `/absolute/qa/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Equity:Opening USD
2024-01-02 * "Fund"
  Assets:Cash 100 USD
  Equity:Opening -100 USD
```

Create `bank.txt` with synthetic text and this `importers.py`:

```python
from beancount.parser import parser

class Imp:
    def identify(self, file):
        return str(file).endswith(".txt")
    def account(self, file):
        return "Assets:Cash"
    def extract(self, file, existing_entries=None):
        entries, errors, _ = parser.parse_string(
            "2024-02-01 close Assets:Cash\n"
        )
        assert not errors, errors
        return entries

CONFIG = [Imp()]
```

```sh
bea --json -f /absolute/qa/main.bean add close --date 2024-02-01 -a Assets:Cash
bea --json -f /absolute/qa/main.bean import /absolute/qa/bank.txt --config /absolute/qa/importers.py
bea --json -f /absolute/qa/main.bean import /absolute/qa/bank.txt --config /absolute/qa/importers.py --apply
bea --json -f /absolute/qa/main.bean query "SELECT account, sum(number) GROUP BY account ORDER BY account"
bea --json -f /absolute/qa/main.bean list close
bea --json -f /absolute/qa/main.bean check
bea --json -f /absolute/qa/main.bean add transaction Drain --date 2024-02-02 -p 'Assets:Cash -100 USD' -p 'Equity:Opening 100 USD'
```

Actual, twice: direct close exits **1**, names the remaining `100 USD`, and
writes nothing. Import preview exits **0**, `ready: 1`, `invalid: 0`, row
status `new`, and `validation_warnings: []`. Apply exits **0**, writes **1**
close and still has no warnings. BQL retains Cash `100` and Equity `-100`,
`list close` shows February 1, and `check` exits 0. The later drain is
refused as a posting to an inactive account, leaving the file unchanged.
Human preview/apply twice show `1 ready` / `Wrote 1 entry` and the close diff,
with no remaining-balance explanation. Preview never writes the ledger.

Controls, twice each: an empty account closes successfully; a proposed
same-day `Cash -100 USD / Equity +100 USD` transaction plus the close writes
both and leaves Cash zero. Moving that drain to February 2 makes the import
invalid and apply exits 1 without writing. With `check_drained`, the funded
close is already invalid and apply likewise refuses unchanged. These are
native semantics, not an invalid fixture or a missing optional dependency.

Cause: `cli/src/bea_engine/importing.py:692–723` treats a Close as an ordinary
non-transaction directive and checks account existence/activity. The only
special accounting guard there is for an imported Balance at 714–720.
Whole-candidate validation at 791–808 uses native Beancount, which permits a
funded close without `check_drained`. The explicit end-of-close-date balance
check in `cli/src/bea_engine/ledger/adding.py:324–350` is reached only by
`add close`, so it cannot contribute an import warning. Caller/history
searches found no native-import close balance check.

Fix scope: keep the native import operation compatible and add a clear
**nonblocking warning** for a newly included close whose account retains a
balance after the complete proposed batch is booked. Name the account,
close date and remaining amounts, and advise moving the money on or before
that date or reviewing the close. Carry it in preview and successful apply
JSON `validation_warnings` and human output. Judge the complete candidate,
so a same-day drain in the same import does not produce a false warning;
do not warn just because a parent has independently open children. Reuse
the owning CLI balance collection where appropriate. This note does not add
an import override flag or change hosted API acceptance.

The close is still written; an empty account and a same-day drain in the same import stay quiet, the late-drain and `check_drained` refusals are unchanged, and a preview leaves the bytes alone. `cli/tests/test_import_funded_close_warning.py` fails for the two warning cases without the fix; shipped in the commit that moves this note (`cli`). Human rendering reuses the warning field and was not rerun separately.

**Resolved 2026-10-23** — the funded-close advisory now reads every close in the loaded candidate ledger rather than only the imported `close` rows, and skips accounts the ledger had already closed before the import. A parent close that `close_tree` carries to a funded child or grandchild now warns for that descendant in JSON `validation_warnings` and in human preview and apply, naming the account, the close date and the remaining units (`Assets:Bank:Checking is closed on 2024-02-01 while it still holds 100.00 USD; …`). The parent close is still written exactly as imported; without `close_tree` the funded child stays open and quiet; a child closed earlier stays quiet; the explicit funded close, empty-account and same-day-drain controls are unchanged, and no new refusal or override flow was added. `cli/tests/test_import_funded_close_warning.py` adds child/grandchild preview/apply cases (all four fail without the fix) plus apply-bytes, no-plugin and already-closed controls.
