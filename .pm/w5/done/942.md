# `importStagedBankTransactions` reports a write with no `wrote` file and no `entryHashes`

**Trivial · backend-v2 · 15–20m · A1.** Found 2026-10-21 in [w5/m5/t004](./blocked/m5/README.md).

A successful import without `filename` answered `addedCount: 1` with `wrote: []` and `entryHashes: []`. The agent had to run a separate query to confirm and locate the entry. Other MCP write tools report the file and the hashes they wrote.

Cause: `submitTransactions` (`src/features/ai-agent/tools/bank-import-tool.ts`) sets `wrote` only when `filename` was passed, and always returns `entryHashes: []`. The default target is the ledger's root file.

Fix: report the file the entries actually landed in, taken from the write's result rather than assumed. Return the new entries' hashes as the other write tools do.

Acceptance: a default-target import reports its file and one hash per entry, and a test pins it.


---

**Resolved 2026-10-22** — fixed: `PlaidSyncService.submitTransactionsToLedger` (`backend-cluster/backend-v2/src/features/plaid/service/plaid-sync-service.ts`) now returns the `entry_hashes` the ledger's bulk write reports and the file the entries landed in (the requested `filename`, else the bulk endpoint's documented default `main.bean`, since its response carries hashes but not a path), and `importStagedBankTransactions` (`ai-agent/tools/bank-import-tool.ts`) reports them as `wrote` and `entryHashes` like the other MCP write tools instead of `[]`; a dry run still reports none. REST receives the same two extra fields in its open result; the GraphQL `PlaidSubmitResult` type is unchanged (it already omits the preview fields). Regression tests in `plaid-sync-service.test.ts` and `bank-import.test.ts` fail without the fix; backend typecheck, eslint, knip and the full jest suite are green. Shipped in this commit (`backend-v2`).
