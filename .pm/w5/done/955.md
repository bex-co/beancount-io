# Count existing same-day assertions before treating a pad as staged

**Major · cli · 30–45m · A1.** A pad already used by a USD assertion is
treated as still staged when a new EUR assertion has that same date. Both
ordinary `add balance` and import accept an incorrect amount and silently
create a backdated EUR adjustment. Moving only the new assertion to the
next day correctly refuses it. Follow-up to completed
[796](./done/796.md) and [871](./done/871.md). No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `b734b3d83` (CLI unchanged from `b7fc4fd77`),
checkout `bea 0.3.1`, macOS 26.5.1 arm64, frontend Python 3.13.3, existing
managed Python 3.12.10 / Beancount 3.2.3. Fresh bounded processes, closed
stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier
disabled, inherited `BEA_FILE`/`BEA_TOKEN` removed. Synthetic local files.

Create a disposable `/abs/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD,EUR
2024-01-01 open Equity:Opening USD,EUR
2024-01-01 * "Capital"
  Assets:Cash 100.00 USD
  Assets:Cash 25.00 EUR
  Equity:Opening -100.00 USD
  Equity:Opening -25.00 EUR
2024-01-02 balance Assets:Cash 25.00 EUR
2024-01-02 pad Assets:Cash Equity:Opening
2024-01-03 balance Assets:Cash 200.00 USD
```

The initial book is valid. Its pad has already inserted 100 USD for the
written January 3 USD assertion. Cash holds **200 USD / 25 EUR**; there is
no EUR padding. The January 2 EUR assertion precedes that day's padding
transactions under native start-of-day balance semantics.

From `/abs/books`, run:

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean query 'SELECT currency,sum(number) WHERE account="Assets:Cash" GROUP BY currency ORDER BY currency'
bea --json -f /abs/books/main.bean add balance --date 2024-01-03 --account Assets:Cash --amount '26.00 EUR'
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean query 'SELECT currency,sum(number) WHERE account="Assets:Cash" GROUP BY currency ORDER BY currency'
bea --json -f /abs/books/main.bean query 'SELECT date,flag,account,number WHERE flag="P" AND currency="EUR" ORDER BY account'
bea --json -f /abs/books/main.bean add balance --date 2024-01-03 --account Assets:Cash --amount '26.00 EUR'
bea --json -f /abs/books/main.bean add balance --date 2024-01-03 --account Assets:Cash --amount '25.00 EUR'
```

Actual exits: **0, 0, 0, 0, 0, 0, 0, 4**. The first add returns
`written: 1`, `pad: null`, `warnings: []`, although the previously held
25 EUR has become **26 EUR**. Native padding now adds **+1 EUR** to Cash
and **−1 EUR** to Equity on **January 2**. Only the new assertion is
appended to the source; the adjustment comes from the existing pad. Check
still passes. Repeating skips as a duplicate; trying the true 25 EUR amount
afterward conflicts with the incorrect assertion already written. Human
add likewise exits 0 with `Added 1 balance` and empty stderr.

Expected: an ordinary assertion remains strict unless padding is explicitly
requested or it completes a genuinely unused staged pad, as USAGE's
`add balance` contract and 796/871 require. An assertion already present on
the new assertion's date is evidence that this pad has been used. Refuse
the unrequested 1 EUR fill before writing and keep Cash at 25 EUR.

The other entry path reproduces with just **one imported balance**, without
batch reordering or a new cash transaction. In another fresh directory,
restore the initial `main.bean` above. Put `Synthetic statement` in
`/abs/books/bank.statement` and create `/abs/books/importer.py`:

```python
from datetime import date
from decimal import Decimal
from beancount.core import data, amount

class Statement:
    def identify(self, file):
        return str(file).endswith(".statement")
    def account(self, file):
        return "Assets:Cash"
    def extract(self, file, existing=None):
        return [data.Balance(
            data.new_metadata(file, 1), date(2024, 1, 3), "Assets:Cash",
            amount.Amount(Decimal("26.00"), "EUR"), None, None,
        )]

CONFIG = [Statement()]
```

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean query 'SELECT currency,sum(number) WHERE account="Assets:Cash" GROUP BY currency ORDER BY currency'
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.statement --config /abs/books/importer.py
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.statement --config /abs/books/importer.py --apply
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean query 'SELECT currency,sum(number) WHERE account="Assets:Cash" GROUP BY currency ORDER BY currency'
bea --json -f /abs/books/main.bean query 'SELECT date,flag,account,number WHERE flag="P" AND currency="EUR" ORDER BY account'
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.statement --config /abs/books/importer.py --apply
```

All exit **0**. Preview leaves bytes unchanged but reports `new` / ready 1;
apply writes 1 and produces the same January 2 EUR adjustment. The unchanged
repeat writes 0. The row should instead be blocked and apply should refuse
at exit 4, preserving the ledger as in 871's later-day control.

Cause: `_refuse_used_pad_fill` in
`cli/src/bea_engine/ledger/adding.py:737–743` and
`_padded_balance_reason` in `cli/src/bea_engine/importing.py:1956–1959`
both look for a balance with `cover.date < entry.date < date`. Existing
USD January 3 is excluded when `date` is January 3, so both take their
staged-pad exception. A January 4 target includes that USD assertion and
correctly refuses. The source balance and its context are already loaded;
there is no missing incoming transaction here.

Fix: count eligible assertions already present on the target date when
deciding whether the covering pad is still staged. Keep start-of-day
holdings arithmetic and the rule that a pad precedes its assertion. Keep
the two guard paths consistent; review the related used-pad advice
predicate in `adding.py:549–552` as well. `_balance` calls the first guard
at :443; import calls the second at :718. The advice branch is source-traced
scope, without a separate source-mismatch reproduction. CLI only; no
dependency or API change needed.

Controls: 32 fresh cases, each combination twice: direct-account versus
parent-account holdings, add versus import, same versus next date, and
26 EUR versus the true 25 EUR. Only the same-day wrong amount is silently
padded. Later-day gaps refuse (add 1 / import apply 4), correct values write
without EUR adjustments, and every resulting book passes native check.
Parent totals are correctly calculated; the initial longer journey's

Ten further fresh controls, five modes twice each: human output repeats the silent

an actually unused pad staged with `add pad --allow-errors` still completes

**Resolved 2026-10-22** — fixed: a pad counts as already used when an assertion on the account sits on the new assertion's own date in another currency, not only on days strictly between (`pad_already_used` in `cli/src/bea_engine/ledger/adding.py`, shared by `add balance`'s used-pad refusal and import's `_padded_balance_reason`). A wrong 26 EUR assertion dated with the USD assertion that consumed the pad is refused before writing (and blocked in import, apply exit 4, ledger bytes unchanged), as the next day already was; the true 25 EUR assertion still writes, a genuinely staged pad still completes silently, and a same-day assertion in the new assertion's own currency stays the duplicate/conflict case. Regression tests in `cli/tests/test_pad_same_day_assertion_used.py` fail without the fix. Shipped in this commit (`cli`).
