# Do not treat calculated transaction copies as written entries

**Major · cli · 45–60m · A1.** A plugin-calculated transaction copy keeps
the source payee/narration but changes its amounts. `list` marks both rows
as written and `--on-disk` keeps both, although the file declares only one.
A limited listing can therefore show the calculated 20 USD movement instead
of the written 10 USD movement. When the copy inherits a bank reference,
import also accepts its changed amount as an exact duplicate at exit 0,
although the file records a different source amount that should conflict.
No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `309340740`, checkout `bea 0.3.1`, macOS
26.5.1 arm64, frontend Python 3.13.3, existing managed Python 3.12.10.
Separate subprocesses, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`. The local calculation plugin below is synthetic;
it runs through the normal native loader, with no mocked CLI result.

Create disposable `/abs/books/qa_derive.py`:

```python
from decimal import Decimal
from beancount.core.data import Transaction

__plugins__ = ("derive",)

def derive(entries, options, config=None):
    out = []
    for entry in entries:
        out.append(entry)
        if isinstance(entry, Transaction) and entry.narration == "Source row":
            postings = [
                p._replace(units=p.units._replace(number=p.units.number * Decimal(2)))
                for p in entry.postings
            ]
            out.append(entry._replace(meta=entry.meta.copy(), postings=postings))
    return out, []
```

Actual: all seven exit 0, preserving the ledger, plugin and CSV bytes. The loaded
ledger correctly has Cash -30 USD / Food 30 USD: the declared 10 and the
calculated 20 both participate in bookkeeping.

The full listing returns amounts `-10.00` and `-20.00` with neither row
carrying `generated: true`. `--on-disk` incorrectly returns both too. Its
newest/limit-1 form returns only `-20.00`, still marked as written, and
`truncated: true`. The file declares only the 10 USD transaction.

Import preview calls the 20 USD correction `duplicate`, and apply exits 0
with `written: 0`. The unchanged bank reference is judged against the
calculated copy's 20 rather than the written source's 10. The requested
correction is therefore reported already recorded without changing the file.

Expected: retain both entries in the full loaded listing, mark only the
calculated 20 as generated, and return only the written 10 under `--on-disk`.
The limited answer should be that same 10 with `truncated: false`. This is
the documented distinction between loaded entries and what the file declares,
and completed w5/401 explicitly requires at most one written transaction for
one source declaration. The changed native-bank-ID amount must be a conflict
at exit 4 with unchanged files; the original 10 USD export must still skip.

Eight further fresh bank-ID ledgers, twice across same-header, changed-header,
changed-flag and reversed-order copies, exercise three preview/apply pairs

Public working control: in a pristine copy, add `narration="Derived row"`
to the calculated transaction's `_replace(...)` call. Its amounts and bank
reference stay the same. The copy is then marked generated, `--on-disk`
returns the written 10 only, and the 20 USD correction conflicts at exit 4.

Cause: `cli/src/bea_engine/ledger/reader.py:shared_locations` (:143–166)
correctly identifies the shared filename/line/type/date. Its transaction
branch in `_declares` (:190–209) then compares **only payee and narration**
with the cached plugin-free source entry. It ignores the different posting
amounts and even a different flag. Both copies therefore return true, so
`entry_generated` (:214–272) calls both written. `listing.answer` (:110)
does not drop either before its limit, and `list_transactions` uses the same
test for each row's generated mark (:342).

Import builds `on_disk` and its native-ID index from that same classification
(`cli/src/bea_engine/importing.py:425–445`). Both entries inherit `bank_id`,
so `_under_id` (:1730–1751) finds the calculated 20 as an agreeing amount
and `_same_row` accepts it as the native-ID source row. Excluding that copy
when its narration changes leaves the real 10 in the index and restores
the correct conflict. This is the same false written-entry classification,
not a request to change native-ID conflict semantics.

Fix: distinguish the written transaction using compatible file-stated facts,
and allocate at most one written representative per source declaration.
Keep the correct original regardless of plugin return order; do not merely
keep the first matching header, deduplicate separate source lines, or mark
every transformed entry generated. Preserve booked/inferred posting support,
source-context parsing and the existing changed-header/date controls.
Default listing, `--on-disk`, truncation and details must agree.
Calculated copies must also stay out of authored native-ID evidence, so the
20 USD correction conflicts and the real 10 USD repeat still skips.

Shared-caller search also finds import's on-disk and declared-content indexes
(`cli/src/bea_engine/importing.py:425–430`), all directive readers, and
price/balance provenance guards. Runtime coverage is transaction listing and
native-ID CSV preview/apply; other import matching and directive types are
source-traced only. Preserve stable-ID/header-normalization controls from w5/866 and
the source-fact requirements of open w5/881 when changing the shared helper.
No dependency or backend/API change needed.
