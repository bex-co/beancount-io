# The unknown-account hint can suggest a name that looks identical to the one it rejected

**Severity:** minor. **Estimate:** 40–60 minutes. **Owner:** cli. **A2:** a
newcomer is told "unknown account 'Expenses:Café'. Did you mean
Expenses:Café?" and has no way to see the difference, because there is nothing
visible to see.

Found 2026-09-16 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME`. Synthetic local fixtures only.

## Repro

The ledger opens the account in Unicode NFD (decomposed: `e` + U+0301), which
is what macOS filesystem paths and some input methods produce. The posting is
written in NFC (precomposed U+00E9), which is what most editors produce.

```sh
python3 - <<'PY'
import unicodedata
nfd = unicodedata.normalize("NFD", "Expenses:Café")
open("nfd.bean", "w").write(f'''option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open {nfd} USD

2026-01-05 * "Seed" "x"
  {nfd}   1.00 USD
  Assets:Cash  -1.00 USD
''')
PY

bea --file nfd.bean check          # exit 0 — the ledger is valid
NFC=$(python3 -c "import unicodedata;print(unicodedata.normalize('NFC','Expenses:Café'))")
bea --file nfd.bean add transaction "NFC attempt" --date 2026-02-01 \
    -p "$NFC 2.00 USD" -p "Assets:Cash -2.00 USD"
```

```text
Error: The change would leave the ledger invalid; nothing was written.
  nfd.bean:9: Invalid reference to unknown account 'Expenses:Café' Did you
  mean Expenses:Café? To create it, use bea add open --account 'Expenses:Café'
  --date YYYY-MM-DD.
```

The rejected name, the suggestion, and the `bea add open` command in the same
sentence are three different byte strings that render identically. Following the
hint verbatim reproduces the error; following the `add open` advice creates a
second account that also looks identical to the first.

The account filter misses the same way, silently:

```sh
bea --file nfd.bean list transaction --account "$NFC"
# No transactions found.
```

## Expected / actual

`cli/docs/USAGE.md` (Adding directives) says "Account typos include suggested
matches" and "Unicode letters and configured root names are supported". A
suggestion exists to show the user what to type instead, so a suggestion that is
visually identical to the input fails at its only job.

Expected: when the only difference between the input and a candidate is Unicode
normalization, say so — for example "differs only in Unicode normalization
(NFD vs NFC); the ledger spells it with a combining accent" — or normalize
account names to NFC at the input boundary so the two forms match. A silent
`--account` miss should likewise be distinguishable from a genuinely absent
account.

Actual: the hint is emitted with no indication that the difference is invisible,
and the filter returns an empty result with no hint at all.

## Root cause

`cli/src/bea_engine/ledger/write.py:358-363` extracts the rejected name out of
upstream's message and appends bea's own suggestion:

```python
account = message.split("unknown account '", 1)[1].split("'", 1)[0]
matches = difflib.get_close_matches(account, accounts, n=3, cutoff=0.6)
if matches:
    message += f" Did you mean {', '.join(matches)}?"
```

`difflib.get_close_matches` compares code-point sequences, so the NFC and NFD
spellings of the same name score well above the `0.6` cutoff and the suggestion
is produced — correctly, by its own measure, and uselessly to a reader. The
"unknown account" verdict itself is upstream's; the suggestion is bea's.

`cli/src/bea_engine/query.py:282` builds the same kind of hint for the query
path and would behave the same way.

A repository-wide search finds no Unicode normalization anywhere in `src/cli/`
or `src/bea_engine/` — the only `normalize` hits are `Decimal.normalize()` and
`normalize_entry_strings`, which flattens CR/LF in text fields. Account names
are compared as raw strings throughout, including the `--account` substring
filter.

## Fix

Detect the case rather than guessing at it: when a candidate and the rejected
name are equal under `unicodedata.normalize("NFC", …)` but not as written, say
that explicitly instead of printing two identical-looking names, and quote the
form the ledger actually uses. Consider normalizing account names to NFC when
they enter the CLI (`--posting`, `--account`, bulk JSON, importer output) so
the forms match in the first place; that is the larger change and needs a
decision about whether it also applies to what gets written to the file.
Apply the same treatment to the query-side hint at `query.py:282`. Add
coverage with an NFD ledger and an NFC input, asserting the message names the
normalization difference and that the two forms are not offered as if distinct.

## Blast radius and adjacent states

Affects account-name comparison generally: the `add` suggestion, the query
hint, and the `--account` substring filter on `list`, `balance` and `report`.
The ledger itself is never corrupted — the write is refused and the file is left
byte-identical, which is correct. ASCII account names, and NFC-vs-NFC or
NFD-vs-NFD comparisons, are unaffected and behave correctly; the ordinary typo
suggestion still works (`Expenses:Fudd` → "Did you mean Expenses:Food,
Expenses:Rent?"). Not exercised: normalization inside payees, narrations, tags,
links or metadata keys, and whether `document` paths resolved from a macOS
filesystem introduce NFD names through `bea import`.

## How likely is this in practice

Narrow but real, and macOS-specific in origin: HFS+/APFS return NFD path
components, so an account name copied out of a file path, or produced by an
importer deriving names from paths, arrives decomposed while anything typed in a
normal editor arrives composed. It is filed as minor for that reason — the cost
is a confusing diagnostic and a silent filter miss, not lost data.

---

**Resolved 2026-09-16** — Both halves fixed. The write path now detects an open account that differs from the rejected name only in Unicode normalization and explains that, quoting both spellings as escapes and naming each form (NFD/NFC); it replaces the identical-looking "Did you mean" and the `bea add open` advice rather than joining them, since the account already exists and following that advice would open a second indistinguishable one. Genuine typos still get the ordinary close match, and genuinely absent accounts still get the `add open` recipe. The silent `--account` miss was the same raw comparison: `list` (all seven filtered types), `balance`, and the listing readers now compare through a shared `fold_account` that normalizes to NFC and case folds — NFC rather than NFD because these keys are matched as substrings and NFC keeps an accented letter one code point, so a substring boundary falls where a reader sees one. Shipped in `99ab28b7` (`cli`).

Two stale details in the note: the query-side hint it cites (`query.py:282`, now `:340`) is `_column_suggestions` for BQL **column** names, not accounts, and BQL column names are ASCII identifiers, so there was nothing to fix there — the account suggestion exists only in `write.py`. And the engine boundary forbids sharing one helper, so `fold_account` is a twin pair (`bea_engine.ledger.text` / `cli.utils`) following the `single_line` precedent already in those two modules, with a test pinning both copies to the same answers.

Deliberately not done: writes stay exact — `bea add` refuses rather than silently rewriting the name typed into the file, so the note's larger "normalize at the input boundary" change, which needs a decision about what gets written, is still open. `bea report --account` is untouched because it is a regular expression handed to Fava and normalizing a pattern can change what it matches.

Coverage: `cli/tests/test_account_normalization.py` drives the note's own repro end to end through a real subprocess — the NFD ledger, the NFC input, the diagnostic's exact escaped forms, the absence of both misleading lines, the file left byte-identical, all three filter surfaces matching, plus guards that a real typo still gets a suggestion, an absent account still gets the open recipe, a non-matching filter still matches nothing, and the two `fold_account` copies agree. Reverting the fix fails 5 of the 10. `make check-all` passes (828 tests).

Observed but out of scope: table column padding counts code points, so an NFD name renders one column narrow in `bea list open`. Cosmetic, pre-existing, and unrelated to the comparison bug. Still not exercised, as the note flagged: normalization inside payees, narrations, tags, links and metadata keys, and whether `bea import` introduces NFD names from macOS document paths.
