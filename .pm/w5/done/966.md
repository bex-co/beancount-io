# Keep leap day in February's current fiscal year

**Minor · cli · 20–30m · A1.** With a February fiscal year end, relative
`fiscal_year` advances one year too early on leap day. A **clock-controlled
real CLI reproduction** for 2024-02-29 selects FY2025 and reports 100 USD
profit; absolute FY2024 and the current fiscal quarter correctly report 30.
This is selection of the wrong period, not incorrect addition within it.
No product fix implemented.

Environment: 2026-10-22 QA, clean main `6cc033e7c` (initial reproduction on
`db78aa3d7`, implicated source unchanged), checkout `bea 0.3.1`, frontend
Python 3.13.3, managed Python 3.12.10 / Beancount 3.2.3 / Beanquery 0.2.0,
macOS 26.5.1 arm64. Fresh subprocesses, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR` and `XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`.

The inspected local plugin below replaces only the existing
`fava.util.date.local_today` time provider in each helper process. It returns
the ledger entries unchanged. **The machine clock is not changed.** This
makes the leap-day branch reproducible on other dates; it is not a claim
that today's natural clock is February 29.

Create a fresh disposable fixture:

```python
from pathlib import Path
books = Path('/abs/books')
books.mkdir(parents=True, exist_ok=True)
(books / 'qa_clock.py').write_text('''from datetime import date
from fava.util import date as fiscal_dates
__plugins__ = ('clock',)
def clock(entries, options):
    fiscal_dates.local_today = lambda: date(2024, 2, 29)
    return entries, []
''')
(books / 'main.bean').write_text('''option "insert_pythonpath" "TRUE"
option "operating_currency" "USD"
plugin "qa_clock"
2020-01-01 custom "fava-option" "fiscal-year-end" "02-28"
2020-01-01 open Assets:Cash USD
2020-01-01 open Income:Salary USD
2024-02-28 * "Before leap day"
  Assets:Cash 10 USD
  Income:Salary -10 USD
2024-02-29 * "Leap day"
  Assets:Cash 20 USD
  Income:Salary -20 USD
2024-03-01 * "Next fiscal year"
  Assets:Cash 100 USD
  Income:Salary -100 USD
''')
```

All nine exit **0** with empty stderr and unchanged ledger/plugin bytes.
`check` is valid. The relative year returns **[2024-03-01, 2025-03-01)**,
which does not contain the effective today, with profit **100 USD**.
Absolute FY2024 and the explicit calendar range both return
**[2023-03-01, 2024-03-01)** and **30 USD**. The relative current quarter is
**[2023-12-01, 2024-03-01)** with 30 USD; `day` is February 29 with 20 USD.
The full-ledger BQL control has Cash 130 / Salary -130 USD.

Offsets inherit the wrong base year: `fiscal_year-1` returns the current
FY2024 and 30 USD instead of FY2023 / zero; `fiscal_year+1` returns FY2026 /
zero instead of FY2025 / 100 USD. Human output agrees with the wrong period
and profit. A working comparison changes only the clock provider to
`date(2024, 2, 28)`: relative FY matches absolute FY2024, and its previous/next
years have zero/100 USD. March 1 correctly selects FY2025.

Reproduction and scope:

- Six initial fresh clocked ledgers: two repetitions of February 28/29 and
  March 1. The leap-day relative year alone advances early; absolute years
  and current quarter remain consistent.
- Sixteen further fresh cases, twice each: leap years 2024 and 2028 reproduce
  with both `02-28` and following-year `14-28`. The latter should select
  FY2023 on 2024-02-29, but selects FY2024. All eight failing cases show the
  same offset errors, correct day/current-quarter controls and unchanged
  files. Overview, balance sheet, trial balance and the `balance Cash` alias
  directly reproduce the wrong relative period as well; human income reports
  show 100 USD.
- Non-leap 2023-02-28, March/calendar year ends (`03-31`, `12-31`) and the
  distinct non-month-end `02-27` year work. Its unsupported fiscal quarter
  remains an explained exit-2 refusal. Sixteen unwrapped native Beancount
  references omit only the clock-fixture plugin line, validate the same three
  salary entries and confirm Cash 130 USD; the original clocked books also
  pass the real CLI check.

**Cause.** `cli/src/fava/util/date.py:361–364` in `substitute` decides
`after_fye` by comparing `(today.month, today.day)` with the configured
`(month_of_year, day)`. On February 29 it treats `02-28` as already past and
increments the label. But `get_fiscal_period` (`:525–531`) explicitly treats
`02-28` as February month end across leap years and starts the next year on
March 1. The two branches disagree about which fiscal year contains leap day.
Following-year month 14 uses the same month/day comparison, then subtracts
`year_offset`, so it has the same defect.

Caller search: `parse_date` (`:420`) performs this substitution;
`TimeFilter` in `cli/src/fava/core/filters.py:394` consumes it, and the shared
`bea_engine/report.py:_load` filtering path (`:443–480`) reaches all report
kinds and balance. The other found `parse_date` consumer is Fava JSON
serialisation; relative-date writes are not claimed here. Local CLI reporting
is the verified scope; hosted implementations were not exercised.

**Fix / acceptance.** Resolve relative fiscal-year labels using the same
effective February month end as absolute fiscal periods. On leap day,
`fiscal_year` must contain that date and match FY2024 (or FY2028), while
`14-28` keeps its following-year label offset. Previous/next relative years
must match their absolute controls. Preserve February 28/March 1, non-leap
February, other month ends, `02-27`, fiscal-quarter behavior and relative range
substitution. Add meaningful clock-controlled report regressions asserting
both period bounds and monetary results, plus the controls above; run CLI
`make check-all` when implementing. Preserve vendored Fava attribution. No
dependency or backend/API change is indicated by this local cause.
