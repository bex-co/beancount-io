# `.output` to an unwritable path dumps a Python traceback into the interactive query shell

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** cli. **A1/A2:** a
user exploring a ledger in `bea query`'s shell mistypes a redirect path and gets
a stack trace through `cmd.Cmd` instead of an error line.

Found 2026-09-15 by a report-only CLI QA sweep against `main`, HEAD `10465c05`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME` and `BEA_NO_UPDATE_NOTIFIER=1`, driving the
shell over a pty. Synthetic local fixture only.

## Repro

```sh
mkdir nodir && chmod 555 nodir
bea --file main.bean query          # interactive shell, needs a terminal
```

Then at the prompt:

```text
beanquery> .output /abs/path/nodir/x.txt
```

The shell prints an unhandled traceback and returns to the prompt:

```text
  File ".../python3.12/cmd.py", line 138, in cmdloop
    stop = self.onecmd(line)
  File "cli/src/bea_engine/query.py", line 206, in onecmd
    return super().onecmd(line)
  File ".../beanquery/shell.py", line 272, in onecmd
    return func(arg)
  File "cli/src/bea_engine/query.py", line 174, in do_output
    destination = open(arg, "w", encoding="utf-8") if arg else stream
PermissionError: [Errno 13] Permission denied: '/abs/path/nodir/x.txt'

beanquery> SELECT account LIMIT 1
    account
---------------
Assets:Bank:USD
```

## Expected / actual

`cli/docs/USAGE.md:283-284` says: "In the interactive query shell, `.output
FILE` redirects results and `.output` restores the original output stream. A
failed redirection leaves that stream usable."

Half of that holds — the subsequent `SELECT` still renders, so output is not
lost. The other half does not: the failure is reported as a raw traceback
rather than a message. `--debug` was not set, and
`cli/docs/USAGE.md:88` documents `--debug` as what makes errors "include
exception tracebacks".

Expected: one line such as `Cannot write to <path>: Permission denied.` on
stderr, the output stream unchanged, and the shell continuing — matching how
every non-interactive write failure in this CLI is already phrased (`bea add`
against a read-only ledger says "Ledger file is read-only or not writable: …;
nothing was written.").

## Working controls

In the same pty session, `.output FILE` to a writable path redirects correctly,
a bare `.output` restores stdout, `.tables` lists the ten beanquery tables, and
queries render at full precision before and after the redirect. The shell also
opens correctly on a ledger with loader errors, printing them as a banner and
staying lenient because stdin is a terminal — consistent with the documented
strictness matrix.

## Root cause

`cli/src/bea_engine/query.py:168-175`, bea's own `do_output` override on
`PreciseShell`:

```python
def do_output(self, arg: str) -> None:
    """Send output to FILE or restore the original output stream."""
    # Beanquery 0.2.0 calls open(sys.stdout) on reset and closes the old
    # stream before opening its replacement. Remove this override when
    # upstream supports reset and failed redirection without losing output.
    destination = open(arg, "w", encoding="utf-8") if arg else stream
    if self.outfile is not stream:
        self.outfile.close()
    self.outfile = destination
```

The override exists precisely to survive a failed redirection — it opens the
replacement before closing the old stream, which is why output is not lost. But
`open()` is unguarded, so `OSError` propagates out of `do_output`, through
`onecmd` at `:206` and `beanquery/shell.py`'s dispatch, to `cmd.Cmd.cmdloop`,
which has no handler. This is bea-owned code, not a delegated upstream program,
so unlike `.pm/w5/004.md` there is no stream-ownership reason for the raw
output.

## Fix

Wrap the `open()` in the override in `try/except OSError` and report the failure
the way the rest of the CLI reports write failures: a single message naming the
path and the reason, written to stderr, leaving `self.outfile` untouched so the
current stream keeps working. That completes the behavior the override's own
comment claims. Add a regression driving the shell with a redirect to an
unwritable path and asserting no traceback, an error line, and that a following
query still renders.

## Blast radius and adjacent states

Affects the interactive shell's `.output` only — the non-interactive
`bea query -o FILE` path is separate and already reports write failures
correctly, preserving an existing export on failure. Other dot commands were
not systematically fuzzed; `.tables`, `.output` restore, and the quiet aliases
in `onecmd` behaved correctly. Not exercised: a redirect target that exists but
is read-only, a directory passed as the target, and Windows.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for interactive shell, `.output`,
redirect and traceback terms. `.pm/w2/done/021.md` covers `bea query` output
flags under `--json` and the `--format beancount` message, both non-interactive
and both fixed. `.pm/w5/004.md` covers `format --in-place` crashing through an
upstream delegation; this is bea's own shell override and a different file.
Nothing on the board covers the interactive shell. `git log` on
`cli/src/bea_engine/query.py` shows the override arriving with the engine split
and no later hardening of its `open()`.

## Evidence and unverified areas

Driven through a pty helper under `cli/tmp/qa-20260915/run2/`, which recorded

Directory permissions were restored after the run. Synthetic fixture only; no

---

**Resolved 2026-09-16** — The interactive shell now reports failed output opens with the path and reason, preserves its current output destination, and continues without a traceback. Shipped in `2598252d` (`cli`). Real PTY regressions cover missing parents, directory targets, and read-only files/directories, both from terminal output and an existing file redirection. Reverting the handler fails the regression. All four PTY cases and `make check-all` (741 tests) pass.
