# Check imported balances against every dated row in the batch

**Major · cli · 45–60m · A1.** A newest-first Python importer bypasses
the used-pad guard: a stale **200 EUR** statement is accepted, and the old
pad silently inserts **−50 EUR** before a real 50 EUR receipt, cancelling
its effect on the account. The correct **250 EUR** statement is instead
blocked. Returning the same entries oldest-first restores both expected
outcomes. No product fix implemented.

26.5.1 arm64, frontend Python 3.13.3, managed Python 3.12.10 / Beancount

isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled,
no inherited `BEA_FILE`/`BEA_TOKEN`. Synthetic local files only.

`/abs/books/importer.py` explicitly returns newest-first entries, as bank
exports commonly do. The native parser itself sorts, so the final sort
here is necessary to reproduce the importer's actual returned order:

```python
from pathlib import Path
from beancount.parser import parser
from beancount.core.data import Transaction, Balance

NEWEST_FIRST = True

class Rows:
    def identify(self, file):
        return str(file).endswith(".bank")
    def account(self, file):
        return "Assets:Checking"
    def extract(self, file, existing=None):
        entries, errors, options = parser.parse_string(Path(str(file)).read_text())
        assert not errors, errors
        return sorted(
            [e for e in entries if isinstance(e, (Transaction, Balance))],
            key=lambda e: e.date, reverse=NEWEST_FIRST,
        )

CONFIG = [Rows()]
```

Actual: preview exits **0**, both rows are `new`, `ready: 2`, with no
validation errors. Apply exits **0/written 2**. A fresh check succeeds,
but the loaded ledger now has a second generated `P` transaction dated
**2024-01-09**: Checking **−50.00 EUR**, Opening **+50.00 EUR**. Checking
ends at **200 EUR**, despite the real receipt taking its known 200 EUR to
**250 EUR**. Opening equity changes from −200 to **−150 EUR**. The
historical USD assertion and its 100 USD pad are unaffected.

The imported balance must be a strict assertion, not authorization for a
new adjustment from a pad already used by an earlier assertion. USAGE's
Adding directives section says ordinary balances remain strict assertions;
completed [871](./done/871.md) explicitly applies that guard to imports.
Without the pad (replace the original 1000 USD opening with 1100 USD and
remove its `pad` line), this 200 EUR assertion fails natively, while
250 EUR succeeds. The independent arithmetic is 200 + 50 = 250 EUR.

Repeat from pristine books with `250.00 EUR` in the source assertion:
newest-first preview instead marks the correct balance `blocked`, claims
the account holds only 200 EUR and the pad would insert 50 EUR, then
apply exits **4** with every ledger byte preserved. With
`NEWEST_FIRST = False`, the correct 250 EUR pair writes **2** and needs no
EUR pad; the stale 200 EUR pair is correctly blocked at exit **4**. All
four combinations reproduced twice in fresh books.

Cause: `cli/src/bea_engine/importing.py:718` calls
`_padded_balance_reason(entry, [*existing, *included], options)` while
walking the importer's returned list. `included` contains only rows
visited earlier in that list, not every transaction dated before the
assertion. The helper at 1936–1965 books this incomplete context. A
newest-first balance therefore sees 200 EUR: equality returns early for
the stale assertion, while the correct one is blocked. Full candidate
validation cannot catch the first mistake because the upstream pad
silently balances it. Pad-blocked rows are deliberately excluded from
the open-account second look, so the false block persists too.

Fix the guard's monetary context to include the whole proposed batch at
each balance's native start-of-day boundary, while retaining earlier
assertion/pad consumption, duplicate and blocked-row semantics. Rechecking
the settled candidate must not use its generated pad adjustment as proof
that a source assertion agreed. Do not merely sort unrelated same-day
transactions or relax the used-pad guard. The helper's only production
caller is this import loop; the related single-add guard is in
`ledger/adding.py`. CSV imports return transactions, so the observed
balance path is Python importers. No API surface change is indicated.

Adjacent controls: a receipt on the assertion day or the following day
does **not** fund its start-of-day balance. In both cases 200 EUR remains
a valid assertion and 250 EUR is correctly blocked, in two fresh repeats
each, with no EUR pad generated on success. Preserve those date controls,
the oldest-first outcomes, exact repeat behavior, and byte-preserving
refusals when repairing newest-first batches.

Pin preview statuses, apply exits, final balances and generated pad amounts

**Resolved 2026-10-22** — fixed: import's used-pad guard (`cli/src/bea_engine/importing.py`) now runs after every row is classified, judging each included balance against the ledger plus the whole proposed batch instead of only the rows visited before it, and removes a blocked assertion from the write set. A newest-first Python importer therefore sees the receipt its assertion follows: the correct 250 EUR statement is written (2 rows, no EUR pad generated) and the stale 200 EUR one is blocked (exit 4, ledger bytes unchanged), matching the oldest-first outcomes. Regression tests in `cli/tests/test_import_pad_guard_newest_first.py` fail without the fix. Shipped in this commit (`cli`).
