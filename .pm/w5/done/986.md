# Reject day 366 in a non-leap CSV year

**Minor · cli · 30–45m · A1 · worker1.** Real local CLI QA, 2026-10-22,
checkout `bea 0.3.1` at `07dfc6c96dcba07275a829f6ec285a262059136b`,
macOS 26.5.1 arm64, frontend Python 3.13.3 and managed Python 3.12.10 /
Beancount 3.2.3. No product fix implemented.

With `--date-format '%Y-%j'`, CSV `2023-366` previews and writes as
`2024-01-01`; `%y-%j` does the same for `23-366`. The named year has only
365 days. Preview exits 0 with one ready row, no invalid rows or date warning;
apply exits 0 and writes it. Native check also exits 0 because the new date
is a valid day in the next year. Repeating the import skips the now-misdated
entry. An unattended import therefore records the expense in 2024 instead of
refusing the bad source date.

Expected: reject a day-of-year that does not exist in its explicitly supplied
calendar year, before any ledger write, naming the row, column and format as
other bad dates do. Do not guess a replacement day. IMPORTING promises
row/column errors for bad dates. Python's [date-format documentation](https://docs.python.org/3.12/library/datetime.html#strftime-and-strptime-format-codes)
defines `%j` as the day of the year, and allows an omitted leading zero;
retain valid inputs such as `2023-1`.

Replace `/abs/ordinal-date-case` with a fresh absolute directory, then run the
standalone reproducer. Repeat in a second fresh directory. Other `mode` values
exercise the two-digit year and nearby working controls. Each real command
has closed stdin/no TTY, isolated config/cache, a 25-second bound, separate
streams, file hashes and the CSV-preservation result.

```python
import datetime, hashlib, json, os, pathlib, subprocess
case = pathlib.Path('/abs/ordinal-date-case')
mode = 'overflow'
cases = {
    'overflow': ('2023-366', '%Y-%j'),
    'short-year': ('23-366', '%y-%j'),
    'leap': ('2024-366', '%Y-%j'),
    'last-day': ('2023-365', '%Y-%j'),
    'unpadded': ('2023-1', '%Y-%j'),
    'iso-crossyear': ('2020-W53-5', '%G-W%V-%u'),
}
value, date_format = cases[mode]
case.mkdir(parents=True)
ledger = case / 'main.bean'
base = '''option "operating_currency" "USD"
2020-01-01 open Assets:Cash USD
2020-01-01 open Expenses:Food USD
2020-01-01 open Equity:Opening USD
2020-01-01 * "Capital"
  Assets:Cash 100.00 USD
  Equity:Opening -100.00 USD
'''
ledger.write_text(base, encoding='utf-8')
(case / 'pristine.bean').write_text(base, encoding='utf-8')
csv = case / 'bank.csv'
csv.write_text('Date,Description,Amount\n' + value + ',Coffee,-7.75\n', encoding='utf-8')
original_csv = csv.read_bytes()
env = os.environ.copy()
for key in ('BEA_FILE', 'BEA_TOKEN', 'BEANCOUNT_LOAD_CACHE_FILENAME'):
    env.pop(key, None)
env.update(BEA_CONFIG_DIR=str(case / 'config'),
           XDG_CACHE_HOME=str(case / 'cache'), BEA_NO_UPDATE_NOTIFIER='1')
print(json.dumps(dict(tag='calendar', input=value, date_format=date_format,
                     days_in_2023=(datetime.date(2024, 1, 1)-datetime.date(2023, 1, 1)).days)),
      flush=True)
def run(tag, args):
    before = ledger.read_bytes()
    cmd = ['bea', '--json', '--no-input', '--file', str(ledger), *map(str, args)]
    result = subprocess.run(cmd, cwd=case, env=env, stdin=subprocess.DEVNULL,
                            capture_output=True, text=True, timeout=25)
    print(json.dumps(dict(tag=tag, args=cmd, exit=result.returncode,
                          stdout=result.stdout, stderr=result.stderr,
                          ledger_preserved=ledger.read_bytes()==before,
                          csv_preserved=csv.read_bytes()==original_csv,
                          ledger_sha256=hashlib.sha256(ledger.read_bytes()).hexdigest())), flush=True)
run('baseline', ['check'])
args = ['import', csv, '--csv', 'date=Date,narration=Description,amount=Amount',
        '--account', 'Assets:Cash', '--default-account', 'Expenses:Food',
        '--date-format', date_format]
run('preview', args)
run('apply', args + ['--apply'])
run('repeat', args + ['--apply'])
run('facts', ['query', "SELECT date,number WHERE account='Expenses:Food'"])
run('year-2023', ['report', 'income-statement', '--time', '2023'])
run('year-2024', ['report', 'income-statement', '--time', '2024'])
run('check', ['check'])
```

Both overflow modes reproduce twice:

- The public calendar calculation gives 365 days for 2023. `preview` returns
  `ready: 1`, `invalid: 0`, row date `2024-01-01`, and no validation error.
  The source ledger is unchanged by preview and every later read.
- `apply` returns `written: 1`, `invalid: 0`, changing the source ledger.
  `facts` returns `[["2024-01-01", "7.75"]]`; the 2023 income statement reports
  zero net profit and 2024 reports `-7.75 USD`. Cash is now 92.25 USD. Every
  command exits 0 with empty stderr; the CSV stays byte-identical.
- `repeat` returns `written: 0`, `duplicates: 1`. Both CLI and independent,
  unwrapped Beancount loads consider the saved ledger valid. The pristine
  control still has Cash 100 USD and no expense in either year, the required
  state after refusing an invalid source date.

Valid controls also pass twice: `2024-366` becomes 2024-12-31,
`2023-365` becomes 2023-12-31, unpadded `2023-1` becomes 2023-01-01,
and ISO week `2020-W53-5` correctly becomes 2021-01-01. The last case is a
legitimate ISO-year/calendar-year crossing and must remain accepted.
Additional fresh controls refuse ordinal `000` and `367`, invalid ISO week
2021-W53 and week 54 with exit 2 and no ledger write. Valid ISO weeks 52/53
work. These are ordinary calendar dates and small amounts.

A mixed-file control reproduced twice for each year format: valid day 365
(`-2.25 USD`) followed by invalid day 366 (`-7.75 USD`) writes both rows with
exit 0. Fresh queries and native loads find 2023-12-31 / 2024-01-01;
the annual expenses are 2.25 / 7.75 USD and Cash is 90 USD. The fix must reject
the invalid row before writing this batch, rather than allowing its valid
prefix to mask the rollover. The ordinary unmatched-category review flag is
independent; there is no warning about the date conversion.

Cause: `cli/src/bea_engine/csv_mapper.py:CsvImporter.extract` at line 1770
uses `datetime.strptime(cell, format).date()` and only rejects a raised
`ValueError`. The exact managed Python runtime also turns `2023-366` and
`23-366` into 2024-01-01, so this is inherited standard-library normalization
missing a CLI calendar-validity check, not a Beancount report error. The
explicit-year guard `_has_year_directive` correctly accepts these `%Y`/`%y`
formats; it does not validate their day number. Validate the encoded ordinal
against its calendar year before creating a Transaction. Preserve tolerant
zero padding and genuine ISO-week crossings; do not reject every custom
format or require every input to equal `strftime` byte-for-byte.

the mapping/date format, and preview/apply share `extract`. Explicit mappings
and the resolved/remembered CSV paths converge here; remembered-setting replay
was not separately exercised for this defect. Python importer implementations,
Beancount, reports, REST, GraphQL and MCP need no change for this local fix.

**Resolved 2026-10-23** — fixed: CSV date parsing in the engine (`_strptime` in `cli/src/bea_engine/csv_mapper.py`, used by the row reader and the format check) now refuses a day of the year its year does not have. A format naming both a year (`%Y` or `%y`) and `%j` has those two fields read out of the cell, and an ordinal above 365 (366 in a leap year) raises the same `cannot parse date … in column … with format …` usage error as any bad date, before any ledger write. `2023-366` with `%Y-%j` and `23-366` with `%y-%j` no longer preview ready and write as 2024-01-01; `2024-366`, `2023-365`, `2023-1` and `23-365` still import. Regression tests in `cli/tests/test_import_day_of_year_dates.py` fail without the fix. Full suite green. Shipped in this commit (`cli`).
