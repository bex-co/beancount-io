# Name generator extraction failures without the configuration repair hint

**Minor · cli · 10–15m · A1.** A `SystemExit` raised while consuming a
generator returned by `extract()` is blamed on configuration loading.
The error advises guarding an unrelated `beangulp.Ingest(CONFIG)()` call,
even when the configuration contains no such call. An immediate exit from
the same method already gets the correct method-specific message. Writes
are correctly refused; this finding concerns the repair advice. No fix
implemented.

Real CLI QA, 2026-10-21, HEAD `32401a5d8`, checkout `bea 0.3.1`, macOS
26.5.1 arm64, frontend Python 3.13.3, managed Python 3.12.10 / Beancount
3.2.3, Beangulp already enabled. Fresh processes, closed stdin/no TTY,
isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled,
no inherited `BEA_FILE`/`BEA_TOKEN`. Synthetic local files only.

Create disposable `/abs/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Create `/abs/books/statement.bank` containing `Synthetic statement`, and
`/abs/books/importer.py`:

```python
from datetime import date
from decimal import Decimal
from beancount.core.data import Transaction, Posting, new_metadata
from beancount.core.amount import Amount

class Rows:
    def identify(self, file):
        return str(file).endswith(".bank")
    def account(self, file):
        return "Assets:Cash"
    def extract(self, file, existing=None):
        entry = Transaction(
            new_metadata(file, 1), date(2024, 1, 2), "*", None, "Coffee",
            frozenset(), frozenset(), [
                Posting("Assets:Cash", Amount(Decimal("-7.75"), "USD"), None, None, None, None),
                Posting("Expenses:Food", Amount(Decimal("7.75"), "USD"), None, None, None, None),
            ],
        )
        yield entry
        raise SystemExit(0)

CONFIG = [Rows()]
```

```sh
bea --json -f /abs/books/main.bean check
bea --json --no-input -f /abs/books/main.bean import /abs/books/statement.bank --config /abs/books/importer.py
bea --json --no-input -f /abs/books/main.bean import /abs/books/statement.bank --config /abs/books/importer.py --apply
bea --json -f /abs/books/main.bean check
```

Actual: checks exit **0**; preview and apply exit **1/validation**, empty
stdout, one JSON error on stderr. The message begins:

```text
Importer failed (SystemExit: 0): the configuration called sys.exit, as an unguarded beangulp.Ingest(CONFIG)() does. Put that call under if __name__ == "__main__": to use the script with --config.
```

The configuration has no top-level exit or Ingest call. The exit happens
inside `Rows.extract()` after yielding a valid transaction. Adding a main
guard to the configuration cannot fix it. Exit status 2 inside the generator
reproduces the same wrong advice. Repeated twice from pristine books;
preview, apply and another apply all preserve ledger/source/config bytes,
and fresh checks remain clean.

Expected: keep exit 1 and atomic refusal, but identify `Rows extract()`
or consumption of its returned entries and say to return entries or raise
an ordinary parser exception. This is the behavior established by
[852](./done/852.md) for immediate exits from importer methods.

Working controls, all reproduced twice: removing the final exit leaves a
supported finite generator (preview ready 1, apply written 1, re-import
written 0); returning a list works too. Replacing `yield entry` with
`raise SystemExit(0)` makes `extract()` a nongenerator and correctly says
`Importer Rows extract() called sys.exit (0); an importer method must return
its answer or raise an exception, not exit.` A `ValueError` during iteration
names that parser exception without configuration-guard advice. An actual
module-level exit still belongs to the configuration diagnostic.

Cause: `cli/src/bea_engine/importing.py:_extracted` at 973–976 catches
`SystemExit` only around the call to `importer.extract`. A generator's
body runs later, in `copy.deepcopy(list(result))` at 991, outside that
guard. The exception reaches the Python-import outer handler, which calls
`_exited` and emits its configuration-load hint. The shape check between
them explicitly accepts `Iterable`, and the finite-generator control
demonstrates this is an accepted return form.

Fix: apply the existing method-specific exit handling while consuming the
returned iterable too, keeping the real configuration-loading handler for
exits during module loading. Preserve the ordinary exception details and
all-or-nothing extraction before any write. `_extracted` is shared by
Python and CSV import paths (calls at 351 and 278); the built-in CSV
extractor returns a list, so the observed deferred-execution case is a
Python importer. No dependency or API change needed.

Dedupe: searched all `.pm` states for generator/iterator extraction,
`SystemExit`, `sys.exit`, and the Ingest hint. Completed 634 introduced
the useful configuration-load diagnostic; completed 852 (`aa268c7b7`)
distinguished immediate method exits but its extraction guard excludes
iteration. Its tests exercise immediate calls, not this deferred body.
No overlapping open repair or later materialization guard was found.

Acceptance: generator exits 0 and 2 name extraction in both preview and
apply, keep one structured exit-1 error and preserve files; immediate
method exits retain their current message; actual configuration exits
retain the configuration hint. Finite generators and lists still import
and re-import correctly. Pin these real-command controls. Other operating
systems and repaired behavior remain unverified.
