# Preserve JSON float markers when sending batch updates to the engine

**Minor · cli · 20–35m · A1 · worker1.** A malformed row containing an ordinary
JSON decimal such as `1.25` aborts an entire update batch before per-row
validation. A valid first row receives no preview and cannot be applied.
The previous batch implementation rejects the bad row and processes the valid
row as documented; integer/string mistakes still do so on current main.
The shared JSON-reader refactor introduced a typed float marker without
teaching Update's request serializer to transport it. No product fix implemented.

Real local CLI QA, 2026-10-25, clean main
`5a502b97c4e9f6c40f1b86a9bf68d5597e9e983f`; runtime identical to frozen
`94cb785b1319e309134a7f79af9922186c07751a` (1,630 tracked CLI files).
Checkout `bea 0.3.1`, frontend Python 3.13.3, existing managed Python 3.12.10 /
Beancount 3.2.3 / Beanquery 0.2.0, macOS 26.5.1 arm64. Fresh bounded
subprocesses, closed stdin/no TTY, isolated absolute config/cache, notifier
disabled. Synthetic local books, no plugins or services.

The valid book starts with pending R1 **9.99 USD** and R2 **3.01 USD**,
both in Uncategorized; Cash is **87.00 USD**. The first mapping is:

```json
[{"id":"R1","account":"Expenses:Food","flag":"*"},{"id":1.25,"flag":"*"}]
```

Both `bea --json -f main.bean update transactions --from mapping.json` and
its `--apply` form exit **1** with empty stdout and this stderr envelope:

```json
{"error":{"category":"validation","message":"Object of type JsonFloat is not JSON serializable. Pass --debug before the command for a traceback.","exit_code":1}}
```

There are no per-row results, no ready R1 preview and no valid-row write.
Every ledger byte stays unchanged; native checks remain valid, with Food **0**,
Uncategorized **13.00**, Cash **87.00 USD**, both flags still `!`.
Human preview/apply show the same failure. Replacing the second row with
`{"id":"R2","flag":1.25}`, the scalar `1.25`, or
`{"id":"R2","flag":"*","rate":1.25}` also aborts the entire batch.
These are invalid update rows; the bug is the lost per-row rejection/partial
processing, not refusal to accept numeric ids, numeric flags or unknown fields.

Expected: the engine receives the typed invalid value, preview reports one
ready row and one rejected row, and apply writes only R1 while returning the
normal partial result/error for row 2. Native after: Food **9.99**,
Uncategorized **3.01**, Cash **87.00 USD**, R1 cleared and R2 still pending.
Preserve the decimal literal and invalid type through transport; do not turn
it into a usable id/flag or a lossy Python float.

## Cause, dedupe and acceptance

`cli/src/cli/rows.py:142` now calls
`json.loads(..., parse_float=JsonFloat)`. Before the shared-reader refactor,
Update used the default JSON float parser. `cli/src/cli/commands/update.py:58`
still passes `json.dumps(request)` to `launch.helper_json`: Python cannot
encode `JsonFloat`, so evaluation fails before the engine can classify rows.
Every caller of this `_update` helper shares that serializer; the actual
JSON batch entry point is the exercised path that supplies float markers.
Single update's typed command options do not produce this marker.

Add already sends `json.dumps(request, default=json_float_default)` at
`cli/src/cli/commands/add.py:101`. The existing helper at
`cli/src/cli/amounts.py:39–42` transports the literal under `__json_float__`;
`bea_engine.main._request` (:950–960) restores it with `object_hook` before
engine validation. Reuse that transport for Update; keep marker restoration
and invalid-row validation intact. No new parser, dependency or engine fork
is needed.

Dedupe: searched **5,639 board Markdown files / 44 non-done milestone
