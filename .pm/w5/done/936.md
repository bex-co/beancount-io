# Keep four-digit years in relative periods and ISO-week parsing

**Minor · cli · 20–30m · A1.** Relative periods landing before year 1000
produce an unpadded year that the next parser stage rejects. Valid absolute
ISO weeks below year 1000 similarly lose their padding before `strptime`.
Equivalent absolute calendar periods work. This is an early-date edge case;
ordinary four-digit years work. No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `bd1cc131f` (CLI unchanged after pulling
`d6399ffc7`), checkout `bea 0.3.1`, macOS 26.5.1 arm64, frontend Python
3.13.3, existing managed Python 3.12.10. Separate subprocesses, closed
stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`.
The real local clock was used; no clock patch or time simulation.

Create disposable `/abs/books/main.bean`:

```beancount

0001-01-01 open Income:Salary USD
```

From `/abs/books`, with the isolated child environment above, use the actual
current year so the example also reproduces after 2026:

```sh
qa_year=$(date +%Y)
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean report income-statement --time 0999 --interval yearly
bea --json -f /abs/books/main.bean report income-statement --time "year-$((qa_year-999))" --interval yearly
bea --json -f /abs/books/main.bean report income-statement --time 1000 --interval yearly
```

Actual command exits: **0, 0, 2, 0, 0, 0, 2, 2, 0**, with unchanged source
bytes. In 2026, the failing relative terms are `year-1027` and
`fiscal_year-1027`. Absolute 0999 and FY0999 report
`[0999-01-01, 1000-01-01)` and profit 2 USD. Their relative equivalents
return empty stdout and usage envelopes on stderr:

```text
Invalid time filter 'year-1027'. … Failed to parse date: year-1027
Invalid time filter 'fiscal_year-1027'. … Failed to parse date: fiscal_year-1027
Invalid time filter '0999-W01'. … time data '999-W1-1' does not match format '%G-W%V-%w'
```

Both year-1000 forms work and report 3 USD. The explicit date range covering
ISO week 0999-W01 works and reports 2 USD. Expected: keep the four-digit year
between parser stages, so equivalent valid spellings select identical periods
and accounting values.

Reproduction and controls:

- Sixty real reports, twice across years 0001/0999/1000, five period families
  (year, month, quarter, fiscal year and fiscal quarter), and absolute/relative
  spellings. Every relative year-0999 family refuses while its absolute form
  works; all year-1000 pairs work. First-year calendar absolute forms work and
  relative forms refuse too. First-year fiscal absolute forms already fail for
  open w5/932 and are not claimed as a distinct failure here.
- Eight day/week comparisons across two repetitions: day offsets use ISO dates
  and correctly match the absolute day at 0999-01-02; both absolute and
  relative ISO-week forms refuse on the three-digit intermediate year.
- Eight additional direct alias calls, two repetitions × overview, balance
  sheet, trial balance and balance, all refuse the same relative year-0999
  term. Eight further controls verify the explicit week date range, week
  1000-W01, an ordinary 2024 week and refusal of invalid 2021-W53.
- All ledgers initially check, every read preserves source bytes, and expected
  period income is fixed independently at 1/2/3 USD in the three test years.

Cause: `cli/src/fava/util/date.py:substitute` (:363–382) formats replacement
years with `str(year)` or unpadded f-strings. `parse_date` then requires
four digits in YEAR/MONTH/QUARTER/FY patterns (:29–44), so it rejects its own
replacement. Its WEEK branch (:449–450) parses a valid four-digit input to
an integer, then rebuilds it unpadded for `%G`, causing the second failure.
Both are loss of the required year width at an internal string boundary.

Fix: preserve four-digit years in all relative replacement families and avoid
the unpadded intermediate ISO-week string, using native date construction or
correct formatting. Keep real out-of-range dates and invalid ISO weeks refused,
relative range substitution, fiscal month offsets and ordinary-year behavior.
Do not patch the real clock or rewrite customer ledger dates. `substitute`
has one production caller, `parse_date`; report `TimeFilter` and account-period
hints consume that parser. All four report kinds and balance share the runtime
failure. No dependency or backend/API change needed.

Dedupe: searched all board states for relative/ISO-week year padding and
0999; scanned 46 active/blocked milestone scopes with no matching repair.
Completed w5/618 (`79505f176`) fixed replacing variable occurrences in ranges,
not year width. Open w5/932 fails after a correctly parsed fiscal label by
constructing year zero; FY0999 works absolutely here, so this failure occurs
earlier and needs a different correction. Completed w5/842 fixes calendar
opening-summary underflow and is why the explicit first-year controls work.
Targeted helper history shows no later padding fix after vendoring
(`41a2e6299`). Unrelated mobile date-padding work does not change this parser.

Acceptance: the public relative periods and ISO week match their absolute
controls and profits; year/month/quarter/fiscal variants preserve year width.
Day offsets, ordinary years, range substitutions and invalid-week refusals
remain intact. The nine public commands were replayed twice. Only
macOS/checkout tested; repaired behavior unverified.
