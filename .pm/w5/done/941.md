# Hosted bank imports write no `import-id`, so the shared dedup contract cannot see them

**Minor · backend-v2 · 30–45m · A1.** Found 2026-10-21 in [w5/m5/t004](./blocked/m5/README.md)'s confirmed import on a bank-linked ledger.

`importStagedBankTransactions` (and its REST and GraphQL twins) booked the staged row as a plain transaction: payee, narration, and two postings. It wrote no `import-id` or any other metadata naming the Plaid transaction. A `SELECT … meta('import-id')` on the new entry is empty.

What keeps hosted imports from repeating today is the staging row's `syncedToLedger` flag. Nothing in the ledger itself marks the entry as imported. So:

- **Re-staging can duplicate.** If the same bank transaction is staged again, after a relink or a sync-cursor reset, the playbook's amount-and-date check is the only defense. It is fuzzy, and the review table only flags it as a *suspected* duplicate.
- **A CLI import of the same account cannot exact-match.** `bea import` or the `beancount-import` skill dedupes by `import-id`, and finds none to match against.
- **The shared convention says otherwise.** [`skills/beancount-import/references/dedup.md`](../../skills/beancount-import/references/dedup.md) already names a bank-feed prefix such as `plaid:<txn-id>`.

Cause: `buildBeancountTransaction` (`src/features/plaid/utils/plaid-mapper.ts`) emits no `meta`.

Fix: write `import-id: "plaid:<transactionId>"` on every hosted bank import, through the shared service so all three protocols get it. Have the submit path refuse, or flag, a staged row whose `import-id` the ledger already holds. Check that the CLI's generic-prefix handling (w5/601, w5/823) treats `plaid:` as a native id.

Acceptance: a hosted import writes the `import-id`. Re-submitting a row whose `import-id` is in the ledger writes nothing new. Tests pin both.


---

**Resolved 2026-10-22** — fixed: `buildBeancountTransaction` (`backend-cluster/backend-v2/src/features/plaid/utils/plaid-mapper.ts`) now writes `import-id: "plaid:<transactionId>"` on every hosted bank import, and `PlaidSyncService.submitTransactionsToLedger` — the single path behind the GraphQL, REST and MCP submit operations, preview included — asks the ledger which of the batch's ids it already holds and refuses the batch (`BadUserInputError`, naming the transaction and its import-id) instead of booking it again. The `syncedToLedger` flag stays the primary guard, and a failed lookup is logged and does not block the import. The CLI already treats `plaid:<id>` as a native id (it is not a `<source>:sha256:` generated id), so a later `bea import` of the same account exact-matches the hosted entry. Regression tests in `plaid-mapper.test.ts` and `plaid-sync-service.test.ts` fail without the fix; backend typecheck, eslint, knip, prettier and the full jest suite are green (the `archive-parity` timing flake passes alone). Not verified against the live ledger service: the lookup uses `meta('import-id')` in BQL through `queryShell`. Shipped in this commit (`backend-v2`).
