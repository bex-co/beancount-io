# Preserve dateless cost lots when replaying listed inferred quantities

**Minor · cli · 45–60m · A1 · worker1.** A valid book buys the same shares
twice with quantities left to native interpolation, then sells part of the
combined lot. `list transaction --json` completes the two share quantities
but loses the fact they were inferred. Feeding that unedited list to
`add transactions` turns the dateless native cost into two differently dated
lots, so the valid sale becomes ambiguous and the whole replay is refused.
Both source and untouched destination still pass `check`; the refusal is
atomic. No product fix or lost-source-data claim.

Real local QA, 2026-10-24, clean main
`e007ad39bd2face10c8e7b3eda5c3dabab18241e`; CLI is byte-identical to frozen
`ee4b7702516da4535bb3b478e2efe9913b09481b`, checked before/after execution.
Checkout `bea 0.3.1`, frontend Python 3.13.3, existing managed Python 3.12.10 /
Beancount 3.2.3 / Beanquery 0.2.0, macOS 26.5.1 arm64. Fresh bounded
subprocesses, closed stdin/no TTY, isolated absolute config/cache, notifier

## Standalone reproduction

Put the checkout's `bea` on PATH and replace the two `/abs/…` paths with an
unused disposable directory and the existing managed engine Python.
The real native parser supplies the importer entries. The importer source
account is Cash and every Cash posting has its explicit amount, so this
meets the source-amount requirement. Native reference loads disable caches.

## Cause and scoped repair

The native behavior is independently verified, not a proposed change to
Beancount. In installed Beancount 3.2.3, `parser/booking_full.py:622–624`
passes a posting with a missing units number through before augmentation's
default-date assignment at `:702–704`; later interpolation and
`convert_costspec_to_cost:747–773` retain its absent date. With the units
already stated, the default date is assigned instead.

`cli/src/bea_engine/ledger/reader.py:530–531,551–584` encodes the loaded
quantity and cost, including `date=None`, without carrying the original
inferred-number representation. `writer.format_transaction:484–525`
reconstructs the cost as `CostSpec(..., date=None)` but now writes explicit
quantities. In the input model that null date is an omitted constraint
(`models.py:144–162`), so native booking supplies each purchase's date.
`adding.py:1970–1972` formats these rows and correctly rejects the now
different combined book. This is not a bulk ordering failure: the two buys
and sale occur on three different dates.

Preserve enough original inference information across list-to-bulk replay
to retain the native cost identity while still reporting actual quantities
to readers. An explicit round-trip representation of the source's inferred
unit number can use the already supported null-number write path; make
it portable rather than depending on access to the old source filename.
Keep a genuinely unknown booked cost date distinct from requesting the
normal default date on a new explicit acquisition. Do not rewrite the
source's native cost dates, suppress the sale, or weaken booking validation.
CLI-only repair, no new dependencies or API changes.

Caller search: `reader.list_transactions:634` produces the transaction
models for `listing.answer`, and `listing.py:130` also formats their details;
`adding.py:1915,1970,2101,2166` uses the shared transaction formatter for
bulk validation/planning. Real JSON listing, import, single-add replies,
bulk output and fresh checks are exercised. `--details` text replay,
`query PRINT`, other booking methods and other operating systems remain
unverified; this note does not promise to change upstream printer behavior.
