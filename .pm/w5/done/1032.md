# Accept a UTF-8 BOM before OFX XML prologs

**Minor · cli · 25–35m · A1 · worker1.** An otherwise valid bank/card
OFX XML export is refused solely because it starts with a UTF-8 byte-order
mark. Preview, apply and repeat all exit **2** with `is not an OFX file:
cannot read its header.` The same bytes without the three-byte signature
import once and then deduplicate. The refusal preserves the book; no product
fix implemented.

Change only `bom` to `plain` for the working control. Repeat in another unused

`--ofx` on a `.export` file; `configured` selects an inspected local
`OfxImporter` configuration explicitly. The config has a non-discovery
filename, so its presence does not redirect the automatic cases.

The XML has an ordinary OFX 2.x processing instruction, uppercase bank/card
aggregates, sign-on/status fields, native FITID B1, a UTF-8 merchant name,
an escaped ampersand, and a closing balance. Python's XML reader verifies that
adding the signature changes no document nodes. The recipe protects every
input byte and captures exact argv, safe environment overrides, streams,
exits, timing, ledger hashes and independent uncached native graphs.

Expected: a legal UTF-8 encoding signature should not change which bank
transactions can import. [XML 1.0 §4.3.3](https://www.w3.org/TR/xml/#charencoding)
allows a leading BOM for UTF-8 and treats it as an encoding signature outside
the document content. `cli/docs/IMPORTING.md`'s OFX section supports XML/OFX
exports, and this decoder already chooses `utf-8-sig` for UTF-8 bodies.

Root: `cli/src/bea_engine/ofx_importer.py:62–69` reads the raw file, partitions
at the first `<`, and decodes the preceding bytes as ASCII. For XML preceded
by `EF BB BF`, that prefix is exactly the BOM and raises UnicodeDecodeError.
The file is rejected before the XML-prolog codec selection (:72–75) and
`raw.decode(codec)` (:79) can use the existing `utf-8-sig` mapping (:42).
Removing just the signature makes the prefix empty and reaches the same
UTF-8 parser with the same transaction. This is this adapter's pre-parser
check, not an upstream XML parsing failure.

Fix in `cli/`: recognize a single leading UTF-8 signature before the ASCII
header scan, and decode the full XML consistently with that choice, without
rewriting the input. Do not strip an interior U+FEFF or guess past invalid
encoding bytes. Keep strict declared-charset diagnostics, legacy SGML
decoding, native IDs, duplicate policy and exact decimals. No dependency or
server API change is needed.
