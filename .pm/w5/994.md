### A total cost must weigh what native booking actually holds

The first recipe buys 2 HOOL with one inferred cost component, 3 BOND at
`{{10 USD}}`, and pays 11 USD cash. Native booking first divides the BOND
total by three, then weighs that unit cost. Its BOND weight is exactly
`9.999999999999999999999999999 USD`; the HOOL lot costs exactly
`0.5000000000000000000000000005 USD` per share. The original single add and
first import write that correct book. The reply completes HOOL's cost using
an algebraic BOND weight of 10 instead. Unchanged bulk replay succeeds but
holds a different lot at `0.5 USD` per share. Both books pass `check`.
Shares, cash and rounded totals agree; the reply defect alone is an exact
lot-fidelity error in the final decimal places, not a claim of cash loss.

Import has the same normalization error. The script obtains the actual cost
from a real `bea query`, then restates it explicitly. Native reference graphs
for that restatement and the original trade are identical. Yet re-import is
`possible_duplicate` / exit 4 with generated IDs, or `conflict` / exit 4
with the same bank ID, instead of an exact duplicate / exit 0. A genuinely
different, native-valid `0.50 USD` lot is incorrectly an exact duplicate /
exit 0, even with `--duplicates include`. The generated-ID two-trade reference
holds 4 HOOL, 6 BOND and 978 USD cash; the actual file remains at 2 HOOL,
3 BOND and 989 USD. Under a reused bank ID that changed lot should conflict.
Raw exact repeats still skip correctly.

Set `companion = 'unit'` to state BOND's native unit cost explicitly. It
books the same native first trade and all replay/matching decisions work.
Both inferred-part forms and `use_precise_interpolation` reproduce the gap.

## Cause, dedupe and acceptance

`cli/src/bea_engine/ledger/writer.py:745` `_stated_cost_weight` returns
`number * per + total.copy_sign(number)`. For a total cost this bypasses
native unit-cost division and multiplication; for a negative total it also
changes the component's sign. Its sole caller is
`with_inferred_cost_parts` at line 844. That helper feeds both the single-add
answer in `ledger/adding.py:1377` and import's `_source_postings` at
`importing.py:1507`, before lot comparison and generated identity. The two
actual public CLI consumers reproduce the consequences above. Actual helper
proofs on every new profile compare its known weight and completed cost to
the native booked posting, using the same source module bytes.

The existing unfinished sections are adjacent guards in that same completion
helper: the required known counterpart component rejects a fully inferred
`{USD}` cost, the string-currency guard rejects an omitted currency, and
`if not solved` leaves a resolved zero indistinguishable from unresolved
input during identity. Preserve source text and genuinely ambiguous cases;
complete only what native booking determines, including zero and currency.

source history. `_stated_cost_weight` was introduced by the existing 994

different helper, `importing._stated_weight`, using native
