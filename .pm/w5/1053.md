# Refuse unsupported OFX correction records before importing payments

**Major · cli · 30–45m · A1 · worker1.** A bank correction replacing a10USD
charge with12USD is imported as another charge: expenses become22USD and
net worth falls to78USD instead of88USD. A deletion record imports a zero
transaction while retaining the old10USD charge. Preview and apply both
succeed without an advisory. This reproduces for bank OFX and card QFX,
explicit `--ofx`, automatic detection, and configured `OfxImporter`.
No product fix implemented. The bounded repair is an unsupported-record
refusal before any append; automatic replacement/deletion is outside scope.

## Reproduce and independently check the money

Begin with100USD cash. Import a January2 payment with `FITID=OLD-1`,
`TRNAMT=-10`. Import another statement row with `FITID=NEW-1`,
`CORRECTFITID=OLD-1`, `CORRECTACTION=REPLACE`, `TRNAMT=-12`.
In the OFX standard, CORRECTFITID identifies the previously sent transaction;
REPLACE replaces it and DELETE deletes it. These are correction instructions,
not another payment. See the primary [OFX Banking Specification2.3,
§11.4.4.1, printed225/PDF240](https://financialdataexchange.org/wp-content/uploads/2025/12/OFX-Banking-Specification-v2.3.pdf#page=240).

The append-only adapter need not implement those instructions: it must tell
users it cannot handle them and preserve the ledger, rather than silently
book their amounts as additional spending. A configured importer that
explicitly handles corrections remains a separate user workflow.

Put the current checkout's `bea` on PATH, save this standalone recipe, and
run `python3 recipe.py /absolute/new/book replace bank explicit json standard /absolute/engine/bin/python`.
Use a fresh directory for every run. Change `replace` to `delete`,
`new-payment`, `same-id`, or `mixed`; `bank` to `card`; `explicit` to
`auto` or `configured`; `json standard` to `human renamed`. The renamed
profile uses Spanish account roots and EUR. The configured profile uses
an inspected local instance of the same built-in adapter.
The recipe records argv, cwd, safe child overrides, stdin/TTY mode,
separate streams, exit codes, durations, before/after hashes and native
snapshots, including a hand-written semantic reference.

## Root cause, affected callers, and bounded repair

`cli/src/bea_engine/ofx_importer.py:182–193` iterates raw STMTTRN nodes,
reads only FITID for identity, and calls `_build_row` without examining
CORRECTFITID/CORRECTACTION. `_build_row` delegates to installed Beangulp
`examples.importers.ofx.build_transaction` at line261. The inspected
Beangulp0.2.0 function builds an ordinary posting from date/amount/text;
it does not interpret corrections. The local adapter then completes the
counter-posting and reconstructs metadata with only FITID and its rule
marker at `ofx_importer.py:200–220`. A distinct new FITID is thus a normal
new payment to generic duplicate review; the old-reference link is lost.

Searches cover the explicit and detected OFX/QFX branches in
`cli/src/bea_engine/importing.py`, frontend dispatch in
`cli/src/cli/commands/import_.py`, and configured `OfxImporter` instances.
All three share the affected adapter and reproduce. Arbitrary third-party
importers were not claimed to have this behavior.

While raw statement nodes are available, refuse actual unsupported
correction markers with a bounded usage diagnostic naming the source row,
action, new FITID and referenced old FITID. Finish extraction before any
append, including when an ordinary row precedes the correction. Explain
that the user must reconcile the correction manually or use an importer
that explicitly implements it. Keep parsing upstream; do not fork Beangulp,
add a dependency, implement automatic upserts/deletes, or reinterpret
ordinary distinct-FITID payments as corrections. Document the limitation
beside OFX support in `cli/docs/IMPORTING.md`.
