# A signed-out reader who opens a private ledger's receipt link gets HTTP 500 "Something went wrong — We encountered an unexpected error", not the sign-in page (gap in w0/018)

**Severity:** minor (no data is changed or shown, but a receipt link opened outside a signed-in tab dead-ends on a crash page). **Owner:** dashboard. **Estimate:** 30–45 minutes including tests. **A2:** receipt links are written into the ledger itself (`receipt: "https://beancount.io/ledger_assets/<repo-id>/static/<file>.png"` on every Upload Receipt or `insertReceiptTransaction` transaction), so people open them from a local clone, an editor, a terminal or another app, where the browser often has no Beancount.io session. w0/018's acceptance says that visitor "is sent to login"; production shows them an unexpected-error page instead. **Found by:** `/qa-find-bugs-dashboard` on 2026-11-21 against `https://beancount.io` (dashboard entry chunk `main-CIyNN76T.js`), QA-owned headless Chromium 153 at 1440×1000, English, plus `curl` with no cookies. Local HEAD `df74db037`.

## Repro

1. On a private ledger you own, record a receipt transaction (for this run: the QA account's disposable private ledger, `insertReceiptTransaction` with a 122-byte synthetic PNG; the transaction was removed again and `main.bean` restored byte for byte). Copy the `receipt:` link it writes, `/ledger_assets/<repo-id>/static/<file>.png`.
2. Control, signed in: opening the link answers **307** to the stored file's signed download URL, and the image opens.
3. In a fresh browser profile with no session, open the same link. The response is **HTTP 500**. The server-rendered page is the router's bare "Something went wrong! / Show Error"; after hydration it becomes "Something went wrong — We encountered an unexpected error. Please try again or go back to the previous page." with Go Home, Go Back and Try Again. **Error Details** reads `Error: Authentication required`. The URL never changes to sign-in.
4. Only **Try Again** reaches `/auth/login?next=%2Fledger_assets%2F…`. A reader has no reason to expect that a retry of an "unexpected error" is the way to sign in.
5. The same happens with a session cookie the server no longer accepts (a revoked session): 500 on the receipt link.

Controls on the same build, same signed-out profile: `/ledger/<owner>/<private-ledger>/journal`, `/…/income-statement` and `/settings/general` all go straight to `/auth/login?next=…` (also with the revoked cookie). Signed in, a missing file or a ledger id the reader cannot read answers 404 "Attachment unavailable", as w0/018 intended. Each result was repeated from a fresh load.

## Cause

`dashboard/src/routes/ledger_assets.$ledgerRepoId.static.$.tsx:31-40` maps `NOT_FOUND`, `FORBIDDEN` and `BAD_USER_INPUT` to `notFound()` and rethrows everything else, including `UNAUTHENTICATED`, counting on the root `ErrorPage` to redirect (the route's comment says so, and `routes/__tests__/ledger-assets-route.test.ts` "keeps … the signed-out redirect path as errors" only checks that it throws). On a server render that never happens: the error raised in `beforeLoad` is rendered with status 500 and handed to the client as a plain `Error("Authentication required")`, without the `CombinedGraphQLErrors` class or `extensions.code`. `isUnauthenticatedError` (`common/apollo/links/auth-error-link.ts:34-43`) needs both, so the redirect in `common/root-route/error-page.tsx:40-45` does not run. Try Again re-runs `beforeLoad` in the browser, where the Apollo error keeps its class, which is why only that path reaches sign-in. Every other private route redirects before rendering through `requireAuth` (`common/lib/auth/auth.ts:156-185`), which throws `redirect({ to: "/auth/login", search: { next } })` in `beforeLoad` when the root context has no `userProfile`.

## Fix

In the asset route's `beforeLoad`, when the download-URL read fails with `UNAUTHENTICATED` and the root context has no `userProfile`, throw the same redirect `requireAuth` throws: `/auth/login` with `next` from `getSafeReturnPath(location)`, so a server render answers a redirect, not a 500. Keep the 404 mapping for `NOT_FOUND`, `FORBIDDEN` and `BAD_USER_INPUT`, and keep 5xx for real service failures. A signed-in reader whose session is refused still lands on sign-in, not on "Attachment unavailable". Do not leave the redirect to `ErrorPage`.

## Definition of done

- In a profile with no session, opening a private ledger's receipt link answers a redirect to `/auth/login?next=%2Fledger_assets%2F<repo-id>%2Fstatic%2F<file>`; after signing in, the reader lands on the file. A revoked session cookie behaves the same.
- Signed in, the owner's link still answers 307 to the signed download URL, and a missing or foreign file still answers 404 "Attachment unavailable".
- The route test asserts that `UNAUTHENTICATED` without a `userProfile` throws a redirect to `/auth/login` carrying `next`, and it fails on the current code. Dashboard gates (`yarn format:check`, `yarn lint`, `yarn test`, `yarn build`) pass.
