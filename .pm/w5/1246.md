# The same BQL query lists an entry's metadata in a different order on every run: `name=SPDR Gold Trust (ETF), price=…, export=…`, then `export=…, name=…, price=…`, though the file writes `export, name, price` (gap in w21/778)

**Severity:** minor. No value is wrong or missing, but a query's output is not reproducible: two runs of the same `SELECT … meta …` on an unchanged ledger return different text, and two entries whose keys are written in the same order come back in different orders in one result. **Owner:** `backend-cluster/ledger` (the dashboard prints the text it receives). **Estimate:** 30–45 minutes including tests. **A1/A3:** BQL is the one surface the dashboard Query page, the REST `query` route and the MCP `runBqlQuery` tool share, and agents and scripts compare its output between runs. A reader who keeps invoice fields as metadata (`invoice`, `po`, `due`, `paid`) and queries them gets the fields shuffled on each run, and a downloaded CSV differs from the last one in every `meta` cell. w21/778 fixed this for the Journal and transaction detail, but not for BQL. Stock beanquery prints the keys in the order the file writes them, every time. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English. Public example ledger, read-only. Local HEAD `6ae3ef9d0`.

## Repro

Public ledger, no write needed. `main.bean` in `open_ledger/example` writes every commodity's metadata in the order `export`, `name`, `price`. For example, lines 46–49:

```beancount
2004-11-01 commodity GLD
  export: "NYSEARCA:GLD"
  name: "SPDR Gold Trust (ETF)"
  price: "USD:google/NYSEARCA:GLD"
```

1. Open `/ledger/open_ledger/example/query?query=SELECT date, meta FROM entries WHERE type = 'commodity' AND date >= 1995-01-01` (URL-encoded). The query runs on load and shows `Rows: 6`.
2. Read the `meta` column. On the first load, 1995-09-18 read `name=…, export=MUTF:VBMPX, price=…`, 2004-01-26 read `price=…, export=NYSEARCA:VHT, name=…`, and 2009-05-01 read `export=MUTF:RGAGX, price=…, name=…`. All six entries write their keys in the same order, yet one result already lists them in four different orders.
3. Reload twice. Each load reorders the cells again: 2004-01-26 became `name=…, price=…, export=…`, and 1995-09-18 became `export=…, price=…, name=…`. Only one of the 18 cells across the three loads matched the file's order.
4. API control (GraphQL `queryShell`, as the page sends it). `SELECT date, meta FROM entries WHERE type = 'commodity' AND date = 1792-01-01` sent 16 times returned `export=CASH, name=US Dollar` 7 times and `name=US Dollar, export=CASH` 9 times.
5. REST control. `POST /api-gateway/v1/ledgers/open_ledger/example/query` with `Accept: text/plain` and `SELECT date, meta FROM entries WHERE type = 'commodity' AND date = 2004-11-01`, sent 8 times, printed 5 different orders of GLD's three keys (`export, price, name`; `export, name, price`; `name, export, price`; `price, export, name`; `name, price, export`).
6. Stock control. The same two GLD/VHT commodity blocks in a local file, run three times through `bea query` (beanquery), print `{'filename': …, 'lineno': 2, 'export': …, 'name': …, 'price': …}` every time, in source order.

Repeated from fresh page loads. The ledger file did not change between runs.

## Cause

BQL runs on the engine's own parse, which never gets w21/778's reordering:

- `LedgerShellService.runQuery` (`backend-cluster/ledger/src/features/ledger/service/ledger-shell-service.ts:171–207`) passes the files to `queryLedgerFilesResult` (`foundation/rustledger/engine.ts:1031`). That function evaluates the query inside rustledger, whose metadata is a hash map. Its iteration order varies between parses and between entries.
- w21/778 added `orderMetaAsWritten` (`foundation/rustledger/meta-order.ts`), which the directive path calls once per parse (`engine.ts:949`). Journal, context and transaction-detail reads get source order from it, but the BQL path never calls it.
- `formatCellValue` (`foundation/rustledger/mappers.ts:95–98`) writes an object cell as `Object.entries(cell).map(… key=value …).join(", ")`, so the hash-map order becomes the text. `toShellCell` (`features/ledger/service/ledger-shell-mappers.ts:334–357`) feeds GraphQL and REST JSON from it, and `formatTextCell` (`:399–404`) feeds REST `text/plain` and MCP.

## Fix

Owned by `backend-cluster/ledger`, in the shared shell mapper, so GraphQL, REST and MCP change together (parity rule). No dashboard change is needed.

- Every `meta` cell lists its keys in the order the source writes them, on every run, in both the structured and the text result, as stock beanquery and the Journal (w21/778) do. A meta cell carries no entry identity (`filename` and `lineno` are empty on this engine, per w23/016). Recover the order from the parse's source-ordered directives where a cell's key/value set identifies one entry. For example, reuse `orderMetaAsWritten`'s output from the snapshot the service already caches.
- Where a cell cannot be placed on exactly one entry, list its keys by name. w21/778 accepted that order as the stable fallback. Do the same for nested objects such as the `entry` column, so no object cell prints in hash order.
- Report the hash-ordered meta to rustledger upstream (an insertion-ordered map), alongside the gaps in w23/022, so the service-side ordering can be dropped once upstream preserves the order itself.

## Definition of done

- On production, the step 1 query lists every row's keys as `export=…, name=…, price=…` on each of 5 reloads. The GraphQL control in step 4 returns `export=CASH, name=US Dollar` on 16 of 16 calls, and the REST `text/plain` control in step 5 prints GLD's keys as `export, name, price` on 8 of 8 calls.
- Ledger unit tests feed the mapper object cells whose key order differs from the source's: two entries with the same keys, and one cell that matches no single entry. They assert source order for the first case and name order for the second, in the structured and the text results. The tests fail with the ordering disabled. Ledger lint, typecheck, test and `verify:rustledger` pass.

## Blast radius

Every caller of `LedgerShellService` shares the cause. That covers the dashboard Query page and its Download CSV (`dashboard/src/features/bql/components/query-result-export.tsx` exports the result as received), REST `query` in both representations, the MCP `runBqlQuery` tool, and `bea` hosted queries that call REST. `postings.meta` arrives pre-stringified as `k: "v"` lines (w23/170). Its multi-key order was not exercised: the example ledger has no posting metadata. A fix in `formatCellValue` alone would not reach it if the engine already wrote that string in hash order. Working control: Journal and Entry Context metadata are reordered by `orderMetaAsWritten` (w21/778). Single-key cells and `meta('key')` lookups are unaffected.

## Dedupe

Searched every board state for `meta` together with order, `hash map`, `formatCellValue`, `Object.entries(cell)`, `meta column` and `SELECT … meta`. w21/778 (done) fixed the order for directive reads only, and its closeout lists Journal and context responses. w23/170 (done) unified the `meta` dialect and dtype across tables but not key order. w23/016 and w23/022 cover the missing `filename`/`lineno` and other upstream gaps. w5/230 and w1/145 cover CSV `meta` cell content. None covers key order in query results. `git log` on `mappers.ts`, `ledger-shell-mappers.ts` and `ledger-shell-service.ts` shows no ordering change, so this is not deployment lag.

## Unverified

The MCP tool, which shares the service but was not called. The `entry` column's nested meta. Posting-level multi-key meta. Firefox and Safari, which do not affect a server-side order.
