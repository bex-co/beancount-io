# Keep Cash Flow cash balances in native arithmetic after inferred payments

**Minor · cli · 45–60m · A1 · worker1.** After an inferred cash payment,
Cash Flow JSON reports **1000.0000000000000000000000001 USD**, while native
Beancount, Register, BQL and a cash-filtered Balance Sheet report **1000 USD**.
The discrepancy is **1e−25 USD**, including the opening and closing of a quiet
month. It appeared when 1077's fix put the entire Cash Flow calculation in a
100-digit context. Human output rounds this fixture to 1000.00; this finding
concerns the exact JSON amounts agents consume, not a visible cent error or
corruption of the ledger.


Use child-only `BEA_CONFIG_DIR` and `XDG_CACHE_HOME` inside the fresh case,
`BEA_NO_UPDATE_NOTIFIER=1`, and unset inherited `BEA_FILE` and `BEA_TOKEN`:

```sh
bea --json --no-input --offline --file /absolute/case/main.bean check
bea --json --no-input --offline --file /absolute/case/main.bean report cash-flow --time 2024-01
bea --json --no-input --offline --file /absolute/case/main.bean report cash-flow --time 2024-02

bea --json --no-input --offline --file /absolute/case/main.bean query "SELECT currency,sum(number) WHERE account = 'Assets:Cash' GROUP BY currency"
```

Every command exits 0; the ledger is valid and the reports claim complete
valuation. Native booking infers the payment as
**−999.9999999999999999999999999 USD**. Its cash inventory uses precision 28
and closes at **1000.000000000000000000000000 USD**. Register, BQL and Balance
Sheet agree numerically with that native balance. Cash Flow instead exposes:

| View | Native cash | Cash Flow JSON |
| --- | --- | --- |
| January closing | 1000 USD | 1000.0000000000000000000000001 USD |
| Quiet February opening | 1000 USD | 1000.0000000000000000000000001 USD |
| Quiet February closing | 1000 USD | 1000.0000000000000000000000001 USD |

February has no activity rows and zero net change. The extra precision also
appears in its per-account cash balance. Reports preserve every source byte.
Two pristine USD roots repeat the result; an included EUR ledger with renamed
roots does too. The original 1071 journey also reproduces it after a real
`bea add transaction` with the stock posting above and a bare cash posting.

An independent control uses the prepared managed interpreter, without the
frontend's module path:

```sh
/absolute/managed-engine/bin/python -B - /absolute/case/main.bean <<'PY'
import json, sys
from decimal import getcontext
from beancount import loader
from beancount.core import data, inventory
loader.initialize(use_cache=False)
entries, errors, _ = loader.load_file(sys.argv[1])
assert not errors, [error.message for error in errors]
cash = inventory.Inventory()
for entry in entries:
    if isinstance(entry, data.Transaction):
        for posting in entry.postings:
            if posting.account == "Assets:Cash":
                cash.add_position(posting)
print(json.dumps({"precision": getcontext().prec,
                  "cash": [str(position.units.number) for position in cash]}))
PY
```

Expected native result: precision **28**, cash numerically **1000 USD**.
This oracle reads booked postings and native inventory; it does not reproduce
the Cash Flow implementation's closing-minus-movement formula.

Nearby current-source controls pass: explicitly pay **−1000.00 USD**, or use
an exactly divisible **990.00 EUR** total cost with an inferred payment
(native closing **1010 EUR**). Both inferred fixtures also pass on the prior
immutable source `f9033fdeaab58374baafe6f8ed2829c0b5a89db5`, with the same
runtime and original native arithmetic.

## Cause and repair scope

[`answer`](../../../cli/src/bea_engine/report.py#L137) now calls all of
`_cash_flow` inside `localcontext()` with `wide.prec = 100`, introduced by
`85c526173` for 1077. That context reaches the cash inventories as well as the
rounding-reconciliation calculation. The closing accumulation in
[`_cash_flow`](../../../cli/src/bea_engine/report.py#L1105) uses
[`CounterInventory.add`](../../../cli/src/fava/core/inventory.py#L127), whose
addition obeys the active context. Here it retains
`2000 − 999.9999999999999999999999999` at 100 digits, instead of the native
28-digit inventory result. The same `closing` values feed the statement's
bottom line and cash-account rows; a quiet opening copies the discrepancy.

The protocol's Decimal serializer at
[`protocol.py:338`](../../../cli/src/bea_engine/protocol.py#L338) faithfully emits
fixed-point digits. The
[`cash-flow` frontend](../../../cli/src/cli/commands/report.py#L619) forwards the
payload unchanged for JSON and uses normal display precision for human output.
Caller search finds one Cash Flow dispatch; changing the renderer cannot repair
the underlying amount. Other report commands continue using the native context.

Keep reported cash-account inventories and opening/closing amounts consistent
with native Beancount, Register and Balance Sheet. Reconcile accepted cost
rounding without changing that cash arithmetic contract. Retain the new success
of repeated purchases and costed postings carrying prices, and preserve genuine
price-weighted FX refusals. Do not round or rewrite the inferred posting, alter
native booking, add an epsilon, or hide the difference in JSON formatting.
CLI-local; no dependency or API changes are needed.

This follows [ADR024](../../../docs/adrs/ADR024-cli-cash-flow-report.md)'s CCE
balance semantics and 1071's original acceptance requiring native cash bounds.
The precision context may be local to one command, but its scope still changes
the inventory result that command promises to report.
