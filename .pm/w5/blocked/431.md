# `add balance`, `add price` (new price) and `add transaction` with a bare number load the whole ledger, plugins included, an extra time for a pre-check, so they take ~35% longer than a plain add and run plugin side effects twice

**Current scope, 2026-11-04:** the owner approved the ordinary-transaction
validation standard below. That independent implementation is ready in
[w5/1120](../1120.md). This note remains blocked only for the balance/price/pad
pre-read redesign; its original report and blocker are retained as history.

**Trivial · cli · 20–30m · A2.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Most `add` commands load the ledger once, the validation load of the
proposed ledger. Three paths first do a full `managed_load.load_file`
of the current ledger for a pre-check, then validate with a second load.
Each load runs every plugin. A2, because the pre-reads are deliberate
under w5/115's snapshot rule. The cost is time and doubled plugin side
effects, not wrong output. No product fix implemented.

The hunter used a counter plugin that appends one line per invocation,
on a small ledger and on a 10k-transaction ledger, with a fresh
`XDG_CACHE_HOME` per run.

| Command | Loads | Time at 10k |
|---|---|---|
| `add transaction` (explicit amounts), `add open/close/note/…` | 1 | 0.82 s |
| `add transaction -p 'Expenses:Food 1'` (bare number) | 2 | 1.10 s |
| `add balance` (succeeds or fails), `add price` (new price), `add pad` | 2 | 1.11 s |

Both fixtures gave the same counts. I confirmed the call sites.

Expected: one load per single `add`, as the other kinds manage.

Cause: full loads made only for pre-checks:

- the balance duplicate/conflict pre-read,
  `cli/src/bea_engine/ledger/adding.py:293`;
- the price conflict pre-read, `adding.py:598`;
- currency inference for a bare number, `adding.py:724`.

Fix: run these checks against the single validation load, excluding the
appended lines, or use a plugin-free parse where realised entries are not
needed (currency inference needs only `Open` directives). No dependency
change.

Blast radius: `add balance`, `add price`, `add pad` and bare-number
postings, on large ledgers or with side-effecting plugins.

Dedupe: w1/167 budgets bulk-refusal loads. r48 measured only plain `add`.
430 is the `check` double load. None covers these pre-reads.

Acceptance: the counter plugin runs once for each command in the table,
and the conflict and duplicate refusals are unchanged. A test counts
plugin invocations.

---

**Blocked 2026-10-15** — Still wanted, but the fix is a design change to the shared write path rather than a local edit, and both routes break something the acceptance requires. Triage at HEAD `1674c3bc` confirmed all three pre-reads (`cli/src/bea_engine/ledger/adding.py`: the balance pre-read before `_balance_match`/`_balance_conflict`, the price pre-read before the local/managed price scan, and the bare-number `Open` scan in currency inference). Each needs more than raw text:

- `add balance` turns a same-date assertion into "already recorded" (no write) or "already has a … balance … Pass --force". Run against the single validation load, the conflicting case fails validation inside `validate_candidate` before any caller could see it. Keeping that refusal means `validate_candidate`, shared by every write, has to hand callers the candidate's realized entries and pre-existing errors before it judges them. That reworks w5/115's capture → decide → write rule.
- `add price` must see managed-feed prices (the "shadows the managed quote" warning) and filter plugin-made `implicit_prices`. A plugin-free parse loses both.
- Strict callers (`strict_read`) gate on the current ledger's errors, with today's wording.

A plugin-free pre-check would remove the extra loads, but it changes the duplicate and conflict refusals that the acceptance says must stay unchanged: plugin-made balances (`check_closing`), managed shadows, and strict-read errors.

**Original unblock condition (2026-10-15):** the maintainer picks a route. (a) Add a pre-commit inspection hook to `validate_candidate`, so these checks read the candidate load: one load, refusals kept, at the cost of a refactor of the core write path. (b) Accept plugin-free pre-checks with the semantic differences listed above. The bare-number currency inference is the cheap independent piece under either route. It needs only `Open` directives and `operating_currency`, so a scan of the snapshot's files removes its load. The only difference is a plugin-generated `Open` that carries currency constraints, which `auto_accounts` does not produce.

## Confirmed decision and remaining block — 2026-11-04

The owner confirmed that ordinary transactions must receive one full candidate
ledger validation before committing; parameter checks can occur earlier,
completion should avoid full loads wherever possible, and identical genuine
purchases must remain separately appendable. The rationale is to eliminate
unnecessary engine/plugin execution while preserving accounting validation and
legitimate repeated transactions. No content deduplication or request-key
feature is authorized by this performance decision.

This clears the decision blocker for the independent transaction work, now
tracked solely in [w5/1120](../1120.md). It does not choose the balance/price
redesign, change their acceptance criteria, or establish that a fix shipped.

Current-source review also found an existing `inspect` callback in
`validate_candidate`; balance duplicate checks now use authored entries, and
price warnings have additional preview logic. The 2026-10-15 mechanism notes
above are historical, not an instruction to add a duplicate callback or restore
old plugin semantics. The extra pre-reads still exist in the reviewed source.

**Unblock:** the CLI maintainer/owner chooses the remaining balance/price/pad
approach: preserve current duplicate/conflict, managed-price warning and
strict-read behavior while refactoring the shared validation flow, or
explicitly accept a precisely described behavior change. Next, the worker
must recheck these cases against current source and existing tests and record
the selected behavior before this residual note returns to the inbox. The
ordinary-transaction decision alone does not unblock this residual scope.
