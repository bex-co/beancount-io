# Decide the supported way to give a custom importer a third-party dependency

**Severity:** minor (documentation/product decision, not a defect). **Estimate:** 30–45 minutes. **Owner:** cli. **A1:** an agent or author writing a custom importer that needs a third-party package can see *which* environment needs it, but not a supported way to put it there.

Split out of [w5/013](./done/013.md) on 2026-09-16, which fixed the wrong half of the problem — the error message that named the frontend instead of the managed engine. That wording is now correct (`b2650f1f`) and this note covers only the open question it deliberately left.

## The gap

Importer configurations execute under the managed engine interpreter, so a `import some_package` in a config needs that package installed in the managed engine. Today:

- `bea engine enable` covers only the known optional features (`beangulp`, `beanprice`). There is no supported command for an arbitrary package.
- `cli/docs/IMPORTING.md` answers vaguely: add third-party importer packages "the same way you would for any engine-side dependency once Beangulp is enabled, or keep a separate project environment for custom importer development." Neither branch is a concrete instruction.
- `BEA_ENGINE_PYTHON` would technically work — point it at an interpreter you prepared yourself — but `cli/docs/USAGE.md` frames it as an advanced override for "tests and recovery tooling" that ordinary installs never set. Recommending it as the routine answer for custom importers contradicts that framing.

The managed engine is also provisioned from generated runtime locks (`scripts/export-runtime-locks.py` from `src/cli/engine/manifest.json`), so anything installed into it by hand is liable to be lost on the next re-provision — which is itself part of what makes this a decision rather than a doc tweak.

## What to decide

Pick one and make the docs and the error message say it in one line:

1. **A supported command** — extend `bea engine` to install an arbitrary package into the managed engine, accepting that it must survive or be re-applied across re-provisioning.
2. **`BEA_ENGINE_PYTHON` is the answer** — promote it from "tests and recovery tooling" to the documented path for custom importer development, and say so in `USAGE.md` as well as `IMPORTING.md`.
3. **Out of scope by design** — custom importers with third-party dependencies are for people running their own engine environment, stated plainly, so nobody goes looking for a command that will not exist.

## Not in scope

The `ImportError` wording itself, which w5/013 already fixed and which points at `docs/IMPORTING.md` correctly under any of the three answers.

## Blocked

**Blocked 2026-09-16** — This note is a product decision, not a defect, and the three options above lead to materially different work: option 1 adds a new `bea engine` command and a re-provisioning story, option 2 changes how `USAGE.md` frames `BEA_ENGINE_PYTHON` for every reader, and option 3 closes the door and only edits docs. Picking one from the repository alone would be inventing product direction: nothing in the code, the ADRs or the board says which is intended, and each rules the others out.

**Unblock:** the user (or whoever owns CLI product direction) picks option 1, 2 or 3. Once chosen, the work itself is small — one `IMPORTING.md` section, a matching line in the `ImportError` message, and for option 1 the command and its tests.

Nothing is waiting on this. The defect it was split from ([w5/013](../done/013.md)) is fixed and shipped in `b2650f1f`: the error message now names the managed engine and points at `docs/IMPORTING.md`, which is correct under all three answers. This note only covers making that documentation concrete.
