# Validate ordinary added transactions once before committing

**Minor · cli · 45–60m · A1/A2.** Worker: worker1. Ready for implementation;
split from the independently actionable transaction portion of
[w5/431](431.md) after the owner's decision on 2026-11-04.

**Decision confirmed 2026-11-04:** ordinary transactions receive one full
ledger validation before committing. Parameter and transaction-syntax checks
may run earlier. Completing omitted information should avoid a full ledger
load wherever possible. Two genuine purchases with identical date, payee,
amount and postings must remain separately appendable.

The approved flow is: check the input; acquire the existing ledger-graph lock
and consistent snapshot; complete the transaction; stage the candidate ledger;
load and validate that candidate once, including normal plugins and accounting
checks; verify the original snapshot is unchanged; atomically commit. A failed
validation or changed snapshot must leave the original ledger unchanged. No
second full validation is needed after committing an unchanged validated
candidate.

## Current evidence and implementation scope

Source reviewed 2026-11-04: `cli/src/bea_engine/ledger/adding.py`,
`_transaction`, still calls `managed_load.load_file(file)` when a posting gives
a number without its currency. It reads `Open` currency constraints and
`operating_currency`, then `write.append` separately validates the complete
candidate in `cli/src/bea_engine/ledger/write.py`. The counter-plugin QA and
historical timings are retained in 431; this decision review did not rerun
those measurements or implement a product fix.

Remove the avoidable full load for ordinary currency completion, reusing the
existing snapshot and native parsing facilities rather than introducing a
second parser or weakening validation. Preserve include/root options, account
currency constraints, unambiguous inference and clear ambiguity refusals.
Plugin-generated constraints must not silently disappear from supported
behavior. `--allow-errors` and investment paths that need the old ledger for
error comparison or lot state can require additional loads; keep their
existing guarantees and document the reason rather than treating the ordinary
one-load target as permission to remove necessary reads.

## Acceptance

- On an ordinary valid ledger, explicit-currency and inferable bare-number
  coffee transactions each run one full candidate validation and invoke a
  counter plugin once per successful add.
- Two separate adds with the same date, payee, amount and postings append two
  transactions with the correct combined balance. Do not introduce content
  deduplication or a new idempotency-key feature. The local add command does
  not currently promise request-key replay protection.
- Early malformed-input refusals need no full ledger load; ambiguous currency
  and accounting-validation failures leave all original ledger files intact.
- A candidate remains subject to whole-ledger checks, including downstream
  balance assertions and plugins. Locking, snapshot checks and atomic commit
  guarantees remain in place.
- Add meaningful real-CLI regressions for the load/plugin count, repeated
  identical transactions and safe refusals; run `make check-all` from `cli/`.

Balance/price/pad pre-read redesign remains in blocked 431. This note makes no
decision about changing their duplicate, conflict, warning or strict-read
behavior, adds no dependencies, and does not modify import duplicate review.

**Blocked 2026-11-05** — The ordinary counter-plugin repro still confirms one
invocation for explicit currency and two for a bare number. An optimistic
native-snapshot completion was implemented but is not safe to ship: comparing
the candidate's effective currencies with authored declarations cannot reveal
every constraint the plugin supplied before the transaction existed.

A fresh real-CLI counterexample uses operating currency USD, two unconstrained
authored Opens and a stateless plugin that supplies EUR constraints only before
a transaction named Coffee exists. On shipped `74c5e9e91`, the original-ledger
load selects EUR and the valid candidate writes 5 EUR / -5 EUR. The optimistic
candidate-only route also succeeds but writes 5 USD / -5 USD. A second variant
terminates on a USD candidate before the inspection callback: the shipped route
still succeeds with EUR, while the optimistic route refuses. Both are concrete
compatibility failures, not an opportunity to weaken accounting checks.

Arbitrary unknown plugins require evaluating the original state to preserve
that behavior, as well as evaluating the candidate to validate the new entry.
The current requirement that a custom counter plugin runs once therefore
conflicts with preserving every original-state plugin-generated currency
constraint. The owner has been asked to choose the completion contract; no
answer is inferred from elapsed time.

Partial code and its usage-document draft are isolated in local named stash
`loopx-w5-1120-partial-20261105`
(`1bd429c10803255025702941bc709a286af8bd90`). This is an unsafe experimental
candidate, not a fix to apply without revising its contract. Sanitized repros
are retained under `cli/tmp/1120-plugin-context-e4vqmqa_/` (`results.json` and
`exit_results.json`), plus `cli/tmp/loopx-w5-1120-baseline.jsonl`. No product
changes from 1120 shipped.

**Unblock:** the CLI owner chooses either (a) preserve existing plugin behavior,
allowing the necessary original-ledger read for unknown custom plugins while
keeping ordinary plugin-free writes at one full candidate validation, or
(b) define currency completion from authored Open/options and explicitly accept
the changed plugin-completion semantics. A separately approved currency-neutral
plugin capability could provide another route, but none is currently promised.
Record the choice, revise the counter-plugin acceptance accordingly, then
implement and verify the repeated-purchase, inference, plugin and atomic-write
regressions with a green `make check-all`. Balance/price/pad scope remains 431.
