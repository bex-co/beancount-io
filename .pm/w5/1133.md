# The personal access token page still says tokens are for the API, and no scope says which one Git clone or push needs

**Severity:** minor. **Owner:** dashboard. **Estimate:** 25–40 minutes. **A1/A2:** since w3/m68 a personal access token is also the Git HTTPS password, and the clone dialog now sends readers to this page, but the page gives them no way to choose the right permission. **Found by:** `/qa-find-bugs-dashboard` on 2026-11-15 against `https://beancount.io` (local HEAD `ae0e4c7ba`; the copy below is unchanged at HEAD), headless Chromium at 1440×1000, signed in as the QA account. Nothing was created: the New token dialog was opened and cancelled.

## Repro

1. Open `/settings/api-keys`. The description reads "Create scoped credentials for scripts and integrations that use the Beancount.io API."
2. Activate **New token**. The permissions read `ledger.read` "Read ledger data.", `ledger.write` "Create and update ledger data.", `ledger.admin` "Perform administrative ledger operations.", with "Start with read access and grant more only when required."
3. Compare with the clone dialog's HTTPS hint at HEAD (`ledgerEditor.httpsCredentialHint`, shipped in w3/m68 and linking here): "Username: anything. Password: a personal access token, not your account password."

**Actual:** neither surface mentions Git. A reader who follows the hint keeps the default `ledger.read`, which can clone and pull but not push (m68: `git-receive-pack` needs `ledger.write`). Their first `git push` then fails with a 401 that looks like a wrong password, which is also the failure a stale stored credential produces (m68 t003).

**Expected:** the page says that a token also works as the Git password over HTTPS, and the scope descriptions say what each one allows in Git: `ledger.read` clones and pulls, `ledger.write` is needed to push.

## Fix

Owned by `dashboard`, in `src/features/user-settings/pages/api-keys/translations.ts` and its 15 locales:

- `userSettings.apiKeysDescription`: name Git over HTTPS alongside the API.
- `userSettings.apiKeyReadScopeDescription` / `apiKeyWriteScopeDescription`: add "clone and pull" and "push" respectively.
- Optionally, update `userSettings.apiKeysEmptyDescription` ("when a script or integration needs API access") the same way.

Keep the backend scope mapping unchanged.

## Acceptance

- `/settings/api-keys` and the New token dialog say that a token works as the Git HTTPS password, and that pushing needs `ledger.write`.
- Every supported locale carries the new strings, translated like their neighbors.
- The existing `api-key-create-dialog.test.tsx` / `api-key-page.test.tsx` assert the Git wording, and the dashboard checks pass.
