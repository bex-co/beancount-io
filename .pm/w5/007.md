# `bea add` rejects scientific-notation amounts on three paths and silently accepts them on the fourth

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** cli. **A1:** an
agent generating a batch from a float-producing serializer gets `1e3 USD`
written happily by `add transactions`, then exit 2 from `add transaction` for
the identical value — two documented entry points disagreeing about the same
input.

Found 2026-09-15 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME` and `BEA_NO_UPDATE_NOTIFIER=1`. Synthetic
local fixtures only.

## Repro

```sh
bea --no-input init books --currency USD --date 2026-08-01
cat > batch.json <<'JSON'
[{"date":"2026-08-05","narration":"x",
  "postings":[{"account":"Assets:Cash","amount":"1e3 USD"},
              {"account":"Expenses:Dining"}],
  "tags":[],"links":[]}]
JSON

bea --file books/main.bean add transactions --from batch.json      # exit 0, writes
bea --file books/main.bean add transaction "t" --date 2026-08-07 \
    -p "Assets:Cash 1e3 USD" -p "Expenses:Dining"                  # exit 2, refuses
```

The single-posting form refuses with a dedicated message:

```text
Error: Scientific notation '1e3' is not supported in Beancount amounts.
Use decimal notation, such as '1000' instead of '1e3'.
```

The bulk form writes:

```text
2026-08-05 * "x"
  Assets:Cash  1000 USD
  Expenses:Dining
```

## Behavioral matrix

Same value, `1e3 USD`, against the same ledger:

| Path | Exit |
| --- | --- |
| `add transaction --posting "Assets:Cash 1e3 USD"` | 2 |
| `add balance --amount "1e3 USD"` | 2 |
| `add price --amount "1e3 USD"` | 2 |
| `add transaction -p "Assets:Brokerage 10 AAPL {1e2 USD}"` (cost spec) | 2 |
| `add transactions --from batch.json` (`"amount": "1e3 USD"`) | **0** |
| `import sci.csv --account Assets:Checking` (`Amount` column `1e3`) | **0** |

The split falls exactly on argv-parsed versus file-parsed input: every amount
typed as a command-line argument is rejected, and every amount read out of a
file — a JSON batch row or a CSV amount column — is accepted and normalized.
The CSV case writes `Assets:Checking  1000 USD` from a cell reading `1e3`.
Nothing documents that distinction.

The file-parsed paths accept every exponent form and expand them correctly:
`1e21` and `1E+21` both write `1000000000000000000000 USD`, `1e-7` writes
`0.0000001 USD`, and `-2.5e3` writes `-2500 USD`. `bea check` on the resulting
ledger exits 0 in every case, so this is an input-validation inconsistency, not
data corruption — nothing malformed reaches the file.

## Expected / actual

`cli/docs/USAGE.md` (Adding directives) states the rule for the whole section,
which covers both forms: "Amounts use decimal notation (e.g. `1000`, not
`1e3`)". The three single-directive paths enforce it; the bulk path does not,
and says nothing.

Expected is one answer for both. Either is defensible, and the evidence
favors accepting:

- **Accept everywhere** — the bulk path already demonstrates that the value is
  parsed to a `Decimal` and written in plain decimal notation, so nothing
  invalid can reach the ledger. Drop the guard, and soften the `USAGE.md`
  sentence to say amounts are written in decimal notation.
- **Reject everywhere** — apply the existing guard to the bulk rows too, so a
  batch fails with the same row/field-path error shape the other schema errors
  already use.

Actual: the guard is applied on three paths and skipped on the fourth.

## Root cause

`cli/src/cli/commands/add.py:62-71` defines `_check_decimal_notation`, and it is
called from exactly three places: `:52` (the decimal option parser), `:152`
(`--posting` text) and `:224` (`add balance` / `add price` `--amount`). The bulk
command at `:451` reads its rows through `_load_transactions_json` (`:425-442`)
and hands them to the engine without ever calling it; the engine's model coerces
the string with `Decimal`, which accepts exponents.

The comment at `:220-222` — "this only rejects an exponent, which no Beancount
amount accepts" — is accurate about Beancount's *grammar*: `1e3` is not valid in
a `.bean` file. It is the CLI's input layer, not the file format, that the two
paths disagree about, and the bulk path is safe precisely because it normalizes
before writing.

## Fix

Pick one of the two behaviors above and make all four paths agree. If rejecting,
raise the error during row validation so it arrives as
`Row N, postings.0: …` alongside the existing schema errors rather than as a
global usage error, and keep `--partial` semantics intact. If accepting, delete
`_check_decimal_notation` and its three call sites rather than leaving a guard
that only some inputs meet. Either way update the `USAGE.md` sentence and add
coverage that pins the same verdict for `--posting`, `add balance --amount`,
`add price --amount` and a `--from` batch row.

## Blast radius and adjacent states

Affects amount strings only, on both file-parsed paths (`add transactions
--from` and `import --csv`). Every other bulk-input validation behaves
correctly and leaves the ledger byte-identical: a non-array top level
(exit 2), invalid JSON syntax with line/column (exit 2), a non-object row, both
`units` and `amount` on one posting, an unknown posting field, and a
non-ISO date all produce `Row N, <field path>: …` errors at exit 1. An empty
array is a no-op at exit 0. `--partial` still writes accepted rows and exits 1.

## Dedupe

Searched all `.pm/**/*.md`, including `done/`, for scientific notation,
exponent, `1e3`, and bulk-transaction validation terms. The hits are unrelated —
`.pm/w4/done/024.md` is mobile chart-axis number formatting and
`.pm/w3/done/136.md` is dashboard import selection. No item covers CLI amount
parsing, and nothing on the board mentions `_check_decimal_notation`.
`git log -S '_check_decimal_notation' -- cli/src` shows the guard arriving with
`790791ac` and never extended to the bulk path. Reproduced at `b78efe7d`, so
not deployment lag.

## Evidence and unverified areas

Bounded subprocess captures under `cli/tmp/qa-20260915/run5/cases/` recorded
argv, cwd, isolated environment, separate streams, exit codes, and the resulting
ledger text plus a `bea check` re-validation for each exponent form. Synthetic
fixtures only. Cost-spec (`{1e2 USD}`) and CSV amount-column cases were
exercised and are included in the matrix above. Not exercised: exponent forms
in a Python importer's extracted amounts, and Windows.
