# The `bea login` device page shows two "Authorize a device" h1s after a too-short code, and an unknown code drops keyboard focus to the page body (gap in w5/1163)

**Severity:** minor (accessibility; WCAG 1.3.1, 2.4.3, 2.4.6). **Owner:** `dashboard`. **Estimate:** 15–25 minutes including tests. **A1/A2:** `bea login` sends people, and the agents working for them, to this page. w5/1163 gave it one `main` and one `h1`. Its error states break that. A screen-reader user who mistypes the code hears the page title twice in the heading list. After a code the server does not know, focus goes nowhere. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, production entry chunk `main-BBmi61Hs.js` (contains `d31a395a2`, the w5/1163 fix). QA-owned headless Chromium 158, isolated context, 1440×1000, English, signed in as the QA owner. Two unknown codes were submitted; no device was authorized. Local HEAD `dd228d85f`.

## Repro

Signed in, open `/auth/login/device`. The **One-time code** field has focus.

1. Type `abc` and press Enter. The alert "Enter the 8-character code shown in your terminal." appears, and focus stays in the field. The page now has **two** `h1` elements, both "Authorize a device": a `sr-only` one and the card's own title. Before the error, there was one.
2. Reload and type an 8-character code no terminal issued (`ZZZZ9999`). The page submits once (one `GetCliAuthRequest`) and shows the alert "This code is unknown or has expired. Run `bea login` again…" with **Use a different code**. `document.activeElement` is `BODY`: the field that had focus was unmounted with the form. One Tab reaches **Use a different code**, and Enter returns to the field with focus in it, so only the step in between is broken.

## Cause

- `dashboard/src/features/auth/pages/device-auth-page/device-auth-card.tsx:30-31` renders a `sr-only` `h1` whenever `loading || error`, for the loading and error cards, which have no title of their own. `cli-auth-code-entry-view.tsx:146` passes its validation `error` to the same card, and its form keeps its own `<h1>` (`:160`). A too-short code therefore renders both.
- `index.tsx` (`CliAuthRequest`) swaps the entry form for the loading card and then for the error card. No element takes focus on that swap. `RestartFooter`'s button is the only control left.
- `__tests__/cli-auth-code-entry-view.test.tsx:159-163` covers the short-code message but not the headings. The one-`h1` checks (`:32-37`, `:47-58`) cover only the clean entry and consent states.

## Fix

Render the `sr-only` heading only when the card has no title of its own. One way is a `title` prop or a flag that the entry view sets, so a validation error on the entry form keeps exactly one `h1`. When the unknown/expired (or other error) card replaces the form, move focus to its alert or heading (`tabIndex={-1}`) or to **Use a different code**, so focus never lands on `body`. Copy, the attempt budget and the one-request-per-code behaviour do not change.

## Definition of done

- `/auth/login/device` has exactly one `h1` in the clean entry state, after a too-short code, while loading, in the unknown-code state and in the consent state.
- After an unknown code, `document.activeElement` is inside the card (its heading, alert or **Use a different code**), not `body`.
- Rendered tests assert both and fail on the current code. Dashboard gates pass.

## Dedupe

Searched `.pm/**`, including `done/`, for `login/device`, `device-auth`, `cli-auth`, "Authorize a device", and device focus. w5/1163 (done, `d31a395a2`) added the landmark and headings, and its DoD asks for one `h1` "in both the code-entry and approve states". The error variant of the entry state was not covered. w0/019 (done) is the unknown-code wording. No open item covers either. `main` is unchanged since `d31a395a2`, so this is not deployment lag.
