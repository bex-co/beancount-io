# Retry the engine publish rename on Windows and sweep stale partial engines

**Major · cli · 45–60m · A2 · worker1.** Found by the native Windows
rehearsal in [w5/m13/t004](./m13/done/t004.md), 2026-10-28: published
`bea 0.3.1` (uv tool) on Windows 11 Pro 26H2 ARM64, build 26300, Windows
PowerShell 5.1, Microsoft Defender active. Evidence in
[the Windows rehearsal](../../docs/skills/windows-rehearsal.md).

First use cannot provision the managed engine. In an agent session and in
a plain terminal, `bea` fails with:

```text
Could not move the finished engine into place at …\bea\engine\0.3.1:
[WinError 5] Access is denied: '…\engine\0.3.1.partial.<pid>' -> '…\engine\0.3.1'
```

A standalone repro shows Windows keeps the freshly built virtual environment
locked for about 29 seconds after `uv pip install` returns. `_publish` in
`cli/src/cli/engine/provision.py` tries `os.replace` once and gives up, so
every retry rebuilds and fails the same way.

Each failure also leaves a `.partial.<pid>` engine of tens of megabytes. The
stale-directory sweep never removes them on Windows because
`_process_alive` returns `True` for every PID there.

The documented workaround (build with uv and the shipped hash lock, wait,
then rename) is in `docs/skills/installation.md` under "bea on Windows".

**Fix:** retry the publish rename with bounded backoff on Windows for
`PermissionError`/WinError 5 and 32 before failing. Give `_process_alive` a
real Windows liveness probe (for example `OpenProcess` through `ctypes`), so
stale partial engines are swept. Add tests for both, ship a CLI release, then
remove the workaround block from installation.md and rerun the m13 first-use
step on Windows.
