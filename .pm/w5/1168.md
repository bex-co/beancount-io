# Invite Collaborators: "Invite (2)" adds only the first person chosen, and a failed invite closes the dialog and forgets the selection

**Severity:** major (silent partial write). **Owner:** dashboard. **Estimate:** 1 hour including rendered tests. **A3:** an owner sharing a ledger with two people sees a success toast, but only the first person gets access. The second is dropped without a word. **Found by:** `/qa-find-bugs-dashboard` on 2026-11-18 against `https://beancount.io` (entry chunk `main-LGv2TZLj.js`), headless Chromium 153 at 1440×1000, English/light, signed in as the QA owner on the synthetic ledger `mcp-agent-eval`. No invitation was sent: the second search result was a synthetic response served by the test browser, and the add request was aborted before it left the browser. Ledger Settings still reads "No Collaborators". Local HEAD `a95dfa7d3`.

## Repro

1. Ledger Settings → **Invite Collaborator**. Type `open_ledger` into **Search Users** and choose the result. Search again and choose a second user. The dialog lists both under **Selected Users**, and the button reads **Invite (2)**.
2. Choose **Invite (2)**. The browser sends exactly one `AddLedgerCollaborator`, `{ ledgerId, collaborator: "open_ledger", permission: "read" }`. The second user is never sent. By the code, a successful add then shows "collaborator added", closes the dialog and clears the selection. The success path was not run live, since it would share the ledger.
3. If that one request fails (here: aborted), the toast reads "Failed to add collaborator · Connection problem…". The dialog still closes and the selection is still cleared, so the owner must search for everyone again.

Also in the same dialog (by observation):

- Each selected user's remove control is an unnamed `button`, so a screen reader announces only "button".
- Choosing a result with Enter removes the focused result button, and focus falls to the dialog container instead of the search field.
- Escape, Close or an outside click with users selected closes the dialog at once and discards the selection, without the **Discard what you typed?** question (w2/123, w2/134). Invite also does not pass `busy`, so Escape closes the dialog while the write is pending.

## Cause

- `dashboard/src/features/ledger-data/settings/collaborators-section/index.tsx:85-108`: `handleInvite(users, permission)` sends `users[0].username` only. It also catches every failure itself (toast) and resolves normally.
- `dashboard/src/features/collaboration/components/invite-collaborators-dialog.tsx:41-51`: after `await onInvite(…)` it always clears `selectedUsers` and closes. Because the caller swallowed the error, the failure path closes too. `DialogContent` (`:76`) has no `busy`, and there is no `useDiscardDraftGuard`.
- `dashboard/src/features/collaboration/components/multi-user-search.tsx:81-86` appends to the selection, so selecting several users is supported. The remove button at `:232-239` is icon-only with no `aria-label`.
- `addLedgerCollaborator` takes one `collaborator`, so the dialog must send one request per user.

## Fix

- Send one `AddLedgerCollaborator` per selected user, one at a time or with bounded parallelism, then refetch the list once. Report the outcome per user: "Added 2 collaborators", or "Added open_ledger; couldn't add <user>: <reason>". Keep only the users that failed selected, and leave the dialog open when any failed. Keep the existing owner-limit wording (w1/181) for a limit refusal.
- Hold the dialog during the write: `usePendingAction` plus `busy={pending}` on `DialogContent`. Route dismissals through `useDiscardDraftGuard(selectedUsers.length > 0)`.
- Name each remove button (`Remove <username>`, localized), and return focus to **Search Users** after a result is chosen.
- Alternatively, make the search single-select and rename the dialog "Invite collaborator". Do not leave a multi-select that writes one user.

## Definition of done

- Selecting two users and choosing **Invite (2)** sends two adds. Both appear in the Collaborators table after one refetch, and the toast counts both.
- When one add fails, the dialog stays open with that user still selected and the error beside **Invite**. The user who was added is not offered again.
- Escape with a selection asks before discarding. Escape during a pending invite does nothing. Every remove button has a name, and choosing a result leaves focus in **Search Users**.
- Rendered tests cover two users, a partial failure, and the discard question, and fail on the current code. Dashboard gates pass.

## Dedupe

Searched `.pm/**` for Invite Collaborators, `multi-user-search`, `addLedgerCollaborator` and `users[0]`. w4/done/1050 (retrying the Collaborators read) and w5/1164 (the "Transactions" header) touch the same section, not the invite. w2/done/134 added discard guards to four other dialogs but not this one. `users[0]` dates back to the initial import (`af5339de0`), so it is not deployment lag.
