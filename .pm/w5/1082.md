# Distinguish invalid decimal text from query precision failures

**Minor · cli · 25–40m · A1 · worker1.** A native CSV query over a blank
amount, or a decimal-comma string such as `12,50`, correctly fails but says
its result needs more than 28 significant digits and recommends rounding
or smaller numbers. These inputs never produce a Decimal: the native
column converter raises `ConversionSyntax`. The advice cannot repair the
data. Existing exports are preserved; no money or source data is changed.
No product fix made.

```sh

```

Use `comma text` in another directory for the other input/output variant.
The recipe captures commands, safe environment, separate streams, exits,

The initial CSV column `amount` is inferred as Decimal from the valid
first row `12.50`; its next value is blank (`blank`) or `12,50` (`comma`).
The CSV syntax is valid, including quoting around `12,50`. The target is
ordinary BQL: `SELECT day,amount,merchant FROM bank ORDER BY day`.

Both text and CSV query output modes return exit **1**, empty stdout, and:

```text
error: Decimal arithmetic failed while running this query (InvalidOperation): a result needs more than the 28 significant digits the arithmetic keeps. Round to fewer places, or keep the numbers smaller. Pass --debug before the command for a traceback.
```

Independent native Beanquery execution raises
`InvalidOperation([decimal.ConversionSyntax])` in
`beanquery.sources.csv.Column.__call__`, where `self.func` is Decimal and
`row[self.key]` is that CSV value. It is not a display overflow, arithmetic
precision failure, NaN or infinity. `SELECT count(*)` still answers 2 because
it need not convert those cells; fixing the data to valid decimal-point text
makes the original query succeed and replaces the export with the new result.
Every failed query leaves the preceding successful export byte-identical.

Expected: preserve the failure/status and export protection, but explain that
an input value cannot be read as decimal text. Do not advise rounding or
smaller numbers for `ConversionSyntax`. Native CSV may continue rejecting
these values: this task changes diagnostics, not its schema inference,
missing-value policy, decimal-comma support or BQL evaluation.

| Mode | Observed / required disposition |
| --- | --- |
| `blank` | second amount is empty; failure is misdiagnosed as precision |
| `comma` | second amount is `12,50`; same misdiagnosis |
| `round` | `round(amount,30)` really exceeds the arithmetic precision; current advice is correct |
| `good` | ordinary Decimal cells query/export successfully |
| `first-blank` | first amount is empty, so native inference chooses text; query succeeds unchanged |
| `literal` | BQL `decimal('rail')` intentionally returns NULL; query succeeds |

The last two controls matter: do not turn every empty cell or invalid string
into an error. Explicit BQL `decimal()` catches failed conversions itself;
this bug arises when the native CSV typed-column converter calls Decimal
directly. `--source` also deliberately refuses `--json`; no JSON defect or
new output mode is proposed.

## Cause and repair

`cli/src/bea_engine/query.py:1168–1198`, `decimal_failure`, first distinguishes
native display overflow and non-finite operands. Its remaining
`isinstance(exc, InvalidOperation)` branch assumes every other signal means
insufficient 28-digit precision. `ConversionSyntax` also belongs to
InvalidOperation and falls into that branch. The classifier's AST is
unchanged from `19b1c0fce`, [846](./done/846.md)'s item3 repair, which correctly
handled its two finite precision examples but did not cover failed conversion.

Recognize the conversion signal before the generic precision wording and
say that a value is not valid decimal text. A source/column detail is useful
when available, but removing the false diagnosis does not need a CSV parser
fork or a new dependency. Preserve actual precision, native rendering-limit,
non-finite and unexpected-exception messages, the debug hint/stack, and the
existing nonzero status. Never silently substitute zero or skip the row.

Caller search finds `unexpected_failure` at :1164 (native query failures)
and `_compiled` at :2407 (local query error translation). This reproduction
exercises native CSV one-shots in text/CSV modes. The same helper is used by
recovery/error paths, so keep mode-specific existing messages. Local BQL's
invalid-string-to-NULL control remains successful; it is not another
reproduction. No API, generated client or other package change is required.
