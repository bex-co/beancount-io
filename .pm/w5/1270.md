# New Entry ignores a known payee: picking "WHOLE FOODS" leaves the narration and both postings empty, though Fava and the mobile app fill them from the payee's last transaction

**Severity:** minor (Fava parity, data entry speed). In Fava's add-transaction form, choosing a payee that already exists fills the narration and postings from that payee's most recent transaction, as long as the narration and every posting account are still empty. The native app's New Transaction fills the payee's usual accounts the same way (w21/023). The web app's New Entry keeps whatever was typed, so every repeat purchase needs its accounts picked by hand. The backend already answers the lookup on GraphQL, REST and MCP. **Owner:** `dashboard` (`features/journal`). **Estimate:** about an hour, including tests. **A2:** most entries a person types are repeats ("WHOLE FOODS again"). Someone moving from Fava expects the second one to take a payee and an amount, not four picks.

**Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-28 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English/light, signed in as the QA owner on its designated disposable ledger. That ledger's `main.bean` is the synthetic fixture `backend-cluster/backend-v2/evals/mcp-agent/fixtures/main.bean`. Nothing was saved: each draft was closed with **Discard**. Local HEAD `27a68409e`. The dashboard has never read the payee lookup: `git log -S getLedgerPayeeTransactions -- dashboard` finds only the generated schema in the import commit `af5339de0`. This is not deployment lag.

## Repro

On a ledger whose last `WHOLE FOODS` transaction is the fixture's `2026-08-20 * "WHOLE FOODS" "Groceries"` (`Assets:Bank:Checking -62.10 USD`, `Expenses:Food:Groceries 62.10 USD`):

1. Open Journal → **New Entry** (`/journal?action=new-entry&directive=transaction`). The form opens with today's date, `* Cleared`, an empty Narration and two empty postings in USD.
2. In **Payee**, type `WHOLE` and click the suggestion **WHOLE FOODS** (ArrowDown + Enter gives the same result).
3. Wait. Payee reads `WHOLE FOODS`. Narration stays empty, and **Posting 1 account**, **Posting 1 amount**, **Posting 2 account** and **Posting 2 amount** stay empty.
4. Open **Posting 1 account**. The list is in file order (`Assets:Bank:Checking`, `Assets:Bank:Savings`, `Assets:Cash`, `Liabilities:CreditCard:Visa`, `Income:Salary`, `Expenses:Food:Groceries`, …). It is not ranked for the payee.

Repeated from a fresh load. None of the 155 JavaScript chunks the page loaded mentions `getLedgerPayeeTransactions` or `getLedgerPayeeAccounts`.

**API control (same session):** `getLedgerPayeeTransactions(ledgerId: "<owner>/<ledger>", payee: "WHOLE FOODS")` returns `date 2026-08-20`, `narration "Groceries"` and postings `Assets:Bank:Checking -62.10 USD`, `Expenses:Food:Groceries 62.10 USD`. `getLedgerPayeeAccounts` for the same payee returns `Assets:Bank:Checking, Expenses:Food:Groceries, Assets:Cash, …`, with the payee's own accounts first.

**Expected:** picking an existing payee while the narration and every posting account are still empty fills the narration (`Groceries`) and the postings (`Assets:Bank:Checking -62.10 USD`, `Expenses:Food:Groceries 62.10 USD`) from that payee's last transaction. The date and status stay as they were, and every field stays editable. (Fava also lists the payee's accounts first in each account picker. That part is optional here.)

## Cause

- `dashboard/src/features/journal/components/new-directive-dialog/transaction-form.tsx:464-488` binds the payee to `PayeesCombobox` with `onValueChange={field.onChange}` only. Nothing reacts to a chosen payee.
- The dashboard has no GraphQL document for `getLedgerPayeeTransactions` or `getLedgerPayeeAccounts`. The types exist only in the generated schema (`dashboard/src/graphql/definitions.ts:2586-2588`).
- The producer exists: `backend-cluster/backend-v2/src/features/ledger/api/resolvers/ledger-data-resolver.query.ts:391-412` ("the most recent transaction for a payee, or null when none matches"). It returns null for a new payee (w6/019).
- Working control: the native app's `mobile/src/screens/multi-postings-transaction/payee-seed.ts` (w21/023, w21/045, w21/411) fills a picked payee's usual accounts.

## Fix

Owned by `dashboard`. No backend change.

- Add a `GetLedgerPayeeTransactions` document beside the dashboard's other ledger reads and run `yarn codegen`.
- In the transaction form, when the reader picks a payee from the suggestions (not on every keystroke), and the narration and every posting account are still empty, read that payee's last transaction. Fill the narration and the postings' accounts, amounts and currencies from it. Keep the date and status. A posting the form cannot express (a cost or price) gets its account only. An account closed by the entry's date is left blank, as the native app does (w21/045).
- A late answer must not overwrite anything typed meanwhile. A null answer (new payee) or a failed read leaves the form as it is.
- Optionally rank each posting's account suggestions with `getLedgerPayeeAccounts`, as Fava does.

## Definition of done

- In the repro, picking **WHOLE FOODS** fills Narration `Groceries`, Posting 1 `Assets:Bank:Checking` `-62.10` `USD` and Posting 2 `Expenses:Food:Groceries` `62.10` `USD`. The date stays today, and saving it books a balanced transaction.
- With an account or narration already typed, picking the payee changes nothing else.
- A payee with no history, and a failed lookup, leave the form unchanged, with no error shown.
- A component test with the real form fails on the current code: it picks a payee whose mocked last transaction has two postings and asserts the filled fields. A second test asserts that a typed account is kept.
