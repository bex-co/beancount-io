# A profile link with an unknown tab, such as `/ledger/open_ledger?tab=ledgers` or w3/630's own `?tab=follower`, opens a blank profile: no tab is selected and nothing lists under the header (gap in w3/630)

**Severity:** minor. **Owner:** `dashboard` (`features/user-profile`). **Estimate:** 20–30 minutes including a route-level test. **A2/A3:** `/ledger/open_ledger` is the public collection of example books that newcomers are sent to. The first tab reads **Ledgers**, so `?tab=ledgers` is the obvious thing to type or share, and a stale or mistyped tab is ordinary. These links return HTTP 200 and the profile header, then an empty page with nothing selected and no hint, signed in or out. w3/630 fixed the HTTP 500 and set the acceptance "`tab=follower` shows the Ledgers tab". The schema now drops the value, but the page still receives it. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English. Reproduced signed in as the QA account and in a fresh signed-out context. Read-only. Local HEAD `394abaf85`.

## Repro

Public profile, no sign-in needed.

| URL | Status | Tabs (`aria-selected`) | Tab panels | Below the tab strip |
| --- | --- | --- | --- | --- |
| `/ledger/open_ledger` (control) | 200 | Ledgers = true | 1 | "Ledgers 50 · Find a ledger…", the ledger cards |
| `/ledger/open_ledger?tab=overview` (control) | 200 | Ledgers = true | 1 | the same |
| `/ledger/open_ledger?tab=Followers` (control) | 200 | Followers = true, URL rewritten to `?tab=followers` | 1 | the follower list |
| `/ledger/open_ledger?tab=ledgers` | 200 | **all false** | **0** | **nothing** |
| `/ledger/open_ledger?tab=follower` | 200 | **all false** | **0** | **nothing** |
| `/ledger/open_ledger?tab=bogus` | 200 | **all false** | **0** | **nothing** |

The URL keeps the unknown value, so a reload shows the same blank page. Clicking a tab recovers. The same happens on any profile, including the reader's own (`/ledger/<you>?tab=ledgers`). Repeated from a fresh load.

## Cause

- `userProfileSearchSchema` (`dashboard/src/features/user-profile/lib/search.ts:62-71`) maps `tab` through `searchEnum`. For an unknown value that yields `undefined`, and the transform then leaves `tab` out of its result (`if (raw.tab !== undefined) search.tab = raw.tab`, `:71`).
- TanStack Router builds a match's search as `{ ...parentSearch, ...validatedSearch }` (`@tanstack/router-core` 1.167.0, `dist/esm/router.js:1162-1168`). The root route does not validate, so its search is the raw URL search. A key that the child's schema leaves out is not removed: the raw `tab: "ledgers"` survives into `useSearch({ from: "/ledger/$username" })`. A `z.object` field whose transform returns `undefined` keeps the key, so it does override. That is why the login, billing and file-blob schemas are not affected.
- The page passes `search.tab || "overview"` (`features/user-profile/pages/user-profile-page.tsx:70`, `:253`) as `initialTab` to `UserProfileTabs` (`components/user-profile-tabs.tsx:109-113`, `:141-143`). `<Tabs value="ledgers">` matches none of the four triggers and none of the four `TabsContent` panels (`:203-360`).
- The w3/630 tests call the schema alone (`routes/__tests__/search-typo-tolerance.test.ts:81-87` expects `parse({ tab: "follower" }).tab` to be `undefined`). They never see the merged route search, so they pass.

## Fix

Owned by `dashboard`. An unknown or unusable `tab` renders the Ledgers tab (`overview`), as w3/630 required. Make the schema always return the key, with `tab: undefined` when the value is unknown, so that the router's merge overrides the raw value. Alternatively, have the page accept only a value from `USER_PROFILE_TABS` before falling back to `"overview"`. Doing both is cheap. Optionally also accept `ledgers` as a spelling of `overview`, since that is what the tab is called. Valid tabs, the case-insensitive match and the `q`/`sort`/`show` handling stay as they are.

## Definition of done

- On production, each "all false" row in the table shows the Ledgers tab selected and the ledger cards beneath it, signed in and signed out. The three control rows are unchanged.
- A test that renders the real `/ledger/$username` route from `?tab=follower` (through the router, not the schema alone) asserts that the Ledgers tab is selected and its panel is present. It fails on the current code. Dashboard gates pass.

## Blast radius

Hand-built transforms that leave keys out share the pattern: `accountsActionSearchSchema` and `journalActionSearchSchema` (`common/lib/ledger-action-search.ts`). Their consumers re-check the values. `/accounts?type=Bogus` shows All Types. `/journal?action=new-entry&directive=bogus` opens New Entry on Transaction and rewrites the URL. `/journal?offset=abc`, `?offset=-60` and `?offset=2000000` all land on a real page. The profile's own `?sort=bogus` and `?show=abc` fall back to the default list. Schemas built from `z.object` fields keep an `undefined` key and are not affected: login `reason`/`next`, billing, the file blob's `editMode`/`lineNumber`, and Query `query`. Only the profile `tab` was observed blank.

## Dedupe

Searched `.pm/**` (open, `done/` and `blocked/`) for `searchEnum`, `userProfileSearchSchema`, `USER_PROFILE_TABS`, `tab=follower`, `tab=ledgers`, `tab=bogus` and "raw search". w3/630 (done) turned the 500 into this blank page and set the acceptance it misses. w4/154 and w4/336 (done) kept the other profile params across tab changes. w3/120, w3/131 and w3/164 (done) were raw-search crashes on other keys. No open item covers this. `main` still omits the key, so this is not deployment lag.
