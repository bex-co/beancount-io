### Root cause and affected caller

`cli/src/bea_engine/ledger/writer.py:761`, `with_inferred_prices`, solves
only when every other posting's units are already in the missing price's
currency and that posting has neither cost nor price (`:793–799`). It
therefore returns the original postings for both known-weight cases above.
`_source_postings` in `cli/src/bea_engine/importing.py:1504–1511` is its sole
production caller, after inferred cost-part normalization.
`_price_text` (`:1589`) omits the still-missing numeric price; `_legs`
(`:1642`) and the hash-input construction reached by `_hash_import_ids`
(`:3107`) consequently see the same `2 HOOL` fingerprint. Actual helper
probes confirm MISSING price, empty price text and equal fingerprints for
the two inferred weighted rows; native booking gives their distinct prices.
The explicit controls and the original plain-leg inference retain those
prices and have distinct fingerprints.

Fix the incoming source normalization before identity, preview and matching:
derive the one open posting price from fully determined native weights,
including known costs and prices in another commodity. Preserve native
rounding, original written text, exact-repeat behavior, native-ID correction
conflicts and the existing incomplete-input safeguards. Do not treat an
unresolved price as equality evidence or remove prices from identity.
The nearby cost-weight support in [994](./994.md) and native authored
owner recovery in [1010](./done/1010.md) concern other helpers; their fixes
already remain present. No API or dependency change is needed.

Directly exercised: parser-based Python importers, generated and native IDs,
`@` / `@@`, known per-unit costs, known per-unit/total foreign-cash prices,
JSON/human second apply, exact first repeats, explicit source-price controls
and fresh native/CLI reads. CSV cannot express these annotated source rows
through its amount mapper. Other cost shapes, underdetermined counterparts,
includes, other platforms and a repaired implementation are unverified.

## Repeating unit prices: native-valid trades are silently skipped

**Additional current acceptance, 2026-10-24.** The same immutable CLI source
`ee4b7702516da4535bb3b478e2efe9913b09481b` remains byte-identical to current
main. This case needs only an ordinary cash counterparty, with no costed
asset or foreign-currency leg. There is no plugin.

A valid purchase of **3 HOOL for 1.00 USD** infers the native unit price
`0.3333333333333333333333333333 USD`. A second purchase on the same date of
**3 HOOL for 4.00 USD** infers `1.333333333333333333333333333 USD`.
The first import writes once and its exact repeat skips. The second also
reports an exact duplicate, exit 0 / zero writes, even with
`--duplicates include`: the ledger stays at **3 HOOL / 999 USD cash**

the first bank ID for that real price correction is falsely skipped too,
instead of conflicting at exit 4. Both reference books and the actual book
pass native checks; the omitted purchase is demonstrated by complete native
trade/holding graphs and fresh CLI queries.

The defect is independent of the weighted-counterparty gap above. At
`cli/src/bea_engine/ledger/writer.py:798`, `with_inferred_prices` rejects
its solved price unless `solved * abs(count) == abs(others)`. Native
Decimal division followed by multiplication need not reproduce the exact
cash total: `3 * (1 / 3)` is
`0.9999999999999999999999999999`, and `3 * (4 / 3)` is
`3.999999999999999999999999999`. Native booking accepts these ordinary
cents-funded trades with their actual inferred prices. The helper leaves
both prices MISSING, `_source_postings` passes that through, and `_price_text`
erases both before identity/comparison. Actual helper proofs on both real
source entries show missing prices, empty price text and equal fingerprints;
the generated IDs emitted by the CLI collide too.

Writing the native prices explicitly works, both as per-unit prices and
explicit total prices. A nearby inferred-price control paying 3.00 then
6.00 USD for three shares also works because those quotients are exact.
The same failure reproduces for omitted `@ USD` and `@@ USD`, generated and
native IDs, and human and JSON apply. It is a missing normalization case,
not a request to change native rounding, written total-price annotations or
the exact-ID policy.
