# A budget added with Add Budget's default date reads "Above target +210.00 USD 625%" as soon as it is saved: this month's target counts only the days from today (40.00 of 300.00 USD) but the actual counts the whole month (250.00 USD), and mobile reads the same ledger against 300 (dashboard gap in w21/301)

**Severity:** major. It is the default path. Add Budget's Date is today, so any budget added after the 1st, on an account with spending earlier in the month, is judged at once against a fraction of its target. The summary sorts it first under "Missed targets first", and the mobile app gives the opposite verdict for the same ledger. **Owner:** `dashboard` (`features/ledger-data/budget`). **Estimate:** 30–45 minutes including tests. **A2:** setting a first budget is a newcomer's step, and the first thing they see is that they have already overspent more than sixfold. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English, signed in as the QA account. Local HEAD `46b910b4e`.

## Repro

Run on a disposable synthetic QA ledger, which was restored byte-for-byte afterwards.

1. Add an account with spending earlier this month:

   ```beancount
   2025-01-01 open Assets:Wallet USD
   2025-01-01 open Expenses:Food USD
   2026-11-05 * "Shop" "earlier this month"
     Expenses:Food   250.00 USD
     Assets:Wallet
   ```

2. On 2026-11-27, open `/ledger/<owner>/<ledger>/budget` and choose **Add Your First Budget**. The Date shows `2026-11-27`. Pick `Expenses:Food`, keep **Monthly**, enter `300.00`, keep `USD`, and choose **Add Budget**. The commit is `Add 2026-11-27 custom budget Expenses:Food`.
3. The summary row and the card both read **`Monthly · November 2026 | 40.00 USD | 250.00 USD | Above target +210.00 USD 625%`**. The card's Targets table, directly below, lists `2026-11-27 Monthly 300.00 USD`.
4. All time, This year and Last 12 months all read the same. Reloading the page gives the same result.

## Cause

`calculateBudgetForInterval` (`dashboard/src/features/ledger-data/budget/budget-utils.ts:233-283`) walks the period's days and skips every day before the first directive (`if (!active) continue;`, `:258`). November's target is therefore 4/30 × 300 = 40.00. The actual comes from `getLedgerIntervalTotals` for the whole of November, including the 250.00 USD spent before the budget existed. The headline (`budget-snapshot.ts:218-229`) judges the period because the first target falls inside it, not after it (`firstTargetAfterPeriod`, `:209`). w5/1193 leaves unjudged only the periods that end before the first target.

The two clients disagree. Under w21/301 the mobile app chose to back-fill: "a budget set on the 21st is a budget for that month, not for its last ten days" (`mobile/src/screens/budget-screen/selectors/budget-selectors.ts:618-650`). Mobile's comment says the dashboard budgets the full month too. Production shows it does not. Fava's daily arithmetic also gives 40.00 here, but w21/301 recorded the product decision, and w21/994 made the two apps agree on in-progress verdicts.

## Fix

Dashboard only. In `calculateBudgetForInterval`, treat every directive dated on the earliest budget date as in effect from the start of the period it falls in. Use the later of the chart period's start and the start of that directive's own interval period, as mobile does for a cadence change (w21/762). A same-day correction governs the whole back-filled period, as in w21/622. Later directives still take effect on their own dates, so a mid-period change is still prorated. Periods that end before the first directive stay unjudged (w5/1193). If w5/1251's window clamp lands first, the back-fill must not reach before the window start.

## Definition of done

- With the repro on production, the new budget reads **`300.00 USD | 250.00 USD | In progress`** (−50.00 USD, 83%) in the summary and on the card, and the November Period data row reads `300.00 USD`.
- Unit cases fail on the current code:
  - monthly, weekly and quarterly first directives dated mid-period budget the whole period;
  - a same-day correction (500 then 300) gives 300;
  - a monthly directive followed the next day by a yearly one does not back-fill the year;
  - a raise later in the same period is still prorated;
  - periods before the first directive stay `null`.
- Dashboard gates pass.

## Dedupe

- w21/301 (done) is the mobile fix. Its note says "the dashboard has the same pre-budget actuals", but only mobile changed.
- w21/622 and w21/762 (done) are mobile follow-ups that this fix should mirror.
- w21/994 (done) aligned how the two apps judge an in-progress period, and assumed the dashboard already budgeted the whole month.
- w5/1193 (done) covers periods before the first target.
- w5/1251 (filed with this one) covers a time span's cut-off first period, in the same function.
