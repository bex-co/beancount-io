# Query History in two tabs: running a query in one tab erases the queries the other tab ran

**Severity:** minor (lost work). **Owner:** dashboard. **Estimate:** 30–45 minutes including a rendered test. **A2:** a reader who keeps two Query tabs open (one per ledger, or a scratch tab beside a report) loses every query the first tab ran as soon as the second tab runs one. The lost queries are gone from every tab opened later. **Found by:** `/qa-find-bugs-dashboard` on 2026-11-18 against `https://beancount.io` (entry chunk `main-LGv2TZLj.js`), headless Chromium 153 at 1440×1000, English, isolated profile, signed in as the QA owner on its disposable `qa-` ledger. Local HEAD `68056e47e`. Read-only BQL; nothing was written to the ledger.

## Repro

1. Open `/ledger/<owner>/<ledger>/query` in tab A and again in tab B (same browser).
2. In tab A, execute `SELECT 'qa-a1' AS probe`, then `SELECT 'qa-a2' AS probe`. `localStorage["beancount-query-history"]` is `["SELECT 'qa-a2' AS probe", "SELECT 'qa-a1' AS probe"]`.
3. In tab B, execute `SELECT 'qa-b1' AS probe`.
4. The stored history is now only `["SELECT 'qa-b1' AS probe"]`. Open the Query page in a third tab with no `?query=`: Query History lists only the B query. Both A queries are gone.

Reproduced twice from fresh loads. Deleting a card works the same way in reverse: a query deleted in one tab comes back when the other tab runs anything.

**Expected:** the history holds the union of what every tab ran, newest first, de-duplicated, capped at 50, and a deletion in one tab stays deleted.

## Cause

`dashboard/src/features/bql/hooks/use-query-history.ts:24` uses `useLocalStorageState` without `syncAcrossTabs`. In `dashboard/src/common/hooks/use-local-storage-state.ts:102-113`, `setValue` runs the functional update (`addQuery`'s `[query, ...prev]`) on `storedValueRef.current`, the copy this tab read when it mounted. It then writes the whole array back with `localStorage.setItem`. With `syncAcrossTabs` off (`:70`, `:155`), no `storage` event refreshes that copy, so tab B's write replaces tab A's entries with B's stale list.

Working controls in the same codebase: the changelog watermark passes `syncAcrossTabs: true` (`common/hooks/use-changelog-watermark.ts:26`, `:125`, `:141`). The Overview layout re-reads storage inside its update (`features/reports/overview/hooks/use-dashboard-layout.ts:118-131`) and subscribes to `storage` (`:99`).

## Fix

In `useQueryHistory`, apply each add or remove to the latest stored list, read from `localStorage` at write time as the Overview layout does. Also pick up other tabs' writes: pass `syncAcrossTabs: true`, or use the same `useSyncExternalStore` pattern. Keep today's behavior otherwise: newest first, de-duplicated, at most 50, malformed values recovered (w4/272). A history row that arrives from another tab must not open or run itself. Today the first card opens on mount and opening it runs the query (`features/bql/pages/index.tsx:421`, `components/query-result-card.tsx:313`; w4/1098). [1130](./1130.md) changes the same hook's storage key to one per user. Do both in one change, so the per-user key keeps this merge behavior.

## Definition of done

- With two Query tabs, running A1 and A2 in one and B1 in the other leaves the stored history as B1, A2, A1. A third tab lists all three.
- Deleting a query in one tab, then running another query in the second tab, does not bring the deleted query back.
- A query that reaches the history from another tab neither opens its card nor sends a BQL request in the receiving tab.
- A dashboard test drives two hook instances over one `localStorage` (with a `storage` event) and fails on the current code. Dashboard gates pass.
