# BQL `PRINT FROM <expr>` prints every non-transaction directive whatever the expression: `PRINT FROM payee ~ "zzzz-no-such-payee"` returns 1,009 rows on the public example, where bean-query returns none

**Severity:** minor (wrong query result; no data is changed). **Owner:** `backend-cluster/ledger` (hosted BQL, shared by the dashboard's Query page, GraphQL, REST and MCP). **Estimate:** 45–60 minutes including tests. **A1:** an agent or user who asks the hosted ledger to print one month's entries, or one payee's, to copy them elsewhere gets every `open`, `commodity`, `price`, `balance` and `note` in the ledger mixed in, from every year. Nothing says the filter was not applied to them. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-21 against `https://beancount.io`, entry chunk `main-CIyNN76T.js`, isolated headless Chromium at 1440×1000, plus MCP `runBqlQuery` on the designated synthetic ledger. Read-only queries. Local HEAD `8724f3464`.

## Repro

On the public `/ledger/open_ledger/example/query`, run each query (also reachable as `?query=…`):

| Query | Hosted rows | First rows | bean-query 0.2.0 (Beancount 3.2.3) |
| --- | --- | --- | --- |
| `PRINT FROM payee ~ "zzzz-no-such-payee"` | **1,009** | `1792-01-01 commodity USD`, `1900-01-01 commodity VMMXX`, `1980-05-12 open Equity:Opening-Balances`, … | none |
| `PRINT FROM payee ~ "Cafe Modagor"` | **1,053** (the 44 matching transactions plus the same 1,009) | as above | the matching transactions only |
| `PRINT FROM year = 2016 AND month = 3` | **1,043** | as above | March 2016's entries only |

On a small synthetic ledger (12 `open`s on 2026-01-01, transactions, one `balance` on 2026-08-29), MCP `runBqlQuery` `PRINT FROM payee ~ 'CITY BUS'` returns every `open` and the `balance` plus the two CITY BUS transactions, and `PRINT FROM year = 2026 AND month = 8` returns the January `open`s along with August's entries. Local control on the same shape of ledger: `bean-query t.bean "PRINT FROM year = 2026 AND month = 8"` prints only the August transaction and the August `balance`, and `PRINT FROM payee ~ 'BLUE'` only the BLUE BOTTLE transaction.

`SELECT` is unaffected in practice: only transactions have postings.

## Cause

Unverified in the engine itself. The ledger service passes the statement straight to the WASM engine (`backend-cluster/ledger/src/foundation/rustledger/engine.ts:1125`, `ledger.query(query)` from `@rustledger/wasm` 0.24.0) after a list of guards that refuse other known deviations (`:1107-1124`); none covers `PRINT … FROM`. The engine evidently applies the FROM expression to transactions only and passes every other directive through, where beanquery evaluates it on every entry: date columns (`year`, `month`, `day`, `date`) against the directive's own date, and transaction-only columns (`payee`, `narration`, `flag`, `tags`, `links`) as NULL, which does not match.

## Fix

Target behavior: `PRINT FROM <expr>` prints exactly the directives for which `<expr>` holds, as bean-query does, with the `OPEN ON` / `CLOSE ON` / `CLEAR` clauses unchanged.

- Preferred: fix it in the engine (upstream rustledger) and bump the pinned version.
- Until then, in the ledger service: either filter the PRINT result by evaluating the FROM expression per directive the same way, or refuse `PRINT` with a FROM expression with an actionable message (as the other guards do) rather than return unfiltered output. Do not leave it silently wrong.
- The same answer reaches GraphQL, REST and MCP through the one BQL entry point, so no surface work is needed beyond the shared fix.

## Definition of done

- On `open_ledger/example`, `PRINT FROM payee ~ "zzzz-no-such-payee"` returns no rows, `PRINT FROM payee ~ "Cafe Modagor"` returns the 44 matching transactions only, and `PRINT FROM year = 2016 AND month = 3` returns only directives dated in March 2016 (or, with the interim refusal, each is refused with a message saying why).
- A ledger test with an `open`, a `price`, a `balance` and two transactions asserts the PRINT FROM results for a payee and a month predicate, compared with bean-query's. It fails on the current code. Ledger gates (`yarn typecheck`, `yarn test`, `yarn verify:rustledger`) pass.
