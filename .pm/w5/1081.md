# Validate cumulative include edits in batch-update previews

**Minor · cli · 40–55m · A1 · worker1.** `bea update transactions`
previews two category changes in different includes as ready, with no
rejection, although applying the unchanged mapping necessarily rejects the
second file after writing the first. Both edits pass alone but jointly
violate the ledger's `onecommodity` rule. A one-file preview detects that
same conflict. Apply correctly preserves a valid ledger and reports its
partial result; the defect is the misleading preview. No product fix made.

## Root and repair

`cli/src/bea_engine/ledger/updating.py:716–783`, `_validate_plans`, groups
plans by file and validates each file's candidate against the **same original
LedgerSnapshot**. A's candidate sees unedited b, and b's candidate sees
unedited a, so each introduces only one Travel currency. `_validate_text`
at :708–713 stages just that candidate through `validate_candidate`.
The preview branch at :919 then combines these individually successful
file diffs and reports both rows ready without validating their cumulative
state. The one-file branch validates both edits together and catches it.

Apply initially calls the same planner at :951, but its sorted write loop
recaptures the graph at :967 and validates each candidate at :1003 after
previous replacements. Its second real candidate therefore sees both
currencies and refuses correctly. Two source-aware helper controls delegate
to the real validator: split preview performs two successful validations
against one identical original snapshot; one-file preview rejects the
combination, accepts each row alone, then rejects their combination again.

Make preview simulate the existing sorted per-file apply sequence against
staged logical ledger contents: incorporate only earlier accepted target
edits before validating later targets, without modifying source files or
reusing that simulated state for live conflict checks. Report the same
ready/rejected input rows and reasons the unchanged apply will produce.
Retain per-file atomic writes, later live revalidation, accurate partial
results, unchanged rows and the same-file combined-failure policy. Do not
weaken native plugin validation or make all batch writes atomic as an
incidental fix.

`_validate_plans` has two callers, both in `_transactions` (preview and
apply preparation); `answer` dispatches the bulk type there. Frontend
`cli/src/cli/commands/update.py` sends both JSON and CSV mappings to this
helper and renders its row statuses/diff. The witnessed trigger is bulk
JSON, from a file; the first-month control also covers JSON stdin. The
single-row verb has a different planning path. Pure local CLI scope;
no API, generated client or dependency change is required.

History: the validator's AST is unchanged from batch introduction
`62c0e1910`. This is an untested cross-include interaction, not a regression
introduced by the recent source-edit or success-diff fixes.

## Preview exit-policy and help clarification — 2026-10-28

Additional real invoice review/reversal controls establish the intended exit policy while the cumulative preview repair above remains pending. **A preview containing rejected rows intentionally exits 0**, returns its per-row statuses and `ready` / `rejected` counts, and writes nothing. An applied batch with a rejected row writes the accepted rows and exits 1. Keep that existing preview policy when repairing cumulative validation.

The current `update transactions --help` says the exit status is 1 “whenever any row was rejected”; `cli/docs/USAGE.md:1743` likewise says “Any rejection exits 1”. Those unqualified statements obscure the default preview's actual contract. Qualify the `src/cli/commands/update.py:298–303` help and the usage-guide sentence with **`--apply`**, and state that preview callers inspect `data.rejected` / row statuses. Run the owning package's docs generator/check when changing help; keep generated reference output generated. This is a documentation correction to the preview adoption surface, not a request to change its intentional exit code or weaken apply's partial-result policy.

The implementation's preview branch (`cli/src/bea_engine/ledger/updating.py:915–943`) returns `report(..., written=0, rejected_rows=...)`; the frontend renders that successful report. Existing regressions explicitly require this: `test_preview_with_a_reject_still_exits_0` and `test_csv_preview_flags_rejects` in `tests/test_update_batch.py`, and the malformed-cell preview in `tests/test_update_batch_float_cell.py`.
