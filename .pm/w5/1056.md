# Preserve same-day posting order in parent registers

**Minor · cli · 25–40m · A1 · worker1.** `report register Assets:Bank`
groups same-day rows by child account, then calculates running balances in
that reordered sequence. A payment originally first at **140 USD** is shown
second at **120 USD**. A start-of-day balance assertion can appear after a
payment and show **130 USD** instead of the parent's actual **150 USD** at
that assertion. JSON and human output both reproduce, exit0 with a valid
ledger and complete valuation. Final balances, stored data, leaf registers
and trial-balance totals remain correct. No product fix implemented.

## Cause and bounded repair

`cli/src/bea_engine/report.py::_register:639` groups entries by account.
`cli/src/fava/core/group_entries.py:96` returns that map sorted by account
name. Register flattens each account's rows at `report.py:660`, then its
stable date-only sort at`:665` leaves account-name grouping in place for
equal dates. The loop at`:669–705` accumulates in this artificial order.
The original loaded sequence and posting positions were already correct;
the native snapshot proves them before any report grouping occurs.

Keep subtree resolution, but collect selected rows in the original filtered
entry order and retain each transaction's posting order. Preserve the
loader's same-day placement of assertions and other supported row types.
Date-only sorting after account grouping cannot recover those ties. Reuse
the existing entry traversal pattern in
`cli/src/fava/ledger.py::account_journal:141–151` rather than duplicating
booking or adding a new source parser. Keep one row per selected posting,
existing cost/conversion behavior, period opening rows, final totals and
the refusal of genuinely ambiguous selectors.

`report.answer:133` is the one engine caller; frontend
`cli/src/cli/commands/report.py::register:498–524` renders the producer's
rows in supplied order for JSON and human output. The shared grouping
helper correctly serves account-local consumers; do not globally change
its map contract. No new dependency, API schema or backend change is needed.
The defect here is the CLI Register's merge of those groups.
