# The update notice runs and prints from a checkout install, which it documents as never happening

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** cli. **A1/A3:** a
contributor working in the repo gets a daily PyPI call they were told would not
happen, and — once a release is newer than the checkout — a notice telling them
to run `bea upgrade`, which on a checkout upgrades nothing.

Found 2026-09-15 by a report-only CLI QA sweep against `main`, HEAD `b78efe7d`,
using `uv run bea` 0.2.0 on Darwin 26.5.1 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME`, driving a real pty. Synthetic local ledger.

## Repro — part 1, the check runs (no simulation)

With a fresh config directory, `BEA_NO_UPDATE_NOTIFIER` unset, no `CI`, no
`--json`/`--no-input`, and stderr on a terminal:

```sh
rm -rf "$BEA_CONFIG_DIR" && mkdir -p "$BEA_CONFIG_DIR"
bea --file main.bean list open --limit 1      # in a pty
cat "$BEA_CONFIG_DIR/update-check.json"
```

```text
{"checked_at": 1789538904.9325209, "version": "0.2.0"}
```

The cache is written, so the check ran and reached the real PyPI. The same
session classifies itself as a checkout:

```sh
bea upgrade --check
# bea 0.2.0 (installed by: checkout)
# Latest release: 0.2.0
# Would run: nothing — upgrade it yourself with: git pull; uv sync --all-groups
```

`bea --version` alone writes no cache, which matches its documented
cache-only behavior.

## Repro — part 2, the notice prints (simulated index)

Nothing is visible while latest == installed, so this step points the existing
`BEA_UPDATE_API_URL` override at a local server returning
`{"info": {"version": "9.9.9"}}`. **The index is simulated; the gating is not** —
part 1 already shows the real check running from a checkout.

```text
$ bea --file main.bean list open --limit 1        # pty, checkout install
DATE        ACCOUNT          CURRENCIES
----------  ---------------  ----------
2026-01-01  Assets:Bank:USD  USD
Showing the first 1; pass --limit for more.
bea 9.9.9 is available (you have 0.2.0) — run 'bea upgrade' to update.

$ bea --version
bea 0.2.0
bea 9.9.9 is available (you have 0.2.0) — run 'bea upgrade' to update.
```

The advice is wrong for this install: the documented table says a checkout's
`bea upgrade` runs nothing and prints `git pull` / `uv sync --all-groups`.

## Expected / actual

`cli/docs/USAGE.md` ("The update notice") says the notice "never runs at all
under `--json`, `--no-input`, `CI`, or `BEA_NO_UPDATE_NOTIFIER=1`, without a
terminal on stderr, **or from a development install**." Expected: a checkout
makes no network call and prints no notice. Actual: it does both.

The five suppressors that *are* implemented all work. Verified individually
against the same simulated index, each blocking both the notice and the cache
write, where the unsuppressed baseline does neither:

| case (checkout install) | notice printed | cache written |
| --- | --- | --- |
| baseline pty, no suppressor | **yes** | **yes** |
| `--json` | no | no |
| `--no-input` | no | no |
| `CI=1` | no | no |
| `BEA_NO_UPDATE_NOTIFIER=1` | no | no |
| stderr not a tty | no | no |

Only the development-install condition is missing.

## Root cause

`cli/src/cli/update.py:172-183` — `start()` returns early on `muted(...)`
(`:89-95`: json / no-input / `BEA_NO_UPDATE_NOTIFIER` / `CI` / stderr not a
tty) and then on `not is_release(package_version())`. `is_release` (`:66-67`)
delegates to `release_parts` (`:48-62`), which is purely a **version-string
shape** test: canonical `X.Y.Z` passes, anything else fails.

Its docstring states the intended mechanism — "a checkout's `.dev` version, a
local version segment, a pre-release … stay silent rather than guess, which is
also how a development install ends up never checking at all." That assumption
does not hold: `cli/pyproject.toml` carries `version = "0.2.0"`, a canonical
release string (it must, since releases are tagged from it), so every checkout
of `main` passes the gate.

The channel is already resolved at the call site.
`cli/src/cli/main.py:199` calls
`update.start(json_output=…, no_input=…, channel=current_channel().name)`, and
`current_channel()` (`cli/src/cli/commands/upgrade.py:87`) returns the
`CHECKOUT` channel (`:44`) for this install — but `start()` uses `channel` only
to pick the fetch URL and cache file, never to decide whether to run.

## Related completed work — a gap in a shipped DoD

`.pm/w2/done/m25/done/t003.md:19` lists the acceptance criterion as
"Development installs from a checkout (version ends in `.dev` or package
metadata is missing) never check." That criterion conflates two different
notions: it treats "checkout" as equivalent to a non-canonical version string.
A checkout sitting on a tagged release version satisfies neither listed
condition yet is still a development install, so the shipped behavior met the
written criterion while missing the documented promise. This is a DoD gap in
completed work, not a regression — `git log -S 'is_release' -- cli/src` shows
the gate arriving with `96169e40` and never changed since. m25 is under
`done/`, so this is filed as a new note rather than reopening it.

## Fix

Return early in `start()` when the resolved channel is not one the notice can
act on — `checkout`, and `unknown` (whose `bea upgrade` also runs nothing and
exits 2). The value is already passed in, so this is a guard, not new
plumbing. Keep `is_release` as the separate version-shape guard it is.
`bea upgrade --check` must keep working on a checkout, since that is the
explicit user request path and already reports the right advice. Add coverage
pinning that a checkout channel neither fetches nor writes the cache, and that
`--version` stays silent with no cache, alongside the existing suppressor
tests.

## Blast radius and adjacent states

Affects any development install whose version string is canonical — every
checkout of `main` between releases. Installed channels (Homebrew, uv tool,
pipx) are unaffected and should keep checking. `bea --version` reads the cache
only and makes no network call; it inherits whatever the notifier cached, so it
goes quiet once the gate is fixed. The Homebrew cache file
(`update-check-homebrew.json`) and the tap-formula fetch path were not
exercised.
