# The Query page hides why the engine refused a query: `PRINT FROM year = 2016`, `BALANCES AT value`, `… FROM CLEAR`, `date = '2016-01-01'` and five more all read "Some of the information provided is invalid" (gap in w2/126 and w5/1201)

**Severity:** minor. Nothing is computed wrongly, but every refusal below already carries a one-line fix from the server ("Use SELECT account, value(sum(position)) GROUP BY account instead"), and the page throws it away. **Owner:** `dashboard`. A structured refusal reason from `backend-cluster/ledger` is the more durable fix (see Fix). **Estimate:** 60–90 minutes, dashboard-only, including tests and the 15 locales. **A2:** people who come from Fava or bean-query type stock BQL. The Query page is the only place where a person types BQL (mobile has none). When the engine refuses a stock spelling, the page says only that "some of the information provided is invalid". w5/1201 (2026-11-23) added the `PRINT FROM` refusal so that each such query would be "refused with a message saying why". On the dashboard, that message never appears. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, entry chunk `main-BBmi61Hs.js`, isolated headless Chromium 158 at 1440×1000, English, signed in as the QA account. Read-only queries on the public `open_ledger/example`. Local HEAD `634566e8f`.

## Repro

On `/ledger/open_ledger/example/query`, put each query in the editor (or open `?query=…`) and press **Execute Query**. Each one was repeated from a fresh load.

| Query | Page shows | GraphQL `queryShell` error (`BAD_USER_INPUT`), after `Invalid BQL query: ` |
| --- | --- | --- |
| `PRINT FROM year = 2016` | generic | "This engine cannot apply PRINT FROM predicates to non-transaction directives. Use SELECT … FROM entries WHERE … for filtered rows, or plain PRINT for the complete ledger in Beancount syntax." |
| `SELECT account, sum(position) FROM CLEAR GROUP BY account` | generic | "FROM … CLEAR is not supported by this query engine: … Drop CLEAR and read the period's earnings …" |
| `BALANCES AT value` | generic | "BALANCES … AT value is not supported by this query engine: it would return units, not market values. Use SELECT account, value(sum(position)) GROUP BY account instead." |
| `SELECT date WHERE date = '2016-01-01' LIMIT 1` | generic | "Mixed-type comparison (date compared to str with =) is not supported … Compare same-typed values instead — date('…') for dates …" |
| `SELECT "date" LIMIT 1` | generic | "Quoted identifiers are not supported by this query engine outside FROM: … Use the bare column name (date) instead of the quoted spelling." |
| `SELECT * AS x LIMIT 1` | generic | "SELECT * AS <alias> is not supported by this query engine: … Use SELECT * … (no alias), or name the columns explicitly instead." |
| `SELECT date WHERE tags = tags LIMIT 1` | generic | "Comparing composite BQL values … with = or != is not supported … Compare scalar values instead …" |
| `SELECT balance, count(date) GROUP BY balance` | generic | "Grouping by the inventory column balance is not supported … List distinct inventories with SELECT DISTINCT balance, or group by a scalar column such as account, instead." |
| `SELECT date FROM #"x"` | generic | "syntax error at position 17: found '#' expected identifier, …" |

"Generic" means the error card reads **Some of the information provided is invalid. Please check and try again.**

**Controls.** `SELECT date + 1 LIMIT 1` shows "This query engine can't add or subtract days with + or -. Use date_add(date, days) …" (w2/126). `SELECT foo` shows "Unknown column “foo”…" and `SELEC date` shows "Syntax error near “selec” at character 1…". So the page explains the refusals it knows. REST and MCP callers receive the full server text (w2/126).

## Cause

`dashboard/src/features/bql/lib/query-error.ts:118-217` (`getQueryErrorFeedback`) recognizes engine diagnostics by regex and, by design, never shows raw server text. Anything it does not recognize falls through to `getErrorMessageKey` at `:217`, which gives `common.errors.badUserInput`. It knows only three of the ledger's refusal guards: date arithmetic, string concatenation and the `id` column (w2/126, `81f9dc5f7`). The guard chain in `backend-cluster/ledger/src/foundation/rustledger/engine.ts:1121-1137` has many more. Some predate w2/126: `at-value-guard.ts` (2026-10-20), `star-alias`, `composite-comparison`, `inventory-group-by` and `mixed-comparison` (2026-10-27), `quoted-column` (2026-10-28) and `clear-scope` (2026-11-10). `print-from-guard.ts` came after it (w5/1201, `6852a4ac9`). There are also `integer-overflow`, `ordinal-range`, `window-from`, `value-target` and `joinstr-arity`. w2/126 shipped its "dashboard-only minimum" and recorded the rest as "worth filing on its own". Nobody filed it. Separately, `FOUND_TOKEN_PATTERN` (`:36-37`) accepts only tokens in `[A-Za-z0-9_.,;()*=!~+-]`. A syntax error at `#`, `"` or `'` therefore loses its position too.

## Fix

Target: each refusal above shows a specific, localized message that names what to write instead, with BQL spellings passed as untranslated placeholders (as w2/126 did for `date_add(date, days)`). Raw server text stays hidden. **Try Again** stays hidden for `BAD_USER_INPUT` (w2/111).

- **Preferred:** each ledger guard attaches a stable reason (for example `extensions.bqlRefusal: "printFrom" | "atValue" | "clearScope" | "mixedComparison" | "quotedColumn" | "starAlias" | "compositeComparison" | "inventoryGroupBy" | …`, plus the validated column or statement name it cites). backend-v2 forwards that reason on GraphQL, and the root parity rule puts the same field on REST and MCP. The dashboard maps reasons, not English prose, so a new guard cannot silently fall back to the generic message again.
- **Minimum (dashboard only):** add a stable-prefix pattern and a `bql.errors.*` key for each refusal in the table, PRINT FROM included. Accept `#` in the found-token class, so `SELECT date FROM #"x"` gets "Syntax error near “#” at character 18". Admit a quote character only if the interpolated value stays a single, validated character.

## Definition of done

- Each of the nine queries above shows its specific message on `open_ledger/example`, in English and in at least one other locale, with no raw server text. The `SELECT date + 1`, `SELECT foo` and `SELEC date` controls are unchanged.
- `query-error.test.ts` holds the recorded production message for each new case, and `query-result-card-engine-errors.test.tsx` renders at least three of them with the real English catalog. The new cases fail on the current matcher. Dashboard gates pass, and the translation tests pass for all 15 locales.

## Dedupe

Searched `.pm/**` (open, `done/` and `blocked/`) for the guard file names, `bqlRefusal`, "not supported by this query engine", "cannot apply PRINT FROM", `query-error.ts` and "information provided is invalid". w2/126 (done) mapped three guards and left the rest unfiled. w2/111, w4/160, w0/002 and w4/971 (done) cover the other diagnostics. w5/1201 (done) added the PRINT FROM refusal on the server only. w23/127, w23/128, w23/129, w23/132, w23/153, w23/154, w23/157, w23/165 and w1/192 (done) added the guards and did not touch the dashboard. w2/101 (done) is the Journal header filter's own classifier, which is a separate surface. `git log -S` finds none of these refusal prefixes under `dashboard/`, and HEAD `634566e8f` matches production, so this is not deployment lag.
