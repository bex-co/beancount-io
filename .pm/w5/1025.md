# Preserve multiline strings when retargeting transaction postings

**Minor · cli · 35–50m · A1 · worker1.** `bea update transaction --account`
changes account-looking text inside an existing multiline memo, narration
or posting-metadata string as well as the real posting. Preview shows the
extra edit; apply persists it and reports success. The ledger checks valid
and its requested financial recategorization is correct, but text the user
did not ask to change is overwritten. No product fix implemented.

Real local QA, 2026-10-25, clean main/frozen source
`22d622a67ceacb9135e400b758ad2de14f2b4112`: the actual frontend update
command added there. Checkout `bea 0.3.1`, frontend Python 3.13.3, existing
managed Python 3.12.10 / Beancount 3.2.3 / Beanquery 0.2.0, macOS 26.5.1
arm64. Fresh bounded subprocesses, closed stdin/no TTY, isolated absolute
config/cache, notifier disabled. Synthetic local books, no plugins, services
or added dependencies. The 1,628-file source snapshot is unchanged before
and after the run.

## Standalone reproduction

Put this checkout's `bea` on PATH, save the following as `recipe.py`, then run:

```sh
python3 recipe.py /absolute/unused/book metadata json /absolute/managed-engine/bin/python
```

Repeat in another unused directory with `human`, or choose `narration`,
`posting-meta` or `explicit` for the other affected forms. The remaining
modes are controls. The recipe builds an independently native-loaded
`expected.bean` that changes only the real posting and flag; `results.json`
records arguments, safe environment, streams, exits, durations, book hashes

In `metadata`, the valid source transaction includes:

```beancount
2024-01-02 ! "Shop"
  import-id: "review-1"
  memo: "Spending plan
    Expenses:Uncategorized 9.99 USD
  classify after review"
  Expenses:Uncategorized 9.99 USD
  Assets:Cash -9.99 USD
```

The real command is:

```sh
bea --json --no-input --offline -f main.bean update transaction --id review-1 --account Expenses:Food --flag '*'
```

Preview exits **0**, `written: 0`, and preserves the file, but its diff
changes **both** `Expenses:Uncategorized` lines to `Expenses:Food` as well
as clearing `!`. Repeating with `--apply` exits **0**, `written: 1`, and
saves those edits. Native parsing confirms the memo value itself changed,
not merely its table rendering. `check`, fresh JSON listing and position
query all succeed. A later flag-only no-op writes zero and preserves the
already changed file.

`narration` puts the same account-looking continuation line in the quoted
transaction narration; recategorization changes that literal narration.
`posting-meta` puts it inside a posting's multiline `receipt:` value; that
string changes too. `explicit` uses
`--account Expenses:Uncategorized=Expenses:Food` and repeats the memo change.
These all pass native validation before/after. This is one line-selector
failure, not four separate defects.

Expected: change the selected transaction's real posting account and the
explicitly requested flag, while preserving every string value. An account
name inside quoted text is a literal, not a posting to retarget. The
[update help/reference](../../cli/docs/REFERENCE.md#bea-update-transaction)
describes retargeting postings, and the engine helper's `_edit_postings`
contract explicitly limits the edit to account tokens. The independently
constructed expected file is native-valid and retains all original text.

In affected modes, both actual and expected financial results are Cash
**89.00 USD**, Food **11.00 USD**, Uncategorized **0 USD**. The 1.01 USD
neighbor transaction, capital entry and surrounding comment remain exact.
No missing payment, changed amount or arithmetic failure is claimed. The
defect is an unintended annotation/narration write, visible in the diff.

Exact public verification: **16 fresh cases / 128 CLI commands / 48

The three native snapshots per case load source, independently authored

Working controls, both repetitions:

- `plain`: a one-line memo with the same literal account text stays exact.
- `prose`: a multiline memo whose line starts `Planned Expenses:…`, rather

- `flag-only`: a multiline account-looking memo stays exact when no account

- `other-entry`: the account-looking text in a separate multiline Note after

Every control's final file matches its manually constructed expected file

## Cause, ownership and scoped repair

`cli/src/bea_engine/ledger/updating.py:369–381`, `_edit_postings`, scans every
physical line in the entry's span. `_POSTING_LINE` (:328) matches whitespace
plus the old account token. It has no quoted-string context: a continuation
line inside a multiline string is indistinguishable from a posting to that
regex. The comment at :373 about metadata keys ending in `:` applies to the
opening metadata line, not the continuation. `plan_rewrite` (:420–422) invokes
it for bare and explicit account changes; both preview (:481) and apply
(:494) use that plan. A valid candidate cannot reveal the wrong text: the
changed string is still legal ledger text.

Restrict replacements to the selected transaction's actual posting-account
tokens, using parser/source locations or full-file lexical context that
recognizes multiline strings. Preserve literal fields and unrelated bytes;
retain preview-only behavior, precise requested account/flag effects, native
validation, no-ops and atomic writes. Do not rewrite all occurrences of an
account name or normalize the existing strings. No upstream fork, dependency
or API-surface change is required.
