# Preserve inferred quantities in multiline lot postings

**Minor · cli · 35–50m · A1 · worker1.** Export a valid ledger with
newline-valued lot labels, check the first copy successfully, then export
that copy again: both exports exit 0, but the second copy fails `bea check`
with an ambiguous sale. The first printer renders the label across physical
lines; the reader then forgets that the share quantities were inferred.
Reloading the next export gives two dated lots in place of one undated lot.
An already multiline source fails on its first export. Single-acquisition
and FIFO cases still check while silently changing lot dates. Source files
remain byte-identical. No product fix implemented.

Local CLI QA, 2026-10-28, `bea 0.3.1` checkout sources pinned to
`e08f21ca46c6127e897d3da54f597e15d25b7ec1` (1,741 fingerprinted CLI files),
frontend Python 3.13.3, existing managed Python 3.12.10 / Beancount 3.2.3 /
Beanquery 0.2.0, macOS 26.5.1 arm64. Main `4ee778036` has the same local
reader/query implementation; its CLI differences are generated cloud clients.
Fresh offline subprocesses, closed stdin/no TTY, isolated child config/cache,
HOME unchanged, synthetic ledgers only.

## Standalone reproduction

Put checkout `bea` on PATH, save as `recipe.py`, and run:

```sh
python3 recipe.py /absolute/unused/qa-multiline-export
```

The input uses one physical line per posting and the native `\n` spelling
inside the quoted label. No multiline posting is manually introduced by
the user: the first `PRINT` produces it. The script retains the five command
transcripts and input hashes in `results.json`.

Actual exits: **0, 0, 0, 0, 1**. The final error names two matching
`First\nLot` lots dated **2024-01-02 / 2024-01-03**. Native comparisons:

| File | Native lots after the sale | Check |
| --- | --- | --- |
| original | one 4 HOOL lot at 5 USD, `Cost.date=None` | valid |
| first export | the same 4 HOOL undated lot | valid |
| second export | 2 HOOL dated Jan 2 and 3 HOOL dated Jan 3; sale cannot book | invalid |

Before export, `list transaction --search Buy --json` reports
`units.inferred: true` for both acquisitions. Listing those same buys from
the first export omits the marker, though a complete native parse still
finds both source quantities missing. Numeric booked quantities remain 2/3;
the missing source marker is the read defect before export changes any lot.

Repeated fresh controls confirm the boundary:

- Literal multiline labels fail on the first `PRINT`, including an included
  Unicode-named journal. Their native values equal the escaped-label source.
- Plain one-line labels and explicit quantities with a shared acquisition
  date remain valid and preserve lot identity through both exports.
- A single inferred acquisition silently changes `None` to Jan 2 while all
  checks pass. FIFO splits the undated 4-share position into dated 1/3-share
  lots, also with successful checks and unchanged cash/total cost.

## Cause and repair

`cli/src/bea_engine/ledger/reader.py:533–573` (`_number_left_open` /
`_line_leaves_number_open`) reads only `lines[lineno - 1]` and parses it after
a fake transaction header. A line opening the multiline cost-label string
is not a complete posting; parsing fails to recover its posting and the
helper returns false. The real whole-file parse is valid and already retains
`MISSING` in that posting's units.

The false result suppresses `Units.inferred` in `_to_transaction` (:613) and
prevents `query._with_inferred_units` (`query.py:1887–1907`) from leaving an
undated lot's quantity open again. The printer emits its booked number;
native reload dates that augmentation, so the two purchases separate and
the sale becomes ambiguous. This is source parsing, with real filename/line
metadata, rather than a native booking failure.

A three-state trace compares the escaped original, its first printed copy,
and a literal multiline source. `reader.declared_entry`'s existing parsed
source cache finds `MISSING` in all three; the line-based helper returns
**true / false / false**. The last two individual-line parses have syntax
errors and no recoverable posting. The information needed for the repair is
already available without loading plugins or inferring accounting math.

Inspect the complete source posting, reusing the parsed-entry/source cache,
when deciding whether its number was left open. Keep current explicit-number,
missing/generated-source, source provenance and reload/cache semantics.
Preserve the inferred marker and missing-number rendering for representable
source-backed lots. No dependency or backend/API change is needed.
