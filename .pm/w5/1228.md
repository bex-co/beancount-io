# The sidebar's upcoming-events count reaches one day further than Fava's, and `upcoming-events 0` does not turn it off: "Events 1" for an event 7 days away, and again on an event's day when the count is disabled

**Severity:** minor. Nothing is computed wrongly in the books, but the sidebar's only reminder disagrees with the option that configures it. A reader who sets `upcoming-events` to `0` to silence the badge, as Fava's help says to, still gets a status badge on every event's day. **Owner:** `dashboard`. **Estimate:** 15–25 minutes including tests. **A2:** a newcomer bringing a Fava ledger keeps its `fava-option` lines and expects them to mean what they meant in Fava. **Found by:** `/qa-find-bugs-dashboard` (`dashboard-qa` routine) on 2026-11-27 against `https://beancount.io`, production entry chunk `main-BBmi61Hs.js`. QA-owned headless Chromium 158, fresh isolated contexts with `timezoneId: "UTC"` and a fixed Playwright clock, 1440×1000, English. Reproduced signed out on the public ledger and signed in on a disposable `qa-` ledger. The probe lines were added, then removed: `main.bean` is byte-for-byte restored (blob `64a178bd` again) and the ledger has no errors. Local HEAD `45cf006cd`.

## Repro

**Default horizon, public ledger, no sign-in.** `open_ledger/example` keeps the default `upcoming-events` of 7 (GraphQL `favaOptions.upcomingEvents: 7`). Its last event is `2017-06-03 event "location" "New Metropolis"`.

1. Fix the browser clock at 2017-05-26 12:00 UTC and open `/ledger/open_ledger/example/journal`. The sidebar has no Events link (8 days away).
2. Fix it at 2017-05-27 12:00 UTC (7 days away) and reload. The sidebar shows link **Events** with badge **1**.
3. At 2017-05-28 and 2017-06-03 it shows Events 1. At 2017-06-04 the link is gone.

Fava 1.30's `upcoming_events` (`fava/core/misc.py`) keeps an event when `0 <= (event.date - today).days < upcoming_events`. Its help calls them "events less than `upcoming-events` days away". So for 7, Fava counts today through today+6, and step 2 would show nothing.

**Disabled count, any ledger you own.** Add:

```beancount
2026-01-01 custom "fava-option" "upcoming-events" "0"
2026-07-01 event "location" "qa-probe"
```

GraphQL returns `favaOptions.upcomingEvents: 0`.

4. With the clock at 2026-07-01, open the Journal. The sidebar shows **Events** with badge **1**. At 2026-06-30 there is no link.

Fava's help: "Set this value to `0` to disable this feature."

## Cause

`dashboard/src/common/lib/events/upcoming-events.ts:20-27` builds an inclusive window, `endDate = today + N` with `event.date <= endDateString`. That counts N+1 days, and with N = 0 it still matches today. The count drives `common/components/ledger-layout/ledger-sidebar.tsx:167-170`: the Events link's visibility (`:316-317`), its badge (`:319-321`) and the status group's badge (`:353`). The tests in `common/lib/events/__tests__/upcoming-events-timezone.test.ts` pin the inclusive window: `:76` "still shows the November 16 event on November 9", `:93` "includes the last day inside the horizon" and `:112` "treats a zero horizon as today only". w4/done/124 fixed a time-zone shift in this window and kept "the inclusive configured horizon" as it found it. It never compared that horizon with Fava's.

## Fix

Owned by `dashboard`. Count an event when `today <= event.date < today + N`: keep `endDate = today + N` and compare with `<`. N = 0 then counts nothing, and the Events link stays hidden except on the Events page itself. Keep w4/124's calendar-day handling (date-fns `format` on the local date, never `toISOString`). Move the three tests above to Fava's boundaries.
