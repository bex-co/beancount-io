## Typed metadata becomes false evidence of a written entry

The default source has one Note with `approved: FALSE`. Its inspected plugin
keeps the Note and appends a copy at the **same date, type, filename and line**,
changing only `approved` to Decimal zero. Both are valid native metadata.
Cash stays **100 USD** in the authored reference and calculated ledger.
The full calculated view legitimately has two Notes.

Actual JSON for both full and on-disk lists includes:

```json
{"meta":{"approved":false}}
{"meta":{"approved":{"kind":"number","value":"0"}}}
```

Neither row is marked generated. The source file never states the numeric
value. On-disk count is **two**, and limit 1 wrongly reports
`truncated: true`; human on-disk output also prints two unmarked rows.
Reversing plugin order keeps the error and lets the numeric copy occupy the
limited result. Fresh checks/native loads pass and every input byte remains
unchanged. This is a read/provenance and pagination defect; no monetary write
or accounting loss is claimed.

The same result occurs for TRUE→1, 0→FALSE and 1→TRUE, and for Event and Price
copies. JSON faithfully retains each native type, so serialization is working;
source classification is incorrectly equating those typed values. Expected:
keep both calculated rows, mark the type-changed copy generated, and retain
only the original declared type/value under on-disk filtering. That result
must be independent of plugin order and limiting.

## Root cause and consumer path

`cli/src/bea_engine/ledger/reader.py:_field_declared` (:236–254), the `meta`
branch, checks that each authored key exists and `held[key] == value`.
Python gives true for these bool/Decimal pairs. `_declares` (:200–232) uses
that helper for the known fields of non-transaction directives. At a shared
location, `entry_generated` (:456–511) therefore marks both the original and
its contradictory typed copy as written.

Forty-eight real helper proof runs read the actual full-file declaration and
loaded copies through `declared_entry`, `_field_declared`, `_declares`,
`shared_locations` and `entry_generated`. Every failing copy has a different
native type, equal Python value, `meta_declares: true`, declaration true and
generated false. The original also passes. The reader module SHA-256 matches
the immutable CLI source for every proof. Controls retain their correct
field/metadata eligibility.

`ledger/listing.py:110` applies that classification before sorting and the
limit, causing both wrong membership and truncation. `metadata_to_json`
(`reader.py:534–548`) correctly distinguishes Decimal numbers from booleans;
`list_notes` (:656), `list_prices` (:688) and `list_events` (:840) return that
metadata and the same generated marker. The frontend
`cli/src/cli/commands/list.py:418–467` shows the row count/source markers from
those results. Producer, classifier, JSON serializer and human consumer
therefore locate the failure in the declaration comparison.

Compare explicitly declared metadata with its native value type as well as
its value, keeping numeric Decimal equivalence and supported numeric subclasses.
A boolean must not match a number solely through Python equality. Preserve
source-known keys, allowed added metadata, location/internal-key exclusions,
current unique-location policies, omitted booking/tolerance wildcards and
allowed-currency set equality. Keep the full calculated view and all original
field checks. No dependency, upstream fork or backend/API change is needed.
A1 outcome: agents reading on-disk review annotations receive the types the
ledger actually declares and reliable pagination over those declarations.
