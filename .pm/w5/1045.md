# Preserve native bank IDs when extracting CSV cells

**Major · cli · 25–40m · A1 · worker1.** A quoted CSV native reference
` payment-2026` or `payment-2026 ` is changed to `payment-2026` before
identity lookup. After importing a real payment under that unspaced ID,
the second distinct same-day payment is falsely skipped as an exact
duplicate, even with `--duplicates include`. Apply exits0/written0 and
Cash stays90USD instead of80. A different amount falsely conflicts instead
of importing. Native Python-importer controls preserve both IDs and the
expected amounts. No product fix implemented.

Both statements are produced with `csv.QUOTE_ALL`. The first references
`payment-2026`; the second has one additional leading or trailing space
inside the quotes. Python's independent DictReader control recovers that
exact distinct string before the CLI runs. All other fields are identical:
January2 Payment, −10USD, Cash→Food, initial Cash100/Opening−100.

Actual second CSV preview, human and JSON: one `duplicate`, zero ready,
reason `import-id bank:payment-2026 is already in the ledger`. Its entry
already contains **unspaced** bank_id/import-id. Include/apply and repeat
both exit0/written0, no diff. Native source after has only one Payment:
Cash90, Food10, Opening−100USD. Check passes, BQL and balance-sheet agree.
The human preview explicitly reports “Nothing new to import.” No existing
row or amount is erased; a distinct real payment is omitted.

With a second amount of−12USD, the same identity collapse yields
`conflict`, apply/repeat exit4/written0 and unchanged Cash90. The error
advises editing/removing an existing entry, changing the bank ID or dropping
the row even though the input IDs already differ. This is a second effect
of the same extraction loss, not another finding.

The inspected Python importer passes the raw ID cell as bank_id. For the
same amount the ordinary classifier correctly says `possible_duplicate`
because date/narration/source amount agree while bank IDs differ; explicit
include writes one new row. For changed amounts it correctly says `new`
and writes one. Final native Cash80/Food20, or Cash78/Food22, and
Opening−100; both native IDs/import-ids persist and repeat writes0. Standard
and renamed roots agree. These controls retain the normal fuzzy-review
policy; distinct native IDs need not bypass that review automatically.

Case-only differences, interior spaces and IDs containing commas/quotes
also preserve both IDs under CSV, write the reviewed second row and skip
its repeat. The identical-ID control correctly skips an identical payment
and refuses a changed amount as a conflict, keeping Cash90. These must
remain exact-ID protections after fixing extraction.

Expected: preserve a nonblank mapped native reference's parsed field value
before constructing bank_id/import-id. Spaces within a field are data
([RFC4180 §2.4](https://www.rfc-editor.org/rfc/rfc4180.html#section-2)).
The CLI's existing [native-ID contract](../../cli/docs/IMPORTING.md)
distinguishes exact identity from possible duplicates; completed
[919](./done/919.md) explicitly preserves case and whitespace differences.
Do not merge two distinct references into the same exact-match key.
