# Let identical heuristic orders reach the same-day booking planner

**Major · cli · 45–60m · A1 · worker1.** A same-day partial short cover
listed before its opening is refused even though the complete batch books.
`--partial` unnecessarily writes only the cover, leaving a long holding
instead of the requested remaining short. The same gate also misses a
short-position split and a custody chain. This is a remaining boundary of
completed [884](./done/884.md) and [980](./done/980.md); their full original
acceptance is rechecked below. Their completed records remain unchanged.

Environment: reproduced 2026-10-27, bea 0.3.1, macOS 26.5.1 arm64,
frontend Python 3.13.3, existing managed Python 3.12.10 / Beancount 3.2.3.
Tested immutable CLI source `0c2c69bd09407962f0a51e17411155acfcca035c`;
all 1,741 tracked CLI files match current main at `466715b032082c1f5545ceb3256e0780f74caadd`.
No product fix implemented.

## Reproduce

Run this complete recipe with the real `bea` for that checkout on PATH and a fresh absolute
`case` path. It uses synthetic ledgers, closed stdin, no TTY, isolated child
configuration/cache paths, a 25-second limit per command, unchanged HOME,
and no hosted service. Each command prints its argv, streams, status,
timing, and before/after hashes. The independently applied valid-order
control uses the same rows and amounts.

## Split and custody cases, controls, and file effects

Set `shape='split'`: open −3 HOOL at cost 100 USD, split into −6 at cost
50 USD, cover four at 40 USD. The reverse batch refuses atomically; partial
writes only the cover. Set `shape='custody'`: the original −3 lot moves
A → B → C before that split and cover. Reverse input refuses atomically;
partial writes three of five, omitting B → C and the split. The result
holds **−3 HOOL at 100 USD in B** and **+4 HOOL at 50 USD in C**, rather than
**−2 HOOL at 50 USD in C alone**. Both have cost net worth 1040 USD and
profit 40 USD, so headline totals do not establish that custody completed.

## Root cause and bounded repair

[`_transactions`](../../cli/src/bea_engine/ledger/adding.py#L2030) calls
`_booking_order` before the whole-batch append is validated. In
[`_booking_order`](../../cli/src/bea_engine/ledger/adding.py#L2175), the rule,
original input and eager heuristic all produce the same row indexes here.
It immediately returns that order, before testing whether it books and
before calling `_built_booking_order`. Identical guesses are treated as
proof that another order cannot work.

The heuristic at
[`_same_day_purchases_first`](../../cli/src/bea_engine/ledger/adding.py#L2267)
uses positive cost postings as buyers and negative ones as sellers. A
positive partial cover remains before its later negative opening, so neither
heuristic changes this input. The existing builder already handles it when
reached. Three read-only traces of the actual installed helper sources show:

| Batch | Selected / rule / eager | Validations during selection | Builder calls during selection | Direct existing builder |
| --- | --- | --- | --- | --- |
| Pair | `[0,1]` | 0 | 0 | `[1,0]`, valid |
| Split | `[0,1,2]` | 0 | 0 | `[1,0,2]`, valid |
| Custody and split | `[0,1,2,3,4]` | 0 | 0 | `[1,0,2,3,4]`, valid |

Each selected whole order fails native append validation; the direct
builder's whole order passes without changing any file. The valid order
need not equal the chronological reference's physical order; its exact
financial positions must agree. Observer hooks only record calls and invoke
the existing functions; they do not replace validation or change the CLI.

Fix in the CLI engine: do not skip a booking-aware decision solely because
the heuristic permutations coincide. Preserve an order that already books;
when this same-day costed batch fails, let the existing bounded builder
try it before refusing or recovering a subset. Preserve its n²+64 bound,
lot selectors, original input indexes, genuine-error validation, partial
status, and valid LIFO/HIFO sale choices. No exhaustive scheduler, weaker
validation, dependency, or server change is needed.

History: the equivalent early return originated in `0500e45b6` (884), was
preserved by `b629ab35d` (1002), and remains after `686e2ece1` (980's
backtracking). The root is reaching the planner, rather than its back-up
strategy. Caller search finds this path only under bulk `add transactions`:
frontend `cli/src/cli/commands/add.py:611` → engine dispatch
`adding.py:69` → `_transactions` at :2030. Single add, native import and
backend behavior are not claimed.
