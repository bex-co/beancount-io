# 192 — Calendar-impossible bare date literals silently evaluate as arithmetic (`2024-02-30` → `1992`)

**Severity:** minor (loud on stock via crash; silent reinterpretation on MCP).
**Estimate:** 1–2h (lex date-shaped `N-N-N` strictly; refuse like `date()` does).
**Owner:** ledger engine lexer. **A1:** agents typoing a month/day in a bare date.

Valid bare dates agree (`2026-01-15` → date both; non-padded `2026-1-5` →
MCP date, stock arithmetic `2020` — MCP the sensible side there). But when the
shape is date-like and the calendar value impossible, the engine falls back to
subtraction with no signal:

| literal | MCP | stock |
|---|---|---|
| `SELECT 2024-02-30` | `1992` (Decimal) | `ValueError: day is out of range for month` (crash, loud) |
| `SELECT 2026-13-01` | `2012` | `ValueError: month must be in 1..12` (crash, loud) |

- REST twin agrees with MCP (`rows:[["1992"]]`, dtype Decimal) — shared path.
- MCP is internally inconsistent here: `date('2024-02-30')` is a typed error
  (`invalid date …`, 022:it.5179) while the bare literal silently arithmetizes.
  The bare form should refuse with the same typed date error.
- Stock's crash is loud but graceless; no oracle change asked — the ask is the
  typed refusal MCP already implements one layer up.
- Zero legs: `2026-00-01` → MCP `2025` (arithmetic), stock month-crash;
  `2026-01-00` → MCP `2025`, stock day-crash — same fallback. Exception:
  `0000-01-01` → MCP returns the proleptic DATE (not arithmetic) while stock
  crashes (`year 0 is out of range`) — year-0 is accepted-date leniency, a
  different cell from the arithmetic fallback (beancount dates are Python
  `datetime.date`, which has no year 0).
- QA ledger untouched (read-only probes; byte-identical + stock-clean re-verified
  this loop: blob f1a0b83c, SHA-256 77c3a591, 2817 B).
