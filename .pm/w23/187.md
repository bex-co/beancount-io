# 187 — Past-i64 GROUP/ORDER BY ordinals silently degrade to constants (w23/133 followup)

## Summary
w23/133 exempted bare GROUP/ORDER BY ordinals from integer rescue on the premise that "a huge ordinal is an out-of-range error on both sides today" (`bql-int-literals.ts`). That holds only through i64::MAX: `ORDER BY 9223372036854775807` errors loudly, but `ORDER BY 9223372036854775808` silently answers one row (dead no-op sort, ASC and DESC alike), and `GROUP BY 99999999999999999999999` silently collapses to one group (`* 34`) — while stock loudly refuses both (`invalid ORDER-BY/GROUP-BY column index …`). The hole band is (i64::MAX, Decimal::MAX]: the rewrite exempts ordinals by design, the `integerOverflowError` guard's literal rule fires only past MAX, and the engine constant-folds what it cannot lex as an ordinal. (Past-MAX numerals stay loud via the guard on main / token-reject on prod.)

## Repro
- `call runBqlQuery {"ledger":"puncsky/mcp-agent-eval","query":"SELECT flag ORDER BY 9223372036854775808 LIMIT 1;"}` → `1 row / *` (GraphQL `queryShell` twin: `[["*"]]`, engine-level, all surfaces). Same silence at 20 and 25 digits; i64::MAX itself errors.
- `… GROUP BY 99999999999999999999999 …` → `1 row / * 34`.
- Stock controls: `CompilationError: invalid ORDER-BY column index 9223372036854775808…` / `invalid GROUP-BY column index …`.

## Expected
Refuse past-i64 ordinals in GROUP/ORDER key lists (extend the guard's ordinal-unaware literal rule, or bound the exemption), restoring the loud error both sides agree on below the band. Owner decides guard-vs-rewrite; bisected edges live above.
