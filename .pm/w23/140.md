# 140 — Nested multi-word keys are camel-only while top-level params dual-accept snake/camel (it.6373-6380)

**Severity:** minor (one wasted agent turn per paste; schema error names the fix). **Owner:** backend-v2 entry schemas. **A1:** agents writing pads.

## Repro (prod, puncsky/mcp-agent-eval, dry_run — no writes)

`addLedgerEntries` top-level params accept both spellings (`dry_run`/`dryRun`, `allowInvalid`/`allow_invalid` — verified live it.6367), and every other nested entry key is a single caseless word (`account`, `units`, `cost`, `price`, `flag`, `meta`, `tags`, `links`, `tolerance`, `booking`). But pad's source field is camel-only:

- `pad: {date, account, sourceAccount}` → schema-accepted (reaches bean-check: `Unused Pad entry`, it.6373).
- `pad: {date, account, source_account}` → `BAD_USER_INPUT: …sourceAccount: Invalid input: expected string, received undefined; …Unrecognized key: "source_account"` (it.6373).
- REST `POST …/entries` refuses identically (`VALIDATION_FAILED` naming `body.entries.0.entry.sourceAccount`, it.6374) — consistent, all surfaces.

`sourceAccount` and posting `totalPrice` are the only multi-word nested keys in the entry schema — `total_price` is likewise `Unrecognized key` (it.6380). Both splits, same fix. m3 unified top-level splits (`entry_hash`, commit message) only; nested casing was never in scope.

## Expected

Accept `source_account` alongside `sourceAccount` (alias, same as the top-level dual-spell params), on all surfaces; or document camel-only nested keys where agents read the entry schema.
