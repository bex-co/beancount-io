# BQL queries over ~10 KB fail with `INTERNAL_SERVER_ERROR` instead of a documented limit refusal

**Severity:** minor (a client-size problem answers 5xx with a retry-hint that cannot help; agents chasing the hint waste calls). **Estimate:** 1–2 hours. **Owner:** `backend-cluster/backend-v2` (shell service / tool schema) + `backend-cluster/ledger` (shell endpoint). **A1/A2:** agents build long generated queries (bulk `OR` chains, long literals) and get an unactionable server error.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`runBqlQueryStructured`, bisected by shape and size (each retried per the hint; failures persist):

- 450 `OR` payee clauses (~9.1 KB) → `ok`, 0 rows; 500 clauses (~10.1 KB) → `INTERNAL_SERVER_ERROR: Failed to execute shell query` with "Retry once. If it persists the failure is server-side…".
- Single 9,000-char string literal → `ok`; 30,000-char literal → same `INTERNAL_SERVER_ERROR`.

So the boundary is query size (~10 KB), not shape. `runBqlQuery` (text) shares the path.

## Cause (unverified past backend-v2)

Backend-v2 forwards the query to the ledger service as a GET query parameter (`backend-cluster/ledger/src/api/shell.ts`: `strQuery(ctx.query.query)`), and wraps any downstream failure in `unwrapFavaResponse(..., "execute shell query")` (`backend-cluster/backend-v2/src/features/ledger/service/ledger-shell-service.ts:59-65`), so a transport/parser size cap downstream surfaces as a generic 500. No length is validated or documented on the MCP tool, REST, or GraphQL schemas (searched: max/query/length — nothing).

## Fix (keep REST/GraphQL/MCP in parity)

Either validate the query length up front and refuse oversize queries with `BAD_USER_INPUT` naming the cap (and document it in `docs/mcp.md` next to the BQL tools), or move the backend→ledger hop to a POST body so legitimate long queries work. Prefer the refusal if the engine itself cannot take more.
