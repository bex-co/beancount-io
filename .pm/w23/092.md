# BQL queries over ~16 KB URL-encoded fail with `INTERNAL_SERVER_ERROR` instead of a documented limit refusal

**Severity:** minor (a client-size problem answers 5xx with a retry-hint that cannot help; agents chasing the hint waste calls). **Estimate:** 1–2 hours. **Owner:** `backend-cluster/backend-v2` (shell service / tool schema) + `backend-cluster/ledger` (shell endpoint). **A1/A2:** agents build long generated queries (bulk `OR` chains, long literals, CJK text) and get an unactionable server error.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`runBqlQueryStructured`, bisected by shape and size (each retried per the hint; failures persist). Cliff pinned exactly (it.447):

- `'A'`×15,979 literal (15,979 raw / ~16,026 URL-encoded chars incl. query scaffolding) → `ok`, 0 rows; `'A'`×15,984 → `INTERNAL_SERVER_ERROR: Failed to execute shell query` with "Retry once…".
- `'é'`×2,650 (only 2,681 raw chars, ~15,947 URL-encoded) → `ok`; `'é'`×4,000 → same 500.

So the budget is ~16 KB of **URL-encoded** query text, not raw size or shape — CJK/accidental-unicode queries hit it at ~1/6 the raw length of ASCII ones. `runBqlQuery` (text) shares the path. Earlier 500-`OR` (~10.1 KB raw) failure is consistent: its spaces/quotes expand past the encoded budget.

## Cause (unverified past backend-v2)

Backend-v2 forwards the query to the ledger service as a GET query parameter (`backend-cluster/ledger/src/api/shell.ts`: `strQuery(ctx.query.query)`), and wraps any downstream failure in `unwrapFavaResponse(..., "execute shell query")` (`backend-cluster/backend-v2/src/features/ledger/service/ledger-shell-service.ts:59-65`), so a transport/parser size cap downstream surfaces as a generic 500. No length is validated or documented on the MCP tool, REST, or GraphQL schemas (searched: max/query/length — nothing).

## Fix (keep REST/GraphQL/MCP in parity)

Either validate the **URL-encoded** query length up front and refuse oversize queries with `BAD_USER_INPUT` naming the cap (and document it in `docs/mcp.md` next to the BQL tools), or move the backend→ledger hop to a POST body so legitimate long queries work. Prefer the POST: a raw-char cap would still mislead on unicode-heavy queries. Fix must cover REST/GraphQL/MCP equally.
