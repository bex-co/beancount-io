# A file-write gate reads an unreadable baseline as "no errors", so every existing error reads as new

**Bug · backend-v2 · minor · ~30m · A1.** Found by the `w23/m39` review, 2026-11-10, from source; no runtime repro.

- **Where:** `gateFileWrite` (`src/features/ledger/utils/file-write-gate.ts`) catches a failed baseline `getErrors` read and uses `[]`, with the comment "fail-open, as in the post-write verdict". The post-write verdict no longer does that: `withPostWriteValidation` reports `checked: false` with the reason (`w23/031`).
- **Effect:** when the baseline cannot be read but the projection can, the preview and the commit gate of every file tool and of the rename preview read each error the ledger already had as a new one and answer `valid: false` with `checked` unset, which is the `w1/236` symptom. The commit gate can refuse a write that adds nothing.
- **Expected:** one rule for an unreadable baseline on every verdict: the verdict says it was not checked and names why, and the gate does not refuse on it.
- **Fix:** return the baseline's failure from the gate and report `checked: false` as `withPostWriteValidation` does; decide whether the commit gate refuses or passes in that case (it should not refuse on errors it cannot tell apart from existing ones).
- **Check:** a case in `preview-commit-differential.test.ts` whose fake `getErrors` throws once: preview and commit carry the same `checked: false`.
