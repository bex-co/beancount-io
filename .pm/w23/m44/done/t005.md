## Objective

A host that surfaces only a JSON-RPC error's `message` should still show the agent what to do next.

## Context

- Resources and prompts have no `isError` result, so a refusal is a JSON-RPC error. `McpRequestFailure` (`backend-cluster/backend-v2/src/features/ai-agent/api/mcp-errors.ts`) sets the message to `envelope.message` and puts `code`, `hint`, `newLedgerErrors` and `limitOwner` only in `data`.
- Tool refusals already lead their text with `CODE: message` and `Hint: …` (`renderErrorText`) and, since `f58c89d64`, end with the envelope.
- The SDK prefixes `MCP error <code>:` once on the client. Keep it to one prefix (w2/m28:t003).

## Steps

1. Build the resource and prompt refusal message from the envelope, `CODE: message` then the hint, keeping `data` unchanged.
2. Update the tests that assert resource or prompt error messages.
3. Note the format in `docs/mcp.md` § The result envelope.

## Acceptance criteria

- [x] A refused resource read's `error.message` contains its code and hint, with exactly one `MCP error` prefix after the client round trip.
- [x] `error.data` still equals the envelope.

## Out of scope

- REST and GraphQL error messages.

## Result

`McpRequestFailure` builds its message with `renderErrorText(envelope)`, the same `CODE: message`, `Hint: …` (and `Retry after: Ns`) lines a tool refusal's text leads with, and leaves `data` as the envelope. The SDK client still adds exactly one `MCP error <n>:` prefix. Every resource and prompt refusal goes through it, including an unmatched resource URI and a malformed prompt argument. Tests: `mcp-errors.test.ts` asserts the message, with no SDK prefix. `mcp-resources.test.ts` (an argument refusal, a URI that is not a resource, an unknown resource) and `mcp-prompt-list.test.ts` (a malformed prompt argument) assert the full client message, `MCP error <n>: CODE: message` followed by the `Hint:` line. `docs/mcp.md` § Failure codes describes the format.
