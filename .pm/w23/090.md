# Mutation tools disagree on parameter naming: `entry_hash` vs `entryHash`, commit message `description` vs `message` vs none

**Severity:** minor (papercut; strict-schema errors guide recovery, but copy-paste across tools fails). **Estimate:** 1–2 hours incl. parity. **Owner:** `backend-cluster/backend-v2`, MCP tool schemas + REST/GraphQL counterparts. **A1/A2:** agents copy hashes from list output into mutation calls and reuse one commit-message argument across file tools.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

1. `listLedgerEntries {limit: 2}` returns entries keyed `entry_hash` (snake). Passing one straight into `getEntryContext {entry_hash: ...}` fails strict validation:
   `BAD_USER_INPUT: entryHash: Invalid input: expected string, received undefined; Unrecognized key: "entry_hash"`.
   The tool wants `entryHash` (camel) — while its own result echoes `entry_hash` back. Same split on `updateEntrySource` / `deleteEntrySource` / `deleteEntrySources`.
2. The commit-message argument differs per file-mutation tool: `createLedgerFiles` / `updateLedgerFiles` / `deleteLedgerFiles` take `description`; `renameLedgerFile` takes `message` (passing `description` → `Unrecognized key: "description"`); `addLedgerEntries`, `appendLedgerText`, and the entry-source tools take neither (server-composed message).

## Fix (pick one per split, keep REST/GraphQL/MCP in parity)

1. Accept both `entryHash` and `entry_hash` on the entry tools (alias, not rename — outputs already say `entry_hash`), or rename outputs to camel; document the one rule.
2. Accept both `description` and `message` on the file-mutation tools (alias), or converge on one name everywhere; document which tools compose their own message and why.
