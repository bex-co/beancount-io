## Objective

Give an agent a bounded page of staged bank transactions, with a signal that says whether more remain, so a first sync with months of history does not overflow the host's tool-result limit.

## Context

- `getUnsyncedByAccountId(s)` in `backend-cluster/backend-v2/src/features/plaid/data/plaid-transaction-model/postgres-impl.ts` has no limit, and a row has about 23 fields. The MCP tool (`mcp-list-tools.ts`), the `bankUnsyncedTransactions` resource, REST `GET …/bank-transactions/unsynced` and GraphQL `getUnsyncedPlaidTransactions` all return every row.
- Since `f58c89d64` the whole result also lands in the text block that claude.ai reads.
- The dashboard's Bank Sync page reads the GraphQL query and expects every row (`dashboard/src/features/plaid/hooks/use-plaid-accounts.ts`). Mobile ships the same query in its generated schema.
- Page signals come from one table, `backend-cluster/backend-v2/src/server/api/page-signals.ts` (`PAGED_READ_NAMES`).
- The root `AGENTS.md` parity rule: inputs, defaults and results match on REST, GraphQL and MCP.

## Steps

1. Add `limit`/`offset` and `total` to the read on all three surfaces and the resource, and register its page signal.
2. Choose defaults so that an agent following the MCP description gets a bounded page while the dashboard still gets every row. Either the dashboard pages or passes an explicit limit, or `limit` stays optional and the description makes it the documented path. Record the choice in `docs/mcp.md`.
3. Update the tool description, the categorize-imports prompt and the OpenAPI snapshot (`yarn generate-v1-openapi`).

## Result

`listStagedBankTransactions`, the `bank-transactions/unsynced` resource, REST `GET …/bank-transactions/unsynced` and GraphQL `getUnsyncedPlaidTransactions` take an optional `page` and a `limit` of at most 100. REST and MCP use the shared `paginationSchema`. All four call `PlaidItemService.getUnsyncedTransactions`, which applies the bound through the shared `assertPageArgs` (moved from the ledger workflow to `@/shared/page-info`), so GraphQL refuses what the schemas refuse. Each read carries the page signal from `page-signals.ts` (`listStagedBankTransactions`, `bankUnsyncedTransactions`): the MCP `page`, the resource `_meta.page`, the REST `X-Has-More`/`Link` headers and GraphQL `extensions.page`. The staged-row query now breaks date ties by id, so a page holds the same rows on every read.

Two deviations, both following the rest of the board:
- **No `total`.** The result stays a bare array, so this is a `page`/`limit` read like `listLedgers`: `hasMore` means "the page came back full".
- **Omitting `limit` still returns every row.** The dashboard reads the staging area that way, and `listLedgers` behaves the same. An agent following the tool description passes `limit`. The description, the categorize-imports prompt and `docs/mcp.md` also say why: imported and discarded rows leave the list, so after acting on a page, read page 1 again rather than the next page.

Tests: `staged-paging-parity.test.ts` drives the real service and all four adapters with 250 rows. It checks the first page (100 rows, `hasMore: true`, REST `Link` to page 2), the short last page, every row without `limit`, and refusal of `limit` 101, `limit` 0 and `page` 0. REST refuses with 400 `VALIDATION_FAILED`, like the catalog lists; the other surfaces use `BAD_USER_INPUT`. Removing the slicing fails two of these tests, and removing the bound fails three. OpenAPI was regenerated, and the CLI's pinned spec and client were re-synced.
