`readLedgerFiles` with no `start_line`/`end_line` returns the whole file, and the server sets no default bound (`backend-cluster/backend-v2/src/features/ai-agent/tools/read-ledger-files-tool.ts`; only the description suggests ranges). Since `f58c89d64` that whole file also lands in the text block claude.ai reads, so one unranged read of a multi-megabyte `main.bean` can exceed a host's tool-result limit. A naive cap is unsafe: an agent that reads a truncated file and then writes it back through `updateLedgerFiles` `content` would delete the rest. Decide on a bound that cannot lead to that, for example a refusal past N bytes that names the line count and asks for a range, rather than a silent truncation. Measure the largest files in the QA and example ledgers first, and record the decision in `docs/mcp.md`. Found in the 2026-11-13 MCP channel review (see `w23/m44`).

**Blocked 2026-11-13.** This needs a parity decision only the owner can make.
- **Correction to the note:** a ledger file is capped at 1 MiB, so the worst case is a 1 MiB whole-file read (about 250k tokens), not a multi-megabyte one. That is still far past a host's tool-result limit.
- **The decision:** the unranged read is the same operation as REST `GET …/files/{path}` and the GraphQL file read, and the dashboard editor needs whole files from those. A bound therefore either applies to the MCP tool alone, which needs a documented parity exception in `docs/api-parity.md` and ADR 0008 (a model reads tool results through a host with result-size limits), or changes all three surfaces and the editor.
- **Proposal, if MCP-only is accepted:** an unranged `readLedgerFiles` read of a file past 256 KiB is refused with `BAD_USER_INPUT`, naming `totalLines` and asking for `start_line`/`end_line`. That rules out a silent truncation followed by a truncated whole-file write-back.
- **Unblock:** the owner chooses MCP-only (with the exception recorded) or all surfaces, and picks the threshold.
