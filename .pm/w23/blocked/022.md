# Report rustledger BQL gaps upstream: multi-currency `cost(sum(position))`, `neg`/`filter_currency` signatures, empty `meta('lineno')`, `AT value`, `BALANCES FROM` lot booking

Split from `w23/012` (resolved 2026-10-20 in `20b15532e` with an in-repo guard). `@rustledger/wasm` 0.24.0 returns `cost(sum(position))` over several currencies as one `Amount`: the cost numbers of every currency summed under the first currency's label. beanquery returns one inventory entry per currency.

**Reproducer** (no network):

```beancount
2024-01-01 open Assets:Hours
2024-01-01 open Assets:Broker
2024-01-01 open Assets:Cash
2024-01-01 open Equity:Opening
2024-01-02 * "hours"
  Assets:Hours  -13 VACHR
  Equity:Opening
2024-01-03 * "buy"
  Assets:Broker  17 GLD {268.22 USD}
  Assets:Cash
```

```text
SELECT cost(sum(position)) WHERE account ~ '^Assets:(Hours|Broker)'
  → [{"number":"4546.74","currency":"VACHR"}]      expected: -13 VACHR, 4559.74 USD
SELECT sum(cost(position)) WHERE account ~ '^Assets:(Hours|Broker)'
  → -13 VACHR, 4559.74 USD                         (correct)
```

**Also from `w23/016`** (same engine, same report): `neg(sum(position))` and `-sum(position)` are refused ("NEG expects a number or amount" / "negation requires numeric value"), and so is `filter_currency(position, 'USD')` ("FILTER_CURRENCY expects (inventory, string)"). beanquery accepts all of these forms. `SELECT meta('lineno')`, `lineno` and `entry_meta('lineno')` return null, while beanquery returns the posting's line. On the ledger above:

```text
SELECT account, neg(sum(position)) WHERE account ~ '^Income' GROUP BY account   → type error
SELECT account, sum(filter_currency(position, 'USD')) GROUP BY account          → type error
SELECT meta('lineno') LIMIT 1                                                    → [[null]]
```

**Also from `w23/020`:** `BALANCES … AT value` and `JOURNAL … AT value` ignore the clause and return units. On a holding of `4 VHT` priced at `120.00 USD`, beanquery returns `480.00 USD` and rustledger returns `4 VHT`; `value(sum(position))` is correct. `BALANCES FROM year = 2021` fails with "No matching lot for VHT in Assets:Broker" when the window sells a lot bought before it. `SELECT account, sum(position) FROM year = 2021 GROUP BY account` runs. Separately, `BALANCES FROM CLOSE ON 2016-01-01` omits beanquery's `Equity:Conversions:Current` row. The reproducer ledger is in `w23/020` (`.pm/w23/done/020.md`) and in `verify:rustledger`.

**Also confirmed 2026-10-25** (same accessor family): `entry_meta('filename')` returns `""` on MCP while beanquery returns the path; `meta('lineno')`/`entry_meta('lineno')` still `""`/`null`. Include the filename accessor in the upstream report.

**Also confirmed 2026-10-26** (aggregate-of-aggregate): beanquery refuses `SELECT sum(cost(sum(position)))` (`CompilationError: aggregates of aggregates are not allowed`) while MCP answers one row of `""`. Same family as the `cost(sum(position))` collapse — include the silent-`""`-vs-refusal difference in the upstream report.

**Also confirmed 2026-10-26** (date arithmetic): beanquery runs `SELECT max(date) + 7` and `WHERE date >= today() - 10000`; MCP refuses both (`type error: arithmetic requires numeric values`). `today()` itself works on both. Workaround: compute the date client-side. Include in the upstream report. Extended it.826: `SELECT max(date) - min(date)` likewise runs locally (`239`) and refuses on MCP — date-date subtraction is in the same gap.

**Also confirmed 2026-10-26** (reverse direction, it.873): `SELECT payee, count(*) HAVING count(*) > 1` — MCP accepts it (implicit grouping, correct filtered rows), local beanquery rejects with `syntax error`. With explicit `GROUP BY payee` both return identical rows (modulo the NULL→`""` rendering gap). So the engine is a permissive superset here, not just a subset: queries valid on MCP can fail on stock beanquery. Include in the upstream report as a portability note. Extended it.1068: `HAVING n > 3` on a `count(*) AS n` alias likewise runs on MCP (5 correct rows) and refuses on stock (`column "n" not found`) — aliases are visible to HAVING only on MCP.

**Also confirmed 2026-10-26** (star expansion, it.905): `SELECT * LIMIT 1` returns 6 columns on MCP (`date, flag, payee, narration, account, position`) but 5 on stock beanquery (same minus `account`). Explicit `SELECT balance` works on both, so only the `*` expansion set differs — by exactly the `account` column. Positional consumers of `SELECT *` see different shapes. Include in the upstream report.

**Also confirmed 2026-10-26** (superset function, it.939): `SELECT currency(position)` returns `'USD'` on MCP; stock beanquery 0.2.0 has no `currency()` overload at all (`position`, `inventory`, and `str` all refuse). Same portability direction as the HAVING note: valid-on-MCP queries can fail on stock beanquery. Include in the upstream report.

Extended it.941: `number(position)` (`'3000.00'`) and `only("USD", position)` (3000.00 USD) likewise run on MCP and refuse on stock beanquery 0.2.0 (`no function matches`). The position-function superset is at least the trio `currency/number/only`.

Extended it.945: `safediv(1, 0)` runs on MCP (`'0'`) and refuses on stock beanquery — fourth superset function. Extended it.957: `substring(account, 1, 6)` likewise (`substr` matches on both) — fifth. Extended it.959: `trim("  x  ")` runs on MCP, refuses on stock — sixth; `replace()` is refused by both.

**Also confirmed 2026-10-26** (`id` scheme, it.983): `SELECT id, date ORDER BY date LIMIT 3` — same grouping on both (all three postings of the opening-balances txn share one id), but MCP reports a small ordinal (`12`) where stock beanquery reports a stable content hash (`a97a30004a873f788a94de8abf442116`). Same column name, different identity scheme: positional vs content-addressed. Include in the upstream report.

**Also confirmed 2026-10-26** (`cost` column, it.990): MCP accepts `SELECT cost` (renders `""`, NULL everywhere on the cost-free fixture; bogus columns still error, so it is a real column), while stock beanquery 0.2.0 has no `cost` column (`column "cost" not found`). Superset schema — values on cost-bearing postings unverified (fixture has none). Neighbors behave: `price` exists on both (`""` vs `None`), `meta` is whole-blanked on MCP vs a dict locally (the w23/016 `lineno` gap).

**Also confirmed 2026-10-26** (empty-table aggregation, it.1004): on the empty `prices` table (`SELECT *` → `[]` with identical `date/currency/amount` schema on both), `SELECT count(*)` returns `[[0]]` on MCP but `[]` (no rows) on stock beanquery. Same for `commodities`. MCP follows the SQL-standard single-row aggregate; stock returns nothing — another portability split in the reverse direction. Same for `sum(amount)` (it.1006: MCP `[['']]`, stock `[]`). Generalizes to any empty input: `SELECT count(*) WHERE 1 = 0` on the non-empty postings table gives `[[0]]` vs `[]` (it.1010). Grouped aggregation over empty input agrees (`[]` both, it.1008). Include in the upstream report.

**Also confirmed 2026-10-26** (`FROM close`, it.1012): stock beanquery silently runs `SELECT count(*) FROM close` against postings (34 rows, posting columns) — the `close` keyword collides and the parser falls back to the default table — while MCP correctly refuses (`evaluation error: table 'close' does not exist`). Sibling `FROM open/note/query/custom` refuse on both (varied messages). Here stock's leniency is the quirk and MCP is strict; include in the upstream report so the portability doc cuts both ways. Extended it.1089–1090 (set args): `length(accounts)` on the 4-account set returns `4` on MCP but crashes stock with a bare `__mro__` error; `upper(accounts)` refuses on both, but MCP names the expected type (`UPPER expects a string`) where stock again leaks `__mro__`. MCP is the better-behaved side on set-typed inputs. And a NULL-handling split: `maxwidth(payee, 10)` on a NULL payee passes `NULL` through on stock beanquery but hard-errors on MCP (`type error: MAXWIDTH: first argument must be a string`), while sibling `upper(payee)` on the same NULL coerces to `""` on MCP. So MCP is internally inconsistent on NULL string args (coerce vs error) and diverges from stock (pass-through) on `maxwidth`. Include both in the upstream report. Full NULL matrix (it.947, first row payee NULL): stock passes `NULL` through `upper/lower/length/maxwidth`; MCP coerces `upper/lower/length` to `""` (note `length` returns a *string* `""`, not int/null) and errors only on `maxwidth`.

**Also confirmed 2026-10-26** (NULL rendering): `SELECT 1/0 LIMIT 1` yields `None` in beanquery but `[[""]]` with dtype `str` on MCP structured output; absent payees likewise render `""` instead of JSON `null`. (Text output matches beanquery byte-for-byte — structured only.) Agents cannot distinguish NULL from empty string. Include in the upstream report.

**Also confirmed 2026-10-26** (`first()` null-skipping): row order is identical on both engines (null payees first), but `SELECT first(payee), last(payee)` yields `('NETFLIX', 'FARMERS MARKET')` in beanquery vs `[["", "FARMERS MARKET"]]` on MCP — beanquery's `first()` skips leading NULLs, rustledger takes the literal first row. Non-null `first(narration), last(narration)` agree. `last()` over trailing NULLs is symmetric-suspect (untested — no trailing-null column in the fixture). Include in the upstream report.
