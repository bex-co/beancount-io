# Report rustledger BQL gaps upstream: multi-currency `cost(sum(position))`, `neg`/`filter_currency` signatures, empty `meta('lineno')`, `AT value`, `BALANCES FROM` lot booking

Split from `w23/012` (resolved 2026-10-20 in `20b15532e` with an in-repo guard). `@rustledger/wasm` 0.24.0 returns `cost(sum(position))` over several currencies as one `Amount`: the cost numbers of every currency summed under the first currency's label. beanquery returns one inventory entry per currency.

**Reproducer** (no network):

```beancount
2024-01-01 open Assets:Hours
2024-01-01 open Assets:Broker
2024-01-01 open Assets:Cash
2024-01-01 open Equity:Opening
2024-01-02 * "hours"
  Assets:Hours  -13 VACHR
  Equity:Opening
2024-01-03 * "buy"
  Assets:Broker  17 GLD {268.22 USD}
  Assets:Cash
```

```text
SELECT cost(sum(position)) WHERE account ~ '^Assets:(Hours|Broker)'
  → [{"number":"4546.74","currency":"VACHR"}]      expected: -13 VACHR, 4559.74 USD
SELECT sum(cost(position)) WHERE account ~ '^Assets:(Hours|Broker)'
  → -13 VACHR, 4559.74 USD                         (correct)
```

**Also from `w23/016`** (same engine, same report): `neg(sum(position))` and `-sum(position)` are refused ("NEG expects a number or amount" / "negation requires numeric value"), and so is `filter_currency(position, 'USD')` ("FILTER_CURRENCY expects (inventory, string)"). beanquery accepts all of these forms. `SELECT meta('lineno')`, `lineno` and `entry_meta('lineno')` return null, while beanquery returns the posting's line. On the ledger above:

```text
SELECT account, neg(sum(position)) WHERE account ~ '^Income' GROUP BY account   → type error
SELECT account, sum(filter_currency(position, 'USD')) GROUP BY account          → type error
SELECT meta('lineno') LIMIT 1                                                    → [[null]]
```

**Also from `w23/020`:** `BALANCES … AT value` and `JOURNAL … AT value` ignore the clause and return units. On a holding of `4 VHT` priced at `120.00 USD`, beanquery returns `480.00 USD` and rustledger returns `4 VHT`; `value(sum(position))` is correct. `BALANCES FROM year = 2021` fails with "No matching lot for VHT in Assets:Broker" when the window sells a lot bought before it. `SELECT account, sum(position) FROM year = 2021 GROUP BY account` runs. Separately, `BALANCES FROM CLOSE ON 2016-01-01` omits beanquery's `Equity:Conversions:Current` row. The reproducer ledger is in `w23/020` (`.pm/w23/done/020.md`) and in `verify:rustledger`.

**Also confirmed 2026-10-26** (empty-table aggregation, it.1004): on the empty `prices` table (`SELECT *` → `[]` with identical `date/currency/amount` schema on both), `SELECT count(*)` returns `[[0]]` on MCP but `[]` (no rows) on stock beanquery. **Also confirmed 2026-10-26** (`FROM close`, it.1012): stock beanquery silently runs `SELECT count(*) FROM close` against postings (34 rows, posting columns) — the `close` keyword collides and the parser falls back to the default table — while MCP correctly refuses (`evaluation error: table 'close' does not exist`). Extended it.1089–1090 (set args): `length(accounts)` on the 4-account set returns `4` on MCP but crashes stock with a bare `__mro__` error; `upper(accounts)` refuses on both, but MCP names the expected type (`UPPER expects a string`) where stock again leaks `__mro__`. MCP is the better-behaved side on set-typed inputs. And a NULL-handling split: `maxwidth(payee, 10)` on a NULL payee passes `NULL` through on stock beanquery but hard-errors on MCP (`type error: MAXWIDTH: first argument must be a string`), while sibling `upper(payee)` on the same NULL coerces to `""` on MCP. So MCP is internally inconsistent on NULL string args (coerce vs error) and diverges from stock (pass-through) on `maxwidth`. Include both in the upstream report. Full NULL matrix (it.947, first row payee NULL): stock passes `NULL` through `upper/lower/length/maxwidth`; MCP coerces `upper/lower/length` to `""` (note `length` returns a *string* `""`, not int/null) and errors only on `maxwidth`. Extended it.1128: `SELECT NULL = NULL` evaluates to NULL on MCP (`""`) but errors on stock (`operator "equal(NULL, NULL)" not supported`) — the NULL-comparison direction favors MCP.

**Also confirmed 2026-10-26** (NULL rendering): `SELECT 1/0 LIMIT 1` yields `None` in beanquery but `[[""]]` with dtype `str` on MCP structured output; absent payees likewise render `""` instead of JSON `null`. **Also confirmed 2026-10-26** (`first()` null-skipping): row order is identical on both engines (null payees first), but `SELECT first(payee), last(payee)` yields `('NETFLIX', 'FARMERS MARKET')` in beanquery vs `[["", "FARMERS MARKET"]]` on MCP — beanquery's `first()` skips leading NULLs, rustledger takes the literal first row. **Also confirmed 2026-10-26** (`;` tail comments, it.1514, corrected it.1680 with parser-source truth): neither engine has `--` comments — `--` is double negation on both (`SELECT --6` → `6` on both; `SELECT 1 -- trailing` parses as subtraction and fails column resolution on both). The real divergence is stock's tatsu `eol_comments` rule (`\;[^\n]*?$` in `beanquery/parser/parser.py`): a `;` starts a rest-of-line comment, so `SELECT 2 LIMIT 1; garbage here` runs on stock but refuses on MCP (`BAD_USER_INPUT`, 3-surface parity). A second statement on its own line errors on stock too, so the split is only the same-line `;` tail. Retraction of the it.1514 mechanism story: the silent exit-0 on comment-only/leading-`--` input is a `bean-query` CLI artifact (`cmd.Cmd.parseline` yields an empty command for a leading `--`, so the shell no-ops without ever parsing) plus argv newline-joining — the stock *parser* raises `ParseError` there exactly like MCP. MCP is the strict side on the `;` tail; include as a keep-strict portability note.

**Also confirmed 2026-10-26** (dot-edge number literals, it.1540): `SELECT .5 LIMIT 1` and `SELECT 5. **Also confirmed 2026-10-26** (invalid bare dates, it.1546): `SELECT 2024-13-45` / `SELECT 2024-02-30` run on MCP as plain arithmetic (`1966` / `1992`) but crash stock beanquery with an uncaught `ValueError` (exit 1, traceback).
