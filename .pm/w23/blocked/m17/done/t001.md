## Objective

Run the current `createPullRequest` flow against the local Gitea in `deploy/docker-mac` (not a second stack) and find out whether `repoCreateBranch` through the per-user client fails there, and why. Compare the credentials the user-scoped client carries with the client the other (succeeding) ledger writes use. Record the cause, or that it does not reproduce locally, in the milestone README.

## Context

- `backend-cluster/backend-v2/src/features/gitea/pull-request/service/pull-request-service.ts` (step 3, `repoCreateBranch`, via `giteaClientFactory.getUserApiClient`)
- Every other production write succeeds; only branch creation fails, so a token-scope or per-user-client difference is a candidate, not a conclusion.

## Steps

1. Run the existing PR service tests, then a live `createPullRequest` against the local stack
2. Capture the Gitea response for `repoCreateBranch` and the token scopes the user client carries
3. Write the finding into the milestone README

## Acceptance criteria

- [x] The cause is recorded, or the note says it does not reproduce locally and which production-only difference remains

## Finding (2026-10-31)

On a standalone local Gitea 1.24.7 (one container, basic auth as the repo owner), `POST /branches` from `main` answers 201, and a single `POST /contents` with `branch` plus `new_branch` creates the branch and the commit in one request (201); a pull request from that branch then opens (201). So the production 500 does not reproduce on a stock Gitea: it is specific to the production server or to the per-user token the service uses (token scope, branch protection, server config). The single-commit design does not call `repoCreateBranch` at all, so it removes the failing call whichever of those it is; t008's production rerun is what confirms it. Not tested locally: the service's own per-user token.
