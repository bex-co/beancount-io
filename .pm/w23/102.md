# `commits?page=` past the int32 offset answers `INTERNAL_SERVER_ERROR` instead of an empty page

**Severity:** minor (pathological input, but a 5xx with a retry-hint that cannot help; agents paging blindly can trip it). **Estimate:** 30–60 minutes incl. parity. **Owner:** `backend-cluster/backend-v2`, commits resource + REST/GraphQL counterparts. **A1/A2:** agents paginate commit history; one page too far turns an empty page into a server error.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`…/commits?page=N&limit=10`, bisected exactly (it.573):

- `page=214748365` (offset 2,147,483,640) → `ok`, `[]`.
- `page=214748366` (offset 2,147,483,650 — one past int32 max) → `INTERNAL_SERVER_ERROR: Failed to fetch commits from Gitea` with "Retry once. If it persists the failure is server-side…".

The cliff is exactly the int32 offset overflow in the downstream Gitea commit list; backend-v2 wraps it in `unwrap`-style generic 500 (same shape as w23/092's BQL size cliff). Sibling paginations handle the same input cleanly: `collaborators?page=214748366` → `[]`, `social/followers?page=214748366` → `{"users":[],"total":0}` — only the commits path overflows.

## Fix (keep REST/GraphQL/MCP in parity)

Cap `page` (or `page*limit`) up front and refuse absurd values with `BAD_USER_INPUT`, or map the Gitea overflow to an empty page — either beats a 500. Same fix shape as w23/092: validate client-bounded inputs before the downstream hop.
