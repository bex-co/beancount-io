# BLOCKER: concurrent same-entry `updateEntrySource` calls corrupt the ledger — duplication, silent deletion, and lying status codes

**Severity:** blocker (silent data loss and duplication on a ledger; a reported `OK` that deleted an entry). **Estimate:** 2–4 hours (fence + mistranslation fix + race tests). **Owner:** `backend-cluster/backend-v2` entry-source update path (slice read-modify-write) plus the `FORBIDDEN` mistranslation of commit failures. **A1/A2:** agents that retry or parallelize edits — the normal agentic pattern — can corrupt any ledger they touch.

## Repro (production, 2026-10-25, API key pinned to `puncsky/mcp-agent-eval`)

Append one transaction, read its `entryHash` + `sha256sum`, then fire two `updateEntrySource` calls with the SAME hash+sha and different `newContent` in true overlap (single event loop, two child processes). Three rounds, three different outcomes:

| round | A | B | file afterwards |
| --- | --- | --- | --- |
| 1 | `OK` | `FORBIDDEN` | **both** narrations present — the entry DUPLICATED (1 → 2) |
| 2 | `FORBIDDEN` | `OK` | **neither** present — the entry is GONE (1 → 0) although B reported `OK` |
| 3 | `OK` | `FORBIDDEN` | only A present — the one correct outcome |

The `FORBIDDEN` body is itself wrong:

```json
{"code": "FORBIDDEN",
 "message": "Operation 'commit ledger files' not allowed: request failed with status 500",
 "hint": "This credential lacks the authority for that operation. …"}
```

The credential holds `ledger.admin`; nothing about authority failed — the loser collided with the winner's commit (a Gitea 500, the w23/072 lock signature) and a commit failure got mistranslated into "not allowed". A sequential retry with the stale hash correctly returns `NOT_FOUND` ("Entry hashes change when an entry is edited…"), so only the overlapped loser takes the `FORBIDDEN` path.

All probe entries were deleted after; the fixture verifies byte-identical (87 lines), `checkLedger` clean, 29 entries. No further race rounds were run once the corruption was confirmed.

## Cause (unverified, hypothesized)

The entry-source update is an unfenced read-modify-write: both racers resolve the slice against the pre-race file, then both commits land in some order — last-writer-wins explains neither the duplicate nor the deletion, so the losing commit likely mis-resolves its slice against the post-race file (appending instead of replacing in round 1, removing instead of replacing in round 2). Separately, a commit-step 500 inside this flow is wrapped as `ForbiddenError` where the append flow reports `SERVICE_UNAVAILABLE` for the same Gitea lock.

## Fix

1. Fence same-entry updates so the loser deterministically gets `CONFLICT` (stale `sha256sum`) or `NOT_FOUND` (hash already rotated) — never `FORBIDDEN`, never a second commit.
2. Translate commit-step failures as `SERVICE_UNAVAILABLE` (retryable), not `FORBIDDEN`, on every write path.
3. Race tests: overlapped same-entry updates always leave exactly one entry with the winner's content and report the loser honestly; run them repeatedly (this bug needed 3 rounds to show all 3 outcomes).

## Dedupe

No `.pm` item covers update races, duplication, or a race `FORBIDDEN` (searched: duplicate, lost update, corrupt, same-sha, concurrent update; open milestones). w23/072 (blocked) is append races that fail LOUDLY with `SERVICE_UNAVAILABLE` and lose nothing committed — the opposite failure mode: this bug corrupts silently while reporting `OK`/`FORBIDDEN`.
