# 189: GROUP-BY coverage guard false-fires on PIVOT BY (blocks a query stock runs)

**Severity:** minor (loud refusal, misleading advice, narrow trigger). **Estimate:** sub-hour
(one regex word + tests). **Owner:** ledger shell (`group-by-coverage-guard.ts`).
**A1:** agents pivoting with PIVOT-column order differing from GROUP-BY order.

The w23/131 coverage guard's key-list terminator (`KEY_LIST_END`) stops at
HAVING/ORDER/LIMIT/OFFSET/`)`/»; it does not stop at `PIVOT BY`. The trailing
GROUP-BY key therefore absorbs the pivot clause into one contaminated key, and a
selected column naming that key reads as uncovered:

```
SELECT account, date, sum(position) GROUP BY account, date PIVOT BY date, account LIMIT 1;
```

extracts keys [`account`, `date PIVOT BY date`, `account`]; `date` matches none,
so the guard refuses — `Bare column "date" is not grouped and not aggregated …
Add "date" to GROUP BY` — while `date` is sitting in GROUP BY. Following the
advice changes nothing (already grouped): the hint loops.

- Stock bean-query runs the query (pivot row `2026-01-01 / 3000.00 USD`).
- The same-column-order twin (`… PIVOT BY account, date`) runs on MCP (1 pivot
  row) — only the guard stands between this spelling and the engine, and the
  engine's own checks pass it (two PIVOT columns, both in SELECT, GROUP BY
  present). Single-key `… GROUP BY account PIVOT BY account` misfires the same
  way (there the PIVOT guard would refuse next with the accurate
  two-columns message, so that cell is message-only).
- REST twin refuses identically (same service path).
- Fix: add `pivot\s+by` to `KEY_LIST_END` in
  `backend-cluster/ledger/src/foundation/rustledger/group-by-coverage-guard.ts:41`
  plus a PIVOT regression test. The guard's header contract ("fires ONLY on
  proven bare-column violations … never refuses a working query") is what breaks.
- QA ledger untouched (read-only probes; byte-identical + stock-clean re-verified
  this loop: blob f1a0b83c, SHA-256 77c3a591, 2817 B).
