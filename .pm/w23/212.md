# BQL `FROM <column> <operator…>` is wrapped as a table and refused with a bogus `syntax error at position ~325` (regression from the FROM-fold rewrite)

**Severity:** major (valid, documented stock queries are refused with a misleading position). **Owner:** `backend-cluster/ledger`; REST, GraphQL and MCP all route through it, so parity is automatic. **Estimate:** 30–60m. **Pillar:** A1.

## Repro (production 2026-11-03, `beancount-mcp` 1.0.0, protocol 2025-11-25, API key; synthetic ledgers `puncsky/mcp-agent-eval`, `puncsky/example`, `open_ledger/example`, `open_ledger/crypto-example`)

REST `POST /api-gateway/v1/ledgers/{owner}/{name}/query` and MCP `runBqlQueryStructured` return the identical `BAD_USER_INPUT` on every ledger:

| Query | Result |
| --- | --- |
| `SELECT COUNT(*) FROM year > 2026` | `Invalid BQL query: syntax error at position 325: found '>' expected identifier, ' ', …` |
| `SELECT COUNT(*) FROM year = 2026` | same, position 325 |
| `SELECT account FROM month = 8 LIMIT 1` | same, position 325 |
| `SELECT COUNT(*) FROM date > 2026-12-31` | same, position 325 |
| `SELECT account FROM account ~ 'Cash' LIMIT 1` | same, position 327 |

Positions are about 300 past the end of a ~40-character query. Controls that work: `SELECT account FROM postings WHERE year = 2026 LIMIT 1`, `SELECT COUNT(*) FROM has_account('Cash')` (12), bare `FROM year;` (folds), `JOURNAL 'Assets:Cash'`.

## Expected

Stock beanquery 0.2.0 treats `FROM <expr>` as an entry filter (`FROM year = 2016 AND month = 4`). Before 2026-10-26 these queries ran on MCP/REST (`w6/blocked/023` recorded `FROM year > 2026` returning 174 on `open_ledger/crypto-example` on 2026-10-15). Those counts were wrong for a separate engine reason, tracked in `w6/blocked/023`; the refusal is new.

## Root cause

`backend-cluster/ledger/src/features/ledger/service/bql-from-fold.ts`: `matchFoldFrom` returns `kind: "wrap"` whenever a `FOLD_COLUMNS` name (`year`, `month`, `date`, `account`, …) is followed by anything except `)` or `;`. `foldBqlColumnFrom` then rewrites `FROM year = 2026` into `FROM (SELECT <INNER_COLUMNS> FROM year) = 2026`, which is not valid BQL. The long inner column list explains the ~+300 offset. The wrap was added for `FROM payee LIMIT 1` (w23/116, 125, 130), where a clause follows the name; an operator following the name makes it an expression, not a column table.

## Fix

In `matchFoldFrom`, leave the FROM untouched when the name is followed by an operator or expression continuation (`=`, `!=`, `<`, `<=`, `>`, `>=`, `~`, `AND`, `OR`, `IN`, `IS`, `NOT`, `BETWEEN`, `+`, `-`, `*`, `/`); keep wrapping for clause keywords (`WHERE`, `GROUP`, `ORDER`, `LIMIT`, `HAVING`, `PIVOT`). Add `bql-from-fold.test.ts` cases for each operator and a `verify:rustledger` live pin. Do not fix the engine's FROM evaluation here (`w6/blocked/023`).

## Dedupe

Searched `.pm/**` (including `done/`, `blocked/`) for `bql-from-fold`, `FROM year`, and `position 32x`. Only the fold-rewrite owners (`w23/116`, `124`, `125`, `130`, `199`) and the engine-semantics item (`w6/blocked/023`) touch it; none covers an operator after the name. Adjacent states: `FROM <fold column>;`, `FROM <fold column> LIMIT 1` and `FROM has_account(…)` still work.
