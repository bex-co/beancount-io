# Pinned credential can create ledgers it can never see, touch, or delete

**Severity:** minor (self-inflicted litter on one's own account; a leaked pinned key could also spam ledger creation past the pin's single-ledger intent). **Estimate:** 1–2 hours (refuse `createLedger` on pinned credentials, or scope the new ledger into the pin). **Owner:** `backend-cluster/backend-v2` ledger-create authorization (pin enforcement). **A1/A2:** agents holding a least-privilege pinned key can create ledgers outside their confinement and leave permanent litter they cannot clean up.

## Repro (production, 2026-10-25, API key pinned to `puncsky/mcp-agent-eval`)

1. `createLedger {"name":"qa-20261025-lifecycle","private":true}` → `ok:true`, `id: puncsky/qa-20261025-lifecycle`.
2. `listLedgers {}` on the same credential → returns ONLY `puncsky/mcp-agent-eval`; the new ledger is invisible.
3. `deleteLedger {"ledger":"puncsky/qa-20261025-lifecycle"}` → `FORBIDDEN` "The selected ledger is outside this credential's ledger restriction".
4. Any read/write naming the new ledger → same `FORBIDDEN` (pin).

The creating credential can never see, use, or remove what it created. Cleanup needed an owner session key (`DELETE /api-gateway/v1/ledgers/...` → 200, verified gone with a second DELETE → 404). No residue remains.

## Cause (unverified, hypothesized)

Pin enforcement applies to ledger SELECTION (read/update/delete name a ledger, so the pin bites) but `createLedger` names no ledger, so nothing checks the pin — creation escapes the confinement the pin is supposed to impose.

## Fix (pick one)

1. Refuse `createLedger` (and its REST/GraphQL counterparts) on pinned credentials with `FORBIDDEN` naming the pin — a single-ledger credential has no business creating ledgers; OR
2. Scope the newly created ledger into the creating credential's pin so it stays manageable.
3. Either way, keep REST/GraphQL/MCP in parity and document the rule in `docs/mcp.md` next to the pin paragraph.
