# Every write preview's `validation.newErrors[]` item carries `code`, but the published `outputSchema` forbids it (`additionalProperties: false`), so a schema-validating MCP client rejects the result

**Severity:** major for SDK clients (any preview or committed write that reports a new bean-check error fails client-side validation), minor otherwise. **Estimate:** 30–40 minutes with a test. **Owner:** `backend-cluster/backend-v2`. **A1:** the MCP TypeScript SDK client validates `structuredContent` against the tool's `outputSchema` and throws on a mismatch, so the one result an agent needs most when fixing a ledger error (`newErrors`) is the one it cannot read.

Same class as [w23/077](./done/077.md) (the error envelope's `additionalProperties: false` against the SDK client), on a different object.

## Repro (production, 2026-11-08, `beancount-mcp 1.0.0`, read/write API key, synthetic ledger `mcp-agent-eval`; `dry_run`, nothing written)

`appendLedgerText {ledger: "<owner>/<name>", dry_run: true, text: "2026-11-08 * \"qa\" \"x\"\n  Assets:Cash  -1.00 USD\n  Expenses:Nope  1.00 USD\n"}` returns `ok: true` with

```json
"validation": {"newErrors": [{"message": "Account Expenses:Nope was never opened", "source": "main.bean:93", "code": "E1001"}], "valid": false, …}
```

`tools/list` declares the same item for `addLedgerEntries`, `appendLedgerText`, `createLedgerFiles`, `updateLedgerFiles`, `deleteLedgerFiles` and `updateEntrySource` as

```json
{"type":"object","properties":{"message":{"type":"string"},"source":{"type":"string"}},"required":["message"],"additionalProperties":false}
```

Validating the real result against the published schema (a small JSON-Schema checker over `tools/list`): `$.result.validation.newErrors[0].code: unexpected key` for `appendLedgerText` and `addLedgerEntries` (an unbalanced entry) previews. `createLedgerFiles`, `updateLedgerFiles` and `deleteEntrySources` previews with no new errors validate fine, because the array is empty.

## Cause

`beanCheckErrorSchema` in `src/features/ai-agent/tools/types.ts` (about line 107) declares only `message` and `source`. The real `BeanCheckError` in `src/features/ledger/utils/bean-check-errors.ts` has an optional `code` (the engine's stable code, w2/013), and the result is not passed through the zod schema, so `code` reaches the client while the JSON Schema generated from it carries `additionalProperties: false`.

## Fix

Declare `code: z.string().optional()` on `beanCheckErrorSchema`, so the published item allows what the handler returns. Check the `tools/list` size budget (w23/077 notes the schema is inlined into many output schemas and the byte budget is tight; one optional string property per inlined copy). Test: extend `mcp-output-schema.test.ts` (or a parity test through an SDK client, as `directive-text-parity.test.ts` does) so a preview with a real new error validates against the published `outputSchema`; the existing schema-only test cannot see this because it never sees a populated `newErrors`.

## Blast radius and dedupe

Every tool whose `validation` is built from `validationSchema` (the six above, plus any `withWriteOutcome` user). REST and GraphQL are unaffected (REST returns the same JSON without a published strict item; GraphQL types it separately). Searched `.pm/**` (including `done/`) for `outputSchema`, `additionalProperties` and `newErrors`: w23/077 is the nearest, covering the error envelope only; nothing covers this item. Not documented as intended in `docs/mcp.md`, which lists `newErrors` without a per-item shape.

Unverified: I did not run a real SDK client against this result; the claim that it throws rests on w23/077's description of the SDK's validation and on the schema mismatch shown above.
