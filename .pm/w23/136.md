# 136 — Computed-value dtypes flip to `str` on empty input (derived columns AND expressions) (it.5722-5725)

## Summary
`id` and `other_accounts` (postings) / `accounts` (entries) report different dtypes depending on input cardinality: with rows they are `int`/`set`; over an empty result they flip to `str`. All stored columns (`date`, `year`, `number`, `tags`, `position`, `balance`, `cost_number`, …) keep their schema dtype on empty input — only the derived columns (id assigned during scan, account-sets computed per row) lose their type, falling back to `str` when there are no rows to infer from. A consumer branching on `dtype` (e.g. parse `id` as a number, iterate `accounts` as a set) breaks exactly when the result is empty. Same fallback-`str` symptom as w23/134 (alias-name fallback) and w23/135 (unresolved-name fallback), but this hits real columns of real tables.

## Repro (prod, puncsky/mcp-agent-eval)
- `SELECT id, other_accounts, number FROM postings WHERE FALSE LIMIT 1;` → dtypes `str`/`str`/`Decimal`, `rows: []`.
- Same without the filter → dtypes `int`/`set`/`Decimal`, row `[12, 'Assets:Bank:Savings  …', '3000.00']`.
- `SELECT id, accounts FROM entries WHERE FALSE LIMIT 1;` → `str`/`str`, `rows: []`; unfiltered → `int`/`set`, row `[0, '']`.
- Controls holding dtype on empty: `date`→`date`, `year`→`int`, `tags`→`set`, `position`→`Position`, `balance`→`Inventory`, `cost_number`→`Decimal` (it.5723). Star agrees: `SELECT * WHERE FALSE` flips the same two columns (it.5722).

## Expected
Derived columns carry their schema dtype (`int`/`set`) regardless of row count, like every stored column does.

## Status
Open (inbox). MCP-side (engine dtype inference for derived columns).
- Extended it.5725: the flip is not column-specific — ALL computed values lose their dtype on empty input. `SELECT upper(payee), number + 1, year(date) WHERE FALSE` → `str`/`str`/`str`; unfiltered → `str`/`Decimal`/`int`. Rule refined: stored columns keep schema dtypes; every derived column AND every expression falls back to `str` with zero rows. (`upper` only looks stable because its real dtype is `str`.)
- Extended it.5726: aggregates follow the same rule — `count(*), sum(number), min(date), max(payee)` over `WHERE FALSE` → `int`/`str`/`str`/`str` (row `[0, '', '', '']`); unfiltered → `int`/`Decimal`/`date`/`str`. Only `count(*)` (real `0` value) and coincidentally-`str` results keep their dtype.
- Extended it.5727: even literals flip — `SELECT 1, 'a', 1.5, TRUE, NULL WHERE FALSE` → all `str`; unfiltered → `int`/`str`/`Decimal`/`bool`/`str`. Final rule: on empty input EVERYTHING except stored-column references falls back to `str`, including constants whose type is knowable at parse time. The dtype system is purely value-inferred outside stored columns.
- Parity it.5728: REST masks identically (all-`str` on the empty literal query) — engine-wide, all surfaces consistent.
- Extended it.5730: all-NULL input behaves like empty for expressions — `SELECT cost_number + 1, upper(cost_currency)` (34 rows, all NULL) → `str`/`str`. Stored all-NULL columns hold schema dtype (`cost_number`→`Decimal`, it.5729); only computed values need a non-null sample. Same value-inference mechanism, no separate defect.
