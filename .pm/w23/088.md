# `appendLedgerText` ignores its documented `pushtag`/`pushmeta` handling; the native checker cannot parse them at all

**Severity:** minor (valid beancount refused with parse errors; workaround: write tags/metadata onto each transaction directly). **Estimate:** 2–4 hours (implement the documented apply-before-write in the append path + teach the native grammar push/pop, or scope the doc down). **Owner:** `backend-cluster/backend-v2` append path + the native beancount checker/grammar it shares with `bea`. **A1:** agents following the documented push/pop pattern get `VALIDATION_FAILED` on real-beancount-valid text.

## Repro (production, 2026-10-25, API key pinned to `puncsky/mcp-agent-eval`)

`docs/mcp.md` ("Writing directives as Beancount text") promises: "`pushtag`/`poptag` and `pushmeta`/`popmeta` around entries are applied to them — the tag written onto each enclosed transaction, the metadata under each enclosed directive — and the statements themselves are not written … a push that is never popped, or a pop with no push, is refused naming the line."

Reality, dry-run and commit alike, balanced push/pop, pushmeta/popmeta, never-popped push, and pop-without-push:

| input | dry-run | commit |
| --- | --- | --- |
| balanced `pushtag`/`poptag` block | "Would add 3 directives … 2 new bean-check errors: parse error: unexpected input" | `VALIDATION_FAILED` naming both parse errors |
| balanced `pushmeta`/`popmeta` block | same shape, 2 parse errors | `VALIDATION_FAILED` |
| push never popped | "Would add 2 directives … 1 parse error" | `VALIDATION_FAILED` |
| pop with no push | "Would add 1 directive … 1 parse error" | (not committed; dry shows no line-naming refusal) |

Nothing is applied, nothing names the offending line as `BAD_USER_INPUT` — the raw push/pop lines hit the checker and die as parse errors. The syntax itself is real beancount ([language docs](https://bradyt.github.io/beancount-docs/06_beancount_language_syntax/) show `pushtag`/`poptag`; `beancount.parser.grammar.Builder` has `pushtag`/`pushmeta`), but the native stack cannot parse it either: `bea check` (bea 0.3.1, native engine, no PyPI beancount installed) reports "syntax error, unexpected PUSHTAG/POPTAG" on the same text. No fixture residue: every commit-path probe was refused, dry-runs commit nothing, and the companion budget probe was deleted after (fixture byte-identical, `checkLedger` clean).

## Fix (pick a scope and do all of it)

1. Either implement the documented behavior: apply push/pop to enclosed entries in `appendLedgerText` (and refuse unbalanced push/pop as `BAD_USER_INPUT` naming the line), with the native grammar learning to parse push/pop so file-written ones also check; or
2. Scope the doc down to reality: push/pop/popmeta are not supported — refused as `BAD_USER_INPUT` naming the line (not a bean-check parse error), with the tag-per-transaction workaround.
3. Keep REST/GraphQL/MCP in parity either way; `bea check` and server `checkLedger` must agree on push/pop.
