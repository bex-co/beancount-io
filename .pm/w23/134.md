# 134 — Structured `dtype` lies for all-NULL aliased columns: falls back to the alias name's table type (it.5371-5377)

## Summary
`runBqlQueryStructured` infers column `dtype` from result values when any are non-NULL, but for an all-NULL column it falls back to the table type of the alias *name* — so `SELECT payee AS number … LIMIT 1` (NULL row) reports `dtype: Decimal` for string data, and `SELECT payee AS date …` reports `dtype: date`. The values themselves are correct; only the type metadata lies. An agent trusting `dtype` to parse or validate the column gets the wrong type exactly when the alias shadows a different-typed column.

## Repro (prod, puncsky/mcp-agent-eval)
- `SELECT payee AS date FROM postings LIMIT 1;` (NULL payee row) → rows `[['']]`, dtype `date` — should be `str` (it.5371, re-verified it.5373).
- `SELECT payee AS number FROM postings LIMIT 1;` → dtype `Decimal` for string data (it.5375).
- `SELECT payee AS xyz FROM postings LIMIT 1;` (unknown name) → dtype `str` fallback (it.5375).
- Controls: `SELECT payee AS date … WHERE payee IS NOT NULL` → dtype `str` (expression wins when values present, it.5372); `SELECT date AS payee …` → dtype `date` (it.5374); non-aliased `SELECT payee … LIMIT 1` → `str` via schema (it.5376).
- Stock beanquery has no `dtype` metadata, so there is no differential — this is MCP-side only.
- Extended it.5380: the fallback also bites expressions — `SELECT upper(payee) AS number … LIMIT 1` (NULL row) reports `Decimal` for a string expression. Non-aliased expression dtypes are correct (`year(date) AS y` → `int`, it.5379). Typed empties are immune: `tags AS t` (empty set, unknown alias) correctly reports `set` (it.5386) — only untyped-NULL columns take the name fallback. Zero-row results take it too: `… WHERE 1 = 0` reports `Decimal` for the same alias (it.5388). REST `POST …/query` returns the identical lying envelope (it.5565) — the fallback sits below both surfaces.

## Expected
`dtype` should follow the expression type (or the pre-alias column type) even when all values are NULL — never the alias name's lookalike table type. At minimum, fall back to a neutral/unknown marker rather than a confidently wrong concrete type.
