# With-clause `FROM` resolves table-first where stock resolves column-first (bare/LIMIT scope split)

**Severity:** major (same `FROM` name yields different scopes — and different row counts — depending on trailing clauses; silent). **Estimate:** 3–5h (one FROM resolver with stock's column-first/table-fallback order on every path + regression test). **Owner:** query path below backend-v2 (same area as w23/109, w23/115 — likely the ledger/engine service). **A1/A2:** agents adding LIMIT to a working bare query silently change its scope.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`accounts` is both a postings column and a registered table (`AccountsTable`, 12 rows). Stock resolves unquoted FROM names column-first with table fallback (`compiler.py` `_compile_from`, From branch); MCP resolves differently per clause form:

| query | stock | MCP |
| --- | --- | --- |
| `SELECT count(*) FROM accounts;` (bare) | `34` (column-fold over postings) | `34` (fold — agrees) |
| `SELECT count(*) FROM accounts LIMIT 1;` | `34` (fold — one rule, all forms) | `12` (AccountsTable — scope changed by adding LIMIT) |
| `SELECT count(*) FROM accounts WHERE date > 2020-01-01;` | `34`-family (fold; date valid in postings scope) | `BAD_USER_INPUT: column 'date' not found in subquery result` (table scope has no `date`) |
| `SELECT count(*) FROM "accounts" LIMIT 1;` (quoted) | `12` (pure table reference) | `34` (name ignored — w23/115) |

So MCP has three unquoted-FROM rules where stock has one: bare = column-only with no table fallback (w23/109: bare `FROM postings` errors), with-clause = table-only with no column-first (this note: `FROM accounts` flips scope), quoted = ignored (w23/115). Stock: column-first, table fallback, else error — identical results in every clause form.

Corollary mechanism fix for w23/blocked/022's `FROM close` note: stock has NO `close`/`open` tables (`Open`/`Close` in `sources/beancount.py:125-131` are `types.Structure` column types, not in `_TABLES`). Unquoted `FROM close` hits the parser's CLOSE-date keyword with no date → plain postings scope (34 rows, postings-shaped); `FROM clear` → 48 (CLEAR scope); `FROM open` → ParseError (OPEN needs a date). MCP's with-clause `table 'close' does not exist` is therefore "no CLOSE-keyword form", not "missing table" — the divergence stands, the mechanism is keywords, and it is recorded as a correction on w23/blocked/022.

Fixture is byte-identical to the pinned snapshot (2817 B, sha `77c3a591efd3`), so this is not data drift. Deterministic (it.2320–2322).

## Fix

Give every FROM path (bare, with-clause, quoted) one resolver matching stock order: postings-column fold first, registered-table lookup second, keywords (`OPEN`/`CLOSE`/`CLEAR`) per the grammar, error otherwise. At minimum, bare and with-clause forms of the same `FROM` name must scope identically. Add a regression test running each dual-meaning name (`accounts`, `balance`, `close`, `clear`) bare, +LIMIT, +WHERE on MCP and stock, asserting identical scopes.
