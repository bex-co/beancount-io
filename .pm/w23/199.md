# 199 — Trailing `;;` refused only on bare-FROM tails, with a bogus column error

## Summary
A stray trailing `;;` is now tolerated on most MCP paths (matching stock) but
still refuses when a bare `FROM <name>` is the last clause — with a misleading
`column '<table>' not found` message for a table that exists:
- `SELECT payee FROM postings;;` → `column 'postings' not found` (also with a
  space before `;;`, with `; ;`, and quoted `FROM "postings";;`; `FROM
  entries;;` identical). REST twin refuses identically (shared pipeline).
- `SELECT payee FROM entries LIMIT 1;;`, `SELECT COUNT(*) FROM postings LIMIT
  5;;`, `SELECT 1;;` → all RUN (1 row / 34 / 34 rows).
- Stock runs every shape above (silent second-statement tolerance).

So the same stray semicolon both runs and refuses depending on tail position,
and the refusal misdiagnoses a table as a missing column — the w23/116
normalize pipeline's terminator now strips trailing `;;` on most paths but the
bare-FROM fold path (`foldBqlColumnFrom` interplay) chokes on the residue and
reports the fold name as a column lookup failure.

## Repro
- `call runBqlQuery {"ledger":"puncsky/mcp-agent-eval","query":"SELECT payee FROM postings;;"}` → `BAD_USER_INPUT: … column 'postings' not found`.
- `… "SELECT 1;;"` → 34 rows; `… "SELECT COUNT(*) FROM postings LIMIT 5;;"` → 34.
- Stock CSV twins: `SELECT payee FROM postings;;` → rows; `SELECT 1;;` → rows.

## Expected
One rule for trailing `;;` everywhere: either strip-and-run on all paths
(stock parity — the with-clause/no-FROM paths already do) or refuse on all
paths with an accurate stray-semicolon message (never `column 'X' not found`
for an existing table). Note w23/022 it.2540's record (`SELECT 1;;` refuses)
is stale for the now-lenient positions — the upstream report should carry the
position matrix, not blanket strictness.
