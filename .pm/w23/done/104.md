# Map a stray 431 from the ledger hop to BAD_USER_INPUT

Follow-up from `w23/m5/t001`: the ledger 431 cliff (Node 16 KiB `maxHeaderSize`) falls into `error-to-domain.ts`'s `default` branch and surfaces as `INTERNAL_SERVER_ERROR: Failed to ...` with a retry hint. m5 moves the shell hop to POST, but any other long-URL ledger route (a long journal `filter`, a deep file path) can still 431 the same way.

Consider `case 431: return new BadUserInputError(...)` naming the oversize URL, as defense-in-depth behind every GET hop. Sub-hour: one case + one mapping test.

**QA confirmation 2026-10-26** (it.766, same session): three more routes 431 exactly as predicted — `payee-transactions/{payee}`, `narration-transactions?narration=`, and `account-report/{account}` with 20 KB values all answer `INTERNAL_SERVER_ERROR: Failed to get ledger …` with the retry hint. Payee cliff bisected: 16,000 chars → `null` (clean miss), 16,500 → 500. Ruled out as vectors: a maxed-out journal URL (256-char filter + every param) is only 489 chars, and file paths cap far below the cliff — so the fix's test should target the three unbounded segments above, not filter/path. Also ruled out (it.767): 20 KB `banks/{itemId}` and `commit-details?sha=` answer clean `NOT_FOUND` — the Gitea-backed paths are immune; only ledger-GET routes 431.

Fourth vector (it.768): 20 KB `entry-context/{hash}` (resource) and `getEntryContext` (tool) both 500 (`INTERNAL_SERVER_ERROR: Failed to get entry context`). A cheap up-front guard exists here too — entry hashes are fixed 32-hex (`:N` twin suffix) — but the 431 mapping covers it regardless.

Fifth/sixth vectors (it.772): 20 KB `journal?account=` and `journal?time=` both 500 (`INTERNAL_SERVER_ERROR: Failed to get ledger journal entries`) — the general rule is that *every* unbounded string forwarded to a ledger GET 431s past ~16 KB. Enumerating each param is whack-a-mole; the 431→`BAD_USER_INPUT` mapping (or per-param length caps) is the systemic fix.

Canonical BQL cliff probe (it.883, recorded wrapper for post-deploy rechecks): `SELECT 1 WHERE payee ~ "A×N"` via `runBqlQueryStructured` — N=15990 ok, N=15992 `INTERNAL_SERVER_ERROR`, razor-sharp, consistent with the 16 KiB header budget. Sibling deploy signals checked the same iteration (tool count 44, no holdings/register/capital-gains tools, 084 `./` still refused, m3 `entry_hash` alias absent, m2 `tag:#` still bare lexer error): no deploy has landed; prod still predates m2/m3/m4/m5.

Unicode twin (it.885): `SELECT 1 WHERE narration ~ "é×N"` — N=2660 ok, N=2665 `INTERNAL_SERVER_ERROR`. Encoded totals converge with the ASCII cliff (fail at query+wrapper ≈16017–16019 encoded chars in both alphabets), confirming the budget is URL-encoded bytes, not raw chars — the recorded rationale for preferring the POST hop over a raw-char cap.

---

**Resolved 2026-10-26** — fixed in `backend-cluster/backend-v2`: `favaApiErrorToDomainError` maps ledger 431 to `BadUserInputError` ("the request URL exceeded the ledger's length limit; shorten the value or split it into smaller requests") instead of falling into the `default` 500 branch. The mapping sits behind every ledger hop on every surface, so all six QA-confirmed vectors (payee/narration/account-report/entry-context/journal params) are covered without enumerating params. Mapping test fails with the case removed. No schema change, no OpenAPI regen needed.
