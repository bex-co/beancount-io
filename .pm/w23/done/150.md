# 150 — Journal subtype filters pass non-family directives through, and `total` counts them (`pending` → 13 rows, 0 transactions)

## Summary
`transactionSubtypes`/`documentSubtypes`/`customSubtypes` on `journal` (and `account-journal`) filter only their own directive family and pass every other family through unfiltered — and `total` counts the passthrough rows. `transactionSubtypes=["pending"]` (fixture has zero pending/flagged transactions) returns `total: 13`: 1 Balance + 12 Opens, 0 transactions. `documentSubtypes=["discovered"]` (zero documents exist) returns all 29 rows. An agent asking for "pending transactions" receives 13 rows that look like results. Sibling filters (`account`, `time`, `directiveTypes`) narrow the whole set; subtypes are the odd ones, and the template description ("Subtype filters are JSON-encoded string arrays") documents only the array format, never the family-scoping.

## Repro (prod, puncsky/mcp-agent-eval, read-only)
- `journal?transactionSubtypes=["cleared"]` → total 29 (16 cleared txns + 13 passthrough); `["pending"]` → total 13 (0 txns + same 13); `["other"]` → total 13.
- `journal?documentSubtypes=["discovered"]` → total 29 (0 documents + everything else).
- `account-journal?account=Assets:Cash&transactionSubtypes=["pending"]` → 2 rows (Balance + Open), 0 transactions; unfiltered Cash → 7.
- Control: `pending` + `directiveTypes=["Transaction"]` → total 0 — the filter works within its family, so a correct query exists but the bare filter misleads.
- REST twin: `GET …/journal?transactionSubtypes=["pending"]` → identical total 13, Balance first. Shared semantic; GraphQL journal query carries the same three args.

## Root cause (main)
Deliberate passthrough, undocumented at the surface: `filterTransactionSubtypes`/`filterDocumentSubtypes`/`filterCustomSubtypes` (`backend-cluster/ledger/src/foundation/rustledger/journal-serialize.ts`) each return `true` for non-family items ("Non-transactions pass through", engine parity). The MCP template description never states family-scoping, and `total` counts matches + passthrough together.

## Expected
One of: (a) narrow the whole result to matches (`pending` → 0 rows, breaking the cited engine parity deliberately); (b) keep passthrough but split the counts so `total` reflects matches; or at minimum (c) document family-scoping in the template description so agents know to combine with `directiveTypes` or filter client-side. (c) is a one-line doc fix; (a)/(b) is the design question. Sub-hour for (c).
