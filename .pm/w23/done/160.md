# 160 — Decimal literals past Decimal precision silently round to fit

## Summary
w23/133's `integerOverflowError` refuses decimal literals whose magnitude exceeds Decimal::MAX — but the engine also silently misreports decimals *below* the max once they carry more significant digits than rust_decimal's 96-bit mantissa holds (~28-29). `SELECT 79228162514264337593543950334.9` (30 significant digits, below MAX by 0.1) renders `79228162514264337593543950335` with no error; stock renders the exact `Decimal('79228162514264337593543950334.9')`.

## Repro (live engine + stock beanquery 0.2.0, October 2026 triage)
- `SELECT 79228162514264337593543950334.9` → engine `[["79228162514264337593543950335"]]` (rounded up to MAX, no error); stock `Decimal('79228162514264337593543950334.9')` exact.
- Controls that agree: `SELECT 1.5` / `0.5` / `3000.00` / `9007199254740992.5` / `9223372036854775808.5` render exactly on both; `SELECT 79228162514264337593543950335.0` (mantissa exactly MAX) renders exactly on both.
- Suspect, needs probing to scope: the true boundary is the *mantissa* (digits with the point removed) against MAX, not the value — e.g. `7922816251426433759354395033.50` fits by value but its 30-digit mantissa exceeds MAX, and rust_decimal's `from_str` trailing-zero handling there is unprobed. Significant-digit counting (leading zeros, trailing-zero scale) needs the same probe cycle.

## Expected
Refuse decimal literals the engine cannot represent exactly (mantissa analysis with the trailing-zero/scale edges probed first), or document the precision boundary loudly. Never silently round a literal stock renders exactly.

**Resolved 2026-10-28** — fixed in `daec2e138`: decimal literals past engine precision refused.
- Scoping probes, worker1 it.111 (prod; stock = beanquery on the byte-identical fixture; all MCP cells ×34 implicit rows): repro live (`...50334.9` → `...50335`). Trailing zeros absorb cleanly: `...5033.50` → `...5033.5` exact (same as `...5033.5`), so the 30-digit-mantissa suspect does NOT trip — `from_str` normalizes scale before the boundary bites. Leading zeros neutral: `000...50334.9` rounds to MAX identically. Rounding is half-up on positives: `...50334.1` → `...50334`, `...50334.5` → `...50335`; negative mirrors (`-...50334.9` → `-...50335`; stock renders `-7.92…E+28`, display-only). Value-over-MAX already refuses — `...50335.9`, integer `...50336`, and `99999999999999999999999999999.9` all `BAD_USER_INPUT` — but the message is the 162-class bogus fallback (`syntax error at position 0: unexpected token 'SELECT'`), never naming the literal/overflow; the refusal branch of Expected exists, its message needs the 162 fix. Net boundary: value > MAX → refuse (message wrong); mantissa > MAX ≥ value → silent half-up round (this note); else exact.
