# `allowInvalid` commits syntactically unparseable text on the typed/entry path (all three surfaces)

**Severity:** major (one flag turns a loud refusal into a committed file no parser can load; reads/checks degrade until repaired). **Estimate:** 1–3h (schema-validate cost.date + never bypass parse errors, or document-and-guard the break-glass). **Owner:** ledger service (`ledger-journal-service.ts` gate) + typed-entry schemas. **A1/A2:** agents pass `allowInvalid: true` per the hint ("to record them anyway") for balance breaks and silently cross into syntax breaks.

The typed path validates thoroughly everywhere else (txn date/account/number/flag, posting flag/amounts, double auto-postings — each refused with a precise schema error, worker1 it.221-228), but `cost.date` is interpolated raw: `cost: {number, currency, date: "yesterday"}` renders `10.00 USD {1.00 USD, yesterday}`, which no parser accepts. The default path catches it in projection (`VALIDATION_FAILED … parse error: unexpected input`, vague but safe). With `allowInvalid: true`, the single shared gate `assertNoNewErrors` early-returns (`ledger-journal-service.ts:606`, `if (allowInvalid) return`) — parse errors bypassed exactly like check errors — and the unparseable text COMMITS.

Live (prod, QA ledger `puncsky/mcp-agent-eval`; committed once, restored byte-identical, see below):

- MCP `addLedgerEntries {…, cost.date: "yesterday", allowInvalid: true}` (real call) → `ok: true`, "Added 1 entry to main.bean. 1 new bean-check error: parse error: unexpected input (main.bean:91)", `entryHashes: ["49cb6460…"]`. Fetched bytes end `… 10.00 USD {1.00 USD, yesterday}`; stock `bean-check` exit 1: `Invalid token: 'yesterday}'`.
- `checkLedger` on the broken file still reports faithfully (`errors: [{P0012 parse error…}]`) — readers degrade to the error, they don't crash.
- REST twin (no commit): `POST …/entries {…, dryRun: true, allowInvalid: true}` → `{"success":true,"message":"Would add 1 entry successfully","preview":[…yesterday…]}`.
- GraphQL twin (no commit): `bulkEntries(…, dryRun: true, allowInvalid: true)` → `{"message":"Would add 1 entry successfully","success":true,"preview":[…yesterday…]}`.
- Default-path control on all three: same payload without the flag → `VALIDATION_FAILED` ("parse error: unexpected input"), nothing written.

The bypass exceeds the flag's documented contract: GraphQL's own `allowInvalid` description promises "Record entries deliberately even when they are unbalanced (UNBALANCED) or would add bean-check errors such as a second open" (`ledger-entry-resolver.mutation.ts`) — unbalanced and check errors, not unparseable files. A balance break keeps every reader working; a syntax break means the file cannot load at all.

Fix direction: (a) schema-validate `cost.date` (and audit sibling nested fields: cost.label? price/totalPrice shapes are amount-only) with the same "not a calendar date" error txn dates get, so the garbage never renders; (b) decide what `allowInvalid` may bypass — check errors yes, parse errors never (a file that cannot load is not "invalid", it is broken); at minimum surface `isParseError` in the refusal so the hint can warn that `allowInvalid` will break the file.

Restore: `updateLedgerFiles` full-file `content` replace with the known-good bytes (file path needs no parse), then verified `cmp` byte-identical to the pre-probe fixture + stock `bean-check` clean + `checkLedger` clean.

Sibling-field audit (worker1 it.230): `cost.label` renders quoted (`{1.00 USD, "not a label!!!"}` — stock-clean, any content safe), balance `tolerance` is schema-validated (`tolerance "garbage!!!" is not a decimal number`), and price/totalPrice are amount-only decimals. `cost.date` is the lone raw-interpolated nested field — the (a) fix is one field, not a family.

Dedupe: distinct from w23/149 (file tools commit invalid with NO flag — no gate at all) and w23/171 (typed tags render invalid that the check cannot see — no flag, blind check). Here the check SEES the error and the flag overrides it: the defect is the override's scope (parse errors included), plus the missing cost.date schema validation that lets the typed path render garbage every other field is checked against. Searched: allowInvalid parse, cost.date, "unexpected input"; open: 140–173.

---

**Resolved 2026-10-28** — `cost.date` now gets the same calendar-date refusal as every other typed date (`entry N: postings[M].cost.date "yesterday" is not a calendar date; use YYYY-MM-DD`) in the shared entry service, so MCP, REST, and GraphQL refuse it before anything renders, with or without `allowInvalid`; three regression tests (two fail with the fix reverted), shipped in `96d05c896` (`backend-v2`). Fix direction (a) only: the lone raw-interpolated field was the sole way typed input reached a parse error, so (b) (narrowing what `allowInvalid` may bypass in the ledger service) was not changed; the file-tool path stays under blocked w23/149.
