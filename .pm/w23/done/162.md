# 162 — BQL rejects Unicode whitespace stock accepts (NBSP/VTAB/EMSP), with a bogus position-0 error

## Summary
MCP's tokenizer accepts only ASCII space/`\t`/`\r`/`\n`: a query with U+00A0 (NBSP), U+000B (VTAB), or U+2003 (EM SP) anywhere refuses with `syntax error at position 0: unexpected token 'SELECT'` — even though the query starts with SELECT and the offending char sits mid-string. Stock beanquery 3.2.3 runs all three (34 rows). Copy-paste from rendered docs routinely introduces NBSPs, so an agent reusing a documented example hits a refusal that also mislocates the fault at position 0. The bogus position-0 shape matches w23/133's MAX+1 instance (fixed on main for integer literals only — this unknown-token fallback persists).

## Repro (prod, puncsky/mcp-agent-eval; stock = 3.2.3 on the byte-identical fixture)
- `SELECT<NBSP>count(*) AS n FROM postings;` → MCP `BAD_USER_INPUT: syntax error at position 0: unexpected token 'SELECT'`; stock `34`.
- Same split for U+000B and U+2003 in the same slot.
- Controls, all agree: space, `\t`, `\r\n` → 34 on both.

## Root cause (main)
Engine tokenizer whitespace class (rustledger WASM): ASCII-only, with an unknown-token fallback that reports position 0 regardless of the true offset. w23/133's `integer-overflow-guard.ts` reroutes only the integer-literal instances of the position-0 misreport; no service-level rewrite touches whitespace.

## Expected
Accept the same whitespace class as stock (at minimum NBSP/VTAB/EMSP — one tokenizer-class line), or refuse with the TRUE offset and the offending character named so the error is actionable. Keep the strictness loud (per w23/151) but make it truthful; verify post-deploy that 133's guard didn't already relocate this fallback.
