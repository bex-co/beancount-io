# `plaintext-journal` has no limit or paging: one read returns the whole ledger's text (276 KB on `open_ledger/example`), unbounded for premium ledgers

**Severity:** minor. This is the w23/010 context-blowup class on a resource. **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/backend-v2`, in the `plaintextJournal` resource in `mcp-resources.ts`, plus the matching REST suffix and GraphQL query. **A1:** an agent reaching for "show me the journal as text" gets the entire ledger, roughly 70k tokens on a mid-sized public ledger. It has no way to ask for less except `account`/`filter`/`time`.

## Repro (production, 2026-10-21, OAuth `ledger.read` account-wide token, public ledgers)

| Ledger | `beancount://<ledger>/plaintext-journal` |
| --- | --- |
| `open_ledger/example` | 275,702 characters in one `{ "content": … }` |
| `open_ledger/alphabet` | 117,577 |
| `open_ledger/nvidia` | 56,149 (REST `GET …/plaintext-journal` returns the same 56,149) |

By contrast, `journal` (structured) defaults to a page of entries (7.6 KB on `open_ledger/example`), and `account-journal` defaults to 20 entries with `limit`/`offset`. `docs/mcp.md` documents `plaintext-journal` only as `{ "content": "..." }`. The template accepts `account`, `filter` and `time`, with no `limit`/`offset` and no size ceiling. Free ledgers are bounded by the 1,000-directive cap; premium ledgers are not.

## Fix

Give `plaintext-journal` the structured journal's paging: `limit` (default, say, 200 entries; maximum 1,000) and `offset`, on MCP, REST and GraphQL alike. Return `total` and `truncated` beside `content`. Alternatively, apply 010's ceiling: cut at an entry boundary at 100 KB with an in-band `[truncated: …]` line naming the paging parameters. Document the defaults. Tests: a ledger above the ceiling returns a bounded page with a correct `total`, and `offset` walks the rest without gaps or overlaps.

**Resolved 2026-10-22** — The plaintext export now pages, on every surface.

**Ledger:** `plaintextJournal` (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts`) takes optional `limit` and `offset` over the exported entries and returns `{content, total, truncated}`. `total` counts the entries the filters select. Every page keeps the option header, so each one loads on its own. The route parses both parameters, and `backend-cluster/idl/beancount-ledger.openapi.json` declares them and the two new fields, regenerated into backend-v2's `src/foundation/fava/Api.ts`.

**backend-v2:** REST `GET …/plaintext-journal`, GraphQL `getLedgerPlaintextJournal` (`query.limit`/`offset`, response `total`/`truncated`) and the MCP `plaintext-journal` resource all accept `limit` (1–1,000) and `offset` and return `total` and `truncated`. The service validates them for GraphQL, whose Int arguments arrive unchecked. **Default:** without `limit`, the MCP resource returns the first 200 entries. REST and GraphQL keep returning every entry, because the dashboard's export button downloads the whole ledger through GraphQL. This is recorded as a deliberate protocol difference in `docs/api-parity.md` beside w23/010's BQL bound, and documented in `docs/mcp.md`.

**Tests:** a new ledger `plaintext-journal-paging.test.ts`: every entry without paging; three pages walk five entries without gaps or overlaps, with the right `total` and `truncated` and the option header on each page; `limit 0` and `offset -1` refused. backend-v2 `journal-parity.test.ts` covers the MCP default (`limit: 200` on the MCP call only), an explicit `limit`/`offset` page that is identical on REST, MCP and GraphQL, and `limit 1001` refused on all three before the ledger is called. Reverting fails 3 backend-v2 tests and the ledger suite.

**Gates:** ledger typecheck, lint and 1614 tests; backend-v2 typecheck, lint/Knip and 6657 tests, with OpenAPI regenerated (the two query parameters). The one failure was the environment-only `upstream-survival.test.ts` (see w23/027).
