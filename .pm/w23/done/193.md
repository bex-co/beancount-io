# 193 — Mixed-comparison guard false-fires on parenthesized comparisons (`(1 < 2) = TRUE`)

**Severity:** minor (loud; wrong reason; blocks an MCP-valid spelling).
**Estimate:** sub-hour (don't strip parens containing a comparison). **Owner:**
ledger shell (`mixed-comparison-guard.ts`). **A1:** agents comparing a
parenthesized predicate to a boolean.

The w23/132 guard strips "redundant" parens before scanning for `=`/`!=`, but
`(1 < 2)` is not redundant — stripping yields `1 < 2 = TRUE`, and the `=` scan
then matches the phantom `2 = TRUE`:

- `SELECT (1 < 2) = TRUE` → `Mixed-type comparison (number compared to bool
  with =) …` — yet both real operands are bool, and the engine answers
  bool `=` bool fine (`SELECT TRUE = TRUE` → `TRUE`, the 022:it.3211 superset).
- Same-shape `(TRUE) = TRUE` runs (parens around a literal strip harmlessly),
  so two identical-shape queries split on paren *content*.
- REST twin refuses identically (shared guard path).
- Stock refuses the unparenthesized chain at parse and bool `=` bool at
  compile, so no stock oracle demands this spelling work — the defect is
  internal: the guard's header contract ("anything unproven abstains, so the
  guard never refuses a working query") breaks, and the message misdiagnoses
  bool-vs-bool as number-vs-bool.
- Fix: in `mixed-comparison-guard.ts` (lines 198–207), only strip paren groups
  whose inner text holds no comparison operator; anything else abstains.
- QA ledger untouched (read-only probes; byte-identical + stock-clean re-verified
  this loop: blob f1a0b83c, SHA-256 77c3a591, 2817 B).

---

**Resolved 2026-10-28** — the mixed-comparison guard no longer strips a paren group that holds a predicate (a comparison or boolean operator), so `(1 < 2) = TRUE` is read as bool = bool and the engine answers it instead of the guard misdiagnosing a phantom `2 = TRUE` as number-vs-bool; plain redundant parens still strip, and a real mixed comparison beside a predicate group still refuses. Four new regression cases (fail with the guard change reverted) plus a live `verify:rustledger` pin; shipped in `7d84869d3` (`backend-cluster/ledger`).
