# `/api-gateway/mcp` never rejects a request by `Origin`, which the MCP transport spec says servers MUST do

**Severity:** minor (spec conformance; no known exploit, because every call needs a bearer token that a cross-site page cannot attach). **Estimate:** 30 minutes. **Owner:** `backend-cluster/backend-v2`, the global `cors({ origin })` in `src/server/start-server.ts` plus the MCP route (`src/features/ai-agent/api/mcp-route.ts`). **A1/A3:** MCP clients, registries and security reviewers check the transport rules; a MUST that is silently skipped shows up in directory reviews.

## Spec

MCP transport (2025-06-18 and later, "Security Warning"): "Servers MUST validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks. If the `Origin` header is present and invalid, servers MUST respond with HTTP 403 Forbidden."

## Repro (production, 2026-10-24, OAuth token pinned to the QA fixture; `ping` only)

`POST /api-gateway/mcp` with `Authorization: Bearer <token>` and a JSON-RPC `ping`:

| `Origin` | status | `Access-Control-Allow-Origin` |
| --- | --- | --- |
| none | 200 | none |
| `https://evil.example` | **200** | none |
| `null` | **200** | none |
| `https://beancount.io` | 200 | echoed |
| `http://localhost:3000` | 200 | echoed |

`OPTIONS` preflights from `https://evil.example` and `https://claude.ai` answer 200 with no `Access-Control-Allow-*`, which blocks a browser from reading the answer; the request that carries the bearer token is still executed whenever a non-browser client (or a script with the token) sends it. Anonymous requests are `401` whatever the `Origin`.

## Cause

The one CORS middleware for the whole gateway only decides the response headers (it returns `""` for a foreign origin). It never answers 403, and nothing in the MCP route checks `Origin`.

## Fix

Owner decision:

- (a) On the MCP route only, answer `403` (JSON-RPC error, id null) when `Origin` is present and fails the same allow rule the CORS middleware uses; leave requests without `Origin` alone, since native and server-side clients send none. Keep the preflight behaviour.
- (b) Record in `docs/mcp.md` and ADR 0007 that the endpoint is bearer-only and deliberately does not validate `Origin`, with the reasoning.

(a) matches the spec. Tests: a foreign `Origin` gets 403 before any tool runs; no `Origin`, `https://beancount.io` and `http://localhost:<port>` are unchanged; anonymous requests still get 401 with the discovery header.

## Note for the reviewer

The allow rule is "any `*.beancount.io` host, `localhost` or `127.0.0.1` on any port, with credentials". Any page on a sibling subdomain (for example the repository host) is therefore treated as trusted by the CORS layer. That is a wider surface than the single dashboard origin; it is worth a deliberate look when this is decided.

## Dedupe

No board item mentions `Origin` or CORS for the MCP endpoint (a search for CORS and DNS-rebinding terms across w23 and w5 returned only an unrelated CLI note).

**Blocked 2026-10-25, unblocked 2026-10-30** — the owner chose option (a) on 2026-10-30: on the MCP route only, answer `403` (JSON-RPC error, id null) when `Origin` is present and fails the CORS allow rule; requests without `Origin` stay unchanged, preflight behaviour is kept. Rationale: matches the MCP transport spec, no effect on native/server-side clients. The fix must also record in `docs/mcp.md` / ADR 0007 that the allow rule is any `*.beancount.io` host plus `localhost`/`127.0.0.1`, which is wider than the single dashboard origin. Earlier blocker (kept for history): owner decision between (a) 403 and (b) documented non-validation.

---

**Resolved 2026-10-30** — the MCP route now answers 403 (JSON-RPC error, id null) for a present untrusted `Origin`, after the credential gate, sharing `isAllowedOrigin` with the CORS middleware; `docs/mcp.md` and ADR007 D12 record the allow rule (any `*.beancount.io` host plus `localhost`/`127.0.0.1`). Tests: `mcp-origin.test.ts` (`backend-v2`).
