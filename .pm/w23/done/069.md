# Admin actions on a ledger the caller can read answer "Ledger not found": collaborators, rename and delete conceal a denial that hides nothing

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/backend-v2`, `src/server/api/authorization/authorization-service.ts`. `LEDGER_NOT_FOUND_CONCEALMENT` is on `LEDGER_ADMINISTRATION_UPDATE`/`_DELETE` and `LEDGER_COLLABORATORS_LIST`/`_PERMISSION_READ`/`_UPDATE`/`_DELETE`, shared by REST, GraphQL and MCP (`updateLedger`, `deleteLedger`, `setLedgerCollaborator`, `removeLedgerCollaborator`, `collaborators` resources). **A1:** an agent told "Ledger not found" about the ledger it just queried concludes the ledger is gone or its credential is broken, instead of reporting "you need admin rights".

## Repro (production, 2026-10-22, OAuth `ledger.admin` account-wide on a QA account, read-only)

On a public ledger owned by another account (`open_ledger/3m` from `catalog/ledgers/search`):

- `metadata`, `runBqlQuery`, `commits` and `listLedgerFiles` all succeed.
- `beancount://open_ledger/3m/collaborators` and `…/collaborators/permission?collaborator=open_ledger` → `NOT_FOUND` "Ledger not found".
- Control: `appendLedgerText {dry_run: true}` and `createLedgerFiles {dry_run: true}` on the same ledger → `FORBIDDEN` "Authorization denied".

The same applies to a read-only collaborator on a private ledger: a ledger they can read is reported missing by every admin action. Admin writes against another account's ledger were not attempted; the policy table shows the same concealment on all six actions.

## Cause

The concealment fires on any `relationship_denied`, whether or not the caller can see the ledger. It exists to hide ledgers the caller cannot see. w23/063 fixed the same pattern for `LEDGER_COLLABORATORS_LEAVE` only, in `leaveLedger`: it catches the concealed `NOT_FOUND`, checks the caller can read the ledger's metadata, and refuses with the real reason.

## Fix

Do it once in the authorization service rather than per workflow. When a `LEDGER_NOT_FOUND_CONCEALMENT` action is denied by relationship, check the ledger metadata read relationship. If it holds, refuse with `FORBIDDEN` naming the missing authority ("Managing collaborators on open_ledger/3m requires admin access to it"). Otherwise keep the concealment. Then `leaveLedger`'s special case can reuse it. Tests on all three surfaces: a public-ledger reader and a read-only collaborator get `FORBIDDEN` for list/permission/set/remove/update/delete; a caller who cannot see a private ledger still gets byte-identical `NOT_FOUND` for an existing and a missing ledger.

## Dedupe

w23/063 (done) covers leave only. w23/066 is the numeric-ID existence leak for asset URLs, the opposite direction. No item covers admin actions on visible ledgers.

---

**Resolved 2026-10-23** — the six concealed admin actions now tell a caller who can read the ledger why they are refused, once, in the authorization service. REST, GraphQL and MCP share it.

`ActionRequirement.deniedToReader` (`backend-cluster/backend-v2/src/server/api/authorization/authorization-service.ts`) is set on `LEDGER_ADMINISTRATION_UPDATE`/`_DELETE` and `LEDGER_COLLABORATORS_LIST`/`_PERMISSION_READ`/`_UPDATE`/`_DELETE`. When one of them is denied by relationship, the PDP asks the evaluator whether the caller holds `READ_CONTENTS` on the ledger, the relationship every content read needs. If it does, the denial carries the new reason `insufficient_relationship`, which the "Ledger not found" concealment does not cover, and leaves as `FORBIDDEN` naming the authority. Examples: "Managing collaborators on open_ledger/3m requires admin access to it", "Deleting alice/main requires admin access to it". A caller who cannot read the ledger, and any outage of that second check, keeps the concealed `NOT_FOUND`, so an existing hidden ledger and a missing one still answer identically. Leaving (`LEDGER_COLLABORATORS_LEAVE`) is unchanged: `leaveLedger`'s w23/063 refusals are more specific ("an owner can't leave", "not a collaborator") than "requires admin access", so it was not folded into this. `docs/api-parity.md` records the rule.

**Tests:**
- `authorization-service.test.ts`: each of the six actions, refused to a reader, gives `insufficient_relationship` and `FORBIDDEN` with its message. A failing reader check keeps "Ledger not found". The existing all-denied case still conceals all seven actions.
- `collaborator-parity.test.ts`, on REST, MCP and GraphQL: a public-ledger reader and a read collaborator get `FORBIDDEN` for list, permission, set and remove, and nothing is written. A caller who cannot see the private ledger still gets `NOT_FOUND` "Ledger not found". The read collaborator's expectation in the scope/relationship/pin case moved from 404 to 403.
- `lifecycle-parity.test.ts`, on all three surfaces: a public-ledger reader reads the ledger and gets `FORBIDDEN` for update and delete, with nothing changed. The existing missing-vs-inaccessible concealment cases still pass.

Reverting the fix fails 12 of these cases.

**Gates:** backend-v2 typecheck, ESLint, Knip, 6876 unit tests. `upstream-survival.test.ts` failed as usual (environment-only). `archive-parity`, `git-proxy-handler`, `ssh-proxy-server` and `auth-service-password-budget` failed under full-suite load and pass alone (79/79). The authorization model (`authz/`) is unchanged: no relationship grant moved. Needs a backend-v2 deploy.
