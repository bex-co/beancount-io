# Concurrent writes still fail with `SERVICE_UNAVAILABLE` on production after w23/017: the lost-race signature there is not the one the fix matches

**Severity:** moderate. **Estimate:** 30–60 minutes once the production signature is read. **Owner:** `backend-cluster/ledger`, `isGiteaWriteConflict` in `src/features/gitea/utils/gitea-error.ts` and the error middleware, plus `backend-cluster/backend-v2`'s edit-tool retry. **A1:** coding agents issue tool calls in parallel by default, so three entries written at once routinely become one success and two "service unavailable" errors. The agent then retries blindly or reports an outage.

## Repro (production, 2026-10-22 ~14:40 PDT, OAuth `ledger.admin` account-wide, disposable `qa-` ledger, since deleted)

The build is the 01:43 deploy, which includes `73822e134` (w23/017, 2026-10-20). Three parallel calls each, at human scale:

| tool | result |
| --- | --- |
| `appendLedgerText`, 3 distinct transactions | 1 `ok`; 2 `SERVICE_UNAVAILABLE` "Ledger API is temporarily unavailable" (~2.2 s each) |
| `addLedgerEntries`, 3 distinct transactions | 1 `ok`; 2 `SERVICE_UNAVAILABLE` |
| `updateLedgerFiles`, 3 exact-text edits to different lines of one file, two rounds | each round 1 `ok`; 2 `SERVICE_UNAVAILABLE` "commit failed: Ledger API is temporarily unavailable"; the file holds only the winner's edit |

No write was lost silently; exactly the winners landed. But w23/017's promised behavior is absent: retried exact-text edits landing together, and a 409 `CONFLICT` "re-read and retry" otherwise.

## Cause (to confirm from logs)

017 observed the lost race on a local Gitea 1.24.7 as HTTP 500 `cannot lock ref 'refs/heads/main'` and matched that text, plus `PushOutOfDate`. Its note left "production confirming the same signature" open. Production evidently returns something else: different text, a different status, or a timeout on a slower store. So the classifier misses it, and the raw failure is mapped to `SERVICE_UNAVAILABLE`.

## Fix

1. Read the ledger service's log for one losing call (the three-parallel `updateLedgerFiles` above reproduces it on any ledger) and record the exact host status and body.
2. Extend `isGiteaWriteConflict` to that signature. If the host gives no usable text, classify "the branch head moved during this commit" by comparing the head before and after the failed call.
3. Add a regression test with the production body.

Acceptance: on production, the same three-parallel runs land all three `appendLedgerText`/`addLedgerEntries` entries (they don't overlap) and all three exact-text edits, or return `CONFLICT` with the retry message; never `SERVICE_UNAVAILABLE`.
