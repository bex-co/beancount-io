# 149 — File writes COMMIT bean-check-invalid content (`updateLedgerFiles` has no validation gate; entry writes refuse)

## Summary
`updateLedgerFiles` commits content that fails bean-check and answers `ok:true`: writing `NOT BEANCOUNT ===` over `main.bean` committed (sha `f1a0b83c…` → `67e385e2…`, 2817 → 17 bytes) with summary "Committed 1 change(s)… 1 new bean-check error". The entry twin refuses the same class: `addLedgerEntries` with a failing balance answers `VALIDATION_FAILED` on both the real and `dry_run` paths. Any agent file typo therefore corrupts a ledger with a success envelope. Major: silent ledger corruption behind `ok:true`.

## Repro (prod, puncsky/mcp-agent-eval — induced once, restored byte-identical, see below)
- MCP `updateLedgerFiles {"files":[{"path":"main.bean","content":"NOT BEANCOUNT ===","sha":"f1a0b83c…"}],"message":"…"}` (no `dry_run`) → `ok:true`, "Committed 1 change(s) to main.bean. 1 new bean-check error: parse error: unexpected input (main.bean:1)", `validation.errorsAfter: 1`.
- MCP `dry_run:true` with the same content → `ok:true` preview with `validation.errorsAfter: 1` — no refusal either (contrast entry `dry_run`, which refuses).
- Control, entry path: `addLedgerEntries` balance 999.00 USD vs 49.75, real and `dry_run` → both `VALIDATION_FAILED`, nothing written.
- Extended: `deleteEntrySources` `dry_run` deleting the `Equity:Opening-Balances` open → `VALIDATION_FAILED` ("was never opened"). Entry add/update/delete all refuse invalid; file create/update/delete all commit it (shared executor) — the split is exactly tool-family vs tool-family.
- REST twin: `PUT …/files/main.bean` `dryRun:true` with the same invalid content → `{"ok":true,"dryRun":true}` (no validation info at all); the commit handler calls the same un-gated `changeFiles` and returns `ok:true` unconditionally, so REST commits invalid too (live commit probe withheld to avoid a second corrupt/restore cycle — proven by shared-service source).
- GraphQL file mutations route through the fava API client (`ledger-workflow.ts`), a separate path — gate status there needs the parity check.

## Restoration (same session)
`main.bean` restored via `updateLedgerFiles` from the byte-identical local fixture (git blob `f1a0b83c1aaf9608113c6bd3174bf7d2dab35407`): sha, size (2817), `checkLedger` errors `[]`, BQL postings 34, journal total 29 all match pre-incident values. History holds the two commits (induced + restore); content is exact.

## Root cause (main)
The file-write commit path (`executeEditLedgerFiles`, `backend-cluster/backend-v2/src/features/ai-agent/tools/edit-ledger-files-tool.ts`) wraps the repo write in `withPostWriteValidation` — validation runs *after* the commit and is only reported in the payload/summary. No pre-commit gate exists, and no `allowInvalid` flag exists either (nothing ever refuses). The executor is shared behind the create/update/delete file tools, so all three commit invalid results. The entry path gates pre-commit (`VALIDATION_FAILED` unless `allowInvalid`).

## Expected
Gate file commits on new bean-check errors like entries (refuse unless an explicit override), and make `dry_run` refuse invalid exactly as the commit would (m7: "previews alike"); verify REST refuses identically and check the GraphQL/fava path. Either the file tools gain the entry-style gate, or all surfaces document that file writes commit-invalid — silently committing behind `ok:true` is the one unacceptable state.
