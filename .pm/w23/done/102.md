# `commits?page=` past the int32 offset answers `INTERNAL_SERVER_ERROR` instead of an empty page

**Severity:** minor (pathological input, but a 5xx with a retry-hint that cannot help; agents paging blindly can trip it). **Estimate:** 30–60 minutes incl. parity. **Owner:** `backend-cluster/backend-v2`, commits resource + REST/GraphQL counterparts. **A1/A2:** agents paginate commit history; one page too far turns an empty page into a server error.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`…/commits?page=N&limit=10`, bisected exactly (it.573):

- `page=214748365` (offset 2,147,483,640) → `ok`, `[]`.
- `page=214748366` (offset 2,147,483,650 — one past int32 max) → `INTERNAL_SERVER_ERROR: Failed to fetch commits from Gitea` with "Retry once. If it persists the failure is server-side…".

The cliff is exactly the int32 offset overflow in the downstream Gitea commit list; backend-v2 wraps it in `unwrap`-style generic 500 (same shape as w23/092's BQL size cliff). Sibling paginations handle the same input cleanly: `collaborators?page=214748366` → `[]`, `social/followers?page=214748366` → `{"users":[],"total":0}` — only the commits path overflows. Cross-surface confirmed 2026-10-26 (it.759): REST `GET …/commits?page=214748366` fails identically (`INTERNAL_SERVER_ERROR: Failed to fetch commits from Gitea`) — same downstream, same fix on every surface.

## Fix (keep REST/GraphQL/MCP in parity)

Cap `page` (or `page*limit`) up front and refuse absurd values with `BAD_USER_INPUT`, or map the Gitea overflow to an empty page — either beats a 500. Same fix shape as w23/092: validate client-bounded inputs before the downstream hop.

## Dedupe

No `.pm` item covers pagination overflow (searched: page overflow, int32, commits page, huge page; w23/092 owns the BQL size cliff — same 500-shape family, distinct path). Open: m4, 092–101.

---

**Resolved 2026-10-26** — fixed in `backend-cluster/backend-v2`: `CommitsService.listCommits` answers the empty page when `(page - 1) * limit` exceeds int32max instead of hopping to Gitea and 500ing, positioned after authorization so forbidden callers still get 403. All three surfaces share the service method, so REST, GraphQL, and MCP are fixed together. Regression tests pin the note's bisected cliff (page 214748365 hops, 214748366 answers `[]` at limit 10) plus the limit-50 boundary pair, and fail with the guard disabled. No OpenAPI change (no schema touched).

**Prod re-verified it.6365:** `commits?page=214748366&limit=10` → `[]` (empty page, no 500). The int32 guard holds live.
