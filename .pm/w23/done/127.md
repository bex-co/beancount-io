# 127 — `SELECT * AS x` collapses star to one mismatched column (it.3583)

## Summary
MCP accepts `SELECT * AS x FROM postings` but produces a metadata/rows mismatch: the structured result declares ONE column (`x`, dtype `str`) while each row still carries all 31 star cells. The text renderer shows only the first cell per row, silently dropping the other 30 values. Stock beanquery `ParseError`s the query.

## Repro (prod, puncsky/mcp-agent-eval)
- Structured: `SELECT * AS x FROM postings LIMIT 2;` → `types: [{name:'x',dtype:'str'}]`, but each `rows[]` has 31 cells.
- Text: `SELECT * AS x FROM postings LIMIT 1;` → header `x`, single value `transaction` (30 values dropped).
- Stock: `ParseError: syntax error` (star takes no alias).
- Bare alias `SELECT * x ...` → MCP `Invalid BQL query: syntax error at position 9` (rejected correctly).

## Expected
Either reject `* AS alias` like stock (and like the bare-alias form), or expand the alias over the star consistently in metadata, rows, and text. The current state — 1 declared column vs 31 delivered cells, silent truncation in text — can mislead agents consuming the structured shape.

## Status
Open (inbox). MCP-side (preprocessing/rendering), not an upstream engine divergence.

## Update (it.4193)
Also reproduces over a subquery scope: `SELECT * AS x FROM (SELECT account, date LIMIT 1);` → 1 declared column (`x`) vs 2 delivered cells; stock ParseErrors. Same collapse, not postings-specific.

## Update (it.6319)
Qualified form `SELECT postings.* AS x FROM postings LIMIT 1` co-refuses on both (MCP `found '*' expected identifier`, stock ParseError) — the collapse is specific to the unqualified `* AS x`.
