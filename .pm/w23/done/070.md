# REST answers a bearer token it rejected with "send `Authorization: Bearer <token>`", the header the caller just sent

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** `backend-cluster/backend-v2`, `requireIdentity` in `src/server/rest/v1-route.ts` and the bearer resolution in front of it. **A1:** agents connected over MCP routinely try the same token against REST, for the archive fallback (w23/023) or a REST-only read. Told to send the header they already sent, they retry or conclude the API is broken, instead of switching credentials.

## Repro (production, 2026-10-22)

`GET /api-gateway/v1/ledgers/<owner>/mcp-agent-eval/years` with `Authorization: Bearer <token>`:

| token | status | message |
| --- | --- | --- |
| valid OAuth token issued for the MCP resource (`…/api-gateway/mcp`) | 401 | "This endpoint requires a credential: send `x-api-key: <personal-access-token>` or `Authorization: Bearer <token>`." |
| `garbage.token.value` | 401 | same |
| no header | 401 | same |

The MCP audience refusal is by design (ADR 0007, `docs/mcp.md`: "Application API/mobile tokens targeting `{issuer}/v1` do not authenticate to MCP", and the reverse holds too). The defect is the message: a presented but rejected credential, whether wrong audience, expired, or malformed, is reported as an absent one.

## Fix

When an `Authorization: Bearer` or `x-api-key` header is present but resolves to no identity, answer 401 `UNAUTHENTICATED` with a message saying the credential was not accepted. When the token verifies for the MCP resource, name it: "This token was issued for the MCP endpoint (`/api-gateway/mcp`); REST needs a personal access token or an application token". Otherwise say "expired, revoked, malformed, or issued for another resource". Keep the current text for requests with no credential. Tests: no header, garbage bearer, MCP-audience token and expired token each get their own message; GraphQL's equivalent refusal gets the same wording.

**Resolved 2026-10-23** — a credential header that resolves to no identity is now refused as not accepted, not as missing, on REST and GraphQL alike.

`credentialRejection` (`backend-cluster/backend-v2/src/server/api/identity.ts`) runs only when a request sent `Authorization` or `x-api-key` and resolved no identity. It explains the refusal:

- A token that verifies for the MCP resource gets "This token was issued for the MCP endpoint (`/api-gateway/mcp`) and is not accepted here: send a personal access token (`x-api-key`) or an application token instead."
- Anything else gets "The credential sent was not accepted: it is expired, revoked, malformed, or issued for another resource. Send a current personal access token (`x-api-key`) or `Authorization: Bearer <token>`." These reasons are deliberately not told apart, as `resolveApiKeyIdentity` already requires, so a caller cannot learn which keys were once real.

REST's `requireIdentity` (`v1-route.ts`) and GraphQL's two refusals use it: `getCurrentIdentity`/`getCurrentUserId` in `context.ts`, and `@Authenticated` in `authenticated.ts`. A request with no credential keeps its old text on both. So does a browser's expired session cookie, which keeps its sign-in refusal. The MCP endpoint's own 401 already points at its discovery document (ADR 0007) and is unchanged. `docs/mcp.md` records the reverse audience rule.

**Tests:** `src/server/api/__tests__/credential-rejection.test.ts` signs real ES256 tokens. No header, a stale cookie, an MCP-audience token, an expired application-API token, a malformed bearer and an unknown API key each get their own answer from the helper, from REST (`GET …/years`, 401 `UNAUTHENTICATED`) and from GraphQL (`getCurrentIdentity` and `@Authenticated`). The no-credential cases keep the old wording. Reverting the REST and GraphQL wiring fails the 2 surface cases.

**Gates:** backend-v2 typecheck, ESLint, Knip, 6888 unit tests. `upstream-survival.test.ts` failed as usual (environment-only). `archive-parity`, `git-proxy-handler` and `batch-processor` (timing) failed under full-suite load and pass alone (84/84). Needs a backend-v2 deploy.
