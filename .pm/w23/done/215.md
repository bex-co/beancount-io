# BQL `sum(1)` reports dtype `Decimal` where stock beanquery 0.2.0 reports `int`

**Severity:** minor (the cell value agrees). **Owner:** `backend-cluster/ledger` (dtype rules in `ledger-shell-mappers` / `bql-expression-typer`). **Estimate:** 30m. **Pillar:** A1.

Found by the w23/m20 oracle replay, query id `inner-sum1`: `SELECT sum(1) FROM (SELECT * FROM postings)` answers `"22"` with dtype `Decimal`; stock answers `22` with dtype `int`.

Check whether the engine types every integer-input `sum` as `Decimal` or only the literal/inner form, then give integer sums the integer dtype or document the exception.

Once resolved, remove the `inner-sum1` entry from `backend-cluster/ledger/scripts/bql-oracle/allowlist.json`.

---

**Blocked 2026-11-05** — Triaged on `main` by probing `LedgerShellService.queryShell` against stock beanquery 0.2.0 on the w23/m20 fixture. The note under-states it: the engine reports dtype `Decimal` with a string cell for every integer-input `sum` and for integer arithmetic (`sum(1)` `"22"`, `sum(year)` `"44564"`, `1 + 1` `"2"`, `year + 1` `"2026"`, `count(*) + 1` `"23"`), where stock reports `int` with a JSON number; `count(*)` and `min`/`max` of integers already report `int` with a number.

The dtype is also unstable across the empty/non-empty boundary: `SELECT sum(1) WHERE FALSE` reports `int` (the w23/164 static typer), while the same expression with rows reports `Decimal` (value sniffing in `classifyColumnDtype`, `ledger-shell-mappers.ts`).

The cause is deliberate. The engine does integer arithmetic in exact decimals and returns strings, because a JS number loses integers above 2^53 (`SELECT 9007199254740993` is exact here and in stock; see `bql-int-literals.ts` and `w23/done/133.md`). Giving integer sums the `int` dtype therefore also needs number cells, which changes the JSON type of cells on REST, GraphQL and MCP and needs a rule for results past 2^53. That is a contract decision, not the 30-minute dtype fix the note assumed. Nothing was changed in code.

**Unblock:** the owner picks one of:

- **(a)** `int` dtype with JSON-number cells for integer-valued arithmetic up to 2^53 and exact strings beyond (mixed cell types; all three surfaces and their docs updated together);
- **(b)** keep `Decimal` as the engine's numeric domain, make the empty-input typer report `Decimal` for integer sums and arithmetic so the dtype stops flipping with row presence, and document it in `backend-cluster/ledger/README.md` next to the `str()` input-domain section;
- **(c)** accept the difference as documented and only record it.

Recommended: **(b)**, the smallest change that removes the instability without touching cell types.

**Who can clear it:** the repository owner (a public contract decision).

**Allowlist:** the `inner-sum1` entry in `backend-cluster/ledger/scripts/bql-oracle/allowlist.json` stays; its reference follows this note to `.pm/w23/blocked/215.md`.

---

**Resolved 2026-11-05** — The owner chose option (b). The engine answers a Decimal string for integer `sum` and integer `+ - *` (`sum(year)` "44564", `year + 1` "2026") and a number for `%`, count, min, max, round, abs and bare integer columns. The static typer for empty results reported `int` for the first group, so the dtype flipped to `Decimal` once a row appeared. `bql-expression-typer.ts` now types integer `sum` and integer `+ - *` as `Decimal` and leaves `%`, `min`, `max`, `round` as `int`; the tests that pinned the old `int` are corrected and `count(*) % 3` and `min(year(date))` added. `backend-cluster/ledger/README.md` gains "BQL integer arithmetic is `Decimal`". The `inner-sum1` oracle allowlist entry stays (stock still says `int`; the difference is now deliberate and documented) and points at this note. Cell types are unchanged on REST, GraphQL and MCP. Shipped in the commit that moves this note (`backend-cluster/ledger`).
