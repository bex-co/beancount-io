# w23/119 — set-typed BQL cells render space-joined in text but comma-joined in structured results

Status: inbox
Opened: 2026-10-26 (loop it.2932)
Surface: BQL results (MCP text vs MCP structured vs REST vs GraphQL)
Severity: minor (same cell, two strings; a client switching tools must re-parse)

## Summary

`SELECT other_accounts LIMIT 1;` returns the same set through every surface,
but the TEXT surfaces and the STRUCTURED surfaces serialize it differently:

| surface | `other_accounts` cell |
|---|---|
| MCP `runBqlQuery` (text table) | `Assets:Bank:Savings  Assets:Cash  Equity:Opening-Balances` (space-separated, no commas) |
| GraphQL `queryShellText` | same space-separated text (agrees with MCP text) |
| stock `bean-query` | same space-separated text (agrees with MCP text) |
| MCP `runBqlQueryStructured` | `"Assets:Bank:Savings, Assets:Cash, Equity:Opening-Balances"` (one comma-joined string; column dtype is `set`) |
| REST `POST …/query` | same comma-joined string + `dtype: "set"` (agrees with MCP structured) |

Each side is self-consistent — but the two sides disagree with each other, so a
client that renders `runBqlQuery` text in one place and `runBqlQueryStructured`
rows in another shows two different strings for the same cell.

Two sub-oddities inside the structured side:

1. The column dtype is `set` but the value is a flat comma-joined STRING, not an
   array. A `set` dtype that never carries a set is a mistyped schema — clients
   must string-split on `", "` to recover the members (works today only because
   account names cannot contain commas).
2. Empty sets render as `""` (verified: `SELECT tags` / `SELECT links` on this
   tagless fixture return `""` on both MCP and stock), so `""` means "empty set"
   while any non-empty set is comma-joined — the join is the only framing.

## Why it matters

`other_accounts` (and any future set-typed column) is the one BQL cell shape
whose serialization depends on which tool rendered it. The repo already unified
the typed entry schema (w23/m6) and the write-flag spellings (w23/m9); the
text/structured BQL split is the same class of inconsistency one level down.

## Suggested fix

Pick one serialization and use it in both renderers — either:

- (a) structured returns a real JSON array for `set` dtypes (schema-honest; text
  keeps its stock-compatible spacing), or
- (b) both sides join identically (comma- or space-joined everywhere).

(a) is strictly better: it also fixes the dtype/value mismatch. Either way,
document the empty-set `""` rendering (or return `[]` under (a)).

## Repro

```bash
node .agents/skills/qa-shared/scripts/qa-mcp.mjs call runBqlQuery \
  '{"query":"SELECT other_accounts LIMIT 1;"}'
# → …Assets:Bank:Savings  Assets:Cash  Equity:Opening-Balances  (no commas)
node .agents/skills/qa-shared/scripts/qa-mcp.mjs call runBqlQueryStructured \
  '{"query":"SELECT other_accounts LIMIT 1;"}'
# → rows: [["Assets:Bank:Savings, Assets:Cash, Equity:Opening-Balances"]] (commas)
```

**Resolved 2026-10-26** — fixed as option (b) in `backend-cluster/ledger` (`ledger-shell-mappers.ts`): structured set cells now render through the same sorted double-space join as the text table (stock-compatible), via one shared `formatArrayCell`, instead of comma-joined.
