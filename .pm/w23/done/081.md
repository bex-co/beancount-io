# Raw writes accept an amount with more than 28 significant digits, and every report then reads a rounded value, with "No new bean-check errors"

**Severity:** minor-to-moderate (silent value change; it needs a 29+ digit amount, which 18-decimal tokens reach at modest holdings). **Estimate:** 45–60 minutes. **Owner:** `backend-cluster/backend-v2` (`DirectiveAppendWorkflow` behind `appendLedgerText`, and the file-edit tools' bean-check projection) with `backend-cluster/ledger` for the shared check. The cause is upstream in the engine (`@rustledger/wasm` 0.24.0); report it there only with the user's OK. **A1:** a coding agent importing wei-denominated or high-supply token balances writes the literal it was given and is told it is clean.

## Repro (production, 2026-10-24, disposable `qa-` ledger since deleted, OAuth `ledger.admin` account-wide)

`appendLedgerText` with

```beancount
2021-01-02 * "raw"
  Assets:Cash  999999999999999999999999999.99 USD
  Equity:Initial
```

returns "Added 1 directive to main.bean. No new bean-check errors." The file keeps the digits exactly as sent. `SELECT narration, number WHERE account = 'Assets:Cash'` then returns `1000000000000000000000000000.0`: the engine kept 28 significant digits and rounded the cents away. The same with `9999999999999999999999999999.99` (30 digits) reads as `10000000000000000000000000000`. `checkLedger` stays clean. The structured `addLedgerEntries` path behaves the same today (its literal is written, then read back rounded); `43b88b801` (w21/997) makes that path refuse more than 28 digits once deployed.

A 29-digit integer with no fraction is the case the engine does reject (`P0012` on both postings), so the user sees an error there. The silent case is any literal whose significant digits exceed 28 while its integer part does not.

## Cause

The projected bean-check runs the engine over the new text; the engine rounds instead of failing, so nothing is "new". w21/997 added a digit-count check to the ledger service's structured-entry builder (`foundation/rustledger/entry-build.ts`), not to the raw-text paths.

## Fix

Apply the same 28-significant-digit rule to numeric literals in text that `appendLedgerText`, `updateLedgerFiles`/`createLedgerFiles` (new text only), `updateEntrySource` and bank import write, reusing the helper from `43b88b801`, and refuse with `BAD_USER_INPUT` naming the literal and the 28-digit limit. Alternatively compare each posting's literal with the value the engine reports after the write and fail on any difference. Tests: the two literals above are refused on every raw write tool; 28-digit amounts and ordinary amounts are unchanged; text that merely contains long digit strings outside amounts (narrations, meta) is unchanged.

## Dedupe

w21/997 (done, `43b88b801`) covers the structured path and the mobile form. No item covers raw text, file edits or entry-source edits.

**Resolved 2026-10-25** — new `assertAmountsFitEngineDecimal` (same 28-significant-digit rule as 997, applied to `number currency` pairs in text with quoted spans and comments aside) is enforced on the new text of every raw write: `DirectiveAppendWorkflow` (append, all surfaces), `executeEditLedgerFiles` (per-op new text only, so edits around a legacy long literal still land), REST PUT file, GraphQL create/update file (binary uploads skip the scan), and `LedgerJournalService.updateSourceSlice` (all surfaces); refusal is `BAD_USER_INPUT` naming the literal. Shipped in the commit that moved this note (`backend-cluster/backend-v2`). Deviations: bank import needed no change (it submits structured entries through the ledger builder 997 already guards); the shared check is ported into backend-v2 rather than imported (packages share no code); REST PUT and the GraphQL twins were included for parity though the note named only the MCP tools.
