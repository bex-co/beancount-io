# 171 — Typed posting tags/links render stock-invalid beancount; backend check blind, reads blank

## Summary
The typed path accepts posting-level `tags`/`links` (shipped as w23/m6: "posting tags/links hold live") for a construct beancount cannot express — posting lines have no tag/link slot in the grammar — and renders them as a trailing suffix after the amount (`3.50 USD #qa-ptag1`), which stock rejects with a syntax error. Worse, the backend bean-check passes the invalid text (`Added 1 entry… No new bean-check errors`) and commits stock-invalid bytes to the ledger; every read path then comes back empty (list postings carry no tags field, BQL `tags` blank, `#tag` filter misses). A write that succeeds, corrupts (by stock's grammar), and reads back as if it never happened. Transaction-level tags/links are unaffected (verified exact in it.177).

## Repro (prod, puncsky/mcp-agent-eval; probe entry added + deleted, byte-identical restore + stock-clean re-verified; stock = beancount 3.x CLI on fixture + same bytes)
- Typed add with posting `tags: ["qa-ptag1"]` → `Added 1 entry to main.bean. No new bean-check errors.` Slice: `Expenses:Food:Coffee  3.50 USD #qa-ptag1`.
- Stock `bean-check` on the resulting prod bytes → `:90: syntax error, unexpected TAG, expecting end of file or EOL or ATAT or AT`, exit 1. The tag-before-amount position (`#qa-ptag1 3.50 USD`) fails identically — no valid slot exists.
- Reads on the committed entry: `listLedgerEntries` postings expose account/units/cost/price/meta/flag only (no tags/links); BQL `SELECT tags WHERE payee='qa-ptag'` → blank both rows; `listLedgerEntries {"filter":"#qa-ptag1"}` → total 0.
- Links share it (dry_run only, no second invalid commit): posting `links: ["qa-link9"]` previews `3.50 USD ^qa-link9` with "No new bean-check errors".
- Disproven claim: done/m6 README "Prod re-verified it.6376: posting `tags: [\"qatag\"]` dry_run passes schema… Posting tags hold live" — the re-verify was dry_run-only and never committed, never stock-checked the render, never read back. Live, all three fail.

## Root cause (main)
Two compounding decisions: (1) `entry-build.ts:182-188` spreads posting tags/links onto a render-side extension *known* to have no engine representation ("PostingJson carries neither… the engine never sees it", w23/m6/t003); (2) `journal-serialize.ts:759-771` (`tagsLinksSuffix`, :721-725) appends them trailing after the aligned amount — inventing syntax beancount has no slot for. The backend bean-check then waves the text through (same validator-blindness family as w23/149: projections don't run a real stock parse). Shared typed path — REST/GraphQL accept the same fields (GraphQL `LedgerPostingInput.tags/links` exist), so every surface can commit the invalid bytes.

## Expected
One of: (a) refuse posting tags/links in the typed schemas with a loud "beancount has no posting-level tags" error (schema-only, sub-hour, stops the corruption today); or (b) define a real representation (e.g. hoist to txn-level tags with provenance, or metadata) with stock-valid rendering + read-back + filter support. Also consider a stock-parse backstop in the projection check so invented syntax can never commit silently again (w23/149's lesson, same hole). Do not leave accept-render-blank as the steady state.

## Narrowing (worker1 it.182)

`checkLedger` itself is faithful: with a deliberately committed unbalanced txn (`allowInvalid`, 2 errors), it returned both errors (E1001 + E3001, line 89) in `structuredContent.result.errors`, exactly matching stock `bean-check` on the fetched bytes (exit 1, same 2 errors). So the 171 blindness is not "the checker never reports" — it is specifically that the backend checker does not flag the invented trailing `#tag`/`^link` syntax (stock-vs-backend parser divergence on that construct), and the write-path projection therefore reports "No new bean-check errors". Fix can target the divergence (renderer + a stock-parse backstop) without touching `checkLedger`.
