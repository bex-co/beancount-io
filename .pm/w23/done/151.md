# 151 — BQL refuses post-`;` tails stock silently drops — strictness is right, but legitimate trailing `--` comments get swept up

## Summary
MCP rejects any non-whitespace after the first `;` (`syntax error … found '-' expected … end of input`) while stock beanquery 3.2.3 silently drops the entire tail. The strictness is the *desirable* direction — stock answers `[(34,)]` for `SELECT …; GARBAGE!!!` and `SELECT …; SELECT 1;`, masking agent mistakes (the repo's own w1/m25/t005 rule enforces one statement at the BQL boundary for the same reason). The gap is only that legitimate trailing `--` comments are refused along with garbage and second statements: `SELECT count(*) …; -- trailing` → MCP `BAD_USER_INPUT`, stock `34`. Lead `--` comments co-refuse (both `ParseError`/syntax error) and inline `/* */` co-tolerate (both 34), so the split is exactly the post-`;` tail.

## Repro (prod, puncsky/mcp-agent-eval; stock = API-level `run_query` on the byte-identical fixture)
- `SELECT count(*) AS n FROM postings; -- trailing` → MCP `BAD_USER_INPUT` (position 36); stock `[(34,)]`.
- `SELECT count(*) AS n FROM postings; GARBAGE!!!` → MCP refuses; stock `[(34,)]` (tail dropped).
- `SELECT count(*) AS n FROM postings; SELECT 1;` → MCP refuses; stock `[(34,)]` (second statement dropped).
- Controls: `-- lead…\nSELECT …` refuses both; `/* inline */` returns 34 both; bare query 34 both.
- REST twin: `POST …/query` with the trailing-comment query → identical `BAD_USER_INPUT` (shared engine path).

## Expected
Keep refusing second statements and garbage (that strictness matches w1's single-statement rule — do not regress to stock's silent truncation), but accept trailing whitespace *and comments* (`--…`, `/*…*/`) so documented BQL comment habits work; or document the no-trailing-content rule with the exact error as the pointer. Either half is sub-hour; the load-bearing property is that multi-statement input keeps refusing loudly.
