# 140 — Nested multi-word keys are camel-only while top-level params dual-accept snake/camel (it.6373-6380)

**Severity:** minor (one wasted agent turn per paste; schema error names the fix). **Owner:** backend-v2 entry schemas. **A1:** agents writing pads.

## Repro (prod, puncsky/mcp-agent-eval, dry_run — no writes)

`addLedgerEntries` top-level params accept both spellings (`dry_run`/`dryRun`, `allowInvalid`/`allow_invalid` — verified live it.6367), and every other nested entry key is a single caseless word (`account`, `units`, `cost`, `price`, `flag`, `meta`, `tags`, `links`, `tolerance`, `booking`). But pad's source field is camel-only:

- `pad: {date, account, sourceAccount}` → schema-accepted (reaches bean-check: `Unused Pad entry`, it.6373).
- `pad: {date, account, source_account}` → `BAD_USER_INPUT: …sourceAccount: Invalid input: expected string, received undefined; …Unrecognized key: "source_account"` (it.6373).
- REST `POST …/entries` refuses identically (`VALIDATION_FAILED` naming `body.entries.0.entry.sourceAccount`, it.6374) — consistent, all surfaces.

`sourceAccount` and posting `totalPrice` are the only multi-word nested keys in the entry schema — `total_price` is likewise `Unrecognized key` (it.6380). Both splits, same fix. Schema-verified it.6381: a camelCase scan of the live `addLedgerEntries` inputSchema finds no other nested multi-word keys (top-level `allowInvalid`/`dryRun` dual-accept; rest are schema keywords). m3 unified top-level splits (`entry_hash`, commit message) only; nested casing was never in scope.

## Expected

Accept `source_account` alongside `sourceAccount` (alias, same as the top-level dual-spell params), on all surfaces; or document camel-only nested keys where agents read the entry schema.

## Status

Open (inbox). Backend-v2 (entry zod schemas + REST/GQL counterparts).
- Parity it.171: GraphQL shares the gap by construction (`LedgerPadInput.sourceAccount`, no snake alias) — `source_account` → `GRAPHQL_VALIDATION_FAILED` + `Field "source_account" is not defined… Did you mean "sourceAccount"?`. Same missing alias, but GraphQL's error is best-in-class (names the fix); the MCP/REST fix could mirror its suggestion UX.

**Resolved 2026-10-28** — fixed in `backend-cluster/backend-v2` with a service-level twin fold. `LedgerEntryService` accepts `source_account`/`total_price` on all three surfaces (REST zod, GraphQL inputs, MCP via the shared schema) and folds them once in `FavaLedgerEntryWriter.writeBulkEntries`, so REST/GraphQL/MCP plus the receipt workflow share one rule: null counts as missing, identical twins merge, two different values are refused naming the entry (`entry 0: pass one source account, not sourceAccount and source_account with different values`), and a pad carrying neither is refused m3-style. Amount twins compare as text (`10` vs `10.0` refuses — different directive text). The writer sees canonical keys only (new `CanonicalLedgerEntryInput`), so downstream validation and the Fava build are untouched. REST-spec wrinkle: two inline amount objects under `totalPrice`/`total_price` collapse to one model name in openapi-python-client (which drops the endpoint), and differing descriptions wrap the twin in a rejected allOf — so both twins register under one `PostingTotalPrice` component with one description (verified: verbatim attr pair in the regenerated client; GraphQL SDL keeps the explicit alias note). Pinned by 8 service tests (break-checked: 5 fail with the split condition inverted) and 9 surface-parity tests (3 cases × rest/gql/mcp). Full backend suite green (7705), lint/typecheck clean, tools/list budget bumped 116→117 KB per the recorded-measurement convention (118,989 bytes), v1 spec regenerated with the CLI client re-pinned in the same change.
