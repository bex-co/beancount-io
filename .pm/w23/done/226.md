# 226 — table-driven test: every `ErrorCategory` maps to one MCP code and one HTTP status

`runToolSafely` carries the thrown error's `ErrorCategory` as `errorCode`, and REST and GraphQL translate the same category separately. No test enumerates the categories and asserts the resulting MCP `code`, REST status and GraphQL extension code together, so a new category can drift on one surface.

Steps: enumerate `ErrorCategory`; for each, throw it from a stub service and assert the MCP `code`, the REST status and the GraphQL error code against one expected table; fix any category that disagrees and note the fix in the resolution. If the table already holds, the deliverable is the test.

Pillar A1 (agents branch on the machine code). Estimate ~45m. Parity rule: all three surfaces in the same change.

---

**Resolved 2026-11-08** — `error-category-parity.test.ts` (backend-v2, `src/server/api/__tests__/`) holds one explicit table (REST status, JSON-RPC number, whether the category can reach MCP) and, for each of the 15 `ErrorCategory` values, drives the real REST error middleware, the GraphQL `formatError` hook and the MCP envelope, then checks the MCP guide's failure table lists exactly the categories that can reach MCP, with the same JSON-RPC number. No category disagreed, so no adapter changed; `BILLED_BY_STORE` is the one category absent from the MCP guide, by design (only the session-only store-billed plan change raises it, and billing has no MCP tool). Mutation checks: changing `CONFLICT`'s REST status and `PREMIUM_REQUIRED`'s JSON-RPC number each fail a case. Shipped in the commit that moves this note (`backend-cluster/backend-v2`).
