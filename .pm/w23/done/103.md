# `addLedgerEntries` has no batch-size cap: 20,000 entries commit in one call

**Severity:** minor (a runaway agent loop can land tens of thousands of entries in a single call — with no `dry_run` to preview per w23/095 — bounded only by the 2 MiB body cap). **Estimate:** 1–2 hours incl. parity. **Owner:** `backend-cluster/backend-v2`, entry bulk-add + REST/GraphQL counterparts. **A1/A2:** bulk import is the typed path's job; without a cap or a chunking hint, one bad loop iteration writes 20k entries that must be reverted entry by entry (or by whole-file restore).

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`addLedgerEntries` with 20,000 minimal `note` entries in one call (1.86 MB body) → `ok`, "Added 20000 entries to main.bean", 25 s server-side. No item-count validation, no warning, no preview (095). Fixture restored byte-identical immediately after via snapshot (`main.bean` 2817 B, `errors: []`, 29 entries — verified).

Neighbor caps all exist: file content 1 MiB with a split hint, body 2 MiB with a chunking hint, journal `limit` ≤ 1000, staged-bank arrays ≥ 1 — and file batches cap at 50 (`createLedgerFiles` with 1001 files → `BAD_USER_INPUT: at most 50 files may be projected at once`, it.724). Only the entry batch is unbounded below the body cap.

## Fix (keep REST/GraphQL/MCP in parity)

Cap `entries` per call (e.g. 500–1000, matching the read `limit` cap) with `BAD_USER_INPUT` naming the cap and telling the caller to chunk, on every surface. `deleteEntrySources` takes the same array shape — cap it identically if it is likewise unbounded.

**Cross-surface scoping 2026-10-26** (it.760): REST `EntriesRequest.entries` has no `minItems`/`maxItems` either (keys: `description/items/type`), and MCP batch-delete takes 1001 bogus entries straight to lookup with no size validation (it.726) — uncapped on every surface as stated. (Also noted: REST budget `interval` is an enum `daily…yearly` while MCP takes a free string — a minor strictness difference, not filed.)

## Dedupe

No `.pm` item covers batch size caps (searched: batch cap, batch size, max entries, unbounded; w23/095 owns the missing preview — distinct gap, same call). Open: m5, 093–102.

---

**Resolved 2026-10-26** — fixed in `backend-cluster/backend-v2`: one call carries at most 1000 entries (`MAX_BULK_ENTRIES`, matching the journal read cap), enforced at the shared zod schemas (`entriesBodySchema`, `deleteSlicesInput` — published as OpenAPI `maxItems`) and asserted in `addBulkEntries` / `deleteMultiSourceSlices` for the GraphQL path, whose arguments arrive unchecked. Refusals name the count, the cap, and the chunking fix; REST schema refusals leave as `VALIDATION_FAILED` per the established REST mapping. Batch delete capped identically. Parity tests refuse 1001 on all three surfaces for both add and delete, commit exactly 1000 on REST, and fail with either layer disabled. Follow-up: `w23/121` (CLI re-pin).

**Prod re-verified it.6366:** `addLedgerEntries` with 1001 notes + `dry_run` → `BAD_USER_INPUT: entries: at most 1000 entries per call; split into several calls`. The batch cap holds live (no writes made).
