## Objective

Accept `meta` on open, close, commodity, price, balance, note, event, document and pad in the REST schema, the GraphQL inputs and the MCP input.

## Context

- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/entries-handler.ts` (about lines 122-210) defines each variant as a strict object
- GraphQL `LedgerOpenInput`, `LedgerCommodityInput` and `LedgerPriceInput` have no `meta` field
- `w1/233` has the repro on the public example ledger

## Steps

1. Add `meta` to each variant on all three surfaces
2. Keep the three descriptions identical through the shared description module

## Files

- backend-cluster/backend-v2/src/features/ledger/api/

## Acceptance criteria

- [x] Each variant accepts string-valued `meta` on REST, GraphQL and MCP

## Out of scope

## Result

`meta` (string values) is accepted on open, close, commodity, price, balance, note, event, document and pad, and on the transaction with the same description, on REST (`directiveMeta()` in `entries-handler.ts`), GraphQL (one `DIRECTIVE_META_FIELD` on each input class) and MCP (which reuses the REST schema). One `DIRECTIVE_META_DESCRIPTION` serves all three. The service types carry it, a non-string value is refused before anything is written for every directive type (`assertStringMeta`), and `buildEntry` puts it on the wire row; the IDL's `DocumentCreate`, the one item that lacked it, gained `meta` and the fava client was regenerated. The pad's twin-key fold rebuilt the entry by hand and dropped `meta`; it now spreads the rest of the entry, so the next field cannot be lost the same way. Tests: `directive meta via %s` in `structured-entry-parity.test.ts` writes each type with meta, leaves the key off when none is sent, and refuses a non-string value, on all three surfaces.
