## Result

Two causes, both fixed. The commit read the moved file's errors as new because the diff keys on file path: `diffBeanCheckErrors`, `toWriteValidation`, `gateFileWrite` and `withPostWriteValidation` take a `renames` path map that carries the `before` errors to the new path. The preview never checked at all, because a dry run changes nothing and the before/after read was always clean: `LedgerWorkflow.renameLedgerFile` hands the files the rename would leave to an optional `onProjectedFiles` hook, and the MCP tool projects bean-check over them with `projectedWriteValidation` (a check that cannot run reads `checked: false`, not clean). REST and GraphQL rename return no validation block, so nothing changes for them. Tests: the differential case, four unit tests for the rename-aware diff, and the existing rename parity suite. Reverting either half fails the differential case.
