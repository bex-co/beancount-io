## Objective

Decide whether the differential runs the real repository service on an in-memory Gitea client with the real engine, or as a replay against the hosted endpoint, and record why.

## Context

- `backend-cluster/ledger/scripts/single-file-repo.ts` is an in-memory Gitea client for one file
- Existing parity tests use fakes under `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/__tests__/`
- A new production replay needs a deploy before it can pass; prefer in-process

## Steps

1. Check what the repository service needs from a fake (multi-file trees, commits)
2. Write the decision and its limits in a `## Harness` section of the milestone README

## Files

- `.pm/w23/m39/README.md`

## Acceptance criteria

- [x] The harness decision is recorded with the reason and what it cannot cover

## Out of scope

- Building the runner; that is t003

## Result

Harness: in-process, through the real MCP registry, the real `LedgerWorkflow` and `LedgerRepoService`, over a fake ledger service that is a stateful file map with a rule-based bean-check (a `BAD` line is an error in any file the include graph from `main.bean` reaches; an include naming no file is an error; globs are followed). Chosen over a hosted replay because a replay needs a deploy before a fix can pass and the hosted ledger has no state a test can reset (and no second stack may be built for it, `.pm/DO_NOT_DO.md`). What it covers: the three file tools and the rename. What it cannot cover: what the real engine decides (balance assertions, lot matching, plugins) and the entry, append and source-slice tools, whose preview and commit run through one ledger-service projection call; those keep their parity suites and a written reason in the registry. Recorded in the header of `preview-commit-differential.test.ts` (the task text said the milestone README; the test header is where the next reader of the harness looks).
