# Bare `SELECT … FROM <table>` (no other clause) fails on all three surfaces

**Severity:** major (every explicit-FROM query without WHERE/GROUP BY/ORDER BY/LIMIT fails; paginated product surfaces are unaffected, which is why it is silent). **Estimate:** 2–4h (find the no-clause query path + regression test). **Owner:** query path below backend-v2 (backend-v2 itself is pre-deploy: m2/m3 signals unchanged) — likely the ledger/engine service. **A1/A2:** agents and CLI users routinely omit LIMIT on single-row or small queries.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

Any `FROM` with no further clause resolves the *table* as a *column*:

| query | MCP | REST | GraphQL |
| --- | --- | --- | --- |
| `SELECT count(*) FROM postings;` | `BAD_USER_INPUT: … column 'postings' not found` | same | same (`queryShellText`) |
| `SELECT date FROM postings;` | `column 'postings' not found` | — | — |
| `SELECT * FROM prices;` | `column 'prices' not found` | — | — |
| `SELECT * FROM commodities;` | `column 'commodities' not found` | — | — |
| `SELECT count(*) FROM close;` | `column 'close' not found` | — | — |
| `SELECT count(*) FROM open;` | `column 'open' not found` | — | — |

Subquery-FROM is unaffected: bare `SELECT * FROM (SELECT payee LIMIT 1);` (no outer clause) works and matches stock byte-for-byte (it.1799) — only a bare table *name* mis-resolves, so the broken path is name resolution, not FROM parsing.

Adding ANY clause fixes it (verified on MCP unless noted):

| query | result |
| --- | --- |
| `SELECT count(*) FROM postings LIMIT 1;` | `34` (also via REST table rows `[[34]]` and GraphQL text) |
| `SELECT date FROM postings LIMIT 2;` | rows |
| `SELECT date FROM postings WHERE date > 2020-01-01;` | rows |
| `SELECT date FROM postings ORDER BY date;` | rows |
| `SELECT count(*) FROM prices LIMIT 5;` (structured) | `[[0]]` |
| `SELECT * FROM prices LIMIT 5;` (structured) | `date/currency/…` schema |
| `SELECT count(*) FROM close LIMIT 5;` | `evaluation error: table 'close' …` (the it.1012 message) |
| `SELECT count(*);` (implicit FROM, no clause) | `34` |

Fixture is byte-identical to the pinned snapshot (2817 B, sha `77c3a591efd3`), so this is not data drift. Failure is deterministic (3/3 reruns), not a routing flake.

## Extended matrix (it.1983–1984): the bare path resolves FROM as a postings *column*

Probing more tables exposed the exact mechanism — and a perverse inversion:

| query | MCP bare | MCP + LIMIT | stock |
| --- | --- | --- | --- |
| `FROM balance` | OK, `0` | `table 'balance' does not exist` | crashes (`NotImplementedError: __bool__`) both forms |
| `FROM journal` | `column 'journal' not found` | `table 'journal' does not exist` | `ParseError` both forms |
| `FROM inventory` | `column 'inventory' not found` | `table 'inventory' does not exist` | `CompilationError: column "inventory" not found` both forms |
| `FROM options` | `column 'options' not found` | `table 'options' does not exist` | same CompilationError both forms |

`balance` is a valid *column* of postings — so it is the one name the bare path resolves at first glance, while every real-table name that is not a postings column errors. That confirms the bare-FROM path never does table resolution at all: it treats the FROM name as a postings column reference. Extended it.1987–1989: the prediction holds for every postings column probed — bare `FROM payee/date/narration/position/flag/account` all "work". The fold is a per-column row filter, SQL-truthiness-like for strings (`FROM payee` → 28 rows ≡ `WHERE payee` → 28 ≡ `WHERE payee IS NOT NULL` → 28; `SELECT * FROM payee` returns postings-shaped rows), but `FROM balance` folds to the EMPTY set (`count(*)` → `0`, `SELECT *` → 0 rows) while `WHERE balance`, `WHERE balance IS NOT NULL`, and `count(balance)` all see 34 — so the fold is not WHERE-equivalent for the inventory-typed column (possibly Python-truthiness or an unbound evaluation dropping every row). `FROM balance` is thus self-contradictory inside MCP (bare → `0`, +LIMIT → table does not exist), and stock gives no ground truth (it crashes on `FROM balance` outright — a stock bug, not ours to file). Caution: postings counts flapped 34↔36 mid-probe (sibling-loop transient per w23/110); every equivalence above was verified inside a self-consistent window, and the row-set diff (`SELECT date, account, position`, bare vs +LIMIT) is byte-identical at 34. Extended it.1993: quoting the table name bypasses the bug — bare `SELECT count(*) FROM "postings";` returns 34 on MCP and stock alike. Only *unquoted* bare table names take the column-fold path.

Note on scope: the with-clause path recognises `postings`, `prices`, `commodities` as tables (`FROM prices LIMIT 5` → `[[0]]`); `close`/`open`/`balance`/`journal`/`inventory`/`options` all answer `table 'X' does not exist` there (verified it.1984–1985). Stock agrees `journal`/`inventory`/`options`/`open` are invalid (both forms fail there too) and crashes on `FROM balance` outright — so the bare-specific regressions vs stock are `postings`/`prices`/`commodities` (stock runs them bare; MCP needs a clause). `FROM close` is different: stock returns 34 postings rows in both forms while MCP errors in both (bare: column error; +LIMIT: table error, unchanged since it.1012) — a pre-existing engine gap, tracked in w23/blocked/022, not this regression. The bare-form message flip for `close` (table error → column error) remains regression evidence for the two-path bug.

## Fix

Make the no-further-clause path resolve FROM exactly like the with-clause path (one planner, no bare-query fast path — or fix the fast path to keep FROM). Add a regression test running the same `SELECT … FROM <table>` with and without LIMIT/WHERE on every table including empty `prices`/`commodities`, asserting identical results modulo row caps.

## Dedupe

New shape: no open note covers FROM-clause resolution. Related: w23/blocked/022 (engine BQL splits — the table-case retraction and LIMIT-workaround pointers live there). Searched: FROM, from postings, column not found; open: m7, 095–108.

### it.3176 — the trigger is specifically `FROM <table>;` (semicolon-terminated, no further clause)
- Omitting the trailing semicolon rescues every bare-FROM query: `SELECT payee FROM postings` (no `;`) → 34 rows; `SELECT count(*) FROM postings` → 1 row; `SELECT * FROM prices` → 0 rows; even a trailing space `SELECT payee FROM postings ` → 34 rows.
- So EOF-terminated `FROM <table>` resolves the table correctly, but `;`-terminated `FROM <table>;` mis-resolves it as a column. The `;` token after a bare table name (with no intervening clause) is what breaks name resolution — consistent with a parser that needs a lookahead token after the table name and chokes specifically on the statement terminator there.
