# MCP's `VALIDATION_FAILED` envelope drops `newLedgerErrors`, which the tool descriptions promise and REST/GraphQL carry

**Severity:** minor (parity). **Estimate:** 20–30 minutes. **Owner:** `backend-cluster/backend-v2`, `envelopeFromThrown` in `src/features/ai-agent/api/mcp-errors.ts`. It copies only `code`, `message`, `hint` and `retryAfter` from a `DomainError`. **A1:** an agent fixing the errors a write would introduce has to parse them out of a sentence, while REST and GraphQL clients get the field.

## Repro (production, 2026-10-22, token pinned to the QA fixture; both writes refused, nothing committed)

`appendLedgerText {text: "2021-01-01 balance Assets:Cash 5 USD\n"}` →

```json
{"ok": false, "error": {"code": "VALIDATION_FAILED",
  "message": "Validation failed for text: appending it would introduce 2 new bean-check errors: Account Assets:Cash was never opened (main.bean:8); Balance failed for Assets:Cash: expected 5 USD, got 0 USD (main.bean:8)",
  "hint": "… Fix the directives, or pass `allowInvalid: true` to record them anyway."}}
```

`addLedgerEntries` with a failing balance gives the same shape: no `newLedgerErrors`. The descriptions of `updateEntrySource`, `deleteEntrySource`, `deleteEntrySources` and the `allowInvalid` argument say "VALIDATION_FAILED with newLedgerErrors". `docs/mcp.md` says "each new error named in `newLedgerErrors`". The unit test (`mcp-errors.test.ts`) states that apps read it from "GraphQL extensions, REST error.metadata".

## Fix

When a `DomainError`'s metadata holds `newLedgerErrors`, add it to the MCP error envelope (`error.newLedgerErrors`) and to the text block. Better, also carry it as an array of `{message, source, code}`, as the success path's `validation.newErrors` already does, so the refusal and an `allowInvalid` success share one shape. Update the output schema. Tests: an append, an add and an entry-source update that would break the ledger each return the field on MCP, matching REST `error.metadata`.

---

**Resolved 2026-10-23** — MCP's `VALIDATION_FAILED` for a write that would break the ledger now carries `error.newLedgerErrors`. It is the same `message (file:line); …` string REST returns in `error.metadata` and GraphQL in its extensions.

Both of MCP's failure paths carry it (`backend-cluster/backend-v2`):

- A thrown `DomainError` goes through `envelopeFromThrown` (`src/features/ai-agent/api/mcp-errors.ts`), which now copies the field from the error's metadata.
- A tool that refuses through `runToolSafely` (`src/features/ai-agent/utils/run-tool.ts`) keeps it as a carrier, and `splitToolFailure` moves it into the envelope rather than leaving it loose at the top level.

The text block already names the errors, since they are in the message.

**The schema.** The published error object (`mcpErrorSchema`, `src/features/ai-agent/tools/types.ts`) had `additionalProperties: false`, and the MCP SDK client validates an error result's `structuredContent` against it. So the field could not simply be emitted, and declaring it costs 1,584 bytes: it is inlined into 44 output schemas, which put `tools/list` at 108,077 bytes against its 106,496 budget ("growing it stays a decision"). Declaring it only on the write tools was not safe either: a tool that did not declare it, such as the bank import's submit, which writes entries too, would fail validation. The error object now admits fields it does not list (`.loose()`), which fits the budget. `docs/mcp.md` documents `newLedgerErrors`, and the schema's comment says why it is not listed. The note's "better" array form (`{message, source, code}`) was not built: the refusal carries only the joined string, the same as REST and GraphQL.

**Tests:**
- `directive-text-parity.test.ts`: an `appendLedgerText` refusal gives MCP `error.newLedgerErrors` equal to REST's `error.metadata.newLedgerErrors`.
- `structured-entry-parity.test.ts` (`addLedgerEntries`) and `source-slice-parity.test.ts` (`updateEntrySource`/`deleteEntrySource`) now assert the field on MCP. Their SDK clients validate it against the published schema.
- `mcp-errors.test.ts`: `envelopeFromThrown` copies it, `runToolSafely` → `splitToolFailure` carries it into the envelope and not into the loose fields, and a refusal without it gains none.

Reverting fails 5 cases, and the unit file no longer compiles.

**Gates:** backend-v2 typecheck, ESLint, Knip, 6913 unit tests, `tools/list` within its budget. `upstream-survival.test.ts` failed as usual (environment-only), and `archive-parity` failed under full-suite load and passes alone. Needs a backend-v2 deploy.
