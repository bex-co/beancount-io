# 139 — Window functions work only with omitted FROM; any explicit FROM fails as "subquery" (it.6146-6148)

## Summary
MCP's window functions (`row_number`, `rank`, `dense_rank` — stock has none, it.4538) run only when no table is named. Omit FROM, or use the table-less scope form (`FROM OPEN ON …`), and windows number rows; name any table — `FROM postings`, quoted `FROM "postings"`, `FROM entries` — and the identical window fails with `Window functions not supported in subquery expressions`, though the query contains no subquery. The error message is doubly wrong: it names a subquery that isn't there, and it refuses a placement (top-level SELECT target) the engine otherwise supports.

## Repro (prod, puncsky/mcp-agent-eval)
- `SELECT row_number() OVER () LIMIT 3;` → `[[1],[2],[3]]`.
- `SELECT payee, row_number() OVER (ORDER BY payee) LIMIT 3;` → rows.
- `SELECT row_number() OVER () FROM postings LIMIT 3;` → `evaluation error: Window functions not supported in subquery expressions`.
- Same with `FROM "postings"`, with `OVER (ORDER BY payee)`, with `rank()`, and with `FROM entries` — all named-table forms fail identically.
- Refined it.6149: `FROM OPEN ON 2020-01-01` + window WORKS (`[[1],[2]]`) — the scope form names no table. Rule is unnamed-vs-named, not bare-vs-explicit.
- Corrects the it.4538 verdict ("No defect in the implemented subset"): the subset has a FROM-form hole. The it.4545-4547 subquery refusal uses this same message, suggesting the engine routes explicit FROM through its subquery path.

## Expected
Named-table FROM behaves like omitted FROM for top-level windows (or all top-level windows are refused with an accurate message — but bare works today, so parity means fixing named, not breaking bare).

## Status
Open (inbox). MCP-engine-side (FROM-form routing into the window evaluator); no stock differential exists.
- Extended it.6150: a derived-table FROM breaks top-level windows too (`SELECT row_number() OVER () FROM (SELECT …) ` → same subquery error). Windows survive only bare and table-less-scope FROM; any table name or derived table routes into the refusing path.
- Parity it.6153: REST refuses the explicit-FROM window identically (same subquery message) — engine-level hole, all surfaces consistent.
- Extended it.6327: other clauses don't affect the hole — bare `SELECT row_number() OVER () WHERE flag = '*' LIMIT 3` works (1,2,3), as does `ORDER BY 1 DESC LIMIT 3` (34,33,32, it.6328). Only the FROM form (named/derived vs bare/scope) routes into the refusing path.
- Extended it.6329: GROUP BY breaks bare windows too, with its own message — `SELECT flag, row_number() OVER () GROUP BY flag LIMIT 5` → `evaluation error: Window function cannot be evaluated in posting context` (vs the named-FROM subquery error). The window evaluator never leaves posting context: named/derived FROM misroutes, GROUP BY never switches. Numbering groups (legal SQL: windows evaluate post-grouping) is unsupported. Control it.6330: DISTINCT does not break bare windows (`SELECT DISTINCT row_number() OVER () LIMIT 5` → 1-5) — only GROUP BY and named/derived FROM refuse.

**Resolved 2026-10-28** — fixed in `backend-cluster/ledger` in two layers. New `dropPostingsFromForWindows` pipeline stage (after unquote, before the terminator) drops a top-level `FROM postings` under a top-level implemented window without GROUP BY: bare and postings return identical rows in identical order under WHERE/ORDER BY/DISTINCT/GROUP BY (verified live, only bad-column error shapes differ — and there the bare form is the accurate one), so named postings windows now number exactly like bare, including OVER-ORDER, star, quoted (via unquote), and any-case spellings. New `windowFromError` engine guard (second in chain) refuses what the stage cannot rescue with the actual cause instead of the bogus subquery error: unimplemented names (`sum() OVER` → "not implemented", matching the engine's own bare message), GROUP BY (replacing the cryptic posting-context error), unpipelined `FROM postings` (advises omitting FROM), and other/derived FROM (names the table; no bare advice since bare would number postings rows, not the table's). Live corrections to the note: quoted `FROM "postings"` works raw (quoted FROMs never leave the default scope — the note's prod failure came from the pipeline's unquote, now rescued downstream) and `SELECT`/`OVER`/function/table names are all case-insensitive. Residuals: entries/derived/GROUP BY windows need upstream engine support (loud refusal meanwhile); paren-wrapped top-level windows stay with the engine.
