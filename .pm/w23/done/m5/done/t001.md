## Findings (2026-10-26)

Reproduced live against the real ledger HTTP server (`http.createServer(buildApp().callback())`, no `maxHeaderSize` override — Node default 16 KiB):

- `GET /shell/o/r/query?query=<N ASCII chars>`: N ≤ 16000 reaches the app (service-layer 500 for the fake ledger — the point is it passes the parser); N ≥ 16384 answers **431 with an empty body**, before Koa/auth/app. Cliff between 16023 and 16407 URL bytes — exactly the production ~16 KB URL-encoded cliff (CJK expands ~3x under `encodeURIComponent`, so it trips at ~1/3 the raw length).
- `POST` with a 100 KB JSON body to the same route reaches the app (405 from the router — no POST route yet): bodies bypass the parser cap, which is header/request-line only.
- Backend-v2 chain: `queryShell` is `GET ...?query=` (`foundation/fava/Api.ts`); the 431 throws `FavaApiError`, unmapped in `error-to-domain.ts` (`default` branch, status < 500) → `InternalServerError("Failed to execute shell query")` → the production 500 with its useless retry hint, on every surface.

**Decision for t002/t003: POST hop.** Add POST shell endpoint(s) taking the query in the JSON body, update the IDL contract, regenerate the client, switch backend-v2 to POST. Keep the GET endpoints (short queries, back-compat). Rejected alternative: raising `maxHeaderSize` — any cap still cliffs, and it widens per-connection parser memory.

No committed test here: the 431 is Node-core behavior, not ours — pinning it would test the platform. Durable regression tests (long query through POST) belong in t002/t003.
