The hosted bean-check disagrees with stock beancount on a few constructs, in both directions, and the customer contract says only that the write gate "bean-checks the projected ledger". I ran 86 constructs (every `bean-check` error class a user is likely to hit plus valid syntax variants) through `appendLedgerText` with `dry_run: true` on the disposable `puncsky/mcp-agent-eval` (production `beancount-mcp 1.0.0`, 2026-11-11) and through stock beancount 3.2.3 `loader.load_string(snapshot + text)`. The valid/invalid verdict matched on 82; the rest, with the hidden one found on a follow-up, are the five below. Everything else agrees, including unbalanced and unopened accounts, closed-account postings, duplicate opens, failed balances, currency constraints, pads, missing documents, lot reduction and ambiguous lots, negative cost, bad dates, numbers, accounts and currencies, tolerances and the `option`/`plugin`/`include`/`pushtag` refusals.

The engine accepts what stock refuses (checked again through `updateLedgerFiles` with whole-file `content` and `dry_run: true`, which bypasses the append tool, so it is the engine): (1) `2026-11-12 open Assets:Stock ABC STRICT`, an unquoted booking method, is `valid: true`; stock says `ParserSyntaxError: syntax error, unexpected CURRENCY` (the grammar wants `"STRICT"`); (2) two `commodity ZZZ` directives, even on different dates, are valid; stock says `ValidationError: Duplicate commodity directives for 'ZZZ'`; (3) the same metadata key twice on one transaction, or on one posting, is valid; stock says `ParserError: Duplicate metadata field on entry` and `Duplicate posting metadata field`. So `checkLedger` can report 0 errors for a ledger whose `bea check` or Fava load fails locally.

The other direction, in the append tool only: `appendLedgerText` refuses `2026/11/12 event "x" "y"` (a slash date, which stock accepts) and a transaction whose narration spans two lines (a legal multi-line string) with `BAD_USER_INPUT` "line N: not a Beancount directive: …" (`backend-v2/src/features/ledger/utils/directive-text.ts:269`; the date test at `:186` is `^\d{4}-\d{2}-\d{2}`, and each line is classified alone), while the same text through `updateLedgerFiles` is valid and stock loads it. `docs/mcp.md` says only that it "refuses anything that is not" a directive, so an agent gets no hint that the check is a line classifier narrower than the grammar.

Cause: (1)–(3) are the engine (`@rustledger/wasm` 0.24.0, `backend-cluster/ledger/package.json:32`), cause not traced further; no ADR or README lists them as known differences. Fix: decide each of the five (report the error, mirror stock, or document the difference next to the ledger README's other known gaps), and add a stock-versus-hosted case table like these 86 to a gate; `yarn verify:rustledger` is the natural home for the engine half, and the milestone-sized version is the release gate m20 and m41 gave the query and report engines. The small first step is documenting the five and refusing (1)–(3) at the write gate where the engine does not.
