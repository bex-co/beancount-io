Finding from qa-find-bugs-mcp, 2026-11-02.

**The ledger search `private` query parameter is a documented but effectively no-op filter, confusingly overlapping with the real exclusive filter `isPrivate`.**

Severity: minor (confusing API surface, no data leak; read-only reproduction, no write).

Env: `https://beancount.io`, `serverInfo` `beancount-mcp` 1.0.0, protocol `2025-11-25`, OAuth-less `bcio_` API key on the QA account's own ledgers.

Repro (helper: `node .agents/skills/qa-shared/scripts/qa-mcp.mjs read "<uri>"`):

1. `beancount://catalog/ledgers/search?private=true&limit=10` and `?private=false&limit=10` return the identical list of public `open_ledger/*` demo repos (`"private":false` on every row) — passing `true` vs `false` changes nothing observable.
2. `?isPrivate=true&limit=10` correctly returns only the caller's own private ledgers, all `"private":true`.
3. Every other param on this same endpoint is validated or has a visible effect (`sort`, `mode`, `groupBy`, `shape`, `template`, `archived`) — `private` is the one outlier.

Control: REST `GET /api-gateway/v1/ledgers/search?private=true&limit=5` reproduces the same result byte-for-byte, so this is a shared backend-v2/ledger bug, not MCP-specific.

Root cause (traced, not guessed): `private` is not typo'd, shadowed, or dropped — it is parsed and forwarded unchanged through every layer (`backend-cluster/backend-v2/src/features/ledger/api/rest/v1/catalog-reads.ts:20-21`, reused by the MCP resource at `src/features/ai-agent/api/mcp-resources.ts:783-796`, `src/features/ledger/workflow/ledger-workflow.ts:1741-1742`, the generated client at `src/foundation/fava/Api.ts:4469-4510`) down to the handler that actually builds the Gitea filter: `backend-cluster/ledger/src/api/ledgers.ts:234-249`, which spreads both into `repoSearch` (`backend-cluster/ledger/src/features/gitea/client/gitea-api.ts:5602-5659`). Gitea's own upstream semantics explain the symptom: `private` is a weak *inclusion* toggle ("include private repos this user can see alongside public matches", defaults to `true`), while `is_private`/`isPrivate` is the real *exclusive* filter. `private=true` changes nothing because inclusion already defaults to true; `private=false` only removes private rows, invisible whenever the query matched no private rows for that caller.

Fix: in `backend-cluster/ledger/src/api/ledgers.ts`'s search handler (lines 234-249), either map `private` onto the same `is_private` Gitea parameter `isPrivate` already uses, or deprecate/remove the raw `private` passthrough and document `isPrivate` as the only filter, across REST/GraphQL/MCP per ADR 0008. `docs/mcp.md:987` lists both params with no semantic distinction and should be updated either way. Add a test next to `catalog-parity.test.ts` asserting `private=false` actually excludes private ledgers from a query where the caller has both public and private matches.

Owner: `backend-cluster/ledger` (handler) + `backend-cluster/backend-v2` (shared schema/docs). Blast radius: REST, GraphQL, and MCP all share the `searchLedgers` workflow call, confirmed by `catalog-parity.test.ts` asserting all three pass `private`/`isPrivate` through unchanged.

Estimate: 30-45 minutes. Unverified: GraphQL surface not independently re-tested this round (relying on the cited parity test); whether any caller currently relies on today's weak-inclusion `private` behavior.

---

**Resolved 2026-11-01** — the premise did not hold; documented instead of changed. On production, with a query that matches the caller's private ledgers (`q=mcp-agent-eval`): the default and `private=true` return both private ledgers, `private=false` returns none, `isPrivate=true` returns both, `isPrivate=false` returns none. So `private` is a working inclusion toggle (Gitea's `private`, default true) and `isPrivate` the exclusive filter; the note's lists looked identical because a broad query fills its page with public ledgers first. `backend-cluster/backend-v2/docs/mcp.md` now states the difference for REST, GraphQL and MCP. No schema or generated-client change, so no OpenAPI or CLI client drift.
