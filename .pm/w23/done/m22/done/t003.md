## Objective

Reuse the case list to probe the REST routes and GraphQL operations that accept the same parameters, confirming one boundary guards all three surfaces.

## Context

- Route-level parsers may reject earlier with their own code; the assertion is `BAD_USER_INPUT`/400, never a 5xx.

## Steps

1. Map tool parameters to their REST and GraphQL spellings.
2. Run the cases through the parity fixtures.

## Files

- `backend-cluster/backend-v2/src/features/ai-agent/api/__tests__/nul-contract.test.ts`

## Acceptance criteria

- [ ] No surface answers 5xx for a NUL in a covered parameter.
- [ ] Surface-specific exceptions are listed with a reason.

## Out of scope

- Cloudflare-level filtering of path segments (already a 400).

## Resolution

REST and GraphQL now refuse U+0000 at their own single boundary, with the same exempt file-content paths as MCP (`src/shared/nul-exempt-paths.ts`, shared by all three): `validateRequest` (`server/rest/validation-middleware.ts`) checks path segments, query values and the body before schema parsing, and `graphqlNulMiddleware` (`server/graphql/nul-middleware.ts`, registered after the rate limiter) checks every root field's arguments. Both answer `BAD_USER_INPUT` naming the argument and never reach a handler or resolver. `src/server/rest/__tests__/nul-boundary.test.ts` covers path, query, query arrays, body strings, nested bodies, body keys, the file-content exemption (a content-named query parameter is not exempt), clean requests, and the GraphQL root-versus-nested rule. The parity-fixture schemas build their own middleware stacks, so the GraphQL guard is proved by the middleware test rather than per mutation.
