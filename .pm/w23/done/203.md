# 203 — Multi-directive text writes double the blank separator: `appendLedgerText` / `directives/text` commit two blank lines between entries the caller separated with one

**Severity:** minor (ledger hygiene; no data change, `checkLedger` stays clean). **Estimate:** 30–40 minutes with tests. **Owner:** `backend-cluster/backend-v2` — `insertDirectives` in `src/features/ledger/utils/directive-text.ts`, shared by REST `POST …/directives/text`, GraphQL and MCP `appendLedgerText` (dry-run previews and real commits). **A1:** agents write several entries in one call, separated by a blank line as every beancount style guide shows.

Distinct from w23/055 (delete left separators; resolved): that note says the delete now mirrors "the same normalization the append path applies when it inserts" — but the append path only normalizes the single-directive case.

## Repro (production, 2026-10-30, API key pinned to the disposable QA ledger; real commit, restored byte-for-byte to blob `f1a0b83`)

`appendLedgerText` with this text (one blank line between the entries):

```
2026-10-01 * "qa" "one"
  Assets:Cash  1.00 USD
  Expenses:Food:Groceries  -1.00 USD

2026-10-02 * "qa" "two"
  Assets:Cash  1.00 USD
  Expenses:Food:Groceries  -1.00 USD
```

- Committed bytes (read back with `readLedgerFiles`): `…-1.00 USD\n\n\n2026-10-02 * "qa" "two"…` — **two** blank lines between the entries.
- Dry-run diff on MCP and the REST `directives/text` route (`dryRun: true`) show the identical doubled `+`/`+` pair, so all surfaces agree on the defect.
- Three blank lines supplied → four committed (the supplied blanks survive and one more is added).
- Out-of-order pair (`2026-12-01` first, `2026-02-01` second) inserts the earlier entry mid-file as `…Equity:Opening-Balances\n\n\n2026-02-01 …` — the same extra blank before it.
- Control: a single directive, or a pair with no blank line between them, gets exactly one separator.
- The reported `wrote[].line` values are consistent with the doubled blank (89 and 94), so entry hashes and line numbers are right; only the whitespace is off.

## Root cause

`insertDirectives` (`directive-text.ts`, loop at ~345–360) adds its own separator — `prefix = at > 0 && !isBlank(working[at - 1]) ? [""] : []` — but each later directive's `block` already carries the blank line that separated it in the caller's text (the loop's own comment says so at ~357). The prefix check looks only at the file, never at `block[0]`, so a block that starts with a blank line gets the prefix as well. It also keeps any number of leading blanks.

## Fix

Normalize each `block` before splicing: drop its leading blank lines, then let the single `prefix` rule supply exactly one separator (and keep the trailing-blank handling that `content.replace(/\n+$/, "")` already does). Adjust the `inserted[].line` math, which currently reads `Math.max(head, 0)` to skip the leading blank. Tests: pair separated by 1 and by 3 blank lines appended at the end; out-of-order pair inserted mid-file; first-directive-at-top; CRLF input; the line numbers in `wrote`/`entryHashes` still point at each header.

Cross-surface: one shared function, so REST/GraphQL/MCP all change together; no adapter work, but add one parity assertion that all three previews match.

## Dedupe

Searched `.pm/**` for blank/separator/insertDirectives: w23/055 (delete side, resolved), w23/060 (reported line of a later directive carrying its blank — mechanism noted, whitespace not), w23/076 (heading placement). None covers the doubled separator.

**Resolved 2026-10-30** — `insertDirectives` now drops the leading blank lines a later directive carries, so the single prefix is the only separator (one blank between entries whatever gap the caller used; reported lines still point at each header). Tests in `directive-text.test.ts` (gaps of 0/1/3, out-of-order pair, CRLF) fail without the fix (`backend-v2`).

**Verified in production 2026-10-31 (MCP QA loop, after the redeploy carrying `2fb54f922`).** Dry-run diffs for two entries separated by one, three and no blank lines, by CRLF input, and by an out-of-order pair (earlier entry lands mid-file, later one at the end) each add exactly one blank line between entries and never two. A real two-entry `appendLedgerText` read back `…-1.00 USD\n\n2026-10-02 …`. A single entry, a leading-blank-lines text and an out-of-order insert are unchanged. `main.bean` restored byte-for-byte afterwards.
