# 205 — `readLedgerFiles`, `updateLedgerFiles` and `deleteLedgerFiles` fail with a false `NOT_FOUND` when a call names more than 30 existing files

**Severity:** major (a documented batch operation breaks at an undocumented size, and the error accuses a file that exists). **Estimate:** 30–45 minutes with tests. **Owner:** `backend-cluster/ledger` — `POST /ledgers/{owner}/{repo}/files-content` in `src/api/files.ts` (~L257–285), which hands the whole path list to the repository host's batched file-contents call and treats whatever does not come back as missing; consumed by backend-v2's file tools. **A1:** agents reading, rewriting or removing a folder of statements in one call (a 40-file import folder is ordinary).

## Repro (production, 2026-10-30, API key pinned to the disposable QA ledger; all 60 probe files deleted afterwards, `main.bean` untouched at blob `f1a0b83`)

Setup: `createLedgerFiles` with 60 one-line files `qa-20261030-many/f0.bean … f59.bean` (committed, "Committed 60 change(s)"). Every one reads fine on its own, as a resource (`beancount://…/files/qa-20261030-many/f45.bean`) and over REST `GET …/files/…/f45.bean`.

| call | files named | result |
| --- | --- | --- |
| `readLedgerFiles` | `f0…f29` (30) | ok, 30 returned |
| `readLedgerFiles` | `f0…f30` (31) | `NOT_FOUND` "file not found: qa-20261030-many/f30.bean" |
| `readLedgerFiles` | `f0…f59` (60) | same, naming `f30` |
| `deleteLedgerFiles` (dry run and real) | `f0…f29` / `f30…f59` (30 each) | ok |
| `deleteLedgerFiles` (dry run and real) | `f0…f30` (31) … `f0…f59` (60) | `NOT_FOUND` "File with ID 'qa-20261030-many/f30.bean' not found" |
| `deleteLedgerFiles` dry run | `f29…f59` (31, a different window) | `NOT_FOUND` naming `f59`, the 31st path |
| `updateLedgerFiles` dry run | 30 exact-text edits / 31 / 45 whole-file replacements | 30 ok; 31 and 45 `NOT_FOUND` naming `f30` |

The boundary is the count, not the folder or the file: any 30 of the files work, a window of 31 fails on its 31st path. The failures return in 0.4–0.6 s, so no commit is attempted and nothing is written.

## Root cause

`files-content` passes `{ files }` straight to `client.repos.repoGetFileContentsPost` and then does `items.filter(item => item !== null)`. The repository host answers a batched file-contents request with at most 30 entries (its default page size; the host's setting is unverified from here), and the ledger service has no way to tell "truncated" from "absent". backend-v2 then reports the first path with no result as `NOT_FOUND`. The `"at most N"` guards elsewhere (the 50-file projection cap, 50 per page) never fire first, and `docs/mcp.md` states no file-count cap for these tools.

## Fix

In `files-content`, request the paths in chunks of at most 30 (or the host's documented maximum) and concatenate in input order; or compare the returned count with the requested count and refuse with a precise `BAD_USER_INPUT` "at most 30 files per call" before any lookup. Chunking is the better behavior (the docs promise no count cap, and w23/m15 file-write gating already walks multi-file batches). Add the same bound or chunking to any other caller of `repoGetFileContentsPost`. Tests: 30, 31, 60 existing files through read, update (edits and whole content) and delete, preview and commit; a genuinely missing path in the middle of a 60-file batch still names that path, not the 31st.

Cross-surface: the REST file routes take one path, so only MCP's multi-file tools and any REST/GraphQL multi-file route that calls `files-content` are affected; add one parity assertion for every surface that exposes it.

## Dedupe

Searched `.pm/**` for files-content, `repoGetFileContentsPost`, "31st", "more than 30 files" and readLedgerFiles batch limits. Nothing matches; w23/028 (same path twice in one call) and w23/074 (batch body-size hop) are different mechanisms.

---

**Resolved 2026-10-30** — `files-content` now looks paths up in chunks of 30 (the host's per-request cap) and concatenates in input order, so read/update/delete of any count work; a genuinely missing path is still the one omitted. Tests in `files-large.test.ts` (`backend-cluster/ledger`).

**Verified in production 2026-10-31 (MCP QA loop, after the redeploy carrying `843527a86`).** With 60 files in one folder: `readLedgerFiles` of 31, 45 and 60 paths returns every file; `updateLedgerFiles` previews 31 edits and 60 whole-file replacements; `deleteLedgerFiles` previews 31 and 60, and a real 60-file delete in one call commits. A genuinely missing path is still named exactly, at position 5, 33, 35 and 44 of 40–45-path batches, for both read and delete.
