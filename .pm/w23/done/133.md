# 133 — Integer handling has a dead zone at 2^53..i64::MAX, silent overflow NULL, and a bogus position-0 error past Decimal::MAX (it.5227-5235)

## Summary
MCP integer literals fall into four regimes, two of them broken. Values ≤ 2^53-1 work; values from 2^53 through i64::MAX hard-error with `can't be represented as a JavaScript number` even though they fit i64 exactly; values from i64::MAX+1 through rust-decimal MAX (79228162514264337593543950335) work again (string-rendered); anything larger fails with a bogus `syntax error at position 0: unexpected token 'SELECT'`. Separately, integer arithmetic that overflows (10^20 * 10^20 = 10^40) silently yields NULL instead of erroring. Stock beanquery 0.2.0 computes every cell exactly (arbitrary-precision ints).

## Repro (prod, puncsky/mcp-agent-eval; stock = beanquery 0.2.0 on the byte-identical fixture)
- `SELECT 9007199254740991` → MCP `[[9007199254740991]]` (it.5234).
- `SELECT 9007199254740992` / `...993` → MCP `Error: ... can't be represented as a JavaScript number`; stock exact (it.5234).
- `SELECT 9223372036854775807` → MCP same JS-number error; stock exact (it.5232-5233).
- `SELECT 9223372036854775808` → MCP `[['9223372036854775808']]` — works again past i64::MAX (it.5233). Two-column form errors on the i64 cell the same way (it.5232).
- `SELECT 79228162514264337593543950335` (Decimal::MAX) → MCP string OK; `...336` (MAX+1) → MCP `syntax error at position 0: unexpected token 'SELECT'`; stock exact on both (it.5235). A 31-digit literal fails the same way (it.5231).
- `SELECT 100000000000000000000 * 100000000000000000000` → MCP `[['']]` (silent NULL); stock exact `10^40` (it.5228). The `99999999999999999999999 + 1` cell agrees.
- Routing is by magnitude: negatives mirror — `-9007199254740992` and `-9223372036854775807` error (it.5237, it.5239) — but `-9223372036854775808` (i64::MIN, magnitude 2^63 overflows i64) escapes to the decimal path and works, as does `-9223372036854775809` (it.5238). So the dead zone is magnitudes in (2^53-1, i64::MAX] on both signs.
- The hole is in result serialization, not parsing: `int('9007199254740992')` parses (i64) then fails render with the same JS-number error (it.5242), while `int('9223372036854775808')` fails earlier at parse (`cannot parse ... as integer`, it.5241) — `int()` is i64-capped where stock `int()` is unbounded. Literals past i64 escape only because the decimal path string-renders. `decimal('9223372036854775808')` agrees past-i64 on both (it.5245) — the decimal render path is the fix template; `number(str)` is rejected on both sides (it.5244, agreement). The hole is literal-only: computed `4503599627370496 * 2` (= 2^53, the exact failing literal) string-renders fine on MCP (it.5247) — arithmetic results take the decimal render path while literals take the JS-number path. The text `runBqlQuery` tool fails identically on the 2^53 literal (it.5249) — the hole sits below both MCP query tools. REST `POST /v1/ledgers/{owner}/{name}/query` (it.5557) and GraphQL `queryShellText` (it.5558-5561) fail with the identical JS-number error — the dead zone is service-wide, below all three API surfaces.
- Overflow boundary is Decimal::MAX, not i64: computed `4611686018427387904 * 2` (= 2^63) works (it.5251), but `Decimal::MAX + 1` and `Decimal::MAX * 2` both silent-NULL on MCP while exact on stock (it.5252). Underflow mirrors: `Decimal::MIN - 1` silent-NULLs on MCP, exact on stock (it.5254). REST parity: the 10^40 overflow silent-NULLs identically over REST (it.5563).
- Predicates escape the hole: `WHERE number = 9007199254740992` evaluates fine on MCP (count `0`, no JS-number error, it.5256) — only result-set serialization of literals is holed. (Stock returns zero rows for the empty count — the covered it.2296 empty-set family, not this note.)
- Read-back: `SELECT 99999999999999999999999` → MCP string OK, stock exact (it.5227).

## Expected
No dead zone: every value that fits i64 (and ideally every value up to Decimal::MAX) should evaluate — route through the same decimal/bigint path that already serves i64::MAX+1. Overflow of integer arithmetic should error loudly, never silent-NULL. Out-of-range literals past Decimal::MAX should report range, not a position-0 syntax error pointing at `SELECT`.

## Status
Open (inbox). MCP-side (literal routing through a JS-number path + silent overflow + misreported parse failure), not an upstream divergence — stock is exact in every cell.
- Extended it.6339: literal underflow mirrors — `SELECT -79228162514264337593543950336` (Decimal::MIN-1) → same bogus `syntax error at position 0: unexpected token 'SELECT'` on MCP, exact on stock. The misreported range failure covers both signs.
- Extended it.6340: past-MAX literals in predicates misreport differently — `WHERE number = ±79228162514264337593543950336` → `syntax error at position 43: found '=' expected identifier…` on MCP (both signs; small `-5` works, so magnitude is the trigger), while stock returns empty counts (it.2296 family). Three misreported shapes for one range failure: position-0 in SELECT lists, `found '='` in predicates, silent-NULL for computed overflow.
- Extended it.6341-6342 (fourth member — LIMIT truncation): `LIMIT` keeps only the low 32 bits. `LIMIT 9007199254740992` (2^53) → 0 rows, `LIMIT 2^53+1` → 1 row, `LIMIT 4294967296` (2^32) → 0 rows, `LIMIT 2^32+5` → 5 rows on MCP; stock returns all 34 for every one. Silent wrong row counts for any LIMIT ≥ 2^32 — an agent paging with a huge LIMIT gets an empty or short page with `truncated: false`. Control it.6343: `LIMIT 2^31`/`2^31+5` return all 34 (correct) — the truncation is unsigned low-32, biting only at ≥ 2^32. Control it.6344: negative `LIMIT -1` is a syntax error on both (agreement). Parity it.6345-6346: REST `POST …/query` and GraphQL `queryShell` truncate identically (`LIMIT 2^32+5` → 5 rows) — full MCP=REST=GQL triple, engine-level.
- Extended it.6347: past-MAX `LIMIT` is token-rejected — `LIMIT 79228162514264337593543950336` → `syntax error at position 33: unexpected token '79228…'`. LIMIT routing by magnitude (bisected it.6348-6350): 0..i64::MAX lexes (`LIMIT 9223372036854775807` → 34 rows), > i64::MAX token-rejected (`…808`, u64::MAX, Decimal::MAX all `unexpected token`). Within the lexed band, ≥ 2^32 silent-u32-truncates. So LIMIT has BOTH a cap (i64::MAX) and a truncation (u32) — stock returns all rows in every cell.

**Resolved 2026-10-28** — fixed in `backend-cluster/ledger` in two layers, verified against the live engine and a stock beanquery 0.2.0 oracle run (dead-zone/MAX literals exact, MAX+5-5 exact, LIMIT 2^32 all rows, `2.5e3` a parse error both sides). New `routeIntegerLiterals` pipeline stage (terminator → rescue, comments already stripped): dead-zone bare literals `[2^53, i64::MAX]` become `decimal('<digits>')` (sign stays in place; decimals, quoted digits, identifier-adjacent digits, and GROUP/ORDER BY bare ordinals exempt — a huge ordinal stays a loud out-of-range error), `int()` over a dead-zone string/bare argument becomes `decimal('<signed>')` (`+` dropped as identity, `-` rides inside; past-i64 `int()` already fails loud with an accurate parse message), and unsigned `LIMIT ≥ 2^32` caps at i32::MAX 2147483647 (lexable, untruncated, past any real row count; negative/fractional LIMITs stay for the engine, which rejects both loudly). New `integerOverflowError` guard heads the engine chain: LIMIT ≥ 2^32 refuses as a backstop for unpipelined callers (raw LIMIT 2^32 answers zero rows silently; past i64::MAX token-rejects — bisected boundary confirmed live), past-MAX int/decimal literals refuse with the range (MAX+0.5-style fractions included), and constant `+`/`-`/`*` runs refuse when any BigInt intermediate in standard precedence exceeds ±MAX (decimals blanked first so `0.5 * <huge>` can't false-fire; division shapes, identifiers, and bare dates abstain). Out of scope by probe: non-constant (column/aggregate) overflow stays silent-NULL with no engine signal (upstream-only); `int(int(dead-zone))` still throws (single-pass); 30-significant-digit decimals below MAX round silently (filed as followup w23/160). Type note: rescued cells render as decimal strings where stock renders ints — the value-exact tradeoff the note's Expected endorses. Pinned by 66 rewrite + 51 guard unit tests (break-checked: 7+7+9 fail with the fix reverted) and live pins (4 raw load-bearing checks incl. the throw, int() rescue, predicate `[[0]]` parity, MAX control, cap-vs-uncapped row equality, 3 refusals, small-value controls). Full ledger gates green (169 suites / 2401 tests, typecheck, lint, build, live verify).
