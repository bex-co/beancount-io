## Result

Gap table, probed in-process on a real socket with the real route (`@koa/cors` in front, as `start-server.ts` has it) on 2026-11-08, against the MCP Streamable HTTP transport rules:

| Row | Observed | Spec / expectation | Verdict |
| --- | --- | --- | --- |
| `Accept` missing or lacking `application/json` or `text/event-stream` | refused by the transport (pinned by `mcp-request-envelope.test.ts`) | 406 | covered |
| `Content-Type` absent / `text/plain` / duplicated | 415 (pinned, same file) | 415 | covered |
| malformed JSON, empty body | `-32700` parse error (pinned) | `-32700` | covered |
| empty batch `[]`, invalid batch member | `-32600` (w23/213, pinned) | `-32600` | covered |

| `initialize` with an unsupported `protocolVersion` | 200, negotiates `2025-11-25` | server answers its latest supported version | ok, not pinned |
| `initialize` carrying an unsupported `MCP-Protocol-Version` header | 200 | the header applies after initialization | ok, not pinned |
| a JSON-RPC response or notification POSTed | 202 with no body | 202 | ok, not pinned |
| unknown method | 200 SSE with `-32601` | `-32601` | ok, not pinned |

| cross-origin 401 | `WWW-Authenticate` is set but **not** in `Access-Control-Expose-Headers` | a browser client must read `WWW-Authenticate` for its `resource_metadata` pointer | **gap** |

One gap: `start-server.ts` exposes only `PAGE_RESPONSE_HEADERS` (w23/m28), so cross-origin browser JavaScript cannot read `WWW-Authenticate` and cannot discover where to sign in. t003 fixes it; the four "ok, not pinned" rows get tests there too. HEAD and `OPTIONS` are covered by t001.
