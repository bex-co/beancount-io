# 194 — `runBqlQuery` text drops trailing all-blank row lines (`3 rows`, zero row lines)

**Severity:** moderate (silent data loss on the text surface; structured/REST/GQL correct).
**Estimate:** sub-hour (trim the final newline, not trailing blank rows). **Owner:**
backend-v2 (`mcp-result-text.ts`). **A1:** text-only agents reading query results.

`renderBqlTable` applies `table.trimEnd()`, which eats trailing
whitespace-only row lines along with the final newline:

- `SELECT payee FROM postings ORDER BY upper(payee) LIMIT 3;` → text
  `'3 rows\npayee\n-----'` — the header claims 3 rows but renders none.
- Interior blank rows survive (`ORDER BY payee LIMIT 8` shows 6 blank lines
  then `ACME CORP` × 2) — only TRAILING all-blank lines vanish, so the
  visible line count disagrees with the claimed count by the trailing-blank
  run length.
- Every other surface is correct: `runBqlQueryStructured` text carries the
  JSON payload with all 3 rows; REST `POST …/query` returns the rows;
  GraphQL `queryShellText { text }` returns
  `"payee\n-----\n     \n     \n     \n"` with blank lines intact.
- Stock renders the blank row lines (rows agree); its own all-blank-column
  quirk is header truncation (`payee`→`p`), tracked separately at
  022:it.6361 — not this defect.
- Root cause: `backend-cluster/backend-v2/src/features/ai-agent/api/mcp-result-text.ts:75`
  (`const readable = table.trimEnd();`) — the trim cannot distinguish
  padding blank lines (data) from trailing whitespace (noise).
- Fix: strip only the final newline (or trailing newlines), preserving
  blank row lines; pin with an all-blank-rows query asserting visible row
  lines equal the claimed count.
- QA ledger untouched (read-only probes; byte-identical + stock-clean re-verified
  this loop: blob f1a0b83c, SHA-256 77c3a591, 2817 B).
