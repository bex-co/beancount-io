# Entry-source tools mark `entryHash` optional but refuse calls without it, on all three surfaces

**Severity:** minor (the refusal names the missing arg, so agents recover in one retry; still, every schema lies about required-ness). **Estimate:** 30–60 min (mark required in three schemas + OpenAPI/GraphQL regen + test). **Owner:** `backend-cluster/backend-v2`, source-slice handlers. **A1/A2:** agents build calls from `tools/list` / OpenAPI / the GraphQL schema and pass only the documented-required `sha256sum` first.

`deleteEntrySource`, `deleteEntrySources` (per entry), and `updateEntrySource` publish `entryHash`/`entry_hash` as optional and `sha256sum` as required — but every handler calls `resolveEntryHash` first, which throws unless one hash spelling is present:

- MCP `tools/list`: `deleteEntrySource required: ['sha256sum']`, `updateEntrySource required: ['sha256sum', 'newContent']` (live, prod).
- REST `source-slice-handler.ts:17-22`: `entryHash: z.string().optional()`, `sha256sum: z.string()`.
- GraphQL `ledger-journal-resolver.mutation.ts:25,92,156`: `entryHash?: string` on all three inputs.
- Runtime, all three: `resolveEntryHash` (`ledger/utils/entry-hash-alias.ts:24-30`) throws `BAD_USER_INPUT: entryHash is required…` — MCP `mcp-source-slices.ts:130,163,194`, REST `source-slice-handler.ts:107,135,165`, GraphQL `ledger-journal-resolver.mutation.ts:239` (+delete-many/update equivalents).

Live repro (prod, QA ledger `puncsky/mcp-agent-eval`, no mutation — dry-runs and refused calls only):

- `call deleteEntrySource {"ledger":"…","sha256sum":"<file sha>"}` → `BAD_USER_INPUT: entryHash is required — the entry_hash list output returns works too.` (worker1 it.182; two further attempts with only one identifier each also failed before the both-identifiers call succeeded)
- `call updateEntrySource {"…","sha256sum":"<64 hex>","newContent":"…","dry_run":true}` → same `BAD_USER_INPUT`
- `call deleteEntrySources {"…","entries":[{"sha256sum":"<64 hex>"}],"dry_run":true}` → same `BAD_USER_INPUT`
- REST `PUT /api-gateway/v1/ledgers/puncsky/mcp-agent-eval/entry-source` `{"sha256sum":"…","newContent":"…","dryRun":true}` → `{"ok":false,"error":{"code":"BAD_USER_INPUT","message":"entryHash is required — …"}}`
- GraphQL `mutation { deleteLedgerEntrySourceSlice(ledgerId:"…", input:{sha256sum:"…",dryRun:true}) { message dryRun } }` → `errors:[{message:"entryHash is required — …", extensions:{code:"BAD_USER_INPUT"}}]`

Fix direction: mark `entryHash` required in the MCP zod schemas, the REST zod schemas, and the GraphQL inputs (keeping the `entry_hash` alias), and regenerate OpenAPI. Alternatively make the handlers accept `sha256sum`-only — but the per-entry `sha256sum` (from `getEntryContext`) is the concurrency token, not the identity, so required-ness is the honest contract.

Dedupe: sibling theme to w23/107 (resource templates advertising `{?…}` params as optional), but a different surface — tool/input schemas, not resource URIs. Searched: "entryHash is required", schema optional/required; open: m6-ish leftovers, 140–171.

Strengthening (worker1 it.205): the tools' own prose already admits the requirement — `deleteEntrySource`/`updateEntrySource` descriptions say "addressed by the entry_hash … (as entryHash or entry_hash) and sha256sum" (`mcp-tools.ts`), so only the machine-readable `required` list disagrees. Pattern-sibling w23/173 extends the same lie to the bank-id and file-message alias families (MCP-only there).
