# Concurrent QA loops share `puncsky/mcp-agent-eval` with no coordination

**Severity:** minor (no product bug — the ledger faithfully stores what was written; but loops silently invalidate each other's count/file baselines). **Estimate:** 1–2h (per-loop ledger or a reservation note) + skill-doc line. **Owner:** QA process (`.agents/skills/qa-*` + whoever runs loops). **A1/A2:** any loop asserting entry counts or fixture bytes.

## Observation (production, 2026-10-26)

Mid-run, this loop's `listLedgerEntries` total moved 29 → 30 and `main.bean` grew 2817 → 2869 bytes. Diff of the live file vs the pinned snapshot:

```
87a88,90
>
> 2026-10-25 open Assets:Qa-20261025-RoundTrip-1440
```

`Qa-20261025-RoundTrip-1440` is another QA loop's round-trip probe (this loop's own writes use different names, and it has been read-only for hundreds of iterations) — left untouched, as deleting a sibling loop's mid-flight entry could break its verification. The live file still `bean-check`s clean and postings stay 34 on both engines, so only entry-count/file-byte baselines shifted.

Extended it.1884: with `main.bean` byte-identical to the snapshot, `listLedgerEntries` total flapped 29 → 30 → 29 within one minute (offset-29 page empty throughout; 5/5 re-polls stable at 29) — consistent with the sibling loop adding and removing a round-trip entry between two QA reads. Count baselines cannot be trusted even minute-to-minute on the shared ledger.

## Fix

Pick one: (a) one ledger per loop (`mcp-agent-eval`, `dashboard-agent-eval`, …) with the skill docs naming each loop's ledger; (b) a short-lived reservation note (known path + TTL) a loop writes before committing probes; or (c) document that count/byte baselines must be re-pinned per comparison, never assumed stable. (a) is the real fix; this loop now keeps a live-synced stock baseline (`.tmp/qa-20261025/main-bean.live`) alongside the pinned snapshot and re-pins on mismatch.
