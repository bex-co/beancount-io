## Objective

Close the confirmed occurrence-ambiguity hole (t001 experiment 3): when overlapped updates address one of several identical entries, the loser must fail with `CONFLICT` — never silently edit the surviving twin and report `OK`. Unique-entry overlap already fences honestly (t001 experiment 2); pin that with regression tests too.

## Context

- Fix point (t001): `relocateSlice` (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:146`) matches by (`sha256sum`, `localOccurrence`) without verifying entry identity. After locating the sha-matched block in fresh content, re-resolve its entry ID at that span and require it to equal the addressed entry (`SliceTarget.base` already carries it); on mismatch throw `ConflictError` like the changed-since-loaded case. Deletes share `relocateSlice` — the same hole and the same fix cover `makeDeleteTransform`.
- The fence must hold across processes: two racers in true overlap, not just two awaits in one event loop.
- The single-entry 1→2/1→0 production counts are NOT reproducible on main (t001 impossibility argument); they need prod evidence (deployed revision + Gitea log, same owner ask as w23/072), not more fencing here.

## Steps

1. Verify entry identity at relocate for replace and delete transforms.
2. Add durable race regression tests with a fake Gitea (production-like CAS: stale blob SHA → unrecognized 500): unique-entry overlap → 1 `OK` + 1 `Conflict`, single winner-content entry, repeated runs; identical-entry overlap → never a silent wrong-entry edit.
3. Run the ledger package gates plus backend-v2's (both packages' scoped `AGENTS.md`).
