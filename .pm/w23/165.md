# 165 — BQL refuses date arithmetic stock supports (`date ± int`, `date − date`)

## Summary
Stock beanquery does day arithmetic on dates: `date + 7` shifts forward, `date - 7` shifts back, `7 + date` commutes, and `date - date` yields a day-count integer. MCP refuses all four with `type error: arithmetic requires numeric values` — the same engine-eval refusal as w23/154's string-`+`, but this time the missing operand pair is one stock fully supports, so any agent-side date windowing (`WHERE date > today() - 30`, aging buckets) has no BQL spelling at all.

## Repro (prod, puncsky/mcp-agent-eval; stock = beanquery 0.2.0 on the byte-identical fixture)
- `SELECT date + 7 LIMIT 1;` → MCP `BAD_USER_INPUT: … arithmetic requires numeric values`; stock `2026-01-08`.
- `SELECT date - 7 LIMIT 1;` → MCP refuses; stock `2025-12-25`.
- `SELECT 7 + date LIMIT 1;` → MCP refuses; stock `2026-01-08` (commutes).
- `SELECT date - date LIMIT 1;` → MCP refuses; stock `0` (day count).
- REST twin: `POST …/ledgers/puncsky/mcp-agent-eval/query` with `date + 7` → identical `BAD_USER_INPUT … arithmetic requires numeric values` (shared engine path; GraphQL `queryShell` rides the same).
- Controls, both sides agree: `ORDER BY number + 1` (numeric exprs fine), `COALESCE(payee,'NONE')` (works both), `NULLIF` (refused both — genuinely unsupported function).

## Root cause (main)
The refusal text originates in the rustledger WASM engine, not TS service code (no service hit for the string; same as w23/154's framing) — the engine's arithmetic evaluator accepts numeric pairs only and has no date±int / date−date overloads. No service-level rewrite target exists. Engine feature or documented gap.

## Expected
Support `add/sub(date, int)` (day shifts, both orders) and `sub(date, date)` (day count) in the engine to match stock, or document that MCP BQL has no date-arithmetic spelling (with the refusal message pointing at the limitation rather than the generic numeric hint). Sub-hour to document; engine work if supported.
