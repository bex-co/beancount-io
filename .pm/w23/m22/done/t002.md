## Objective

Guard each failing parameter at the shared service boundary with `assertNoNul`/`assertNoNulIn`, never by stripping the byte.

## Context

- Fix at the service or workflow all three surfaces share, as w23/210, 218 and 220 did.
- Pull-request fields: confirm what `createPullRequest` forwards to the git host.

## Steps

1. Group failures by owning service.
2. Add the guard once per chokepoint, with the parameter name in the message.

## Files

- `backend-cluster/backend-v2/src/features/**` (per finding)

## Acceptance criteria

- [ ] All t001 cases are green except documented allowlist entries.
- [ ] `yarn typecheck` and `yarn test` pass.

## Out of scope

- Rejecting other control characters.

## Resolution

Fixed once at the transport boundary instead of per parameter: `tools/call` now runs `assertNoNulDeep` (`src/shared/assert-no-nul.ts`) over the raw arguments before schema validation or any domain work (`composition-root.ts`), so every string argument and object key is refused with `BAD_USER_INPUT` naming its path. This covers the parameters w23/210, 218 and 220 listed as unverified (`createPullRequest` fields, `entryHash`, `sha`, `requestId`, `objectKey`, `prNumber` as a string where it is one). Only the file-content arguments are exempt (`mcp-nul-exempt.ts`: `files[].content`, `files[].old_string`, `files[].new_string`, `changes[].content`, `newContent`, plus `text` and `query`, which stay verbatim as before); the test pins that list. The service-level guards from w23/210, 218 and 220 stay as defense in depth for REST and GraphQL. Verified: `yarn typecheck`, full `yarn test` 430 suites / 8431 tests.
