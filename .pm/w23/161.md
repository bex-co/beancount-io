# 161 — `allowInvalid:true` suppresses error *detection*, not just refusal (`errorsAfter: 0` for content that refuses without it)

## Summary
With `allowInvalid: true`, the structured entry paths (add/update/delete) report `errorsAfter: 0`, `newErrors: []`, "No new bean-check errors" for content that provably fails validation — the same balance-999-vs-49.75 entry refuses with `VALIDATION_FAILED` naming the error when the flag is off. Every description promises the opposite: the MCP tool text ("refused with VALIDATION_FAILED naming each new error; allowInvalid records them deliberately"), REST ("allowInvalid records either deliberately"), source-slices ("VALIDATION_FAILED with newLedgerErrors … instead of refusing"). The text-append path implements the documented contract correctly: the same invalid balance with `allowInvalid` previews "1 new bean-check error: Balance failed…". So the flag's meaning differs by path — skip-and-lie vs detect-and-override — and an agent force-committing with known errors cannot distinguish "clean" from "dirty-but-forced" on structured paths.

## Repro (prod, puncsky/mcp-agent-eval; all `dry_run`, nothing written)
- `addLedgerEntries` balance 999.00 vs 49.75, `dry_run` only → `VALIDATION_FAILED: expected 999.00 USD, got 49.75 USD`.
- Same entry + `allowInvalid: true` → `ok: true`, "Would add 1 entry successfully", `validation: {errorsBefore: 0, errorsAfter: 0, newErrors: []}`.
- `updateEntrySource` unbalanced newContent + `allowInvalid` → `ok: true`, "No new bean-check errors" (same skip).
- Control, the correct path: `appendLedgerText` balance 999, `dry_run` + `allowInvalid` → `ok: true`, "Would add 1 directive… 1 new bean-check error: Balance failed for Assets:Cash: expected 999.00 USD, got 49.75 USD".
- The real (non-dry) commit shares the gate by source (below); no live invalid commit was attempted — w23/149 already proved where that leads.

## Root cause (main)
Both gates skip the projection check instead of overriding the refusal: add path `if (!allowInvalid) { check + refuse }` (`backend-cluster/ledger/src/api/entries.ts:404`), source-slice path `if (allowInvalid) return;` (`backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:606`, ahead of `refuseNewLedgerErrors`). The response's validation section is then built from a check that never ran. The append path runs detection unconditionally and gates only the refusal — the shape to mirror.

## Expected
Run projection validation always; let `allowInvalid` suppress only the refusal while reporting the would-be errors (`errorsAfter`/`newErrors` populated, summary naming them), on add/update/delete exactly as append already does. Keep all surfaces identical — the flag's contract is cross-surface text today.
