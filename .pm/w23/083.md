# `insertReceiptTransaction` returns `wrote: []` and `entryHashes: []` for a committed write, so the agent must list-and-guess its own entry

**Severity:** minor (same class as w23/060 and w5/942, which fixed the other write tools). **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/backend-v2` (`insertReceiptTransaction` in `src/features/ai-agent/api/mcp-tools.ts:482`, `receiptInsertResult` in `src/features/ledger/api/rest/v1/receipt-insert-handler.ts:33`, and the GraphQL receipt mutation), reusing the `projectedEntryHashes` mechanism w23/060 built. **A1:** add → verify → fix is the core agent loop, and `getEntryContext`, `updateEntrySource` and `deleteEntrySource` all take the hash.

## Repro (production, 2026-10-25, API key pinned to `puncsky/mcp-agent-eval`)

Upload a 1px PNG through `generateTempAssetUploadUrl`, PUT the bytes, then `insertReceiptTransaction {receiptObjectKey: "tmp/<uid>/2026-10-25-elIFm6vQ.png", input: {date: "2026-09-15", payee: "qa-20261025-cafe", description: "…", postings: [{account: "Assets:Bank:Checking", amountNumber: "-5.00", amountCurrency: "USD"}, {account: "Assets:Bank:Savings", amountNumber: "5.00", amountCurrency: "USD"}], documentAccount: "Assets:Bank:Checking"}}` →

```json
{"ok": true, "result": {"summary": "Inserted receipt transaction for qa-20261025-cafe on 2026-09-15. No new bean-check errors.", "success": true, "wrote": [], "entryHashes": []}}
```

The transaction does land (verified in `main.bean`, with a `receipt:` metadata URL; deleted after). But the result names neither the file nor the hash, so the agent must call `listLedgerEntries` with filters and guess which row is new — ambiguous when identical entries exist. The output schema says "Entry hashes the write created or touched, when known", and the hashes are knowable here exactly as for append/add.

## Cause

The MCP handler hard-codes both fields (`mcp-tools.ts:482`). The sibling `[]`s in `edit-ledger-files-tool.ts` and `bank-import-tool.ts` are dry-run/no-op branches (legitimate); `renameLedgerFile`'s is legitimate too (a rename touches no single entry, and it reports `wrote`). REST is further behind: `receiptInsertResult` is a bare `{success: boolean}` with no file or hash.

## Fix

After the commit, resolve the written entry's file, line and hash through the same `projectedEntryHashes`/bulk-route mechanism w23/060 built, and return them in request order — on MCP, REST and GraphQL together (additive fields). Tests, mirroring w23/060: one hash per written entry; it resolves through `getEntryContext`; `deleteEntrySource` with that hash removes exactly that entry; dry-run-equivalent paths (none exist for insert) and lookup failures keep `[]`.
