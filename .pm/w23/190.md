# 190 — Engine accepts fractional `@@` stock refuses (per-unit division dust)

## Summary
Stock beancount converts a total price (`@@`) to per-unit and multiplies back when weighing, so `3 HOOL @@ 1000 USD` against `-1000 USD` leaves a `-0.0000000000000000000000001 USD` dust residual and refuses under whole-number legs (zero tolerance). The engine reports the same text clean — it weighs the total at face value (or tolerates the dust), verified live on `parseLedgerFiles`. The w23/163 pre-check matches the engine (face value), which is the correct layering — the projection check is authoritative — but committed content can now diverge from stock by dust on inexact totals.

## Repro (stock beancount 3.2.3 vs live engine, October 2026 triage)
- `3 HOOL @@ 1000 USD` + `-1000 USD` → stock `Transaction does not balance: (-0.0000000000000000000000001 USD)`; engine clean.
- Control, exact totals agree: `10 USD @@ 20 USD` + `-20 USD` → both pass.

## Root cause (main)
Upstream engine balancing semantics (rustledger WASM): total-price weighing does not reproduce stock's divide-then-multiply dust. No service-level code is involved past the w23/163 face-value pre-check, which is intentionally engine-aligned.

## Expected
Upstream: weigh `@@` as stock does (per-unit division in Decimal28, dust included), or document the face-value divergence. Service-side, nothing to do unless the engine changes — then the pre-check follows it.
