A one-character metadata key passes the typed-entry token check, so it is refused late and vaguely, while any other malformed key is refused up front and by name. Repro (production `beancount-mcp 1.0.0`, 2026-11-11, read/write key on the disposable `puncsky/mcp-agent-eval`, same on REST `POST …/entries`): `addLedgerEntries` with `dry_run: true` and a transaction whose `meta` is `{ "k": "v" }` answers `ok` with `validation.valid: false`, `errorsAfter: 1` and `newErrors: [{ message: "parse error: unexpected input", source: "main.bean:90", code: "P0012" }]`; without `dry_run` the commit is refused `VALIDATION_FAILED` ("adding these entries would introduce 1 new bean-check error: parse error: unexpected input (main.bean:90)") and the ledger is unchanged. Controls: `meta: { "kk": "v" }` is valid, and `meta: { "Key": "v" }` is refused up front, `BAD_USER_INPUT`, "entry 0: meta.Key "Key" is not a valid metadata key". A posting-level `meta: { "k": "v" }` behaves the same. Stock beancount 3.2.3 agrees with the engine: `k: "v"` is `Invalid token: 'k:'` (its key grammar needs at least two characters), so nothing wrong reaches the ledger. The gap is that the guard disagrees with the grammar.

Cause: `backend-cluster/ledger/src/features/ledger/utils/entry-tokens.ts:44` holds the metadata key to `/^(?!(?:filename|lineno)$)[a-z][A-Za-z0-9_-]*$/` (w23/033 wrote `[a-z][A-Za-z0-9_-]*`), where `*` admits one character; the lexer's key is `[a-z][A-Za-z0-9_-]+`. The same pattern sits in `backend-v2/src/features/ledger/utils/directive-text.ts:94` and `:135` (`pushmeta`/`popmeta` and the raw-text key scan), and the published schema (`tools/list`, OpenAPI) advertises no key pattern at all (`propertyNames: { type: "string" }`), so an agent cannot know the rule. An agent that sends a short key such as `n` or `k` gets an error that names no field and cites a line number in the would-be file.

Fix, sub-hour: change `*` to `+` in `entry-tokens.ts:44` (and the two `directive-text.ts` patterns) so `k` is refused `BAD_USER_INPUT` naming `meta.k` / `postings.0.meta.k` on MCP, REST and GraphQL, and say "at least two characters" in the refusal; test the one-character key on the entry, the posting and the raw-text paths; optionally advertise the key pattern as `propertyNames.pattern` in the published schema.
