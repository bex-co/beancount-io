# Map a stray 431 from the ledger hop to BAD_USER_INPUT

Follow-up from `w23/m5/t001`: the ledger 431 cliff (Node 16 KiB `maxHeaderSize`) falls into `error-to-domain.ts`'s `default` branch and surfaces as `INTERNAL_SERVER_ERROR: Failed to ...` with a retry hint. m5 moves the shell hop to POST, but any other long-URL ledger route (a long journal `filter`, a deep file path) can still 431 the same way.

Consider `case 431: return new BadUserInputError(...)` naming the oversize URL, as defense-in-depth behind every GET hop. Sub-hour: one case + one mapping test.

**QA confirmation 2026-10-26** (it.766, same session): three more routes 431 exactly as predicted — `payee-transactions/{payee}`, `narration-transactions?narration=`, and `account-report/{account}` with 20 KB values all answer `INTERNAL_SERVER_ERROR: Failed to get ledger …` with the retry hint. Payee cliff bisected: 16,000 chars → `null` (clean miss), 16,500 → 500. Ruled out as vectors: a maxed-out journal URL (256-char filter + every param) is only 489 chars, and file paths cap far below the cliff — so the fix's test should target the three unbounded segments above, not filter/path.
