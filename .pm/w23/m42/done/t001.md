## Objective

Decide how a revert is written (a Gitea diff-patch endpoint versus reverse file edits through the existing write path), whether it stays atomic under the main-only branch policy, and what the commit reads already return.

## Result

Decision: a revert is a set of inverse file operations written through the ledger service's existing `change-files`, so it is one atomic commit on the default branch (no side branch, which the main-only policy refuses, `w23/m17`). For each file the commit touched, read it at the commit, at the commit's parent (`repoGetContents` with `ref`) and now (the ledger service's `getLedgerFile`); an added file is deleted, a removed one is created again from the parent, a modified one is set back to its parent's contents. It is refused with `CONFLICT` naming the file when its blob sha now differs from its sha at the commit (a later commit touched it): per file, simpler and safer than per line, and it never discards newer work. A merge or root commit cannot be reverted. The commit reads already return files with statuses and parents. The write answered no sha: Gitea's `ChangeFiles` response carries `commit.sha`, which the ledger service's `changeExistingFiles` discarded and its endpoints answered `null`, so the exact sha is returned from there (a read of the head before and after was rejected: it names the wrong commit when another writer lands in between).
