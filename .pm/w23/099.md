# Resource param-validation errors hint at `tools/list` instead of the resource templates

**Severity:** minor (wrong pointer in an otherwise good refusal; agents following it list tools for a resource-param mistake). **Estimate:** 30–60 minutes incl. parity. **Owner:** `backend-cluster/backend-v2`, shared error-hint builder. **A1/A2:** agents fix rejected resource params by reading the hint; this one sends them to the wrong catalog.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`resources/read beancount://puncsky/mcp-agent-eval/journal?limit=0` → JSON-RPC `-32602` with `data: {code: BAD_USER_INPUT, message: "limit: Too small…", hint: "Fix the named argument and call again; \`tools/list\` publishes each tool's input schema."}`.

The refusal is correct; the hint is a tool hint. On a resource read there is no tool and no `tools/list` entry — the equivalent pointer is `resources/templates/list`. Neighbor hints are already resource-appropriate (bogus `entry-context` → "read fresh ones with `listLedgerEntries`"), so only the shared zod-validation hint misfires.

## Fix (keep REST/GraphQL/MCP in parity)

Make the generic validation hint surface-aware: on resource reads point at `resources/templates/list` (and the offending template), on tools keep `tools/list`. Same hint-accuracy area as w23/093 (append hint wording) — distinct hint, distinct path.

**Cross-surface scoping 2026-10-26** (it.756): `hint` exists only on MCP. REST errors carry `metadata: {field, reason}` (e.g. `VALIDATION_FAILED` on bulk-add) and GraphQL errors carry `extensions: {code, field}` (verified live) — both already point at the offending field by their own convention. So this fix is MCP-internal (tools vs resources vs prompts); no REST/GraphQL change needed.
