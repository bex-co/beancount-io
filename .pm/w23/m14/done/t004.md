## Resolved 2026-10-28

Triage per t001's verdict (engine-internal inconsistency, no shell code involved), re-verified live against the pinned engine (rustledger 0.24.0, synthetic ledger): `date(NULL)` → `DATE: argument must be a string or date`, `weekday(NULL)` → `WEEKDAY expects a date`, `substr(NULL,…)` → `SUBSTR expects (string, int, [int])`, `subst(NULL,…)` → `SUBST expects (pattern, replacement, string)`, `startswith(NULL,…)` → `STARTSWITH expects two strings`, `maxwidth(NULL,…)` → `MAXWIDTH: first argument must be a string`, while `upper`, `year`, `month`, `day` and `quarter` pass NULL through (the `int/decimal/bool/str` casts are lenient too). Stock passes NULL through for all of them.

- **Adapted (shipped, `be3d90815`, `backend-cluster/ledger`):** each of the six refusals now carries the workaround in its message (`ENGINE_GAPS`: drop the NULL rows first with `WHERE payee IS NOT NULL`, or apply the function after aggregating). Unit tests pin each message; the live `verify:rustledger` check shows the engine still errors on a NULL payee in `substr`/`startswith`/`maxwidth`/`subst` and that the named workaround runs.
- **Not adapted in the shell, on purpose:** rewriting these calls to pass NULL through would change what the engine computes; the correct fix is in the engine.
- **Upstream report (filing pending):** the strict-camp cluster is part of the batch the owner approved on 2026-10-28 (see `w23/blocked/022.md`); it needs someone with rustledger tracker access to file it. Draft text: "Builtins `date`, `weekday`, `substr`, `subst`, `startswith`, `maxwidth` raise a type error when an argument is NULL, while `upper`, `year`, `month`, `day`, `quarter` and the `int/decimal/bool/str` casts return NULL, as beanquery does for all of them; one NULL row fails a whole query (`SELECT substr(payee, 0, 2) FROM postings` on a ledger with a payee-less transaction). Expected: NULL in, NULL out." No issue link exists yet; whoever files it records the link in `w23/blocked/022.md`.
