# Bare `SELECT … FROM <table>` (no other clause) fails on all three surfaces

**Severity:** major (every explicit-FROM query without WHERE/GROUP BY/ORDER BY/LIMIT fails; paginated product surfaces are unaffected, which is why it is silent). **Estimate:** 2–4h (find the no-clause query path + regression test). **Owner:** query path below backend-v2 (backend-v2 itself is pre-deploy: m2/m3 signals unchanged) — likely the ledger/engine service. **A1/A2:** agents and CLI users routinely omit LIMIT on single-row or small queries.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

Any `FROM` with no further clause resolves the *table* as a *column*:

| query | MCP | REST | GraphQL |
| --- | --- | --- | --- |
| `SELECT count(*) FROM postings;` | `BAD_USER_INPUT: … column 'postings' not found` | same | same (`queryShellText`) |
| `SELECT date FROM postings;` | `column 'postings' not found` | — | — |
| `SELECT * FROM prices;` | `column 'prices' not found` | — | — |
| `SELECT * FROM commodities;` | `column 'commodities' not found` | — | — |
| `SELECT count(*) FROM close;` | `column 'close' not found` | — | — |
| `SELECT count(*) FROM open;` | `column 'open' not found` | — | — |

Adding ANY clause fixes it (verified on MCP unless noted):

| query | result |
| --- | --- |
| `SELECT count(*) FROM postings LIMIT 1;` | `34` (also via REST table rows `[[34]]` and GraphQL text) |
| `SELECT date FROM postings LIMIT 2;` | rows |
| `SELECT date FROM postings WHERE date > 2020-01-01;` | rows |
| `SELECT date FROM postings ORDER BY date;` | rows |
| `SELECT count(*) FROM prices LIMIT 5;` (structured) | `[[0]]` |
| `SELECT * FROM prices LIMIT 5;` (structured) | `date/currency/…` schema |
| `SELECT count(*) FROM close LIMIT 5;` | `evaluation error: table 'close' …` (the it.1012 message) |
| `SELECT count(*);` (implicit FROM, no clause) | `34` |

Fixture is byte-identical to the pinned snapshot (2817 B, sha `77c3a591efd3`), so this is not data drift. Failure is deterministic (3/3 reruns), not a routing flake.

## Regression evidence

- it.1012 (2026-10-25 ~20:13 PDT): `SELECT count(*) FROM close` → `evaluation error: table 'close' does not exist` — the table-aware error, only reproducible today *with* a further clause.
- it.1004/it.1006: `SELECT count(*)` / `SELECT sum(amount)` over `FROM prices`/`commodities` returned rows (`[[0]]`, `[['']]`) — today bare-FROM errors before any row logic.
- Break window is therefore (it.1012, it.1560] (≈20:13–21:30 PDT Oct 25), *unless* those early probes secretly carried LIMIT — the filed quotes show bare queries, and single-row count/sum probes have no output-cap reason to carry LIMIT. Owner can confirm against deploy history.
- backend-v2 did NOT deploy in the window (tool count still 44, no holdings/register tools, m2 tag hint absent, m3 `entry_hash` alias absent), so the change is in the ledger/engine service or query-path config below the API layer.

## Fix

Make the no-further-clause path resolve FROM exactly like the with-clause path (one planner, no bare-query fast path — or fix the fast path to keep FROM). Add a regression test running the same `SELECT … FROM <table>` with and without LIMIT/WHERE on every table including empty `prices`/`commodities`, asserting identical results modulo row caps.
