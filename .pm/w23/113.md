# REST journal queries silently drop unknown keys instead of refusing them

**Severity:** minor (silent wrong filter; same family as w23/112). **Estimate:** 0.5h (`.strict()` on the journal query schema + regression test). **Owner:** backend-v2. Found by the QA loop while sweeping w23/112's pattern across REST GET routes.

## Observation (production, 2026-10-26)

`GET /api-gateway/v1/ledgers/puncsky/mcp-agent-eval/journal?bogus_param=1&limit=1` returns 200 with the unknown key silently dropped. The schema is validated but non-strict: a mistyped *declared* param fails loudly (`?limit=abc` → `VALIDATION_FAILED: … query.limit: Invalid input: expected number, received NaN`), so only *undeclared* keys slip through — an agent pasting `account_name` for `account` gets an unfiltered page with no error.

Parity, verified live (it.2157):

- REST: `?bogus_param=1` → 200, dropped.
- MCP `listLedgerEntries {"limit": 1, "bogus_param": 1}` → `BAD_USER_INPUT: Unrecognized key: "bogus_param"`.
- GraphQL `getLedgerJournal` rejects unknown args by construction (`GRAPHQL_VALIDATION_FAILED`; cf. w23/112 it.2153).

So of the three surfaces, only REST drops the key.

## Fix

`.strict()` on the journal query schema (and audit sibling GET query schemas — `bank-accounts` takes no query params at all so its 200-with-junk is plain pass-through, not this bug; `bank-transactions` GET is 405). Flip/add a regression test asserting 400 on an undeclared key. Blast radius: REST clients passing unknown query params to the journal route start getting 400 instead of silently unfiltered 200s.

Same pattern as w23/112 (`bankAccountQuery`), different schema — filed separately so each fix/test lands against its own route. Searched: strict, unknown key, silently drop, query leniency; open: m8, 095–112.
