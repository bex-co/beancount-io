# 131 — GROUP BY accepts bare non-grouped columns and silently reports an arbitrary row's value (it.4594)

## Summary
`SELECT account, date GROUP BY account` runs on MCP, reporting one date per account — the first row's date in scan order — while stock beanquery 0.2.0 refuses (`all non-aggregates must be covered by GROUP-BY clause`). The reported value is silently arbitrary: `Assets:Bank:Checking` shows `2026-01-01` but its 9 postings span 9 distinct dates. Unlike the benign fn-of-key leniency (w23/blocked/022 it.4588, deterministic), this can hand agents a confidently wrong per-group value. MCP should refuse like stock (or document first-row semantics deliberately).

## Repro (prod, puncsky/mcp-agent-eval; stock = beanquery 0.2.0 on the byte-identical fixture)
- `SELECT account, date GROUP BY account ORDER BY account LIMIT 12;` → MCP 12 rows with one date each (e.g. Checking `2026-01-01`); stock `CompilationError`.
- Control: Checking's dates are `{2026-01-01, 2026-02-10, 2026-03-15, 2026-07-01, 2026-07-03, 2026-07-25, 2026-08-01, 2026-08-03, 2026-08-20}` — MCP shows only the first.
- Related accepts (same root cause, it.4588/4592): `length(account)` and `length(account) + count(*)` in SELECT under GROUP BY run on MCP (deterministic, benign) and refuse on stock.
- Extended it.4596–4598: the pick is the first row's value per group, row-consistent across multiple bare columns (date+payee pairs match), and ORDER BY / HAVING operate on the picked values — so the arbitrary value propagates through the whole query.

## Expected
Refuse bare non-grouped, non-aggregated columns under GROUP BY like stock. If first-row-pick is intended, document it and prefer an explicit `first()`/`any_value()` spelling.

## Status
