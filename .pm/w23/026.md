# Decide whether MCP OAuth clients get a streaming archive route for archives over 8 MiB

Split from `w23/023` (resolved 2026-10-20 in `ba1e497aa` with option 2). The MCP `archive/{archive}` blob stops at 8 MiB. The streaming fallback `archive-download-url` returns a REST URL that refuses an MCP-audience OAuth token, by ADR 0007's separate-resource design, and the docs and hint now say so. So a host connected only through MCP OAuth (Claude, ChatGPT, Cursor, VS Code, Claude Code with OAuth) still can't download a ledger whose archive exceeds the cap. A personal API key or browser session can.

**Option 1 from `w23/023`:** serve the stream under the MCP resource, e.g. `GET /api-gateway/mcp/archive/{owner}/{name}/{archive}`. It would accept the MCP audience with the same credential pin, `LEDGER_ARCHIVE_READ` authorization and shared download budget as `streamLedgerArchive`. `archive-download-url` would return it for MCP callers, the docs and hint would be updated, and an end-to-end test would cover an over-cap archive with an MCP-audience token. About 60m.

**Why it needs a decision:** it adds a non-JSON-RPC HTTP route under the MCP resource. That widens what an MCP-audience token can reach beyond the JSON-RPC endpoint ADR 0007 scopes it to, so the ADR's trust boundary has to be amended deliberately, not by a worker.

---

**Unblocked 2026-10-31** — the owner chose option 1 (a streaming archive route under the MCP resource); blocked since 2026-10-20 on that decision. The worker implements it as described above (same credential pin, `LEDGER_ARCHIVE_READ` authorization and shared download budget as `streamLedgerArchive`; `archive-download-url` returns it for MCP callers; docs and hint updated; end-to-end over-cap test) and writes the ADR 0007 amendment that widens the MCP-audience boundary in the same change.
