`revertCommit` answers `INTERNAL_SERVER_ERROR` ("Internal server error") for every commit that exists, on MCP, REST and GraphQL, so the undo that `w23/m42` shipped cannot be used on production. Repro (production `beancount-mcp 1.0.0` after the 2026-11-12 deploy, `tools/list` 45 tools with sha prefix `ed177d7e986a`, a read/write key, the disposable `puncsky/mcp-agent-eval`): `revertCommit { ledger, sha: "main", dry_run: true }` returns `isError: true` with `error.code: INTERNAL_SERVER_ERROR`; REST `POST /api-gateway/v1/ledgers/puncsky/mcp-agent-eval/revert-commit` with `{ "sha": "main", "dry_run": true }` returns 500 with the same code; GraphQL `revertLedgerCommit(ledgerId: "puncsky/mcp-agent-eval", sha: "main", dryRun: true)` returns `errors[0].extensions.code: INTERNAL_SERVER_ERROR`. The same holds for the full sha that `addLedgerEntries` and `createLedgerFiles` returned in `commit` a moment earlier (it is the newest commit `beancount://…/commits` lists), for the newest, a middle and an old commit of the ledger, and for a commit that only created a file; the real call without `dry_run` fails the same way and writes nothing (the ledger gained only the commit the add made).

What still works, so the failure can be placed: an empty `sha` is `BAD_USER_INPUT` ("sha is required"), an unknown sha or branch name is `NOT_FOUND` ("Commit with ID … not found") on MCP and REST, and a read-only key is `FORBIDDEN` (scope `ledger.write`), so authorization and the commit lookup run. The `commit` half of m42 is fine: `commit` on `addLedgerEntries`, `createLedgerFiles`, `updateEntrySource` and `deleteEntrySource` equals the newest commit the ledger lists, and a byte-identical `updateEntrySource` reports `unchanged: true` with no commit (m43).

Cause, not traced (production masks the message): the failure comes after `findCommit` resolves a real commit and before any answer, so it is inside `undoLedgerCommit` (`backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts:1582`): the reads of each touched file at the commit and at its parent through Gitea `repoGetContents`, the ledger service's `getLedgerFilesContent`, or the preview projection. m42 changed backend-v2 and the ledger service together (`c70a9ff93`, `4d541a5ab`), and its tests drive a fake repository (`revert-commit-parity.test.ts`), so a deploy that reached one service and not the other, or a difference between the real Gitea and the fake, would produce exactly this. Whoever deploys can read the logged error for a request id; no local stack was running to compare.

Fix: read the logged error and repair that step, then add the case the milestone's gate missed: `yarn mcp:conformance` has no `revertCommit` check (the file does not mention it), so a deployed build whose undo always fails passes 17 of 17. A live check that previews `revertCommit` on the newest commit of the QA ledger and expects the file list (never a 500) belongs next to check 17; and an existing commit must never end in `INTERNAL_SERVER_ERROR` on a preview, whatever the cause, so name the failing step in the error the way `operationNotAllowedFromCause` does for the file read.
