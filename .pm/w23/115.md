# Quoted `FROM "<table>"` names are silently ignored (postings scope for any name)

**Severity:** major (silent wrong data: any quoted table name returns postings rows, including nonexistent tables). **Estimate:** 2–4h (resolve quoted FROM names through the same table path as unquoted + regression test). **Owner:** query path below backend-v2 (same area as w23/109 — likely the ledger/engine service). **A1/A2:** agents quote identifiers routinely; a quoted typo'd table name returns plausible-looking postings rows instead of an error.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

Every quoted FROM name returns the postings count (34), even names that resolve correctly unquoted and names that cannot exist:

| query | MCP | stock beanquery |
| --- | --- | --- |
| `SELECT count(*) FROM "postings" LIMIT 1;` | `34` | `34` (correct by accident — postings is the default scope) |
| `SELECT count(*) FROM "entries" LIMIT 1;` | `34` (WRONG — entries count is 29) | `29` |
| `SELECT count(*) FROM "open" LIMIT 1;` | `34` (WRONG) | `CompilationError: table "open" does not exist` |
| `SELECT count(*) FROM "close" LIMIT 1;` | `34` (WRONG) | 34 postings rows (stock resolves `FROM close` to postings — see w23/blocked/022) |
| `SELECT count(*) FROM "nosuchtable" LIMIT 1;` | `34` (WRONG — should error) | `CompilationError: table "nosuchtable" does not exist` |

Scope proof: `SELECT account FROM "entries" LIMIT 2;` returns postings accounts (`Assets:Bank:Checking`, `Assets:Bank:Savings`) on MCP — entries rows have no `account` column, so the FROM name is dropped and the query runs in default postings scope.

Unquoted names resolve correctly on the with-clause path (`FROM entries LIMIT 1` → 29, `FROM prices LIMIT 1` → 0, `FROM "…" quoting` is the only trigger), and unquoted unknown tables error loudly (`FROM balance LIMIT 1` → `table 'balance' does not exist`, w23/109). So there are three FROM paths: bare-unquoted (column-fold bug, w23/109), with-clause-unquoted (correct), and quoted (name silently ignored — this note).

Note: w23/109's it.1993 line ("quoting the table name bypasses the bug — `FROM "postings"` returns 34 on MCP and stock alike") is consistent: `"postings"` is the one quoted name whose ignored result happens to be correct. The bypass advice is unsafe for any other table.

Fixture is byte-identical to the pinned snapshot (2817 B, sha `77c3a591efd3`), so this is not data drift. Failure is deterministic (4/4 quoted names in one sweep, it.2317).

## Fix

Resolve quoted FROM names through the same table-resolution path as unquoted names (one planner for quoted and unquoted), so `"entries"` scopes to entries and `"nosuchtable"` errors. Add a regression test running `SELECT count(*) FROM "<table>" LIMIT 1` quoted and unquoted over every table plus one nonexistent name, asserting identical results or identical errors.
