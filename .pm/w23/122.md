# Non-`count` aggregates over an empty set return a `str`-typed empty string

**Severity:** minor (wrong value + wrong dtype for `sum`/`min`/`max`/`avg`/`first` over an empty filter; `count(*)` is correct). **Estimate:** 1–2h (NULL/zero coercion in the empty-group path + dtype propagation). **Owner:** ledger/engine aggregate path. **A1/A2:** agents summing filtered postings get `""` instead of `0`/`NULL` and a `str` dtype, breaking numeric downstream code.

## Repro (production, 2026-10-26, API key pinned to `puncsky/mcp-agent-eval`)

`SELECT sum(1) AS s, count(*) AS c FROM postings WHERE year(date) > 2030;` (matches nothing):

```json
{"types": [{"name": "s", "dtype": "str"}, {"name": "c", "dtype": "int"}],
 "rows": [["", 0]]}
```

| aggregate over empty filter | MCP value | MCP dtype | expected |
| --- | --- | --- | --- |
| `sum(1)` | `""` | `str` | `0`/`NULL`, numeric dtype |
| `min(1)` / `max(1)` / `avg(1)` | `""` | (same shape) | `NULL`, numeric dtype |
| `first(payee)` | `""` | (same shape) | `NULL` |
| `count(*)` | `0` | `int` | `0` — correct |

So the empty-group path emits one row (unlike stock beanquery, which emits zero rows — see w23/blocked/022 it.3175), but every non-`count` aggregate cell is a `str`-typed empty string instead of a NULL/zero with the aggregate's natural dtype.

## Controls

- Non-empty `sum` works: `SELECT sum(1) AS s … WHERE <matches>` returns a numeric cell (the empty-input path is the only broken one).
- `count(*)` over the same empty filter returns `0` with dtype `int` — correct value and dtype, so the row exists and only the non-`count` cells are mistyped/misvalued.
- Stock beanquery (0.2.0 API) returns **zero rows** for any aggregate over an empty set (`nrows: 0` for both `count(*)` and `sum(1)`), so the one-row-vs-zero-row split is a separate stock/MCP portability divergence tracked in blocked/022; this note is only about the `""`/`str` cell content within MCP's one row.

## Probes (it.3175–3176)

- `sum`/`min`/`max`/`avg`/`first` over `WHERE year(date) > 2030` (empty): all `[['']]` via `runBqlQueryStructured`.
- Full structured shape inspected: `types: [{s, str}, {c, int}]`, `rows: [["", 0]]`.
- Stock API (`beanquery.connect('beancount:…')`, 0.2.0): `count(*)` and `sum(1)` over the same empty filter both yield `nrows: 0`; `count(*)` unfiltered yields `[(34,)]`.

### it.3178 — parity control: the `""`/`str` shape is engine-level, all surfaces agree
- `runBqlQuery` (text): `s\n-\n \n` — empty cell.
- REST `POST /v1/ledgers/{owner}/{name}/query`: `{"types":[{"name":"s","dtype":"str"}],"rows":[[""]]}` — identical shape.
- So text, structured, and REST all emit the same mistyped empty string; the bug sits below the surfaces in the shared aggregate path.

### it.3186 — string-typed aggregates: dtype accidentally right, value still `""`
- `SELECT last(payee) AS l … WHERE <empty>` → `[['']]` with dtype `str` — the dtype is correct for a payee (unlike `sum`'s numeric-typed-as-`str`), but the value is still an empty string where `NULL` belongs.
- So the empty-group path has two separable defects: (a) every non-`count` cell is `""` instead of NULL (all aggregates incl. string ones); (b) numeric aggregates additionally report dtype `str`.

### it.3193 — the `""`-for-NULL coercion is general, not empty-set-only
- `SELECT payee, count(*) FROM postings GROUP BY 1 LIMIT 3;` → MCP `['', 6]` vs stock `(None, 6)` for the missing-payee group. Same ordering, same counts — only the NULL cell renders as `""` on MCP.
- So defect (a) (`""` instead of NULL) affects every NULL cell on every surface, while defect (b) (`str` dtype on numeric aggregates) is specific to the empty-group path. GROUP BY ordinals themselves agree (both accept `GROUP BY 1`).
