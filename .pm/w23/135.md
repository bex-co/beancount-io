# 135 — Empty input masks unknown-function/column errors and fabricates a `str` dtype (it.5710-5712)

## Summary
MCP resolves SELECT names lazily at row-evaluation time, so any query whose input is empty succeeds even when it names a function or column that does not exist — and the reported column dtype is a fabricated `str`. `SELECT nosuchfn(payee) WHERE FALSE` and `SELECT nosuchcol WHERE FALSE` both return clean `rows: []` with `dtype: 'str'`; the same queries without the filter error (`no function matches "nosuchfn"`, `column 'nosuchcol' not found`). Stock beanquery 0.2.0 errors in all four cells (compile-time resolution). A typo'd name in a legitimately-empty query therefore reads as success, and the `str` dtype invents a type the engine never resolved (same dtype-fabrication theme as w23/134).

## Repro (prod, puncsky/mcp-agent-eval; stock = beanquery 0.2.0 on the byte-identical fixture)
- `SELECT nosuchfn(payee) FROM postings WHERE FALSE LIMIT 1;` → MCP `rows: []`, `types: [{name: 'nosuchfn(payee)', dtype: 'str'}]`; stock `CompilationError: no function matches "nosuchfn(str)"`.
- `SELECT nosuchfn(payee) FROM postings LIMIT 1;` → MCP `no function matches "nosuchfn"`; stock same refusal. (Error exists — only the empty input masks it.)
- `SELECT nosuchcol FROM postings WHERE FALSE LIMIT 1;` → MCP `rows: []`, `dtype: 'str'`; stock `column "nosuchcol" not found`.
- `SELECT nosuchcol FROM postings LIMIT 1;` → MCP `column 'nosuchcol' not found in subquery result`; stock same refusal.
- Found via `string_agg(payee)` (1-arg form exists on neither engine): empty input → MCP `[]`, non-empty → `no function matches "string_agg"` on both.

## Expected
Resolve SELECT names before evaluating rows: unknown functions/columns error regardless of input cardinality, like stock. Never report a dtype for a name that failed to resolve.

Open (inbox). MCP-side (engine name-resolution timing), not an upstream divergence — stock's compile-time refusal is the correct side.
