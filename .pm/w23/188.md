# 188: Double-quoted identifiers outside FROM are string literals (silent wrong results)

**Severity:** major (silent wrong data in all four non-FROM positions; SQL-standard quoting).
**Estimate:** 2–6h (extend the FROM-unquote normalizer pattern or fix the engine lexer).
**Owner:** ledger shell (`unquoteBqlFromTables` family) + engine lexer. **A1:** agents writing
standard-SQL `SELECT "payee"`, `WHERE "payee" = 'VISA'`, `GROUP BY "flag"`, `ORDER BY "date"`.

Stock beanquery treats `"name"` as a quoted identifier everywhere (SQL standard). The engine
parses `"..."` as a string literal; the TS shell only unquotes the FROM position (w23/115,
w23/130 — `FROM "entries"` fixed), so SELECT/WHERE/GROUP-BY/ORDER-BY quoted names silently
degrade to constants:

| position | MCP | stock |
|---|---|---|
| `SELECT "payee" … DESC LIMIT 2` | 2 rows of literal `payee` | `WHOLE FOODS` × 2 |
| `SELECT count(*) WHERE "payee" = 'VISA'` | `0` (literal ≠ VISA) | `2` |
| `SELECT "flag", count(*) GROUP BY "flag"` | 1 group keyed `flag` | 1 group keyed `*` |
| `SELECT payee ORDER BY "payee" DESC LIMIT 2` | constant sort, empty payees | `WHOLE FOODS` × 2 |

Repro (helper command, sanitized — no credential material):

```zsh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs call runBqlQuery \
  '{"ledger":"puncsky/mcp-agent-eval","query":"SELECT \"payee\" ORDER BY payee DESC LIMIT 2;"}'
# → 2 rows of literal `payee`; stock bean-query on the same ledger returns WHOLE FOODS × 2
```

- REST twin (`POST /api-gateway/v1/ledgers/…/query`) agrees with MCP:
  `rows:[["payee"],["payee"]]` — one shared engine path, not a surface gap.
- GraphQL twin (`queryShell`) agrees identically.
- Root cause layer: `backend-cluster/ledger/src/features/ledger/service/bql-from-quotes.ts`
  documents that the engine parses quoted FROM names as non-identifiers and works around only
  that position; SELECT/WHERE/GROUP/ORDER reach the same lexer untouched. Fix direction is
  either a wider careful pre-pass (same offset-preserving trade, identifiers only) or an engine
  lexer fix so `"..."` lexes as identifier outside string-literal positions.
- Alias-position leg (same lexer root cause, opposite failure mode): `SELECT payee AS "p"`
  is *refused* (`syntax error at position 13: unexpected token 'AS'` — the alias rule takes
  no quoted names) while stock accepts it and returns payee values under `p`. Bare `AS p`
  works on both sides, so only the quoted alias is affected. REST twin refuses identically.
- Scope boundary (verified live): stock resolves a quoted name only on *exact* match and
  otherwise falls back to the string literal — `SELECT "PAYEE"` and `SELECT "nosuchcol"`
  return literal rows on *both* sides. The divergence is exactly the quoted-exact-column
  case (`"payee"`, `"flag"`). A fix must resolve-then-fallback, not unquote blindly, and
  must not case-fold quoted names (unlike unquoted, w23/176).
- Not w23/176 (that is case-folding of *unquoted* identifiers; this is quote *kind*).
- QA ledger untouched (read-only probes; byte-identical + stock-clean per it.1210 re-verify).
