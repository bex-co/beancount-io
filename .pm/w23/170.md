# 170 — BQL `meta` column splits by table: `k: v`/`str` on postings vs `k=v`/`object` on entries

## Summary
The `meta` column speaks two dialects. With valued metadata, postings renders `qa-post-key: "post-value"` (colon form, dtype `str`) while entries renders `qa-txn-key=txn-value` (equals form, dtype `object`) — same logical content (one custom key), different serialization, different dtype, on the two tables. Blank cells split too: postings meta is `""`/`str`, entries meta is `""`/`object`. Stock has one dialect: a dict (`{'filename': …, 'lineno': …, 'qa-txn-key': …}`) on both tables. An agent parsing `meta` strings or branching on its dtype gets table-dependent answers for identical questions.

## Repro (prod, puncsky/mcp-agent-eval; probe entry added + deleted, byte-identical restore verified; stock = beanquery 0.2.0 on fixture + same entry)
- Probe txn `2026-10-27 * "qa-meta-131" "metadata probe"` with txn meta `qa-txn-key: "txn-value"` and one posting meta `qa-post-key: "post-value"`.
- `SELECT meta FROM postings WHERE narration = 'metadata probe';` → dtype `str`, rows `[["qa-post-key: \"post-value\""], [""]]` (custom key survives, colon form; bare leg blank).
- `SELECT meta FROM entries WHERE narration = 'metadata probe';` → dtype `object`, row `[["qa-txn-key=txn-value"]]` (equals form; the `object` dtype says the pre-serialization sample is a dict).
- Blank baseline (fixture has no metadata): postings `""`/`str`, entries `""`/`object` — the dtype split exists even with no data.
- Stock: postings row 2 (bare leg) `{'filename': …, 'lineno': 22}`; entries `{'filename': …, 'lineno': 89, 'qa-txn-key': 'txn-value', '__tolerances__': …}` — dicts with filename+lineno+custom on both tables.
- Auto-meta omission (shared root with w23/016 + blocked/022 it.2394, not re-filed here): MCP's meta carries custom keys only — filename/lineno never appear in either table's rendering, while stock includes them. The engine doesn't track source locations; that gap is already upstream-queued.

## Root cause (main)
Two serializers, no shared contract: the postings path stringifies metadata as `k: "v"` lines typed `str`, the entries path stringifies as `k=v` from a dict sample typed `object`. (Exact sites live behind the shell cell coercion around `ledger-shell-mappers.ts`; the fix is one rendering + one dtype for both tables.) The missing filename/lineno rides on the known engine gap (w23/016, 022 it.2394: no source-location surface is populated).

## Expected
One `meta` dialect on both tables: same serialization for the same content and one dtype (`object`, matching stock's dict and the entries endpoint). Keep custom keys flowing (they work today); filename/lineno arrive with the upstream location fix. At minimum, document which table speaks which dialect until they converge.
