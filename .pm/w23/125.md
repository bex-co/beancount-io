## Root causes

1. **Meta-derived columns never fold natively.** `SELECT count(*) FROM filename;` (bare-`;`, the native path) → `[[0]]` on MCP while stock folds to 34 — and the direct-subquery probe `FROM (SELECT * FROM filename)` also yields 0, as do `lineno`/`meta`. The engine's native fold is empty for exactly the meta family, so wrapping cannot rescue them; the fold set promises what the engine cannot deliver. Same for `location`/`id` (engine 0, stock 34).
2. **Fold set under-inclusive where the engine works.** `type`/`weight`/`other_accounts` fold natively to 34 in the direct-subquery probe but are absent from `FOLD_COLUMNS`, so they take the table path and error. One-line fix each (plus tests).
3. **The live-engine pin covers 2 of 19 members.** `scripts/verify-rustledger.ts` (column-fold block) asserts pipelined≡native rows only for `payee`/`narration` (+ dual shape + 3 exclusions). `filename`/`lineno`/`meta` returning 0 never trips it because the pin asserts *pipeline consistency with native*, never *native correctness vs stock* — and native itself is the broken layer here. The pin needs a per-member native-vs-stock row assertion (or at least every member's native non-emptiness where stock is non-empty).

## Suggested triage

- Add `type`, `weight`, `other_accounts` (+ the five empty-fold columns) to `FOLD_COLUMNS` — pure set extension, engine-verified above.
- For `filename`/`lineno`/`meta`/`location`/`id`: either emulate the fold above the engine (e.g. postings scope + `WHERE <col> IS NOT NULL`-style truthiness filter — fold semantics equal non-falsy rows: payee 28 = non-null) or file the engine gap upstream (w23/blocked/022 class). Until then, consider REMOVING the three silent-zero members from the set so they error loudly instead of returning `[[0]]` — a loud error beats a silent wrong count.
- Extend the verify pin to every fold member: native-vs-stock row equality on a fixed fixture.
