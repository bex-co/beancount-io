# 181 — `abs()` over inventory refused with no workaround hint (stock accepts; `neg` got one)

## Summary
Stock bean-query applies `abs()` to an inventory element-wise (`SELECT abs(position)` → `3000.00 USD`), but the pinned engine refuses it with a bare `type error: ABS expects a number`. The sibling `neg()` inventory refusal got a documented workaround via `ENGINE_GAPS` (w23/016: `sum(neg(units(position)))` + message hint + pinned test); `abs()` has no entry, no hint, and no pinned test — agents hitting it get a dead end although a working spelling exists on the engine (`abs(number(units(position)))`).

## Repro
- `call runBqlQuery {"ledger":"puncsky/mcp-agent-eval","query":"SELECT abs(position) LIMIT 1;"}` → `BAD_USER_INPUT: … type error: ABS expects a number` (GraphQL `queryShell` twin: same refusal, engine-level, all surfaces).
- Stock control: `bean-query /tmp/qa-stock.bean "SELECT abs(position) LIMIT 1;"` → `3000.00 USD`.
- Matrix (MCP vs stock): `neg(amount)` both accept; `abs(number)` both accept; `abs(amount)` both refuse; `round(position,2)` both refuse; `abs(int)` MCP-only superset. Only `abs(inventory)` splits — and only `neg(inventory)` is documented.

## Expected
Either the engine accepts `abs(inventory)`, or `ENGINE_GAPS` gains an `ABS expects a number` entry naming the accepted spelling (`abs(number(units(position)))` per posting), with a `verify-rustledger` pin and an engine-gaps test mirroring the NEG one. Owner decides which.
