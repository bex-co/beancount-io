## Objective

Use the fixture to find nested objects whose handlers return keys the schema forbids with `additionalProperties: false` (for example `newLedgerErrors`), and fix each at the schema.

## Context

- w23/077 fixed the error envelope; this audits every other object.
- Do not loosen to `additionalProperties: true`; declare the keys.

## Steps

1. Run the fixture; list each mismatch.
2. Declare the key on the right schema.
3. Re-check the size budget.

## Files

- backend-cluster/backend-v2/src/features/ai-agent/tools/

## Acceptance criteria

- [x] Fixture passes for every tool
- [x] No schema was widened to accept unknown keys

## Out of scope

- Changing handler return shapes

## Result

Audit found no second mismatch. Object literals are excess-checked by TypeScript against the schema's type, so a key can only leak through a spread or a returned variable. Every such MCP site was read: `appendLedgerText`, `addLedgerEntries`, `renameLedgerFile` and the three source-slice tools spread service results whose keys are all declared or destructured away (`files`, `dryRun`, `validation`, `includedFiles`); the four handlers that return a service result untouched (`createLedger`, `previewLedgerSetup`, `parseFile`, `generateTempAssetUploadUrl`) were probed with a type-level excess-key check and each reports none. That check stays as a compile-time guard in `mcp-output-conformance.test.ts` (it fails `yarn typecheck` when a service result gains a key its published schema lacks; verified by swapping a schema). No schema was widened. The in-app `structuredBqlOutputSchema` is not an MCP tool and was not audited. Deviation: no handler fixtures for the ten remaining validation tools; their shared item is covered by t002's published-schema check.
