# Small Journal amounts become invalid Beancount scientific notation

**Severity:** major. **Owner:** backend-cluster/ledger. **Estimate:**45–60 minutes.
**A2:** a valid fractional amount should produce an entry the ledger can parse.

Production `https://beancount.io`,2026-09-08,Chrome152,English/light,
1440×1000 and390×844. QA session, public `open_ledger/minimax`.
Local HEAD`a315c273`, fetched main`afb36a9b`, relevant source unchanged;
deployed SHA unverified. Live mutation attempts were aborted before transmission.
The actual serializer/parser failure was proved locally; production commit
behavior remains unverified.

1. Open `/ledger/open_ledger/minimax/journal?lang=en&action=new-entry&directive=transaction`.
   Select Expenses:CostOfRevenue and Assets:Current:Cash, keeping MUSD.
2. Enter **0.00000001** and **-0.00000001**. Blur the inputs and click Create
   Transaction Entry. The enabled form prepares units.number **1e-8/-1e-8**.
3. Repeat fresh at both widths. On the Balance tab, choose Assets:Current:Cash
   and enter **0.00000001**. Create Balance Entry prepares amount.number
   **1e-8**, at both widths and on fresh repeats.
4. Live controls with **0.000001** prepare the ordinary decimal unchanged in
   both forms. Twelve documents returned200 with zero page exceptions or
   unexpected mutation operations. All contexts closed; no accepted writes.

These wire numbers are valid decimal input. The ledger OpenAPI Amount.number
accepts number or string. This repository's vendored `fava.file.format_entries`
with Beancount3.2.3 Decimal inputs renders1e-8 as **0.00000001 MUSD**, which
parses without errors.

The actual local `entryInputToText` instead emits **1e-8 MUSD**, and pinned
rustledger-WASM0.21.0 rejects that generated text with a LOAD parse error.
Its recovered balance reads1 instead of0.00000001 and reports a secondary
assertion failure. This is local parser recovery, not an observed production
balance change. A plain0.00000001 control is valid.

Fourteen actual serializer→WASM controls cover transactions and balances:
1e-8,-1e-8 and1e+21 fail; plain0.00000001,0.000001,1.2300 and0 pass. Balance
fixtures have matching prior-day funding. Twelve Python/Fava controls,
including those exponent inputs, all pass. The existing0.21.0 archive's SHA512
was rechecked against its exact registry version. Actual source was loaded
through existing jiti without installing dependencies or editing product code.

Root and call path:

- Dashboard `src/features/journal/components/new-directive-dialog/transaction-form.tsx:239`
  and `balance-form.tsx:86–90` use parseFloat(...).toString(), selecting
  exponential notation. This is the live trigger; a client-only workaround
  would leave the ledger's numeric input contract broken.
- Gateway `src/features/ledger/service/ledger-entry-service.ts:260–269,311`
  forwards the numbers. The actual ledger HTTP handler is
  `backend-cluster/ledger/src/api/entries.ts:33–41,58–74`; it maps each wire
  row into entryInputToText, then appends the rendered text at98–104.
- `backend-cluster/ledger/src/foundation/rustledger/entry-build.ts:29–33`
  incorrectly assumes verbatim numeric input matches the Python builder.
  Numeric mappings at84/90/113/131 and custom values at52/56 retain exponents.
- `journal-serialize.ts:455,470,576,630,685` interpolates those numbers into
  Beancount text. The directive-limit count does not normalize syntax; no
  accepted write was invoked to establish the downstream production outcome.
