# Read-only account filter offers Create and sends users to a blocked screen

Severity: minor. Estimate: 25m. Package: mobile. A2 — searching a public example should not offer an action that its permissions forbid.

Environment: September 10 and fresh September 11 repeat at HEAD f943005d; native build 1.20260906.47/current JS, iPhone 17e iOS26.5, English/System/light/default-large. Signed-in QA at https://beancount.io, public open_ledger/example. Fresh GetLedger permissions are admin:false, pull:true, push:false.

Repro: Transactions → Filters → All accounts → search for a nonexistent account such as QaNoSuchAccount20260910. Under No matching accounts, the picker offers an enabled Create row. Tap it: the app opens the Ledger screen saying “This ledger is read-only. Choose a ledger you can edit to make changes.” The account form does not mount. After terminating/relaunching and repeating through Filters, the Create option and blocked destination recur (the repeat needle was QaNoSuchAccount2026091, also no match). Back returns to the picker; clearing search restores the accounts, and choosing Assets:US:BofA:Checking correctly fills the filter draft.

Expected: read-only users can search/select existing accounts, with an honest no-match state and no enabled creation action. Actual: a normal read-only filtering journey advertises an impossible next step. This is misleading navigation, not an authorization bypass: the destination write guard works, and no creation was submitted.

Root cause: mobile/src/screens/account-picker-screen/account-picker-screen.tsx:324 makes showCreateRow depend only on a nonempty query and zero visible sections; render at418 and onCreate at326 route to Open Account without checking ledger write access. app/(app)/open-account.tsx wraps the destination in LedgerWriteGuard, producing the observed dead end. Accounts screen at118 already gates its Open Account header action with canWrite, providing a correct source and native control.

Fix: gate the shared picker's create affordance on resolved write permission, while preserving search and selection for read-only users. Loading/error/denied permission states must not flash an enabled Create action. Retain the destination guard for deep links and permission changes. Preserve the existing writer create flow; add focused coverage for writer/read-only/loading cases. No backend change or new dependency is needed.

Blast radius: shared picker callers include transaction filters, add-transaction next-step source/destination, quick-add account selection and multi-posting selection. The real read-only Filters caller was tested; write-flow callers are source-traced only and must retain current behavior. The existing-account control selected the right draft without a write. Permission expiry/races, successful writer creation, Android and physical devices were not exercised.

Evidence: mobile/tmp/qa-2026-09-10/filter-no-match-create.jpg and filter-create-readonly-guard.jpg; mobile/tmp/qa-2026-09-11/picker-readonly-create-repeat.jpg, picker-readonly-guard-repeat.jpg, picker-clear-control.jpg, picker-existing-selected.jpg and example-access.json.
