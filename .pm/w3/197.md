# The file editor warns about unsaved changes when there are none

**Minor · 30–45m · dashboard.** A2: a "Leave site?" prompt that fires when nothing was typed teaches users to dismiss the one that matters.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), English/light, 1440×1000, authenticated QA account with write access on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. Read-only — nothing was typed and nothing was saved.

Two clean-room reproductions, each on a fresh load with **no keystrokes at all**:

1. Open `/ledger/<owner>/example/files/new/main` (Create File). Both the filename input and the content editor read `""`. Navigate away → the browser's `beforeunload` "Leave site?" dialog fires.
2. Open `/ledger/<owner>/example/files/blob/main/README.md` and click **Edit**. Type nothing. Navigate away → the same dialog fires.

Expected: the native prompt appears only when there is unsaved work — which is exactly what completed [m29](./done/m29/README.md) specified: *"Reload/unload uses the existing platform confirmation while a draft is dirty."* Actual: it appears unconditionally whenever either surface is open.

Root: both call sites pass the literal `true`.

- `dashboard/src/features/ledger-editor/create-file/index.tsx:68-78` — `useBlocker({ shouldBlockFn: () => hasDraft, enableBeforeUnload: true, withResolver: true })`
- `dashboard/src/features/ledger-editor/file-editor/components/ledger-file-view/file-edit-mode.tsx:72` — the same `enableBeforeUnload: true`

The dirty check already exists and is already correct for router navigation: `create-file/index.tsx:67` computes `hasDraft = filename.trim() !== "" || content.trim() !== ""`, and `shouldBlockFn` consults it — so in-app navigation behaves properly. Only the native unload path ignores it. The installed router supports the fix directly: `node_modules/@tanstack/react-router/dist/esm/useBlocker.d.ts:35` declares `enableBeforeUnload?: boolean | (() => boolean)`.

Fix: pass the dirty predicate instead of the literal at both sites — `enableBeforeUnload: () => hasDraft` (and the file editor's equivalent dirty flag). Keep `shouldBlockFn` and the `allowNavigationRef` escape hatch exactly as they are; this changes only when the *native* prompt is armed. Owning package: `dashboard` only; no dependency, API or schema change.

Blast radius: the two call sites above are the only `enableBeforeUnload` usages in the package (`grep -rn "enableBeforeUnload" src` returns exactly those two lines). Both are covered by m29's shipped behavior, so re-run that milestone's dirty-draft journeys after the change — a draft that *is* dirty must still prompt on reload and on close, and confirmed departure must still discard it.

Adjacent states: a draft that was typed and then cleared back to empty should stop prompting; saving should clear the dirty state and stop prompting; the Cancel button's own confirmation flow (m29's work) is unchanged.

Dedupe: searched every queue including `done/` for beforeunload, unsaved, draft and leave-confirmation terms. Completed [m29](./done/m29/README.md) is the owner of this behavior and its DoD is what this violates — a residual of that milestone, not a new historical group, and too small (≤1h, two lines plus tests) to reopen it as a milestone. Completed `179` is a mobile missing-file state. My note [196](./196.md) is the same Create File page's *filename validation* — a different defect on the same screen; coordinate the two edits.

Not deployment lag: `git show HEAD` confirms `enableBeforeUnload: true` at both paths on current main, and the most recent commits touching these files (`53b0babb`, `baee2ce5`, `7f4bf483`) do not change it.

Unverified: the dirty-draft prompt itself (not re-exercised in this pass), the Upload Files flow, other locales, narrow viewport, and the patched behavior.
