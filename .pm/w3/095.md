# Mobile account journal drops the sign of negative running balances

**Severity:** minor. **Owner:** mobile. **Estimate:** 30–40 minutes.
**A2:** an account's running balance remains trustworthy when it crosses zero.

Environment: 2026-09-08, production https://beancount.io API, mobile HEAD
`a623f745`, native 1.20260906.47 on iPhone 17e / iOS 26.5, English/light,
390×844 logical, authenticated reader of public synthetic `open_ledger/example`.
No production writes.

Repro, repeated through native navigation after terminate/relaunch:
1. Open Accounts, expand US:Vanguard and tap Cash. The table shows -$0.02.
2. The Cash detail header also shows -$0.02.
3. Its latest August 14, 2017 row has change -$150.02 but `Balance: $0.02`.
4. The next row correctly shows change -$100.01 and `Balance: $150.00`.

Expected: the first running balance is `-$0.02`, preserving the negative asset
balance. Actual: it appears positive even though the header and source agree it
is negative. This is not a convention for presenting liability debt as positive:
the reproduced account is an Asset account and the same screen already signs
its headline correctly.

Live GetLedgerAccountJournal variables: ledgerId `open_ledger/example`, query
`{account:"Assets:US:Vanguard:Cash",offset:0,limit:20,with_children:true,conversion:"at_cost"}`.
Successful response has total 277. Latest item hash
`13a84292f04f253ed521beb85ba63b9f` has change `{USD:"-150.02"}` and balance
`{USD:"-0.02"}`. Next item has change `{USD:"-100.01"}` and balance `{USD:"150.00"}`.
The precise source slice for the latest transaction is also preserved in the
entry-context control from w3/094.

Trace: ledger `src/foundation/rustledger/journal-running-balance.ts:491` adds
postings into a LotInventory and returns its signed reduction at 529. Journal
service at 726 passes row.balance through; backend-v2's journal service at 260
also preserves it. Mobile `selectAccountJournalRows` resolves balance without
changing its sign (`src/screens/account-detail-screen/selectors/select-account-journal.ts`).
`components/account-entry-row.tsx:107` then calls unsigned
`formatMoneyWithCurrency(row.balance,currency)`. In `src/common/number-utils.ts`,
that formatter delegates to groupThousands, which applies Math.abs at 56.
The same row already uses `formatSignedMoneyWithCurrency` for change at 104.

Fix: use the existing signed currency formatter for the running-balance label,
without a plus prefix for positive/zero balances. Preserve grouping, currency
symbol/code fallback and the independent change styling. Do not change the
unsigned helper globally: other callers explicitly add a sign or intentionally
show magnitudes. No backend/schema/calculation change is required.

Blast radius: AccountEntryRow has one production consumer, account-detail-screen
at 242; every account-detail route uses it. The unsigned helper also serves Home
budgets, budget groups, merchant totals, report category breakdowns, the editor's
zero indicator and date-section totals. The latter explicitly prepend a sign,
so a global helper change would double-prefix negative values. Those other
surfaces have not been established as failures by this repro. Working controls:
the account table uses formatSignedMoneyWithCurrency at 254, the detail header
retains -$0.02, and the positive 150.00 row and signed entry changes are correct.

Acceptance: normal navigation and relaunch both show Balance: -$0.02 on the
latest row while the next row remains Balance: $150.00. Add meaningful coverage
for the actual balance rendering path with negative, zero, positive and unknown
currency-code values; testing only the existing signed helper would miss the
wrong call site. Preserve loading, paging and error states. Other currencies,
negative liabilities, offline/expired access, Android and physical devices are
source-scoped but not live-verified here.

Dedupe: searched all open/completed records and open milestone headings for
negative balances, running balances and lost signs. w3/016 is the Reports net
profit sign conversion; w3/025 is dashboard table clipping, and w3/094 is posting
quantity precision. No overlap. Current unsigned call appears in 95e47224, but its
parent already uses groupThousands(row.balance); targeted history traces that
path to 80bf63f4. Thus this is not claimed as a regression from the currency-label
change. Current local source retains it; no known landed local repair.
