# Holdings shows unrealized profit % to 29 significant digits

**Minor · 45–60m · dashboard.** A1: a portfolio table an agent or reader scans must show a percentage they can compare at a glance.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), English/light, authenticated QA account on its own synthetic `example` ledger, 1440×1000. Local/fetched main `84231f9c`; deployed SHA unverified. Read-only.

Open `/ledger/<owner>/example/holdings` and read the **unrealized_profit_pct** column. Rows render as `49.144717659636505005345514630`, `32.643270809923070274008125160`, `10.007527151510806838954801250`, `0.9008120458953874478087911400`, `35.796805980292218824328916070`. The column is unreadable and unsortable by eye, and it stretches the table. Expected: a percentage rounded for display (two decimals is the convention used elsewhere in the dashboard). Actual: the raw engine Decimal, verbatim.

API control — the exact BQL the page issues (`holdings-statement.ts:8`) returns HTTP 200 with `{"name":"unrealized_profit_pct","dtype":"Decimal"}` and the row value `"14.423220316680556164744067720"` for `Assets:US:ETrade:GLD`. So the full precision comes from the engine and the dashboard prints it as-is; this is a display decision, not a computation defect.

Root: `dashboard/src/features/ledger-data/holdings/utils.ts:59-64` — `formatDecimalCell` returns any decimal string "verbatim" by documented design, and `formatNumber` (`:82-83`) is just an alias for it. `holdings-table.tsx:172-174` applies it to every cell. That losslessness is **correct and deliberate for quantity and amount columns** (its docstring calls out small crypto units such as `0.004 ETH` that must not round to zero) — do not remove it. The gap is that a *derived ratio* column gets the same treatment as a holding quantity.

Fix: round only the derived percentage column for display, leaving every quantity, cost, price and value column losslessly verbatim. Either round in the display layer keyed on the `unrealized_profit_pct` column name, or round in the BQL statement itself — pick one and apply it to all four statement variants in `holdings-statement.ts:8,19,31,41` (Holdings, by Account, by Currency, by Cost Currency). Keep the sign, keep a genuine `0`, and keep the CSV export consistent with the screen (decide deliberately whether the export keeps full precision; if it does, say so in the column header or the note). Owning package: `dashboard` only — no API, schema or engine change.

Blast radius: `formatDecimalCell` / `formatNumber` are used for **every** Holdings cell and by `csvObjectToString`, so a blanket rounding change would silently damage quantity columns — that is the trap this note exists to flag. Scope any change to the ratio column.

Adjacent states: a zero-cost holding (`safediv` guard) must still render `0` rather than an error or a long zero string; a null cell must stay empty; the `isEmpty` row-pruning behavior at `utils.ts:100+` must not change which rows appear.

Dedupe: searched every queue including `done/` for `unrealized`, `profit_pct`, holdings precision and decimal-display terms — no existing item. Completed `110` was the shared number formatter/hydration repair and `116` was journal display precision; neither covers this column. Not a regression: `formatDecimalCell`'s verbatim rule is the documented intent, and no later change on fetched main addresses the ratio column.

Related but separate: `m37` repairs raw-JSON inventory cells in the **BQL query** result table and export. This note is the Holdings table's ratio column and must not be folded into that milestone's shared-formatter move — if `m37` lands first, keep its shared formatter losslessly verbatim and add the ratio rounding on top.

Unverified: other locales, other ledgers, narrow viewport, the Holdings CSV export contents, and the patched behavior.
