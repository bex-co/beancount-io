# `bea ask` is outside the control-character sanitizer that `w3/392` closed: the write-approval panel, the answer, and the appended ledger text all pass C0 through

**Severity:** major (the consent surface a ledger write is gated on can be
repainted by the text being approved; the same bytes are then persisted).
**Owner:** cli. **Estimate:** 45–60 minutes. **A1:** the write-approval panel is
the only gate between an AI-proposed directive and the user's books, so what it
shows has to be what the file will contain.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, synthetic ledger, real PTY, and a **local stub model server**
(`BEA_API_URL` pointed at 127.0.0.1) — no hosted AI call is needed to reproduce.

## What is wrong

`w3/done/392` established the invariant and its threat model in
`cli/src/bea_engine/ledger/text.py:13-19`: C0/C1 control characters "must never
reach a ledger file or a terminal", because a cursor-up plus erase-line sequence
"erases the row printed above it, so an import preview can show something other
than what `--apply` will write". That fix lives in `single_line()`, which the
**field-by-field** writers (`bea add`) and readers (`output.table`, `bea list`,
the `query` text used as an `ask` tool result) all go through.

`bea ask` does not go through it anywhere:

1. `cli/src/cli/ask/repl.py:157-171` builds the approval panel with
   `Text.append(directive, style="green")`. Rich emits the string verbatim, so
   control characters inside a directive the model proposes execute in the
   user's terminal while the panel is on screen — the panel can repaint itself
   and what is read need not be what is in the text being approved.
2. `cli/src/cli/ask/agent.py:155-185` → `bea_engine/ledger/appending.py` appends
   the raw directive text. Nothing escapes C0, so the bytes land in the `.bean`
   file. The typed path refuses to do this: the same payload through
   `bea add -n …` is written as a visible `\xNN`.
3. `cli/src/cli/commands/ask.py:79` / `repl.py:234` print the model's answer
   through `rich.markdown.Markdown`, also unescaped, so answer text is a second
   raw-control channel.

Observed, driving a real PTY: the emitted bytes contain the sequence verbatim
inside the panel, the approved append leaves `\x1b` bytes in `main.bean`, and
`bea check` exits 0 on the result. Nearby working control in the same run: the
`run_bql_query` tool result built from that ledger comes back **escaped**
(`\x1b[…]` as literal text), which is the 392 fix doing its job on the read
side and shows the gap is confined to the `ask` write/render path.

Evidence for this run (local, not on this board): PTY captures and fixtures
under `.tmp/qa-2026-09-26/cli-run10/logs/pty-esc.raw`,
`.../logs/pty-answer-esc.raw`, and the fixture ledger under
`.tmp/qa-2026-09-26/cli-run10/fixture/`. The payload class is the one already
described in `w3/done/392` (cursor-up + erase-line CSI); this note does not
restate it. No code execution is claimed and there is no remote vector: the
text comes from the model, which in turn can be steered by narrations, payees,
metadata or note text already in the ledger.

## Expected

The `ask` surfaces obey the invariant the rest of the CLI now obeys:

- the approval panel renders the proposed directive with C0/C1 (except the
  newlines that structure a directive) escaped to a visible `\xNN`, so the panel
  cannot be repainted by its own contents;
- the model's answer is rendered with the same neutralization;
- the raw-text append path refuses or escapes control characters, so a `.bean`
  file written by `ask` holds no `\x1b` — matching `bea add`.

## Fix

Escape in the engine append path (`bea_engine/ledger/appending.py`, where the
directive text is parsed — a directive body needs `\n` and spaces and nothing
else from C0) so no writer can persist control bytes, and neutralize on the two
`ask` render paths (`ask/repl.py` panel, both Markdown answer prints). Keep
escaping rather than deleting, per 392's reasoning. Decide deliberately whether
a control character in proposed directive text is an outright rejection
(`Write rejected: …`) — for a write the user is being asked to consent to,
refusing is defensible and simpler to test.

Regression coverage: a stub-model PTY test asserting (a) the bytes the panel
emits contain no raw `\x1b`, (b) after approval the ledger bytes contain no
`\x1b`, (c) an answer containing control characters is emitted neutralized;
plus a unit test pinning the append path's refusal/escaping. Assert on emitted
bytes, not rendered text — a piped capture under-reports this (392's wrinkle).

## Blast radius

`ask --print` cannot write (verified: the tool returns "Write skipped"), so the
persistence half is interactive-only; the answer-render half affects both modes.
`bea add`, `bea import`, `bea list` and `query` tool results are already
sanitized (verified in this run). `--json` is unaffected (`ask` has no JSON).

**Resolved 2026-09-27** — fixed in `w3/m50` ("Make the `ask` consent surface
honest and its session survivable"): the engine append path refuses control
characters in raw directive text, the approval panel and both answer prints
neutralize them, the panel names the destination the dry run resolved in a body
line that cannot be trimmed, a Ctrl-C or a failed turn costs one turn instead of
the session, and `ask` sets its own per-question request budget and retells the
AI SDK's failures in the CLI's own words. Regression coverage in
`cli/tests/test_ask_consent_surface.py`,
`cli/tests/test_ask_session_resilience.py` and the shared stub-model/PTY harness
in `cli/tests/conftest.py`. Before/after evidence was captured locally against a
local stub model server on a real terminal (no hosted AI calls); it is not on
this board.
