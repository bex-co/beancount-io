# A tool-calling loop in `ask` spends 50 hosted requests and then fails with pydantic-ai's internals and a third-party docs link

**Severity:** major (raised from minor 2026-09-26 — see the run12 addendum: the same leak fires live, on an ordinary question, via a second exception type). **Owner:** cli. **Estimate:** 25–40 minutes. **A1/A3:** the
one command that costs money per call has no cost-aware ceiling of its own, and
when its borrowed ceiling trips, the user is handed the SDK's vocabulary
(`request_limit`) and a link to another project's documentation.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR`, synthetic
ledger, closed stdin. Driven by a **local stub model server** (`BEA_API_URL` at
127.0.0.1) that answers every request with another `run_bql_query` tool call —
a model that never stops calling tools. The loop and the resulting message are
the CLI's own behavior; the stub only supplies the model's side.

## Repro

Stub returns, for every request, one tool call (`run_bql_query`, any valid
query) and never a final answer.

```sh
bea --file main.bean ask --print "loop"
```

Observed: 50 requests are sent (counted at the stub), each carrying the full
growing message history, and then

```
Error: The next request would exceed the request_limit of 50. Consider raising
the limit, or see the docs on usage limits for budget-aware patterns:
https://ai.pydantic.dev/agent/#usage-limits
```

exit **1**. Nothing of the 50 turns is shown or kept — no partial answer, no
note of what the model had been doing, no indication that the ledger was never
modified (it was not).

## Expected

`bea ask` owns this ceiling rather than inheriting pydantic-ai's default, and
reports tripping it in the CLI's own words: what happened ("the model kept
calling tools without answering"), that nothing was written, and what to do
(rephrase, narrow the question). No third-party limit name and no third-party
URL in user-facing output — `cli/src/cli/errors.py` exists precisely so hosted
failures read the same way everywhere, which `translated_failures`
(`cli/src/cli/ask/agent.py:84-96`) already does for HTTP status. This exception
is not an HTTP failure, so it falls past that translation into the catch-all at
`cli/src/cli/main.py:160-161`.

## Fix

Pass an explicit `UsageLimits` to `agent.run_sync` in
`cli/src/cli/commands/ask.py:78` and `cli/src/cli/ask/repl.py:228` — a
deliberate request/tool-call ceiling, chosen for cost rather than borrowed — and
catch `UsageLimitExceeded` in `translated_failures`, mapping it to a `BeaError`
whose message names the situation and confirms nothing was written. Related but
separate: `w3/446` asks for a `max_tokens` cap on each request; this is the cap
on the number of requests. Both belong in one "give ask explicit budgets" pass.

Regression coverage: a stub that always returns a tool call must produce the
CLI's own message, the documented exit code, and no ledger change; assert the
request count stops at the configured ceiling.

## Dedupe

Searched `.pm/**/*.md` including `done/` and `blocked/` for usage-limit,
`request_limit`, pydantic-ai and tool-loop terms. `w3/446` (open) is the missing
`max_tokens` cap on a single request — adjacent, not the same limit. `w3/445`
(open) is the raw JSON envelope reaching stdout and `w3/450` is Python reprs in
`cloud ledger show`; both are output-hygiene items on other surfaces, and
neither covers an unmapped SDK exception from `ask`. `git log -S"UsageLimits"`
and `-S"usage_limits"` in `cli/` return nothing — the limit has never been set.

## Unverified

Whether a real model ever loops this way (not tested; the QA account's AI quota
was exhausted during this run). Whether the hosted proxy bills the retried
requests.

## Extended 2026-09-26 (run12) — the same leak, now observed **live** on an ordinary question

This note was filed from a stub that never stopped calling tools, which is a
contrived model. The identical defect — a pydantic-ai exception escaping past
`translated_failures` into the catch-all at `cli/src/cli/main.py:160-161`, so the
user reads the SDK's vocabulary and a link to another project's documentation —
fires on the real service with no stub involved, from a second exception type.

HEAD `8cd9732b`, `bea` 0.3.0, macOS 26.5.1 arm64, isolated `BEA_CONFIG_DIR`,
stdin closed, live hosted AI (`gpt-4o` via the beancount.io proxy), 11-transaction
synthetic ledger:

```sh
bea --file multi.bean ask --print "What is my single largest expense transaction, and how much was it?"
```

Two of four consecutive runs, stderr, exit **1**:

```
Error: Tool 'run_bql_query' exceeded max retries count of 2. Consider raising the
retry limit, or see the docs on tool retries:
https://ai.pydantic.dev/tools-advanced/#tool-retries
```

That is `UnexpectedModelBehavior` from the tool's `retries=2`
(`cli/src/cli/ask/agent.py:138`), and it reads exactly like the `request_limit`
message this note is about: a third-party limit name, a knob the CLI does not
expose (there is no flag to raise the retry limit), and an `ai.pydantic.dev` URL
in front of a paying user. Deterministically reproducible with no quota by
pointing `BEA_API_URL` at a stub that always returns
`run_bql_query("SELECT x FROM y ORDER BY LIMIT")` — three requests, then that
message.

So the fix should not special-case `UsageLimitExceeded`. Translate the
pydantic-ai exception family once, in CLI vocabulary: what happened, that nothing
was written, what to try. The session-lifetime half of the same trigger is in
`w3/449` (same five lines of `repl.py`); do both in one pass.

**Severity raised from minor to major** on the strength of the live rate: about
one in two runs of a plain analytical question, each one costing the hosted tokens
already spent on the turn.

**Resolved 2026-09-27** — fixed in `w3/m50` ("Make the `ask` consent surface
honest and its session survivable"): the engine append path refuses control
characters in raw directive text, the approval panel and both answer prints
neutralize them, the panel names the destination the dry run resolved in a body
line that cannot be trimmed, a Ctrl-C or a failed turn costs one turn instead of
the session, and `ask` sets its own per-question request budget and retells the
AI SDK's failures in the CLI's own words. Regression coverage in
`cli/tests/test_ask_consent_surface.py`,
`cli/tests/test_ask_session_resilience.py` and the shared stub-model/PTY harness
in `cli/tests/conftest.py`. Before/after evidence was captured locally against a
local stub model server on a real terminal (no hosted AI calls); it is not on
this board.
