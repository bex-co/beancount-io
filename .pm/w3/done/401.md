# `bea --strict query` silently opens a lenient interactive shell

**Minor · 45–60m · cli · A1.** `--strict` refuses a partial answer for a
one-shot query but is dropped when the same command opens the interactive
shell. Adding `--no-errors` then hides even the failed balance assertion.

Found 2026-09-21 using checkout `bea 0.3.0` (`cli/.venv/bin/bea`), Python
3.13.0, macOS 26.5.1 arm64. Two pristine fixtures and fresh PTY processes
reproduce the failure; captures record HEAD and unrelated concurrent edits.
Query code is unchanged from `358b17ce`. Only synthetic books were used.

## Reproduce and controls

Save `/absolute/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-02 * "Lunch"
  Assets:Cash -10 USD
  Expenses:Food
2026-01-03 balance Assets:Cash 0 USD
```

The balance assertion intentionally fails: cash is -10 USD, not 0 USD.

```sh
bea --strict --file /absolute/main.bean query 'SELECT sum(position)'
# exit 1, no stdout; stderr names the balance failure and --allow-errors
bea --strict --file /absolute/main.bean query
```

The second command opens a prompt instead of refusing. Enter:

```text
SELECT account, sum(position) GROUP BY account
.exit
```

It prints Cash **-10 USD**, Food **10 USD**, and exits **0**. Stderr prints
the failed assertion, exactly as a lenient session would. Repeat with
`bea --strict --file /absolute/main.bean query --no-errors`: `SELECT count(*)`
prints **2**, exit **0**, with completely empty stderr.

Expected from `cli/docs/USAGE.md:86` and the read-policy paragraph: `--strict`
refuses partial answers even in a terminal, unless `--allow-errors` explicitly
opts in. Hiding the error banner must not disable validation. Refuse this
invalid startup with exit 1 and the existing diagnostic before answering.

Working controls: `--strict query --allow-errors` opens and returns results
with the error banner; removing the failed balance produces a working strict
session with no errors. Global `--json query` without a query correctly exits
2 in a PTY because JSON implies no input; it does not enter this bad branch.
Every fixture is unchanged before/after, and no subprocess times out.

## Cause and fix scope

`cli/src/cli/commands/query.py:205` returns from the no-query/TTY branch by
launching `shell --file ...` with rendering options. It never reaches the
`ctx.strict_reads()`/`allow_errors` decision at lines 224–225.
`cli/src/bea_engine/main.py:451` `shell` has no read-policy argument, and
`bea_engine/query.py:201` `interactive` constructs the shell and calls
`cmdloop()` without the `_gate` used for one-shot answers. `--no-errors` is
forwarded as a display flag, so it suppresses the only remaining evidence
of the invalid ledger.

Carry the resolved strict/allow-errors policy into interactive execution and
enforce it before returning data from an invalid load. Preserve default
lenient terminal use and the explicit `--allow-errors` override. Keep display
suppression separate from validation. Add a real PTY regression for strict
invalid startup, the quiet variant, valid startup and explicit override.

Caller search covers the sole frontend `shell` launch, helper `shell`
registration and `bql.interactive` call. One-shot text/JSON use separate gated
helpers and are working controls. Reloading a ledger that becomes invalid
during a session, stdout redirected while stdin stays a TTY, other platforms
and native `--source` delegation remain unverified. CLI-only; no API changes.

---

**Resolved 2026-09-22** — `--strict` now refuses an interactive session on a
ledger that does not load, before the prompt appears.

The no-query/TTY branch launched the engine's `shell` command with rendering
options only, so the frontend-resolved read policy never reached it. Three
small changes carry it through: `cli/src/cli/commands/query.py` appends
`--allow-errors` to the shell argv under the same condition the one-shot path
uses, the engine's `shell` command accepts it, and `bea_engine.query.interactive`
runs the existing `_gate` after the load and before `cmdloop`.

The engine's `shell` error handler now also wraps `bql.interactive`, so the
refusal reads as `error: Ledger has 1 error(s). Pass --allow-errors to report
anyway.` with its detail line, rather than the rich traceback my first attempt
produced. Its details are printed too, matching the one-shot rendering.

Verified in real PTYs, with exit codes:

| invocation | result |
| --- | --- |
| `--strict … query` | exit 1, refusal, no prompt |
| `--strict … query --no-errors` | exit 1, refusal, no prompt |
| `--strict … query --allow-errors` | exit 0, banner shown, session answers |
| `… query` (no `--strict`) | exit 0, lenient as before |
| `--strict` on a clean ledger | exit 0, session answers |

The `--no-errors` row is the one that mattered most: display suppression no
longer disables validation, and the refusal names the error even with the
banner off — where before the session was completely silent about an invalid
ledger.

Regression coverage is `cli/tests/test_strict_interactive_shell.py`. Reverting
the fix fails exactly the two strict-invalid cases while all four controls pass
either way. `cd cli && make check-all` passes (1837 tests).

Gate note: the first run had
`tests/test_release.py::test_customer_smoke_runs_against_the_installed_cli`
fail; it passes in isolation and passed on a clean rerun of the whole suite.
That test builds and installs the CLI and is load-sensitive under `-n auto` —
the same flake recorded in w3/396, unrelated to this change.

Unverified, as in the note: reloading a ledger that becomes invalid mid-session
(`.reload` re-attaches without re-gating), stdout redirected while stdin stays
a TTY, native `--source` delegation, and other platforms.
