# Ctrl-C during `bea format --in-place` can leave the ledger 0 bytes long

**Severity:** major (total data loss of the interrupted file). **Owner:** cli.
**Estimate:** 30–45 minutes. **A1/A2:** pressing Ctrl-C on a formatting run
that is taking too long can empty the ledger. Every other `bea` write is
staged and atomically replaced precisely so an interrupt cannot do this.

Found by continuous CLI QA 2026-09-26, `uv run bea` 0.3.0 at HEAD `8cd9732b`,
Darwin 25.5.0, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, synthetic ledger,
closed stdin, SIGINT delivered to the process group as a terminal Ctrl-C would.

## Repro

Synthetic single-file ledger, 40 000 transactions, ~3.2 MB, deliberately
unformatted (three-space posting indent) so `format -i` must rewrite it. Two
accounts opened `2020-01-01`; each transaction is `YYYY-MM-DD * "tN"` with
`Expenses:Food 1.00 USD` / `Assets:Checking -1.00 USD`.

```sh
cp unf.bean main.bean
bea format main.bean --in-place &          # completes in ~1.47s on this fixture
sleep 1.41                                 # Ctrl-C while it is rewriting
kill -INT -$!                              # process group, as a terminal does
wait
wc -c < main.bean                          # 0
```

Harness result: 160 interrupted runs, offsets swept in 1 ms steps across the two
rewrite moments (1.400–1.417 s and 1.455–1.476 s), **3 runs left `main.bean` at
0 bytes**, exit 130 each time, no message on stdout or stderr. Hits landed at
1.409 s, 1.415 s (the `bean-format` rewrite) and 1.457 s (the CLI's own
`write_bytes`), so both writes in the path are exposed. Byte-level artifact
retained locally under `.tmp/`.

Controls that behave correctly:

- SIGINT anywhere in `bea add` on the same fixture: 6 offsets from 0.5 s to
  3.7 s, exit 130 every time, the file is either byte-identical to the original
  or contains the complete appended transaction — never partial — and no
  `.bea-*` staging file is left behind.
- SIGINT before the rewrite (offsets ≤ 1.40 s) leaves `format -i`'s input
  byte-identical.

Separately, interrupts in the middle band leave the file *fully* rewritten by
`bean-format` but without the CLI's own canonical-indent pass. Those files are
valid ledgers, so they are a convergence nit rather than loss, but a single
atomic replacement removes that state too.

## Expected

An interrupted `bea format --in-place` leaves each file either exactly as it was
or completely formatted, like every other `bea` write. Zero bytes is never a
valid outcome.

## Root cause

Two non-atomic truncating writes, neither staged:

1. upstream `bean-format --in-place`, launched by
   `cli/src/cli/commands/format.py` `_format_in_place` (~l.165) via
   `launch.capture_native("bean-format", [..., "--in-place", ...])`, opens each
   file for writing in place;
2. the CLI's own `file.write_bytes(fixed)` at `format.py:178`.

Either one truncates the destination and then writes; a signal in between
leaves it empty. Contrast `cli/src/bea_engine/ledger/write.py`, which stages
into `candidate_file` (`.bea-*.tmp` beside the original, fsynced) and replaces
atomically, and whose `sweep_abandoned_candidates` docstring already states the
intent that a signal must not damage the books.

## Fix

Give `format --in-place` the same staged-replace discipline: format into a
candidate file beside the original (reusing `ledger_write.candidate_file`) and
`os.replace` it into place, so no window exists in which the destination is
truncated. That means not handing the user's own file to
`bean-format --in-place` — copy to the candidate, format the candidate, then
replace — which also removes the middle band where only upstream's pass has
been applied. Blocking SIGINT around the replacement is a complement, not a
substitute: it cannot protect against SIGKILL or a lost power, and `os.replace`
does not need it.

Regression coverage: a test that formats through the staged path and asserts the
destination inode content is either the original or the fully formatted bytes,
never empty; and a test that a failure raised between formatting and
replacement leaves the original intact.

## Blast radius

Every `format --in-place` target: one file, a split-ledger root, and each file
of a recursive `format -i dir/` (whose per-file loop at `format.py:176–178`
repeats the same unprotected write for every file). `--check` and `--dry-run`
write nothing. `bea add`, `add transactions`, `import --apply` and `ask`'s
append are unaffected (verified above). The same missing discipline is what
lets a concurrent writer be clobbered — filed separately as w3/434; a staged
replacement plus the write lock fixes both.

Dedupe: searched `.pm/**` including `done/` and `blocked/` for
`format -i` / `--in-place` / SIGINT / interrupt / truncat* / atomic. w3/415 and
w3/426 are about `format -i` content and reporting; w3/done/390 is the
picklecache sidecar leak; w3/done/398, w3/done/401 and w3/done/412 are engine
write-path and export guards, all on the already-atomic side. `git log -S` on
`_format_in_place` shows only `5592d63a`.

**Re-verified 2026-09-26** (CLI QA consolidation round, run11) — reproduced
again from a pristine synthetic fixture in fresh processes on the same HEAD
`8cd9732b`, `bea` 0.3.0, macOS 26.5.1 arm64, isolated
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed.
Confirmed, with the mechanism now shown **deterministically** rather than by
timing luck. Polling the target's size for the whole duration of an
*uninterrupted* `bea format -i` run shows the ledger pass through **0 bytes
twice** every time — once for upstream `bean-format --in-place`, once for the
CLI's own `write_bytes` — in 4/4 trials:

```text
size transitions: 3228995 -> 0 -> 3308995 -> 0 -> 3228995
```

Firing SIGINT at the process group the instant the size reads 0 leaves the
ledger at **0 bytes with exit 130 in 5/5 runs**. Correction to the filed hit
rate: a blind offset sweep (662 interrupted runs, 4–5 ms steps across both
rewrite moments) hit **0** zero-byte outcomes this round, because each window is
only a few milliseconds wide — the filed "3 in 160" is fixture- and
machine-specific and should not be read as a stable probability. The
intermediate state the note already describes (upstream rewrite applied, the
CLI's canonical-indent pass not) reproduced 42 times in 200 runs.

**Resolved 2026-09-26** — Fixed. `bea format --in-place` now runs as `bea-engine format --in-place`: it aligns the bytes it read in memory, takes the same `lock_file` every other writer takes for every target, and replaces each file with one `os.replace` of a staged `.bea-*.tmp` candidate.
