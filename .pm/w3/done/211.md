# Keep long narration drafts visible above the native keyboard

**Minor · 40–60m · mobile.** A2: users composing a transaction must be able to see and correct the text they are entering.

Environment: Sep13,2026, HEAD84231f9c, native io.beancount.ios1.20260906.47(47), Expo57/RN0.86, iPhone17e/iOS26.5, English, default large text, System/light. Dedicated QA login against https://beancount.io, public open_ledger/minimax selected. Only an unsaved transaction draft was changed; no ledger mutation.

Reproduce through actual navigation: Home plus → Enter new transaction → Narration. Enter 24 newline-separated lines, `QA line 01 - draft only.` through `QA line 24 - draft only.`. The native helper asserts that the entire value matches, then tap an actual software keyboard letter. Only lines01–18 remain visible above the keyboard; line24 and the active caret are hidden. An upward native drag inside the visible text field leaves the same first18 lines displayed. The native value contains all24 lines plus the appended letter (`Z` in the first run). Terminate and relaunch, repeat the same blank-draft journey and type24 lines, then tap software `X`: the same failure occurs in fresh process28971. A direct XCTest screenshot independently agrees with Expo MCP's screenshot.

Expected: growing multiline text and the active insertion point remain visible above the keyboard; users can scroll to review and edit every line. Actual: accepted trailing text is visually inaccessible while the keyboard remains open. This is a display/editing failure, not demonstrated data loss. A prior two-line narration with quotes and a backslash displayed normally, survived the field's local Save/reopen with exact value, and disappeared correctly when the parent draft was discarded.

Source: `mobile/src/screens/multi-postings-transaction/narration-input-screen.tsx:21–28` enables multiline on shared `TextInputScreen`. `mobile/src/components/text-input-screen/index.tsx:35–46,181–226` places a content-sized TextInput in an ordinary View inside SafeAreaView, without keyboard avoidance or an explicitly bounded multiline scroll viewport; the separate ScrollView below is only for suggestions. Native AX reports the visible TextView region at x16/y117/358×392 with keyboard focus. Installed RN's `RCTTextInputComponentView.mm:362–369` sizes its native view from layout bounds, and `RCTUITextView.mm:60,212–215` enables scrolling and delegates scrollRangeToVisible to UIKit. Thus keyboard-aware sizing is missing at the application boundary; the exact native content-size/content-offset contribution remains unverified, and AX bounds alone must not be treated as those internal values.

Fix target: give multiline narration a viewport that respects the keyboard and supports scrolling to the selection as text grows. Preserve complete text, newlines, local field Save/Back behavior, suggestion selection and ordinary single-line Payee layout. Do not impose a narration length limit or disable text scaling to conceal the failure. Verify with native keyboard input and a long draft; a pure string test cannot catch this layout issue. No API change is indicated. Shared component callers searched: PayeeInputScreen (single-line, working synthetic payee control) and NarrationInputScreen (reproduced). Add/edit route aliases using Narration should receive coverage, but only New Transaction was exercised here.

Acceptance: after24 lines and another actual keyboard character, the newest text/caret is visible; swiping can reveal the first and final lines while the keyboard is open. Two-line and single-line controls still work, exact draft text survives local Save/reopen, and parent cancellation discards it. Check default and enlarged text and keyboard dismissal/reopening during implementation. No server Save is required for this regression.

Worth knowing for anyone re-testing this: the Simulator shows no software keyboard by default because its hardware keyboard is connected, which is what makes the documented `osascript` typing work. Toggle it at runtime with **⌘K** (`osascript -e 'tell application "Simulator" to activate' -e 'tell application "System Events" to keystroke "k" using command down'`); `defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool false` does not affect a running Simulator.
