# Open the receipt photo picker without requiring broad library access

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2: users can choose a receipt through the system picker without granting unnecessary access to their photo library.

September 11, 2026; HEAD f1965988/mobile7538fb0d; io.beancount.ios1.20260906.47; iPhone17e/iOS26.5; English/System-light/default large. Authenticated production session, public open_ledger/minimax. Actual native Home -> plus -> Scan Receipt -> gallery action. No image selected, uploaded or parsed; no ledger mutation.

1. With Photos permission denied, tap receipt-pick-library. The app shows “Photo library access is needed to choose a receipt. Enable it in Settings.” with only OK; no system chooser opens.
2. Relaunch PID80703 and repeat through the Home menu. The same blocking alert appears. Initial denied state and fresh repeat are captured. The earlier cross-test coordinate taps on permission alerts are not proof of which OS permission button was selected: automation attachment could dismiss those alerts. This finding concerns the resulting denied state and repeatable app gate.
3. Working control: reset only this app's photos permission, launch PID82074, open the same screen. A single native XCTest taps gallery, waits for the system Allow Full Access button, verifies its label/hittable state, and taps it. One test passes; the actual system Photos/Collections chooser then displays the six stock simulator images. Cancel returns to the receipt screen and Close returns Home. Reset only photos afterward and relaunch PID82480.

Expected: the image-only system picker opens without broad photo-library authorization, including when that authorization was declined. Actual: the app requests authorization first and returns early when denied, preventing the supported picker flow.

Root: mobile/src/screens/receipt-capture-screen/receipt-capture-screen.tsx:48–57 unconditionally calls requestMediaLibraryPermissionsAsync and returns unless status is granted before launchImageLibraryAsync({mediaTypes:["images"],quality:0.85}). This is the only caller of both APIs in src/app. Installed expo-image-picker/ios/ImagePickerModule.swift:65–67 launches the library without a permission guard; its non-editing library branch at96–97 constructs PHPickerViewController at151+. The app supplies no editing option. [Expo's current ImagePicker documentation](https://docs.expo.dev/versions/latest/sdk/imagepicker/) explicitly documents that launching the image library needs no permission request. This is the image picker, not direct PhotoKit enumeration or video editing/original-file access.

Fix: use the supported image-only system picker without this broad-library prerequisite; preserve cancel, asset handling, explicit upload, localized genuine picker errors and selected-ledger write guards. Check supported Android behavior before changing its permission handling; do not remove permissions needed by unrelated camera capabilities. Test denied/not-determined/granted Photos states reach the picker, Cancel preserves the capture state and selected images reach preview without uploading automatically. Keep actual upload/parse/persist verification on authorized disposable data. No dependency or backend change needed.

Dedupe: all .pm open/done searched for receipt/photo-library/PHPicker/permission combinations. No matching open item. w4/done/m4/t005 concerns ledger write authorization, a different permission layer; w2/m30 concerns upload/parse/quota failures after selection. git log -S traces the broad request to76289769;3ae25ee9 reworks capture and later a7c088d2 removes analytics without correcting it. Camera denial, camera hardware, limited-library selection, VoiceOver, Android and successful receipt upload remain unverified. Do not infer a camera-denial bug from earlier automation-disappearing alerts.
