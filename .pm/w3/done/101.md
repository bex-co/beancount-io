# Mobile picker confirms the first option instead of its displayed initial selection

Severity: minor. Estimate: 45–60 minutes, mobile. A2: checking a preference without changing it should preserve that preference.

Environment: 2026-09-09, main `7f4b6190`, rebuilt io.beancount.ios 1.20260906.47, iPhone 17e/iOS 26.5, local Metro 8083 with production API https://beancount.io. Authenticated QA session; this is a local settings operation and needs no ledger mutation.

Repro:

1. Set Theme to System, then terminate and launch the app. Settings must show System. Native setup/restoration used a real wheel scroll followed by Confirm, not injected app state.
2. Open drawer → Settings → Theme.
3. Wait for the wheel to settle with System centered and highlighted.
4. Do not scroll. Tap Confirm (`picker-confirm`).
5. Settings now shows Light. Expected System to remain selected.

Reproduced twice, including after fresh launch with the simulator in light appearance. First reproduction under dark system appearance visibly switched the app to light. Control: scrolling the wheel to System before confirming correctly saves System, and that survives relaunch. Cancel leaves the preference unchanged. Simulator accessibility action AXScrollDownByPage on the picker ScrollArea supplied the real scroll; ordinary item taps do not scroll this custom wheel and are not used as evidence of a selection change.

Evidence under `mobile/tmp/qa-2026-09-09/`: `theme-repeat-start.jpg` (System after relaunch), `theme-repeat-picker.jpg` (centered System), `theme-repeat-result.jpg` (Light after Confirm). Earlier `settings-system-dark.jpg`, `theme-confirm-unchanged.jpg`. Working control/restoration: `theme-scrolled-system.jpg`, `theme-system-restored.jpg`, `theme-final-scroll.jpg`, `settings-restored-final.jpg`. Local preference producer is themeVar, persisted through AsyncStorage; there is no corresponding GraphQL/REST operation. `picker-logs.json` contains an empty capture, not proof of no runtime errors.

Root cause: `mobile/src/components/picker/index.tsx:157` initializes scrollY to zero. selectedIndex/initialScrollY reflect selectedValue, and the native ScrollView receives initialScrollY through contentOffset, but only onScroll updates scrollY. Initial positioning did not emit a usable scroll event in the reproduced run. `handleDone` at lines 216-222 computes the submitted index from scrollY, so an untouched picker returns items[0] regardless of the visibly centered option. Settings `src/screens/setting/main-content.tsx:269-285` correctly persists the returned item, making the component error visible as System → Light.

Fix: initialize/reset the pending selection and scroll offset from selectedValue on each opening and when the active item set changes; do not depend on a native initial onScroll event. Keep pending selection synchronized with the wheel and clamp it to available items. Confirm must submit the centered option, and Cancel must preserve the caller's prior selection. Avoid an effect that resets the user's in-progress scroll on every render. Meaningful regression: untouched non-first initial value confirms itself; scroll then confirm uses the new value; cancel/reopen restores the selected value; switching the item list for a reused picker does not carry an old offset into the new choices. Repeat the native fresh-launch scenario.

Blast radius: callers are Settings language/theme, Open Account root/currency, and Add Budget interval/currency. These forms share the same Picker but only Theme was reproduced live. The transaction-filter screen's PickerTarget type is not a caller of this component. Test the reused form pickers without submitting production mutations. API/network, denied ledger state and authentication are independent of this local selection bug.

Dedupe: searched all .pm markdown including done for picker confirm/reset/initial/selection/offset and theme reset. No overlap found; w3/019 is dashboard system-color reactivity, a different package and cause. `git log -S 'const scrollY = useSharedValue(0)'` traces this implementation through monorepo move `182a07f1`; recent picker history (`86062503`, `5ee21328`, `6dda6746`) leaves the initialization unchanged.

Unverified: other picker callers, Android, physical iPhone, keyboard/VoiceOver selection. Original English/System preference and light simulator appearance restored and verified. No product fix, ledger write or shipping.
