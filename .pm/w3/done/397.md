# Interactive query usage errors print Python tracebacks and lose recovery details

**Severity:** minor. **Owner:** cli. **Estimate:** 30–45 minutes.
**A1/A2:** ordinary query-shell mistakes should have readable remedies, as
they do in one-shot queries. Bea's own usage exceptions instead look like
internal crashes, without `--debug`, and discard structured recovery hints.

Found 2026-09-21 on `main`, HEAD `ada8bb97`, checkout `cli/.venv/bin/bea`
0.3.0, Python 3.13.0, macOS 26.5.1 arm64. Reproduced twice in real PTYs,
each with a pristine synthetic fixture, isolated config/cache/data and a
bounded helper. Stdin/stdout use the PTY; stderr is captured separately. No
credentials or hosted resources are involved. Concurrent metadata-listing
edits do not touch query execution.

## Reproduce

Create `main.bean` in a disposable directory:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-02 * "Dinner"
  Assets:Cash -10 USD
  Expenses:Food
2026-01-03 query "cash" "SELECT sum(position) WHERE account = 'Assets:Cash'"
```

`bea --json --file "$PWD/main.bean" check` succeeds. Start
`bea --file "$PWD/main.bean" query` in a terminal and enter:

```text
.run missing
.run cash
SELECT broken(
.format csv
PRINT
.format text
SELECT count(*) AS n;
.exit
```

Both repeats emit two stderr tracebacks: one for `.run missing`, another for
`PRINT` in CSV mode. Representative sanitized excerpts:

```text
error:
Traceback (most recent call last):
  File ".../beanquery/shell.py", line 244, in cmdloop
    super().cmdloop(intro)
  ...
  File ".../bea_engine/query.py", line 317, in do_run
    raise protocol.UsageError(...)
bea_engine.protocol.UsageError: query "missing" not found.
```

The other stack ends at `query.py:365` with:

```text
bea_engine.protocol.UsageError: PRINT renders Beancount directives; --format csv cannot represent them. Use --format text or --format beancount, or SELECT for a CSV table.
```

The shell stays alive: `.run cash` returns `-10 USD`, the final SELECT returns
2, and `.exit` ends with status 0. Ledger hashes remain unchanged. This finding
does not claim a hang, session loss, or incorrect final shell exit status.

## Expected and working controls

Display the usage message and any recovery details on stderr, without a
traceback, then keep accepting commands. USAGE's global-option contract makes
`--debug` the explicit request for exception tracebacks.

- The one-shot `bea --file "$PWD/main.bean" query '.run missing'` correctly
  exits 2 and prints `Error: query "missing" not found.` followed by
  **`Stored queries in this ledger: cash.`** The interactive traceback loses
  that useful detail entirely.
- The malformed `SELECT broken(` reports a short syntax error and caret in
  the same PTY, with no traceback; recovery SELECT still works.
- A missing-parent `.output` in another real PTY reports a readable path
  error and recovers, preserving the completed w5/006 behavior.

## Root cause and fix

`cli/src/bea_engine/query.py:294` (`do_run`) and `:360` (`on_Print`) raise
`protocol.UsageError` for expected bad input. The same `PreciseShell` serves
one-shot and interactive execution. `interactive()` at `:214` enters the
upstream loop without translating these bea-specific exceptions.

The installed Beanquery `shell.py:240` catches every exception in `cmdloop`;
`render_exception` at `:74` renders only its own ParseError/CompilationError
with parse locations as short diagnostics. All other classes use
`traceback.format_exc()`. Bea's `EngineError.details` is not rendered there.

At the interactive command boundary, handle known `protocol.EngineError`
failures with their message/details and continue. Keep one-shot propagation
so its existing nonzero exit and JSON envelope remain correct. Avoid a broad
exception suppression that hides unexpected programming errors. Shared
callers also include the beancount-output entry-shape guard; inspect it when
adding the handler, but only missing stored queries and CSV PRINT were
reproduced here. Native syntax-error rendering and output redirection must
retain their current behavior.

- [ ] Both reproduced PTY mistakes produce concise messages with no stack
  trace; missing-query output includes the available `cash` query.
- [ ] The same PTY can run the valid stored query and final SELECT, then exit
  normally with source bytes unchanged.
- [ ] One-shot missing-query still exits 2 with its existing message/details;
  preserve readable native parse errors and w5/006 redirection recovery.
- [ ] Add a real PTY regression and run `make check-all` inside `cli/`.

---

**Resolved 2026-09-21** — the query shell reports bea's own usage errors as
messages, not stack traces, and keeps the recovery details.

`PreciseShell.onecmd` now dispatches through a `_dispatch` helper and catches
`protocol.EngineError` around it. Interactively it prints the message and each
`details` line to stderr and returns, so the prompt continues. One-shot
execution re-raises, because its exit code and JSON error envelope are built
from that exception — that split is the whole fix, and both halves are pinned.

The catch is deliberately `EngineError`, not `Exception`: an unexpected
programming error still surfaces as upstream renders it, which is what the note
asked for and what keeps `--debug` meaningful as the documented way to ask for
a traceback.

Acceptance, verified in real PTYs:

- [x] `.run missing` prints `query "missing" not found.` followed by
      `Stored queries in this ledger: cash.` — the detail the interactive path
      used to discard — with no stack trace. `PRINT` under `--format csv`
      likewise prints its one-line explanation.
- [x] The full reported session runs: two mistakes, then `.run cash` returning
      `-10 USD`, then `SELECT count(*)` returning 2, then `.exit` at status 0,
      with the ledger text unchanged.
- [x] One-shot `.run missing` still exits 2 with `Error: …` plus its indented
      detail, and the `--json` envelope still carries
      `category: usage`, `exit_code: 2` and the same `details` array.
- [x] Beanquery's own syntax-error rendering (short diagnostic plus caret) is
      untouched, and w5/006's `.output` recovery still reports a readable path
      error and continues.
- [x] PTY regression coverage in
      `cli/tests/test_query_shell_usage_errors.py`; reverting the fix fails
      the three interactive tests while every control passes either way.
