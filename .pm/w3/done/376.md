# `bea --json list transaction --account` keeps counterparty postings human table hides

**Severity:** minor. **Estimate:** 20–35 minutes. **Owner:** cli. **A1:** an
agent piping `bea --json list transaction --account Checking` believing the
filter narrows each row’s postings gets every leg — including counterparties —
while the human `MATCHING POSTING AMOUNTS` column shows only the filtered
account.

Found 2026-09-16 by continuous CLI QA ([c1210 hunt](e8ac6095-0ec6-49c6-b7b6-c618726d65e9)),
HEAD `0835b3c3`, `uv run bea` 0.2.0, Darwin 25.5.0 arm64. Evidence:
`cli/tmp/qa-20260915/c1210/`.

## Repro

```sh
bea --file main.bean list transaction --account Checking --search Transfer
# MATCHING POSTING AMOUNTS: Assets:Bank:Checking: 100 USD only

bea --json --file main.bean list transaction --account Checking --search Transfer
# postings == [Checking +100, Cash -100]
```

USAGE documents that with `--account`, amounts show **only matching postings**.

## Expected

JSON trims `postings` to matching accounts (or adds `matching_postings`) with
documented semantics.

## Actual

Human branch filters at render time; JSON emits full engine `postings`.

## Fix

Filter JSON `postings` (or emit `matching_postings`) when `--account` is set.
Regression: repro JSON has one Checking posting; unfiltered JSON still returns
all legs.

## Dedupe

Not w3/366, 330, 322, 287/286. No open note on JSON `--account` returning
non-matching postings on `list transaction`.

---

**Resolved 2026-09-17** — `bea --json list transaction --account` now emits a
`matching_postings` array holding exactly the postings the filter selected, in
entry order, while `postings` keeps the complete entry so an agent can still
read the counterparty legs; without `--account` the key is absent. The human
`MATCHING POSTING AMOUNTS` column and the JSON array share one selector, so
they cannot drift. Documented in `cli/docs/USAGE.md`; covered by
`cli/tests/test_list_transaction_matching_postings.py`. Shipped with this board
close.
