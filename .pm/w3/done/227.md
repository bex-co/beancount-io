# `bea import` on non-UTF-8 CSV says columns are `(none)` and suggests `--csv`, hiding the encoding failure

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** cli. **A2:** a
newcomer whose bank export is Latin-1 / Windows-1252 gets a dead-end mapping
error instead of being told the file is not UTF-8 (or offered an encoding flag).

Found 2026-09-15 by continuous CLI QA (`qa-find-bugs-cli`) against `main`,
HEAD `f2957cd1`, using `uv run bea` 0.2.0 on Darwin 25.5.0 arm64 with isolated
`BEA_CONFIG_DIR` / `XDG_CACHE_HOME` and `BEA_NO_UPDATE_NOTIFIER=1`. Synthetic
local fixtures only.

## Repro

```sh
bea --no-input init books --currency USD --date 2024-01-01
# Latin-1 "Café" amount row (byte 0xe9), not UTF-8:
python3 -c "open('latin1.csv','wb').write(b'Date,Description,Amount\n2024-03-10,Caf\xe9,-4.50\n')"

bea --no-input --file books/main.bean import latin1.csv --csv auto \
  --account Assets:Checking
# exit 2
# Error: Cannot read a column mapping from the header row of latin1.csv.
# Its columns are: (none). Name them with --csv date=Date,amount=Amount,narration=Description.
```

Same shape for a file with an invalid UTF-8 byte in a data row when discovery
runs first (`columns are: (none)`).

Working control — explicit `--csv` on the invalid-byte file surfaces the real
error:

```sh
bea --no-input --file books/main.bean import badutf.csv \
  --csv date=Date,amount=Amount,narration=Description \
  --account Assets:Checking
# Error: Importer failed (UnicodeDecodeError): 'utf-8' codec can't decode byte …
```

Comma-separated UTF-8 CSV with the same headers imports normally.

## Expected

Discovery should report an encoding failure (exit 2, usage/validation) naming
UTF-8 and the path/byte, not pretend the header had zero columns. Optionally
accept `--encoding` (or document that only UTF-8/BOM is supported). Do not
suggest `--csv date=Date,…` when the reader never decoded the file.

## Actual

`read_header` catches `UnicodeDecodeError` and returns `None`. The import
fallback then formats `columns are: (none)` and recommends a column mapping.

## Root cause

```text
cli/src/cli/csv_mapper.py:265-271  read_header
  except (OSError, UnicodeDecodeError, UsageError):
      return None

cli/src/cli/commands/import_.py:~70-80
  headers = read_header(source)
  # … "Its columns are: {columns}. Name them with --csv …"
```

Twin: `cli/src/bea_engine/csv_mapper.py` `read_header` (same swallow).

## Fix

1. Distinguish decode failures from empty/unreadable CSV: re-raise or return a
   typed error so import can say the file is not valid UTF-8.
2. Keep BOM stripping (`utf-8-sig`) as today; add a regression for a Latin-1
   body byte and for `0xff` in the payload.
3. Optional follow-up: `--encoding` for common bank exports; not required to
   close the misleading `(none)` message.

---

**Resolved 2026-09-16** — non-UTF-8 CSV discovery now raises a usage error naming the decode failure instead of columns (none) and a useless --csv mapping hint. Covered by cli/tests/test_csv_encoding_feedback.py. Shipped with this board close.
