# `bea init --opening-balance` and `add custom number:` accept `1e3`, `1_000` and non-ASCII digits

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** cli. **A2:** USAGE.md
promises amount strings use decimal notation and that scientific notation
"is refused on every path with the same message"; init and custom values
use Python `Decimal()` parsing instead and quietly rewrite the input.

Found 2026-09-25 by CLI QA against `main` HEAD `8cd9732b`, `uv run bea` 0.3.0,
Darwin 25.5.0 arm64, isolated config/cache.

## Repro

```sh
bea --no-input init a --currency USD --date 2026-01-01 --opening-balance 'Assets:Checking 1e3'
# exit 0, writes "Assets:Checking 1000 USD"
bea --no-input init b --currency USD --date 2026-01-01 --opening-balance 'Assets:Checking 1_000'
# exit 0, writes 1000
bea --no-input init c --currency USD --date 2026-01-01 --opening-balance 'Assets:Checking ٥٠'
# exit 0, writes 50
bea --file a/main.bean add custom --date 2026-01-02 --type budget --value 'number:1_000'
# exit 0, writes 1000   (number:1e3 is correctly refused)
```

Controls: `add transaction -p 'Expenses:Groceries 1e3 USD'` exits 2 with the
documented scientific-notation message; `1_000` and `٥٠` exit 2
(`Invalid token`).

## Root cause

`cli/src/cli/commands/init.py:63` (and the engine mirror
`cli/src/bea_engine/initiating.py:74`) call `Decimal(value)` directly;
`cli/src/cli/commands/add.py` `_parse_number` (~61) does the same for custom
`number:`/`amount:` values after only the scientific-notation check.

## Fix

Route these through the same decimal-notation validator `add` uses for
amounts (ASCII digits, optional sign and point; the shared scientific
message), so every write path accepts and refuses the same spellings.

## Acceptance

The four repro commands exit 2 with the shared message; tests for init
(flag and prompt) and custom values.

## Dedupe

`w5/007`, `w3/259`, `w1/m27` (done) covered add/bulk/import/CSV paths; none
covered init or custom values.
