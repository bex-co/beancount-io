# Live `bea ask` answers basic counting and ranking questions with confidently wrong numbers

**Severity:** major (a wrong financial number stated as fact, with no hedge and
exit 0; the user has no way to tell it apart from a right one). **Owner:** cli.
**Estimate:** 40–60 minutes. **A1:** `ask` is the agent-facing read surface over
a local ledger. "How many transactions do I have?" and "what was my largest
expense?" are not exotic questions, and the answers come back wrong more often
than right.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, stdin closed, **live hosted AI** (model `gpt-4o` via the
beancount.io proxy — not a stub), synthetic ledger, authorized QA account.

### A. Transaction count returns the posting count — 2 of 2 runs wrong

```sh
bea --file multi.bean ask --print "How many transactions are in my ledger in total? Give just the count."
# run 1: "There are 22 transactions in your ledger."
# run 2: "22"
# exit 0 both times.  Correct answer: 11.
```

`22` is the posting count. The default BQL table is postings, so `SELECT count(*)`
answers a different question than the one asked, and nothing in the result says
so — the model has no signal that it counted rows, not entries. Independent
controls on the same fixture (all verified, exit 0):

```sh
bea --file multi.bean query "SELECT count(*)"                                  # 22  (postings)
bea --file multi.bean query "SELECT count(*) FROM #entries WHERE type = 'transaction'"   # 11
bea --file multi.bean query "SELECT count(*) FROM (SELECT DISTINCT id)"        # 11
bea --file multi.bean query "SELECT DISTINCT id"                               # 11 rows
bea --file multi.bean query "SELECT count(DISTINCT id)"                        # syntax error (exit 2)
```

Note which of those work: the entry count needs either the `#entries` table or a
subquery over `DISTINCT id`. `count(DISTINCT …)` — the formulation anyone coming
from SQL reaches for first — is a **syntax error** in this BQL dialect.

### B. "Largest expense" — 1 of 4 runs right

Same question, four consecutive `--print` runs on the same pristine fixture:

| run | result |
| --- | --- |
| 1 | crashed (see `w3/449` / `w3/454` — pydantic-ai retry exhaustion, exit 1) |
| 2 | "a dinner at Trattoria on 2024-02-14 … 64.75 USD" — the **smallest** expense |
| 3 | crashed, exit 1 |
| 4 | "February rent to Landlord on 2024-02-01 … 1200.00 USD" — **correct** |

Control: `SELECT date, payee, narration, number WHERE account ~ '^Expenses'
ORDER BY number DESC LIMIT 1` → `2024-02-01 Landlord February rent 1200.00`.
Five plausible formulations of that query (including `ORDER BY position DESC`
and a `GROUP BY` form) all run and all return 1200.00, so the right query is
easy to write; run 2 ordered ascending and reported the first row.

## Expected

For a question with one arithmetic answer over a local file, `ask` either states
the right number or says it could not determine it. A wrong number presented
without qualification, at exit 0, is worse than a refusal: the whole value of
the surface is that the user does not have to check it.

Concretely: asking for a count of transactions returns the entry count; asking
for the largest expense returns the largest.

## Root cause (CLI-side, not "the model was unlucky")

The system prompt in `cli/src/cli/ask/agent.py:19-67` is the only thing steering
these queries, and it has two gaps that map exactly onto the two failures:

1. It says "The default table is postings — one row per posting" and "Use
   SELECT DISTINCT to deduplicate (e.g. one row per account or per transaction)",
   but **every worked example is a per-posting or per-account aggregate**. There
   is no counting example at all, so the obvious `count(*)` is never contrasted
   with the entry count. Worse, the prompt never mentions the `#entries` table
   and explicitly says "`FROM OPEN ON <date>` / `FROM CLOSE` / `FROM CLEAR` are
   temporal modifiers, **not table names**" — so as written it tells the model
   that `FROM` cannot name a table, which is exactly how the one correct entry
   count (`FROM #entries WHERE type = 'transaction'`) is reached. The model is
   steered away from the right query.
2. There is no **ranking** example — no `ORDER BY … DESC LIMIT n`. `ORDER BY`
   appears only as `ORDER BY account` (ascending, alphabetical) in two examples,
   which is the ascending pattern run 2 reproduced.

Neither is a model defect this repository cannot fix: the prompt is a file in
this checkout, and both failures are one worked example away.

Aggravating, and separately fixable: the tool result is a bare text table
(`run_bql_query`, `agent.py:139-152`) with no row count and no statement of what
was counted, so the model cannot notice that its 22 rows are 11 entries. That is
the same structural gap `w3/447` identifies for a zero total — fixing
`run_bql_query` to return a row count and typed cells serves both notes.

## Fix

1. Add worked examples to `_SYSTEM_PROMPT` for the two shapes that fail:
   - counting entries versus postings
     (`SELECT count(*) FROM #entries WHERE type = 'transaction'` versus
     `SELECT count(*)`, with a sentence saying the bare form counts postings) —
     and, while there, correct the "`FROM` is not a table name" line, which is
     false for `#entries` / `#postings`, and say that `count(DISTINCT x)` is not
     valid here;
   - top-N ranking
     (`SELECT date, payee, narration, number WHERE account ~ '^Expenses' ORDER BY number DESC LIMIT 1`),
     stating that `DESC` is what "largest" means.
2. Prefix `run_bql_query` results with a row count and say which table was
   queried, so "22 posting row(s)" cannot be read as 22 transactions. Shared
   with `w3/447` item 1 — do them in one pass.
3. Regression coverage: a stub-model test asserting the prompt contains the
   counting and ranking examples is worthless on its own; instead add a
   **recorded-query** test over this fixture that runs the documented example
   queries through `run_bql_query` and asserts the row count prefix and the
   1200.00 / entry-count results, so the numbers the prompt promises are pinned
   even if the prompt is reworded.

## Dedupe

Searched `.pm/**/*.md` including `done/` and `blocked/` for "largest expense",
"counted postings", system-prompt and wrong-answer terms. `w3/447` names both
symptoms in its **Out of scope** section and declares them "individual model
mistakes with no CLI-side cause" — that disposition is **corrected by this
note**: both are reproducible, both trace to identifiable gaps in a prompt that
lives in this repository, and 447 has been updated to point here. `w3/448` is
the unbounded tool result (size, not content). `w3/449` / `w3/454` are the
crashes seen in runs 1 and 3 — a different defect that happened to fire on the
same question. `w3/done/353` is a `SELECT DISTINCT tags` rejection in the engine.
`git log -S"_SYSTEM_PROMPT" -- cli` shows the prompt has only ever been appended
to (skills index), never revised for query correctness.
