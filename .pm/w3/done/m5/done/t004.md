## Objective

Prove the primitive that makes 52 read verbs reachable. Resources are URI-addressed, paginated, RFC 6570 templated, and — the reason this matters — **do not compete with tools for the model's selection attention**, which is the entire objection that kept the reads off MCP.

One template, working against real data, with real authorization. Not the port.

## Context

- Spec: <https://modelcontextprotocol.io/specification/2025-06-18/server/resources>. Server must declare the `resources` capability; `resources/templates/list` and `resources/list` both paginate; `resources/read` takes a URI.
- `src/server/api/composition-root.ts` — `assembleMcpRegistry` builds the server; the registration for resources goes alongside the tool loop, with the same per-call gate.
- **Authorization is the part that must not be special-cased.** A resource read is a `read`-class op and goes through the same `authorizeLedger` seam every tool uses (ADR 0007 D5), so a revoked grant is refused on the very next read. A resource layer that authorizes once at listing time would reintroduce exactly what ADR 0006 D4/D9 removed.
- Pick a template whose data already has a service behind it, so this task is about the MCP shape and not about new ledger code.
- URI scheme is an open question in ADR 0008 — `beancount://` vs `https://`. The spec reserves `https://` for resources a client can fetch itself, which these are not. Decide, and record the decision in the ADR.

## Steps

1. Declare the `resources` capability on the `McpServer`.
2. Register one resource template with an RFC 6570 URI, routed to an existing ledger service.
3. Authorize per read through `authorizeLedger`; refuse a revoked grant.
4. Drive it with a real MCP client over `InMemoryTransport`: `resources/templates/list`, then `resources/read`.
5. Record the URI-scheme decision in ADR 0008.
