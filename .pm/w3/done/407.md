# Reports blame an absent time filter when a ledger date exceeds report range arithmetic

**Minor · 25–40m · cli · A1.** A syntactically valid maximum-date ledger
makes unfiltered reports return `Invalid time filter None`. The command names
an option the user never passed and gives no indication which ledger fact
caused the failure. Scope this item to an accurate diagnostic and recovery;
full reporting support through year 9999 is not required.

Found 2026-09-21, HEAD `aefe02e3`, checkout `bea 0.3.0`, Python 3.13.0,
macOS 26.5.1 arm64. Two pristine synthetic fixtures, fresh subprocesses,
closed stdin, isolated config/cache, unchanged source hashes. No hosted data.

## Reproduce

Create `/absolute/main.bean`:

```beancount
option "operating_currency" "USD"
9999-12-31 open Assets:Cash USD
9999-12-31 open Equity:Opening USD
9999-12-31 * "Boundary"
  Assets:Cash 1 USD
  Equity:Opening
```

```sh
bea --json --file /absolute/main.bean check
bea --json --file /absolute/main.bean list transaction
bea --json --file /absolute/main.bean balance
bea --json --file /absolute/main.bean report overview
```

Check and list succeed (exit 0, valid ledger, one transaction). Balance and
overview both exit **2**, with empty stdout and this JSON usage message on
stderr, identically on a fresh copy:

```text
Invalid time filter None. Use month, year, YYYY, YYYY-MM, or a date range such as '2026-01 - 2026-06'. date value out of range
```

Independent `query 'SELECT account, sum(position) GROUP BY account'` succeeds
with Cash 1 USD and Equity -1 USD. `report overview --time 2026` succeeds with
an empty 2026 interval, demonstrating a bounded-filter recovery path.
Changing all fixture dates to `2026-12-31` or `0001-01-01` also makes check,
list, balance and overview succeed. Files are not mutated by any probe.

Expected: if this boundary is unsupported, identify the offending ledger date
and the report-range limitation, with a useful bounded-time recovery hint.
Do not call a missing option invalid or silently omit/clamp the dated entry.
Malformed explicit time filters must retain their existing usage diagnostics.

## Cause, scope and dedupe

`cli/src/fava/ledger.py:203` computes the exclusive end as
`entry.date + timedelta(1)` during `FilteredLedger` construction. The maximum
date overflows. `cli/src/bea_engine/report.py:329` wraps every
`ValueError`, `OverflowError` and `FilterError` from `get_filtered` as an
invalid **time filter**, even when `time is None`. The wrapper dates to
`a90b1706`. `_metadata` at line 363 repeats exclusive-end arithmetic; changing
only the first addition to clamp would not constitute complete date support.

Distinguish report-bound failures from supplied-filter parsing errors at the
appropriate adapter boundary. Preserve vendored attribution and reuse the
existing report/error machinery. Add real-command regression coverage for
the maximum-date error and ordinary-date / explicit-filter controls. No new
dependency or backend/API work is needed. Balance and all four report kinds
share `_load`; runtime reproduction covers balance and overview, while income
statement, balance sheet and trial balance remain source-traced only.

Searched all board queues including done/blocked for maximum dates,
`date.max`, overflow, and invalid-time diagnostics. `w3/327` (completed via
w1/m25) rejects an explicitly empty filter; here no filter is supplied.
No matching open item was found. This is an edge-case diagnostic issue, not
evidence that normal accounting periods fail.

Ignored evidence: `cli/tmp/qa-20260922T052032Z-loop/date-extremes/` and
`captures/date-extreme-*.json`, retaining argv/cwd/environment, separate
streams, exits, timings, revisions and before/after source contents/hashes.
Other platforms and additional near-maximum interval shapes are unverified.

---

**Resolved 2026-09-22** — a report at the date boundary now names the ledger
fact that caused the failure, instead of an option nobody passed.

`_load` wrapped every `ValueError`, `OverflowError` and `FilterError` from
`get_filtered` as an invalid **time filter**, even when `time is None`. When
the ledger's last dated entry is `9999-12-31`, building the exclusive period
end overflows, and the user was told `Invalid time filter None`.

`_unreportable_boundary` identifies that case — the last dated entry, skipping
Open/Close/Commodity for the same reason the period bounds skip them — and
`_load` uses it only when no filter was supplied. Anything else keeps the
existing filter diagnostic exactly, so a malformed `--time` is still reported
as a malformed `--time`, including on this same ledger.

The scope the note set is respected: this is a diagnostic and a recovery, not
year-9999 reporting support. The message says what cannot be bounded and how
to get an answer, and the tests say so too rather than implying otherwise.

One thing I checked rather than assumed: the recovery hint has to work.
`--time 9999` genuinely reports this ledger, so the hint names it and a test
runs it. My first wording said "a period that ends earlier", which was wrong —
`--time 9999` does not end earlier, it is simply bounded — so the message now
says "Name the period explicitly and it reports fine".

Correction to the note's scope line: it lists income statement, balance sheet
and trial balance as source-traced only. All four report kinds **and**
`balance` are now exercised directly, and all five were affected and are fixed.

The message also states that `check`, `list` and `query` read this ledger
unaffected — and a test runs all three rather than leaving that as a claim.

Regression coverage is `cli/tests/test_report_date_boundary_diagnostic.py`,
including a unit test of the boundary detection over declarations-only,
ordinary-date and at-boundary entry lists. Reverting the branch fails 6 of its
16 while every control passes either way. `cd cli && make check-all` passes
(1923 tests).

Left as the note allows: `_metadata` still repeats the exclusive-end
arithmetic, so a bounded report is what works — the boundary ledger is still
not reportable without `--time`, by design here.

Unverified: other platforms, and near-maximum interval shapes other than the
exact `date.max` boundary.
