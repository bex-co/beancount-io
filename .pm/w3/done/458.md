# Keep the mobile ledger directory stable after creation

Source: user-reported drawer reordering after creating and selecting a ledger, 2026-10-01.
Pillar: A2 — newcomers can create a ledger and reliably find it again.

Retain Apollo caching and load the complete lightweight account directory in explicit pages. Share it between the drawer and creation screen, refresh after creation, and keep a deterministic owner/name order independent of selection. Show an out-of-directory current ledger separately rather than inserting it into an owner group.

Acceptance: a newly created ledger remains visible after switching away, including beyond the first 30 results; refresh failures retain usable data and do not report a successful creation as failed; late requests cannot replace newer directory state. Cover paging, cache reuse, refresh, and stable selection with meaningful regression tests, run the mobile checks, and ship.

Scope: mobile only; no dependencies, API changes, store release, or ledger-content preloading. Estimated under one hour using the existing Apollo client and drawer components.

---

**Resolved 2026-10-01** — Shared the cached lightweight directory across creation and the drawer, loaded every explicit page, refreshed list variants after creation, and kept deterministic owner/name order with out-of-directory selections in a separate Current ledger section. Confirmed creations survive refresh failures; aborted older reads cannot overwrite newer state or cache. Shipped in `bc416323` (`mobile`). Validation: 2,031 unit tests, format check, typecheck, ESLint, and dead-code/GraphQL operation checks passed. Regression coverage includes more than 30 ledgers, cache reuse, later-page failures, stale responses, and the real creation submission handler. Native simulator verification was not performed; no simulator was booted during this change.
