# `bea ask` answers "there are no entries in your ledger" for a dated net-worth question, because a zero total renders as blank

**Severity:** major (a confidently wrong financial answer about a ledger that
has entries). **Owner:** cli. **Estimate:** 30–40 minutes. **A1:** "what is my
net worth?" is one of the REPL's own suggested questions; adding "as of
<date>" turns the answer into a denial that the ledger has any data.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR`, synthetic
ledger, authorized QA account, model `gpt-4o` via the hosted proxy.

## Repro

Synthetic ledger (`main.bean`), balances known by hand — checking holds
`4500.00 USD` on 2024-03-01:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Bank:Checking USD
2024-01-01 open Income:Salary USD
2024-01-01 open Expenses:Rent USD
2024-01-01 open Equity:Opening-Balances USD

2024-01-01 * "Opening" "seed"
  Assets:Bank:Checking   1000.00 USD
  Equity:Opening-Balances
2024-01-31 * "ACME Corp" "January salary"
  Assets:Bank:Checking   5000.00 USD
  Income:Salary
2024-02-05 * "Landlord" "February rent"
  Expenses:Rent   1500.00 USD
  Assets:Bank:Checking
```

```sh
bea --file main.bean ask --print "What is my net worth as of 2024-03-01? Give the exact number."
```

Three consecutive runs all denied the data (wording varies, substance does not):

> It seems there is no data recorded in your ledger up to the date of
> 2024-03-01. Therefore, I'm unable to calculate your net worth as of that date.

The same question without a date answers the correct total. Controls on this
exact ledger:

```sh
bea --file main.bean query "SELECT sum(position) WHERE account ~ '^(Assets|Liabilities)'"
#  4500.00 USD                                  <- the right answer
bea --file main.bean query "SELECT sum(position) WHERE date <= 2024-03-01"
# sum(position)
# -------------
#                                               <- the blank cell the agent misreads
```

The second control is the deterministic half of this bug and needs no model
call: the tool result the agent receives for a legitimate query is a table whose
only data row is whitespace.

## Root cause

The model reached for the whole-ledger sum restricted by date —
`SELECT sum(position) WHERE date <= 2024-03-01` — which is *correct BQL* and,
because a balanced ledger nets to zero, produces an **empty Inventory**. The
engine's text formatter renders an empty Inventory as a run of spaces, so
`run_bql_query` (`cli/src/cli/ask/agent.py`) hands back:

```
sum(position)
-------------
             
```

A header, a rule, and a blank cell. `.strip()` on the whole blob is non-empty,
so the tool does not use its `(empty result set)` branch, and nothing in the
result distinguishes "the total is zero" from "there are no rows". The model
reads the blank as missing data and tells the user their ledger is empty. The
same blank cell appears in `bea query` and `--json` (`"rows": [[[]]]`), which is
upstream beanquery's rendering; the defect here is that the agent's tool passes
it on with no row count and no zero marker.

## Fix

1. In `run_bql_query`, return the result with structure the model cannot
   misread: prefix a row count (`3 row(s)`), and render an empty/zero Inventory
   cell explicitly (`0`) rather than as whitespace — or return the JSON result
   shape instead of the human text table.
2. Add a worked "balance as of a date" example to the system prompt in
   `cli/src/cli/ask/agent.py` (`FROM CLOSE ON <date>` with an
   `account ~ '^(Assets|Liabilities)'` filter), since the temporal modifiers are
   currently one unexemplified line.
3. Regression coverage: a test that a query whose only row is an empty Inventory
   comes back with a row count and a visible zero, and never as whitespace only.

## Re-verified 2026-09-26 (run12) — model half now confirmed **live**, and a second manifestation

The half this note previously carried as unverified is confirmed. Same HEAD
`8cd9732b`, `bea` 0.3.0, macOS 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, stdin closed, **live hosted AI** (`gpt-4o` via the
beancount.io proxy; the quota window had reopened), same pristine fixture as the
original repro.

```sh
bea --file main.bean ask --print "What is my net worth as of 2024-03-01? Give the exact number."
```

Two consecutive runs, both exit **0**, both denying the data:

> run 1 — "It seems there was an issue retrieving the net worth as of 2024-03-01.
> The query returned no results. This could be because there are no transactions
> or account balances available for that date in the ledger."

> run 2 — "It looks like there is no data available for your net worth as of
> 2024-03-01. This could mean either there are no transactions recorded up to
> that date or all entries sum to zero."

The correct answer is **4500.00 USD** (`SELECT sum(position) WHERE account ~
'^(Assets|Liabilities)'` on the same file). Run 2 is the sharpest evidence for
this note's diagnosis: the model itself offers "or all entries sum to zero" as an
alternative reading of the blank cell and still cannot tell which it is looking
at — because the tool result does not say.

**Second manifestation, same mechanism, different question shape.** On the
11-transaction multi-currency fixture in `w3/455` (which holds `800.00 EUR` in
`Assets:Bank:Euro`):

```sh
bea --file multi.bean ask --print "How much EUR do I hold? Give the exact amount."
# "It seems that there is no EUR balance in your ledger at the moment."   exit 0
```

Control on the same file:

```sh
bea --file multi.bean query "SELECT sum(position) WHERE currency = 'EUR'"
#                                     <- blank cell: the EUR legs net to zero ledger-wide
bea --file multi.bean query "SELECT sum(position) WHERE account = 'Assets:Bank:Euro'"
#  800.00 EUR
```

So the blank-zero-Inventory cell does not only break "net worth as of <date>" —
any whole-ledger `sum(position)` restricted by something other than account type
hits it, and multi-currency holdings questions are a natural way to land there.
That widens the fix's value and argues for item 1 (row count + explicit zero
rendering in `run_bql_query`) over item 2 (one more prompt example), since no
number of examples covers every filter that happens to net to zero.

**Correction to this note's "Out of scope" section.** It disposed of the
largest-expense and count-of-transactions failures as "individual model mistakes
with no CLI-side cause". That is wrong and is superseded by **`w3/455`**: both
reproduce, and both trace to identifiable gaps in `_SYSTEM_PROMPT` and in the
tool result shape — files in this checkout. Items 1 and 2 of the fix here are
shared with `w3/455` item 2; do them in one pass.
