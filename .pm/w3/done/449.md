# The `bea ask` session dies on a Ctrl-C or a single failed turn, and the conversation is discarded

**Severity:** major (raised from minor on 2026-09-26 — see the run12 addendum at
the end: the session also dies, live, on about half of an ordinary read-only
question, not only on the user's own Ctrl-C). **Owner:** cli.
**Estimate:** 25–40 minutes. **A1:** the multi-turn session is the flagship
interactive surface; the one key people press to clear a half-typed line ends the
session instead — and so does one malformed query the model wrote itself.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR`, synthetic
ledger, driven through a real PTY with a local stub model (no hosted calls
needed to reproduce).

## Repro

```sh
bea --file main.bean ask          # interactive session, needs a TTY
```

1. Ask anything; get an answer. The session is now multi-turn (the next question
   carries the history).
2. Press Ctrl-C at the prompt — empty line or half-typed text.
3. The session prints `Goodbye.` and exits 0. The conversation is gone.
4. Press Ctrl-C while the spinner is up (during a model call): same, the whole
   session ends rather than the turn being cancelled.

Its own help disagrees. `?` inside the session prints:

```
Keyboard shortcuts
  ↑ ↓     Browse input history
  Ctrl-C  Cancel current input
  Ctrl-D  Exit
```

and the bottom toolbar reads `? for help · ↑↓ history · Ctrl-D to exit`.

## Expected

The behaviour the session advertises, which is also the prompt-toolkit and
REPL-wide convention: Ctrl-C at the prompt clears the current line and stays in
the session; Ctrl-C during a model call abandons that turn, prints something like
`(cancelled)`, and returns to the prompt with the history intact; Ctrl-D (EOF)
exits. `--print` mode is already correct on the exit contract — a single-shot answer
interrupted by Ctrl-C exits 130 with no error message, as `cli/docs/USAGE.md`
requires. (Nit worth fixing in the same pass: it leaves the last `⠼ Thinking…`
spinner frame on the line instead of clearing it.)

## Root cause

`cli/src/cli/ask/repl.py:211-218` — the read loop is

```python
try:
    user_input = session.prompt(...).strip()
except (KeyboardInterrupt, EOFError):
    console.print("\n[dim]Goodbye.[/dim]")
    break
```

`KeyboardInterrupt` (Ctrl-C) and `EOFError` (Ctrl-D) share one handler, so both
exit. The model call at `:225-233` has no `KeyboardInterrupt` handler at all, so
an interrupt there propagates out of `run_repl` and ends the process; the
`finally` stops the spinner but the turn cannot be abandoned.

## Fix

1. Split the two: `except KeyboardInterrupt: continue` (prompt-toolkit has
   already discarded the buffer), `except EOFError:` keeps the `Goodbye.` exit.
2. Wrap the `agent.run_sync(...)` call so `KeyboardInterrupt` cancels only that
   turn: print a short `cancelled` line, leave `messages` as it was before the
   turn, and loop.
3. Regression coverage: extend the existing PTY interrupt harness
   (`cli/tests/test_interrupt_contract.py`, which already drives click prompts
   and the `beanquery>` shell) with an `ask` case — Ctrl-C at the prompt keeps
   the session alive and a following question still answers; Ctrl-D exits 0.

## Dedupe

No `.pm` item covers the ask REPL's interrupt semantics. `w3/done/388` is
Ctrl-C at a click prompt (exit code contract), `w3/435` (open) is
`format --in-place` truncation, `w3/440` (open) is SIGTERM/SIGHUP staging files.
Commit `8cd9732b` ("re-send Ctrl-C when the interrupt lands before the prompt's
read") only touches that click-prompt/`beanquery>` harness.
`git log -S"Goodbye" -- cli/src/cli/ask/repl.py` shows the line has never been
revisited since it arrived.

## Folded in 2026-09-26: `w3/453` — one server-side failure ends the whole session

Consolidated during the CLI QA verification round. `w3/453` and this note are the
**same five lines** — the model call at `cli/src/cli/ask/repl.py:225-233`, which
has no handler for either a `KeyboardInterrupt` or the `BeaError` that
`translated_failures` raises, so both propagate out of `run_repl` to
`cli/src/cli/main.py:160-161` and end the process with the conversation lost.
Both notes already said they belonged in one pass; fixing one half alone would
leave the other open, so they are tracked here as one item and `453` was dropped
with a tombstone. The combined fix is: wrap that call once, map
`KeyboardInterrupt` to "this turn cancelled" and a `BeaError` to the normal error
renderer, leave `messages` untouched in both arms, and continue the loop — plus
the prompt-read split (`except KeyboardInterrupt: continue`, `except EOFError:`
exits). Regression coverage: one PTY harness that covers Ctrl-C at the prompt,
Ctrl-C during a turn, a 5xx turn, and a following question that still answers and
still sees the earlier history. `w3/453`'s full record:


**Severity:** minor (no data loss; loses a multi-turn conversation to a single
transient failure). **Owner:** cli. **Estimate:** 15–25 minutes — fix in the
same pass as `w3/449`, which is the other half of this loop. **A1:** the
interactive session is the flagship AI surface; a 5xx from the proxy should cost
one turn, not the session.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR`, synthetic
ledger, real PTY. The failing HTTP status came from a **local stub server**
pointed at with `BEA_API_URL` — a simulation of the transport, not an observation
about the hosted service. What is real is the CLI's reaction to it.

## Repro

Point `BEA_API_URL` at a local server that answers the first
`/api-gateway/ai/openai/chat/completions` call normally and the next with HTTP
500 and `{"message": "Upstream model provider failed."}`.

```sh
bea --file main.bean ask        # interactive, needs a TTY
```

1. Ask a question — it answers; the session is now multi-turn.
2. Ask a second question. After the SDK's own retries the CLI prints

   ```
   Error: Server error (Upstream model provider failed.).
   ```

   and **the process exits**. The `❯` prompt does not come back and the first
   turn's history is gone.

The translation itself is right: `--print` against the same stub exits **1** for
500 and **3** for a 401 with the BEA_TOKEN-aware remedy, matching the exit table
in `cli/docs/USAGE.md:135-142`. The defect is only that an interactive session
treats a per-turn failure as fatal. (A 429 and a 400 were retried transparently
by the SDK in the same run and never reached the user.)

## Expected

In the REPL, a failed turn prints the same translated error and returns to the
prompt with `messages` unchanged, so the next question still carries the earlier
history. Exiting is right for `--print`, not for a session. An auth failure (3)
is arguably the one case worth ending on, since every later turn will fail the
same way — decide that deliberately rather than by omission.

## Root cause

`cli/src/cli/ask/repl.py:225-232` wraps the model call in `try/finally` that
only stops the spinner; nothing catches the `BeaError` that
`translated_failures` (`cli/src/cli/ask/agent.py:84-96`) raises, so it
propagates out of `run_repl` to the top-level handler in
`cli/src/cli/main.py:160-161`, which prints and exits. Same five lines as
`w3/449` (Ctrl-C at that call), which is why the two belong in one pass: 449's
fix adds a `KeyboardInterrupt` arm and would leave this one open.

## Fix

Catch `BeaError` around the turn, print it through the normal error renderer,
leave `messages` as it was, and continue the loop. Regression coverage: extend
the stub-model PTY harness with a turn that fails 5xx and a following question
that still answers and still sees the first turn's history.

## Dedupe

Searched `.pm/**/*.md` including `done/` and `blocked/` for ask session /
conversation-loss / server-error terms. `w3/449` (open) is Ctrl-C ending the
session — same code, different trigger, and its fix as written does not cover a
server error. `w3/445`, `446`, `447`, `448`, `450` are the JSON envelope, the
`max_tokens` cap, the zero-total render, the unbounded tool result and
`cloud ledger show`. `w3/done/271` is credential validation. `git log -S`
on `translated_failures` shows it added for exit-code translation only, with no
REPL recovery arm.

## Unverified

Whether the hosted proxy actually returns 5xx under load (not tested — the AI
quota for the QA account was exhausted during this run). Windows behavior.

## Extended 2026-09-26 (run12) — a **third** trigger, observed live, and a severity bump to **major**

Same five lines (`cli/src/cli/ask/repl.py:225-233`). This note and the folded-in
`453` both describe exceptions that escape the turn; a third one does too, and
**the fix as currently written does not catch it.** The arms proposed above are
`KeyboardInterrupt` and `BeaError`. This exception is neither: it is pydantic-ai's
own `UnexpectedModelBehavior`, raised when the `run_bql_query` tool exhausts its
`retries=2` (`cli/src/cli/ask/agent.py:138`).

### It fires on an ordinary question against the real service

Not a stub, not an interrupt. On an 11-transaction synthetic ledger, live hosted
AI (`gpt-4o` via the beancount.io proxy), HEAD `8cd9732b`, `bea` 0.3.0, macOS
26.5.1 arm64, isolated `BEA_CONFIG_DIR`, stdin closed:

```sh
bea --file multi.bean ask --print "What is my single largest expense transaction, and how much was it?"
```

**Two of four consecutive runs** ended with, on stderr, exit **1**:

```
Error: Tool 'run_bql_query' exceeded max retries count of 2. Consider raising the
retry limit, or see the docs on tool retries:
https://ai.pydantic.dev/tools-advanced/#tool-retries
```

(The other two runs answered — one correctly, one with the wrong number; that
half is `w3/455`.) So this is not a rare edge: one ordinary analytical question
hit it half the time.

### Deterministic reproducer, no quota needed

```sh
# stub at BEA_API_URL answers every request with the same invalid tool call:
#   {"tool_calls":[{"name":"run_bql_query",
#                   "arguments":{"query":"SELECT x FROM y ORDER BY LIMIT"}}]}
bea --file main.bean ask --print "anything"
# -> exactly the message above, exit 1, after 3 requests (initial + 2 retries)
```

And in the interactive session, driven through a real PTY against the same stub:
the first turn prints that error and **the process exits 1**. The `❯` prompt does
not return; the two further questions queued in the harness were never read.
One malformed query ends the session.

### Severity

Raised from **minor** to **major**. The original minor rating rested on "no data
loss; loses the conversation", with triggers that were either the user's own
Ctrl-C or a simulated 5xx. With this trigger the session dies on its own, from a
plain read-only question, against the real service, at a rate of about one in
two — and each death costs the hosted tokens already spent on that turn.

### Fix addendum

The wrap around `agent.run_sync` must be broad enough to cover anything the
agent loop can raise, not an enumeration of two types. Catch
`KeyboardInterrupt`, `BeaError`, and pydantic-ai's `UnexpectedModelBehavior` /
`UsageLimitExceeded` (the latter is `w3/454`) — or simply `Exception` with a
deliberate re-raise list — print through the CLI's own renderer, leave `messages`
untouched, and continue the loop.

The **message text** in this trigger is a separate defect and is tracked in
`w3/454`, which already describes the same leak for the request-limit ceiling and
the same escape route (`cli/src/cli/main.py:160-161`). `454` is now confirmed
live rather than stub-only; see its own addendum.

Raising `retries=2` is worth considering in the same pass but is not the fix: the
session must survive a tool that cannot be made to work, at any retry count.

honest and its session survivable"): the engine append path refuses control

neutralize them, the panel names the destination the dry run resolved in a body
line that cannot be trimmed, a Ctrl-C or a failed turn costs one turn instead of

`cli/tests/test_ask_consent_surface.py`,
`cli/tests/test_ask_session_resilience.py` and the shared stub-model/PTY harness
in `cli/tests/conftest.py`. Before/after evidence was captured locally against a
local stub model server on a real terminal (no hosted AI calls); it is not on
this board.
