# `bea import --csv` books euro and pound cells as the ledger's operating currency and ignores the source account's own currency

**Severity:** major. **Estimate:** 45–60 minutes. **Owner:** cli (engine
import). **A1/A2:** a foreign-currency account export imports with exit 0
and a green `bea check`, but every amount is in the wrong commodity. The
w1/m24/t003 design note says "the account still supplies the commodity";
the code uses the ledger's single `operating_currency` instead.

Found 2026-09-25 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD
`8cd9732b`, `uv run bea` 0.3.0, Darwin 25.5.0 arm64, isolated config/cache,
stdin closed. Synthetic ledger only.

## Repro

```sh
printf 'option "operating_currency" "USD"\n2026-01-01 open Assets:Wise\n2026-01-01 open Expenses:Uncategorized\n' > main.bean
printf 'Date,Description,Amount\n2026-02-02,Cafe Paris,"-4,50 €"\n2026-02-03,London Pub,"-£12,00"\n' > e.csv
bea --file "$PWD/main.bean" import e.csv --account Assets:Wise --apply; echo exit=$?   # exit=0
grep Assets:Wise main.bean    # -4.50 USD and -12.00 USD
bea --file "$PWD/main.bean" check; echo $?                                          # 0
```

Second shape, same cause: with `2026-01-01 open Assets:EurBank EUR` in a
USD-operating ledger, the same export previews every row `blocked` with
`Cannot post USD to 'Assets:EurBank' (open for EUR only). Add USD to its
open directive.` — advice that, if followed, books euros as dollars. There
is no way to name a constant currency: `--csv …,currency=EUR` fails with
`The mapping names column 'EUR' for currency, which e.csv lacks.` (exit 2),
so the only workaround is editing the bank CSV to add a currency column.

## Root cause

- `cli/src/bea_engine/importing.py:127–134`: `CsvImporter(currency=operating[0]
  if len(operating) == 1 else None)` — the source account's open-currency
  constraint is never consulted.
- `cli/src/bea_engine/csv_mapper.py:64–95` `_split_amount_sign` strips any
  Unicode `Sc` symbol and discards it, so a cell's `€`/`£`/`¥` never meets
  the currency the row is posted in (`csv_mapper.py:~807`).
- `importing.py:540–541` `_blocked_reason` always recommends widening the
  open directive.

## Fix

- Resolve the row currency as: currency column → the source account's
  single open currency → the single operating currency → refuse naming the
  remedy.
- Keep stripping symbols, but refuse (exit 2, row named) a cell whose
  unambiguous symbol (`€` EUR, `£` GBP, …) contradicts the resolved currency;
  `$`/`¥` stay accepted as ambiguous.
- Accept a constant currency (e.g. `--csv …,currency=EUR` when no such
  column exists, or a `--currency` option) and remember it with the mapping.
- When a blocked row's cells carried another symbol, the hint should point
  at the currency setting, not at editing the open directive.

## Acceptance

- The `Assets:EurBank EUR` repro imports as `-4.50 EUR` / `-12.00 EUR` with
  no flags; the `Assets:Wise` repro is refused naming row 1 and the `€`
  symbol, and succeeds with the constant-currency option.
- A `$` column in a USD ledger is unchanged (existing tests keep passing).
- Regression tests for account-currency default and symbol contradiction.

## Dedupe

Searched `.pm/**` for currency symbol, `€`, operating currency + import:
w3/256 and w1/m24/t003 (done) added symbol stripping and explicitly left
symbol inference out, on the assumption that the account supplies the
commodity; w3/411 is init. No open item.
