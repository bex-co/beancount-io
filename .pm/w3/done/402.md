# Query statement counting treats comment punctuation as executable syntax

**Minor · 40–55m · cli · A1.** A semicolon in a BQL block comment rejects a
valid single query. An apostrophe in that comment causes the opposite failure:
two real statements are accepted, but only the first runs, with exit 0.

Found 2026-09-21 at HEAD `358b17ce`, checkout `bea 0.3.0` via
`cli/.venv/bin/bea`, Python 3.13.0, macOS 26.5.1 arm64. Both failures were
repeated with pristine synthetic ledgers in fresh processes; no file changed.

## Reproduce

Save `/absolute/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-02 * "Lunch"
  Assets:Cash -10 USD
  Expenses:Food
```

Run:

```sh
bea --json --file /absolute/main.bean query \
  '/* explanation; one query */ SELECT count(*) AS n'
# exit 2; stderr: One BQL statement per invocation; got 2.
bea --json --file /absolute/main.bean query \
  "/* don't ignore the tail */ SELECT 11 AS first LIMIT 1; SELECT 22 AS second LIMIT 1"
# exit 0; data.columns = [first], data.rows = [[11]]; empty stderr
```

Expected: the first query returns **2**; the second is refused with the
existing multi-statement usage error. Comment content is not executable BQL.

Controls: replacing the comment's semicolon with a colon makes the single
query work. Replacing `don't` with `do not` makes the two-statement input
correctly fail with exit 2. A quoted `'a;b'` literal and a single trailing
semicolon still work. The valid commented query also fails in human mode
and through stdin. A real interactive shell accepts that exact query and
returns 2, as it does for `SELECT count(*) AS n /* note; one statement */`.

## Cause and fix

`cli/src/cli/commands/query.py:67` `_split_statements` tracks quotes and escapes
but has no block-comment state. It splits a comment's semicolon, or treats a
comment's apostrophe as an opening string quote and never recognizes the real
statement separator. `_refuse_multi_statement` at line 95 therefore either
raises prematurely or forwards both SELECTs to Beanquery, which runs only
the first. This check has one caller, the local-file query path at line 210,
after argument/stdin selection and before JSON/text/CSV dispatch.

Count actual top-level statements while respecting BQL comments and quoted
text. Keep the query text intact and keep genuine multiple statements
rejected; do not disable the guard. Preserve the frontend/engine dependency
boundary if using the real parser. Add regressions for both directions above,
including a comment containing quotes, actual multi-statement input with
comments, and the existing quoted/trailing-semicolon controls.

Dedupe: searched all open/done/blocked queues for comments, semicolons,
apostrophes and multi-statement handling. Completed `w3/282` / `w1/m23/t005`
introduced this guard in `15629c14`; their full acceptance criteria require
real multi-statement refusal but tests omit comment punctuation. Completed
`w1/026` fixed leading-comment dispatch in the engine, a different layer;
`w3/102` is the hosted service. Open `w3/399` rewrites reserved table names
inside literals, not statement counting. Targeted helper history has no later
comment-aware fix. CLI-only; native `--source`, other OSes and malformed or
nested comments remain unverified.

Evidence: ignored `cli/tmp/qa-20260922T052032Z-loop/`, including
`query-comments-{repeat,multi-1,multi-2}.bean` and
`captures/query-comments-*.json`. Captures retain argv/cwd, isolated config,
stdin/PTY mode, separate streams, exit codes, duration and unchanged hashes.
The PTY control uses only a history/init path relocation hook; execution is
unchanged. Public reproduction needs only the fixture above.

---

**Resolved 2026-09-22** — statement counting now reads BQL comments as
comments, in both directions the note reported.

`_split_statements` tracked quotes but had no comment state. It now walks the
string with the same rules as the engine's `_code_mask`: a quote runs to its
unescaped close (BQL doubles a quote to escape it) and `/* */` runs to its
terminator; only a `;` outside both separates statements.

**A correction to my own earlier work.** I probed the parser instead of
assuming, and BQL has **no line-comment form** — `--`, `#` and a bare `;` are
each a syntax error, with or without a following statement. w3/399 (shipped
earlier in this run) had modelled `--` as a comment in `_code_mask`. That was
wrong, so this change removes it from both copies and corrects the w3/399 test
case that asserted it. Neither twin now describes a rule the grammar lacks.

Verified on the note's fixture: `/* explanation; one query */ SELECT count(*)`
returns 2 (was exit 2), and `/* don't ignore the tail */ SELECT …; SELECT …`
exits 2 with the multi-statement error (was exit 0 with only the first result).
All the note's controls hold — real multi-statement input is still refused, a
quoted `'a;b'` still works, a trailing `;` is still not a second statement, and
a dot command is still never split.

The frontend may not import the engine, so the rules live in two places.
`cli/tests/test_query_statement_comments.py` pins that they agree, by checking
that the `;` positions the splitter treats as separators are exactly the ones
the mask leaves visible — across literals, comments, doubled quotes,
unterminated constructs and the empty string. Reverting the fix fails 8 of its
26 tests, including that agreement pin. `cd cli && make check-all` passes
(1863 tests).

Unverified, as in the note: native `--source` delegation, other platforms, and
nested block comments (BQL's `/* */` does not nest, and an unterminated one is
a syntax error either way, so the splitter runs it to end of input and lets the
parser complain).
