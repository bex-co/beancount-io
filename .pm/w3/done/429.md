# `bea cloud ledger list` reports `truncated: true` on a full final page

**Severity:** minor. **Owner:** cli. **A1.** The `--json` envelope's
`truncated` flag is set by an off-by-one comparison, so a final page that is
exactly `--limit` rows long is reported as truncated even though there is no
next page. An agent that pages until `truncated == false` fetches one wasteful
empty page and may conclude more data exists when it does not.

Found by continuous CLI QA 2026-09-26, `bea` 0.3.0, HEAD `8cd9732b`, Darwin
25.5.0, authenticated file credential.

## Repro (needs a signed-in account with N accessible ledgers)

```sh
# With exactly 7 accessible ledgers:
bea --json cloud ledger list --limit 7   # rows=7, truncated=true  (WRONG: no page 2)
bea --json cloud ledger list --limit 7 --page 2   # rows=0, truncated=false
bea --json cloud ledger list --limit 8   # rows=7, truncated=false (correct)
```

Observed exactly this: `--limit 6` → 6 rows truncated true; `--limit 7` → 7
rows truncated true; `--limit 8` → 7 rows truncated false.

## Expected

`truncated` should mean "a further page exists." When the server has no
next-page signal, the only sound local proxy is `len(rows) == limit AND the
server did not indicate this is the last page` — and a full page that is also
the last page must not be flagged. The v1 list endpoint returns a bare array
with no total/next indicator, so the exact boundary is genuinely ambiguous from
one response; the fix is to stop over-claiming (e.g. only flag `truncated` when
`len(rows) == limit` and treat the truthful signal as "there may be more — request page+1", or fetch/expose the server's own has-more/total if the v1 contract can carry it).

## Root cause

`cli/src/cli/commands/cloud/generated/ledger.py:35`

```python
output.emit(rows, target=output.server_target(), truncated=len(rows) >= limit, limit=limit, page=page)
```

`len(rows) >= limit` is true whenever the page is full, including the last one.
This line is generated by `scripts/gen_cloud_commands.py:204-206`
(`truncated=len(rows) >= limit, limit=limit, page=page`), so the fix belongs in
the generator's emitted expression (and any hand-path that mirrors it), not in
the generated file. `docs/USAGE.md:444` documents `truncated` as "reports
`truncated` when more exist," which the current behavior violates on the exact
boundary.

## Out of scope

- Adding a real total/next-cursor to the v1 list contract (backend change);
  note it as the durable fix if the boundary must be exact.

**Resolved 2026-10-02** — Full JSON ledger pages now make one additional authenticated read for the first row after the requested page; `truncated` is true only when that row exists. Full final pages report false, short/empty pages need no probe, and human output keeps its single request. Probe errors propagate without inventing a flag. The shared API parser guard also rejects non-array JSON that generated array parsers would otherwise misread as an empty catalog. Shipped in `fc65f86d` (`cli`). The generator owns the change and `make codegen` regenerated its output; the backend contract is unchanged. Triage reproduced the seven-ledger boundary against localhost. The first full run was intentionally stopped after that source change; a fresh `make check-all` passed with 2,406 tests and one skip. Final source review and the updated public-tree secret scan passed. Documentation explains the extra read and its error behavior; all server responses were synthetic.
