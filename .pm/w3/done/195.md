# An Ask deep link sends its question to the AI on arrival, and again after login

**Minor · 45–60m · dashboard.** A3: opening a link someone sent you should not spend your AI quota on a prompt you never typed — least of all immediately after you sign in.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), 1440×1000, authenticated QA account on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. **No question was submitted** — the auto-submit path is traced in source, and the Ask page was only rendered in its idle state, so no AI quota was spent by this run.

`/ledger/<owner>/<name>/agent?q=<text>` (and `/ask?q=<text>`, which redirects to it) sends `<text>` to the AI agent on mount, with no confirmation and no chance to read it first. The page's idle state is otherwise correct: an empty composer with the **Ask** button disabled until you type.

Two distinct behaviors here, and only one of them looks deliberate:

1. **Deep-link auto-submit.** `dashboard/src/features/ai-agent/pages/agent/page.tsx:198-206` — a mount effect reads `q` from the search params and calls `sendMessage({ text: initialQuestion.trim() })`, guarded by `hasAutoSubmittedRef` so it fires once. The analytics call tags it `surface: "deep_link"`, so this is a designed feature. Note it is *not* a silent write: the agent's write tools go through explicit approval UI (`file-edit-approval.tsx`, `receipt-insert-approval.tsx`, `addToolApprovalResponse`), so a crafted prompt cannot edit a ledger without the user approving it. What it can do is spend the recipient's AI quota and put attacker-chosen text and its answer into their session history.
2. **Re-submit across the login boundary.** `page.tsx:99-107` — on a `401` the transport redirects to login with `next = window.location.pathname + window.location.search`, and the comment says so plainly: *"Keep q/mode/lang so login return can auto-submit the same Ask."* So an anonymous visitor who opens a crafted link is asked to sign in, and the moment they authenticate, the prompt is sent on their account. That is the sharp edge: the action crosses an authentication boundary the user did not intend to spend anything behind.

Expected: a deep-linked question is **prefilled** in the composer and the user presses Ask; at minimum, a question that arrived before authentication is never sent automatically after it. Actual: it is sent in both cases.

Fix: recommend prefilling rather than sending — it preserves the whole point of a shareable Ask link (the recipient sees the question in context, on the right ledger) while making the spend an explicit act. If product wants to keep same-session auto-submit, then at least drop `q` from the `next` URL on the 401 path so a post-login mount prefills instead of sending. Keep the existing `hasAutoSubmittedRef` single-fire guard, the streaming transport, the approval gates on write tools, and the `noIndex` already applied to `?q=` URLs (`routes/ledger.$ledgerOwner.$ledgerName.agent.tsx`, `…ask.tsx`). Owning package: `dashboard` only — no API or schema change.

Blast radius: both routes render the same component (`useParams({ strict: false })`, `page.tsx:60-66`), so one change covers `/agent` and `/ask`; the sandbox harness variant (`?mode=sandbox|agent` → `SandboxAgentPage`) shares the surrounding page and needs the same treatment. Check the Overview page's ask box, which links into this surface.

Adjacent states: an empty or whitespace-only `q` must stay inert (it already is — `initialQuestion?.trim()`); an over-long or malformed `q` must not break the composer; the read-only case (`isReadOnly`, `page.tsx:71`) and the unauthenticated case must both behave.

Dedupe: searched every queue including `done/` for auto-submit, deep link, prefilled and Ask terms. The hits (`114`, `121`, `137`, `178`, `179`) are all mobile deep-link findings about permissions, share sheets and journal contents — none concerns this surface. Completed `w2/m8` already treats prefilled Ask URLs as a special parameterized surface for indexing (canonicalising them to the base agent page and marking them `noIndex`), which is consistent with treating them cautiously here too, but it made no behavioral change. Nothing owns this.

Unverified: server-side rate limiting or plan gating on the chat endpoint (not probed, since probing means spending quota), the sandbox harness variant's own behavior, whether any quota is consumed for a rejected/empty response, and the patched behavior. This is a source-traced finding plus the rendered idle page — the auto-submit itself was deliberately not triggered.
