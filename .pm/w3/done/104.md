# Guest Star and Follow discard the sign-in return destination

**Minor · dashboard · 35–50m.** A2/A3: a visitor choosing to save a public
example or follow its author should return to that page after signing in.

## Reproduce

In a fresh signed-out browser:

1. Open /ledger/open_ledger/example?lang=en&time=2017 and click **Star**.
2. Wait for the Welcome back form. Its URL is /auth/login, with no next
   parameter. Its Sign Up link is likewise only /auth/sign-up.
3. Repeat at /ledger/open_ledger?lang=en&tab=followers using **Follow**.
   The same bare login URL loses the selected profile and tab.
4. Browser Back restores the original page, URL state and action. Login has no
   saved destination to consume.

Repeated on https://beancount.io on 2026-09-09 in four fresh Chrome
152.0.7977.77 contexts: both actions at 1440×1000 and 390×844, English/light,
zero initial cookies. Initial public documents return 200, with no page errors
or mutation requests. Final screenshots wait for the actual login heading;
earlier captures taken before route rendering settled were discarded.

Working control in four additional contexts: manually supplying the full
relative destination as next preserves it on login and through Sign Up. After
adding the existing QA session cookies in memory, opening that same login link
returns to the exact public ledger/year or profile/tab, HTTP 200. Star and
Unfollow controls are available there. This tests the authenticated login guard,
not a new password/OTP submission.

Evidence in dashboard/tmp/qa-20260907-w3-loop/:
social-login-next-evidence.json and
social-login-next-{star,follow}-{1440,390}.png. Source/fetched main 7f4b6190;
deployed SHA unverified, current source matches the missing search parameter.
No credentials or private profile payloads are in these captures.

## Root cause and fix

dashboard/src/features/reports/overview/components/star-button/index.tsx:40–44
and src/features/user-profile/components/follow-button.tsx:35–39 both navigate
to /auth/login without a search object for unauthenticated visitors. Each has
one production mounting caller, Overview :317 and user-profile-page :213.

LoginPage's actual success callback at features/auth/pages/login-page/index.tsx:
28–38 prioritizes a safe next destination; if absent, it selects the user's
default ledger or Welcome. Thus it cannot resume the chosen public action page.
This post-password consequence is source-traced. Its loader.ts:13–19 also
honors safe next for an existing session, as verified by the live controls.
Five existing login continuation tests pass, including safe-target preference
and rejection of external/protocol-relative/backslash destinations.

Have both guest action handlers supply the current same-origin relative route,
including relevant search state, as next using the existing auth-navigation
convention. Preserve encoding once, the selected ledger/profile and time/tab.
Keep getSafeRedirectPath in common/lib/auth/auth.ts and the existing login
consumer behavior. Authentication should return the visitor to the action's
page; it should not silently perform a deferred star/follow mutation.

Acceptance: both exact guest journeys emit their original relative destination
in next at both widths; Sign Up retains it and authenticated continuation opens
that destination. A component/router regression must start with each guest
action, since injecting an already-correct next into LoginPage alone misses the
defect. Signed-in Star/Unfollow pending, error and retry behavior should retain
the passing controls recorded in social-action-recovery-control.json.

## Dedupe and limits

Searched all open/done board notes, open milestones and targeted history for
social actions, login and return destinations. No existing item owns these two
handlers. 029 concerns Settings' fixed parent guard, 058 the password-recovery
link, and 082 Ask's custom 401 redirect; each has a different producer.
Commit c4e65a5b fixes consuming explicit next, not these missing values.
The action handlers have no next fix since import; aeec496b changes localized
copy only. No backend or GraphQL/REST/MCP change is needed.

These actions did not invoke the API while signed out. Expired-session races,
other public sign-in links, full password/OTP completion, other locales and
other browsers were not exercised in this probe. All temporary contexts closed;
no social relationship or product source changed.
