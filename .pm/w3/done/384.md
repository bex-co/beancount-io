# `bea report -i quarterly` silently drops a complete final quarter (regression from w3/375's fragment fix)

Severity: minor. **Estimate:** ~1h. **Owner:** cli. A full-year quarterly
breakdown reports three quarters, not four, and the JSON envelope contradicts
itself about how many periods the filter covers.

Found 2026-09-21 by continuous CLI QA. HEAD `6998a659` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, no login. Synthetic fixture only; no credentials used.

## What is wrong

`report income-statement -i quarterly` over a full year emits only three of the
four quarters whenever the last quarter has no entries. `-i monthly` over the
same filter emits all 12 months including an empty December, so the two
intervals disagree about the same filtered period. Under `--json` the
contradiction is explicit: `period.end_exclusive` is `2027-01-01`, `interval`
is `quarterly`, `truncated` is `false` — and `periods` holds three dates.

## Repro (synthetic, no login)

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-02-10 * "Grocer"
  Expenses:Food   10.00 USD
  Assets:Cash
EOF

bea --file main.bean report income-statement -t 2026 -i quarterly
# PERIOD END  INCOME  EXPENSES   NET PROFIT
# 2026-03-31  —       10.00 USD  -10.00 USD
# 2026-06-30  —       —          0.00 USD
# 2026-09-30  —       —          0.00 USD
#                                             <-- no 2026-12-31 row

# control — monthly keeps its empty final period:
bea --file main.bean report income-statement -t 2026 -i monthly | tail -1
# 2026-12-31  —  —  0.00 USD

# the JSON envelope disagrees with itself:
bea --json --file main.bean report income-statement -t 2026 -i quarterly
# data.period.end_exclusive = "2027-01-01", data.interval = "quarterly",
# truncated = false, data.periods = ["2026-03-31","2026-06-30","2026-09-30"]
```

Adding any Q4 entry (e.g. a `2026-11-20` rent transaction) makes the
`2026-12-31` row reappear, so the drop is conditioned on the quarter being
empty, not on the filter. `-t "2026-01 - 2026-12"` and
`-t "2026-01-01 - 2026-12-31"` behave identically, and
`-t "2025-01 - 2026-12"` yields 2025 Q1–Q4 plus 2026 Q1–Q3 — the trailing
quarter is the one lost.

## Expected

Four quarterly rows for a full-year filter, the same way monthly yields twelve
and yearly yields one. A complete quarter that happens to be empty is a real
reporting period and reads `0.00`, exactly as empty Q2 and Q3 already do in the
same table.

## Root cause (verified)

`cli/src/fava/util/date.py:140` — `_IntervalQuarter.get_prev` scans
`for i in [10, 7, 4]` with a strict `>`, so it is not idempotent on a quarter
start:

```
get_prev(2026-01-01) = 2026-01-01   idempotent
get_prev(2026-04-01) = 2026-01-01   NOT idempotent
get_prev(2026-07-01) = 2026-04-01   NOT idempotent
get_prev(2026-10-01) = 2026-07-01   NOT idempotent
```

`_IntervalMonth.get_prev` is idempotent on every month start, which is why
monthly is unaffected.

`cli/src/fava/modules/chart.py:56` decides whether the last flow range is a
complete interval or a clipped fragment with:

```python
whole = interval.get_prev(last.begin) == last.begin and interval.get_next(last.begin) == last.end
```

For the Q4 range (`begin=2026-10-01`, `end=2027-01-01`) the second conjunct
holds but the first is `2026-07-01 == 2026-10-01` → `False`, so a whole quarter
is classified as a fragment and `_flow_ranges` returns `ranges[:-1]`
(`chart.py:59`) whenever that quarter carries no entries. The same
misclassification applies to Q2 and Q3 when either is the last range of a
filter.

## Fix

Make `_IntervalQuarter.get_prev` idempotent on quarter starts (`>=` in the
`[10, 7, 4]` scan, matching `_IntervalMonth`), so the `whole` test at
`chart.py:56` recognises a complete quarter. Add regression coverage for
`get_prev` idempotence on all four quarter starts and for a full-year quarterly
breakdown yielding four periods in both the human table and `--json`. Keep the
w3/375 weekly behaviour green: `-t 2020-03 -i weekly` must still end on
2020-03-29, and `-t 2020-12 -i weekly` must still keep 2020-12-31.

## Blast radius

- `report income-statement -i quarterly` — the row disappears entirely.
- `report overview -i quarterly` — the `2026-12-31` row survives, because its
  cumulative assets series drives the date union, but the INCOME and EXPENSES
  cells render `—` instead of `0.00`, reading as missing data rather than zero.
- `_flow_ranges` has no caller other than `ChartModule.interval_totals`
  (`cli/src/fava/modules/chart.py:168`). Cumulative series (`net_worth`,
  `account_balance`) use `filtered.interval_ranges` directly and are unaffected
  — confirmed by the surviving overview assets column.
- `interval_ends` also calls `get_prev`, but only to clamp a range start
  backwards, where the non-idempotence is harmless:
  `interval_ends(2026-01-01, 2027-01-01, quarterly, complete=True)` already
  yields all four quarter boundaries.
- Weekly and daily `get_prev` are idempotent on their own period starts, so the
  heuristic behaves for them.
- No money is lost — a dropped range is empty by definition. The defect is a
  missing (or blank) reporting period and a JSON envelope that under-reports
  its own period count while claiming `truncated: false`.

## Adjacent states

Exercised: empty trailing quarter (dropped), Q4 carrying entries (kept),
multi-year filters, filters shorter than one quarter (exempted by the
`len(ranges) < 2` guard at `chart.py:53`), and `-i monthly|yearly|weekly` as

---

**Resolved 2026-09-21** — a full-year quarterly breakdown reports four
quarters again, and the JSON envelope agrees with itself.

The note's root cause held exactly. `_IntervalQuarter.get_prev` scanned
`[10, 7, 4]` with a strict `>`, so it was not idempotent on a quarter start,
and `_flow_ranges`' `whole` test at `chart.py:56` classified a complete Q4 as a
clipped fragment — dropping it whenever it was empty. The scan now uses `>=`,
matching every other interval, whose `get_prev` is already idempotent on its
own period starts.

The non-idempotence was wider than the reported symptom: with `>`, *every date
in April, July and October* answered the previous quarter's start, not just the
1st. That also made `number_of_days` report the wrong quarter's length for
those months (91 days of Q1 for a date in Q2), so the regression test pins
`get_prev` and `number_of_days` directly across all twelve months rather than
only through the report.

Verified: `-t 2026 -i quarterly` yields 2026-03-31/06-30/09-30/12-31 in the
human table and in `data.periods`, with the empty final quarter reading
`0.00 USD` exactly as Q2 and Q3 do; `end_exclusive` 2027-01-01 with
`truncated: false` now means four periods; `-t "2025-01 - 2026-12"` yields all
eight quarters; monthly/quarterly/yearly agree at 12/4/1 over the same filter.
`report overview -i quarterly` renders the 2026-12-31 row consistently with its
empty siblings.

w3/375's definition of done is rechecked and green, which is what the note
asked for: `-t 2020-03 -i weekly` still ends on 2020-03-29 (empty fragment
dropped) and `-t 2020-12 -i weekly` still keeps 2020-12-31 (fragment with a
transaction). Its own test file passes unchanged, and both cases are pinned
again here.

Regression coverage is `cli/tests/test_report_quarterly_final_period.py`.
Reverting the fix fails 13 of its 27 tests; `test_report_weekly_month_end_
fragment.py` passes either way, which is what makes it a control. `cd cli &&
make check-all` passes (1589 tests).

Not done here: this is a bug in vendored Fava code that likely affects upstream
too. Reporting it upstream is worth doing but is its own item, not this fix.
