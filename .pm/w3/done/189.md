# The account journal rounds a posting the transactions list shows in full

**Severity:** minor. **Estimate:** 45–60 minutes. Package: mobile. A2/A3 — a public example ledger recorded to three decimals should not show two different amounts for one posting depending on which screen you opened.

Production https://beancount.io, September 12, 2026; local HEAD `84231f9c` with JS served from a local Metro dev server, native development build `io.beancount.ios` 1.20260906.47, iPhone 17e / iOS 26.5, English / System-light / default text size. Authenticated QA session, public read-only `open_ledger/minimax` (operating currency `MUSD`, recorded to three decimals). Read-only; no ledger write.

## Repro

1. Transactions tab → filter icon → date range `YTD`, account `Assets:Current:Cash` → Apply. One entry remains, June 29 2026, displayed **+423.284 MUSD**.
2. Open `beancount:///(app)/account-detail?account=Assets:Current:Cash`. The same June 29 entry is the only transaction row; it displays **+423.28 MUSD**, its day-section total displays **+423.28 MUSD**, and its running balance displays **Balance: 930.90 MUSD** (the preceding Pad row reads 507.62, and 507.62 + 423.284 = 930.904).
3. The unfiltered Transactions list and Home “Recent Transactions” independently show three decimals for this ledger (`3,994.853`, `2.081`, `5.583`, `357.997`, `112.444` MUSD).

## Expected / actual

Expected: one posting reads the same on every surface that shows it, at the precision the ledger recorded — this is the contract `w3/done/109` established when it fixed the transactions/Home headline (“preserve meaningful commodity precision … rather than applying a universal cents cap”). Actual: the transactions list honours the recorded scale and the account journal silently truncates the same value to cents.

## Root cause

Two formatters with different contracts:

- `mobile/src/screens/transactions-screen/utils/transaction-display-utils.ts:27–54` — `amountScale()` recovers the scale from the API's decimal **string** and `formatAmount()` uses it as `maximumFractionDigits`. This is `w3/done/109`'s fix, and it is why the list shows `423.284`.
- `mobile/src/common/number-utils.ts:49–54` — `groupThousands()` hard-codes `safe.toFixed(2)`, and `formatSignedMoneyWithCurrency` / `formatMoneyWithCurrency` (`:104–124`) build on it. The account-detail entry row (`account-detail-screen/components/account-entry-row.tsx:125`), its running balance (`utils/format-account-journal-balance.ts:14`) and its day totals (`selectors/select-account-journal.ts:182`) all go through it, so every amount on that screen is capped at cents regardless of what was recorded.

`w3/done/109` called this out explicitly and scoped it out: *“AccountEntryRow uses a separate selector and is not claimed affected by this cause.”* This note is that residue, reproduced.

## The product decision this needs

`w3/done/171` (the chart-counting note, same MUSD ledger) treated the two-decimal balance formatter as the **reference** rendering for the Accounts table (`-367.985` → expected `-367.99`). So the board has accepted cents for aggregate balances while requiring recorded scale for per-entry amounts. Decide which contract the account journal's rows fall under and apply it consistently; the defensible split is: **per-entry change amounts follow the recorded scale (109), aggregate/converted balances may stay at cents (171)** — but the day-section total and running balance in this same list then need a stated rule too, because a cents-rounded running balance under exact-scale rows will visibly fail to add up.

## Fix

Give the account-journal amounts the same recorded-scale treatment the entry list already has, reusing the existing `amountScale`/`formatAmount` approach rather than adding a second implementation or a new dependency. Whatever rule is chosen for the running balance and day totals must keep the column internally consistent (rows and the balance they roll into must agree). Do not fix this by widening `groupThousands` to a fixed three decimals — that changes every caller listed below, including USD ledgers where `$1,234.500` would be wrong — and do not relabel MUSD or convert it to USD.

## Blast radius

`groupThousands` reaches `formatSignedMoney`, `formatMoneyWithCurrency` and `formatSignedMoneyWithCurrency`, whose callers are: account-detail entry rows / balance / day totals; `components/account-table/account-table.tsx:257` (Accounts tab); `common/d3/interactive-line-chart.tsx:352,359` (chart headline and tooltip — the surface `w3/done/171` fixed); `screens/reports-screen/components/category-breakdown.tsx:221,274,355`; `screens/budget-screen/components/budget-group-card.tsx:186,253`; `screens/home-screen/components/budget-card.tsx:105` and `selectors/select-budget-panel.ts:98–99`; `screens/merchant-detail-screen/merchant-detail-screen.tsx:472`; and `screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:506,635` (whose own cents model is already owned by **w3/m34** — do not fold that in here). Any change to the shared helper must leave those surfaces' current behaviour deliberate rather than incidental. Working control: the Transactions list and Home on the same ledger, which already render `423.284`.

## Adjacent states

Ordinary two-decimal USD ledgers (must keep `$1,234.50`, not gain trailing zeros), an account whose rows are converted to the operating currency (`Assets:Staking:Ethereum:ETH` on `open_ledger/crypto-example` renders in USD, so it is not affected by scale at all), zero and negative changes, the `Balance`/`Pad` directive rows that render `+0.00`, and the initial loading skeleton.

## Dedupe

Searched every open and `done/` queue across w1–w5 for `groupThousands`, `number-utils`, `toFixed`, decimal/precision/rounding and account-detail terms. `w3/done/109` is the same defect class on a **different** helper and explicitly excludes this row type; `w3/done/171` shares the ledger and the formatter but is an animation-target bug, already fixed; `w3/m34` is the multi-posting **draft entry** cents model (write path), not this read path; `w3/done/116` and `w3/done/m26` are dashboard formatting. No open item covers the account journal's read-side precision. No current-main repair exists — `toFixed(2)` is present at `number-utils.ts:51` at HEAD `84231f9c`.

## A third surface deliberately implements the opposite rule

`transaction-detail-screen/selectors/select-transaction-detail.ts:55–91` formats posting units **from the recorded decimal string**, with a comment saying so explicitly (“so commodity quantities keep their source scale … Avoids `parseFloat` → `maximumFractionDigits: 2` which rounded share quantities away”), and pads to two digits only for USD. Observed on the June 30 2026 `FY2026 H1 Income Statement` entry: `-116.573`, `+95.760`, `+296.870`, `+57.203`, `+31.025 MUSD`, and a genuinely zero-scale posting rendering as `0 MUSD` — all faithful to the source. So the transactions list, the merchant detail rows and the transaction detail all preserve recorded scale by design; the account journal's `groupThousands` path is the outlier, which narrows the decision in the section above. Evidence: `mobile/tmp/qa-20260912/ca05-menu.png`.

## Fix ordering against `w4/016` (added September 13)

Adjacent states above notes that `Assets:Staking:Ethereum:ETH` on `open_ledger/crypto-example` "renders in USD, so it is not affected by scale at all". That is true today and it has a consequence worth stating: **`w4/016` is currently masking this defect on every commodity account, and fixing it will expose this one.**

Re-checked on `crypto-example` at HEAD `038faeeb`: Home's Recent Transactions shows `+0.005 STETH` with scale intact (the `formatAmount` path), while the same holding reads `$1,694.75` in the Accounts tree, `$1,694.75` in the account-detail hero, and `+$16.75` / `+$12.50` in its rows — all USD, all through `groupThousands`. Two decimals is correct for dollars, so nothing looks wrong there now.

`w4/016` asks for those surfaces to show the commodity the ledger actually records. The moment they do, `0.9012 STETH` starts flowing through `toFixed(2)` and renders as `0.90`. Whoever takes `w4/016` should take this note with it, or the first fix will appear to have introduced the second.

## A related question this note does not claim as a defect

While tracing the two formatters, both turn out to be **US-formatted regardless of app locale**: `groupThousands` hardcodes `,` grouping and `.` decimals in a regex, and `formatAmount` calls `toLocaleString("en-US", …)`. A German user sees `3,177.39` where the convention is `3.177,39`.

This is deliberately **not** filed as a bug. Pinning number format has the same defensible justification `common/date-format.ts` gives for pinning the calendar to Gregorian — these figures are reconciled against a plain-text `.bean` file that uses `.` as its decimal separator, and *"a list header that disagrees with the file it describes is a bug however well-localized it is."*

What is missing is the decision itself. `date-format.ts` opens with an explicit rationale for pinning one thing while localizing everything else; `groupThousands` carries no comment, and `formatAmount` expresses the pin as `toLocaleString("en-US")` — which is what an oversight looks like, not a choice. That same file records that *"Every screen used to hard-code `toLocaleDateString("en-US", …)`"* before it was cleaned up, so an `en-US` literal here has a history of meaning "not yet fixed". Whoever consolidates the formatters should write one sentence either way. `w4/056` is the same ambiguity on a third surface (the date picker's `locale="en_US"`).
