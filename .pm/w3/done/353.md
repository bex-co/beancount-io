# `bea query` `SELECT DISTINCT tags|links` fails on set columns agents are told to dedupe

**Severity:** minor. **Estimate:** 30–60 minutes. **Owner:** cli. **A1:** Ask/BQL
guidance lists `tags`/`links` and recommends `SELECT DISTINCT`, but
`SELECT DISTINCT tags` exits **1** with “cannot use starred expression here”
while `SELECT DISTINCT account` works.

Found 2026-09-16 by continuous CLI QA ([c950 hunt](90f597af-bab2-4fe5-bfc7-4780047afb2e)),
HEAD `68428a51`, `uv run bea` 0.2.0, Darwin 25.5.0 arm64. Confirmed
`cli/tmp/qa-20260915/c951/`. Evidence: `c950/`.

## Repro

```sh
bea --file main.bean query 'SELECT tags'
# grocery duplicated per posting

bea --file main.bean query 'SELECT DISTINCT tags'
# exit 1 — cannot use starred expression here

bea --file main.bean query 'SELECT DISTINCT account'
# exit 0 — works
```

Same failure for `links` / `GROUP BY tags`.

## Expected

Return unique tags/links, or document the set-column limitation with a working
recipe (flatten/unnest).

## Actual

Beanquery types `tags`/`links` as sets; DISTINCT/GROUP BY cannot hash them.
Opaque error; Ask prompt still recommends DISTINCT.

## Fix

Flatten set columns for DISTINCT, add scalar accessors, or document + fix Ask
prompt. Regression: fixture returns `grocery`/`travel` once each.

## Dedupe

Not w3/247. No open note covers DISTINCT on `tags`/`links`.

**Resolved 2026-09-17** — Took the "document with a working recipe" branch:
`tags`/`links` are sets and beanquery genuinely cannot hash them, so teaching our
fork to unnest would be re-implementing upstream (`.pm/DO_NOT_DO.md`). What was
actually broken was the answer. `SELECT DISTINCT tags` leaked a raw Python
compile error — `cannot use starred expression here (<string>, line 4)`, exit 1,
naming neither the query nor the column. It now exits **2** with
"BQL cannot use DISTINCT or GROUP BY on tags: a set is not a value it can
compare", followed by recipes that work: `SELECT DISTINCT joinstr(tags)`,
`GROUP BY joinstr(tags)`, and `WHERE 'grocery' IN tags`. The same recipes are
appended to beanquery's own non-hashable GROUP BY error, so both routes to the
limitation end in the same advice.

The `bea ask` system prompt recommended `SELECT DISTINCT` without the set-column
caveat; it now names the limitation and carries both recipes as examples. All
three recipes are exercised by the regression test, including that `joinstr`
does not order set members stably — so membership, not joined text, is what to
compare. Documented in `cli/docs/USAGE.md`; covered by
`cli/tests/test_query_set_columns.py`. Shipped with this board close.
