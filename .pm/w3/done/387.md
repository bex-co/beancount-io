# A signed-out managed price include reports "redirects are not followed (HTTP 302)" instead of saying to sign in

Severity: minor. **Estimate:** ~1h. **Owner:** cli (server note below). The
documented one-line price feature fails, for the single most likely reason,
with a transport detail that never mentions authentication.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, signed out. Synthetic fixture; no credentials used or needed
to reproduce.

## What is wrong

`USAGE.md`'s "Managed price includes" section presents a one-liner:

```beancount
include "https://beancount.io/prices/BTC-USD"
```

and notes, several sentences later, "Sign in with `bea cloud login` or set
`BEA_TOKEN` before fetching Beancount.io prices." A user who has not done that
gets no hint of it. The endpoint 302-redirects an unauthenticated request to
its login page, the CLI correctly refuses to follow the redirect, and reports
only the refusal:

```
fetch failed (redirect): redirects are not followed (HTTP 302). Run bea price status to inspect the source.
```

`bea price status` then repeats the same string in its `ERROR` column, so the
suggested next step adds nothing. Nothing in either surface says "you are not
signed in", which is what actually happened.

This is the same class of defect as the closed `w3/done/381` (`bea ask` with a
rejected credential dumped SDK internals instead of the standard "Not logged
in…"), on a path that fix did not touch.

## Repro (synthetic, no credentials)

```sh
printf 'option "operating_currency" "USD"\ninclude "https://beancount.io/prices/BTC-USD"\n2026-01-01 open Assets:Cash USD\n' > pr.bean

bea --file pr.bean price status
# exit 0
# ALIAS    FRESHNESS    REVISION  OBSERVED AT  …  ERROR
# BTC-USD  unavailable  -         -            …  fetch failed (redirect): redirects are not followed (HTTP 302).

bea --strict-prices --file pr.bean check
# exit 1
# Error: managed price source https://beancount.io/prices/BTC-USD is unavailable in strict mode:
#        fetch failed (redirect): redirects are not followed (HTTP 302).
```

Signed out and holding a rejected `BEA_TOKEN` are indistinguishable — both
produce the identical 302 string, each verified against its own freshly created
cold cache directory:

| Credential state | Reported error |
| --- | --- |
| no token | `fetch failed (redirect): redirects are not followed (HTTP 302)` |
| invalid `BEA_TOKEN` | `fetch failed (redirect): redirects are not followed (HTTP 302)` |

## Evidence that this is the auth path

The endpoint redirects unauthenticated callers to the login page:

```sh
curl -s -o /dev/null -D - https://beancount.io/prices/BTC-USD
# HTTP/2 302
# location: http://beancount.io/auth/login?next=%2Fprices%2FBTC-USD
```

So "redirects are not followed" is, in the common case, "you are not signed in".

## Expected

When a managed price fetch is refused because of a redirect whose target is the
deployment's own login path — or when the response is 401/403 — say so in the
source's error and point at the documented remedy, e.g. `not signed in: run
bea cloud login or set BEA_TOKEN`, the same vocabulary `bea cloud status`
already uses. Keep refusing the redirect; only the diagnosis changes. A
redirect to anywhere else should keep today's transport wording, since that
genuinely is an unexpected hop rather than a login wall.

## Working controls

- **The allowlist is correct and does distinguish cases.** Non-allowlisted
  origins and non-`/prices/` paths never reach a fetch — they fall through to
  the ordinary loader as an unmatched glob, while the valid form produces the
  distinct `managed price source unavailable` message. Verified refused:
  `https://evil.example.com/prices/BTC-USD`,
  `https://beancount.io/../etc/passwd`, `https://beancount.io/graphql`,
  `http://beancount.io/prices/BTC-USD` (plain HTTP),
  `https://beancount.io/prices/BTC-USD/../../admin`.
- **`--offline` is honoured on a cold cache.** It reports
  `managed price source unavailable: … : None` with no fetch attempted, rather
  than reaching the network. The 302 text only appears once an online read has
  recorded it.
- **`bea cloud status` gets this right** signed out (`exit 3`, "Not logged in.
  Run 'bea cloud login', or set BEA_TOKEN.") and with a rejected token
  (`exit 3`, naming `BEA_TOKEN` as the credential in use). That is the
  vocabulary the price path should borrow.

## Blast radius

- Every command that resolves managed price includes shares the message:
  `check`, `list`, `query`, `report`, `import`, and write validation, per
  `USAGE.md`'s own list. `--strict-prices` turns it into a failed load (exit 1);
  without it the load succeeds and the source is merely `unavailable`.
- `bea price status` and `bea price refresh` surface the same stored error
  string.
- Not a data-integrity or security defect: the redirect is refused, no bearer
  header goes anywhere but the exact allowlisted endpoint per the documented
  contract, and no ledger content is sent. Only the diagnosis is wrong.

## Server-side note (separate owner)

The redirect `location` is **`http://`beancount.io/auth/login**, not `https://`.
The CLI refuses to follow it either way, so there is no CLI exposure, but a
production endpoint emitting a plaintext redirect target is worth fixing where
that route is owned. Not filed as CLI work and not verified beyond the single
`curl -D -` above.

## Adjacent states

Exercised: cold cache, `--offline`, `--strict-prices`, signed out, rejected
token, five refused origin/path spellings, and the valid alias. Split-ledger

## Unverified

The authenticated happy path — a real fetch, `recent` freshness, revision and
`observed-at` values, `price refresh`, `price export`, shadowing by a
ledger-authored price — was not exercised: it needs a CLI token, and the device
flow requires interactive browser approval that this run had no authorization

to this 302) already produces a better message.

---

**Resolved 2026-09-21** — a signed-out managed price include now says so, in
the same vocabulary `bea cloud status` uses.

The diagnosis the note asked for already existed in `managed_prices.py`: a 3xx
whose `Location` is the login path already mapped to `reason="auth"` with
`Not logged in. Run bea cloud login, or set/replace BEA_TOKEN.` It never fired
because it matched the raw header against a set of two literal spellings —
`/auth/login` and `https://beancount.io/auth/login` — and production sends
`http://beancount.io/auth/login?next=…`. The note recorded that `http://`
location under "server-side note" without connecting it to the miss; it is in
fact the whole cause of the CLI symptom.

`_is_login_redirect` now parses the `Location` and compares the path (and the
host only when the target carries one), so scheme, query string and a trailing
slash cannot hide a login wall. This decides wording only — the redirect is
still refused, and a hop anywhere else keeps the transport message, because
that genuinely is an unexpected redirect.

That also resolves the note's "signed out and rejected BEA_TOKEN are
indistinguishable" complaint: the existing branch already picks
`Credential rejected` over `Not logged in` based on whether a token was sent,
and both now reach it.

One thing the fix surfaced and fixed with it: `--strict-prices` appends a full
stop to the cause, which was invisible while the cause was
`…(HTTP 302)` but produced `…BEA_TOKEN..` once the cause became a sentence.

Verified on cold caches: signed out reports `fetch failed (auth): Not logged
in. Run bea cloud login, or set/replace BEA_TOKEN.`; a rejected `BEA_TOKEN`
reports `Credential rejected.`; `--strict-prices check` exits 1 with the same
diagnosis and a single period. `--offline` on a cold cache is unchanged.

Regression coverage is in `cli/tests/test_price.py`: the login-wall spellings
are parameterized (production `http://` with `?next=`, `https://` with and
without a query, relative, relative with a trailing slash), with a matching
set of non-login redirects — login path on another host, same host other path,
relative other path, and a missing header — pinned to keep the transport
wording. The pre-existing test here used only the relative `/auth/login`
spelling, which is why the production form slipped through. Reverting the fix
fails 4 of the 12. `cd cli && make check-all` passes (1624 tests).

Still open, unchanged by this: the note's server-side observation that the
redirect target is `http://` rather than `https://`. That route is not owned
here, and the CLI refuses to follow it either way, so there is no CLI exposure
— but it is worth fixing where that route lives, and this fix deliberately
does not depend on the scheme so it stays correct either way.

Also still unverified, as the note says: the authenticated happy path needs a
CLI token and interactive device-flow approval, which this run had no
authorization to complete. Whether a genuine 401/403 already produced a good
message is now moot for 401 — it takes the same `auth` branch, which the tests
cover — but the live authenticated fetch remains unexercised.
