# Keep the code editor's active line above the native keyboard

**Severity:** minor. **Estimate:** 45–60 minutes. **Package:** mobile.
**Goal:** A2 — people editing a ledger can see what they type without repeatedly scrolling manually.

## Native reproduction

September 13, 2026; HEAD84231f9c; production API; authenticated QA session with writable public synthetic `open_ledger/minimax`; iPhone17e, iOS26.5, native development build1.20260906.47(47), Expo57/RN0.86; English, light, default large text size.

1. Select MiniMax, open the actual Files tab, then `main.bean` (73 lines). Scroll to the final blank line73.
2. Tap that line and type the unsaved comment `; QA final draft` using the guarded native text-entry helper. Do not press Save.
3. With the software keyboard open, tap its X key. The draft contains `; QA final draftx`, but automatic cursor visibility is incorrect.
4. Scroll upward inside the editor. The line can be brought into view manually. Back → Discard removes the local draft; reopening shows the original content.

Initial PID66436: the bottom of line73/caret is covered by the quick-insert bar, including after a real software keypress. A manual upward drag brings it fully into view. After discarding, terminating and relaunching (PID78317), the original file has blank lines3 and73 and disabled Save. Repeating from that fresh editor leaves line73 entirely behind the keyboard: only lines43–57 are above the quick-insert bar. It remains hidden after the software X key. One upward drag brings line73 to the bar's top edge, still partly clipped. The text-entry helper asserts the comment exists; the native attachment captures the keyboard and editor in the same test.

Expected: focusing and typing on the final line keeps the entire caret and text line above both the native keyboard and application quick-insert bar after layout settles. Actual: typing continues in obscured content until the user manually scrolls. This is not a save/data-loss finding; neither draft was saved.

## Cause and fix scope

`mobile/src/components/code-editor/code-editor.tsx:451` handles `keyboardInset` only by setting `view.scrollDOM.style.paddingBottom`. The container remains fixed with `inset:0`. The caller computes keyboard overlap plus the44-point accessory height at `src/screens/ledger-file-editor-screen/index.tsx:489–500` and passes it at651, while rendering the native bar separately. Padding supplies scrollable space but does not itself update the active selection or describe the obscured viewport to CodeMirror.

Installed `@codemirror/view/dist/index.js:3420–3462` computes cursor scrolling from its measured rectangle and `getScrollMargins`; its mobile visual-viewport fallback does not know the app's separate bar. This is the integration gap indicated by the observed behavior. The precise WKWebView visual-viewport timing and relative contributions of keyboard appearance versus subsequent selection updates remain uninstrumented.

Make the editor account for the actually obscured area when revealing its selection, including after keyboard/inset changes. Use the editor's viewport/scroll-margin mechanisms or an appropriately resized viewport and request selection reveal after measurement; do not merely add more constant padding. Avoid double-counting any viewport shrink already performed by WKWebView. Preserve manual scrolling and hiding the keyboard. Verify native keyboard opening on a bottom line, continued typing, and accessory insertion, plus the keyboard-hidden control.

Shared caller search finds both LedgerFileEditorScreen and EditTransactionScreen (`src/screens/edit-transaction-screen/edit-transaction-screen.tsx:442`). The latter needs regression coverage but was not independently reproduced for this symptom. Read-only files have no editing accessory; plain-text editing without the Beancount bar is also unverified. No backend/API behavior change is required.
