## Objective

Give `addBulkEntries`, `appendDirectiveText`, and `insertReceiptTransaction` an optional `requestId` with ledger creation's semantics, keyed by user + ledger + requestId, kept 24 hours.

## Context

- Template: `features/ledger/workflow/ledger-workflow.ts` (createLedger idempotency, `CACHE_KEYS.ledger.createRequestByUserAndId`, strict cache helpers).
- Claim the id atomically in Redis (SET NX), not with the process-local `AsyncLock`, so two backend instances cannot both write.
- Request fingerprint: the normalized write input (entries/text, target file, receipt fields), not transport details.

## Acceptance criteria

- [x] Same id + same request → stored result, no second write; same id + different request → validation error; id in progress → retryable conflict; failed write → id released.
- [x] A Redis error on any step logs and lets the write proceed unprotected (fail-open); no write fails because of the store.
- [x] No `requestId` → no Redis access at all.
- [x] Service-level tests cover each case with a real in-memory store double.

## Out of scope

- Transport plumbing (t002); clients (t003/t004).

## Done 2026-11-03

- `foundation/redis/redis-idempotency.ts`: `redisIdempotencyStore`, an atomic claim (one Lua `SET NX PX`, then `GET`), plus complete and release. Every method fails open, returning `undefined` or a no-op, when Redis is down. It uses the raw client, following the `redis-counter.ts` pattern, because the cache helper's get-then-set is not atomic across instances.
- `features/ledger/utils/entry-write-idempotency.ts`: `runIdempotentEntryWrite`, keyed by `CACHE_KEYS.ledger.entryWriteRequest(user, ledger, id)` with a 24h TTL and a SHA-256 fingerprint of the operation and the normalized request.
  - Replays a done record; refuses a fingerprint mismatch (`ValidationError` on `requestId`); answers in-progress with `ConflictError` and a retry hint.
  - Releases the id when the write throws or returns `success: false`.
  - Runs the write unprotected when the store is unavailable; with no id it never touches the store. The id is 1–200 characters, like creation's.
- Wired in after authorization:
  - `LedgerEntryService.addBulkEntries` takes a new `requestId` argument; the fingerprint is the inputs and `allowInvalid`, and dry runs skip idempotency.
  - `appendDirectiveText` takes `requestId`; the fingerprint is text, path and `allowInvalid`, and dry runs skip.
  - `LedgerReceiptWorkflow.insertReceiptTransaction` takes `params.requestId`. It wraps everything after authorization, so a retry neither promotes the receipt again nor posts again.
- Tests:
  - `entry-write-idempotency.test.ts` (11) covers the state machine with an in-memory store: no id, replay, mismatch, cross-operation, concurrent conflict, release on throw or `success: false`, store down, crash after commit, and length bounds.
  - `entry-write-request-id.test.ts` (9) covers the three services with the `fake-redis-idempotency` module double, including authorization on every replay, per-ledger keys, dry runs, and Redis down.
  - `redis-utils.integration.test.ts` checks the Lua against a real `redis-server`: 1 of 20 concurrent claims wins, the TTL is set, and replay and release work.
- Gates: typecheck; full `yarn test` (8148); ESLint; Knip, whose only finding is the existing, unrelated oauth export; Prettier on the changed files.
