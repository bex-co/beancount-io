# `bea query -o FILE` truncates an existing export when the query fails (docs promise preservation)

Severity: major. **Estimate:** ~1h. **Owner:** cli. A failed text-mode
query destroys the previous export instead of preserving it.

`cli/docs/USAGE.md`: "a failed query or write preserves an existing
export." Actual: the destination is truncated to 0 bytes before the
query runs, so any execution failure leaves an empty file where the
last good export was.

## Repro (synthetic, no login)

```sh
cd cli
cat > /tmp/q.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
EOF
echo "SENTINEL" > /tmp/keep.txt
uv run bea --file /tmp/q.bean query "SELECT FROM WHERE bad" -o /tmp/keep.txt
# exit 2 (correct) — but /tmp/keep.txt is now 0 bytes (SENTINEL gone)
```

HEAD `b94d9461`, bea 0.2.0, Darwin arm64, isolated config/cache.
Reproduced 2/2 (fresh file each time).

## Root cause

`text_answer` (`cli/src/bea_engine/query.py:90-135`) opens the
destination for write *before* executing the query:

```python
destination = output.open("w")   # truncates here
shell.outfile = destination
try:
    _executed(...)                # BQL syntax error raises here
finally:
    destination.close()          # leaves a 0-byte file
```

The existing comment carefully orders the open after the *ledger load*
(so `-o` cannot truncate the books) but not after the *query*. The
`--json` path is unaffected: the engine returns columns/rows and the
frontend writes via `output.emit(destination=...)` only on success
(verified: `SENTINEL` survives a failed `--json` query), and `format -o`
fails before opening (verified). So only text/csv/beancount `-o` exports
are affected — including partial writes if a query fails mid-stream.

## Fix direction

Render into the existing `StringIO` buffer and move the
`output.open("w")` (or an atomic replace) to after `_executed`
succeeds; on failure the old export must be byte-identical. Keep the
`_refuse_alias` guard (it already runs pre-write and must stay there).
Regression tests: failed-query-keeps-export for text and csv (before/
after hash), success still replaces, alias refusal unchanged. Also
cover a mid-stream execution failure if one is constructible, since
streaming would otherwise leave a partial file.

## Blast radius / dedupe

- Affected: `query -o` in text/csv/beancount formats whenever the query
  fails after the open (BQL syntax errors confirmed; other execution
  failures by inspection). The source ledger is never at risk (alias
  refusal runs first). Interactive `.output` redirection is a separate
  path (engine `do_output`) and out of scope for this report.
- Working controls: `--json -o` preserves (atomic frontend emit);
  `format -o` usage failure preserves (fails before open); success
  paths replace as documented.
- Searched all `.pm/**/*.md` for export-preserve/truncate: no match.

---

**Resolved 2026-09-21** — a failed `bea query -o FILE` now leaves the previous
export byte-identical, as `USAGE.md` promises.

`text_answer` (`cli/src/bea_engine/query.py`) opened the destination for write
before executing the query, so the truncation happened first and any execution
failure left a 0-byte file behind. The existing comment already ordered the
open after the *ledger load* — so `-o` could not truncate the books — but not
after the *query*.

The shell now renders into the `StringIO` buffer it was already given, and the
destination is opened only once `_executed` has returned. The `_refuse_alias`
guard stays where it was, before the query: refusing to write over the ledger
being read is a refusal, and a refusal has to come before any work. Buffering
also removes the partial-file case the note flagged, since nothing reaches disk
until the whole render is done. When an export is written the envelope's `text`
is empty, which is what keeps the table from also printing to stdout — the same
split as before, where the shell wrote straight to the file.

Verified: the note's repro leaves `SENTINEL` intact at exit 2 (was 0 bytes);
same for `--format csv` and `--format beancount`; a successful query still
replaces the export and prints nothing to stdout; `-o` naming the ledger is
still refused with the ledger untouched. The `(no rows)` stderr notice and the
empty file it produces are unchanged — compared byte-for-byte against the old
code, since that is pre-existing behavior and not part of this fix.

Regression coverage is `cli/tests/test_query_export_survives_failure.py`.
Reverting the fix fails all three truncation cases; the three control tests
(`--json` preservation, success-replaces, alias refusal) pass either way by
design. `cd cli && make check-all` passes (1531 tests).
