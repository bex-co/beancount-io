# Overview Recent activity dates omit the year, so old entries read as this week

**Minor · 45–60m · dashboard.** A2: a newcomer's first ledger view must not present a nine-year-old transaction as recent activity.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright `--headless --isolated`), English/light, authenticated QA account on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. Read-only; no production mutation.

Open `/ledger/<owner>/example` and read the **Recent activity → Transactions** card, described as "Newest transactions matching the current dashboard filters". Fresh 1440×1000 and 390×1000 loads both render, in order: `Sep 1`, `Sep 1`, `Aug 31`, `Sep 8`, `Sep 7`, `Sep 6`, `Sep 4`, `Sep 4`. Read as written, the list looks unsorted and the last five look like the last week.

API control — `getLedgerJournal(query: {directiveTypes: ["Transaction"], offset: 0, limit: 8})` returns HTTP 200, `total` 1047, dates `2026-09-01, 2026-09-01, 2026-08-31, 2017-09-08, 2017-09-07, 2017-09-06, 2017-09-04, 2017-09-04`. The API order is correct and strictly descending; only the rendered labels are ambiguous. Expected: a reader can tell a 2017 row from a 2026 row. Actual: the year is dropped, so a 2017-09-08 entry is labelled `Sep 8` four days after 2026-09-08 and appears to be newer than the `Aug 31` row above it. No amount, ordering or filter defect is claimed.

Working control: the Journal page renders the same eight records as full `2026-09-01 … 2017-09-08` dates and is unambiguous. Statement exports also carry explicit period dates.

Root: `dashboard/src/features/reports/overview/components/recent-activity-card.tsx:37-44` — `formatActivityDate` builds `Intl.DateTimeFormat(language, { month: "short", day: "numeric" })` with no `year`. It has exactly two callers, both in this card: the desktop column at `:235` and the narrow-layout line at `:264`. This is the only date formatter in the dashboard that omits the year — `common/lib/format/format-datetime.ts:26-28` and `features/plaid/components/transaction-review-table.tsx:297-299` both include `year: "numeric"`, and `overview/components/net-worth-card.tsx` renders month + year.

Fix: make the activity label unambiguous across years while keeping the compact look. Include the year (or an explicit relative form) whenever the entry's year differs from the current year, and keep the short month/day form for same-year entries; keep the localized `language` argument, the existing invalid-date fallback (return the raw string), and the identical desktop and narrow renderings. Do not change ordering, the eight-row limit, the query, or any other formatter. Owning package: `dashboard` only — no API, schema or cross-package change.

Blast radius: the two call sites above; the shared Overview card is rendered from `overview/index.tsx`. No other consumer imports `formatActivityDate`.

Adjacent states: loading skeleton, `noRecentActivity` empty state, and `recentActivityError` are unchanged; a filtered period that yields only same-year rows must keep the current compact labels.

Dedupe: searched every queue including `done/` for recent-activity, `formatActivityDate`, and date-format terms. Completed `144` is the *language* of these labels (it added the `language` argument now present) and never addressed the missing year; completed `m22` covers relative timestamps and date calendars elsewhere; open `m31` owns Entry Context keyboard behavior in the dialog this card opens, not the row label. `git log -S formatActivityDate` shows no later year-related change on fetched main. Not a regression of shipped work; not deployment lag.

Unverified: other locales and languages, other ledgers, and the patched behavior. Only the Overview journey and the statement-export control were exercised in this pass.

Evidence (gitignored, local only): `dashboard/tmp/qa-20260912/recent-activity-year.json` (API + both viewports' rendered rows), `recent-activity-year-1440.png`, plus `income-statement-2017.md` / `.csv` as the passing export control.
