# A concurrent edit during `bea import --apply` is reported as "would leave the ledger invalid" with exit 1, not the documented conflict/exit 4

Severity: minor. **Estimate:** ~1h. **Owner:** cli. The conflict is detected
correctly and nothing is written — but it is announced as a data problem, so a
retrying script stops retrying and a person goes looking for invalid data that
does not exist.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, no login. Synthetic fixtures only; no credentials used.

## What is wrong

`cli/docs/USAGE.md:593` promises:

> An external edit detected before replacement produces exit **4** and is
> preserved.

and the exit table assigns `4` to `conflict` — "Conflict, or a write whose
outcome is unknown" — while `1` is `validation`, "Ledger or validation error".

When another writer touches the ledger while `bea import --apply` is running,
the safety behaviour is right (nothing is written, the ledger stays valid) but
the report is wrong on both counts:

```
Error: Import would leave the ledger invalid; nothing was written.
  The ledger changed during the operation: /…/fr.bean. Nothing was written; retry.
```

The headline says the *import data* is bad. The detail line, one level down,
says the opposite and the true remedy: retry. Under `--json` the envelope
agrees with the wrong headline:

```json
{"error": {"category": "validation", "exit_code": 1, …}}
```

Expected `"category": "conflict"`, `"exit_code": 4`, and a headline naming the
concurrent edit.

**It is also non-deterministic.** The identical command racing itself reports
the same situation two different ways, depending on which internal check
notices the concurrent edit first. Eight attempts, two identical
`import --apply` processes each time, split 4/4:

```
4×  exit=4  Error: The ledger changed during the operation: /…/imp.bean. …
4×  exit=1  Error: Import would leave the ledger invalid; nothing was written.
```

Same command, same race, same underlying `ConflictError` — so a retry wrapper
keyed on exit 4 works about half the time and fails the rest for no reason the
caller can see. That coin-flip is arguably worse than a uniformly wrong code.

## Repro (synthetic, no login)

Race a long-running `import --apply` against fast writers on the same ledger.
The import's extract/preview phase runs before its final validation, so a
concurrent `add` lands in between.

```sh
cat > fr.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Equity:Opening USD
2026-01-05 * "seed"
  Assets:Cash   10000.00 USD
  Equity:Opening
EOF
printf 'Date,Amount,Description\n2026-03-01,-7.00,IMPORTED ROW\n' > mix.csv

bea --file fr.bean import mix.csv --csv auto --account Assets:Cash --apply & IMP=$!
for i in 1 2 3 4 5 6; do
  bea --file fr.bean add transaction --date 2026-07-0$i --narration "x$i" \
    --posting "Expenses:Food 1.00 USD" --posting "Assets:Cash" >/dev/null 2>&1 &
done
wait $IMP; echo "import exit=$?"     # 1 — expected 4
```

Observed 2 of 3 human-mode attempts and 4 of 4 `--json` attempts (the
remaining attempt won the race and correctly exited 0, writing its row). The
ledger passes `bea check` in every case, and the import's row is absent — the
refusal itself is correct.

## Working controls

- **`add` hits the same conflict and reports it correctly — exit 4,
  `category: "conflict"`.** This is the decisive control: the defect is
  import-specific, not a weakness in the shared write/launch plumbing.

  `add` cannot be made to lose against another `add` — the lock at
  `$XDG_CACHE_HOME/bea/locks` serializes same-command writers properly (eight
  concurrent `add`s all landed; six further attempts to starve a victim never
  produced a conflict). But `format -i` is upstream's own formatter writing the
  file directly, so racing against *it* does produce the conflict:

  ```sh
  bea format fmt.bean -i &          # ~2s on a 240k-line ledger
  sleep 0.4
  bea --json --file fmt.bean add transaction --date 2026-12-01 --narration j1 \
      --posting "Expenses:Food 9.00 USD" --posting "Assets:Cash"
  # exit 4 — {"error": {"category": "conflict", "exit_code": 4, …}}
  ```

  Reproduced in 3 of 3 attempts (one victim per attempt). The other four adds
  landed each time, the ledger stayed valid, and no write was lost. So
  `ConflictError` travels intact from `write.py` through `answering`,
  `launch.py` and `errors.py` to the exit code — it is only `import` that
  discards it.

  `import` is exposed to the race in the first place because its
  extract/preview phase runs before the final validated write, leaving a window
  a concurrent writer can enter. (That window is inferred from the observed
  asymmetry, not read off a lock trace.)
- **The same guard reports correctly elsewhere.** `bea init` against an
  existing ledger exits **4** (`Already exists: … init never overwrites a
  ledger`), and `example -o` on an existing file exits **4**. So `conflict`/4
  does reach the surface on paths that raise it directly.

## Root cause (verified)

The engine raises the right error and the frontend can map it; the category is
dropped in between, inside the import command.

1. `cli/src/bea_engine/ledger/write.py:121` raises
   `ConflictError("The ledger changed during the operation: …")`.
   `ConflictError` carries `category = "conflict"` and
   `exit_code = EXIT_CONFLICT` (`cli/src/bea_engine/protocol.py:83`).
2. `cli/src/bea_engine/importing.py:306` catches **every** `EngineError` from
   `validate_append` and flattens it to a list of plain strings, discarding the
   class, its category and its exit code:

   ```python
   except EngineError as exc:
       validation_errors = exc.details or [str(exc)]
   ```

3. `cli/src/bea_engine/importing.py:379` re-raises the accumulated strings as a
   `LedgerError` — category `validation`, exit 1 — with the conflict text
   demoted to a `details` line:

   ```python
   if validation_errors:
       raise LedgerError(
           "Import would leave the ledger invalid; nothing was written.",
           details=validation_errors, result=preview,
       )
   ```

`protocol.answering` (`protocol.py:105`) would have serialized
`exc.category` faithfully had the `ConflictError` reached it, and
`cli/src/cli/errors.py:96` already maps `"conflict"` → `ConflictError`, so
nothing downstream needs changing. `cli/src/cli/engine/launch.py:289`
(`failure.get("category", "validation")`) is the default that makes the loss
invisible.

**Why it is a coin flip.** `import` can notice the concurrent edit at either of
two points, and only one of them is wrapped:

| Where the conflict is caught | Wrapped by `:306`? | Result |
| --- | --- | --- |
| `importing.py:303` `validate_append(...)` | **yes** | flattened → `validation` / exit 1 |
| `importing.py:386` `ledger_write.append(...)` | no | propagates intact → `conflict` / exit 4 |

Both raise the same `ConflictError` from `write.py:121`. Whichever runs into
the concurrent write first decides the exit code, which is exactly the observed
4/4 split. The unwrapped `:386` call is the behaviour to match.

## Fix

Let a `ConflictError` out of `importing.py:306` instead of flattening it —
re-raise it unchanged, so it reaches `answering` with its category intact and
behaves the way the unwrapped `:386` call already does. Keep the flattening for
genuine validation failures, which is what that handler is for.

Regression coverage should assert that a conflict raised by `validate_append`
surfaces as exit 4 with `"category": "conflict"`, that a conflict raised by
`append` still does, that the two paths now agree, and that an ordinary
invalid-import still exits 1 with the existing headline.

## Blast radius

- `bea import --apply` is the reachable case, and it is the *only* one: `add`
  through the same `ConflictError` reports exit 4 correctly (see controls), so
  the loss is confined to `importing.py:306`.
- The same broad `except EngineError` also swallows `AuthError` (exit 3 — a
  read-only destination) and `UsageError` (exit 2) from `validate_append`, so
  those categories are presumably flattened to `validation`/1 the same way. Not
  exercised: a read-only ledger fails earlier, at the writability check, before
  this handler is reached.
- `importing.py:205` and `:374` raise `ConflictError` directly and are
  unaffected — the `--duplicates review` path correctly exits 4, verified in an
  earlier sweep.
- Not a data-integrity defect: the conflict is detected, the write is refused,
  and the ledger remains valid and unmodified in every observed run. The cost
  is a misleading headline and a retry signal a script cannot act on — exactly
  what the `conflict` category exists to convey.

## Adjacent states

Exercised across this run: 8-way concurrent `add` (all landed); 12 concurrent
`add --into` split across two different includes of one root (all 12 landed,
ledger valid); a mixed race of 4 root `add`s + 3 `add --into` + 1
`import --apply` (all seven adds landed, the import correctly refused); `add`
to a 600k-line ledger (atomic, correctly placed, `check` clean); and `format`
idempotence at that scale.

**No integrity failure was found anywhere in this area**, which is worth
recording alongside the defect:

- 30 reads running continuously against 30 concurrent writes produced **0**
  read failures — the atomic replace never exposes a torn file.
- Two identical `import --apply` processes racing wrote the probe row
  **exactly once** in every one of 11 attempts; never zero, never twice.
- Every race left the ledger passing `bea check`, with no lost or duplicated
  entries.

The defect is confined to how the refusal is *reported*.

## Dedupe

Searched `.pm/**/*.md` including `done/` for "changed during the operation",
"conflict", "exit 4" and "retry-safe". The nearest item is
`w3/blocked/003` — "Bulk entry writes are not retry-safe after a false
timeout" — which is the hosted Fava/HTTP write path (timeouts, idempotency
across REST/GraphQL/MCP) and is blocked on an idempotency contract. Different
surface, different mechanism: this note is the local CLI import path, where the
conflict *is* detected and merely mislabelled. No open w3 item covers it
(`385`–`388` are the other open notes: import row numbering, import account
validation, managed-price auth, Ctrl-C at a prompt).

## Unverified

Whether `AuthError` and `UsageError` from `validate_append` are flattened the
same way by `importing.py:306` was reasoned from the handler's breadth, not
observed — both fail earlier on the paths tried here. The precise size of
import's unlocked window was not measured; only the asymmetry against `add` was
established.

(An earlier revision listed the `add` control itself as untestable. That is now
resolved — racing `add` against `format -i` produces the conflict, and `add`

---

**Resolved 2026-09-21** — a concurrent edit during `import --apply` now exits
**4** with `category: "conflict"` and a headline naming the real cause.

The note's diagnosis was exact. `importing.answer` caught every `EngineError`
from `validate_append` and flattened it to a list of strings, so a
`ConflictError` was re-raised as `LedgerError("Import would leave the ledger
invalid…")` at exit 1 with "retry" demoted to a details line. The catch is now
narrowed to `LedgerError` — which is what that handler is actually for —
letting conflict, auth and usage failures propagate with their categories
intact, exactly as the unwrapped `append` call already did.

That single change also closes the coin flip: both detection points now answer
alike, so a retry wrapper keyed on exit 4 works every time instead of about
half the time.

The note's "Unverified" item is now settled rather than left open: `AuthError`
and `UsageError` from `validate_append` **were** flattened the same way. The
injected-failure tests reach them (they cannot be reached through a real run,
which is why the note could only reason about them) and both fail against the
old code and pass against the new.

Verified live on the note's own race — one `import --apply` against six
concurrent `add`s, six attempts each way:

- before: 6/6 `exit=1 category=validation`
- after: 6/6 `exit=4 category=conflict`

Regression coverage is `cli/tests/test_import_conflict_category.py`. It injects
the failure at the engine boundary rather than racing processes, because a race
is not something a suite can assert on reliably; the live race above is the
observation behind it, and the module docstring says so. Controls: a genuine
`LedgerError` still flattens into the existing headline with its details, and a
clean import still writes its row. Reverting the fix fails 4 of the 6.
`cd cli && make check-all` passes (1637 tests).

Scope note: the narrowed catch also applies to preview runs (no `--apply`).
A concurrent edit there now surfaces as a conflict instead of being shown as a
validation note on a preview that was computed against a ledger which has since
changed — the preview would be stale, and "retry" is the honest answer. That
goes slightly beyond the note, which framed the defect around `--apply`; it is
the same mislabelling and the same fix, so it did not seem right to leave the
preview path reporting a conflict as a data problem.

Unmeasured, as in the note: the precise size of import's unlocked window. Only
the asymmetry against `add` was established, and the fix does not depend on the
window's size — it changes how the detected conflict is reported, not when it
is detected.
