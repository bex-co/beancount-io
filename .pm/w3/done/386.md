# `bea import` reports a syntactically invalid account as "not open" and hands back a `bea add open` remedy that cannot work

Severity: minor. **Estimate:** ~1h. **Owner:** cli. A typo in `--account`
blocks every row with the wrong diagnosis and a dead-end fix, where `bea add`
rejects the same name immediately with the right one.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, no login. Synthetic fixtures only; no credentials used.

## What is wrong

`bea import` never validates the account names it is given. A name the
Beancount loader could never accept — anything with a space, a lowercase root,
an illegal character — is simply "not in the set of open accounts", so every
row is `blocked` with:

```
Row 1: Account 'Bogus Account' is not open. Run: bea add open --account Bogus Account --date 2026-02-01 -c USD.
```

Both halves are wrong:

1. **The diagnosis.** The account is not *unopened*, it is *unopenable*. No
   `open` directive can ever make `Bogus Account` valid.
2. **The remedy.** Running it verbatim fails — and it is emitted unquoted, so a
   shell would parse it as `--account Bogus` plus a stray `Account` argument
   before it even got that far:

```sh
bea --file main.bean add open --account "Bogus Account" --date 2026-02-01 -c USD
# exit 2
# Error: Invalid account 'Bogus Account'. Account names use colon-separated segments,
# such as Assets:Checking. The root starts with an uppercase letter; …
```

So `import` sends the user to a command that `add` refuses, using `add`'s own
account vocabulary.

## Repro (synthetic, no login)

`main.bean` opens `Assets:Bank:Checking`, `Expenses:Food` and
`Expenses:Uncategorized`. `bank.csv` is any three-row export.

```sh
bea --file main.bean import bank.csv --csv auto --account "Bogus Account"
# exit 0
# csv → Bogus Account: 0 ready, 0 exact duplicates, 0 possible duplicates, 3 blocked
# Row 1: Account 'Bogus Account' is not open. Run: bea add open --account Bogus Account …
```

Three entry points reproduce it:

| Entry point | Result |
| --- | --- |
| `--account "Bogus Account"` | all rows `blocked`, "is not open" |
| `--default-account "Bogus Account"` | all rows `blocked`, "is not open" |
| `account = "Bogus Account"` in a `--rules` TOML | matching rows `blocked`, "is not open" |

## Working controls

**A valid-but-unopened account behaves correctly** — same message shape, and
the remedy actually resolves it:

```sh
bea --file main.bean import bank.csv --csv auto \
  --account Assets:Bank:Checking --default-account Expenses:NeverOpened
# Row 1: Account 'Expenses:NeverOpened' is not open. Run: bea add open --account Expenses:NeverOpened …

bea --file main.bean add open --account Expenses:NeverOpened --date 2026-02-01 -c USD
# Added 1 open …   → the next import reports "3 ready"
```

**A category *column* already gets this right**, which shows import can tell
the two cases apart where it chooses to look:

```sh
# Category column holds 'Bogus Account'
bea --file main.bean import cat.csv --csv date=Date,amount=Amount,narration=Description,category=Category \
  --account Assets:Bank:Checking
# 1 row(s) carry a category that is not an account name ('Bogus Account'); they post to
# Expenses:Uncategorized with flag '!'. Categorize them with --rules, or map a column of
# full account names with --csv category=Column.
# → 1 ready, nothing blocked
```

## Expected

`--account`, `--default-account`, and a `--rules` `account` value should be
validated as account *names* before the preview runs, and an invalid one should
fail fast with exit 2 and the same message `bea add` already produces. A name
that is well-formed but unopened keeps today's `blocked` + `bea add open`
behaviour, which works.

## Root cause (verified)

`cli/src/bea_engine/importing.py:473` computes the blocked set purely by
set-membership against the opened accounts:

```python
missing = sorted({posting.account for posting in entry.postings if posting.account not in open_currencies})
if missing:
    remedies = []
    for name in missing:
        currency = next(p.units.currency for p in entry.postings if p.account == name)
        remedies.append(f"bea add open --account {name} --date {entry.date.isoformat()} -c {currency}")
    …
    return f"{noun} {quoted} {verb} not open. Run: {'; '.join(remedies)}."   # :482
```

An invalid name is trivially absent from `open_currencies`, so it takes the
"not open" branch and gets a `bea add open` line built by string interpolation
at `:478` — unquoted, and unreachable for any name the loader rejects.

The validator that would catch it already exists:
`cli/src/bea_engine/ledger/text.py:74` `parse_account()`, which raises the
`Invalid account …` `UsageError` quoted above. Its only callers are in
`cli/src/bea_engine/ledger/adding.py` (`:99`, `:104`, `:108`, `:109`, `:114`,
`:138`, `:153`, `:195`, `:243`, `:472`) — the `add` command family. Nothing on
the import path calls it.

## Fix

Call `parse_account()` on `--account`, `--default-account`, and each `--rules`
`account` value at the point import resolves them, surfacing its `UsageError`
as the usual exit 2. Separately, quote the interpolated account in the
`bea add open` remedy at `importing.py:478` so the suggestion is copy-pasteable
in every case. Add regression coverage that an invalid name exits 2 with the
`Invalid account` text from all three entry points, and that a valid-unopened
name still produces today's `blocked` row and working remedy.

## Blast radius

- Three import entry points, listed above. The category-column path
  (`--csv category=…`) is already correct and must keep its graceful fallback.
- `parse_account()` is engine-side and NFC-normalizes before `is_valid`, so
  reusing it also gets import the Unicode-normalization behaviour `add`
  already has.
- No data-integrity impact: blocked rows refuse the write and the ledger is
  left byte-identical. The cost is a wrong diagnosis and a wasted fix attempt.
- The unquoted-remedy defect at `:478` is latent for well-formed names, since
  valid account names cannot contain spaces — it only surfaces together with
  the missing validation.

---

**Resolved 2026-09-21** — an unopenable account name is refused up front with
`add`'s own message, instead of blocking every row with the wrong diagnosis.

The root cause held: `_blocked_reason` computed the blocked set purely by
set-membership against the opened accounts, so an invalid name was trivially
absent and took the "is not open" branch. `parse_account()` — the validator the
whole `add` family already uses — was simply never called on the import path.

All three entry points the note lists now validate before the preview runs:

- `--account` and `--default-account` go through a new `_valid_account()` in
  `importing.py`, which surfaces `parse_account`'s `UsageError` prefixed with
  the option that named it, so the user knows where to fix it.
- A `--rules` `account` value is validated in `CsvRule.compile`, where the rule
  number is available and says which line to fix.

The unquoted-remedy defect is fixed too: `bea add open --account …` now passes
the name through `shlex.quote`. That is belt-and-braces once invalid names are
refused (valid account names hold no spaces), but a suggestion that only
sometimes pastes cleanly is worse than one that always does.

Verified: all three entry points exit 2 with `Invalid account 'Bogus Account'.
…` and no "is not open" or dead-end remedy. Controls hold — a valid-but-
unopened account still blocks with its working remedy (the test runs the
suggested `bea add open` and requires the next import to report "2 ready"), and
a bad value in a category *column* keeps its graceful fallback to
`Expenses:Uncategorized` with a note rather than becoming a hard error.

Reusing `parse_account` also gives import the NFC normalization `add` has, as
the note predicted.

Regression coverage is `cli/tests/test_import_rejects_invalid_accounts.py`,
parameterized over four invalid shapes (space, lowercase root, illegal
character, bare root-less name). Reverting the fix fails 10 of its 13 tests;
the other 3 are the controls. `cd cli && make check-all` passes (1613 tests).

Not done — the note's "Unverified" item: whether a Python (Beangulp) importer
returning an invalid account name takes the same branch. It still would, since
`_blocked_reason` is shared and only the CSV entry points are validated. That
path takes account names from importer code rather than from a user option, so
it is a different fix (validate extracted entries, not options) and wants its
own item rather than being folded in here.
