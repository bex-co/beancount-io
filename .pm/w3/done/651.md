# A blocked account may still clone and push over Git

**Severity:** major if it reproduces: a ban that leaves ledger access open. **Estimate:** 30–45 minutes, including tests. **Owner:** `backend-cluster/backend-v2`. **A1:** blocking an account must end every way it reaches its ledgers, not only dashboard sign-in.

## What the code shows (main, 2026-11-15; read, not yet reproduced)

- Dashboard sign-in refuses a blocked user. See `issuePasswordSession` and the two other `isBlocked` checks in `src/features/auth/service/auth-service.ts`.
- The Git HTTPS proxy (`src/features/gitea/api/git-proxy-handler.ts`) calls `verifyPasswordCredentials`, which never reads `isBlocked`. It then forwards with the user's generated Gitea credential.
- No `isBlocked` check appears under `src/features/gitea/`. That covers the SSH proxy's public-key path and the Gitea passthrough.
- No check appears in `ApiKeyService.verify` either. A blocked user's personal access tokens would therefore also work for Git once w3/m68 lands, unless the check is added there.
- Blocking only sets `users.is_blocked`. Nothing found in `src/features/admin/` disables the Gitea account.

## Fix

1. Reproduce with a synthetic local user: block it, then try HTTPS clone with email + password and SSH clone with its key.
2. If either succeeds, refuse blocked users at one shared point used by every Git credential path: email + password, Gitea passthrough, SSH key, and personal access token (once w3/m68 adds it). Check whether REST/GraphQL/MCP refuse a blocked user's API keys and OAuth tokens; if they do not, that is the same defect and is fixed at the same point.
3. If nothing reproduces, close this note with the evidence of where the refusal happens.

**Acceptance:** a blocked user is refused on Git over HTTPS and over SSH, with every credential type, and an unblocked user works again. Tests cover each path.

**Dedupe:** searched `.pm/**` for `isBlocked`, banned, and blocked user together with git. No match.

**Resolved 2026-11-15** — Reproduced by test rather than on a live stack: with the account blocked, every Git HTTPS credential (email + password, Gitea passthrough, personal access token), an SSH key, and an API key, OAuth token, or existing session on REST/GraphQL/MCP all still authenticated. One check, `accountMayAuthenticate` in `src/server/api/identity.ts`, now refuses a blocked account in the API-key resolver, `resolveIdentity` (OAuth and session), the Git HTTPS proxy, and `SshAuthenticator`; unblocking restores access. Tests: `identity.test.ts`, `api-key-identity.test.ts`, `git-proxy-credentials.test.ts` ("a blocked account"), `ssh-authenticator.test.ts`. Not covered: a Gitea-native token created directly in Gitea is checked by Gitea alone. Shipped in `369978266` (`backend-cluster/backend-v2`).
