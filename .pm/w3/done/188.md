# The merchant Recurring switch announces the opposite of its own state

**Severity:** minor. **Estimate:** 45–60 minutes. Package: mobile. A2 — a newcomer using VoiceOver (or reading the row) must be able to tell whether a merchant is currently marked recurring before flipping it.

Production https://beancount.io, September 12, 2026; local HEAD `84231f9c` with JS served from a local Metro dev server, native development build `io.beancount.ios` 1.20260906.47, iPhone 17e / iOS 26.5, English / System-light / default text size. Authenticated QA session, public read-only `open_ledger/crypto-example`. No ledger write; the recurring override is device-local and was **not** toggled.

## Repro

1. Open the drawer → Merchants on `open_ledger/crypto-example`. `Ethereum 2.0` appears in the `RECURRING` section and again in the full list carrying a `RECURRING` badge.
2. Open the `Ethereum 2.0` merchant. The header shows the cadence chip `Monthly`, confirming the app considers it recurring.
3. Read the toggle row: the visible title is **“Mark as not recurring”** and the switch is **on** (green).
4. Inspect the control directly: `automation_find_view {"testID":"merchant-recurring-toggle"}` returns `label: "Mark as not recurring"`, `value: "1"`, `is_enabled: true`.

## Expected / actual

Expected: a switch is labelled by the **setting** it controls, so an assistive-technology user hears “Recurring, on” for a recurring merchant. Actual: the switch is labelled by the **action** that flipping it performs, while its value reports the current state — so it announces “Mark as not recurring, on”, which reads as *“not recurring is on”*, the exact opposite of the truth. The helper line underneath (“Pin this merchant in Recurring…”) describes only the on-direction, so it contradicts the title whenever the title says “Mark as not recurring”.

## Root cause

`mobile/src/screens/merchant-detail-screen/merchant-detail-screen.tsx:440–442` derives the title from the state as an inverted action:

```
const toggleTitle = resolved.isRecurring
  ? t("merchantsMarkNotRecurring")   // "Mark as not recurring"
  : t("merchantsMarkRecurring");     // "Mark as recurring"
```

That same string is then used as the control's visible title (`:487`) **and** its `accessibilityLabel` (`:498`), while `value={resolved.isRecurring}` (`:500`) supplies the state. The code comment at `:494–497` is right that `Switch` reports its own checked state — which is precisely why the label must not also encode the pending action. `resolved.isRecurring` comes from `merchants-screen/selectors/resolve-recurring.ts:26–60` (manual override wins, else detection), so the value is a state, never an action.

## Fix

Label the control by the setting, not by the transition: one stable title (e.g. `Recurring`) with `value={resolved.isRecurring}`, so it renders and announces “Recurring — on/off”. Make the helper text direction-neutral (it currently only explains pinning) while keeping the existing “manual choices beat automatic detection and stay on this device” explanation. Do not fix this by inverting `value`, by dropping the `accessibilityLabel` (that regresses the unnamed-switch fix the comment describes), or by keeping the action wording and adding an `accessibilityState` that disagrees with the visible text. `merchantsMarkRecurring` / `merchantsMarkNotRecurring` exist in `src/translations/en.ts:66–67`; a new key must be added to the English base and may be left to fall through in the other 12 locales, per `mobile/CLAUDE.md`.

## The same screen already gets this right for a button

The Merchants list's sort control (`merchants-sort`) is an icon-only **button**, and an action label is correct there: inspected live, it reports `label: "Sort alphabetically"` while showing the `Aa` icon, and after a tap it reports `label: "Sort by transaction count"` with the `⇅` icon — icon and label both describe the next action, and the control has no on/off state to contradict. That is the pattern the recurring control borrowed; the difference is that a `Switch` also publishes `value`, so an action label and a state value end up asserting opposite things. Use the sort button as the precedent for buttons and the setting-name rule for the switch — the fix is not to make the app consistent in one direction.

## Blast radius

Only the merchant detail screen renders this switch (`merchant-recurring-toggle` is defined once). The merchants list conveys the same state as a section plus a `RECURRING` badge (`merchants-screen/merchant-row.tsx:169,184`) and has no toggle, so it is unaffected — but the badge is the working control that proves the intended reading. The toggle writes a device-local override only; no API, ledger, or cross-surface parity is involved. `src/__tests__/accessibility-labels.test.ts` guards *missing* labels, not contradictory ones, so it stays green today.

## Adjacent states

Cover both directions: a detected-recurring merchant (source `detection`), a manually pinned one (`override: "recurring"`), a manually unpinned one (`override: "notRecurring"`), and a non-recurring merchant with no detection — the last renders with no cadence chip and the switch off, where the current action-wording happens to read correctly, which is why the defect is easy to miss.

## Correction from w4/015 (2026-09-14)

The "same screen already gets this right for a button" section above misreads the Merchants sort button. Its label and icon observations are accurate, but both described the sort already applied, not the next action. A count-ordered list carried "Sort by transaction count" and the `⇅` icon, and tapping the button sorted alphabetically; `w4/015` checked the list order against the label in both states. `w4/015` fixed the button: its accessible name now names the order a tap switches to, while the icon still shows the applied order. Use the fixed button as the precedent for icon-only buttons. This item's own conclusion is unchanged: a `Switch` is labelled by the setting it controls, and `value` carries the state.
