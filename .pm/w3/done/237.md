# `bea import --id-key id` disables bank-ID dedupe because CSV writes `bank_id`, not `id`

**Severity:** major. **Estimate:** 30–45 minutes. **Owner:** cli. **A2/A1:** an
agent that maps a bank ID column with `--csv …,id=ID` and passes
`--id-key id` (matching the CSV field name) silently falls back to content
hashes; reused bank IDs with different amounts are imported twice instead of
conflicting.

Found 2026-09-15 by continuous CLI QA against `main`, HEAD `09ea4d6b`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only (`Expenses:Uncategorized` opened so `--apply` can succeed).

## Repro

```sh
printf 'Date,Description,Amount,ID\n2024-03-10,Cafe,-4.50,id1\n' > a.csv
printf 'Date,Description,Amount,ID\n2024-03-11,Other,-9.99,id1\n' > b.csv

bea --no-input --file main.bean import a.csv \
  --csv date=Date,amount=Amount,narration=Description,id=ID \
  --account Assets:Bank:Checking --id-key id --apply
# writes bank_id: "id1" with import-id: "csv:sha256:…" (not bank:id1)

bea --no-input --file main.bean import b.csv \
  --csv date=Date,amount=Amount,narration=Description,id=ID \
  --account Assets:Bank:Checking --id-key id --apply
echo exit=$?
# exit 0 — WRITES a second txn with the same bank_id: "id1"
```

Working controls:

```sh
# default id keys (omit --id-key): second file is a conflict, exit 4
bea … import a.csv --csv …,id=ID --account … --apply
bea … import b.csv --csv …,id=ID --account … --apply
# → status conflict: "Stable ID matches an entry with different transaction data."

# explicit metadata key name also works:
bea … --id-key bank_id …   # conflict as documented
```

## Expected

Per `cli/docs/IMPORTING.md`: an `id` column becomes `bank_id` metadata and
stable bank IDs deduplicate; reused IDs with different dates/amounts are
conflicts. `--id-key` used with CSV `id=` must not turn that off. Either:

1. treat CSV field name `id` as alias for metadata key `bank_id`, or
2. refuse `--id-key id` for `--csv` with a usage error naming `bank_id`, or
3. keep default `bank_id` in the key list when the CSV mapping includes `id`.

## Actual

`--id-key` **replaces** `_DEFAULT_ID_KEYS` (`bank_id`, `fitid`, …). CSV always
writes meta key `bank_id`. Looking up key `id` finds nothing, so
`_native_import_id` returns None and the row gets a content-hash `import-id`.
Same `bank_id` across files never conflicts.

## Root cause

```text
cli/src/bea_engine/csv_mapper.py — id column → meta["bank_id"]
cli/src/bea_engine/importing.py:154  keys = id_keys or _DEFAULT_ID_KEYS
cli/src/bea_engine/importing.py:369  _native_import_id(meta, keys)  # looks for meta[key]
# --id-key id → keys=["id"] → miss bank_id → csv:sha256 fallback
```

## Fix

When the CSV mapping includes `id`, ensure `bank_id` remains among the
effective id keys (or map `--id-key id` → `bank_id`). Regression: the two-file
repro with `--id-key id` must conflict/exit 4 like the default-key control;
`--id-key bank_id` and omit-`--id-key` stay green; a true custom meta key still
replaces the defaults.

**Resolved 2026-09-16** — `--id-key id` aliases to metadata key `bank_id` so CSV `id=` dedupe stays on; reused IDs with different data conflict (exit 4). Covered by `cli/tests/test_id_key_id_alias.py`. Shipped with this board close.
