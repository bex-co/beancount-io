# Terminal escape sequences from an imported CSV reach the terminal raw, can falsify the import preview, and are persisted into the ledger

Severity: **major**. **Estimate:** ~1h. **Owner:** cli. Untrusted CSV text is
rendered to the terminal without sanitization, so a crafted description can
make the import preview — the review surface `--apply` is gated on — display
something other than what will be written. The sequences are then written into
the user's ledger and re-emitted on every later read.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5`, `uv run bea` 0.3.0,
Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` / `XDG_CACHE_HOME`, no login.
Synthetic fixtures only; no credentials used. Terminal behaviour verified by
driving a real PTY.

## What is wrong

`bea` collapses CR/LF in string fields — `USAGE.md:558` states the intent:

> Payees, narrations, string metadata, and the string fields of `note`,
> `event`, and `custom` are written on one line: runs of CR/LF line breaks
> become spaces … so a pasted multi-line value can never write a directive that
> breaks the file.

That protection stops at `\r\n`. `single_line()` is
`re.sub(r"[\r\n]+", " ", text)` in both copies
(`cli/src/cli/utils.py:16`, `cli/src/bea_engine/ledger/text.py:14`) — every
other control sequence passes through untouched, including `ESC`.

## The chain (each step verified)

1. **An untrusted bank CSV carries escapes.** `import` reads external files;
   this is the untrusted input.
2. **The preview renders them raw to the terminal.** Under a PTY, the emitted
   bytes contain the sequences verbatim — twice, once in the table and once in
   the diff.
3. **A crafted description can falsify the preview.** Cursor-up + erase-line
   inside a cell overwrites the row printed above it, so what the user reviews
   is not what the file says.
4. **`--apply` persists the escapes into the ledger**, byte for byte.
5. **`bea check` passes** — the ledger is considered valid.
6. **Every later `bea list` re-emits them** to the terminal.

## Repro (synthetic, no login)

**Raw passthrough, on a real TTY:**

```sh
python3 -c "open('evil.csv','w').write('Date,Amount,Description\n2026-02-01,-1.00,\x1b]0;INJECTED\x07\x1b[31mDANGER\x1b[0m\n')"
bea --file imp.bean import evil.csv --csv auto --account Assets:Cash
```

PTY capture of what `bea` wrote to the terminal:

```
raw CSI: [b'\x1b[31m', b'\x1b[0m', b'\x1b[31m', b'\x1b[0m']
raw OSC: [b'\x1b]0;INJECTED\x07', b'\x1b]0;INJECTED\x07']
```

**The preview lying — the part that matters.** Row 2 uses `\x1b[1A` (cursor
up) and `\x1b[2K` (erase line):

```sh
python3 -c "open('lie.csv','w').write(
 'Date,Amount,Description\n'
 '2026-02-01,-1.00,HARMLESS SMALL CHARGE\n'
 '2026-02-02,-9999.00,\x1b[1A\x1b[2K(row hidden)\n')"
bea --file lie.bean import lie.csv --csv auto --account Assets:Cash
```

The bytes `bea` emits for that row:

```
2    new     2026-02-02  \x1b[1A\x1b[2K(row hidden)   -9999.00 USD   hash  unmatched
+2026-02-02 ! "\x1b[1A\x1b[2K(row hidden)"
+  Assets:Cash             -9999.00 USD
```

On any terminal those two sequences execute — cursor-up and erase-line are
universally supported, so this needs no unusual terminal feature. The
`-9999.00` row erases the line above it as it draws.

**Persistence:**

```sh
bea --file imp.bean import evil.csv --csv auto --account Assets:Cash --apply   # exit 0
python3 -c "import re; d=open('imp.bean','rb').read(); print(re.findall(rb'\x1b\][^\x07]*\x07', d))"
# [b'\x1b]0;INJECTED\x07']
```

The ledger now holds `2026-02-01 ! "\x1b]0;INJECTED\x07\x1b[31mDANGER\x1b[0m"`
and `bea check` exits 0.

## A wrinkle worth knowing when reproducing

Redirecting stdout **hides half of it**. Click's `echo` strips CSI sequences
when the stream is not a TTY, so `bea list … > out.txt` shows the colour codes
gone while the OSC sequence survives. On a real terminal **nothing is
stripped** and both get through. Any test for this must use a PTY; a piped
capture will under-report the problem.

That stripping also mildly corrupts alignment in the piped case — the column
width is computed on the unstripped string, so the cell pads short. Related to
`w3/391` (same `output.table` width computation), but a different trigger.

## Expected

Escape and other C0/C1 control characters should not survive into terminal
output or into the ledger. Treat them the way CR/LF is already treated in these
fields, since `USAGE.md:558` already asserts that control characters in string
fields are `bea`'s problem to neutralise.

## Fix

Widen the sanitizer both copies of `single_line()` share: in addition to
`[\r\n]+`, strip or replace `ESC` and the remaining C0 range (and C1
`\x80-\x9f`). Apply it on both sides of the boundary — the display path
(`cli/src/cli/utils.py:16`, used by `output.table`) so nothing reaches a
terminal raw, and the write path (`cli/src/bea_engine/ledger/text.py:14`) so
nothing is persisted. Escaping to a visible form (`\x1b`) is preferable to
silent deletion, so a user can see that the source contained something odd.

Note the two copies are deliberately not shared (each file says the other side
cannot import it), so both must be changed and a test should pin that they
agree.

Regression coverage: a CSV description containing `\x1b[1A\x1b[2K`,
`\x1b]0;x\x07` and a C1 byte must (a) produce preview bytes free of raw
control sequences under a PTY, and (b) after `--apply`, leave a ledger whose
bytes contain no `\x1b`. Assert on the emitted bytes, not on rendered text.

## Blast radius

- **`bea import` preview and `--apply`** — the untrusted-input path, and the
  one where a falsified preview has consequences.
- **`bea list <type>`** — re-emits whatever the ledger holds, so the injection
  is durable once applied.
- **`bea add`** with a crafted `--payee` / `--narration` / `--comment`; lower
  concern, since that text is the user's own.
- Anything rendering through `output.table()`
  (`list.py:232`/`:236`/`:385`, `import_.py:670`, `report.py:231`/`:276`/`:331`,
  `price.py:63`) will pass cell contents through unchanged.
- `--json` is not affected in the same way: the envelope JSON-escapes control
  characters, so a JSON consumer sees `\u001b` rather than a live sequence.
  This is one more reason the defect is easy to miss from automated testing.
- Scope limits worth stating: no code execution was demonstrated, and no
  remote vector exists — the user must choose to import the file. The
  realistic harm is review subversion plus durable terminal noise.

## Adjacent states

Exercised: CSI colour, OSC title-set, cursor-up/erase-line, and a literal bell;
piped vs PTY output; preview vs `--apply`; ledger re-read after apply; and
`bea check` on the resulting ledger. Precedent exists elsewhere in the codebase
for rejecting control characters — `w3/done/271` has `BEA_TOKEN` refused for
containing them — so this is a gap in coverage, not an unconsidered area.

## Dedupe

Searched `.pm/**/*.md` including `done/` for escape/ANSI/control-character and
`\x1b` terms. Closest are `w3/done/271` and `w1/done/005`, both about control
characters and whitespace in **`BEA_TOKEN`** (credential validation), not about
ledger or CSV text reaching the terminal; `w3/done/170` is a web redirect
guard. Nothing covers terminal escape handling in rendered output or in written
ledger text. Related but distinct: `w3/391` (open) is display-width padding in
the same `output.table`, a rendering-geometry bug with no untrusted-input or
persistence angle. No other open w3 item covers it (`385`–`391`).

## Unverified

Whether any terminal in common use still answers an OSC title *query* (the
classic path from title-set to input injection) was not tested and is not
claimed — modern terminals generally disable it. No attempt was made to achieve
code execution. Windows console behaviour was not exercised. Whether the
hosted/dashboard surfaces render the same persisted bytes unsafely is out of
scope here and worth a separate look, since step 4 means the escapes now live
in the ledger itself.

---

**Resolved 2026-09-21** — control characters from untrusted text no longer
reach the terminal or the ledger.

Both copies of `single_line()` now escape the C0 range (beyond CR/LF, which
still collapse to a space), `DEL`, and C1 to a visible `\xNN`. Escaping rather
than deleting was the note's preference and is what keeps the oddity visible:
the text came from somewhere, and silently dropping bytes would hide that.

Every step of the note's chain is closed, verified against its own fixtures
under a real PTY:

- preview emits no raw CSI or OSC (was four CSI and two OSC sequences),
- `--apply` leaves no `\x1b` byte in the ledger,
- a later `bea list` of the applied ledger emits nothing executable,
- `bea add --narration` with the same payload is sanitized too.

One deliberate widening beyond the literal report: **tab is escaped as well**.
The note said "the remaining C0 range", which includes it, and a tab is layout
control in exactly the sense this function exists to neutralise — it shifts a
table cell to the next tab stop as surely as a cursor sequence would. The old
docstring promised "preserving other whitespace"; that promise now means
spaces, and both docstrings say so. Nothing in the suite depended on tabs
surviving (1694 tests pass).

`cli/docs/USAGE.md` is updated, since its one-line-fields paragraph was the
stated contract this extends.

Regression coverage is `cli/tests/test_control_character_sanitization.py`:
a parameterized sanitizer table run against **both** copies, an explicit
agreement test between them (neither can import the other, so nothing else
keeps them in step, as the note asked), and the four end-to-end steps asserting
on emitted bytes under a PTY. Reverting the fix fails 19 of its 37 tests.
`--json` is pinned as the control it always was.

Out of scope and unchanged, as the note frames them: no code execution was
attempted or claimed, and there is no remote vector — the user chooses to
import the file. The realistic harm addressed here is review subversion plus
durable terminal noise.

Carried forward, not done here:

- The note's closing question — whether the hosted/dashboard surfaces render
  the same persisted bytes unsafely. Newly written ledgers no longer contain
  escapes, but ledgers already written before this fix still do, and those
  surfaces are outside `cli/`. Worth its own item against the owning package.
- Windows console behaviour was not exercised.
- The piped-output alignment nit the note mentions (click strips CSI from a
  non-TTY stream, so the width was computed on the unstripped string) is moot
  now that no CSI survives sanitization.
