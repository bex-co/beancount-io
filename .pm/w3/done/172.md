# Password reset calls a validation outage an expired token

**Minor · dashboard · 40–55m.** A2/A3: account recovery should distinguish an unavailable validation service from a rejected reset link.

Controlled live-client reproduction, September11,2026: in a fresh signed-out headless Chrome152.0.7977.83 context open `/auth/reset-password?lang=en&token=qa-controlled-no-real-token`. Intercept only ValidateEmailToken with HTTP503 and a SERVICE_UNAVAILABLE GraphQL error. After loading settles, the page says “Token Expired”, “The password reset token is expired or invalid”, and “This password reset token is expired. Please request a new one.” There are no buttons and only Back to Sign in. Repeat at1440×1000 and390×844 gives the same false conclusion. Change the browser-local fixture to200 with data.validateEmailToken.isValid=true and reload: the two password fields appear, with empty-form submit disabled.

This is explicitly a simulated dependency failure and simulated valid-token control in the production client, not an observed production outage or a real reset token. Separate unmodified controls with no token and deliberately invalid `qa-invalid-no-real-token` correctly show the invalid/expired state; the latter's actual ValidateEmailToken request returns200. No email was requested, credential entered, or reset mutation sent.
