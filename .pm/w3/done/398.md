# Stored and interactive queries bypass table resolution and date-window validation

**Major · 45–60m · cli · A1.** An agent moving a working query into a stored
`query` directive gets a different answer: three accounts become four postings.
The interactive shell has the same failure. Both paths bypass the shared
pre-execution handling that direct queries use.

Found 2026-09-21 at HEAD `8d0e28d9` using checkout `bea 0.3.0`, Python 3.13.0,
macOS 26.5.1 arm64.
Executable: `cli/.venv/bin/bea`; synthetic fixtures, isolated configuration and
cache, no credentials. Two pristine fixtures and separate real processes gave
the same results. Captures record exact HEAD and concurrent unrelated changes;
the query implementation is unchanged from `ada8bb97`.

## Reproduce

Save this as an absolute-path `main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Equity:Opening USD
2026-01-01 open Expenses:Food USD
2026-01-01 * "Opening"
  Assets:Cash  100 USD
  Equity:Opening
2026-01-02 * "Lunch"
  Assets:Cash  -10 USD
  Expenses:Food
2026-01-03 balance Assets:Cash 90 USD
2026-01-10 query "accounts" "SELECT count(*) AS total FROM accounts"
2026-01-10 query "empty" "SELECT date, narration FROM OPEN ON 2026-01-02 CLOSE ON 2026-01-02 WHERE narration = 'Lunch'"
```

`bea --json --file /absolute/main.bean check` succeeds. Then:

```sh
bea --json --file /absolute/main.bean query 'SELECT count(*) AS total FROM accounts'
# exit 0; data.rows = [[3]]; empty stderr
bea --json --file /absolute/main.bean query '.run accounts'
# exit 0; data.text is a table containing 4; empty stderr
bea --json --file /absolute/main.bean query '.run empty'
# exit 0; data.text = ""; empty stderr
bea --json --file /absolute/main.bean query \
  "SELECT date, narration FROM OPEN ON 2026-01-02 CLOSE ON 2026-01-02 WHERE narration = 'Lunch'"
# exit 2; usage error on stderr explains the exclusive end and suggests Jan 3
```

In a real terminal, run `bea --file /absolute/main.bean query`, enter
`.set narrow false`, then:

```sql
SELECT count(*) AS total FROM accounts
SELECT count(*) AS total FROM "accounts"
SELECT * FROM balances
SELECT * FROM "balances"
.run empty
.exit
```

The counts are **4** then **3**. Unquoted `balances` reports a syntax error;
quoted `"balances"` returns the real 90 USD assertion. `.run empty` reports
`(no rows)` rather than the documented invalid-window diagnostic. Entering
the empty-window SELECT directly in the shell behaves the same way. Changing
its CLOSE bound to `2026-01-03` returns the two Lunch postings in both direct
and interactive modes. The PTY sessions exit normally; every ledger hash is
unchanged.

Expected: the same BQL text resolves to the same relation and follows bea's
documented window validation in every supported entry path. Keep upstream's
exclusive CLOSE semantics; refuse the zero-day request with the existing hint,
while keeping an interactive session usable after the refusal.

## Cause and fix scope

`cli/src/bea_engine/query.py:445` `_executed` performs reserved-table handling
and `_refuse_empty_window`, but callers at lines 77 and 131 only wrap the outer
one-shot request. For `.run accounts`, that request is the dot command, not
the stored SQL. `PreciseShell.do_run` at line 294 calls inherited `execute`
directly. Interactive `onecmd` at line 323 also reaches that inherited method
without `_executed`. Installed `beanquery/shell.py:394` `BQLShell.execute`
parses and dispatches with no bea preparation; unquoted `accounts` therefore
binds to postings and `balances` is a keyword parse error.

Apply the shared preparation/validation at the boundary that receives actual
BQL, covering direct text/JSON, interactive SQL and named/wildcard stored
queries. Preserve `default_close_date`, shell utilities, and quoted tables;
avoid recursion or double error wrapping. Validate the actual parsed window
after stored-query defaults as appropriate. Keep literals intact. CLI-only;
no API surface changes are needed.

Caller search found both `_executed` callers and the `do_run` named/wildcard
dispatches. Named stored queries and interactive SQL are reproduced here;
wildcard and default-date variants remain unverified. Other platforms and
native `--source` delegation are not covered by this finding.

---

**Resolved 2026-09-21** — the same BQL text now resolves to the same relation
and gets the same window validation whichever path submits it.

The preparation moved to `PreciseShell.execute`. That is the one boundary every
BQL path arrives at — dot commands dispatch to `do_*` instead — so direct text,
interactive SQL and named stored queries all get reserved-table quoting and the
empty-window refusal from one place. `_executed` keeps its outer wrapping
unchanged, which the JSON path still needs because it never builds a shell;
double preparation is harmless because the quoting pattern skips names already
quoted and the window check only validates.

Verified against the note's fixture:

- [x] `.run accounts` now counts **3** accounts, matching the direct query
      (was 4 postings). Interactively, unquoted and quoted `FROM accounts`
      both give 3, and `SELECT * FROM balances` returns the real 90 USD
      assertion instead of a syntax error.
- [x] `.run empty` exits **2** with the same usage message and the
      `CLOSE ON 2026-01-03` hint the direct form gives, in both the human and
      JSON envelopes.
- [x] Upstream's exclusive CLOSE semantics are untouched: moving the bound to
      2026-01-03 still returns the two Lunch postings.
- [x] An interactive session stays usable after the refusal — it prints the

      just before this, renders `EngineError` at the prompt instead of a
      traceback; the two fixes compose exactly as the note anticipated when it
      said to coordinate at the shared shell boundary.
- [x] Dot commands, shell utilities and string literals are unaffected, pinned
      by tests (`.tables` still answers, and a `'Lunch'` literal is not
      rewritten). `cd cli && make check-all` passes (1780 tests).

Coverage is `cli/tests/test_query_dispatch_preparation.py`, mixing one-shot
JSON with real PTY sessions. Reverting only the `execute` override — leaving
w3/397's handler in place — fails 5 of its 7 tests.

Unverified, as the note says: wildcard `.run` and `default_close_date`
variants, other platforms, and native `--source` delegation. The
`default_close_date` keyword is passed straight through to upstream and is not
touched by the preparation.
