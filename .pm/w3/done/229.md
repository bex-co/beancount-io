# Single-letter `--meta` keys fail with the posting-blame "Invalid transaction options" message

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** cli. **A1:** an
agent that uses short metadata keys (`n`, `id`-style single letters are invalid
in Beancount) is told to fix postings; two-letter keys work.

Found 2026-09-15 by continuous CLI QA against `main`, HEAD `07547c5e`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only.

## Repro

```sh
bea --json --file main.bean add transaction --date 2024-03-01 --narration short \
  --posting 'Expenses:Food:Groceries 1 USD' --posting 'Assets:Bank:Checking' \
  --meta 'n:3'
# exit 2
# {"error":{"category":"usage",
#   "message":"Invalid transaction options; use postings such as 'Assets:Checking -30 USD'. Nothing was written.",
#   "details":["Transaction options: Invalid token: 'n:'"]}}
```

Working control — same value, two-letter key:

```sh
bea --json --file main.bean add transaction --date 2024-03-01 --narration ok \
  --posting 'Expenses:Food:Groceries 1 USD' --posting 'Assets:Bank:Checking' \
  --meta 'aa:3'
# exit 0 — writes `aa: 3`
```

Upstream Beancount rejects single-character metadata keys (`Invalid token: 'n:'`
from `parser.parse_string`). The CLI's `_parse_metadata` fallback accepts the
key as a raw string, then the full transaction re-parse fails and mis-labels
the failure as posting/options guidance (same family as w3/223 for tags/links).

## Expected

Reject single-letter (and other Beancount-illegal) metadata keys at `--meta`
parsing with a usage error that names the key and the Beancount rule, without
mentioning postings. Keep two-letter keys and USAGE examples (`rate`,
`reviewed`, …) working.

## Actual

Misleading posting-oriented usage error; nothing written (safe) but the agent
edits the wrong flags.

## Root cause

```text
cli/src/bea_engine/ledger/adding.py:366-391  _parse_metadata fallback to raw
cli/src/bea_engine/ledger/adding.py:308-322  full parse_string; errors →
  "Invalid transaction options; use postings…"
```

## Fix

1. After Beancount's meta parse fails for a bare value, do not silently store
   raw text when the error is `Invalid token: '<key>:'` / illegal key shape —
   raise UsageError naming `--meta` and the key.
2. Optionally validate key length ≥ 2 to match the lexer before parsing.
3. Regression for `--meta n:3` (clear meta error) and `--meta aa:3` (success).
4. Same posting-blame string as w3/223 — fix can share the location classifier
   improvement, but this note is specifically about `--meta` keys.

---

**Resolved 2026-09-16** — single-letter --meta keys are rejected with a --meta-focused usage error before the transaction re-parse. Covered by cli/tests/test_meta_key_feedback.py. Shipped with this board close.
