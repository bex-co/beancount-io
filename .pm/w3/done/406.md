# CSV cell errors report the wrong physical line after quoted multiline fields

**Minor · 40–55m · cli · A1/A2.** Valid quoted multiline cells make subsequent
cell errors point at the wrong file line. The data-row ordinal remains correct,
but the documented hand-editing locator can point inside an earlier record.

Found 2026-09-21 at HEAD `98359325`, checkout `bea 0.3.0`, Python 3.13.0,
macOS 26.5.1 arm64. Repeated bad-date and bad-amount cases on two pristine
synthetic ledgers, with separate single-line controls. No authentication used.

## Reproduce

Create `/absolute/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

Create `/absolute/bank.csv` with these exact five physical lines:

```csv
Date,Amount,Description
2026-01-02,-5,"Coffee
and
food"
2026-13-02,-7,Dinner
```

```sh
bea --json --file /absolute/main.bean import /absolute/bank.csv \
  --csv date=Date,amount=Amount,narration=Description \
  --date-format %Y-%m-%d --account Assets:Cash \
  --default-account Expenses:Food --apply
```

Actual: exit **2**, empty stdout, JSON usage error on stderr:
`Row 2 (line 3): cannot parse date '2026-13-02' in column 'Date' with format '%Y-%m-%d'.`
Expected: **Row 2 (line 5)**, matching the physical line documented in
`cli/docs/IMPORTING.md:95`. Line 3 contains `and`, not the invalid date.

Changing the last record to `2026-01-03,bad,Dinner` produces the same wrong
`Row 2 (line 3)` for its amount error. Both failures reproduce twice; source
and ledger hashes remain unchanged. Replacing the first description with
single-line `Coffee and food` makes the bad amount occur at physical line 3,
and that control correctly reports `Row 2 (line 3)` in both repetitions.

## Cause and bounded fix

`cli/src/bea_engine/csv_mapper.py:519` `open_records` uses `csv.reader` but
discards its physical line tracking when yielding dictionaries. In
`CsvImporter.extract`, the pre-pass assigns `index + 2` as the physical line,
counting logical CSV records rather than lines consumed. `_at` passes that
incorrect locator to date, amount, debit/credit, currency and category cell
diagnostics. `new_metadata(filepath, line)` also receives it; that metadata
impact is source-traced, not independently verified through CLI output.

Retain each record's actual starting physical line while parsing and carry it
separately from the nonblank data-row ordinal. Preserve blank-row skipping and
the preview's existing row vocabulary. Cover multiline cells followed by bad
dates/amounts, including blank records in between, and retain single-line
controls. `open_records` also serves header discovery and date inference;
check those callers when changing its record representation. CLI-only;
no new dependencies or API changes are needed.

---

**Resolved 2026-09-22** — a cell diagnostic names the line the record actually
starts on, even after quoted multiline cells.

This is the case w3/385 left unverified, as the note says. That fix separated
the data-row ordinal from the physical line, but derived the line from the
record's *position* (`index + 2`) — which is only the file line while one
record is one line. A quoted cell containing newlines breaks that assumption
and every later error pointed inside an earlier record.

`open_records` now yields each row with its starting line, taken from the
reader: `csv.reader.line_num` counts lines consumed, so a record starts one
past wherever the reader stood before it. `CsvImporter.extract` carries that
through instead of computing one, and `infer_date_format` ignores it.

The surplus-field refusal added by w3/405 also moved onto this line, so it
names a multiline record's first line rather than its last — the two changes
touch the same reader and are consistent, which the note asked for.

Verified on the note's fixture and beyond it: bad date and bad amount after a
three-line quoted cell both report `Row 2 (line 5)` (was line 3, which holds
`and`); a skipped blank row after a multiline record gives `Row 2 (line 6)`,
advancing the line but not the ordinal; two multiline records compound
correctly to `Row 3 (line 6)`. The single-line control and the first data
record are unchanged, and a multiline description still imports cleanly.

w3/385's row vocabulary is untouched — only the parenthesised line was wrong —
and a test pins that the blank row still does not consume an ordinal.

Regression coverage is `cli/tests/test_csv_multiline_physical_lines.py`.
Reverting the fix fails its four multiline cases while both controls pass
either way. `cd cli && make check-all` passes (1907 tests).

The note flagged `new_metadata(filepath, line)` as source-traced only: it takes
the same corrected value, so entry metadata now records the record's real
starting line too. I did not add a separate assertion for the rendered
metadata, so that remains inferred rather than observed.

Unverified, as in the note: multiline *headers*, other delimiters and
encodings, and other platforms. The frontend's `cli/src/cli/csv_mapper.py`
twin keeps the old shape deliberately — it is used only for header discovery
and inference, and emits no cell diagnostics.
