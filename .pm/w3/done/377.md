# `csv:sha256` import-ids split across Unicode normalizations (re-import duplicates)

**Severity:** minor. **Estimate:** 60–90 minutes (spec + dual-hash migration). **Owner:** cli. **A2:** a
bank row whose description arrives NFD in one export and NFC in the next gets
two different `import-id` values, so the second import posts a duplicate
instead of exact-matching the first.

Found 2026-09-17 during the w1/m26/t006 skill review against `main`, HEAD
`0b5fa215`, `uv run bea` 0.2.0, Darwin arm64, isolated config/cache. Synthetic
fixtures only.

## Repro

```sh
python3 -c "
import unicodedata
nfd = unicodedata.normalize('NFD', 'Café X')
nfc = unicodedata.normalize('NFC', 'Café X')
open('nfd.csv','w').write('Date,Payee,Amount\n2026-08-10,' + nfd + ',-28.40\n')
open('nfc.csv','w').write('Date,Payee,Amount\n2026-08-10,' + nfc + ',-28.40\n')
"
printf '[[rule]]\nmatch = "caf"\naccount = "Expenses:Food"\n' > rules.toml
bea --file main.bean import nfd.csv --csv date=Date,amount=Amount,payee=Payee --account Assets:Checking --rules rules.toml
# import-id: "csv:sha256:fafae216cb2748c5"
bea --file main.bean import nfc.csv --csv date=Date,amount=Amount,payee=Payee --account Assets:Checking --rules rules.toml
# import-id: "csv:sha256:0d2aa9afca7ff6ee"  <- same logical row, different id
```

## Cause

`bea_engine/importing.py::_hash_import_id` uppercases and hashes the raw row
description without NFC-normalizing it first, and
`skills/.claude/skills/beancount-import/references/dedup.md` specifies the
`csv:sha256` form the same way. w1/m26/t004 normalized every other comparison
surface; the hash was left out deliberately: changing it alters ids already
written to ledgers, so the fix needs a spec update plus a migration (dual-hash
lookup or a re-hash pass), not a one-line normalize.

## Fix sketch

1. NFC-normalize the description (and account) before hashing in
   `_hash_import_id`, and the same inputs in `_fingerprint`/`_candidate_key`.
2. Update the `dedup.md` hash normalization spec to match.
3. Migrate existing ids: look up both the legacy and the normalized hash on
   import, or ship a re-hash command; pin with a test that imports one row in
   each normalization and gets one entry.

---

**Resolved 2026-09-19** — fixed in `cli` along the sketch above, all three steps.

Reproducing it first turned up a second, worse symptom sharing the root cause: re-importing an **identical** accented export reported `conflict — Stable ID matches an entry with different transaction data`. The loader NFC-normalizes payee on read while the CSV row keeps the bank's form, so `_fingerprint` compared the NFC-stored entry against the NFD row that had just written it. The id matched (it is an ASCII literal in the file) but the data did not. An ASCII control re-imported cleanly as `duplicate`, which isolated the cause. So the dedup path was broken outright for any accented description, not only across normalizations.

The note's premise was also slightly pessimistic: the cross-normalization re-import was caught as `possible_duplicate` and excluded by the fuzzy layer, so it did not silently post a duplicate — it degraded from exact match to fuzzy match.

What shipped:

1. `_hash_import_ids` NFC-normalizes the description and account before hashing, normalizing *after* `upper()` since uppercasing decomposed text can itself emit a non-canonical form.
2. `_fingerprint` normalizes payee and narration through a shared `_match_text`, which is what repairs the `conflict`.
3. Migration needs no re-hash pass: the pre-NFC digest is computed alongside and added as a lookup-only identity, so a ledger carrying a legacy id still deduplicates while anything newly written uses the canonical id. ASCII descriptions are unaffected — NFC is a no-op there, and their ids stay byte-identical.
4. `dedup.md` records the NFC rule, the normalize-after-uppercase ordering, and the legacy-id compatibility.

Verified: `csv:sha256:feb28befc4acd45e` for the ASCII control is unchanged; NFD and NFC exports of one row now both yield `csv:sha256:0d2aa9afca7ff6ee`; re-importing the same accented export is `duplicate` instead of `conflict`; the other normalization is `duplicate` instead of `possible_duplicate`; and a ledger holding the legacy `fafae216cb2748c5` still reports `duplicate`. Regression coverage is `cli/tests/test_import_id_normalization.py` — reverting the fix fails four of its five tests (the fifth is the ASCII-stability guard, which must pass either way). `cd cli && make check-all` passes (1478 tests).
