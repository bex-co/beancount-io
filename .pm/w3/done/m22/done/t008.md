## Objective

Make the common calendar's visible dates and accessibility names use the selected application language, even when it differs from the browser preference.

## Context

- Fresh desktop and narrow Chinese Budget dialogs contain English calendar dates and labels; active English in a Chinese browser gets a Chinese month dropdown.
- DatePicker omits locale and Calendar overrides the month formatter with the browser default. The pinned DayPicker locales already provide translated labels.
- Seven forms share DatePicker; the milestone README separates live evidence from source-only callers.

## Steps

1. Pass the active locale from t001 to Calendar with its DayPicker label extensions. Preserve upstream selected/today qualifiers rather than translating only the visible caption.
2. Remove the browser-default month override or replace it with formatting using that same explicit locale. Keep the existing calendar system, selected date and text-input contract; coordinate m24 and069.
3. Exercise zh/en-US and en/zh-CN at both widths, including keyboard date selection and a language transition. Use local fixtures for the source-only callers.

## Files

- dashboard/src/common/components/ui/date-picker.tsx
- dashboard/src/common/components/ui/calendar.tsx
- Shared active-language infrastructure from t001

## Acceptance criteria

- [ ] Caption/dropdown months, weekdays, dates and all calendar accessibility names follow the active app language.
- [ ] Date selection preserves the same underlying calendar date and existing keyboard behavior.
- [ ] A locale transition never leaves a settled mixture of languages; failed/superseded loads preserve the existing transition contract.

## Out of scope

Typed-date parsing/validation in m24, year bounds in069, new calendar systems,
global RTL redesign, new dependencies, API changes and production mutations.
