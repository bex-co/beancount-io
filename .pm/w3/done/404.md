# A failed text or CSV export write destroys the previous successful export

**Major · 45–60m · cli · A1.** Query execution succeeds, but an OS-enforced
write failure leaves an existing export replaced by a partial result. JSON
export under the identical failure preserves the original bytes.

Found 2026-09-21 at HEAD `98359325`, checkout `bea 0.3.0`, Python 3.13.0,
macOS 26.5.1 arm64. Both text and CSV reproduced twice with fresh destinations.
This is a deliberately induced **EFBIG** failure using the child process's
`RLIMIT_FSIZE`; no actual full-disk/ENOSPC event was observed, and the user's
filesystem limits were not changed. Only synthetic local files were affected.

## Reproduce

From `cli/`, create `tmp/` if needed and run the following using the existing
environment's Python. It launches the real executable, not a mocked writer:

```python
import os
from pathlib import Path
import resource
import signal
import subprocess
import tempfile

bea = str(Path('.venv/bin/bea').resolve())
run = Path(tempfile.mkdtemp(prefix='qa-export-', dir='tmp')).resolve()
ledger = run / 'main.bean'
ledger.write_text('''2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-02 * "Lunch"
  Assets:Cash -10 USD
  Expenses:Food
''')
destination = run / 'previous.csv'
original = b'previous successful export: preserve these bytes\n'
destination.write_bytes(original)
env = {k: v for k, v in os.environ.items() if not k.startswith(('BEA_', 'QA_'))}
env.update(BEA_CONFIG_DIR=str(run / 'config'), XDG_CACHE_HOME=str(run / 'cache'),
           BEA_NO_UPDATE_NOTIFIER='1', PYTHONDONTWRITEBYTECODE='1')
def limit_writes():
    resource.setrlimit(resource.RLIMIT_FSIZE, (64, 64))
    signal.signal(signal.SIGXFSZ, signal.SIG_IGN)
query = "SELECT '" + 'q' * 150 + "' AS value LIMIT 1"
result = subprocess.run(
    [bea, '--file', str(ledger), 'query', query, '--format', 'csv',
     '--output', str(destination)], cwd=run, env=env,
    stdin=subprocess.DEVNULL, capture_output=True, timeout=35,
    preexec_fn=limit_writes,
)
print(result.returncode, result.stdout, result.stderr)
print('preserved:', destination.read_bytes() == original)
print(repr(destination.read_bytes()))
```

Actual: exit **1**, empty stdout, stderr `Error: [Errno 27] File too large`.
The old export is gone; the destination is a 64-byte CSV prefix containing
the `value` header and a truncated `q` row. Default text mode likewise leaves 64 spaces from the
wide header instead of the old export. Source ledger hashes are unchanged.

Expected: a failed one-shot export preserves the previous complete result.
Write the fully rendered result to a sibling temporary file and replace the
destination only after the write and close succeed. Preserve successful
replacement behavior and ledger-alias refusal.

Controls: resetting the same original and using global `--json` (without
`--format`) under the same cap exits 1 with a JSON error and keeps the original
byte-identical. Removing the cap makes the text export succeed and replace
the destination normally. No subprocess hung or was killed by a signal.

## Cause, scope and dedupe

`cli/src/bea_engine/query.py:132` waits for `_executed` to finish, then opens
the existing destination with `"w"` and writes `buffer.getvalue()` directly.
That protects against query/render errors but truncates before an I/O failure
during write/close. `text_answer` serves text, CSV and Beancount rendering;
text/CSV are reproduced, Beancount format is source-indicated only. JSON
reaches `cli/src/cli/output.py` `emit` and the existing atomic writer instead.
Keep the frontend/engine dependency boundary when reusing or moving the write
operation. Interactive streaming `.output` is outside this finding.

All queues, completed/blocked records and open milestones were searched for
partial exports, write failures, EFBIG/ENOSPC and output preservation.
Completed `w3/380` (`cbb0d6ad`) fixed **query/render failure** by buffering,
with a resolution promising a failed export leaves the previous bytes intact;
its full tests do not induce an I/O failure after successful rendering.
The engine comment also explicitly describes failed-write preservation.
USAGE's explicit atomic-write promise is currently phrased for JSON, whose
implementation passes this control; clarify text/CSV coverage with this fix.
`w1/m22/t001` owns JSON export and `w3/400` incomplete ledger-alias protection,
not this later write phase. Targeted query history contains no atomic text
export fix. Add a real bounded write-failure regression plus success and alias
controls; no dependency or API changes are needed.

Evidence: ignored `cli/tmp/qa-20260922T052032Z-loop/export-write-failure/`
and `captures/export-fsize-*.json` retain exact argv, the 64-byte limit,
environment, streams, statuses and before/after contents/hashes. The harness
also redirects only Beanquery init/history paths. Other OSes, actual ENOSPC
and abrupt power loss are unverified; do not describe this as those events.

---

**Resolved 2026-09-22** — a failed text, CSV or Beancount export now leaves the
previous export byte-identical.

This is the residual of w3/380, which buffered the render so a *query* failure
could not destroy the destination. The write itself was still
`output.open("w")`, which truncates before any byte is safely down — so an I/O
failure partway through left a fragment of the new result where the last good
export had been.

The rendered text now goes to a sibling temporary file and is swapped in with
`os.replace`. That reuses `bea_engine.ledger.write.candidate_file`, the
engine's existing safe-sibling primitive: same directory (so the replace is
atomic), fsync, and guaranteed cleanup — rather than adding a third copy of
that pattern beside the frontend's `cli.utils.atomic_write` and the price
cache's inline version. The frontend/engine boundary is untouched; JSON keeps
using `atomic_write`, which is why it already preserved.

Verified with the note's own `RLIMIT_FSIZE` harness: text, CSV **and**
Beancount all preserve the original bytes at a non-zero exit, no `.bea-*` temp
survives, and the controls hold — a successful export still replaces, w3/380's
failed-query preservation still holds, and the ledger-alias refusal is
unchanged.

Regression coverage is `cli/tests/test_export_write_is_atomic.py`. Reverting
the fix fails the text and CSV cases; the Beancount case passes either way
because that renderer refuses this query before any write, so it is a control
rather than a proof for that format.

Two things worth recording:

- The harness must set `PYTHONDONTWRITEBYTECODE=1`, as the note's repro does.
  Without it the write cap truncates `.pyc` files in the shared source tree
  and every later run dies with `marshal data too short`. I hit exactly that
  and the test says why, so the next person does not.
- As the note insists: this is an induced EFBIG, a real os-level write failure
  after a successful query. It is **not** a disk-full or power-loss test and
  nothing here claims to be.

`cd cli && make check-all` passes (1888 tests). `USAGE.md`'s atomic-write
promise needs no rewording now that text and CSV meet it too; it is phrased
generally and was only true of JSON before.

Unverified, as in the note: other platforms, and an actual ENOSPC event.
