# CSV sign changes round exact decimal amounts before writing the ledger

**Major · 40–55m · cli · A1.** The no-code CSV importer uses arithmetic unary
minus to change signs. For inputs wider than Decimal's active precision,
negation silently rounds the amount. Parentheses, trailing-minus, debit and
`sign=ledger` paths can therefore persist a different source amount; every
generated counterposting also passes through this rounding operation.

Found 2026-09-21, reproduced through HEAD `aefe02e3`, checkout `bea 0.3.0`, Python 3.13.0,
macOS 26.5.1 arm64. Real subprocess apply/read/check journeys, isolated
synthetic ledgers and child config/cache, closed stdin. Parentheses reproduce
on two pristine roots; nearby spellings and short-precision controls checked.

## Reproduce

Create `/absolute/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

Create `/absolute/bank.csv`:

```csv
Date,Amount,Description
2026-01-02,(1234567890.123456789012345678901),Exact
```

```sh
bea --json --file /absolute/main.bean import /absolute/bank.csv \
  --csv date=Date,amount=Amount,narration=Description \
  --account Assets:Cash --default-account Expenses:Food --apply
```

Actual: exit **0**, empty stderr, `written=1`. Both the returned entry and the
new ledger bytes contain:

```beancount
  Assets:Cash    -1234567890.123456789012345679 USD
  Expenses:Food   1234567890.123456789012345679 USD
```

Expected source amount: **-1234567890.123456789012345678901**, with an exact
opposite counterposting. `check` in a fresh process reports valid (exit 0),
and BQL reads the rounded amount, so accounting validation does not expose the
changed input. Source CSV bytes remain unchanged; before/after ledger content
and hashes prove this is a persisted write, not human display rounding.

Verified variants:

- `1234567890.123456789012345678901-` produces the same rounded source amount.
- Plain positive text with `sign=ledger`, and a positive value in the mapped
  debit column, also write the rounded negative value and pass `check`.
- A plain leading-minus input preserves its full source token **on disk**,
  but the generated positive counterposting rounds. Plain positive input
  likewise retains its source token and rounds the negative counterposting.
- `(1234.56)` writes exactly `-1234.56` / `1234.56` and passes `check`.

The fresh BQL read of a plain negative token also rounded it despite its exact
source bytes; this note does not claim fixing importer sign changes resolves
all downstream Beancount arithmetic. Disk tokens isolate the importer defect.

## Cause and scoped fix

`cli/src/bea_engine/csv_mapper.py:178` returns `-number` for parentheses or
trailing-minus inputs. `CsvImporter.extract` applies unary minus again for
debits, `sign=ledger`, and the counterposting (around lines 736, 738 and 751).
Constructing `Decimal` from the input string retains all digits; unary minus
then applies the active arithmetic context and rounds to 28 significant digits.
The parentheses/trailing path was introduced in `1aa50d2e` (w1/m24/t003).

Use context-independent sign changes (for example `Decimal.copy_negate`) at
these sign-only sites; do not globally increase Decimal precision or truncate
the input to fit it. Preserve bank/ledger signs, zero semantics, grouping and
notation validation. Add actual no-code CSV preview/apply regressions with
more than 28 significant digits that inspect **both written posting tokens**,
plus the ordinary-precision controls. Assertions must not compute the expected
opposite with the same rounding unary-minus operation. No dependency or API
change is needed; standalone Python importer implementations remain outside
this scoped repair.

**Resolved 2026-09-22** — changing a CSV amount's sign no longer changes the
amount.

Unary minus is arithmetic: it applies the active decimal context and rounds to
28 significant digits. The amount is parsed exactly from its source text, so
every sign-only step rewrote a wider value before it reached the ledger — and
`check` then confirmed the rounded figure as valid.

A named `_negated()` using `Decimal.copy_negate` replaces all four negation
sites the note identified: the parentheses/trailing-minus branch, the debit
column, `sign=ledger`, and the generated counterposting. Nothing else changes
— no global precision increase, no truncation of the input — exactly as the
note scoped it.

Verified on disk across all six shapes, each writing the full
31-significant-digit value with an exact opposite:

| input | source posting | counterposting |
| --- | --- | --- |
| `(1234567890.123456789012345678901)` | exact negative | exact positive |
| trailing minus | exact negative | exact positive |
| leading minus | exact negative | exact positive |
| plain positive | exact positive | exact negative |
| `sign=ledger` | exact negative | exact positive |
| debit column | exact negative | exact positive |

The ordinary-precision control (`(1234.56)`) is unchanged, and the written
ledger still passes `check` — exactness is not bought at the cost of the
postings balancing.

Regression coverage is `cli/tests/test_csv_exact_sign_changes.py`. As the note
required, the expected opposite is a **literal**, never computed with `-value`
— deriving it with the operation under test would have made the tests agree
with the bug. A unit test pins `_negated` directly (including that `0.00`
keeps its scale as `-0.00`), and another pins that plain unary minus is what
rounds, so the reason for `copy_negate` stays legible. Reverting the fix fails
11 of the 14; the ordinary-precision control and the mechanism pin pass either
way. `cd cli && make check-all` passes (1937 tests).

Explicitly **not** fixed, as the note says: a BQL read of an exact on-disk
token still rounds it. That is downstream Beancount/Beanquery arithmetic, not
importer sign handling — the disk tokens are what isolate this defect, and
they are now correct. Standalone Python importers stay outside this repair.

Unverified: other platforms and non-default decimal contexts.
