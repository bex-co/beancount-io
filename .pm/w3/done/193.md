# One number, three labels: Statistics calls the same count both "Postings" and "Entry count"

**Minor · 45–60m · dashboard.** A1: in a double-entry product, "entry" and "posting" are different things, and the product should not use them interchangeably for one number.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), English/light, 1440×1000, authenticated QA account on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. Read-only.

Open `/ledger/<owner>/example/statistics`. One card carries two contradictory labels for one column:

- title: **"Postings per Account"**
- description directly beneath it: **"Entry count per account (59 Accounts)"**

The same numbers appear on `/accounts` under a third label, the column header **"Entries"** — `Expenses:Food:Restaurant` is `370` on both pages.

The value is provably a **posting** count. BQL control: `SELECT account, count(position) AS postings WHERE account ~ 'Vanguard:Cash|Restaurant|Mercury' GROUP BY account` returns `Assets:Bank:Mercury:Checking 3`, `Assets:US:Vanguard:Cash 276`, `Expenses:Food:Restaurant 370` — matching the rendered values exactly. The producer agrees: `backend-cluster/ledger/src/features/ledger/service/ledger-account-service.ts:146-148` documents the derivation as "per-account **posting** counts". The GraphQL field is nevertheless named `entryCount`, and that misnomer is what both wrong labels inherit.

The two labels are separate keys in the same locale file, both rendered by the same card: `dashboard/src/features/ledger-data/statistics/locales/en.ts:81-86` (`page.statistics.postingsPerAccount` = "Postings per {account}") and `:28-31` (`page.statistics.entryCountPerAccount` = "Entry count per account"). The Accounts column uses a third key, `dashboard/src/features/ledger-data/accounts/locales/en.ts:87` (`page.accounts.entries`).

Fix: settle on one term for this number and use it in all three places. "Postings" is the right one — it is what the value is, what the producer calls it, and what completed [m14](./done/m14/README.md) already named it ("Make Statistics **postings** counts honor the active filters"). Update the card description and the Accounts column header to match the title, in all 15 locale files, and keep the descriptions accurate rather than merely swapping a word. **Do not rename the `entryCount` GraphQL field** — that is a cross-package API-contract change subject to the repo's REST/GraphQL/MCP parity rule and needs its own decision; if the field name is worth fixing, raise it separately. Owning package: `dashboard` only.

Blast radius: three locale keys across 15 files each, and any test asserting the current strings. Check whether `page.statistics.entryCountPerAccount` and `page.accounts.entries` have other consumers before changing their meaning; if either is reused for a genuine entry count elsewhere, add a new key instead of repurposing it. `src/test/translations.test.ts` checks locale shape.

Adjacent states: the counts are filter-sensitive (that is what m14 shipped), so whatever wording is chosen must still be true when filters narrow the ledger; the empty and single-account cases must read correctly.

Not a defect, checked in the same pass: the Statistics card says "(59 Accounts)" while `/accounts` says "61 / 61". The API returns 61 open-directive accounts of which exactly two — `Assets:US:Vanguard` and `Assets:US:BofA` — have zero postings, so the card is honestly listing only accounts that have postings. Not counted.

Dedupe: searched every queue including `done/` for statistics, postings, entry count and these key names. Completed [m14](./done/m14/README.md) made these counts honor active filters — it fixed *which* postings are counted, never what the column is called, and its own title establishes "postings" as the intended term. Completed `m25` gave the Accounts table its row/cell structure, not its header wording. Nothing owns this terminology.

Unverified: the other 14 locales' current wording, whether any ledger in production has an entry with two postings to one account (which would make the two counts numerically diverge, not just verbally), and the patched behavior.

Evidence (gitignored, local only): `dashboard/tmp/qa-20260912/statistics-postings-vs-entries.json` (both labels, the shared numbers on both pages, the BQL control, and the 59-vs-61 account-count check).
