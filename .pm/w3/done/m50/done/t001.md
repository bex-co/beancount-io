## Objective

`w3/done/392` made it impossible for a control character to reach a ledger file
through the field-by-field writers, because each field goes through
`single_line()`. Raw directive text — what `bea ask` hands the append path — has
no fields to escape: it *is* the file content. Close that path.

## Context

- `cli/src/bea_engine/ledger/text.py` owns `CONTROL_CHARACTERS` and the reasoning
  behind it; reuse that pattern rather than writing a second one.
- `cli/src/bea_engine/ledger/appending.py` parses and appends the text.
- Escaping is the wrong answer here: it would write bytes other than the ones the
  user was shown and approved. Refusing is both safer and simpler to test.

## Steps

1. Add `refuse_control_characters(text, what=…)` beside `single_line`, built on
   the same `CONTROL_CHARACTERS` pattern, allowing tab, LF and CR — the
   whitespace a ledger is legitimately written with.
2. Call it first in `_parse_directives`, before the snapshot and before any
   write, so a refusal cannot leave the ledger touched.
3. Name the offending byte and its offset in the message, and keep the
   `Write rejected: …` prefix the `ask` tool already recognizes.

## Files

- `cli/src/bea_engine/ledger/text.py`
- `cli/src/bea_engine/ledger/appending.py`

## Acceptance criteria

- [x] A directive carrying `\x1b[1A\x1b[2K`, an OSC title, NUL, DEL or a C1 CSI
      is refused with `Write rejected` and `nothing was written`.
- [x] Tab, LF and CRLF in directive text are still accepted.
- [x] The ledger is byte-identical after a refusal; a clean directive still
      appends, including through `--into`.

## Out of scope

- The render paths (t002) and the destination shown on the panel (t003).
