## Objective

Replace the constant `DISPLAY_PATTERN = "MM/dd/yyyy"` with a pattern resolved from the active application language, and parse using that pattern plus the existing `yyyy-MM-dd` fallback — and nothing else.

The single most important constraint: **do not try several orderings and accept the first that parses.** That would turn today's one-way silent error into a two-way one. Exactly one locale pattern is in force at a time; input that does not match it, or the ISO fallback, is invalid.

## Context

- Source of truth: `dashboard/src/common/components/ui/date-picker-utils.ts:10-11` and `parseStrictCalendarDate` at `:31-42`, which requires an exact `format(parsed, pattern) === trimmed` round-trip — keep that strictness.
- `date-fns` is already a dependency and already supplies per-locale objects; completed `m22` established the locale-loading approach for `react-day-picker` and its date-fns locale modules. Reuse that machinery rather than adding a dependency or a hand-written locale→pattern table if the existing locale objects can supply the format.
- The active language comes from `useTranslations()`; the picker must not read the browser locale (that is the mistake note `190` records elsewhere).
- Completed `m22` requires that changing the language does not reinterpret an already-selected date or an in-progress typed draft. Decide and implement what happens to a draft mid-edit when the language changes.
- Completed `m24`'s guarantees all run through this function: no partial-input expansion, no month-length rollover, invalid input blocks submission.

## Steps

1. Resolve the display/parse pattern from the active language.
2. Keep `yyyy-MM-dd` as an always-accepted fallback.
3. Preserve the exact round-trip strictness and the single-pattern rule.
4. Handle the language-change-mid-draft case explicitly.
5. Check SSR/hydration behaves like m22's locale loading.

## Verification record

Implemented 2026-09-15 in `dashboard/src/common/components/ui/date-picker-utils.ts` and `date-picker.tsx`: no new dependency and no hand-written locale table — `getDisplayPattern` reads the order and separators from the resolved locale's own `formatLong.date({ width: "short" })`, widening any year run to `yyyy` so short years (fr `dd/MM/y`, zh `yy-MM-dd`) can never round-trip. English derives byte-identical `MM/dd/yyyy`. `parseStrictCalendarDate` takes the active pattern and tries exactly it plus `yyyy-MM-dd`, keeping the exact round-trip strictness; cross-order input is refused, never reinterpreted. The picker resolves the locale through `useDateLocale()` — the same object the calendar popup uses — so the browser locale has no effect and SSR/hydration behave exactly like m22 (sync read of the settled locale, English default). On language change the effect re-renders the same selected Date in the new pattern without calling `onChange`, and a mid-edit draft is left untouched (m22). A probe over all 15 date-fns locales confirmed every derived pattern round-trips. Covered by the t005 suite (43 picker tests green).
