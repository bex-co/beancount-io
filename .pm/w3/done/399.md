# BQL reserved-table rewriting changes quoted strings and silently loses matching transactions

**Major · 40–55m · cli · A1.** A narration search containing ordinary words
such as `from accounts` returns no matches even when the transaction exists.
The CLI inserts quotes inside the search literal before Beanquery sees it.

Found 2026-09-21, HEAD `8d0e28d9`, checkout `bea 0.3.0` via
`cli/.venv/bin/bea`, Python 3.13.0, macOS 26.5.1 arm64. Reproduced twice from
pristine synthetic ledgers in fresh processes with isolated config/cache and
no credentials; all ledger hashes remain unchanged.

## Reproduce

Save this as `/absolute/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-02 * "transfer from accounts"
  Assets:Cash -10 USD
  Expenses:Food
```

The ledger passes `bea --json --file /absolute/main.bean check`. Run:

```sh
bea --json --file /absolute/main.bean query \
  "SELECT narration WHERE narration = 'transfer from accounts'"
# exit 0; data.rows = []; empty stderr
bea --json --file /absolute/main.bean query 'SELECT narration'
# exit 0; rows contain "transfer from accounts" twice (one per posting)
bea --json --file /absolute/main.bean query \
  "SELECT 'from accounts' AS phrase LIMIT 1"
# exit 0; the value is: from "accounts"
bea --json --file /absolute/main.bean query \
  'SELECT "from balances today" AS phrase LIMIT 1'
# exit 2; syntax error, although the literal itself is valid BQL
```

Expected: string literals retain their contents; the equality search returns
the two matching postings and the scalar query returns `from accounts`
unchanged. The output is already wrong before formatting: text and CSV
one-shot scalar queries also render the inserted quotes.

Working control: run `bea --file /absolute/main.bean query` in a terminal,
then `.set narrow false`, the equality SELECT and the single-quoted scalar
SELECT above, then `.exit`. The real PTY session returns both matching
postings and the unchanged string, with empty stderr and exit 0. This path
currently bypasses the rewriter (separately tracked in `w3/398`). Direct
`SELECT count(*) FROM accounts` and its quoted-table equivalent both still
work; preserve that table compatibility when fixing the literal handling.

## Cause and fix

`cli/src/bea_engine/query.py:44` `_RESERVED_TABLE_FROM` matches `FROM`/`JOIN`
plus `accounts`/`balances` anywhere in the query text. `_quote_reserved_tables`
at line 47 runs a global regex substitution, and `_executed` at line 452
applies it before parsing. It cannot distinguish a relation name from words
inside a quoted literal. Single quotes permit the newly inserted double
quotes as content; a double-quoted literal with more words becomes invalid
syntax. A double-quoted string ending immediately after `balances` happens
to survive because the regex's trailing `(?!")` excludes that match.

Make reserved-relation handling aware of BQL lexical boundaries, preserving
quoted literals, escaped quotes and comments byte-for-byte while quoting
only the intended relation token. Keep unquoted `FROM accounts` and
`FROM balances` selecting their actual tables, and keep quoted table names
unchanged. Do not work around this by changing users' search text or removing
the original table compatibility fix. Regression coverage should execute
the matching transaction search, literal projection, and true table-name
controls through real JSON/text paths.

Caller search: `_executed` is used by `rows_answer` and `text_answer`, so
one-shot JSON, human text and CSV are affected. All three scalar modes and
JSON filtering are reproduced. Interactive/stored queries currently skip
the transformation; coordinate with `w3/398` before extending it to those
paths. Escaped-literal/comment variants, native `--source`, and other
platforms remain unverified. CLI-only; no server/API change is required.

---

**Resolved 2026-09-21** — the reserved-relation rewrite is now lexically aware
and returns the user's own text byte-for-byte.

`_quote_reserved_tables` ran a global regex over the raw query, so it could not
tell a relation from words inside a literal. It now matches against a
`_code_mask` — the query with every string literal and comment blanked to
spaces, same length — and splices the quotes back by offset. Code is rewritten;
text is untouched.

Blanking a literal whole, quotes included, also handles already-quoted
relations for free: `FROM "accounts"` is invisible in the mask, so nothing
rewrites it, which is the right answer since it needs no rewriting.

The mask understands what BQL actually accepts, probed against the parser
rather than assumed: `''` as an escaped quote inside a single-quoted string,
`--` line comments and `/* */` block comments. An unterminated literal is
treated as running to end of input, so a malformed query is passed through
untouched for the parser to complain about rather than being edited first.

Verified on the note's fixture: the narration search returns both matching
postings (was `[]`), `SELECT 'from accounts'` projects `from accounts` (was
`from "accounts"`), and the double-quoted multi-word literal returns its value
instead of exiting 2. Text and CSV rendering agree. Controls hold — `FROM
accounts` unquoted and quoted both count 3, and `FROM balances` still returns
the real balance assertion, so w3/246 and w3/247's compatibility survives.

Urgency note worth recording: this landed right after **w3/398**, which routed
stored and interactive queries through this same preparation. The note observed
that the interactive path was a *working control* because it bypassed the
rewriter — that stopped being true when 398 shipped, so between those two
commits the corruption reached the shell too. It does not now, and a stored
query carrying the literal is pinned as a test.

Regression coverage is `cli/tests/test_query_literals_survive_rewriting.py`,
testing the transformation directly (including a query holding both a literal
and a real relation, which a whole-string rule cannot get right) and through
real JSON, text and CSV runs. Reverting only the rewriter body fails 12 of its
23 tests. `cd cli && make check-all` passes (1803 tests).

Remaining gap, stated honestly: `FROM /* comment */ accounts` now masks the
comment to spaces and still rewrites correctly, but a relation split across a
construct the mask does not model would simply not be rewritten — it would
bind as before rather than corrupt anything. Native `--source` delegation and
other platforms remain unverified, as in the note.
