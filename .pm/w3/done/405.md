# CSV imports silently discard fields beyond the header and can persist shifted amounts

**Major · 40–55m · cli · A1/A2.** A CSV row with four fields under a
three-column header is accepted as ready; its fourth field disappears.
An unquoted thousands separator can consequently turn a bank export into
a balanced but incorrect transaction that `bea check` cannot detect.

Found 2026-09-21 at HEAD `98359325`, checkout `bea 0.3.0` via
`cli/.venv/bin/bea`, Python 3.13.0, macOS 26.5.1 arm64. Preview, apply and
fresh-process BQL verification repeated on two pristine synthetic ledgers.
Both automatic mapping and explicit mapping reproduce the acceptance.

## Reproduce

`/absolute/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

`/absolute/bank.csv` deliberately has an unquoted comma in the amount:

```csv
Date,Amount,Description
2026-01-02,-1,234.56,Coffee
```

Run:

```sh
bea --json --file /absolute/main.bean import /absolute/bank.csv \
  --csv date=Date,amount=Amount,narration=Description --delimiter ',' \
  --account Assets:Cash --default-account Expenses:Food
# exit 0, ready=1, narration="234.56", amount="-1 USD", no warning
```

Repeat with `--apply`: exit **0**, `written=1`, ledger appended, empty stderr.
A new process running
`bea --json --file /absolute/main.bean query 'SELECT narration, account, number, currency'`
returns `234.56 / Assets:Cash / -1 / USD` and the balancing Food posting.
`bea check` passes. The original `Coffee` field is absent from the transaction.
The source CSV remains unchanged; ledger before/after contents and hashes
prove persistence rather than just a misleading preview.

Expected: reject the row/header field-count mismatch with a usage error
(exit 2), naming the file/line and expected versus actual counts, before any
append. Ask the user to fix quoting or delimiters; do not guess how to merge
the extra fields. In a fresh ledger the correctly quoted control
`2026-01-02,"-1,234.56",Coffee` previews/applies **-1234.56 USD**, narration
**Coffee**, and passes a fresh check and BQL read. Both repetitions agree.

## Cause and fix scope

`cli/src/bea_engine/csv_mapper.py:519` `open_records` uses
`csv.reader(..., strict=True)`, but that validates quoting, not row width.
At line 545 it constructs a dictionary by enumerating only `headers`, so
`record[len(headers):]` is silently discarded. `CsvImporter.extract` at line
687 materializes those already-truncated records, then parses and validates
the wrong surviving cells. Accounting validation cannot recover the lost
source structure.

Validate record width before converting it to a header-keyed dictionary.
Keep declared but unmapped columns supported, properly quoted separators and
multiline fields intact, and existing blank-row behavior. Avoid broad changes
to short-row/optional-field policy in this overflow fix. Cover both preview
and apply, including an overflow after a valid row to prove no partial append,
and retain the correctly quoted amount control. CLI-only; no new dependency
or API surface is needed.

Caller search: `open_records` serves header reading, date inference and
`CsvImporter.extract`; automatic and explicit mappings therefore converge
on the same truncation. Actual comma-separated preview/apply is reproduced.
Other delimiters, encodings, trailing empty overflow cells, standalone Python
importers and other platforms remain unverified.

**Resolved 2026-09-22** — a CSV row carrying more fields than its header is
refused before anything is written.

`open_records` keyed each row by enumerating the headers, so everything past
the last one was dropped and the surviving cells shifted. The reported case is
the dangerous shape: `2026-01-02,-1,234.56,Coffee` under a three-column header
imported as `-1 USD` narrated `234.56`, balanced, persisted, and passed `bea
check` — the description gone and the amount off by three orders of magnitude.

`_refuse_surplus_fields` now validates width before the row becomes a
header-keyed dict, so the check sits ahead of mapping, parsing and any append.
The row is ambiguous rather than merely wrong — bad quoting, or the wrong
delimiter — so it is refused rather than guessed at, naming the file, the
physical line, both field counts and what would have been lost, with the two
fixes (quote the value, or name the real `--delimiter`) as details.

One deliberate narrowing: surplus cells that are **empty** are tolerated and
dropped. A trailing separator is common and loses no data, and refusing it
would be a change of short-row/optional-field policy rather than a fix for
this defect — which the note explicitly asked to avoid. Only content is
refused.

Verified on the note's fixture: preview and `--apply` both exit 2 with the
ledger byte-identical, and a good row *before* the bad one does not land on
its own. Controls hold — the correctly quoted `"-1,234.56"` still imports as
-1234.56 USD with `Coffee` intact, a quoted field containing the delimiter is
not an overflow, short rows still pad, a declared-but-unmapped column is
still fine, and automatic mapping refuses it too (both mappings share the one
reader, which the note predicted and the test confirms).

Regression coverage is `cli/tests/test_csv_field_overflow.py`. Reverting the
fix fails its 4 refusal tests while every accept-case passes either way.
`cli/docs/IMPORTING.md` documents the new refusal beside the existing
duplicate-header and unclosed-quote ones. `cd cli && make check-all` passes
(1899 tests).

Unverified, as in the note: other delimiters and encodings (the check is on
field count, after `csv.reader` has already applied the delimiter, so it is
delimiter-agnostic by construction), standalone Python importers, and other
platforms.
