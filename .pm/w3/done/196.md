# Create File offers Save for names the server will refuse — including your main ledger's

**Minor · 40–55m · dashboard.** A2: a newcomer typing a filename should learn it is unusable before they commit to saving, not after.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), English/light, 1440×1000, authenticated QA account with write access on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. **Nothing was saved** — only the filename field was typed into and the Save button's state read; the field was cleared afterwards.

Open `/ledger/<owner>/example/files/create` (it resolves to `/files/new/main`). Type each of these and watch **Save**:

| typed | Save | inline message |
| --- | --- | --- |
| `notes.bean` | enabled | — (correct) |
| `../evil.bean` | **enabled** | none |
| `/etc/passwd` | **enabled** | none |
| `a/b/c.bean` | enabled | — (valid nested path) |
| `   ` (spaces) | disabled | — (correct) |
| `main.bean` | **enabled** | none |

The last row is the one that matters in practice: `main.bean` is this ledger's existing 311 KB file. The page invites you to "create" it, with an empty editor below and an enabled Save, and says nothing.

**No data is at risk, and this is not a traversal hole.** The server refuses all three bad cases:

- `backend-cluster/backend-v2/src/features/ledger/utils/safe-repo-path.ts:8-23` — `assertSafeRepoPath` rejects an empty path, `\0`, `\`, and any `""`, `.` or `..` segment, so `../evil.bean` and the leading slash in `/etc/passwd` are both refused.
- `backend-cluster/ledger/src/api/files.ts:143-173` — create calls Gitea's `repoCreateFile` **without** a `sha`, so it fails when the path already exists; update (`:175+`) is the one that passes `sha` to `repoUpdateFile`. An existing file cannot be silently overwritten by this form.

So the defect is purely that the client validates almost nothing and defers every rejection to the server. `dashboard/src/features/ledger-editor/create-file/index.tsx:65` is the whole rule: `const isSaveDisabled = !filename.trim() || isSaving;`.

Fix: validate on the client before enabling Save, and mirror the server's rules rather than inventing new ones — reject any `.`/`..`/empty segment, backslashes and control characters, matching `assertSafeRepoPath` so the two cannot drift. Separately, check the typed name against the file list the Files tree has already loaded and show an "already exists" state; that check is advisory (a race is always possible), so keep the server error path intact rather than trusting the client. Show the reason next to the field, not only by disabling the button — a disabled control with no explanation is its own problem. Owning package: `dashboard` only; the server rules stay as they are.

Blast radius: the same create form is reached from Files → Create File and from `/files/new/<branch>/<path>`. Check whether the Upload Files flow and the rename action share any of this validation before duplicating it. Keep `m29`'s draft protection intact — that milestone made this editor's drafts survive navigation, and a new validation state must not discard a draft or block Cancel.

Adjacent states: an empty name stays disabled as today; a name that is valid but whose directory does not exist yet should still be allowed (`a/b/c.bean` works); a name colliding with a file added by someone else after the tree loaded must still fail cleanly on the server with a readable error.

Dedupe: searched every queue including `done/` for create file, filename validation, path traversal and overwrite terms. Completed [m29](./done/m29/README.md) covers **draft preservation** in this editor, not filename validation. Completed `179` is a mobile missing-file state. Nothing owns this. Not a regression: `isSaveDisabled` has had this shape since the editor's import.

Unverified: the actual server responses for these names (deliberately not submitted), the Upload Files and rename flows, other locales, narrow viewport, and the patched behavior. The server behavior above is read from source, not observed live.

Evidence (gitignored, local only): `dashboard/tmp/qa-20260912/create-file-validation.json`.

## A working implementation of this already exists in the monorepo (mobile)

Checked 2026-09-13 at HEAD `038faeeb` while QA-ing the native app. **Mobile's Create File flow rejects every case this note reports the dashboard accepting**, so the fix here has a model to copy rather than needing a design.

`mobile/src/screens/ledger-file-browser-screen/utils.ts` — `normalizeLedgerFileName` returns `null` (rather than a name) for: empty/whitespace, `.`, `..`, anything containing `/` or `\`, any C0 control character, and a bare `.bean`/`.beancount`; it appends `.bean` when no extension is given, and finally returns the name only if `isBeancountFile` accepts it. So `../evil.bean` is refused on the `/` check.

`mobile/src/screens/ledger-file-browser-screen/index.tsx:352-372` then wires that to the button *and* re-checks on submit — `isValidNewFilename` requires a non-null normalization **and** no existing entry of that name (which covers this note's "including your main ledger's"), and `handleCreate` independently re-validates null name, duplicate, `canWrite`, and an in-flight ref before issuing the write.

The transferable shape is: **normalize → require the normalization to be non-empty → check collisions → re-validate on submit**, rather than validating the raw string. The same pattern is used for ledger names in `mobile/src/screens/create-ledger-screen/create-ledger-screen.tsx:147-155`, where a Zod schema pairs `.min(1)` / `.max(100)` with `.refine((val) => slugifyLedgerName(val).length > 0)` so a name that slugifies away (`!!!`, `---`) is rejected with its own message.

Caveat: this is a **dashboard** note and the mobile code is a different package, so nothing is directly importable — it is offered as a reference implementation and a set of cases to test against, not as a shared module. Mobile was not re-tested on device for this; the above is read from source.
