# `bea format -i` pads every posting to the longest account name, with no ceiling — one long account inflates a ledger 9–26×

**Severity:** minor. **Owner:** cli. **Estimate:** 25–35 minutes. **A2:** the
width a user can *ask for* is capped at 200 (w3/331), but the width computed from
the ledger's own data is not, so a single long account name turns `bea format -i`
into a whitespace bomb across every posting in the file.

Found by continuous CLI QA 2026-09-26, `bea` 0.3.0 at HEAD `8cd9732b`, Darwin
26.5.1 arm64, isolated config/cache, closed stdin, synthetic ledgers, no flags
beyond `-i`.

## Repro

```sh
python3 - <<'EOF'
import pathlib
long='Assets:'+'L'*300          # a 307-character account name
L=['option "operating_currency" "USD"\n', f'2024-01-01 open {long} USD\n',
   '2024-01-01 open Assets:Bank USD\n','2024-01-01 open Expenses:Food USD\n',
   '2024-01-02 * "one long"\n  %s  1.00 USD\n  Assets:Bank  -1.00 USD\n' % long]
for i in range(4000):
    L.append(f'2024-02-01 * "t{i}"\n  Assets:Bank  -1.00 USD\n  Expenses:Food  1.00 USD\n')
pathlib.Path('books/wide.bean').write_text(''.join(L))
EOF

wc -c books/wide.bean          # 287687
bea format -i books/wide.bean  # exit 0 — "1/1 file(s) formatted."
wc -c books/wide.bean          # 2651984   (9.2x)
bea --file books/wide.bean check   # exit 0
```

With a 907-character account name the same 4000-posting ledger goes
288,887 → 7,453,784 bytes (25.8×). The result is idempotent — reformatting does
not grow it further — and semantically unchanged; the cost is the file.

## Expected

The same ceiling that protects `-w` / `-W` / `-c` protects the width derived from
the ledger: either clamp the computed prefix width (accounts past the cap keep
their own line's natural width instead of setting the column for the whole file),
or refuse with a documented remedy when formatting would inflate the file beyond
a sane multiple of its input, naming the account responsible.

## Actual

`cli/src/cli/commands/format.py:494` (`_MAX_ALIGNMENT_WIDTH = 200`) is enforced in
`_alignment()` only, i.e. against values the user supplies. With no alignment
flags, `bea` forwards nothing and upstream `bean-format`'s `align()` picks the
longest prefix in the file and pads every posting line to it.

## Fix

Pass an explicit `--prefix-width` capped at `_MAX_ALIGNMENT_WIDTH` when the
ledger's own longest prefix exceeds it (or pre-check and raise a `UsageError`
naming the account and suggesting a shorter name / an explicit `-w`). Regression
coverage: a ledger with one >200-char account formats to within a small constant
factor of its input size, stays idempotent, and still passes `check`; ordinary
ledgers keep byte-identical formatting.

## Dedupe

Extends w3/331 (done 2026-09-17), whose fix covered only explicit
`-c`/`-w`/`-W` values and whose own "Expected" already contemplated "cap padding
… or refuse growth beyond a sane multiple of natural width". Not a regression —
the computed-width path was never guarded. Not w3/426, w3/434 or w3/435 (other
`format -i` items: locking and interrupt safety).

**Resolved 2026-10-02** — Shipped in `92ab6818`. Automatic prefix and number
widths ignore values wider than 200 characters; oversized values remain complete
on their own lines. Formatting and appending share the rule, while ordinary
ledgers keep native output and explicit widths keep their documented behavior.
The original 4,000-transaction reproductions now grow only 1.042×, pass ledger
validation, and are idempotent. Eleven pre-fix regression failures were verified;
15 width tests cover every destination, numeric outliers, all-wide fallback, zero
and explicit widths, and append consistency. `make check-all` passes (2,479 tests,
one skip); source review and the public-tree secret scan are clean.
