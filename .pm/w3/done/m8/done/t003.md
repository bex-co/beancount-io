## Objective

Expose the agent-approved subset on MCP: reads as resource templates, writes as **one grouped tool**, not six.

## Context

- Needs m5/t004's resource layer.
- The write group is a natural family in ADR 0008 D3's sense — sync, submit, delete, and the mapping updates share a shape and an authorization class, so one tool with an `operation` discriminator is the honest form. `editLedgerFiles` is the precedent: one tool, three verbs.
- **Grouping is legitimate only when the members really share a shape.** If `unlinkPlaidItem` does not fit the same argument set as `syncPlaidTransactions`, it is a second tool, not a bent enum.
- Whatever confirmation shape t001 decided — `dry_run`, preview-then-commit — applies here, where the caller is a model.
- Reads use the same services as t002.

## Steps

1. Register the approved reads as resource templates.
2. Add the grouped write tool with the `operation` discriminator and t001's confirmation shape.
3. Authorize per call through the same seam every tool uses; refuse after revocation.
4. Drive both with a real client over `InMemoryTransport`.

## Files

- `src/features/ai-agent/api/`, `src/server/api/op-class.ts`

## Acceptance criteria

- [ ] Approved reads appear in `resources/templates/list` and read real data.
- [ ] The write tool covers its family; `tools/list` grows by at most one.
- [ ] Each resolves through the same service as its REST twin.
- [ ] A write after revocation is refused, proven by revoking between two calls.

## Out of scope

- Anything t001 left REST-only.
