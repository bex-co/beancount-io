## Objective

A tool result is spent whole in every later request of the same question, so an
unbounded result put a 15,000-row table into the request body and the gateway
refused it with `request entity too large` — exit 1, no answer, no explanation.
Bound it, and tell the model it was bounded.

## Context

- `w3/448`: ~90 KB body answers 200, ~1.8 MB answers 413.
- Truncating rendered text would cut a row in half; truncating rows keeps every
  value the model can quote intact.

## Steps

1. Cap at `MAX_ROWS = 200` and `MAX_CHARS = 12_000`, whole rows only.
2. Append `… truncated: showing the first N of M rows`, telling the model to
   disclose it and to prefer an aggregate, a date range or a `LIMIT`.
3. Say the same thing in the prompt so enumeration is not the first choice.

## Acceptance criteria

- [x] A 15,000-row result renders within the character budget and names the
      15,000 rows it is not showing.
- [x] End to end against a local stub: the tool result inside the outbound body
      is truncated and the whole body stays well under 100 KB.
- [x] A result that fits says nothing about truncation.

## Out of scope

- Paging a large result across several tool calls.
