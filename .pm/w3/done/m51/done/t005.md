## Objective

`ask` sent no output cap, so every request reserved the model's whole default
allowance; and a connection-level failure escaped the CLI's own translation, so
`ask` said `Connection error.` where every other command says
`Could not reach the server (…)`.

## Context

- `w3/446` (amended): with an open window an uncapped request succeeds, so the
  cap is a near-exhaustion boundary effect — but a request that reserves
  worst-case output is the first one refused at the edge, and setting a cap is
  ours to do. The quota-accounting mismatch (a five-hour window retiring an
  account that reports 12% of its tokens used) is backend work and stays on 446.
- `w3/448` item 2: `translated_failures` caught only `ModelHTTPError`;
  pydantic-ai raises `ModelAPIError` for a connection failure.

## Steps

1. Add `MAX_OUTPUT_TOKENS` and `model_settings()`, and build the `Agent` with it.
2. Catch `ModelAPIError`, walk the cause chain for the HTTP client's transport
   error, and word it with the same `to_bea_error` the API client uses.
3. Detect the proxy's `QUOTA_EXCEEDED` code wherever the envelope nests it and
   say which quota was hit, when it resets, and what to do meanwhile.

## Files

- `cli/src/cli/ask/agent.py`

## Acceptance criteria

- [x] The outbound body carries the output cap (read from the wire, not the
      source).
- [x] Against a closed port, `ask` and `bea cloud status` both say
      `Could not reach the server (…)`, and `Connection error.` never appears.
- [x] A quota refusal names the quota and its reset time and leaks no model name.

## Out of scope

- Surfacing remaining AI quota in `bea cloud status`, and the proxy's own error
  mapping — both stay on `w3/446` as backend/follow-up work.
- The nested-envelope rendering defect, which is `w3/445`.
