# `bea add transaction` rejects scientific amounts (`1e2`) while `import` and bulk JSON accept them

**Severity:** minor. **Estimate:** 20–35 minutes. **Owner:** cli. **A1:** an
agent that reuses the same amount token across write paths sees
`add transaction` refuse `1e2` with a usage error, while `import --csv` and
`add transactions` silently accept Decimal scientific form and write `100 USD`.

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `d11e8855`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only.

## Repro

```sh
bea --json --file main.bean add transaction --date 2024-03-02 --narration sciadd \
  --posting 'Assets:Cash 1e2 USD' --posting 'Income:Salary -1e2 USD'
# exit 2
# Scientific notation '1e2' is not supported in Beancount amounts.
# Use decimal notation, such as '1000' instead of '1e3'.

printf 'Date,Description,Amount\n2024-03-01,Sci,1e2\n' > sci.csv
bea --json --file main.bean import sci.csv --apply \
  --csv date=Date,payee=Description,amount=Amount \
  --account Assets:Bank:Checking
# (Expenses:Uncategorized open) exit 0 — ledger posts 100 USD;
# preview amount field shows "1E+2 USD"

printf '%s\n' '[{"date":"2024-03-03","narration":"scibulk","postings":[
  {"account":"Assets:Cash","units":{"number":"1e2","currency":"USD"}},
  {"account":"Income:Salary","units":{"number":"-1e2","currency":"USD"}}]}]' \
  > sci.json
bea --json --file main.bean add transactions --from sci.json
# exit 0 — writes 100 / -100 USD

# Extreme exponents that Decimal accepts but Beancount cannot lex:
printf 'Date,Description,Amount\n2024-03-04,Huge,1e999\n' > huge.csv
bea --file main.bean import huge.csv \
  --csv date=Date,payee=Description,amount=Amount \
  --account Assets:Bank:Checking
# exit 0 preview — "1 ready", SOURCE AMOUNT `1E+999 USD`, diff expands to a
# ~1000-digit literal; apply then fails: ValueError Invalid number format
```

## Expected

One policy across CLI write paths: either reject scientific notation everywhere
with the same usage message, or accept it everywhere and normalize to plain
decimal before write (and show `100 USD` in import preview, not `1E+2 USD`).
Reject exponents whose normalized decimal exceeds what Beancount can write/lex
at preview time (not only at apply).

## Actual

Posting string parsing for `add transaction` has an explicit scientific-notation
guard. `csv_mapper._parse_decimal` is bare `Decimal(value.strip())`, which
accepts `1e2`. Bulk JSON units `number` likewise go through Decimal without that
guard. Import JSON even surfaces `1E+2 USD` in the row `amount` field.

## Fix

Share one amount-token normalizer: reject `e`/`E` exponents with the existing
message, or accept and rewrite to fixed-point decimal strings before ledger
print/preview. Apply in posting parse, CSV `_parse_decimal`, and bulk units/
amount fields. Cap or reject magnitudes that cannot round-trip through
Beancount’s amount lexer. Regression: the `1e2` repros either all exit 2 or
all write `100 USD` with preview `100 USD`; `1e999` fails at preview (not
false-ready); no path-only divergence.

## Dedupe

Not w3/256 (`$` / thousands / parentheses). Not w3/235 (bool `--meta`).
Not w3/265 (`NaN`/`Infinity` non-finite CSV amounts). Historical w1 notes on
scientific *output* formatting are unrelated. No open note covers input
scientific-notation disagreement across add/import/bulk.
