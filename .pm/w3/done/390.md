# Every successful write to a slow-loading ledger leaves a full-size `..bea-*.picklecache` beside it — both cleanup paths miss it by one dot

Severity: **major**. **Estimate:** ~1h. **Owner:** cli. Unbounded disk growth
in the user's ledger directory from ordinary, successful, single-threaded use —
no crash, no kill, no concurrency required. Four routine `bea add`s on a 12 MB
ledger leave 51 MB of hidden garbage; a 20-operation session left 233 MB.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, no login. Synthetic fixtures only; no credentials used.

## What is wrong

`bea` stages a write in `.bea-XXXXXXXX.tmp` beside the ledger, loads that
staged file to validate it, then `os.replace`s it over the real file. Loading
it makes Beancount write a pickle cache sidecar next to it. The staged file is
renamed away; **its sidecar is orphaned**, at full ledger size, and never
cleaned up.

`bea` does try to clean it up, and the stale-file sweep added by `w5/done/014`
tries too. Both miss the same way: Beancount's
`PICKLE_CACHE_FILENAME = ".{filename}.picklecache"` **prepends** a dot, so the
real name carries two leading dots and neither cleanup expression matches it.

```
bea stages          .bea-acdn4plk.tmp
beancount writes   ..bea-acdn4plk.tmp.picklecache     ← two dots
bea unlinks         .bea-acdn4plk.tmp.picklecache     ← one dot, never exists
w5/014 sweep globs  .bea-*                            ← cannot match "..bea-*"
```

## Repro (synthetic, no login, no concurrency)

Needs a ledger slow enough to load that Beancount decides to cache it —
`PICKLE_CACHE_THRESHOLD = 1.0` seconds. A 60k-transaction / 240k-line file
loads in ~1.7 s here; the small control loads in ~0.2 s.

```sh
python3 - <<'PY'
import datetime
d0 = datetime.date(2020, 1, 1)
L = ['option "operating_currency" "USD"', '2019-12-31 open Assets:Cash USD',
     '2019-12-31 open Expenses:Food USD', '2019-12-31 open Equity:Opening USD',
     '2019-12-31 * "seed"', '  Assets:Cash   10000000.00 USD', '  Equity:Opening', '']
for i in range(60000):
    d = d0 + datetime.timedelta(days=i % 2000)
    L += [f'{d.isoformat()} * "V{i%997}" "p{i}"',
          f'  Expenses:Food   {1+(i%50)}.{i%100:02d} USD', '  Assets:Cash', '']
open('big.bean', 'w').write('\n'.join(L))
PY

ls -a                      # big.bean only

bea --file big.bean add transaction --date 2026-01-01 --narration single \
    --posting "Expenses:Food 1.00 USD" --posting "Assets:Cash"
# Added 1 transaction to …/big.bean.      ← exit 0, a completely normal success

ls -a
# ..bea-acdn4plk.tmp.picklecache          ← 12 MB, orphaned
# big.bean
```

It accumulates linearly, one per write:

| after | leftovers | ledger dir |
| --- | --- | --- |
| 1 add | 1 | 16 MB |
| 2 adds | 2 | 27 MB |
| 3 adds | 3 | 39 MB |
| 4 adds | 4 | 51 MB |

`bea import --apply` and `bea add note` leak identically — anything that stages
a write.

**An import *preview* leaks too**, which is worse: the command writes nothing
to the ledger and says so ("Preview only. Review the entries, then repeat with
`--apply` to write"), yet still leaves a full-size orphan behind.

```sh
bea --file big.bean import lk.csv --csv auto --account Assets:Cash   # no --apply
ls -a | grep '\.\.bea-'
# ..bea-bmygp7ro.tmp.picklecache        ← 12 MB, from a read-only preview
```

## Working controls

- **Plain read commands never leak.** `check`, `list transaction`,
  `report trial-balance` and `query PRINT` run back-to-back against the same
  big ledger add zero orphans — they only maintain the ledger's own legitimate
  cache. Only commands that *stage* a candidate file leak, and that includes
  `import` without `--apply`.
- **Small ledgers never leak.** Three `add`s against a 6-line ledger leave the
  directory containing exactly `m.bean`. Its ~0.2 s load is under Beancount's
  1.0 s threshold, so no cache is written and there is nothing to orphan.
- **The ledger's own cache is legitimate and must be left alone.**
  `.big.bean.picklecache` (one leading dot, the ledger's real name) is created
  by ordinary reads and genuinely works: cold `list transaction` takes 3.58 s,
  warm takes 1.27 s. A fix must delete only the orphaned `..bea-*` sidecars —
  **not** every `*.picklecache` in the directory, which would throw away a
  working cache on exactly the ledgers that need it.

## Root cause (verified)

`beancount/loader.py:75`:

```python
PICKLE_CACHE_FILENAME = ".{filename}.picklecache"
PICKLE_CACHE_THRESHOLD = 1.0
```

The sidecar is `<dir>/.<basename>.picklecache`. For a staged file already
named `.bea-XXXXXXXX.tmp`, that is `..bea-XXXXXXXX.tmp.picklecache`.

Both `bea` cleanups compute a different string:

- `cli/src/bea_engine/ledger/write.py:231` —
  `Path(str(candidate) + ".picklecache").unlink(missing_ok=True)` yields
  `.bea-XXXXXXXX.tmp.picklecache`, one dot short. It has never matched a real
  file. Introduced in `a90b1706` (ADR014), wrong since.
- `cli/src/bea_engine/ledger/write.py:171` — the abandoned-candidate sweep
  `directory.glob(".bea-*")`. `fnmatch('..bea-x.tmp.picklecache', '.bea-*')`
  is `False`, so the sweep cannot reach it either. Introduced in `7df6d57f`,
  the `w5/done/014` fix.

Confirmed mechanically:

```python
cand = Path('/ledger/.bea-acdn4plk.tmp')
str(cand) + '.picklecache'                              # /ledger/.bea-acdn4plk.tmp.picklecache
cand.parent / ('.' + cand.name + '.picklecache')        # /ledger/..bea-acdn4plk.tmp.picklecache
# equal? False
```

The unlink at `:231` also sits on the failure branch, so even with the correct
name the success path (`os.replace` at `write.py:778`) would still need to
remove it.

## Fix

Compute the sidecar the way Beancount does —
`candidate.parent / ("." + candidate.name + ".picklecache")` — and remove it on
**both** the success and failure paths, next to the `os.replace` at
`write.py:778` as well as the existing unlink at `:231`. Widen the sweep glob
at `:171` to cover the doubled-dot form (`.bea-*` plus `..bea-*`, or match on a
suffix) so previously abandoned sidecars are reclaimed too. Prefer deriving the
name from `beancount.loader.PICKLE_CACHE_FILENAME` rather than re-spelling the
convention a third time.

Regression coverage: after a successful `add` to a ledger whose load exceeds
the threshold, the ledger directory must contain only the ledger. A unit test
asserting the computed sidecar path equals Beancount's own formatting would
have caught this without needing a slow fixture.

## Blast radius

- Every command that stages a candidate file: `bea add` (all directive types),
  `bea import` **with or without `--apply`**, `bea add transactions`, and per
  `write.py:31` `bea ask`'s append path — the module's own docstring names them
  as sharing this writer. The preview case means even a user who never commits
  an import still accumulates orphans.
- Only bites ledgers that load in over 1.0 s — i.e. exactly the large, real
  ledgers where a full-size copy per write costs most. A user on a small ledger
  never sees it, which is likely why it has survived.
- The orphan always lands **beside the root ledger**, even for
  `add --into sub/inc.bean`, because it is the staged root that gets loaded.
  A fix only needs to sweep the root's directory, not every include's.
- Files are hidden (leading dot) and named unlike anything a user recognises,
  so the space is lost silently. `git status` in a ledger repo will not show
  them if `.bea-*` or `.*` is ignored.
- Not a data-integrity defect: the ledger itself is written correctly and
  passes `check` in every case. Nothing is corrupted or lost — this is disk
  consumption and directory hygiene.
- `USAGE.md`'s locking section already promises "No lock files are created in
  ledger directories"; this is the same expectation broken by a different file.

## Adjacent states

Exercised: single and repeated sequential writes; `add transaction`, `add note`
and `import --apply`; read-only commands as a control; a small-ledger control;
and the concurrency races from `w3/389` (which is how the pile was first
noticed — 20 leftovers, 233 MB, in one race directory).

## Dedupe

Searched `.pm/**/*.md` including `done/` for `.bea-`, `tmp`, `picklecache` and
temp-file terms. The ancestor is **`w5/done/014`** — "A `bea` write killed by
PID leaves full-size `.bea-*.tmp` copies beside the ledger" — same family
(full-size hidden copies accumulating beside the books) and its fix
(`7df6d57f`) added the very sweep that misses this file.

It is distinct and strictly worse: `w5/014` needs the write to be **killed**
(`Popen.kill()`), whereas this needs nothing at all — an ordinary write that
exits 0 leaks on every invocation. Treat it as a gap in `w5/014`'s fix rather
than a duplicate, and recheck that item's definition of done against the
doubled-dot name. No open w3 item covers it (`385`–`389` are import row
numbering, import account validation, managed-price auth, Ctrl-C at a prompt,
and import conflict category).

## Unverified

Windows behaviour was not exercised (the dot-prefix convention is Beancount's,
not platform-specific, so it is expected to be identical). Whether an
abandoned-but-correctly-named `.bea-*.tmp` is still swept by `:171` was not
retested here — `w5/014` covers that and nothing in this finding contradicts
it. The exact load-time threshold was not bisected; the 1.0 s figure is read
from `beancount/loader.py:79` and is consistent with the ~0.2 s control not
leaking and the ~1.7 s fixture leaking every time.

---

**Resolved 2026-09-21** — a staged write no longer leaves a pickle-cache
sidecar beside the ledger. The note's diagnosis was exact, including the
two-dots mechanism and both missed cleanups.

`pickle_cache_of()` now computes the sidecar by asking Beancount's own
`get_cache_filename()` rather than re-spelling the convention a third time,
and the sweep glob is widened to `(".bea-*", "..bea-*")` so orphans already on
disk are reclaimed.

Two corrections to the note's fix plan, both from reading the code:

1. It says the unlink at `write.py:231` "sits on the failure branch, so even
   with the correct name the success path would still need to remove it". It
   is a `finally:` in `candidate_file`, so it already ran on both paths —
   fixing the name there covers success and failure, and no second removal
   beside the `os.replace` was needed.
2. It suggests deriving from `PICKLE_CACHE_FILENAME`. Going one step further to
   `get_cache_filename()` also honours `BEANCOUNT_LOAD_CACHE_FILENAME`, which
   `loader.initialize` respects and a hand-formatted template would have
   ignored — the same class of drift that caused this bug.

Verified live on the note's 60k-transaction fixture: four `add`s plus an
import preview, an `import --apply` and an `add note` now leave the directory
holding only `big.bean`, `lk.csv` and the ledger's own legitimate
`.big.bean.picklecache` — zero `..bea-*` orphans, where before one add alone
left 12 MB. The working control holds: the ledger's real cache is created by
reads and survives writes.

Regression coverage is `cli/tests/test_candidate_pickle_cache_cleanup.py`. It
includes the cheap name test the note asked for (the one that would have caught
this without a slow fixture), a sweep test for pre-existing orphans, and the
control that a real `.main.bean.picklecache` is never swept — deleting every
`*.picklecache` would have "fixed" the leak by gutting the cache on exactly the
ledgers that need one.

Worth recording honestly: my first end-to-end test was vacuous. It patched
`loader.PICKLE_CACHE_THRESHOLD = 0.0` and passed against the *unfixed* code,
because `initialize()` binds the threshold into a closure — the constant alone
changes nothing. It only became a real test after adding
`loader.initialize(use_cache=True)`, and now fails against the old code. The
comment in the driver says so, since the trap is easy to fall into again.

Recheck of the ancestor, as the note asked: `w5/014`'s definition of done was
about abandoned `.bea-*.tmp` files after a killed write, and that behaviour is
untouched — its sweep still collects them, now alongside the doubled-dot form
it could not reach. This was a gap in that fix, not a regression of it.

Unexercised, as in the note: Windows. The dot-prefix convention is Beancount's
rather than platform-specific, and the fix now derives the name from upstream
instead of assuming a spelling, so it should hold there — but it was not run.
