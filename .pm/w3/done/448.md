# `bea ask` sends unbounded query results, so a normal-sized ledger fails with "request entity too large" or "Connection error."

**Severity:** major (a plausible question on a real-sized ledger fails with no
usable explanation and no partial answer). **Owner:** cli. **Estimate:** 40–50
minutes. **A1:** an agent asking `bea ask` to enumerate anything hits a wall
whose message names neither the cause nor a smaller question to try.

Found 2026-09-26 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD `8cd9732b`,
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR`, synthetic
ledger, authorized QA account.

## Repro

Generate a synthetic ledger with 15,000 transactions (about 2 MB — a few years
of real bookkeeping), one expense account, one checking account:

```sh
bea --file big.bean check                       # exit 0, a valid ledger
bea --file big.bean ask --print "List every single transaction in my ledger with its date, payee and narration. Do not summarize."
```

Two runs, two different messages, both exit 1, both after ~8 seconds:

```
Error: request entity too large
Error: Connection error.
```

Independent confirmation of the mechanism, using the same credential straight
against the proxy: a `chat/completions` body of ~90 KB answers `200`; ~1.8 MB
answers `413 request entity too large`. The agent's tool had produced a
15,000-row text table and handed all of it to the model.

## Expected

Either a bounded tool result the model can still answer from — "showing the
first N of 15000 rows", so the answer says it was truncated — or a refusal that
names the real problem ("the result of that query is too large to send; ask for
a total, a filter, or a date range"). A transport-level sentence that names
neither the ledger nor the query is the one outcome that leaves the user with
nothing to do.

`cli/docs/USAGE.md` also promises network failures read the same way across the
CLI. They do not here: against a dead port, `bea cloud status` says
`Could not reach the server (ConnectError).` while `bea ask` says
`Connection error.`

## Root cause

1. `cli/src/cli/ask/agent.py::run_bql_query` returns `data["text"]` with no size
   or row cap; the only special case is the empty-result branch. Whatever the
   engine printed goes into the conversation, and the conversation is the request
   body.
2. `translated_failures()` in the same file catches only `ModelHTTPError`.
   pydantic-ai raises `ModelAPIError` for a connection-level failure (its
   `_map_api_errors` wraps the SDK's `APIConnectionError`), which is not
   translated, so the user gets the SDK's bare `Connection error.` rather than
   the CLI's own network sentence. Whether a too-large body surfaces as `413` or
   as a reset is timing-dependent, which is why the two runs differ.

## Fix

1. Cap the tool result in `run_bql_query`: truncate to a documented budget
   (rows and characters), and append an explicit
   `… truncated: showing N of M rows` line so the model must disclose it. The
   engine already reports truncation for listings, so the wording exists.
2. Extend `translated_failures()` to `ModelAPIError` (and any pydantic-ai
   connection/timeout error), mapping it to the same
   `Could not reach the server (…)` sentence `cli/src/cli/api/client.py` uses.
3. Regression coverage: a stub tool result far over the cap is truncated with
   the disclosure line; a connection-refused proxy produces the shared network
   sentence and exit code from `ask` and from a `cloud` command alike.

## Dedupe

No `.pm` item mentions a tool-result cap, `413`, `entity too large`, or
`ModelAPIError`; `git log -S"ModelAPIError"` is empty repo-wide. `w3/done/381`
built `translated_failures` for `ModelHTTPError` only and never mentioned
connection failures. `w3/428` (open) quotes `Error: Connection error.` only
incidentally, as the observed output of a blank question against a dead port.

---

**Resolved 2026-09-27** — tool results are capped at 200 rows / ~12,000
characters with a `… truncated: showing the first N of M rows` line the model is
told to disclose, and `translated_failures` now covers `ModelAPIError`, so a
connection failure reads `Could not reach the server (ConnectError).` exactly as
`bea cloud status` does. The truncation and the network sentence are verified
against a local stub model server and a closed port (simulated); the live
15,000-transaction enumeration could not be re-run because the account's AI
window closed mid-session, so that one confirmation is outstanding. Shipped in
`w3/done/m51` (cli: `src/cli/ask/results.py`, `src/cli/ask/agent.py`,
`docs/USAGE.md`, `tests/test_ask_result_shape.py`).
