# Import Configure dates follow the browser, not the app language — and change format mid-wizard

**Minor · 45–60m · dashboard.** A2: a newcomer reviewing their first import must be able to read the dates they are about to commit.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), 1440×1000, authenticated QA account on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. **No import was submitted** — CSV parsing and preview are client-side, and the Import button was never clicked.

Open `/ledger/<owner>/example/import?lang=fr` and upload the product's own sample, `/lgasset/csv_transactions.csv` (10 rows, ISO dates). The whole UI is French (`html lang="fr"`, "Configurer les paramètres d'importation", "Compte source", "Bénéficiaire"), and the browser is `navigator.language = "en-US"`.

- **Preview** step shows the dates as authored: `2025-12-01`, `2025-12-02`, `2025-12-03`, …
- **Configure** step shows the same rows as `12/1/2025`, `12/2/2025`, `12/3/2025`, …

Two problems in one place. First, `12/1/2025` is US month-first format produced from the **browser** locale while the selected app language is French; a French reader reads it as 12 January. Expected: the selected app language decides, as it does everywhere else. Second, the same wizard shows the same date in two different formats one click apart, and the page's own instructions say "Date (YYYY-MM-DD)". An English run reproduces the format change identically (`2025-12-01` → `12/1/2025`), so the inconsistency is not locale-dependent.

Root: `dashboard/src/features/importer/utils/format-import-date.ts:17-28` — `formatImportDateForDisplay(isoDate, locales?)` correctly takes a `locales` argument and its unit tests pass one (`"en-US"`, `"de-DE"`). Its **single production caller**, `dashboard/src/features/importer/components/steps/configure/account-mapping-table.tsx:322`, calls `formatImportDateForDisplay(txn.date)` with no locale, so `toLocaleDateString(undefined, …)` falls back to the browser's preference. That component already has `useTranslations()` at `:74`, so the active language is in hand.

This is the same defect class as completed [144](./done/144.md), which added an explicit `language` argument to `formatActivityDate` and `formatMonth` for exactly this reason ("with an undefined locale `Intl.DateTimeFormat` falls back to the browser's preference instead of the selected app language"). This caller was not in that note's scope — it is a residual of the same class, in a different feature.

Fix: pass the active `i18n.language` from the existing `useTranslations()` into the one call site, and decide the format question deliberately rather than leaving two representations in one wizard. Either keep the canonical `YYYY-MM-DD` the Preview step and the page instructions already use, or use the localized form in both steps — do not keep one of each. Preserve the helper's UTC-safe day handling and its verbatim fallback for unparseable input (`format-import-date.ts:9-15, 21-23`), and keep the helper's `locales` parameter optional so its tests stay valid. Owning package: `dashboard` only — no API or schema change; the submitted value is `txn.date` (ISO) and must not change.

Blast radius: `formatImportDateForDisplay` has exactly one production caller (`account-mapping-table.tsx:322`); the other references are its own tests. If the format decision lands on ISO in both steps, check the Preview step's own renderer too so the two stay aligned.

Adjacent states: an unparseable date must still render verbatim, not "Invalid Date"; an empty date must stay empty; switching app language on the Configure step should update the rendered dates.

Dedupe: searched every queue including `done/` for import date, `formatImportDateForDisplay`, locale and date-format terms. Completed `144` is the Overview Net Worth / Recent Activity instance of this class and does not cover the importer. Completed `m22` localized relative timestamps and date calendars; completed `m24` kept *typed* entry dates consistent with submitted entries — neither is this display path. Open `m36` owns lossy CSV **amount** conversions in the same wizard and open `m33` owns Configure state across Back; coordinate edits to `account-mapping-table.tsx` with them without folding this in. My own note [186](./186.md) is the Overview activity **year** omission, a different component and a different question.

Not a defect, checked in the same pass: the Configure step showing `-4.5` for `-4.50` and `2500` for `2500.00` is value-preserving trailing-zero display, and `m36`'s stated boundary explicitly treats equivalent spellings as acceptable — not counted here.

Unverified: the other 13 locales, narrow viewport, live language switching on the Configure step, and the patched behavior. No import, AI fill, or upload request was submitted.
