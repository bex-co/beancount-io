# `bea add transactions --from` rejects UTF-8 BOM JSON while `bea import` accepts BOM CSV

**Severity:** minor. **Estimate:** 15–30 minutes. **Owner:** cli. **A1:** agents
or editors that emit UTF-8 BOM JSON (common on Windows) fail bulk add with a
decode error, even though the same BOM is stripped for CSV import.

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `8e0d5210`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only.

## Repro

```sh
# BOM + valid array
printf '\xef\xbb\xbf%s\n' '[{"date":"2024-04-01","narration":"t","postings":[
  {"account":"Expenses:Food:Groceries","amount":"1 USD"},
  {"account":"Assets:Bank:Checking"}]}]' > rows.json

bea --json --file main.bean add transactions --from rows.json
# exit 2
# Invalid JSON at line 1, column 1: Unexpected UTF-8 BOM (decode using utf-8-sig).
```

Working controls:

- Same payload without BOM writes successfully.
- `bea import` on a CSV that starts with UTF-8 BOM infers columns and previews
  (BOM stripped).

## Expected

Bulk JSON should decode with `utf-8-sig` (or equivalent) so a leading BOM is
ignored, matching CSV import and common editor defaults.

## Actual

JSON loader uses strict UTF-8 and surfaces the BOM as a usage error, telling the
caller to decode with utf-8-sig instead of doing so itself.

## Fix

Open `--from` / stdin JSON with `utf-8-sig` (path and pipe). Regression: BOM
array writes like a BOM-less file; still reject true invalid JSON; CSV BOM
behavior unchanged.

## Dedupe

Not w3/227 (non-UTF-8 CSV discovery). No open note covers JSON BOM.

---

**Resolved 2026-09-16** — `add transactions --from` reads UTF-8 with BOM stripped (`utf-8-sig` / leading U+FEFF), matching CSV import. Covered by `cli/tests/test_transactions_json_bom.py`. Shipped with this board close.
