# `list transaction --search` / BQL `~` miss Unicode-equivalent narrations (NFC vs NFD)

**Severity:** minor. **Estimate:** 25–40 minutes. **Owner:** cli. **A1:** on
macOS, pasting or typing `café` often yields NFD (`cafe` + combining acute);
a ledger that stored NFC `café` (or the reverse) returns “No transactions
found” for `--search`, and the matching BQL `narration ~ "…"` is empty, even
though the strings are canonically equivalent.

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `845f2ecd`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only.

## Repro

```sh
# NFC in the ledger (common from many editors / JSON)
bea --file main.bean add transaction --date 2020-02-01 --narration 'café' \
  --posting 'Assets:Cash -1 USD' --posting 'Expenses:Food 1 USD'

# NFD needle (common from macOS text fields): cafe + U+0301
bea --file main.bean list transaction --search $'cafe\u0301'
# exit 0 — No transactions found.

bea --file main.bean query $'SELECT narration WHERE narration ~ "cafe\u0301"'
# empty / no matching row

# Control — same normalization form:
bea --file main.bean list transaction --search 'café'
# finds the row
```

Reverse direction (NFD stored, NFC search) also misses.

## Expected

Case-insensitive `--search` (and ideally BQL `~` used for the same job) should
match Unicode-canonical equivalents, e.g. compare after `unicodedata.normalize
("NFC", …)` (or NFKC if that is the documented policy), so agents and humans
are not split by invisible combining marks.

## Actual

Search is a case-insensitive substring on the raw Python/Beancount strings;
NFC and NFD forms of the same visible word do not match.

## Fix

Normalize both haystack and needle to NFC (or document NFKC) in the list
`--search` path before comparing. Optionally note the same for query helpers
or leave BQL as upstream. Regression: the NFC/NFD pair above finds the row;
ASCII and already-matching Unicode controls stay green.

## Dedupe

Not w3/252 (control chars in metadata). Not w3/257 (BOM). Account-name NFC/NFD
identity (doppelgänger opens / unknown posting) is w3/278. No other open note
covers Unicode normalization for list search / narration match.

**Resolved 2026-09-19** — `--search` and the BQL `~` path normalize to NFC before comparing, shipped in `0ebedb41` (`cli`, w1/m26/t004) and closed out with the milestone in `5caa2189`. Re-ran this note's repro at HEAD with explicitly constructed bytes (NFC `63 61 66 c3 a9` stored, NFD `63 61 66 65 cc 81` as the needle): `bea --json list transaction --search <NFD>` returns the stored row, and `SELECT narration WHERE narration ~ "<NFD>"` returns its postings, where both were previously empty. The same-normalization control still matches. Regression coverage lives in `cli/tests/test_unicode_normalization.py`.

Note that the `csv:sha256` import-id hash was deliberately left un-normalized by that task, because changing it rewrites ids already written to ledgers; that residue is tracked separately as [377](../377.md).
