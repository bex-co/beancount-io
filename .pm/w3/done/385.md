# `bea import --csv` cell errors cite a different row number than the preview table and every other import diagnostic

Severity: minor. **Estimate:** ~1h. **Owner:** cli. A rejected import points the
user at the wrong row, and the offset is not a constant they can mentally
correct for.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, no login. Synthetic fixtures only; no credentials used.

## What is wrong

`bea import` numbers rows two different ways in the same command:

- the preview's `ROW` column, the `blocked` explanations, and the duplicate /
  conflict explanations all use a **1-based data-row index** that skips blank
  rows;
- CSV **cell parse errors** (date, amount, debit/credit, currency, category)
  use the **physical file line**, which counts the header row *and* every
  skipped blank row.

So "Row 5" in an error and "Row 5" in the preview are different records. Since
a cell parse error aborts the whole batch, the row number is the only thing
the user has to go on.

## Repro (synthetic, no login)

`main.bean` opens `Assets:Bank:Checking`, `Expenses:Food` and
`Expenses:Uncategorized`.

**1 — the off-by-one, with no blank rows.** The bad cell is the *first* data row:

```sh
printf 'Date,Amount,Description\n2026-13-45,-1.00,THE ONLY BAD ROW\n2026-02-02,-5.00,good\n' > one.csv
bea --file main.bean import one.csv --csv auto --account Assets:Bank:Checking --apply
# exit 2
# Error: Row 2: cannot parse date '2026-13-45' in column 'Date' with format '%Y-%m-%d'.
#        ^ the preview calls this record Row 1
```

Walking a bad date through each position gives a consistent `+1`:

| bad cell at data row | file line | error says |
| --- | --- | --- |
| 1 | 2 | `Row 2` |
| 2 | 3 | `Row 3` |
| 3 | 4 | `Row 4` |

**2 — the offset is not constant.** Blank rows are skipped by the preview
(`w3/done/263`) but still counted by the error:

```sh
printf 'Date,Amount,Description\n2026-02-01,-1.00,good one\n,,\n,,\n2026-13-45,-9.00,BAD ROW\n' > drift.csv
bea --file main.bean import drift.csv --csv auto --account Assets:Bank:Checking --apply
# Error: Row 5: cannot parse date '2026-13-45' …
```

Make that same record valid and the preview calls it **Row 2**:

```
csv → Assets:Bank:Checking: 2 ready, 0 exact duplicates, 0 possible duplicates, 2 blank rows skipped
ROW  STATUS  DATE        PAYEE / NARRATION  SOURCE AMOUNT  ID    RULE
1    new     2026-02-01  good one           -1.00 USD      hash  unmatched
2    new     2026-02-05  WAS BAD ROW        -9.00 USD      hash  unmatched
```

`Row 5` vs `Row 2` — a gap of 3, which grows with every blank row above the
failure.

**3 — the control: every other diagnostic uses preview numbering.** A blocked
row at data row 3 is reported as `Row 3`, agreeing with the table:

```
3    blocked  2026-02-03  THE BLOCKED ONE  -3.00 USD  hash  Expenses:NeverOpened
Row 3: Account 'Expenses:NeverOpened' is not open. Run: bea add open …
```

The duplicate explanations agree too (`Row 1: import-id csv:sha256:… is already
in the ledger.` for data row 1).

## Expected

One row vocabulary for the whole command. A cell parse error should name the
same row the preview's `ROW` column would — the 1-based data-row index, blank
rows not counted — so "fix row N" sends the user to the record the table shows.
If a physical file line is genuinely more useful for hand-editing, it should be
labelled as such (`line 5`) and ideally reported *alongside* the row
(`Row 2 (line 5)`), never as a bare `Row` that collides with the other meaning.

## Root cause (verified)

`cli/src/bea_engine/csv_mapper.py:677` — `line = index + 2`, where `index`
enumerates `materialized`, which still contains blank rows:

```python
for index, row in enumerate(materialized):
    line = index + 2
    if self._is_blank_row(row, blank_headers):
        self.skipped_blank_rows += 1
        continue
```

`+2` reconstructs the physical file line (one header line, 0-based index), and
because the blank-row `continue` comes *after* the assignment, skipped rows
still advance it. Every `UsageError` in this module interpolates that `line`
under the label `Row`: `csv_mapper.py:125`, `:147`, `:158`, `:627`, `:686`,
`:697`, `:706`, `:749`.

The other family uses the preview index: `src/bea_engine/importing.py:345`
(`f"Row {row['row']} ({row['status']}): {row['reason']}"`) and
`src/cli/commands/import_.py:689`, `:692`, `:696` all read `row['row']`, which
is the same value rendered in the table's `ROW` column.

## Fix

Track the data-row ordinal separately from the physical line: increment a
`row_number` only for rows that survive the blank check, and interpolate that
into the eight `UsageError` messages in `csv_mapper.py`. Keep the physical line
if it is worth reporting, but label it distinctly. Add regression coverage
asserting that a cell error's row number equals the `ROW` the preview assigns
the same record, including a fixture with skipped blank rows above the failure
so a constant offset cannot pass.

## Blast radius

- All eight `csv_mapper.py` diagnostics share the bug: unparseable date
  (`:686`), unparseable amount (`:125`), non-finite amount (`:147`), cell
  access errors (`:158`), missing mapped column (`:627`), debit/credit both or
  neither filled (`:697`), no currency column (`:706`), missing category column
  (`:749`).
- `--csv auto` and an explicit `--csv date=…,amount=…` mapping behave the same;
  both require a header row, so `+2` always overshoots by at least one.
- Only the no-code `--csv` path is affected. Python-importer rows go through
  Beangulp and are reported by `importing.py` / `import_.py`, which already use
  the preview index.
- Not a data-integrity bug: the batch is refused and the ledger is left
  byte-identical (verified by md5 before/after on every repro above).

## Adjacent states

Exercised: bad cell at first/middle/last data row; blank rows before the
failure; `--apply` and preview-only (both refuse identically); blocked rows and
exact-duplicate rows as working controls; a clean import and a re-import
(dedupe writes 0 entries, ledger unchanged).

## Dedupe

Searched `.pm/**/*.md` including `done/` for row-numbering and `--csv` terms.
Closest neighbours, both distinct and both already closed:

- `w3/done/263` — "`bea import --csv` treats blank / whitespace-only rows as
  hard date-parse failures". That fix introduced the `skipped_blank_rows`
  counter this note builds on; its repro happens to show `Row 3` for a blank
  line, but it was about *rejecting* blank rows, not about which number they
  are given. Its fix is what makes the offset variable rather than constant.
- `w3/done/264` — "Failed `bea add` / bulk rejects cite ledger line numbers
  that do not exist". Same family of complaint, different surface and code
  (`ledger/adding.py`, ledger lines) — not this one.

No open w3 item covers it; w3 had no open notes at filing time.

---

**Resolved 2026-09-21** — `bea import --csv` has one row vocabulary. A cell
error now names the same record the preview's `ROW` column does, and reports
the physical file line beside it, labelled: `Row 2 (line 5)`.

The note's root cause held. `csv_mapper.py` derived `line = index + 2` from an
enumeration that still contained blank rows, and the blank-row `continue` came
*after* the assignment, so skipped rows advanced it. Every diagnostic in the
module interpolated that reconstructed file line under the label `Row`.

The two numbers are now derived once, together, and handed down as a pair: a
pre-pass numbers the surviving data rows and keeps each row's physical line
alongside. Diagnostics quote a single locator built by `_at()`; `line` survives
only where it is genuinely a file line (`new_metadata`, and `_malformed`, which
already said `Line`). Threading one formatted locator also removed the `Row {}`
prefix duplicated across the eight message sites.

The note listed eight diagnostics; a ninth had the same bug and is fixed with
them — the mixed-decimal-convention refusal (`_resolve_decimal_comma`) was fed
`index + 2` too, so `row 3 uses comma decimals` could name a row the preview
called `row 1`. It now receives data-row ordinals. Blank rows never voted on
the convention (blank cells are skipped), so only the numbering changed.

Verified against the note's own repros: case 1 reports `Row 1 (line 2)` where
the preview says Row 1 (was `Row 2`); case 2 reports `Row 2 (line 5)` where the
preview says Row 2 (was `Row 5`). Controls unchanged — blocked rows still read
`Row 3` agreeing with the table, duplicate explanations still agree, and a
rejected batch still leaves the ledger byte-identical.

Ten existing tests asserted the old numbering (`test_import.py` ×7,
`test_decimal_notation.py` ×3). They encoded the bug, so each was updated to
the corrected locator rather than worked around; each fixture was re-read to
confirm which data row its bad cell actually is.

Regression coverage is `cli/tests/test_csv_error_row_matches_preview.py`. Its
main test uses the preview as the oracle — repair the bad cell, read the `ROW`
the table gives that record, require the error to have named the same number —
across six shapes including blank rows above, among, and before the failure, so
a constant offset cannot pass. Reverting the fix fails 9 of its 11 tests.
`cli/docs/IMPORTING.md` now states the format and why the two numbers differ.
`cd cli && make check-all` passes (1600 tests).

Not done: the note's "Unverified" item — multi-line quoted CSV cells, where the
physical line desynchronises further — was not exercised. The row ordinal is
correct regardless; only the parenthesised line could be off for such a file.
