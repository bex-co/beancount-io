## Objective

Decide, and record in an ADR, what introspection means across three credential kinds that do not share a shape. The implementation tasks are small; the decisions are not, and making them inside a route handler is how they end up undiscoverable.

## Context

- `src/server/api/identity.ts` — `resolveIdentity`, the `Identity` type, `effectiveCapabilities`, `AuthMethod`.
- Read this milestone's README first: "The shape this takes" and "Known traps" state the problems this task must answer.
- ADR numbering: next free is `ADR017`; existing backend-v2 ADRs are 007, 008, 009, 010, 011, 016.

## Decisions to make

1. **Mount path and caller authentication.** **The endpoint is authenticated. Anonymous access is not one of the options here** — RFC 7662 §2.1 requires the caller to authenticate, and an anonymous introspection endpoint turns any stolen credential into "valid, user X, may write ledger Y" and is a free brute-force oracle against the API-key digest lookup. What this task decides is *which* credential admits a caller, not whether one is required. Our dynamic OAuth clients are public/PKCE, so "any registered client" is not available; the real options are a full signed-in session (`assertSessionIdentity`), the `admin` op-class, the existing `x-admin-token` operator secret, or a dedicated confidential client. Note the trap: mounting under `/api-gateway/oauth/` inherits the `REST ALL /api-gateway/oauth/{*path}` always-public census entry, which would make the endpoint anonymous **silently** — the census test would stay green because the catch-all already covers the path. Either mount outside that prefix, or add an explicit narrower entry that overrides it, and say in the ADR which was chosen and why.
2. **What goes in `scope`.** Sessions have an empty `scopes` set and full `capabilities`. Decide whether the response projects `effectiveCapabilities()` into the standard `scope` field, or reports capabilities in a namespaced field and leaves `scope` to mean literally the granted OAuth scopes. Whichever is chosen, a gateway reading only the standard fields must not conclude a session may do nothing.
3. **Which non-standard fields we publish.** Candidates: credential kind (`session`/`oauth`/`apikey`), the `assurance` type (`interactive`/`delegated`/`workload`), and `ledgerScope` — the single-ledger ceiling. These are the facts that make the endpoint worth calling and none are in RFC 7662; namespace them deliberately.
4. **Whether `token_type_hint` is honored.** `resolveIdentity` already orders its attempts cheaply (the `bcio_` prefix check short-circuits). A hint may be accepted and ignored.
5. **Non-goal, stated explicitly:** migrating session JWTs to asymmetric signing. Record why introspection is the answer instead, so the question does not get re-litigated.
