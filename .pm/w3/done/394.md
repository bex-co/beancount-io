# Valid slash and unpadded dates make on-disk entries disappear from `bea list --on-disk`

**Severity:** major. **Owner:** cli. **Estimate:** 40–55 minutes.
**A1:** an agent using the on-disk filter can receive an empty, successful,
untruncated answer for a ledger whose transactions and account opens are
actually written in the file. Ordinary listings falsely label them generated.

Found 2026-09-21 by continuous CLI QA on `main`, HEAD `e213e53b`, checkout
`cli/.venv/bin/bea` 0.3.0, Python 3.13.0, macOS 26.5.1 arm64. Isolated
synthetic fixtures and config/cache/data, absolute `--file`, fresh subprocesses
with closed stdin and 35-second timeouts. No credentials or hosted resources
are needed. Concurrent text-sanitization edits do not touch this code path.

## Reproduce

Create this `main.bean` in a disposable directory:

```beancount
2026/01/01 open Assets:Cash USD
2026/01/01 open Expenses:Food USD
2026/01/02 * "Written transaction"
  Assets:Cash -10 USD
  Expenses:Food
2026/01/03 note Assets:Cash "Written note"
```

```sh
bea --json --file "$PWD/main.bean" check
bea --json --file "$PWD/main.bean" list transaction
bea --json --file "$PWD/main.bean" list transaction --on-disk
bea --json --file "$PWD/main.bean" list open --on-disk
bea --json --file "$PWD/main.bean" list note --on-disk
bea --file "$PWD/main.bean" list transaction
bea --json --file "$PWD/main.bean" query \
  "SELECT date, narration WHERE account = 'Assets:Cash'"
```

All commands exit **0** with empty stderr. Check reports `valid: true`.
The ordinary transaction JSON includes its real `source.filename` and
`source.lineno: 3`, but also **`"generated":true`**. Its human table says:

```text
DATE        FLAG  PAYEE  NARRATION            SOURCE     POSTING AMOUNTS
2026-01-02  *            Written transaction  generated  Assets:Cash: -10 USD; Expenses:Food: 10 USD
```

Each `--on-disk` command returns **`"data":[],"truncated":false,"limit":50`**.
The BQL control returns `["2026-01-02","Written transaction"]`. Source file
hashes are unchanged. A fresh second slash fixture reproduces the result.

Additional transaction-date cases were independently run through check,
ordinary list, and on-disk list:

| Date in the file | Check | Ordinary JSON | `--on-disk` rows |
| --- | --- | --- | --- |
| `2026/01/02` | valid | falsely generated | 0 |
| `2026-1-2` | valid | falsely generated | 0 |
| `2026/1/2` | valid | falsely generated | 0 |
| `2026-01-02` | valid | no generated marker | 1 |

These are accepted Beancount ledger spellings, not invalid command-line date
arguments: the real parser and check validate each. The installed upstream
`beancount/parser/lexer_test.py:test_lex_iter` also explicitly covers slash
dates. CLI option syntax can retain its documented `YYYY-MM-DD` requirement.

## Expected, cause, and blast radius

`cli/docs/USAGE.md` defines `--on-disk` as hiding directives synthesized by a
plugin and returning the directives written in a ledger file. All source
entries above must be retained regardless of accepted date spelling.

`cli/src/bea_engine/ledger/reader.py:66` defines:

```python
_DATE_TOKEN = re.compile(r"^\s*\d{4}-\d{2}-\d{2}\s+(\S+)")
```

`entry_generated()` at `:106` treats a failed match as a generated entry even
when the filename and line number are real. Slash dates and single-digit
months/days fail that narrower regex. `listing.py:100` removes those entries
before limiting or returning the answer.

Caller search found `entry_generated` in all eleven directive readers plus
the shared on-disk filter. The real CLI reproduction covers transaction,
open, and note; the other eight types share the mechanism but were not each
run with alternate dates. No reporting, monetary calculation, or file-write
data loss is claimed.

Working plugin control: an inspected upstream `auto_accounts` plugin with an
ISO-dated transaction still produces correctly marked opens, hides those
opens under `--on-disk`, and retains the transaction. Do not remove generated
entry detection to fix this false-positive case.

## Fix and acceptance

Recognize source dates using Beancount's accepted syntax, preferably its
existing lexer, while retaining the source-location and directive-kind checks.
Keep the result independent of how the parser normalizes dates for JSON.

- [ ] The three alternate date spellings retain their real transaction under
  `--on-disk` and never label it generated in human or JSON output.
- [ ] Slash-dated open and note entries survive the same filter.
- [ ] ISO controls, genuine generated opens, filtering before truncation,
  and source-file preservation remain correct.
- [ ] Meaningful shared-helper and actual CLI regression coverage passes;
  run `make check-all` inside `cli/`.

---

**Resolved 2026-09-21** — `--on-disk` keeps every written directive whatever
date spelling the ledger uses, and a written entry is no longer labelled
generated.

`_DATE_TOKEN` matched only `YYYY-MM-DD`. `entry_generated()` treats a failed
match as synthesized, so in a slash-dated ledger every real entry — sitting at
a real filename and line number — was reported `generated: true` and removed by
the on-disk filter before the limit was applied.

The pattern is now `^\s*\d{4}[-/]\d+[-/]\d+\s+(\S+)`. I probed the installed
parser rather than guessing which spellings matter: it accepts `-` or `/`, in
any mix (`2026-01/02` parses), with unpadded month and day, and rejects
`26-01-02`, `2026.01.02` and `20260102`. The note's preference for reusing
Beancount's own lexer was not possible — the parser is compiled and exposes no
pattern — so the separator and digit counts are deliberately loose, which is
the safe direction: what identifies a synthesized entry is the directive word
after the date, and that check is untouched.

Acceptance:

- [x] All three alternate spellings retain their transaction under `--on-disk`
      and carry no generated marker in JSON or the human table. Extended to
      seven spellings, including the mixed-separator form the note did not
      list.
- [x] Slash-dated `open` and `note` survive the same filter.
- [x] ISO controls unchanged; genuine `auto_accounts` opens are still marked
      generated and still hidden — verified in both ISO and slash ledgers,
      which is the control the note explicitly demanded. Filtering still runs
      before truncation (a hidden generated open must not spend a slot), and

- [x] Coverage at both levels — `entry_generated` directly, and the real CLI —

The helper-level tests include the negative cases that keep the widening
