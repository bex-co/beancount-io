# Ctrl-C at a `bea` prompt exits 1 with `Aborted!` instead of the documented silent 130

Severity: minor. **Estimate:** ~1h. **Owner:** cli. The sibling half of the
`w3/378` pipe contract, on the one path neither that fix nor `w5/010`'s tests
reach.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, driven under a real PTY. Synthetic fixtures only; no
credentials used.

## What is wrong

`cli/docs/USAGE.md` (the "These five codes are the whole table" paragraph)
carves out exactly two signals:

> The exceptions are the two signals that mean the run was ended on purpose:
> `Ctrl-C` still exits **130** and a closed downstream pipe still exits **141**,
> both **without a message**.

`bea query`'s interactive shell honours it. A `bea`-owned Typer prompt does
not: Ctrl-C there exits **1** and prints **`Aborted!`**.

| Ctrl-C delivered at | Exit | Message |
| --- | --- | --- |
| `bea query` interactive shell | **130** | `(interrupted)`, returns to prompt — complies |
| mid-computation (`check`, `list`, `query`, `report`) | **130** | none — complies |
| `bea init` date prompt | **1** | `Aborted!` — violates both halves |

The prompt path is the **only** one that violates the carve-out. See
"Mid-computation is compliant" below for the evidence.

## Repro (synthetic, needs a PTY)

A terminal is required — the prompt never appears otherwise, so this cannot be
reproduced with redirected stdin. Driven here through `pty.fork()`.

```sh
bea init books --currency USD
# Earliest date you will record (opening balances must be as of this date) [2026-09-21]: ^C
# Aborted!
echo $?    # 1     — expected: 130, and no message
```

Control, same run, same harness:

```sh
bea --file main.bean query
# beanquery> ^C
# (interrupted)
# beanquery> .quit
echo $?    # 130   — complies
```

Reproduced twice at the `init` prompt. Nothing is written: the target
directory does not exist afterwards, so the abort itself is clean — only its
status and its noise are wrong.

## Expected

Ctrl-C at any prompt exits 130 and prints nothing, the same way
`bea query`'s shell already does and the same way `w3/378`'s fix made a closed
pipe exit 141 silently.

## Root cause (verified)

`typer.prompt` / `typer.confirm` translate a `KeyboardInterrupt` at the prompt
into `click.Abort`. `cli/src/cli/main.py:134` catches it and re-raises:

```python
except typer.Abort:
    output.flush_warnings()
    raise
```

Click's own top-level handler then prints `Aborted!` and exits 1. There is no
`bea`-side handler converting that into the documented status, whereas the
broken-pipe half got exactly such a handler in `w3/378`:
`cli/src/cli/main.py:49` `_exit_on_broken_pipe()`, which calls
`sys.exit(141)` explicitly (and points the fd at devnull so the shutdown flush
cannot re-break it). `git show f9e2545d` touches only the pipe path — its diff
contains no `130`, `SIGINT`, `KeyboardInterrupt` or `Abort` handling.

## Fix

Add the SIGINT counterpart beside `_exit_on_broken_pipe()`: catch
`typer.Abort` (and a bare `KeyboardInterrupt`) in `_GuardedGroup.invoke` and
`sys.exit(130)` without emitting anything, instead of re-raising into Click's
`Aborted!` path. Keep `output.flush_warnings()` out of it — the contract says
silent. Add regression coverage next to
`cli/tests/test_broken_pipe_contract.py` asserting exit 130 and empty
stdout/stderr for a Ctrl-C at a prompt, with the interactive shell's existing
130 kept as a control.

## Blast radius

Every `bea`-owned prompt takes this path:

- `cli/src/cli/commands/init.py:109` — operating-currency prompt
- `cli/src/cli/commands/init.py:122` — earliest-date prompt (the repro)
- `cli/src/cli/commands/init.py:141` — opening-balance prompt
- `cli/src/cli/context.py:132` — `RunContext.confirm()`, the shared
  destructive-action gate. Its only current caller is
  `cli/src/cli/commands/cloud/generated/ledger.py:82`
  (`Permanently delete ledger '<name>'?`), so an operator who aborts a hosted
  delete at the confirmation also gets exit 1 + `Aborted!`. Every future
  DELETE command inherits it, since `AGENTS.md` says DELETE operations get the
  confirmation gate automatically.

Not a data-integrity defect: aborting writes nothing, and `--yes` / `--no-input`
bypass the prompt entirely (`--no-input` raises a `UsageError` with exit 2, per
contract). The cost is a script that cannot distinguish a deliberate Ctrl-C
from a genuine failure, which is the whole reason the carve-out exists.

## Adjacent states

Exercised under PTY in the same run, all correct: the interactive query shell

## Mid-computation is compliant (verified 2026-09-21)

An earlier revision of this note left this open. It is now settled: a
mid-computation Ctrl-C **does** honour the carve-out, so the fix must not
disturb it.

Method: a 600k-line / 12 MB synthetic ledger (150k transactions) makes every
command run long enough to interrupt reliably — `check` takes ~15s, `report
trial-balance` ~5.4s uninterrupted. Ctrl-C was written to a real PTY, so the
signal reaches the whole foreground process group the way a terminal delivers
it, not just the parent.

| Command | Ctrl-C at | Exit | Output |
| --- | --- | --- | --- |
| `check` | 5s | **130** | none (only the terminal's own `^C` echo) |
| `list transaction --limit 200000` | 5s | **130** | none |
| `query PRINT` | 5s | **130** | none |
| `report trial-balance` | 2s, ×4 trials | **130** | none |

One earlier observation of `report trial-balance` exiting **0** with no output
was a measurement artefact, not a defect: the interrupt was sent at 5.0s
against a 5.4s runtime, so the command had already finished. Re-running it at
2s four times gives a clean 130 every time.

---

**Resolved 2026-09-21** — Ctrl-C at a `bea`-owned prompt now exits **130**
with nothing printed, the way the exit table's carve-out promises and the way
`w3/378` made a closed pipe exit 141.

`_exit_on_interrupt()` sits beside `_exit_on_broken_pipe()` in `cli/main.py`,
and `_GuardedGroup.invoke` catches `typer.Abort` and a bare `KeyboardInterrupt`
into it instead of re-raising into click's `Aborted!` path. The old clause's
`output.flush_warnings()` is deliberately gone: the contract says silent.

On the `Abort`-also-means-EOF question, which the note did not raise: click
raises `Abort` for an EOF at a prompt too and suppresses the original
exception, so the two cannot be told apart. Treating both as 130 is right here
because no `bea` prompt passes `abort=True` — an `Abort` reaching the guard is
always an interrupted prompt, never a declined confirmation. A declined
confirmation returns `False` and the caller reports it ("Cancelled.", exit 0),
and there is now a test pinning that boundary, since it is the one thing this
change could plausibly have broken.

Verified under a real PTY on all three `init` prompts (currency, date, opening
balance): exit 130, nothing on screen past the terminal's own `^C` echo, and
no `books/` directory left behind. Controls verified the same way — `bea
query`'s interactive shell still exits 130 with its own `(interrupted)`, and
mid-computation Ctrl-C on a 450k-line ledger stays silent and reports 130 to
the shell (three trials: two died on SIGINT, which a shell renders as 130, one
exited 130 explicitly). An earlier trial of mine showing exit 0 was the same
measurement artefact the note documents — I had set the interrupt at 4.0s
against a 4.0s runtime.

Regression coverage is `cli/tests/test_interrupt_contract.py`, next to
`test_broken_pipe_contract.py` as the note asked, driving `pty.fork()` because
the prompts never appear on redirected stdin. Reverting the fix fails 4 of its
7 tests; the shell and confirmation-gate controls pass either way.

Two honest caveats:

- The PTY tests emit a `DeprecationWarning` about `forkpty()` in a
  multi-threaded process (pytest-xdist workers). The child `execve`s
  immediately, which is the pattern that makes this safe, and the suite is
  green — but the warning is real and not silenced.
- The hosted `cloud ledger delete` confirmation is still inference, not
  observation, exactly as the note said: it needs credentials this run did not
  have. It goes through the same `RunContext.confirm()` → `typer.confirm`, so
  it shares the fix, and the unit test above covers that gate directly.
