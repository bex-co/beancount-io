# `bea format --in-place` silently discards a concurrent `bea add`: both exit 0, the transaction is gone

**Severity:** major (silent data loss, both commands exit 0). **Owner:** cli.
**Estimate:** 40–60 minutes. **A1:** an agent (or a pre-commit hook, or a
watcher) that runs `bea format -i` while another `bea add` is in flight loses
the added directive with no error anywhere; the ledger simply does not contain
what `bea add` said it wrote.

Found by continuous CLI QA 2026-09-26, `uv run bea` 0.3.0 at HEAD `8cd9732b`,
Darwin 25.5.0, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, synthetic ledger,
closed stdin.

## Repro

Synthetic ledger — one file, 40 000 formatted transactions (any size works; a
bigger file just widens the window). Two accounts, `Assets:Checking` and
`Expenses:Food`, opened `2020-01-01`; each transaction is
`YYYY-MM-DD * "tN"` with `Expenses:Food 1.00 USD` / `Assets:Checking -1.00 USD`.

```sh
# t=0: start the append; it commits at ~3.7s on this fixture
bea --file main.bean add transaction --date 2022-01-01 -n PROBE \
    -p 'Expenses:Food 9 USD' -p 'Assets:Checking' &
sleep 2.6            # land format's read before the append, its write after
bea format main.bean --in-place
wait
grep -c PROBE main.bean      # 0
```

Observed, three consecutive runs at `sleep 2.6` plus hits at 2.5 and 2.8:

- `bea add` exit **0**, stdout `Added 1 transaction to …/main.bean.`, stderr empty.
- `bea format --in-place` exit **0**, `1/1 file(s) formatted.`
- `grep -c PROBE main.bean` → **0**. The committed transaction is not in the file.

A 16 000-line fixture reproduced the same loss once in ~20 attempts, so this is
not an artifact of the large fixture — it is a timing window that exists at
ordinary ledger sizes. Nearby control: at other offsets `bea add` instead exits
**4** with "The ledger changed during the operation … retry" and writes nothing,
which is the correct outcome; the bug is the offsets where it reports success.

## Expected

Either `bea add` fails with the existing conflict error and writes nothing, or
the append survives. A write that returns exit 0 and the message "Added 1
transaction" must be in the file afterwards. `bea format --in-place` must not
be able to replace a file with a copy of content that was already superseded.

## Root cause

`cli/src/bea_engine/ledger/write.py` `append` (~l.822–824) serializes every
engine-side writer with `lock_file(...)` on the root and the destination, then
re-verifies the snapshot and replaces atomically.
`cli/src/cli/commands/format.py` `_format_in_place` (~l.150–180) is the only
other writer and takes **no** lock: it reads each file, runs
`bean-format --in-place` (which reads and rewrites the file itself), then
re-reads and may `file.write_bytes(fixed)`. `grep -rn lock_file src/` finds
exactly one caller — `write.py:824` — so `format -i` and `add`/`import`/`ask`
never contend, and `bean-format`'s stale in-memory copy wins the last write.

## Fix

Make `format --in-place` use the same serialization as every other writer:
take `ledger_write.lock_file(file)` for each file it will rewrite (sorted, to
keep the existing lock order), and re-read + compare the bytes it based the
formatting on immediately before replacing, refusing with the existing
`ConflictError` wording ("The ledger changed during the operation … retry")
rather than overwriting. Because the lock lives engine-side and
`_format_in_place` is frontend code, the locking (and the rewrite) most likely
belongs in a `bea-engine` format command that owns read → align → replace under
the lock, rather than in the frontend around a `bean-format` subprocess.

Regression coverage: a test that holds the ledger lock while `format -i` runs
and asserts it waits rather than clobbering, and a test that mutates the file
between the read and the replace and asserts the conflict error with the file
unchanged.

## Blast radius

Every `format --in-place` caller: single file, `--in-place` on a split-ledger
root, and recursive `format -i dir/` (which rewrites many files in one
`bean-format` invocation, so one interleaved `add` to any of them is lost).
`bea add`, `bea add transactions`, `bea import --apply` and `bea ask`'s append
all go through the locked path and are safe against each other — verified: two
interleaved `bea add` loops (6 appends each) produced 12 directives, exit 0
throughout, `bea check` clean. `--check`/`--dry-run` write nothing and are not
affected.

Dedupe: searched `.pm/**` (including `done/` and `blocked/`) for
`format -i` / `--in-place` / lock / concurren*; w3/415 (multi-line strings),
w3/426 (partial-failure reporting), w3/done/332, w3/done/273, w3/done/362 are
all about *what* `format -i` writes, none about serialization. `git log -S`
on `_format_in_place` shows only `5592d63a` (partial-failure reporting), and
`lock_file` has never had a second caller.

**Re-verified 2026-09-26** (CLI QA consolidation round, run11) — reproduced
again from a pristine synthetic fixture in fresh processes on the same HEAD
`8cd9732b`, `bea` 0.3.0, macOS 26.5.1 arm64, isolated
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed.
Still holds on a 40 000-transaction fixture: sweeping the `format -i` start
offset, both runs at `sleep 2.5` and single runs at 3.0 s and 4.0 s ended with
