# Every `bea` table misaligns on CJK and emoji text — `output.table` pads by character count, not display width

Severity: minor. **Estimate:** ~1h. **Owner:** cli. Cosmetic in mechanism, but
it lands hardest in the import preview, where a Japanese or Chinese bank
description pushes the amount out from under its own header while the user is
deciding whether to commit the write.

Found 2026-09-21 by continuous CLI QA. HEAD `432af8f5` (clean tree),
`uv run bea` 0.3.0, Darwin 26.5.1 arm64, isolated `BEA_CONFIG_DIR` /
`XDG_CACHE_HOME`, no login. Synthetic fixtures only; no credentials used.

## What is wrong

`output.table()` sizes and pads columns with `len()` and `str.ljust()`, which
count **characters**. East Asian Wide characters and emoji occupy **two**
terminal columns each, so any row containing them is padded short and every
column to its right shifts.

```
DATE        FLAG  PAYEE          NARRATION              POSTING AMOUNTS
----------  ----  -------------  ---------------------  -----------------
2026-01-08  *     🏪 emoji shop   emoji payee            Expenses:Food: …
2026-01-07  *     Ünïcödé Störé  accented               Expenses:Food: …
2026-01-06  *     Cafe           plain ascii narration  Expenses:Food: …
2026-01-05  *     日本語商店          ラーメンを食べた               Expenses:Food: …
```

Measured drift to the `NARRATION` column, all rows padded to the same 33
*characters*:

| row | chars | display columns | drift |
| --- | --- | --- | --- |
| header / ASCII | 33 | 33 | 0 |
| `Ünïcödé Störé` | 33 | 33 | 0 |
| `🏪 emoji shop` | 33 | 34 | **+1** |
| `日本語商店` | 33 | 38 | **+5** |

`Ünïcödé Störé` is the control that makes the cause precise: this is not
"non-ASCII breaks it", it is specifically characters whose display width is not
1.

## Repro (synthetic, no login)

```sh
cat > wide.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-05 * "日本語商店" "ラーメンを食べた"
  Expenses:Food   12.34 USD
  Assets:Cash
2026-01-06 * "Cafe" "plain ascii narration"
  Expenses:Food    5.00 USD
  Assets:Cash
EOF

bea --file wide.bean list transaction     # the CJK row's columns sit 5 places right
```

**The consequential case — import preview.** A bank CSV with Japanese
descriptions pushes `SOURCE AMOUNT` out from under its header:

```sh
printf 'Date,Amount,Description\n2026-02-01,-12.34,日本語商店\n2026-02-02,-5.00,Plain Cafe\n2026-02-03,-7.00,ラーメン屋\n' > cjk.csv
bea --file cjk.bean import cjk.csv --csv auto --account Assets:Cash
```

```
ROW  STATUS  DATE        PAYEE / NARRATION  SOURCE AMOUNT  ID    RULE
1    new     2026-02-01  日本語商店              -12.34 USD     hash  unmatched
2    new     2026-02-02  Plain Cafe         -5.00 USD      hash  unmatched
3    new     2026-02-03  ラーメン屋              -7.00 USD      hash  unmatched
```

Same 44-character padding measures 44 display columns on the ASCII row and 49
on both CJK rows.

## Expected

Pad to display width. `日本語商店` is 10 columns, not 5; `🏪` is 2, not 1; a
combining mark is 0. Every row should present the same column boundaries, the
way the ASCII and accented-Latin rows already do.

## Root cause (verified)

`cli/src/cli/output.py:98` — `table()`:

```python
widths = [len(h) for h in headers]          # :103
for row in rows:
    for i, cell in enumerate(row):
        widths[i] = max(widths[i], len(cell))   # :107
...
typer.echo(sep.join(h.ljust(widths[i]) for i, h in enumerate(headers)))   # :109
typer.echo(sep.join(cell.ljust(widths[i]) for i, cell in enumerate(row))) # :112
```

`len()` and `ljust()` are both character-based. There is no width-aware
helper anywhere in `src/cli/` — a grep for `wcwidth` / `east_asian` returns
nothing.

## Fix

Introduce a display-width helper (`unicodedata.east_asian_width` in `("W","F")`
→ 2, `unicodedata.combining(c)` → 0, else 1) and use it for both the `widths`
computation and the padding, replacing `ljust` with an explicit
`cell + " " * (width - dw(cell))`. Apply it once in `output.table()` so every
caller inherits the fix. Regression coverage: a table whose rows mix ASCII, a
CJK string, an emoji and a combining-accent string must produce identical
display-column offsets for the second column on every row — assert on computed
width, not on a golden string, so the test states the property rather than
pinning today's spacing.

`beanquery`'s own interactive tables and upstream-rendered output are outside
this function and out of scope.

## Blast radius

Every caller of `output.table()`, i.e. every human-mode table `bea` renders
itself:

- `cli/src/cli/commands/list.py:232`, `:236`, `:385` — `bea list <type>`;
  payee, narration, and the free-text fields of `note`, `event` and `custom`.
- `cli/src/cli/commands/import_.py:670` — the import preview (the case above).
- `cli/src/cli/commands/report.py:231`, `:276`, `:331` — report breakdowns.
- `cli/src/cli/commands/price.py:63` — `bea price status`.

Reach is narrower than it first looks, and the limit is worth recording:
**CJK account names cannot occur**, so report and balance tables keyed on
account names are unaffected. Upstream Beancount rejects them outright —
`2026-01-01 open Assets:現金` fails with `Invalid account name: Assets:現金`.
The exposure is free-text columns: payee, narration, note/event/custom strings,
and imported CSV descriptions.

Not a data defect: `--json` is unaffected (it does not go through `table()`,
which returns early in JSON mode), the ledger is written correctly, and every
value is present and correct — only the spacing is wrong.

## Adjacent states

Exercised: CJK payee and narration, CJK CSV descriptions through the import
preview, an emoji payee, precomposed accented Latin (aligns correctly), and
pure ASCII as the baseline. A CJK *account* name was attempted and is rejected
upstream, which bounds the blast radius above.

## Dedupe

Searched `.pm/**/*.md` including `done/` for `east_asian`, `wcwidth`, `CJK`,
`full-width`, `align`/`misalign` and Unicode terms. The Unicode-adjacent CLI
items are all different mechanisms and all closed: `w3/done/227` (non-UTF-8

normalizations), `w3/done/256` (bank amount spellings), `w3/done/165` (native
Open Account accepting Unicode names). The dashboard items under `w4` concern
locale text length in UI components, not terminal column width. Nothing covers
display-width padding in `output.table()`. No open w3 item covers it
(`385`–`390` are the other open notes).

## Unverified

Terminal-dependent rendering was not surveyed — the drift is computed from
Unicode display width, which is what a conforming terminal uses, but an
individual terminal's font or emoji-presentation handling can differ,
particularly for emoji with variation selectors. Only one emoji (`🏪`, no
variation selector) was tested. Right-to-left text and zero-width joiner
sequences were not exercised.

---

**Resolved 2026-09-21** — `output.table()` sizes and pads by terminal columns.

A `display_width()` helper implements the rule the note specified — combining
mark 0, East Asian Wide/Fullwidth 2, else 1 — and both the width computation
and the padding go through it, with `ljust` replaced by an explicit pad. The
fix lands once in `output.table()`, so every caller the note lists (`list`,
the import preview, report breakdowns, `price status`) inherits it.

Verified on the note's own fixtures: the four-row `list transaction` table
(CJK, emoji, precomposed accented Latin, ASCII) and the CJK import preview now
have every line at the same display width. Reverting the padding reproduces the
reported drift exactly — 79 columns on the CJK rows against 74 on the header.
`Ünïcödé Störé` aligned before and after, which is the control that keeps the
rule precise.

Regression coverage is `cli/tests/test_table_display_width.py`: a
parameterized unit test of `display_width` (including fullwidth Latin and a
decomposed combining accent, neither of which the note listed), plus the
end-to-end property on both surfaces. As the note asked, it asserts on measured
width rather than a golden string.

Two notes on the test, honestly:

- My first attempt parsed per-column offsets by splitting on the two-space
  separator. That was fragile arithmetic and gave a false failure; the property
  actually being tested is simpler — in a fully padded table every line
  occupies the same number of columns — and that is what it asserts now.
- The row count is passed in rather than inferred from a trailing blank line,
  because the import preview prints its write diff immediately after the last
  row and a diff's `---` header even looks like a table rule.

Out of scope and unchanged, as the note says: `beanquery`'s own interactive
tables and upstream-rendered output do not go through this function. `--json`
is untouched (it returns before the table) and is pinned as a control.

Unexercised, as in the note: real-terminal rendering, emoji with variation
selectors, RTL text and ZWJ sequences. The implementation follows Unicode
display width, which is what a conforming terminal uses, but a specific
terminal's emoji presentation can still differ — a ZWJ sequence in particular
will measure wider here than it renders.
