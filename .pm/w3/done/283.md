# `bea add transactions --from` on non-UTF-8 JSON dumps a raw codec error (exit 1)

**Severity:** minor. **Estimate:** 15–25 minutes. **Owner:** cli. **A1:** an
agent (or Windows export) that feeds UTF-16 / Latin-1 JSON into `--from` gets
`'utf-8' codec can't decode byte 0xff…` as a validation error instead of a
usage message that names UTF-8 (and the BOM/`utf-8-sig` path from w3/248).

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `fd2187f4`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only.

## Repro

```sh
python3 - <<'PY'
from pathlib import Path
row = '[{"date":"2020-06-01","narration":"ok","postings":[
  {"account":"Assets:Cash","amount":"-1 USD"},
  {"account":"Expenses:Food","amount":"1 USD"}]}]'
Path('utf16.json').write_bytes(row.encode('utf-16'))
Path('latin1.json').write_bytes(
    b'[{"date":"2020-06-01","narration":"Caf\xe9","postings":['
    b'{"account":"Assets:Cash","amount":"-1 USD"},'
    b'{"account":"Expenses:Food","amount":"1 USD"}]}]'
)
PY

bea --json --file main.bean add transactions --from utf16.json
# exit 1
# {"error":{"category":"validation",
#   "message":"'utf-8' codec can't decode byte 0xff in position 0: invalid start byte",
#   "exit_code":1}}

bea --json --file main.bean add transactions --from latin1.json
# exit 1 — same shape for 0xe9 invalid continuation byte
```

Working controls:

```sh
# UTF-8 array writes (exit 0)
bea --file main.bean add transactions --from utf8.json

# UTF-8 BOM is a different, clearer usage path (w3/248):
# Invalid JSON … Unexpected UTF-8 BOM (decode using utf-8-sig).
```

## Expected

Exit **2** (usage) with a short message that `--from` must be UTF-8 text
JSON (optionally mentioning BOM → `utf-8-sig` / w3/248). Do not leak a raw
`UnicodeDecodeError` string or classify it as ledger validation.

## Actual

`_load_transactions_json` in `cli/commands/add.py` calls
`Path.read_text()` (locale/UTF-8) and only maps `FileNotFoundError`,
`IsADirectoryError`, and `OSError` to `UsageError`. `UnicodeDecodeError` is a
`ValueError`, so it escapes and surfaces as a generic validation envelope with
exit 1. Stdin UTF-16 often becomes a misleading `Invalid JSON … Expecting value`
instead (text decode with replacement / NULs), so path and pipe disagree.

## Fix

Catch `UnicodeDecodeError` beside the existing OS errors and raise
`UsageError` naming `--from` and UTF-8. Keep successful UTF-8 (and, once
w3/248 lands, UTF-8 BOM) unchanged. Regression: the UTF-16 / Latin-1 fixtures
exit 2 with a stable usage message and no `codec can't decode` wording.

## Dedupe

Not w3/248 (UTF-8 **BOM** still decodes as UTF-8; json.loads then warns).
Not w3/227 (CSV encoding discovery). Not w3/257 (ledger file BOM). Not
w3/251 (`format` binary decode). No open note covers non-UTF-8 **JSON**
`--from` decode failures.

**Resolved 2026-09-19** — undecodable inputs are reported as usage errors naming the path, byte offset, and attempted encoding, shipped in `e0abb312` (`cli`, w1/m26/t003) and closed out with the milestone in `5caa2189`. Re-ran this note's repro at HEAD; both fixtures now exit **2** under a `usage` envelope rather than exit 1 under `validation`, and the raw `codec can't decode` wording is gone:

- UTF-16 → `Cannot decode 'utf16.json' as UTF-8: invalid start byte at byte 0. Re-save the file as UTF-8 and retry.`
- Latin-1 → the same shape, `invalid continuation byte at byte 38`.

The UTF-8 control still exits 0. The fix went further than this note asked: rather than a fixed message, the error carries the byte offset, and the same treatment covers the ledger, `format`, and CSV read paths. Regression coverage lives in `cli/tests/test_input_feedback.py` (`test_non_utf8_json_input_reports_path_offset_and_encoding`, plus the sibling ledger and `format` cases).
