# Interactive query output can overwrite included settings files with no dated entries

**Major · 35–50m · cli · A1.** The `.output` guard misses an included file
containing only options/comments, truncates it, and writes a query result over
it. The next ledger load fails. The ordinary one-shot `--output` guard correctly
refuses the same destination.

Found 2026-09-21 at HEAD `358b17ce`, checkout `bea 0.3.0`, Python 3.13.0,
macOS 26.5.1 arm64; executable `cli/.venv/bin/bea`. Reproduced twice with
fresh synthetic split ledgers through real PTY subprocesses. No user ledger
was used or changed.

## Reproduce

Create three sibling files in a disposable directory. `main.bean`:

```beancount
include "settings.bean"
include "accounts.bean"
2026-01-02 * "Lunch"
  Assets:Cash -10 USD
  Expenses:Food
```

`settings.bean`:

```beancount
; synthetic settings to preserve
option "operating_currency" "USD"
```

`accounts.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

`bea --json --file /absolute/main.bean check` succeeds. The one-shot control:

```sh
bea --file /absolute/main.bean query \
  'SELECT 73 AS sentinel LIMIT 1' --output /absolute/settings.bean
```

exits **2**, naming the included file and preserving every byte. Next run
`bea --file /absolute/main.bean query` in a terminal and enter:

```text
.output /absolute/accounts.bean
.output /absolute/settings.bean
SELECT 73 AS sentinel LIMIT 1
.output
.exit
```

The first command prints a refusal on stderr and preserves `accounts.bean`.
The second silently opens/truncates `settings.bean`. After the SELECT and
normal exit **0**, settings contains `se\n--\n73\n` instead of its original
comment and option. (`se` is the current interactive renderer's narrow header.)
The root and accounts hashes are unchanged; the settings hash changes.
A fresh JSON `check` exits **1** with `settings.bean:1: Invalid token: 'se'`.

Expected: `.output` refuses every loaded source file before opening it,
including files with only options, comments, include directives, or no entries.
A refusal leaves all files byte-identical and keeps the session's current
output stream usable. External export destinations remain writable.

## Cause and bounded fix

`cli/src/bea_engine/query.py:140` `_loaded_files` claims to return the include
closure but constructs `[root]` plus `entry.meta.filename` from the entries
table. Options/comments do not produce entries, so `settings.bean` is absent.
`_find_alias` at line 170 consequently returns no match, and `PreciseShell`
`do_output` at line 242 opens it with `"w"`.

Use the loader's actual file closure as the protection set, retaining root
and same-inode/symlink handling. Installed Beancount `loader.py:525` stores
`sorted(filenames_seen)` in `options_map["include"]`; this is available on
the connection, and `bea_engine/managed_load.py:315` already remaps those
filenames back to original source paths. Verify that representation while
implementing rather than inferring membership only from dated entries.

Caller search: `_loaded_files` feeds `_find_alias`, which is used by both
`_refuse_alias` and interactive `do_output`. The frontend's
`cli/src/cli/output.py:235` `refuse_ledger_alias` independently walks includes,
which explains the working one-shot control. Keep that protection. Add an
integration regression with an option-only child and a working external
destination, plus the existing root/dated-include controls. CLI-only; no API
changes are needed.

Include-only containers, truly empty files, hard-link/symlink variants and
other platforms are source-indicated but not newly exercised here. This
report claims observed destruction only of the synthetic option-only file.

---

**Resolved 2026-09-21** — interactive `.output` now refuses every file the
query reads, including children that carry no entries.

`_loaded_files` claimed to return the include closure but built it from
`entries[].meta.filename`. A child holding only `option` lines, comments or
further includes produces no entries at all, so it was absent from the
protection set, `_find_alias` found no match, and `do_output` opened it with
`"w"`.

It now reads the loader's own closure from `options["include"]` — confirmed
against the fixture to list all three files where the entry-derived set listed
two. Entry filenames are still folded in as a fallback for a connection
carrying no options, so nothing that was protected before can become
unprotected.

Verified on the note's fixture: `.output` against `settings.bean`,
`accounts.bean` and the root are all refused with every file byte-identical,
`bea check` still exits 0 afterwards, an external destination is still
writable, and the session keeps its output stream after a refusal.

Regression coverage is `cli/tests/test_output_protects_entryless_includes.py`,
driving a real PTY. It adds a file the note only listed as source-indicated
rather than exercised: a child with **no entries and no options at all**, just
a comment — the sharpest case for an entry-derived guard. Reverting the fix
fails exactly the two entry-less targets plus the ledger-still-loads and
session-recovery tests, while the entry-bearing files and the one-shot control
pass either way. `cd cli && make check-all` passes (1831 tests).

The one-shot `--output` guard in `cli/src/cli/output.py` walks includes
independently and was always correct; it is untouched and pinned as a control,
as the note asked.

Unverified, as in the note: hard-link and symlink variants of an entry-less
include, and other platforms. `_same_file` compares by inode, so those are
expected to hold, but they were not run.
