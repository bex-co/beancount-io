# `bea import` turns an already-imported row into a blocking "conflict" once the user has cleaned up its payee, narration or date

**Severity:** major. **Estimate:** 45–60 minutes. **Owner:** cli (engine
import). **A1/A2:** the documented loop is import → review the `!` queue →
tidy the entry → import the next statement. After any payee/narration
cleanup, the next overlapping statement cannot be applied at all: `--apply`
exits 4, writes nothing (the genuinely new rows are held back too), and the
suggested remedy is to undo the user's edit. This breaks the normative
`import-id` convention (`skills/.claude/skills/beancount-import/references/dedup.md`):
an `import-id` hit is "already imported … mechanical — no user decision
needed", and the hash deliberately uses the raw bank description "because
payee-cleanup rules may improve over time and must not change hashes".

Found 2026-09-25 by CLI QA (`qa-find-bugs-cli`) against `main` HEAD
`8cd9732b`, `uv run bea` 0.3.0, Darwin 25.5.0 arm64, isolated
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed. Synthetic ledger only.

## Repro

```sh
cat > main.bean <<'B'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Groceries USD
2026-01-01 open Expenses:Uncategorized USD
B
printf 'Date,Payee,Narration,Amount\n2026-02-02,Whole Foods,groceries,-20.00\n' > jan.csv
bea --file "$PWD/main.bean" import jan.csv --account Assets:Checking --apply   # exit 0, writes import-id csv:sha256:80941c97f55fc75c
# the user reviews and tidies the entry (keeps the import-id line):
sed -i '' 's/! "Whole Foods" "groceries"/* "Whole Foods Market" "groceries"/' main.bean
printf 'Date,Payee,Narration,Amount\n2026-02-02,Whole Foods,groceries,-20.00\n2026-02-10,Cafe,coffee,-3.00\n' > feb.csv
bea --file "$PWD/main.bean" import feb.csv --account Assets:Checking --apply --duplicates skip
echo exit=$?   # exit=4, file byte-identical, the Cafe row is not written
```

stderr: `Error: Import needs review; nothing was written. A stable ID already
matches a ledger entry with different data — edit or remove that entry,
change the bank ID, or drop the row.` / `Row 1 (conflict): Stable ID matches
an entry with different transaction data.` The preview shows row 1 as
`conflict` although its `csv:sha256` id is in the ledger.

Changing only the counter-account and flag (categorizing) is fine — row 1 is
`duplicate`. Editing the payee, the narration, or the date each produces the
conflict. A bank-ID row (`--csv …,id=Id`) whose ledger payee/narration was
tidied behaves the same.

## Root cause

`cli/src/bea_engine/importing.py` ~243–262: every ID hit is compared with
`_fingerprint(found, account)` (~455–472), which is `(date, payee,
narration, source amounts)` read from the **current ledger entry**. Any
difference marks the row `conflict`. For a `csv:sha256` id the hash already
covers date, exact source amount, raw description and account, so an equal
id proves the same source row; the only possible difference is the user's
own edit. For native ids the payee/narration comparison has the same effect
after cleanup.

## Fix

- A `csv:sha256` (content hash) id hit is always `duplicate`; never compare
  the ledger entry's mutable text against it.
- For native ids, detect genuine ID reuse from bank-owned facts only — the
  source-account amount(s) and, at most, the date — not payee/narration,
  which the convention expects the user (or payee-cleanup rules) to change.
- Keep the w3/m45 content check for lookup-only legacy digests unchanged.

## Acceptance

- The repro exits 0, writes only the Cafe row, and previews row 1 as
  `duplicate`; same with a tidied bank-ID row.
- A native id reused with a different source amount is still `conflict`.
- Regression tests for both hash and native ids with edited payee,
  narration and date.

## Dedupe

Searched `.pm/**` for fingerprint, conflict, payee cleanup, "different
data": w3/383 (tallies omit conflicts), w3/326 (conflict hint), w3/377
(NFC split), w3/m45 (reordered amounts becoming conflicts) are all done and
cover different inputs; none covers user-edited entries. No open item.
