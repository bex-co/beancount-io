# Keep confirmation dialog actions above the keyboard

Severity: minor. Estimate: 35–50m. Package: mobile. A2: users can read and cancel text-confirmation dialogs while editing the required input.

Environment: production server, authenticated QA, iPhone17e/iOS26.5, English/System-light, ordinary content_size large; HEAD f1965988/mobile7538fb0d, native1.20260906.47. No ledger or account mutation submitted.

Repro:
1. Open Settings → Delete Account. The first native alert's Delete Account action only opens a second text-confirmation modal; source verified before exercising it. Leave the required phrase absent and enter the deliberately invalid text `qa-cancel-only` instead.
2. The software keyboard opens with its prediction panel. The modal remains centered in the full screen: the keyboard covers the bottom of its Cancel / disabled Delete Account action row, clipping the button area and lower edge of the labels.
3. Initial PID20830 (Settings reached by inspected internal route) and fresh PID23643 (actual Home drawer → Settings) reproduce. Each native input test executed one passing test and verified the invalid value. No valid confirmation phrase was entered or second-stage delete action tapped.
4. Press keyboard Return: this only dismisses the keyboard. The unchanged invalid-text modal now shows its complete action row. Cancel closes it and returns to Settings. Cancel also worked by tapping its exposed upper portion with the keyboard present in the initial run; this is partial occlusion, not an inability to escape or a deletion bypass.

Expected: the focused input and complete action row remain visible above the keyboard/prediction panel. Actual: the modal does not adjust its position or available height for that panel. Native metadata records Cancel at y480,height47.33 and Delete Account disabled. The native Keyboard element frame starts at553 and excludes the visibly higher prediction panel; use the inspected screenshots for the overlap, not subtraction of those two AX frames. An earlier pre-focus capture had no visible keyboard and is not failure evidence.

Root cause: mobile/src/components/text-input-modal/index.tsx centers a full-screen overlay (22–37) around a content-sized modal. The render tree has no keyboard avoidance/inset handling or scrollable height constraint; its autoFocus TextInput and horizontal action row remain in the full-screen center. Opening/focusing and invalid-input validation are local state; no API data is needed to reproduce this layout.

Fix: size and position the dialog against the visible area above the software keyboard, allowing content to scroll on short/enlarged-text layouts while keeping input and actions reachable. Preserve the current no-keyboard geometry, outside-tap/Cancel dismissal, per-open input reset, disabled invalid confirmation, and caller validation. Return must not begin submitting destructive actions as a side effect of this repair. Add meaningful keyboard-layout coverage and verify native focus → invalid text → keyboard dismissal → Cancel at ordinary and enlarged text sizes.

Blast radius: two production TextInputModal callers: Settings account confirmation in screens/setting/main-content.tsx:287 and Files Create File in screens/ledger-file-browser-screen/index.tsx:610. Only Settings was exercised; file creation, valid confirmation and actual deletion remain unverified and were not submitted. No dependencies/API/cross-package imports needed. Android, physical devices, alternate keyboards/locales, enlarged text and patched behavior remain unverified.
