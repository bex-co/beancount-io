# `bea query` `FROM accounts` runs against `postings`, not the accounts table `.describe` documents

**Severity:** major. **Estimate:** 1–2 hours. **Owner:** cli (beanquery
surface). **A1:** agents that trust `.describe accounts` (columns `account`,
`open`, `close`) or treat `FROM accounts` as the open/close directory get
posting rows instead; asking for the documented columns fails with “column
open not found in table **postings**”.

Found 2026-09-15 by continuous CLI QA against `main`, HEAD `5ffe65d9`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only (7 open directives, 10 postings).

## Repro

```sh
bea --file main.bean query '.describe accounts'
# table accounts: account (str), open (open), close (close)

bea --json --file main.bean query "SELECT * FROM accounts LIMIT 3"
# columns: date, flag, payee, narration, position  ← postings shape
# rows: Opening / Paycheck postings, not open directives

bea --json --file main.bean query "SELECT count(*) FROM accounts"
# [[10]]  — same as:
bea --json --file main.bean query "SELECT count(*) FROM postings"
# [[10]]
# bea list open → 7 opens (not 10)

bea --json --file main.bean query "SELECT account, open, close FROM accounts LIMIT 5"
# exit 2
# column "open" not found in table "postings"
# Columns in postings: account, date, flag, payee, …

# quoting forces the real accounts table:
bea --json --file main.bean query 'SELECT account, open, close FROM "accounts"'
# exit 0 — 7 rows with open/close objects (matches bea list open)
# count(*) FROM "accounts" → 7; unquoted FROM accounts → 10 (postings)
```

Working control: `SELECT * FROM prices` / `FROM entries` match their
`.describe` schemas. Bare `bea list open` lists the seven opens.

## Expected

`FROM accounts` should use the accounts table `.describe` advertises (one row
per account with open/close), or discovery must not claim that schema.
Documented columns must be selectable.

## Actual

Name resolution binds unquoted `accounts` to the postings relation (likely
because postings has an `accounts` column / default-table parse path). Quoted
`"accounts"` selects the real table. Discovery and unquoted execution disagree;
the failure text admits the effective table is `postings`.

Same class (unquoted `FROM <postings-column>`): `FROM currency|weight|id|type|
year|month|day` returns `count(*)=10` (postings); `FROM balance` errors with
“Use explicit is_empty() method instead.” Real tables whose names do not collide
(`prices`, `notes`, …) work unquoted.

Likely beanquery identifier/default-table collision in the managed engine; bea
owns the agent-facing discovery story and error wrapping.

## Fix

Make `FROM accounts` bind to the accounts table env (or rename/disambiguate so
`accounts` cannot mean postings). Align `.describe accounts` with whatever
SELECT actually runs. Regression: `SELECT account, open, close FROM accounts`
returns open/close metadata; `count(*)` equals distinct opens (or documented
account rows), not posting count; `FROM postings` unchanged.

## Dedupe

Related discovery footgun: w3/246 (`FROM balances` syntax error). This ticket
is the `accounts`→`postings` misbind (SELECT runs, wrong table). Update w3/246’s
“SELECT account FROM accounts succeeds” control — that query returns posting
accounts, not the accounts directory.

## Extension (2026-09-16 continuous CLI QA, HEAD `b9d019c8`)

Interactive `.parse` shows the misbind is a **parser** shape, not only runtime
name lookup:

```text
.parse SELECT account FROM accounts
  from-clause: (from expression: (column name: 'accounts'))   ← column

.parse SELECT account FROM "accounts"
  from-clause: (table name: 'accounts')                     ← table

.parse SELECT account FROM postings
  from-clause: (from expression: (column name: 'postings')) ← also column!
```

So unquoted `FROM <ident>` is parsed as a column expression; execution then
falls through to the default postings relation (hence `FROM accounts` and
`FROM postings` both yield 10 posting rows). Quoted `"accounts"` is the only
shape that builds a real `table` node. Fix/regression should cover the AST
(`.parse`) as well as SELECT results.
