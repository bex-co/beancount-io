# Smart Import accepts truncated numeric prefixes as valid transaction amounts

**Promoted to [w3/m19](./m19/README.md).** That milestone is the sole
implementation queue and estimate for this finding and its independently
reproduced error-loss extension. This note retains the original evidence.

Severity: **major**. Owning package: **dashboard**. The original scope is
complete-token amount validation and shared conversion in upload/edit; m19 also
preserves rejected raw input, whole-row validity and the configuration boundary.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, System/light;
authenticated QA reader of public `open_ledger/crypto-example`. Desktop
1440×1000 and fresh narrow 390×844. Local `a315c273` and fetched
`origin/main cc3f4c2f` have unchanged implicated importer files; deployed SHA
unverified. No actual transaction submission was performed.

1. Open `/ledger/open_ledger/crypto-example/import?lang=en` and select this CSV:

   ```csv
   Date,Payee,Description,Amount
   2025-12-01,QA Amount Control,Whole decimal,-1234.56
   2025-12-02,QA Amount Grouping,Quoted thousands,"-1,234.56"
   2025-12-03,QA Amount Suffix,Unexpected suffix,12oops
   ```

2. Preview says **3 Valid**, with amounts **-1234.56, -1, 12** and no error.
   It has silently discarded the suffix of both problematic tokens. A fresh
   narrow upload reproduces the same values and validity count.
3. Edit the second preview amount back to **-1,234.56** and press Enter. The
   cell now displays that entire string, still with **3 Valid** and no error.
4. **Continue to Configure** shows **-1.00** for that row. The edited preview
   and configuration therefore disagree on the number; the input was already
   truncated before any transaction submission.

Expected: validate the entire amount token. `12oops` must be invalid. The
quoted grouped amount must either be deliberately parsed as **-1234.56** under
a documented grouping grammar or be rejected clearly; it must never silently
become **-1**. The minimal repair may retain the documented plain signed-decimal
format and reject grouping. Supporting locale/currency-specific formats is not
required by this finding.

Working controls: the complete `-1234.56` token stays correct through Preview
and Configure. Replacing the suffix row with **abc** produces **2 Valid /
1 Errors** and “Amount must be a valid number”; configuration correctly skips
that invalid row. Continue remains enabled for the two valid rows, consistent
with the page's explicit skip warning. A source probe also verifies legitimate
zero and whitespace-trimmed `99.9`, while Infinity is rejected.

Root cause: `dashboard/src/features/importer/utils/csv-validator.ts:60–78`
calls **parseFloat(trimmed)** and only checks NaN/finite. `parseFloat` accepts a
numeric prefix, so both reproduced incomplete tokens pass validation.
`hooks/use-csv-parser.ts:127–141` stores the truncated number and counts the row
as valid. In the inline editor, `utils/row-edit-schema.ts:37–43` uses the same
permissive validator, while `editable-preview-row.tsx:65–76` independently runs
`parseFloat(value) || 0` for the workflow model. React Hook Form retains the full
display string, explaining the visible edit/configuration mismatch.

Producer/consumer trace: FileReader supplies intact CSV text; the quoted comma
is correctly handled as one field by `parseCSVLine`. The local parser returns
the three rows directly through `use-multi-stage-parser`, since it considers
them valid. `use-import-workflow` stores that result, and
`transaction-config-form.tsx:112–133` copies the numeric amount into its form.
The real source probe returns `{valid:true,amount:-1}` for `-1,234.56` and
`{valid:true,amount:12}` for `12oops`, matching both UI repeats.

This is a browser validation/conversion defect, not an API serialization error.
The monitored desktop parse made zero GraphQL requests; no AI parse, storage
upload or Import action ran. AI-parser input conversion and actual persisted
imports were not exercised. All local previews were cleared afterward.

Fix the shared validator to require a full match for its supported numeric
grammar before converting. Keep optional surrounding whitespace and legitimate
finite signed values/zero; reject trailing text, malformed exponents, multiple
decimal separators and unsupported grouping/base prefixes. Do not blindly strip
characters until a number emerges. Reuse the validated conversion result for
inline edits instead of parsing a second time. Keep rejected input available
for correction or identify it clearly in the validation error, and never allow
the invalid result's fallback zero to become a valid row.

Callers: `parseAmount` is used by the browser CSV hook and inline-row schema;
the only second conversion is EditablePreviewRow. The CSV hook is reached by
the active multi-stage upload path and FileUpload's fallback callback branch.
Preserve valid-row filtering, date/payee/description checks, row editing and
configuration behavior; no API, dependency or broad importer redesign is needed.

Acceptance: actual hook/FileReader and row-form tests cover the reproduced
tokens, complete positive/negative/fractional values, zero, whitespace, malformed
suffixes and supported exponent rules. Upload and edit must agree on validity
and the amount passed to Configure. A test that merely checks parseFloat's
known output is insufficient. Run dashboard format, lint, tests and build.

Dedupe: searched all open/completed `.pm` for CSV amounts, numeric prefixes,
parseFloat, separators and truncation. `w3/015` is multiline record splitting,
`w3/037` row identity after deletion, and `w3/035` Holdings display/export
precision. CLI import and statement-export tasks use separate parsers. History
`git log -S parseFloat` traces this conversion to `af5339de`; fetched main has
no repair. Existing validator/schema tests reject wholly nonnumeric strings but
omit numeric prefixes followed by invalid characters.
