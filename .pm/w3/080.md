# Ask has no control to stop a pending request

**Severity:** major for an in-flight Ask journey. **Owner:** dashboard.
**Estimate:** 45–60 minutes. **A2:** users can stop waiting and continue composing
without abandoning the page. This regresses the cancellation outcome completed
in `w1/m1/t004`; server-side cancellation remains outside that task's scope.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light; authenticated reader of public `open_ledger/example`.
Fresh 1440×1000 and 390×844, repeated on both `/agent` and
`/ask?mode=sandbox`. Local HEAD `a315c273`, fetched main `5b70f569`;
implicated files unchanged, deployed SHA unverified.

1. Open `/ledger/open_ledger/example/agent?lang=en` and enter
   **qa-20260908-network-control**.
2. With a browser route holding `POST /api-gateway/agent` **before transmission**,
   press Enter. The question is appended, the input clears, and input,
   attachment and send controls become disabled.
3. There is no Stop/Cancel action. Escape leaves the request pending and
   composer disabled. The same pre-response state occurs on
   `/ledger/open_ledger/example/ask?mode=sandbox&lang=en`, whose held endpoint
   is `/api-gateway/ask-agent`.
4. Repeat from fresh contexts at both widths. This is controlled latency,
   not evidence of a real server hang.
5. In separate isolated controls, call the actual mounted SDK chat instance's
   `stop()` while the request is held. The browser request becomes
   **net::ERR_ABORTED**, the input re-enables, and a new unsent draft can be
   typed. Observations completed in 157–195ms including a deliberate 150ms
   settling wait; no console error or error toast appears. This SDK diagnostic
   is not an action currently available to users.

Expected: a named, keyboard-operable cancellation action is available while
status is submitted or streaming. It aborts the browser request, retains any
partial content, communicates a stopped turn and restores the composer.
Actual: the UI disables the only composer actions until completion/failure or
navigation. This does not establish that cancelling a browser request stops
server-side model work, and no such guarantee is proposed.

Root cause: `dashboard/src/features/ai-agent/pages/agent/page.tsx:120`
destructures messages/send/status/approval from `useChat`, omitting `stop`.
Lines132 and384–393 pass loading only as `AgentChatInput.disabled`;
`agent-chat-input.tsx:226–266` disables the textarea/attachment/send controls
without rendering a cancellation action.

Pinned `@ai-sdk/react 4.0.73` exposes `stop` at
`src/use-chat.ts:246`. Pinned `ai 7.0.70`, `src/ui/chat.ts:605–610`,
aborts pending/active request controllers; `:825–830` handles AbortError as
ready rather than an error. `src/ui/http-chat-transport.ts:199` supplies that
signal to fetch. Both published packages were SHA512-integrity verified.
The [SDK chatbot documentation](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot)
also describes the Stop control. No SDK upgrade or new AbortController layer
is needed.

Wire the existing SDK action through the current page/input, preserving a named
native button and visible focus while Send is unavailable. Keep completed text,
use a localized stopped indication for an interrupted turn, restore input focus,
and prevent Stop from submitting again or generating a failure toast. Use SDK
finish/status signals rather than implementing a second stream reader.
Cover submitted and partial-stream cancellation with real SDK behavior in a
local test transport; preserve approval-required controls and permissions.
Coordinate inbox062's Send naming and 063's IME guard without conflating them.
