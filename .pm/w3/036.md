# Holdings by Currency keeps unnamed rows for fully sold assets

Severity: **minor**. Owning package: **dashboard**. Estimate: **30–45 minutes**.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, System/light;
authenticated QA reader of public `open_ledger/crypto-example`. Desktop
1440×1000 and fresh narrow 390×844. Deployed SHA unverified; local `a315c273`
and fetched `origin/main cc3f4c2f` have unchanged implicated Holdings files.

1. Open `/ledger/open_ledger/crypto-example/holdings?lang=en` and choose
   **Holdings by Currency** (desktop tab; narrow **View** combobox).
2. Results says **14 Rows**, but two rows have no units/currency name and no
   book or market value. They contain only prices **2480.00** and **520.00**,
   with zero-like display cells. A fresh narrow repeat shows the same rows.
3. Desktop **Export CSV** downloads 14 rows, including both unnamed records.
   Parsed cells are respectively `["","","2480.00","","","0"]` and
   `["","","520.00","","","0"]`.
4. Working control: default **Holdings** has 43 rows, no empty units cells, and
   no NFT or Uniswap LP rows. The same ledger's actual remaining positions are
   available and the tab/combobox transitions work.

Expected: the current-holdings view and CSV contain the **12 nonempty unit
inventories**. A remembered price alone must not keep a fully sold position as
an unnamed holding. A real holding with a missing or zero quote must remain.

The actual QueryShell request and REST query both return HTTP200 and the same
valid grouped rows, including `[{},"","2480.00",{},{},"0"]` and
`[{},"","520.00",{},{},"0"]`. A read-only diagnostic query that adds
`currency` to the same SELECT identifies them as **CRYPTOPUNK** and
**UNIV2ETHUSDC**, each with an empty units inventory. Generic BQL may correctly
return an empty historical group; current-holdings filtering belongs to its
dashboard consumer. This is not an API error or a missing price response.

Root cause: `dashboard/src/features/ledger-data/holdings/index.tsx:67–72` uses
`defaultRowsFilter` for this view. That helper at `utils.ts:130–132` ignores
column 0 and keeps a row if any later cell is nonempty. It was shaped for an
account-name-first table; here column 0 is the units inventory, and a nonzero
price keeps an otherwise empty row. `holdingsRowsFilter` at134–138 correctly
gates the default view's units at column 1, explaining the working control.

`holdings-table.tsx:61–69,77–85` applies the caller's same filter to CSV and UI;
the badge at105–107 counts that filtered set. Fix this view's predicate using
its actual units column, and apply it consistently to display/count/export.
Keep the other three caller layouts correct; do not blindly substitute a
column-1 predicate into this column-0 view. No query, API, dependency or general
table refactor is required.

Producer/serializer: ledger `ledger-shell-mappers.ts:40–55` deliberately drops
zero-net currency keys. Its `toShellCell` at164–182 and shell-result mapper
at190–200 preserve these empty inventories and valid scalar quotes. Gateway
LedgerShellService copies them to the shared GraphQL/REST/MCP shell result.
GraphQL and REST were exercised; live MCP was not. Do not change that generic
typed-result contract to suppress rows for one dashboard view.

Acceptance: both widths show 12 meaningful currency rows and the parsed CSV
contains the same rows, with neither unnamed sold group. Cover known-price and
missing-price empty groups, real positive/negative/small positions, a legitimate
zero quote and all four column layouts through the actual DatasetTable caller.
Preserve the default view's 43-row control and existing nonempty-unit values.
Run dashboard format, lint, tests and build. `w3/035` separately fixes precision;
this repair must not round units to decide whether a position exists.

Dedupe: searched all open/completed `.pm` for zero/empty/fully sold holdings,
unnamed currencies and row filtering. `w3/007` is cost aggregation, `w3/035`
precision and `w3/m18` market-price inference. History `418c17cc` specifically
intended to hide zero-balance holdings by treating null/undefined as empty, but
does not cover this nonempty-price case; its tests exercise the helper without
this real column layout. This is a coverage gap, not a proven production
regression caused by that commit. Fetched main has no repair.
