# Returning from Forgot Password loses the intended login destination

Severity: **minor**. Owner: **dashboard**. Estimate: **30–45 minutes**.
A2: a visitor can open password recovery, return to sign-in, and continue to
the ledger/report they originally requested.

Production `https://beancount.io`, 2026-09-08, Chrome152, English, light.
Fresh signed-out contexts at 1440×1000 and 390×844. Local HEAD `a315c273`;
freshly fetched main `cc3f4c2f` has no change to the implicated sources.
Deployed SHA unverified. The authenticated QA context stayed separate.

1. Open `/auth/login` with `next` set to
   `/ledger/open_ledger/crypto-example?time=2024` (URL-encode the whole value).
2. Focus **Forgot Password?** and press Enter. Wait for the **Forgot your
   password?** form to finish rendering.
3. The URL is now `/auth/forgot-password`, without `next`. Leave Email address
   empty and activate **Back to Sign in** with the keyboard.
4. Login renders at `/auth/login`, still without `next`; its Sign Up link also
   now omits the destination. Fresh desktop/narrow repeats agree.
5. Directly opening `/auth/forgot-password?next=...` preserves that value in the
   address, but its Back to Sign in link is still the bare `/auth/login`.

Expected: both standalone links carry the explicit destination through this
cancelled password-recovery detour. Actual login later takes the default-ledger
or welcome fallback when `next` is absent, as traced in
`dashboard/src/features/auth/pages/login-page/index.tsx:24–38`; the post-login
consequence was not verified through another credential submission.

Working controls: browser Back from the recovery page restores the original
login URL including the exact nested time query at both widths. Login↔Sign Up
already carries the same explicit destination. The recovery page loads normally
and Send reset link remains disabled with its email field empty. Fresh repeats
have HTTP200 initial documents, no page/console errors and no mutation attempts.
No email was entered, no reset link was sent and no password was changed.

Root cause: `dashboard/src/features/auth/components/login-form/index.tsx:105–110`
links to recovery without search, and the fallback link in
`features/auth/components/forgot-password-form/index.tsx:29–43` links back
without search. The latter is used in both the initial and successful-email
states. `routes/auth.forgot-password.tsx` also lacks a declared optional `next`
search field, unlike the login and signup routes.

Fix the standalone links and recovery route's typed search contract so `next`
survives both directions, using the existing auth-link search pattern. Preserve
`getSafeRedirectPath` at destination consumption and existing canonical-URL
behavior; this work must not turn `next` into an unrestricted external redirect.
The successful-email state's shared return link receives the same repair, but
email/OTP delivery and reset-token redirect behavior are outside this task.

Blast radius: the standalone login and forgot-password pages. The three OAuth
consent pages supply `onForgotPasswordClick` and `onBackToSignIn` callbacks to
change their own form step; those branches do not use these fallback links and
must retain their existing interaction state. They were source-traced only.
No backend, REST or MCP change is needed for this navigation-only defect.

Acceptance: keyboard Login→Forgot Password→Back to Sign in retains the exact
safe nested destination at both widths, including a directly supplied recovery
URL. A no-next entry keeps the normal login fallback. Browser Back and
Login↔Sign Up still work, the reset request is not triggered by cancellation,
and the callback-based consent forms remain in their own flow. Add a focused
router/form navigation regression; do not send real reset emails for this check.

Dedupe: searched open/completed board records for recovery, next, cancellation
and return destinations, and scanned all open milestone summaries. 029 loses
the Settings subpage before constructing next; here a correct next already
exists and is discarded by different links. `c4e65a5b` repaired Login↔Sign Up,
but left these links unchanged. Their targeted history is `af5339de` for the
login link and `62146c19` for the extracted shared recovery return link.

The legacy `/forgot-password` alias separately reaches the marketing site's
404 in production; its edge-routing owner is unverified and it is not evidence
for this source repair. Canonical routes above were rerun independently.
Other browsers/locales, successful reset/email states and patched behavior
remain unverified. Temporary guest contexts and unused API guards were closed.
