# Let search fields grow enough to display enlarged typed text

Severity: minor. Estimate: 45–60m. Package: mobile. A2: users who need the largest text can read and revise the query they enter.

Environment: production API, authenticated QA session, public open_ledger/freelancer-invoicing; HEAD f1965988/mobile source7538fb0d, client1.20260906.47, iPhone17e/iOS26.5, English/light appearance.

Repro:
1. Set simulator content_size to accessibility-extra-extra-extra-large and relaunch. Open Transactions; the empty Search placeholder fits visibly inside its rounded field.
2. Focus Search and type IRS. Wait until native field.value is exactly IRS. The entered glyphs are substantially taller than the placeholder and their top/bottom are cut by the fixed-height input. The native clear button also exceeds the visible field vertically.
3. Repeat after another fresh launch (initial PID2990, fresh3298), using the actual Transactions tab. The same clipping reproduces. Native inspection records the populated TextField at x52.33,y148.33,width285.33,height35.33 points, with value IRS intact.
4. Relaunch with accessibility-large (PID3734) and type the same query: letters fit. Repeat at default large (PID3965): letters and clear button fit with normal spacing. Restore default large, clear search and dismiss the keyboard.

Expected: typed query text and its clear action fit inside the search control at the supported text setting. Actual: the field remains approximately36 points tall while the entered text scales past its height. This is vertical clipping of a short three-character query, not intentional horizontal scrolling of a long search. Placeholder-only inspection misses it.

Working/API controls: all runs filter correctly to the two IRS entries (June15 $4,150; April15 $4,500). The read-only quoted IRS journal query returns those two entries; the raw input value stays complete. The result rows' IRS text scales visibly without clipping. The smaller text controls fit. No change to parsing or result filtering is needed.

Root cause: mobile/src/components/search-bar/index.tsx:19–43 fixes the field height at SEARCH_BAR_HEIGHT=36 and nests the scaling TextInput inside it; there is no content-size-dependent height. The native measurement and screenshots establish the resulting constraint. The exact native placeholder-versus-entered-text sizing internals were not established and are not necessary to fix the fixed-height layout.

Fix: make the shared search field accommodate the scaled input's line height and native clear control, retaining36 as an appropriate default/minimum rather than a universal fixed height. Keep vertical padding/alignment and search/filter hit targets coherent without disabling the user's font scaling. Check Transactions, Merchants and Account Picker callers, including the Merchant sort button and Account Picker loading placeholder that use SEARCH_BAR_HEIGHT. Preserve ordinary-size geometry, focus, query, clear, return-key dismissal and filtering. Verify empty→typed→cleared at maximum size plus the two working control sizes; include meaningful layout/render regression coverage.

Blast radius: SearchBar has three production consumers: TransactionsHeader, MerchantsDirectory and AccountPickerScreen. All three consumers were exercised at maximum size and reproduce the clipping; ordinary-size controls fit. Discovery uses its own search implementation. No dependency or backend change needed. Android, physical devices, other locales, hardware keyboards, network/denied/expired states and patched behavior remain unverified. Bounded JS error capture empty; no writes, product code changes or shipping.
