# Journal mistakes invalid filter input for a server outage

Severity: minor. Owner: backend-cluster/backend-v2. Estimate: 45–60 minutes
using the existing error mapper and adapter regression harnesses. A2: readers
can correct a search expression instead of waiting for a nonexistent outage.

Environment: production https://beancount.io, Chrome 152, authenticated QA
public reader, synthetic `open_ledger/example`, English/System light. Fresh
desktop 1440×1000 and narrow 390×844 reproductions on 2026-09-08. Local source
HEAD a315c273; fetched origin/main cc3f4c2f fixes entry metadata, not this path.
The deployed build is not proven identical to either checkout.

Reproduce:

1. Open `/ledger/open_ledger/example/journal?filter=%28`, the expression `(`.
2. Wait for the request to settle, then reload. Both show zero results and
   “Error loading journal entries: Something went wrong on our end. Please try
   again later.” Narrow fresh navigation repeats the error.
3. At desktop, Clear all immediately restores the populated 1044-entry journal.
4. The authenticated GraphQL journal read with `filter: "("` returns HTTP 200,
   `INTERNAL_SERVER_ERROR`, “Internal server error”. REST
   `/api-gateway/v1/ledgers/open_ledger/example/journal?filter=%28&limit=1`
   returns HTTP 500 with the same code. Account Journal for
   `Income:US:Hoogle:Salary` also returns GraphQL `INTERNAL_SERVER_ERROR`.
5. Working controls: the same invalid expression on `getLedgerBalanceSheet`
   returns `BAD_USER_INPUT`, “Unexpected end of filter”. Valid journal expression
   `payee:"Hoogle"` returns 71 entries.

Expected: malformed user filters retain the input-error category through the
gateway, allowing the dashboard's existing invalid-input guidance to appear.
Do not relabel actual network/service failures as invalid input.

Root cause: ledger `src/features/ledger/service/ledger-journal-service.ts:430`
and `:468` translate filter parser failures into `BadUserInputError`; its error
middleware serializes that category as HTTP 400. That first-hop status is
source-traced, not directly observed against the production ledger service.
Gateway `src/foundation/fava/api-client.ts:69` rejects non-2xx responses as
`FavaApiError`. Gateway `src/features/ledger/service/ledger-journal-service.ts:159`
and `:260` await the raw client promise, bypassing the existing
`src/foundation/fava/unwrap-response.ts` mapper. Their later success-envelope
check cannot catch a rejected promise. GraphQL/REST error boundaries recognize
domain errors and mask the unrecognized error as internal failure. Finance reads
already use the shared unwrap helper, explaining the Balance Sheet control.

Fix the journal read family to reuse `unwrapFavaResponse` without a custom
error factory that overrides its category mapping. Audit its plaintext and
context reads (`:231`, `:199`) for the same direct-await pattern; preserve their
success payloads and authorization checks. No new API fields are required.
Keep the dashboard's localized error mapping; no parser duplication or blanket
catch returning empty data. Writes were not exercised and are outside this note.

Acceptance: malformed filter/time input reaches GraphQL as `BAD_USER_INPUT`,
REST as HTTP 400, and MCP as its standard error result; valid journal reads,
empty results, not-found/denied access and real upstream failures retain their
distinct behavior. Exercise the shared service through actual REST, GraphQL and
MCP adapters with the existing harness; include a regression that would fail
when the raw Fava error escapes. Rerun fresh desktop/narrow correction and clear
flows. Preserve the repository's zero-gap parity baseline rather than weakening
or regenerating it to hide a failure.

Dedupe: searched all `.pm` open/done records for invalid filters, bad input and
error categories. `w3/m13` adds account-journal selectors; `w3/m14` adds filtered
statistics and neither covers this mapping gap. Commit b4dc8e09 introduced the
shared category mapper but did not convert this service. Targeted history has no
later journal-read mapping fix; this is an uncovered caller, not deployment lag.

MCP journal resources use the same `JOURNAL_READS` descriptors through
`src/features/ai-agent/api/mcp-resources.ts:667`; verify the resource error
adapter rather than substituting an unrelated MCP tool result.

Unverified: live MCP needs a separate OAuth/API-key credential; the browser
session is deliberately refused there, so MCP impact is source-traced only.
Plaintext/context error cases, expired sessions and genuine service outages
were not exercised live. No product code changes or shipping included.
