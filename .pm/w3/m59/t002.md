## Objective

Teach the backend pure builder and the REST, GraphQL, and MCP create and preview operations to accept `setup.modules` with ADR021's rules.

## Context

- Builder: `backend-cluster/backend-v2/src/features/ledger/setup/build-ledger.ts`; it currently rejects any account outside the preset (`not part of preset`).
- Schemas: `ledgerCreateInput` (REST), `CreateLedgerInput` (GraphQL), and the MCP `createLedger`/`previewLedgerSetup` tool inputs must enumerate module IDs; follow the backend parity workflow and keep `surface-parity` gaps at zero.
- ADR021: modules only with `personal@1`; unknown or repeated modules fail identically; output independent of order.

## Steps

1. Add `modules` (and the rental property name) to the setup type and validation.
2. Open each module's accounts after the preset's, sorted deterministically; allow first accounts to name selected module accounts.
3. Expose the field on all three create and preview bindings; regenerate `docs/openapi/v1.json` and the generated clients.
4. Extend the cross-surface contract test to drive one module specification through REST, GraphQL, and MCP.

## Files

- `backend-cluster/backend-v2/src/features/ledger/setup/`
- `backend-cluster/backend-v2/src/features/ledger/api/`
- `backend-cluster/backend-v2/src/features/ai-agent/api/mcp-tools.ts`
- `backend-cluster/backend-v2/docs/openapi/v1.json`

## Acceptance criteria

- [ ] The same module specification creates identical files through REST, GraphQL, and MCP.
- [ ] Modules with a non-personal preset, unknown IDs, or repeats are refused identically and create nothing.
- [ ] Omitting `modules` leaves `personal@1` output byte-identical.
- [ ] `yarn typecheck` and `yarn test` (including the parity gate) pass.

## Out of scope

- Adding modules to an existing ledger after creation (a later account-group capability).
- CLI and Python engine (t003).
