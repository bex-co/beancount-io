# Star remains selected after the server reports failure

**Minor · dashboard · 45–60m.** A2/A3: saving a public example should show
whether the action succeeded and offer the same action again when it failed.

## Reproduce with a controlled failure

Production UI at https://beancount.io/ledger/open_ledger/example?lang=en:

1. Start with **Star** and the actual ledger status isStarred:false.
2. Click Star. Intercept StarLedger before transport and fulfill it with HTTP200:
   `{"data":{"starLedger":{"__typename":"StarLedgerResponse","success":false,"isStarred":false,"message":"Failed to star ledger"}}}`.
3. Wait for both the error toast and automatic GetLedger refetch. The real
   refetch returns HTTP200, isStarred:false, but the enabled button stays
   **Starred**, with a filled yellow star beside the failure notification.
4. Click that button again: it prepares **UnstarLedger**, rather than retrying
   StarLedger. Abort this request before transport.
5. Reload: the actual saved state renders **Star** again.

This is a schema-valid failure injected into the live client, not an observed
production backend outage. The backend already returns this exact failure
shape when its Gitea write fails. No tested social write reached production.

Repeated in initial and fresh Chrome 152.0.7977.77 contexts at 1440×1000 and
390×844 on 2026-09-10, English/light, authenticated QA GROWTH, public synthetic
example with pull:true/push:false/admin:false. In the fresh repeat both initial
documents and refetches return200; business-failure phases have no page or
console errors. Subsequent transport-abort controls emit expected ERR_FAILED
console messages, recover **Star**, and prepare **StarLedger** on retry.
An initial fulfilled-failure Unfollow control also retains Unfollow correctly.

## Root cause and scoped fix

dashboard/src/features/reports/overview/components/star-button/index.tsx:47–60
optimistically toggles localIsStarred, discards the fulfilled mutation result,
and rolls back only when the promise throws. The hooks' onCompleted callbacks
in use-star-ledger.ts:11–21 and use-unstar-ledger.ts report success:false as a
toast without rejecting. Installed Apollo4.1.3 useMutation.js:88–115 correctly
returns the fulfilled GraphQL result: a domain success flag is not an exception.

The prop synchronization at index.tsx:33–36 runs only when initialIsStarred
changes. Refetch returning false again cannot reset the local true state.
One production StarButton caller exists, features/reports/overview/index.tsx:324;
both mutation hooks have that component as their only production caller.

The response is real API contract, not an invented error envelope:
backend-v2 src/features/ledger/workflow/ledger-workflow.ts:890–896 returns
success:false/isStarred:false after a failed star; :938–944 has the corresponding
unstar failure. api/resolvers/ledger-resolver.mutation.ts:138–159 delegates
unchanged, and ledger-resolver.types.ts:295–303 exposes the fields.

Handle fulfilled failure explicitly in the shared StarButton action. Retain or
restore the last confirmed state when success is false, so the next click
retries the original action. Commit a changed state only for a confirmed
success; preserve transport-error rollback, pending protection and refetch.
The FollowButton's success check provides a working local pattern. Keep the
existing backend contract and authorization; no REST/GraphQL/MCP change is needed.

Acceptance: the exact injected Star failure keeps Star and an error notification
after the false refetch, and retry prepares StarLedger. Cover the symmetric
Unstar failure in an isolated initially-starred fixture, plus confirmed success,
thrown failure and unchanged refetch props. Assert the rendered button and next
operation together. Current hook tests check notifications and callback behavior,
but do not mount the optimistic button, so their assertions miss this state error.
