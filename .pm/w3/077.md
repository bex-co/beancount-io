# Opening another BQL history query cancels the first

Severity: **major**. Package: **dashboard**. Estimate: **45–60m**.
A1/A2: users can inspect multiple saved BQL queries without turning a valid
pending read into a persistent error.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English/light,
authenticated reader of public `open_ledger/example`. Fresh 1440×1000 and
390×844 repeats. Local `a315c273`; latest fetched main `5b70f569` has no
implicated source/dependency change. Deployed SHA unverified.
This is a controlled read-delay reproduction, not a naturally observed outage.
No response or error is fabricated, and no ledger mutation is attempted.

1. Open `/ledger/open_ledger/example/query?lang=en` with the URL-encoded query
   **B**: `SELECT account FROM accounts ORDER BY account LIMIT 3`. Wait for
   its real three-row result; this saves B to local query history.
2. Reload the query page with the URL-encoded query **A**:
   `SELECT account FROM accounts ORDER BY account LIMIT 2`. Hold only A's
   QueryShell request before transmission. Its expanded card shows Executing.
3. While A is pending, click B's history summary. B executes and correctly
   shows three rows. A's request fails with **net::ERR_ABORTED**, before the
   test releases its held route. The application caused this cancellation.
4. Reopen A's history card. It shows **Something went wrong. Please try again.**
   with no result or CSV action. Releasing the held route cannot recover it.
   Collapse/reopen again: the same error remains and no query is retried.
5. Reload the unchanged A bookmark without the delay: HTTP 200, **2 rows**,
   `Assets:US:BofA` and `Assets:US:BofA:Checking`, with a CSV action.

Working controls: holding A for 500ms and then releasing it without starting B
returns the same correct two rows at both widths. Thus delay alone does not
cause the failure. B returns HTTP 200/three rows during the overlap. The public
REST POST `/api-gateway/v1/ledgers/open_ledger/example/query`, body `{query}`,
independently returns the correct two/three rows for A/B, without errors.

Expected: both deliberately started same-ledger history reads can complete
and retain their own result. Opening B must not invalidate A. Keep the existing
per-query loading/result cache and actual API errors; do not make the error
invisible or serialize all unrelated reads as a workaround.

Root: `dashboard/src/features/bql/pages/index.tsx:53–81` shares one
useLazyQuery execution function for every history card and awaits its promise
without retaining it. History opening reaches that function through156–158 and
`components/query-result-card.tsx:45–50`. The page's catch at100–106 caches the
abort as A's error. The card's `!error` toggle condition prevents a retry, and
its alert at179–183 renders the generic safe error text.

Pinned, registry-integrity-verified **@apollo/client 4.1.3** explains the
mechanism: `react/hooks/useLazyQuery.js:103–116` reobserves one ObservableQuery.
`core/ObservableQuery.js:1004–1009` unsubscribes the previous link subscription;
its unfinished promise rejects with AbortError at1377–1387. The same pinned
implementation provides promise.retain at1021–1025, keeping that specific
operation subscribed until it settles. This is documented in the
[Apollo query retention contract](https://www.apollographql.com/docs/react/data/queries#retaining-query-results).
The dashboard CSR factory applies no custom fetch/error policy.

Fix this BQL caller to retain each intentionally independent execution before
awaiting it, preserving its typed variables, cache/error behavior and one
loading entry per query. Coordinate with [055](./055.md): keeping a request
alive must not let an old ledger's completion populate a new ledger's results.
Keep that route's ledger boundary and m12's editor/URL execution work intact.
No dependency update, shared Apollo override, backend or schema change is needed.

Acceptance: delay A, open B, allow both to settle in either order and obtain
the correct two/three-row cards and matching exports without a false error or
duplicate execution. Verify delay alone, a real failed read, reopening cached
results, removal of a pending history item and the existing ledger-switch
boundary. Use a real Apollo client with controlled link completion in an
integration regression; a mocked useLazyQuery promise cannot prove retention.
Repeat the desktop/narrow journey and run dashboard gates. Patched completion
orders, removal and export contents are acceptance work, not results claimed here.

responses establish valid queries. The cancelled A attempt never reaches that
