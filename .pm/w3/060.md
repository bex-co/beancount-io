# A fresh guest is incorrectly told their session has expired

Severity: **minor**. Owner: **dashboard**. Estimate: **35–50 minutes**.
A2: a first-time visitor receives an accurate sign-in prompt when opening an
authenticated feature, without being told a nonexistent session has expired.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, light.
Fresh isolated guest contexts at 1440×1000 and 390×844; each was verified to
have zero site cookies before navigation. Local HEAD `a315c273`, fetched main
`cc3f4c2f`; implicated source is unchanged. Deployed SHA unverified.

1. In a fresh guest context open
   `/ledger/open_ledger/budgeting-envelopes/commits`.
2. The page redirects to `/auth/login` with the exact commit-history path in
   `next` and `reason=expired`.
3. Login displays **Your session has expired. Please log in again.** The
   visitor has never signed in in this context. Both fresh widths reproduce it.

Expected: a neutral sign-in-required prompt. Commit history intentionally
requires authentication even for a public ledger; this task does not remove
that gate. Missing credentials and an expired session are not the same fact.

The actual ListCommits response has HTTP200. An independent native-fetch
GraphQL control, read without triggering another client navigation, returns
`UNAUTHENTICATED` with no data. That code does not assert token expiry.
`backend-cluster/backend-v2/src/features/gitea/commits/api/commits-resolver.ts:11–18`
explicitly applies the authenticated guard. The monitored clean repeat has no
page or console error; the incorrect explanation is generated by the dashboard.

Working controls: in the same guest contexts, opening Settings/API keys goes
to login without an expiry alert. Its separate next-path omission remains029.
With the existing QA session, this public commit history/detail loads at both
widths (m22 evidence). No credentials were entered for the guest checks and
no session was expired, revoked or modified to manufacture the failure.

Root cause: `dashboard/src/common/apollo/links/auth-error-link.ts:73–83`
maps every qualifying generic `UNAUTHENTICATED` response to `reason=expired`.
The client factory installs that link at `common/apollo/factory.client.ts:16`.
`features/auth/pages/login-page/index.tsx:57–61` renders the expiry-specific
message solely from that reason. The root ErrorPage and LedgerRouteError also
construct expiry-labelled redirects for generic unauthenticated loader errors,
and their transitional error panels describe those errors as expired sessions.
Those loader variants are source-traced, not separately live-reproduced.

Fix the generic authentication-required presentation and redirect reason, not
credential validation. For an unclassified `UNAUTHENTICATED` error, use neutral
sign-in-required copy or the ordinary login prompt; existing localized
`common.errors.unauthenticated` already says **Please sign in to continue.**
Update the corresponding generic root/ledger error panels so they do not flash
an expiry assertion before redirecting. Reserve expiry-specific copy for an
explicitly known expiry condition; do not add credential inspection or a new
authentication-state subsystem for this copy correction.

Preserve protected-operation redirects, current next destinations, full-page
cache reset and duplicate-redirect suppression. Keep optional identity probes
and expected SignIn/OTP/refresh/logout failures excluded as they are now.
Backend, REST/MCP authentication policy, and unrelated route-state bugs are
outside this repair.

Acceptance: a fresh guest opening the public history route reaches sign-in
without an expired-session assertion, at both widths. Authenticated history
still loads; generic unauthenticated responses still require sign-in. Focused
tests cover the generic redirect/panel copy and retain the existing operation
exclusions. Any deliberately supplied true-expiry notice remains a distinct
case. Real expiry/revocation, SSR loader variants, other locales/browsers and
patched behavior remain unverified live scenarios.

Dedupe: searched open/completed board records for guest expiry and misleading
session/sign-in messages and scanned current milestones. 029/058 concern
destination loss, not this explanation. `2f982c52` deliberately exempted
optional identity probes while preserving protected-operation redirects;
retain that full behavior. Later OAuth migration/revert history does not
remove the generic expiry assumption, and fetched main has no repair.
