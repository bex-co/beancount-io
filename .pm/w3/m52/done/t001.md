## Objective

The current CLI sends `max_completion_tokens`, but the route's Zod schema strips that field. Preserve modern and legacy output caps end to end, reject an ambiguous request containing both, and give an uncapped request a modest explicit default rather than the provider's model maximum.

## Files

- `backend-cluster/backend-v2/src/features/ai-agent/api/openai-chat-completions-route.ts`
- `backend-cluster/backend-v2/src/features/llm/service/llm-service.ts`
- Backend route/service regression tests and public backend documentation

## Acceptance criteria

- The actual HTTP adapter and real service forward either cap spelling and default an omitted cap.
- Invalid or conflicting caps fail before a model call.
- Authorization, per-user quota checks, usage recording, and the documented wire-compatibility parity exceptions remain intact.
- Regressions fail before the fix; backend checks pass.

## Resolution

Shipped in `18730f77` (backend-v2). The actual HTTP adapter preserves either output-cap spelling, rejects both together and invalid values, and the real service defaults uncapped requests to `max_completion_tokens: 1500`. Public backend documentation records the behavior; existing wire-compatibility parity exceptions remain unchanged.

The real HTTP/LLM/PDP regression suite failed 8 cases before the fix and passed all 17 afterward. It covers exact upstream payloads, invalid/conflicting caps, authentication, write capability, monthly quota refusal, and actual usage recording. The focused suite plus existing authorization tests passed 20 cases. Required checks passed: typecheck, lint/dead-code detection, build, all 294 suites / 4,809 tests, unchanged regenerated v1 OpenAPI, and public-tree secret scan. No real provider or customer ledger was called.
