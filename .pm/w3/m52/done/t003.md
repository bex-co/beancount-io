## Objective

Finish the quota accounting and visibility scope of source note 446 after its external contract is available. Preserve the monthly account entitlement, expose supported shared-provider availability with accurate scope, and show the same supported facts in cloud status and refusal guidance.

## Files

- Backend AI-CFO usage service and REST/GraphQL/MCP adapters
- Backend public contracts and generated clients
- CLI cloud status, Ask-AI guidance, documentation, and regression tests

## Acceptance criteria

- REST, GraphQL, MCP, and CLI agree on the owner-approved presentation (2026-11-02): a shared-service refusal says the hosted AI service is temporarily at capacity, that this is **not** the account's quota and does not consume it, and when to retry; account usage surfaces report only the per-user monthly entitlement. No shared-capacity numbers are exposed.
- A near-limit fixture with a mocked provider proves account-quota refusals and shared-service refusals each produce their own message and reset time on every surface.
- No user is told their account quota is exhausted solely because a shared provider limit was hit.
- Required package, parity, generated-contract, and adoption checks pass.

## Earlier block (resolved 2026-11-02)

The upstream shared-capacity and reservation contract is unavailable in this public repository; see the milestone blocker and ADR 011 D4.

**Unblock:** provider/deployment operator supplies supported window/usage/reset/reservation behavior or sufficient configured capacity, product owner approves the account-versus-service presentation, and a reproducible near-limit setup is available. Owners: provider/deployment operator and product owner.

## Unblocked 2026-11-02 (`/unblock w3`)

Owner decision (option A): distinguish the cause and do not expose shared provider capacity. A refusal with `quotaScope: "shared_service"` (shipped in t002) is shown as temporary service capacity with the retry time, and is never called the user's quota. The CLI's `_quota_refusal` (`cli/src/cli/ask/agent.py`) must not say "This account's hosted AI quota is used up" for it. Usage surfaces keep only the monthly account entitlement. Rationale: users' actual confusion was being told they were out of quota with 88% left; a capacity number adds little. This removes the dependency on a provider usage/window contract. Raising provider capacity remains an optional operator action, not a condition.

## Done 2026-11-02

- backend-v2: the account's monthly refusal now carries `quotaScope: "account_monthly"` and `blockedUntil`, the first instant of the next UTC billing month (`nextBillingMonthStart`). Its message names the account's monthly quota and that reset. The shared-capacity refusal says it is not the account's AI quota and that the refused request used none of it. The README documents both scopes. Usage reads (REST `ai-cfo-usage` and GraphQL `aiCfoUsage`; MCP keeps its documented exemption) already report only the monthly entitlement.
- cli: `_quota_refusal` reads `quotaScope`. `account_monthly` gets "This account's monthly hosted AI quota is used up … It resets at …". `shared_service`, or a raw provider `QUOTA_EXCEEDED`, gets "The hosted AI service is at capacity … not this account's AI quota … Try again at …". An unscoped 429 stays a plain rate limit. Before, both scoped refusals printed "Rate limited … Wait a moment and retry", and a raw provider refusal was called the account's quota.
- Tests: `ai-cfo-usage-service.test.ts` (scope, reset, message, malformed months) and `openai-chat-completions-route.test.ts` (the shared message denies account-quota exhaustion) use mocked-provider near-limit fixtures. In the cli, `test_ask_result_shape.py` covers both scopes and the unscoped control. Both new cli tests fail on the previous `agent.py`.
