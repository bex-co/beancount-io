# Password visibility buttons are skipped by keyboard navigation

Severity: minor. Owner: dashboard. Estimate: 15–25 minutes. A2: keyboard users
can reach the same password visibility control available to pointer users.

Environment: production https://beancount.io, Chrome 152, isolated signed-out
contexts, English/light, 1440×1000 and fresh 390×844 on 2026-09-08. Source HEAD
a315c273; fetched origin/main cc3f4c2f has no matching correction. The deployed
build is not proven identical to local HEAD.

Reproduce:

1. Fresh-open `/auth/login?lang=en` without entering any credentials. Focus
   Password, then press Tab repeatedly.
2. Focus moves directly to Forgot Password?, Sign In and Sign Up. Show password
   is omitted because its native button has `tabindex=-1`.
3. Mouse-click Show password: the empty input changes from type=password to
   type=text, the button is named Hide password, and input focus is preserved.
4. Fresh narrow Login repeats the skipped tab stop. Fresh Sign Up has two
   Show password buttons and both also have tabIndex -1. No SignIn/SignUp
   request is made by these checks.

Expected: sequential keyboard navigation reaches each visibility button and
Enter/Space performs the same toggle, without submitting the form. The current
localized Show/Hide names are correct and should be preserved.

Root cause: `dashboard/src/features/auth/components/password-input/index.tsx:44`
sets `tabIndex={-1}` on the otherwise native, labelled button. There is no
alternate keyboard shortcut in this component. The separate onMouseDown
preventDefault already handles keeping pointer interaction from moving input
focus; excluding the button from sequential keyboard focus is unnecessary.

Fix the shared PasswordInput's tab order while retaining type=button,
mouse-focus behavior and localized state-dependent naming. Production callers
are Login (one field), Register (two fields) and Reset Password (two fields).
Do not change password validation, autocomplete, masking defaults or auth APIs.

Acceptance: at desktop/narrow, Tab and Shift+Tab can reach the toggle; Enter
and Space switch input type and Show/Hide name without a form request. Pointer
use still preserves input focus. A focused browser interaction check suffices;
no credential entry or real reset/signup is needed to verify the change.

Dedupe: searched all open/done board records for password visibility, Show/Hide,
tab order and keyboard access. No overlapping item found. Targeted history
traces the excluded tab stop to af5339de; aeec496b localized the label but did
not restore keyboard reachability. Other named-control findings use unrelated
components.

Unverified: live reset-password token flow, every locale and actual screen-reader
speech. All fields stayed empty, isolated contexts were closed, and the main
QA login was preserved. No product implementation or shipping included.
