## Objective

Answer once, for all sixteen, what a date range looks like, what an account filter looks like, and what happens when a result set is unbounded. Sixteen endpoints that each answered it separately would be sixteen different APIs wearing one prefix.

## Context

- Most of the family takes at least one of: a date range, an account name, an interval (`day`/`week`/`month`/`quarter`/`year`), a filter string.
- Three can return a full ledger history — `journalEntries`, `getLedgerPlaintextJournal`, `getLedgerAccountJournal`. A ledger with a decade of transactions makes an unbounded response a denial-of-service against the caller.
- REST and MCP need the *same* answer: a resource template's RFC 6570 parameters should name the same things as the route's query string, or the two surfaces diverge in the one place a caller notices.
- The GraphQL twins already have argument shapes. Prefer matching them over inventing new ones — ADR 0006 D1's point is that a verb behaves the same everywhere.

## Steps

1. Settle the date-range, account, and interval parameter names against the GraphQL arguments.
2. Decide the bounding rule for the three unbounded reads: page, cap, or refuse-without-range. State which and why.
3. Write the decision into ADR 0008 so t002/t003 and every later family follow it rather than re-deciding.
