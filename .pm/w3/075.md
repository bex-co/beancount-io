# Token permission errors lack focus and field associations

Severity: **minor**. Package: **dashboard**. Estimate: **30–45m**.
A2/A1: users creating a scoped token can find and repair a missing permission
through the keyboard and accessibility tree.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English/light,
authenticated QA account. Fresh 1440×1000 and 390×844 contexts. Local
`a315c273`, fetched main `790791ac`, source unchanged; deployed SHA unverified.
Mutation guards are installed before navigation. No token is created, revealed,
copied or revoked; existing token names, prefixes and metadata are not retained.

1. Open `/settings/api-keys?lang=en` and **New token**.
2. Enter the synthetic name **qa-20260908-validation**, then uncheck the
   initially selected **ledger.read** permission. Leave the optional fields empty.
3. Focus **Create token** and press Enter. Validation correctly blocks creation
   and displays **Select at least one permission.**
4. Focus nevertheless remains on Create token. Neither the Permissions
   fieldset nor any of its three checkboxes has aria-invalid or aria-describedby.
   The error paragraph has an ID, but no control references it and it has no
   alert/live role. Fresh desktop/narrow repeats give the same result.
5. Working control: in a fresh dialog leave Token name empty and keep the
   default read permission. The same keyboard submission correctly focuses
   Token name. Its ordinary registered input/FormControl wiring works.

Expected: when permissions are the first invalid field, focus reaches the first
permission checkbox and the group's error is associated with the relevant
control/group. The group legend and checkbox names already work. Keep the
required-permission validation; this is not a scope authorization failure.

never attaches field.ref or field.onBlur to a focusable checkbox; the fieldset
also bypasses FormControl's description/error attributes. Compare Token name

Radix; no shared primitive or dependency change is needed. The named-field
