# Mobile transaction postings round recorded commodity quantities to two decimals

**Severity:** minor. **Owner:** mobile. **Estimate:** 45–60 minutes.
**A2:** inspecting a transaction reveals the actual recorded quantity, so a
newcomer can reconcile a holding without opening its source file.

Environment: 2026-09-08, production https://beancount.io API, local mobile HEAD
`a623f745`, native `io.beancount.ios` 1.20260906.47, iPhone 17e / iOS 26.5,
390×844 logical, English/light, authenticated reader of public synthetic
`open_ledger/example`. No production writes.

Actual native journey, repeated after termination/relaunch:
1. Open Accounts, expand the chevron beside US:Vanguard, and tap RGAGX.
2. Open the first August 14, 2017 transaction, whose account-journal change is
   +$150.02 and narration is Investing 60% of cash in RGAGX.
3. The detail Money flow shows `+1.84 RGAGX` and `-$150.02`.
4. Relaunch, repeat that same account/entry path: the quantity is still 1.84.

Expected: the posting exposes 1.843 RGAGX, the actual recorded units. Actual:
0.003 shares disappear from the detail display without any approximation label
or way to reveal more digits in that posting. This finding concerns display;
no stored quantity changed.

Read-only evidence: GetLedgerJournal for account `Assets:US:Vanguard:RGAGX`
and GetLedgerEntryContext for hash `13a84292f04f253ed521beb85ba63b9f` both return
units `{number:"1.843",currency:"RGAGX"}` and cash `{number:"-150.02",currency:"USD"}`.
The context source slice independently reads:

```beancount
2017-08-14 * "Investing 60% of cash in RGAGX"
  Assets:US:Vanguard:RGAGX  1.843 RGAGX {81.40 USD, 2017-08-14}
  Assets:US:Vanguard:Cash  -150.02 USD
```

Producer/serializer: ledger `src/foundation/rustledger/journal-serialize.ts:127`
preserves amount.number as supplied; `src/features/ledger/service/ledger-journal-service.ts:618`
returns that serialized entry plus source slice. Backend-v2's corresponding
service at 200 passes ctx.entry through. Mobile detail calls selectPostingRows
at `src/screens/transaction-detail-screen/transaction-detail-screen.tsx:357`.
Its selector at59–69 parses the decimal string with parseFloat and delegates
to `formatAmount`; `src/screens/transactions-screen/utils/transaction-display-utils.ts:15`
sets maximumFractionDigits to 2 for every currency. PostingRow renders the rounded
string and includes it in its accessibilityLabel (component at75), so this is
not merely clipped text. VoiceOver itself was not exercised.

Fix: give detail posting quantities precision-preserving formatting using the
original decimal string. Retain significant fractional digits, commodity label,
positive/negative sign and grouping; preserve ordinary USD two-decimal display
when that is the recorded precision. Avoid a fixed two-decimal cap or floating
conversion that discards a supplied decimal. Keep the existing summary formatter
separate unless another live finding justifies changing its contract. Very small
nonzero quantities must remain nonzero in detail.

Blast radius: selectPostingRows has one production consumer, the transaction
detail screen, reached from transaction/account/home/merchant journeys through
openTransactionDetail. PostingRow has that same sole consumer. formatAmount is
also used by transaction headline selection and merchant recurring summaries;
those summary conventions should not change incidentally. The budget card's
same-named formatter is local and unrelated. Working controls: cash posting
-$150.02 is exact; account table, detail chart and journal running balance all
agree at $49,049.67; changing its chart to 1M produces +$449.98, matching August's
API interval amount 449.9792. The precision defect is in raw posting units.

Acceptance: the reproduced entry shows +1.843 RGAGX after relaunch while cash
remains -$150.02. Add focused tests against the real selectPostingRows for this
API-shaped entry, negative/zero quantities, a small nonzero quantity and a long
decimal string; retain existing money/sign/invalid-value tests. Existing tests
cover USD formatting only. Keep loading, error and permission handling intact.
Empty/denied/expired/offline detail, Android, other locales and physical devices
were not exercised for this finding; tiny-quantity native reproduction is not claimed.

Dedupe: all open/completed .pm records and active milestone headings checked
for precision, fractions, rounded postings/shares. w3/012,035,054 and064 concern
dashboard commodity tooltips, Holdings, import display and browser input;
w3/m26 concerns dashboard inferred amounts. None repairs native posting detail.
Targeted git log -S traces selectPostingRows to 4d3d3e44 and the shared two-digit
formatter to 69001418; current source retains both. No already-landed local fix
