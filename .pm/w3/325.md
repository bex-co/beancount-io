# `bea list …` truncation note says “pass --limit for more” when `--limit` is already set

**Severity:** minor. **Estimate:** 10–15 minutes. **Owner:** cli. **A1:** an
agent that already passed `--limit 1` (or any limiting value) and still sees
more rows exist is told to “pass --limit for more” — which they already did —
instead of raising the limit or using `--from-date` / filters.

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `c13e3f2b`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only. Evidence: `cli/tmp/qa-20260915/c705/`.

## Repro

```sh
# ledger with ≥2 transactions
bea --file main.bean list transaction --limit 1
# … one row …
# Showing the first 1; pass --limit for more.
```

JSON correctly sets `"truncated": true, "limit": 1` with no bad advice.

## Expected

Human note should say to pass a **higher** `--limit` (or omit the advice’s
“pass --limit” when a limit is already present): e.g. `Showing 1 of N; pass
--limit N or omit --limit for more.`

## Actual

`cli/commands/list.py` always emits
`Showing the first {limit}; pass --limit for more.` whenever results are
truncated, regardless of whether the user already supplied `--limit`.

## Fix

If the CLI default limit was used, keep “pass --limit for more”; if the user
set `--limit`, say “raise --limit …” / show total when cheap. Regression: the
repro’s note no longer reads as “pass --limit” without qualification.

## Dedupe

No open note covers this truncation copy. Not a JSON `truncated` flag bug.
