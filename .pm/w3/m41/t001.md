## Objective

Put an explicit confirmation between the Entry Context dialog's **Delete** button and the mutation. Reuse the app's existing `AlertDialog` primitive and follow the pattern already used by `features/ledger-data/budget/delete-budget-dialog.tsx` rather than inventing a second confirmation style. The confirmation must name what is being deleted and state that the action cannot be undone from the app.

## Context

- Defect site: `dashboard/src/features/journal/components/entry-context-dialog.tsx:373-386` (button) and `:210-222` (`handleDelete`, which calls `onDelete` immediately). The parent mutation is at `:471-491`.
- Confirmation primitive: `dashboard/src/common/components/ui/alert-dialog.tsx`.
- Existing precedents in this package: `budget/delete-budget-dialog.tsx`, `user-settings/pages/api-keys/api-key-revoke-dialog.tsx`, `plaid/pages/plaid-connections/components/bank-item.tsx`.
- Three production callers share this dialog: `features/journal/pages/journal-page.tsx`, `features/reports/account/index.tsx`, `features/reports/overview/components/recent-activity-card.tsx`. Implement centrally so all three are covered.
- Nesting a confirmation inside an already-open dialog needs care: focus must move into the confirmation and return correctly on cancel, matching what completed `m23` established. Coordinate with open `m31`, which owns this dialog's keyboard journey.
- The existing `canWrite` gate must keep hiding Delete entirely from read-only users.

## Steps

1. Add the confirmation between the button and `onDelete`, reusing the existing primitive.
2. Make Cancel a true no-op: nothing deleted, Entry Context still open and unchanged, focus back on the Delete button.
3. Guard against a double activation issuing two deletions.
4. Verify by keyboard as well as pointer, at 1440 and 390.

## Files

- `dashboard/src/features/journal/components/entry-context-dialog.tsx`

## Acceptance criteria

- [ ] Delete never mutates without an explicit confirmation, from any of the three callers.
- [ ] Cancel leaves the entry and the dialog untouched and restores focus to the Delete button.
- [ ] Escape cancels; it never confirms.
- [ ] Confirming issues exactly one deletion even under rapid repeated activation.
- [ ] Read-only users still see no Delete; the disabled-Save behavior on an unmodified entry is unchanged.

## Out of scope

An undo/restore feature, changing the delete mutation or its API, the file-draft discard flow owned by completed `m29`, and the mobile package.
