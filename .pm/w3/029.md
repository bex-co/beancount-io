# Settings sign-in redirects discard the requested subpage

Severity: minor. Owner: dashboard. Estimate: 30–45 minutes. A1/A2: a newcomer
following the documented Personal access tokens link can return to that page
after authentication rather than being sent to General Settings.

Environment: production https://beancount.io, Chrome 152, isolated signed-out
browser contexts at 1440×1000 and 390×844, English/light, 2026-09-08. Existing
authenticated QA session was preserved for a destination-heading control only.
Source HEAD a315c273; fetched origin/main cc3f4c2f has no matching guard fix.
Deployed build is not proven identical to local HEAD.

Reproduce:

1. In a fresh signed-out context open `/settings/api-keys?lang=en`.
2. Sign-in opens at `/auth/login?next=%2Fsettings`. Both the api-keys subpage
   and its query string have already been discarded.
3. Repeat at narrow width and in a fresh desktop context. Visiting
   `/settings/ssh-keys?lang=en` produces the identical generic next value.
4. Working control: the existing authenticated QA session opens
   `/settings/api-keys?lang=en` and reaches the Personal access tokens heading.
   The requested route exists and is authorized; no key data was captured.

Expected: the sign-in continuation retains the requested safe Settings
destination. A successful login should return to the selected subpage with
relevant URL state. The authentication requirement itself is correct.

Root cause: `dashboard/src/routes/settings.tsx:6` calls
`requireAuth("/settings")` for the parent shared by every Settings child.
`common/lib/auth/auth.ts:23–33` only accepts context and always puts that fixed
path in next. Login success in `features/auth/pages/login-page/index.tsx:28–31`
honors the safe next path through document navigation, and
`routes/settings.index.tsx:7` redirects `/settings` to `/settings/general`.
The post-login consequence is source-traced; this pass did not submit another
real login through the isolated guest form.

Fix Settings' guard/requireAuth integration to capture the requested route
location, including supported query state and a client fragment when available,
while retaining the existing safe-relative-redirect validation. Do not loosen
authentication or replace a requested subpage with the user's default ledger.
If the shared helper changes, preserve intentional behavior for its other
callers: `/ledger`, `/ledger-gallery` and the legacy default-ledger route.

Acceptance: fresh guest API-key and SSH-key routes produce the correct next
value; the real guard→login-success continuation reaches the original subpage.
Verify authenticated navigation still works, unsafe external next values remain
rejected, and the explicit marketing/pricing continuation covered by existing
login tests stays intact. Include the parent guard in regression coverage;
injecting a pre-corrected next into the login page alone misses this defect.

Dedupe: searched all open/done board records for Settings/login next and
redirect destinations. The public link is documented in
`.pm/w3/done/m10/done/t004.md`; its flow starts already signed in. Commit
c4e65a5b fixes consumption of explicit next through login/sign-up, not this
guard's production of the value. The fixed Settings target dates to af5339de;
no newer correction was found. This is separate from ledger filters in w3/m15.

Unverified: fresh password sign-in completion, sign-up/OTP completion, expired
existing sessions and every Settings child. No production credentials, token
creation, email, profile changes or product implementation were submitted.
Isolated guest contexts were closed; the user's authenticated QA session stayed
available. No shipping included.

Verified evidence under `dashboard/tmp/qa-20260907-w3-loop/`:
`settings-login-next-evidence.json`, `settings-login-next-1440.png`, and
`guest-login-validation-390.png`. Blank form validation was a separate passing
control and produced zero SignIn requests.
