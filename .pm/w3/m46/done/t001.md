## Objective

Reject malformed ledger path parameters at the REST v1 boundary so no encoded
input (`/`, `%2f`, `%252f`, `?`, `#`, `..`, uppercase, spaces) can reach an
upstream client or resolve to a different repository.

## Context

- `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/schemas.ts:14-27`
  — `ledgerPathSchema` is `z.string().min(1)` with no slug rule.
- `src/server/rest/validation-middleware.ts:74` validates `ctx.params` with it.
- A slug rule already exists for request **bodies** at
  `src/features/ledger/api/rest/v1/lifecycle-handler.ts:6-9` (`/^[a-z0-9_-]+$/`)
  and in GraphQL create/update inputs (`ledger-resolver.types.ts:103,128`).

## Steps

1. Constrain both path params in `ledgerPathSchema`: name `z.string().min(1).max(100).regex(/^[a-z0-9_-]+$/)`; owner to the owner slug rule the service accepts (confirm case-sensitivity — REST currently accepts uppercase owners and folds them).
2. Return a 4xx that names the rule (match the existing body-validation error shape) rather than letting it reach `resolveLedgerId`.
3. Add the same guard defensively in `parseLedgerId`/`createLedgerId` (`src/shared/str.ts:33-58`) and in the MCP resolver (`src/features/ai-agent/api/mcp-resources.ts:133`).

## Acceptance criteria

- [x] `GET/PUT/DELETE /api-gateway/v1/ledgers/{owner}/{name}` with `name` containing `/`, `%2f`, `%252f`, `?`, `#`, `..`, uppercase, or a space returns a 4xx naming the slug rule and never calls an upstream client.
- [x] MCP and GraphQL ledger lookups apply the same rule (parity check).

## Out of scope
