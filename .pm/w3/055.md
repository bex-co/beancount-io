# Switching ledgers keeps the previous ledger's BQL results and CSV

Severity: **major**. Owner: **dashboard**. Estimate: **45–60 minutes**,
bounded to the query route's ledger identity and an integration regression.
A1/A2: a query reused across ledgers must report and export the selected
ledger's accounts, rather than silently relabeling another ledger's results.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light. Authenticated QA account; public `open_ledger/example` is readable,
and the existing switcher offers public `open_ledger/minimax` (pull/push true,
admin false). Only reads were performed. The latter is a public company ledger,
not a disposable write fixture. Fresh 1440×1000 and 390×844 repeats.
Local HEAD `a315c273`, fetched main `cc3f4c2f`; implicated code unchanged there.
Deployed SHA unverified.

1. Open `/ledger/open_ledger/example/query` with this URL-encoded `query`
   parameter, or execute it with the button:
   `SELECT account FROM accounts ORDER BY account LIMIT 1000`.
2. Wait for **60 rows**, beginning `Assets:US:BofA`. QueryShell returns HTTP
   200 with `ledgerId: open_ledger/example` and those sixty accounts.
3. At 390px, open Toggle Sidebar. Open **Select a ledger**, search
   `open_ledger/minimax`, then choose **minimax Public**. The initial desktop
   pointer selection and fresh desktop/narrow Enter selections agree.
4. The URL becomes `/ledger/open_ledger/minimax/query` with the same query;
   the browser title says **BQL Query - minimax**. Its GetLedger response is
   HTTP 200 and identifies public `open_ledger/minimax`.
5. The result still says **60 rows** and lists the previous ledger's accounts.
   **Download CSV** also exports all sixty previous accounts. No QueryShell
   request occurs during the observed switch and one-second settled wait.
6. Reload the unchanged minimax URL. QueryShell now requests minimax and
   returns **28 rows**, starting `Assets:Current:AccountsReceivable`,
   `Assets:Current:Cash`, and `Assets:Current:Other`. The table and CSV both
   change to the correct twenty-eight accounts.

Expected: a ledger change invalidates the prior ledger's settled query results
and executes the retained query for the new ledger. During loading or failure,
old results must not appear or remain downloadable as the new ledger's output.
The same query text and history can be reused without reusing another ledger's
result data, errors or in-flight execution state.

Root cause: `dashboard/src/features/bql/pages/index.tsx:43–52` stores results
in component state keyed only by query text; lookup at line 327 uses that same
key. The URL execution effect at lines 123–133 depends only on `urlQuery`, which
does not change in this journey. The result card receives an existing result
and its toggle handler (`query-result-card.tsx:45–49`) does not execute again.
The switcher at `common/components/ledger-layout/ledger-switcher.tsx:130–148`
preserves the current subpage and search parameters as intended.

The sole query route, `src/routes/ledger.$ledgerOwner.$ledgerName.query.tsx:10–13`,
uses the same component without a ledger remount key. Verified pinned
`@tanstack/react-router` 1.167.0 `src/Match.tsx:189–220` derives the component key
only from route/default `remountDeps`; neither is configured here. Changing
route params therefore preserves this local state. Both published router
tarballs were checked against their registry SHA-512 integrity; no dependency
was installed or upgraded.

Fix the **query route's ledger boundary**, for example with route-level
`remountDeps` based on ledger owner/name, so a ledger change receives fresh
result/error/execution state and reruns its retained URL/history query. Keep
ordinary same-ledger query edits and m12's editor restoration contract intact.
An equivalent explicitly scoped cache must also reject late completions from
the previous ledger; adding `ledgerId` to the effect alone leaves other cached
history results and outstanding requests unsafe to reuse. Do not globally
remount every ledger page or clear the user's query-history strings.

Producer/control: REST POST `/api-gateway/v1/ledgers/open_ledger/{name}/query`
with the same query returns HTTP 200 and exactly the corresponding 60/28 rows.
The gateway's `src/features/ledger/service/ledger-shell-service.ts:44–80`
authorizes and dispatches by ledgerId, then preserves the result rows. The
dashboard export chain (`query-result-card.tsx:160` → `query-result-export.tsx:19`
→ `lib/export-utils.ts:10–17`) faithfully serializes the stale table it receives.
No backend, API schema or CSV serializer repair is indicated.

Acceptance: fresh desktop/narrow switching shows minimax's 28 accounts and
matching CSV without a reload, with exactly the intended new-ledger execution.
Verify loading/error states, a switch while an old query is pending, and
reopening another cached history result. A late old-ledger result must never
populate or export under the new ledger. Keep same-ledger history and m12's
button/keyboard/bookmark execution behavior. Cover this with the real route
and page state in a regression test, then run dashboard gates.

Dedupe: searched all open/completed board records for BQL caches, query result
identity and ledger switching; reviewed open milestone summaries. m12 repairs
editor text and shortcut execution; m15 repairs global reporting filters.
Neither resets BQL result state on a ledger change. Completed w2/m22 concerns
chart runtime loading and w2/m23 concerns route/optional metadata loading;
their recorded controls do not establish prior isolation of this BQL cache.
Targeted history traces the cache to `af5339de`, with no later main repair.
Coordinate with m12/t002 because it touches the same page and URL effect.

The monitored switch phases have no page/console errors. Private-ledger
transitions, delayed/failed queries, non-table results, other browsers/locales,
live MCP and patched behavior remain unverified. Those adjacent cases are
