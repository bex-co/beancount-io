# `bea import --apply --allow-errors` writes unknown-account rows and exits 0

**Severity:** major. **Estimate:** 30–45 minutes. **Owner:** cli. **A1:** an
agent that passes `--allow-errors` to import over an existing soft ledger issue
(or copies the flag from `add` / `list`) can `--apply` CSV rows whose counter-
account was never opened; bea prints **Wrote 1 entry**, exits **0**, and leaves
a ledger that **`bea check` rejects** — while the same import without the flag
correctly refuses (w3/276).

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `986e703c`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache. Synthetic
fixtures only. Evidence: `cli/tmp/qa-20260915/c660/` (initial), `c663/`
(confirm).

## Repro

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2020-01-01 open Assets:Cash USD
2020-01-01 open Equity:Opening-Balances
2020-01-01 open Expenses:Food USD

2020-01-01 * "seed"
  Assets:Cash               100 USD
  Equity:Opening-Balances  -100 USD
EOF
printf 'date,amount,description\n2020-08-01,-2.00,coffee\n' > bank.csv

# Control — apply refuses (w3/276):
bea --file main.bean import bank.csv --csv auto --account Assets:Cash \
  --apply --duplicates include
# exit 1 — Import would leave the ledger invalid; nothing was written.

# Bug — apply succeeds with a broken ledger:
bea --file main.bean import bank.csv --csv auto --account Assets:Cash \
  --apply --duplicates include --allow-errors
# exit 0 — Wrote 1 entry to main.bean.
# stderr still notes unknown account Expenses:Uncategorized.

bea --file main.bean check
# exit 1 — Invalid reference to unknown account 'Expenses:Uncategorized'
```

JSON under `--json` is equally misleading: `written: 1`, empty
`validation_errors`, non-empty `validation_warnings` with the unknown-account
message, exit 0.

Currency-constraint variant (same mechanism): CSV `currency=EUR` into a
USD-only `Assets:Cash` with `--allow-errors --apply` also exits 0 / check 1.

## Expected

`IMPORTING.md`: `--allow-errors` is for applying over a ledger that **already**
fails validation (e.g. a failing balance assertion), not for accepting
**newly imported** reference errors. Either keep `--apply` blocked when
appended rows introduce unknown accounts / currency violations, or exit
non-zero / `written: 0` when post-write validation warnings remain — never
print success for a ledger `check` rejects.

`REFERENCE.md` import flag text: “Preview and apply over semantic ledger
errors such as a failing balance assertion; syntax errors still block.”

## Actual

With `--allow-errors`, `validate_append` downgrades unknown-account (and
currency) errors to warnings. The apply gate only checks `validation_errors`,
so append proceeds and the frontend prints “Wrote N entries”.

## Fix

Do not treat newly introduced unknown-account / currency / inactive-account
failures as apply-safe under `--allow-errors` (keep the pad / pre-existing
balance-assertion carve-out). Regression: the repro’s `--allow-errors --apply`
exits ≠ 0 and leaves the pristine ledger; control without the flag unchanged;
`--allow-errors` still lets preview/apply proceed when the **pre-import**
ledger already has a failing balance assertion and the new rows are clean.

## Dedupe

Not w3/276 (preview/`--apply` **without** `--allow-errors` refuses — this is
the `--allow-errors` path that writes anyway). Not w3/232 (`add custom
--allow-errors` pad poison). Not w3/310–311 (sticky import memory). No open
note covers import `--apply --allow-errors` writing check-invalid rows.
