# A language parameter makes the manual language selector ineffective

Severity: minor. Owner: dashboard. Estimate: 40–60 minutes, including shared
language/router regression coverage. A2: readers arriving through localized
public links can choose a language they understand.

Environment: production https://beancount.io, Chrome 152, authenticated QA,
English/Chinese and System light, 1440×1000 plus fresh 390×844. Public synthetic
`open_ledger/example` report and the QA account's General Settings language
control only. Source HEAD a315c273; fetched origin/main cc3f4c2f has no language
selector fix. Deployed build is not proven identical to the checkout.

Reproduce on 2026-09-08:

1. Fresh-open `/ledger/open_ledger/example/balance-sheet?time=2016&lang=zh`.
   The report is Chinese, HTML lang is zh, and the stored locale is zh.
2. Open the desktop avatar menu → language submenu → English. The menu closes,
   but after 300ms and again after 1.4 seconds the report still says
   `资产负债表`; URL, HTML lang and stored preference all remain zh. Reload
   remains Chinese. A second fresh run repeats this result.
3. At 390×844 fresh-open `/settings/general?lang=zh`, open the language
   selector and choose English. After settlement it still displays 中文 and
   HTML/stored language remain zh. Evidence captures only that selector, without
   personal profile fields.
4. Working control: open the same public report with `time=2016` and no lang
   parameter, choose English from the same menu, then reload. HTML/stored locale
   stay en and the heading remains Balance Sheet.

Expected: an explicit choice updates the effective language and any existing
language parameter consistently. URL-language priority should still work for
directly opened localized links. The selector should not silently lose to the
URL that the user is currently changing.

Root cause: `dashboard/src/common/components/user-nav.tsx:124` and
`features/user-settings/pages/general/appearance-section/language-selector.tsx:23`
both call `common/hooks/use-change-language.ts:17`. That shared path changes
resources and persists localStorage/cookie but never updates the existing URL
lang value. `common/providers/language-sync/index.tsx:14–25` explicitly reapplies
the URL language; server/client language detection also gives that parameter
priority. The manual selection and URL therefore disagree. No backend user
preference mutation or locale-resource failure explains the observed result:
English is bundled, the no-parameter control works, and the fresh console has
zero errors/warnings.

Fix the explicit user-choice path to update the existing lang parameter through
the router while preserving pathname, other search parameters and hash. Keep
automatic URL synchronization distinct enough to avoid recursive selection or
the previous URL cancelling the user's pending choice. Preserve lazy loading,
latest-selection-wins and failure recovery: a failed locale load must retain a
usable current interface/preference, and successful selection must survive
reload. Do not remove URL precedence or eagerly import every language.

Blast radius: both desktop avatar and General Settings selectors use the shared
hook; LanguageSync is its third caller. Native bridge invokes the localization
controller separately and was not exercised. This issue is independent of
`w3/m15`, which covers ledger account/filter/time state, not language selection.

Acceptance: the two fresh reproducers can switch zh→en and retain en through
reload, with existing time=2016 preserved on the report. Without a lang parameter
the existing successful preference behavior remains. Verify direct localized
links, rapid choices, and failed-chunk recovery using a real localization/router
integration rather than a mocked changeLanguage success; preserve completed
locale bundle-budget behavior and run applicable dashboard gates.

Dedupe: searched all open/done board records for language/locale switching,
URL parameters and persistence. `w2/done/m21` promises usable language changes;
its full DoD and t004 verification exercise transitions/chunk failure but do not
cover changing a language while an authoritative lang parameter is present.
History af5339de already gave URL language priority and omitted selector URL
updates; 7b7b35ed introduced the current lazy-loading path without filling that
gap. Do not attribute the whole defect to the performance change without a
prior live control. No newer source correction was found.

Unverified: all 15 language combinations, live failed-chunk/rapid-choice behavior
in this pass, actual native app, and anonymous Settings (requires authentication).
No product implementation, profile mutation or shipping included.
