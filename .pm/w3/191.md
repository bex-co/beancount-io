# The horizontal-swipe marker throws on every touch it is supposed to end

**Severity:** major. **Estimate:** 45–60 minutes. Package: mobile. A2 — an ordinary tap on the first screen a newcomer sees must not raise an uncaught error, and the drawer arbitration this code implements must actually run. **Priority note (added after the controlled A/B below): one touch on the Home chart then strands the user in the ledger drawer — `w3/done/143`'s original symptom, reproduced against a passing control.**

**This is a regression from `w3/done/143`'s fix**, shipped in `a7c13568` (2026-09-11) and present on `main` at `84231f9c`. It is not the old defect returning; it is the new terminator never executing.

Production https://beancount.io, September 12, 2026; local HEAD `84231f9c` with JS served from a local Metro dev server, native development build `io.beancount.ios` 1.20260906.47, iPhone 17e / iOS 26.5, English / System-light / default text size. Authenticated QA session, public read-only `open_ledger/minimax`. Read-only; no ledger write.

## Repro (three surfaces, each from a settled screen)

1. Terminate and relaunch the app (fresh PID 30214 used below). Wait for Home to settle on `open_ledger/minimax`.
2. Tap **Assets** in the balance card's tab strip. The tab does switch (headline becomes `1,714.67 MUSD`), and then a full-screen **Uncaught Error** appears:
   `[Worklets] Tried to synchronously call a Remote Function. Called "endManualGesture" on the UI Runtime.`
   Source `horizontal-swipe-owner.ts (44:53)`, call stack `[UI]: horizontalSwipeOwnerTs2`.
3. Dismiss it and tap the **net-worth plot** itself (logical ~196,330). Same uncaught error, one per touch.
4. Dismiss it, open the **Reports** tab, tap its income/expense chart (logical ~196,250). Same uncaught error.
5. Counter-observation worth keeping: tapping a **time-range pill** (`1M`) in the same card did **not** raise it in this run, and neither did the tab-bar, list rows, or any screen without a chart or tab strip. So this is not "every tap anywhere".

Each error is a distinct LogBox entry (`Log 1 of 1` after dismissal), so it is one throw per touch, not a single stuck overlay.

## Expected / actual

Expected: the manual marker that claims horizontal-swipe ownership is terminated on touch-up, silently. Actual: the terminator throws on the UI runtime before it can run, so the marker is never ended **and** the app raises an uncaught error — a redbox in development, and on a release build the same call is still made from the UI runtime (see Unverified).

## Root cause

`mobile/src/common/horizontal-swipe-owner.ts:43–45`:

```
const marker = Gesture.Manual()
  .onTouchesUp((_, manager) => endManualGesture(manager))
  .onTouchesCancelled((_, manager) => failManualGesture(manager));
```

Gesture-handler's touch callbacks are auto-workletized and run on the UI runtime. `endManualGesture` / `failManualGesture` are ordinary JS functions imported from `mobile/src/common/manual-gesture-release.ts:24–30`; without a `"worklet"` directive they are captured as **remote** functions, and calling one synchronously from the UI runtime is exactly what `react-native-worklets` 0.10.1 rejects. The versions in play are `react-native-gesture-handler ~2.32.0`, `react-native-reanimated 4.5.1`, `react-native-worklets 0.10.1`; `babel.config.js` uses `babel-preset-expo`, which already supplies the worklets plugin, so the directive is available.

The module split is what introduced it. `a7c13568`'s own message says “Every behavioural rule landed as a pure, tested helper, because this package has no render harness”, and `manual-gesture-release.ts` says it was “Split out of `horizontal-swipe-owner` so the wiring is unit-testable”. Moving the two calls across a module boundary is precisely what turned them into remote functions.

## Why the test suite is green

`mobile/src/__tests__/manual-gesture-release.test.ts` calls `endManualGesture`/`failManualGesture` directly with a fake manager, from the JS runtime — the one context where the bug cannot occur. It asserts `end`/`fail` are forwarded, which is true and irrelevant to the failure. A regression guard must instead pin the property that broke: that the functions reaching gesture-handler's touch callbacks are workletizable (e.g. assert the `__workletHash`/worklet marker the plugin attaches, or move the calls inline so there is nothing to import). Do not "fix" this by deleting the test; do fix the gap it left.

## Fix

Make the terminators run on the UI runtime: add the `"worklet"` directive to `endManualGesture` and `failManualGesture` (they stay directly callable from Jest, so the existing unit tests keep working), or inline `manager.end()` / `manager.fail()` into the two gesture callbacks. Do **not** route them through `runOnJS`/`scheduleOnRN` — the gesture manager must be driven on the UI runtime, and hopping to JS would reintroduce `w3/done/143`'s late/never termination. Do not silence the error by removing `onTouchesUp`/`onTouchesCancelled`; that restores the original stuck-marker defect. After fixing, re-verify on device that the three reproducers above raise nothing, and that `w3/done/143`'s own repro (tap the plot → `ledger-drawer-button` → `drawer-settings-row`) still reaches Settings.

## Blast radius

All three consumers of `useHorizontalSwipeOwnerGesture` are affected and all three are reproduced: `src/components/segmented-pages/index.tsx:105` (the Home balance card's tab strip, via `home-screen/components/account-charts-card.tsx:182` — the only `SegmentedPages` consumer), `src/common/d3/interactive-line-chart.tsx:404` (Home net-worth chart, and every account-detail balance chart), and `src/common/d3/scrollable-axis-chart.tsx:57` (Reports). Nothing outside these three uses the hook.

## The user-visible consequence is now reproduced, with a control — `w3/done/143`'s symptom is back

Added after a controlled A/B on fresh launches (banner dismissed first in both arms, both taps issued by `testID` so the same elements are hit):

- **Control** — fresh launch (PID 78189), do **not** touch the chart, tap `ledger-drawer-button`, tap `drawer-settings-row`: the drawer opens and **Settings opens**. Evidence: `ei04-open.png` → `ei06-after.png`.
- **Test** — fresh launch (PID 80368), tap the net-worth plot once (raising the error above), dismiss the redbox, then the same two taps: the drawer opens and **Settings never appears** — the drawer just stays open. Evidence: `ej07-open.png` → `ej09-after.png`, which are byte-identical (112,858 bytes each). An earlier run on PID 74820-era state reproduced the same failure (`ef07-drawer.png` → `eg02-after.png`).

That is precisely the symptom `w3/done/143` was opened for: *“Tap the plot … Tap ledger-drawer-button. The drawer opens visibly. Tap drawer-settings-row. The drawer remains open; Settings does not appear.”* So 143's user-visible defect is back on `main`, now caused by the terminator throwing instead of by the terminator being absent. This raises the severity beyond “an uncaught error”: one touch on the Home chart strands the user in the drawer, exactly as before the fix.

Two honesty notes on this evidence. First, the mechanism — a marker stuck in BEGAN holding `blocksExternalGesture` on the drawer's edge swipe — is still **inferred**; what is controlled and reproduced is the behavioural dependency on the chart touch, not the gesture-handler state (which needs gesture-state tracing this MCP cannot do, the same limit 143 recorded). Second, an earlier attempt at this control was **discarded as contaminated**: the development LogBox banner was covering the Settings row, so the tap was being eaten by dev-only chrome; both arms above were re-run with the banner dismissed first.

The stranding is **not Home-specific**: repeating the test arm on the **Reports** screen (fresh launch, banner dismissed, one tap on the income/expense chart, redbox dismissed) leaves the drawer equally unresponsive — `fa07-open.png` → `fa09-after.png`, again byte-identical (110,796 bytes each). Any screen mounting a swipe-owner marker can put the user in this state, which matches the three consumers listed under Blast radius.

Acceptance should therefore include 143's own repro as a regression check, not just the absence of the redbox, and should cover at least one non-Home surface.

**Still live at HEAD `038faeeb`, on a third ledger, and tap-away is stranded too** (re-verified September 13, `open_ledger/alphabet`, same device/build). The A/B above drives a *drawer item* (`drawer-settings-row`); this arm drives the ordinary **tap-away-to-dismiss** on the exposed content instead, at one fixed coordinate (logical `366,298`):

- **Test** — tap the net-worth plot once (redbox raised), dismiss it, open the drawer, tap `366,298`: the drawer **stays open** (`w4l56-04-drawer.jpg` → `w4l56-05-drawer-close.jpg`).
- **Control** — terminate and relaunch, do **not** touch the chart, open the drawer, tap the identical `366,298`: the drawer **closes** and Home returns (`w4l56-06-control-drawer.jpg`).

So the symptom is broader than "drawer rows stop responding": after one chart touch the drawer cannot be dismissed at all, by the most ordinary gesture there is. It also survives dismissing the redbox — arbitration is not restored by clearing the error, which matters because a release build shows no redbox, so a user would meet the stranding with nothing on screen to explain it. That the failure persists across commits since `84231f9c` rules out both a since-landed fix and deployment lag.

Two limits on this arm, stated for the same reason the note already states its others: the coordinate lands on the visible Home content and I did not confirm via the accessibility tree that it is inside the drawer's scrim rather than merely over the card, so "tap-away" is the user-level description, not a claim about which view received the touch; and the control proves the dependency on the chart touch, not the gesture-handler state, exactly as recorded above.

**The tab-strip surface reproduces on `open_ledger/alphabet` too** (September 13, HEAD `038faeeb`, same device/build). The repro at the top of this note uses `open_ledger/minimax`; a single tap on **Assets** in the Home balance card's tab strip on `alphabet` raises the identical redbox — same message, same `horizontal-swipe-owner.ts (44:53)`, same `[UI]: horizontalSwipeOwnerTs2` frame. So the defect is in the shared chart card, not in anything ledger-specific, which was already the expectation but had not been shown on a second ledger for this surface.

Two details from that run. The LogBox header read **`Log 2 of 2`**, not `Log 1 of 1` — consistent with the note's "one throw per touch" finding, and a reminder that entries accumulate across a session rather than replacing one another. And **whether the tab actually switched could not be seen**: the redbox covers the card, and dismissing it did not clear the overlay for me (the `Dismiss` control did not respond to a synthetic tap at its coordinates), so the app had to be relaunched — after which the hero was back on **Net Worth**. The note's step 2 records the headline changing to `1,714.67 MUSD` before the error on minimax; I am not contradicting that, only recording that this run could not re-observe it.

## Unverified

Release-build behaviour: whether `react-native-worklets` 0.10.1 throws identically outside `__DEV__` or degrades differently was not tested — but the remote-function call happens either way, so the marker is not terminated in either mode. The downstream consequence (a marker left in BEGAN keeping `blocksExternalGesture` on the drawer's edge swipe) is source-traced, not observed: the pinned Expo MCP has no swipe tool, so the edge-swipe journey could not be driven; only the button path to the drawer is reachable from here, and `w3/done/143` recorded the same limitation from the other direction. Android, physical devices, and the corrected behaviour remain unexercised.
