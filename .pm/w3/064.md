# Enter rejects precise amounts that a mouse submission accepts

Severity: **minor**. Owner: **dashboard**. Estimate: **40–60 minutes**.
A2: keyboard users can enter the same valid commodity amounts as mouse users
without rounding them to a hard-coded two-decimal step.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, light.
Fresh QA contexts at 1440×1000 and 390×844; public `open_ledger/minimax`, with
pull/push permission and no admin permission. This is not a disposable ledger:
every attempted write was intercepted before network transmission. Local HEAD
`a315c273`, fetched main `cc3f4c2f`, implicated source unchanged; deployed SHA
unverified. The forms retain their default MUSD commodity.

1. Open `/ledger/open_ledger/minimax/budget`, then Add Budget. Select the
   existing Expenses:CostOfRevenue account and enter **0.001** as Amount.
2. Keep the amount field focused and press Enter. The enabled submit action
   does not run. The browser emits an invalid event, leaves the amount focused
   and reports **The two nearest valid values are 0 and 0.01.**
3. On a fresh form, the same **0.001 MUSD** submitted by clicking Add Budget
   reaches the guarded BulkEntries request with number exactly `"0.001"`.
4. Repeat in Journal's New Entry → Balance tab: select Expenses:CostOfRevenue,
   enter 0.001 and press Enter while still focused. Same native rejection.
5. In New Entry → Transaction, enter two explicit MUSD postings:
   Expenses:CostOfRevenue **0.001**, Assets:Current:Cash **-0.001**. Press Enter
   while the second amount remains focused. The two legs balance, but native
   step validation rejects the focused -0.001 before the handler runs.

All three failing forms repeat at both widths. The Journal deep links are
`/journal?action=new-entry&directive=balance` and the equivalent
`directive=transaction` within that ledger. Wait for the selected tabpanel,
not only for the URL change; the previous panel can still render briefly.

Expected: valid amounts retain their precision and have the same acceptance
for Enter and pointer submission. These fields accept commodity quantities,
not a universal two-decimal currency unit. A local synthetic Beancount3.2.3
ledger containing a budget of 0.001 MUSD parses with zero errors and preserves
that exact decimal. The gateway budget serializer also forwards the supplied
number without a two-decimal restriction; no production write was needed to
establish this value contract.

Root cause: three number inputs set `step="0.01"`:

- `dashboard/src/features/ledger-data/budget/add-budget-dialog.tsx:277–282`
- `dashboard/src/features/journal/components/new-directive-dialog/balance-form.tsx:191–196`
- `dashboard/src/features/journal/components/new-directive-dialog/transaction-form.tsx:476–481`

While the controlled number input is focused, its live value is 0.001 but its
value attribute is still empty, so the browser evaluates the step from zero.
The pinned React DOM19.2.3 implementation at
`react-dom-client.development.js:1737–1740` deliberately skips defaultValue
updates for a focused number input and synchronizes it on focusout at 19639–19643.
On a fresh pointer submission, blur changes that attribute to 0.001, making
0.001 the native step base and allowing the exact same text. The
[HTML step contract](https://html.spec.whatwg.org/multipage/input.html#attr-input-step)
explains this validation/base behavior. The pinned package's registry integrity
was verified; no React patch or upgrade is called for.

Set `step="any"` on these three amount inputs so browser validation does not
impose this arbitrary precision restriction. Keep the existing finite-number,
required-field, account/currency and posting validation; preserve exact strings
and existing serialization behavior. Do not add noValidate to whole forms,
round the user's number, force blur before submission or change every common
Input globally. This is a small caller-level repair, not a decimal-library or
backend migration.

Working controls: fresh 0.01 amounts (and -0.01 in the second transaction leg)
submit by Enter with no native invalid event at both widths. In isolated
runtime counterfactuals, changing only the failing input's step to any allows
Enter to reach exactly one guarded request with 0.001/-0.001 intact in all
three forms. These DOM changes were local experiments, not a deployed/source
fix. A retry immediately following the native validation bubble did not yield
a reliable pointer control; the retained pointer success is a fresh Budget
form, not a claim about that retry sequence.

Blast radius: AddBudgetDialog has page/empty-state and card Add Entry callers
(card is source-traced); Journal uses NewDirectiveDialog for Balance and
Transaction through its toolbar/sidebar action links and deep-link variants.
These three amount fields are live-proven. The separate receipt-review form
also sets step0.01 at `features/receipt/components/receipt-review-form.tsx:216`;
that caller remains source-traced and outside this repair until independently
reproduced, because no receipt processing/upload was performed. Existing
number precision in serialization/auto-balance and chart formatting is outside
this repair. m23 independently changes Budget/Journal dialog return focus and
must be preserved when these changes land together.

Acceptance: focused 0.001/-0.001 inputs no longer produce stepMismatch or native
invalid events, and Enter submits the same exact supported values as pointer
activation in all six form/width cases. Preserve the 0.01 control and incomplete,
invalid, zero/negative and uploading/busy behavior as applicable. Use meaningful
native constraint-validation/keyboard checks with the real form; a test that
only mirrors the step attribute would miss the reproduced interaction. Other
commodities, OS keyboards, Safari/Firefox, populated Budget cards, actual write
success and patched behavior remain unverified live states.

Safety: unconditional GraphQL mutation/BulkEntries guards were installed before
navigation, service workers were blocked, and all prepared writes were aborted.
No ledger entry, budget, balance assertion or transaction was created. Retained
request fields contain only the known public ledger and synthetic amounts/
accounts. Expected ERR_FAILED messages come from the deliberate abort controls;
the original keyboard failures make no request, and page exceptions are zero.
All isolated forms, contexts and DOM counterfactuals were discarded.

Dedupe: searched all open/completed records for precision, fractional budgets
and native step validation. 035/054 are output rounding, m19 import parsing,
and063 IME submission; these are different mechanisms. `af5339de` introduced
the three fixed steps; current fetched main has no repair. No new milestone is
needed for these three small input changes and their focused regressions.
