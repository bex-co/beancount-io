# Mobile carries an account filter into a different ledger and hides its journal

Severity: minor. Estimate: 60m. Package: mobile. A2 — opening another public example should show its transactions without an account restriction inherited from a different ledger.

Environment: September 11, HEAD f943005d, native build 1.20260906.47/current JS, iPhone17e iOS26.5, English/System/light/default-large. Signed-in QA at https://beancount.io; public read-only open_ledger/example and open_ledger/crypto-example. No writes.

Repro:
1. In example Transactions, open Filters → All accounts and select Assets:US:BofA:Checking. Apply. Its journal shows Hoogle, BANK FEES and the other matching entries (API total275).
2. Open the drawer → Discover ledgers → Explore; search crypto and open open_ledger/crypto-example. Home correctly shows net worth $114,581.88 and recent Coinbase/Compound transactions.
3. Tap Transactions. It shows No transactions match your search or filters. Search is empty.
4. Open Filters: All dates and no statuses are selected, but Account is still Assets:US:BofA:Checking from the example ledger. Reset/Apply restores the crypto journal.

Repeat/alternate path: first reproduced through beancount:///ledger/open_ledger/crypto-example/journal with BofA plus Cleared/Pending filters; clearing only Account restored the crypto rows while retaining the same statuses. Then terminated/relaunched, recreated only the BofA filter, and repeated through the native Discover flow above. Thus the failure is neither a deep-link-only issue nor caused by the status/search combination.

Expected: account filter scope belongs to the selected ledger. Switching to crypto must use no account filter (or a filter previously chosen for crypto), never automatically reuse example's BofA restriction. Returning to a ledger may restore its own filters if implemented deliberately. Actual: the new ledger's query is narrowed by an account from the old ledger until the user discovers and clears it.

Root cause: mobile/src/screens/transactions-screen/filters/var.ts:13 creates one global makeVar initialized to NO_FILTERS, with no ledger identity. Its only writer is transaction-filters-screen.tsx:201-204. Transactions at110-126 combines that global filter with the current ledgerId. Ledger switches in common/app-links/open-app-link.ts:59 and screens/ledger-selection/index.tsx:156 update ledgerVar without rebinding/resetting account-filter state. Searching all production transactionFiltersVar references found no switch reset. Replacing the route/remounting the component cannot reset a module-level reactive variable.

Fix: make account filter state ledger-scoped, or clear the account restriction atomically when ledger identity changes. Both Discover and shared-link transitions must use the same boundary, including when Transactions is not mounted. Avoid first issuing a new-ledger query with the previous account and then clearing it after render. Preserve same-ledger tab/filter-modal navigation, explicit Reset and correct status/date composition. Cover a switch with Transactions mounted and unmounted plus a same-ledger navigation control. Do not couple unrelated screens or alter ledger permissions/backend filtering.

API and native controls: crypto-stale-filter-api.json returns total0 for the crypto ledger with account Assets:US:BofA:Checking plus cleared/pending; crypto-status-control-api.json returns total68 with the exact same statuses and no account restriction. Native clearing only Account restores Coinbase +$9,785.30, Compound +2,300.00 CUSDC and the other crypto entries. Home already shows correct crypto data before clearing, so ledger selection itself succeeded. The example account filter previously worked and same-ledger modal navigation preserved it correctly.
