# Lot reductions replace current market prices (blocked on upstream engine)

**Major · backend-cluster/ledger · blocked.** A1/A3. Carries forward the finding
from **m18**, which was abandoned as a milestone on 2026-09-10 because its
prerequisite does not exist. The full reproduction, source trace, fixtures and
controls are archived at [`done/m18/README.md`](./done/m18/README.md).

## The defect, in one line

A cost-only reduction of an existing lot is treated as new quote information, so
selling half a position reprices every remaining unit at the historical lot cost.
On the public `open_ledger/crypto-example`, BTC shows **42500** instead of the
declared **98000** quote, and all BTC holdings total **13897.50 USD** instead of
**32046 USD**. Every BQL transport (dashboard, GraphQL, REST, MCP) shares it.

## Why this is not workable in this repo today

The producer is upstream: rustledger's `extract_per_unit_price` returns a cost
fallback without knowing whether the posting reduces an existing position, and
the query price database has no lot-reduction/booking gate. Python Beancount
3.2.3's `implicit_prices` plugin excludes cost-only `MatchResult.REDUCED`
postings and keeps the correct quote — that is the contract to match.

Verified 2026-09-10 against the npm registry:

- `@rustledger/wasm` latest release is **0.24.0** (2026-09-06). m18 proved both
  0.21.0 and 0.24.0 fail the reduction fixture.
- The `1.0.0-rc.*` line is **not** newer: rc.18 was published 2026-01-14 and npm
  marks it deprecated ("Use @rustledger/wasm@0.1.0 or later"). It is an older,
  abandoned line, not a corrected artifact.

So no released or supported engine artifact fixes this. The current WASM query
interface exposes no price-policy option, and `backend-cluster/ledger/CLAUDE.md`
forbids vendoring rustledger source or WASM bytes into this public repo. The
remaining in-repo options — fabricated Price directives, a parallel valuation
engine, a blanket `units < 0` filter, or client-side compensation — were all
ruled out in m18 as either wrong accounting or leaving other surfaces incorrect.

## What unblocks it

An upstream rustledger release whose implicit-price inference is booking-aware,
or a supported engine interface for price policy. When one lands, re-promote
this note: m18's task breakdown (pin the contract in live fixtures → verify the
artifact → integrate at the engine boundary) is still the right plan, and its
`probe-reduction-prices.mjs` fixture still reproduces the failure in one run.

Publishing the upstream issue/patch is outside this repo's scope and was not
done by the QA run that found this.

# Mobile accepts a reversed custom date range and breaks Transactions

Severity: minor. Estimate: 45m. Package: mobile. A2 — date filtering should guide users to a valid range instead of replacing their journal with a server parse error.

Environment: September 10, HEAD 4574a7d8, native build 1.20260906.47 with current JS, iPhone 17e / iOS 26.5, English/System/light/default large text. Signed-in QA at https://beancount.io; public read-only open_ledger/example.

Repro:
1. Open Transactions, then the filter control beside Search. Choose Custom; defaults on this test date are Start 2026-08-10, End 2026-09-10.
2. Open Start, select October 10, 2026 in the native date wheel and Confirm. Leave End at September 10, 2026.
3. Tap Apply. It is enabled and closes the sheet without validation.
4. Transactions shows the active-filter dot and “Failed to load transactions: Failed to parse date: 2026-10-10 - 2026-09-10”.
5. Terminate/relaunch and repeat steps 1–4: same error. Filters are in-memory and reset on relaunch; the second failure was a fresh recreation, not a persisted bad query.
6. Reopen Filters, Reset, Apply: the normal journal returns.

Expected: retain the draft in the modal with a localized explanation that Start must be on or before End, and prevent invalid Apply through all activation methods. Same-day ranges remain valid. Actual: valid individual dates form an invalid interval and reach the API.

Root cause: mobile/src/screens/transaction-filters-screen/transaction-filters-screen.tsx:201-204 writes draft directly to transactionFiltersVar and navigates back. confirmDate:211-219 updates one boundary independently; Button at311 has no invalid-range gate. transactions-screen/filters/select-filter-query.ts:resolveDateRange only checks that both strings exist, then formatTimeFilter serializes them unchanged. Transactions at113 consumes toFilterQuery. The server rejects the reversed interval correctly; it is not a network outage or missing data.

Fix: validate the combined custom interval before committing it, show useful translated field/form feedback and keep the last applied filter intact on failure. Preserve valid same-day/increasing intervals and existing status/account composition. Do not silently drop the date filter or swap the user's dates. Add focused state/selector tests for reversed, same-day, increasing and incomplete ranges, plus the actual native Apply/recovery journey. Keep draft edits cancellable.

Working controls/evidence: reversed-range-api-error.json records HTTP200 GraphQL error “Failed to parse date: 2026-10-10 - 2026-09-10”. valid-date-range-api.json for 2026-08-10 - 2026-09-10 returns total0/data[] successfully, appropriate for this historical example. Native screenshots under mobile/tmp/qa-2026-09-10/: filter-banner-dismissed.jpg shows the reversed draft and enabled Apply; reversed-applied-result.jpg and reversed-fresh-result.jpg show both failures; reversed-fresh-draft.jpg confirms recreation; date-reset-recovery.jpg shows journal recovery. These ignored artifacts supplement the exact textual repro. No ledger writes, product fixes or shipping.

Instrumentation boundary: the initial attempt was blocked by a development LogBox banner and was not filed then. A native accessibility AXPress attempt returned success without submitting and is not used as proof. Dismissing the banner via its close control (logical358,783) exposed Apply; actual MCP coordinate taps at195,780 produced both retained failures. The development banner itself is not the bug.

Blast radius: one transaction-filter modal route and its Transactions consumer. resolveDateRange also supplies the active-filter count; no other production callers of toFilterQuery were found. Loading/empty behavior for valid ranges and reset recovery remain separate from validation. Account/status combination, same-day native selection, other locales, expired/denied/offline states and Android were not yet verified for this finding.

Dedupe: searched all .pm markdown including done for reversed/inverted ranges, date validation and start/end ordering, and checked open milestone scope. Completed dashboard typed-date work in w3/done/m24 concerns a different widget and parser. No overlapping mobile item. Filter query helper dates to 6b86df2c; modal history includes 29cb7bf1 local-midnight parsing, which does not validate boundary order. Current main retains the failing path.
