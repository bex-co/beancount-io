# Forced-open postings still advertise enabled row toggles

Severity: **minor**. Owner: **dashboard**. Estimate: **20–30 minutes**.
A2: Journal controls should accurately communicate which actions are available
while a newcomer explores an example ledger.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light; authenticated QA reader of public synthetic
`open_ledger/crypto-example`. Desktop 1440×1000 and fresh 390×844.
Local HEAD `a315c273`, fetched main `cc3f4c2f`, deployed SHA unverified.
The implicated component is unchanged on fetched main.

1. Open `/ledger/open_ledger/crypto-example/journal`, with Transaction selected,
   Metadata on and Postings off. Find the 2025-02-10 Coinbase sale of 0.10 BTC.
2. As a control, focus its **Toggle postings** button. Space expands its five
   postings; Enter collapses them. The transaction dialog does not open.
3. Turn the global **Postings** setting on. All posting details appear.
4. The same row still offers an enabled, focusable **Toggle postings** button,
   with `aria-expanded="true"`. Clicking it or pressing Space does nothing:
   the same five postings and expanded state remain, without any explanation.
5. Repeat from a fresh narrow page. Then follow a posting's
   `Assets:Crypto:Coinbase:BTC` account link and repeat in Account Journal:
   the same enabled no-op control appears. Turning global Postings off restores
   ordinary row expansion and collapse in both views.

The **global expansion policy is intentional**. The existing test at
`dashboard/src/features/journal/components/__tests__/journal-table.test.tsx:293–318`
explicitly requires postings to stay visible while `showPostings=true`.
Preserve that contract. The defect is the enabled toggle affordance advertising
an action that is deliberately unavailable, not the fact that rows stay open.

Root cause: `dashboard/src/features/journal/components/journal-table.tsx:125–156`
always renders a native Button with the Toggle postings name and expanded state.
`postingsVisible` at185 combines the global and individual states, while
`togglePostings` at197–200 deliberately ignores activation under the global
setting. None of its desktop/main, desktop/account or narrow callers at242,
261 and274 supplies an unavailable state.

Fix in the shared component: when global Postings forces visibility, render a
static, accessible posting count/expanded indicator, or explicitly expose the
disclosure as unavailable with an understandable reason. Keep the count and
posting details visible. When global Postings is off, restore the real native
disclosure and its existing individual state behavior. Do not change the global
setting's meaning or make its forced-open rows independently collapsible.
If replacing the child button, preserve the parent row's separate entry-opening
behavior and coherent keyboard focus when the global setting changes.

Blast radius: the shared JournalTable has two product consumers, main
`journal-page.tsx:254–257` and account `index.tsx:245–248`. Both were exercised.
The main global preference is persisted at `journal-page.tsx:92–93`; the account
view keeps its own state at `index.tsx:92`. No API or filtering contract changes
are needed. Non-transaction rows have no posting disclosure.

Acceptance: with global Postings on, all posting details remain visible and no
enabled action falsely promises a row toggle. With it off, mouse/Enter/Space
expand and collapse the intended row, without opening EntryContext. Check both
responsive branches and the account caller through the actual rendered controls;
preserve the existing forced-expansion test's behavioral assertion. Empty and
loading tables must not acquire phantom controls. Run the normal dashboard
checks when implementing.

Dedupe: searched all open/completed board records for posting toggles,
`showPostings`, expansion and disclosure, and checked open milestone summaries.
006 concerns pagination; m13 concerns server-side account type/status selection
and explicitly preserves Postings as a presentation toggle.026 concerns unnamed
statement hierarchy buttons. None covers this control state. Targeted
`git log -S 'if (!showPostings)'` traces the policy to `af5339de`; there is no
newer source repair, and no claim that the expansion policy is a regression.

The monitored narrow toggle action made no requests; the state change is local.
No transaction dialog or production write occurred. Global Postings was restored
to off in both views. Screen-reader speech, other browsers/locales and a patched
