# Keyboard Save bypasses the file editor's pending-write protection

**Severity:** minor. **Owner:** dashboard. **Estimate:** 50–60 minutes.
**A2:** a person saving a ledger file gets one pending update and can tell when
it is safe to retry.

Production `https://beancount.io`, 2026-09-08, Chrome152 on macOS,
English/light,1440×1000 and390×844. Public `open_ledger/minimax/main.bean`,
existing QA writer session. Checkout `a623f745`, fetched main `120f940d`;
implicated source unchanged, deployed SHA unverified. Only a synthetic comment
was added to isolated local buffers. All UpdateLedgerFile requests were held
and aborted before transmission. No real file or commit changed.

1. Open
   `/ledger/open_ledger/minimax/files/blob/main/main.bean?lang=en&editMode=true`.
   Insert a comment such as `; qa-20260908-file-save-pending`.
2. Press **⌘S** and hold that outgoing UpdateLedgerFile request in the browser
   guard. The toolbar becomes disabled and says **Saving…** at desktop width.
3. Press **⌘S** again while the first request is still held. A second update is
   prepared for the same path, content and original blob SHA.
4. Repeat from a fresh load, starting with the toolbar Save button. While the
   first request is pending, an ordinary pointer click on that disabled button
   correctly prepares nothing. **⌘S** still prepares a second update.
5. Abort just the first request while continuing to hold the second. The
   toolbar becomes enabled and says **Save**, even though one update remains
   pending. A pointer click now prepares a third update.
6. Repeat both sequences at390px. The buttons' text is hidden there (009), but
   the disabled state and request counts behave identically.

Expected: keyboard and pointer Save share one pending save operation. Repeated
activation cannot launch another update or report idle while the operation is
pending. A failed save retains the draft and restores a deliberate retry path.

Working controls: the disabled toolbar blocks an actual pointer click before
the keyboard bypass. In two separate retry documents, aborting a sole request
leaves editMode=true and reenables Save; a subsequent deliberate ⌘S prepares
one new request and makes the toolbar busy again. Preserve this recovery.

Six retained HTTP200 documents: two initial reproductions, two fresh expanded
controls and two sequential-retry controls. Fourteen guarded writes were all
aborted. Every request contains exactly one synthetic marker and the same
original SHA `bbcc1f30739cf27add7edf1e0ff3eea6b80ad11c`. Later real GetLedgerFile
reads return that unchanged SHA. Request content is retained only as byte
length/marker metadata, not a base64 file dump. The14 “Failed to fetch” page
exceptions follow the deliberately aborted requests; no page exception occurs
while requests are held. There are no other mutations, and all contexts close.

Root:

- `features/ledger-editor/file-editor/components/ledger-file-view/text-editor.tsx:94–99`
  handles ⌘S/Ctrl+S whenever edit mode is active and unconditionally invokes
  onSave with the editor value. It receives no pending-save state.
- The shared `text-file-view.tsx:116–125` save-and-exit callback has no
  in-flight guard. Both toolbar and TextEditor receive it at146 and168.
- `file-edit-mode.tsx:134–140` disables only the toolbar button.
- `ledger-file-view/index.tsx:112–136` starts a mutation on every invocation;
  each invocation sets isSaving=false in its own finally. Thus one failed call
  clears the shared boolean while the independently started call still waits.

The prepared mutation includes path, encoded content and the original SHA at
`ledger-file-view/index.tsx:117–125`. Backend-v2
`features/ledger/api/resolvers/ledger-resolver.mutation.ts:89–100` delegates to
`features/ledger/workflow/ledger-workflow.ts:580–620`, which authorizes the
write and forwards all three values to the ledger service. Repeated client
activation is already proven at the network boundary; this is not a query-cache
deduplication issue. No server success, duplicate commit, stale-SHA conflict or
data overwrite was exercised or claimed.

Protect the shared save-and-exit transition with a synchronous in-flight guard,
not just another disabled button or a state update that leaves a same-turn
window. Repeated activation must return before calling either the write or
onExitEditMode. Keep busy state associated with the actual active operation and
release the guard on settlement; retain the draft and allow a new explicit
attempt after failure. The guard belongs at the shared action boundary where
both input methods arrive.

Do not merely return early from the parent's onSave and let the child interpret
that resolved call as a completed save: `handleSaveClick` otherwise continues
directly to onExitEditMode. Preserve the dirty-navigation protection and
success-only exit behavior. Do not queue an automatic second write using the
stale original SHA or add a global mutation-deduplication layer.

Blast radius: TextFileView is the only EditModeToolbar caller, and
FileContentView is its only caller. Supported text files under
`files/blob/$branch/$` share the callback; read-only previews, non-text files,
entry-context editing and new-file creation have separate paths. The Cmd
branch was live-tested; Ctrl+S is source-traced only.

Acceptance: hold a real component's save promise, activate toolbar and keyboard
in both orders, and assert exactly one mutation until it settles. Verify busy
state, no early navigation, failure/draft retention, deliberate retry and a
single successful exit using a local test boundary. Exercise the real action
code. Existing `components/__tests__/ledger-file-view.test.tsx:36–86` defines
a copied “simplified TextEditor” rather than importing this implementation, so
adding another assertion to that copy would not protect the repair. Keep normal
dashboard gates. Success against production and other browsers remain unverified.
