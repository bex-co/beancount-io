# Ask network failures offer no retry of the submitted question

**Severity:** minor. **Owner:** dashboard. **Estimate:** 45–60 minutes.
**A2:** users can retry a failed first question without reconstructing it.
This regresses the retry outcome completed in `w1/m1/t005`.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light; authenticated reader of public `open_ledger/example`.
Fresh 1440×1000 and 390×844 on `/agent` and `/ask?mode=sandbox`, independently
repeated. Local `a315c273`, fetched main `5b70f569`, implicated sources
unchanged; deployed SHA unverified.

1. Open `/ledger/open_ledger/example/agent?lang=en`. Enter
   **qa-20260908-network-control** and press Enter with a browser guard
   intercepting the chat endpoint before transmission.
2. Abort that intercepted request to simulate a network failure. The browser
   reports **net::ERR_FAILED** and the page logs its caught **TypeError: Failed
   to fetch**. There is no uncaught page exception.
3. The toast says **Connection problem. Please check your internet connection
   and try again.** The question remains in the transcript, but the composer
   is empty, Send is disabled, and the page exposes zero Retry/Try again buttons.
   Repeat at both widths and on the sandbox endpoint; all four cases agree.
4. As an isolated diagnostic control, invoke `regenerate()` on the actual
   mounted SDK chat instance. It sends one further intercepted request
   containing exactly one copy of the same user question, with the same
   endpoint and ledger. Abort it before transmission too. The SDK supports
   resubmission without duplicating the question; the user interface omits it.

Expected: a persistent, named Retry action for a recognized network failure
resubmits the failed turn with its existing message parts/context, without
retyping or appending a duplicate user message. Disable it during another
request and remove/reset the error state coherently when that request starts.
Actual: only a transient toast tells the user to try again. Manual retyping is
possible after the input re-enables; this is not a claim that all future chat
input is blocked.

Root cause: `dashboard/src/features/ai-agent/pages/agent/page.tsx:120–129`
omits `error`/`regenerate` from `useChat` and handles failures only by
console/toast. Submission at305–306 clears input immediately.
The rendered message list/composer at353–393 receives no retry state/action.

Pinned `@ai-sdk/react 4.0.73`, `src/use-chat.ts:244–246`, exposes
`regenerate`/`clearError`. Pinned `ai 7.0.70`, `src/ui/chat.ts:448–478`,
retains the last user message (or removes the failed assistant response) and
uses the regenerate trigger; `:712` clears the old error on a new request,
and `:839–853` records recognized fetch failures as error state.
Both registry tarballs have verified SHA512 integrity.
The [SDK error-handling guidance](https://ai-sdk.dev/docs/ai-sdk-ui/error-handling)
shows rendering recovery using chat error state and regeneration.

Use that SDK lifecycle and the existing localized error messages/`common.tryAgain`.

browser fetch-failure TypeErrors, distinguishing them from programming errors.

throws a plain Error for non-2xx responses (`http-chat-transport.ts:203–206`).
Keep 401 navigation, forbidden/approval decisions and quota/upgrade behavior
unchanged; this sub-hour item guarantees the reproduced network-error case,
not a new universal HTTP-error taxonomy. Explicit server failure/limit/stream
cases need separate evidence if they require broader work.
