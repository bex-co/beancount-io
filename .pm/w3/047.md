# Import cell buttons ignore Space and lose focus when editing ends

Severity: **minor**. Owner: **dashboard**. Estimate: **35–50 minutes**.
A2: a newcomer should be able to review and correct imported transactions
using the keyboard with predictable button activation and focus.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light; authenticated QA reader of public synthetic `open_ledger/crypto-example`.
Desktop 1440×1000 and fresh 390×844. Local HEAD `a315c273`, fetched main
`cc3f4c2f`; implicated component unchanged there. Deployed SHA unverified.

1. Open `/ledger/open_ledger/crypto-example/import` and select this local CSV:

   ```csv
   2025-12-01,QA Coffee,Regular purchase,-4.50
   2025-12-02,QA Grocery,Regular purchase,-45.67
   ```

2. Preview shows **2 Valid**. Focus the button named
   **Edit Payee name. Current value: QA Coffee** and press Space.
   It stays focused but no input opens. It is a `DIV` with `role="button"`.
3. Press Enter. A focused Payee name textbox opens with `QA Coffee` selected.
4. Press Escape without changing anything. The textbox disappears, but
   `document.activeElement` is `BODY`, rather than the cell button.
   Enter again does not reopen the cell.
5. Refocus the cell, open with Enter and press Enter to finish unchanged.
   Focus again goes to `BODY`.
6. As a control, reopen and press Tab: the next Description cell receives
   focus correctly. Both values and **2 Valid** remain unchanged.

Desktop and the fresh narrow upload reproduce the Space and focus failures.
The monitored narrow upload and keyboard sequence produced no API requests,
page errors or console errors. No transaction was configured or submitted;
both local previews were discarded through Upload Different File.

Expected: a cell presented as a button supports Enter and Space. Enter/commit
and Escape/cancel return focus to its display control after the input is
removed, so another activation works immediately. Ordinary Tab and pointer
blur retain their chosen next focus destination. Preserve the existing
commit/cancel value semantics and current validation diagnostics.

Root cause: `dashboard/src/features/importer/components/steps/preview/editable-cell.tsx:118–137`
implements a button with a focusable div, but its keyboard handler only checks
Enter. The editing branch replaces it with an Input. The handlers at 56–79
remove that focused input on Enter/Escape without restoring focus; the effect
at 42–48 only focuses the input when entering edit mode. The native input's
ordinary Tab navigation is why the next-cell control still works.

Prefer the existing native button primitive with `type="button"`, retaining
the cell's localized name, visual styling and valid HTML content. Restore
focus after rendering the display control for explicit Enter/Escape exits.
Do not unconditionally focus on every blur or steal focus back from the next
cell. Avoid double activation or committing an Escape-cancelled draft.
Keep disabled cells unavailable to activation and out of the tab sequence.
