# Removing an earlier AI attachment leaves a later upload stuck

Severity: **major**. Owner: **dashboard**. Estimate: **45–60 minutes**.
A2: users can remove a failed attachment and recover from another upload
failure without leaving a finished request marked uploading and blocking Send.

Production client `https://beancount.io`, 2026-09-08, Chrome 152, English, light;
QA contexts at 1440×1000 and 390×844, public `open_ledger/minimax`.
This is a **controlled network-failure reproduction**: upload-URL mutations
were held and aborted before transmission. No natural production upload outage,
successful storage upload or actual AI attachment submission is claimed.
Local HEAD `a315c273`, fetched main `853a4942`, implicated source unchanged;
deployed SHA unverified.

1. Open `/ledger/open_ledger/minimax/agent`, or the same ledger's
   `/ask?mode=sandbox`. Enter **Review the attached CSV.** without submitting.
2. Select two tiny synthetic CSV files together, first.csv then second.csv.
   Hold both GenerateTempAssetUploadUrl requests so both chips show uploading.
3. Abort first.csv's request, wait for its **failed** state, then activate
   **Remove first.csv** while second.csv is still pending.
4. Abort second.csv's request. There are now zero pending upload requests,
   but its remaining chip keeps its spinner, never shows failed, and Send
   stays disabled despite the nonempty typed question.
5. Removing that stuck chip restores Send without changing the question text.

Fresh repeats reproduce the failure and recovery in both routes at both widths.
The actual fixture names are qa-20260908-first.csv and qa-20260908-second.csv;
each contains a header and one synthetic dated row, not private ledger data.
The unchanged bad state was recorded 800ms after the final abort. Source below
shows why the completed callback cannot clear it.

Working controls at both widths: retain both attachments and abort their
requests in the same order, and both chips correctly become failed with Send
enabled for the typed question. Removing only the last pending attachment
also works: the first becomes failed, late completion does not recreate the
removed last chip, and Send is enabled. This isolates removal/index shifting
from ordinary failure handling or upload concurrency alone.

Root cause in `dashboard/src/features/ai-agent/pages/agent/page.tsx:207–249`:
the upload callbacks capture `startIdx + i` and update whichever current row
has that array index. Removing the first chip filters the array, moving the
second from index1 to index0. Its completion still searches for index1 and
updates nothing. `agent-chat-input.tsx:194–200` and `page.tsx:254–257` correctly
block sending while any staged file is marked uploading; that flag is now stale.

The success callback at223–226 uses the same index comparison for objectKey.
Misassociating a successful result with a different current file is therefore
a source-traced risk, not an observed successful upload in this test. Do not
represent that unexercised branch as a production file-content incident.

Fix: assign each staged entry a stable identity when it is created, and match
both success and failure completions by that identity. Ignore completions for
removed entries. Preserve identity across batch additions/removals, including
same-named files, and use it for chip keys; changing React keys alone does not
repair the callback's captured index. Keep each file's name, preview and
objectKey attached to its own entry. Preserve preview URL cleanup and existing
upload/send guards.

Launch each upload once outside the React state-updater callback; keep the
append/completion state transformations pure. React's
[state-updater contract](https://react.dev/reference/react/useState#updating-state-based-on-the-previous-state)
requires pure updaters, and its
[list identity guidance](https://react.dev/learn/rendering-lists#keeping-list-items-in-order-with-key)
explains why removal needs stable keys. No production duplicate-upload claim
was made here; this is part of the corrected scheduling structure.

The producer `features/importer/hooks/use-temp-asset-upload.ts:29–70` requests
an upload URL, uploads the file by PUT, and returns objectKey or rejects.
The broken association is in the consuming AgentPageImpl, not the storage/API
contract. That implementation is shared by agent/index.tsx and
ask-agent/index.tsx; `/ask?mode=agent` is source-traced to the agent flow and
mode-less Ask redirects there. StagedFile is used only by this page and its
AgentChatInput/chips. No backend, import pipeline or native-mobile change is
needed for this repair.

Acceptance: the exact two-file failure/removal sequence leaves the remaining
file failed, zero uploading flags and the typed question sendable in both AI
modes at desktop/narrow widths. Preserve the keep-both and remove-last controls.
Use deferred upload promises with the actual staging logic for success/failure,
out-of-order completion, removing first/middle/last, later batches and duplicate
filenames. Assert a removed file's completion never updates another file and
that each surviving file retains its own objectKey. No live storage/model call
is needed for those success-path regression tests.

Dedupe: searched open/completed records for attachment removal races, upload
indexes, stuck uploads and stagedFiles. 062/063 cover composer naming and IME
submission; 037/049 concern different import row-state mechanisms. No existing
item covers this callback identity bug. git -S traces the index match to
`af5339de`; later sandbox sharing `6415204c` retains it. Fetched main has no fix.
