# `bea engine enable` prints “already enabled” and “Enabled …” on the same run

**Severity:** minor. **Estimate:** 10–15 minutes. **Owner:** cli. **A1:** an
agent that re-runs `engine enable beanprice` (idempotent install scripts) sees
both a note that the feature is already on and a success line claiming it was
just enabled — JSON also has no `already_enabled` / unchanged flag.

Found 2026-09-16 by continuous CLI QA against `main`, HEAD `337f5bbf`,
`uv run bea` 0.2.0, Darwin 25.5.0 arm64, isolated config/cache.

## Repro

```sh
bea engine enable beanprice   # first time may install
bea engine enable beanprice
# stderr/stdout includes both:
#   Engine feature 'beanprice' is already enabled.
#   Enabled 'beanprice' in the managed engine. It is not installed into the bea frontend.
# exit 0

bea --json engine enable beanprice
# same payload as a fresh enable — no "already_enabled": true
```

## Expected

Idempotent re-enable: only the “already enabled” note (or JSON
`already_enabled: true` / `changed: false`), not a second success claiming a
new enable. First-time enable keeps the current success text.

## Actual

`provision.enable_feature` correctly notes and returns early when present, but
`engine_enable` always prints `Enabled '…'` afterward (and always `emit`s the
same JSON shape).

## Root cause

`cli/src/cli/engine/provision.py` (~177–180) returns early after the note.
`cli/src/cli/commands/engine.py` (~74–84) ignores that early-exit case and
always calls `output.success("Enabled …")`.

## Fix

Have `enable_feature` return whether it changed anything (or compare before/
after), and only print success / set `changed: true` when work was done.
Regression: second `enable beanprice` shows only the already-enabled note;
JSON includes `already_enabled` or `changed: false`; first enable unchanged.
