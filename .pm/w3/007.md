# Holdings by Cost Currency combines different units into one book value

**Severity:** major — displayed and exported financial values are wrong.
**Estimate:** 45–60m for a dashboard query correction and focused validation;
keep this mitigation as an inbox item. **Pillar:** A2 — the public example must
demonstrate trustworthy holdings and exports.

Reproduced 2026-09-07 on production, Chrome 152, English/light, 1440×1000 and
390×844, authenticated reader of `open_ledger/example`. Source/fetched main
`57fc1c27`; deployed SHA unverified.

1. Fresh-load `/ledger/open_ledger/example/holdings`.
2. Select **Holdings by Cost Currency** (the View combobox at narrow width).
3. Inspect the first row. Units and market value each contain **906.58 USD**
   and **-13 VACHR**, while book value shows only **893.58 USD**.
4. Export CSV on desktop. The same row contains `893.58 USD` as book value.
5. Repeat from fresh desktop and narrow loads: same result.

Expected: a position without cost retains its own unit in the book-value
inventory. USD and vacation hours must not be added together. Actual: 13 hours
are subtracted numerically from the USD amount and the hours unit disappears.
The real `QueryShell` HTTP 200 response already contains the wrong value:

```json
[
  { "USD": "906.58", "VACHR": "-13" },
  { "USD": "893.58" },
  { "USD": "906.58", "VACHR": "-13" },
  "0"
]
```

The columns are units, book_value, market_value and unrealized_profit_pct.
The backend reports book_value's dtype as Amount, while units/market_value
are Inventory. This is not a CSV or display-rounding error.

Root cause: `dashboard/src/features/ledger-data/holdings/holdings-statement.ts:37–45`
groups all costless positions together by null `cost_currency`, then evaluates
`cost(sum(position))`. The pinned `@rustledger/wasm` 0.21.0 implementation's
[COST inventory branch](https://github.com/rustledger/rustledger/blob/v0.21.0/crates/rustledger-query/src/executor/mod.rs#L854-L894)
sums the numeric costs/units into one decimal and labels it with the first
currency. The repo's ledger shell calls that engine at
`backend-cluster/ledger/src/foundation/rustledger/engine.ts:698`; its mapper
`features/ledger/service/ledger-shell-mappers.ts:199–205` preserves the already
incorrect Amount, and gateway `ledger-shell-service.ts:63–77` forwards it.

Independent local engine probes confirm the boundary: a balanced synthetic
ledger containing 100 USD and -3 VACHR returns **97 USD** for
`cost(sum(position))`, but separate USD/VACHR inventories for
`sum(cost(position))`. Both npm artifacts 0.21.0 and 0.24.0 produce this result
without errors; an upgrade to that checked version alone is not a repair.
No dependency or lockfile was changed during QA.

Concrete dashboard fix: use `sum(cost(position)) as book_value` for the
cost-currency grouped query, preserving typed per-unit inventories. The exact
production query with only that expression changed returns
`{"USD":"906.58","VACHR":"-13"}` for book value; the costed USD group's
`105919.46944` book value and `116742.90828` market value remain unchanged.
The same public two-account control grouped by currency also preserves each
unit. Do not flatten the returned map or invent an exchange rate.

Acceptance: the first row and CSV retain both units with those exact values;
the costed control group and ordinary account/currency tabs remain correct;
empty/zero holdings remain honest. Verify actual query output and export
values, not merely that a query string contains a function name. The same
expression appears in all four holdings queries, but the other three group
by currency/cost currency and did not show this mixing in the exercised
fixture. Scope any additional rewrites to separately verified cases.

Dedupe: searched all open/completed board records for holdings, book value,
cost currency and mixed units; no overlap. Statement-export work
`w4/done/m1` explicitly excludes Holdings. Targeted history finds the query
at `af5339de` and no repair on fetched main. The underlying arbitrary-BQL
engine defect remains upstream even after this dashboard mitigation; do not
claim all BQL is repaired or add a query-rewriting shim/fork in this task.
User-authored BQL can reach the same defect. Other reporting APIs, all market
valuation edge cases, and a patched dashboard are unverified.
