# Import configuration rounds real BTC amounts to zero

Severity: **major**. Owner: **dashboard**. Estimate: **35–50 minutes**.
A2: people importing cryptocurrency can review the actual amounts before
assigning accounts and submitting transactions.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light; authenticated reader of public synthetic `open_ledger/crypto-example`.
Fresh 1440×1000 and 390×844. Local HEAD `a315c273`, fetched main `cc3f4c2f`;
implicated code is unchanged there. Deployed SHA unverified.

1. Open `/ledger/open_ledger/crypto-example/import` and choose this local CSV:

   ```csv
   Date,Payee,Description,Amount
   2025-12-01,QA Crypto Withdrawal,Small crypto transfer,-0.00012345
   2025-12-02,QA Crypto Deposit,Smaller crypto transfer,0.00000001
   ```

2. Preview reports **2 Valid**, with amounts **-0.00012345** and **1e-8**.
3. Continue to Configure, wait for the currency control, and select **BTC**.
4. The two Amount cells show **-0.00** and **0.00**. At 390px, scroll the table
   horizontally to read the Amount column. Neither cell conveys its nonzero
   transaction value.
5. Back restores the same full preview values. Upload Different File clears
   the local preview. Fresh desktop and narrow repeats agree.

Expected: the review table preserves meaningful fractional commodity amounts
and their signs. Zero must not represent a nonzero amount merely because the
selected unit has more than two fractional digits. Read-only inspection of
this local form confirms amounts remain `-0.00012345` and `1e-8`; this finding
is about the final review display, not demonstrated loss in stored data.

Root cause: `dashboard/src/features/importer/components/steps/configure/account-mapping-table.tsx:310`
unconditionally renders `txn.amount.toFixed(2)`. Its sole production caller,
`transaction-config-form.tsx:254`, initializes the original number at line 123
and maps it unchanged into the submit object at line 167. The rounding belongs
to the dashboard table; no API or backend repair is indicated.

Use an amount display that retains the significant fractional value for the
selected commodity, including small positive and negative values. Keep the
original form/submission number unchanged. The common `formatNumber` and
`formatAmount` helpers also cap or truncate decimals, so directly substituting
either would retain this defect. A new dependency is unnecessary.

Working control: a local USD CSV with amounts **-4.50** and **-45.67** shows
**-4.50** and **-45.67** in Configure, and Back/clear works. Both BTC repeats
record no page/console errors or API requests during currency selection and
review. Source and target accounts were left unset; their missing-account
feedback is expected. Import and AI Fill were never invoked.

Acceptance: both fixtures display the same monetary quantities in Preview
and Configure at desktop and narrow widths, including **-0.00012345 BTC** and
**0.00000001 BTC**, without invented zeroes. Keep normal USD values readable,
preserve real zero and sign, and verify that rendering does not change form
values. Add focused behavior coverage for the nonzero fractional boundary and
run the dashboard gates when implementing. No loading/error behavior needs
to change; failed account-loading and actual submission remain unverified.
