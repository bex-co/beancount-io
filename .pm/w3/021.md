# Read-only mobile transaction details expose inert edit and delete controls

**Severity:** minor — a public reader is offered actions that silently do
nothing. **Estimate:** 20–35m, header permission gate and focused coverage.
**Pillar:** A2 — public-example exploration presents usable, honest controls.

Recovered from the concurrent native QA record after an inbox-number collision
with dashboard `w3/013`. This preserves that existing finding; it is not a new
dashboard reproduction. The native report and preserved screenshots were
checked when restoring this note.

Native QA environment: 2026-09-08, local build 1.20260906.47, source `a315c273`,
production API, Expo MCP, iPhone 17e / iOS 26.5, English/light. Authenticated
reader of synthetic public `open_ledger/example`, permissions
`{admin:false,pull:true,push:false}`. Native login survived relaunch.

1. Select the public example through discovery and open Home.
2. Open the Hoogle payroll transaction dated September 7, 2017 from recent
   activity. Its checking posting/hero is +$2,550.60.
3. The transaction header displays a pencil and an ellipsis menu containing
   Delete. The native run recorded that the pencil leaves the same detail
   screen visible; these write actions are unavailable to the reader.
4. The run repeated the header through Home after relaunch and again after
   restarting Metro with `--clear` after an unrelated DOM-editor cache failure.
   The preserved clean-cache
   screenshot still exposes the pencil and ellipsis; the menu capture shows
   Delete. Home correctly omits its add action for the same reader.

Expected: omit unavailable transaction write controls for a reader while
preserving the detail/source/postings and account navigation. Authorized
writers retain working edit/delete controls when source context is ready.

Root cause in **mobile**:
`src/screens/transaction-detail-screen/transaction-detail-screen.tsx:382–423`
renders `headerRight` whenever `sha256sum` exists, ignoring `canWrite`.
The handlers at 271–277 correctly return immediately when `canWrite` is false,
so this is an inert UI affordance, not a demonstrated unauthorized mutation.
The permission is already available at 247, and the source body uses it at 375. The working Home gate is at `src/screens/home-screen/home-screen.tsx:110`.

Fix the header gate to require write access as well as the existing source
readiness. Preserve handler guards, deletion confirmation and backend
authorization. Clear header actions when permissions change; do not grant
write access or make public examples editable to resolve the UI discrepancy.

Acceptance: public readers see neither the pencil nor a Delete-only menu;
the transaction and posting links remain usable. Check a writer with source
context, a writer awaiting/missing context, and a permission transition through
the real header options. Keep guarded handlers as defense in depth. No actual
production transaction mutation is needed for the reader regression.

Dedupe: the original native run checked `w4/done/m4` public-ledger write gates;
the detail header was omitted. Existing `w3/m11` concerns dashboard source
metadata and read-only editor controls, a separate consumer. Source history
shows `221f5a4e` adding the `canWrite` handler/body guards without gating this
header. No historical working header gate was established.

Unverified: writer mutation lifecycle, expired/denied sessions, network outage,
dark mode for this control, Android and physical hardware. The native log
capture returned no text and does not establish complete runtime-log coverage.
No write, fix or shipping is included in this recovery.
