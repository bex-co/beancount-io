# Browser printing keeps a previous statement after filters change

**Severity:** major — the PDF contains the wrong reporting period and financial
values. **Estimate:** 45–60m, current print-document wiring and shared regression
coverage. **Pillar:** A3 — portable statements agree with the report being shared.

Reproduced 2026-09-08 on production, Chrome 152, English/System-light,
authenticated reader of synthetic `open_ledger/example`, source `a315c273`;
deployed SHA unverified. Desktop 1440×1000; Income Statement also verified at
390×844 after selecting the period on desktop. Monthly / At Cost, no account
or expression filter. PDFs use A4.

1. Fresh-load `/ledger/open_ledger/example/balance-sheet?time=2017-09`.
2. Change the header Time selection to `2016` and wait for the report to settle.
   The URL ends in `?time=2016`.
3. Export → Markdown report correctly gives **As of December 31, 2016**,
   Total Assets **80,149.80683 USD** and **25 VACHR**.
4. Print through the browser directly, without first invoking the app's Print
   menu item. QA exercised Chromium's PDF generation and print media. The PDF
   instead shows **As of September 30, 2017**, Total Assets **109,529.33944 USD**
   and **-13 VACHR**. Text extraction confirms the saved PDF's values.
5. A second fresh Balance Sheet journey repeats the mismatch.
6. Repeat on Income Statement: begin at `?time=2017-09`, then select `2016`.
   Markdown exports the full 2016 period, but browser PDF still shows September
   2017 and net income **2,354.89 USD**. Reload the same `?time=2016` URL and
   browser PDF correctly changes to January–December 2016 and **35,792.16 USD**.

Expected: browser printing reflects the current settled statement, including
period, filters, conversion, values and units. Reload should not be needed to
clear an obsolete printable document. No assertion here says the app's own
Print menu produces the stale result; it takes a different refresh path.

Authenticated GraphQL `getLedgerBalanceSheet` for `time:"2016"`,
`interval:"monthly"`, `conversion:"at_cost"` succeeds with HTTP 200 and
`assetsHierarchyData.balanceChildren` `{USD:"80149.80683",VACHR:"25"}`.
This agrees with the current Markdown export. Fresh browser console: zero
errors. There is no API, precision or sign-conversion failure in this repro.

Root cause in **dashboard**: `features/reports/export/statement-export-menu.tsx:54`
initializes `printDocument` with `useState(document)` and renders that stored
snapshot at 171. New report props do not update it. Only the app menu handler
sets a new snapshot at 120–130. In contrast, CSV/Markdown use the current
`document` through `runAction` at 57–105. `statement-print.css:7–25` hides the
app and renders the portal for browser print media, exposing the old snapshot
even when the menu handler was never called. A fresh route mount initializes
the snapshot correctly, explaining the reload control.

Fix: keep the printable content derived from the current report document;
avoid a persistent duplicate financial-data snapshot that only one print
entrypoint refreshes. Refresh generation time for browser/menu printing without
changing period or data. Preserve deliberate loading/empty/error handling and
do not label a previous result as the newly requested scope. No refetch, backend
change or new PDF dependency is required.

Blast radius: all three `StatementExportMenu` callers — Balance Sheet content
at 163, Income Statement content at 210, and Cash Flow content at 199. Balance
Sheet and Income Statement were independently reproduced. Cash Flow is a
shared-code exposure, not a separately exercised stale-print result.

Acceptance: after changing Time on the two exercised reports, browser PDFs
and Markdown have the same current period, values and units, without reload.
The app menu still prints the current statement and refreshes generation time.
Cover the real portal before/after updated report props and browser print
events, including empty/failed transitions; retain duplicate-action and error
feedback behavior. Existing tests that only spy on `window.print` do not prove
that the printed content follows updated props.

Dedupe: searched all open/completed records for stale printing, browser print,
beforeprint and printDocument. `w4/done/m1` introduced current-filter statement
exports; this is an uncovered direct-browser-print path. `w2/done/m22` exercised
statement exports but did not change this state. Targeted history shows the
snapshot behavior already in `d162671f`, with no later fix or overlapping open
item. No historical working implementation establishes a later regression.

Unverified: physical printer output, Cmd/Ctrl+P interaction, the native print
dialog's final preview, Cash Flow repetition, locale-specific output, expired
sessions and network failure. The app menu opened real blocking print dialogs;
QA dismissed them by closing only its public-report tabs and opened a fresh QA
tab. Browser PDF and print-media checks above completed independently. No
financial responses or window.print implementation were mocked.
