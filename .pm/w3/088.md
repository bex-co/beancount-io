# Try Again resets the error display without retrying the failed ledger read

**Severity:** minor. **Owner:** dashboard. **Estimate:** 40–60 minutes.
**A2:** after a recoverable read failure, the advertised Retry action loads
the ledger again without requiring the visitor to reload the page manually.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English/light,
1440×1000 and390×844, existing QA session. Public `open_ledger/example` and
`open_ledger/crypto-example`. Local HEAD `a315c273`, fetched main `afb36a9b`,
relevant source unchanged; deployed SHA unverified.

1. Start on Example Journal. In an isolated browser context, navigate using
   the mounted app router to the public Crypto Example overview.
2. For controlled network-failure testing, abort only the first `GetLedger`
   read for Crypto Example before transmission. The ledger error page shows
   **Network Connection Failed** and **Try Again**. All later reads are allowed.
3. Click **Try Again**. The same error remains and no second `GetLedger`
   request is made. Both widths and fresh repeats reproduce this.
4. Invoke the mounted router's existing `invalidate()` as a diagnostic control.
   A new `GetLedger` reaches the real backend, returns HTTP200 with ledger data
   and no GraphQL errors, and the real overview replaces the error page. No
   successful response is fabricated. Four controlled cases recover this way.
5. On the real missing-ledger failure in087, four guest/QA controls likewise
   show zero new API operations or document requests after clicking Try Again.
   Those permanent denials establish the no-op; the public transient-failure
   cases above establish that recovery was actually available.

Root: `common/components/ledger-layout/ledger-route-error.tsx:13,36–39` forwards
the error boundary's `reset` as `LedgerLayoutError.onRetry`. In pinned
`@tanstack/react-router`1.167.0, `CatchBoundary.reset()` only clears the boundary's
React state; `Match.tsx:275–297` immediately throws the route match's retained
error again. It does not rerun the loader. Pinned router-core1.167.0's
`invalidate()` at2671–2712 explicitly clears error/not-found match state and
calls `load()`, matching the successful live diagnostic control.

Wire Retry to the router's actual loader invalidation/reload lifecycle, with
the boundary reset coordinated as required by that API. Apply the same caller
correction to `common/root-route/error-page.tsx:111`, whose Try Again also calls
only `reset`; this root fallback is source-proven, not separately live-tested.
Keep the user on the same path/search while the read retries, and keep the
action usable if another failure occurs. Avoid duplicate retry submissions.

Do not modify the shared LedgerLayoutError presentation to force a global
reload: its other caller, `common/components/ledger-layout/index.tsx:35–61`,
already provides a real Apollo `refetch()` through `handleRetry`. That mounted
query-error path is a source-audited correct callback. Keep appropriate behavior
for both route-loader and mounted-query failures, and preserve087's intended
auth/unavailable outcomes when a retried operation is denied.

Scope is an explicit read retry. Do not add automatic retries, an Apollo-wide
RetryLink, SDK upgrades, write resubmission or cache clearing across unrelated
ledgers.003's committed-but-timed-out bulk write and081's AI-chat retry are
different operations with different safety requirements.
