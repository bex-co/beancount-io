# Smart Import reverses the bank movement when preparing expense and income postings

Severity: **major**. Owning package: **dashboard**. Estimate: **45–60 minutes**
for the amount-to-posting conversion and meaningful importer regression coverage.
A2: a first bank import must preserve the direction of its cash movements.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, System/light;
authenticated QA reader of public `open_ledger/crypto-example`. Desktop
1440×1000 and a fresh narrow 390×844 journey. Local `a315c273`; fetched
`origin/main cc3f4c2f` has no difference in the implicated importer files.
Deployed SHA unverified.

**Evidence boundary:** this is the real production client's prepared request,
captured under local interception. Every request was unconditionally aborted
before network access during submission. No production import was performed,
and server acceptance or persisted ledger effects are not claimed. Both runs
had zero service workers and exactly one aborted `BulkEntries` request. The
page was navigated to `about:blank` while the guard remained installed, then
the guard was removed, discarding the wizard and any pending retries.

1. Open `/ledger/open_ledger/crypto-example/import?lang=en`. The upload reference
   explicitly says **Negative values represent expenses**, with `-4.50` for
   coffee and `2500.00` for salary. Upload:

   ```csv
   Date,Payee,Description,Amount
   2025-12-01,QA Sign Expense,Synthetic cash expense,-4.50
   2025-12-03,QA Sign Income,Synthetic cash income,2500.00
   ```

2. Preview shows **2 Valid**, with correct amounts **-4.5** and **2500**.
   Continue to Configure; both signs remain correct there.
3. Select source **Assets:Bank:Checking**, described as “The bank account these
   transactions came from”, and currency **USD**. Assign
   **Expenses:Crypto:Fees:Trading** to the expense and
   **Income:Crypto:CapitalGains:LongTerm** to the income. These are existing
   public-fixture accounts. Do not use AI Fill.
4. Install the unconditional network-abort guard before clicking **Import 2
   Transactions**. Inspect only the matching synthetic `BulkEntries` variables.
   Repeat the whole upload/configuration from a fresh narrow page.

Both repeats prepare these posting amounts:

| Row              | Expected bank / target USD | Actual bank / target USD |
| ---------------- | -------------------------- | ------------------------ |
| Expense `-4.50`  | **-4.5 / +4.5**            | **+4.5 / -4.5**          |
| Income `2500.00` | **+2500 / -2500**          | **-2500 / +2500**        |

The payload keeps the selected accounts, dates, payees, descriptions, USD and
cleared flag correctly; each pair balances to zero. Balancing alone therefore
does not detect this reversal. The import's documented convention describes
the signed bank movement, which must remain on the source posting.

Root cause: `dashboard/src/features/importer/hooks/use-import-submit.ts:34–53`
sets source units to `(-txn.amount).toString()` and target units to
`txn.amount.toString()`. It assumes a positive expense magnitude, despite the
signed input contract. The CSV parser preserves the sign;
`components/steps/configure/transaction-config-form.tsx:116–125,155–174`
copies the signed amount into `ImportTransaction` unchanged. Its sole
submission caller, `components/import-workflow-container.tsx:30–38`, forwards
that object directly to the hook. `graphql/query/journal.graphql:9–14` serializes
the already prepared postings.

Server source control: backend-v2
`src/features/ledger/api/resolvers/ledger-entry-resolver.mutation.ts:265–277,321–333`
passes the transaction through to the shared entry service; that service's
`ledger-entry-service.ts:248–278` preserves `posting.units.number`. It has no
CSV/source-account semantics with which to correct the client. This is a
dashboard fix; generic GraphQL/REST/MCP structured-entry signs must remain
caller-controlled. No server mutation endpoint was invoked to test it.

Fix: for the existing signed-movement contract, retain `txn.amount` on the
source and negate it on the target. Keep the same source/target account choices
and preserve signed refunds, income, transfers and zero without applying an
absolute value or inferring sign from an account name. Document the meaning at
the `ImportTransaction` boundary so all parser results feed the same contract.
The LLM parser also reaches this hook and copies `row.amount`; its provider
output/sign normalization was not exercised and must be checked before
claiming all file formats work. This finding does not request AI calls or a
new format-conversion feature.

Acceptance: exercise the actual CSV-to-config-to-submission path with the two
reproduced rows and assert the exact signed postings, alongside a positive
expense refund and a signed transfer control. Preserve dates, currency,
selection and atomic-result handling. Replace the existing hook tests at
`hooks/__tests__/use-import-submit.test.ts:129–191`, which construct a positive
expense and explicitly assert the reversed convention. A test that merely
asserts zero-sum postings is insufficient. Run dashboard format, lint, tests
and build. Live persistence remains a separate authorized verification.

Adjacent states: both local previews and configuration load normally, with
correct signs and validity. The guard produces the expected **Import Failed /
Connection problem** result and `ERR_BLOCKED_BY_CLIENT`; this synthetic network
failure is not a product bug. No AI parse, storage upload, bank linking or real
write was performed. The wizard was cleared and the ordinary upload page
restored after both runs. Other browsers, locales and actual write permissions
remain unverified.
