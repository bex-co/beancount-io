# Signup leaves focus on Create account when the username is invalid

Severity: **minor**. Owner: **dashboard**. Estimate: **35–50 minutes**.
A2: newcomers who submit an invalid username are taken to the field they need
to repair, as they already are for invalid email and password fields.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, light.
Fresh signed-out browser contexts at 1440×1000 and 390×844. Local HEAD
`a315c273`, fetched main `cc3f4c2f`; implicated source is unchanged there.
Deployed SHA unverified. The authenticated QA session was kept separately.

1. Open `/auth/sign-up` and supply a syntactically valid synthetic email and
   matching synthetic passwords of at least six characters.
2. Enter `qa-invalid-name` in **Username**; hyphens are intentionally invalid.
3. Focus **Create account** and press Enter. After validation settles, the only
   error is **Username can only contain lowercase letters, numbers, and
   underscores**, but focus stays on Create account.
4. Fresh desktop and narrow repeats give the same result. The Username field
   has neither `aria-invalid` nor `aria-describedby`; its error has no ID,
   alert role or live region. Its accessibility snapshot contains the label,
   placeholder and synthetic value, without the error association.

Expected: an invalid visible Username receives focus after a rejected submit,
and its validation message is associated with the field. The error is visibly
on screen at both tested widths, so this is not a claim that it is hidden or
that keyboard users cannot manually return to the field.

Working controls: an empty submit focuses Email address. Repairing the username
to `Qa_valid_name` normalizes it to `qa_valid_name` and clears its error; making
the password too short then submitting focuses Password. All validation stays
local: zero signup requests, zero blocked mutations, zero page/console errors
in the fresh repeats. A guard prevented non-read API calls, but was never hit.
No registration, email or OTP was created.

Root cause: `dashboard/src/features/auth/components/register-form/index.tsx:74–92`
uses `watch`/`setValue` for Username, and its input at lines157–165 never receives
`register("username")` or a Controller field ref. Other inputs register their
refs. The error at lines171–173 is an unassociated paragraph. The common Input
already forwards its props to the native input; it does not need a global fix.

The lockfile pins React Hook Form7.71.0. Its `setValue` only updates the value;
`register` adds the mounted field and ref; the enabled `_focusError` traverses
registered mounted fields and calls their refs' `focus`. Verified against the
downloaded package's ESM implementation at lines1768,1904,2060 and2146, matching
the npm tarball's registry integrity and the
[tagged upstream implementation](https://raw.githubusercontent.com/react-hook-form/react-hook-form/v7.71.0/src/logic/createFormControl.ts).

Fix the visible Username's registration/ref while preserving lowercase
normalization, the generated default, validation rules and submitted value.
Give its error a stable ID and wire the invalid state and description to the
field. Let the existing form validation focus the first invalid registered
field; avoid an effect that steals focus while the user is typing.

Blast radius: the standalone `/auth/sign-up` form, reached through `/sign-up`,
and the shared registration forms in `/oauth/consent` and
`/oauth/identity-consent`. The OAuth callers are source-traced only.
`/oauth/mobile-consent` deliberately sets `hideUsername`; preserve its generated
hidden value and existing signup behavior. No auth API change is indicated.

Acceptance: a settled username-only invalid submit focuses Username and exposes
its error association; a repaired username retains normalization and clears
the error. Empty-form/email and password focus controls keep working. Add a
focused component regression using the real form/ref behavior and preserve the
existing hidden-username submission test. Valid signup, OTP, consent sessions,
screen-reader speech, other browsers/locales and patched behavior are unverified.

registration errors and scanned all open milestone summaries. 030 concerns
