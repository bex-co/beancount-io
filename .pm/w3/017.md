# Mobile merchant transaction counts actually count postings

**Severity:** major — merchant history is materially overstated. **Estimate:** 45–60m, two mobile BQL count statements and meaningful query coverage. **Pillar:** A2 — newcomers can trust merchant history summaries and frequency ordering.

Reproduced 2026-09-08 using local native build 1.20260906.47, source a315c273, freshly cleared Metro cache, Expo MCP, iPhone 17e / iOS 26.5, English/light. Authenticated reader of synthetic public `open_ledger/example` on https://beancount.io.

1. Select the public example, open the ledger drawer, and choose Merchants.
2. Hoogle says **1228 transactions**; Chichipotle says94, China Garden92 and BANK FEES66.
3. Open Hoogle. Its detail header also says **1228 transactions**, above an ordinary list of payroll transactions dated September7, August24, August10, etc.
4. Terminate/relaunch, reopen drawer → Merchants. Hoogle again says1228. Reopen the detail for the same result.

Expected: Hoogle has **71 transactions**, Chichipotle47, China Garden46 and BANK FEES33. Actual counts vary with the number of postings per transaction, so dividing by2 would not fix payroll or other multi-posting entries.

Live authenticated evidence:

- The exact app directory query `SELECT payee, count(*) as transaction_count, min(date) as first_date, max(date) as last_date WHERE payee != '' GROUP BY payee ORDER BY transaction_count DESC` returns Hoogle1228 with dates2015-01-01 through2017-09-07.
- `GetLedgerJournal` with Transaction type, filter `Hoogle`, offset0 and limit100 returns total71 and71 rows, all exact Hoogle payees. Those71 rows contain **1228 postings** in total. Thus this is not paging, case merging or missing transactions.
- Read-only corrected directory query, inserting `FROM #entries` before WHERE, returns Hoogle71 and the other expected counts above, preserving first/last dates.
- Read-only corrected detail query `SELECT count(*) as transaction_count, min(date) as first_date, max(date) as last_date FROM #entries WHERE payee = 'Hoogle'` returns `[71, "2015-01-01", "2017-09-07"]`.
- `SELECT DISTINCT id, payee, date WHERE payee = 'Hoogle'` independently returns71 rows. Do not propose `count(DISTINCT id)` as a drop-in fix: this deployed dialect rejects that aggregate syntax.

Root cause in **mobile**: `src/screens/merchants-screen/selectors/aggregate-payees.ts:49–50` aliases posting-row `count(*)` as transaction_count. `aggregatePayees` at108/119 accepts it, sorting by it at190/195; `merchant-row.tsx:137` labels it as transactions. `src/screens/merchant-detail-screen/selectors/merchant-stats.ts:35–40` independently repeats the same posting count for the exact payee; `merchant-detail-screen.tsx:454` renders it. Both need the entries table for transaction metadata aggregation.

Producer trace: ledger `src/features/ledger/service/ledger-shell-service.ts:85–94` loads the file map and forwards the BQL. `src/foundation/rustledger/engine.ts:638–698` executes that supplied query through the WASM ledger. The server correctly counts rows of the requested relation; the public native consumer chose the wrong relation. No API/schema or engine change is needed. BQL's posting-oriented default is also described in the upstream [double-entry data model](https://github.com/beancount/docs/blob/master/docs/the_double_entry_counting_method.md).

Fix: add `FROM #entries` to **both** the fixed directory rollup and `buildMerchantMetaBql`, using the successfully exercised query forms above. Preserve the payee escaping, empty-payee filter, case-folding policy, date span and sorting contracts. Keep per-currency totals and recurring detection on their existing posting-aware queries; changing those relations would break monetary aggregation. Do not cap counts to the detail screen's loaded page or collapse separate same-day/same-payee transactions by date.

Acceptance: the exercised directory/detail/relaunch journey shows71 Hoogle transactions and matching date bounds; BANK FEES shows33. Add a meaningful check that executes the actual count queries against a small fixture with unequal posting counts, two transactions sharing a date/payee, and an empty payee. Both count consumers must count transactions once, and the directory must use corrected counts for frequency ordering. Existing alias/string-presence tests do not prove the counted relation. Preserve loading, empty/error recovery, and exact-payee escaping.

Blast radius: two count-query builders and one production consumer each: Merchants directory and merchant detail routes. `count(*)`/transaction_count searches found no additional count builders in these merchant modules. The live journal and corrected BQL queries are working controls. The monetary totals and recurring toggles were not changed or submitted.

Dedupe: searched open/completed board records for merchants, payee rollups, counts and postings; scanned all open milestone summaries. No overlapping item found. `w3/m14` is an unrelated dashboard Statistics filter/count scope issue. Targeted `git log -S 'count(*) as transaction_count'` identifies `76b9ce33` (directory) and `2b36b2cc` (detail); no later relation fix is present. No verified prior correct transaction counts establish a historical regression.

Unverified: patched UI, other locales/OSes, physical hardware, live case variants, denied/expired sessions and network failures. This report schedules a fix; it does not implement or ship it. No production ledger or recurring-setting mutation was made.
