# Stop offering broken links for generated mobile transactions

Severity: minor. Estimate: 35–50m, mobile only. A3: links offered by public example ledgers should open usable destinations.

Environment: September 11, 2026; https://beancount.io; HEAD f1965988, mobile 7538fb0d; native io.beancount.ios 1.20260906.47 on iPhone 17e / iOS 26.5. Signed-in QA reading public open_ledger/minimax (pull/push true, admin false); no production writes or outbound sharing performed.

Repro: open the public MiniMax Journal, tap the June 29, 2026 padding transaction for 3,994.853 MUSD, then open its ellipsis menu. Detail renders both equity postings and correctly hides Edit/Delete, but offers Share link and Copy link. Its real hash is 508f22c1ceccbfb12344da6959fec867. After relaunching and verifying Home, open beancount:///ledger/open_ledger/minimax/entry/508f22c1ceccbfb12344da6959fec867. The settled destination says “No entry context data available.” Reproduced on fresh PIDs 95866 and 96484; the second capture has the development banner dismissed. Link destination was exercised with simctl, not an external share recipient or clipboard paste.

Expected/actual: do not offer an entry-specific export action whose destination cannot load that entry. The row works only while its complete transaction is stashed in memory; a recipient or a fresh process has no such stash. Ordinary source-backed entry 864c29173af59ac1164edd8214ad41c7 opens correctly through the same link route, with eight postings.

Cause: mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:266–274 requests GetLedgerEntryContext when the stash is cold, regardless of generated status; :323–334 can reconstruct the entry only from that context response. The flags in selectors/select-transaction-detail.ts:8–20 correctly identify generated entries as lacking editable source. Yet detail :421 and :453 onward expose the menu and its Share/Copy actions for every hash, and :345 builds the entry URL unconditionally. resolve-app-link.ts:149–157 routes entry links directly to this screen. The actual API context request for this hash returns HTTP 200 with GraphQL “Ledger resource not found”; GetLedgerJournal contains the real P transaction and both postings. This is not a missing ledger or an auth failure.

Scoped fix: suppress entry-specific Share/Copy actions for generated transactions using the existing generated-source predicate, independently of canWrite; omit the empty ellipsis menu. Preserve ordinary entry sharing for read-only readers, writer Edit/Delete gating, and all generated detail/posting navigation. Add a meaningful selector/render test distinguishing a P entry, an ordinary read-only entry, and a writable source-backed entry; verify the native menu control. Resolving generated hashes independently of source context would be a separate enhancement if full generated-entry sharing is desired; do not quietly export a ledger link labeled as an entry link or invent editable source context.

Blast radius: Home recent rows, Transactions, account detail, Reports recent entries, and merchant detail all use openTransactionDetail and this shared screen. Journal generated-row navigation and ordinary entry-link control were exercised; other callers are source-traced. Cold links already distributed still lack generated-entry resolution; this scoped correction prevents new unusable exports. Other generated flags, Android, denied/expired/offline responses and physical-device behavior remain unverified. Loading settles into the no-context message; no native crash observed. Bounded JS error capture was empty, not proof of no native/network errors.
