# Gallery search retains stale selections and ignores Escape on empty results

**Severity:** minor — a cleared search can navigate to a stale ledger.
**Estimate:** 45–60m including the keyboard clear/selection and empty-result
Escape regressions in the same component.
**Pillar:** A2 — searching and clearing the public-ledger gallery must produce
predictable navigation.

Reproduced 2026-09-07 on production, Chrome 152, English/light, 1440×1000 and
390×844, authenticated QA account. Source/fetched main `57fc1c27`; deployed
SHA unverified. Only the synthetic public crypto example was selected.

1. Fresh-load `/ledger-gallery` and enter `crypto-example`.
2. Wait for the `crypto-example open_ledger/crypto-example` option.
3. Press ArrowDown to highlight it, Tab to **Clear**, then Enter to clear.
4. The input is empty and focused, but the dropdown remains expanded with
   the old option still highlighted. This persists after 700ms, beyond the
   component's 300ms debounce.
5. Press Enter in the empty input. The browser navigates to
   `/ledger/open_ledger/crypto-example`.
6. Fresh desktop/narrow repeats produce the same cleared-input navigation.

Expected: clearing removes the active selection and closes/inactivates old
results; ArrowDown/Enter with an empty input cannot select a ledger from the
previous search. Actual: `value: ""`, `aria-expanded: "true"`, and
`aria-activedescendant: "ledger-search-option-0"` coexist after settling, and
Enter selects the stale result.

The actual `SearchLedgers` request uses `q: "crypto-example", limit: 50` and
returns HTTP 200 with the one correct ID, `open_ledger/crypto-example`.
Working controls: ArrowDown/Enter in a fresh empty gallery does nothing;
normal ArrowDown/Enter after the nonempty query selects the intended example.
The clear button itself is reachable by Tab and returns focus to the input.

Root cause: `dashboard/src/features/ledger-list/pages/gallery-page/index.tsx:222–227`
clears query/dropdown state but keeps `highlightedIndex` and the previous query
result. Its immediate refocus invokes `handleInputFocus` at 96–99 while the
old debounced query still qualifies, reopening the old dropdown. The later
debounce update never closes it. `handleKeyDown` at 103–123 checks only data
and the index; it does not require a current eligible search/open result set.

Fix in **dashboard**: clear the highlight together with the query; derive
dropdown/selection eligibility from the current normalized query and its
matching results, keeping results inactive below the two-character threshold.
Refocusing during Clear must not reopen the old list, and keyboard handlers
must not select stale data from a cleared or closed search. Preserve the
existing accessible Clear button, focus return and valid search navigation.
No debounce timing increase or backend search change is needed.

Acceptance: the exact keyboard journey leaves an empty focused input, closed
dropdown and no active descendant, before and after debounce settles;
ArrowDown/Enter cannot revive/select the old result; entering a new valid
query restores ordinary selection. Cover clearing during an in-flight search
so a late response cannot reactivate the blank input. No API mocking shortcut
should bypass the component's actual focus and keyboard handlers.

Dedupe: searched all open/completed records for gallery clear/highlight/stale
results and search races; no open overlap. Completed
`w5/done/m2/done/t003.md` adds listbox/highlight semantics and keyboard access
to Clear, but its end-to-end highlighted-result clearing was not verified.
The existing test checks input value and focus without the stale-selection
sequence. Targeted history traces highlighting to `af5339de`; `c7049813`
and `42ee1dec` do not repair it. No evidence establishes that this sequence
previously worked, and fetched main contains no newer fix.

One gallery route/caller was found. Empty and valid-query controls were
exercised; late network responses, errors, other browsers/locales and a
patched implementation remain unverified. Source-history and main Journal
pagination bugs are separate. No production data was changed.

Additional reproduced state, 2026-09-08, same production browser/role,
English/System light, local HEAD `a315c273`, fetched main `cc3f4c2f`:

1. Fresh-open `/ledger-gallery` at 1440×1000 and search
   `qa-no-public-ledger-match-20260908`.
2. Wait for **No ledgers found** in the listbox, then press Escape.
   The focused input retains `aria-expanded="true"` and the listbox remains
   open. Fresh 390×844 repeats the same failure.
3. As a control, search `crypto-example`, wait for its real public option and
   press Escape. `aria-expanded` becomes false and the listbox disappears.

The actual narrow SearchLedgers reads both return HTTP 200 without GraphQL
errors: the unmatched query returns `[]`; the control returns only
`open_ledger/crypto-example`. No page errors occurred. This is an ordinary
successful empty search, not a failed or still-loading request.

At `gallery-page/index.tsx:103–104`, the keyboard handler returns before
examining the key if results are absent or empty. Its Escape branch at 123–126
therefore runs only when at least one result exists. Handle dismissal before
result-dependent navigation guards: Escape must close an open empty list and
clear any active-descendant state without selecting anything. Preserve the
existing valid-result dismissal and the cleared-query protections above.
Extend the same component-level keyboard regression with zero-result Escape;
loading/error dismissal should also remain usable, but those cases were not
reproduced live in this extension.

All-board searches found only the existing 010 and the completed w5/m2/t003
accessibility work already cited above. The empty-result guard is unchanged
since `af5339de`; no later repair exists on fetched main. In source, `/gallery`
redirects to `/ledger-gallery`, the sole component route; no second UI needs
an independent implementation. Search text was cleared and the listbox closed.
No ledger selection, production mutation or private result was captured.

Later live routing check on 2026-09-08: direct `/gallery?lang=en` returned
HTTP404, while authenticated `/ledger-gallery?lang=en` returned HTTP200.
