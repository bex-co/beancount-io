## Objective

Give `addBulkEntries`, `appendDirectiveText`, and `insertReceiptTransaction` an optional `requestId` with ledger creation's semantics, keyed by user + ledger + requestId, kept 24 hours.

## Context

- Template: `features/ledger/workflow/ledger-workflow.ts` (createLedger idempotency, `CACHE_KEYS.ledger.createRequestByUserAndId`, strict cache helpers).
- Claim the id atomically in Redis (SET NX), not with the process-local `AsyncLock`, so two backend instances cannot both write.
- Request fingerprint: the normalized write input (entries/text, target file, receipt fields), not transport details.

## Acceptance criteria

- [ ] Same id + same request → stored result, no second write; same id + different request → validation error; id in progress → retryable conflict; failed write → id released.
- [ ] A Redis error on any step logs and lets the write proceed unprotected (fail-open); no write fails because of the store.
- [ ] No `requestId` → no Redis access at all.
- [ ] Service-level tests cover each case with a real in-memory store double.

## Out of scope

- Transport plumbing (t002); clients (t003/t004).
