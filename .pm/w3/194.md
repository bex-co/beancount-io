# Single-entry writes commit "Add 1 entries" into permanent git history

**Minor · 20–30m · backend-cluster/ledger.** A1/A3: a ledger's git history is a user-facing artifact this product advertises ("Every financial change is a Git commit with full history"), and it is currently seeded with broken grammar that can never be corrected after the fact.

Production https://beancount.io, 2026-09-12, isolated headless Chrome (Playwright MCP `--headless --isolated`), English/light, 1440×1000, authenticated QA account on its own synthetic `example` ledger. Local/fetched main `84231f9c`; deployed SHA unverified. Read-only — the commits below are pre-existing history, not writes made by this run.

Open `/ledger/<owner>/example/commits`. The history contains, among others:

```
Add 1 entries    puncsky · 3071c8e · 16 days ago
Add 1 entries    puncsky · 84eed14 · 16 days ago
Add 1 entries    puncsky · e1d1f59 · 16 days ago
Add 3 entries    puncsky · c8e7eb4 · 10 days ago
Add 36 entries   puncsky · 733f5d3 · 17 days ago
```

Every single-entry write produces **"Add 1 entries"**. The dashboard is rendering the stored commit message faithfully, so this is not a display defect — the wrong text is written into the commit itself and is immutable from then on.

Root: `backend-cluster/ledger/src/api/entries.ts:179` — `message: \`Add ${rows.length} entries\``, with no singular form. A second instance of the same omission is in the same package at `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:849` — `message: \`Deleted ${deletedHashes.length} entries successfully\`` — which surfaces in an API response rather than in history, and so is recoverable, but reads the same way to a user or an agent deleting one entry. Note that the neighbouring single-entry paths in that file already get this right: `:781` "Entry deleted successfully" and `:923` "Entry updated successfully".

Fix: give both messages a singular form (`Add 1 entry` / `Deleted 1 entry successfully`). Keep the plural wording byte-identical for counts other than one so existing history stays greppable and any consumer matching on the current plural text keeps working. Owning package: `backend-cluster/ledger` — the commit message is composed there, not in the dashboard, and no API schema changes. Existing commits cannot be corrected and must not be rewritten; this fixes new writes only.

Blast radius: the commit-message path is the bulk-entry write used by the dashboard, the REST `POST …/entries` endpoint and the MCP write tool, so all three surfaces improve together with no per-surface change — worth confirming against the repo's REST/GraphQL/MCP parity rule that none of them asserts the exact current string. Check the ledger package's own tests and any backend-v2 parity test for a hardcoded `"Add 1 entries"` or `"Deleted 1 entries successfully"` expectation before changing the text.

Adjacent states: zero rows (does that path even commit?), and large counts, must be unchanged. If a translation layer is ever added for commit messages, this is the point where it would belong — but do not add one now.

Dedupe: searched every queue including `done/` for commit message, pluralization and these strings — nothing. Completed `m17` made commit **file links** reach deferred and virtualized diffs; completed `m29` protected file drafts during navigation. Neither concerns the message text. This is a different package from my other dashboard findings this session.

Verification limits: this run made no ledger write, so the new singular message was not observed being produced — the defect is established from existing history plus the source line that generates it. The `Deleted …` string was traced in source only, not reproduced live, since that would require a production delete.

Note that `backend-cluster/ledger` has no package-wide GitHub Actions test workflow (root `CLAUDE.md`); run its scoped commands — `yarn test`, `yarn lint`, `yarn typecheck`, `yarn build` — before handing the change off.
