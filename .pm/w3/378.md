# Piping bea output to a closed reader breaks the documented pipe contract (exits 1/120, not silent 141)

Severity: minor. No data loss; scripting/contract violation only.

`cli/docs/USAGE.md` promises a closed downstream pipe exits **141 without a
message**. What actually happens depends on buffer timing:

- `bea example | head -n 5` → exit **1** + `Error: [Errno 32] Broken pipe`
- `bea --file big.bean list transaction --limit 5000 | head -n 3` → exit
  **120** (a code in no exit table) + the same error + `Exception ignored on
  flushing sys.stdout: BrokenPipeError` shutdown noise
- `bea --file big.bean query "PRINT" | head -n 3` → exit **1** + message
- `bea format big.bean | head -n 5` → exit **1**, silent (likely upstream;
  unverified)

## Repro (synthetic, no login)

```sh
cd cli
uv run bea example > /tmp/big.bean
uv run bea --file /tmp/big.bean list transaction --limit 5000 2>/tmp/e | head -n 3 >/dev/null
echo "exit=${PIPESTATUS[0]}"; cat /tmp/e
# exit=120, Error: [Errno 32] Broken pipe, plus shutdown-flush noise
uv run bea example 2>/tmp/e2 | head -n 5 >/dev/null
echo "exit=${PIPESTATUS[0]}"; cat /tmp/e2
# exit=1, Error: [Errno 32] Broken pipe
```

Reproduced 3/3 on `list | head` (120) and `query | head` (1); same with
`.venv/bin/bea` directly, so it is not a `uv run` artifact. HEAD `b94d9461`,
macOS arm64, bea 0.2.0.

## Root cause

Python ignores SIGPIPE by default, so a broken stdout raises
`BrokenPipeError` in the frontend instead of killing the process. Two
compounding faults:

1. `_GuardedGroup.invoke` (`cli/src/cli/main.py:98-99`) catches it as a
   generic exception → `output.error` → exit 1 with a message. The existing
   quiet-signal handling (`_QUIET_SIGNALS` in `cli/src/cli/engine/launch.py`)
   only covers the engine/upstream **child** dying on SIGPIPE, not frontend
   writes (`output.table`, `query` rendering, `example`'s
   `sys.stdout.write` of captured output).
2. Exiting via `SystemExit(1)` with buffered data on a broken stdout lets
   CPython's shutdown flush fail, which **overrides the exit code to 120**
   and prints `Exception ignored on flushing sys.stdout`. Verified with a
   minimal `print("hello"); raise SystemExit(1)` against a closed pipe:
   exit 120 regardless of the intended code. Early-EPIPE runs (buffered
   data remains) show 120; late-EPIPE runs (buffer already flushed) show 1.

## Fix direction

Restore classic Unix behavior for frontend writes: either
`signal(SIGPIPE, SIG_DFL)` at startup so bea dies 141 silently, or catch
`BrokenPipeError` in `_GuardedGroup.invoke` → detach stdout (devnull/close)
→ exit 141 quietly. Note `sys.exit(141)` alone is **not** enough: the
shutdown flush of the still-broken stdout would still print noise and force
120. Regression test must assert exit 141 + empty stderr with a real pipe
and unread output (a `CliRunner` StringIO cannot produce EPIPE).
`format` with inherited streams (observed 1-silent) needs a decision:
translate a child broken-pipe death to 141, or document it as upstream's.

## Blast radius / controls

- Affected: every frontend-rendered stdout path (`list`, `query`,
  `report`, `balance`, `check` diagnostics, `example`, `cloud` reads).
  `update.print_notice` already writes to stderr — not implicated.
- Working control: engine child killed by a signal is already reported
  per the table (`3d6434dc`), and `bea check` on invalid ledgers still
  exits 1 with diagnostics (pipe tests used ledgers that `check` clean).
- Adjacent: with stdout closed (`>&-`), `list` exits 0 printing nothing —
  same "exit 0 is a promise" tension, different errno (EBADF); consider
  while here.
