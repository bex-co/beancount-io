# Holdings rounds real crypto quantities to zero in the table and CSV

Severity: **major**. Owning package: **dashboard**. Estimate: **45–60 minutes**,
scoped to Holdings cell formatting and lossless CSV serialization.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English, System/light;
authenticated QA reader of public `open_ledger/crypto-example`. Desktop
1440×1000 and fresh narrow 390×844. Deployed SHA unverified; local `a315c273`
and fetched `origin/main cc3f4c2f` have the same implicated Holdings files.

1. Open `/ledger/open_ledger/crypto-example/holdings?lang=en`, default
   **Holdings** view. Scroll to `Assets:Staking:Ethereum:ETH`, acquired
   **2024-03-31**. Its units cell says **0.00 ETH**, with book value **14 USD**
   and market value **12.80 USD**. There is no tooltip or accessible label
   containing the unrounded quantity. A fresh narrow page reproduces this.
2. At desktop width, click **Export CSV**. The parsed CSV's same row contains
   **0.00 ETH**, although the actual quantity is **0.004 ETH**. The downloaded
   file has 43 data rows; this is a data-value error, not CSV parsing damage.
3. The January 31 `Assets:Crypto:Mining:BTC` lot is **0.015 BTC** in the API,
   but both the table and CSV say **0.01 BTC**. Other nonzero ETH staking lots
   similarly round to zero; Lido's **0.005 STETH** lots display **0.01 STETH**.
4. The March 10 CUSDC row's table rounds cost **0.0225** and price **0.0230**
   to **0.02**. Its scalar CSV cells correctly retain those quotes, but its
   object-valued book value **2999.999925 USD** and market value
   **3066.666590 USD** export as **3000.00 USD** and **3066.67 USD**.

Expected: asset units and unit prices retain their meaningful precision, and
CSV monetary/quantity values preserve the exact source decimals. Small real
positions must not become zero, and export must not round values differently
depending on whether the API represents them as scalars or currency maps.

The actual GraphQL QueryShell request and REST POST
`/api-gateway/v1/ledgers/open_ledger/crypto-example/query` both return 200 with
the same correct decimal strings and currency maps. The exact default Holdings
query is captured in evidence. Working controls: **1.00 ETH**, **0.10 BTC** and
the bank's **42341.50 USD** retain their values. CSV scalar Decimal strings
already preserve precision. No console errors were captured.

Root cause: `dashboard/src/features/ledger-data/holdings/utils.ts:55–72`
converts unknown cells with `Number(value)` and applies `toFixed(2)` whenever
that number has more than two fractional digits. The conversion also introduces
binary rounding, explaining `0.015` → `0.01`. `holdings-table.tsx:31–40` uses
this formatter for each currency-map value, and at172–175 for scalar cells.
The original precise values are not exposed elsewhere in those cells.

`utils.ts:1–9` reuses the display formatter in `csvObjectToString`.
`tableToCSV` at35–38 calls it for objects while leaving scalar cells as
`String(cell)`. `DatasetTable.handleExportCSV` at58–71 feeds those already
rounded strings to the download helper. The generic secure CSV downloader
receives the damaged contents; changing its quoting or Blob encoding cannot
recover the digits. A local source probe using captured production rows
reproduces the downloaded values exactly.

All four DatasetTable callers are in Holdings `index.tsx:52–80`: default,
by-account, by-currency and by-cost-currency. All four views were exercised
and returned QueryShell 200. The same formatting changes **0.077 BTC** to
**0.08 BTC** by account, and **0.327 BTC** to **0.33 BTC** in the currency and
cost-currency views. Grouped exports share the same handler but were only
source-traced; the actual downloaded control is the default view.

Producer/serializer: ledger `features/ledger/service/ledger-shell-service.ts:92–94`
runs the query and invokes `queryResultToShellResult`.
`ledger-shell-mappers.ts:40–55,164–200` preserves decimal strings and combines
currency-map values with BigNumber. Gateway
`features/ledger/service/ledger-shell-service.ts:44–80` copies those types/cells;
GraphQL and REST delegate to it, as does MCP in source. There is no upstream
rounding of these quantities, and no API/schema change is needed. Live MCP
was not exercised.

Fix the Holdings formatter/serializer together: keep source decimal strings
for quantities, quotes and currency-map amounts; harmless trailing-zero
normalization is acceptable, loss of significant digits is not. Make CSV
serialization independent of display rounding and lossless for all decimal
cells. Any bounded display formatting for percentages must remain explicit to
that column. Preserve blank/missing cells rather than coercing them to zero,
as well as signs, units, text/date columns and existing row-filter behavior.
Do not change global cash formatting or rework unrelated report exports.

Acceptance: actual rendered cells and parsed downloaded CSV agree with these
API-shaped fixtures, including small positive/negative units, precise prices,
currency maps, legitimate zero, blanks, existing two-decimal values and multiple
units in one cell. Exercise all four callers, retain CSV quoting/Unicode and
account-row keyboard navigation, and run dashboard format, lint, tests and
build. Existing `holdings/__tests__/utils.test.ts:42–52,86–90` explicitly expects
small nonzero values to round to zero and object exports to round; replace those
incorrect expectations with the asset-precision contract, rather than preserving
the defect for test compatibility.

Dedupe: searched all open/completed `.pm` for Holdings, quantities, precision,
rounding and exports; read completed `w4/m1`'s full DoD and its t004 exclusion
of Holdings. `w3/012` repairs commodity-chart tooltip/axis formatters, `w3/034`
decodes BQL chart values, and `w3/007` fixes a different upstream cost-currency
query aggregation. None repairs this formatter or its CSV path. Targeted
history traces rounding to `af5339de`; `418c17cc` changes only empty-value row
filtering, and fetched main contains no repair. No historical deployed
