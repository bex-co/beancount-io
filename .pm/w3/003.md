# A timed-out budget write still lands, so the retry duplicates it

Seen 2026-08-27 on `deploy/docker-mac` while demonstrating the budget-write fix
(`w3/done/002.md`).

The dashboard's Add Budget dialog reported *"The service is temporarily
unavailable. Please try again shortly."* and the list stayed at 3 budgets. The
write had in fact succeeded: backend-v2's call to
`POST /entries/{owner}/{repo}/bulk` hit its 30 s client timeout
(`Ledger API is temporarily unavailable`, `SERVICE_UNAVAILABLE`) **after** the
ledger service had already committed the directive. Retrying the same add then
wrote a second identical directive:

```
2026-06-01 custom "budget" Expenses:HealthAndFitness "monthly" 180 USD
2026-06-01 custom "budget" Expenses:HealthAndFitness "monthly" 180.00 USD
```

Budget semantics hide it — same account, same date, so the later one supersedes
and the page still shows one card — but the ledger file now carries a duplicate
the user cannot see or explain. For entry types without that collapsing (a
transaction, say) the same timeout would produce a visible double-post.

The slow call was a one-off: that request took ~29.5 s, while the next writes on
the same ledger took 3.6 s. So it reads as a cold-start cost (WASM load or git
warm-up) landing just the wrong side of the 30 s timeout, not a systemic
slowdown.

Worth fixing on two fronts: make the bulk write idempotent or retry-safe so a
duplicate cannot be created, and stop the first write after an idle period from
approaching the timeout at all.
