Severity: **minor**. Owner: **dashboard**. Estimate: **30–45 minutes**.
A2: a reader following an obsolete file link should understand that the file
is absent and have a clear route back to the ledger's files.

Production `https://beancount.io`, 2026-09-08, Chrome 152, English,
System/light; authenticated QA reader of public synthetic `open_ledger/example`.

Expected: distinguish a successful missing-file result from a failed request.

and their retry behavior separate. Do not change the API's nullable contract
or claim that a network failure proves the file does not exist.

Root cause: `dashboard/src/features/ledger-editor/file-editor/components/ledger-file-view/index.tsx:162–168`
handles initial loading, then combines `error || !fileContent` into FileErrorView.
That view at `file-loading-error-views.tsx:39–60` always shows the same load-error
copy and `window.location.reload()`. Its only product caller is LedgerFileView,
used by the single blob route through `file-editor/index.tsx:58`.

The null is deliberate upstream behavior. Ledger `src/api/files.ts:87–115`
returns a successful null for an absent upstream file, preserving its existing
compatibility contract; genuine non404 failures are thrown. Gateway
`ledger-workflow.ts:1032–1073` preserves the null result, and
`api/resolvers/ledger-resolver.query.ts:85–101` declares a nullable GraphQL field.
This cause differs from032's missing-commit error categorization in backend-v2.
No backend or new API work is required for this filing.

Fix the settled-success-null branch in the dashboard and retain the normal
loading and query-error branches. Use existing file navigation helpers for a
safe recovery link, keeping owner/ledger/branch/path context and proper encoding.
The missing-file state must not depend on rendering FileContentView, which has
no content payload in this case. An unresolved/undefined query result must not
be presented as confirmed absence.
