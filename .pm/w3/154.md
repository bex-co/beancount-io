# Reveal the selected account when the native picker opens

**Minor · 45–60m · mobile.** A2: opening an existing posting's account picker should reveal its current selection without a manual search. Estimate assumes repairing the current positioning lifecycle; promote if broader list-layout work exceeds an hour.

Environment: September11,2026; production https://beancount.io; HEADf1965988/mobile7538fb0d; io.beancount.ios version1.20260906.47; iPhone17e/iOS26.5; English/System-light/default text size. Authenticated QA account; public open_ledger/minimax, pull/push true/admin false. Only unsaved draft navigation; no transaction submitted.

1. Open MiniMax's actual Transactions tab → plus. The new draft has second posting **Expenses:CostOfRevenue**.
2. Tap that second account. The picker opens on All at the top of Recent/Assets, with no visible selected checkmark. Wait for the settled list; the current expense remains offscreen.
3. In the initial session(PID50001), one actual upward drag reveals Expenses:CostOfRevenue lower in the list with its correct green checkmark. Selection has not been lost.
4. Fresh relaunch(PID52322), verify Home, then repeat Transactions → plus → second account. The same top-of-list position repeats.
5. Tap the Expenses category chip in the fresh repeat: the correct selected account and checkmark become visible immediately. No new selection is required. Another working control is opening the first, near-top Assets:Current:Cash account; a recently chosen Income:Revenue is also visible in Recent when reopened.

The local Recent list in these captures includes Income:Revenue from an earlier unsaved draft selection; it is not the current second posting. Do not select the expense before reproducing, because putting it in Recent can hide this positioning failure. No private ledger data is required. ledgerMeta(userId:open_ledger,ledgerId:open_ledger/minimax) returns success:true,28accounts including Expenses:CostOfRevenue, currencyMUSD. Expected behavior is explicit in `push-account-picker.ts:31`: current is the field's current account, scrolled into view and check-marked. The checkmark portion works; initial visibility does not.

Root: `account-picker-screen.tsx:286–301` sets hasScrolledToSelected=true before calling listRef.current?.scrollToLocation, then never retries. Its SectionList at386–405 supplies no getItemLayout and ignores onScrollToIndexFailed. Installed `@react-native/virtualized-lists/Lists/VirtualizedSectionList.js:142–170` translates the section/item index into scrollToIndex; `VirtualizedList.js:179–195` returns through onScrollToIndexFailed when a target is beyond measured cells and no layout estimate exists. The application treats that failed/too-early attempt as complete. The exact native callback/ref-readiness branch was not instrumented; an unmeasured initial target is the source-supported mechanism, not a claimed captured callback log.

Fix: make initial positioning wait for the list/data/layout to be ready and recover from an unmeasured target. Mark completion only after the target is actually visible or the position is otherwise verified. Use correct row/section layout information or a bounded measured/estimated positioning recovery, accounting for font scale and the Recent section. Do not add an unbounded timeout loop, permanently disable virtualization, or snap back after the user scrolls, searches or changes category. Missing selected accounts and empty/denied data must terminate safely; cancel pending recovery on unmount or user navigation. Preserve ranking, query results, callbacks and selected-account identity.
