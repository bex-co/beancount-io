# Expose receipt camera actions and flash state to accessibility

Severity: minor. Estimate: 30–45m. Package: mobile. A2: a newcomer using assistive technology can identify receipt actions and determine whether flash is enabled.

Environment: production API, authenticated QA session, public open_ledger/minimax; HEAD f1965988, latest mobile change 7538fb0d; development client 1.20260906.47, iPhone 17e / iOS 26.5, English, default text size and light appearance. Only local camera controls exercised; no picture taken, selected, uploaded or parsed and no ledger write.

Repro:
1. From settled Home, open plus → Scan Receipt with camera permission granted.
2. Inspect the native accessibility elements receipt-close, receipt-pick-library, receipt-toggle-flash and receipt-shutter. All four are Other (type 1), not Button; their labels are Cancel, Choose from Library, Flash and Take a Photo.
3. Inspect Flash before and after tapping it. The icon changes from crossed-out flash to solid flash, but both native snapshots expose label=Flash, value empty, selected=0, enabled=1, hittable=1.
4. Relaunch the app, wait for Home, and repeat via the actual plus menu. Fresh PID 94976 reproduces both states. Toggle back off and Cancel returns Home.

Expected: camera actions have actionable button semantics; Flash exposes a localized current off/on state that changes when activated. Actual: the role is generic and the visible toggle state is absent from native accessibility metadata. This establishes metadata failure, not a recording of VoiceOver speech or physical flash hardware behavior.

Working controls: sighted Flash activation changes the icon in both runs and Cancel reliably closes the camera. Prior native transaction header inspection identifies Done as Button, demonstrating that the inspector distinguishes button roles; w3/159 records that control. The initial run has no warning overlay; the fresh run has a development banner near the bottom, outside Flash and unrelated to its unchanged metadata.

Root cause: mobile/src/screens/receipt-capture-screen/camera-view.tsx:179–233 gives all four Pressables labels but no accessibilityRole. Flash at205–220 toggles local state and the icon only, with no accessibilityState or accessibilityValue. This CameraView has one production consumer in ReceiptCaptureScreen, mounted by app/(app)/receipt-capture.tsx and reached from Home. The label-only static guardrail in src/__tests__/accessibility-labels.test.ts does not enforce role or toggle state.

Fix: provide button semantics for the camera actions and a supported, localized on/off accessibility value or state for Flash. Preserve the same local state as the camera prop and icon; verify off → on → off and fresh entry reset in native accessibility metadata. Keep labels, hit targets, cancellation and existing capture guard intact. Add focused coverage that fails when the role/state mapping is removed; do not introduce a replacement camera abstraction or dependencies.

Dedupe/history: searched all root .pm open/done queues for flash, receipt/camera accessibility, and scanned open milestones. w3/168 concerns the photo-library permission prerequisite; w3/159 concerns the separate shared Back control; w2/m30 concerns upload/parse failures. Read w4/done/m7 full DoD and closeout: its static label guardrail and residual uncaptured full native audit do not establish these controls' role/state correctness. No matching open fix found. git history traces this camera implementation to3ae25ee9; current source still has the omission.

Unverified: camera hardware, actual capture, permission-denied UI, loading/permission transitions, upload/parse/network failures, VoiceOver audio, Android and physical devices. Photos permission was not changed in this pass. Flash restored off and camera closed. Bounded JS error capture empty. No implementation or shipping performed.
