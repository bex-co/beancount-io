## Objective

A non-UTF-8 CSV reports that its columns are `(none)` and suggests naming them with `--csv`, hiding the real failure. Bank exports from Windows tooling are routinely cp1252.

## Context

- `w3/227`: non-UTF-8 CSV says columns are `(none)`; the encoding failure never surfaces.
- `bea import` already strips a BOM on CSV (`cli/docs/IMPORTING.md` line 76), so BOM handling exists but encoding detection does not.

## Steps

1. Try UTF-8 (with and without BOM) first, then fall back through cp1252 and latin-1, recording which decoding succeeded.
2. Add a `--csv encoding=` override and remember it with the other sticky settings.
3. When every decoding fails, report the byte offset and the candidate encodings tried instead of `(none)` columns.
4. Name the decoding used in the preview.

## Acceptance criteria

- [ ] A cp1252 export with accented payees imports and the payees are correct in the ledger.
- [ ] A BOM-prefixed UTF-8 export still imports, unchanged from today.
- [ ] An undecodable file exits nonzero naming the offset and the encodings tried, never `(none)` columns.
- [ ] `--csv encoding=cp1252` forces the decoding.
