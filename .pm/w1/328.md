# `bea update transaction` retargets a review row onto its own bank account: the entry cancels out, exit 0, and the charge leaves the books

**Bug · cli · minor · 20–30m · A1.** From routine cli-qa, 2026-11-20. Sibling of [w5/468](../w5/done/468.md), which made `bea import` refuse a counter account equal to the `--account` being imported. Clearing the same review queue with `bea update` has no such guard. `bea update transaction --id <import-id> --account Assets:Checking` on a row imported from `Assets:Checking` moves the `Expenses:Uncategorized` leg onto `Assets:Checking`. The entry then posts `+5.00 USD` and `-5.00 USD` to one account. It exits 0, `bea check` passes, and with `--flag '*'` the row also leaves `bea list transaction --flag '!'`. The bank charge is gone from the balance, so the books now disagree with the statement by 5.00 USD. An agent working a long queue through `bea update transactions --from queue.csv` gets the same result per row, with `status: ok`.

Environment: main `d2a42b8df`, `bea 0.4.1` from the checkout (`uv run bea`), Python 3.12.14, macOS 26.5.1. The run used an isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME` with `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, and a scratch working directory. Reproduced in fresh processes from a pristine copy.

## Repro

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "open"
  Assets:Checking  100.00 USD
  Equity:Opening
2026-07-01 ! "Mystery 1"
  import-id: "id-1"
  Expenses:Uncategorized  5.00 USD
  Assets:Checking
2026-07-02 ! "Mystery 2"
  import-id: "id-2"
  Expenses:Uncategorized  7.00 USD
  Assets:Checking
EOF
bea --file main.bean balance checking                                   # Checking 88.00 USD
bea --file main.bean update transaction --id id-1 --account Assets:Checking --flag '*' --apply
bea --file main.bean balance checking                                   # Checking 93.00 USD
printf 'id,account,flag\nid-2,Assets:Checking,*\n' > queue.csv
bea --json --file main.bean update transactions --from queue.csv --apply
bea --file main.bean check                                              # exit 0
bea --file main.bean list transaction --flag '!'                        # empty
```

Actual: the single update exits 0 with `Updated 1 transaction`, and its diff is `-  Expenses:Uncategorized  5.00 USD` / `+  Assets:Checking  5.00 USD`. `--json` answers `"written": 1`. The batch row answers `status: ok`, with `changes: ["account: Expenses:Uncategorized → Assets:Checking", "flag: ! → *"]` and `rejected: 0`, and exits 0. The OLD=NEW form `--account 'Expenses:Uncategorized=Assets:Checking'` does the same. Afterwards `bea report register Assets:Checking` lists `Mystery 1  5.00 USD` and `Mystery 1  -5.00 USD`, and Checking reads 100.00 USD, which is 12.00 USD more than the statement.

Expected: refuse the retarget and write nothing, as `bea import` refuses `--default-account Assets:Checking` ("an uncategorized row would post against its own source and cancel out. Name the account its money goes to or comes from."). The single form should exit 2. A batch row should be `rejected` with that reason while the valid rows still write, and the batch exits 1, as every other rejected row does.

Working control: `bea import s.csv --csv date=Date,narration=Description,amount=Amount --account Assets:Checking --default-account Assets:Checking` exits 2 with that sentence, and a rule naming `Assets:Checking` is refused the same way (`cli/src/bea_engine/importing.py:1196-1214`).

## Cause and fix

`_retarget_accounts` (`cli/src/bea_engine/ledger/updating.py:423`) resolves the leg to move and the new account, but never compares the new account with the entry's other postings. `plan_lines`, `_summarize`, `_notes` and the batch planner (`_plan_rows`) all go through it, so a check there covers the single and batch forms. A `UsageError` raised there already becomes a rejected batch row, as the "posts to the holding account twice" refusal does.

Fix target: refuse a retarget that would leave every posting of the entry on one account, naming the entry's `file:line` and the account, in the import refusal's words. Merging a leg into another *expense* the entry already posts to stays allowed. For example, a split `Expenses:Food 3 USD` plus `Expenses:Uncategorized 5 USD` retargeted to `Expenses:Food` must still write. Leave `bea add transaction`'s explicit two-leg input alone: there the user typed both postings. Add a regression test for the single form, the OLD=NEW form, a batch with one bad row and one good row, and the allowed split-merge control. Document the refusal beside the w5/468 sentence in `cli/docs/IMPORTING.md` ("Clear the queue with `bea update transaction`") and in USAGE.md "Updating directives". Owning package: `cli`. No REST/GraphQL/MCP surface: there is no hosted counterpart of `bea update`.

**Dedupe:** searched `.pm/**` (done and blocked included) for `cancel out`, `self-cancel`, `against its own source`, `own source`, and `update transaction` with `account`. w5/468 fixed import only. w5/1047 and w1/246 changed other parts of update's retarget path. No open item covers this.

**Done when:** on the repro ledger, both update forms refuse with the reason and leave `main.bean` byte-identical. Checking still reads 88.00 USD. The batch rejects only the bad row. The split-merge control still writes. The new tests fail with the check reverted, and `make check-all` passes.
