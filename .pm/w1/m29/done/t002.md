## Objective

Local resolution needs the same failure property the hosted side has: a bad refresh must never replace a good cache entry with nothing, and an outage must not take the last good revision with it.

## Context

- ADR 015 section 5: an immutable blob keyed by revision plus a small mutable head holding the current revision, `nextRefreshAt`, and the last error; refresh is driven by the time stamp, not by key expiry.
- A successful fetch sets the next refresh five minutes ahead; a failure sets it one minute ahead and records the error while the previous revision keeps serving.
- `revision` is the ETag when the server sends one and the body's SHA-256 otherwise.
- The CLI's cache directory should follow the frontend's existing cache-path conventions in `cli/src/cli/engine/paths.py`.

## Steps

1. Store each feed as `<hash>/<revision>.beancount` plus a `head.json` holding the current revision, the next refresh time, the ETag, the observed-at stamp, and the last error.
2. Drive refresh from the head's time stamp; never let a cache expiry remove the fallback.
3. Add an offline mode that reads the head and its blob only and never performs a fetch.
4. Add a strict mode that fails when a source is stale or unavailable, so a consumer can reject degradation.
5. Never delete or replace the last validated blob on a validation failure, timeout, non-2xx status, or empty body.

## Acceptance criteria

- [ ] A successful fetch writes a revision blob and repoints the head; a superseded blob is removed only after the new one is written.
- [ ] A failed refresh leaves the previous revision serving and records the error in the head.
- [ ] Offline mode resolves from the head with no network call.
- [ ] Strict mode exits nonzero when any source is stale or unavailable, naming the source.

## Out of scope

- Sharing the cache between machines.
- A background refresh daemon; refresh happens on load.
