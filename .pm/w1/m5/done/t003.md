## Objective

Enforce `ledger.read`, `ledger.write`, and `ledger.admin` consistently across OAuth-authenticated GraphQL, REST, and MCP operations while preserving the explicitly capability-exempt legacy session path.

## Context

- **Closed 2026-08-27 by `/pm done`:** already shipped ahead of this task. `assertLedgerAuthorization` runs `assertIdentityCapability` before the ledger lookup (`authorize-ledger.ts`), `config.api.scopeEnforcement` is `"enforce"`, the Plaid services stopped minting `trustedIdentity()` in w3/m9, and the `scope-enforcement`, `op-class-coverage`, `authorize-ledger-fail-closed`, `ledger-receipt-scope`, and `llm-service-scope` suites (109 tests) pass.

- `backend-cluster/backend-v2/src/server/api/identity.ts` carries OAuth scopes and marks OAuth identities as non-exempt.
- `backend-cluster/backend-v2/src/features/ledger/utils/authorize-ledger.ts` enforces ledger pinning and user permission but not OAuth capability scopes.
- Operations that do not reach `authorizeLedger`, including account-wide and non-ledger resolver paths, need an equivalent centralized boundary.

## Steps

1. Define one closed mapping from read/write/admin operation classes to the corresponding OAuth scope.
2. Enforce it at the shared authorization seams before protected work or resource lookup occurs.
3. Inventory GraphQL, REST, MCP, receipt, Plaid, and account-wide paths that bypass the ledger service seam and add the same identity-aware check without reconstructing a capability-exempt identity.
4. Keep browser/mobile legacy session identities exempt during the compatibility period and make that distinction explicit in tests.

## Files

- `backend-cluster/backend-v2/src/server/api/identity.ts`
- `backend-cluster/backend-v2/src/features/ledger/utils/authorize-ledger.ts`
- A focused shared OAuth capability helper.
- Affected GraphQL resolvers, REST routes, and MCP boundaries found by the inventory.

## Acceptance criteria

- [x] Read, write, and admin operations require their documented scope for OAuth identities.
- [x] Identity-only and under-scoped OAuth tokens are denied even when the underlying user owns the ledger.
- [x] Scope denial occurs before protected data or resource existence is exposed.
- [x] Legacy session behavior and normal ledger collaborator permissions remain unchanged.
- [x] No caller bypasses scope checks by converting an OAuth identity to `trustedIdentity()`.

## Out of scope

- Adding finer-grained scopes or changing collaborator permission semantics.
