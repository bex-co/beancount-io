## Objective

Move new mobile authentication to OAuth without unexpectedly logging out installed users or breaking older app versions, and define a measurable point at which the custom dashboard token bridge can be removed.

## Context

- Existing mobile sessions contain a legacy session JWT and can remain valid for a long period.
- Older released clients still depend on dashboard login/signup pages posting that token into their embedded WebView.
- Silently exchanging a legacy session JWT for an OAuth refresh token would introduce another custom grant and is not required for a safe staged migration.

## Steps

1. Hydrate and route legacy versus OAuth sessions explicitly; existing valid legacy sessions continue, while every new authentication in the updated app uses OAuth.
2. Keep the dashboard bridge only for the supported older-client window and ensure the new app never consumes it.
3. Define observable retirement criteria using minimum supported app version and coarse, privacy-safe legacy-auth usage telemetry.
4. Document rollback behavior and remove the bridge and obsolete WebView dependency only after the criterion is met, either in this milestone or a named follow-up.

## Files

- `mobile/src/common/vars/session.ts`
- `mobile/src/screens/welcome/`
- `dashboard/src/features/auth/pages/`
- Release/support documentation for the compatibility cutoff.

## Acceptance criteria

- [ ] Updating the app does not force a valid existing user to sign in immediately.
- [ ] Logging out or starting without a session routes the updated app exclusively through OAuth.
- [ ] Older supported versions retain their existing login path until the published cutoff.
- [ ] No session-token exchange extension or silent OAuth grant is introduced.
- [ ] Bridge-removal evidence and rollback conditions are documented without collecting server names, tokens, or user data.

## Out of scope

- Supporting legacy authentication indefinitely or migrating sessions across different servers.
