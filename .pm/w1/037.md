# Directive-text dry runs refuse on new bean-check errors instead of previewing them

**Severity:** minor. **Estimate:** 45–60 minutes, including adapter regression coverage; the shared workflow keeps the fix small. **Owner:** backend-v2. **A1 — Agent-native accounting:** an agent must be able to preview what a write would do — diff plus projected errors — before deciding to commit it.

## Live reproduction

Found 2026-09-22 (America/Los_Angeles) through real HTTPS requests to `https://beancount.io/api-gateway/mcp` and `https://beancount.io/api-gateway/v1`. Checkout: `main`, `d6b5b0e4`; Node 22.17.1. `initialize` reports `beancount-mcp 1.0.0`, protocol `2025-11-25`. The deployment exposes no revision, so equality with HEAD is unverified. Credential: temporary `ledger.write` API key pinned to a dedicated QA account's synthetic `mcp-agent-eval` ledger, used for `dry_run` previews only. No commits were made; `checkLedger` reports the same commit SHA before and after every probe below.

Run from the repository root with a designated QA credential file:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa-write.env call appendLedgerText '{"text":"2026-09-10 * \"QA probe\" \"dry run\"\n  Expenses:Food  2.00 USD\n  Assets:Cash   -2.00 USD","dry_run":true}'
```

`Expenses:Food` is balanced but never opened in the fixture, so the projection introduces one new bean-check error. Two fresh requests returned HTTP 200 with `isError: true` and:

```json
{"ok":false,"error":{"code":"VALIDATION_FAILED","message":"Validation failed for text: appending it would introduce 1 new bean-check error: Account Expenses:Food was never opened (main.bean:89)","hint":"The text is valid Beancount but breaks the ledger — the message names each new error. Fix the directives, or pass `allowInvalid: true` to record them deliberately."}}
```

No diff is returned. Expected per `docs/mcp.md` ("`dry_run` returns the unified diff and the projected errors without committing"), the REST `dryRun` schema ("Run every check and return the diff and projected errors without committing"), and the sibling `editLedgerFiles` preview: `ok: true` with the unified `diff` and `validation.newErrors`, committing nothing.

The refusal also teaches a dangerous workaround: the only way to see the diff is `dry_run: true` plus `allowInvalid: true`, and re-issuing that same call with `dry_run: false` — the documented preview-then-commit workflow — would commit the invalid content the refusal exists to prevent.

## Controls and cause

- `editLedgerFiles` with `dry_run: true` and a change introducing a new error correctly returns `ok: true` with the diff and `validation: {errorsBefore: 0, errorsAfter: 1, newErrors: [...]}`. Same credential, same ledger, same request style.
- `appendLedgerText` with `dry_run: true` and valid text (opened accounts only) correctly returns `ok: true` with the diff, inserted in date order.
- `appendLedgerText` with `dry_run: true` plus `allowInvalid: true` and the same invalid text correctly returns `ok: true` with the diff and the one projected error — proving the result path already supports this shape.
- REST `POST /api-gateway/v1/ledgers/qa-owner/mcp-agent-eval/directives/text` with `{"dryRun": true}` and the same text returns HTTP 400 `VALIDATION_FAILED` with no diff: the same refusal through the same service, so this is a shared-workflow defect, not an MCP adapter defect.
- `src/features/ledger/workflow/directive-append-workflow.ts:158` throws on `newErrors` unless `allowInvalid` before the `dryRun` branch at line 165 is reached. The dry-run result at lines 184–210 already carries `diff` and `newErrors`; it is simply unreachable without `allowInvalid`.
- Callers of the shared `appendDirectiveText`: MCP `appendLedgerText`, REST `POST .../directives/text` (`entries-handler.ts`), and the GraphQL `appendDirectiveText` mutation (`ledger-entry-resolver.mutation.ts`), which also publishes `dryRun`/`diff`/`newErrors` fields. `addBulkEntries` has no dry-run mode and is unaffected.

Fix in the shared workflow so previews return the diff and projected errors while real commits still refuse unless `allowInvalid` — e.g. the throw applies only when not a dry run. Keep the refusal, the error code, and the commit path bit-for-bit. Per the parity workflow, extend the existing `directive-text-parity` contract coverage through the MCP, REST, and GraphQL adapters rather than only unit-testing the workflow.
