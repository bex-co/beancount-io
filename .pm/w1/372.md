# `bea update transaction --id TX-1001` says "No transaction with import-id or ref 'TX-1001'" for a row `bea import` wrote from that bank ID as `bank_id: "TX-1001"` / `import-id: "bank:TX-1001"`, and the batch form rejects the row the same way

**Bug · cli · minor · 20–30m · A1.** From routine cli-qa, 2026-11-23. `update --help` says the command "clears the review queue `bea import` leaves behind: point --id at the row's import-id". When the bank export has an ID column, `bea import --csv …,id=COLUMN` stores the bank's ID twice: as `bank_id: "TX-1001"` and as `import-id: "bank:TX-1001"`. The import preview's `ID` column only says `bank`. So the one identifier the user has in hand, the bank's own transaction ID from the statement, is refused as unknown. The refusal does not mention the `bank:TX-1001` import-id that the same ledger holds. An agent that reconciles from the statement gets exit 2 and has to read the file to find the prefix. A `ref` from someone else's importer resolves (`--id` takes "the row's import-id, a `ref` metadata value, or `file:line`"), but the `bank_id`/`fitid`/`transaction_id` keys that bea's own import treats as stable bank IDs (`importing.py:62`) do not.

Environment: main `d2f88ef76`, `bea 0.5.0` from the checkout (`uv run bea`), managed engine 0.5.0, macOS 26.5.1. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, fresh processes. Reproduced twice from pristine fixtures.

## Repro

```sh
mkdir books && cd books
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Expenses:Food USD
EOF
printf 'Date,Description,Amount,Transaction ID\n2026-02-01,COFFEE SHOP,-4.50,TX-1001\n' > bank.csv
bea --file main.bean import bank.csv --account Assets:Checking \
  --csv 'date=Date,amount=Amount,narration=Description,id=Transaction ID' --apply
bea --file main.bean update transaction --id TX-1001 --account Expenses:Food --flag '*'
printf 'id,account,flag\nTX-1001,Expenses:Food,*\n' > rows.csv
bea --file main.bean update transactions --from rows.csv
bea --file main.bean update transaction --id bank:TX-1001 --account Expenses:Food --flag '*'   # control
```

## Actual

- The import writes `2026-02-01 ! "COFFEE SHOP"` with `bank_id: "TX-1001"` and `import-id: "bank:TX-1001"`, exit 0.
- `update transaction --id TX-1001` exits 2: `Error: No transaction with import-id or ref 'TX-1001' in this ledger. Nothing was written.`
- `update transactions --from rows.csv` previews `1 rejected TX-1001` with the same reason (exit 0, as a preview does).
- Control: `--id bank:TX-1001` previews the retarget, exit 0.

## Expected

An ID that bea's own import recorded as the row's stable bank ID finds that row. Either resolve the import's ID keys (`bank_id`, `fitid`, `transaction_id`, `imported_id`) as a third tier after `import-id` and `ref`, under the same refuse-if-shared rule, or, at minimum, have the not-found refusal name the match: `TX-1001 is the bank_id of the transaction at main.bean:6; its import-id is bank:TX-1001, so pass --id bank:TX-1001.` Basis: `update --help` ("Clears the review queue `bea import` leaves behind"), `docs/IMPORTING.md` (an `id` column "becomes `bank_id` metadata, so stable bank IDs deduplicate"), and the import's own ID-key list.

## Cause

`locate_transaction` (`cli/src/bea_engine/ledger/updating.py:189`) tries `("import-id", "ref")` (`:222`) and otherwise raises the not-found refusal (`:229`). The import side derives `import-id` as `<kind>:<value>` from `_IDENTITY_KINDS` (`cli/src/bea_engine/importing.py:55`, `bank_id → bank`, `fitid → ofx`, …), and the CSV mapper writes `bank_id` (`cli/src/bea_engine/csv_mapper.py:2011`). Nothing on the update side knows those keys or that prefix.

## Fix

Owned by `cli`, engine side only. In `locate_transaction`, after `import-id` and `ref`, look the value up in the importer ID keys (share `_DEFAULT_ID_KEYS` or `_IDENTITY_KINDS` rather than copying them), keeping "a repeated value is ambiguous". If the owner prefers that `--id` stay strict, put the near match in the not-found refusal instead. Cover both forms with a real `bea` subprocess test: a CSV import with an ID column, then `update transaction --id <bank id>` and a batch row with it. Revert the fix and watch the test fail. Update the `--id` sentence in `USAGE.md` and the help, then run `make docs` and `make check-all` in `cli/`. No REST, GraphQL or MCP surface rewrites local entries.

## Blast radius

The single and batch updates both resolve through `locate_transaction`. OFX imports (`fitid → ofx:`) and Python importers that set `transaction_id`/`imported_id` take the same path and were not exercised here: OFX needs the `beangulp` feature, which this run left disabled. Working controls: `import-id`, `ref` (including the decimal and NFC forms of w5/1030) and `file:line` all resolve.

## Dedupe

Searched `.pm/**` for `No transaction with import-id or ref`, `bank_id` together with `update transaction`, and `bank:`. w5/1030 (decimal and NFC refs), w1/340 (`file:line` base) and w1/353 (batch exit status) cover other parts of the lookup. The w5 import-identity notes (881, 919, 1014) cover dedupe, not update. No open item overlaps.
