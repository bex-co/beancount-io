# MCP tool argument validation bypasses the promised structured error envelope

**Severity:** minor. **Estimate:** 45–60 minutes, including adapter regression coverage; the SDK boundary adds uncertainty. **Owner:** backend-v2. **A1 — Agent-native accounting:** an agent must be able to recognize and correct malformed arguments through `error.code` and `error.hint`, without parsing SDK prose.

## Live reproduction

Found 2026-09-21 (America/Los_Angeles) through real HTTPS requests to `https://beancount.io/api-gateway/mcp`. Checkout: `main`, `432af8f51cba834e2df09674ab9f498bbf80103c`; Node 22.17.1. `initialize` reports `beancount-mcp 1.0.0`, protocol `2025-11-25`. The deployment exposes no revision, so equality with HEAD is unverified. Credential: temporary `ledger.read` API key pinned to a dedicated QA account's synthetic `mcp-agent-eval` ledger. No ledger writes.

Run from the repository root with a designated QA credential file:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env call runBqlQuery '{}'
```

The request is `{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"runBqlQuery","arguments":{}}}`. Two fresh requests returned HTTP 200, `Content-Type: text/event-stream`, and this result:

```json
{
  "content": [{"type":"text","text":"MCP error -32602: Input validation error: Invalid arguments for tool runBqlQuery: Invalid input: expected string, received undefined at query"}],
  "isError": true
}
```

There is no `structuredContent`, machine code or hint. Independently reproduced with `runBqlQueryStructured({"query":42})`, `readLedgerFiles({})`, and `readLedgerFiles({"files":[{"path":"main.bean","start_line":0}]})`.

Expected per `docs/mcp.md`'s result/failure contract: `isError:true` plus `structuredContent:{ok:false,error:{code:"BAD_USER_INPUT",message,hint}}`, with the offending field named and matching text. Invalid input must still be refused before domain work.

## Controls and cause

- `runBqlQueryStructured({"query":"SELECT qa_column_that_does_not_exist"})` correctly returns `BAD_USER_INPUT` and a hint. A valid `BALANCES` query succeeds; its typed rows and columns agree with REST and GraphQL.
- With the same API key, REST `POST /api-gateway/v1/ledgers/qa-owner/mcp-agent-eval/query` with `{}` returns HTTP 400 and `error.code:"VALIDATION_FAILED"` naming `body.query`. GraphQL `queryShell` with its required `$query` omitted returns HTTP 400 and `extensions.code:"BAD_USER_INPUT"`. Their protocol-specific envelopes already identify input failures.
- `src/server/api/composition-root.ts:455` registers each descriptor's input schema with `McpServer`, while the application error boundary starts only inside `makeMcpToolHandler` at line 736.
- Installed `@modelcontextprotocol/sdk` 1.30.0 validates at `dist/cjs/server/mcp.js:128`, before calling the handler. Its catch at line 144 returns `createToolError`, whose implementation at line 155 emits only text and `isError`. The application translator never sees these errors. The SDK declares that helper private; do not base a fix on a private-method patch or weaken the published schemas.

Fix the owned MCP adapter boundary so schema-validation refusals receive the same structured envelope as handler refusals while retaining the full discovery schema, existing validation, authorization and output checking. Preserve field paths for nested inputs. The same registration path serves every tool. REST and GraphQL require parity controls, not a change to their already coded validation responses.
