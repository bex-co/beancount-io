# Selection lists mark the current choice with icon opacity alone, so no open list row is programmatically current

**Minor · 35–50m · dashboard.** A2: when a reader opens the ledger or language list and arrows through it, nothing tells them which row they are already on.

Found 2026-09-13 by a dashboard QA sweep. Reproduced on production `https://beancount.io` (authenticated, headless isolated Chromium 1440×1000) and confirmed against **HEAD source**, so this is current code and not the deploy lag affecting other w3 items.

Two components share one pattern: the current choice is distinguished only by toggling a `<Check>` icon's opacity, which is a purely visual channel.

```tsx
// common/components/ledger-layout/ledger-switcher.tsx:285-293
<Check className={cn("mr-2 h-4 w-4",
  currentLedgerId === ledger.id ? "opacity-100" : "opacity-0")} />

// features/user-settings/pages/general/appearance-section/language-selector.tsx:60-65
<Check className={cn("mr-2 h-4 w-4",
  i18n.language === code ? "opacity-100" : "opacity-0")} />
```

In both, the icon is rendered into **every** row, carries no accessible name, and there is no `aria-current`, no `aria-selected` bound to the current value, and no textual marker. The language selector additionally leans on `i18n.language === code && "bg-accent"` — a background colour, also visual-only — and its rows are plain `<Button>`s, so they carry no list-selection semantics at all.

Opening the ledger switcher while viewing `puncsky/example` produces:

```
[role="group"]   label "open_ledger"
  [role="option"]  "open_ledger"   data-value="open_ledger"            aria-selected="true"
  [role="option"]  "minimax"       data-value="open_ledger/minimax"    aria-selected="false"
[role="group"]   label "puncsky"
  [role="option"]  "puncsky"       data-value="puncsky"                aria-selected="false"
  [role="option"]  "example"       data-value="puncsky/example"        aria-selected="false"
```

No row is marked current, so arrowing through the list gives no way to recognise the one already in use.

## Scope correction — what this is NOT

An earlier draft of this note claimed the current ledger never reaches the accessibility tree at all. **That was wrong, and the correction narrows this finding.** The combobox *trigger* does expose it:

```
- combobox "Select a ledger": example
```

The trigger's accessible name is `Select a ledger` and its value is the current ledger's name; the language selector's trigger likewise renders `currentLanguageName` as text (`language-selector.tsx:43`). So a non-visual user **can** determine the current ledger or language — by reading the collapsed trigger.

What is missing is the marker *inside the open list*. That still matters — confirming a choice mid-list means collapsing the popover, reading the trigger, and reopening — but it is a navigation annoyance, not an unobtainable value. Severity is **minor** for that reason, and an implementer should not expect to find a completely inaccessible control.

Expected: the row matching the current value carries `aria-current="true"` (or an accessible name including its current state) alongside today's visual check.

Actual: only `opacity-100` distinguishes it.

## Deliberately not claimed

- **Owner rows being selectable `role="option"` entries** (`open_ledger`, `puncsky`) is **intentional** — `ledger-switcher.tsx:264-274` renders each owner as a `CommandItem` whose `onSelect` navigates to `/ledger/<owner>`. It does mean the listbox offers 4 options where only 2 are ledgers and each owner name is announced twice (group label, then option), but that is a design question and this note does not propose changing it.
- **`aria-selected="true"` on the first owner row** is **cmdk's active-descendant convention** — it tracks the keyboard highlight, not the chosen value, and cmdk highlights the first item on open. Not a defect. It matters only as a constraint: `aria-selected` is already spoken for, so the repair must use `aria-current`.
- **No screen reader was run.** The claim is the observable absence of a programmatic current-row marker in the DOM, not a transcript of what any specific AT announces.

Fix: add `aria-current` (or equivalent accessible text) to the row whose value matches `currentLedgerId` / `i18n.language`, in both components, keeping the existing `<Check>` and `bg-accent` for sighted users and leaving owner rows, group labels, filtering, and cmdk highlight behaviour untouched. Owning package: `dashboard` only.

Blast radius: two call sites, both listed above. `ledger-switcher.tsx` renders on every ledger route via `common/components/ledger-layout`; `language-selector.tsx` renders in user settings → General → Appearance. No shared helper, no API or schema change.

Adjacent states: a single-ledger account (one group, one ledger) must still mark its row; a search-filtered ledger list must keep the marker when the current ledger survives filtering; loading and empty states unchanged; changing language must move the marker.

Dedupe: searched every queue including `done/` for switcher, `Select a ledger`, `aria-current`, language-selector and selected-state terms. `w3/m35/t008` touches `ledger-switcher.tsx` but only as a **timing** vehicle for report/export request identity, never its semantics. Open `w3/219` ("Keep the selected account identifiable on its detail page") is the same *class* on **React Native** — different package and surface. Completed `w3/188` was a native switch announcing an inverted state. `git log -S "currentLedgerId === ledger.id"` and the language-selector equivalent both show only the original import `af5339de`, so no later fix exists on main.

A source sweep for this exact pattern (`opacity-100` gated on a state comparison, excluding transition/hover usages) found **only** these two components, so the note is believed complete for the dashboard.

Unverified: actual screen-reader output, other locales, the narrow-viewport rendering of either control, and the behaviour after repair.
