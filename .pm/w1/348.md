# The ledger-check action's problem matcher keeps the two-space indent of `bea check`'s own error list, so a missing include, a plugin that will not load or an unclosed `pushtag` never lands on its `file:line`, and a narration with `9:30: ` becomes a bogus annotation

**Bug · cli · minor · ~45m · A3.** From routine cli-qa, 2026-11-20. The shared GitHub action (`cli/action/`, w22/m5) promises that "`bea check` errors land on their `file:line`" (`cli/docs/examples/ledger-check.md`). That holds only when `bea check` passes bean-check's output through. For the errors `bea check` reports itself, it prints `Error: <root>: N error(s).` and then one line per error indented by two spaces. That covers a missing or duplicate `include`, a plugin that cannot be imported, an unclosed `pushtag`/`pushmeta`, a valueless `custom`, a reserved metadata key, a booking crash, and a portable-document warning. The matcher's `^(.+):(\d+):\s+(.*)$` captures the indent as part of the file. When any one of those errors is present, every error in the list is printed this way, ordinary ones included. A missing include is the likeliest CI failure in a ledger repository: a file left out of the commit.

Environment: main `3ae696e1a`, `bea 0.5.0` from the checkout (`uv run bea`), Python 3.12.14, macOS 26.5.1 arm64. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY. Ran the action's own command, `bea --no-input --file main.bean check`, from the ledger's directory. Applied the shipped regexp from `cli/action/problem-matcher.json` with Python `re`; .NET reads this pattern the same way. Every command left the files byte-identical.

## Repro

```sh
cat > main.bean <<'EOF'
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
include "2026/march.bean"

2026-01-02 * "Standup 9:30: coffee"
  Assets:Cash  -10 USD
  Expenses:Food  9 USD
EOF
bea --no-input --file main.bean check      # 1: march.bean was never committed
mkdir 2026 && : > 2026/march.bean
bea --no-input --file main.bean check      # 2: the include now resolves
```

Actual. Run 1 exits 1 with this on stderr (paths shortened):

```
Error: /…/main.bean: 2 error(s).
  /…/main.bean:3: include "2026/march.bean" matches no file (looked for /…/2026/march.bean)
  /…/main.bean:5: Transaction does not balance: (-1 USD)
```

The matcher's `file` group is `'  /…/main.bean'`, with the two leading spaces, for both lines. The GitHub runner does not trim captured groups. In `actions/runner`, `IssueMatcher.cs` `GetValue` returns `group.Value`, and `Handlers/OutputManager.cs` ("// File") treats a path that does not start with `/` as relative. It joins the path onto the workspace, `File.Exists` fails, and it logs `Dropping file value … Path does not exist`. Both errors therefore appear as job-level annotations, with no file and no line in the pull request diff. The same happens with a plugin that cannot be imported (`plugin "no_such_plugin_mod"` → `  /…/main.bean:1: Cannot import plugin …`) and with a `document` outside the ledger tree (`  /…/main.bean:3: Document path '../../outside.pdf' resolves to …`).

Run 2 exits 1 in bean-check's own format. Its location line `/…/main.bean:5: Transaction does not balance: (-1 USD)` matches correctly. The context line `   2026-01-02 * "Standup 9:30: coffee"` also matches: file `'   2026-01-02 * "Standup 9'`, line `30`, message `coffee"`. That is a second, spurious error annotation. Any narration, payee or metadata value holding `<digits>: ` does this, such as a time or a `Ref 12: …`.

`cli/tests/test_ledger_check_matcher.py` covers only the one bean-check-format fixture (`docs/examples/ledger-check-broken.bean`), whose narration is `Lunch`. Neither shape is tested.

## Expected

Every error line `bea check` prints yields exactly one annotation, on its own file and line, in both of `bea check`'s output shapes. Context lines yield none. For run 1, the annotations are `main.bean` line 3 (the include) and line 5 (the balance error). For run 2, the only annotation is line 5.

## Cause

- `cli/action/problem-matcher.json:8`: `"^(.+):(\\d+):\\s+(.*)$"`. The greedy `(.+)` keeps leading whitespace and accepts any line holding `:<digits>:` and a space.
- `cli/src/cli/output.py:280` prints each `BeaError.details` entry as `f"  {detail}"`. `cli/src/cli/commands/check.py:191-194` raises `bea check`'s own findings that way, as a `LedgerError` with `details`. So does the portable-document refusal (`cli/src/bea_engine/main.py:1174`).
- bean-check indents its context lines by three spaces, and its location lines start at column 0.

## Fix

Change the matcher, not `bea`'s text output, since other users read that output. A pattern that accepts at most the two-space detail indent and requires a non-space at the start of the file does both jobs. Taking the first location on the line also helps: `"^(?:  )?(\\S.*?):(\\d+):\\s+(.*)$"`. Against the four captures above, it yields exactly the expected locations and nothing for the context line. In `test_ledger_check_matcher.py`, add a missing-include fixture (`bea`'s own list: `group(1)` equals the path with no indent, line 3) and a context line holding `9:30: ` (no match). Keep the existing cases green. The action is consumed at a pinned commit (`cli-v0.5.0`), so the fix reaches users with the next tagged pin in `ledger-check.md` and `ledger-check.yml`.

## Blast radius and controls

- Affected: the `bea-check` matcher in every workflow using `bex-co/beancount-io/cli/action`. That is every summary-mode error class above, plus a spurious annotation for `<digits>: ` text in a bean-check context block. The `bea-format` matcher (`^(would format: (.+))$`) works on `bea format --check` drift output. A missing include under `format --check` prints `missing include: "…" (included by …)` with no line. That line matches neither pattern, but the check step fails first in the action.
- Not affected: the pre-commit hooks (no matcher), and `bea --json check`.
- Working control: an ordinary bean-check error (run 2's location line) lands correctly.
