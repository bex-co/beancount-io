# A `bea update transactions` CSV row with only an id is told to pass `tags` or `narration`, columns the CSV form refuses

**Minor · cli · 15–25m · A1.** Routine cli-qa, 2026-11-23, HEAD `8ca0e9c13`, checkout `bea 0.5.0` (`uv run bea`), macOS 26.5.1, Python 3.12.14. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed, no TTY, cwd the ledger folder. Each run started from a pristine copy in a fresh process. No product fix implemented.

```sh
cat > main.bean <<'EOF'
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Expenses:Food USD

2026-01-02 ! "Coffee"
  import-id: "demo-1"
  Expenses:Uncategorized  4.50 USD
  Assets:Checking

2026-01-03 ! "Lunch"
  import-id: "demo-2"
  Expenses:Uncategorized  12.00 USD
  Assets:Checking
EOF
printf 'id,account,flag\ndemo-1,Expenses:Food,*\ndemo-2,,\n' > queue.csv
bea update transactions --from queue.csv                  # (1)
printf 'id,account,flag,narration\ndemo-2,,,Lunch with team\n' > q2.csv
bea update transactions --from q2.csv                     # (2)
printf 'id,account,flag,tags\ndemo-2,,,reviewed\n' > q3.csv
bea update transactions --from q3.csv                     # (3)
```

Actual:

1. Exit 0 (a preview). Row 2 is `rejected` with `Row 2: Nothing to change: pass 'account', 'flag', 'tags', or 'narration' alongside 'id'.` `--json` carries the same `reason`. With `--apply` it exits 1: `Updated 1 of 2 transactions; 1 row was rejected.`
2. Exit 2: `'q2.csv' (from --from) has unknown column 'narration'; use id, account, flag.`
3. Exit 2: `… has unknown column 'tags'; use id, account, flag.`

So half of the remedy in (1) cannot be followed in the form the user is writing.

Expected: a CSV row's refusal names only what a CSV mapping can carry: `Row 2: Nothing to change: fill its account or flag cell, or drop the row.` The JSON-row wording (`'account', 'flag', 'tags', or 'narration'`) stays for JSON input, where all four fields are accepted. The `--help` text says "CSV rows map an id to an account and a flag; empty cells leave the field" (`cli/src/cli/commands/update.py:354`), and `_CSV_COLUMNS` (`:180`) admits only `id`, `account` and `flag`.

Cause: the engine's `_validate_request` (`cli/src/bea_engine/ledger/updating.py:388-391`) writes one sentence for every row and cannot tell a CSV row from a JSON row. The frontend's `_rows_from_csv` (`cli/src/cli/commands/update.py:191`) drops the empty cells, so the row reaches the engine as `{"id": "demo-2"}`, the same as a bare JSON row.

Fix: have the frontend refuse, or reword, an id-only CSV row before sending it: in `_rows_from_csv`, a row with no non-empty `account` or `flag` cell gets the CSV wording above. Alternatively, pass the mapping's form in the request so the engine words the reason for it. Either way, keep the row `rejected` with the same exit codes.

Blast radius: only `update transactions --from` with CSV input, from a file or stdin. The single-row `bea update transaction --id X` names its own flags (`--account, --flag, --tag, or --narration`), which all exist. JSON rows are worded correctly.

Dedupe: searched `.pm/**` for `Nothing to change`, `unknown column`, `_CSV_COLUMNS`. No item covers it. The CSV form has accepted only id/account/flag since `62c0e1910` (2026-10-25), and the engine sentence dates from `f29921b65`.

Acceptance: (1) names only the account and flag cells for row 2, and a JSON `[{"id":"demo-2"}]` row keeps the four-field sentence. A test pins both wordings.
