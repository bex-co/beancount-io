## Objective

A `main.bean` saved as UTF-8 with BOM — the default in several Windows editors — cannot be checked, listed, queried, or written to, because Beancount sees the byte-order mark glued to the first keyword. `bea import` already strips a BOM from CSV, so the tooling is inconsistent with itself.

## Context

- `w3/257`: `bea` rejects BOM ledger files with `Invalid token: '\ufeffoption'` while import strips BOM CSV.
- Ledger text is read by `cli/src/bea_engine/ledger/reader.py` and `cli/src/bea_engine/ledger/text.py`.
- This blocks every command on the file, so it is a first-contact failure for a Windows newcomer.

## Steps

1. Strip a leading BOM when reading any ledger file, including included files, before the text reaches the parser.
2. Preserve the rest of the file's bytes exactly; stripping the mark must not reformat anything.
3. Make `bea format -i` remove the BOM from the file on disk, so the ledger converges to a clean encoding.
4. Ensure writes never reintroduce a BOM.

## Files

- cli/src/bea_engine/ledger/reader.py
- cli/src/bea_engine/ledger/text.py
- cli/src/bea_engine/ledger/writer.py
- cli/tests/test_writer.py

## Acceptance criteria

- [ ] `bea check`, `list`, `query`, `report`, and `add` all work on a BOM-prefixed ledger and on a BOM-prefixed include.
- [ ] `bea format -i` removes the BOM; running it again is a no-op.
- [ ] No write reintroduces a BOM.
- [ ] Non-BOM ledgers are byte-identical before and after, unchanged from today.

## Out of scope

- UTF-16 or other non-UTF-8 ledger encodings, covered by t003's error reporting.
- CSV BOM handling, which already works.
