# Exported statements are dated in the future, and the date moves with the chart interval

**Minor · 45–60m · dashboard.** A3: an exported Balance Sheet or Income Statement is the artifact a user hands to a lender, an accountant, or a community reader. A statement dated after the day it was generated does not survive that hand-off.

Found 2026-09-13 by a dashboard QA sweep against production `https://beancount.io`, signed in, ledger `puncsky/example`, headless Chromium 1440×1000, generated 2026-09-13.

Every exported statement takes its reporting date from the last **chart interval bucket**, not from the ledger or from any period the user selected. With no time filter, the last monthly bucket for the current month is that month's *end*, so the date lands in the future — and changing the chart's granularity selector moves it further.

Repro:

1. Open `/ledger/<owner>/<ledger>/balance-sheet` with no time filter, interval **Monthly**.
2. Export → **Markdown report**. Header reads `**As of September 30, 2026**`; filename is `…-balance_sheet-2026-09-30-at_cost-2026-09-13.md`.
3. Change only the interval selector to **Yearly**. Export → **Markdown report** again.
4. Header now reads `**As of December 31, 2026**`; filename `…-balance_sheet-2026-12-31-…`.

Expected: a statement is dated no later than the day it is generated — the latest date with actual ledger activity, or the end of an explicitly selected period. A presentation control must not change the reporting date at all.

Actual: both exports are dated in the future relative to their own footer (`Generated by Beancount.io on Sep 13, 2026`), and a chart-granularity change alone moves the asserted date 3½ months. `diff` of the two Markdown files is **four lines**: the header date, the notice date, and the generation timestamp. Every figure is byte-identical:

```
5c5
< **As of September 30, 2026**
---
> **As of December 31, 2026**
21c21
< - No explicit as-of date was selected. This statement uses the latest date available in the report: September 30, 2026.
---
> - No explicit as-of date was selected. This statement uses the latest date available in the report: December 31, 2026.
```

All three renderers carry it, so this is not a Markdown formatting issue:

- CSV row: `as_of_date=2026-12-31` beside `generated_at=2026-09-13T20:03:20.941Z`.
- Income Statement Markdown: `**All available ledger activity through September 30, 2026**`, filename `…-profit_and_loss-through-2026-09-30-…`.
- The filename itself embeds the future date, so the artifact is mis-dated even before it is opened.

The newest transaction in the fixture ledger is `2026-09-01` (API control: `getLedgerJournal(query: {directiveTypes: ["Transaction"], offset: 0, limit: 8})` → HTTP 200, `total` 1047, newest date `2026-09-01`). No date in the data justifies September 30 or December 31.

Root: `dashboard/src/features/reports/export/reporting-period.ts:203-248` — `resolveReportingPeriod` sets `asOfDate: explicit?.endDate ?? latestDate` for `balance_sheet` (`:229`) and `endDate: explicit?.endDate ?? latestDate` for the period statements (`:244`). `latestDate` is `validReportDates(reportDates).at(-1)` (`:221-223`), and `reportDates` are the report's **interval bucket** dates, whose final bucket for an in-progress period ends in the future. The `interval` argument is already threaded into this function (`:214`), which is why the chart selector moves the answer. The explicit-filter path (`explicit?.endDate`) is correct and is not in scope.

Fix: clamp the implicit reporting date to reality — never emit a date after the generation date, and prefer the latest date with actual ledger activity over the trailing interval bucket. The reporting date must not depend on `interval` at all. Keep the explicit-time-selection path, the existing `asOfDateUnavailableNotice` fallback, the internal-draft labelling, and the multi-unit notices exactly as they are. If a partial current period is used, say so in the notices rather than rounding the date forward. Owning package: `dashboard` only — no API, schema, or cross-package change.

Blast radius: `resolveReportingPeriod` is the single date source for all three statement kinds and all three renderers — `export/markdown.ts:70-71` (header) and `:221-226` (notice), `export/csv.ts:49` and `:98` (`as_of_date` column), the print renderer, and the download filename. Working control: an explicit time selection (for example `time=2026-01`) produces a correct in-period date, which is what `.pm/w3/129.md` observed while documenting a different defect.

Adjacent states: loading and error states of the report pages are unchanged; a ledger whose activity genuinely runs to a month end must keep that date; `reportDates` empty must keep the existing `asOfDate: null` + `asOfDateUnavailableNotice` path (`reporting-period.ts:245`).

Dedupe: searched every queue including `done/` for `asOfDate`, `as_of_date`, "as of", and export/date terms. `.pm/w3/129.md` is export **scope lag while a filter is loading** and explicitly records its `as_of_date` as *correct* for an explicit selection — different mechanism, different path. `.pm/w3/done/m18` is holdings lot pricing. `.pm/w4/done/m1/done/t003.md` is unrelated. `git log -S asOfDate -- src/features/reports/export/reporting-period.ts` shows only the original `d162671f feat(dashboard): export professional financial statements` — no later date-clamping change on main, so this is not deployment lag and not a regression of shipped work.
