# On a ledger whose existing `pad` names an inactive account, every write except `add price`, `add balance` and `import` says "The change would leave the ledger invalid", blaming a harmless write for errors the ledger already had

Found by `/qa-find-bugs-cli w1` on 2026-11-18 (HEAD `6352f9223`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, Python 3.12, stdin closed, no TTY, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`). Severity: minor (nothing is written, which is right; the sentence says the write is at fault). A1: an agent told that its own change breaks the ledger retries other spellings of that change instead of fixing the pad. This is an incomplete fix of w5/682, which corrected only the `add price` and `add balance` pre-checks.

**Repro** (a fresh directory):

```sh
cat > main.bean <<'EOF'
2026-01-01 open Assets:Bank USD
2026-01-01 open Equity:Opening USD

2025-12-20 pad Assets:Bank Equity:Opening
2026-01-02 balance Assets:Bank 100 USD
EOF
bea --file main.bean add open --date 2026-01-05 --account Expenses:Fun
bea --file main.bean add open --date 2026-01-05 --account Expenses:Fun --allow-errors
bea --file main.bean add price --date 2026-01-05 --commodity EUR --amount '1.10 USD'
```

**Actual:** the first two exit 1 with `The change would leave the ledger invalid; nothing was written.` The only details are the pad's pre-existing `main.bean:4: Invalid reference to inactive account …` errors, and `bea check` reports them before any write. The JSON envelope carries the same message. `add note`, `add event`, `add custom`, `add commodity`, `add transaction` and `add transactions --from` say the same. The control `add price` (and `add balance`, and `import`) exits 1 with the w5/682 wording: `The ledger already has 4 error(s), including an invalid pad account; nothing was written. Open missing accounts or correct the pad account/date first: --allow-errors cannot bypass an inactive pad account.`, followed by `Pad dated 2025-12-20: Assets:Bank and Equity:Opening must both be active on that date.`. The file is byte-identical after every run.

**Expected:** every write refused only because of an inactive pad the ledger already had says so, in the words `add price` uses: the ledger already has N errors, including an invalid pad account. Open the missing accounts or correct the pad first, since `--allow-errors` cannot bypass it. A write that does add an error of its own keeps "The change would leave the ledger invalid".

**Root cause:** `validate_candidate` in `cli/src/bea_engine/ledger/write.py` (about lines 3118–3164) checks for errors the ledger already had (`_preexisting_errors`) only when `not (any_appended or syntax_errors or invalid_pad_accounts)`. So a pre-existing invalid pad skips that check and falls through to the generic `The change would leave the ledger invalid` at about line 3160. Under `--allow-errors` the `blocking` path keeps the same headline. w5/682 added `preexisting_refusal` (about line 3213) with the right wording, but only the strict pre-checks in `ledger/adding.py` (balance about line 597, price about line 1126), `importing.py:262` and `write.py:4343` call it.

**Fix:** in `validate_candidate`, when every invalid-pad error (and every other error) predates the write, raise the `preexisting_refusal` wording, with and without `--allow-errors`, instead of "The change would leave the ledger invalid". Keep the w5/395 rule that the `--allow-errors` mention appears only when it matters. Add a regression test that runs `add open`, `add note` and `add transaction` against the repro ledger, with and without `--allow-errors`, in human and JSON modes. It should assert the pre-existing pad wording, exit 1 and an unchanged file. Also add a control in which the write itself references an inactive account and still says "The change would leave the ledger invalid". Revert the fix and watch it fail.

**Dedupe:** w5/682 (the price and balance pre-checks: this note's control), w5/508 (syntax errors), w5/395 ("even with --allow-errors" printed without the flag) and w5/396 (a write refused only for errors the ledger already had names `--allow-errors`) are all done. None covers the shared validation path the other writes take. No open item overlaps.
