# `bea report register` with `--time` lists each summarized account's counter-leg on `Equity:Opening-Balances`, so an equity register runs through balances the account never held and names an account the ledger never opened

Found by `/qa-find-bugs-cli w1` on 2026-11-17 (HEAD `ea932eb55`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`). Severity: minor (totals are right; the rows and running balances are not). A1: an agent reading `register Equity:Opening-Balances -t 2024-03` sees the account at -5,500.00 USD, then -1,012.50, then -2,012.50, before it settles at -1,000.00. It also sees rows "for" `Assets:Bank:Checking` and `Liabilities:Card` on an equity account, and cannot tell which rows are real.

bea --file "$PWD/main.bean" report trial-balance -t 2024-03    # Opening-Balances -1,000.00 USD (correct)

Rename the equity account to `Equity:Opening` (`sed -i '' 's/Opening-Balances/Opening/g' main.bean`) and run `report register Equity -t 2024-03`. Four rows now sit on `Equity:Opening-Balances`, an account the ledger never opens and that the w3/288 fix keeps out of every report tree. They net to zero. `--json` and `--format csv` carry the same rows. Exit 0 throughout. I repeated it from a pristine fixture in a fresh process and got the same result. Control: `register Assets:Bank:Checking -t 2024-02` shows one opening row (4,000.00) and is correct.

**Expected.** A period register shows one opening row per account in the subtree, carrying that account's own balance at the period start, then the period's postings. For the repro that is a single `Opening balance … -1,000.00 USD` row. For `register Equity` it is `Equity:Earnings:Previous -4,487.50` and `Equity:Opening -1,000.00` (or `Opening-Balances`), ending at -5,487.50 as the trial balance does. No row names a never-opened account, and no running balance passes through amounts the account never held. Beancount's `summarize` (`beancount/ops/summarize.py`, `FLAG_SUMMARIZE`, "Opening balance for '{account}' (Summarization)") gives each summarized account its own transaction: posting 0 is the account's balance, and posting 1 is the plug on `account_previous_balances` (default `Opening-Balances`).

**Root cause.** `_register` in `cli/src/bea_engine/report.py` (the `ordered` loop at about lines 1049–1062) takes every posting of every period transaction whose account is in the subtree. For a summarization transaction (`flag == "S"`), the plug leg on `account_previous_balances` is therefore listed as if money had moved through that account. The trees avoid the phantom (w3/288) only because they render net inventories.

**Fix.** In the `ordered` loop, keep only the summarized account's own leg of a summarization transaction (`entry.flag == flags.FLAG_SUMMARIZE`: `entry.postings[0]`, or the posting whose account the narration names). Drop the plug leg. Leave real transactions and the conversions entry untouched. The last row must still equal the trial-balance total, and the closing-row logic stays as is.

**Acceptance.** The repro's register shows exactly one row, -1,000.00 USD. The renamed variant's `register Equity -t 2024-03` shows no `Equity:Opening-Balances` row and ends at -5,487.50 USD. The same holds in JSON and CSV. The `Assets:Bank:Checking` control is unchanged, and so is an unfiltered register. Regression tests fail with the fix reverted, and `make check-all` passes.

**Dedupe.** I searched `.pm/**` for `Summarization`, `Opening-Balances`, `phantom` and `register`. w3/288 (done) removed the phantom from report and `balance` trees only. w5/1056 (done) fixed same-day row order in the register, and w1/252 and w1/260 (done) fixed per-row valuation and subaccount naming. No item covers summarization plug legs in the register. Estimate 30–45m.
