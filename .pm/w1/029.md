# Subscription usage counts still follow the browser locale — the w3/132 helper reached two of its three siblings

**Minor · 20–30m · dashboard.** A2: plan quota numbers on `/settings/general` should read in the language the user chose, not the one their browser happens to be set to.

Found 2026-09-13 by a dashboard QA sweep — a source audit of unlocalized formatting. Residual follow-up to completed [w3/132](../w3/done/132.md), not a regression of it.

`w3/132` was scoped to `subscription-plan-banner.tsx:30-38`. Its fix (`254cfea0`) introduced a shared helper whose docstring states the problem plainly:

```ts
// user-settings/pages/general/use-quota-number-format.ts:5-9
/**
 * Formats a plan quota count in the **app** language.
 *
 * A bare `toLocaleString()` follows the browser locale, so a user reading the
 * dashboard in German still saw "1,000,000" instead of "1.000.000".
 */
```

Three components in that directory render quota counts. Two adopted the helper — `subscription-plan-banner.tsx` and `subscription-upgrade-cards.tsx` (whose own comment reads *"App-locale counts; `toLocaleString()` would follow the browser locale"*). The third did not:

```tsx
// user-settings/pages/general/subscription-usage-overview.tsx:47,50,51
used: aiCfoTokensUsed.toLocaleString(),
used: aiCfoTokensUsed.toLocaleString(),
max: aiCfoTokensMax.toLocaleString(),
```

It does not import `useQuotaNumberFormat`, and `git log -S toLocaleString` on that file shows only the original import `af5339de` — so no later change touched these three calls.

Mechanism reproduced live on `https://beancount.io/settings/general?lang=en`, authenticated, isolated headless Chromium 1440×1000 with the browser locale forced to **de-DE** and the app language set to **en**: every grouped number on the page renders with German separators — `2.000.000`, `163.466`, `10.000.000`, `9.202` — and none with English commas. The same page with an en-US browser renders all of them with commas. That is exactly the browser-vs-app divergence the helper exists to prevent.

Expected: quota counts follow the selected app language, like every other number on that page after `254cfea0`.

Actual: the usage-overview counts follow the browser.

**Production-visibility caveat, stated so the repro is not misread.** The live build predates `254cfea0`, so on production *all three* components currently follow the browser and the inconsistency between them is not yet observable. The measurement above therefore demonstrates the **mechanism**, not the sibling mismatch. The mismatch is proven from HEAD source, and will become visible on `/settings/general` as soon as `254cfea0` deploys — at which point the banner and upgrade cards will read in the app language while the usage counts beside them do not. (The same sweep used this result to narrow the deployed dashboard build to between `86ca4531` 22:17 and `254cfea0` 23:12 on 2026-09-11.)

Fix: call `useQuotaNumberFormat()` in `subscription-usage-overview.tsx` for the three counts, exactly as `subscription-plan-banner.tsx` and `subscription-upgrade-cards.tsx` already do. No new helper, no API or schema change, no quota or billing logic touched. Owning package: `dashboard` only.

Blast radius: one component, three call sites; it is rendered by the subscription section of `/settings/general`. A directory-wide sweep for bare `toLocaleString()` found no other unconverted quota consumer.

Adjacent states: an unlimited or absent quota must keep its existing fallback rendering; the `used`/`max` pairing and its translated surrounding copy are unchanged; switching app language must update the counts without a reload, as it already does for the two converted siblings.

Dedupe: searched every queue including `done/` for subscription, quota, locale, `toLocaleString` and number-formatting terms. Completed `w3/132` is the **plan banner** and explicitly names only `subscription-plan-banner.tsx:30-38`; it never mentions this component, so this is scope it never covered rather than a reopen. Completed `w3/144` is Net Worth / Recent Activity date language, and completed `w3/110` is shared report number formatting and hydration, which `132`'s own dedupe records as explicitly excluding inline quota formatters. No open item covers it.

Unverified: other locales beyond de-DE/en-US, the narrow viewport, screen-reader output, and the behaviour after repair.
