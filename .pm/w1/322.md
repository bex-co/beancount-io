# In a whole-number ledger, one `2.5 FUND {10000 JPY}` purchase with the cash leg omitted makes every text report print that currency with a `.0`: `Net Profit: -1,200.0 JPY`, `Equity -1,000,000.0 JPY`

**Source:** routine cli-qa, 2026-11-19. **Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** cli. **A1:** a yen or won ledger is written in whole units, and so is a whole-dollar ledger. Suppose one purchase of a fractional quantity at a whole-unit cost leaves its cash leg for Beancount to infer, the usual way to book a buy: `2.5 FUND {10000 JPY}`, or `0.5 BTC {80000 USD}`. From then on, every `balance` and `report` table prints that currency with one decimal it never had. The trial balance shows `-1,000,000.0 JPY`, the income statement `Net Profit: -1,200.0 JPY`, and the holdings table `AVG COST 10,000.0 JPY`. With the cash leg written out, the same ledger prints whole yen. The figures are right. Only the display changes, and `--json` stays exact. An agent pasting the table into a summary still reports amounts in a precision the books do not use. This is a gap left by w5/093.

Found at `68d477f52` with the checkout's `uv run bea` 0.4.1, Python 3.12.14, macOS 26.5.1. The run used an isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME` with `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, stdout piped, and a synthetic ledger. Reproduced in fresh processes from a pristine copy. The ledger's hash was unchanged, and stderr was empty.

## Actual

```
  Assets                                          999,800.0 JPY
    Bank                                          973,800.0 JPY
      Checking                                    973,800.0 JPY
    Broker                                        26,000.0 JPY
  Equity                                          -1,000,000.0 JPY
  Valuation/translation adjustment:               -1,000.0 JPY
  Expenses                                        1,200.0 JPY
```

The income statement reads `Net Profit: -1,200.0 JPY`, with `0.0 JPY` and `1,200.0 JPY` in its breakdown. The holdings row reads `10,000.0 JPY  25,000.0 JPY  26,000.0 JPY`. JSON is exact: `{"JPY":"-1200"}`. `bea list transaction` shows the inferred leg as `Assets:Bank:Checking: -25000.0 JPY`: 2.5 × 10000 keeps the unit count's decimal place, though its value is a whole number.

The same happens with `2.5 FUND @ 10000 JPY` and `0.5 FUND {10000 JPY}`. In a USD ledger written in whole dollars, `0.5 BTC {80000 USD}` with the cash leg omitted prints `-100,000.0 USD`, `Net Profit: 0.0 USD` and, at `price BTC 62036.26 USD`, a holdings market value of `31,018.1 USD`.

Controls:

- The same ledger with the leg written as `Assets:Bank:Checking  -25000 JPY` prints `999,800 JPY`, `-1,000,000 JPY` and `1,200 JPY`.
- `2.5 FUND {{25000 JPY}}` and `2.5 FUND @@ 25000 JPY` print whole yen.
- `2.5 FUND {10001 JPY}` infers a real half yen (`-25002.5 JPY`), and printing one decimal is right there.
- `bea query` renders with Beancount's own display context and is unaffected.

## Expected

`docs/USAGE.md` (Reports): "Human tables round each currency to the finest precision the ledger itself uses for it, so a whole-dollar ledger prints `10 USD` rather than `10.00`". An inferred amount counts only so that "an inferred `31.5 USD` in a whole-dollar ledger is not rounded away" (w5/093). An inferred `-25000.0` has no subunits: its value is a whole number. It should teach the display nothing more than `-25000` would. In this ledger every JPY figure prints in whole yen, as the control with the written leg does. An inferred amount with a real fraction (`-25002.5`, w5/093's `31.5` and `68.5`) still shows its digits.

## Root cause

- `cli/src/bea_engine/report.py:2599` `_display_precision.learn` counts digits from `number.as_tuple().exponent`, so trailing zeros count.
- For an inferred leg, the loop at `report.py:2630-2652` calls `learn(number, …, inferred, limit)` on Beancount's product `-25000.0`. The cap from `_written_transaction_precision` (`report.py:2744`, `places(units) + places(cost.number_per)` = 1 + 0) allows one digit, so `inferred["JPY"] = 1`.
- `report.py:2653-2655` then adopts it, because the ledger's written JPY amounts have zero fractional digits.

## Fix

For the interpolated (pending) postings only, count the digits of the normalized value: strip trailing zeros, so `Decimal("-25000.0")` counts 0 and `Decimal("31.5")` counts 1. A whole-number product then adds nothing, and a real fraction keeps its digits under the existing cap. Leave written postings and balance assertions counting their typed digits: a ledger that writes `100.00 USD` keeps its cents.

`cli/tests/test_at_value_costless.py` currently asserts `"21.0 USD"`. That is the inferred leg of `2 HOOL @ 10.5 USD` in a whole-dollar ledger, so the same artifact. Update it to `"21 USD"`; its subject, costless lots priced at value, is unchanged.

Add cases to `cli/tests/test_report_precision_ignores_interpolated_legs.py`:

- this repro prints `-1,200 JPY` and `-1,000,000 JPY` in `balance`, the income statement and holdings, matching the written-leg control;
- `@` and `{}` variants;
- the existing `68.5 USD` and a `{10001 JPY}` half-yen control keep their decimal.

Run `make check-all` in `cli/`.

## Blast radius

`_display_precision` feeds every frontend-rendered report: `balance`, overview, income statement, balance sheet, trial balance, holdings, register, capital gains, cash flow and budget (`report.py`). The `bea doctor` scoped trees build their own context in `bea_engine/scoped.py` (`_context_of`, w5/571/997) and are not changed by this fix. JSON and CSV carry exact values and are unaffected.

## Dedupe

Searched `.pm/**` for `display precision`, `_display_precision`, `trailing zero`, `.0 USD`, `.0 JPY`, `inferred` and `interpolated`. Two items are related and done:

- w5/093 (`1b51b7b8`) stopped an inferred leg from teaching a cents ledger a cost's digits. Its resolution keeps inferred legs counting in whole-number ledgers, to show a real `31.5`. It names a remaining gap, "a whole-number ledger with a many-decimal cost and an omitted leg". That is a different case: here the cost is a whole number and the inferred amount's value is integral.
- w5/668 capped `@@`/`{{}}` totals, which is why those controls pass.

w1/052 (price quotes), w3/365 (forced `.00`), w5/946 (plugin fractions) and w1/313/317 (repeating quotients) cover other precision sources. No open item covers this. It is not deployment lag: HEAD still counts trailing zeros.
