# reconcile-account's Verify step assumes a failing assertion still writes

**Copy · backend-v2 (MCP prompts) · minor · ~20m · A1.** From `/qa-find-bugs-mcp`, 2026-11-09, production `beancount-mcp 1.0.0`, the disposable QA ledger, no banks linked.

- **Repro:**
  1. Call `prompts/get reconcile-account {"ledger":"<o>/<n>","account":"Assets:Bank:Checking","period":"2026-08"}`. Step 5 says: append the transactions and the `balance` entry in one `addLedgerEntries` call, then read `validation.newErrors`, and if the assertion fails, report the residual. The ground rules also say to read `validation.newErrors` "from the result".
  2. Follow that with a statement balance that doesn't tie. The call returns `isError` `VALIDATION_FAILED` ("Balance failed … expected 6600.00 USD, got 6702.01 USD") and has no `validation` object. Nothing in the batch is written, so the missing transactions are not written either. The hint offers `allowInvalid: true`, which the playbook never mentions.
  3. **Control:** the same call with `dry_run: true` returns `validation.newErrors` with `valid: false`.
- **Expected:** the playbook says what MCP actually does:
  - preview the batch with `dry_run` first and read the residual from that preview;
  - if the residual is not zero, withhold the assertion (report `partial`) and commit only the confirmed transactions;
  - never use `allowInvalid` to land a failing assertion.
  The CLI skill it was ported from covers this case (`skills/beancount-reconcile/SKILL.md:194,295`).
- **Cause:** `src/features/ai-agent/api/mcp-prompts.ts:242-246` (reconcile Verify) and `:133` (the shared ground rule) describe a write that lands and then reports errors. The text dates from adfcf5870 (w2/008).
- **Fix:** reword reconcile Propose/Verify and the ground rule ("read `validation.newErrors` from the `dry_run` or the result; a commit that would add errors is refused `VALIDATION_FAILED`"). Give the close-month and categorize-imports write steps the same wording.
- **Check:** update the prompt text tests.
