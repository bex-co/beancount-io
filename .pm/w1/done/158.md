# A zero-day `CLOSE ON` window inside a subquery bypasses the empty-window refusal

**Severity: minor. Owner: cli. Estimate: ~30m. A1:** a confident empty answer for a day with entries misleads agents. Continuous CLI QA, 2026-10-03 (round 12); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with before/after hashes and a working control. Found by a regression hunt over shipped fixes.

Ledger with `2024-02-01 * "x"` / `Expenses:Food 5 USD` / `Assets:Cash`:

```sh
bea --file /abs/q.bean query "SELECT date, narration FROM (SELECT date, narration FROM OPEN ON 2024-02-01 CLOSE ON 2024-02-01)"
```

Actual: exit 0 `(no rows)` (also with an outer `WHERE date = 2024-02-01`); a reversed window in a subquery gets upstream's bare "CLOSE date must follow OPEN date" without bea's hint. Controls: the top-level form, `JOURNAL`, `BALANCES`, `PRINT` refuse correctly; the subquery with `CLOSE ON 2024-02-02` returns the row.

Cause: `cli/src/bea_engine/query.py:794` reads only the outer `from_clause`; nested `Select` nodes aren't searched. Gap in `b991525d` (`w3/done/372`).

Fix/acceptance: walk nested `Select` nodes and check every dated `From`. The repro exits 2 with the "covers no days … use CLOSE ON 2024-02-02" hint; the valid subquery still returns rows.

---

**Resolved 2026-10-04** — zero-day or reversed `OPEN ON`/`CLOSE ON` windows inside subqueries now get the same "covers no days" refusal and hint as top-level ones; the check walks the whole parsed query. Tests in `tests/test_query_empty_date_window.py` cover it. Shipped in the commit that moved this note (`cli`).
