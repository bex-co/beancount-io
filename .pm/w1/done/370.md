# `bea add balance --amount '6,500.00 USD,'` says "Invalid amount '6,500.00'. A comma is read only as a thousands separator…" about a number bea accepts; `$1,500.00`, `~1,500` and `1,500.5.5` get the same comma advice, and removing the separators only earns a second refusal

**Bug · cli · minor · 30–45m · A1/A2.** From routine cli-qa, 2026-11-23. The comma-grouping help ("A comma is read only as a thousands separator between groups of three digits, such as '1,538.25'; write the fraction after a decimal point, or remove the separators") is printed whenever an amount fails to parse and contains a comma anywhere. It is right for `4,50` and `1.234,56` (w5/534, w5/722). It is wrong when the comma grouping is valid and something else is the problem: a stray comma after the amount, a currency symbol, a leading `~`, or a second decimal point. The message then quotes a number bea itself accepts as "Invalid amount", and a user or agent who follows it (removes the separators) gets a different refusal on the next try. Nothing is written in any case; only the diagnosis is wrong.

Environment: main `6d3277fb4`, `bea 0.5.0` from the checkout (`uv run bea`), macOS 26.5.1. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, fresh processes. Reproduced twice from a pristine fixture; the ledger is byte-identical after every refusal.

## Repro

`main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-01-01 commodity HOOL
```

```sh
bea --file /abs/main.bean add transaction Lunch --date 2026-02-01 -p 'Expenses:Food 1,000.00 USD, Assets:Checking' -p Assets:Checking
bea --file /abs/main.bean add balance --date 2026-02-01 -a Assets:Checking --amount '6,500.00 USD,'
bea --file /abs/main.bean add price --date 2026-02-01 -c HOOL --amount '$1,500.00 USD'
bea --file /abs/main.bean add price --date 2026-02-01 -c HOOL --amount '$1500.00 USD'      # following the advice
bea --file /abs/main.bean add custom --date 2026-02-01 -t goal -v 'number:1,500.5.5'
bea --file /abs/main.bean add custom --date 2026-02-01 -t goal -v 'amount:~1,500 USD'
bea --no-input init books --currency USD --date 2026-01-01 --opening-balance 'Assets:Checking $1,000.00'
```

## Actual

All exit 2 and write nothing:

1. `--posting 1: Invalid amount '1,000.00'. A comma is read only as a thousands separator between groups of three digits, such as '1,538.25'; write the fraction after a decimal point, or remove the separators.`
2. `--amount: Invalid amount '6,500.00'. A comma is read only as a thousands separator …`
3. `Invalid amount '$1,500.00'. A comma is read only as a thousands separator …`
4. Doing what 3 says: `Invalid amount '$1500.00'. Use finite decimal notation with ASCII digits, such as '1538.25'.`
5. `Invalid amount '1,500.5.5'. A comma is read only as a thousands separator …`
6. `Invalid amount '~1,500'. A comma is read only as a thousands separator …`
7. `--opening-balance 'Assets:Checking $1,000.00': Invalid amount '$1,000.00'. A comma is read only as a thousands separator …` The interactive init prompt answers `Assets:Checking 1,500.00` the same way.

The bulk path does too: `bea add transactions` with `"amount": "1,000.00 USD,"` reports `Invalid amount '1,000.00'. A comma is read only as a thousands separator …`.

Controls: `-p 'Expenses:Food 1,000.00 USD'` and `add price --amount '1,500.00 USD'` are accepted (exit 0, written as `1000.00 USD` / `1500.00 USD`), so cases 1 and 2 call an accepted number invalid. `-p 'Expenses:Food 10.00 USD, Assets:Checking'`, with no grouped number, gets Beancount's own `syntax error, unexpected COMMA …`. A bulk `"amount": "$1,000.00 USD"` gets `Invalid token: '$1,000.00'`, which names the real problem. `-p 'Expenses:Food 4,50 USD'` keeps the comma help, correctly.

## Expected

The comma help appears only when the comma is the obstacle: the quoted text is made of digits, commas and at most one decimal point, and its commas are not three-digit grouping (`4,50`, `1.234,56`, `1,5000`). Otherwise the refusal names what is actually wrong, and following it leads to an accepted command:

- a stray comma after a valid amount (cases 1, 2 and the bulk row): say the text after the amount is not part of it, and for `-p`, that each posting takes its own `--posting`;
- a symbol, `~` or other non-numeric character (cases 3, 6, 7): the generic "Use finite decimal notation with ASCII digits" message, or one that names the character (`'$' is not part of a number; give the currency after it, such as '1,500.00 USD'`);
- a second decimal point (case 5): the generic message.

Basis: `cli/docs/USAGE.md` documents comma grouping in threes as accepted on these flags, and the controls above accept it, so a message calling `1,000.00` invalid contradicts the contract.

## Cause

Two places pick the comma help from the mere presence of a comma:

- `cli/src/cli/amounts.py:73-74` (`parse_decimal_number`, frontend: `add price`, `add custom`, `init --opening-balance` and its prompt) and its engine twin `cli/src/bea_engine/amounts.py:221-222` raise `_GROUPING_MESSAGE` / `DECIMAL_COMMA_HELP` for any non-matching text with `","` in it.
- `cli/src/bea_engine/query.py:3581-3588` (`readable_parser_message`, the w5/722 mapping used by `--posting`, `add balance --amount` and bulk `amount` strings through `ledger/adding.py:1236`, `:1502` and `ledger/models.py:353`) answers every Beancount `unexpected COMMA` with the first `[0-9][0-9.,]*,[0-9.,]*` run in the input, even when that run is valid grouping and the unexpected comma is a later one.

## Fix

Owned by `cli`. In both `parse_decimal_number` twins, give the comma help only when the text matches `[+-]?[0-9.,]+` with at most one `.` and is not valid grouping; otherwise fall through to the generic message (optionally naming the first character that is not a digit, sign, comma or point). In `readable_parser_message`, use the comma help only when the matched run is not valid three-digit grouping (reuse the grouping regex); when it is valid, report the stray comma after it instead. Add subprocess regression cases to `cli/tests/test_flag_numbers_read_comma_grouping.py` (or `test_add_decimal_comma_and_tag_wording.py`) for repro cases 1–7 and the bulk row, asserting the new wording and that `thousands separator` is absent, plus the `4,50` / `1.234,56` cases still getting the comma help. Revert the fix and watch them fail. Run `make check-all` in `cli/`.

## Dedupe

Searched `.pm/**` for `comma is read only`, `thousands separator between groups`, `unexpected COMMA`, `Invalid amount`: w5/534 and w5/722 (done) added the comma help and the `unexpected COMMA` mapping this overreaches from. w1/367 (done) noted the prompt shape under "Adjacent" ("`cli/src/cli/amounts.py:56` picks the comma message for any unparseable text containing a comma"); its fix made the prompt accept a trailing currency but left this rule in place, and the stray-comma and bulk paths were not named there. ---

**Resolved 2026-11-23** — The comma help now appears only when the comma is the obstacle, shipped in the commit carrying this note (`cli`). Both `parse_decimal_number` twins (`cli/src/cli/amounts.py`, `cli/src/bea_engine/amounts.py`) give it only for text made of digits, commas and points whose commas are not grouping in threes before the fraction (`4,50`, `1.234,56`, `1,5000`, `1.234.567,89`); `$1,500.00`, `~1,500`, `1,500.5.5` and the `init --opening-balance` / prompt forms get the generic "Use finite decimal notation with ASCII digits" message. `readable_parser_message` (`cli/src/bea_engine/query.py`) quotes the first comma run that is not valid grouping, so `1,000.00 USD @ 1.234,56 USD` names `1.234,56`; when every run groups correctly it names the stray comma instead (`Unexpected ',' after '6,500.00 USD'; the text from the comma on is not part of it.`, commas inside a cost's braces skipped), and `--posting` adds "Give each posting its own --posting." The same reaches `add balance --amount` and bulk `amount` strings, and `10.00 USD,` (no grouped number) now gets the stray-comma wording too instead of Beancount's raw `unexpected COMMA`. `cli/docs/USAGE.md` records the rule. Regression tests: `tests/test_add_decimal_comma_and_tag_wording.py` (subprocess: repro cases 1–7, the bulk row, the later decimal comma, and following the symbol advice to an accepted `add price`) and `tests/test_flag_numbers_read_comma_grouping.py` (both twins agree; decimal commas keep the advice); 15 of them fail with the fix reverted.
