# `bea query` prints nothing and exits 0 when the query starts with a comment — only `--json` returns the rows

**Major · 40–55m · cli.** A1: a query that begins with a `/* … */` header comment is how an agent or a script documents what it is asking. Today that query runs, produces rows, and prints an empty result with a success exit code.

Found 2026-09-13 by a CLI QA sweep of this checkout at `bea 0.2.0`, macOS 26.5.1, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` removed from the child environment. Synthetic fixture only.

The query executes correctly — `--json` proves the rows exist — but every human-readable and passthrough format renders nothing, with **exit 0**. Nothing anywhere signals that output was lost.

Minimal reproducer:

```bash
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2024-01-01 open Assets:Bank:Checking USD
2024-01-01 open Equity:Opening-Balances
2024-01-01 * "Opening" "Initial funding"
  Assets:Bank:Checking   10000.00 USD
  Equity:Opening-Balances
EOF

Q='SELECT account FROM accounts ORDER BY account LIMIT 2'

bea --file main.bean query "$Q"            # 83 bytes: the table, exit 0
bea --file main.bean query "/* qa */
$Q"                                        # 0 bytes, exit 0          <-- rows lost
bea --json --file main.bean query "/* qa */
$Q"                                        # rows present, exit 0     <-- data is there
```

Measured on the fixture above:

| Query | `--format text` | `--format csv` | `--json` |
| --- | --- | --- | --- |
| `SELECT …` | 83 bytes, exit 0 ✅ | 53 bytes, exit 0 ✅ | 2 rows ✅ |
| `/* qa */\nSELECT …` | **0 bytes, exit 0** ❌ | **0 bytes, exit 0** ❌ | 2 rows ✅ |
| `/* qa */ SELECT …` (same line) | **0 bytes, exit 0** ❌ | — | 2 rows ✅ |
| `SELECT … /* qa */` (trailing) | 83 bytes ✅ | — | 2 rows ✅ |
| `SELECT /* c */ account …` (inline) | 83 bytes ✅ | — | 2 rows ✅ |

The trigger is precise: **the query text begins with a comment**. Trailing and inline comments are unaffected, which is why this survived earlier sweeps.

Expected: the rendered output matches `--json` for the same query — the leading comment is stripped by the parser and the table prints — or, failing that, the command reports that it could not render and exits nonzero. Exit 0 with empty output for a query that returned rows is the one outcome a script cannot detect.

## Second, inconsistent variant: a leading `;` comment

```bash
bea --file main.bean query "; qa
$Q"                                        # 0 bytes, exit 0
bea --json --file main.bean query "; qa
$Q"                                        # exit 2, usage error: "Cannot run this BQL query: syntax error."
```

Same input, two verdicts: human mode calls it success-with-no-output, JSON mode calls it a syntax error. At most one can be right. `;` is *not* accepted here even though upstream `beanquery` accepts it (verified below), so the JSON path's rejection is itself questionable — but the mode disagreement is the defect being reported.

## Upstream comparison — this is not upstream behavior

Checked against real `beanquery` through this same CLI, so the comparison is like-for-like:

- `/* … */` leading, inline and trailing, nested `/* a /* b */ */`, and leading `;` **all execute** (exit 0) — upstream's parser accepts them.
- `-- qa` line comments are rejected both locally and by the hosted engine, so `--` is genuinely not BQL comment syntax and is **not** part of this report.

So the parser is fine; only `bea`'s rendering of the result drops it.

Root: `cli/src/cli/commands/query.py:111-114` —

```python
text = str(data.get("text", ""))
if text:
    typer.echo(text, nl=False)
```

The human path prints the engine's pre-rendered `text` and has **no fallback**: when `text` is empty the command silently prints nothing, even though the same envelope carries populated `columns` and `rows` (line 106 is what `--json` emits, and it is correct). A leading comment evidently yields an empty `text` while leaving the rows intact; the engine-side reason for that is not traced here and should be confirmed before choosing where to fix.

Fix: make the rendered and structured paths agree. Either render from `columns`/`rows` when `text` is empty but rows exist, or fix the engine so a leading comment still produces `text` — and in **either** case make "no renderable output for a result that has rows" impossible to exit 0 on. Decide the `;` question at the same time so human and JSON modes return the same verdict for the same query. Do not strip comments from the query string in the frontend as a workaround: `cli/CLAUDE.md` keeps parsing engine-side, and rewriting a user's query would be a new source of wrong answers.

Blast radius: `query.py:111-114` is the only renderer for `--format text`; `--format csv` and `--format beancount` go through the native passthrough at `:72`/`:86` and lose output the same way, so a fix must cover both paths. `--json` is already correct and must stay byte-identical.

Adjacent states: an empty result must keep printing `(no rows)` (today's correct behavior for `SELECT account WHERE account = 'Nope'`); a genuinely malformed query must keep its caret diagnostic and exit 2; the interactive shell (no query argument) is untouched.

Dedupe: searched every queue including `done/` for `bea query`, `query.py`, BQL and comment terms. `w2/021` is the adjacent `bea query` note from the 2026-09-12 sweep but covers `--output`/`--numberify` being dropped under `--json` and `-f beancount`'s raw Python error — flag handling, not result rendering, and it never exercised a comment. Completed `w3/102` is the *hosted* ledger service accepting `/* */` block comments (its fix is confirmed still working on production during this same sweep) — different package, and it is what prompted looking here. `git log -S 'data.get("text"' -- src/cli/commands/query.py` shows only `a90b1706`, so no later fix exists on main.

Unverified: whether the empty `text` originates in `bea_engine` or in vendored `fava`/`beanquery` rendering, other output formats' behavior on non-`SELECT` statements, Windows/Linux, and the behavior after repair.

---

**Resolved 2026-09-14** — fixed in `cli` by `fix(cli): run BQL queries that open with a comment`. Triage reproduced the note at HEAD `cae190b3` before the fix; the note was not stale.

The root cause sat one layer below the frontend renderer the note suspected: `cmd.Cmd.parseline` finds no command in a line that starts with `/*` or `;`, and beanquery's shell `onecmd` returns silently for an empty command, so the text and CSV path never reached the parser while `--json` (a bare `execute`) did. The engine's shell (`src/bea_engine/query.py`) now hands any such non-blank line to the parser. A leading `/* … */` renders the same table as the query without it, and a leading `;` is a syntax error (exit 2) in text, CSV, and JSON alike — beanquery 0.2.0's parser does not accept `;` comments, so the note's upstream `;` observation was the same silent path. No query text is rewritten in the frontend.

Regression tests: `tests/test_feedback_regressions.py::test_query_opening_with_a_comment_renders_the_rows_json_returns` and `::test_query_rejects_what_the_parser_rejects_in_every_mode`.
