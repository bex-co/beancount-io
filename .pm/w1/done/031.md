# Drawer quick-switch omits a ledger that Browse lists (default pagination)

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2 — the primary ledger switcher must not silently hide an owned ledger.

Environment: 2026-09-15, main `10465c05`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5 (sole booted simulator, light appearance), Metro over localhost:8081, English. Authenticated QA session against `https://beancount.io/` (no `serverUrlOverride` stored, `EXPO_PUBLIC_SERVER_URL` unset). Read-only; no ledger writes.

Repro (public `open_ledger/alphabet` selected throughout):

1. Open the Home drawer. It lists exactly two collection ledgers grouped by owner: `OPEN_LEDGER/minimax` and `puncsky/example` (`open_ledger/alphabet` appears prepended only because it is the selected public ledger outside the collection). The list is complete — Browse/Merchants/Settings rows render below with no truncation.
2. Open Browse ledgers → Your ledgers. It lists three: `puncsky/example`, `puncsky/mcp-agent-eval` ("Synthetic ledger for MCP agent journey evals", Private), `open_ledger/minimax` (Public).
3. Repeat after terminate/relaunch: same two rows in the drawer, same three in Browse. `puncsky/mcp-agent-eval` is reachable only through Browse, never through quick-switch.

Expected: the drawer shows every ledger Browse → Your ledgers shows (plus the selected out-of-collection public ledger). Actual: the drawer omits `mcp-agent-eval` with no indication anything is missing.

Root: the drawer calls the collection query with no pagination arguments — `mobile/src/components/ledger-drawer/ledger-drawer.tsx:380` runs `useListLedgersQuery()` with no variables — while Browse pages explicitly (`mobile/src/screens/ledger-selection/use-discovery.ts`, `PAGE_SIZE = 30`, looping `MyDiscoveryLedgers` with `{page, limit}`). Both resolve the same `listLedgers` field (`mobile/src/common/graphql/queries/listLedgers.graphql` vs `ledgerDiscovery.graphql`), but the server answers the two argument shapes with different sets (2 vs 3 rows). Server-side, `backend-cluster/backend-v2` passes the args straight through (`ledger-resolver.query.ts:36-44` → `ledger-workflow.ts:952+` → `favaApiClient.ledgers.listLedgers({page, limit})`), so the effective default lives downstream and was not pinned from here.

Fix (mobile): pass explicit pagination in the drawer query matching Browse (`{page: 1, limit: 30}`), or a reasoned quick-switch cap. If a cap is intentional, document which ledgers qualify and say so in the UI instead of silently dropping one. Preserve `getDrawerLedgers` ordering/selection/fallback (`drawer-ledgers.ts`), owner grouping, conditional filter, and share actions. Do not touch Browse or the backend default in this note.

Blast radius: one `LedgerDrawer` hosted by `LedgerDrawerProvider` (`mobile/app/(app)/(tabs)/_layout.tsx`), opened from Home/Accounts/Transactions/Reports/Files headers. Browse, discovery tabs, starring, and selection persistence are untouched. Colleagues: `w3/199` (drawer large-text layout) and `w3/done/191` (chart touch stranding the drawer) cover the same component with distinct causes; neither owns this query-argument gap.

Adjacent states: empty/error/refresh drawer states, filter-with-many-ledgers, and ledgers beyond 30 (the drawer has no paging — beyond matching Browse page one is out of scope here).

Dedupe: searched every queue including `done/` for drawer-missing/omit/subset, default page/limit/pagination, `mcp-agent-eval`, and `listLedgers`; scanned all open milestones (none open anywhere) and open inbox notes. `w5` `mcp-agent-eval` references own the backend eval harness, not the drawer list. `w3/done/161`, `w3/done/137`, `w3/done/191` are drawer-adjacent with distinct causes. No duplicate found.

Acceptance: with the same QA account, the drawer lists all of Browse → Your ledgers plus the selected out-of-collection public ledger; switching to and from the previously missing ledger works from the drawer. Add regression coverage asserting the drawer query carries explicit pagination args.

Unverified: the exact server-side default that yields 2 rows; other locales; Android.

Evidence (gitignored, local only): `mobile/tmp/qa-2026-09-15/49-drawer-alphabet.png` (drawer, two collection rows), `43-browse-ledgers.png` (Your ledgers, three rows). No product fix, commit, or shipping.

**Resolved 2026-09-16** — fixed in `mobile` by `fix(mobile): page the drawer ledger query explicitly`. Triage confirmed at HEAD that `ledger-drawer.tsx` ran `useListLedgersQuery()` with no variables while Browse loops `MyDiscoveryLedgers` with `{page, limit: 30}`; both resolve the same `listLedgers` field, and the server answers the two argument shapes with different sets.

`ledger-drawer.tsx` now passes `variables: {page: 1, limit: DRAWER_LEDGERS_PAGE_SIZE}`, with the limit exported from `drawer-ledgers.ts` and kept equal to Browse's page size. `getDrawerLedgers` ordering/selection/fallback, owner grouping, conditional filter, and share actions are unchanged.

Regression tests: `mobile/src/components/ledger-drawer/__tests__/ledger-drawer-pagination.test.ts` asserts the drawer call site carries explicit `page`/`limit` variables and that the drawer page size equals Browse's `PAGE_SIZE`. Verified the new tests fail with the fix reverted and pass with it applied.
