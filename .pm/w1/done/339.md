# `bea add balance --pad-from` on a statement's closing date pads away that day's own transactions: a 1,800.00 USD closing balance after a 1,200.00 USD rent payment writes a -1,200.00 USD pad, exit 0, and the account reads 600.00 USD (gap in w5/611)

**Bug · cli · major · ~45m · A1.** From routine cli-qa, 2026-11-20. A bank statement's closing balance is the balance at the end of its last day. Beancount checks a `balance` assertion at the start of its day. Plain `bea add balance` knows this: when the assertion fails, it says "Balance assertions run at the start of the day … For a statement closing balance, use the following day's date." `--pad-from` is the documented way to write an opening adjustment, and the `beancount-reconcile` skill allows it on a first reconcile. It skips that check. The pad absorbs the gap the day's own transactions explain, so validation passes and the write exits 0. The day's transactions are now counted twice. The answer does say "the pad inserts -1200.00 USD", but nothing tells the user that the amount is exactly that day's activity. `bea check` stays green, so nothing later catches it either.

Environment: main `1efafc9af`, `bea 0.5.0` from the checkout (`uv run bea`), Python 3.12.14, macOS 26 (Darwin 25.5.0) arm64. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, cwd a scratch directory. Reproduced in fresh processes from a pristine copy. The refused run in step 1 left the file byte-identical (same md5).

## Repro

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Rent USD
2026-01-01 open Equity:Opening-Balances USD
2026-01-02 * "Opening"
  Assets:Checking 3000.00 USD
  Equity:Opening-Balances
2026-01-10 * "Landlord" "Rent"
  Expenses:Rent 1200.00 USD
  Assets:Checking
EOF
cp main.bean pristine.bean
bea --file main.bean add balance --date 2026-01-10 -a Assets:Checking --amount '1800.00 USD'                                    # 1
bea --file main.bean add balance --date 2026-01-10 -a Assets:Checking --amount '1800.00 USD' --pad-from Equity:Opening-Balances  # 2
bea --file main.bean check                                                                                                      # 3
bea --file main.bean report register Assets:Checking                                                                            # 4
```

Actual:

1. Exit 1, nothing written: `Balance failed for 'Assets:Checking': expected 1800.00 USD != accumulated 3000.00 USD (1200.00 too much)`, followed by the start-of-day hint above.
2. Exit 0: `Added 1 pad and 1 balance to …/main.bean; the pad inserts -1200.00 USD into Assets:Checking from Equity:Opening-Balances.` It writes `2026-01-09 pad Assets:Checking Equity:Opening-Balances` and `2026-01-10 balance Assets:Checking 1800.00 USD`. `--json` gives `written: 2`, `pad.amount` `-1200.00 USD`, `warnings: []`.
3. Exit 0.
4. The register runs `3,000.00` → padding `-1,200.00` on 2026-01-09 → `1,800.00` → rent `-1,200.00` → **`600.00 USD`**. The statement says 1,800.00 USD, and `Equity:Opening-Balances` holds a 1,200.00 USD adjustment that nothing caused.

The same happens on an empty account. With the 3,000.00 USD opening deposit dated 2026-01-02, `--date 2026-01-02 --amount '3000.00 USD' --pad-from Equity:Opening-Balances` pads 3,000.00 USD on 2026-01-01, exit 0, and the account reads 6,000.00 USD from then on.

Control: on the pristine file, the same command dated the day after the statement (`--date 2026-01-11`) answers `Book balance already matches 1800.00 USD; omitted the pad from --pad-from and wrote the assertion alone.`, exit 0.

## Expected

Without `--force`, `add balance --pad-from` refuses with exit **2** and writes nothing when two things hold:

- postings dated on the assertion's own day move the account (with its children, in that currency);
- the balance at the end of that day matches the asserted amount within the assertion's tolerance, while the balance at its start does not.

The refusal names those postings (`file:line`, payee or narration, amount) and says assertions run at the start of the day. It says a statement's closing balance goes on the next day, with the exact retry `--date 2026-01-11`, which needs no pad. It also says what the pad would insert and that `--force` pads anyway. This mirrors the w5/611 sign refusal, which catches the other "almost always a statement figure" mistake before it is padded. Dates where the day's postings do not explain the gap keep today's behavior. So do assertions with no postings on their day and `--force`.

## Cause

`_balance` in `cli/src/bea_engine/ledger/adding.py` (from line 640) computes `held = write.book_units(before, account, currency, date)` at line 742. That is the start-of-day balance (`write.py:1691`, which counts only `entry.date < date`). The only check run before the pad is written is `negated_credit_hint` (line 743). The start-of-day hint (`_BALANCE_DATE_HINT`, `write.py:1684`) is attached only when a plain assertion fails validation (`write.py:1787`). With a pad, validation succeeds, so that hint can never fire on this path.

## Fix

Owner `cli`, engine side. In the pad-from branch, next to the sign check, compare `book_units` at `date + 1 day` with `held`. If the day's postings move the account and the end-of-day balance is within tolerance of `number` while `held` is not, raise a `protocol.UsageError` as specified above, unless `request["force"]`. Mention the case in `cli/docs/USAGE.md` next to the `--pad-from` sign paragraph ("Liabilities, equity and income balances are negative…").

Regressions, text and `--json`:

- the repro's run 2 and the empty-account variant exit 2 with the file byte-identical;
- `--force` still writes the pad;
- the next-day control and the existing `tests/test_add_balance_pad_from_*.py` suites still pass.

Revert the fix and watch the new tests fail. Run `make check-all` in `cli/`. No REST/GraphQL/MCP change: `--pad-from` is `bea`'s own atomic pad-and-balance (backend-v2 has no pad-from helper), and hosted writes take pad and balance directives as given.
