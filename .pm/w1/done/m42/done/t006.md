**Deviations and what they found.**

1. Two setup runs were discarded. In the first, Codex's login shell rebuilt `PATH` and ran an older `bea` (0.3.0) installed on this host; in the second, the fresh `bea`'s engine was not yet provisioned and could not download inside Codex's sandbox. Both times Codex then used a different `bea` it found on disk, and the second time it also edited the generated `AGENTS.md` to describe that fallback, against `compatibility.md` ("An installed but failing `bea` is repaired, not swapped"). Filed as [w1/382](../../../382.md). The kept run provisioned the engine once in a terminal first, as guide step 3 does, and the rehearsal pinned the login shell's `PATH` to the fresh `bea`.
2. The guide's `codex exec --sandbox read-only` question command failed on macOS: `bea query` found no usable temporary directory, and Codex fell back to the engine's raw `bean-query` (right figure, wrong path). With the scratch-only permission profile the first-query guide gives for Linux, the turn passed through `bea`. Fixed in `docs/skills/existing-ledger.md`; the same command in the first-query and installation guides is [w1/383](../../../383.md).
3. This host's Codex configuration inherits only core environment variables, so the run passed the isolated engine location with `-c shell_environment_policy.set.XDG_DATA_HOME=…`. A default install keeps the engine in its standard location and needs no such setting.

**Guide corrections:** step 1 says `init --existing` first shipped in `bea` 0.4.0; step 4 gives the scratch-only Codex command; "If something goes wrong" covers a first-use engine install that fails inside Codex's sandbox and the missing temporary directory; "Tested with" records this run. `python3 scripts/skills/test_beancount_skills.py` passes (199 tests) against the checkout's `bea`, and `ci-check.py` passes.
