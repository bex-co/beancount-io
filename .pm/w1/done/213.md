# Bulk OR chains of comparisons are refused at about 250 terms, though the doc says they run

**Bug · ledger · minor · ~30m · A1.** From `/qa-find-bugs-mcp`, 2026-11-09, production `beancount-mcp 1.0.0`, read-only on the public example ledger.

- **Repro:** `runBqlQuery` `SELECT count(*) WHERE account = 'Expenses:QA0' OR …` fails at 251 terms with `BAD_USER_INPUT` "an expression chains 501 operators, over the limit of 500. Split it into smaller expressions." The same query with 250 terms runs.
  - **Control:** `account IN ('…' × 1000)` runs.
  - An agent that builds an OR list from a few hundred accounts or payees is refused. The hint ("Split it into smaller expressions") doesn't tell it about `IN`.
- **Contract:** `docs/mcp.md:1310-1312` (w23/m5/t004) says "bulk `OR` chains and long literals run as written on every surface".
- **Cause:** `backend-cluster/ledger/src/features/ledger/service/bql-complexity.ts:195-224` (`countBinary`) adds every binary operator to the same per-level chain counter, the comparisons as well as `AND`/`OR`. A k-term OR of comparisons therefore counts 2k−1 and trips `MAX_OPERATOR_CHAIN = 500` (`:38`). The limit came with 0dbe35519, a week after the doc line was written.
- **Fix:** do one of the following.
  - Count only the loosest operator's chain at each level, and keep `MAX_TOTAL_OPERATORS` as the backstop.
  - Keep the counter and correct the doc ("up to ~250 OR'd comparisons; use `IN (…)` for longer lists").
- Either way, make the refusal name the workaround: "use `x IN (…)` for long OR lists".
- **Check:** add a `bql-complexity` test for a 300-term `account = '…' OR …` chain. The fix lives in the shared ledger service, so it covers every BQL entry point on REST, GraphQL and MCP.

---

**Resolved 2026-11-10.** Bulk OR lists of comparisons now run. `bql-complexity.ts` counts a chain as a run of one operator class (OR, AND, comparison, additive, multiplicative) at one parenthesis level. A looser operator closes every tighter run before it, so a k-term `account = '…' OR …` list counts as an OR chain of k−1, not 2k−1.
- **Why this is safe:** live probes of the pinned engine parse 1,500-term OR lists, 1,500-long `AND` runs and 1,500-long `+` runs in milliseconds. The limit of 500 per run, and the 2,000-operator total backstop, keep wide headroom. `yarn verify:rustledger`'s guard and poisoned-worker checks still pass.
- **Refusal wording:** an over-limit chain is now told "for a long OR list of comparisons, use `x IN (…)`".
- **Tests:** `bql-complexity.test.ts` adds the note's 300-term OR case (accepted, with a chain of 299), the over-limit list with its `IN` hint, and per-class run resets. The tests that pinned the old all-operators count now pin each run. Reverting the fix fails 6.
- **Docs:** `docs/mcp.md` now states the real bound (an `OR` list of up to 501 comparisons, at most 2,000 operators) instead of "run as written". The fix lives in the shared ledger service, so it covers every BQL entry point on REST, GraphQL and MCP. (`ledger`, `backend-v2` docs)
