# A computed zero divisor saved in a ledger (`120/(3-3) USD`, `100/(0)`, `100 / 0`) is reported with no line by `bea format --check`/`-i`/`--dry-run` and with no file by `bea check` and every read, whose hint to search for `/0` finds nothing, while `bea format FILE` names `FILE:2`

**Bug · cli · minor · ~45m · A1/A2.** From routine cli-qa, 2026-11-22. Suppose a ledger file holds an amount whose divisor works out to zero, such as a bill split by a head count of `(3-3)`. Beancount's parser segfaults on it. `bea check` is the command whose whole job is to say what is wrong, and it names neither the file nor the line. Its only hint is "searching the ledger for '/0' is the first thing to try". For `120/(3-3)`, `100/(0)`, `100/(1*0)` and `100 / 0` that search finds nothing. Since `9393033ce` (2026-11-21), `bea format FILE` names `FILE:LINE` for every one of these spellings. The format walking modes still use only the literal scan, so for a computed divisor they name the file but not the line, and they give the same `/0` hint.

Environment: main `fe80c2cfe`, `bea 0.5.0` from the checkout (`uv run bea`), macOS 26.5.1, Python 3.12.14. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, stdin closed, no TTY, fresh processes, synthetic ledger.

## Repro

```sh
mkdir -p 2026
printf 'option "operating_currency" "USD"\ninclude "2026/feb.bean"\n2026-01-01 open Assets:Bank USD\n2026-01-01 open Expenses:Food USD\n' > main.bean
printf '2026-02-01 * "Split"\n  Expenses:Food  120/(3-3) USD\n  Assets:Bank\n' > 2026/feb.bean

bea --file "$PWD/main.bean" check
# exit 1, stdout empty:
# Error: The Beancount engine (bean-check) was killed by SIGSEGV and produced no result.
#   Upstream's parser crashes this way on a zero divisor in an amount expression, such as '100/0 EUR'; searching the ledger for '/0' is the first thing to try.
#   Command: …/bean-check --no-cache …/main.bean
bea --json --file "$PWD/main.bean" check      # exit 1, same message and hint; no file, no line
grep -rn '/0' .                                # no match: the hint leads nowhere

bea format --check "$PWD/main.bean"
# exit 1: cannot parse: …/2026/feb.bean: Beancount's parser crashed reading this file (the engine was killed by SIGSEGV), so it was not parsed. Upstream's parser crashes … searching the ledger for '/0' …
bea format "$PWD/2026/feb.bean"
# exit 1: …/2026/feb.bean:2: Division by zero in an amount expression; Beancount's parser crashes on a zero divisor, so this file was not parsed.
```

`bea list transaction`, `bea query`, `bea balance`, `bea report overview` and `bea doctor parse` give the same SIGSEGV message and hint as `check`, with no file or line. The ledger stays byte-identical throughout. `format -i` and `--dry-run` give the same per-file line as `--check`.

The same check, one spelling per file, gives these results:

| amount | `bea check` | `format --check` / `-i` / `--dry-run` | `bea format FILE` |
| --- | --- | --- | --- |
| `100/0`, `100/0.00`, `(100/0)` | SIGSEGV, no file | `FILE:5: Division by zero …` | `FILE:5` |
| `100 / 0` | SIGSEGV, no file (and `/0` grep misses it) | `FILE:5` | `FILE:5` |
| `100/(2-2)`, `100/(0)`, `100/(1*0)` | SIGSEGV, no file | file named, **no line**, `/0` hint | `FILE:5` |

## Expected

- `bea format --check`, `-i` and `--dry-run` refuse a computed divisor the way stdout and `-o` already do (`cli/docs/USAGE.md:845-846`: "Stdout and `-o` refuse malformed input with exit 1, naming its file (or stdin) and line"), as `FILE:LINE: Division by zero in an amount expression; …`. The crash isolation from w5/759 stays as the fallback for a crash the scan cannot see.
- When a load dies on a crash signal, `bea check` and the reads name the `FILE:LINE` of the first zero divisor in the ledger's closure if one exists, instead of only the `/0` search hint. The exit code (1) and `--json` envelope shape stay as they are. Only when no file holds a zero divisor does the current generic hint remain.

Basis: `USAGE.md:1387-1390` already treats literal (`100/0`, `100/(0)`) and computed (`100/(2-2)`) divisors as one exactly detectable class, and `add` refuses all of them before the engine (w1/274). [w5/010](../../w5/done/010.md) left existing-ledger crashes at "name the signal" because nothing could find a divisor without parsing. [w5/759](../../w5/done/759.md) and [w1/274](274.md) treated computed divisors as out of reach for the same reason. That reason no longer holds: since w1/274, both the frontend and the engine carry an exact `Decimal` evaluator over Beancount's `number_expr` grammar.

## Root cause

- `cli/src/cli/commands/format.py:531-583` (`_syntax_failures`) pre-scans each file with `zero_divisor_line` (`:544`), the literal regex in `cli/src/cli/amounts.py:192`. A computed divisor slips past it. The batch then dies, and the per-file rerun (`:554-566`) can name only the file. The exact evaluator `_divides_by_zero` sits beside it in the same module (`cli/src/cli/amounts.py:160`) and is unused here. The engine's render path, by contrast, calls `evaluated_zero_divisor_line` (`cli/src/bea_engine/amounts.py:145`) after the literal scan (`cli/src/bea_engine/ledger/formatting.py:190-194`, added in 9393033ce).
- A signal death is reported in two places. `cli/src/cli/engine/launch.py:1553-1573` (`_died_on_signal`) handles human `check`'s `run_native`, and `:958-967` (`_parse`, `SignalError`) handles every helper read. Both use `_signal_hint` (`:1576-1582`), a fixed sentence that knows nothing about the ledger. The closure walk that format already uses (`cli/src/cli/output.py:500`, `walk_closure`) could feed the scan on this failure path only, so a healthy load pays nothing.

## Fix

1. Add an evaluated line scan to the frontend twin (`cli/src/cli/amounts.py`: the counterpart of `evaluated_zero_divisor_line`, over the same `_NOT_ARITHMETIC` stripping), keeping the twin drift guards in step. Use it in `_syntax_failures` after the literal scan.
2. On a crash signal (SIGSEGV/SIGBUS class, `_CRASH_SIGNALS`) from a load, scan the closure files (skipping encrypted members, as format does). If a file holds a divisor, put `FILE:LINE: Division by zero in an amount expression; …` first in the details and drop the `/0` search sentence. Otherwise keep today's hint. Writes keep their exit-4 "outcome unknown" wording, plus the location when one is found.
