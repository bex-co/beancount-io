# Three write paths round user-entered amounts through IEEE-754, producing invalid or silently wrong ledger numbers

**Major · 60–75m · dashboard.** A1/A2: an amount a person typed must reach the ledger as the number they typed. All three can turn a valid entry into one Beancount rejects, or into a different number that it accepts.

Found 2026-09-13 by a dashboard QA sweep — a source audit of precision-loss patterns, with the transformations computed directly and the resulting syntax checked against real Beancount via this repo's `bea` CLI. **No ledger was written**: the target ledgers are the user's own and the QA contract forbids using them as fixtures, so the end-to-end write is deliberately unverified (see Limits).

All three take the amount as a **decimal string** and pass it through a JavaScript double before serializing it back.

```tsx
// 1. New Transaction — features/journal/components/new-directive-dialog/transaction-form.tsx:218
number: Number.parseFloat(posting.amount).toString(),

// 2. Receipt — features/receipt/hooks/use-receipt-workflow.ts:104,109
amountNumber: parseFloat(formData.amount).toFixed(2),
amountNumber: (-parseFloat(formData.amount)).toFixed(2),

// 3. CSV import (bulk) — features/importer/hooks/use-import-submit.ts:40,47
number: txn.amount.toString(),
number: (-txn.amount).toString(),
```

## What each produces

**New Transaction** (`parseFloat(x).toString()`):

| Typed | Serialized | Consequence |
| --- | --- | --- |
| `0.00000001` (1 satoshi) | `1e-8` | **exponential notation — invalid Beancount** |
| `0.000000012345678901` | `1.2345678901e-8` | invalid syntax *and* digits lost |
| `12345678901234567890` | `12345678901234567000` | **silently a different number** |
| `123456789.123456789` | `123456789.12345679` | silently truncated |
| `100.10` | `100.1` | harmless normalisation |

**Receipt** (`parseFloat(x).toFixed(2)`):

| Typed | Serialized | Consequence |
| --- | --- | --- |
| `0.00000001` | `0.00` | **a real amount becomes zero** |
| `1.005` | `1.00` | rounds *down* |
| `0.005` | `0.01` | rounds *up* — inconsistent with the line above |
| `12345678901234567890` | `12345678901234567168.00` | silently a different number |
| `123.456` | `123.46` | truncated to 2 dp regardless of the selected currency |

The receipt path hard-codes 2 decimal places while `formData.currency` is user-selectable, so any commodity with more precision than a typical fiat currency is truncated — and a small crypto amount collapses to `0.00`.

**CSV import** (`txn.amount.toString()`), the bulk path — and the one that contradicts its own written contract:

| CSV cell | Grammar accepts | Serialized | Consequence |
| --- | --- | --- | --- |
| `0.00000001` | yes | `1e-8` | **invalid Beancount** |
| `1e-8` | **yes** | `1e-8` | invalid — the grammar explicitly allows scientific input |
| `-0.00000002` | yes | `-2e-8` | invalid |
| `12345678901234567890` | yes | `12345678901234567000` | silently a different number |
| `123456789.123456789` | yes | `123456789.12345679` | silently truncated |

`ImportTransaction.amount` is typed `number` (`importer/types/index.ts:39`), so the original token is discarded at parse time and never reaches the submit builder. `parseAmount` (`importer/utils/csv-validator.ts:78`) returns `Number(trimmed)` and its whole-token grammar `^[+-]?(?:\d+(?:\.\d*)?|\.\d+)(?:[eE][+-]?\d+)?$` **deliberately admits a scientific exponent**, so a CSV containing `1e-8` passes validation and is forwarded unchanged into the ledger.

This directly contradicts `features/importer/CLAUDE.md`, which states: *"Keep original amount tokens and revalidate every field after an edit."* The token is not kept. The same guide shows the codebase already knows how to do this for the neighbouring field — `ImportTransaction.date` is documented as *"Canonical ledger calendar day (`YYYY-MM-DD`); never a zone-bound instant"* and `use-import-submit.ts` notes *"no `Date` instant exists on this path, so no zone can shift the day."* Amounts never got the same treatment.

Severity is highest here: a single import can carry hundreds of rows, so one bad export corrupts or rejects them in bulk rather than one at a time.

## Upstream check — exponential notation is genuinely invalid

Verified against real Beancount through this repo's CLI on a synthetic fixture, not assumed:

```
2024-01-02 * "exponential"
  Assets:Crypto   1e-8 BTC
  Equity:Opening
→ exp.bean:6: Invalid token: 'e-8'        (exit 1)

2024-01-02 * "plain decimal"
  Assets:Crypto   0.00000001 BTC
  Equity:Opening
→ (exit 0)                                  valid
```

So `0.00000001` is a legitimate amount that Beancount accepts, and the form converts it into something Beancount cannot parse.

## Reachability

`transaction-form.tsx:94` validates the amount with `!isNaN(parseFloat(val)) && isFinite(parseFloat(val))`, `receipt-review-form.tsx:74` with `!isNaN(parseFloat(v)) && parseFloat(v) > 0`, and the importer with the `parseAmount` grammar above. Every input in the tables above passes its respective check. Nothing upstream constrains decimal places or magnitude, so no validation blocks these values before serialization.

This is not a hypothetical commodity set: the deployment hosts a public `crypto-example` ledger, and `w3/109` ("Mobile Home and journal round nonzero crypto rewards to zero") already established that high-precision crypto amounts occur in real ledgers here.

Expected: the typed decimal string reaches the ledger unchanged, in plain decimal notation, with precision decided by the commodity rather than by a JavaScript double.

Actual: the string is parsed to a double and re-serialized, so it can gain exponential notation, lose significant digits, or be rounded to a fixed 2 dp.

Fix: stop round-tripping through `number`. Keep the amount as a string end to end — for the importer that means carrying the original CSV token on `ImportTransaction` exactly as `date` already is, rather than a parsed `number`, normalising it textually (trim, strip a leading `+`, collapse a leading `.`) and validating it with a decimal regex plus a bounded-precision check. Where arithmetic is genuinely required — the receipt path negates the amount for its balancing posting — negate the string (or use a decimal library already present) rather than `-parseFloat(x)`. Never emit exponential notation, and never impose 2 dp on a commodity that is not a 2 dp currency. Owning package: `dashboard` only; the GraphQL inputs already accept the number as a string (`units.number`, `amountNumber`), so no API or schema change is needed.

Blast radius: the three call sites above. `transaction-form.tsx` backs the New Entry dialog reachable from the Journal and the Overview "New Entry" action; `use-receipt-workflow.ts` backs receipt import; `use-import-submit.ts` backs the CSV import wizard's submit step and is reached from Smart Import. `transaction-auto-balance.ts:22` also uses `Number.parseFloat` — it computes an *inferred* balancing amount rather than echoing typed input, so it is adjacent and should be reviewed in the same change, but this note does not claim a defect there.

Adjacent states: ordinary 2 dp fiat entry must stay byte-identical on all three paths; the importer's inline preview editing and per-field revalidation must keep working against the token rather than a number, and `parseAmount`'s scientific-notation branch should be reconsidered at the same time (accepting `1e-8` as input is defensible only if it is normalised to plain decimal before submit); the auto-balance inference must keep working; an invalid amount must still be rejected by form validation with today's message; the editor's own file-size formatting (`shared/lib/utils.ts`) is unrelated and out of scope.

Dedupe: searched every queue including `done/` for precision, `parseFloat`, `toFixed`, rounding and truncation terms. Every existing item in this class is **display-side**: completed `w3/116` (journal truncates units/quotes to 2 dp), completed `w3/109` (mobile rounds crypto rewards to zero), open `w3/189` (account journal rounds a posting the transactions list shows in full), and `w4/016`/`024`/`036` (commodity cost basis, `shortNumber`, balance-change window). None touches a **write** path, and none mentions `transaction-form.tsx` or `use-receipt-workflow.ts`. `git log -S "Number.parseFloat(posting.amount)" -- src/features/journal/` shows only `842361a1`, which changed *which* postings get an inferred amount, not how amounts are serialized — so no later fix exists on main and this is not deployment lag.

Limits and what remains unverified: the transformations and the Beancount syntax verdict are proven, and reachability through form validation is source-traced. Not verified: whether the server rejects `1e-8` before it lands (which would make the satoshi case a blocked entry rather than a corrupt one) and whether the large-integer case is accepted end to end — both need a **disposable** ledger to test, which this run did not have. Acceptance work should confirm the end-to-end write on such a ledger, and add regression coverage for each row of both tables.

---

**Resolved 2026-09-14** — fixed in `dashboard` by `fix(dashboard): submit typed amounts as exact decimal strings`. Triage confirmed all three write paths at HEAD before the fix; the note was not stale. The backend passes the posting number string through unchanged (`backend-cluster/backend-v2/src/features/ledger/service/ledger-entry-service.ts`, `ledger-receipt-workflow.ts`), so no API change was needed.

A new shared helper, `dashboard/src/common/lib/beancount/decimal-number.ts`, keeps amounts as text. `parseDecimalNumber` validates a typed number and normalizes it to a plain Beancount decimal: it drops a leading `+`, adds the zero before a bare leading `.`, expands an exponent into digits, and keeps fractional digits as typed. `negateDecimalNumber` and `sumDecimalNumbers` (BigInt-scaled) do the only arithmetic the forms need, exactly.

- **New Transaction** (`transaction-form.tsx`) validates with the helper and submits the typed decimal rather than `Number.parseFloat(...).toString()`.
- **Receipt** (`use-receipt-workflow.ts`, `receipt-review-form.tsx`) submits the typed amount and its exact textual negation instead of `toFixed(2)`, so a small crypto amount no longer becomes `0.00` and the selected currency's precision is kept. The review form rejects non-numeric input such as `12abc`, which `parseFloat` had accepted.
- **CSV import** (`types/index.ts`, `transaction-config-form.tsx`, `use-import-submit.ts`) now carries the original CSV token, as the importer guide requires. `ImportTransaction.amount` is the normalized decimal string, and the balancing posting is its textual negation. A CSV `1e-8` is normalized to `0.00000001` before submit rather than rejected.
- **Auto-balance** (`transaction-auto-balance.ts`), the adjacent path the note asked to review, did have a defect of the same class. It summed doubles and wrote the result into the posting, so `0.1` + `0.2` inferred `-0.30000000000000004`. It now sums decimal strings and infers `-0.3`.

Ordinary two-decimal fiat entries submit byte-identically. Not changed: the receipt review form still pre-fills an AI-parsed amount with `toFixed(2)` — a display default the user can edit before submit. The end-to-end write was not repeated on a disposable ledger; the helper output is plain decimal notation, which the note verified Beancount accepts.

Regression tests: `common/lib/beancount/__tests__/decimal-number.test.ts`, `receipt/hooks/__tests__/use-receipt-workflow.test.ts`, `journal/.../transaction-auto-balance.test.ts` (exact residuals), `journal/.../amount-step-precision.test.tsx` (satoshi, 20-digit, and long-fraction entries submitted through the form), and `importer/hooks/__tests__/use-import-submit.test.ts` (high-precision and large amounts).
