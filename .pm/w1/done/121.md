# Engine installs silently drop hash verification when the cached lockfile can't be refreshed

**Severity: major. Owner: cli. Estimate: ~1h. A1:** supply-chain checks must fail closed. Continuous CLI QA, 2026-10-03 (round 7); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, bea 0.3.1, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`XDG_*`/`BEA_CONFIG_DIR`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with a working control.

Artifact under test: wheel built from `cli/` with `uv build`, installed into a fresh venv (Python 3.12.14, uv 0.12.13) with HOME, XDG dirs, `BEA_CONFIG_DIR` and `UV_CACHE_DIR` inside the run dir; after the first engine install everything ran with `UV_OFFLINE=1`. Package-manager steps were **simulated** with fake `brew`/`uv` executables on PATH.

Make `<engine parent>/engine-requirements.lock` a **read-only** file whose content differs from the shipped lock (as a stale copy from another bea version would), remove the engine, then run `bea --file /abs/main.bean check` with `BEA_UV` pointing at a logging uv wrapper.

Actual: the log shows `uv pip install … beancount==3.2.3 beanquery==0.2.0 typer>=0.12 pydantic>=2.0 …` — no `--require-hashes`, no `--only-binary`, transitive dependencies unpinned; the installed set differs from the lock (`regex 2026.9.29` vs locked `2026.9.10`, `wcwidth 0.9.1` vs `0.8.3`); exit 0, no warning. Reproduced twice (also with a non-default `BEA_ENGINE_DIR`). Control: the same read-only file with identical content takes the hashed path.

Expected: `provision.py`'s docstring and USAGE — the installed artifact provisions "the hash-pinned combination"; the pin fallback is for checkouts only.

Cause: `cli/src/cli/engine/provision.py:307–335` `_find_packaged_file` copies the shipped lock to `engine_root().parent/<name>`, a path shared by all bea versions; any `OSError` on that write is swallowed (`:333`) and it returns None, so `provision` (`:121`) falls back to `_requirements()`. `_install_feature` has the same fallback for optional Beangulp/Beanprice locks (from `cc5ce3f9`).

Fix/acceptance: use the lock's real installed path (it is a real file in the wheel) or `resources.as_file`, copy via temp + rename rather than a shared path, and refuse unhashed installs when the artifact ships a lock. A read-only stale cache still produces a `--require-hashes` install or a clear error.

---

**Resolved 2026-10-03** — engine installs from a released artifact now always use the hash-pinned lock shipped inside the package (copied atomically by content name when zipped) or stop with a clear error, instead of silently installing without hash verification. `tests/test_engine_launch.py` (`TestReleaseLocks`) covers it. Shipped in the commit that moved this note (`cli`).
