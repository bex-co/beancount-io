# REST file previews skip the sha check that the commit makes

**Bug · backend-v2 · minor · ~20m · A1.** From `/qa-find-bugs-mcp`, 2026-11-10, production. Nothing was written.

- **Repro:**
  - `PUT …/files/main.bean {content, sha:"000…0", dryRun:true}` returns 200 `{"ok":true,"dryRun":true,"valid":true}`. `sha:"not-a-sha"` gives the same result.
  - `DELETE …/files/<path> {sha:"000…0", dryRun:true}` returns 200.
  - The same requests without the flag return 409 `CONFLICT`. An approved preview then fails, which breaks the preview rule (`docs/mcp.md:376-388`).
  - **MCP control:** `updateLedgerFiles` / `deleteLedgerFiles` with `dry_run` and a stale sha return `CONFLICT` "preview refused: File conflict: … changed since you read it".
- **Cause:** the dry-run branch of `ledger-repo-service.ts` `commitFileChanges` (around `:330-370`) checks only create-over-existing and returns before any sha comparison. MCP compares the sha itself in `edit-ledger-files-tool.ts` `prepare()`, while REST `files-handler.ts:250,322` relies on the service.
- **Fix:** in the dry-run branch, compare each update/delete sha with the current blob sha, and throw the same `ConflictError` and hint that MCP uses.
- **Check:** add a file-write parity case on REST and MCP for a stale sha with `dryRun`.
- **Related:** this is the same class as w1/195, a dry run that skips a check the commit makes.

**Resolved 2026-11-10.** The service's file-write dry run now checks each update or delete `sha` against the file's current blob, as the commit does.

- **Fix:** `commitFileChanges` reads the versioned paths in the same lookup as the create check. A `sha` that is not current, `not-a-sha` included, is refused `CONFLICT` "`<path>` changed since you read it", before the bean-check gate. A versioned path that is not there is `NOT_FOUND`. A path the batch created or deleted earlier is not re-checked, and a write without a `sha` still reads nothing.
- **Surfaces:** REST `PUT` and `DELETE …/files/<path>` with `dryRun` now answer 409 `CONFLICT`, as their commits do. A REST commit from a stale read is refused at the same step, so the commit's refusal names the file rather than reporting Gitea's 409. MCP already refused it in `prepare()`. MCP and the service now share `staleFileConflict` (`features/ledger/utils/stale-file-conflict.ts`), whose hint names both the MCP `readLedgerFiles` tool and REST `GET`. GraphQL's file mutations take no preview.
- **Tests:**
  - `file-write-gate-parity.test.ts` covers a stale and a malformed `sha` on REST `PUT`/`DELETE`, with and without `dryRun`. It also covers the MCP update and delete tools, and checks that a current `sha` still previews valid. Reverting the service change fails the two REST cases.
  - `ledger-repo-service.test.ts` covers the dry-run refusals.
  - `write-conflict-parity.test.ts` now serves the file at the read `sha`, so it still proves that a lost race after the preview is a 409. (`backend-v2`)
