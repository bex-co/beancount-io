# Post-save back-navigation strands deep-link-rooted entry forms (GO_BACK unhandled)

**Severity:** minor. **Estimate:** 45–60 minutes. Owner: mobile. A2 — a save that succeeds must leave the form, and must never invite a duplicate resubmit.

Environment: 2026-09-16, main `10465c05`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5 (sole booted simulator, light appearance), Metro over localhost:8081, English. Authenticated QA session against `https://beancount.io/`. Writes: one synthetic $0.01 transaction (payee `QALOOP3`, reverted same session).

Repro (ledger `puncsky/example` selected throughout):

1. Terminate the app, then open a form as the root route with no back stack: `beancount:///add-transaction?prefillPayee=QALOOP3&prefillNarration=...&prefillAmount=0.01`. The form renders prefilled (Assets −0.01 / Expenses +0.01, balanced) with Done enabled.
2. Tap Done. The `addEntries` mutation succeeds (the entry appears at the top of Transactions seconds later).
3. The app stays on the form and raises `The action 'GO_BACK' was not handled by a navigator` (red banner). There is no success navigation and no toast naming the new entry; the form still looks submittable.

Expected: after a successful save the form leaves (or shows an explicit saved state). Actual: the user is stranded on a live form after a committed write; tapping Done again would submit a second identical entry.

Root: all three entry forms navigate post-save with a bare `router.back()` and no fallback — `mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:548` (`if (outcome.ok) { savedOutRef.current = true; router.back(); }`), `mobile/src/screens/add-budget-screen/add-budget-screen.tsx:240`, `mobile/src/screens/open-account-screen/open-account-screen.tsx:284`. A deep link opened over a terminated app leaves no entry to pop, so the back action is unhandled. The normal push flow (form opened from a tab, e.g. budget submit popping to detail) is unaffected, which is why this only bites cold links.

Fix (mobile): after a successful save, navigate with a fallback instead of a bare back — e.g. `router.canGoBack() ? router.back() : router.replace/dismissTo(...)` the owning tab (Transactions/Budget/Accounts) — in all three forms. While there, disable the submit control once the save commits so a stranded form cannot double-submit. Keep the dirty-guard behavior (`savedOutRef`) and the push-flow back destination unchanged.

Blast radius: three form screens' post-save navigation only. Save mutations, validation, dirty guards, and the push-flow return path are untouched. Colleague: `w3/203` (cold native detail links, inert header Back) is the same GO_BACK family on a different screen with a different trigger (header back vs programmatic post-save back) and fix; neither subsumes the other.

Adjacent states: save failure (stays + error, unchanged), dirty-form back guard (unchanged), forms opened via receipt scanner / account picker callbacks (push flow, unchanged).

Dedupe: searched every queue including `done/` for go_back/router.back/deep-link root/unhandled action. `w3/203` owns the detail cold-link back button; `w3/done/159` is Back-button a11y naming; `w3/done/201` and `w3/m2/done/t002` are unrelated navigation notes. No duplicate found.

Acceptance: terminate, cold-link each of the three forms with valid input, submit; the app leaves the form to the owning tab (no GO_BACK banner) and the new entry/budget/account is listed exactly once. Regression coverage asserting the post-save navigation falls back when `canGoBack()` is false.

Unverified: other locales; Android; universal-link (https) cold starts vs scheme links.

Evidence (gitignored, local only): `mobile/tmp/qa-2026-09-15/113-prefill.png` (prefilled form, Done enabled), `114-saved.png` (GO_BACK banner after successful save), `115-txns.png` (entry listed despite the banner). Probe entry slice-deleted and journal convergence verified later the same session; no residue.

---

**Resolved 2026-09-16** — fixed in `mobile` by `fix(mobile): fall back post-save navigation on cold-link forms`. Triage confirmed at HEAD that all three live entry forms navigated post-save with a bare `router.back()` at exactly the cited lines, and that the `(app)` layout already establishes the `canGoBack`-with-fallback pattern for the header Back button.

Each form now navigates with `router.canGoBack() ? router.back() : router.replace(...)` to its owning screen — Transactions tab, `/(app)/budget`, Accounts tab — and a committed save sets a `saved` flag folded into `canSave`/`canSubmit`, so the submit control disables and the handler cannot resubmit. Dirty-guard behavior (`savedOutRef`) and the push-flow return path are unchanged; the account form still delivers `runAccountCreatedCallback` after navigating (a documented no-op with nothing registered).

Scope note: `/add-transaction-next` shares the bare-back shape via `useLedgerWrite`'s default `goBack`, but that route is parked off every UI path and redirects to the live flow without an amount, so it was left untouched; the transaction-detail delete path uses the same default and belongs to a separate note if it reproduces.

Regression tests: `mobile/src/__tests__/cold-form-save-navigation.test.ts` asserts per form that the single `router.back()` is guarded by `canGoBack`, that the owning-screen fallback replace is present, and that `setSaved(true)` feeds `!saved` into the submit guard. Verified all 9 tests fail with the fix reverted and pass with it applied.
