## Objective

Make the local preview cover every customer email and use it to verify the refreshed theme under representative desktop, mobile, light, dark, and CSS-degraded conditions before declaring the styling complete.

## Context

- `generate-preview.ts` and `all-templates.html` provide the existing visual review path but currently omit the signup-OTP template and carry their own older blue preview chrome.
- Browser preview alone cannot guarantee identical rendering in every email client, so validation should distinguish guaranteed inline fallbacks from progressive enhancements.
- Generated preview artifacts must remain deterministic and safe to commit.

## Steps

1. Add welcome, signup-OTP, and password-reset cases to the preview generator using public fixture data.
2. Align preview-page chrome with the dashboard theme without obscuring the emails being reviewed.
3. Regenerate the committed preview and inspect desktop/mobile widths, light/dark preferences, and a fallback with embedded styles disabled.
4. Record the supported behavior and any intentional client limitations in the template README.

## Acceptance criteria

- [ ] One deterministic command generates a preview containing all three templates with non-sensitive fixture values.
- [ ] Each template is reviewed at desktop and narrow mobile widths in light and dark preferences.
- [ ] With embedded CSS unavailable, inline light-mode fallbacks remain branded, legible, and actionable.
- [ ] The README accurately states dark-mode enhancement limits instead of promising identical rendering in all clients.

## Out of scope

- Purchasing a hosted email-rendering service or guaranteeing pixel parity across every historical mail client.
