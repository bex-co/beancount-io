## Objective

Translate the dashboard's established visual tokens into a small email-compatible theme contract with explicit light defaults and dark-mode overrides, without making the email renderer depend on dashboard code or unsupported CSS color formats.

## Context

- `dashboard/src/style.css` is the source of truth for the dashboard's brand hue, light/dark foreground and surface relationships, borders, radii, and semantic contrast decisions.
- `backend-cluster/backend-v2/src/shared/email-templates/` must remain independently deployable and should use broadly supported sRGB values and inline fallbacks.
- Email clients vary in their support for embedded styles, CSS custom properties, `prefers-color-scheme`, and automatic color inversion.

## Steps

1. Inventory the dashboard tokens needed by email: canvas, card, foreground, muted foreground, border, primary, primary foreground, accent/callout, and focus/link colors.
2. Define named email-theme values or rendering helpers in backend-v2 using email-safe color values, with documented mapping back to the dashboard tokens.
3. Specify light-mode inline defaults plus progressive dark-mode overrides that degrade cleanly when a client strips embedded CSS.
4. Check foreground/background and CTA contrast for both intended modes.

## Files

- `dashboard/src/style.css` (reference only)
- `backend-cluster/backend-v2/src/shared/email-templates/components/`
- `backend-cluster/backend-v2/src/shared/email-templates/README.md`

## Acceptance criteria

- [ ] The email theme has one named source for every shared visual role used by templates.
- [ ] Each role maps intentionally to the dashboard light/dark theme and uses email-compatible values.
- [ ] Light-mode inline fallbacks remain legible without embedded CSS, and intended foreground/background pairs meet WCAG AA contrast.
- [ ] The theme does not introduce a cross-package runtime import or a new dependency.

## Out of scope

- Changing the dashboard theme tokens or redesigning the dashboard.
