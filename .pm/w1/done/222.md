# REST v1 errors outside the route handlers break the error contract, and 401s carry no challenge

**Bug · backend-v2 (REST adapter) · minor · ~1h · A1.** From `/qa-find-bugs-mcp`, 2026-11-10, production. Reads ran against the public example ledger; body probes went to the disposable QA ledger and were dry runs or refused. Nothing was written.

The OpenAPI info promises "Errors share one shape: `{ ok:false, error:{code,message} }`". A generated client or agent that parses every error as JSON gets a parse failure and no code in the cases below.

- **Plain-text failures:**
  - **Unknown path:** `GET /api-gateway/v1/qa-no-such-route` and an unknown sub-route under a ledger return 404 `text/plain` "Not Found".
  - **Wrong method:** `DELETE`/`POST …/payees`, `PATCH …/journal` and `PUT …/options` return 405 `text/plain` with `Allow: HEAD, GET`.
  - **Unreadable body:** a body of `{"text":`, `null` or `"str"` returns 400 `text/plain` "Bad Request". A 2.2 MiB body returns 413 `text/plain`. `Content-Encoding: br` returns 415 `text/plain`.
- **Misleading text:**
  - A body route sent `Content-Type: text/plain` or form-urlencoded, with a valid JSON body, returns 400 `VALIDATION_FAILED` "body.text: expected string, received undefined". It never mentions the content type.
  - A missing required query still gets zod's default text on REST ("query.account: expected string, received undefined", "query.ledgerRepoId: expected number, received NaN"). e086abb7f (w1/187) fixed the MCP side to "`<name>` is required".
- **No 401 challenge:** an anonymous request, `x-api-key` with a bad key, or `Bearer bcio_garbage` on any v1 route returns 401 `UNAUTHENTICATED` with no `WWW-Authenticate` header. RFC 9110 §15.5.2 requires one. MCP sends `Bearer resource_metadata=…`.
- **Controls:**
  - Inside a matched route, every refusal is the JSON envelope.
  - MCP answers an unreadable body with a JSON-RPC error (w5/048), non-POST with 405 `Allow: POST`, and a wrong content type with 415.
- **Cause:**
  - `start-server.ts:62`: the app-level `bodyParserMiddleware` rethrows parser errors for non-MCP paths (`body-parser-middleware.ts:81`). `restErrorMiddleware` is registered at router level (`composition-root.ts:409`), below that parser, so it never sees them.
  - Unmatched paths fall through to Koa's default 404.
  - `start-server.ts:139` `router.allowedMethods()` writes the plain-text 405.
  - `error-middleware.ts:71-80` sets only the status and body for `UNAUTHENTICATED`.
- **Fix:** for `/api-gateway/v1/*`:
  - Translate `BodyParseFailure` into the v1 envelope (`VALIDATION_FAILED`, or 413/415).
  - Add a catch-all 404 `{ok:false,error:{code:"NOT_FOUND",message:"No such endpoint",hint:<docs URL>}}`.
  - Render the 405 as JSON and keep `Allow`.
  - Refuse a non-JSON `Content-Type` on body routes with 415 "send application/json".
  - Reuse the "`<name>` is required" wording for missing query names.
  - On a 401, set `WWW-Authenticate: Bearer realm="beancount.io"`, adding `error="invalid_token"` when a credential was presented and rejected (the same rule as w1/206 for MCP).
- **Check:** add an error-middleware or route test for each case. GraphQL and MCP are unaffected.

**Addendum 2026-11-10 (GraphQL sweep):** the same cause reaches GraphQL. A POST to `/api-gateway/` with malformed JSON (`{"query":`) returns 400 `text/plain` "Bad Request". Apollo's own malformed-request errors are JSON (`BAD_REQUEST`). The body-parser fix should also cover `/api-gateway/` and return JSON `BAD_REQUEST`.

**Resolved 2026-11-10.** Every v1 refusal made before a route runs now uses the JSON envelope, and a 401 now carries a challenge.

- **Envelope:** `server/rest/v1-envelope.ts`:
  - `v1FallbackMiddleware`, mounted ahead of the router, answers an unknown v1 path with 404 `NOT_FOUND` "No such endpoint", pointing at `openapi.json`. It answers the router's 405/501 in JSON and keeps `Allow`.
  - The app's body parser answers a body it cannot read on a v1 path in the envelope: 400 `VALIDATION_FAILED` for truncated JSON, `null` or a JSON string, 413 for an oversized body, 415 for Brotli. On the GraphQL endpoint it answers `{errors:[{extensions:{code:"BAD_REQUEST"}}]}`.
- **Content type:** a route that declares a body refuses a non-JSON `Content-Type` with 415, naming the type it got and `application/json`. A request with no body, or an empty one, is not checked.
- **Wording:** a missing required query name reads "`<name>` is required", several listed together, as MCP's resources say (w1/187). A name that is present but malformed keeps zod's message.
- **401:** `restErrorMiddleware` sets `WWW-Authenticate: Bearer realm="beancount.io"` and adds `error="invalid_token"` when a bearer token or an `x-api-key` was presented and rejected. The header covers every REST route, not only v1. CORS already exposed it.
- **Not changed:** the OpenAPI document still lists only the statuses error categories produce. The transport-level 405/413/415 are not in it, so there is no spec diff.
- **Tests:**
  - `v1-error-envelope.test.ts` runs a real socket with the server's middleware order and covers every case above. With the fallback off and the parser, route and error-middleware changes reverted, 12 of its 13 original cases fail.
  - `error-middleware.test.ts` pins the challenge for no credential, a rejected bearer and a rejected key.
  - Two tests with a fabricated ctx gained `get`/`set`. (`backend-v2`)
