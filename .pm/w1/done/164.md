# The `--meta` invalid-date check misses slash and unpadded dates and stores them as strings

**Severity: minor. Owner: cli. Estimate: 15–20m. A1:** metadata typing must not depend on which valid date spelling was used. Continuous CLI QA, 2026-10-03 (round 14); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with a working control. Found by a regression hunt over shipped fixes.

```sh
bea --file /abs/main.bean add transaction --date 2026-01-05 --payee P --posting "Expenses:Food 5 USD" --posting Assets:Cash --meta "when:2026/02/30"
```

Actual: exit 0; the file gets `when: "2026/02/30"` (quoted string). `2026-2-30` behaves the same, while valid `2026/2/3` is stored as a real date. Bulk JSON `"when":"2026/02/30"` also writes the string. Control: `--meta when:2026-02-30` exits 2 (invalid calendar date).

Cause: `cli/src/bea_engine/ledger/adding.py:742` checks `re.fullmatch(r"\d{4}-\d{2}-\d{2}", raw)`. Gap in `602b23e8` (`w3/347`).

Fix/acceptance: use the Beancount date grammar `\d{4}[-/]\d{1,2}[-/]\d{1,2}` there (and in the bulk path). `2026/02/30` and `2026-2-30` exit 2 with nothing written; `2026/2/3` still stored as a date.

---

**Resolved 2026-10-04** — `--meta` now refuses impossible dates in every spelling Beancount reads as a date (`2026/02/30`, `2026-2-30`) instead of storing them as text, while valid slash dates are still stored as dates. `tests/test_add_meta_rejects_invalid_date.py` covers it. Shipped in the commit that moved this note (`cli`).
