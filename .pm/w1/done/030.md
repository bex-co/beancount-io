# The Markdown statement export silently drops zero-amount accounts that CSV and print both keep

**Minor · 30–45m · dashboard.** A2/A3: the three exports of one statement must describe the same books. Today the Markdown report is missing accounts the CSV of the same report contains.

Found 2026-09-13 by a dashboard QA sweep, comparing the three renderers of one Balance Sheet export against each other. Read-only; exports downloaded from `https://beancount.io`, ledger `puncsky/example`, authenticated, headless isolated Chromium 1440×1000.

Two of the three renderers explicitly keep an account that has no amounts, emitting one row with a blank value:

```ts
// export/csv.ts:35
const amounts = row.amounts.length > 0 ? row.amounts : [null];

// export/printable-statement.tsx:30
return row.amounts.length > 0 ? row.amounts : [null];
```

`export/markdown.ts` has no such fallback. Its row emitters map straight over `amounts` (`:134`, `:162`, `:182` and the section-row emitter), so an account whose `amounts` array is empty produces **zero** lines and disappears from the document.

Observable on one export of one report, taken at the same moment:

| Account | CSV | Markdown |
| --- | --- | --- |
| `Liabilities:AccountsPayable` | row present, `unit`/`raw_amount`/`display_amount` blank | **absent** |
| `Assets:US:Federal` (subtotal) | row present, blank | **absent** |
| `Assets:US:Federal:PreTax401k` | row present, blank | **absent** |

3 of the CSV's 30 rows have no counterpart in the Markdown. The Markdown's Liabilities section lists only `Liabilities:US`, `Liabilities:US:Chase`, `Liabilities:US:Chase:Slate` and the total — `Liabilities:AccountsPayable` is simply not there.

This ledger has the fava option `show_accounts_with_zero_balance: true` set, so the reader has explicitly asked for these accounts to be visible.

Expected: all three renderers emit the same row set from the same `StatementExportDocument`, differing only in formatting. `features/reports/CLAUDE.md` calls for "renderer-neutral statement modeling separate from CSV, Markdown, and print renderers", which the shared model already provides — the row set should not depend on which button was pressed.

Actual: Markdown silently omits any account with no amounts.

**Which behaviour is right is a product call, and this note does not force it.** Two of three renderers already agree on "keep the account, blank the amount", so the cheapest consistent fix is to give Markdown the same fallback. The alternative — dropping these accounts everywhere — would contradict `show_accounts_with_zero_balance` and is not recommended. Worth deciding at the same time: a zero-balance account arguably reads better as `0` than as a blank in all three, since the balance is known to be zero rather than unknown (the same empty-vs-zero conflation reported for the Accounts page in [025](./025.md), though that one is a different component and a different data path — this note does not depend on it).

Fix: add the `row.amounts.length > 0 ? row.amounts : [null]` fallback to the Markdown row emitters, rendering the unit and amount cells as the CSV does for a null amount. Keep the existing escaping, bold subtotal/total styling, section ordering, summary blocks and notices untouched. Owning package: `dashboard` only — the model already carries these rows, so no API, schema or model change is needed.

Blast radius: `export/markdown.ts` only. The same omission applies to every statement kind the Markdown renderer handles — Balance Sheet, Income Statement and Cash Flow all share these emitters — so a fix covers all three, and regression coverage should assert row-set equality between the CSV and Markdown of one document rather than testing Markdown alone.

Adjacent states: a section whose rows all lack amounts must still render its heading and table header rather than an empty fragment; multi-unit accounts must keep one line per unit as today.

Checked and **not** a complication: `model.ts:448-453` `hasStatementExportData` tests the same `amounts.length > 0` condition, but it is a **whole-document** gate (does this statement contain any amount at all) rather than a per-section filter, so it does not drop sections upstream of the renderers and needs no change. A statement whose every row lacks amounts is reported as having no export data, which is the intended behaviour and is unaffected by this fix.

Dedupe: searched every queue including `done/` for export, Markdown, renderer, and zero-balance terms. Completed `w3/175` ("Keep zero-balance accounts inside their actual parent branches") is **mobile** account-tree parentage — different package and surface. Completed `w3/117` is Download ZIP failure feedback. Open `w3/m35/t003` guards exports while replacement data is pending — a staleness concern, not the row set. `w1/022` is the reporting **date** on these same exports and is independent of this. `git log -S ": [null]"` shows the fallback arriving with the original export feature `d162671f`, which also introduced `markdown.ts` without it — so this asymmetry has existed since the feature shipped and is neither a regression nor deployment lag.

Unverified: the print renderer's rendered output was read from source rather than printed; other statement kinds were not downloaded in both formats; other locales; and the behaviour after repair.

---

**Resolved 2026-09-14** — fixed in `dashboard` by `fix(dashboard): keep accounts without amounts in Markdown statement exports`. Triage confirmed at HEAD that `markdown.ts` `rowLines` mapped straight over `row.amounts` while `csv.ts` and `printable-statement.tsx` fall back to `[null]`; the note was not stale.

`dashboard/src/features/reports/export/markdown.ts` now applies the same fallback in `rowLines`, the one emitter every supporting section uses. An account or subtotal with no amounts keeps a single row, and like the print renderer it shows `—` in the unit and amount cells, with bold subtotal and total styling kept. Balance Sheet, Income Statement, and Cash Flow Markdown now list the same accounts as their CSV and print exports. Escaping, section order, summaries, and notices are unchanged. Summary blocks still map only real amounts. The whole-document `hasStatementExportData` gate is unchanged, as the note concluded.

The note's side question — whether a known-zero balance should read `0` rather than a blank or dash in all three renderers — is a presentation decision left open. This fix only makes the row set consistent.

Regression tests: `dashboard/src/features/reports/export/__tests__/markdown.test.ts` covers an account row and a subtotal with no amounts, asserts each non-total account appears in both the Markdown and the CSV of one document, and checks that a supporting section whose rows all lack amounts keeps its heading and rows.
