# A hand-written `custom` with no values is reported as `<ledger>:0: Plugin "beancount.ops.pad" failed while running: TypeError: 'NoneType' object is not iterable`, and the unapplied pads add a false "Balance failed", so `bea check` points at the wrong lines

Found by `/qa-find-bugs-cli w1` on 2026-11-19 (HEAD `d1d681e2f`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, synthetic ledgers). Severity: minor. A1/A2: one marker line such as `custom "reminder"` stops every pad in the ledger from running. The user, or an agent, gets a traceback summary with no file or line, plus a balance failure on a line that is correct. `bea` already knows the cause: `bea add custom` refuses to write such a line because "A custom with no values breaks Beancount's pad plugin" ([w3/232](../../w3/done/232.md)).

**Repro** (synthetic `main.bean`; Beancount 3.2.3 parses it, and `bean-check` fails the same way with a full traceback at `<load>:0`):

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Bank USD
2024-01-01 open Equity:Opening-Balances USD
2024-01-01 pad Assets:Bank Equity:Opening-Balances
2024-01-02 balance Assets:Bank 500.00 USD
2024-03-01 custom "reminder"
```

```sh
bea -f main.bean check
bea -f main.bean --json check
```

**Actual** (exit 1):

```
Error: …/main.bean: 2 error(s).
  <ledger>:0: Plugin "beancount.ops.pad" failed while running: TypeError: 'NoneType' object is not iterable.
  …/main.bean:5: Balance failed for 'Assets:Bank': expected 500.00 USD != accumulated 0 USD (500.00 too little)
```

- Neither line names line 6, the one to fix. The second error comes from the first: the pad never ran, so the correct assertion on line 5 fails. `--json check` carries the same two `details`.
- The same `<ledger>:0` message appears when the valueless `custom` sits in an included file, and on every command that loads the ledger (`list`, `balance`, `report`, write validation). With `--allow-errors`, every pad is skipped and only that same unlocated line explains why, so the balances are wrong.
- **Control:** delete line 6, or give it a value (`custom "reminder" "renew passport"`): `bea check` exits 0.

**Expected.** Report the cause at its own line, once per valueless `custom` and in the file that holds it, with the remedy `bea add custom` already states. For example: `main.bean:6: custom "reminder" has no values, which Beancount's pad plugin cannot read; give it a value (custom "reminder" "text") or delete the line`. Do not also report a balance failure that only exists because the pad was skipped. Exit 1 still: Beancount rejects this ledger.

**Root cause.** Beancount 3 parses a `custom` with no values as `values=None`. `realization.postings_by_account` (`beancount/core/realization.py:311`), called by the auto-run `beancount.ops.pad` plugin, iterates it and raises. The loader reports that against `<load>:0`. `format_error` (`cli/src/bea_engine/query.py:3193`) passes it to `_plugin_message` (`:3374`). That function looks for the plugin's own `plugin "…"` line through `plugin_directive` (`:3567`), but `beancount.ops.pad` runs by default and has no such line. So it falls back to `<ledger>:0` (`:3400`). Nothing connects the failure to the `custom` entries whose `values` is `None`. The loader leaves the entry list unpadded, so `beancount.ops.balance` then fails the assertion.

**Fix** (cli only). When a load error is the `beancount.ops.pad` failure, and the loaded entries hold `Custom` directives with `values is None`, replace that error with one located error per such directive (`meta` `filename:lineno`) carrying the remedy. The balance failures that depend on the skipped pads can stay, or be noted as caused by it, whichever the implementer can prove right. The same message should reach `check`, `--json check` `details`, and the write-refusal paths that format loader errors.

**Regression.** A test loads the repro and asserts that `bea check` (text and `--json`) names `main.bean:6` and `custom "reminder"`, and has no `<ledger>:0` line. A second test does the same for the valueless `custom` inside an included file, naming that file. Both fail with the fix reverted. The existing w3/232 refusal in `bea add custom` and the w5/172 `list custom --allow-errors` row stay as they are.

**Dedupe.** I searched `.pm/**` for `ops.pad`, `no values`, `NoneType' object is not iterable` and `<ledger>:0`. [w3/232](../../w3/done/232.md) stopped `bea add custom` from *writing* a valueless custom. [w5/172](../../w5/done/172.md) fixed `list custom --allow-errors` crashing on one. [w1/269](./269.md), [w1/273](./273.md), [w1/275](./275.md) and [w1/284](./284.md) located other `<load>:0` errors (includes, plugins with a `plugin` line). None of them covers a valueless custom that is already in the file, which reaches the user through the auto-run pad plugin. Estimate: 30–45 minutes.

---

**Resolved 2026-11-19** — the engine wraps Beancount's pad plugin: it pads with each valueless `custom` holding an empty list of values, and reports it at its own line, in the file that holds it, as `FILE:LINE: custom "reminder" has no values, which Beancount's pad plugin cannot read; give it a value (custom "reminder" "text") or delete the line.` The error is upstream's `PadError`, so the load cache stays readable by bean-check. The repro's `check` and `--json check` now answer that one line (exit 1) with no `<ledger>:0` and no balance failure: the pad applies, so `Assets:Bank` reads 500.00 USD, also under `--allow-errors`, while a balance no pad covers still fails. `check --documents-only` answers these as `valueless_customs`, so plain `bea check` and `check` with bean-check options (`-v`) print the located line instead of bean-check's traceback; `--debug` keeps the traceback. One addition: `bea doctor` now refuses such a ledger before upstream loads past it, as it does a failing plugin; the located message would otherwise have let `doctor missing-open` run and exit 0. Raw plugin-processing mode, where no pad runs, is unchanged. Both load caches change revision. The w3/232 refusal and the w5/172 `list custom --allow-errors` rows are unchanged; that test now asserts the located line instead of the plugin name. Covered by `cli/tests/test_check_valueless_custom.py` (text, JSON, an included file, `-v`, a genuine balance failure, `--allow-errors`, doctor) and `cli/tests/test_list_custom_valueless_allow_errors.py`; shipped in `c9f87dfe8` (`cli`).
