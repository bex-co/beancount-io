# `BEA_TOKEN` with ASCII spaces is accepted, then fails as a network error

**Severity:** major  
**Package:** `cli`  
**Env:** `bea 0.1.0`, production API, isolated `BEA_CONFIG_DIR` (no login required)

## Repro

```bash
BEA_TOKEN='abc ' bea cloud status
# → exit 1: Could not reach the server (LocalProtocolError).

BEA_TOKEN=$'abc\t' bea cloud status
# → exit 3: Invalid BEA_TOKEN … (contains whitespace or control characters)
```

`_validate_token('abc ')` / `(' abc')` / `('ab c')` all **accept**; only `[\x00-\x1f\x7f]` is rejected.

## Expected

Any whitespace (including ordinary space) is rejected up front as an auth/usage error, matching the existing error copy. A bad token must not surface as a transport failure (exit 1 / `validation`).

## Actual

The message claims “whitespace or control characters,” but space (`0x20`) is allowed. A trailing space reaches httpx, blows up header construction as `LocalProtocolError`, and is classified as “Could not reach the server.”

## Root cause

`cli/src/cli/auth/credentials.py` — `_INVALID_TOKEN = re.compile(r"[\x00-\x1f\x7f]")` omits `0x20`; comment above it only mentions control characters, while the raised message says whitespace.

## Fix

Reject `\s` (or at least ` `) in `_validate_token`; add unit cases for leading/trailing/mid space; keep tab/newline coverage. Optionally map remaining `LocalProtocolError` from bad headers to auth rather than transport.

## Estimate

~20–30m
