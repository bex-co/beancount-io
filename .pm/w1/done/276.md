# A leg already in the account's currency but priced in another (`49.50 USD @ 0.909 EUR`) gets the hint "price the USD leg at the rate paid: `… 49.50 USD @ RATE USD`"

Found by `/qa-find-bugs-cli w1` on 2026-11-17 (HEAD `49daca66f`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`). Severity: minor. A1: an agent follows the refusal's remedy literally, and this one tells it to price a USD amount in USD. Following it with any rate writes `Expenses:Dining 49.50 USD @ 1 USD`, a self-price that Beancount accepts, instead of the fix the user needed.

**Repro** (a fresh directory):

```sh
printf 'option "operating_currency" "USD"\n2026-01-01 open Assets:Bank USD\n2026-01-01 open Liabilities:Card USD\n2026-01-01 open Expenses:Dining\n' > main.bean
bea --file "$PWD/main.bean" add transaction "Dinner in Paris" --date 2026-03-05 \
  -p 'Expenses:Dining 49.50 USD @ 0.909 EUR' -p 'Liabilities:Card'
```

**Actual.** The command exits 1 and leaves the file unchanged (same hash before and after). It prints:

```
Proposed append (not written): Invalid currency EUR for account 'Liabilities:Card'
Liabilities:Card was given no amount, so Beancount filled in EUR from the other legs. If it was charged in USD, price the USD leg at the rate paid: 'Expenses:Dining 49.50 USD @ RATE USD'.
```

`--json` carries the same line in `error.details`, and bulk `add transactions` gives it per row (a row with `"amount":"1 USD","price":{"number":"1","currency":"EUR"}`). `@@ 0.9 EUR` gives the same hint.

**Working controls** (same ledger): `-p 'Expenses:Dining 45 EUR'` hints `'Expenses:Dining 45 EUR @ RATE USD'`. `-p 'Expenses:Dining 45 GBP @ 1.1 EUR'` hints `'Expenses:Dining 45 GBP @ RATE USD'`. Both are right: the leg's units are in another currency, and the remedy replaces the price.

**Expected.** When the priced leg's units are already in the account's currency (`target`), the `@ EUR` price is what moved the weight out of USD, so re-pricing cannot help. The hint should say so. One possible wording: `'Expenses:Dining 49.50 USD' is already in USD; its '@ 0.909 EUR' price makes it weigh EUR. Drop the price, or if the amount was in EUR, write 'Expenses:Dining NUMBER EUR @ RATE USD'.` The hint must never suggest `X CUR @ RATE CUR`.

**Root cause.** `_interpolated_leg_hint` in `cli/src/bea_engine/ledger/write.py` (about lines 3807–3890) has a non-cost branch that always emits `f"{leg} @ RATE {target}"`. It runs for each explicit leg whose `get_weight` currency is the filled-in currency, and it never compares `posting.units.currency` with `target`. w5/660 taught it to follow the weight so that a third-currency price is replaced, but the case where the units already match the target was not covered. The cost branch has the same gap in principle (`2 USD {0.9 EUR}`), which is rare.

**Fix.** In that branch, when `posting.units.currency == target` (and `posting.price` is set), emit the "already in TARGET; drop the price" remedy instead of the re-price example. Keep the other branches as they are.

**Acceptance.** The repro's text, its `--json` `error.details`, and the bulk row all give the new remedy, and none contains `USD @ RATE USD`. Both controls are unchanged. A regression test beside the w5/660 cases fails with the fix reverted, and `make check-all` passes. This is local-only, with no REST/GraphQL/MCP change.

**Dedupe.** Searched `.pm/**` for `rate paid`, `@ RATE`, and `filled in`. w5/488, w5/660 and w5/804 (all done) built and corrected this hint for other leg shapes, and none covers a leg that is already in the target currency. `git log -S` on the hint string shows only `6b494c7b4` (w5/660). No open item covers it. Estimate 20–30m.

---

**Resolved 2026-11-17** — `_interpolated_leg_hint` (`cli/src/bea_engine/ledger/write.py`) now checks whether a priced leg's units are already in the account's currency. When they are, the hint says to drop the price (`drop the EUR price from 'Expenses:Dining 49.50 USD', which is already in USD (the price makes it weigh EUR)`) or, if the amount was in EUR, to write `'Expenses:Dining NUMBER EUR @ RATE USD'`; it no longer suggests `USD @ RATE USD`. The repro's text, `--json` `error.details`, the bulk `add transactions` row, and `@@` all give the new remedy; the `45 EUR` and `45 GBP @ 1.1 EUR` controls are unchanged. Regressions in `cli/tests/test_followup_write_remedies.py` (`test_a_leg_already_in_the_account_currency_is_told_to_drop_its_price`), all six of which fail with the fix reverted. Shipped in `922b92e39` (`cli`).
