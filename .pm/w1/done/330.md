# `bea query` text tables print every amount in a currency at a per-unit cost's or price's digits: one `{191.559998 USD}` lot makes `SELECT account, sum(position) GROUP BY account` read `7963.730000 USD` and `-10000.000000 USD`

**Bug · cli · minor · 45–75m · A1.** From routine cli-qa, 2026-11-20. In a `bea query` text table, every amount in a currency prints with as many decimals as the finest per-unit cost or price anywhere in the result. One lot at `{191.559998 USD}` makes the checking balance, the opening equity and a 12.30 USD lunch print six decimals. A `@ 1.083721 USD` rate in a `price` column does the same to every USD posting in a journal query. Under `-m` the cost is not even shown (numberify drops it), yet the USD column still prints six decimals. The values are right. The table does not match what the ledger holds, and an agent pasting it into a summary reports `12.300000 USD`. Per-unit figures with more than two decimals are common: fund NAVs, ESPP and RSU basis, crypto lots, FX rates.

The same thing was fixed for report tables in w1/052 (a long price quote) and w5/093 (a cost's decimals). Reports now take their precision from posting amounts and balance assertions, "not from price quotes or cost numbers". w1/324 lets a per-unit cost column keep its own digits without touching amounts. On this ledger, `bea balance -x units` prints `7,963.73 USD`. w1/325 and w1/326 removed division noise and sum residue from query tables, but a real per-unit number still sets the precision for the whole currency.

Environment: main `2d3adb30c`, `bea 0.4.1` from the checkout (`uv run bea`), Python 3.12.14, macOS 26.5.1. The run used an isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME` with `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, and the cwd in a scratch directory. Every command exits 0 with empty stderr. Reproduced in fresh processes from a pristine copy. The ledger hash was unchanged.

Assets:Broker          10 AAPL { 191.559998 USD}
Assets:Euro                                        100.00 EUR

`-m` prints `7963.730000`, `-10000.000000` and `12.300000` in the USD column, though no cost appears in it. The journal query prints `10000.000000 USD`, `12.300000 USD`, `-12.300000 USD`, `-1915.600000 USD` and `-108.370000 USD` beside the price `1.083721 USD`.

Controls:

- The same `sum(position)` query with `WHERE account != 'Assets:Broker'` prints `7963.73 USD`, `-10000.00 USD` and `12.30 USD`: no per-unit cost is in the rows.
- `--source main.bean` (native rendering) prints `7963.73 USD` too, but it rounds the cost to `{191.56 USD}`, which w1/324's rule says not to do.
- `--json` is exact (`"7963.73"`, cost `"191.559998"`).

## Expected

A text table keeps money and rates apart, as the report tables do:

- An amount prints at the finer of two precisions: the one the ledger writes its currency in (posting amounts, balance assertions or `option "display_precision"`, via `report.written_precision`), and the meaningful digits of the amounts in its own column.
- A per-unit figure keeps its own meaningful digits and does not widen how amounts print. That covers a cost inside a position, an inventory or a cost column, and a rate in a `price` column.

On the repro:

- The first query prints `7963.73 USD`, `10 AAPL {191.559998 USD}`, `100.00 EUR`, `-10000.00 USD` and `12.30 USD`.
- `-m` prints `7963.73`, `-10000.00` and `12.30`.
- The journal prints `10000.00 USD`, `12.30 USD`, `-12.30 USD`, `-1915.60 USD` and `-108.37 USD`, with the price still `1.083721 USD`.

The existing controls in `cli/tests/test_query_result_precision.py` must still hold:

- a `convert()` at an eight-decimal quote keeps its eight decimals in its own column;
- a written `0.0042 USD` posting amount still sets USD to four decimals, since it is a posting amount;
- a whole-dollar ledger's `12.5 USD` keeps `.5`;
- w1/325's quotient and w1/326's residue rules still apply.

`--json`, `--format csv` and their `-m` cells stay unchanged and exact.

## Root cause

`cli/src/bea_engine/query.py:3741` `result_context` builds one display context per currency for the whole result. `visit` (`:3792`) sends every `Cost` (a position's or inventory's per-unit cost) and every lone `Amount` (a `price` column's rate included) through `learn`, which raises `digits_by_currency[currency]` to that value's meaningful digits. The context then gives every value in the currency that many places (`:3822`–`:3827`, "Every value in a currency receives the maximum precision present in these results"). Upstream's `PositionRenderer` and `CostRenderer` (`beanquery/query_render.py`) already format units and costs with separate column contexts, but both quantize through `ctx.dcontext.quantize`, the one `ResultContext.quantize`. So a cost's digits reach the units, and one column's digits reach every other column. Callers: the shell's `on_Select` text path (`:1666`, used by one-shot queries, stdin and the interactive shell), which also quantizes text `-m` cells (`:1668`). The JSON `-m` path in `rows_answer` (`:339`) calls it without `written`, stays lossless, and is not part of this.

## Fix

Owner `cli` (engine side, `bea_engine/query.py`). In the text path, size amounts per column from that column's own amounts, at least the written precision, and size per-unit costs separately, so a cost's digits never widen the units. One way to do it is a cost-aware quantize in bea's text renderers (`_text_renderers`, `:2315`), which already replace `AmountRenderer` and `DecimalRenderer`. A `price` column holds `Amount`s, so per-column sizing is what keeps its rate's digits out of the `position` column.

Add tests to `cli/tests/test_query_result_precision.py`: the three repro queries with the expected cells above, and the existing controls. Revert the fix and watch them fail. Update the query precision paragraph in `cli/docs/USAGE.md` ("A text table shows each currency …") and the module docstring to say per-unit costs and rates keep their digits without setting the amounts'. Run `make check-all` in `cli/`. No REST/GraphQL/MCP change: the hosted query surfaces return structured rows, and `bea ask`'s BQL tool reads `--format json`.

## Dedupe

Searched `.pm/**` for `result_context`, `ResultContext`, `written_precision`, `191.559998`, and `bea query` with `per-unit cost`/`sub-cent`/`cost number`. Ran `git log -S digits_by_currency` (`790791acc`, `a90b17065`, `d89215fe8`).

- w1/325 (noise) and w1/326 (residue) cover the same table but only digits that mean nothing. Their resolutions keep a lone rate's digits ("a `0.0042 USD` price four") without saying what that does to the rest of the table.
- w1/052 and w5/093 are the report-table analogues, fixed there.
- w1/324 fixed per-unit cost columns in holdings and register.

No open or done item covers a real per-unit cost or rate widening every amount in a query table. This is not a regression: the table-wide per-currency rule dates from `790791acc`.
