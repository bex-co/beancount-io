# `add balance` reports a more precise assertion as a duplicate and records nothing

**Severity: minor. Owner: cli. Estimate: ~20m. A1:** reconciling agents must know whether the strict statement balance was recorded. Continuous CLI QA, 2026-10-03 (round 9); report and filing only, no fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced twice with a working control.

Header `B`: `option "operating_currency" "USD"`, `2020-01-01 open Assets:Cash USD`, `2020-01-01 open Expenses:Food USD`.

Add `open Equity:Open USD`, a transaction `Assets:Cash 10.34 USD`, and `2020-02-01 balance Assets:Cash 10.3 USD` (passes, tolerance 0.05). Then:

```sh
bea --json --file /abs/bal.bean add balance --date 2020-02-01 --account Assets:Cash --amount '10.30 USD'
```

Actual: exit 0, `"written": 0, "duplicate": true`, file unchanged. On its own, `10.30 USD` (tolerance 0.005) fails (`expected 10.30 USD != accumulated 10.34 USD`) — it is a different, stricter assertion.

Cause: `cli/src/bea_engine/ledger/adding.py:284–302` `_balance_match` compares with Decimal `==` (`10.3 == 10.30`); `_balance_conflict` likewise.

Fix/acceptance: include the number's exponent in the comparison when no explicit tolerance is given. The repro is written (and fails validation) or refused as a conflict — never reported as an identical duplicate.

Dedupe: `w1/done/m27/t006`, `w3/done/297` introduced matching without precision.

---

**Resolved 2026-10-03** — `add balance` now treats a more precise assertion than an existing one (`10.30` vs `10.3 USD`, no explicit tolerance) as a conflict needing `--force` instead of an identical duplicate. A test in `tests/test_add_idempotency.py` covers it. Shipped in the commit that moved this note (`cli`).
