# REST write routes drop a preview flag sent in the part they don't read, so the "preview" commits

**Bug · backend-v2 (REST adapter) · major · ~45m · A1.** From `/qa-find-bugs-mcp`, 2026-11-10, production. Each probe below was built so the commit would be refused: unbalanced text or a stale sha. Nothing was written.

A caller who sends `?dry_run=true` to a body-flag route, or a body `dryRun` to a bank route, gets the commit path instead of a preview. On a DELETE route that is destructive.

- **Repro:**
  - `POST …/directives/text?dryRun=true` with unbalanced text is refused 400 `UNBALANCED`. That is the commit refusal; with a body `{dryRun:true}` the same call previews 200.
  - `POST …/entries?dryRun=true` does the same.
  - `PUT …/files/main.bean?dry_run=true` with a stale `sha` returns 409 `CONFLICT`, which is the commit path.
  - `DELETE …/files/<path>?dry_run=true` with a stale `sha` returns 409, which is the commit path.
  - **Controls:**
    - Routes with a strict query refuse the stray flag, e.g. `PUT …/entry-source?dry_run=true` returns 400 'Unrecognized key: "dry_run"'.
    - MCP and GraphQL take the flags as strict arguments and are unaffected.
- **Why it matters:**
  - `docs/mcp.md:359-368` says the flag works "everywhere the flag exists", so a call pasted from another surface need not be respelled.
  - The bank routes take it in the query (`DELETE …/banks/{id}?dry_run=true`), so a client naturally sends it there on the file and ledger DELETEs too. w23/207's own repro did this.
- **Cause:**
  - `src/server/rest/v1-route.ts:186-191` validates only the parts a route declares, and `validation-middleware.ts:53` passes an undeclared query through unchecked.
  - Write routes with no query schema:
    - `entries-handler.ts:345,407`
    - `files-handler.ts:214,270`
    - `lifecycle-handler.ts:279,297` (PUT/DELETE ledger)
    - `collaborators-handler.ts:127,148,168`
  - The mirror case: `banks-handler.ts` reads only `query.dry_run`. Its submit and discard bodies (`:223-246`) are not `.strict()`, so a body `dryRun` is stripped and the import or discard runs.
- **Fix:**
  - Give every write route a strict query that accepts `dryRun`/`dry_run` as twins of the body flag through `resolveFlagAlias`, refusing a conflict. Refusing the query flag outright is also acceptable.
  - Make the bank bodies `.strict()`, or accept the body flag.
  - Simplest guard: `v1Route` defaults an undeclared query to `z.object({}).strict()`.
- **Check:**
  - A test sends `?dry_run=true` and `?dryRun=true` to every mutating v1 route. Each is either honoured as a preview or refused 400, never committed.
  - Ledger, collaborator and bank routes are confirmed from source only.

**Addendum 2026-11-10 (REST sweep, GET side, same cause):** about 20 GET routes ignore unknown query keys silently. Every other route refuses them with `VALIDATION_FAILED` 'Unrecognized key'.
- **Routes with no query schema:** ledger metadata, `files/{path}`, `payees`, `narrations`, `currencies`, `tags`, `links`, `years`, `commodities`, `managed-prices`, `errors`, `attributes`, `options`, `banks`, `bank-accounts`, `tier-quotas`, `health`, `api-keys`.
- **Routes with a non-strict declared schema:** `accounts` (`reports-handler.ts:14`) and `feature-flags` (`configuration-routes.ts:12`).
- **Divergence from MCP:** REST `…/accounts?statu=closed` returns all accounts. MCP `beancount://…/accounts?statu=closed` returns `-32602` "Unknown or repeated resource parameter: statu".
- **Fix:** the `v1Route` default-strict guard covers the first group. The second group also needs its declared schemas made strict.

**Resolved 2026-11-10.** A v1 REST route now accepts only the query and body keys it declares.

- **Default:** `v1Route` validates an undeclared query or body as an empty strict object. Absent or `{}` still passes. Every route now parses its body, so a body sent to a route that declares none is checked too. The repros now get 400 `VALIDATION_FAILED` naming the key, before any service runs: `?dryRun=true` on `entries`, `?dry_run=true` on `directives/text`, on file PUT/DELETE and on ledger PUT/DELETE and collaborators.
- **Mirror case:** the bank writes' preview query is strict, and so are the submit and discard bodies. A body `dryRun` on submit or discard is refused, and so is one sent to sync, reconcile or unlink, which take no body. `DELETE /account` with a body `dryRun` is refused the same way; it used to delete the account.
- **Found in the sweep:** `POST /api-keys` dropped unknown keys, so a mistyped `ledger_scope` minted a key with no ledger confinement. Its body is now strict. Two POSTs that change nothing keep lenient bodies: the BQL `query` and token introspection, which follows RFC 7662.
- **GET addendum:** the ~20 GETs with no query schema refuse unknown keys through the same default. `accounts` and `feature-flags` are strict in their keys, as their MCP resources are: `?statu=closed` is refused. w23/m12 recorded these two as lenient in their values, and that leniency stays: an unknown `status` lists every account, and any `userId` is ignored.
- **Contract:** the OpenAPI snapshot gains `additionalProperties: false` on the three bodies. The CLI's pinned spec is re-synced and its client regenerated. `docs/mcp.md` and `docs/api-parity.md` say where the preview flag goes on REST.
- **Tests:** `undeclared-request-parts.test.ts` checks every declared v1 route. Each must refuse an unknown query key. On writes, it checks that `dry_run`/`dryRun` in the query and the body is either read or refused. Over HTTP it replays the repros and checks that no service is called. Simulating the old pass-through fails 103 of these cases. Four older tests pinned the drop and now pin the refusal: `rest-query-strictness`, `events-filter-parity`, `archive-routes` (a query token is now refused 400, still before any credential is read), and the synthetic routes in `page-signals`, which now declare their query. (`backend-v2`, `cli` generated client)
