# Auth next guard still accepts percent-encoded control characters — the w3/170 fix covers only the raw form

**Major · 40–55m · dashboard.** A2/A3: an authentication continuation link must keep the visitor on the application origin. This is an incomplete-fix follow-up to completed [w3/170](../w3/done/170.md), not a new class of bug.

Found 2026-09-13 by a dashboard QA sweep against production `https://beancount.io`, existing authenticated QA session, fresh isolated headless Chromium contexts, 1440×1000. Read-only: no credential submission, no ledger write, no mutation. External destinations use the reserved `evil.example` name and were never expected to resolve.

`w3/170` shipped in `86ca4531`, adding `hasControlCharacter` to `getSafeRedirectPath`. That check runs against the **decoded** value, so it catches a literal control character but not its percent-encoded spelling. When `next` arrives double-encoded, the guard sees the ordinary characters `%`, `0`, `9` and accepts the path.

Repro — visit each URL in a signed-in session and watch the redirect chain:

| `next` value | Guard verdict | Resulting chain |
| --- | --- | --- |
| `/\t/evil.example` (raw tab) | **rejected** ✅ | `307 → /auth/welcome` → `307 → /ledger/<owner>/<ledger>` (safe default) |
| `/%09/evil.example` | **accepted** ❌ | `307 → /%09/evil.example`, then `308 →` a different origin over plaintext `http://` |
| `/%0d/evil.example` | **accepted** ❌ | same as above |
| `/%0a/evil.example` | **accepted** ❌ | same as above |
| `/%5cevil.example` (encoded backslash) | **accepted** ❌ | same as above |
| `/%00/evil.example` | accepted | stays on the application origin |
| `/%2f%2fevil.example` | accepted | normalized to `/evil.example`, stays on the application origin |

Concretely, `GET /auth/login?next=%2F%2509%2Fevil.example` returns **HTTP 307** with `Location: /%09/evil.example` — the application itself emitting an attacker-influenced continuation path. A separate edge layer then answers that path with **HTTP 308 to a different host over plaintext HTTP**.

**Scope of the claim — deliberately limited.** A fully attacker-controlled open redirect is **not** demonstrated: the second hop currently lands on an internal origin's 404 page rather than `evil.example`, because an edge layer intercepts the normalized path. What *is* proven is (a) `getSafeRedirectPath` fails its own documented contract, and (b) a user-supplied parameter drives a cross-origin HTTPS→HTTP downgrade. The dashboard does not own or control that interception, so it must not be treated as the mitigation. Fix the guard on its own merits.

The second hop's behavior belongs to deployment/CDN configuration outside this repository and is **not** proposed as work here, per `DO_NOT_DO.md`. Its exact hostname is deliberately omitted from this public note; it is recorded only in the local evidence below.

Root: `dashboard/src/common/lib/auth/auth.ts` — `hasControlCharacter` (the scan added by `86ca4531`) and the `startsWith("//")` / `startsWith("/\\")` prefix tests all inspect the value as received. The doc comment above `getSafeRedirectPath` claims it rejects "paths obfuscated with control characters (`/\t/evil.example`)"; that holds for the raw form only. `new URL("/%09/evil.example", RESOLUTION_BASE)` keeps the escape sequence in `pathname`, so the origin equality test passes and the guard returns `/%09/evil.example` unchanged.

Fix: before the control-character scan, decode the candidate's percent escapes (tolerating malformed sequences without throwing) and re-run the control-character and protocol-relative checks against that decoded form; reject when either spelling would escape. Keep the existing browser-normalization approach and the relative-path requirement, preserve legitimate query/hash destinations, and do not "repair" a hostile value by stripping characters and returning a newly dangerous path — reject and fall back to the safe default. Owning package: `dashboard` only; no API, schema, or cross-package change.

Blast radius: the same consumers `w3/170` enumerated — `features/auth/pages/login-page/loader.ts`, `register/loader.ts`, the password and OTP completion paths via `common/lib/navigation/hard-navigate.ts`, `requireAuth`, `use-login-next-path`, and the ledger route's guest guard. All share this one helper, so all inherit the gap.

Regression coverage must extend `w3/170`'s cases to the encoded spellings — `%09`, `%0d`, `%0a`, `%5c`, mixed case (`%0A`), and double-encoded (`%2509`) — alongside the existing raw-character cases, and must keep valid relative routes with query and hash working.

Dedupe: searched every queue including `done/` for redirect, safe-next, `getSafeRedirectPath` and `next=` terms. Completed [w3/170](../w3/done/170.md) is the raw-control-character form of this same guard and its fix is confirmed still working (the raw-tab row above falls back safely) — this note is the encoded variant its DoD never listed, so it is an incomplete fix rather than a regression or a stale reopen. Completed `w3/104` is a missing continuation destination, not validation. `git log -S hasControlCharacter -- src/common/lib/auth/auth.ts` shows only `86ca4531`, so no later hardening exists on main and this is not deployment lag.

Unverified: signed-out completion flows, password/OTP submission paths (source-traced through the shared guard, not exercised), other browsers, and the behavior after repair.

Evidence (gitignored, local only): `dashboard/tmp/qa-20260913/auth-next-encoded-control.json` — the seven probes above with their full redirect chains, including the second hop's actual host, which is kept out of this public note.

---

**Resolved 2026-09-14** — fixed in `dashboard` by `fix(dashboard): reject percent-encoded escapes in auth continuation paths`. Triage confirmed the root cause at HEAD before the fix: `getSafeRedirectPath` inspected only the value as received, so it returned `/%09/evil.example` unchanged. The note was not stale.

`dashboard/src/common/lib/auth/auth.ts` now runs the existing checks (relative path, control characters, `//` and `/\` prefixes, browser resolution against the fixed placeholder origin) on the value as received and on every further percent-decoding of its path, up to four layers. Decoding is byte-wise, so a malformed escape neither throws nor ends the checks early — `/%09/evil.example?q=100%` is still rejected. A path that is still decoding after four layers is rejected, never repaired. Only the path is decoded for these checks, so legitimate destinations keep their encoded query strings and hashes (for example, a BQL deep link with `%0A` in `q`). Every consumer the note lists shares this helper, so all of them inherit the fix.

Regression tests in `dashboard/src/common/lib/auth/__tests__/auth.test.ts` cover `%09`, `%0d`, `%0a`, `%0A`, `%00`, `%5c`, `%5C`, `%2f%2f`, double-encoded `%2509` and `%250A`, dot-segment `..%2f%2f`, a malformed-escape suffix, the depth cap, and legitimate encoded destinations. The 13 new rejection cases fail against the previous guard. The edge-layer HTTPS→HTTP hop remains outside this repository, as the note scoped.
