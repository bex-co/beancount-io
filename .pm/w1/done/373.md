# `bea update --id` does not resolve a merged transfer's second-leg import ID

Follow-up from w1/372 (541c7130d, `cli`). That fix let `bea update transaction --id` (and the batch `update transactions`) find a transaction by the bank ID `bea import` stamped on it, as a third lookup tier over `bank_id` / `fitid` / `transaction_id` / `imported_id` (one shared `BANK_ID_KEYS`).

When `bea import` merges the two legs of a transfer into one transaction, the second leg's ID is kept as `import-id-2` (and its bank-ID counterpart). The w1/372 worker noted that this second-leg ID still does not resolve through `--id`, so a user holding the ID from the second account's statement gets "No transaction with import-id or ref …". Not reproduced end to end yet.

Triage first: import two synthetic CSV statements whose rows merge into one transfer, then run `bea update transaction --id <second-leg id>`. Close as not reproducing if it already resolves. If it reproduces, include the second-leg keys in the same lookup (one place, not a parallel list), keep the not-found wording from w1/372, and add a regression test that fails without the fix.

**Resolved 2026-11-23** — `bea update transaction --id` and `bea update transactions` rows now find a merged transfer by its second row's `import-id-2`, shipped in the commit carrying this note (`cli`). Triage: the two-CSV repro does not create that key. `bea import` holds the second statement's row as a possible duplicate of the transfer and `--duplicates skip` writes nothing, so the second statement's own ID is never stored and no second bank-ID key exists. `import-id-2` comes from beancount-migrate's merged pairs, and there the gap reproduced: importing the savings statement reported `import-id bank:2002 is already in the ledger`, while `update transaction --id bank:2002` exited 2 with `No transaction with import-id, ref, or bank ID 'bank:2002'` and a batch row was rejected. `locate_transaction` (`cli/src/bea_engine/ledger/updating.py`) now reads its first tier from one shared `IMPORT_ID_KEYS = ("import-id", "import-id-2")` (`cli/src/bea_engine/ledger/text.py`), which the import's digest lookups use too, and walks the import-id, `ref` and bank-ID tiers in one loop. A value two entries hold within a tier, under one key or two, is refused as ambiguous naming each `file:line`; the not-found wording from w1/372 is unchanged. `cli/docs/USAGE.md`, the engine contract in `cli/src/bea_engine/README.md` and the `update transaction` help record it. Regression test: `cli/tests/test_update_merged_transfer_id.py` (subprocess: a migrated transfer the savings import reports by `bank:2002`, then the single and batch updates by that ID, applied, with a re-import that still skips the row; engine-side: a generated second id, precedence over `ref` and bank ID, one entry holding the value under both keys, and cross-key ambiguity); five of its six fail with `import-id-2` removed from the tier.
