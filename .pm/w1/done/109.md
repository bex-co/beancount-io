# Bulk metadata errors abort the whole batch, ignore `--partial`, and name no row

**Severity: minor. Owner: cli. Estimate: 45–60m. A1:** agents rely on `--partial` row reports to fix only the bad rows. Continuous CLI QA, 2026-10-03 (round 6); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1 (Beancount 3.2.3), Python 3.13, macOS 26.5.1 arm64. Fresh process per command, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed unless piping JSON. Reproduced twice with a working control; compared against native `bean-check`/`bean-query`.

Three rows of the shape `{"date":"2026-02-01","narration":"rN","postings":[{"account":"Expenses:Food","amount":"10 USD"},{"account":"Assets:Cash"}]}` (N = 1..3); row 2 adds `"meta":{"bad":{"x":1}}`. Run `bea --json --file /abs/main.bean add transactions --from rows.json --partial`.

Actual: exit 1 `{"category":"validation","message":"Unsupported metadata value for 'bad'."}` — no row number, no `result`, nothing written. `{"kind":"number","value":"abc"}` in posting meta gives `Invalid 'number' metadata for 'q': [<class 'decimal.ConversionSyntax'>]`; an array value `[1,2]` gives `Unexpected value: '[1, 2]'` (wording `w3/230` said must never surface), even with explicit amounts on every posting. Control: with explicit amounts and an object value, `--partial` writes rows 1 and 3 and reports `Row 2: …` with `rejected_rows:[1]`.

Expected: per-row rejection with a field path; `--partial` writes the valid rows (USAGE bulk section).

Cause: `_directive_infers_zero` calls `writer.format_transaction` (`cli/src/bea_engine/ledger/adding.py:584`) at `:785–790` outside per-row error handling, only for rows with one amount-less posting, so `metadata_for_write`'s `LedgerError` (`write.py:905/907`) escapes; arrays raise a plain `ValueError` from Beancount's printer, which the partial loop (`:844`, catches only `protocol.LedgerError`) misses. `meta: dict[str, Any]` (`models.py:95`, `:205`) is never schema-validated.

Fix/acceptance: validate meta values in the model (str, bool, int, None, or a tagged `{kind,…}` with exact keys), or at least run the zero-net guard inside per-row handling. Repro exits 1 with `Row 2, meta.bad: …`; with `--partial` rows 1 and 3 are written and `rejected_rows:[1]`; an array value yields a schema error.

Dedupe: `w3/230` fixed numeric values only; [045](./045.md) is float precision.

## Also affected: reserved metadata keys (round 14, 2026-10-03)

Bulk rows don't run the reserved-key check that `--meta` does (`_parse_metadata`, `cli/src/bea_engine/ledger/adding.py:711`, from `98ad2f63` / `w3/284`): `bea --file /abs/main.bean add transactions --from b.json` with `[{"date":"2026-02-01","narration":"b","meta":{"filename":"x","when":"2026-02-01"},"postings":[{"account":"Expenses:Food","amount":"1 USD"},{"account":"Assets:Cash"}]}]` exits 0 "Added 1 transaction", writing `when:` and silently dropping `filename`. Include in this fix: reject `filename`/`lineno` keys in bulk rows with the `--meta` message, counted as per-row rejections (reported under `--partial`).

---

**Resolved 2026-10-04** — bad bulk metadata values (arrays, unknown objects, reserved `filename`/`lineno`, malformed numbers) now reject only their own row with a `meta.<key>` path, and `--partial` writes the rest; w1/045 had already covered floats. `tests/test_bulk_meta_row_rejections.py` covers each case. Shipped in the commit that moved this note (`cli`).
