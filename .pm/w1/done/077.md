# A truncated managed-price download is cached as a new revision and then pinned forever by 304s

**Severity: major. Owner: cli. Estimate: ~45m. A1:** silently wrong valuations undermine every report an agent produces. Continuous CLI QA, 2026-10-03 (round 3); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1 (Beancount 3.2.3, beanquery 0.2.0), Python 3.13, macOS 26.5.1 arm64. Fresh process per command, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with a working control.

Managed-price cases are **local simulations**: a threaded `http.server` stub on `127.0.0.1:8765`, enabled with `MANAGED_PRICE_ORIGINS=http://127.0.0.1:8765` and the ledger line `include "http://127.0.0.1:8765/prices/BTC-USD"`. Base fixture: open `Assets:Bank USD`, `Assets:Crypto BTC`, `Equity:Opening`; fund 10000 USD; buy `1 BTC {5000 USD}`; then the include.

Full feed: three BTC prices (60000, 61000, 62000 USD on 2026-09-01/02/03), ETag `"t3"`.

1. Stub in `short` mode: declares `Content-Length` 100 bytes larger than sent, cuts off before the `2026-09-03` line, closes.
2. `bea --file /abs/main.bean price refresh` → `BTC-USD: none → t3`, exit 0.
3. Stub back to the full body with the same ETag; `price refresh` → `unchanged at t3` (stub log: `If-None-Match: "t3"` → 304).
4. `bea --file /abs/main.bean balance Assets:Crypto -x USD` → **61,000 USD**. Control: a fresh cache with the full body gives 62,000.

The same pinning traps an externally corrupted blob: truncate `<rev>.beancount` mid-number and `price refresh` still reports `unchanged`, exit 0, while the ledger carries a syntax error.

Expected: a short body is a fetch failure (ADR018 §6: a failure "never replaces… the last good blob"), and a cached revision is never pinned when its bytes aren't what the ETag describes.

Cause: `cli/src/bea_engine/managed_prices.py:196–207` (`_read_capped`) and `:307–320` — `HTTPResponse.read(amt)` returns `b""` at early EOF, nothing compares received bytes with `Content-Length`; revision id from the ETag at `:509–515`; on 304 the blob is trusted without an integrity check (`managed_price_cache.py:117–148`, `:226–231`).

Fix/acceptance: fewer bytes than `Content-Length` → `FetchFailed(reason="network")`; store the text's sha256 in `<rev>.json` and treat a mismatch as a missing blob (no ETag sent, full refetch). The scenario keeps the last good revision serving with the error recorded; a corrupted blob heals on the next refresh.

Dedupe: no `.pm` hit for IncompleteRead / Content-Length / truncated managed feed.

---

**Resolved 2026-10-03** — a managed-price download shorter than its declared length is treated as a network failure so the last good revision keeps serving, and each cached revision records a sha256 so a corrupted blob is refetched in full instead of being pinned by 304s. Tests in `tests/test_price.py` cover both. Shipped in the commit that moved this note (`cli`).
