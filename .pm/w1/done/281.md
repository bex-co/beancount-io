# A write refusal folds a note's, document's or pad's error into a transaction's paragraph, so one directive is told to "Correct the transaction date" (or a transaction "the note date"), and with a pad the grouping changes from run to run

Found by `/qa-find-bugs-cli w1` on 2026-11-18 (HEAD `6352f9223`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, Python 3.12, stdin closed, no TTY, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`). Severity: minor (nothing is written; the remedy printed for some lines is wrong). A1: an agent repairing a refused write follows the remedy for each line it names, and w5/393 made that remedy name the directive to fix.

**Repro** (a fresh directory):

```sh
cat > main.bean <<'EOF'
2026-01-01 open Assets:Bank USD
2026-01-01 open Expenses:Food USD

2025-12-10 note Assets:Bank "Called the bank"

2025-12-16 * "Lunch"
  Expenses:Food  5 USD
  Assets:Bank
EOF
bea --file main.bean add open --date 2026-01-05 --account Expenses:Fun
```

**Actual** (exit 1, file unchanged, same text under `--json` in `error.details`):

```text
Error: The ledger already has 3 error(s); nothing was written. Pass --allow-errors to write anyway.
  main.bean:4: Invalid reference to inactive account 'Assets:Bank' Account opened 2026-01-01 at main.bean:1. Correct the note date or edit that directive; for new books use bea init --date YYYY-MM-DD. Same problem on 1 more line: 6.
  main.bean:6: Invalid reference to inactive account 'Expenses:Food' Account opened 2026-01-01 at main.bean:2. Correct the transaction date or edit that directive; ...
```

Line 6 is the transaction, but its `Assets:Bank` error is listed as "the same problem" under the note's "Correct the note date". Swap the order (transaction first, then a `note` and a `document` on `Assets:Bank` dated before the open) and the note and document lines become "Same problem on 2 more lines: 8, 9." under "Correct the transaction date".

With a pad, the output also changes between identical runs:

```sh
cat > pad.bean <<'EOF'
2026-01-01 open Assets:Bank USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Equity:Opening USD

2025-12-16 * "Lunch"
  Expenses:Food  5 USD
  Assets:Bank

2025-12-20 pad Assets:Bank Equity:Opening
2026-01-02 balance Assets:Bank 100 USD
EOF
PYTHONHASHSEED=3 bea --file pad.bean add open --date 2026-01-05 --account Expenses:Fun
PYTHONHASHSEED=8 bea --file pad.bean add open --date 2026-01-05 --account Expenses:Fun
```

`PYTHONHASHSEED=3` prints the pad's `Assets:Bank` error on its own line with "Correct the pad date" and "Pad accounts must be open on the pad date, 2025-12-20." `PYTHONHASHSEED=8` folds it into the transaction's paragraph: "Correct the transaction date … Same problem on 1 more line: 9." Without a fixed seed, 8 identical runs gave 4 different outputs in human mode and 4 in JSON mode. `bea check` on the same ledger prints the same text every run.

**Expected:** errors are grouped only when the remedy is the same. A transaction, a note, a document and a pad keep their own "Correct the … date" paragraph, even when they name the same account. The pad's lines keep the pad hint. Identical runs print identical details.

**Root cause:** `_collapse_repeats` (`cli/src/bea_engine/ledger/write.py:1899`) groups records on `(record.kind, tuple(record.hints))`. `kind` is the raw upstream message (`Invalid reference to inactive account 'Assets:Bank'`, from `records.append(_ErrorRecord(...))` at about line 3113). The directive-specific remedy that w5/393 added (`fix = f"Correct the {noun} date"`, about line 2842) lives only in `record.message`, so records that differ only in that remedy fold under whichever came first. Two things make the pad case vary. The pad hint is attached only to the first pad error that produces it (`if pad_hint not in pad_hints`, about line 2991). Upstream `validate_active_accounts` reports one entry's accounts by iterating `getters.get_entry_accounts(entry)`, a `set`. So which pad error gets the hint, and so whether the other pad error's key matches the transaction's, depends on the hash seed.

**Fix:** group on the rendered remedy, not only on the upstream message. For example, key on `(kind, message-without-its-location, hints)` or carry the noun in the key. Make the details order independent of the hash seed: within one source line, sort by account or message before grouping, and attach the pad hint to every pad error, or to the pad's group, instead of only to the first one seen. All callers of `_collapse_repeats` (lines ~1885, 3115, 3156, 3197, 3200) get the change. Add a regression test that drives both repros through real `bea` subprocesses under at least two `PYTHONHASHSEED` values. It should assert that the note and transaction keep separate remedies, that the pad keeps "Correct the pad date" and its hint, and that the output is identical across seeds. Revert the fix and watch it fail.

**Blast radius:** every write that reports loader errors through `validate_candidate`: `add *`, `add transactions`, `update transaction(s)`, `import --apply`. A working control: two transactions before the open fold correctly ("Same problem on 1 more line") because their remedy is the same.

**Dedupe:** w1/118 (identical messages for the same line repeated) and w5/146 (bare line numbers from other files) fixed other `_collapse_repeats` defects. w5/393 introduced the per-directive remedy this grouping undoes. w5/105 and w5/179 (unstable set order in query cells) concern query output. No open item covers grouping across directive types or the seed-dependent order.

---

**Resolved 2026-11-18** — `_collapse_repeats` (`cli/src/bea_engine/ledger/write.py`) now groups on the record's text past its location as well as the upstream message and hints, so a note, a document, a pad and a transaction naming one inactive account each keep their own "Correct the … date" paragraph, while two transactions still fold ("Same problem on 1 more line"). `validate_candidate` sorts each line's adjacent errors by message before building records (and the tolerated ledger errors the same way), so which pad error carries the pad hint no longer depends on the hash seed: both repros print identical human and `--json` details under every seed tried, with the pad's "Correct the pad date" and "Pad accounts must be open on the pad date, 2025-12-20." kept. Regressions in `cli/tests/test_collapsed_repeats_keep_their_remedy.py` drive real `bea` subprocesses under `PYTHONHASHSEED` 3 and 8 in both modes, including the `--allow-errors` refusal; the four bug tests fail with the fix reverted and the two-transaction control passes either way. `bea check` itself still prints one line's errors in upstream's set order; that output is the loader's and was left alone. Shipped in `cb085c03d` (`cli`).
