# Rerunning a `bea update transactions` mapping rejects the rows it already applied

Found by `/qa-find-bugs-cli w1` on 2026-11-15 (HEAD `4cd2197dc`, `bea 0.3.1`, macOS 26.5, checkout `uv run bea`, stdin closed). Severity: minor.

**Contract.** `bea update transactions` writes every valid row and exits **1** when any row is rejected (`cli/docs/USAGE.md`, "Updating directives"). The natural recovery is to fix the rejected rows and run the same mapping again. The engine's own contract (`_plan_rows` in `cli/src/bea_engine/ledger/updating.py`) says "a row that resolves but changes nothing plans to no edits; it reports `unchanged`, never rejected". A flag-only row already does this.

**Repro** (synthetic ledger):

```sh
mkdir q && cd q
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Expenses:Groceries USD

2026-03-01 ! "SAFEWAY"
  import-id: "a1"
  Assets:Checking  -12.34 USD
  Expenses:Uncategorized  12.34 USD

2026-03-02 ! "SAFEWAY"
  import-id: "a2"
  Assets:Checking  -12.34 USD
  Expenses:Uncategorized  12.34 USD
EOF
printf '%s\n' '[{"id":"a1","account":"Expenses:Groceries","flag":"*"},{"id":"a2","account":"Expenses:Grocery","flag":"*"}]' > map.json
bea --file main.bean update transactions --from map.json --apply; echo "exit $?"   # 1: a1 written, a2 rejected (typo)
sed -i.bak 's/Grocery"/Groceries"/' map.json
bea --file main.bean update transactions --from map.json --apply; echo "exit $?"
```

Actual: the second run writes `a2` but rejects `a1` and exits **1**: `Row 1: The entry at main.bean:6 posts to Assets:Checking, Expenses:Groceries, so Expenses:Groceries alone does not say which leg to retarget; name it as OLD=NEW.` The mapping can never finish clean, so a script or agent that retries until exit 0 loops, and one that reads the exit code reports a failure for a queue that is fully categorized. The single-row form has the same bug: repeating `bea update transaction --id a1 --account Expenses:Groceries --flag '*'` after it succeeded exits **2** with the same message.

Expected: a bare `--account NEW` against an entry that already posts to `NEW` and has no holding-account leg left resolves to a no-op. The batch row reports `unchanged`, and the single row behaves like a repeated `--flag '*' --apply` does today: it prints `No changes to main.bean:6; the entry already matches.` and exits 0. The second run above then exits 0 with `a1` unchanged and `a2` written.

**Root cause.** `_retarget_accounts` in `cli/src/bea_engine/ledger/updating.py` (around line 423) resolves a bare account to the unique posting on the holding account (`Expenses:Uncategorized`), or to the only posting. Once a row is applied, the holding leg is gone, so it falls through to the "does not say which leg" `UsageError` without checking whether `NEW` is already one of the entry's postings. `_summarize` and `plan_lines` both call it, so the error rejects the row before the no-op check can mark it unchanged.

**Fix.** In `_retarget_accounts`, when there is no holding-account candidate and `new` is already among the entry's posting accounts, return `(new, new)`. The callers already skip `old == new`, so the row plans no edits and reports `unchanged`. Keep the refusal for an entry with no holding leg that does not already post to `NEW`. Add regression tests in `cli/tests/test_update_batch.py` (a re-applied mapping exits 0 with the applied row `unchanged` and the file byte-identical) and in the single-row update tests (a repeat exits 0 and writes nothing). Estimate: about 30 minutes.

**Dedupe.** Searched `.pm/**` for `which leg`, `retarget`, `already up to date` and `update transaction`. The hits (w5/1025 multiline retargeting, w5/1051 batch target release) cover other paths. `git log -S"alone does not say which leg"` shows only the original feature commit `f29921b65`. This is current code on `main`, not deployment lag.

---

**Resolved 2026-11-15.** `_retarget_accounts` in `cli/src/bea_engine/ledger/updating.py` now resolves a bare `--account NEW` to a no-op when the entry has no holding-account leg and already posts to `NEW`, so a row a previous run applied plans no edits. Rerunning the fixed mapping from the repro exits 0 with `a1` unchanged and `a2` written, and a repeated `bea update transaction --id a1 --account Expenses:Groceries --flag '*' --apply` prints `the entry already matches` and exits 0. An entry with no holding leg that does not post to `NEW` is still refused with the OLD=NEW hint. Regression tests `test_rerunning_an_applied_mapping_reports_its_rows_unchanged` in `cli/tests/test_update_batch.py` and `test_repeating_an_applied_retarget_succeeds_without_writing` in `cli/tests/test_update_command.py` both fail with the fix reverted. `cli/docs/USAGE.md` now describes the fix-and-rerun recovery.
