# Cloud JSON error bodies without the `{ok, error}` envelope surface as `'ok'` and lose 401/403/409 exit codes

**Severity: major. Owner: cli. Estimate: 30–45m. A1:** agents branch on auth vs conflict exit codes. Continuous CLI QA, 2026-10-02; report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`, synthetic fixtures. Reproduced twice from pristine fixtures.

Local simulation: a stub HTTP server answering every request with status 401 (also 403, 409, 429, 500), `content-type: application/json`, body `{"message":"upstream overloaded"}`, header `x-request-id: req-qa-1`.

```sh
BEA_TOKEN=abc BEA_API_URL=http://127.0.0.1:PORT bea --json cloud status
BEA_TOKEN=abc BEA_API_URL=http://127.0.0.1:PORT bea --json cloud ledger create qa-20261002-x
BEA_TOKEN=abc BEA_API_URL=http://127.0.0.1:PORT bea --json -y cloud ledger delete qa/x
```

Actual: exit **1** for every status, stderr `{"error":{"category":"validation","message":"'ok'","exit_code":1}}`, no `request_id`; human mode `Error: 'ok'`. Controls: the same statuses with an HTML body or the proper envelope map correctly (401/403 → 3, 409 → 4); an undocumented 502 with the same JSON body gives `Server error (upstream overloaded)`.

Expected: USAGE "Exit codes" — cloud commands map HTTP status (401/403 → 3, 400 → 2, 409 → 4, else 1) and keep the server message and request ID.

Cause: generated parsers call `V1Error.from_dict(response.json())` for documented statuses; `cli/src/cli/api/rest_client/models/v1_error.py:50` does `d.pop("ok")` → `KeyError`. `call()` in `cli/src/cli/api/client.py:127–129` re-raises parser exceptions on non-2xx (the `w3/m46/t004` guard covers 2xx only); `_install_tolerant_json` (`client.py:25–53`) only handles undecodable JSON; the `KeyError` reaches the catch-all at `cli/src/cli/errors.py:235`.

Fix/acceptance (no generated-file edits): in `call()`, on non-success with a parse `KeyError/ValueError/TypeError/AttributeError`, raise `error_from_status(status, server_message(body) or None, request_id=…)`. For 400/401/403/404/409/429/500 × bodies `{"message":"m"}`, `{"error":"m"}`, `[]`, `"str"`: category and exit follow the table, message "m" or "HTTP N", request ID kept, `'ok'` never appears. Tests in `cli/tests/test_cloud_transport.py`. This is a client-only change; no REST/GraphQL/MCP surface changes.

Dedupe: `.pm` search for `'ok'` / KeyError → `w3/m46/t004`, `t006` (2xx only). `git log -S "if response is None or not response.is_success"` → `aadc7eb9`.

---

**Resolved 2026-10-03** — cloud commands keep the documented status-to-exit-code mapping, the server message and the request ID when an error response carries a JSON body without the `{ok, error}` envelope, instead of reporting `'ok'` with exit 1. `tests/test_cloud_transport.py` covers 400/401/403/404/409/429/500 against several body shapes in JSON and human mode. Shipped in the commit that moved this note (`cli`).
