# Hosted capital gains still read posting signs: a short opening is reported as a sale at zero gain, and the cover's realized gain is missing

**Parity bug · backend-v2 · major · ~1h · A1.** From routine cli-qa, 2026-11-19. [w5/1035](../../w5/done/1035.md) fixed `bea report capital-gains` on 2026-10-27 (`efca4dad5`), but the hosted composer that serves the same report over REST, GraphQL and MCP was not changed. An agent that reads gains over MCP and one that runs `bea` on the same ledger get different realized gains.

Environment: main `adb290b19`, macOS 26.5.1, `bea 0.4.1` from the checkout (`uv run bea`), isolated config and cache, stdin closed, no TTY. The hosted side was run as the backend-v2 composer itself (`composeGains` in `backend-cluster/backend-v2/src/features/ledger/utils/gains.ts`, through `tsx`) on the journal rows this ledger produces. It was not run against production.

Repro ledger (`main.bean`):

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Broker HOOL "NONE"
2026-01-01 open Assets:Cash USD
2026-01-01 open Income:Gains USD
2026-01-01 open Equity:Opening

2026-01-02 * "Open short"
  Assets:Broker  -2 HOOL {100 USD} @ 100 USD
  Assets:Cash     200 USD

2026-01-05 * "Cover one"
  Assets:Broker   1 HOOL {100 USD, 2026-01-02} @ 80 USD
  Assets:Cash   -80 USD
  Income:Gains  -20 USD
```

- `bea --file main.bean check` exits 0. `bea --file main.bean report capital-gains` exits 0 and prints one row: sold 2026-01-05, `1 HOOL`, proceeds `100 USD`, basis `80 USD`, gain `20 USD`; one year or less `20 USD`. This matches the booked `Income:Gains -20 USD` and the rule in `cli/docs/USAGE.md` (Reports): covering a short reports the opening cost as proceeds and the cover price as basis, and opening a short realizes nothing.
- The hosted composer on the same two transactions returns one row: sold **2026-01-02**, quantity `2 HOOL`, proceeds `200`, basis `200`, gain `0`; totals `one_year_or_less: {"USD": "0"}`. The 20 USD realized gain is missing, and the short opening is listed as a sale.

**Root cause:** `closedLot` in `gains.ts` returns null for any posting whose units are not negative (`if (!quantity.isNegative()) return null;`), so a cover is never read. Every negative costed and priced posting becomes a closed lot, a short opening included. This is the pre-1035 classifier. The file's header still says it mirrors `bea report capital-gains`, and the REST description still says a lot closes when "a reducing posting carries booked cost and price". `LedgerFinanceService.getCapitalGains` also loads only the `time` window's journal, so it cannot follow lots opened before the window, which the CLI does (it tracks lots from the first entry, whatever the bounds).

**Do:** port `_capital_gains`' reduction rule (`cli/src/bea_engine/report.py`) to `composeGains`: follow each account's costed inventory from the first transaction, and report only what a priced posting actually closed, long or short, with proceeds and basis swapped for a cover. Opening a short realizes nothing. Load the whole journal for that inventory, and apply `time`, `fromDate`/`toDate` and `account` to the rows only. Keep REST (`GET /v1/ledgers/{owner}/{name}/capital-gains`), GraphQL (`Query.getLedgerCapitalGains`) and the MCP `ledgerCapitalGains` resource on the one service path, and update the REST/GraphQL descriptions and `docs/mcp.md` if they describe the rule.

**Done when:** for the ledger above, all three hosted surfaces return the single 2026-01-05 cover row (1 HOOL, proceeds 100, basis 80, gain 20 USD) that `bea` prints. A 1035-style costed-payable settlement and a long sale match `bea` row for row. `gains.test.ts` and the analysis parity test gain cases that fail with the change reverted, and `yarn test` (parity gate included) stays green in `backend-cluster/backend-v2`.

**Blast radius:** `composeGains` is the only gains composer; its callers are `LedgerFinanceService.getCapitalGains` and through it REST, GraphQL and MCP. The dashboard and mobile app do not show capital gains. Working control: a plain long sale (`-3 AAPL {150 USD} @ 170 USD`) gives the same row on both sides.

**Dedupe:** searched `.pm/**` for `gains.ts`, `composeGains`, `getCapitalGains`, and hosted plus capital-gains. Only [w22/m6](../../w22/done/m6/README.md) (which built the hosted report) and w5/1035 (CLI only) match. This is parity drift after w5/1035, not a new design.

**Unverified:** production. The hosted run used the composer at HEAD on synthetic journal rows shaped like the journal API's.

---

**Resolved 2026-11-19** — `composeGains` (`backend-cluster/backend-v2/src/features/ledger/utils/gains.ts`) now follows each account's costed inventory from the first transaction, as `bea`'s `_capital_gains` does, and reports only what a priced posting actually closed, long or short, with proceeds and basis swapped for a cover. Opening a short realizes nothing, and a transaction the engine could not book moves no lot. `LedgerFinanceService.getCapitalGains` reads the whole journal for that inventory and applies `time` (by the entries its own journal read keeps), `fromDate`/`toDate` and `account` to the rows only. On the repro, REST, GraphQL and the MCP `capital-gains` resource return the single 2026-01-05 cover row (1 HOOL, proceeds 100, basis 80, gain 20 USD). Run on the ledger service's own journal output, the hosted report matches `bea` row for row on 18 cases: short gains and losses, a short opening, the w5/1035 costed-payable settlement, FIFO long sales and a priceless transfer, `time` windows that start after a lot opened, and an unbooked sale. The REST/MCP description, the v1 OpenAPI snapshot and the CLI's pinned copy describe the rule. Covered by `gains.test.ts` (10 cases fail with the old sign rule restored), `ledger-finance-service.test.ts` and the new `capital-gains-cover-parity.test.ts` (REST, GraphQL, MCP), which also fail when the service reads only the window. Shipped in `c951f7685` (`backend-v2`, `cli` spec pin).
