# BQL `FROM … CLEAR` is accepted and silently ignored

**Bug · ledger · major · ~30m · A1.** From `/qa-find-bugs-mcp`, 2026-11-08, production `beancount-mcp 1.0.0`, read-only.

- **Repro:**
  - `runBqlQueryStructured` `SELECT account, sum(position) FROM CLOSE ON 2026-08-01 CLEAR GROUP BY account` keeps the Income and Expenses balances and has no `Equity:Earnings:Current` row.
  - Stock beanquery on the same file zeroes those accounts and adds `Equity:Earnings:Current`.
  - REST `POST …/query` shares the engine and returns the same wrong result. A balance-sheet-as-of query gets wrong numbers with no error.
- **Cause:** rustledger 0.24.0 parses `CLEAR` and does nothing with it. The ledger service does not handle it either; it appears only in the `bql-complexity.ts:82` keyword list.
- **Fix (ledger):** refuse `CLEAR` with `BAD_USER_INPUT` and a workaround hint, as `ledger-shell-service.ts:272` already does for `BALANCES FROM`. Document it next to "FROM OPEN ON is suffix-only" in the ledger README, and report it upstream along with the w23/022 batch.
- **Check:** a test asserts the refusal on REST, GraphQL and MCP. Queries without `CLEAR` are unchanged.

---

**Resolved 2026-11-10.** The ledger engine now refuses `FROM … CLEAR` before the query runs. It uses the same query-error path as the other engine-gap guards (`AT value`, `joinstr` arity), which every surface reaches through the shared `/query` route. The refusal says the engine would ignore the clause and names the stand-in: `SELECT sum(position) FROM <the same scope> WHERE account ~ '^(Income|Expenses):'`, the earnings `CLEAR` would book to `Equity:Earnings:Current`.
- **Scope of the guard:** it fires on a bare `CLEAR` after `FROM` outside a string literal. Queries without the clause run unchanged.
- **Tests:** `clear-scope-guard.test.ts` covers refusals and lookalikes. In `yarn verify:rustledger`, live checks confirm the raw engine still ignores `CLEAR`, which reproduces the bug. The same checks show that the query path refuses it and that the named earnings sum runs. The first check fails once an engine bump honours the clause, and the guard can then go.
- **Docs:** documented in the ledger README beside "FROM OPEN ON is suffix-only".
- **Still to do:** the upstream report belongs with the w23/blocked/022 engine-gap batch. It was not filed from this run. (`ledger`)
