# Confirm upstream path-parameter hardening on production after deploy

**Verify · backend-v2 · ~15m · A1.** Follows `8a2e14649` (2026-11-09).

The generated ledger-service and Gitea clients now encode every single-segment path parameter. The shared services also validate entry hashes (32 lowercase hex), user and collaborator names (the Gitea username rules) and pull-request base branches (git ref rules). These checks cover REST, GraphQL and MCP together, and parity tests cover them.

- **Blocked on:** an operator deploy of backend-v2.
- **Check after deploy:**
  - `getEntryContext` with a non-hex `entryHash` returns `BAD_USER_INPUT` on MCP, REST and GraphQL.
  - `beancount://social/profile?username=` with a name containing `?` or `/` returns `BAD_USER_INPUT`.
  - A valid hash and a valid username still read normally.

**Addendum 2026-11-10:** the hardening first refused the `<hash>:<k>` IDs that list output gives the second and later byte-identical duplicates. That is fixed before deploy in the commit that follows this note on `main` ("entry context accepts the :<k> ID of a repeated entry"). After the deploy, also check that `getEntryContext` resolves a suffixed ID from `listLedgerEntries`, on MCP, REST and GraphQL. The public example ledger has one (a `Custom` entry dated 2026-10-30).

**Blocked 2026-11-10** — production does not yet run `8a2e14649`. A read-only probe through the session's hosted MCP connection, `getEntryContext` with `entryHash: "not-a-hex-hash"`, answered `NOT_FOUND` "Entry with ID 'not-a-hex-hash' not found", not the `BAD_USER_INPUT` the change returns. The same day, `yarn mcp:conformance https://beancount.io` still failed checks 3 and 18, and those were fixed on `main` on 2026-11-08 (`435cef7cf`, `2028eb90a`). So production predates both. The code and its parity tests are on `main`, and only the production check remains. **Unblock:** an operator deploys backend-v2 at or after `a23eeb234` (which includes `8a2e14649` and the `:<k>` fix above). Then run the checks above, the addendum's `:<k>` check included, on MCP, REST and GraphQL. Cleared by the user (deploy).

**Resolved 2026-11-12** — production now runs the hardening; all checks pass live, shipped in `8a2e14649` and `a23eeb234` (`backend-v2`). After the 2026-11-12 deploy (the build includes `126cc8220`), `getEntryContext` with `entryHash: "zz"` returns `BAD_USER_INPUT` ("entryHash must be an entry_hash from list output: 32 lowercase hex digits, with a :<n> suffix on a repeated entry") on MCP, REST (400) and GraphQL (`extensions.code`), and a `../../x` value is refused the same way on REST. `beancount://social/profile?username=a%3Fb` and `…=a%2Fb` return `BAD_USER_INPUT`, and a valid username reads its profile. In the public example ledger, a repeated `Custom` budget entry dated 2026-08-27 (not 2026-10-30 as the addendum guessed) lists as `<hash>` and `<hash>:1`. Each ID resolves to its own line on all three surfaces: the base ID to `main.bean:6526` and `:1` to `main.bean:6529`. The same run of `yarn mcp:conformance https://beancount.io --ledger <qa-owner>/mcp-agent-eval` gave 17 passed and 0 failed, with only the read-only-key check skipped. `qa-contract-replay.mjs --commit-probes` gave 16 probes and 0 mismatches.
