# `bea query` crashes with a raw `TypeError` (exit 1) on `PIVOT BY` a column that holds a NULL or mixed-type values, such as `payee`, and on `min()`/`max()` over mixed-type metadata

**Bug · cli · minor · 45–75m · A1.** From routine cli-qa, 2026-11-20. A pivot by payee is a common first question: spend per payee per month. Any transaction written with one string (`2026-01-10 * "Rent"`) has no payee, and so does every pad. One such row makes `bea query "… GROUP BY month, payee PIVOT BY month, payee"` fail with `Error: TypeError: '<' not supported between instances of 'str' and 'NoneType'. Pass --debug before the command for a traceback.` and exit **1**, the ledger-validation code. The ledger is fine, and the same rows grouped and ordered without `PIVOT BY` run. The same `TypeError` comes back for a pivot key whose values mix types (`ref: "A-12"` beside `ref: 5`), and for `min()`/`max()` over such a column. Yet `ORDER BY` on that column already works, since w5/562, w5/760 and w5/965. An agent cannot tell from this message whether the query, the ledger or `bea` is at fault. The hosted query engine (`runBqlQueryStructured`, REST, GraphQL) pivots the same NULL keys without error.

Environment: main `9baf62a82`, `bea 0.5.0` from the checkout (`uv run bea`), beanquery 0.2.0, beancount 3.2.3, Python 3.12.14, macOS 26.5.1. The run used an isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME` with `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, and the cwd in a scratch directory. Each command was reproduced in fresh processes from a pristine copy, and the ledger hash was unchanged after every run. The interactive shell was also checked under a PTY: it prints `error: TypeError: …` and keeps running.

## Repro

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Expenses:Rent USD

2026-01-05 * "Cafe" "Lunch"
  Expenses:Food  12.00 USD
  Assets:Checking

2026-01-10 * "Rent"
  Expenses:Rent  900.00 USD
  Assets:Checking

2026-02-05 * "Cafe" "Lunch"
  Expenses:Food  8.00 USD
  Assets:Checking
EOF
bea --file main.bean check                                                                                     # exit 0
bea --file main.bean query "SELECT month, payee, sum(number) WHERE account ~ '^Expenses' GROUP BY month, payee PIVOT BY month, payee"
bea --file main.bean query "SELECT payee, month, sum(number) WHERE account ~ '^Expenses' GROUP BY payee, month PIVOT BY payee, month"

cat > mixed.bean <<'EOF'
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-01-05 * "Cafe" "Lunch"
  ref: "A-12"
  Expenses:Food  12.00 USD
  Assets:Checking
2026-01-06 * "Cafe" "Lunch"
  ref: 5
  Expenses:Food  8.00 USD
  Assets:Checking
EOF
bea --file mixed.bean query "SELECT account, entry_meta('ref') AS r, sum(number) WHERE account ~ 'Food' GROUP BY account, r PIVOT BY account, r"
bea --file mixed.bean query "SELECT min(entry_meta('ref')), max(entry_meta('ref'))"
```

Actual: each of the four queries prints a line like `Error: TypeError: '<' not supported between instances of 'str' and 'NoneType'. Pass --debug before the command for a traceback.` (`'decimal.Decimal' and 'str'` for the mixed ledger) and exits **1**. Under `--json` the error is `{"category": "validation", "message": "TypeError: …"}`. The result is the same with `-f csv`, with BQL on stdin, and with `--source main.bean`.

Controls:

- `… GROUP BY account, month PIVOT BY account, month` on the same ledger pivots, exit 0 (`Expenses:Food 12.00 8.00`, `Expenses:Rent 900.00`). No key is NULL.
- `SELECT account, entry_meta('ref') AS r, sum(number) … GROUP BY account, r ORDER BY r` exits 0 and orders `5` before `A-12`: w5/965's rule (a mixed column compares by text).
- `SELECT min(payee), max(payee)` exits 0: upstream skips NULLs in aggregates.
- The hosted engine on a synthetic ledger answers `… GROUP BY month, payee PIVOT BY month, payee` with a column named `NULL` first, and `… PIVOT BY payee, month` with a row whose key is `null`.

## Expected

Pivots and `min`/`max` order their values the way `bea`'s `ORDER BY` already does: a NULL comes first and is only compared with another NULL, and a column whose values are of different kinds compares by text. A uniform column keeps its native order, so months stay `1, 2, …, 10`.

On the repro:

- `PIVOT BY month, payee` exits 0 with columns `month/payee`, `NULL`, `Cafe` (the NULL key's column is headed `NULL`, as the hosted engine names it): month 1 is `900.00` and `12.00`, month 2 is empty and `8.00`.
- `PIVOT BY payee, month` exits 0. Its first row has an empty key cell (`null` in JSON) with `900.00` under `1`, followed by `Cafe` with `12.00` and `8.00`.
- The mixed pivot exits 0 with columns `account/r`, `5`, `A-12`, and `Expenses:Food` reads `8.00` and `12.00`.
- `min(entry_meta('ref'))` is `5` and `max(…)` is `A-12`, keeping each value's own type in JSON.

Text, CSV, `--json`, `.run`, stdin and the interactive shell all give the same answer. `--source` may keep native rendering, but it must not raise.

## Root cause

Upstream `beanquery/query_compile.py` `EvalPivot.__call__` sorts the pivot keys natively (`keys = sorted({row[col2] for row in rows})`, line 654). It then sorts the rows by the first pivot column (`rows.sort(key=operator.itemgetter(col1))`, line 667). `beanquery/query_env.py` `Min.update`/`Max.update` (lines 866–890) compare `value < cur` / `value > cur`. All three comparisons raise on `None` against a `str`, or on a `Decimal` against a `str`.

`cli/src/bea_engine/query.py` `_null_safe_ordering` (line 277) replaces only `query_execute.nullitemgetter`, which is ORDER BY's key. That replacement is how w5/562 (NULLs), w5/760 (mixed types) and w5/965 (one rule per column, via `_Column`/`_Orderable`/`_null_aware`) fixed `ORDER BY`. The pivot and aggregate comparisons never go through that key. The raw `TypeError` then reaches the catch-all, so it is reported as exit 1.

## Fix (cli only)

Install bea's ordering for the two remaining comparison sites, next to `_null_safe_ordering`, so every path that calls `connect`/`load` gets them:

- the pivot's key set and row sort use the `present`/`_Column` key, and a NULL key's column is named `NULL`;
- `min`/`max` choose by the same rule once a group's values are known to mix kinds.

No backend change is needed. The hosted engine already pivots NULL keys, and REST, GraphQL and MCP do not run beanquery.

**Done when** the four repro queries exit 0 with the values above in text, CSV and `--json`, and both controls are unchanged. A regression test in `cli/tests/` (beside the w5/965 ordering tests) covers a NULL pivot key in each position, a mixed-type pivot key, and mixed `min`/`max`. The test must fail with the fix reverted.

**Dedupe.** Searched `.pm/**` (including `done/` and `blocked/`) for `PIVOT`, `pivot`, `min(`/`max(` with meta, `Column(name`, and `'<' not supported`. w23/022 notes, in its upstream-report list, that stock beanquery crashes on NULL pivot keys while the hosted engine pivots them (it.3478). It files no `bea` CLI fix, and its other PIVOT entries are hosted-engine portability notes. w5/562, w5/760 and w5/965 (done) fixed only `ORDER BY`. No open item covers this, and `git log -S EvalPivot -- cli` is empty.

**Also seen, not part of this fix:** `PIVOT BY account, year` when `year` is not a SELECT target reports `PIVOT BY column Column(name='year') is not in the targets list`, a Python repr. It is followed by `Run bea query .tables to list what you can query.`, which does not help: the column exists but is missing from the targets.

---

**Resolved 2026-11-20** — Reproduced at `b324ea338`: all four repro queries exited 1 with `TypeError: '<' not supported …`, and the controls answered. `cli/src/bea_engine/query.py` now replaces upstream `EvalPivot.__call__` so the pivot's key set and row sort use ORDER BY's per-column key (`_column_key`, shared with the w5/965 `nullitemgetter`): NULL first, a mixed column by text, a uniform one natively. A NULL key's column is headed `NULL`. `min()`/`max()` keep a group's values and pick once it is whole: by text when the group mixes kinds, natively otherwise. Each value keeps its own type (`min` is `Decimal('5')`, `max` is `'A-12'`). On the repro, `PIVOT BY month, payee` gives `month/payee`, `NULL`, `Cafe` with `1 900.00 12.00` and `2 · 8.00`. `PIVOT BY payee, month` leads with the NULL-key row. The mixed pivot gives `account/r`, `5`, `A-12`. Text, CSV, `--json`, stdin, `.run`, `--source` and the interactive shell (PTY) all answer, and both controls are unchanged. A pivot with no value columns still answers as upstream does. On a 60,000-transaction ledger, eight `min`/`max` aggregates cost 0.30–0.51 s, against upstream's 0.23–0.44 s. `cli/tests/test_query_pivot_and_min_max_order.py` covers a NULL pivot key in each position, a mixed pivot key, `min`/`max` over every source order of a mixed column, the uniform controls, and value types: 22 of its 23 tests fail with the fix reverted, and the one that passes is the uniform `min`/`max` control. `make check-all` passes. The `PIVOT BY … is not in the targets list` wording noted above is not part of this fix. Shipped in `9ca01af18` (`cli`).
