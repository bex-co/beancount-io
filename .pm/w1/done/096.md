# One long cell bypasses `ask`'s ~12,000-character query-result limit

**Severity: minor. Owner: cli. Estimate: 30–45m. A1:** oversized tool results blow the model budget on every later request. Continuous CLI QA, 2026-10-03 (round 4); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled. **Local simulation:** a fake OpenAI-compatible model server on `127.0.0.1`, reached via `BEA_API_URL` and a fake `BEA_TOKEN`; no hosted AI service was used. Reproduced twice with a working control.

Fixture `main.bean`: `option "operating_currency" "USD"`; open `Assets:Checking`, `Expenses:Food`, `Equity:Opening` (USD); one opening transaction.

Add a transaction whose narration is 300,000 `x` characters, then (model asks for `SELECT narration WHERE payee = 'Big'`):

```sh
bea --file /abs/huge.bean ask --print "query the big row"
```

Actual: the second model request is 306,657 bytes and contains the whole cell. Control: over 4 rows where the long row is not first, truncation works (6,627-byte request).

Expected: USAGE — results beyond "roughly 12,000 characters" are truncated; `cli/src/cli/ask/results.py` sets `MAX_CHARS = 12_000`.

Cause: `results.py:111` — `if used + len(line) + 1 > MAX_CHARS and shown:` always accepts the first row whatever its length; cells are never clipped.

Fix/acceptance: clip each cell/line to the remaining budget with a visible "…(N chars cut)" marker and the truncation footnote. A 300 KB first row yields `format_result` output ≤ ~12,000 chars that says it was truncated.

Dedupe: `w3/448` / `m51` (`79ef0386`) introduced the limit; no item covers a single huge row.

---

**Resolved 2026-10-04** — a single oversized query row is now cut to the `ask` result budget with a visible `…(N chars cut)` marker and the truncation notice. Tests in `tests/test_ask_result_shape.py` cover it. Shipped in the commit that moved this note (`cli`).
