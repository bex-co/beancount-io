## Objective

Decide strictness once, in the output layer, so reads follow the same rule the CLI already uses for prompts: a human at a terminal gets data plus a banner, automation gets a refusal unless it opted in.

## Context

- `cli/src/cli/output.py::render_ledger_errors(errors, *, allow, message)` is the single choke point; `list`, `query`, and `report` call it with `allow=allow_errors`, and `check` calls it with `allow=False`.
- Prompts are already disabled when stdin is not a terminal, under `--json`, or when `CI` is truthy (`cli/src/cli/context.py`); reuse that detection for stdout.
- Today's behavior is documented in `cli/docs/USAGE.md` ("Checking, formatting, querying") and `cli/README.md` ("Check"); `cli/docs/PRFAQ.md` FAQ 9 states the automation principle this task preserves.

## Steps

1. Add a global `--strict` flag next to `--json` and `--no-input`; define `strict_reads()` in the context as `--strict or --json or not stdout.isatty() or CI`.
2. In `render_ledger_errors`, when `allow` is false and `strict_reads()` is false, print the errors as a banner on stderr and return instead of exiting.
3. Keep `bea check` unconditional: it always exits 1 on errors.
4. Keep `--allow-errors` as the explicit opt-in for strict mode; its help text should say so.

## Acceptance criteria

- [ ] With a failed balance assertion, `bea list transaction` in a pseudo-terminal prints the table and the banner and exits 0.
- [ ] The same command with `--json`, with stdout piped, or with `--strict` exits 1 with the current error message.
- [ ] `bea check` still exits 1.
- [ ] `--allow-errors` behavior under `--json` is unchanged.
