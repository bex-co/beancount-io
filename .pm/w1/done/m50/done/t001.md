## Objective

Each batch row stops rescanning the ledger: `shared_locations`, the on-disk transactions, the id tiers and each file's written line numbers are computed once per batch.

## Context

- `cli/src/bea_engine/ledger/updating.py`: `locate_transaction`, `entry_span`, `plan_lines`, `_plan_rows`.
- The id tiers (import-id keys, `ref`, bank-ID keys) keep their order and their refuse-if-shared rule; `file:line` ids keep their lookup.

## Steps

1. Build one index per batch: `shared`, the on-disk transactions, a value → entries map per id tier, and each file's sorted written line numbers.
2. Resolve ids through the index and find a span's end with `bisect`.
3. Let the single-row path share the helpers.

## Files

- `cli/src/bea_engine/ledger/updating.py`

## Acceptance criteria

- [x] `reader.shared_locations` runs once per batch, whatever the row count.
- [x] Every existing locate and batch test passes unchanged.

## Out of scope

- Diffs and validation (t002, t003).

## Done — 2026-11-23

`EntryIndex` (`cli/src/bea_engine/ledger/updating.py`) is built once per load: the shared locations, the on-disk test of every entry, a value → entries map per id tier (import-id keys, `ref`, bank-ID keys, keeping the refuse-if-shared rule), transactions by line, and each file's sorted written line numbers, which `span` searches with `bisect`. `_plan_rows`, the single-row `answer` and `locate_transaction` all read it; `plan_lines` takes the span it computes. `test_the_ledger_is_indexed_once_per_batch` asserts one `shared_locations` call and one `entry_generated` call per entry for a 64-row batch, and fails when the index is rebuilt per row.
