# `.reload` bypasses the interactive query session's strict-read policy

**Severity: minor. Owner: cli. Estimate: 40–50m. A1:** a strict accounting session must refuse partial answers after reload as well as at startup. Found by continuous CLI QA on 2026-10-02; no product fix applied.

Environment: `main` HEAD `1a1480c8ad2dee049c4bccf4a646c2513082b04c`, checkout `cli/.venv/bin/bea`, Python 3.13.0, macOS 26.5.1 arm64. Installed editable metadata says 0.3.0 while source/engine are this HEAD (0.3.1). Isolated synthetic ledgers/config/cache, notifier disabled, no inherited ledger target or token. Two pristine fixtures and fresh PTYs reproduce each variant below.

## Reproduce

Save `/absolute/main.bean` in a disposable directory:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Equity:Opening USD
2024-01-02 * "Start"
  Assets:Cash 100 USD
  Equity:Opening -100 USD
```

1. Open `bea --strict --file /absolute/main.bean query --no-errors` in a terminal. The valid ledger correctly opens a prompt.
2. In a second terminal/editor, append `2024-01-03 balance Assets:Cash 999 USD` to that synthetic file. This intentionally introduces a failed assertion: actual cash is 100 USD.
3. In the existing query shell, enter `.reload`, then `SELECT sum(position) WHERE account = 'Assets:Cash';`, then `.exit`.

Actual: `.reload` accepts the invalid load, the query prints **100 USD**, stderr is completely empty with `--no-errors`, and the session exits **0**. Without `--no-errors`, the validation banner prints but the strict session still answers. An additional unbalanced-transaction fixture likewise returns totals incorporating the invalid posting.

Working controls: a fresh one-shot `bea --strict --file /absolute/main.bean query 'SELECT sum(position)' --no-errors` refuses with exit **1**, no stdout, and a diagnostic naming the failed assertion and `--allow-errors`. Interactive `--strict query --allow-errors` intentionally returns partial results with its banner. Restoring the valid fixture and reloading allows correct results again. Fixture changes are the explicit harness/editor edits; the query commands do not write the ledger.

Expected from `cli/docs/USAGE.md`'s `--strict` option and strict-read paragraph: refuse answers from any invalid load unless `--allow-errors` is explicit. `--no-errors` controls the banner, not validation. A shell opened successfully must not lose this policy when files change.

## Cause, fix and acceptance

`cli/src/cli/commands/query.py:252–258` correctly forwards the startup read policy. `cli/src/bea_engine/query.py:302–304` calls `_gate` only once, after `build_shell` and before `cmdloop`. `PreciseShell.do_reload` at lines 355–366 clears errors/options and attaches the new ledger without a policy check. Its `execute` at lines 413–433 checks BQL syntax/window rules but never gates the new load; `build_shell` does not retain `allow_errors` for later use. `--no-errors` suppresses the only remaining diagnostic.

Retain the resolved read policy for the lifetime of an interactive shell. After a reload introduces errors, surface the refusal and block subsequent queries (including `.run` stored queries) from returning partial results until a successful reload, or close the session with the documented validation failure. Keep recovery/diagnostic commands usable if the session stays open; never silently reuse an old valid answer under the new invalid file. Preserve default lenient terminal use, explicit `--allow-errors`, and valid reloads. CLI-only; no API changes.

Acceptance: real PTY regressions cover valid startup → failed assertion → reload/query, with/without `--no-errors`, plus valid recovery and the explicit override. Strict failed reload must not emit a result table; no unintended ledger write or traceback. Retain the existing strict-invalid-startup control and run `make check-all` inside `cli/` when implementing. Stored-query gating is shared-code scope; that additional branch and non-macOS platforms remain unverified by this QA run.

---

**Resolved 2026-10-03** — a strict interactive `bea query` session keeps its read policy after `.reload`: a reload that introduces errors prints a refusal (even under `--no-errors`) and typed and `.run` stored queries are refused without a result table until the ledger reloads cleanly, while `.reload`, `.errors` and `.exit` keep working and explicit `--allow-errors` still answers. Real-PTY tests in `tests/test_strict_interactive_shell.py` cover both banner modes, recovery and the override. Shipped in the commit that moved this note (`cli`).
