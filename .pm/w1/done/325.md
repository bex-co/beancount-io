# `bea query` prints every amount in a currency to 26 decimals when one value in the result is a division quotient: `SELECT account, sum(position) GROUP BY account` reads `-10000.00000000000000000000000000 USD` once a ledger holds a `{{100 USD}}` lot or an `@@` total price

**Bug · cli · minor · 30–45m · A1.** From routine cli-qa, 2026-11-19. Beancount divides a total cost `3 HOOL {{100 USD}}` into a per-unit `33.33333333333333333333333333 USD`. It also divides a total price `3 EUR @@ 10.00 USD` into a per-unit `@ 3.333333333333333333333333333 USD` and infers its cash leg as `-9.999999999999999999999999999 USD`. `bea query` text tables size each currency to the most fractional digits of any value in the result. So once one of those quotients is in the rows, every amount in that currency prints 26 or 27 decimals: the opening balance, a lunch, the checking total. `sum(cost(position))` for a lot bought for 100 USD reads `99.99999999999999999999999999 USD`. Native rendering of the same query (`bea query --source`) prints `-10000.00 USD`, `100.00 USD` and `3 HOOL {33.33 USD}`. Both are common ways to record a purchase, and `bea add`'s own w1/317 refusal recommends the total-cost form. The query that triggers this is the first one most people run.

A smaller form of the same mechanism: a product's trailing zeros count as precision too. `12.50 EUR @ 1.10 USD` infers its card leg as `-13.7500 USD`, and from then on every USD amount in `SELECT account, sum(position) GROUP BY account` prints four decimals (`4800.0000 USD`, `-45.1000 USD`). `--source` prints `4800.00 USD` and `-13.75 USD`.

`--json` and `--format csv` without `-m` stay exact (`"99.99999999999999999999999999"`, `9887.70`). The values are not wrong. The text table is unreadable, and an agent pasting it into a summary reports 26-decimal dollars, or a 100 USD purchase as 99.99999999999999999999999999.

Environment: main `5dc45262d`, `bea 0.4.1` from the checkout (`uv run bea`), Python 3.12.14, macOS 26.5.1. The run used an isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME` with `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, and the cwd in a scratch directory. Each command exits 0 with empty stderr. Reproduced in fresh processes from pristine copies, and the ledger hashes were unchanged.

## Expected

The repo's rule for per-unit figures (w1/324, `report._cost_digits`) applies here too: "a quotient that ran to the decimal context's full precision contributes none". So does the rule for report tables (w1/052, w1/322): a currency shows the precision the ledger itself uses for it. A trailing zero of a product teaches the display nothing. `docs/USAGE.md`'s query promise still holds: "Query tables preserve the precision of result values, including calculated amounts … cents are never discarded".

- Repro 1 prints `9887.70 USD`, `-10000.00 USD`, `12.30 USD`, `3 HOOL {33.33 USD}` (or the lot's own written digits), and `100.00 USD` for `sum(cost(position))`, matching `--source`.
- Repro 2 prints `3.33 USD`, `-10.00 USD`, `990.00 USD` and `10.00 USD`.
- Repro 3 prints `1000.00 USD` and `-13.75 USD`.
- Controls keep their digits. A `convert()` at an eight-decimal quote such as `price BTC 61234.56789012 USD` still shows its eight computed decimals. A `12.5 USD` posting in a whole-dollar ledger still shows `.5`, and a written `0.0042 USD` amount still shows four decimals.
- `--json` and `--format csv` without `-m` are unchanged and exact.

## Root cause

`cli/src/bea_engine/query.py:3677` `result_context` records `-int(value.number.as_tuple().exponent)` for every `Amount` and `Cost` in the rows (`:3689`). That count includes a 28-digit quotient's 26–27 fractional digits and a product's trailing zeros. `:3720` then gives every value in that currency that many places. Callers: the text/CSV/beancount shell path `on_Select` (`:1646`, used by one-shot, stdin and the interactive shell) and `rows_answer`'s `-m` numberify (`:332`). The `--source` path keeps upstream's display context, which is why it is the working control. `bea ask`'s BQL tool reads `--format json` without numberify, so it is not affected.

## Fix

In `result_context`, give each currency the larger of:

- (a) the ledger's own display precision for it, as the report tables compute it: posting amounts and balance assertions, or `option "display_precision"`; see `report._display_precision`;
- (b) the meaningful fractional digits of each result value: trailing zeros stripped, and nothing for a value whose coefficient reached the decimal context's precision (the `report._cost_digits` test).

Reuse the report helpers rather than copying them. Keep `ResultContext.quantize`'s large-integer handling (w5/472). For `-m` cells in JSON/CSV, which carry today's padding (`"9887.70000000000000000000000000"`, numerically equal), make sure the change does not round any value there. If keeping them lossless needs a separate context, give them one.

Tests (new `cli/tests/test_query_result_precision.py`): Repros 1–3 through the real `bea query` subprocess or the engine's `text_answer`, with expected cells as above; the eight-decimal `convert()`, whole-dollar `12.5` and `0.0042` controls; `--json` rows unchanged. Revert the fix and watch them fail. Update the "Result precision" paragraph in `query.py`'s module docstring and the `docs/USAGE.md` query precision paragraph (around "Query tables preserve the precision of result values") to state the quotient rule. Run `make check-all` in `cli/`.

## Dedupe

Searched `.pm/**` for `result_context`, `ResultContext`, `33333333`, `0000000000`, `bea query` with `precision`/`digits`. w1/052 and w1/322 fixed report tables, and w1/324 fixed holdings/register per-unit cost. w1/322 states "`bea query` renders with Beancount's own display context and is unaffected", but that is true only of `--source`. w3/309 fixed `bea add` writing `@@` as a repeating `@`. w5/472 and w5/628 cover `--source`'s twelve-integer-digit failure. w21/160 is the dashboard's money-flow analogue. None covers `bea query`'s own text precision. `git log -S digits_by_currency` shows the rule unchanged since `790791acc` (2026-09-08).

---

**Resolved 2026-11-19** — `bea query` text tables now show each currency at the finer of the precision the ledger writes it in and the meaningful digits of its values. The first comes from posting amounts, balance assertions or `option "display_precision"`, through `report.written_precision`, which was split out of `_display_precision` so the report tables and the query table share one rule. For the second, trailing zeros are stripped and a quotient that ran to the decimal context's full precision contributes none (`report._cost_digits`). On the repro ledgers, Repro 1 prints `9887.70 USD`, `-10000.00 USD`, `12.30 USD`, `3 HOOL { 33.33 USD}` and `100.00 USD` for `sum(cost(position))`, also under `-m` and on stdin. Repro 2 prints `3.33 USD`, `-10.00 USD`, `990.00 USD` and `10.00 USD`. Repro 3 prints `1000.00 USD` and `-13.75 USD`. The controls hold: a `convert()` at `price BTC 61234.56789012 USD` still shows `30617.28394506 USD`, a whole-dollar ledger's `12.5 USD` still shows `.5`, and a written `0.0042 USD` still shows four decimals. `--json`, `--format csv` and their `-m` columns are byte-identical to before and exact, because those cells keep the lossless context. The interactive shell reads the written precision once per load and again after `.reload`. The precision rule is documented in `cli/src/bea_engine/query.py`'s module docstring and `cli/docs/USAGE.md` (query precision paragraph). Tests: 10 cases in the new `cli/tests/test_query_result_precision.py`, of which 7 fail with the fix reverted. The other 3 are controls, and the `convert()` control also fails when the meaningful-digits half of the rule is removed. `make check-all` passes. No REST/GraphQL/MCP change: the hosted query surfaces return structured rows, not this text table. A sum that cancels a quotient to a residue (for example `sum(weight)` across a `{{100 USD}}` purchase and its `-100.00 USD` cash leg, which reads `-0.00000000000000000000000001 USD`) still shows that residue's digits. Shipped in `d9667954c` (`cli`).
