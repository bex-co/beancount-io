# A write with `--file` on a month file under a shared year index is judged by whichever ledger sorts first: two roots are never asked about, and a forecast overlay above the root becomes the judge, so a true balance is refused and a false one lands with exit 0 (gap in w5/775 and w5/933)

**Severity:** major. **Owner:** `cli`. **Estimate:** 45–60 minutes including tests. **A1:** an agent pointed at the month file it is editing (the documented year-index layout) gets a write checked against the wrong ledger, with exit 0 for the wrong answer and a remedy that edits the wrong root. **Found by:** `/qa-find-bugs-cli` (`cli-qa` routine) on 2026-11-26. Checkout `bea 0.5.0` at `5096eca03`, macOS 26.5.1, Python 3.14, fresh process per command, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier off, no inherited `BEA_FILE`/`BEA_TOKEN`, stdin closed. Each case reproduced twice from pristine fixtures, with the controls below. No product fix applied.

## Repro 1 — two roots above one year index

`books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Equity:Opening
2026-01-01 * "open"
  Assets:Cash 100 USD
  Equity:Opening
include "2026/index.bean"
2026-01-20 * "dinner"
  Expenses:Food 30 USD
  Assets:Cash
```

`books/main-backup.bean`: the first eight lines of `main.bean` (no dinner). `books/2026/index.bean`: `include "jan.bean"`. `books/2026/jan.bean`: `; january`.

```sh
bea --file books/2026/jan.bean add balance -a Assets:Cash --amount '70 USD' --date 2026-02-01
bea --file books/2026/jan.bean add balance -a Assets:Cash --amount '100 USD' --date 2026-02-01
bea --file books/main.bean check
```

Actual: the true 70 exits 1 (`expected 70 USD != accumulated 100 USD (30 too much)`); the false 100 exits 0 and lands in `jan.bean`. Both print `jan.bean is included by …/main-backup.bean; the write goes to jan.bean and is checked against that whole ledger.` `check` on `main.bean` then exits 1: `jan.bean:3: Balance failed for 'Assets:Cash': expected 100 USD != accumulated 70 USD`.

`update` goes the same way. Add `2026-01-01 open Expenses:Groceries USD` to `main.bean` only, put a `! "Shop"` entry with `import-id: "j1"` posting `Expenses:Food 5 USD` in `jan.bean`, then run `bea --file books/2026/jan.bean update transaction --id j1 --account Expenses:Food=Expenses:Groceries`. It exits 1 with `Invalid reference to unknown account 'Expenses:Groceries' … To create it, use bea --file …/main-backup.bean add open …`. That refuses a write that is valid for the real root, and its remedy edits the backup instead.

## Repro 2 — a forecast overlay above the root

Same `main.bean` without the dinner. `books/forecast.bean`:

```beancount
include "main.bean"
2026-01-10 * "planned dinner"
  Expenses:Food 30 USD
  Assets:Cash
```

Running the same two `add balance` commands, the true 100 exits 1 (`expected 100 USD != accumulated 70 USD`), and the false 70 exits 0 with `jan.bean is included by …/forecast.bean`. `bea --file books/main.bean check` then fails on it. That is the w5/578 / w5/774 outcome, with the forecast entry counted.

## Controls

- With `jan.bean` included directly (no `index.bean`), Repro 1 exits 2 with `jan.bean is included by more than one root ledger: …main-backup.bean, …main.bean` (the w5/775 fix). Repro 2 writes the 100 through `main.bean` with exit 0, and `main.bean` checks (the w5/933 fix).
- Renaming `main-backup.bean` to `zz-backup.bean`, or `forecast.bean` to `zforecast.bean`, makes both index cases pick `main.bean`. So the judge is chosen by file-name order. Even then, Repro 1 still gives no exit 2 for the two roots.

## Root cause

`cli/src/bea_engine/ledger/write.py`. `write_through_root` (`:2479`) runs the w5/775 ambiguity check over `_nearest_includers(file)` (`:2447`) only. For a month file that list holds just `index.bean`, because both roots (and the overlay) include it. `defining_root(file, first=index.bean)` (`:2278`) then finds `index.bean` defines nothing and climbs on with `above = including_root(current)` (`:2303`). `including_root` (`:2199`) is `next(_scan_includers(file))`, the first includer in scan order. Every other includer of the intermediate is dropped, so there is no second-root check and no overlay filter. An overlay's closure contains the root's `open`s, so `_defines_in` accepts it as the root.

## Fix

When the climb passes a pass-through intermediate, branch over all of that intermediate's nearest includers, as `write_through_root` already does for the leaf. Apply the w5/933 rule at each step: drop an includer whose closure contains another includer, and keep the overlay stop. Collect the distinct defining tops. More than one top exits 2 with the existing `included by more than one root ledger … --into 2026/jan.bean` message. Exactly one top is the root. `root_read_hint` and `root_ledger_hints` should use the same climb and name every root, not one picked by name order.

## Blast radius

`write_through_root` serves engine `add` (every directive type and `add transactions`), `update` (single and batch), `import` (preview, apply, and the `root` lookup that keys import memory, so the mapping would be remembered under the wrong root), and `append` (`bea ask`). `defining_root` also feeds the read hints in `check`, `list`, `query` and `report` (`root_read_hint`) and the write-refusal recipe (`root_ledger_hints`). `--into` from the named root is unaffected. Existing tests (`cli/tests/test_leaf_ambiguous_roots.py`, `test_leaf_forecast_overlay_root.py`, `test_month_leaf_sibling_entries.py`) cover direct includes, or a year index with one root above it, only.

## Acceptance

- Repro 1: both `add balance` commands, and the `update`, exit 2 naming `main.bean` and `main-backup.bean`, and `jan.bean` is unchanged.
- Repro 2: the 100 lands through `main.bean` with exit 0, the 70 is refused naming `main.bean`, and `main.bean` checks.
- Renaming the second root or the overlay does not change either outcome.
- A regression test pins both shapes and fails with the fix reverted.

## Dedupe

Searched `.pm/**` for `main-backup`, `index.bean`, `more than one root`, `two roots`, `included by both`, `overlay`, `year index` and `pass-through`. w5/775 (done, `560514d4b`) and w5/933 (done, `f81b97c05`) fixed the direct-include shapes. w1/375 and w1/377 (done) made a year index a pass-through to a single root. None covers two roots, or an overlay, above a shared intermediate. No open item overlaps.

**Resolved 2026-11-26** — A write with `--file` on a month file under a shared year index is now judged by every ledger above it, shipped in the commit carrying this note (`cli`). `defining_root` and its `first` climb became `defining_roots` (`cli/src/bea_engine/ledger/write.py`): every step branches over that file's `_nearest_includers`, so the w5/933 filter and the overlay stop apply at the index as at the leaf, and the distinct defining tops are collected. A branch that reaches no defining step adds nothing, so one root stays one root. `write_through_root` exits 2 on more than one top; `root_read_hint` and `root_ledger_hints` name every root (the latter with an `--into` recipe per root) instead of one picked by file-name order. The now unused `including_root` is gone. In the note's fixtures, Repro 1's two `add balance` commands and the `update` exit 2 naming `main.bean` and `main-backup.bean` with `jan.bean` unchanged; Repro 2 writes the 100 through `main.bean` with exit 0, refuses the 70 naming `main.bean`, and `main.bean` checks; renaming the backup to `zz-backup.bean` or the overlay to `zforecast.bean` changes neither outcome. `cli/docs/USAGE.md` records the two-roots refusal. Regression tests: `cli/tests/test_year_index_shared_roots.py` (both shapes under both names, the `update`, the hints, and a dead-end pass-through beside the root); the shell-level cases for the original names and `zz-backup.bean` fail with the source change reverted. `test_root_hint_computed_once.py` now counts `_nearest_includers` lookups (still one climb per write).
