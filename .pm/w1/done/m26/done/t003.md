## Objective

A non-UTF-8 `.bean` file in a formatted tree fails with an opaque codec error naming no path, a non-UTF-8 JSON input to `add transactions --from` dumps a raw codec error, and BOM-prefixed JSON is rejected outright even though BOM CSV is accepted.

## Context

- `w3/251`: `bea format -i` on a tree with a non-UTF-8 `.bean` fails with an opaque codec error and no path.
- `w3/283`: `bea add transactions --from` on non-UTF-8 JSON dumps a raw codec error, exit 1.
- `w3/248`: `add transactions --from` rejects UTF-8 BOM JSON while `bea import` accepts BOM CSV.
- m25/t001 establishes the envelope; this task supplies the specific message content.
- Triage 2026-09-17: w3/248 is fixed and tested (`test_transactions_json_bom.py`); w3/251 names the path (`test_format_binary_path.py`) but not the byte offset or re-save hint. Remaining work is w3/283 plus the offset/hint/encoding content.

## Steps

1. Wrap every text read of a caller-supplied file so a decoding failure reports the path, the byte offset, and the encoding attempted.
2. Accept a BOM on JSON input, matching the CSV path.
3. In multi-file operations, name the file that failed to decode and keep the files already processed reported, consistent with m25/t001.
4. Suggest the re-save action in the message.

## Acceptance criteria

- [ ] A non-UTF-8 `.bean` inside a formatted tree fails with its path, byte offset, and attempted encoding named.
- [ ] Non-UTF-8 JSON input fails the same way, with no raw codec traceback.
- [ ] BOM-prefixed JSON input is accepted, matching BOM CSV.
- [ ] Every message is a structured error under `--json`.

## Out of scope

- Guessing or transcoding the input encoding for ledger and JSON files; only CSV gets fallback decoding (m24/t002).
- Rewriting files to fix their encoding.
