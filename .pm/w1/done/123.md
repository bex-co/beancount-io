# An interrupted first-use engine install leaves a ~25 MB `.partial` directory forever

**Severity: minor. Owner: cli. Estimate: ~30m. A1:** disk leaks accumulate on laptops and CI caches. Continuous CLI QA, 2026-10-03 (round 7); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, bea 0.3.1, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`XDG_*`/`BEA_CONFIG_DIR`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with a working control.

Artifact under test: wheel built from `cli/` with `uv build`, installed into a fresh venv (Python 3.12.14, uv 0.12.13) with HOME, XDG dirs, `BEA_CONFIG_DIR` and `UV_CACHE_DIR` inside the run dir; after the first engine install everything ran with `UV_OFFLINE=1`. Package-manager steps were **simulated** with fake `brew`/`uv` executables on PATH.

Send SIGTERM to `bea check` during first-use provisioning: a `0.3.1.partial.<pid>` directory (~25 MB) remains, and the orphaned uv child keeps writing to it. Later runs provision fine but never remove it. Control: SIGINT to the process group cleans up.

Cause: `cli/src/cli/engine/provision.py:89–91` removes only its own pid's partial; the `except BaseException` cleanup doesn't run on SIGTERM/SIGHUP (e.g. closing the terminal).

Fix/acceptance: sweep `*.partial.*` directories whose pid is dead, under the provisioning lock from [120](./120.md). After an interrupted install, the next run leaves no partial directories.

---

**Resolved 2026-10-03** — the next provisioning run now removes `.partial`/`.discarded` engine directories left by interrupted installs whose process is gone, leaving live ones alone. `tests/test_engine_provision_races.py` kills a real provision mid-build. Shipped in the commit that moved this note (`cli`).
