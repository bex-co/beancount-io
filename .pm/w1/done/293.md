# `bea add close` on an account already closed with money in it says "still holds … pass --force", and both remedies it offers are refused

Found by `/qa-find-bugs-cli w1` on 2026-11-19 (HEAD `010cfc4cc`, `bea 0.4.1`, macOS 26.5.1, Python 3.12.14, checkout `uv run bea`, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`). Severity: minor. A1: an agent asked to "close the wallet account" usually runs `add close` without first checking whether the account is already closed. Here the refusal sends it down two dead ends before it learns the one fact that matters.

**Repro** (synthetic). The ledger passes `bea check`: without `check_drained`, Beancount allows a close over a balance, and `bea add close --force` writes exactly this.

```sh
printf 'option "operating_currency" "USD"\n2024-01-01 open Assets:Wallet USD\n2024-01-01 open Equity:Open\n2024-01-02 * "fund"\n  Assets:Wallet 20.00 USD\n  Equity:Open\n2024-02-01 close Assets:Wallet\n' > main.bean
bea --file main.bean check                                                   # exit 0
bea --file main.bean add close --date 2024-03-01 -a Assets:Wallet            # 1
bea --file main.bean add close --date 2024-03-01 -a Assets:Wallet --force    # 2: remedy B
bea --file main.bean add transaction "move out" --date 2024-02-15 -p 'Assets:Wallet -20.00 USD' -p Equity:Open   # 3: remedy A
bea --file main.bean add close --date 2024-01-15 -a Assets:Wallet            # 4: earlier date
```

**Actual.** Each run exits 1 and leaves the file byte-identical.

1. `Assets:Wallet still holds 20.00 USD on 2024-03-01. Move that balance out of Assets:Wallet with a transaction dated on or before 2024-03-01, then close it, or pass --force to close it with the balance.` The output never says that the account is already closed. `--json` gives the same single message, with no details.
2. With `--force`: `Duplicate close directive for Assets:Wallet` / `The proposed close would close Assets:Wallet on 2024-03-01, but it is already closed 2024-02-01 at …/main.bean:7; an account closes once — edit that close's date.` This is the answer run 1 should have given.
3. The suggested move-out transaction is refused: `Invalid reference to inactive account 'Assets:Wallet' … Account closed 2024-02-01 at …/main.bean:7`.
4. The same "still holds" refusal as run 1. Here too, `--force` only reaches the duplicate-close hint.

**Control.** On an account that was drained before its close, the same `add close` runs straight to the w5/773 hint, `already closed 2024-02-01 at …; an account closes once — edit that close's date`. `tests/test_closed_account_hints.py` covers only that case: its fixture moves the money out before the close.

**Expected.** When the requested account already has an explicit close in the ledger as read, `add close` without `--force` gives the w5/773 duplicate-close refusal, naming the existing close and its date and saying to edit that close's date. It does not report the balance, and it suggests neither a move-out transaction nor `--force`. The funded-close refusal keeps its current wording for accounts that are not yet closed.

**Root cause.** `_close` (`cli/src/bea_engine/ledger/adding.py:491`) passes `judge` (line 516) as `validate_append`'s `inspect` hook. `write.py:2604-2605` runs that hook on the candidate entries *before* the candidate's validation errors are classified and hinted. `judge` calls `_funded_close_refusal` (line 465), which raises on the 20.00 USD before the `Duplicate close directive` error and its `_duplicate_close_hint` (`write.py:2980`, `3813`) are ever reached. `--force` returns before `judge` (line 504), which is why only the forced run sees the real reason.

**Fix** (cli only). In `judge`, skip the funded check for `directive.account` when `entries` (the ledger before the write) already holds an explicit `Close` for it, and let validation report the duplicate with its existing hint. Keep the check for descendants that `close_tree` moves (`_moved_closes`). Regressions: an already-closed funded account at a later date and at an earlier date (text and `--json`), the drained control unchanged, and a funded open account still refused with the move-out/`--force` advice.

**Blast radius.** Only `bea add close`. `import` shares `_remaining_balance` through `_funded_close_advisories` (`importing.py`), but CSV/OFX imports never write a close. Hosted writes do not use this path.

**Dedupe.** Searched `.pm/**` for `still holds`, `already closed`, `Duplicate close`, `funded`. w5/773 (done) added the duplicate-close hint but tested only a drained account. w5/888, w5/1062 and w5/1063 (done) shaped `judge`. [blocked/254](./blocked/254.md) asks whether flow accounts (Income/Expenses) should be refused at all. That question is separate: this repro is an Assets account. Estimate: 20–30 minutes.

---

**Resolved 2026-11-19** — Reproduced at `7e0dd303a`: the four runs exited 1 as described, and `--json` carried only the balance message. `_close` (`cli/src/bea_engine/ledger/adding.py`) now skips the funded-close judge when the ledger as read already declares a close for the requested account. A close the close_tree plugin generated does not count, because an explicit close replaces it. Validation then answers with the w5/773 duplicate-close hint (`already closed 2024-02-01 at …; an account closes once — edit that close's date`) at a later or earlier date, in text and `--json`. The answer carries no balance, no move-out and no `--force`. One deviation from the note's fix: the descendants close_tree would move are skipped as well. Before, an earlier second close over a parent with a funded child gave the same "still holds … pass --force" dead end for the child, so the duplicate is the only refusal that holds there too. A funded account not yet closed keeps its move-out/`--force` advice. Regressions in `cli/tests/test_closed_account_hints.py` (five fail with the fix reverted): later and earlier dates in text and `--json`, the close_tree descendant, a child closed only by close_tree (still judged; `--force` writes), and a funded open account. `make check-all` green. Shipped in `1c59da750` (`cli`).
