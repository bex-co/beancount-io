# A comma-decimal bank amount like `0,125` is imported 1000× too large

**Severity: major. Owner: cli. Estimate: 30–45m. A1:** three-decimal currencies and unit prices must import exactly. Continuous CLI QA, 2026-10-03 (round 8); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced twice with a working control.

```sh
printf 'option "operating_currency" "EUR"\n2026-01-01 open Assets:Bank EUR\n2026-01-01 open Income:Zinsen EUR\n' > main.bean
printf 'Date;Description;Amount\n2026-02-01;Zinsen;0,125\n' > lead0.csv
bea --file /abs/main.bean import /abs/lead0.csv --csv date=Date,amount=Amount,narration=Description --account Assets:Bank --default-account Income:Zinsen --apply
```

Actual (any locale): exit 0, preview `125 EUR`, ledger `Assets:Bank 125 EUR` / `Income:Zinsen -125 EUR`; `bea check` passes. Controls: `0,12` → `0.12 EUR`; `0,125` beside `-1,50` in the same column → `0.125 EUR`; a column of only `0,125` and `1,500` → `125` and `1500`.

Expected: `0.125 EUR` (or a refusal). The `w4/done/164` fix says a comma that is "not a valid three-digit thousands group" must not be deleted, and IMPORTING.md resolves the convention from the whole column — a first group of `0` is never valid US/Indian grouping.

Cause: `cli/src/bea_engine/csv_mapper.py:37` `_COMMA_GROUPING` accepts a leading `0` group; `_separator_vote` (`:140–146`, `_COMMA_DECIMAL_TAIL` at `:35`) gives `0,ddd` no vote, so `_resolve_decimal_comma` falls back to point decimals and the branch at `:233–238` strips the comma.

Fix/acceptance: treat an all-zero first group (`\A0+,\d{3}`) as a strong comma-decimal vote and refuse it as point-decimal grouping. `0,125` and `-0,500` import as `0.125`/`-0.500` alone and mixed; `0,125` beside `1,234.56` is refused as mixed conventions; `1,234` alone is unchanged. Regressions in `cli/tests/test_csv_decimal_comma_precision.py`. Applies to `amount=` and `debit=`/`credit=`.

Blast radius: comma-decimal amounts below 1 with exactly three decimals — KWD/BHD/OMR/JOD/TND, unit prices, interest.

Dedupe: gap left by `w4/done/164` (`b0259c1a`), which left arbitrary three-digit inputs unverified.

## Also affected: whole part longer than a thousands group (round 17 fuzzing, 2026-10-03)

A single-comma amount whose whole part can't be US/Indian grouping (`-1613,030`, 4 leading digits) gets no comma-decimal vote either, so the file is refused ("comma decimals like 1.000,00 only when the whole column uses them") even when every cell is comma-decimal; it also fails to rescue its 3-decimal neighbours (`-5,740` beside `-1613,030` should give `-5.740`). Control: the same value spelled `-1.613,030` imports correctly. Widen the fix: in `_separator_vote` (`cli/src/bea_engine/csv_mapper.py:140–146`; `_COMMA_DECIMAL_TAIL` at `:35`), treat a single comma whose whole part fails `_COMMA_GROUPING` (leading `0` group **or** more than 3 leading digits) as a strong comma-decimal vote. Additional acceptance: a column `-1613,030` imports as `-1613.030`; `-5,740` + `-1613,030` → `-5.740` / `-1613.030`; `-1613,030` beside `1,234.56` refused as mixed; `1,234` alone unchanged; same for `debit=`/`credit=`.

---

**Resolved 2026-10-04** — comma-decimal bank amounts whose whole part cannot be a thousands group (`0,125`, `1613,030`) now import exactly, and beside `1,234.56` are refused as mixed. `tests/test_csv_decimal_comma_precision.py` covers it. Shipped in the commit that moved this note (`cli`).
