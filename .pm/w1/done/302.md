# `bea add transactions` writes a same-day custody chain sale-before-transfer: the sale opens a short the transfer then covers, exit 0, and `report capital-gains` says "No sales" for a gain the entry books

**Severity: major** (exit 0 and `bea check` passes, but a realized gain vanishes from the capital-gains report and the register shows a short the user never took). **Owner:** cli. **Estimate:** 30–45m. **A1:** an agent (or the `beancount-trade` skill) that bulk-adds a broker's same-day buy, transfer and sale, listed newest first, gets books whose final balances are right but whose tax report misses the sale.

Found by `/qa-find-bugs-cli w1` on 2026-11-19 (HEAD `2137b4ad9`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, engine served from the checkout with Beancount 3.2.3). Fresh process per command, stdin closed, no TTY, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier off, no `BEA_FILE`/`BEA_TOKEN`, synthetic ledgers. Reproduced twice from a pristine copy, with a working control.

## Actual

`Added 3 transactions`, exit 0; `check` exits 0. The rows are written **Buy into A → Sell from B → Transfer A->B**. The sale now comes before the transfer that supplies its shares. Beancount accepts an explicit-cost sale from an empty account as opening a short, and the transfer then covers it:

```

2025-02-01  Sell from B    -5 HOOL  50 USD (2025-02-01)  -5 HOOL
2025-02-01  Transfer A->B  5 HOOL   50 USD (2025-02-01)  —
```

`report capital-gains` prints `No sales.` (opening a short realizes nothing, and a transfer carries no price; USAGE.md:2079), while `Income:Gains` holds -50 USD. `--partial` and `--json` behave the same (`written: 3`, no notice of the reorder).

## Expected

`cli/docs/USAGE.md:1772`: "within a date a row selling a commodity at cost that another row buys at cost into the same account that day is written after that day's other rows". `:1778`: "a newest-first custody chain … still books whole". The transfer buys HOOL at cost into B that day, so the sale from B is written after it. Every input order above should write Buy → Transfer → Sell, and `capital-gains` should report the one 50 USD sale, as the control does.

## Root cause

`_same_day_purchases_first` (`cli/src/bea_engine/ledger/adding.py:2295`) does two things wrong for a chain:

1. **Its gate reads the input order, then breaks it.** At `:2373`–`:2386` it judges whether each sale "already books in input order" from the lots that earlier input rows bought (`before |= own`). For `Transfer, Sell, Buy` the sale is ungated because the transfer precedes it. The transfer is gated, though: it sells A, which the later Buy supplies. `:2389`–`:2390` then move the gated transfer behind the ungated sale, so the sale loses the lot it was judged to book against.
2. **Moved rows keep their input order** (`:2390`). In the newest-first chain, Sell and Transfer both move behind Buy, but Sell stays ahead of the Transfer that supplies it.

`_booking_order` (`:2159`, loop at `:2205`) then accepts the first candidate that validates. The rule's order validates, because the explicit-cost sale from an empty B opens a short. So neither the input order nor the row-by-row builder (`_built_booking_order`, `:2236`) is ever tried. w5/980's own control noted that an explicit-cost leg "may use a temporary short and still finish with the correct lots". The table above shows the result is not the same booking: the sale is no longer a sale.

## Fix

In `_same_day_purchases_first`, order each day's moved rows by their lot dependencies. A moved row that buys at cost a lot another moved row sells goes before it. A row whose input-order judgement relied on a row that moves must move behind that row too. Keep the existing behaviour everywhere else: a sale that books where it stands stays put, and a deliberate short opened and then covered the same day keeps its order (`test_a_short_opened_then_covered_keeps_its_order`, w5/1079's cover-listed-first case). No change to `bea import`, which does not use this helper.
