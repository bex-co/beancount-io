# `bea add transactions` answers a JSON float written with an exponent (`1.25e1`, `2.5E0`) with "send it as a decimal string, such as '1.25e1'", and sending that string is refused as scientific notation (regression of w5/335 from w5/735)

Found by `/qa-find-bugs-cli w1` on 2026-11-20 (routine cli-qa; HEAD `785e255cc`, checkout `uv run bea` 0.5.0, macOS 26.5, Python 3.12.14, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, synthetic ledger). Severity: minor. A1: an agent that builds bulk rows with a JSON serializer can emit an exponent float (`1.25e1`, `1E+2`). The refusal is right, but its hint names a replacement the next run refuses, so an agent that follows hints loops between two errors. w5/335 fixed exactly this loop; w5/735 (`467119cd3`) brought it back for exponent literals by quoting the literal verbatim.

**Repro** (synthetic, fresh process each step):

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
EOF
printf '[{"date":"2026-03-02","narration":"Lunch","postings":[{"account":"Expenses:Food","units":{"number":1.25e1,"currency":"USD"}},{"account":"Assets:Checking"}]}]' > rows.json
bea --file main.bean add transactions --from rows.json            # exit 1
printf '[{"date":"2026-03-02","narration":"Lunch","postings":[{"account":"Expenses:Food","units":{"number":"1.25e1","currency":"USD"}},{"account":"Assets:Checking"}]}]' > followed.json
bea --file main.bean add transactions --from followed.json        # exit 1
```

**Actual.** The first run says `JSON number 1.25e1 is not supported in Beancount amounts; floats cannot represent decimals exactly. Send the amount as a decimal string, such as '1.25e1'.` The second run, doing exactly that, says `Scientific notation '1.25e1' is not supported in Beancount amounts. Use decimal notation, such as '1000' instead of '1e3'.` The ledger is unchanged both times. The same echo happens for a cost (`"cost":{"number":1.5e1,…}` → `'1.5e1'`), a price (`2.5E0` → `'2.5E0'`), a huge value (`1E400` → `'1E400'`), and untagged metadata (`"meta":{"rate":2.5E0}` → `{"kind":"number","value":"2.5E0"}`, which the tagged-number path refuses for its exponent). Control: `12.50` is told `'12.50'`, and sending that string writes `12.50 USD`.

**Expected.** The hint names a string that the same field accepts on the next run, as w5/335 established and `decimal_string_hint`'s docstring still promises ("a string this same input accepts"). For an exponent literal that is the literal's exact decimal form, which keeps every typed digit: `1.25e1` → `'12.5'`, `1e2` → `'100'`, `-0.5E-1` → `'-0.05'`, `2.5E0` → `'2.5'`.

**Root cause.** `cli/src/bea_engine/amounts.py` `decimal_string_hint` (about line 419) returns `value.literal` unchanged for a `JsonFloat`. w5/735 did that so `1.10` is not told `'1.1'`, but `require_decimal_notation` (same file, about line 443) refuses any string with an exponent. `cli/src/bea_engine/ledger/adding.py` `_untagged_float_problem` (about line 1942) quotes the literal the same way for untagged metadata, and `ledger/write.py` `_exact_metadata_number` (about line 4888) reaches `decimal_string_hint` for tagged metadata. `cli/tests/test_bulk_float_hint.py` (about lines 90–104) asserts the verbatim exponent quote and its refusal on rerun, so the regression is pinned by a test.

**Fix (cli only, local operation; no REST/GraphQL/MCP surface).** For a `JsonFloat` literal with an exponent, suggest `format(Decimal(literal), "f")`. That form is exact, so it keeps w5/735's guarantee that following the hint never changes the amount or its digits. A literal without an exponent keeps being quoted as typed (`12.50` stays `'12.50'`). When the decimal form could not be written either (`1E400`, past the digit limit an amount may hold), offer no replacement, as non-finite values already get none. Apply the same rule in `_untagged_float_problem`.

**Done when** the repro's first run suggests `'12.5'` and sending `"12.5"` writes `Expenses:Food 12.5 USD` with exit 0. The cost, price, tagged-metadata and untagged-metadata cases suggest a value their own field accepts on rerun. `12.50` is still told `'12.50'`. `cli/tests/test_bulk_float_hint.py` asserts that every finite suggestion is accepted on rerun (exponent literals included) and fails with the fix reverted. `make check-all` passes.

**Dedupe.** Searched `.pm/**` for `exponent`, `decimal string, such as`, `JSON number` and `scientific notation` hints. w5/335 (`147be9a9`, the original loop) and w5/735 (`467119cd3`, quoting the literal) are done; this is the gap between them. w5/007, w3/259 and w5/722 cover refusing scientific amounts, not the hint. No open item.

---

**Resolved 2026-11-20** — the hint now names `exact_decimal_form`. A literal without an exponent is still quoted as typed (`12.50` stays `'12.50'`), and an exponent literal is written out exactly (`1.25e1` becomes `'12.5'`, `1.250e1` becomes `'12.50'`). The repro's first run now suggests `'12.5'`, and sending `"12.5"` writes `Expenses:Food  12.5 USD` with exit 0. A value whose decimal form exceeds the 255 characters Beancount's lexer reads (`1E400`, `1e255`) gets no suggestion, as a non-finite value already did. Untagged metadata suggests the same form as a tagged number. `cli/tests/test_bulk_float_hint.py` reruns every finite suggestion on units, cost, price, tagged and untagged metadata, and it fails with the fix reverted. Shipped in `c172d171c` (`cli`).
