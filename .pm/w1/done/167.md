# A refused bulk add without `--partial` reloads the ledger once per row just to build its hint

**Severity: minor. Owner: cli. Estimate: ~45m. A1:** agents batch dozens of rows; a refusal must not take minutes. Continuous CLI QA, 2026-10-03 (round 16); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced twice with a working control. Found by a regression hunt over shipped fixes.

On a 60k-transaction ledger (4.5 MB, ~5 s per load), a JSON batch of 10 valid rows plus 1 row posting to `Expenses:Nope`:

```sh
bea --file /abs/big.beancount add transactions --from /abs/b.json
```

Actual: exit 1 after **66.0 s** ("Pass --partial to append the 10 valid rows."); 2 rows take 17.8 s, a lone bad row 12.4 s. Control: a successful 10-row batch takes 11.1 s. Cost grows ~5.5 s per row, so ~20+ rows exceed two minutes just to refuse.

Cause: `cli/src/bea_engine/ledger/adding.py:813–834` — the `if not partial:` branch runs `write.validate_append` per row (a full candidate load each, no pickle cache) only to count recoverable rows. From `4d54bed8` (`w3/315`).

Fix/acceptance: derive the count from the single batch load (map error lines back to rows) or word the hint without a count. A refusal of N rows without `--partial` does at most 2 full loads; `w3/315` tests still pass.

---

**Resolved 2026-10-04** — refusing an invalid bulk batch without `--partial` now takes at most two ledger loads, mapping error lines back to rows instead of reloading once per row to build the hint. `tests/test_bulk_refusal_load_count.py` counts loads. Shipped in the commit that moved this note (`cli`).
