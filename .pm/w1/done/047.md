# `bea list transaction` crashes on any ledger containing a posting-less transaction (regression of w3/261)

**Severity: major. Owner: cli. Estimate: 20–30m. A1:** a valid ledger must stay listable by agents. Continuous CLI QA, 2026-10-02; report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`, synthetic fixtures. Reproduced twice from pristine fixtures.

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-03-01 * "Reminder" "renew passport" #todo
```

```sh
bea --file /abs/main.bean check                         # exit 0
bea --file /abs/main.bean list transaction              # exit 1
bea --json --file /abs/main.bean list transaction --tag todo
```

Actual: `list` exits **1** with `Error: 1 validation error for TransactionDirective postings List should have at least 1 item after validation, not 0 [type=too_short …]` (JSON: `category: validation`), so the whole ledger becomes unlistable. BQL `query` and `add` still work. Re-verified independently by the filer.

Expected: Beancount accepts posting-less transactions (`bea check` passes), and `w3/done/261`'s own repro shows `list` returning `postings: []`.

Cause: the `w3/261` fix (`a95a28cf`) set `TransactionDirective.postings = Field(min_length=1)` at `cli/src/bea_engine/ledger/models.py:218`; the reader builds the same model for every loaded entry at `cli/src/bea_engine/ledger/reader.py:182`.

Fix/acceptance: enforce min-length only on bulk input (validate the input array in `add transactions`, or give the reader an unconstrained read model). The repro lists the row with `postings: []`; bulk `postings: []` is still refused (`tests/test_bulk_empty_postings.py`). Regression test for listing a posting-less transaction. Run `make check-all`.

Dedupe: `.pm` search for too_short / empty postings / min_length → only `w3/done/261`; this is its regression. `git log -S"min_length=1"` → `a95a28cf`.

Independent corroboration (same HEAD): two fresh-process repetitions using a valid seed plus `2025-05-01 * "annotation"` reproduced JSON/human listing failure, including `--allow-errors` and `--search annotation --details`. `check`, `query PRINT`, and `report overview` all succeed. `--sort oldest --limit 1` succeeds when the empty row lies beyond that limit, isolating construction of that row as the trigger. Captures and public-safe driver are `cli/tmp/qa-20261002-loop/captures.jsonl` and `empty_transaction.py`; every read leaves the file unchanged. The same model error masks the actual loader diagnostic for insufficient lots when booking produces an empty transaction (observed separately in `invalid_reads.py`); preserve ordinary strict loader failures and explicitly permitted partial reads when separating read and write validation.

---

**Resolved 2026-10-03** — `bea list transaction` reads loaded rows through `TransactionHeader` (no at-least-one-posting rule), so a ledger with a posting-less transaction lists it with `postings: []`; bulk `add transactions` still refuses empty postings through `TransactionDirective`, and a transaction emptied by booking now reports the loader's own diagnostic instead of a model validation error. `tests/test_list_postingless_transaction.py` covers both. Shipped in the commit that moved this note (`cli`).
