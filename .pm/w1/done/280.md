# `bea import` tells a row whose own currency column says EUR to "name the row's commodity with --csv currency=CODE", and following it books 50 EUR as 50 USD

Found by `/qa-find-bugs-cli w1` on 2026-11-17 (HEAD `c1e285d3a`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, frontend and engine Python 3.12.14, stdin closed, no TTY, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`). Severity: minor (the first run writes nothing; the advice it prints, followed as written, records the wrong money). A1: an agent clearing a blocked import follows the printed fix. Here that fix relabels a euro charge as dollars, exits 0, and passes `bea check`.

**Repro** (a fresh directory):

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Bank:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Equity:Opening-Balances USD
EOF
cat > bank.csv <<'EOF'
Date,Description,Debit,Credit,Currency
2026-01-15,Coffee,4.50,,USD
2026-01-16,Paycheck,,100.00,USD
2026-01-17,Hotel,50.00,,EUR
EOF
bea --file main.bean import bank.csv --csv auto --account Assets:Bank:Checking
bea --file main.bean import bank.csv --csv date=Date,debit=Debit,credit=Credit,narration=Description,currency=USD --account Assets:Bank:Checking
```

**Actual:**

1. The header read maps `currency=Currency`. Row 3 is `blocked`: `Cannot post EUR to 'Assets:Bank:Checking' (open for USD only). Post USD instead — name the row's commodity with --csv currency=CODE — or add EUR to its open directive.` Exit 0. `--apply` exits 4 and writes nothing, which is correct.
2. Following that advice prints `currency=USD names no column of bank.csv, so every row posts in USD.`, and row 3 becomes `ready` as `Assets:Bank:Checking -50.00 USD`. Exit 0. `--apply` writes it. Nothing says that the file's own `Currency` column named EUR for that row.

Reproduced in fresh processes from a pristine ledger.

**Expected:** if the row's commodity comes from a mapped currency column, the export itself states the currency. In that case `currency=CODE` is not a fix: it relabels foreign money, the same harm the code comment beside the hint gives as the reason widening the `open` comes last. The reason should name the column and the row's currency, then point at an account open for that currency (`--account`, or split the export) before it offers widening the `open`. Example: `The export's Currency column names EUR for this row; import EUR rows into an account open for EUR with --account, or add EUR to its open directive.` The `currency=CODE` advice stays for rows whose commodity came from the account's single currency or the operating currency (the w3/421 and w5/318 control: no currency column).

**Root cause:** `_blocked_reason` in `cli/src/bea_engine/importing.py` (source-account branch, about line 2913) chooses its remedy from only whether the blocked account is the CSV run's `source`. Where the row's currency came from is not passed in, so a currency read from a mapped column gets the same `--csv currency=CODE` advice as a fallback currency. The caller at about line 811 passes `source=account if nocode_mode else None`. It also needs to say whether the mapping reads the currency from a column, and which column.

**Fix:** pass the currency column (or None) from the CSV mapping into `_blocked_reason`. When the row's currency came from that column, word the source-account remedy as above. Keep the reason identical in text and in the JSON `reason`. Update `cli/docs/IMPORTING.md` ("A currency mismatch offers a fix the run can apply first…") to say the column case differs. Add a regression test next to `cli/tests/test_import_currency_mismatch_remedy.py` that drives the repro through JSON and asserts the column case never offers `currency=` and the no-column control still does. Revert the fix and watch it fail.

**Dedupe:** w5/318 (the hint for a Python importer and for a category account), w5/841 and w5/874 (an empty ledger and an unrestricted account), w5/1021 (an amount column headed with a commodity) and w3/421 (the order currencies are resolved in) all keep `currency=CODE` for the source account. None covers a currency that comes from the file's own column. No open item overlaps.

---

**Resolved 2026-11-17** — `_blocked_reason` now learns, per row, which mapped CSV column named the row's commodity. When the column did, a source-account currency mismatch names that column and the row's currency, then points at an account open for that currency with `--account` before it offers widening the `open`; it no longer offers `--csv currency=CODE`. Rows whose commodity is a fallback (no column, or a blank cell) keep that advice. The repro's row 3 now reads `The export's Currency column names EUR for this row; import EUR rows into an account open for EUR with --account, or add EUR to its open directive.` `cli/docs/IMPORTING.md` describes the column case. Regression tests are in `cli/tests/test_import_currency_mismatch_remedy.py`. Shipped in `0d9f4fc72` (`cli`).
