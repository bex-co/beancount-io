# A 1000-entry `deleteEntrySources` batch overruns the write deadline, commits, and says "retry"

**Bug · ledger + backend-v2 · major · ~45m · A1.** From `/qa-find-bugs-mcp`, 2026-11-10, production `beancount-mcp 1.0.0`. The disposable QA ledger held 1000 byte-identical QA transactions with hashes `h … h:999`.

The documented cap is "at most 1000 entries per call". At that size an agent is told to retry a delete that has already landed. On larger ledgers much smaller batches hit the same wall.

- **Repro:**
  - `addLedgerEntries` with 1000 entries commits in 6.4s. The hashes are unique, and `getEntryContext` resolves `h:999`.
  - `deleteEntrySources` dry runs of the first N hashes slow down linearly, about 65ms per entry on this file:

    | N | Time |
    | --- | --- |
    | 50 | 4.0s |
    | 200 | 13s |
    | 500 | 31s |
    | 1000 | 68s |

  - Committing the delete of all 1000 returns, after 91.8s, `SERVICE_UNAVAILABLE` "Ledger API is temporarily unavailable" with the hint "A dependency is down. Retry with backoff; this is not a problem with the request." The delete had landed: the BQL count is 0 and the latest commit is "Delete entries".
  - **Control:** a 1000-entry add (6.4s) and a 1000-posting transaction (6s) stay well inside the deadline.
- **Cause:**
  - In the ledger, `ledger-journal-service.ts:1137-1149` (`deleteMultiSourceSlices`) calls `locateSlice` once per entry.
  - `locateSlice` (`:595-612`) goes through `findEntrySliceAsync` (`source-slice-worker.ts:6-11`). That hands the whole FileMap to a worker, which re-parses it for every hash. The cost is O(entries × ledger size), and the snapshot already parsed at `:1129` is never reused.
  - The 90s write deadline is `FAVA_WRITE_TIMEOUT_MS`.
- **Fix (ledger):** locate every requested slice from one parse, either as a single worker task that takes the hash list or from the snapshot parsed at `:1129`. Keep the per-entry sha check and the all-or-nothing refusal.
- **Fix (backend-v2):**
  - Until the ledger fix lands, lower the delete cap to what fits the deadline on a realistic ledger, or document the size bound.
  - Consider adding `requestId` to `deleteEntrySources`, as entry adds have, so a timed-out delete can be retried safely.
  - The timeout-specific hint ("A write may already have committed…", 656d251d3) is on `main` but not deployed.
- **Check:** a 1000-hash batch on a 1000-entry ledger finishes well under 30s.
- **Blast radius:** MCP `deleteEntrySources`, REST `POST …/entry-source/delete-many` and GraphQL `deleteMultipleLedgerEntrySourceSlices` share the service. Dry runs are affected too.

**Addendum 2026-11-10 (scale sweep):** the same batch delete has a second per-item whole-file loop, so fixing only `locateSlice` won't make it linear.
- **Where:**
  - `sliceTarget` runs `countShaMatches` for every target (`ledger-journal-service.ts:180`).
  - The commit transform `makeDeleteTransform` calls `relocateSlice` per target (`:237-238`). That runs `countShaMatches` again (`:203`) and then `findEntrySliceBySourceSha` (`source-slice.ts:513-527`).
  - Each of these splits the whole file and sha256-hashes every dated block, so a batch of N costs about 3·N·blocks hashes on top of the N re-parses.
- **Fix:** build one block-to-sha index per file once and share it across all targets.
- **Measured on production, 2026-11-10:** single-entry and single-file writes stayed under about 11 s up to about 8,000 transactions (1.2 MB) and grow linearly. No other per-item parse loop exists in the journal service, repo service or file-edit tool. By linear extrapolation, single-entry commits would approach about 40 s around 4 MB. That is an inference, not a measurement.

**Resolved 2026-11-10.** A batch delete now does one parse for the whole batch, and hashes each file revision once.
- **One lookup:** the worker task is now a batch (`find-entry-slices`): `findEntrySlicesWithFullLedger` resolves every hash from one full-ledger parse and one scan per file. `deleteMultiSourceSlices` locates the whole batch through `locateSlices`, with the per-entry sha check, the managed-path refusal and the all-or-nothing order unchanged. The single-entry paths go through the same task with one hash.
- **One index per file revision:** `indexDatedBlocks` (`source-slice.ts`) hashes each dated block once, indexed by start line and by source sha in file order. `sliceTarget` reads twin counts from the index of the snapshot. The delete transform relocates every target from one index of the fresh content (`relocateSlices`). Both used to split and hash the whole file per target. `entrySliceFromSourceLocation` and `findEntrySliceBySourceSha` use the same index. The twin-count CAS refusals are unchanged.
- **Measured:** a 1,000-entry dry run on a 1,000-entry ledger takes about 0.16 s on the live engine, where the old code took 4.3 s on the same fixture; the note measured 68 s on production.
- **Tests:**
  - `batch-delete-scale.test.ts`, 300 entries: one lookup for the batch, and SHA-256 work bounded by a few passes over the file rather than about 270,000 hashes. A stale sha, or an unknown hash, still refuses the whole batch. With the old journal service it fails on the lookup count.
  - `yarn verify:rustledger` runs the 1,000-entry dry run against a 3 s budget (`scripts/batch-delete-scale.ts`).
  - The six service tests that mock the slice worker gained the batch entry point, and the pool test pins one task for a batch.
- **Not done:** the backend-v2 interim cap is moot once this deploys. `requestId` on `deleteEntrySources` (the note's "consider") is not added. The deadline hint `656d251d3` is a deploy question. (`ledger`)
