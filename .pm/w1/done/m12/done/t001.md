## Objective

Produce a definitive mapping from each GraphQL operation the CLI uses today to its v1 REST equivalent in `backend-cluster/idl/`, and a gap list of endpoints that do not exist yet. This scopes t002 precisely — expected gap: the CLI auth-session flow.

## Context

- Current operations (from `cli/src/cli/api/gql_client/`): `createCliAuthSession`, `getCliAuthSession`, `consumeCliAuthSession`, `logout`, `getCurrentUser`, `listLedgers`, `getLedger`, `createLedger`, `deleteLedger` (clone uses `getLedger`).
- REST contract: the v1 OpenAPI spec in `backend-cluster/idl/`, kept honest by the backend parity gate and the `yarn generate-v1-openapi` snapshot drift check.

## Steps

1. List every operation in `cli/graphql/operations/` and confirm the set above is complete.
2. For each, locate the corresponding path + method in the v1 spec; record `operationId`, auth requirements, and payload differences.
3. Write the mapping table plus the gap list into this task file (update it in place) so t002 and t005 work from one source.

Gap list for t002:

1. REST endpoints for the CLI auth-session device flow: create session, read session status by device code, consume session for a token (all pre-auth), plus token revocation (logout, bearer-auth).
2. Typed response schemas for ledger list and ledger get (LedgerInfo shape: id, name, fullName, sshUrl, httpUrl, private, empty, createdAt, updatedAt at minimum).
3. `operationId`s: **no v1 operation has one** — generators fall back to path-derived names; add mechanical operationIds in `scripts/generate-v1-openapi.ts` if cheap, else name only the CLI-consumed operations.

REST-vs-GraphQL shape notes for t005: REST addresses ledgers as `{owner}/{name}` directly, so `full_name_to_ledger_id` conversion becomes unnecessary; auth uses the same bearer token (`bearerAuth` scheme).
