## Objective

When `SELF_HOST` is on and `EXTERNAL_GITEA_HOST_NAME` is unset, the API learns the external Git host from the deployment itself and never falls back to `git.beancount.io`.

## Context

- `backend-cluster/backend-v2/src/config/config.ts` (`gitea.hostname`: `process.env.EXTERNAL_GITEA_HOST_NAME || DEFAULT_EXTERNAL_GITEA_HOST`).
- `src/shared/gitea-utils.ts` `generateGiteaUrl` builds `sshUrl`/`httpUrl`; callers include `src/features/ledger/utils/mappers.ts`, `operations/create-ledger.ts`, `ai-agent/workflow/sandbox-agent-workflow.ts`, `scheduler/jobs/ai-health-check-job.ts`.
- w22/007 (`cd730fc90`) solved the same problem for pull-request links by using Gitea's own `html_url` (built from its `ROOT_URL`, which the bex wrapper derives). Reuse that source of truth rather than inventing a new variable.
- `bex.yaml` deliberately sets no hostname; the Docker targets set `EXTERNAL_GITEA_HOST_NAME` from `GIT_DOMAIN`.

## Steps

1. Choose the smallest reliable source for the external host (Gitea's reported root URL, read once and cached, is the expected one).
2. Apply it only when `SELF_HOST` is on and the host is the built-in default; an operator's explicit value and the managed service are unchanged.
3. If no host can be learned, fail loudly at the call (or omit the URL) rather than emit `git.beancount.io`.

## Files

- `backend-cluster/backend-v2/src/config/config.ts`
- `backend-cluster/backend-v2/src/shared/gitea-utils.ts` and its test

## Acceptance criteria

- [x] A self-hosted config with no `EXTERNAL_GITEA_HOST_NAME` never produces a `git.beancount.io` address (unit test).
- [x] An explicit `EXTERNAL_GITEA_HOST_NAME`, and a non-`SELF_HOST` config, produce the same addresses as before (unit tests).
