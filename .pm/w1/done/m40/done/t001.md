## Objective

`changePlan` applies a downgrade, a switch to monthly and the "monthly at renewal" half of a split choice as a Subscription Schedule. The current phase runs to the period end and the next phase holds the new price. It returns `SCHEDULED` with `effectiveAt`, and charges nothing today.

## Context

- m39/t001 previews these kinds with `effectiveAt` and nothing due; m39/t002 refuses them until this task lands.
- Tier comes from the subscription's current price (`backend-cluster/backend-v2/src/features/stripe/service/subscription-plan.ts`). When the phase starts, the `customer.subscription.updated` webhook changes the limits with no extra code.
- Stripe: `subscriptionSchedules.create({ from_subscription })`, then update its phases.
- Rule from PRFAQ005 question 14: gains now, losses at period end; nothing is refunded.

## Steps

1. Create a schedule from the subscription, or update the existing one. Keep the current phase until the period end, then the new price.
2. Return `SCHEDULED` with the effective date. Refuse legacy prices as targets.
3. Confirm the webhook path resolves the new tier at the phase change, and that renewal caches update only the matching binding (w1/m37 rule).

## Implementation notes

- **Stripe behaviour, checked in test mode** on API `2025-12-15.clover` before writing the code, with throwaway objects that were deleted or archived afterwards:
  - A schedule made `from_subscription` has one phase, the current price to the period end. Giving it a second phase (`end_behavior: release`, `proration_behavior: none`) creates no invoice, and the next invoice bills the new price.
  - Discounts carry by the subscription's discount ids. Passing the coupon instead starts a new discount, which would restart a limited one.
  - While a schedule is attached, Stripe refuses a direct cancellation, but accepts a direct price change that the schedule then undoes at renewal.
  - Scheduling a subscription whose cancellation is pending withdraws the cancellation.
  - Releasing a schedule keeps the subscription's current price and discounts.
- **Scheduling** (`operations/plan-change-schedule.ts`):
  - `changePlan` schedules `DOWNGRADE`, `TO_MONTHLY` and `SPLIT` (its monthly-at-renewal half) as a two-phase schedule. Phase one keeps every item and quantity to the period end; phase two swaps the plan item to the target for one interval. Both phases keep the same discounts. It returns `SCHEDULED` with `effectiveAt` and charges nothing.
  - A schedule already attached has its phases replaced, so a subscription never holds two. Only Stripe's invalid-request error counts as a lost race (a concurrent confirm attached one first) and is recovered; a network failure is not.
  - Subscriptions are read with the schedule expanded, so its status and phase cost no extra request.
- **Release before every other change**:
  - An immediate change releases any attached schedule first, so renewal cannot undo the upgrade.
  - It cannot wait for the outcome. A payment the bank must approve, or one that failed, leaves Stripe holding the update, and paying the invoice later still applies it; a schedule restored meanwhile would revert it at renewal.
  - The scheduled change is therefore replaced at confirm time, and the preview must say so (t002's `replacesScheduledChange`).
  - `cancelSubscription` and the account-deletion cancel do the same, because Stripe refuses a cancellation otherwise.
  - This is the minimum t002 builds on (status, undo, replacement flags). t002 must also tell the reader that a change withdraws a pending cancellation; today that happens silently.
- **Retired prices**: `PlanConfig.retired` marks prices never offered again. Today that is the $9.99 monthly, because the $99.99 yearly is still sold.
  - Preview and apply share `resolveTargetPlan`, which refuses a retired target before any Stripe call.
  - A split's same-tier alternative skips retired prices too.
  - Checkout is unchanged, so the pricing page keeps working.
- **Legacy mutation**: `upgradeSubscription` stays immediate-only (an `immediateOnly` apply option). It refuses an end-of-period change as `SCHEDULED_CHANGE` instead of quietly scheduling it under a failure result, and reports a retired price's validation message.
- **API**:
  - `PlanChangeStatus` gains `SCHEDULED`, and `PlanChangeResult` gains `effectiveAt`. The dashboard schema copy and the generated types are updated; the dashboard still shows "coming soon" for scheduled kinds until t007.
  - Preview and apply both take the effective date from the current period end.
- **Phase change**: when the scheduled phase starts, `customer.subscription.updated` refreshes the matching binding from the subscription's new price. The webhook test covers this with the schedule still attached.
