## Objective

Implement PRFAQ005 question 21 decision 1. A `past_due` subscription keeps its paid tier until Stripe stops retrying and moves it on. Status exposes `past_due`, the failing card and the open invoice's next payment attempt for the banner. A Stripe lookup failure uses the last verified tier instead of Free.

## Context

- `subscriptionTier` returns Free for any status but `active` (`backend-cluster/backend-v2/src/features/stripe/service/subscription-plan.ts:17`).
- Since `ef3d197bd`, a verified paid-period cache (`periodVerificationVersion`, `SUBSCRIPTION_PERIOD_VERIFICATION_VERSION`, `paidCustomer.updatePeriodIfUnchanged`) answers `hasActiveSubscription` without Stripe. It records that a paid period exists, not which tier it is.
  - Treating `past_due` as paid must agree on the cached path and the live path.
  - Changing what counts as a verified paid period means bumping the verification version.
  - A Stripe-error fallback to the last verified tier needs that tier stored with the verified period.
- `getUserTier` lists only `status: "active"` subscriptions and returns Free on any error (`backend-cluster/backend-v2/src/features/stripe/operations/get-user-tier.ts`).
- Quotas, the account profile used by the CLI, API-key minting and the entry cap all read `getUserTier`.
- `subscriptionStatus.hasActiveSubscription` is computed from the same tier (`subscription-service.ts`), and the pricing page reads it to choose between Checkout and "Manage subscription". Counting `past_due` as paid deliberately makes it true for such a subscriber, so the pricing page stops offering a second subscription.
- w1/m37 kept the active-status policy out of its scope. This task changes it for `past_due` only, by the user's decision of 2026-10-17. Trials, `unpaid` and `canceled` keep today's behaviour.
- Stripe exposes the next attempt; the date the retries end comes from the account's retry settings (t006). Show the next attempt, unless t006 records a rule that derives the final date.

## Steps

1. Treat `past_due` as paid in tier resolution and subscription listing.
2. Add the past-due state, card and next attempt to status.
3. On a Stripe lookup error, use the last verified paid tier when one is recorded and log the fallback. Record the tier with the verified period, and bump the verification version if the rule changes. Without a verified record, keep today's behaviour.

## Implementation notes

- **Paid statuses**: `holdsPaidTier` (`service/subscription-plan.ts`) counts `active`, and `past_due` only while its latest invoice is open with a `next_payment_attempt` (`pastDueRetry`).
  - The grace therefore ends with Stripe's last retry even if the account leaves subscriptions past due afterwards (t006 is unconfirmed).
  - `unpaid`, `canceled`, trials and incomplete subscriptions resolve to Free as before.
  - One rule drives tier resolution, the verified period cache and plan changes. Tier listings expand `data.latest_invoice` in the same request.
- **Past-due period is not paid**: for a past-due subscription the cached period end is capped at the next retry. Neither the status cache nor the outage fallback can outlive the grace, even if the final webhook is lost.
- **No plan changes while past due**: preview and apply refuse with `PAST_DUE`, before any Stripe write, and point at updating the payment method. A change would otherwise charge the failing card, or credit "unused" time in a period that was never paid. Dashboard copy in 15 locales names each locale's own Manage billing label.
- **Listing**: tier lookups, period refreshes (webhooks and the active-only status read), the second-Checkout guard and plan changes list the customer's subscriptions with Stripe's default filter (`status: "current"`: everything not canceled), then apply `holdsPaidTier`. A past-due subscription is included without paging through canceled history.
- **Cache**: `SUBSCRIPTION_PERIOD_VERIFICATION_VERSION` is now 2, because the rule changed.
  - A verified period now stores the tier it paid for (`paid_customers.period_tier`, migration `0022`). It is rewritten when only the tier moves, and cleared with any unverified write.
  - Old caches re-read Stripe once.
  - `hasActiveSubscription` is true for `past_due` on both the cached and live paths, because a past-due renewal keeps its advanced period; `unpaid` and `canceled` clear it.
- **Stripe outage**:
  - `getUserTier` falls back to `lastVerifiedTier` (the highest tier of a still-current, current-version verified period on the billing client) and logs it. It does so only for transient Stripe errors (connection, API, rate limit); our own binding check and any other error stay Free.
  - Without such a record, or if reading it fails, the result is Free as today.
  - The seven callers (quotas, account profile and CLI, API keys, the entry cap, ledgers, collaborators, AI usage) are unchanged.
- **Banner data**: the full status view lists with the schedule and latest invoice expanded (`expandForStatus`). A `past_due` subscription reports `nextPaymentAttempt` from its open invoice, beside the existing `paymentMethod` card. The dashboard schema copy has the field; the banner is t009.
- **Repair scripts**: `billing-repair-store` clears `period_tier` with any unverified period write. `reconcile-billing-core` uses `holdsPaidTier`.
- **Follow-up**: version-1 rows are re-verified only by a webhook or a status read, so the outage fallback covers each subscriber from their next such event. A reconcile backfill would cover everyone at once.
