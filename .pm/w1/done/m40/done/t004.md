## Objective

Fix the two limit-check bugs PRFAQ005 question 21 item 6 records.

## Context

- **Ledger count** (`backend-cluster/backend-v2/src/features/ledger/operations/create-ledger.ts:71–96`): counts the owner's ledgers among only the first 10 the ledger service lists (`limit: 10`). So it can never fire at Growth's 20 or Organization's 100. The mobile skip (`platform !== "mobile"`) is intended and stays.
- **Collaborators** (`backend-cluster/backend-v2/src/features/ledger/workflow/ledger-collaborators-workflow.ts:136–160`): uses the plan of whoever adds the collaborator, not the ledger owner's. It throws an internal server error that always says "Upgrade to PREMIUM".
- Both paths serve GraphQL, REST and MCP, so the error must render consistently on all three (root `AGENTS.md` parity rule). The dashboard already maps `RESOURCE_LIMIT_REACHED` to a localized message (`dashboard/src/common/lib/errors/error-message.ts`) and has a collaborator-limit indicator. Check that the new error reaches both.

## Steps

1. Count every ledger the owner owns, by paginating the list or querying by owner, independent of collaborated ledgers and list order.
2. Resolve the ledger owner's tier for the collaborator limit. Raise the resource-limit error ledger creation uses, naming the owner's plan and limit.
3. Check the GraphQL, REST and MCP error envelopes for both refusals.

## Files

- `backend-cluster/backend-v2/src/features/ledger/operations/create-ledger.ts`, `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-collaborators-workflow.ts`

- [x] Both refusals are resource-limit errors on GraphQL, REST and MCP, and the parity gate passes.

## Outcome — 2026-10-18

**Bugs fixed** (two recorded in PRFAQ005, three found here):
- **Ledger count past the first page.** It counted the owner's ledgers among the first ten repositories the caller could see, so it never fired at Growth's 20 or Organization's 100. It now reads the owner's own ledger list (`listUserLedgers`, Gitea's per-user list), every page. Collaborated and organization ledgers never count, and letter case cannot hide one.
- **Collaborator limit by owner.** The limit is the ledger owner's plan, found through the owner's account. An admin on Growth adding to a Free owner's ledger is held to Free's limit.
  - A ledger no account owns, such as an organization's, falls back to the acting user's plan, and logs that it did.
  - The refusal is a `ResourceLimitReachedError` naming the owner's plan, not an internal error saying "Upgrade to PREMIUM".
- **Unlimited tiers were always refused.** `count >= -1` is always true, so on the web Enterprise could never create a ledger, and Enterprise ledgers could never take a new collaborator. Both checks now skip an unlimited tier without listing anything.
- **Profile `ledgersUsed`** asked for one page of 100, which Gitea clamps to 50. It now uses the same owner count, alongside the tier lookup. A count failure is logged and reported as 0, so the profile still loads.
- **Collaborator check hardened:**
  - every page of the collaborator list is read;
  - a list that cannot be read refuses the change instead of silently skipping the limit;
  - logins compare case-insensitively;
  - changing an existing collaborator's permission never counts.

**Shared code:**
- `src/shared/gitea-pages.ts` (`readGiteaPages`, `GITEA_PAGE_SIZE`) is the one Gitea pager. It carries the explanation of `MAX_RESPONSE_ITEMS` and the page-cap warning. The ledger catalog's `readCatalogWindow` now uses it.
- `operations/owned-ledgers.ts` is used by ledger creation and the profile.
- `TIER_DISPLAY_NAMES` names plans in messages.
