# Bulk dates accept numeric strings as Unix timestamps and other non-ISO spellings

**Severity: minor. Owner: cli. Estimate: 20–30m. A1:** a date typo must never silently become a different date. Continuous CLI QA, 2026-10-03 (round 6); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1 (Beancount 3.2.3), Python 3.13, macOS 26.5.1 arm64. Fresh process per command, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed unless piping JSON. Reproduced twice with a working control; compared against native `bean-check`/`bean-query`.

`"date":"1769904000"` (and `"1769904000000"`) exits 0 and writes `2026-02-01`; `"20260201"` gives the misleading "Datetimes provided to dates should have zero time"; `"0"` becomes 1970-01-01; `"2026-02-01 00:00"` and `"…T00:00:00+05:00"` are accepted. Meta `{"kind":"date","value":"2026-W05-7"}` and `"20260201"` pass `fromisoformat`. Control: `bea add transaction --date 1769904000` exits 2 `Use YYYY-MM-DD format`.

Cause: `_require_calendar_date` (`cli/src/bea_engine/ledger/models.py:33–41`) rejects only numeric JSON types, so numeric strings reach Pydantic's timestamp parsing; meta dates via `write.py:901`. (`Cost.date` is covered in [108](./108.md).)

Fix/acceptance: require a strict `YYYY-MM-DD` string (regex then `date.fromisoformat`) for the transaction date and kind:date meta; every case above exits 1 with row and field path.

Dedupe: `w3/245` handled numeric JSON values only.

## Also affected: single-date flags (round 8, 2026-10-03)

The frontend `parse_date` shares the gap, so this note's "working control" holds only for Unix-timestamp strings. `bea --no-input init /abs/i.bean --currency USD --date 2026-W01-1` exits 0 and writes `2025-12-29 open …` (books start in the previous year); `--date 20260102` writes `2026-01-02`; `add transaction … --date 2026-W53-4` writes `2026-12-31`; `list transaction --from-date 20261231 --to-date 2026-W53-4` is accepted. Controls `2026-365` and `2026-12-31T10:00` are refused with "Use YYYY-MM-DD format". Cause: `cli/src/cli/utils.py:154–158` uses `date.fromisoformat`, which accepts ISO basic and week dates on Python ≥ 3.11; callers `init.py:139`, `add.py:146–473` (including `--meta date:` at `:473`), `list.py:405–537`. Extend the fix with a strict `^\d{4}-\d{2}-\d{2}$` check there; every spelling above exits 2 and writes nothing.

---

**Resolved 2026-10-04** — bulk row and cost dates, tagged date metadata and every `--date`-style flag now accept only `YYYY-MM-DD`; numeric timestamps, ISO basic and week dates are refused. `tests/test_strict_iso_dates.py` covers each path. Shipped in the commit that moved this note (`cli`).
