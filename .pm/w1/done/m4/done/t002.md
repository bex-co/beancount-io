## Objective

Make every server-relative mobile request resolve against the hydrated runtime selection so switching servers does not require rebuilding or restarting the app.

## Context

- `mobile/src/common/request.ts` builds relative endpoints from `config.serverUrl`.
- `mobile/src/common/apollo/client.ts` captures the GraphQL URI when its module initializes.
- `mobile/src/screens/welcome/login-web-view.tsx` uses `getEndpoint()` for `/auth/login` and `/auth/sign-up` and then queries the selected server after receiving its token.
- Hard-coded hosted URLs must be reviewed intentionally: some may be Beancount.io marketing/referral destinations rather than API traffic.

## Steps

1. Make `getEndpoint()` read the current selected base URL and preserve any supported base pathname.
2. Change Apollo transport construction so each operation uses the current server, or safely recreate the client after the persisted value hydrates/changes.
3. Audit mobile GraphQL, REST, WebView auth, download, upload, and agent request paths for direct hosted URLs; route server-owned endpoints through the common resolver.
4. Keep genuinely hosted-only marketing/referral destinations explicit and document why they do not follow a custom server.

## Files

- `mobile/src/common/request.ts`
- `mobile/src/common/apollo/client.ts`
- `mobile/src/screens/welcome/login-web-view.tsx`
- `mobile/src/common/referral-url.ts`
- Other mobile request consumers found by the endpoint audit.

## Acceptance criteria

- [ ] Sign-in and sign-up WebViews open on the selected server.
- [ ] GraphQL and app-owned REST traffic resolves against the selected server after hydration and after an in-app change.
- [ ] No API request remains accidentally pinned to `beancount.io`.
- [ ] The default hosted flow behaves exactly as before.

## Out of scope

- Supporting servers that do not implement the Beancount.io auth and API contract.
