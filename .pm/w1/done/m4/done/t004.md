## Objective

Help users distinguish malformed, unavailable, and incompatible server URLs before attempting authentication, without making online validation a prerequisite for saving configuration.

## Context

- A compatible backend exposes the unauthenticated GraphQL `health` query at `/api-gateway/`; checking only that a host returns HTTP 200 is not enough to establish compatibility.
- Mobile users may configure a server while offline, behind a VPN, or before local DNS is available, so the test must remain advisory.
- Custom hostnames are user configuration and must not be attached to analytics, Sentry breadcrumbs, or public logs.

## Steps

1. Add a bounded-time unauthenticated compatibility probe against the candidate URL without first persisting it.
2. Present distinct results for connected/compatible, malformed URL, timeout/unreachable, TLS/cleartext rejection, and reachable but incompatible API.
3. Keep Save available for syntactically valid URLs when the probe fails, with clear language that login may not work until the server is reachable.
4. Ensure errors avoid echoing credentials or sensitive URL components and that analytics record at most a coarse success/failure category, never the hostname.

## Files

- `mobile/src/screens/welcome/`
- `mobile/src/common/request.ts` or a focused server-connection helper.
- `mobile/src/translations/en.ts`

## Acceptance criteria

- [ ] Test connection succeeds only when the expected unauthenticated Beancount.io API responds.
- [ ] The probe times out and can be retried without leaving stale loading state.
- [ ] Valid URLs remain saveable while offline; malformed or unsafe URLs do not.
- [ ] No custom hostname or full URL is emitted to analytics or error-reporting metadata.

## Out of scope

- Negotiating API versions or automatically upgrading an incompatible server.
