## Objective

Treat the selected server as part of session identity so credentials, ledger selection, and cached responses from one deployment cannot leak into another deployment.

## Context

- Session credentials persist through `mobile/src/common/vars/session.ts` using secure storage.
- Apollo data persists separately and is cleared through `mobile/src/common/apollo/session-teardown.ts` and `mobile/src/common/apollo/cache-persist.ts` during logout.
- This milestone exposes server changes only from the signed-out welcome flow, but startup races and stale persisted state must still fail safely.

## Steps

1. Define the invariant that a server URL change happens only while unauthenticated; guard or perform a complete local sign-out if stale session state exists.
2. Reuse the session teardown choke point to clear persisted/in-memory Apollo data and server-scoped reactive variables before activating a different server.
3. Ensure no request can combine server B's URL with server A's authorization header during hydration or transition.
4. Verify restoring the official server follows the same isolation path.

## Files

- `mobile/src/common/apollo/session-teardown.ts`
- `mobile/src/common/apollo/cache-persist.ts`
- `mobile/src/common/vars/`
- `mobile/src/screens/welcome/`
- `mobile/src/common/providers/splash-provider/`

## Acceptance criteria

- [ ] Changing or resetting the server clears credentials and persisted/in-memory server-scoped data before requests target the new server.
- [ ] No transition frame or startup race sends an old bearer token to the new origin.
- [ ] The server editor is not exposed as an authenticated hot-switch control.
- [ ] Logging out and returning to the same server retains the existing expected behavior.

## Out of scope

- Simultaneous accounts on multiple servers or automatic per-server credential vaults.
