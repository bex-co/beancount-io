## Objective

Since `59810c3e`, every public client (`clientAuthMethod === "none"`) whose token is not sender-constrained rotates at any chain age. The mobile client is public, so the leading `isMobileOAuthClient` check looks redundant. The two differ only for a sender-constrained mobile token, which still rotates under the special case.

## Context

- `backend-cluster/backend-v2/src/features/oauth/data/config.ts` (`shouldRotateRefreshToken`, mobile `tokenEndpointAuthMethod: "none"`)
- `backend-cluster/backend-v2/src/features/oauth/api/__tests__/oidc-route.test.ts` ("OAuth refresh-token rotation")

## Steps

1. Check whether a mobile token can ever be sender-constrained (DPoP, mTLS) with the provider's current configuration.
2. If it cannot, remove the special case. If it can and the special case matters, leave the code and add a one-line comment saying why.

## Verdict

**Refuted: the special case is not redundant.** oidc-provider 9.12.2 enables DPoP by default (`features.dPoP.enabled: true` in its defaults), and this server does not turn it off. A public client can therefore get a sender-constrained refresh token, and the public-client rule stops rotating those. The mobile app sends no DPoP proof today. If it ever did, only `isMobileOAuthClient` would keep its token rotating, and with it the idle window sliding. The check stays, with a comment giving that reason, and a new test pins it: "rotates the native credential even when it is sender-constrained". Deleting the check fails that test. backend-v2 `typecheck`, `lint`, and `test` (5074 tests) pass.
