## Objective

`publishToolSecuritySchemes` monkey-patches `server.server.setRequestHandler` and depends on the SDK installing the `tools/list` handler at the first `registerTool`. An SDK upgrade could silently drop the top-level field. Separately, `mcpToolSecuritySchemes(name)` filters all of `VERB_TABLE` for every tool on every `tools/list`, and again at registration. A map built once at module load removes that repeated work.

## Context

- `backend-cluster/backend-v2/src/server/api/composition-root.ts` (`publishToolSecuritySchemes`, `assembleMcpRegistry`)
- `backend-cluster/backend-v2/src/server/api/op-class.ts` (`mcpToolSecuritySchemes`)
- `backend-cluster/backend-v2/src/server/api/__tests__/mcp-tool-list.test.ts`

## Steps

1. Confirm a test fails if the wrapper stops applying, i.e. one that asserts top-level `securitySchemes` on the real `tools/list` wire response. Add one if not.
2. Measure whether precomputing matters. Precompute only if it simplifies the code as well.

## Closed by triage

- **The SDK hook is already pinned.** Turning `publishToolSecuritySchemes`'s wrapper into a pass-through on `a22bfebe` fails `mcp-tool-list.test.ts` › "publishes each tool's derived scheme top-level and in _meta" (1 failed, 8 passed). That test reads the raw `tools/list` wire response, so an SDK upgrade that stops routing the list handler through `setRequestHandler` fails CI instead of silently dropping the field.
- **Precomputing is not worth it.** Deriving every tool's schemes costs about 42 µs per `tools/list` (30 tools against 148 `VERB_TABLE` rows, measured over 1000 iterations). A module-level cache would add state and fight `mcpToolSecuritySchemes`'s injectable `table` parameter, which the tests use, for no measurable gain.

No code changed.
