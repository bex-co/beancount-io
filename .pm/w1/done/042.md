# One-shot queries silently drop trailing statements through native and stored-query paths

**Severity: minor. Owner: cli. Estimate: 45–60m. A1:** agents must be able to trust that a successful query executed the requested statement. Continuous CLI QA, 2026-10-02; report and filing only.

Environment: clean `main` at `97dab6b04c6e40e4cf47e0c1d668731d36c7ec41`, source-checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13.0, Darwin 25.5.0 arm64. Commands run in a disposable cwd with isolated `BEA_CONFIG_DIR`, `XDG_CACHE_HOME`, and `XDG_DATA_HOME`; inherited `BEA_FILE`/`BEA_TOKEN` removed, update notifier disabled. Stdin closed, no TTY, 15-second subprocess timeout.

Save this synthetic `main.bean`:

```beancount
2025-01-01 open Assets:Cash USD
2025-01-01 open Equity:Opening USD
2025-01-02 * "opening"
  Assets:Cash 1 USD
  Equity:Opening -1 USD
```

Run:

```sh
bea --no-input query --source /absolute/main.bean 'SELECT 1; SELECT 2'
bea --no-input query --source beancount:/absolute/main.bean 'SELECT 1; garbage'
```

Actual: exit **0**, a table containing only `1` rows on stdout, empty stderr. The second statement is neither executed nor rejected; even invalid trailing BQL is ignored. Reproduced twice from reset valid fixtures in fresh processes, for both bare paths and `beancount:` URIs. Ledger hashes remain unchanged.

Expected: `cli/docs/USAGE.md`'s one-shot contract says exactly one statement; multiple statements must exit **2** with the existing statement-count usage error before an output file is opened. Working controls: `bea --json --file /absolute/main.bean query 'SELECT 1; SELECT 2'` exits 2 with `One BQL statement per invocation; got 2.`; native `SELECT 1;` and `SELECT ';'` succeed and return their expected values.

Cause: `cli/src/cli/commands/query.py:231–244` dispatches native one-shots before `_refuse_multi_statement` at line 270. `cli/src/cli/engine/launch.py:76–87` forwards to upstream `bean-query`, whose `BQLShell.execute` parses and executes one statement (`beanquery/shell.py:386–399`). Caller search finds the common validator only on the managed local branch; native bare-path and URI inputs share the bypass.

Fix/acceptance: apply the existing comment/quote-aware one-shot statement guard to native queries before dispatch. Cover explicit argv and piped stdin, bare-path/URI forms, quoted/commented semicolons, a trailing separator, and output-file preservation on rejection. Keep native output and JSON/strict exceptions. Run meaningful subprocess regressions and `make check-all` in `cli/`; no new dependency or API change.

Dedupe: searched all `.pm` states and open milestone README files for multi-statement, semicolon, native/source queries and success-on-partial-answer. This is residual scope from completed `w3/282` (fixed by `15629c14` / `w1/m23/t005`) and `w3/402` (comment-aware splitting). Their common guard is present on HEAD but absent from this adapter. Open `w1/040` explicitly leaves native multiple-statement behavior outside its missing-input finding. No overlapping open implementation item found; this note does not reopen completed work.

Evidence: sanitized argv, cwd, stdin/TTY mode, separate streams, exit codes, duration, and before/after hashes in `cli/tmp/qa-20261002-loop/captures.jsonl`; reproducer driver `repeat_native.py` there. Invalid first draft of the stored-query fixture was corrected before final reproduction and is not evidence for this finding. Public reproduction above is self-contained. CSV/memory/test sources, PTY behavior and other operating systems unverified. No credentials, hosted resources, fixes or shipping.


## Additional reproduced caller: managed stored queries

The same missing statement guard also affects the managed helper when the SQL lives in a `query` directive. Append this to the valid fixture above:

```beancount
2025-01-03 query "saved" "SELECT 1; SELECT 2"
```

`bea --json --file /absolute/main.bean check` exits 0; then both `bea --json --file /absolute/main.bean query '.run saved'` and `bea --json --file /absolute/main.bean query '.run *'` exit **0**, empty stderr, with only `1` rows in `data.text`. Changing the stored body to `SELECT 1; garbage` likewise succeeds. Repeated twice from reset fixtures; human `.run saved` also returns only `1` rows with exit 0. Valid stored `SELECT 1;` and `SELECT 1 /* ; */` are successful controls. No ledger bytes change.

The frontend guard deliberately skips dot commands. `PreciseShell.do_run` in `cli/src/bea_engine/query.py:437–464` retrieves the stored body and calls `execute`; `execute` at lines 466–486 normalizes reserved tables and checks empty windows, but does not enforce statement count. Both named and wildcard `.run` share this inner path. The bounded fix must enforce one statement at the actual BQL execution boundary as well as native frontend dispatch; the engine cannot import frontend code. Preserve `.run *` running multiple *separate* valid stored directives, and quote/comment semantics within each body. Add meaningful regression cases for named/wildcard stored queries alongside native calls. Estimate expanded to include this shared no-silent-tail repair, still a bounded inbox item.

Additional dedupe: completed `w3/398` (`39c6894f`) moved reserved-table and empty-window preparation to this execution boundary but does not claim multiple-statement support. `w4/182` / `w3/402` correct the frontend splitter's comment semantics. No open item covers stored statement tails. Additional evidence: `stored_queries.py` and its repeated captures in the same evidence directory. A subsequent managed-shell PTY session reproduced both `.run saved` and directly entered `SELECT 1; SELECT 2` returning only `1` rows, then successfully answered `SELECT count(*)` and exited normally via `.exit`. Stdin used a real PTY; stdout/stderr were separately piped. A child-only startup hook relocated upstream Beanquery history/init paths beneath the isolated configuration directory without altering HOME or command behavior. Capture: `cli/tmp/qa-20261002-loop/pty-capture.json`; driver: `pty_sweep.py`. Apply the engine guard to direct interactive BQL as well, reporting an ordinary recoverable usage error and keeping subsequent valid queries usable. Native interactive behavior remains unverified.

---

**Resolved 2026-10-03** — a query with a second BQL statement after a `;` is now refused with exit 2 on every path — native one-shots, stored `.run` bodies, the interactive prompt and direct engine calls (including `ask`) — through an engine-side check that shares the frontend's quote, comment and trailing-`;` rules; `.run *` over separate queries is unchanged. `tests/test_query_statement_tail.py` covers each path. Shipped in the commit that moved this note (`cli`).
