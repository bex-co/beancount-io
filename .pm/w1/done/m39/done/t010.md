## Objective

Make PRFAQ005 question 19 measurable:

- The dashboard emits `billing_toggle_changed`, `plan_change_previewed`, `plan_change_confirmed`, `payment_action_required` and `payment_action_failed`.
- The backend emits one server-side `purchase` for each paid Checkout or immediate change, from the verified Stripe webhook.

## Context

- `dashboard/src/common/analytics/events.ts` and `dashboard/docs/event-taxonomy.md`: `purchase` is designed but not wired, and carries the same `user_id` so it joins the client journey.
- Webhooks: `backend-cluster/backend-v2/src/features/stripe/api/stripe-webhook-handler.ts`.
- The GA4 Measurement Protocol needs a measurement ID and an API secret. They are operator-provided, set in runtime config and never committed.

## Steps

1. Add the client events with typed parameters (kind, from, to, surface) and document them in the taxonomy.
2. Send `purchase` once per paid invoice, idempotently across webhook retries, with value and currency and no personal data. Do nothing when the secret is unset.

- `dashboard/src/common/analytics/events.ts`, `dashboard/docs/event-taxonomy.md`, the billing components

## Implementation notes

- **Client events** live in `dashboard/src/common/analytics/events.ts`, documented row by row in `dashboard/docs/event-taxonomy.md` §6.
  - Every plan-change event carries `{kind, from, to, surface}`:
    - `from` and `to` are plan values (`free`, `premium_monthly`, `growth_yearly`, …), with `from` taken from the plan and cycle Billing shows, so legacy prices keep their cycle;
    - `surface` is where the change started: Billing's plan rows, the pay-yearly offer, a prompt's deep link (its `from` parameter), or `deep_link` for a link from outside the app.
  - `plan_change_previewed` fires when a preview request resolves with a `kind`, so a retry counts again and a re-render never does. The preview runs only when the target price changes, so a refetched plan does not trigger a second one.
  - `plan_change_confirmed` fires on the sheet's confirm button, including a `NEW` checkout, which also sends `checkout_started` (now with the entry surface).
  - `payment_action_required` and `payment_action_failed` follow `changePlan`'s `REQUIRES_ACTION` and `FAILED` results; a missing result is not counted as a decline.
  - The confirm button is disabled while a Checkout session is being created. A double-click used to open two sessions and count the confirm twice.
  - `billing_toggle_changed` fires only when the cycle actually changes.
- **Server `purchase`** (`backend-cluster/backend-v2/src/features/stripe/operations/report-purchase.ts`) runs from the webhook's new `invoice.paid` case.
  - It sends only `subscription_create` and `subscription_update` invoices with a non-zero `amount_paid`. Renewals are not new purchases, and a 100%-off QA Checkout sends nothing.
  - The user comes from the subscription's signed metadata, because a first Checkout's invoice can arrive before `checkout.session.completed` binds the customer. A binding, when present, must name the same user.
  - It filters before looking up the user, so renewals cost nothing.
  - Once only: a `reported_purchases` row (migration `0021`, invoice id only, no user data) is claimed before sending.
    - A failed send gives the claim back and the webhook answers 400, so Stripe redelivers within its retry window.
    - A claim the database cannot record also fails the delivery.
    - The one possible duplicate is a send that timed out after GA4 received it; `transaction_id` identifies it.
  - Amounts use the currency's own minor unit.
  - It is off unless `GA_MEASUREMENT_ID` and `GA_MEASUREMENT_PROTOCOL_SECRET` are both set; the operator steps are in t004 step 5. The webhook receives the analytics config from the composition root. Errors log only their kind, because the request URL carries the secret.
- **Deviations:**
  - The taxonomy's "no monetary amounts" rule gains one documented exception, `purchase`'s value: what the customer paid us, sent server-side only.
  - The server derives GA4's `client_id` from the user id, because the webhook has no browser client id. The join with the dashboard journey relies on `user_id`, so `purchase` carries no traffic source of its own. Carrying the browser's GA client and session id through Checkout metadata would fix that, but it changes `createSubscriptionSession`, which the pricing page also calls. That is left to t011.
- **For t015:** the 100%-off QA purchases deliberately produce no `purchase` event. Verify instead that the webhook acknowledged `invoice.paid` and nothing was reported.
