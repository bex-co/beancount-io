## Objective

Add `changePlan(clientId, priceId, prorationDate)`. It applies upgrades and switches to yearly immediately, at the proration time the customer previewed, so the charge equals the amount shown. It reports the outcome truthfully: `ACTIVE`; `REQUIRES_ACTION` with the payment's client secret and the invoice's hosted payment URL; or `FAILED` with nothing changed.

## Context

- `upgradeSubscription` (`backend-cluster/backend-v2/src/features/stripe/service/stripe-service.ts:205`) updates in place with `always_invoice` and `pending_if_incomplete`, but its authentication branch cannot run. The update does not expand `latest_invoice`, and on API `2025-12-15.clover` an Invoice carries `payments`, not `payment_intent`. A change that needs authentication is therefore reported as "Payment failed. Your subscription was not changed." while Stripe holds a pending update (PRFAQ005 question 13, defect 6).
- Since `ef3d197bd`, a verified paid-period cache can answer `subscriptionStatus.hasActiveSubscription` without calling Stripe:
  - The cache is trusted only when `periodVerificationVersion` equals `SUBSCRIPTION_PERIOD_VERIFICATION_VERSION`.
  - Verified periods are written with `paidCustomer.updatePeriodIfUnchanged`.
  - A plain `updateCustomerById` period write invalidates the verification, which is what the upgrade path does today (`stripe-service.ts:324`).
  - A switch to yearly moves the period end by a year, so the new period must be recorded through the verified write. Otherwise the pricing page's subscribed check falls back to a live Stripe read.
- A customer without a subscription keeps using `createSubscriptionSession` (Checkout). The pricing page calls it, so its arguments, accepted prices and results stay as they are. The pricing page does not call `upgradeSubscription`.

## Steps

1. Implement `changePlan` for immediate kinds only, with `proration_date`, `proration_behavior: "always_invoice"`, `payment_behavior: "pending_if_incomplete"` and the latest invoice's payments expanded.
2. Map the result:
   - Payment requires action → `REQUIRES_ACTION`, with the client secret and `hosted_invoice_url`.
   - Declined → `FAILED`, saying nothing changed.
   - Paid → `ACTIVE`, with the provider's new period recorded through `updatePeriodIfUnchanged` at the current verification version.
3. Make a repeated confirm harmless:
   - send an idempotency key derived from the subscription, the target price and the proration time, so a double click or a retried request applies the change once;
   - re-read the subscription before writing, so a change that already landed returns `ACTIVE` instead of charging twice.
4. Stop a second subscription: `createSubscriptionSession` refuses Checkout when the customer already has an active subscription on a configured price, and directs them to Billing. The pricing page only offers Checkout to visitors without one, so this only catches races and stale state.
5. Refuse scheduled kinds without any Stripe write until m40 implements them, and have `upgradeSubscription` delegate to the same path so no client can apply a downgrade immediately.
6. Add the authorization action and the parity-baseline, op-class and rate-limit entries, and update the dashboard schema copy.

## Implementation notes

- Shipped `Mutation.changePlan(clientId, priceId, prorationDate)` (`user.billing.plan_change.apply`, browser session only). Its result is `ACTIVE | REQUIRES_ACTION | FAILED | REFUSED`, with the client secret and the hosted invoice URL when the bank must approve. The operation lives in `src/features/stripe/operations/plan-change-apply.ts`. Preview and apply read the customer's subscription through the same loader (`operations/current-plan.ts`).
- **Second latent bug fixed:** under `pending_if_incomplete`, Stripe keeps a subscription `active` on its *old* price while a payment awaits action or has failed. `upgradeSubscription` treated `status === "active"` as success, so it could report "upgraded successfully" for a change that never applied. Success now requires no `pending_update` and the item on the target price.
- The idempotency key is `plan-change:<subscription>:<price>:<prorationDate>`. A confirm whose change already landed returns `ACTIVE` without another Stripe write. Proration times more than 60 s in the future or over an hour old are refused, so the customer previews again.
- `upgradeSubscription` keeps its result shape but runs through `changePlan`, so a downgrade or a switch to monthly is now refused instead of applied at once. The two tests that pinned the old behaviour were rewritten. Its "no customer" and "no active subscription" messages became the single `NO_SUBSCRIPTION` refusal.
- `createSubscriptionSession` refuses Checkout to a customer who already has an active paid subscription. The pricing page only offers Checkout to visitors without one, so this changes nothing on its normal path.
- Successful changes record the provider's new period through `paidCustomer.updatePeriodIfUnchanged` at the current verification version, so `hasActiveSubscription` keeps answering from the verified cache.
