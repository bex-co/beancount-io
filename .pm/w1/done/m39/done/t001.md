## Objective

Add `previewPlanChange(clientId, priceId)`. It classifies a change from tier order and billing interval, and returns what the customer is charged today, the credit for unused time, the next charge, the proration time used, the limits that change and the default payment method. Also expose that payment method on `subscriptionStatus` for the Billing summary card. This is the single place a change is classified; the dashboard renders what it returns.

## Context

- Rules and contract: [PRFAQ005](../../../../../docs/prfaqs/PRFAQ005-plan-changes-and-yearly-billing.md) questions 14 and 16.
- `SUBSCRIPTION_CONFIG` (`backend-cluster/backend-v2/src/features/stripe/service/stripe.ts`) maps each price to a tier but records no interval, so classification would need a Stripe call. Tier order is `SubscriptionTier`, and limits are `TIER_LIMITS`.
- Stripe SDK 20.2.0 on API `2025-12-15.clover`: `invoices.createPreview` takes the subscription plus `subscription_details` (items, `proration_date`, `proration_behavior`).
- Billing operations are GraphQL-only and browser-session-only: see `backend-cluster/backend-v2/authz/README.md` § Self-service billing. Their gates are `src/server/api/__tests__/fixtures/parity-baseline.json`, `src/server/api/op-class.ts` and `src/server/api/rate-limit.ts`.

## Steps

1. Record `interval` on every plan in `SUBSCRIPTION_CONFIG`, and pin it with a test against each plan's description.
2. Classify each change from the current plan and the target price:
   - `NEW` — no subscription; full price through Checkout.
   - `UPGRADE`, `TO_YEARLY`, `DOWNGRADE`, `TO_MONTHLY`.
   - `SPLIT` — a higher tier combined with a switch from yearly to monthly.
   - Refuse the current price.
   - Refuse a change that keeps the tier and the cycle but moves to a different price, for example a $99.99 legacy Premium yearly subscriber choosing $143.88. That would raise their price for nothing, so the refusal names the plan they already have.
   - When the customer has more than one active subscription on a configured price, refuse every change with a distinct error rather than guessing which one to change. Log it, because it means a duplicate purchase.
3. For immediate kinds, call the invoice preview at a fixed `proration_date`. Map the amount due, the credit (proration lines) and the next amount and date. For scheduled kinds, return the current period end as `effectiveAt` and nothing due today. m40 applies them.
4. Return `limitChanges` from `TIER_LIMITS`, from → to, with the current usage the account summary already computes. Return the customer's default payment method brand and last four, and add the same field to `subscriptionStatus`.
5. Add an authorization action that makes one PDP call before any Stripe request. Add the parity-baseline, op-class and rate-limit entries. Update `dashboard/api-gateway.graphql` and the dashboard's generated definitions.

## Implementation notes

- Shipped as `Query.previewPlanChange` (browser-session billing, `user.billing.plan_change.preview`), plus `Subscription.paymentMethod` on `subscriptionStatus`. The pure classifier is `src/features/stripe/service/plan-change.ts`, and the Stripe-backed preview is `src/features/stripe/operations/plan-change-preview.ts`.
- The kind list gains `NEW` for a customer without a subscription, so the dashboard can render one sheet for every case. Refusals are their own field (`CURRENT_PLAN`, `SAME_TIER_AND_CYCLE`, `MULTIPLE_SUBSCRIPTIONS`).
- `limitChanges` carries the from → to values only. Current usage is already on the dashboard through `useUserLimits`, so the preview does not read the account summary across features.
- Amounts are in minor units (cents), as Stripe reports them, like `SubscriptionPrice.amount`.
