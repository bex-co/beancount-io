# A schema-invalid bulk batch suggests `--partial` "for some of the 0" valid rows

**Severity: minor. Owner: cli. Estimate: ~10m. A1:** advice that cannot help wastes an agent round trip. Continuous CLI QA, 2026-10-03 (round 16); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced twice with a working control. Found by a regression hunt over shipped fixes.

`[{"date":"2024-06-01","narration":"x","postings":["Expenses:Food 5 USD","Assets:Bank"]}]` (postings as strings):

```sh
bea --file /abs/s.beancount add transactions --from /abs/bulk.json
```

Actual: "Fix them, or pass --partial to try appending schema-valid rows (ledger validation may still reject some of the 0)." Following it yields "Added 0 of 1 transactions" (exit 1).

Cause: `cli/src/bea_engine/ledger/adding.py:798–801` appends the hint even when `len(valid) == 0` (wording from `w3/done/231`).

Fix/acceptance: omit the `--partial` clause when no row passed schema validation.

---

**Resolved 2026-10-04** — a bulk batch where no row passes the schema no longer suggests `--partial` for "some of the 0" valid rows. `tests/test_partial_recovery_count.py` covers it. Shipped in the commit that moved this note (`cli`).
