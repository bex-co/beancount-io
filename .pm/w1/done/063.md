# Import rules miss Unicode-equivalent text (NFD vs NFC)

**Severity: minor. Owner: cli. Estimate: 15–20m. A1:** bank exports mix normalization forms; rules must match what users see. Continuous CLI QA, 2026-10-02 (round 2); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed unless a PTY is stated. Reproduced at least twice from pristine fixtures.

CSV with two rows whose description is `Café Nero` — one written NFD (`e` + U+0301), one NFC (`é`) — and a rule `match = "café"`, `account = "Expenses:Dining"`; import with `--rules … --apply`.

Actual: the NFD row is `unmatched` (booked to Uncategorized with `!`); the NFC row matches. The NFD narration is also written un-normalized.

Expected: `cli/docs/USAGE.md` says search terms and literals compare NFC-normalized, and `list --search` already treats both spellings as equal (`w3/done/275`).

Cause: `_categorize` runs the regex over raw cells (`cli/src/bea_engine/csv_mapper.py:944–946`, `:976–981`); neither the pattern (`:277`) nor the text is NFC-normalized.

Fix/acceptance: NFC-normalize the pattern source and payee/narration/category text before `search`. Both rows match in either direction (NFC rule on NFD data and vice versa).

Dedupe: `w3/377`, `w3/275`, `w3/278` cover import IDs, search and accounts, not rules (`w3/377`'s repro used the pattern `caf`).

---

**Resolved 2026-10-03** — import rules now compile their pattern and match payee, narration and category text in Unicode NFC, so composed and decomposed spellings such as `café` match either way; the written narration stays as the bank exported it. `tests/test_import.py` covers both directions. Shipped in the commit that moved this note (`cli`).
