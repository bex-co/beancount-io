# Beancount's load cache ignores newly matching include-glob files, so repeated `bea import --apply` writes duplicates

**Severity: major. Owner: cli. Estimate: 1–2h (may warrant promotion). A1:** agents re-running imports rely on exact-ID dedupe; stale reads silently duplicate entries. Continuous CLI QA, 2026-10-03 (round 3); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1 (Beancount 3.2.3, beanquery 0.2.0), Python 3.13, macOS 26.5.1 arm64. Fresh process per command, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with a working control.

Needs a ledger that loads in > 1 s (Beancount writes `.main.bean.picklecache` only above that; ~60k transactions suffices):

```sh
mkdir -p L/txns; cat > L/main.bean <<'EOF'
2000-01-01 open Assets:Bank USD
2000-01-01 open Expenses:Food USD
2000-01-01 open Expenses:Uncategorized USD
include "big.bean"
include "txns/*.bean"
EOF
python3 -c "open('L/big.bean','w').writelines(f'2020-01-01 * \"t{i}\"\n  Expenses:Food  1 USD\n  Assets:Bank\n\n' for i in range(60000))"
bea --file /abs/L/main.bean query 'SELECT count(*)'          # warms the cache; glob matches nothing yet
printf '2021-01-01 * "fresh"\n  Expenses:Food  1 USD\n  Assets:Bank\n' > L/txns/jan.bean
bea --file /abs/L/main.bean list transaction --search fresh
BEANCOUNT_DISABLE_LOAD_CACHE=1 bea --file /abs/L/main.bean list transaction --search fresh   # control
```

Actual: the warm run exits 1 with `File glob "txns/*.bean" does not match any files`; the control lists the row.

Duplicate import (150k transactions across 180 files under `include "txns/*/*.bean"`, warm cache): create an empty `txns/2032/01.bean`, then run `bea import bank.csv --csv date=Date,narration=Description,amount=Amount,id=Id --account Assets:Bank:Checking --into txns/2032/01.bean --apply` **twice** — both report "2 ready, 0 exact duplicates" / "Wrote 2 entries", and the file holds 4 entries with the same `import-id` values. Small-ledger control: the second run writes 0.

Same cause: `bea add transaction … --into` a new glob file prints "Added" (exit 0) but `list`/`balance`/`query` don't show it; appending `include "later.bean"` then creating `later.bean` keeps failing with "does not match any files".

Expected: reads reflect files on disk; USAGE says "exact IDs are always skipped", and exit 0 means the documented effect happened.

Cause: upstream `beancount/loader.py` `pickle_cache_function` / `needs_refresh` / `compute_input_hash` hash only mtime and size of files already in `options_map["include"]`; a newly matching glob file or a newly created missing include is never considered. bea uses the cached loader at `cli/src/bea_engine/managed_load.py:232` (staged path `:284`), feeding `importing.py:103` (dedupe), `ledger/adding.py:204,386,512`, `ledger/write.py:530`, `reader.py:62`, `query.py:116`, `fava/beans/load.py:40`.

Fix/acceptance: before trusting a cache hit, expand every include pattern (`LedgerSnapshot.patterns`, `ledger/write.py:61–76`); if the expansion differs from `options["include"]` or a previously missing include now resolves, drop the cache and reload. (Blunt alternative: `BEANCOUNT_DISABLE_LOAD_CACHE` for engine children, ~40% slower cache hits.) The repro finds "fresh", the repeated import writes 0 entries, and `add --into` a new glob file is immediately listable. Cover with a test that lowers the cache threshold. Promote to a milestone if the fix and tests exceed an hour.

Dedupe: no `.pm` hit for stale/glob/invalidation + picklecache; `w3/390`, `w3/440`, `w5/014`, [074](./074.md) cover leaked cache files only. `git log -S BEANCOUNT_DISABLE_LOAD_CACHE` empty.

---

**Resolved 2026-10-03** — reads now reload when Beancount's pickle cache would miss files that newly match an include glob or a previously missing include, so repeated `bea import --apply` dedupes correctly on large ledgers. `tests/test_load_cache_new_includes.py` covers it. Shipped in the commit that moved this note (`cli`).
