# `bea add balance` refuses a second, different balance for the day with "Pass --force to record another assertion", and `--force` then always fails: Beancount allows one balance number per account, currency and day

**Bug · cli · minor · 30–45m · A1.** From routine cli-qa, 2026-11-23. A bank statement and the books disagree, so a person or an agent runs `bea add balance` for a day that already has an assertion. bea refuses with exit 4 and one next step: `Pass --force to record another assertion.` For any number other than the one on record, that step can never work. Beancount's own validation (`validate_duplicate_balances` in `beancount/ops/validation.py`) rejects two balance assertions for one account, currency and day whose amounts differ, so the forced write always fails with exit 1. When the new number is inside the old one's tolerance, the forced failure is a bare `Duplicate balance assertion with different amounts`, with no line and no next step. An agent that follows the refusal's advice burns a retry and learns nothing. This is the balance counterpart of [w5/397](../w5/done/397.md), fixed for `add price` under `unique_prices`.

Environment: main `5e085027f`, `bea 0.5.0` from the checkout (`uv run bea`), macOS 26.5.1, managed engine 0.5.0 (Beancount 3). Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, stdin closed, no TTY. Reproduced from a pristine copy in fresh processes.

## Repro

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Opening"
  Assets:Checking 100.00 USD
  Equity:Opening
2026-01-31 balance Assets:Checking 100.00 USD
```

```sh
bea --file main.bean add balance --date 2026-01-31 -a Assets:Checking --amount '120.00 USD'
bea --file main.bean add balance --date 2026-01-31 -a Assets:Checking --amount '120.00 USD' --force
bea --file main.bean add balance --date 2026-01-31 -a Assets:Checking --amount '100.03 ~ 0.05 USD'
bea --file main.bean add balance --date 2026-01-31 -a Assets:Checking --amount '100.03 ~ 0.05 USD' --force
```

## Actual

- Each plain run: exit 4, `Assets:Checking already has a 2026-01-31 balance of 100.00 USD (at main.bean:7); refusing 120.00 USD. Pass --force to record another assertion.` (the same for `100.03 ~ 0.05 USD`).
- `120.00 USD --force`: exit 1. `Proposed append (not written): Balance failed …`, then `The 2026-01-31 assertions for Assets:Checking in USD disagree. Remove or correct the conflicting assertion …`, then `Proposed append (not written): Duplicate balance assertion with different amounts`.
- `100.03 ~ 0.05 USD --force`: exit 1. The only detail is `Proposed append (not written): Duplicate balance assertion with different amounts`. It names neither the assertion at `main.bean:7` nor what to do.
- `--force --allow-errors` fails the same way. `--pad-from Equity:Opening --force` fails too, and its own hint says "two different assertions for one account and currency on one day cannot both hold, so remove one of the two". bea contradicts its own refusal.
- The file is byte-identical after every run (no data loss).
- Control: `--amount '100.00 ~ 0.01 USD' --force` (the same number, another tolerance) writes the second assertion, exit 0, and `bea check` passes. `--force` is the right advice only for this case: the same number at another precision or tolerance.

## Expected

The refusal offers only a step that can succeed. When the existing assertion's number differs from the new one's, bea still exits 4 but drops `--force`: `Assets:Checking already has a 2026-01-31 balance of 100.00 USD (at main.bean:7); refusing 120.00 USD. Beancount allows one balance per account, currency and day, so correct or delete the assertion at main.bean:7 instead.` A forced attempt with a different number gets the same refusal before staging, as w5/397 did for prices, instead of the validation error. When only the precision or tolerance differs, the message stays as it is, and `--force` writes as today. `cli/docs/USAGE.md:1812-1814` says a different value "is a conflict (exit **4**) and needs `--force` (ledger validation still applies, so a conflicting value cannot land)". That sentence contradicts itself. It should say `--force` records the same number at another precision or tolerance, and that a different number means correcting the existing line. The `--force` help (`cli/src/cli/commands/add.py:292`) should say the same.

## Cause

`_conflict_refusal` (`cli/src/bea_engine/ledger/adding.py:641-650`) always ends with "Pass --force to record another assertion." `_balance_conflict` (`:986-1007`) counts every assertion that is not `_same_assertion` (`:1010-1019`) as a conflict. That covers two different cases: the same number at another precision or tolerance, which Beancount accepts, and a different number, which `validate_duplicate_balances` refuses (`entry.amount != previous_entry.amount`; tolerance is not compared). Both callers (`:740-741` and the `--pad-from` retry at `:791-792`) skip the refusal under `--force`.

## Fix

Owned by `cli`, engine side only. In `_balance`, when the conflict's `amount.number` differs from the requested number, raise the refusal with or without `--force`, and use the correct-or-delete wording. Keep the `--force` wording, and the forced write, when the numbers are equal. Update USAGE and the `--force` help as above, then run `make docs`. Tests (real `bea` subprocesses, in the style of `tests/test_add_balance_pad_from_conflict.py`):

- A different number, plain and with `--force` (also with `--pad-from` and with a tolerance-covered number): exit 4, the message names `main.bean:7`, no `--force` advice, and the file is unchanged.
- The same number at another tolerance or precision: still refused without `--force`, and written with it.
- An exact repeat: still `duplicate: true`, exit 0.

Update any test that pins the old wording (`tests/test_add_balance_concurrent.py`, `tests/test_add_balance_pad_from_conflict.py`). Run `make check-all` and `make docs-check` in `cli/`. No hosted surface is involved: the REST, GraphQL and MCP writes do not give this advice.

## Blast radius

`_conflict_refusal` has two callers, both in `_balance`, so the plain and `--pad-from` paths are affected. `add price` was fixed in w5/397 for `unique_prices`. Without that plugin, a second price for the day does land, so its `--force` advice is right. `bea import` already reports a conflicting incoming assertion as a `conflict` row (w5/1008) and offers no `--force`.

## Dedupe

Searched `.pm/**`, including `done/` and `blocked/`, for `record another assertion`, `Duplicate balance assertion`, `different amounts`, `cannot both hold` and `--force` with `balance`. w5/115 (concurrent writers), w5/487 (`--pad-from` advice dated the pad after the day), w5/993 and w5/1008 (judging conflicts from what the files declare) all keep the "Pass --force" wording and do not test a forced different number. w5/397 is the same defect for prices under `unique_prices`, fixed in `abc16946`. `git log -S'record another assertion'` shows the wording since `32c47086c` (w1/m27/t006) and the self-contradicting USAGE sentence since `632960943` (w1/m27/t007).
