# `bea cloud git setup --undo` deletes the user's own empty `credential.<url>.helper` reset for that address, not just the two values setup wrote

Found by `/qa-find-bugs-cli w1` on 2026-11-19 (HEAD `7b5e06004`, `bea 0.4.1` from the checkout, macOS 26.5.1, Python 3.12.14, git 2.55.0, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, and `GIT_CONFIG_GLOBAL` pointing at a scratch file with `GIT_CONFIG_NOSYSTEM=1`, so the real Git config was never touched). Severity: minor. The code is from w22/m12 (blocked on its live check and release), so this can land before that release. A2: a self-hoster who already scoped Git's helpers for their server with Git's documented empty-value reset finds that `--undo` silently brings a machine-wide helper (macOS Keychain, Git Credential Manager) back for that server.

**Repro.** The state file is the one `bea cloud git setup` writes, filled in by hand because no self-hosted server was available. The two `git config --add` lines write exactly what `setup`'s `install_helper` adds; calling `install_helper` directly against the same config produced the same four values. `BEA` is the absolute path to the checkout's `cli/.venv/bin/bea`.

```sh
export BEA_CONFIG_DIR=$PWD/cfg GIT_CONFIG_GLOBAL=$PWD/gitconfig GIT_CONFIG_NOSYSTEM=1
mkdir -p cfg && chmod 700 cfg && cat > cfg/git-credential.json <<'EOF'
{"api_url": "https://api.v3.beancount.io", "git_url": "https://git.example.com", "key_id": "k1", "key_name": "bea git on qa", "token": "synthetic", "expires_at": "2099-01-01T00:00:00+00:00"}
EOF
chmod 600 cfg/git-credential.json
# The user's own config before setup: Git's empty-value reset, then their own helper for this host.
printf '[credential "https://git.example.com"]\n\thelper =\n\thelper = store --file /tmp/qa-store\n' > gitconfig
# What setup appends:
git config --global --add credential.https://git.example.com.helper ""
git config --global --add credential.https://git.example.com.helper "!$BEA cloud git credential"
"$BEA" cloud git setup --undo          # signed out: exit 1, names the token, as documented
git config --global --get-all credential.https://git.example.com.helper
```

**Actual.** Before `--undo` the address has four values: `""`, `store --file /tmp/qa-store`, `""`, `!…/bea cloud git credential`. After it, one: `store --file /tmp/qa-store`. The user's own leading `""` is gone, so any helper configured for every host (the system `osxkeychain`, a global `manager`) answers for this server again. The same happens when `setup` is run again from a different `bea` path (after moving from `uv tool` to Homebrew, say): the last two values no longer match, `install_helper` calls `remove_helper` first, and the user's reset is deleted before the new pair is added.

**Expected.** USAGE ("Cloud: Git sign-in on a self-hosted server") and w22/m12/t002's acceptance say `--undo` "removes exactly the two config values" and that "only that address is touched". After `--undo` the address holds exactly what it held before `setup`: `""`, `store --file /tmp/qa-store`. A re-run of `setup` from a new path replaces only bea's own pair. With no user values (the common case) the result is unchanged: the key is gone entirely.

**Root cause** (cli only). `remove_helper` (`cli/src/cli/commands/cloud/git/helper.py:243`) runs `git config --unset-all <key> ' cloud git credential$'` and then `git config --unset-all <key> '^$'` (line 251). The second call removes every empty value for the address, whoever wrote it. `install_helper` (line 237) reuses it when the last two values are not bea's current pair, and `_undo` (`cli/src/cli/commands/cloud/git/app.py:121`) calls it directly.

**Fix.** Remove only the pairs bea wrote: each `!… cloud git credential` value and the single empty value immediately before it. `git config --unset-all` cannot address one value by position, so read the list (`--null --get-all`, as `configured_helpers` already does), compute the remaining values in order, and when the list changed rewrite the key: `--unset-all` it, then `--add` each remaining value. Regressions in `cli/tests/test_cloud_git_sign_in.py` with real `git`: a pre-existing `["", "store …"]` survives `setup` then `--undo` byte for byte as a value list; a re-run of `setup` from another `bea` path keeps the user's values and leaves one bea pair; the existing setup/undo tests (no user values) still pass.

**Blast radius.** `setup --undo`, and `setup` re-run when the stored helper path changed. `cloud logout` leaves the Git config alone and is not affected. Only the global config is touched (`git config --global`). Not exercised live: `setup` against a real self-hosted server (w22/m12/t006 is still blocked).

**Dedupe.** Searched `.pm/**` for `cloud git`, `remove_helper`, `credential.<url>.helper`, `empty value`, `^$`, `undo`. w1/294 (address spelling) and w22/m12 (the feature; t002 promises "`--undo` removes exactly what it wrote") are the only related items, and neither covers a user's own empty value. Estimate: 30–45 minutes.

---

**Resolved 2026-11-19** — `remove_helper` now takes out only the pairs `setup` wrote: each `!… cloud git credential` value and the one empty value immediately before it. Since `git config` cannot unset by position, it reads the list with `--null --get-all`, and when anything is bea's it rewrites the key with the remaining values in order (`--unset-all`, then `--add` each). The note's repro now ends with `""`, `store --file /tmp/qa-store` after `--undo`, and a re-run of `setup` from another `bea` path keeps the user's values and leaves one bea pair; with no user values the key is gone, as before. USAGE ("Cloud: Git sign-in on a self-hosted server") now says the user's own values for the address stay. Regression tests in `cli/tests/test_cloud_git_sign_in.py` (`test_undo_leaves_the_users_own_reset_and_helper_for_the_address`, `test_setup_from_another_bea_path_replaces_only_its_own_pair`, `test_undo_takes_out_each_bea_value_and_the_reset_just_before_it`) drive real `git` and fail without the fix.
