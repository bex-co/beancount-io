# Account-table balances wrap mid-number at default text size

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2 — the public ledgers are the app's shop window, and on the largest of them a balance that splits its sign from its figure misreads at a glance.

Environment: 2026-09-15, main `10465c05`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5 (sole booted simulator, light appearance), Metro over localhost:8081, English, default text size (`large`), authenticated QA session against `https://beancount.io/`, public `open_ledger/alphabet`, read-only. No ledger writes.

Repro:

1. Open Accounts on `open_ledger/alphabet` at the default text size.
2. The Income row (`-$1,743,597,000,000.00`, 22 chars) wraps mid-number: the `-` is stranded on its own line above `$1,743,597,000,000.0` / `0`. Every digit is visible — nothing is clipped — but the sign is detached from the figure.
3. The Expenses row (`$1,202,771,000,000.00`, 21 chars) breaks across two lines the same way. The Assets row (`$921,983,000,000.00`, 20 chars) fits on one line, so at this size 20 characters fit and 21 wrap.

Expected: each balance renders on one line with its sign attached (or in a clean stacked layout). Actual: 21+ character balances wrap mid-number with a detached sign.

Root: the balance `AmountText` (`mobile/src/components/account-table/account-table.tsx:278`) carries no line constraint inside the `amounts` container (`maxWidth: "55%"`, `account-table.tsx:148-151`). The `AmountText` contract (`mobile/src/components/amount-text/amount-text.tsx`) forbids ellipsizing ("can't ellipsize without lying") but says nothing about wrapping. Note `96837d1d` (which closed `w3/done/217`) only stacks the row when `prefersStackedLayout(fontScale)` is true (`mobile/src/common/theme/dynamic-type.ts:33`, threshold `STACKED_LAYOUT_FONT_SCALE = 1.3`), so the default-size path (`large`, scale 1.0) is unchanged and this case survives that fix — verified by code inspection, not yet re-shot on device.

Fix (mobile): constrain the balance line at default size too — single-line via shrink-to-fit (the pattern established for `w4/done/005`, same stranded-sign symptom on the transaction detail hero) or extend the stacked layout below the 1.3 threshold — never a mid-number wrap, never ellipsized digits. Keep the large-text stacked behavior from `96837d1d` intact.

Blast radius: the account-table balance cell only. Transaction detail hero (`w4/done/005`), journal postings, and the large-text stacked row are untouched. Colleagues: `w3/done/217` (AX1/maximum clipping on the same row, fixed) and `w4/done/005` (shrink-to-fit precedent); neither covers the default-size wrap.

Adjacent states: AX1/maximum sizes (stacked, covered by `w3/done/217`), short balances (unchanged single line), narrow devices in landscape.

Dedupe: searched every queue including `done/` for mid-number/stranded/default-size wrap. `w3/done/205` is date-dialog actions at largest text; `w4/done/005` is the transaction-detail hero (distinct screen, established pattern); `w3/done/217` is the same row at AX1/maximum only. No duplicate found.

Acceptance: default-size alphabet shows Income and Expenses each on one line (or cleanly stacked) with the sign attached to the figure, alongside the existing AX1/maximum acceptance. Add regression coverage for a 21+ character balance at fontScale 1.0.

Unverified: on-device re-check on current HEAD (Metro was down; verified by code inspection that the default-size path is unchanged since the finding); other locales; Android.

Evidence (gitignored, local only): `mobile/tmp/qa-2026-09-15/14-accounts-deeplink.png`. No product fix, commit, or shipping.

---

**Resolved 2026-09-16** — fixed in `mobile` by `fix(mobile): shrink account-table balances to one line`. Triage confirmed at HEAD that the balance `AmountText` carried no line constraint at any size (cited lines had drifted; the element sits in `amountBlock` in `account-table.tsx`) while the stacked layout only engages at fontScale ≥ 1.3 — so 21+ character balances wrapped mid-number at the default size.

The balance now spreads the shared `{...HERO_AMOUNT_FIT}` props (`numberOfLines={1}`, `adjustsFontSizeToFit`, floor 0.35) — the w4/done/005 precedent for the same stranded-sign symptom — so a too-wide figure shrinks instead of wrapping or ellipsizing. The `HERO_AMOUNT_FIT` docstring now names the table balance; the large-text stacked path is untouched and its tests still pass.

Regression tests: `mobile/src/__tests__/account-table-dynamic-type.test.ts` gains a default-size block asserting the balance element carries the fit spread and no `ellipsizeMode`. Verified the spread assertion fails with the fix reverted and passes with it applied.
