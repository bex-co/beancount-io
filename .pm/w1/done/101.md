# Plugin failures lose the exception type and point at the wrong `plugin` line

**Severity: minor. Owner: cli. Estimate: 20–30m. A1:** agents fix plugin config from the reported cause and location. Continuous CLI QA, 2026-10-03 (round 5); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with a working control.

```sh
printf '__plugins__=["boom"]\ndef boom(e,o):\n    raise ValueError("Bad account mapping:\\n  Assets:Old -> ?")\n' > boom.py
printf 'option "insert_pythonpath" "TRUE"\nplugin "boom"\n2024-01-01 open Assets:Cash USD\n' > main.bean
bea --json --file /abs/main.bean check
```

Actual: `main.bean:2: Plugin "boom" failed while running: Assets:Old -> ?.` — the exception type and first message line are gone. With a plugin `cfgp` that fails only for config `"bad"` and the lines `plugin "cfgp" "good"` (line 4) / `plugin "cfgp" "bad"` (line 5), the error points at line 4. The same strings appear in `query`/`list`/`report` stderr banners.

Expected: `ValueError: Bad account mapping: …` against lines 2 and 5; native `bean-check` prints the full exception, and `format_error` documents keeping the "final exception line".

Cause: `cli/src/bea_engine/query.py:895–898` keeps only the last non-empty traceback line (wrong for multi-line messages and exception notes); `:913–920` (`_plugin_directive`) returns the first textual `plugin "name"` match, ignoring config. From `0f7fac5f` (`w1/done/m25/t004`).

Fix/acceptance: take the cause from the exception header line after the last `File …` frame (keeping the whole block), or carry the exception summary out of the loader; locate the directive by name and config in loader order. Both fixtures render `ValueError: Bad account mapping:…` at lines 2 and 5.

Dedupe: `w3/232`, `w3/359` cover different plugin-message issues.

---

**Resolved 2026-10-04** — plugin failures now keep the exception type and full message and point at the `plugin` directive whose config failed, not the first one with that name; the loader error is recorded only during the plugin loop so the load cache still pickles. `tests/test_plugin_failure_details.py` covers it. Shipped in the commit that moved this note (`cli`).
