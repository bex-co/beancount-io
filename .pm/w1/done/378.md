# Three `bea update` refusals mislead: a ledger with an existing error gets a bare `main.bean: 1 error(s).` with no `--allow-errors` remedy, a one-row JSON object is parsed as CSV columns, and a numeric `id` is told the row has no `id`

**Minor · cli · 20–30m · A1.** Routine cli-qa, 2026-11-23, HEAD `8105b095f`, checkout `bea 0.5.0` (`uv run bea`), macOS 26.5.1, Python 3.12.14, managed engine 0.5.0. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed, no TTY, fresh process per run. Every refusal below writes nothing (`cmp` against the pristine file). No product fix implemented.

`bea update` is how an agent clears the review queue `bea import` leaves. In all three cases the command refuses correctly, but its text sends the agent somewhere else.

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Equity:Opening USD

2026-01-01 * "Open"
  Assets:Checking  100.00 USD
  Equity:Opening

2026-01-05 ! "Lunch"
  bank_id: "TX-1"
  import-id: "bank:TX-1"
  Expenses:Uncategorized  4.50 USD
  Assets:Checking

2026-01-06 ! "Dinner"
  transaction_id: 12345
  Expenses:Uncategorized  6.00 USD
  Assets:Checking

2026-01-31 balance Assets:Checking 90.00 USD
EOF
bea update transaction --id TX-1 --account Expenses:Food                           # (1)
bea add note --date 2026-01-06 -a Assets:Checking -m hi                            # (1) control
sed -i.bak '/balance/d' main.bean                                                  # the rest on a valid ledger
echo '{"id": "TX-1", "account": "Expenses:Food"}' > one.json
bea update transactions --from one.json                                            # (2)
echo '[{"id": 12345, "account": "Expenses:Food"}]' | bea update transactions --from -   # (3)
```

1. **A ledger that already fails.** Exit 1 with `Error: /…/main.bean: 1 error(s).` and the failing assertion, nothing else; `--json` carries the same bare message. It does not say nothing was written or how to proceed. The control, `bea add note` on the same books, says `The ledger already has 1 error(s); nothing was written. Pass --allow-errors to write anyway.`, and so does `bea import`. `bea update transaction … --allow-errors` does preview the change, so the remedy exists; the refusal just never names it. A statement assertion that fails until the queue is categorized is the common way to get here.
2. **A one-row JSON object.** Exit 2 with `'one.json' (from --from) has unknown column '{"id": "TX-1"', '"account": "Expenses:Food"}'; use id, account, flag.`: a JSON file is read as CSV and its text quoted back as column names. The array form (`[{…}]`) previews the change. `bea add transactions` answers the same object with `JSON file must contain an array of transactions.`
3. **A numeric id.** The row is rejected with `Row 1: An update needs an 'id': an import-id, a ref, a bank ID, or file:line.`, while the table's ID column shows `12345`. The same row with `"id": "12345"` previews the change. A Python importer that keeps an `int` writes `transaction_id: 12345`, and `bea --json list transaction` returns it as `{"kind": "number", "value": "12345"}`, so an agent copying that ID is likely to send a number.

Expected:

1. The refusal reads like every other writer's: `The ledger already has N error(s); nothing was written. Pass --allow-errors to update anyway.`, with the same details, and for a syntax error the `Fix the syntax error first` wording `add` uses. Text and `--json` agree.
2. Content that opens with `{` is JSON: refuse it with the array message `_rows_from_json` already has (`must hold an array of rows, or CSV with an id column`), or accept a single object as a one-row batch.
3. A JSON integer `id` is read as its decimal text, as the CSV form reads every id as text. Any other non-string `id` (a float, `true`, an object) is refused, naming the field and its type, instead of saying the `id` is missing.

Cause:

- (1) `cli/src/bea_engine/ledger/updating.py` `_gate_load_errors` (`:372`) raises `LedgerError(f"{file}: {len(errors)} error(s).")`, the wording `bea check` uses (`cli/src/cli/commands/check.py:194`). It is called from `:1201`, `:1454` and `:1486`, so `update transaction` and both batch paths share it.
- (2) `cli/src/cli/commands/update.py` `_load_mapping` (`:244`) treats content as JSON only when it starts with `[` (`:253`). Everything else goes to `_rows_from_csv`, so `_rows_from_json`'s non-array refusal (`:186`) cannot be reached for an object.
- (3) `cli/src/bea_engine/ledger/updating.py:330-334` refuses any `id` that is not a `str` with the "needs an 'id'" text.

Fix: as Expected. Keep the batch's per-row reasons and `--partial`-style exit codes as they are.

Dedupe: searched `.pm/**` for `error(s).`, `_gate_load_errors`, `needs an 'id'`, `unknown column`, `--from`, `update transactions` and `JSON object`. w1/275 (done) covers located loader errors under `--into`, w1/353 (done) the batch preview's exit status, w5/1027 and w5/1037 (done) CSV column repeats and quoted line breaks. No item covers these three messages.

Acceptance: each command above, rerun on the same fixture, prints the expected text (text and `--json`), writes nothing, and keeps its exit code (1, 2, and 0 for the preview). Tests pin all three. `bea update transaction … --allow-errors` still previews on the ledger in (1).

---

**Resolved 2026-11-23** — The three `bea update` refusals now point the caller at the fix, shipped in the commit carrying this note (`cli`). (1) `_gate_load_errors` (`cli/src/bea_engine/ledger/updating.py`) raises the shared `preexisting_refusal` that `add` and `import` use, so `update transaction` and both batch paths say `The ledger already has 1 error(s); nothing was written. Pass --allow-errors to write anyway.` with the same located details, text and `--json` alike. A syntax error gets the `Fix the syntax error first` wording and an invalid pad the pad wording, each true for update, whose `--allow-errors` already refused both. The remedy reads "write anyway", as every other writer and update's own batch rows say, not the note's suggested "update anyway". (2) `_load_mapping` (`cli/src/cli/commands/update.py`) treats content opening with `{` as JSON, so a one-row object gets `must hold an array of rows, or CSV with an id column.` (exit 2) instead of being quoted back as CSV columns. (3) `_validate_request` reads a JSON integer `id` as its decimal text, so `[{"id": 12345, …}]` previews and applies against `transaction_id: 12345`. A float, boolean, object or array is refused as `'id' must be text or a whole number, not the number 1.5.` (or `the boolean true`, `an object`, `an array`), and a rejected float id is echoed as typed rather than as `JsonFloat('1.5')`. A missing or empty id keeps its message. `cli/docs/USAGE.md` says a one-row mapping is still an array and an id may be a whole number. Regression tests: `cli/tests/test_update_refusal_wording.py` (18 cases: the note's three commands in text and `--json`, the batch gate, the syntax-error wording, every rejected id type, and controls showing `--allow-errors`, the array form and a missing id unchanged), 14 failing with the source change reverted. Each refusal writes nothing, and exit codes stay 1, 2 and 0. `make check-all` green.
