# `query --source` forwards the query without `--`, so a dash-leading query injects `--output=` past the guard

**Severity: major. Owner: cli. Estimate: ~20m. A1:** argument forwarding must never let data become options. Continuous CLI QA, 2026-10-03 (round 12); report and filing only, no product fix applied.

Environment: `main` HEAD `97dab6b0`, checkout `cli/.venv/bin/bea` 0.3.1, Python 3.13, macOS 26.5.1 arm64. Fresh process per command with timeouts, isolated `HOME`/`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, notifier disabled, no inherited `BEA_FILE`/`BEA_TOKEN`/`CI`, synthetic fixtures, stdin closed. Reproduced at least twice with before/after hashes and a working control. Found by a regression hunt over shipped fixes.

```sh
echo 'SELECT account' | bea query --source main.bean -- '--output=main.bean'
```

Actual: exit 0 and `main.bean` is replaced by the stdin query's table — native `bean-query`'s Click parses the positional as `--output`, then reads the query from stdin; bea's `_refuse_source_alias` never sees that destination.

Expected: the string is treated as a query (bad BQL, non-zero exit) or refused; ledger unchanged.

Cause: `cli/src/cli/commands/query.py:242–244` builds `native_args = [*rendering, source, query_string]` without a `--` separator; a `source` beginning with `-` is equally exposed (also in the `source-shell` argv). Gap in `e168b0aa` (`w4/done/181`).

Fix/acceptance: `[*rendering, "--", source, query_string]` and the same `--` for `source-shell`. The repro exits non-zero or is refused with the ledger hash unchanged; normal `--source` queries unaffected. Same class as [141](./141.md).

---

**Resolved 2026-10-04** — a dash-leading query is now always BQL on every `bea query` path (a syntax error with exit 2, ledger unchanged): the `--file` and `source-shell` engine calls pass the query and source after `--`, and comment-leading native queries now run instead of silently exiting 0. `tests/test_query_dash_leading_query.py` covers it. Shipped in the commit that moved this note (`cli`).
