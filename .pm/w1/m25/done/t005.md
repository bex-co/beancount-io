## Objective

Several filters treat an empty string as a wildcard because the implementation is a substring test, so a template hole or an unset shell variable silently returns everything instead of nothing or an error — and a few flags silently fall through to a default.

## Context

- `w3/286`, `w3/287`, `w3/294`: `list transaction --search ''`, `list … --account ''`, and `balance ''` match every row because `'' in text` is always true; whitespace-only values correctly return nothing.
- `w3/333`: `list transaction --tag ''` / `--link ''` poison combined filters to zero rows.
- `w3/335`, `w3/327`, `w3/328`: `report -a ''` silently means unfiltered, `-t ''` silently means all-time, and `-x ''` silently uses the default conversion.
- Filters live in `cli/src/cli/commands/list.py`, `report.py`, and the engine's listing code.

## Steps

1. Reject an empty or whitespace-only value for every filter flag with exit 2 and the flag named, in human and `--json` mode.
2. Apply one shared validation helper so the behavior cannot drift between `list`, `report`, and `balance`.
3. Make the flags that silently fall back to a default (`-t`, `-x`, `-a`) refuse the empty value rather than choosing for the caller.
4. Keep legitimate values, including values that happen to be a single character, working unchanged.

## Files

- cli/src/cli/commands/list.py
- cli/src/cli/commands/report.py
- cli/src/cli/utils.py
- cli/tests/test_input_feedback.py

## Acceptance criteria

- [ ] Every listed flag exits 2 for an empty value, naming the flag; none returns a full or empty result set instead.
- [ ] Whitespace-only values behave identically to empty ones.
- [ ] Combined filters behave predictably: no empty value poisons a combination.
- [ ] Non-empty filter behavior is unchanged across `list`, `report`, and `balance`.

## Out of scope

- Filter semantics themselves — substring versus regex matching (`w3/334` and the report account-scope defects are separate).
- The `report -a` counterparty-posting defect (`w3/322`), left to `/loopx w3`.
