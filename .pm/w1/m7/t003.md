## Objective

Lock in that the mobile interaction completes from the login result alone, keep refresh tokens flowing, and tell self-hosters why the request still carries `prompt=consent`.

## Context

- `oidc-provider` strips `offline_access` unless `prompt` contains `consent`; the app therefore keeps sending it (`mobile/src/common/oauth/authorization-url.ts` explains this). The provider's `native_client_prompt` check is satisfied by the `consent.grantId` the single interaction POST already returns.
- `oidc-route.test.ts` has a case proving no refresh token is issued without `prompt=consent`; it must keep passing.
- `mobile/README.md` "Mobile OAuth contract" and `backend-cluster/backend-v2/README.md` describe consent as a step today.

## Steps

1. Add a backend test: a mobile authorization completes to a code + refresh token when the interaction result comes straight from the login POST (no separate consent submission), and the grant carries exactly the requested resource scopes.
2. Reword both READMEs: first-party client, no consent screen, `prompt=consent` is a refresh-token requirement of the provider, not a UI promise; the one-tap signed-in path and its rationale.
3. Confirm the MCP and identity consent flows are untouched (existing tests).
