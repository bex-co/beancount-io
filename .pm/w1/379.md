# A day-first bank's next export with no day past the 12th is booked month-first: `bea import` keeps no record of the convention the last file proved, and calls its fresh guess "remembered"

**Major · cli · 45–60m · A1.** Routine cli-qa, 2026-11-23, HEAD `8ca0e9c13`, checkout `bea 0.5.0` (`uv run bea`), macOS 26.5.1, Python 3.12.14, managed engine 0.5.0. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`/`BEA_ENGINE_DIR`, no `BEA_FILE`/`BEA_TOKEN`, stdin closed, no TTY, cwd the ledger folder. Reproduced twice from pristine fixtures, each run in a fresh process. No product fix implemented.

A UK bank exports `DD/MM/YYYY`. The July export has days past the 12th, so `bea import` reads it day-first, which is correct, and the user had no reason to pass `--date-format`. The August export covers only 3–11 August. Run flag-free for the same header and account, it is read month-first and written with exit 0: 3 August becomes 8 March, 7 August becomes 8 July, and 11 August becomes 8 November. The settings line says that month-first format was "remembered from july.csv", but July was read day-first.

```sh
mkdir books && cd books
cat > main.bean <<'EOF'
option "operating_currency" "GBP"
2026-01-01 open Assets:Current GBP
2026-01-01 open Expenses:Uncategorized GBP
EOF
printf 'Date,Description,Amount\n14/07/2026,TESCO,-12.40\n21/07/2026,PRET,-6.10\n28/07/2026,BOOTS,-9.99\n' > july.csv
printf 'Date,Description,Amount\n03/08/2026,TESCO,-15.20\n07/08/2026,PRET,-5.80\n11/08/2026,BOOTS,-4.25\n' > august.csv
bea --file main.bean import july.csv --account Assets:Current --apply   # (1)
bea --file main.bean import august.csv                                  # (2)
bea --file main.bean import august.csv --apply                          # (3)
bea --file main.bean list transaction --sort oldest                     # (4)
```

Actual:

1. Exit 0. `Read the column mapping from the header row: --csv date=Date,amount=Amount,narration=Description --date-format %d/%m/%Y.` The rows are dated 2026-07-14, 21 and 28 (correct). The remembered record under `importers/` stores `"date_format": null`.
2. Exit 0, stderr:
   `Using settings remembered from july.csv for august.csv: --csv date=Date,amount=Amount,narration=Description --account Assets:Current --date-format %m/%d/%Y.`
   `Dates parse as %m/%d/%Y but the column has no day past the twelfth, so day-first and month-first cannot be told apart. Pass --date-format if that is the wrong reading.`
   The preview rows are dated 2026-03-08, 2026-07-08 and 2026-11-08. Under `--json`, `data.remembered` reads `{"source": "july.csv", "date_format": "%m/%d/%Y", …}`.
3. Exit 0, `Wrote 3 entries`.
4. The ledger holds TESCO on 2026-03-08, PRET on 2026-07-08 and BOOTS on 2026-11-08 beside July's rows. `bea check` exits 0, so nothing downstream catches it.

Control: the same three commands with `--date-format %d/%m/%Y` typed on (1) book August as 2026-08-03, 07 and 11, and (2) then says `--date-format %d/%m/%Y`. Run (1) prints the same `Read the column mapping … --date-format %d/%m/%Y` line in both cases, so the user cannot tell from it whether the next export will be read the same way.

Expected: one source account's exports share one date convention. When a run proved its convention (the column was not ambiguous), a later flag-free run of the same remembered mapping (same root, header and account) whose column is ambiguous should read it the same way, `%d/%m/%Y` here, and say that the earlier file is the reason. A file that unambiguously proves another convention still wins, so w3/308's concern (two exports sharing a header but not a convention) stays covered. Separately, a format inferred for the current file must never be printed as one of the settings "remembered from" another file, or reported in JSON `remembered.date_format`. `docs/IMPORTING.md` says the ambiguity note exists so that bea "says so instead of choosing quietly". Here the remembered line hides the guess behind the earlier file's name.

Cause: `cli/src/cli/commands/import_.py`:

- `:1196-1199` keeps only a typed format (`chosen_date_format = date_format`, with the comment "An inferred one belongs to the file it was read from"), and `:1767`/`:1801` store `kept_date_format`, which is None for July.
- On the August run, nothing is recalled. `:1654-1692` re-infer through `inspect_date_column` (`cli/src/cli/csv_mapper.py:948`), and an ambiguous column takes the first candidate in `_DATE_FORMATS` (`:435`), which is month-first. `:1690` adds only the generic note.
- `settings_notes` (`:1214`, `:1233-1243`) lists that fresh `date_format` among the remembered settings, and `json_remembered` (`:1967`) reports it as `remembered.date_format`.

`docs/IMPORTING.md:414` documents "Only a `--date-format` you passed is remembered".

Fix: in the remembered CSV record, store the format a run's dates proved unambiguously, in a field of its own (a tie-breaker, not a typed setting). On recall, when the new column is ambiguous between that format and another, read it with the stored format and note `read day-first as july.csv was (--date-format %d/%m/%Y)`. When the new file is unambiguous, use what it proves; if that differs from the stored format, add a note saying the convention changed. Keep a typed `--date-format` authoritative, along with its current re-validation (w3/308, w5/267, w5/911, w5/1087). Print an inferred format outside the "remembered from" sentence, and keep it out of JSON `remembered.date_format`, so the line states only what memory supplied. Update IMPORTING.md's memory paragraph.

Blast radius: every flag-free CSV import whose remembered mapping came from a run without `--date-format` and whose next file has no day past the 12th. That covers weekly or mid-month exports from any day-first bank, in `DD/MM/YYYY`, `DD/MM/YY` or `DD-MM-YYYY`, since each has a month-first twin listed ahead of it in `_DATE_FORMATS`. `DD.MM.YYYY` has no twin and is read correctly. Month-first banks are unaffected, because the tie already breaks their way. OFX and Python importers are unaffected, because they date rows themselves. The `Using remembered settings for <file>` form of the line (same file name) has the same mislabel.

Dedupe: searched `.pm/**` for `day-first`, `month-first`, `twelfth`, `%d/%m/%Y`, `date-format` with `remember`/`infer`. Related, all done: w5/267 (a typed format erased by an explicit refresh, so the next ambiguous file is read month-first; fixed by keeping the typed format), w3/308 (a typed format poisoning another convention; re-validation added), w5/911, w5/1087, w4/176 (evidence past 200 rows). None covers an inferred, proven format being dropped, or the settings line labelling a fresh guess as remembered. No open item overlaps.

Acceptance: in the fixture above, (2) previews and (3) writes 2026-08-03, 07 and 11 with no `--date-format` typed, with a note naming july.csv as the source of the day-first reading. A third file `15/09/2026` still imports as 2026-09-15. A month-first account (`07/14/2026` then `08/03/2026`) still books 2026-08-03 as 3 August. A file that unambiguously proves the other convention (`08/13/2026` after July) imports as it reads, with a note that the convention changed. No inferred format appears in a "remembered from" line or in `remembered.date_format`. A regression test pins the July → August sequence and fails with the change reverted.
