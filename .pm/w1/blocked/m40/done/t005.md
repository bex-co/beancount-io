## Objective

Send one confirmation email when a downgrade or switch to monthly is scheduled, and one reminder before it takes effect, as PRFAQ005 question 17 describes. Both state the effective date, what changes and how to keep the current plan.

## Context

- Transactional email: `backend-cluster/backend-v2/src/foundation/sendgrid.ts` and `backend-cluster/backend-v2/src/shared/email-templates/`, matching the dashboard's visual language (w1/m9).
- The backend has no scheduler. Stripe's `invoice.upcoming` webhook fires a configurable number of days before the renewal a scheduled change takes effect at. t006 sets that to seven days.

## Steps

1. Send the confirmation from the scheduling path, after the schedule is stored.
2. On `invoice.upcoming` for a subscription with a scheduled change, send the reminder.
3. Make both idempotent across webhook retries and repeated schedule edits, and follow the existing templates' locale handling.

## Files

- `backend-cluster/backend-v2/src/features/stripe/`, `backend-cluster/backend-v2/src/shared/email-templates/`

## Acceptance criteria

- [x] Exactly one confirmation per schedule, and one reminder per upcoming invoice that carries a scheduled change. Retried deliveries send nothing new.
- [x] No email is sent when nothing is scheduled, and templates render in each supported email locale.

## Out of scope

- Renewal reminders for unchanged yearly plans; those are Stripe's emails (t006).

## Outcome — 2026-10-18

- **Template** `plan-change.template.ts` (HTML and text, shared theme, escaped values, validated link) has two kinds.
  - **Confirmation:** the effective date, current → new plan, nothing charged today.
  - **Reminder:** that renewal is billed at the new plan's price.
  - Both list the limits that move (from → new), say nothing is deleted, and link to Billing settings to keep the current plan. The link is `SUBSCRIPTION_CONFIG.portalReturnUrl`.
  - Transactional email is English-only today, so that is the one supported email locale. Both kinds are in the committed preview.
- **Confirmation path:** `applyPlanChange` reports what it scheduled (schedule, current price, the new change and the change it replaced), so no extra Stripe read is needed. `SubscriptionService.changePlan` takes that off the API result, then emails only when the pending change actually changed: a double click sends nothing. A failed email is logged, and the change still succeeds.
- **Reminder path:** the webhook handles `invoice.upcoming`.
  - It leaves another product's renewal (the shared account) before any lookup.
  - It finds the binding, reads the subscription with its schedule, and reminds only when the scheduled change lands at this renewal (`changeAtRenewal`).
  - A failed send answers with an error so Stripe redelivers.
- **Once only:** a `sent_billing_emails` claim table (migration 0023) is keyed by kind, schedule, scheduled price and date.
  - A confirmation's key also names the change it replaced, so A → B → A announces all three, while confirming A twice announces it once.
  - The recipient lookup and rendering happen before the claim, so nothing that can throw sits between claiming and sending. A failed send gives the claim back.
- **Tests:** the operation, the template, the service path and the webhook path are covered, including retries, A → B → A, a missing recipient, a lookup failure, a send failure, a change at a later renewal, and another product's invoice. The guards were mutation-checked.
- **Depends on t006 only for timing:** Stripe sends `invoice.upcoming` the configured number of days before renewal, and t006 sets that to seven. `invoice.upcoming` is already enabled on the live webhook.
