## Objective

Make the shipped change discoverable and accurate on every surface it exposes, including the agent-facing limit errors.

## Context

- Surfaces:
  - the Billing tab, the banner and the emails;
  - `dashboard/docs/event-taxonomy.md`;
  - the authorization rows in `backend-cluster/backend-v2/authz/README.md`;
  - the ledger-count and collaborator errors, as GraphQL, REST and MCP clients and `bea` see them;
  - [PRFAQ005](../../../../../docs/prfaqs/PRFAQ005-plan-changes-and-yearly-billing.md).
- Agent-facing errors must read the same for Claude Code and Codex users, because they come from the same API.

## Steps

1. Check that the CLI and the customer skills render the new resource-limit errors sensibly. Flag any drift in `skills/` or `cli/` as follow-up work.
2. Add rows for the new operations to the authorization table.
3. Record in the PRFAQ's status line that stage 2 has shipped, citing the commit.

## Outcome — 2026-10-18

- **Authorization table:** `user.billing.plan_change.cancel` (`cancelScheduledPlanChange`) is listed, browser-session-only. m40 adds no other operation; "keep current plan" is that same mutation.
- **Event taxonomy:** the stage-2 lifecycle is documented: `plan_change_scheduled`, `plan_change_reverted`, `cancel_started`, `cancel_confirmed{reason}` and `subscription_resumed`. The failed-renewal banner and the emails add no event.
- **Emails:** the plan-change template is in `src/shared/email-templates/README.md` and the committed preview.
- **Limit errors** are now one shape on every surface: `RESOURCE_LIMIT_REACHED`, HTTP 403 on REST, and the same code on MCP and GraphQL. A parity test pins the collaborator case.
  - This review made both messages name the plan that sets the limit. A ledger refusal used to tell a Premium user to "Upgrade to Premium". It now reads "You own 5 ledgers, the most your Premium plan allows…". The collaborator message is grammatical for one ("1 collaborator").
  - Two clients reword the error; that is [w1/181](../../../done/181.md): `bea` frames it as "Not authorized", and the dashboard tells an admin on someone else's ledger to upgrade.
  - The customer skills do not special-case limit errors. They pass the server's message through.
- **PRFAQ005:** the status line records that stage 2's code is on `main`, through `87eac2708`, and that its deploy, Dashboard settings and production test are pending.
