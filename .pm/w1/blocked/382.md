# Codex swaps in another `bea` when the installed one fails, and once rewrote the generated `AGENTS.md`

**Skills · minor · 45–60m · A1.** Found by the w1/m42/t006 Codex rehearsal, 2026-11-25 (Codex CLI 0.171.0, `gpt-6.2-sol`, macOS, published `bea` 0.5.0, revision `62d57e694`).

`beancount-init/references/compatibility.md` says: "An installed but failing `bea` is repaired, not swapped for another engine." Codex did the opposite three times when the `bea` on its `PATH` could not serve a command:

1. **Old `bea` first on `PATH`** (setup prompt `init-existing-books-here`): the login shell resolved a `bea` 0.3.0 without `init --existing`. Codex searched the disk, found a development checkout's `bea`, and ran `init --existing` with it.
2. **Engine not yet provisioned** (same prompt, published 0.5.0 from `uv tool install`): `bea` answered `Could not install the hash-pinned engine packages (uv exited 2)` because Codex's sandbox has no network. Codex again ran a checkout `bea`, then **edited the `AGENTS.md` that `bea` had just written** to tell later agents to use that checkout. The skill says the generated file is `bea`'s, and the user expects no file to change except the two agent files `bea` writes.
3. **No temporary directory under `--sandbox read-only`** (question turn): `bea query` failed, and Codex ran the engine's raw `bean-query` instead. The figure was right, but `bea`'s plugin handling, JSON contract and checks were skipped.

Ledger files were unchanged in every case (checksums matched).

**Expected:** when the installed `bea` fails, the agent reports the failure and the one step that repairs it, and stops. For an engine that cannot provision: run any `bea check` once in your own terminal (the network is needed once). For a missing temporary directory: the scratch-only Codex profile (`docs/skills/first-query.md`). For an old version: `bea upgrade`. It never runs another `bea`, `bean-query`, or a checkout found on disk, and never edits a generated agent file.

**Where to look:** `skills/beancount-init/references/bea-cli.md` (the version and failure guidance agents read first), `references/compatibility.md`, and `beancount-ask`'s pointer to the developer fallback in `references/bql-recipes.md`. Consider also whether `bea`'s provisioning error should name the fix itself ("needs the network once; run `bea check` outside the sandbox"), so every agent relays it (`cli/src/cli/engine/provision.py`).

**Verify:** a Codex run with the fresh `bea`'s engine unprovisioned stops with the repair step and does not run another engine. Rerun the m42 routing entries and the existing-ledger question on both clients after any skill text change.
