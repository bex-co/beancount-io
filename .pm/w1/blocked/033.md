# Slice-delete success precedes removal by minutes; refetch resurrects the row

**Severity:** major. **Estimate:** 2–4 hours (backend async-application visibility plus mobile resurrect handling). Owner: backend, with a mobile companion. A2 — tapping delete must read as deleted; a row that comes back minutes later reads as data loss in reverse.

Environment: 2026-09-16, main `10465c05`, native development build `io.beancount.ios` on iPhone 17e / iOS 26.5 (sole booted simulator, light appearance), Metro over localhost:8081, English. Authenticated QA session against `https://beancount.io/`. Writes: synthetic probes only (one $0.01 transaction, one $0.01 Health-yearly budget, one file, one opened-then-closed account), all reverted same session.

Repro (ledger `puncsky/example` throughout; entry case):

1. Save a $0.01 probe transaction (payee `QALOOP3`), note its `entryHash` (`0bde0bd3…`), then delete it via `deleteLedgerEntrySourceSlice` with a fresh `sha256sum`. At 23:55 the server returns success with message `Deleted entry 0bde0bd3cf5f0b8c566d2e418c0a10ab`.
2. At 23:57 a cold restart + fresh Transactions mount still lists the probe at the top. At 00:02 `getLedgerEntryContext` for the deleted hash still resolves the full entry. Only by 00:04 does a `network-only` context query come back empty, and only by ~00:29 is the journal row gone.
3. Same shape for a `custom "budget"` probe: delete accepted ~00:16, context still present 15s later, gone by ~00:26 with neighbors intact (2 pre-existing monthlies untouched).

Expected: a success response means the slice is gone from subsequent reads (or the API says it is still applying). Actual: success precedes removal by ~5–9 minutes, and the journal stays stale after the file is clean — every slice delete the session issued lagged.

Mobile impact (verified, no crash): the app's post-delete refetch (`invalidateLedgerData(client, "entries")`) repaints the resurrected row; tapping it renders the stashed entry (stale paint, looks alive); Edit/Delete correctly no-op once `sha256sum` resolves null, but silently. So the user-visible sequence is delete → toast success → row returns → row opens showing the "deleted" entry.

Root: server-side `deleteLedgerEntrySourceSlice` applies asynchronously (or behind a journal materialization lag) while reporting synchronous success. Not investigated from here whether the lag is a queued worker, replica lag, or journal cache TTL — the file (`main.bean` tail) still held post-probe lines ~5 minutes after the success response, and the journal lagged the context query further still.

Fix: backend — make the delete response truthful (apply synchronously, or return a pending state the client can honor). Mobile companion — bridge the window: keep the deleted row optimistically removed across refetches until a server read confirms it back, and surface the pending state on the detail screen instead of a silent no-op. Do not weaken the `sha256sum` optimistic lock or the existing invalidation call sites.

Blast radius: the slice-delete path shared by transaction delete (`transaction-detail-screen`), budget delete (`use-delete-budget-entry`), and any future caller. Entry save, budgets save, file create/delete (synchronous in this session), and account open/close are untouched.

Adjacent states: delete-then-immediately-edit, delete with a changed-underneath file (lock failure messaging), offline delete queueing if any.

Dedupe: searched every queue including `done/` for delete lag/async delete/resurrect/reappear/stale journal/eventual. `w3/done/115` is an account-filter leak across ledgers; `w3/m30` filter pagination hides stale settled results (distinct cause); `w1/done/m10/COVERAGE.md` rows are API-parity gaps for unrelated delete mutations. No duplicate found.

Acceptance: delete an entry and a budget directive; within the same minute a fresh journal mount and a `network-only` context query both agree the slice is gone, and the list never repaints it. If async application stays, the UI instead shows the pending state until convergence. Add contract coverage asserting read-after-delete consistency inside an explicit bound.

Unverified: whether all slice deletes lag or only under load; exact lag distribution; other ledgers/locales; Android.

Evidence (gitignored, local only): `mobile/tmp/qa-2026-09-15/125-deleted.png` (server DELETED), `132-fresh.png` (row persists post-restart), `137-ctx.png` vs `138-retry2.png` (context alive → gone), `147-bdel2-small.png` → `155-blist-small.png` (budget STILL PRESENT → PROBE GONE, neighbors intact), `154-budget2-small.png` (yearly card converged away). All probes reverted; no residue.
