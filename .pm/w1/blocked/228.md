# Idea: give agents the write primitives a hosted session keeps reaching for

**Idea · backend-v2 · A1 · needs /pm-brainstorm before sizing.** From `/qa-find-bugs-mcp` 2026-11-10. An MCP-only agent completed six realistic requests on the QA ledger, and every one of them could be done, but several only through workarounds. None of these primitives exist on any surface, so they are not parity gaps.

- **Write results carry no commit sha.** `diff` is empty on commits. To undo "the last change I made", the agent has to infer the commit from the commits list, which is racy with other writers, and then reverse-apply the commit-details diff by hand.
  - A `commit` field on every write result is the small, concrete step. A `revertCommit` tool, or a read at a ref, is the larger one.
- **Account rename.** It is only possible as a whole-file rewrite, because `old_string` must match exactly once. w2/m46 covers renames in the local `bea` skill only.
- **Moving entries between files.** Deleting first, or including first, each previews `valid:false` whenever a balance assertion spans the move. Only "create the file, then rewrite the whole main file" works, and it leaves an orphan file in between (see w1/227). The one atomic multi-file path, `createPullRequest`, is blocked (w3/645).
- **Bulk source reads.** Collecting the source of 8 entries took 8 `getEntryContext` calls, because `listLedgerEntries` returns no source text.

**Blocked 2026-11-10.** Triaged against `main`, this note is still an idea with no sizing; it asks for `/pm-brainstorm` before any work.
- **First bullet:** the commit sha on write results and the revert have since been sized and routed by the user to `w23/m42`, "Name the commit every write makes, and let an agent undo it" (commit `0cfeaaf73`). That half is that milestone's work, not this note's. **Shipped 2026-11-10** in `c70a9ff93` and `4d541a5ab`: every write that commits returns its `commit` sha on REST, GraphQL and MCP, and `revertCommit` undoes one with a preview.
- **Other three:** account rename, an atomic move of entries between files, and bulk source reads from `listLedgerEntries` are not in any milestone. No surface has them, so they are not parity gaps, and nothing on the board decides whether they are wanted or how large they are.

**Unblock:** the user runs `/pm-brainstorm` on the three remaining primitives, or routes or drops each of them. A routed primitive becomes its own note or milestone; once all three are decided, this note closes. Cleared by the user (product decision).
