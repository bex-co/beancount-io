## Objective

A Plaid account mapped to the renamed account, or to one under it, maps to the new name after the commit, so the next bank sync does not post to an account that no longer exists.

## Context

- `ledger_account` on `plaid_accounts` (`src/features/plaid/data/plaid-account-model/schema.ts`) holds the mapped ledger account; `mapBankAccount` sets it.
- `syncBankTransactions` and `importStagedBankTransactions` write to the mapped account.

## Steps

1. In the rename workflow, list the ledger's mappings that name the old account or a descendant, and include them in the preview.
2. After the commit succeeds, update those mappings. If that update fails, the result must say which mappings still name the old account, and the operation must report a failure rather than plain success.
3. Test a mapped account, a mapped descendant, an unrelated mapping, and a failed mapping update.

## Files

- `backend-cluster/backend-v2/src/features/plaid/`
- the rename workflow from t002

## Acceptance criteria

- [x] After a rename, every affected mapping names the new account, and the preview listed it first.
- [x] A mapping update failure is reported in the result with the mappings it left behind.

## Out of scope

- Mappings in other ledgers.

## Outcome — 2026-11-13

- **Port and adapter:** `AccountRenameWorkflow` takes an optional `LedgerBankMappings` port, defined in the ledger feature (`account-rename-workflow.ts`) and implemented by `PlaidLedgerBankMappings` (`src/features/plaid/service/plaid-ledger-bank-mappings.ts`).
  - The adapter resolves the ledger's repo id through the ledger service. It lists every member's mapped Plaid accounts via `plaidItem.getByLedgerRepoId` and `plaidAccount.getByItemId`, and updates them in one transaction with `updateForItem`.
- **Whose mappings (decision):** every member's mappings on the ledger, not only the caller's. A mapping names an account of *this* ledger, so leaving a collaborator's mapping on the old name would make their next sync post to an account that no longer exists.
  - The result names only the caller's own bank accounts (`Chase Checking ••1234`); another member's appears as a mapping with `plaidAccount: null`, so a rename never reveals someone else's bank.
- **Flow:**
  - Mappings are read before the commit, so a preview lists them with `updated: false`.
  - They are updated only after the files commit, and never when the rename is refused.
  - If the update fails, the commit stands, each mapping reports `updated: false`, and `message` ends "N bank mappings still name FROM: map them to TO with mapBankAccount".
- **Tests:**
  - Workflow (4 new): preview lists the account and its descendant but not a prefix neighbour or an unrelated one, and moves nothing; a commit moves both after the files commit; a failed update keeps the commit and reports what it left; a refused rename touches nothing.
  - Adapter (2): every member's mappings, named only for the caller; one transaction.
- Wired into the composition with the adapters in t004.
