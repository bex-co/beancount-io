# GraphQL file writes skip the bean-check gate and have no preview

**Parity bug · backend-v2 (+ dashboard decision) · major · ~1h · A1.** From `/qa-find-bugs-mcp`, 2026-11-09, production, introspection and source; no live invalid commit was run.

- **What happens:** the live schema's `createLedgerFile`, `updateLedgerFile` and `deleteLedgerFile` take no `dryRun`/`dry_run` and no `allowInvalid`/`allow_invalid`. Passing either is refused as an unknown argument (`GRAPHQL_VALIDATION_FAILED`).
  - On MCP (`create`/`update`/`deleteLedgerFiles`) and REST (`PUT`/`DELETE …/files/{path}`), a change that adds bean-check errors previews `valid: false` and is refused `VALIDATION_FAILED` on commit (w23/m15).
  - On GraphQL the same change commits with no check.
  - GraphQL `appendLedgerText(dryRun: true)` already follows the rule.
- **Contract:** `docs/mcp.md:376-388` ("The preview rule") and `docs/api-parity.md:240` say the rule is the same on all three surfaces.
- **Cause:** `gateFileWrite` (`src/features/ledger/utils/file-write-gate.ts:54`) is called only from the REST files handler (`:253`, `:323`) and the MCP edit tool (`:479`, `:513`). GraphQL `ledger-resolver.mutation.ts:96-145` calls `LedgerWorkflow.create`/`update`/`deleteLedgerFile` (`ledger-workflow.ts:1007+`), which never gates.
  - w23/114 recorded "GraphQL has no file-content writes at all", and w23/149, w23/197, w23/147 and w23/m15 repeated that N/A. These mutations have existed since the import, and the dashboard file editor saves through `updateLedgerFile`.
- **Fix:**
  - Add the flag pairs to the three GraphQL mutations. Move the gate into the shared file-write path so no adapter can skip it, and return `valid`/`newErrors` the way GraphQL `appendLedgerText` does.
  - Add GraphQL rows to `FILE_PARITY` in `write-preview-matrix.test.ts`.
  - Correct the w23/114 exception in the docs.
- **Owner decision first:** the dashboard file editor can save a mid-edit invalid state. Before gating, decide one of:
  - (a) the editor passes `allowInvalid: true`, which keeps today's behaviour with explicit intent;
  - (b) the editor adopts refuse-then-confirm.

**Blocked 2026-11-10** — confirmed still open on `main`. GraphQL `createLedgerFile`, `updateLedgerFile` and `deleteLedgerFile` declare no `dryRun`/`dry_run` or `allowInvalid`/`allow_invalid` arguments. `gateFileWrite` is still called only from the REST files handler and the MCP file tools, so a GraphQL file write commits with no bean-check gate. The work is not started, because gating GraphQL changes what the dashboard file editor does when it saves a mid-edit invalid state. The note names that as the owner's call. **Unblock:** the user picks the editor's behaviour once gated:
- (a) the editor passes `allowInvalid: true`, which keeps today's saves with explicit intent; or
- (b) the editor adopts refuse-then-confirm: show the new errors, and save with `allowInvalid` only after the user confirms.

The backend half is the same either way: the flag pairs on the three mutations, the gate moved into the shared write path, GraphQL `FILE_PARITY` rows, and the docs correction. Cleared by the user (product decision).
