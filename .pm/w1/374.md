# `bea update transactions` gets slower with every row times the size of the ledger: 2,000 rows that `bea import` wrote in 9 s take 280 s to preview, and one mistyped account makes a 500-row preview take 134 s instead of 11 s

**Bug · cli · major (time; the results are correct) · 45–60m · A1.** From routine cli-qa, 2026-11-23. The batch form is how the docs say to clear the review queue `bea import` leaves: "For a longer queue, `bea update transactions --from queue.csv` applies a whole `id,account,flag` mapping in one previewed write per file" (`cli/docs/IMPORTING.md`). Its run time grows with rows × ledger size, for two reasons. First, every row scans the whole ledger twice and diffs the whole file. Second, one rejected row makes the command reload and re-validate the whole ledger once per row. An agent recategorizing a statement goes past a coding agent's usual two-minute command timeout, and so does a person who mistyped one category. `bea add transactions` fixed the same per-row reload in w5/123, w5/537 and w5/720. On the same ledger it settles a 500-row batch with one bad row in 2 s.

Environment: main `3e21e42da`, `bea 0.5.0` from the checkout (`uv run bea`), managed engine 0.5.0, Python 3.12.14, macOS 26.5.1 (arm64, 28 cores; the engine is single-threaded). Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, fresh processes. Reproduced twice from fresh fixtures (11 s / 134 s here; 13 s / 132 s on a fixture with varied amounts).

## Repro

```sh
mkdir books && cd books
python3 - <<'EOF'
import datetime, json
lines = ['option "operating_currency" "USD"',
         '2020-01-01 open Assets:Checking USD',
         '2020-01-01 open Expenses:Uncategorized USD',
         '2020-01-01 open Expenses:Groceries USD', '']
for i in range(5000):
    day = datetime.date(2020, 1, 2) + datetime.timedelta(days=i // 5)
    lines.append(f'{day} ! "MERCHANT {i}"\n  import-id: "bank:TX-{i}"\n'
                 f'  Assets:Checking  -12.34 USD\n  Expenses:Uncategorized  12.34 USD\n')
open('main.bean', 'w').write('\n'.join(lines))
rows = [{"id": f"bank:TX-{i}", "account": "Expenses:Groceries", "flag": "*"} for i in range(4500, 5000)]
json.dump(rows, open('ok500.json', 'w'))
rows[0]["account"] = "Expenses:Typo"            # one mistyped category
json.dump(rows, open('typo500.json', 'w'))
EOF
time bea --json --file main.bean update transactions --from ok500.json >/dev/null
time bea --json --file main.bean update transactions --from typo500.json >/dev/null
```

## Actual

| Ledger (one file) | Batch | Time |
| --- | --- | --- |
| 5,000 transactions | 500 rows, all valid, preview | 11 s |
| 5,000 transactions | the same 500 rows, row 1 names `Expenses:Typo`, preview | **134 s** (499 ready, 1 rejected) |
| 5,000 transactions | 100 rows, one bad, `--apply` | 27 s, against 3 s with none bad (exit 1, 99 written, `bea check` clean) |
| 20,000 transactions | 1 / 50 / 100 / 200 valid rows, preview | 2.6 / 11.4 / 21.2 / 40 s; 200 rows with `--apply` 41 s |
| 22,000 transactions | 2,000 rows that `bea import … --apply` had just written in **9 s**, preview | **280 s** |

Controls: `bea add transactions --partial` with 500 rows on the same 5,000-entry ledger takes 2 s whether or not one row names `Expenses:Typo`, and the single-row `update transaction` on the 20,000-entry ledger takes 2.4 s. Every result is correct. The preview leaves `main.bean` byte-identical (same SHA-1 before and after), and the rejected row names `main.bean:…: Invalid reference to unknown account 'Expenses:Typo'`.

A cProfile of the engine for 50 valid rows on the 20,000-entry ledger (28.7 s) shows where the time goes. The per-row whole-file `unified_file_diff` takes 13.2 s, `entry_span` takes 6.0 s (1,987,700 `entry_generated` calls), and `locate_transaction` takes 4.8 s.

## Expected

A batch costs about one ledger load, plus work proportional to the rows, plus a small number of extra loads per rejected row, as `add transactions --partial` does since w5/720. A 2,000-row recategorization of a 20,000-entry ledger takes about as long as importing those rows. One bad row adds seconds, not one ledger load per row. The output must not change: the same per-row `diff`, `status`, `reason` and `details`, the same combined diff, and the same written bytes.

## Cause

All in `cli/src/bea_engine/ledger/updating.py`:

- `_plan_rows` (`:761`) calls `locate_transaction` (`:801`) for each row. That call recomputes `reader.shared_locations(entries)` (`:207`), runs `reader.entry_generated` over every entry to build `on_disk` (`:208`), and then scans every entry once per id tier.
- For each row, `plan_lines` (`:817`) calls `entry_span` (`:594`). That recomputes `shared_locations` (`:348`) and walks every entry again (`:350`) to find the next written line in the file.
- `_row_payload` (`:975`) builds a full copy of the file for each row (`:1015`) and runs `difflib.unified_diff` over the whole file (`:1024`, then `text.py:689`) to show a few changed lines.
- `_validate_plans` (`:874`): when the file's combined rewrite fails, every row of that file is validated alone with `_validate_text` (`:905`–`:918`). Each of those is a full ledger load, so one bad row costs a load per row. This is the pattern w5/123 removed from `add transactions` (`_named_rows` and `_refused_in_order` in `adding.py`).

## Fix

Owned by `cli`, engine side only.

- Compute `shared` and the on-disk transactions once per batch. Index the id tiers once (a value maps to the entries that hold it, per tier, keeping the refuse-if-shared rule). Keep each file's sorted on-disk line numbers so `entry_span` finds the next one with `bisect`. The single-row path can share these helpers.
- Build each row's diff from a window around its span, a few lines of context on each side with the hunk header offset, instead of diffing the whole file. The output must stay byte-identical, including the BOM and no-final-newline cases.
- On a failed combined validation, attribute the batch error's located lines to the rows whose spans hold them. Re-validate the rest once, and bisect only what cannot be attributed, as `adding.py` does. Keep the "valid alone, but … fail together" and cumulative-include reasons.
- Regression tests should count loads instead of timing them, so they do not flake. With one bad row among N, the number of `managed_load.load_file`/`validate_candidate` calls stays bounded, around log N, not N. `reader.shared_locations` runs once per batch. Existing batch tests keep their exact diffs. Revert each part and watch its test fail.
- Record before/after timings for the repro in the closeout text, then run `make check-all` in `cli/`. No REST, GraphQL or MCP surface rewrites local entries.

## Blast radius

`bea update transactions` with and without `--apply`, and with `--into`. Single-row `bea update transaction` does each scan once, so it pays one pass and no per-row multiplier. A ledger split across yearly files pays the diff cost per target file, but it still pays the per-row entry scans over the whole ledger. `bea import` and `bea add transactions` are the working controls.
