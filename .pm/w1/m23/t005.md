## Objective

Several one-shot `bea query` invocations do nothing and exit 0: a whitespace-only query, `.output PATH` with no query, `.run NAME` for a stored query that does not exist, a two-statement input where only the first runs, and an empty column SELECT that flips exit code with the format.

## Context

- `w3/262`: `bea query '   '` exits 0 with empty stdout, while `--json` and stdin whitespace correctly reject.
- `w3/277`: one-shot `bea query '.output PATH'` exits 0 after creating an empty file; no query ever runs.
- `w3/236`: `bea query '.run NAME'` for a missing stored query exits 0 with empty output.
- `w3/282`: two SELECT statements joined by `;` run only the first, exit 0, no warning.
- `w3/269`: `query --format beancount` on a column SELECT exits 0 with `(no rows)` when empty but exit 2 when rows exist.
- One-shot handling lives in `cli/src/cli/commands/query.py`; the engine side is `cli/src/bea_engine/query.py`.

## Steps

1. Reject a blank or whitespace-only query in every mode with the same exit code the `--json` path already uses.
2. Refuse a one-shot whose only content is a dot-command that produces no result, naming what was expected.
3. Make a missing stored query a nonzero error that lists the available names.
4. Either run every statement in a multi-statement input or refuse it explicitly; do not silently drop the tail.
5. Make the `--format beancount` exit code depend on whether the query succeeded, not on whether it returned rows.

## Files

- cli/src/cli/commands/query.py

## Acceptance criteria

- [ ] Each of the five reproducers exits nonzero with a message naming the cause, in human and `--json` mode.
- [ ] A valid query returning zero rows still exits 0 in every format.
- [ ] A multi-statement input either reports every statement's result or exits nonzero saying multi-statement input is unsupported.
