# `bea update transaction --apply` on an entry in a symlinked ledger file replaces the symlink with a plain copy: exit 0, but the real file never gets the edit, and every later write goes to the orphan copy

**Bug · cli · major · 30–45m · A1.** From routine cli-qa, 2026-11-23. Users keep a ledger file in a synced or shared folder and link it into the books: `~/books/main.bean -> ~/Dropbox/ledger/main.bean`, or a year file `2026.bean -> ../shared/2026.bean`. `USAGE.md` ("Choosing the ledger") promises that writes "land in that file through the link". w5/391's control also holds that "a symlinked target or include stays a symlink, and the write lands in the real file". `bea add`, `bea import --apply` and `bea format -i` keep that promise. `bea update transaction` and `bea update transactions` do not. With `--apply`, they write the edited copy over the link itself. They exit 0 and print `Updated 1 transaction in …/books/2026.bean`, and the link is now a regular file. The real file still holds the old entry. Every later `bea` write through the same path lands in the orphan copy, so the two diverge for good. Nothing reports it. The refusal for a hard-linked ledger even tells the user to "replace the extra name with a symbolic link (writes land in the real file)", which is the setup `update` breaks.

Environment: main `ad0ad3afa`, `bea 0.5.0` from the checkout (`uv run bea`), managed engine 0.5.0, macOS 26.5.1. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, scratch cwd, fresh processes. Reproduced twice from pristine fixtures, for a symlinked include and for a symlinked root.

## Repro

```sh
mkdir books shared
cat > books/main.bean <<'EOF'
option "operating_currency" "USD"
include "2026.bean"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Expenses:Food USD
EOF
cat > shared/2026.bean <<'EOF'
2026-01-10 ! "Grocer" "Weekly shop"
  import-id: "imp-2"
  Expenses:Uncategorized  52.30 USD
  Assets:Checking
EOF
ln -s ../shared/2026.bean books/2026.bean
shasum shared/2026.bean
bea --file "$PWD/books/main.bean" update transaction --id imp-2 --account Expenses:Food --flag '*' --apply
ls -l books/2026.bean
shasum shared/2026.bean
head -1 shared/2026.bean books/2026.bean
```

## Actual

- Exit 0. The diff names `books/2026.bean`, then `Updated 1 transaction in …/books/2026.bean.`
- `ls -l books/2026.bean` shows a regular `-rw-r--r--` file, no longer `-> ../shared/2026.bean`.
- `shared/2026.bean` has the same hash as before and still reads `2026-01-10 ! "Grocer" "Weekly shop"` with `Expenses:Uncategorized`. `books/2026.bean` reads `2026-01-10 * …` with `Expenses:Food`. `bea check` passes, so nothing flags the split.
- The batch form does the same: `[{"id":"imp-2","flag":"*"}]` through `bea update transactions --from rows.json --apply` turns the link into a regular file and leaves `shared/2026.bean` unchanged.
- A symlinked root behaves the same way. With `home/main.bean -> ../real/main.bean` and the entry in the root, `update --apply` makes `home/main.bean` a regular file, and `real/main.bean` keeps its hash. A following `bea --file home/main.bean add transaction …` then writes only to the orphan copy, and `real/main.bean` never sees it.
- Control on the same layout: `bea --file books/main.bean add transaction … --into 2026.bean` prints `Added 1 transaction to …/shared/2026.bean`, and `books/2026.bean` stays a link.

## Expected

`update transaction` and `update transactions` write through a symlinked ledger file, as `add`, `import --apply` and `format -i` do. After `--apply`, `books/2026.bean` is still `-> ../shared/2026.bean`, `shared/2026.bean` holds the edited entry, and the success line names the file that was written (as `add` names `…/shared/2026.bean`). Basis: `cli/docs/USAGE.md` "Choosing the ledger" ("writes such as `add` land in that file through the link"), w5/391's control, and the hard-link refusal's own advice.

## Cause

- `updating.answer` (`cli/src/bea_engine/ledger/updating.py:1306`) takes the write target from the entry's `meta["filename"]`, which is the lexical path through the link. `replace_checked` (`cli/src/bea_engine/ledger/write.py:4828`) then runs `os.replace(candidate, file)` (`:4856`) on that path. The rename replaces the link, not the file it points to. The checks before it (`target.stat()`, `require_writable`, `replace_checked`'s identity check) all follow the link, so they pass.
- The batch path has the same flaw. It groups rows by the same lexical `meta["filename"]` (`updating.py:778`, `:786`) and calls `replace_checked` at `:1199`.
- Working controls: `append` resolves its target through `destination()` (`write.py:94`, `return target.resolve()`), and `format` resolves its files before locking (`cli/src/bea_engine/ledger/formatting.py:109`). Both call the same `replace_checked` with the real path.

## Fix

Owned by `cli`, engine side only. In both update paths, resolve the entry's file to its real path (as `destination()` does) before locking, staging (`candidate_file`, which stages beside its argument), validating and calling `replace_checked`. The lexical name can stay in the diff header if wanted, but the success line and `--json` `target` should name the file actually written, as `add` does. Keep `_require_into`'s `same_file` comparison working on the resolved path. Regression tests through real `bea` subprocesses: a symlinked include and a symlinked root, for both `update transaction --apply` and `update transactions --apply`. After each, assert the link is still a link, the real file holds the edit, and `bea check` passes. A hard-linked target must still be refused. Revert the fix and watch the tests fail. Run `make check-all` in `cli/`. No REST, GraphQL or MCP surface writes local files.

## Blast radius

`replace_checked` has four callers: `updating.py:1199` (batch) and `:1325` (single row), both affected, plus `write.py:4962` (append) and `formatting.py:150` (format), which both resolve first. `bea ask` and `bea import` write through `append`. Not covered here and left as is: the hard-link refusal (`replace_checked`, w5/391) and `--into` matching (`_require_into` uses `same_file`, and the preview with `--into 2026.bean` on the link works).

Adjacent and minor, same command: the batch success line names the root ledger rather than the file written. `bea update transactions --from rows.json --apply` on the plain pristine layout (no links), with the row's entry in `2026.bean`, prints `Updated 1 of 1 transactions in …/main.bean.`, from `cli/src/cli/commands/update.py:300`, which formats `{file}`, the root. Its `--json` rows carry the right `target`. The single-row form names `2026.bean`.

Searched `.pm/**`, including `done/` and `blocked/`, for `symlink`, `symbolic`, `stays a symlink`, `write through` and `regular file`, crossed with `update transaction`, `bea update` and `updating.py`. w5/391 (hard links split on write) lists `add`, `import --apply` and `format -i`, and its control covers symlinks only for those. w5/1029 (batch update diffs per include) marks symlink includes unverified. w5/1125 covers `--into` discovery for update. w3/329 and related notes cover `format` and `query -o` destinations.
