## Objective

Give the consent page what it needs to identify the requester: the authorization's redirect URI, the client's self-asserted name, the CIMD `client_id` host when there is one, and whether every registered redirect is loopback.

## Context

- backend-cluster/backend-v2/src/features/oauth/api/oidc-route.ts — `GET /api-gateway/oauth/interaction/:uid` returns `client_id` today, no name or redirect.
- Keep REST/GraphQL/MCP parity rules in mind: this is an OAuth interaction endpoint, not a customer API capability, so no parity twin is required — record that in the change.

## Steps

1. Add `redirect_uri`, `client_name`, `client_id_host` (null unless the id is a URL), and `loopback_only` to the response.
2. Tests for a DCR client, a static client, and a loopback-only client.

## Files

- backend-cluster/backend-v2/src/features/oauth/api/oidc-route.ts
- backend-cluster/backend-v2/src/features/oauth/api/__tests__/oidc-route.test.ts

## Acceptance criteria

- [x] The endpoint returns the four fields with correct values for each fixture.
- [x] No field leaks another client's data; an expired `uid` still answers as before.

## Out of scope

- Rendering (t005).

## Result

2026-10-06. `GET /api-gateway/oauth/interaction/:uid` keeps `uid`, `client`, `scope`, `resource` and adds `redirect_uri`, `client_name` (null when the app gave none), `client_id_host` (the host of an `https://` client id, i.e. CIMD; null otherwise), and `loopback_only` (every registered redirect is `http` to `localhost`, `127.0.0.1`, or `[::1]`). The endpoint still needs the interaction cookie, so only the browser that started the authorization reads it. It is an OAuth interaction endpoint, not a customer API capability, so it carries no REST/GraphQL/MCP parity twin. Tests: named DCR client, loopback-only client, mixed redirects not flagged, unknown interaction still `400 interaction_not_found`; a mutation of `isLoopbackOnly` turns them red. CIMD hosts are exercised in w1/m31.
