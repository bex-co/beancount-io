## Objective

Decide the move's inputs, guarantees and refusals before any code.

## Context

- Entries are addressed by `entry_hash` (from `listLedgerEntries`) and `sha256sum` (from `getEntryContext`, or from `listLedgerEntries` once [m44](../m44/README.md) ships), as `deleteEntrySources` already takes them.
- File creation never auto-includes (owner decision 2026-10-30, w21/588); `appendLedgerText` refuses a path no loaded file reaches (w23/035).

## Steps

1. Inputs: `entries[{entry_hash, sha256sum}]` (both spellings), `toPath`, optional `includeFrom` (the loaded file that gets the `include` line), `dry_run`, `allowInvalid`.
2. Guarantees: entry text moves byte for byte; source order among moved entries is kept; the target is created when absent; one commit.
3. Refusals with codes: a target not reachable from the root and no `includeFrom`; an `includeFrom` that is not loaded; a stale `sha256sum`; a target equal to an entry's current file; new bean-check errors without `allowInvalid`.
4. Result: per-file diff on preview, moved count, `notLoaded` if any, and `commit` on a real write.

## Outcome — 2026-11-13

**Where it lives:** in the ledger service, as `moveSourceSlices` beside `deleteMultiSourceSlices`, because slice location, the sha check and commit-time relocation are already there. It is exposed as `POST /journal/{owner}/{repo_name}/move-source-slices` in the ledger IDL. backend-v2 exposes MCP `moveEntrySources`, REST `POST /api-gateway/v1/ledgers/{owner}/{name}/entries/move` and GraphQL `moveLedgerEntrySources` (t003).

**Inputs:**
- `entries`: each `{entry_hash | entryHash, sha256sum}`, as `deleteEntrySources` takes them;
- `toPath`: repository path of a `.bean`/`.beancount` file;
- optional `includeFrom`: a loaded file that gets `include "<toPath relative to it>"` when the target is not already reached;
- `dry_run`/`dryRun`, `allowInvalid`/`allow_invalid`.

**Guarantees:**
- Each entry's text moves byte for byte; a plugin-rewritten entry resolves to its source block, as the deletes do.
- The moved entries are appended to the target in ledger order (by file, then line), after a blank line. The target is created when absent, with a trailing newline.
- Removal uses the batch delete's transform: bottom-to-top, re-located against fresh content, de-duplicated.
- Sources, target and include line all land in **one** commit, gated on new bean-check errors over the whole projection.
- No `include` is added when `includeFrom` is omitted or the target is already reached (the owner's 2026-10-30 rule, w21/588).

**Refusals (nothing written):**

| Case | Code |
| --- | --- |
| no entries, an unsafe or non-ledger `toPath` | `BAD_USER_INPUT` |
| the target is not reached by the loaded files and no `includeFrom` is given | `BAD_USER_INPUT`, naming `includeFrom` as the fix (as `appendLedgerText` refuses an unloaded path, w23/035) |
| `includeFrom` is not a loaded file | `BAD_USER_INPUT` |
| an entry already lives in `toPath` | `BAD_USER_INPUT` |
| a stale `sha256sum` for any entry | `CONFLICT` |
| an entry in a managed price include | `OPERATION_NOT_ALLOWED`, as the edits refuse it |
| the move adds a bean-check error the ledger did not have | `VALIDATION_FAILED`, unless `allowInvalid` |
| a credential without file write | `FORBIDDEN` |

**Result:**
- `message`;
- `moved`, the count;
- `movedHashes`;
- `files`: every changed path, meaning the sources, the target, and `includeFrom` when it gained the line;
- `includeAdded`;
- `preview`: each moved slice as `{path, text}`, where `path` is its old file;
- `validation`;
- `dry_run`;
- `commit` on a real write.

`revertCommit` undoes it.
