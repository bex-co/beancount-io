# A text append rewrites a CRLF file to LF

**Bug · backend-v2 · minor · ~30m · A1.** From `/qa-find-bugs-mcp`, 2026-11-09, production `beancount-mcp 1.0.0`, unpinned read/write API key, the disposable QA ledger.

- **Repro:**
  1. `createLedgerFiles` `qa-x/crlf.bean` = `"2020-01-01 open Assets:X USD\r\n2020-01-02 note Assets:X \"a\"\r\n"`, and include it from `main.bean`.
  2. `appendLedgerText {"path":"qa-x/crlf.bean","text":"2020-05-01 note Assets:X \"b\"\n","dry_run":true}`. The diff removes both existing lines and adds them back with LF endings.
  3. Commit it on MCP, or on REST `POST …/directives/text` with the same path. `readLedgerFiles` then shows 0 CRLF and 4 LF line endings. The ledger still parses, but every append to a Windows-authored file produces a whole-file diff.
- **Expected:** the existing lines stay byte-identical and the new block uses the file's CRLF ending. That is how the ledger service's structured add (w21/673) and the slice edit (w21/252) already behave.
- **Cause:** `src/features/ledger/utils/directive-text.ts:325` (`insertDirectives`) runs `existing.replace(/\r\n?/g, "\n")`, and `:364` joins the lines with `"\n"`. Its only caller is `directive-append-workflow.ts:196`, the text-append path that REST, GraphQL and MCP share.
- **Fix:** detect the file's line ending the way ledger's `line-ending.ts` `lineEndingOf` does. Split the normalized text as now, then join the lines and the inserted block with the detected ending.
- **Check:** add a CRLF case to `directive-text.test.ts`: the existing lines are byte-identical, the new block uses CRLF, and the `wrote` / `entryHashes` line numbers are still right. Add REST and MCP parity cases.
