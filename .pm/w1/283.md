# A transaction the user flagged `P` is called a "pad" in write refusals ("Correct the pad date")

Found by `/qa-find-bugs-cli w1` on 2026-11-18 (HEAD `6352f9223`, `bea 0.4.1`, macOS 26.5.1, checkout `uv run bea`, Python 3.12, stdin closed, no TTY, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`). Severity: minor (wording only). A1: `bea add transaction --flag P` and `bea update transaction --flag P` accept the flag, since any capital letter is a Beancount flag. The refusal then tells the user to fix a pad the ledger does not have.

**Repro** (a fresh directory):

```sh
cat > main.bean <<'EOF'
2026-01-01 open Assets:Bank USD
2026-01-01 open Expenses:Food USD
EOF
bea --file main.bean add transaction --date 2025-12-15 --flag P -n "Paid back" -p 'Expenses:Food 5 USD' -p Assets:Bank
bea --file main.bean add transaction --date 2025-12-15 --flag '*' -n "Paid back" -p 'Expenses:Food 5 USD' -p Assets:Bank
```

**Actual:** both exit 1 and write nothing, as they should, since the date is before the opens. The `*` control says `Correct the transaction date or edit that directive`. The `P` one says `Correct the pad date or edit that directive` for both legs. The same happens when such a transaction is already in the file (written by hand, or with `update transaction --flag P --apply`): any later write lists it as `main.bean:4: … Correct the pad date …`.

**Expected:** a transaction is a transaction whatever its flag: "Correct the transaction date". Only the padding transaction Beancount synthesizes from a `pad` directive is named "pad". That is the rule w5/393's resolution states: "flag `P`, at the pad's line".

**Root cause:** `validate_candidate` in `cli/src/bea_engine/ledger/write.py` (about line 2828) names the directive `pad` when `isinstance(error.entry, Transaction) and error.entry.flag == FLAG_PADDING`, which checks only the flag. The engine's query code already tells the two apart correctly: `cli/src/bea_engine/query.py:1891` requires `entry.flag == "P" and _source_location(entry) in pads`, the location of a real `Pad` directive.

**Fix:** treat a `P` transaction as a pad's only when a `Pad` directive sits at its `filename`/`lineno`, as `query.py` does. `_pad_leg_hint` (about line 3632) already looks the pad up by location, so it needs no change. Add a regression test next to the w5/393 tests: an authored `P` transaction before the open says "Correct the transaction date", and a real `pad` before the open still says "Correct the pad date" and collapses with its padding transaction (the w1/118 control). Revert the fix and watch it fail.

**Dedupe:** w5/393 introduced the per-directive noun. w5/985 and w5/1088 already treat authored `P` flags as ordinary transactions in `list --details`. No open item covers the refusal wording.
