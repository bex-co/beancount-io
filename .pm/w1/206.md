# Two MCP refusal details point clients the wrong way: FORBIDDEN hint and invalid-bearer 401

**Copy/spec · backend-v2 (MCP) · minor · ~35m · A1.** From `/qa-find-bugs-mcp`, 2026-11-09, production `beancount-mcp 1.0.0`.

- **FORBIDDEN hint for non-ledger denials:**
  - `beancount://account/feed` with an API key returns `FORBIDDEN` "This credential type cannot perform this operation". The feed is OAuth/session only (`gitea/AGENTS.md:27-31`, `api-parity.md:48-53`).
  - `beancount://account/profile?userId=1` returns `FORBIDDEN` "Authorization denied".
  - Both hint "Check `beancount://{owner}/{name}/metadata` for your permission on the ledger", but no ledger is involved in either.
  - **Cause:** `mcp-errors.ts:91` has one `CATEGORY_HINTS[FORBIDDEN]`. The denial reason the authorization service already computes (`authorization-service.ts:823-873`, e.g. `credential_not_permitted`) is never used.
  - **Fix:** choose the hint from the denial reason and the resource type. For `credential_not_permitted`, name the accepted credential. w23/137 corrected the pointer for ledger denials only.
- **Invalid bearer gets the no-credential challenge:**
  - `POST /api-gateway/mcp` with `Authorization: Bearer bcio_<garbage>` returns 401 with `WWW-Authenticate: Bearer resource_metadata="…"` and `{"error":"unauthorized"}`. That is identical to the response with no credential.
  - RFC 6750 §3.1 calls for `error="invalid_token"` when a presented token is rejected. The provider's own userinfo endpoint already sends it.
  - **Cause:** `mcp-route.ts:39-49` (`refuseUnauthenticated`) writes one fixed header for every refusal.
  - **Fix:** add `error="invalid_token"` to the challenge only when a bearer was presented and rejected. Leave the no-credential and session-cookie cases unchanged; w23/m32 and conformance check 18 pin them.
- **Check:** add `mcp-errors` tests for the feed with an API key and for a foreign `userId`. Add `mcp-route-methods` rows for a rejected bearer and for no bearer.
