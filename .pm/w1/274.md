# A parenthesised or computed zero divisor (`100/(0)`, `100/(2-2)`) in an `add` amount kills the engine: exit 4 "outcome unknown", and `add transactions --partial` writes none of the valid rows

Found by `/qa-find-bugs-cli w1` on 2026-11-16 (HEAD `05254ee80`, `bea 0.3.1`, macOS 26.5, checkout `uv run bea`, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`). Severity: minor. A1: an agent that builds a posting from arithmetic (a split of a bill by a head count that came out zero, a rate difference) gets a crash report that blames the ledger, and in bulk mode one such row discards every good row in the batch.

**Repro** (a fresh directory):

```sh
printf 'option "operating_currency" "USD"\n2026-01-01 open Assets:Bank USD\n2026-01-01 open Expenses:Food USD\n' > main.bean
bea --file "$PWD/main.bean" add transaction z --date 2026-03-08 -p 'Expenses:Food 100/(2-2) USD' -p Assets:Bank
bea --json --file "$PWD/main.bean" add transaction z --date 2026-03-08 -p 'Expenses:Food 100/(0) USD' -p Assets:Bank
bea --file "$PWD/main.bean" add balance --date 2026-03-08 -a Assets:Bank --amount '1/(0) USD'
printf '[{"date":"2026-03-09","narration":"ok","postings":[{"account":"Expenses:Food","amount":"5 USD"},{"account":"Assets:Bank"}]},{"date":"2026-03-09","narration":"bad","postings":[{"account":"Expenses:Food","amount":"100/(0) USD"},{"account":"Assets:Bank"}]}]' > rows.json
bea --json --file "$PWD/main.bean" add transactions --partial --from rows.json
```

**Actual.** Every command exits 4 (`category: conflict`) with

```
Error: The Beancount engine was killed by SIGSEGV answering 'bea-engine add … --type transaction --request -'; the outcome is unknown. Inspect the file before retrying.
  Upstream's parser crashes this way on a zero divisor in an amount expression, such as '100/0 EUR'; searching the ledger for '/0' is the first thing to try.
```

`main.bean` is byte-identical afterwards (no `.bea-*.tmp` left), so the outcome is in fact known; the ledger holds no `/0` to search for, because the divisor was in the input. The `--partial` run writes neither row and names no row. A cost or price (`-p 'Expenses:Food 1 USD @ 1/(0) USD'`) crashes the same way.

**Control.** The same rows with a literal `100/0` are refused before the engine: single `add` exits 2 with `Division by zero in 'Expenses:Food 100/0'…`, and `add transactions --partial` exits 1 with `written: 1`, `written_rows: [0]`, `rejected_rows: [1]`, naming `Row 2, postings.0`. `100/0.0`, `100/00` and `100/-0` are refused too.

**Expected.** `docs/USAGE.md` (around line 1289) promises "A literal zero divisor (`100/0`) is refused as a usage error before it reaches the engine". `(0)` is a literal zero, and any zero divisor in a single amount expression can be found exactly: Beancount's `number_expr` grammar is only numbers, unary `+`/`-`, `+ - * /` and parentheses. So every zero divisor in an `add` amount (flags and bulk rows; units, per-unit and total cost, unit and total price) should get the same refusal as `100/0`: exit 2 naming the posting on the flag path, and the row-level rejection with ordinary `--partial` semantics in bulk.

**Cause.** Both guards are a regex for a slash followed directly by an all-zero number: `_ZERO_DIVISOR` in `cli/src/cli/amounts.py:81` (used by `check_decimal_notation`, `:99-123`, from `cli/src/cli/commands/add.py:212` and `:308`) and its copy in `cli/src/bea_engine/amounts.py:16` (`refuse_zero_divisor`, `:200-213`, called from `cli/src/bea_engine/ledger/models.py:342` before `parse_exact`). A `(` after the slash, or a computed divisor, passes both, and Beancount's parser segfaults inside the engine process. The docstrings record computed divisors as "still upstream's to answer" (w5/010, w5/057), on the view that they cannot be caught statically; for one amount expression they can, by evaluating it with `Decimal`. `_signal_hint` in `cli/src/cli/engine/launch.py:1576-1582` then gives the ledger-oriented advice for a crash caused by the request.

**Fix.** Replace the regex test in both places with a small exact evaluator over the amount's arithmetic tokens (outside quoted labels and comments, keeping slash currencies such as `/0J` as currencies, per w5/489 and w5/656), refusing any division whose divisor evaluates to zero with the existing message. Keep `100/0.5` and `100/10` evaluating. Optionally, when an `add` engine call does die on a signal and the destination hash is unchanged, say nothing was written instead of "the outcome is unknown".

**Blast radius.** `add transaction`, `add balance` (and `--pad-from`), `add transactions` with and without `--partial`, and `--into` share the two guards; `add price` refuses arithmetic altogether (exit 2 "Invalid amount '1/(0)'"), and `--meta` stores arithmetic as text (w5/272), so neither crashes. Existing ledgers holding `100/(0)` in a file are a separate path: `format` isolates them per file since w5/759, and `check` names the signal (w5/010).

**Dedupe.** Searched `.pm/**` for "zero divisor", "Division by zero", "SIGSEGV": w5/010, 057, 489, 565, 656, 759 and 272 are done; 010 and 057 explicitly left computed divisors to upstream, and 759 fixed `100/(0)` only for `format`. No open item covers the `add` path.

**Acceptance.** The repro's four commands exit as the `100/0` control does (2, 2, 2, and 1 with `written_rows: [0]`, `rejected_rows: [1]`), `main.bean` is unchanged by the refused single adds, and `bea check` passes afterwards; regression tests pin `(0)`, `(2-2)` and `0*5/(0)` in units, cost and price, plus the `100/0.5` control.
