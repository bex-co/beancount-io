# Unknown subcommand exits 1 instead of the documented usage code 2

`bea nosuchcommand` (or `bea cloud nosuchcommand`) exits **1**: the vendored
click `UsageError` ("No such command …") is raised inside `Group.invoke`, so
`_GuardedGroup.invoke` in `cli/src/cli/main.py` intercepts it and routes it
through the catch-all (`validation`/1) instead of the documented `usage`/2.
Parse errors caught before dispatch (bad top-level option) still exit 2, so the
same *kind* of mistake gets two different codes.

Fix sketch: map typer's vendored `click.UsageError` to `UsageError` in
`cli/src/cli/errors.py::to_bea_error` (typer has no public re-export — needs
`typer._click` or a duck-typed check), or re-raise it from the guarded group so
click's standalone handler applies its own exit-2 path. Add a regression test;
`tests/test_command_tree.py::test_the_pre_cloud_spellings_stay_dead` currently
asserts only nonzero and should be tightened to 2 once fixed.
