# `bea update transaction` previews an edit the apply will refuse, and says "repeat with --apply"

Found by `/qa-find-bugs-cli w1` on 2026-11-15 (HEAD `ee1ae1f6e`, `bea 0.3.1`, macOS 26.5, checkout `uv run bea`, stdin closed, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, synthetic ledger). Severity: minor. A1: an agent clearing the import review queue follows the documented two-step flow (`USAGE.md` "Updating directives": preview, then `--apply`). The preview promises a clean edit, and the apply then fails with exit 1. The batch form refuses the same row at preview time, so one edit gets two answers.

**Repro** (synthetic):

```sh
cat > main.bean <<'EOF'
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Uncategorized USD

2024-01-03 ! "B"
  import-id: "x2"
  Assets:Cash   -5.00 USD
  Expenses:Uncategorized
EOF
bea --file main.bean update transaction --id x2 --account Expenses:Nope           # exit 0
bea --file main.bean update transaction --id x2 --account Expenses:Nope --apply   # exit 1
printf 'id,account\nx2,Expenses:Nope\n' > q.csv
bea --file main.bean update transactions --from q.csv                             # row 1 rejected
```

**Actual.** The preview prints the diff (`-  Expenses:Uncategorized` / `+  Expenses:Nope`) and then `Preview only. Review the diff, then repeat with --apply to write.`, with exit 0. The apply refuses with `Invalid reference to unknown account 'Expenses:Nope'`, exit 1, and the file is unchanged. The batch preview of the same mapping marks the row `rejected`.

**Root cause.** In `cli/src/bea_engine/ledger/updating.py` `answer()` (about lines 1160–1172), the preview path plans the rewrite and returns the diff. It never validates the candidate text, while the apply path runs `ledger_write.validate_candidate`. The batch preview validates through `_validate_plans` (w5/1081).

**Fix (cli only).** The single-row preview validates the planned text the same way the batch preview does, and keeps the diff. An edit the apply would refuse is reported in the preview as refused: the ledger error, exit 1, and no "repeat with --apply" line. `--allow-errors` keeps its existing meaning.

**Done when** the repro's first command exits 1 naming `Invalid reference to unknown account 'Expenses:Nope'`, a valid retarget still previews exit 0 with its diff, and a regression test in `cli/tests/test_update.py` covers both. The test fails with the fix reverted.
