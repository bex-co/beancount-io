# `bea add transaction` writes a posting like `100/3 USD` as a 28-digit amount, exit 0, and from then on every report prints that currency to 26 decimals

**Source:** routine cli-qa, 2026-11-19. **Severity:** major. **Estimate:** 45 minutes. **Owner:** cli. **A1:** an agent or a person splitting a bill three ways (`-p 'Expenses:Dining 100/3 USD'`, the native posting arithmetic `cli/docs/USAGE.md` advertises with `84/2 EUR`) gets exit 0 and a ledger that permanently holds `33.33333333333333333333333333 USD`. Every human table in that currency then prints 26–27 decimal places, and the trial balance grows a phantom rounding line. Nothing says why until someone hand-edits the entry.

Found at `c8777163f` with the checkout's `uv run bea` 0.4.1, macOS 26.5.1, Python 3.12.14, isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed, stdout piped, synthetic ledger. Reproduced in a fresh process from a pristine copy.

## Repro

```sh
cat > main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Dining USD
2026-01-01 open Equity:Opening-Balances USD

2026-01-01 * "Opening"
  Assets:Checking  1000.00 USD
  Equity:Opening-Balances
EOF
bea --file main.bean add transaction --date 2026-01-10 "Dinner, split three ways" \
  -p 'Expenses:Dining 100/3 USD' -p Assets:Checking   # exit 0
tail -3 main.bean
bea --file main.bean balance
```

## Actual

The file gains:

```
2026-01-10 * "Dinner, split three ways"
  Expenses:Dining  33.33333333333333333333333333 USD
  Assets:Checking
```

`bea check` passes, and `bea balance` (the trial balance) then reads:

```
  Assets                                          966.66666666666666666666666670 USD
    Checking                                      966.66666666666666666666666670 USD
  Equity                                          -1,000.00000000000000000000000000 USD
    Opening-Balances                              -1,000.00000000000000000000000000 USD
  Rounding residual:                              -0.00000000000000000000000003 USD
  Expenses                                        33.33333333333333333333333333 USD
    Dining                                        33.33333333333333333333333333 USD
```

`report income-statement` and `list transaction` print the same digits. The rounding line comes from 28-digit decimal arithmetic: `1000.00 − 33.3…3` rounds to `966.6666666666666666666666667`, so the books stop summing to exactly zero. The same happens with `bea add transactions` (`"amount": "100/3 USD"`), and `add balance --amount '100/3 USD'` refuses but offers to rerun with `--amount '33.33333333333333333333333333 USD'`. Control: `add price --amount '1/3 USD'`, `add custom -v 'amount:100/3 USD'` and a bulk `units.number` of `"100/3"` already refuse arithmetic (`Invalid amount '1/3'. Use finite decimal notation…`). A terminating quotient such as `10/4 USD` is written as `2.5 USD` and harms nothing.

## Expected

A posting or balance amount whose arithmetic does not terminate is refused at the input boundary with exit 2 and nothing written. That is how a zero divisor is already refused, and how `@@` totals stopped being written as repeating unit prices (w3/309). The message names the expression and the amount to write instead, for example: `100/3 USD does not divide exactly (33.333…); write the amount to the cent, such as 33.33 USD (33.34 USD for one share, so the shares add up to 100.00 USD).` Exact arithmetic (`84/2`, `10/4`, `(2+3)*4`) keeps working and is written evaluated, as documented.

## Root cause

- `cli/src/bea_engine/amounts.py` `parse_exact` (around line 220): when even the widened parse is `Inexact`, it returns Beancount's 28-digit reading on purpose ("Only a quotient that does not terminate (`1/3`) … keeps Beancount's own 28-digit reading", from the w5/263 fix). Its callers write that number: the `--posting` path in `cli/src/bea_engine/ledger/adding.py` (around line 1343), the bulk amount shorthand `_posting_fragment` in `cli/src/bea_engine/ledger/models.py` (around line 358), and the balance amount (`adding.py` around line 1101).
- The frontend guard `check_decimal_notation` in `cli/src/cli/amounts.py` (and its engine twin `refuse_zero_divisor` in `cli/src/bea_engine/amounts.py`) refuses only exponents and zero divisors.
- Report precision (`_display_precision` / `_typed_precision` in `cli/src/bea_engine/report.py`) takes the finest fraction digits written in postings, so one 27-digit amount sets the precision for the whole currency.

## Fix

Have `parse_exact` report when the wide parse is still `Inexact`, for example by returning a flag or raising a dedicated error. The three write callers then refuse with the message above. Metadata already treats arithmetic as text and is out of scope. `cli/tests/test_add_negative_amount_keeps_digits.py::test_a_repeating_quotient_keeps_beancounts_reading_beside_a_wide_number` currently pins that `-1/3 SHIB` is written as 28 threes with exit 0. Repoint it to assert the refusal, and keep its wide-number control. Add a regression test for the repro (flag path, bulk `amount`, `add balance --amount`): it must exit 2 and leave the file byte-identical. Add a control showing `10/4 USD` is still written as `2.5 USD`. Update `cli/docs/USAGE.md` next to "Native posting arithmetic such as `84/2 EUR` works" to say that a quotient that does not terminate is refused. Run `make check-all` in `cli/`.

Writing the expression as typed (`100/3 USD`) instead is not enough. Beancount evaluates it to the same 28 digits while parsing, so the report precision and the rounding line come back.

## Dedupe

Searched `.pm/**` for `100/3`, `10/3`, `33.3333`, `inexact`, `repeating`, `non-terminating` and `divide exactly`. w3/309 and w5/802 fixed `@@` totals written as repeating unit prices. w3/304 fixed repeating decimals from conversion. w5/263 kept the 28-digit reading while fixing wide negative numbers, and noted it. w5/010 listed `100/3 EUR` as working arithmetic but never checked what the reports printed. None covers a posting amount's quotient being written or its effect on reports. `git log -S "Only a quotient that does not terminate"` points only at `2b3b5697d` (w5/263). This is not deployment lag.
