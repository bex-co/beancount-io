# Accounts renders "not computed" and "exactly zero" both as `—`, which also unlocks Close on 45 accounts

**Major · 45–60m · dashboard.** A2: the Accounts page is where a reader answers "which accounts hold money". On a ledger whose activity is historical it currently answers `—` for every income, expense and equity account, including one holding −327,691.98 USD.

Found 2026-09-13 by a dashboard QA sweep against production `https://beancount.io`, signed in, ledger `puncsky/example`, headless Chromium 1440×1000. Read-only — no account was closed, opened or deleted; menus were inspected and dismissed with Escape.

`getLedgerAccountDirectives` returns **three** distinct balance states, and the page collapses two of them into one glyph:

| API `balance` | Meaning | Accounts on this ledger | Rendered |
| --- | --- | --- | --- |
| `{"USD":"-8123.35"}` | computed, non-zero | 12 | the amount ✅ |
| `{}` | computed, exactly zero | 4 | `—` ✅ |
| `null` | **not computed** | **45** | `—` ❌ |

All 45 `null` rows are the income-statement and equity accounts — Expenses 37, Income 7, Equity 1 — and many are large. Verified against BQL on the same session:

| Account | Accounts page | `SELECT account, sum(position) … GROUP BY account` |
| --- | --- | --- |
| `Income:US:Hoogle:Salary` (71 entries) | `—` | **-327,691.98 USD** |
| `Expenses:Taxes:Y2017:US:SocSec` (18 entries) | `—` | **5,067.72 USD** |
| `Equity:Opening-Balances` (1 entry) | `—` | **-3,490.52 USD** |
| `Liabilities:AccountsPayable` (6 entries) | `—` | `{}` — genuinely zero, correctly shown |
| `Liabilities:US:Chase:Slate` (528 entries) | `-8123.35 USD` | matches ✅ |

So `Income:US:Hoogle:Salary` and `Liabilities:AccountsPayable` are visually identical rows, while one is empty and the other is a third of a million dollars. The biggest `null` rows by entry count are `Expenses:Food:Restaurant` (370), `Expenses:Food:Groceries` (73), `Expenses:Health:Vision:Insurance` (71).

## The same conflation silently unlocks a safety gate

`canClose = !isClosed && isBalanceEmpty(account.balance)` is clearly meant to offer **Close** only for an emptied account. `isBalanceEmpty` treats `null` as empty, so the gate opens for all 45. Reproduced by opening each row's actions menu:

| Row | Real balance | Menu offers Close? |
| --- | --- | --- |
| `Income:US:Hoogle:Salary` | −327,691.98 USD | **yes** ❌ |
| `Liabilities:AccountsPayable` | zero | yes ✅ correct |
| `Liabilities:US:Chase:Slate` | −8,123.35 USD | no ✅ correctly blocked |

The guard demonstrably works — it blocks `Slate` — and is defeated for every account the API declines to compute. This is the part that makes the finding major rather than cosmetic: a display ambiguity would be annoying, but this one changes which destructive action the UI offers.

Repro:

1. Open `/ledger/<owner>/<ledger>/accounts`.
2. Read the Balance column: 49 of 61 rows show `—`.
3. Compare any `Income:` or `Expenses:` row with `SELECT account, sum(position) WHERE account = '<that account>' GROUP BY account` on the Query page.
4. Open that row's actions menu — **Close** is offered.

Expected: a row whose balance was not computed must not read the same as a row that is genuinely zero, and must not satisfy the emptied-account precondition for Close. Actual: both render `—` and both offer Close.

Root: `dashboard/src/features/ledger-data/accounts/index.tsx`.

- `:97` — `if (!balance || Object.keys(balance).length === 0)` renders the placeholder. `!balance` catches `null` and merges it with the computed-zero case.
- `:61-63` — `isBalanceEmpty` starts `if (!balance || Object.keys(balance).length === 0) return true`, so `null` reports "empty".
- `:154` — `canClose` consumes that result; `:239` renders `BalanceCell`.

The API is not at fault: it already distinguishes the three states, and `GetLedgerAccountDirectives` already selects `balance`. Whether the server *should* compute income-statement balances is a separate product question and is **not** claimed here — this note is only that the client must stop treating "no answer" as "zero".

Fix: branch on `balance === null` separately from `{}`. Render an explicit not-applicable/not-computed affordance for `null` that is visually distinct from the zero placeholder (and give it an accessible name, since `—` alone tells a screen reader nothing), keep `{}` rendering as today, and make `isBalanceEmpty` return `false` for `null` so `canClose` stops treating an uncomputed balance as an emptied account. Do not fabricate a client-side balance by summing entries. Owning package: `dashboard` only — no API, schema or cross-package change.

Blast radius: `isBalanceEmpty` and `BalanceCell` are local to this file; `canClose` is its only behavioral consumer. The close flow itself (`close-account-dialog.tsx`) is unchanged. Working control: every `Assets:`/`Liabilities:` row, where all three states already render and gate correctly.

Adjacent states: the 4 genuine `{}` rows (`Assets:US:Vanguard`, `Assets:US:BofA`, `Assets:US:Federal:PreTax401k`, `Liabilities:AccountsPayable`) must keep today's placeholder and keep offering Close; the two 0-entry rows must not regress; type filters and the 61/61 count are untouched.

Dedupe: searched every queue including `done/` for `isBalanceEmpty`, `canClose`, accounts-balance and close-account terms. `w3/217` and `w4/012` are Accounts **row readability at enlarged text** — layout, not balance semantics. `w3/189` is posting rounding on the account journal. `w3/m32` is statement-hierarchy accessibility. Nothing covers the `null`/`{}` conflation. `git log -S isBalanceEmpty -- src/features/ledger-data/accounts/index.tsx` shows only the original import `af5339de`, so no later fix exists on main and this is not deployment lag.

Confirmed at HEAD on a second ledger (2026-09-13): running this checkout's dashboard locally (`yarn dev`, SSR and client pointed at the production API) against the **public** `open_ledger/example` reproduces the identical pattern — Expenses 37 rows / 0 with a balance, Income 7 / 0, Equity 1 / 0, while Assets show 10 of 13 and Liabilities 1 of 2. So this is current code, not deployment lag, and not specific to one ledger or to a private ledger's permissions.

Unverified: other locales, whether a ledger with current-period income activity renders differently, the narrow viewport, and the behavior after repair. Close was never actually invoked.
