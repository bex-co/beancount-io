## Objective

Expose the option on every surface that reads the journal, with the same default, cap and refusal.

## Context

- MCP: `listLedgerEntriesInput` in `src/features/ai-agent/api/mcp-list-tools.ts`; parameters accept both spellings (w23/m3, w23/m9).
- REST: `src/features/ledger/api/rest/v1/journal-reads.ts`; GraphQL: `src/features/ledger/api/resolvers/ledger-journal-resolver.query.ts`.
- REST GET queries refuse unknown keys (w23/m12), so the new key must be declared.

## Steps

1. Add `include_source` / `includeSource` to the MCP input and output schemas, the REST journal query, and the GraphQL field arguments and type.
2. Add parity rows: a page with source, a page without, and the over-cap refusal.
3. Regenerate the v1 OpenAPI snapshot and re-sync the CLI's pinned spec.
4. Add a test that feeds a listed `entry_hash` and `sha256sum` straight into `updateEntrySource` and `deleteEntrySources`.

## Outcome — 2026-11-13

- **One resolution point:** `JournalQueryParams` takes `include_source` and `includeSource`, and the journal service resolves them once with `resolveFlagAlias` (`INCLUDE_SOURCE_NAMES` in `flag-alias.ts`). A conflict is `BAD_USER_INPUT` before any ledger call. It sends `include_source: true` to the ledger only when asked, so no adapter maps the flag.
- **Surfaces:**
  - MCP `listLedgerEntries` gains `include_source`/`includeSource`, and its description says the page can carry each entry's text and `sha256sum`.
  - REST `GET …/journal` gains `include_source`/`includeSource`, as boolean query values.
  - GraphQL `JournalQueryInput` gains `includeSource`/`include_source`; items are JSON objects, so `source` passes through.
  - All three share `INCLUDE_SOURCE_DESCRIPTION` (`utils/include-source-description.ts`).
- **Parity:** `ai-agent/api/__tests__/journal-parity.test.ts` gains three cases on all three surfaces:
  - each spelling is forwarded to the ledger as `include_source: true`, and each entry's `source` comes back unchanged;
  - no surface asks for source without the flag;
  - disagreeing spellings are refused before any ledger call.
- **Hand-off:** the listed `entry_hash` and `sha256sum` reach the caller byte for byte (asserted above). They equal `getEntryContext`'s because the ledger computes both with the same batch resolver (t001). `updateEntrySource`/`deleteEntrySources` take whatever sha they are given, which their own source-slice parity suites cover.
- **OpenAPI and CLI:** `yarn generate-v1-openapi`; `make spec-sync && make codegen` in `cli/` (the journal client gains the parameter). The CLI static gates and the `cloud journal` tests (6) pass.
- **Checks:** backend-v2 `typecheck`, `lint:deadcode`, `format:check`, `test` (478 suites, 10,610 tests).
