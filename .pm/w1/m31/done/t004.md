## Blocked (cleared 2026-10-08)

**Blocked 2026-10-08.** The conformance half holds: production advertises `client_id_metadata_document_supported: true`, and check 16 passes. The Claude Code half does not yet. Starting sign-in from Claude Code 2.1.289 against `https://beancount.io/api-gateway/mcp` sent an opaque `client_id`, not `https://claude.ai/oauth/claude-code-client-metadata`. Claude Code reuses the DCR registration it stored in its secure storage before CIMD was deployed, so this connection cannot show the CIMD path. **Unblock:** the user clears the `beancount` server's stored authentication in Claude Code (`/mcp` → beancount → clear authentication, or remove and re-add the server). The next sign-in's authorization URL should then carry the CIMD `client_id`. Record it and approve with one ledger. **Who can clear it:** the user. Clearing it touches their Claude Code credential store.

### Update 2026-10-08 (after a second deploy)

The production side of the CIMD path is verified end to end with Claude Code's real published identity, without the Claude Code app. `client_id=https://claude.ai/oauth/claude-code-client-metadata` was used with PKCE `S256`, a `localhost:47123` redirect (a port the document does not list), `resource` set to the MCP endpoint, and `ledger.read offline_access`.

- `/auth` went to consent without any registration. The signed-in consent page shows "you return to localhost:47123", "It calls itself “Claude Code”", "Its details are published by claude.ai", and the loopback-only warning.
- Approved for one ledger. The callback carried `code`, `state`, and `iss=https://beancount.io`.
- The token endpoint (public client, `client_id` as the document URL) answered `200` with the requested scope.
- MCP `initialize` answered `200`, and `listLedgers` returned exactly the one approved ledger.
- Cleanup: the refresh token was revoked (`200`). The access token is a JWT and cannot be revoked (`unsupported_token_type`, as documented); it expires within the hour and was discarded.

Still open: the criterion names a real Claude Code connection. Headless `claude -p` cannot run an OAuth sign-in, and this session's `beancount` entry reuses a pre-deploy DCR client. A fresh local entry, `beancount-cimd-check`, was added for the check. **Unblock (narrowed):** in an interactive Claude Code session, the user runs `/mcp` → `beancount-cimd-check` → Authenticate. The consent page should then say "Its details are published by claude.ai".

### Cleared 2026-10-08

The user ran `/mcp` → `beancount-cimd-check` → Authenticate in Claude Code 2.1.289. The server now reports Connected, and Claude Code's stored client ID for it is `https://claude.ai/oauth/claude-code-client-metadata`, the CIMD document URL rather than a registered ID. No client row is created: oidc-provider resolves a CIMD client from the published document into an in-memory cache (`lib/helpers/client_id_metadata_document.js`) and never writes it through the storage adapter.
