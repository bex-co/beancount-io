# Temp-asset uploads don't bind `mimeType`, so a file uploaded as documented is refused by the parser

**Bug · backend-v2 · minor · ~30m · A1.** From `/qa-find-bugs-mcp`, 2026-11-10, production `beancount-mcp 1.0.0`. The parser itself was not called past its content-type gate, so no AI quota was spent.

This breaks the documented MCP upload→parse flow for any agent that doesn't also send a `Content-Type` header. Dashboard and mobile set the header, so they are unaffected.

- **Repro:**
  1. `generateTempAssetUploadUrl {"filename":"qa-receipt.jpg","mimeType":"image/jpeg"}`. The presigned URL's `X-Amz-SignedHeaders` is `host` only.
  2. PUT the bytes without a `Content-Type` header. Neither the tool description nor `docs/mcp.md` says to send one. The PUT returns 200.
  3. Reading the object back through `beancount://temp-assets/download-url` gives `Content-Type: binary/octet-stream`.
  4. `parseReceipt {ledger, objectKey}` is refused `BAD_USER_INPUT` "s3ObjectKey must be an image (JPEG, PNG, GIF, WEBP) or PDF file". The generic hint can't help, and it names `s3ObjectKey` where the caller sent `objectKey`.
  - Also, a URL minted with `mimeType: text/csv` accepts a PUT with `Content-Type: image/png`, and the object is then served as `image/png`.
- **Expected:** the description says "Optional filename and mimeType preserve the upload metadata". A declared `mimeType` should be enforced, or at least stored, so the parse-time format checks (w21/108, w21/325) see what the caller declared.
- **Cause:** `src/features/s3/service/asset-storage-service.ts:202-210` passes `ContentType` to `PutObjectCommand` but calls `getSignedUrl` without `signableHeaders`. The header is therefore unsigned and the client can send anything. The parse gates read the stored, client-sent type (`llm-service.ts:187,254-263`).
- **Fix:** the service is shared by MCP, REST and GraphQL, so all three get it.
  - When `mimeType` is given, sign it: `signableHeaders: new Set(["content-type"])`.
  - Return the `uploadHeaders` the client must send, and say "PUT with `Content-Type: <mimeType>`" in the description.
  - At parse time, fall back to the filename extension when the stored type is `binary/octet-stream`.
  - Name the caller's alias (`objectKey`) in the refusal.
- **Same pass:** the presigned URL carries `x-amz-checksum-crc32=AAAAAA==`, the CRC32 of an empty body (SDK flexible checksums). Wasabi ignores it, but AWS S3 would reject every non-empty upload. Set `requestChecksumCalculation: "WHEN_REQUIRED"` on the S3 client.
- **Check:** add a temp-asset test asserting that the signed headers include `content-type` when `mimeType` is set.
- **Correction:** QA iterations 2 and 24 on 2026-11-08/10 recorded `mimeType` as harmlessly ignored and as bound. This live check shows neither is the case. The size limit is already tracked in w21/955.
