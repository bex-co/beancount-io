# `bea query` text tables still print bare-number columns with 28-digit division noise: `number`, `cost_number` and `sum(number)` read `-99.99999999999999999999999999`, `33.33333333333333333333333333` and `0.00000000000000000000000001` beside a `position` that reads `-100.00 USD`

**Bug · cli · minor · 45–75m · A1.** From routine cli-qa, 2026-11-20. Follow-up to [w1/325](./done/325.md), [w1/326](./done/326.md) and [w1/330](./done/330.md). Those fixed the precision of amount, position and inventory cells in `bea query` text tables. A column whose type is a bare `Decimal` was left out: `number`, `cost_number`, `sum(number)`, arithmetic such as `number * cost_number`, and `number(…)` of an amount. Such a column still prints every digit of a total cost's or total price's quotient, and of what the quotient leaves in a sum. The shipped BQL cookbook (`docs/skills/bql-cookbook.md`, mirrored in `skills/beancount-ask/references/bql-recipes.md`) is written in these columns. On a ledger with one `3 HOOL {{100.00 USD}}` purchase, its "Open lots at own cost" recipe reads the lot's cost as `99.99999999999999999999999999` and its unit cost as `33.33333333333333333333333333`. "Per-lot market value" reads the unrealized gain as `23.00000000000000000000000001`. An agent that pastes the table into an answer reports a 100 USD lot as 99.99999999999999999999999999, and a cash account emptied by that purchase as holding `0.00000000000000000000000001`. In the same row, `position`, `cost(position)` and the `-m` amount columns already read `-100.00 USD`, `100.00 USD` and `820.00`.

Environment: main `7e4c8ca1b`, `bea 0.5.0` from the checkout (`uv run bea`), Python 3.12.14, macOS 26.5.1. The run used an isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME` with `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, and the cwd in a scratch directory. Each command was reproduced in fresh processes from a pristine copy, and the ledger's hash was unchanged after every run. BQL read from stdin and `-o out.txt` print the same digits.

The width of the noisiest value also sets the column: `1000.00` and `-80.00` are padded out to the 28-digit cell's width. `--json` and `--format csv` give the same exact values (`"-99.99999999999999999999999999"`), which is correct. Upstream `bea query --source main.bean …` (native bean-query rendering) prints the same 28-digit cells, so this is bea's own text-table policy not yet reaching one column type.

Expected: in a text table, a bare-number column follows the rule `docs/USAGE.md` states for amounts (the paragraph that begins "Query tables preserve the precision of result values", around line 1085). A quotient that runs to the decimal context's full 28 digits contributes no digits. A sum's rounding residue past a run of ten zeros or nines contributes none either. A value that is all noise prints at the digits of the column's other values. On the repro that gives `-100.00`, `33.33`, `820.00`, `100.00` and `23.00`, and `0.00` on the emptied account, with no sign.

Working controls: amount, position and inventory cells (`ColumnAmountRenderer`, `SummedInventoryRenderer`), and `-m` columns (`_numberified_text`), which are quantized through `_Digits` with the currency's written precision. Clean bare numbers already print as written: `count(*)` reads `2`, units read `3` and `5`, `number(convert(position, 'USD'))` reads `123.00`.

## Cause

`_text_renderers()` (`cli/src/bea_engine/query.py:2420`) gives `Decimal` columns `FixedPointDecimalRenderer` (`:2429`). It is upstream's `DecimalRenderer` with a fixed-point spelling: it sizes the column to the most fractional digits of any value and prints each value at full precision. The meaningful-digits rule lives only in `_Digits.learn` (`:3900`), through `report._cost_digits` (`cli/src/bea_engine/report.py:979`) and `_before_residue` (`query.py:3882`). Only amount-typed cells and `-m` columns reach it, because `_Digits` is keyed by currency and a bare number has none.

## Fix

In the text path only, size and quantize each `Decimal` column by its own values. Each value keeps its digits as written, so `1000.00` still shows two places and `3` none. A value whose coefficient reaches the context precision (`_cost_digits` returns 0 for it) counts for nothing. A summed value counts only up to its residue (`_before_residue`). Noise values are then quantized to the column's digits. A column with no other digits can fall back to the ledger's finest written precision (`report.written_precision`, already read once per load by `_written_precision`), so `sum(number)` alone reads `820.00`, not `820`. An exact zero prints without a sign and without its 26 trailing zeros (`sum(number(weight))` over the `Buy` entry reads `0.00000000000000000000000000` today).

Keep the w1/326 limit that the residue rule applies to sums only: a lone `0.000000000012` must keep its twelve decimals. Triage decides how a `Decimal` column is known to be a sum, for example from the compiled column expression. `--json`, `--format csv` and their `-m` cells stay exact. Update `query.py`'s module docstring ("Result precision") and the USAGE.md paragraph to name bare-number columns. Owning package: `cli` (`bea_engine/query.py`). No REST/GraphQL/MCP change: the hosted query surfaces return structured rows, not this text table.
