# `bea report capital-gains` says "No sales." for a sale from a `"NONE"`-booked account that names the lot's cost but not its date, though the ledger books the gain

**Bug · cli (+ backend-v2 parity) · major · ~1h · A1.** From routine cli-qa, 2026-11-19. `NONE` is one of the six booking methods `bea add open --booking` accepts, and the `beancount-trade` skill tells an agent to write a `NONE` sale with "the named lot's cost" (`skills/beancount-trade/SKILL.md`, Booking methods). Beancount does no lot matching under `NONE`. It gives a sale that names a cost but no date the sale's own date (`{100 USD, 2026-02-01}`), so the sale becomes a new negative lot beside the long ones, and the account nets the expected 15 units. `bea report capital-gains` matches reductions by the exact lot key, date included. It reads the sale as "opening a short", which realizes nothing, and prints a bare `No sales.` with exit 0, while the transaction books a 500 USD gain. An agent or a user doing taxes reads zero realized gains. The average-cost workaround for `NONE` accounts (`{125 USD}`, which matches no lot) is reported the same way.

Environment: main `4b79e707c`, macOS 26.5.1, `bea 0.4.1` from the checkout (`cli/.venv/bin/bea`), isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY.

Repro ledger (`main.bean`):

```beancount
option "operating_currency" "USD"
2025-01-01 open Assets:Cash USD
2025-01-01 open Assets:Broker "NONE"
2025-01-01 open Income:Gains USD
2025-01-01 open Equity:Opening USD

2025-01-01 * "Fund"
  Assets:Cash  10000 USD
  Equity:Opening

2025-01-10 * "Buy"
  Assets:Broker  10 ABC {100 USD}
  Assets:Cash  -1000 USD

2025-03-10 * "Buy"
  Assets:Broker  10 ABC {150 USD}
  Assets:Cash  -1500 USD

2026-02-01 * "Sell 5 of the 100 USD lot"
  Assets:Broker  -5 ABC {100 USD} @ 200 USD
  Assets:Cash  1000 USD
  Income:Gains
```

- `bea --file main.bean check` exits 0, and `bea --file main.bean balance gains` shows `Gains -500 USD`.
- `bea --file main.bean report capital-gains` exits 0 and prints the heading and then `No sales.`. stderr is empty. `--json` has `rows: []`, `unpriced_reductions: []` and empty totals. The file is unchanged (hash checked).
- `bea query "SELECT date, units(position), cost_number, cost_date, price WHERE account = 'Assets:Broker'"` shows the sale as `-5 ABC`, cost `100`, cost_date **`2026-02-01`**, price `200 USD`.
- Average-cost variant: with `-5 ABC {125 USD} @ 200 USD`, `check` exits 0, the books show `Gains -375 USD`, and the report again prints `No sales.`.
- The `beancount-trade` realized-gains BQL recipe (`skills/beancount-trade/references/realized-gains.md`) does list the sale, with gain 500 but acquired `2026-02-01` and held 0 days, so the skill's command and query recipes disagree.
- Working controls: the same sale written `{100 USD, 2025-01-10}`, or the account opened `"FIFO"`, prints one row: 5 ABC acquired 2025-01-10, proceeds 1,000, basis 500, gain 500 USD, more than one year.
- The hosted composer (`composeGains` in `backend-cluster/backend-v2/src/features/ledger/utils/gains.ts`, run through `tsx` on journal rows shaped like the journal API's, with the sale's cost dated 2026-02-01) also returns `rows: []`, so REST, GraphQL and the MCP capital-gains resource have the same gap.

**Root cause:** `_capital_gains` (`cli/src/bea_engine/report.py`, around line 1410) keys each account's held lots by `(currency, Cost)`. That key includes the cost date, and Beancount fills in the sale's own date under `NONE`. So the sale finds no existing lot, `before == 0`, and the posting counts as an augmentation (line 1416, `if before == 0 or (before > 0) == (units.number > 0): continue`). It is neither a row nor an `unpriced_reductions` entry. `composeGains` makes the same choice with `lotKey(... cost.date ...)` (line 200). Under every other accepted method, Beancount has already matched a held lot, so only `NONE` accounts take this path.

**Do:** when a costed, priced posting matches no held lot exactly but runs against the sign of the account's net holding of that commodity in that cost currency, report it as a reduction of that net. Quantity is `min(|net before|, |units|)`. Basis is quantity × the posting's own cost. Proceeds are quantity × its price. That is the gain the transaction books, because Beancount balanced it at that cost. Any excess beyond the net still opens a short, as now. `acquired` is the date of the one held opposite-sign lot with the same cost number (and label, if given) when exactly one exists. Otherwise it is null, and the row goes to the existing `holding_unknown` bucket with no long/short guess. Apply the same rule in `composeGains`, so REST, GraphQL and MCP match `bea`. Describe the rule in `cli/docs/USAGE.md` (Reports, capital-gains paragraph), in the `beancount-trade` realized-gains reference, and in the `NONE` line of its Booking methods section. Those docs should say that naming the lot's date (`{100 USD, 2025-01-10}`) keeps the acquisition date.

**Done when:** on the ledger above, `bea report capital-gains` prints one row: 5 ABC, acquired 2025-01-10, proceeds 1,000, basis 500, gain 500 USD, in the more-than-one-year total. The `{125 USD}` variant prints one 5 ABC row with gain 375 USD and holding unknown. Both tie to `balance gains`. The dated and `FIFO` controls are unchanged. A `NONE` short opened from zero holdings (w1/307's repro) still realizes nothing, and its dated cover still reports 20 USD. The hosted composer returns the same rows. Tests that fail with the change reverted: `cli/tests/test_report_capital_gains*.py`, plus backend-v2 `gains.test.ts` and the capital-gains parity test. `make check-all` (cli) and `yarn test` (backend-v2) pass.

**Blast radius:** `_capital_gains` is the only CLI caller, and `composeGains` serves `LedgerFinanceService.getCapitalGains` and through it REST, GraphQL and MCP. `report holdings`, `trial-balance` and `balance` net a `NONE` account correctly (15 ABC, 2,000 USD cost, and with a 200 USD price a balanced trial balance). The `beancount-trade` and `beancount-ask` realized-gains answers run this command, and their tie-out to booked gains would show a mismatch without explaining it.
