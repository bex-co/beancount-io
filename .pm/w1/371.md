# A refused `bea add pad` says to "Add both directives atomically with bea add balance --pad-from ACCOUNT --date YYYY-MM-DD …": the command drops `--file` and the pad's own account, source and date, so pasting it from another folder writes the pair into the wrong ledger (exit 0), and filling the date moves the pad

**Bug · cli · minor · 20–30m · A1.** From routine cli-qa, 2026-11-23. Every other command `bea` prints for pasting names the ledger through `bea_command()` (w5/303, w5/619): the unknown-account fix-up prints `bea --file books/main.bean add open …`, and a failing balance prints `Opening adjustment command: bea --file …/main.bean add balance --date 2026-03-31 --account Assets:Savings --amount '100 USD' --pad-from SOURCE_ACCOUNT`. The refusal of a lone `bea add pad` is the one left hard-coded. It prints only placeholders, though the pad it refused already names the account, the source and the date. An agent or user who fills the placeholders and runs it from the folder they are in writes to whatever ledger that folder's discovery finds. And because `--pad-date` defaults to the day before the balance, the pad lands on a different day than the one they asked for.

Environment: main `d2f88ef76`, `bea 0.5.0` from the checkout (`uv run bea`), managed engine 0.5.0, macOS 26.5.1. Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, `BEA_FILE`/`BEA_TOKEN` unset, stdin closed, no TTY, fresh processes. Reproduced twice from pristine fixtures.

## Repro

```sh
mkdir -p home client
cat > client/main.bean <<'EOF'
option "operating_currency" "USD"
2026-01-01 open Assets:Savings USD
2026-01-01 open Equity:Opening-Balances USD
EOF
cp client/main.bean home/main.bean      # the user's own books, in the folder they work from
cd home
bea --file ../client/main.bean add pad --date 2026-03-30 -a Assets:Savings --source Equity:Opening-Balances
# the hint, with its placeholders filled in:
bea add balance --pad-from Equity:Opening-Balances --date 2026-03-31 --amount '100 USD' --account Assets:Savings
shasum ../client/main.bean main.bean
```

## Actual

- The `add pad` refusal (exit 1) reads `Proposed append (not written): Unused Pad entry. Add both directives atomically with bea add balance --pad-from ACCOUNT --date YYYY-MM-DD --amount 'NUMBER CURRENCY' --account ACCOUNT.` `--json` carries the same text in `error.details`.
- The pasted command exits 0: `Added 1 pad and 1 balance to …/home/main.bean; the pad inserts 100 USD into Assets:Savings from Equity:Opening-Balances.` `client/main.bean` keeps its hash. The adjustment went into the other books.
- Run in the right ledger (`cd client`), the same hint with `--date 2026-04-30` writes `2026-04-29 pad Assets:Savings Equity:Opening-Balances`, not the 2026-03-30 pad that was asked for, because nothing in the hint carries the pad's date.
- Run from a folder with no `main.bean`, the pasted command is refused for having no ledger: a second refusal.

## Expected

The hint is a command for the ledger and the pad that were refused, built like the other remedies: `bea --file ../client/main.bean add balance --account Assets:Savings --pad-from Equity:Opening-Balances --pad-date 2026-03-30 --date YYYY-MM-DD --amount 'NUMBER USD'`. Only the facts the pad cannot supply stay as placeholders: the balance date (after the pad date) and the statement amount. The currency can be filled in when the account's `open` allows exactly one. Basis: w5/303 and w5/619 (a printed command names the ledger it is about), and `bea add pad`'s own arguments, which already fix the account, source and date.

## Cause

`_unused_pad_hint` (`cli/src/bea_engine/ledger/write.py:3464`) builds the fixed `atomic` string at `:3489` and returns it at `:3495` and `:3513`. That covers the appended pad that nothing follows, which is the case for a lone `bea add pad`. The `pad` entry it receives already carries `account`, `source_account` and `date`. The only caller, at `:3250`, sits in the same refusal builder that already calls `bea_command(snapshot.root if snapshot else file)` for the `add open` and `add commodity` remedies (`:2872`, `:2892`).

## Fix

Owned by `cli`, engine side only. Pass the root (or the prefix `bea_command()` builds) into `_unused_pad_hint`. When the pad is known, render the atomic remedy with `--account`, `--pad-from` and `--pad-date` filled from it. Keep the generic text only when there is no pad entry. Leave the `staged`, "superseded by a later pad" and "already holds" branches as they are. Add a regression test through a real `bea` subprocess that runs `add pad` from a different working directory with `--file`, and asserts that the printed command carries `--file` and the pad's account, source and date, and that running it with a date and amount writes the pad on the original date into the `--file` ledger. Revert the fix and watch the test fail. Run `make check-all` in `cli/`. No REST, GraphQL or MCP surface writes local pads.

## Blast radius

`_unused_pad_hint` has one caller (`write.py:3250`). The `atomic` text is reached only for an appended pad that no later assertion reaches, which in practice means `bea add pad` without `--allow-errors` (w5/799 already covers the staged warning, and w3/224 the `--pad-from` case that already matches). Working controls: the failing-balance remedy and the unknown-account and missing-commodity remedies all carry `--file` through `bea_command()`.

## Dedupe

Searched `.pm/**` for `Add both directives atomically`, `Unused Pad entry`, `bea_command` and `--file` remedies. w3/224, w5/380, w5/798 and w5/799 quote the same text for other reasons (a circular `--pad-from` hint, a lone CR, a pad-only import batch, the staged-pad warning), and none mentions `--file` or the pad's own values. w5/619 fixed the same gap for `add open`/`add commodity`, so this is the remaining sibling of w5/303. `git log -S"Add both directives atomically" -- cli/src` shows the text unchanged since `790791acc`.
