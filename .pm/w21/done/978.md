# Notifications renders every ledger error at once, with no virtualization

**Severity:** moderate. This is a code-path finding; it was not measured on a device. **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).** `mobile/src/screens/notifications-screen/notifications-screen.tsx:385` is a `ScrollView`, and `:422` is `errors.map((err, i) => ...)`. `useLedgerErrors` (`common/hooks/use-ledger-errors.ts`) returns the whole `getLedgerErrors` list, the OpenAPI operation has no pagination, and there is no server-side cap in `ledger/src`. A bad bank import can produce thousands of "unknown account" errors. Each row mounts a `TouchableOpacity`, three `Text` and an icon, about 8 native views.

Not run natively; it would need thousands of errors written to the shared disposable ledger. `tsx` proof is only a React-DOM stand-in for the JS element cost: 74 ms at 5,000 rows and 639 ms at 50,000, which misses native mounting and layout. It is the same unbounded pattern as w21/379 (commit diff).

## Fix

Make the screen a `SectionList` with the errors and changes sections, or cap the errors at about 50 with a "Show all N" control.

**Acceptance:** with a stubbed 5,000-error response the screen mounts at most about 30 `ErrorRow`s, and scrolling reaches the last error.

## Dedupe

w21/313 and w21/221 touch the same screen for other reasons. Searched for "ErrorRow", "errors.map" and "notifications virtualization".

---

**Resolved 2026-10-24** — Notifications draws the ledger errors 50 at a time (`ERRORS_PAGE`): a "Show more (N)" button (`notificationsShowMoreErrors`, 13 locales, no plural form needed) adds the next 50 until the last, so a bad import of thousands of errors mounts at most about 50 rows (about 400 native views) and every error is still reachable. This is the lighter design w21/379 used for the diff, rather than a `SectionList`. Source cases in `errors-paging.test.ts` (fail without the change; `mobile`). Not run natively.
