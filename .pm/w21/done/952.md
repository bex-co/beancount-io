# Merchant detail stops loading rows at a hidden page cap, and the cap shrinks after every edit

**Severity:** minor to moderate. The header gives the merchant's full transaction count, but the list stops early: no spinner, no "end of list", no notice. **Estimate:** 20 minutes. Owner: mobile.

**Root cause (A3).** In `mobile/src/screens/merchant-detail-screen/merchant-detail-screen.tsx`:
- **Stale cap.** `:94-96` sets `PAGE_SIZE = 20` and `MAX_PAGES = 25`. The comment justifies the cap by the free-text filter, which w21/181 replaced with an exact-payee filter, so the reason no longer applies.
- **Silent stop.** `:439-440` sets `hasMore = rawEntries.length < total && pagesFetchedRef.current < MAX_PAGES`, so loading stops at 500 rows while `total` says more exist. The footer (`:775-784`) only ever shows a spinner.
- **Counter never resets.** `pagesFetchedRef` (`:280`) only goes up (`:510`), and only pull-to-refresh resets it (`:541`).
- Every entry write evicts `getLedgerJournal`, so the list reloads from the first 20 rows, but the counter keeps its old count. Each edit therefore lowers the reachable cap.
- The header count comes from BQL `count(*)` (`selectors/merchant-stats.ts:59`), so it always shows the full number.

Not run natively; it needs about 200 fixture entries for one payee. Code path:
- **Over the cap:** a merchant with 730 entries reads "730 transactions", and the list stops at 500. w21/181's resolution noted this as a deviation, but it was never filed.
- **Through the counter:** with 200 entries, scroll to the bottom (counter 10). Edit a row, save and go back: 20 rows, counter still 10. Scroll down (counter 20), edit again, go back and scroll. Only 5 more pages load, so the list stops at 120 of 200.

**Native steps:**
1. Use a disposable ledger where "QA Bean" has about 200 entries.
2. Merchants ▸ QA Bean, then scroll to the bottom.
3. Edit a row twice, going back and scrolling to the bottom each time.

The list stops at about 120 rows, while the header says 200.

## Fix

Remove `MAX_PAGES` and its stale comment, so `hasMore` is `rawEntries.length < total`. If a safety cap stays:
- reset `pagesFetchedRef` to 1 whenever the journal comes back as a first page;
- show a "Showing N of M" footer when the cap stops loading.

**Acceptance:**
- With `total = 730`, all 730 rows load.
- A 200-row merchant, fully scrolled, then refetched to its first page, can page back to 200.
