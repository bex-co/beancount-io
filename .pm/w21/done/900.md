# A transaction whose header fails to parse still appears in Home's Recent Transactions and the journal, with "Transaction" where its amount should be

**Severity:** minor to moderate. Beancount drops an entry whose header doesn't parse, but here a half-parsed entry with no postings is listed as real. **Estimate:** 20 minutes. Owner: ledger, plus mobile. A3: the engine's error recovery keeps the transaction header (`Qa20261020 Joe`) and drops its postings. The journal returns it, and mobile's `entry-row/index.tsx:300` renders a posting-less transaction's amount slot as the word "Transaction".

Reproduced natively with w21/899's fixture and build: Home ▸ Recent Transactions, top row "**Qa20261020 Joe · Oct 22, 2026 · Transaction**" (no amount), while Notifications reports the parse error on that same line.

## Fix

Don't emit entries whose header or postings failed to parse, matching Beancount (ledger). On mobile, render a posting-less transaction as an error row rather than with a bare type word.

**Acceptance:** with this fixture, no "Qa20261020 Joe" row appears, and only the error does. A unit or engine case is added.

## Dedupe

Related to w21/650 (a % posting flag gives 0 postings; done), but a different trigger. Searched `.pm/**` for "no postings" and parse error together with journal.
