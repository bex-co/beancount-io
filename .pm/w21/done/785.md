# Persian/Arabic search misses the same word written with the other script's letters: "کافی" finds nothing beside a "كافي شاپ" row (also Persian digits, ZWNJ, hamza, diacritics)

**Severity:** moderate for Persian and Arabic users. The iOS Persian keyboard types ی/ک, while Arabic keyboards and many bank exports write ي/ك, so a typed name often never matches. **Estimate:** 30 minutes. Owner: ledger, plus mobile. A3: `mobile/src/screens/transactions-screen/utils/plain-search-filter.ts:84-98` (`searchUnits`/`encodeUnit`) tolerates only NFC/NFD, spacing and quote variants. The ledger's `stringPredicate` (`backend-cluster/ledger/src/foundation/rustledger/directive-filter.ts:610`) matches the regex literally. It already folds Turkish İ (`foldDottedI`), but no Arabic-script variants.

Reproduced natively on the iPhone 17e simulator, English UI, Metro `--clear` at `2dffe6ff5`, on the disposable QA ledger, which was restored byte-for-byte to `f1a0b83c`. Fixture: `2026-10-20 * "كافي شاپ" "Check 1042"`, with 12.50 USD from `Assets:Qa20261020:Bank` to `Expenses:Qa20261020:Food`. The row is listed on Transactions. Pasting **کافی** into Search gives **"No transactions match your search or filters."** Under `tsx`, the real `toPlainSearchFilter` was run against the real `filterDirectives` (the agent's proof). Each of these finds 0 entries, while the control `کافی` vs `کافی شاپ` finds 1:
- `كافي` vs `کافی شاپ`
- `۱۰۴۲` vs `Check 1042`, and `1042` vs `چک ۱۰۴۲`
- `می‌خرم` (with ZWNJ) vs `می خرم`
- `احمد` vs `أحمد`
- `محمد` vs `مُحَمَّد`

## Fix

Fold both sides on the server, next to `foldDottedI`, so REST, GraphQL and MCP searches agree:
- ي/ى → ی, ك → ک, ة → ه, and أ/إ/آ → ا
- Arabic-Indic and Persian digits → ASCII
- strip harakat, and treat ZWNJ as a space

Failing that, have `encodeUnit` emit the equivalent character classes.

**Acceptance:** every pair above matches, and Latin search is unchanged. Unit cases are added to the ledger filter tests.

---

**Resolved 2026-10-23** — The ledger's filter matcher folds Arabic-script text on both sides, next to `foldDottedI`, so REST, GraphQL and MCP searches agree. `foldArabicScript` in `backend-cluster/ledger/src/foundation/rustledger/directive-filter.ts`:
- maps ي and ى to ی, ك to ک, ة to ه, and أ, إ and آ to ا;
- turns Arabic-Indic and Persian digits into ASCII;
- drops harakat, the superscript alef and the tatweel (and with them the hamza an NFD alef carries);
- reads the zero-width non-joiner as a space.

Text without these characters is untouched.

Every pair in the note now matches, in both directions where it applies. That held in a ledger unit case and end to end, with mobile's real `toPlainSearchFilter` run through the ledger's `filterDirectives` under ts-node. In the end-to-end run, "Café" and "iş" (Turkish İ) still match and a different Persian word still misses. The unit case in `directive-filter.test.ts` fails at the previous HEAD.

No mobile change was needed: the app sends the typed text and the server folds it. Ledger lint, typecheck, build and test are green. Needs a ledger-service deploy. Not checked natively. Shipped in the commit that moves this note.
