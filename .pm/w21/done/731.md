# A push whose commit messages run past 200 characters still hides its commit count (w21/716 variant): the server cuts the summary first

**Severity:** trivial. **Estimate:** 15 minutes. Owner: backend-v2 and mobile. A3: w21/716's fix reads the count from the summary's last line (`mobile/src/screens/home-screen/components/feed-logic.ts:186,202`, `pushSummary`). The server cuts summaries at 200 characters with "..." (`backend-cluster/backend-v2/src/features/gitea/feed/service/html-utils.ts:21-22`, called from `activity-transformer.ts:218`). With longer commit subjects, the "+N more commit(s)" line is cut off before the client sees it, `pushSummary` returns null, and the row shows two messages and no count, as before w21/716.

Not run natively: it needs a multi-commit `git push`, and the card is below the fold. Proven under `tsx` (the agent's proof) with the real `parseActivityContent`, `summarizeParsedContent`, `stripHtml`, `feedRowDetail` and `pushSummary`. Five commits with subjects of about 75 characters (e.g. "Import Qa20261020 Checking statement 2026-05 (42 transactions, 3 transfers)") produce a 203-character summary ending "(42...", with no count line. Short subjects still work.

## Fix

Return the commit count as a field (or put it first), rather than relying on the last line of a truncated summary.

**Acceptance:** a five-commit push with long subjects shows "5 commits". Short pushes are unchanged. A unit case is added.

## Dedupe

Variant of w21/716 (done). Searched `.pm/**` for stripHtml and pushSummary.

**Resolved 2026-10-23** — the server's summary keeps its count line: when a push's listed commit subjects (or an aggregated item's messages) would run the summary past its 200-character cut, `summarizeParsedContent` shortens each listed line with "…" so the lines and the "+N more commit(s)" line fit within it (`fitLines`; the cut length is `MAX_SUMMARY_LENGTH`, shared with `stripHtml`). The note's five-commit push with ~75-character subjects now ends "+2 more commit(s)", which w21/716's `pushSummary` reads, so the row shows "5 commits"; short pushes are unchanged, and the summary means the same on REST, GraphQL and MCP. Test in `activity-content-parser.test.ts` (fails at the previous HEAD). backend-v2's full unit run here had three failing suites, none touching the feed: `upstream-survival.test.ts` fails the same way at the previous HEAD (its child process prints nothing in this checkout), and `archive-parity` and `ssh-relay` pass when run on their own. Shipped in the commit that closes this note (`backend-cluster/backend-v2`). Needs a backend-v2 deploy to reach production.

Recheck (2026-10-23): not exercised. It needs a multi-commit `git push` with long subjects, and Home's Latest Updates card is below the fold, where the automation here cannot scroll. Any backend-v2 part also waits on the next backend-v2 deploy, which the read-only poller hasn't seen yet. Covered by the unit cases named in the resolution.
