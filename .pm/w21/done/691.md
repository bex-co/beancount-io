# Editing or deleting an entry in a non-UTF-8 ledger file rewrites its undecodable bytes as U+FFFD (edit-path sibling of w21/679)

**Severity:** major (silent, permanent corruption of user text). **Estimate:** 30 minutes. Owner: ledger. A3: `backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts` reads each file through `readGiteaFileText(...)` with no limits, so `decodeText` (`features/gitea/utils/gitea-file-content.ts`) falls back to the lenient `buffer.toString("utf-8")` unless `requireUtf8` is set. A source-slice edit or delete that commits through `commitLedgerFiles` therefore writes every undecodable byte of the file back as U+FFFD. w21/679 made the bulk/`addEntries` route refuse such a file; this path was left alone because `requireUtf8` decodes with `TextDecoder`, which drops a leading BOM, while this read deliberately hands the transform text with the BOM and writes it back (w21/368).

Code-level, not tried against production: a Latin-1 `main.bean` (byte 0xE9) plus an Edit or Delete of any entry in it should leave the file with `EF BF BD` where the byte was.

## Fix

Read these files strictly (`requireUtf8`) and refuse with the same message as w21/679, keeping the BOM round trip (detect it from the raw bytes before decoding, or decode with `ignoreBOM: true` here).

**Acceptance:** editing or deleting an entry in a file that is not valid UTF-8 is refused and commits nothing; a BOM file keeps its BOM; unit cases cover both.
