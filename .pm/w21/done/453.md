# A write whose response is lost can be retried into a duplicate entry: addEntries and bulkEntries have no idempotency key

**Severity:** moderate (duplicate writes). **Estimate:** 2 hours. Owner: backend-v2 and the ledger service, then mobile. Split from w21/351, whose copy half shipped: a transport failure on a write now reads "The server didn't confirm the save. Check before trying again." instead of "Nothing was saved."

`createLedger` accepts a client `requestId` (ADR021: a Redis-backed record per user, scoped by a request hash, so a repeat returns the original result). `addEntries` and `bulkEntries` have nothing like it, so when a connection drops after the request is sent, the user is told to check, and a retry without checking still writes the transaction or budget a second time.

## Fix

Accept an optional `requestId` on `addEntries` and `bulkEntries` on REST, GraphQL and MCP with the same bounds as ledger creation, keep a short-lived idempotency record per user and ledger (request hash, in-progress marker, stored result), and return the original result for a repeat with the same request. Reject a reused id with a different request. Then send a fresh id per save attempt from mobile and keep it across the retry of that attempt.

**Acceptance:** retrying a write whose response was lost, with the same request id, returns the first result and creates one entry, on all three surfaces; a different request under the same id is refused; a request without an id behaves as today.

## Dedupe

Follow-up to w21/351 (done) and the same mechanism as ADR021 (ledger creation). w21/327 and w21/044 are the copy and double-tap parts. Searched `.pm/**` for idempot and requestId.

---

**Blocked 2026-10-21** — Still wanted, but it adds a field to three customer-facing API surfaces and a new idempotency record with a retention window (ADR021's store, or a new one), which is a contract and retention decision for the owner; mobile can only send ids once a backend-v2 deploy accepts them (production's schema is what the generated client is built from).

**Unblock:** the owner approves the contract (field name, bounds, retention window, scope per user and ledger) in an ADR; backend-v2 ships it with parity tests and deploys; then mobile regenerates its client and sends an id per save attempt. Who can clear it: the repository owner.

---

**Resolved 2026-11-08** — closed by triage: the work landed through [w3/m61](../../w3/done/m61/README.md). The owner chose the contract on 2026-11-02: an optional `requestId` of 1–200 characters, kept 24 hours, scoped to user and ledger. It is documented in [ADR026](../../../docs/adrs/ADR026-dashboard-onboarding.md#setup-specification) and the backend-v2 `docs/mcp.md`.
- Backend: `bulkEntries`, legacy `addEntries`, `appendLedgerText`, and `insertReceiptTransaction` accept it on REST, GraphQL, and MCP, with parity tests (`4f6ea03eb`, `fcf984b59`; `legacy-entry-parity` covers `addEntries` in `3c03cdc72`).
- Mobile sends an id with every entry save, including `addEntries` from New Transaction and receipt capture (`e88183272`). A save still in progress is retried with the same id, and one that never finishes reads "The server didn't confirm the save."
