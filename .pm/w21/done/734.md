# Open Account still says a bare "already open" for a future-opened account stored with decomposed accents (w21/723 vs w21/256)

**Severity:** trivial. **Estimate:** 10 minutes. Owner: mobile. A3: the duplicate check matches names by NFC (`open-account-screen/account-name.ts:253-258`, from w21/256), but w21/723's notice looks up the open date with the typed spelling (`open-account-screen.tsx:320-322`). For an account stored as NFD ("Café" with a combining accent), the check finds it but the date lookup misses, so the generic "already open" message shows. w21/122's closed-account wording has the same gap.

Not run natively: it needs an NFD account name written into the ledger and pasted as NFC. Proven under `tsx` (the agent's proof): `openAccountSubmitState` gives `alreadyOpen: true`, while `existingAccountNotice` with the typed spelling gives `openAccountAlreadyOpen`. With the ledger's own spelling it gives `openAccountOpensLater`.

## Fix

Look up the open and close dates with the same NFC key the duplicate check uses.

**Acceptance:** an NFD future account reads "…is already in this ledger, opening on Nov 2, 2026", and an NFD closed account keeps w21/122's wording. A unit case is added.

## Dedupe

Variant of w21/723 (done) via w21/256 (done). Searched `.pm/**` for existingAccountNotice together with NFC.

---

**Resolved 2026-10-23** — `ledgerSpelling` (`open-account-screen/account-name.ts`) gives the ledger's own spelling of a typed name (exact first, else NFC), and both the duplicate check and the notice's open/close date lookup use it. So an NFD account opening on Nov 2 reads "…opening on Nov 2, 2026", and an NFD closed account keeps w21/122's wording. Unit cases in `open-account-screen/__tests__/future-open-date.test.ts`. Shipped in the commit that moves this note.
