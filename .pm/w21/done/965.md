# Invisible format characters survive trimming in payee, narration and account names, so one merchant splits in two and Open Account refuses a name that looks fine

**Severity:** low to moderate. It affects anyone pasting from web pages, right-to-left apps or bank exports. **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).**
- `mobile/src/components/text-input-screen/index.tsx:171` saves with `selected.trim()`. JavaScript's `trim()` strips NBSP and U+FEFF but not U+200B, U+200E/F, U+2060, U+061C or U+2066–2069.
- `common/merchant-key.ts` (`merchantKey`) and `text-input-screen/match-suggestions.ts` fold NFC, whitespace, quotes, width and Arabic letters, but never strip those marks.
- `open-account-screen/account-name.ts:59` (`composeAccountName`) trims only whitespace. The body regex (`:259`) rejects the mark, and the initial check (`:240`) rejects it as the first character.

Not run natively in this pass. `tsx` proof (the agent's), with the real functions:
- `merchantKey("Costco‎") === merchantKey("Costco")` is false for LRM, RLM, ZWSP, WJ, ALM and FSI/PDI, so Merchants splits them.
- `matchSuggestions(["Costco","Costco‎"], "costco", 5)` returns both rows, which look identical.
- `buildEntryInput(..., payee:"Costco‎", narration:"​")` keeps both values. `entryInputToText` writes `2026-10-01 * "Costco‎" "​"`, and the engine parses it back with the mark intact. A narration of only ZWSP is truthy, so it is written as a blank-looking narration.
- `composeAccountName("Assets","Bank‎")` returns `Assets:Bank‎`, and `validateAccountName` gives `invalidCharacters`. A leading RLM gives `componentMustStartUppercase`. The user sees "Bank" and an error about letters or capitals, with nothing visibly wrong.

**Native steps** (text via paste only):
1. Copy `Costco` followed by U+200E to the clipboard.
2. New Transaction → Payee → paste → Save, then enter a normal "Costco" transaction too.
3. Merchants lists two "Costco" rows, and the payee suggestions show two identical rows.
4. For accounts: Open Account → paste `Bank` followed by U+200E. Done stays disabled with "Use only letters, numbers, and hyphens".

## Fix

Add one shared `cleanFreeText` helper that strips `\p{Cf}`, except ZWNJ and ZWJ, which Persian and Indic text needs. Apply it in the `TextInputScreen` commit, in `merchantKey`, in `matchSuggestions`' fold and key, and in `composeAccountName`. A whitespace-only payee or narration after stripping saves as empty.

**Acceptance:**
- `merchantKey("Costco‎")` equals `merchantKey("Costco")`.
- Committing `"Costco‎"` calls `onSave("Costco")`.
- `composeAccountName("Assets","‏Bank‎")` is `Assets:Bank` and validates.
- A `"​"` narration saves as empty.
- `"خانه‌ها"` (with ZWNJ) is unchanged.

## Dedupe

Related but different: w21/460 and w21/093 (ASCII whitespace), w21/410 (NFC), w21/192 (ZWNJ allowed in account bodies), w21/927 (right-to-left display). None strips these marks. Searched for "zero-width", "LRM", "RLM", "invisible", "U+200B" and "trim".

**Resolved 2026-10-24** — a shared `cleanFreeText` (`common/clean-free-text.ts`) strips the marks that draw nothing (ZWSP, LRM/RLM, the bidi embeddings and isolates, the word joiner and invisible operators, the Arabic letter mark, soft hyphen, a mid-string BOM) and trims, keeping ZWNJ and ZWJ for Persian and Indic words. The text input commits through it, `merchantKey` and `matchSuggestions` fold without the marks, and `composeAccountName` cleans each component, so "Costco" with a trailing LRM is one merchant and one suggestion, a ZWSP-only narration saves empty, and `‏Bank‎` composes to `Assets:Bank` and validates.
