# Copy & Reload (and Reload) after a content change elsewhere lands on "This transaction was changed or removed", not on the current version (gap in w21/817)

**Severity:** minor. The draft is now saved to the clipboard, but the screen the user lands on can't take it: they must go back, find the entry again, open its editor and paste. **Estimate:** 30 minutes. Owner: mobile, plus the ledger if an identity hint is needed. A3: an entry's ID is its content hash. After any change to its postings elsewhere, the old hash is gone, so `copyThenReload` (and plain Reload, w21/253) refetches by the old ID, gets `NOT_FOUND` and renders `RouteLedgerUnavailable`. w21/817's resolution says it "loads the current version, under its new checksum".

Native (iPhone 17e, Metro `--clear` at `b35df662f`; disposable ledger restored byte-for-byte to `f1a0b83c`). Fixture: `2026-10-20 * "Qa20261020 Cafe" "Lunch"` with 12.00 USD. Edit Transaction ▸ paste a 14.00 version ▸ change the entry to 15.00 through the API ▸ Save ▸ **Copy & Reload**. The draft is on the clipboard, and the screen reads **"This transaction was changed or removed. Go back to see the current list."**

## Fix

When the old ID is gone, locate the changed entry by its source position (file and line from the last context read, as the slice endpoint already reports) or by date and payee. If exactly one candidate sits at that location, open the editor on it, so the copied draft can be pasted and saved against its checksum. Otherwise keep the current message, and add a "Copied — paste after reopening" hint.

**Acceptance:** for this fixture, Copy & Reload opens the editor on the 15.00 version with the draft on the clipboard. Twins and deletions keep the "changed or removed" message (w21/693). A unit case is added.

**Resolved 2026-10-23** — When a reload's old ID answers nothing, Edit Transaction (`edit-transaction-screen.tsx`) now looks for the changed entry where it was written, before saying it is gone. The screen keeps the file, line and date of the last context it read. A reload that gets nothing reads that day's transactions with the journal query (a one-day `time` window, which the ledger's `parseDateRange` reads as that day). It then reads each one's context, and adopts the entry only if exactly one sits at that file and line. The editor then holds the current version under its new ID and checksum. The pure helpers are in `relocate-entry.ts`: `entryLocation`, `sameDayTransactionIds` and `relocatedEntryId`.

Copy & Reload and plain Reload both go through this, so for the note's fixture Copy & Reload opens the 15.00 version with the draft on the clipboard. Twins at one place, an entry deleted, or one moved to another file keep the "changed or removed" message (w21/693). No ledger change was needed: the context read already reports file and line.

Unit cases and a wiring check are in `__tests__/relocate-entry.test.ts`; the wiring check fails at the previous HEAD. I didn't add the note's optional "Copied — paste after reopening" hint for the unresolved case. A concurrent change can't be timed through these taps, so this was not checked natively.
