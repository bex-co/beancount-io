# Transaction detail lists metadata in a different, arbitrary order on each load ("note, po, due, invoice, paid", then "paid, invoice, due, note, po")

**Severity:** low. An invoice's fields jump around between visits and never follow the order written in the file. **Estimate:** 30 minutes. Owner: ledger. A3: rustledger's meta map reaches `serializeMeta` (`backend-cluster/ledger/src/foundation/rustledger/journal-serialize.ts:119-130`, posting meta at `:183`) with no stable key order. `Object.keys(meta)` copies that order into the journal JSON, and mobile's `userMetadataLines` (`select-transaction-detail.ts:188`) renders it in that order.

Reproduced natively on the iPhone 17e simulator at `main` `73480f666`, on the disposable QA ledger, which was restored byte-for-byte to `f1a0b83c`. The entry's metadata was written as `invoice`, `po`, `due`, `paid`, `note`, and one posting's as `step1`, `step2`, `step3`. The first load of the detail screen showed **note, po, due, invoice, paid** and **step3, step1, step2**. After the entry was rewritten with only its flag and date changed, it showed **paid, invoice, due, note, po** and **step1, step3, step2**.

## Fix

Emit metadata in source order. If rustledger cannot preserve insertion order, the ledger service can recover it: sort the keys by their line in the entry's source (the meta's `lineno` per key, or the entry's own text). Sorting by key name is an acceptable fallback, because it is at least stable.

**Acceptance:** this fixture lists `invoice, po, due, paid, note` and `step1, step2, step3` on every load. A unit case is added to the ledger's serializer tests.

---

**Resolved 2026-10-23** — The engine now lists metadata in source order. rustledger hands meta back in hash-map order, which varies between parses: the fixture came back as "po, paid, note, invoice, due" in one process and "po, invoice, note, paid, due" in another. A new `orderMetaAsWritten` (`backend-cluster/ledger/src/foundation/rustledger/meta-order.ts`) runs once per parse and reorders each entry's and posting's keys to the order the source writes them. It finds the entry's block by its date and keys, preferring the one with its narration, and claims each block once in include order. Each posting matches by account.

Keys are reordered in place, so directives keep their identity and provenance. Entry IDs are unchanged, because meta is excluded from the entry hash. An entry the source doesn't show (a plugin's copy on another day) gets its keys sorted by name, which is stable. Journal and context responses both carry the order, and mobile's `userMetadataLines` already renders keys in the order it receives them.

The fixture now reads `invoice, po, due, paid, note` and `step1, step2, step3` on every parse.

Tests:
- **Regression:** unit cases in `meta-order.test.ts` (same-day entries across an include, CRLF, a non-transaction, an unseen entry) fail with the pass disabled. A live engine case in `scripts/verify-rustledger.ts` fails at HEAD's wiring.
- **Contract pin:** a case in `journal-serialize.test.ts` pins that the serializer keeps the order. It already held at HEAD.

On a synthetic 30,000-entry ledger with meta on every entry and posting, the pass costs about 90 ms warm against a 2.2 s parse. Ledger lint, typecheck, build, test and verify are green. Needs a ledger-service deploy. Not checked natively. Shipped in the commit that moves this note.
