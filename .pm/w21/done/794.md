# In a zero-decimal ledger (JPY, KRW…), New Transaction reads "0.500" as 500, a 1000× error (regression from w21/697)

**Severity:** minor, but the saved amount is 1000× what was typed. **Estimate:** 10 minutes. Owner: mobile. A3: `postings-utils.ts:97`. w21/697's zero-minor-unit rule, `/^-?\d{1,3}[.,]\d{3}$/`, treats any single group of three digits as thousands. That includes the group after a leading `0`, which can never be a thousands group.

Not run natively (needs a JPY ledger). Under `tsx` with minorUnits 0 (the agent's proof), `"0.500"` gives 500 and `"0,750"` gives 750, and `buildEntryInput` sends `{"Assets:Cash": "500 JPY", "Expenses:Food": "-500 JPY"}`. `"0.5"` stays 0.5. The field shows "0.500" while the auto row shows "500".

## Fix

Require a non-zero first group, for example `/^-?[1-9]\d{0,2}[.,]\d{3}$/`.

**Acceptance:** in a JPY ledger, "0.500" is not read as 500, and "1.500" is still 1500. A regression unit case is added.

Regression from w21/697 (done 2026-10-23). Searched `.pm/**` for "0.500" and "leading zero" together with thousands.

**Resolved 2026-10-23** — w21/697's zero-decimal thousands rule in `parseExactAmount` (`multi-postings-transaction/postings-utils.ts`) now requires a non-zero first group: `/^-?[1-9]\d{0,2}[.,]\d{3}$/`. In a JPY ledger, "0.500" stays 0.500 (and "0,750" is 0.750), where it used to read 500. "1.500" and "9,999" are still 1500 and 9999. A regression case in `__tests__/postings-utils.test.ts` fails at the previous HEAD. Not checked natively (needs a JPY ledger). Shipped in the commit that moves this note.
