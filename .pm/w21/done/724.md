# Merchant detail keeps the payee spellings it was opened with, so an edit that recases the payee drops the entry from the detail while Merchants still counts it

**Severity:** minor. **Estimate:** 20 minutes. Owner: mobile. A3: `merchant-detail-screen/merchant-detail-screen.tsx:698-701` and `:728` build `spellings` once from the route params (`payee`, `otherSpellings`). The header queries (`:274-306`: count, dates and totals by exact `payee = "…"`) and the row filter (`:356-358`, `filterExactPayee`, case-sensitive) all use that frozen list. After an in-app edit, Merchants refetches its rollup and re-merges case variants (`merchants-screen/selectors/aggregate-payees.ts:96-180`), but the detail on the stack never learns the new spelling.

Not run natively: the repro needs the edited entry's payee retyped in the code editor (select-all plus paste), and that isn't reliable here. Proven under `tsx` (the agent's proof) with two `Qa20261020 Cafe` coffees. After one is edited to `QA20261020 CAFE`, `filterExactPayee` with the route spellings `["Qa20261020 Cafe"]` keeps one row, and the header BQL is `WHERE payee = "Qa20261020 Cafe"`. Meanwhile `aggregatePayees` on the refetched rollup returns `{payee: "QA20261020 CAFE", transactionCount: 2, otherSpellings: ["Qa20261020 Cafe"]}`. The detail then reads "1 transaction · $4.00", while Merchants reads 2.

## Fix

Derive the spellings from the refetched rollup (match it by the merged key) instead of the route params, or refresh them after a write.

**Acceptance:** after the recasing edit, the detail shows 2 transactions and $8.00, and both rows. A unit case is added.

**Resolved 2026-10-23** — merchant detail reads by the spellings of the directory row its payee now belongs to: it subscribes to the Merchants list's own payee rollup (the same query, so it shares the cache and is refreshed after a write) and takes the merged row whose case-folded key matches the payee it was opened for (`merchantSpellings`), falling back to the route's spellings until the rollup loads or when no row has the payee. After the recasing edit the detail reads by both spellings, so its header queries and row filter count both coffees (2 transactions, $8.00, both rows); while the spellings hold, the same array is kept and nothing is asked again. A payee renamed to a different word (not a case variant) is still read by its old spelling. Tests in `merchant-spellings.test.ts` with the real `aggregatePayees` and `filterExactPayee` (the screen check fails at the previous HEAD); shipped in the commit that closes this note (`mobile`). Not re-run natively.

Recheck (2026-10-23): not exercised natively. It needs an in-app edit that recases the payee in the Edit Transaction code editor (select-all plus typed or pasted text), which the automation here can't do reliably. An edit made through the API wouldn't go through the app's invalidation path, so it isn't equivalent. Covered by the unit case named in the resolution.
