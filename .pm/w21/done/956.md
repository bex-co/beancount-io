# Receipt Try Again after a failed parse uploads the whole photo again, though it already reached storage

**Severity:** minor. On slow cellular (w21/205 measured 3–4 MB at about 400 kbps, roughly 80 s), every parse retry repeats the full upload. **Estimate:** 20 minutes. Owner: mobile.

**Root cause (A3).** `handleRetry` (`mobile/src/screens/receipt-capture-screen/receipt-capture-screen.tsx:136-139`) calls `handleUpload` → `startCapture`. That always mints a new upload URL and PUTs the photo again (`use-receipt-workflow.ts:94, 117`). The `objectKey` from the successful upload is never kept, though the comment at `:184` says the uploaded file stays valid.

Not run natively; a parse would spend AI quota. `tsx` proof: the real `useReceiptWorkflow`, with React, the file system and the mutations stubbed. The first parse fails with a network error, then Try Again succeeds. The calls are `mintUploadUrl, PUT obj1, parse tmp/u/obj1, mintUploadUrl, PUT obj4, parse tmp/u/obj4`. The second mint and PUT are redundant.

## Fix

- After a successful upload, keep `{objectKey}` on the hook.
- When the failure was `parse_failed`, Try Again calls `parseReceipt` with the stored key.
- Clear the key on Retake, cancel and unmount.
- If the server reports the key missing, fall back to a full upload.

**Acceptance:**
- Try Again after a parse error makes exactly one `parse` call, with no new upload URL and no PUT.
- A failure during the upload itself still re-uploads.
