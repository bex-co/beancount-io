# Adding an entry to a non-UTF-8 ledger file replaces its non-ASCII bytes with U+FFFD, and the precheck counts that as a fix

**Severity:** major (silent, permanent corruption of user text). **Estimate:** 30 minutes. Owner: ledger. A3: `backend-cluster/ledger/src/api/entries.ts:196` decodes the target file leniently (`Buffer…toString("utf8")`) and writes the re-encoded text back. The precheck (`entries.ts:343`) then sees the existing "is not UTF-8 text" error disappear, which it allows. w23/030 fixed this in backend-v2's append and edit tools, but not in this route. Open Account's `bulkEntries` goes the same way.

Production, through the `addEntries` mutation New Transaction sends (`multi-postings-transaction-screen.tsx:687`), on the disposable ledger (restored byte-for-byte after each probe). The agent also ran the real `main` service code (`08cbe6191`) in memory and checked it against Beancount 3.2.

`main.bean` was set to the QA ledger plus one Latin-1 comment line `; qa-20261020 Caf\xE9 latin-1` (byte 0xE9). Before: `getLedgerErrors` = "main.bean is not UTF-8 text (invalid UTF-8 or binary data), so none of its entries were read". `addEntries` (narration "qa latin") returned `success: true`. After: the file holds 0 bytes of 0xE9 and 1 U+FFFD (`EF BF BD`), and the error list is empty. The original "é" is gone for good.

## Fix

Decode strictly, as the loader does, and refuse the write when the target file isn't valid UTF-8, with the same message as w23/030. Never rewrite bytes the user didn't touch.

**Acceptance:** with this fixture, the add is refused and the file's bytes are unchanged. A unit case covers an included Latin-1 file.
