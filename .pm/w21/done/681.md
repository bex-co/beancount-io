# Any add or edit touching an account whose `~`-tolerance balance already fails is refused (gap in w21/618)

**Severity:** minor (an account with such an assertion can't be booked against before the assertion date). **Estimate:** 15 minutes. Owner: ledger. A3: `backend-cluster/ledger/src/features/ledger/utils/new-ledger-errors.ts:18-22` drops the changing "got" figure only from messages that start "Balance failed for". The engine words an explicit-tolerance failure as "Balance exceeds explicit tolerance for A: expected X ~ T, got Y (difference: D)", so after any change the error looks new. w21/533 is the display side of the same message.

Production, through the `addEntries` mutation New Transaction sends (`multi-postings-transaction-screen.tsx:687`), on the disposable ledger (restored byte-for-byte after each probe). The agent also ran the real `main` service code (`08cbe6191`) in memory and checked it against Beancount 3.2.

The QA ledger plus `2026-01-01 open Assets:Qa20261020Tol` and `2026-06-01 balance Assets:Qa20261020Tol 100 ~ 0.01 USD`. Before: "Balance exceeds explicit tolerance for Assets:Qa20261020Tol: expected 100 USD ~ 0.01, got 0 USD (difference: 100)". `addEntries` dated 2026-03-01 (−5.00 USD from that account) is refused: "Validation failed for entries: adding these entries would introduce 1 new bean-check error: Balance exceeds explicit tolerance … got -5.00 USD (difference: 105.00)". It is the same assertion, still failing.

## Fix

Normalize the explicit-tolerance message the way the "Balance failed for" one is: drop the "got" and "difference" figures. Better still, match balance errors by the assertion's location.

**Acceptance:** this add is accepted, and an add that makes a passing assertion fail is still refused. A unit case is added.
