# w21/135 follow-up: padding dropped for being within tolerance still counts when the next balance is checked

**Severity:** major (a failed reconciliation looks like a pass). **Estimate:** 1 hour. Owner: ledger. A3: w21/135 drops padding within the balance's tolerance in `pad-tolerance.ts:77-114`. That happens *after* rustledger has validated with the padding in place, and `engine.ts:718-727` keeps those validation results. A later balance is therefore checked against the padded amount, while the journal shows the unpadded one.

Production, through GraphQL on the disposable ledger (restored byte-for-byte; ledger service as deployed 2026-10-22), and the agent's run of the real `main` service code (`e911af9c8`) against an in-memory store, with `bean-check`/`bean-query` 3.2 as the reference.

```
2026-01-02 * "QA Deposit"      ; PadCash +100.00
2026-01-10 * "QA Lunch"        ; PadCash −2.00
2026-01-31 pad Assets:Qa20261020PadCash Equity:Qa20261020Open
2026-02-01 balance Assets:Qa20261020PadCash  100.00 ~ 5.00 USD
2026-03-01 balance Assets:Qa20261020PadCash  100.00 USD
```

`getLedgerErrors` returns only "Unused Pad entry". bean-check also reports "Balance failed … expected 100.00 USD != accumulated 98.00 USD" on the 03-01 line. Account detail's 03-01 Balance row reads 98.00 with `diff_amount: null`. In a variant where 0.001 of padding is dropped (agent's fixture C), the later failure says "got 90.001 USD" while the row shows 90.

## Fix

Run the tolerance decision before validation: strip the within-tolerance padding, then re-validate the account's later balances. Alternatively, re-check balances after `pad-tolerance` adjusts the stream.

**Acceptance:** this fixture reports the 03-01 failure with the 98.00 figure, and the row shows "Off by −2.00 USD". w21/135's acceptance still holds. A unit case is added.
