# Mobile uploads receipt photos of any size or dimensions, so oversized ones fail with "Could not read receipt" and a Try Again that can't help

**Severity:** moderate. How often it happens depends on the model provider. **Estimate:** 30 minutes. Owner: mobile, with an optional backend guard.

**Root cause (A3).**
- **Mobile picks at full size.** The library pick uses `quality: 0.85` at full resolution and never reads `fileSize`, `width` or `height` (`mobile/src/screens/receipt-capture-screen/receipt-capture-screen.tsx:96-106`). The camera capture does the same (`camera-view.tsx:141`), and `shotFromLibraryResult` drops the size fields.
- **The backend doesn't check size.** It checks only the content type (`backend-v2/src/features/llm/service/llm-service.ts:255-262`), then hands the presigned URL to the model (`utils/prepare-llm-message.ts:50`). The presigned PUT has no length condition (`asset-storage-service.ts:176-180`).
- **The dashboard does cap it.** It limits uploads to 5 MB (`dashboard/src/features/receipt/components/receipt-upload-zone.tsx:13`), which matches the primary model's image limit.

**What fails:** the primary model, `claude-sonnet-4-5`, documents limits of 5 MB per image and 8000 px per side. Images that can exceed them:
- Android "capture more" scrolling screenshots of e-receipts, often 1080×10000 px or more;
- 24 MP library photos re-encoded to JPEG at 0.85, which can pass 5 MB.

With only an Anthropic key configured, these fail every time as `parse_failed`. `receiptCanRetry` keeps offering Try Again, and every tap re-uploads the same file.

**Not proven live:** checking would spend AI parse quota, so this rests on the code path and the provider's documented limits. **Native steps (they spend quota):** `xcrun simctl addmedia booted tall.png` with a 1080×12000 PNG, then Scan Receipt → Choose from photos → Upload.

## Fix

Refuse oversized images before upload, without adding a dependency: mirror the dashboard's 5 MB cap plus an 8000 px guard, using the picker's `fileSize`, `width` and `height`, and show a dedicated "too large" message with no Try Again. Downscaling instead would need `expo-image-manipulator`, which is a new dependency and needs the owner's approval. Optionally, the backend can also refuse by `contentLength` from `getObjectMetadata`.

**Acceptance:** an asset over 5 MB or over 8000 px never starts an upload and shows a distinct message without Try Again. A unit test covers both limits.

## Dedupe

w21/205 deliberately deferred downscaling for upload speed, and never raised the model-limit failure. Searched for "5MB", "MAX_BYTES", "fileTooLarge", "8000", "panorama", "downscale" and "resize".

**Resolved 2026-10-24** — a receipt image over 5 MB, or over 8000 pixels on either side, never starts an upload: the library pick reports `fileSize`, `width` and `height` (the camera its dimensions), `receiptTooLarge` checks them, and the picker and the shutter drop the file and show `receiptTooLarge` (13 locales) with no Try Again. Cases in `too-large.test.ts` (both limits and the screen's two guards; `mobile`). Not done: downscaling (a new dependency, for the owner) and the optional backend guard. Not run natively.
