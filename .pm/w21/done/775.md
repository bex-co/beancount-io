# With `close_tree` declared before `auto_accounts`, a valid posting gets a false "inactive account" error and its save is refused (w21/737 and w21/753 variant: plugin order)

**Severity:** major once deployed (a valid save is refused). **Estimate:** 20 minutes. Owner: ledger. A3: `backend-cluster/ledger/src/foundation/rustledger/generated-closes.ts:49-53` takes the generated closes from the plugin-transformed stream, regardless of plugin order. Beancount's `close_tree` only closes children that already have an `open` when it runs. Declared before `auto_accounts` it sees none, and it drops the parent's close too. The same gap applies to w21/756's `inactivePads` (`:129-133`).

Proven with the real engine under ts-node (as `yarn verify:rustledger` runs it) against Beancount 3.2.3 `bean-check` (the agent's run). Not on production: the ledger service hasn't been redeployed with these fixes. `plugin "beancount.plugins.close_tree"` then `plugin "beancount.plugins.auto_accounts"`; a 2024-01-02 buy into `Assets:Qa20261020Broker:VTI`; `2024-04-01 close Assets:Qa20261020Broker`; then `addEntries` with `2024-05-01 * "Qa20261020 Late"` (Broker:VTI 1 USD / Cash). bean-check reports 0 errors. The engine reports "E1003 Posting to inactive account Assets:Qa20261020Broker:VTI on 2024-05-01 (closed on 2024-04-01)", and `refuseNewLedgerErrors` refuses the save. A pad into Broker:VTI after the close gives a false E1003 too. With the plugin order reversed, both tools agree.

## Fix

Evaluate generated closes at `close_tree`'s position in the plugin order: only children opened before it runs are closed.

**Acceptance:** this add is accepted, and the reversed order still flags as bean-check does. A unit case is added.

## Dedupe

Variant of w21/737 and w21/753 (done); not w21/757 (nounused). Searched `.pm/**` for close_tree together with auto_accounts.

---

**Resolved 2026-10-23** — Generated closes are now evaluated at close_tree's position in the plugin order. A new `closeTreeKeeps` in `backend-cluster/ledger/src/foundation/rustledger/generated-closes.ts` models what Beancount's close_tree sees when it runs: the written opens, or every account once `auto_accounts` (or `auto`) has run before it. Both `inactiveAfterGeneratedCloses` and w21/756's `inactivePads` count a close only when that view keeps it.

The same model covers the other half the note names. close_tree drops the written close of a parent it does not see opened, and the new `withoutDroppedCloseErrors` (run after `openAutoAccounts`) removes the engine's errors about such a close: postings after it, its non-zero balance, and "Account X was never opened" on the close's own line. That fixes close_tree's documented case of closing a parent that was never opened, without auto_accounts too.

Checked against bean-check 3.2.3 on seven variants:
- **Pass, as bean-check does:** close_tree then auto_accounts with the note's late buy, a written parent with an auto-opened child, the pad after the close, and a dropped parent with a later posting to the parent itself.
- **Flag on bean-check's lines:** the reversed order, a written child, and close_tree alone with a parent never opened.

Unit cases in `generated-closes.test.ts` cover these (three fail with HEAD's behaviour), and the live engine cases in `scripts/verify-rustledger.ts` fail at the previous HEAD. The existing w21/737 fixture gained the opens its children need. The engine's stream still holds the dropped close (only its errors go). The ledger `yarn test` run had one failure, the known intermittent `file-request-limit` ECONNRESET, which passed on rerun. Needs a ledger-service deploy. Shipped in the commit that moves this note.
