# Transaction rows and the detail headline show digits the ledger never wrote for amounts of 17 or more significant digits

**Severity:** low. It shows wrong figures for high-supply crypto, and the row and the posting list on the detail screen disagree. **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).**
- `selectTransactionAmount` (`mobile/src/screens/transactions-screen/utils/transaction-display-utils.ts`) parses every leg with `parseFloat` (`:122`, `:154`, `:163`, and the bucket sum near them), then formats with `formatAmount` (`:60`), which calls `toLocaleString("en-US", { maximumFractionDigits: scale })` on that double.
- It also feeds `selectEntryRowAmount`, which is used by the Transactions rows, the Home Recent card, the Reports account card, the merchant rows and the detail headline (`select-transaction-detail.ts:74`).
- The posting rows on the detail screen use the exact-string path (`formatPostingUnits`), so one screen shows two different numbers.
- The ledger sends exact decimal strings; `journal-serialize.ts:serializeAmount` copies `amount.number` as written.

Not run natively in this pass. `tsx` proof (a transaction of `n SHIB` against `Income:Airdrop`):

| Ledger amount | Row | Detail posting row |
|---|---|---|
| 1234567890.12345678 | `+1,234,567,890.12345670 SHIB` | `+1,234,567,890.12345678 SHIB` |
| 98765432109.87654321 | `+98,765,432,109.87654000 SHIB` | `+98,765,432,109.87654321 SHIB` |
| 1000000000000.00000001 | `+1,000,000,000,000.00000000 SHIB` | `+1,000,000,000,000.00000001 SHIB` |
| 9007199254740993 ETH | `9,007,199,254,740,992 ETH` | `…993 ETH` |
| 1.234567890123456789 ETH | `1.2345678901234567 ETH` | `1.234567890123456789 ETH` |

Amounts of 15 or fewer significant digits are fine.

**Native steps:** on the disposable ledger, add `Assets:QaWallet` and `Income:QaAirdrop`, then a transaction with `Assets:QaWallet 1234567890.12345678 QASHIB`. Compare the Transactions row with the detail posting row.

## Fix

When a bucket has a single leg, or every leg's `units.number` is a plain decimal, keep the exact string. Otherwise, sum through the decimal strings, as `addExact` in `multi-postings/postings-utils` does, and render with `formatExactUnits`, as Accounts and account detail already do.

**Acceptance:** `selectEntryRowAmount` with `1234567890.12345678 SHIB` returns `+1,234,567,890.12345678 SHIB`, with the same case for 9007199254740993 and for a two-leg same-currency bucket.

**Resolved 2026-10-24** — `selectTransactionAmount` keeps each bucket's legs as written and, for a figure of more than 15 significant digits, formats the exact decimal sum (through `addExact`, as the form does) or the largest leg as written, instead of a double: `1234567890.12345678 SHIB`, `9007199254740993 ETH` and `1.234567890123456789 ETH` read as the ledger wrote them, the same as the detail screen's posting rows, and two legs of one bucket add exactly. This is the shared selector behind the Transactions rows, Home Recent, the Reports account card, merchant rows and the detail headline. Amounts of 15 digits or fewer take the old path unchanged. Cases in `format-entry-row-amount.test.ts` (fail without the change; `mobile`). Deviation: the fee and income-funded branches still sum floats. Not run natively.
