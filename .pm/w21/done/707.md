# File editor: since w21/689, text typed during a save is lost when that save conflicts and you choose Overwrite or Recreate

**Severity:** minor (silent loss of keystrokes; a narrow window). **Estimate:** 20 minutes. Owner: mobile. A3: w21/689 made a save mark its sent text as the latest at the start (`recoveryRef.current.saving(content)`), in both `handleSave` (`ledger-file-editor-screen/index.tsx:894`) and `recreateFile` (`:817`). When that save hits a conflict and the user picks Overwrite (`:750`) or Recreate (`:841`), the rebase runs on the sent text and overwrites the newer draft. Before 689, the latest text was read before the Overwrite's save.

Not run natively: the window is one network round-trip, the same limit as w21/689. Proven under `tsx` with the real `createEditorRecovery`, in the screen's call order: type AAA ▸ Save ▸ type BBB while saving ▸ the file changed elsewhere ▸ File Changed ▸ Overwrite. The rebase value is `"L1\nAAA\n"` after the fix, where it was `"L1\nAAA\nBBB\n"` before. BBB is neither on screen nor saved.

## Fix

Have the Overwrite and Recreate paths rebase on the latest draft rather than the sent text (call `saving` with the current editor text, or keep "sent" and "latest" separate).

**Acceptance:** with BBB typed during the conflicting save, Overwrite and Recreate keep BBB on screen as unsaved. w21/689's acceptance still holds. A unit case is added.

## Dedupe

Regression from w21/689 (done). Searched `.pm/**` for recoveryRef, rebaseOnSaved and Overwrite together with "typed".

---

**Resolved 2026-10-23** — a retry no longer marks the text it resends as the latest: the save that started it already did, and anything typed since is newer. `handleSave` calls `recoveryRef.current.saving(content)` only for a save of its own (not when Overwrite runs it with `viaRestore`), and `recreateFile` no longer calls it at all (Recreate is offered only after `handleSave` failed). Overwrite and Recreate then rebase on `latest()`, which still holds BBB, so BBB stays on screen as unsaved. w21/689's paths are unchanged: a save of its own still marks its text first, and keystrokes typed during it outlive a restart. Tests in `rebase-after-overwrite.test.ts`: the screen's order with the real recovery, and source checks that the retries do not re-mark (the source check fails at the previous HEAD; w21/689's check that Recreate re-marks was the regression and is replaced). Shipped in the commit that closes this note (`mobile`). Not re-run natively (the window is one round trip).
