# "Load more" silently skips a row after a deletion elsewhere, and repeats one after a reorder

**Severity:** minor. It happens in the same agent or CLI writes scenario as w21/035. **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).** In `mobile/src/screens/transactions-screen/utils/merge-journal-page.ts:24-33`:
- **Deletion:** a deletion shrinks the total, so `moved` is true. But `overlapped` is set only on a repeated hash, so nothing reloads (`transactions-screen.tsx:259`), and the row that shifted across the page boundary is never shown. w21/035 closed this as undetectable from the page, but since w21/419 the totals do detect it.
- **Reorder:** an edit that moves an entry (a date change, or a delete plus an add) leaves the total unchanged. The page is then appended as is, so the boundary row appears twice and the moved entry never appears.

Merchant detail uses the same merge (`merchant-detail-screen.tsx:491`).

Not run natively; the simulator driver can't scroll.

**`tsx` proof, with 45 rows and 20 loaded:**
- Deleting loaded row 5 gives `overlapped=false`, and row 20 is missing from the list.
- Moving row 30 to position 3 (new hash) gives `overlapped=false`, shows `h19` twice, and the edited entry is absent.

## Fix

- Treat any `totals.page !== totals.loaded` as a reason to reload from the top.
- For a same-total reorder, also reload when `page[0]` repeats the last loaded row's hash and source position (`meta.filename`/`lineno`). True twins (w21/419) still page through.

**Acceptance:**
- A deletion between pages loses no row.
- A same-total reorder shows no duplicate and does show the moved entry.
- w21/419's twins still page through.

## Dedupe

Only w21/035 (its claim is now stale), w21/072, w21/116 and w21/419 came up. Searched for "removal elsewhere", "skipped row", "mergeJournalPage" and "offset paging".

---

**Resolved 2026-10-24** — `mergeJournalPage` reports the list as moved whenever the total changed between pages (a delete elsewhere no longer drops the row that shifted across the boundary), and on a same-total page that opens on the last loaded row again at the same file and line (an edit that moved an entry); a true twin sits on another line and pages through. Both screens that use it reload from the top on that signal. Cases in `merge-journal-page.test.ts` (`mobile`). Not run natively; the same-total check relies on the journal rows carrying `meta.filename` and `meta.lineno`, and is inert without them.
