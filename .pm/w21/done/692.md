# w21/672 is undone by Edit ▸ Cancel: the twin guard stays off, and a later Delete removes the surviving twin

**Severity:** major (data loss; the w21/672 scenario with one extra tap). **Estimate:** 20 minutes. Owner: mobile. A3: `handleEdit` sets `adoptNextSha.current = true` (`transaction-detail-screen.tsx:447`) so that the screen's own save can change the slice. That flag is cleared only when the checksum changes (`:410-416`). Cancel writes nothing and changes no checksum, so the flag stays on. The next re-read, even one that returns the other twin's slice, is then adopted silently: `entryReplaced` stays false, and Delete sends the twin's checksum.

Native (iPhone 17e, Metro `--clear` at `cfbde51b0`; disposable ledger restored byte-for-byte; today 2026-10-23), with w21/672's twin fixture (`receipt: "A-001"` and `"B-002"`, both "QA TwinCafe" on 2026-10-01):

1. Home ▸ the A-001 coffee, then the pencil ▸ **Cancel**.
2. TO ▸ Expenses:Qa20261020Coffee ▸ the lower row (A) ▸ ⋯ ▸ Delete ▸ Delete. Account detail then lists one coffee.
3. Back on the first screen, it still shows QA TwinCafe with `receipt: A-001`, while Entry Context now reads **main.bean:94** (B's line). Without step 1, it reads "This transaction was changed or removed" (w21/672's recheck).
4. ⋯ ▸ Delete ▸ Delete. The journal afterwards holds **no** QA TwinCafe entries; B was deleted.

## Fix

Clear `adoptNextSha` when the editor closes without saving, or scope it to the save. Better still, adopt the next checksum only when the save result returns it (match the saved checksum), instead of whatever re-read comes next.

**Acceptance:** with Edit ▸ Cancel added to w21/672's recheck, step 3 reads "changed or removed" and B survives. The screen's own successful edit still adopts its new checksum. A unit case covers cancel.
