# Since w21/823, Reload can adopt a different transaction after the edited one is deleted elsewhere, so the next Save overwrites it

**Severity:** major (a save can overwrite another entry). **Estimate:** 20 minutes. Owner: mobile. A3: `mobile/src/screens/edit-transaction-screen/relocate-entry.ts:52-65` (`relocatedEntryId`), called from `edit-transaction-screen.tsx` `relocateEntry`, adopts whatever single same-day transaction now sits at the old file and line. If the edited entry A was deleted elsewhere, the next same-day entry B moves up to A's line and is adopted. w21/823's resolution says deletions keep the "changed or removed" message.

Not run natively (it needs a concurrent delete timed between taps). Under `tsx` (the agent's proof), with the location main.beancount:10 on 2026-10-20, deleting A shifts B from line 14 to line 10, and the result is `{ids: ['hashB'], found: 'hashB'}`. Native steps once possible:
1. Use two 2026-10-20 entries, A (Cafe) and then B (Rent).
2. Open A ▸ Edit and paste a changed amount.
3. Delete A through the API, then Save ▸ Copy & Reload.

The editor opens on B under B's checksum, and saving the pasted draft overwrites B.

## Fix

Adopt a relocated candidate only if it is still recognisably A: the same payee and narration, or the same posting accounts. Otherwise keep the "changed or removed" message.

**Acceptance:** after A's deletion, Reload shows "changed or removed", and w21/823's amount-change case still relocates. Unit cases are added.
