# A link opened before sign-in is taken twice: the session effect opens it, then the sign-in finisher, finding the slot empty, restores the guest example or Home over it

**Severity:** minor (a shared ledger link is lost after signing in; from guest mode it is lost every time). **Estimate:** 30 minutes. Owner: mobile. A3: two readers share the pending-link slot without coordinating:

- **First reader:** `common/vars/session.ts:35` sets `sessionVar(session)` before the finisher runs. That re-renders `common/app-links/use-app-link-handler.ts`, whose session effect (`:153-158`) takes the stashed link and opens it.
- **Second reader:** `common/oauth/oauth-sign-in-finalizer.ts:38` calls `takePendingAppLink()` only after its `ListLedgers` request. It finds the slot empty and behaves as if no link was pending: it restores the guest view (`:63`, `ledgerVar(visit.ledgerId)` plus a replace at `:84`) or replaces to Home (`:100`). `signed-in-account.ts:17` also resets the selection to the first owned ledger when the link's ledger isn't one the user owns.

The finisher's own code puts a pending link ahead of the guest view. That ordering never applies, because the other reader already took the link.

Not run natively: the flow needs a sign-out, the OAuth sign-in and an accepted deep link, and on this simulator the "Open in Beancount?" alert can't be accepted by automation. The agent proved it under `tsx` with the real handler hook, `openAppLinkTarget`, `finalizeOAuthSignIn`, `initializeSignedInAccount`, `restoreGuestView`, the guest state and the pending-link slot (only React Native, the router and the network stubbed):

- **A. Guest sign-in, both calls 150 ms.** `ledgerVar = alice/books` → `replace /transactions` → `ledgerVar = open_ledger/example` → `replace /(app)/(tabs)/transactions`. It ends on the example ledger, and this happens every time.
- **B. No guest, `ListLedgers` 400 ms vs `GetLedger` 120 ms.** It opens the right ledger's journal, then `replace /(app)/(tabs)`, so it ends on Home and the link is dropped.
- **C. A link to a readable ledger the user doesn't own, `GetLedger` faster.** `ledgerVar = open_ledger/alphabet` → `ledgerVar = me/home`, ending on the wrong ledger's Transactions.

Real-world repro: signed out, Welcome ▸ Explore an example ▸ Transactions. Open `https://beancount.io/ledger/<you>/<your-ledger>/journal?account=Assets:Bank`, which waits for sign-in (w21/345). Then drawer ▸ Sign In. You land back on the example's Transactions.

## Fix

Give the slot one reader. Either the session effect skips while a sign-in is finishing and the finisher opens the link, or the finisher reads the slot before setting the session. Then run `initializeSignedInAccount`'s reset only when no link was opened.

**Acceptance:** in all three cases the app ends on the linked ledger's linked screen. A hook test covers the guest sign-in order.

## Dedupe

Not w21/083 (a link replayed for a later account) or w21/632 (guest detail links). Related to w21/345 (the link waits for sign-in). Searched `.pm/**` for takePendingAppLink, restoreGuestView and "pending link".

Also found, not filed: on Android, the "open in browser" fallbacks (`open-app-link.ts:81`, `use-app-link-handler.ts:101`, `ledger-drawer.tsx:703`) send `beancount.io/ledger/…` URLs that the app's own `autoVerify` App Link filter claims (`app.json:83`). That could loop back into the app once `assetlinks.json` is served, which is blocked in w4/blocked/001. Revisit when that unblocks; w21/346 avoided the same loop for profile links.

---

**Resolved 2026-10-23** — the slot now has one reader. Persisting the OAuth session first moves the waiting link into a held slot (`holdPendingAppLinkForSignIn`), so the link handler's session effect finds nothing; the sign-in finisher takes the held link (`takeHeldAppLink() ?? takePendingAppLink()`), opens it and skips the guest/Home restore, and an unused link is given back when the sign-in ends or fails (`releaseHeldAppLink`). Cases in `pending-app-link.test.ts` (`mobile`). Not run natively: the flow needs a sign-out, the OAuth sign-in and an accepted deep link.
