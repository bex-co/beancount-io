# An amount of 29 or more significant digits is accepted by the form, then the server refuses the save with a misleading "multiple postings with missing amounts" message

**Severity:** minor on production, because the ledger service's would-break guard stops it; the wording is what misleads. **Estimate:** 20 minutes. Owner: mobile, plus the ledger service for the second guard.

**Root cause (A3).**
- `parseExactAmount` (`mobile/src/screens/multi-postings-transaction/postings-utils.ts:93-120`) has no digit-count limit, and `validatePostings` (`:486`) and the budget parser (`budget-screen/build-budget-entry.ts:45-52`) have none either. The amount `TextInput` has no `maxLength`.
- The engine reads at most 28 significant digits: at 29 or more digits it raises `P0012 invalid number in amount (likely exceeds 28-digit Decimal precision)` for both legs, so the server's guard reports the entry as having postings with missing amounts.
- The ledger service's `isDecimalNumber` (`backend-cluster/ledger/src/foundation/rustledger/entry-build.ts:50`) checks only the shape of the number.

**Native (iPhone 17e, 2026-10-24, production).** Home → + → New Transaction, first amount: typing 29 nines on the keypad shows "99999999999999999999999999999" in green with Remainder "✓ $0.00" and Done enabled. Tapping Done keeps the screen open with the red banner "This would add an error to your ledger: Transaction has multiple postings with missing amounts in the same…". The ledger has no new error and no new entry (restored check: identical to the snapshot). I discarded the draft.

**Engine proof** (the agent's, `@rustledger/wasm` on the strings the app would send):
- `99999999999999999999999999999.00 USD` (29 digits) and its negative: `P0012` on both postings.
- `999999999999999999999999999.99` (27 integer digits and 2 decimals): no error, but the value parses as `1000000000000000000000000000.0`, so a silent change. The guard cannot catch that one.
- Add Budget `.0000000000000000000000000000001` becomes `0.0000000000000000000000000000`.

Twenty-eight digits works.

## Fix

Refuse more than 28 significant digits (integer plus fraction) in `parseExactAmount` and `parseBudgetAmount`, so the forms show the existing "Use digits…" message. As a second guard, make `isDecimalNumber` in the ledger service refuse it, so REST and MCP get the same protection.

**Acceptance:**
- Unit tests: 28 digits is accepted and 29 is refused, with and without a fraction (`999999999999999999999999999.99`), on the transaction and budget paths.
- A ledger service test: a 29-digit `units.number` is a 400 and writes nothing.

**Resolved 2026-10-24** — more than 28 digits is refused on both sides. Mobile: `parseExactAmount` returns null when the integer digits (without leading zeros) plus the fraction exceed 28, or the fraction alone does, so the transaction form and the budget parser (which calls it) show the existing "Use digits…" message. Ledger: `isDecimalNumber` applies the same limit to the number as it will be written (after exponent expansion; exponents past ±100 are refused), so REST and MCP writes get a 400 and nothing is committed. Tests: 28 accepted and 29 refused with and without a fraction (including `999…9.99`), and the `0.000…1` truncation case, on the transaction, budget and ledger paths; each fails without its fix.
