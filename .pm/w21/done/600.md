# Latest Updates never shows the commit you just made in the app (not invalidated on write, and cached for 5 minutes on the server)

**Severity:** low. **Estimate:** 20 minutes. Owner: mobile and backend-v2. A3 (code-level at `main` `c9cda71b9`; `tsx` confirmed that `getFeed` isn't cleared after a write): `mobile/src/common/apollo/invalidate-ledger.ts:93` leaves `getFeed` out on purpose ("not ledger-derived"), but its ledger rows are the user's own commits. Separately, `backend-v2/src/features/gitea/feed/service/feed-service.ts:28, 403-410` caches Gitea activity per user for 5 minutes, and nothing clears it on a write. After saving a transaction, Recent Transactions shows it, but Latest Updates doesn't change, even after a pull or a foreground refresh, for up to 5 minutes.

Not run natively: the feed card is below Home's fold.

## Fix

Invalidate `getFeed` after ledger writes, and bust (or shorten) the server's per-user activity cache when that user commits.

**Acceptance:** after an in-app save, a pull on Home shows the new "Committed to …" row. Tests cover both halves.

None found. Searched `.pm/**` for getFeed together with invalidate, and "feed" together with cache.

---

**Was blocked 2026-10-22** — Still wanted, but the server half needs a design decision and the mobile half alone cannot meet the acceptance. Invalidating `getFeed` in the app after a write is a one-line scope change, but it only refetches what the server holds, and backend-v2 caches a user's Gitea activity for five minutes (`feed-service.ts`, `TTL.MIN_5`). A ledger write reaches Gitea by many paths (GraphQL, REST and MCP workflows, the file editor, imports, a `git push` through the proxy), none of which tells the feed service, and the workflow layer may not depend on the feed feature. The choices are an event or hook from the write paths that busts `CACHE_KEYS.feed.giteaByUser` (new plumbing across surfaces, parity cases), or a shorter TTL (more Gitea load for every Home open, which the cache exists to avoid).

**Unblocked 2026-11-01** — Owner decision: bust the server's per-user activity cache when the user commits (a shared write hook), rather than shortening the five-minute TTL. Rationale: a commit should show in Latest Updates at once, without extra Gitea load on every Home open. Implementation notes for the worker: the hook must cover every write path (GraphQL, REST and MCP workflows, the file editor, imports, a git push through the proxy) without the workflow layer depending on the feed feature, plus the mobile `getFeed` invalidation after a write, tests for both halves, and a backend-v2 deploy.

---

**Resolved 2026-11-01** — backend-v2 drops a user's cached Gitea activity (`feed:gitea:all:<userId>`) on every write path without the workflow layer knowing about the feed: `ApiClient` takes an `onWrite` hook that the Fava client factory points at `invalidateUserFeed` for user clients (covers GraphQL, REST and MCP writes, the file editor and imports), and an accepted `git-receive-pack` over HTTPS or SSH does the same. The five-minute TTL is unchanged. Mobile lists `getFeed` in the ledger-write invalidation scopes. Tests: `api-client`, `public-client-factories`, `cache-helper`, `git-proxy-handler`, `ssh-relay`, `invalidate-ledger`. Needs a backend-v2 deploy before the app shows the commit at once. Shipped in the commit that moves this note to `done/` (`backend-v2`, `mobile`).
