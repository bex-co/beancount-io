# A write made while a refresh is still in flight shows pre-write data, because Apollo folds the post-write refetch into the older request

**Severity:** moderate. A deleted row stays listed and tappable, or a new entry is missing, until the next refresh (a tab switch after the 30-s gate, a return from background, or a pull). **Estimate:** 30 minutes. Owner: mobile. A3: `mobile/src/common/apollo/client.ts:30` builds the client without `queryDeduplication: false`, and `invalidate-ledger.ts:181` refetches with `refetchQueries`.

Not run natively in this pass. Proven at runtime with the real Apollo 3.14.1 client under `tsx`, using the app's `APOLLO_DEFAULT_OPTIONS`, `refreshOnForeground` and `invalidateLedgerData`. The fake server answers after 1.5 s with the rows as they stood when each request arrived:

```
server: read at t=105ms -> Coffee,QA DELME     (tab-focus refresh)
delete commits; invalidateLedgerData(entries)
list after the invalidation settled: ["Coffee","QA DELME"]
list 2s later: ["Coffee","QA DELME"]
```

No second request goes out. With `queryDeduplication: false`, a new read goes out at t=511ms and the list shows `["Coffee"]`.

The usual in-flight request is w21/837's tab-focus refresh or the foreground refresh (`refresh-on-foreground.ts:19`, `include: "active"`), which refetch every mounted tab's queries.

**Native steps** (timing-dependent; the delete has to land while the tab refresh is running, and a large or cold ledger widens the window):
1. Stay on Home for more than 30 s.
2. Tap Transactions.
3. Right away, open a disposable row, tap ⋯ and Delete.

**Expected:** after Back, the row is gone. **Actual:** the row is still listed, and tapping it opens "changed or removed".

## Fix

Bypass deduplication for invalidation reads: either set `queryDeduplication: false` on the client, or have `invalidateLedgerData` pass `onQueryUpdated` that refetches with `context: { queryDeduplication: false }`.

**Acceptance:** a unit case overlaps a refresh with an invalidation, and the list reflects the write.

## Dedupe

Searched `.pm/**` for "dedupl", "queryDeduplication" and "in-flight request". The only hits are server-side (w21/245, w21/369). This is different from w21/526 (paging reset, blocked), w21/837, w21/838 and w21/024.

---

**Resolved 2026-10-24** — the app's Apollo client is built with `queryDeduplication: false` (`common/apollo/client.ts`), so the refetch after a write goes out as its own request instead of folding into a refresh already in flight, which answered with pre-write rows. `write-during-refresh.test.ts` runs the real client over a slow link: a refresh overlapping an invalidation ends on the post-write rows (fails with deduplication on). Deviation: the global switch, not a per-refetch context; identical simultaneous reads are no longer merged. Not run natively.
