# Android can loop on a link to a ledger the user can't read: the app re-opens the same https URL it just handled

**Severity:** moderate, but Android only and unverified on a device (it depends on the platform's link verification, which I did not check). **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).** The `catch` after `client.query(GetLedgerDocument)` in `mobile/src/common/app-links/open-app-link.ts:70-80` ends in `Linking.openURL(sourceUrl)` for any query failure: a private ledger, a missing one, or no network.

`sourceUrl` is the same `https://beancount.io/ledger/<owner>/<name>/...` URL the app just handled. `mobile/app.json:75-87` claims that URL for the app with `autoVerify` and `pathPattern "/ledger/..*/..*"`. w21/346 chose `pathPattern` over `pathPrefix` to avoid exactly this re-open loop for profile links; the unreadable-ledger path wasn't covered.

Not run: I can't accept deep links on this simulator, so this is a code-path finding, not a reproduction. The path:
1. On Android, `openURL` of that URL resolves to the app itself.
2. The `url` event reaches `use-app-link-handler.ts:122`, then `handleUrl`, then `open()`.
3. `handlingRef` is true, so the event is queued (`:51-55`).
4. After the failed query the loop picks up `queuedRef.current` (`:84`) and runs again.
5. Each pass makes a network query and another `openURL`, so the user never reaches a browser.

The same path is reachable from the Home feed row (`feed-card.tsx:95`) and from a pending link after sign-in (`oauth-sign-in-finalizer.ts:45`). A teammate's private-ledger link is a realistic trigger.

**Native steps:** on an Android device with verified `beancount.io` app links, signed in as a user without access to `alice/private`, run `adb shell am start -a android.intent.action.VIEW -d "https://beancount.io/ledger/alice/private/journal"`. Expect the app to keep re-querying and never settle, or a flickering chooser.

## Fix

- Don't call `openURL` on an `https` URL the app's own filter claims. Show an in-app "Ledger unavailable, or you don't have access" state, or open it through a route the app doesn't claim, such as `expo-web-browser`.
- At minimum, add a reentrancy guard so a URL that just failed isn't re-handled.
- Treat offline and other transient errors separately from not-found or forbidden, so being offline doesn't hand the user to a browser.

**Acceptance:** a unit test for `openAppLinkTarget` with `GetLedger` rejecting: it must not call `Linking.openURL` with a URL matching the app-link pattern, and the handler must not re-enter for that URL. Extend the second-link harness: a failed link plus a re-delivered identical URL produces at most one probe.
