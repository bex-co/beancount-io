# The New File dialog accepts a path that reuses a file's name as a folder, or a folder's name as a file

**Severity:** minor. **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).**
- `checkLedgerFileName` (`mobile/src/screens/ledger-file-browser-screen/utils.ts:117-141`) compares only the first path segment, and only for case twins. It never checks whether a non-final segment is an existing file.
- The dialog's own existence check (`index.tsx`, about `:508-535`) reads `listingHasFile` (`utils.ts`, about `:215`), which skips `type === "dir"`, so a folder at the full target path passes too.

Not run natively: it needs a create that I expect the server to refuse, and I haven't confirmed what it returns. `tsx` proof (the agent's, with the real helpers):
- `checkLedgerFileName("main.bean/x", ["main.bean"])` returns `{ok: true, filename: "main.bean/x.bean"}`.
- `checkLedgerFileName("LICENSE/notes", ["LICENSE","main.bean"])` returns `ok`.
- `listingHasFile([{path:"sub/x.bean", type:"dir"}], "sub/x.bean")` returns `false`.

I expect Gitea to refuse these, so the dialog would close, the typed name would be lost and a toast would read "Failed to create file". That is unconfirmed.

**Native steps** (a `qa-` ledger only): create `qa-note.bean` first, then Files → + → `qa-note.bean/x` → Create.

## Fix

Pass entry types into `checkLedgerFileName`. Refuse, with the existing `exists` message, when a non-final segment equals an existing non-folder name and when the final name equals an existing folder. Let `listingHasFile` treat a folder at the target path as a clash.

**Acceptance:** the three inputs above return `ok: false` with a reason under the field, and Create is disabled.
