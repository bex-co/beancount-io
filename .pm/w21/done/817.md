# Edit Transaction's conflict alert is a dead end: "Keep Editing" can never save, and "Reload" discards the draft (the Files editor offers Copy & Reload)

**Severity:** minor. **Estimate:** 20 minutes. Owner: mobile. A3: `edit-transaction-screen.tsx:391-398`. After a conflict, `shaRef` and `entryHashRef` change only on a successful save or `handleReload`, so every retry from "Keep Editing" fails the same way. Unlike the Files editor (w21/273), there's no option to copy the draft before reloading.

Not run natively: it needs a concurrent change while the editor is open, which these taps can't time reliably. Code path (the agent's): open Edit Transaction, change the entry elsewhere (for example in the Files editor), then Save. The conflict alert appears, Keep Editing → Save gives the same conflict, and Reload loses the typed draft.

## Fix

Add the Files editor's "Copy & Reload" option, or reload and then re-apply the draft on top of the new checksum.

**Acceptance:** after a conflict, the user can keep their text and save it against the current version. A source case is added.

**Resolved 2026-10-23** — Edit Transaction's conflict alert (`edit-transaction-screen.tsx`) now offers the Files editor's "Copy & Reload" (w21/273) between Keep Editing and Reload. It reuses the existing `ledgerEditorCopyReload` and `ledgerEditorCopyFailed` strings, so all 13 locales already have them. `copyThenReload` copies the text now in the editor, which may be newer than the save's, to the clipboard. Only once that succeeds does it load the current version, under its new checksum. The user can paste their text there and save it against the current version. If the copy fails, the alert says so and nothing is reloaded. Keep Editing and Reload are unchanged.

A source case in `__tests__/save-failure.test.ts` pins the alert's options and the copy-before-reload order; it fails at the previous HEAD. A concurrent change can't be timed through these taps, so this was not checked natively. Shipped in the commit that moves this note.
