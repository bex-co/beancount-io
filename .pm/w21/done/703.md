# Home's net-worth hero draws its rolling digits misaligned for an Arabic-symbol currency: "1,234.5" sits above "00", with a stray digit below the 5

**Severity:** minor (the largest number on Home looks broken for KWD/BHD/OMR ledgers). **Estimate:** 30 minutes, plus investigation. Owner: mobile. A3 (suspected): the hero renders the figure as separate rolling digit columns plus static runs (`components/amount-text/rolling-glyphs.ts`). An Arabic-script symbol run ("ك.د") has a taller font ascent and descent (font fallback), which changes the static run's line box. The digit columns, sized from the Latin font's line height, then sit at a different baseline. Some columns also show part of their neighbouring digit, because the column's clip window no longer matches the glyph height. USD heroes render cleanly on the same device.

Native (iPhone 17e, Metro `--clear` at `eb0f12847`; disposable ledger with `option "operating_currency" "KWD"` and `Liabilities:Qa20261020Card -1234.500 KWD`, restored byte-for-byte afterwards): Home ▸ Net Worth hero, settled after 10 s, reads "-ك.د1,234.5 00". The glyphs "1,234." and "5" sit visibly higher than the trailing "00", and the top of another digit shows below the "5". The same glitch showed before w21/698's fix ("ك.د-1,234.5̥00"), so it isn't caused by that fix. Screenshots: `.tmp/qa-20261020/v3d.png` (local).

## Fix

Size the rolling columns from the line box of the run that actually renders (or render the static symbol run with the same fixed `lineHeight` and `includeFontPadding: false`), and align all runs on a common baseline. Alternatively, fall back to a single `Text` (no rolling) when the symbol is in a non-Latin script.

**Acceptance:** with this fixture, the hero's digits share one baseline and no partial digit is visible. USD, EUR and JPY heroes are unchanged. A render or snapshot case covers an RTL symbol.

## Dedupe

Not w21/698 (done; sign order) or w21/070 (the JPY symbol). Searched `.pm/**` for rolling-glyphs, "rolling digit" and hero together with misaligned.

---

**Resolved 2026-10-23** — root cause confirmed with CoreText at the hero's 28 pt: digits and Latin runs get a 33.0 pt line box, while the Arabic symbol's run falls back to `.SFArabic` with a 34.8 pt one. The glyph row's default `alignItems: stretch` stretched every digit cell to 34.8 pt, and `DigitSlot` steps its 0–9 column by the cell's measured height, so digit *n* drifted up by *n* × 1.8 pt (a 5 sat 9 pt high over the top of a 6; zeros stayed put). The digit cell now sets `alignSelf: "flex-start"`, so its window and step are one digit's line whatever the other runs measure. USD, EUR and JPY heroes are unchanged: all their runs share one line height, so nothing was stretched. The symbol's own run can sit about 0.9 pt lower than the digits (its fallback font's ascent). Tests in `rolling-glyphs.test.ts` cover the KWD glyph split and pin the unstretched window (the window check fails without the change); this runner cannot lay out React Native, so the visual result needs a native recheck. Shipped in the commit that closes this note (`mobile`).
