# Edit's Reload can't find a changed entry on a day with more than 10 transactions

**Severity:** low to moderate. On busy days, such as after a card-statement import, it brings back w21/823's dead end. **Estimate:** 30 minutes. Owner: mobile. A3: `sameDayTransactionIds` defaults to `limit = 10` (`mobile/src/screens/edit-transaction-screen/relocate-entry.ts:58, 75`). The journal comes back newest first, so later lines in the file come first within a day (`ledger-journal-service.ts:709-722`). Only the last 10 entries written that day get a context read, and one written earlier that day is never a candidate. Ten context reads per Reload is also wasteful.

Not run natively in this pass. `tsx` proof: with 12 same-day rows `h11…h0`, the IDs read are `h11…h2`. The target `h0` is never read, so `relocatedEntryId` returns `null`.

**Native steps:**
1. On a disposable ledger, add 12 transactions dated 2026-10-20.
2. Open the first one in the file, which is that day's bottom row, and Edit it.
3. Change it through the API, then Save ▸ Copy & Reload.

The screen reads "changed or removed" instead of showing the current version.

## Fix

- First match the journal rows by payee, narration or accounts (`recognisable`); those rows already carry them.
- Then read contexts only for the matches, with no fixed cap.
- If the day holds more than 50 entries, page through it.

**Acceptance:**
- With 12 or more same-day rows, the first-written target still relocates.
- Context reads are bounded by the number of matches.
