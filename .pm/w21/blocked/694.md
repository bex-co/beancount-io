# Since w21/672, Delete after a metadata-only change elsewhere dead-ends on "changed or removed", under an alert that says to delete again (w21/250 regression)

**Severity:** minor (a legitimate delete is blocked, and the messages contradict each other). **Estimate:** 20 minutes. Owner: mobile. A3: w21/250's acceptance says "a metadata-only change elsewhere followed by Delete succeeds after one refetch". On a stale checksum, Delete's `onStale` refetch (`transaction-detail-screen.tsx:487-490`) now gets a checksum different from the pinned one, and `isShownEntryReplaced` (`:416`, rendered at `:624-633`) switches the screen to "changed or removed" with no Delete. The CONFLICT alert from w21/250 still says the entry was reloaded and to try again.

## Fix

Tell a same-entry change apart from a twin swap. If the refetched slice is still this entry (same date, payee and postings, or the server confirms the ID still names it), adopt the new checksum and show the reloaded entry, as w21/250 intended. Otherwise show "changed or removed" and drop the "try again" alert text.

**Acceptance:** w21/250's metadata-only case deletes on the second try, and w21/672's twin case still reads "changed or removed". The alert never contradicts the screen. Unit cases cover both.

---

**Blocked 2026-10-23** — the two acceptance cases cannot both hold, for the reason recorded on w21/693. The fix proposes telling a same-entry change from a twin swap by "same date, payee and postings", but twin entries are defined by exactly that (they differ only in metadata), and the metadata-only change this note wants to adopt also differs only in metadata. The server's answer to the pinned ID is the same in both cases (another slice and checksum, same position), so any rule that adopts the first adopts the second and deletes the surviving twin, which w21/672 forbids ("B survives"). Reloading and showing the fresh entry before a second Delete would let the user see the difference, but then a confirmed second Delete still removes the twin.

**Unblock:** the same owner decision as w21/693: whether a stale re-read that returns another slice for the same ID is always "changed or removed" (safe; w21/250's metadata-only Delete then needs reopening the entry, and its CONFLICT alert text should say so rather than "try again"), or may be adopted after the user sees the reloaded entry (w21/250's flow, accepting that the swapped twin can then be deleted knowingly). With the first chosen, the work here is the alert wording (`deleteTransactionChanged`) in `transaction-detail-screen.tsx` and its translations. Clearable by the owner only.
