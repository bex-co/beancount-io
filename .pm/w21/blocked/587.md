# Deleting a file that `main.bean` includes just says "Deleted", with no warning, though the ledger then breaks (missing include) or silently loses the file's entries (glob include)

**Severity:** minor (silent data loss from balances). **Estimate:** 45 minutes. Owner: backend-v2 and mobile. A3 (code-level at `main` `b1ba52fcd`): mobile's `ledger-file-browser-screen/index.tsx:588-651` (`confirmDelete`) and `:656-667` (the dialog) say only `Delete "jan.bean"? This cannot be undone.`. The server's delete (`ledger-workflow.ts:972-1011`) checks only `assertKeepsEntryPoint`, while its rename (`:1066-1150`) finds the `include` lines and globs that point at the file and refuses or rewrites them. The file editor warns after saving ("Saved, with a new ledger error"), but delete has no such check.

Scenario: `main.bean` has `include "books/2026/jan.bean"` and `include "books/2025/*.bean"`. Deleting `jan.bean` toasts "Deleted", and a missing-include error appears only on the bell. Deleting `books/2025/a.bean` produces no error at all, and its entries drop out of every balance.

Not run natively (it needs folder fixtures; this QA run keeps file writes minimal).

## Fix

On delete, find includes that reach the file (as rename does). Warn in the dialog ("main.bean includes this file; its entries will be removed from the ledger"), or refuse an exact include, on all three surfaces.

**Acceptance:** both deletes warn before confirming, and the surfaces agree. Tests cover an exact include and a glob.

## Dedupe

See w21/079, w21/380 and w21/550. Searched `.pm/**` for "include" together with delete, warn and break.

**Unblocked 2026-10-30** — Owner decision: before a file is deleted, the app and the web dashboard look up which `include` lines reach it and warn in the confirm dialog, with a checkbox to also remove those references from `main.bean`, checked by default. Delete is never refused. Recorded reading, to confirm with the owner if it matters: only an exact `include` line is removed with the file; a glob include that merely matches it is warned about and left alone (removing it would affect other files); a REST, GraphQL or MCP delete behaves as today unless it asks for the references to be removed, so existing agents and clients are unaffected. Order: backend-v2 and ledger (a read-only lookup of the includes that reach a file, plus an opt-in remove-references option on delete, parity cases on all three surfaces) and deploy, then the mobile and dashboard dialogs. Tests cover an exact include and a glob.

**Blocked 2026-10-30** — re-triaged at `main` before building, and the recorded decision rests on a premise that no longer holds. Confirmed in the code: since w23/m4 (`0ee2cb9b8`, `b3973458f`, `3a22ea011`) the server **refuses** to delete a file another ledger file still `include`s, on REST, GraphQL and MCP, as `BAD_USER_INPUT` naming the includers (`utils/include-references.ts`; proven by `delete guard via %s` in `rename-parity.test.ts`). Glob includes never count, so deleting a file a glob matches still silently drops its entries. The mobile Files screen shows the server's refusal as an error toast through `ledgerWriteFailureMessage`; it does not offer to fix it. So an exact include is not the silent "Deleted" the note describes; the gap that remains is (1) the glob case, and (2) the refusal has no one-step way out (the user must edit `main.bean`, then delete again).

The 2026-10-30 owner decision (warn before deleting, with a checkbox to also remove the references, checked by default, never refused) was made on the note's account. Implementing it as written would change a shipped, parity-tested refusal, so it is not started.

**Unblock:** the owner chooses one of: (a) keep the refusal as the default and add an opt-in `removeIncludes` on delete (REST, GraphQL, MCP, parity cases, deploy), with the app showing the includers from the refusal and offering "Remove the include and delete"; plus a read-only lookup so a glob that matches the file is warned about; (b) only the app and dashboard change: on the refusal they show the includers and a one-tap way to open `main.bean`, no server change, glob case left as is; (c) leave as shipped and drop this note. Recommendation: (a) without the glob warning first, i.e. the opt-in `removeIncludes` and the dialog; the glob warning is a separate read. Who can clear it: the repository owner.
