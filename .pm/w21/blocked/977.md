# `LedgerPrices` pulls every price date for every commodity pair, and Apollo writes and reads all of them on every mount

**Severity:** moderate for ledgers priced daily across many commodities. **Estimate:** 1 hour (needs a backend change). Owner: backend-v2 and mobile.

**Root cause (A3).** `mobile/src/common/graphql/queries/ledgerPrices.graphql` asks for `getLedgerCommodities { base quote prices { date } }`, read through `useLedgerPrices` (`common/hooks/use-ledger-prices.ts:17`) on Home, Accounts and Account detail with the default `cache-and-network` policy, so it refetches on each mount. The schema has no argument to limit the prices, yet the consumer needs very little: `priceCadenceDays` (`common/valuation.ts:183`) uses only the last 10 dates (`CADENCE_WINDOW`, `:65`), and `latestPriceDate` takes the newest.

Not run natively; it needs a daily-priced, multi-commodity ledger. `tsx` proof (the agent's; a real `InMemoryCache`, `@apollo/client` 3.14.1; the payload sizes are the fixture's, not measured production responses):

| Pairs × prices each | Price points | First write | Read | Refetch rewrite |
|---|---|---|---|---|
| 10 × 365 | 3.7k | 31 ms | 53 ms | 32 ms |
| 40 × 365 | 14.6k | 100 ms | 147 ms | 166 ms |
| 40 × 3,650 | 146k | 503 ms | 483 ms | 288 ms |

The 146k-point case is about 7 MB of JSON, so also about 7 MB on the wire per refetch.

## Fix

This is a backend change, so it goes through REST, GraphQL and MCP parity: add something like `prices(last: Int)` or `latestDates`, and request about 11 dates per pair. A mobile-only option is to defer the query until a valuation caption is actually shown.

**Acceptance:** the payload per pair is bounded by a constant; Home mount with 40 pairs × 3,650 days spends under 50 ms in the Apollo write plus read; `selectValuation` stale-price results are unchanged.
