# Edit Transaction's Reload after a conflict opens the other twin's text, so the next Save overwrites it (w21/672 acceptance gap)

**Severity:** major (data loss; misses w21/672's acceptance "Editing from a stale screen never opens the other twin's text"). **Estimate:** 15 minutes. Owner: mobile. A3: w21/672 guards only the editor's first seed with `isOtherSlice` (`edit-transaction-screen.tsx:196`). `handleReload` (`:214-239`), the action behind the conflict alert's "Reload", re-reads by entry ID and reseeds both `shaRef` and the editor text without that check. After the entry's twin moved onto the ID, Reload loads the twin's slice and checksum, and the next Save replaces the twin.

Not run natively: the twin has to be deleted while the editor covers the app, which needs an API write mid-flow (the agent proved the path). Steps:

1. Twins as in w21/672. Home ▸ A ▸ pencil.
2. Delete A elsewhere (another device, or the API).
3. Change any text ▸ Save, which raises the conflict alert ▸ **Reload**.
4. The editor now shows `receipt: "B-002"` under B's checksum. Save overwrites B.

`isOtherSlice("shaA","shaB")` returns `true`, but `handleReload` never calls it.

## Fix

Apply the same `isOtherSlice` check in `handleReload`. When the reload returns a different slice, show "changed or removed" instead of loading it.

**Acceptance:** the steps above end on "changed or removed", and B is untouched. A plain conflict on the same entry still reloads that entry's new text. A unit case is added.

**Blocked 2026-10-23** — the acceptance cannot be met as written, so it needs an owner decision. A conflict on an entry means its slice changed under the same ID. Two cases look identical to the editor: (1) a twin entry moved onto the ID after the entry was deleted elsewhere, and (2) the same entry changed in a way that keeps its content hash (metadata or comment lines). Both answer the ID with a different checksum, and the twin even sits on the deleted entry's old line, so neither the checksum (`isOtherSlice`) nor the source location tells them apart. Applying `isOtherSlice` in `handleReload` therefore refuses every Reload after a conflict (the only way to reach it), which contradicts "a plain conflict on the same entry still reloads that entry's new text". w21/672 already took the safe side on the detail screen (a settled re-read with another slice reads "changed or removed").

**Unblock:** the owner chooses (a) Reload after a conflict always ends on "changed or removed" when the slice differs from the one the editor loaded (safe, consistent with w21/672; the conflict alert's Reload then only helps when the slice is unchanged, so the alert should drop it or say so), or (b) keep Reload as it is and rely on the editor showing the reloaded text. With (a) chosen this note is a 15-minute change in `edit-transaction-screen.tsx` `handleReload` plus the alert copy. Clearable by the owner only.
