# A sale whose lot doesn't match is still counted in every balance: cash +600, broker −5 VTI, gains missing, so the books don't balance

**Severity:** major (Accounts, net worth and account detail all show figures that Beancount rejects). **Estimate:** 1–2 hours. Owner: ledger. A3: `engine.ts:611-627` takes rustledger's `raw.directives` unchanged, including an entry that failed booking. Beancount drops that entry. The error *is* reported ("No matching lot"), but every balance still counts the half-booked sale. Its interpolated Income leg is missing, so the trial balance no longer sums to zero.

Production, through GraphQL on the disposable ledger (restored byte-for-byte; ledger service as deployed 2026-10-22), and the agent's run of the real `main` service code (`e911af9c8`) against an in-memory store, with `bean-check`/`bean-query` 3.2 as the reference.

```
2026-01-02 * "QA Fund"   ; BrCash +5000.00, Equity −5000.00
2026-02-01 * "QA Buy"
  Assets:Qa20261020Broker  10 VTI {100.00 USD}
  Assets:Qa20261020BrCash  -1000.00 USD
2026-03-01 * "QA Sell"
  Assets:Qa20261020Broker  -5 VTI {101.00 USD} @ 120.00 USD
  Assets:Qa20261020BrCash  600.00 USD
  Income:Qa20261020Gains
```

`getLedgerErrors` reports "No matching lot for VTI in Assets:Qa20261020Broker (2026-03-01, "QA Sell")". `getLedgerTrialBalance(conversion:"at_cost")` still gives BrCash **4600.00**, Broker **495** and Gains **{}**. bean-query gives BrCash 4000.00 and Broker 10 VTI {100} = 1000. In the agent's run, at-cost net worth is 5095.00 against 5000, and an ambiguous `{}` sale behaves the same way, adding a stray cost-less "−1 VTI".

## Fix

Exclude entries that failed booking from the realized stream, as Beancount does, and keep reporting the error. Alternatively, mark such entries so that balances skip them.

**Acceptance:** with this fixture, the trial balance matches bean-query and sums to zero, and the error is still listed. A unit case is added.

Beancount drops such an entry. Dropping it from the shared snapshot (a) removes it from the journal and Entry Context, which is where a user opens a broken entry to fix it (w21/367 depends on that), and shifts twin occurrence IDs; keeping it listed but excluding it from balances (b) means marking it and teaching every balance path (trial balance, balance sheet, account journal, BQL) to skip it, with BQL running inside the engine over the original files. Either is a cross-cutting change with a ledger deploy, and the choice (hide vs list-but-flag) changes what the app shows for a broken entry.

**Unblock:** the owner picks (a) drop it from reports and the journal, keeping it reachable through the error list and file editor, or (b) keep it in the journal with a "not booked" flag and exclude it from balances; then this note is workable in `backend-cluster/ledger` (`engine.ts` after `locateBookErrors`, which already pairs `BOOK` errors with transactions by date and narration).
