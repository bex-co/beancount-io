# Merchants keeps full-width and half-width payees as separate merchants, and search can't find the full-width one

**Severity:** minor (moderate for Japanese ledgers). **Estimate:** 20 minutes. Owner: mobile.

This is the Merchants side of w21/912.

**Root cause (A3).** `mobile/src/common/merchant-key.ts:15-20` (`merchantKey`) applies NFC, folds quotes, Arabic script and whitespace, and lowercases. It does no width (NFKC) folding. Both directory grouping (`aggregate-payees.ts:180`) and search (`filterMerchants`, `aggregate-payees.ts:234`) use it.

Not run natively in this pass. `tsx` proof against the real selectors:
- **Grouping:** `ＡＭＡＺＯＮ．ＣＯ．ＪＰ` ×6 and `Amazon.co.jp` ×3 come out as two merchants (6 and 3). So do `ｽﾀｰﾊﾞｯｸｽ` ×4 and `スターバックス` ×2.
- **Search:** `amazon` returns only `Amazon.co.jp`. `merchantKey("ＡＭＡＺＯＮ．ＣＯ．ＪＰ")` is `ａｍａｚｏｎ．ｃｏ．ｊｐ`.

**Native steps:**
1. Add payees `ＡＭＡＺＯＮ．ＣＯ．ＪＰ` and `Amazon.co.jp` to the disposable ledger.
2. Open Drawer ▸ Merchants. There are two rows, and searching `amazon` hides the full-width one.

## Fix

In `merchantKey`, fold U+FF01–FF5E to ASCII and half-width katakana U+FF61–FF9F to their NFKC forms, as in w21/912's engine fix. The detail screen already queries every raw spelling (`otherSpellings`, `exactPayeeFilter`), so its count and totals follow the merged row.

**Acceptance:**
- Each pair above merges into one row whose count is the sum.
- `amazon` finds that row.
- The detail counts both spellings.
- Unit cases sit next to the existing Turkish, Arabic and NFD ones.
