# A token refresh whose response is lost (backgrounding or a network blip) signs the user out on the next refresh, because the server rotated the token and then treats the retry as reuse

**Severity:** major (involuntary sign-out, grant revoked). **Estimate:** 1–2 hours across mobile and backend-v2. Owner: mobile, with a backend-v2 option. A2: the mobile OAuth client always rotates refresh tokens. If the app sends a refresh, the server commits it (RT1 consumed, RT2 issued), and the client never stores RT2, the client keeps RT1. Ways to lose RT2: the response is lost to backgrounding or a cell/Wi-Fi handoff, `persistSession` fails, or the session check rejects the result. The next refresh presents RT1. oidc-provider's reuse detection then **revokes the whole grant** and answers `invalid_grant`, which the client correctly treats as terminal. The user lands on Welcome and must sign in again.

Environment: `main` at `e87a32d61`. Harness-level evidence: the shipped `OAuthTokenManager` (`mobile/src/common/oauth/token-manager.ts`, compiled unmodified) was run against a fake token server implementing oidc-provider's rotation and reuse rules. A dropped response or failed save can't be forced on the simulator with the current tooling.

| scenario | attempt 1 | attempt 2 | grant | sign-out calls |
| --- | --- | --- | --- | --- |
| control | AT2 | AT2 | kept | 0 |
| response lost after the server rotated | `OAuthRefreshError(false)` | `invalid_grant` → terminal | **revoked** | **1** |
| `persistSession` throws after rotation | `OAuthRefreshError(false)` | terminal | **revoked** | **1** |

## Root cause

- Client (`token-manager.ts:150-208`): every failure after the request is sent (fetch reject, JSON parse, token parse, stale-session check, `persistSession`) throws a *transient* error and keeps the old refresh token. That error is retryable only if refresh tokens are reusable.
- Server (`backend-cluster/backend-v2/src/features/oauth/data/config.ts:218-229`): `shouldRotateRefreshToken` returns `true` for the mobile client unconditionally. oidc-provider's refresh grant revokes the grant when a consumed refresh token is presented again.

## Fix

Pick one and record it in the OAuth ADR.

- **Server (preferred):** accept a just-rotated refresh token again within a short grace window (for example 30–60 s, the common rotation-reuse leeway), returning the same successor instead of revoking. Keep reuse detection outside the window.
- **Client:** treat a refresh as possibly committed once it was sent. On a lost response or save failure, keep the session in a "refresh pending" state and retry with the grace-window semantics, instead of replaying RT1 later as if nothing happened. Persist RT2 before anything else can fail.

**Acceptance:** with the harness's lost-response and failed-save scenarios, the next refresh succeeds and the grant survives. True reuse after the grace window still revokes. A contract test covers rotation, the lost response and reuse.

**Was blocked 2026-10-21** — Confirmed at HEAD:
- `shouldRotateRefreshToken` (`backend-cluster/backend-v2/src/features/oauth/data/config.ts`) always rotates for the mobile client.
- `OAuthTokenManager` keeps the old refresh token after any failure that happens once the request is sent.

A client-only change cannot recover a lost response: the client never received RT2, so only the server can hand it back. The fix therefore means accepting a just-rotated refresh token again within a grace window. That relaxes the always-rotate and reuse-detection posture that ADR 019 D5 and the MCP spec's public-client rule set for a public authorization server. The note itself asks for the choice to be recorded in the OAuth ADR. That is a security-policy decision this loop cannot make on its own.

No partial work was shipped.

**Unblocked 2026-11-01** — Owner decision: allow a just-rotated refresh token to be presented again within a 30-second grace window instead of revoking the grant. Rationale: a lost refresh response (backgrounding, network handoff) should not sign the user out; the cost is a slightly relaxed reuse-detection posture for that window. Implementation notes for the worker: backend-v2 accepts the immediately previous refresh token for 30 seconds and returns the already-issued successor, the client keeps its "refresh pending" handling, and the choice is recorded by amending ADR 019 (D5) with the contract test the note asks for (rotation, lost response, reuse after the window still revokes).
