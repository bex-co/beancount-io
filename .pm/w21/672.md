# Deleting one of two same-day twin entries shifts the other onto its ID, so a stale screen's Delete silently removes the survivor

**Severity:** major (data loss; two same-day coffees that differ only in `receipt:` or other metadata are ordinary data). **Estimate:** 1–2 hours. Owner: ledger (and mobile). A3: the entry ID ignores entry and posting metadata (`backend-cluster/ledger/src/foundation/rustledger/entry-hash.ts:189`, `hashEntry`). Twins are told apart only by a position suffix (`base`, `base:1`; `entryIdFor` and `buildEntryIdMap` at `:346` and `:375`), and that suffix moves when one twin is deleted. On mobile, a transaction detail kept open while the entry is deleted from another screen re-reads the same ID on focus (`transaction-detail-screen.tsx:390-395`). That read now returns the *other* twin's slice and checksum, and Delete (`:413`, `:420`) uses them, so the sha guard passes. The screen also keeps showing the row it was opened from (`:362`, `:473`), and "changed or removed" appears only when the re-read fails (`:519`). Edit and Reload (`edit-transaction-screen.tsx:154`, `:205`) re-read by the same ID too. This is the transaction counterpart of w21/476, which was fixed for budgets only.

Production, through GraphQL on the disposable ledger (restored byte-for-byte):

```
2026-10-01 * "QA TwinCafe" "Coffee"
  receipt: "A-001"
  Assets:Qa20261020Cash  -3.00 USD
  Expenses:Qa20261020Coffee  3.00 USD

2026-10-01 * "QA TwinCafe" "Coffee"
  receipt: "B-002"
  Assets:Qa20261020Cash  -3.00 USD
  Expenses:Qa20261020Coffee  3.00 USD
```

1. The journal lists A as `db885261…` and B as `db885261…:1`.
2. Deleting A with its checksum succeeds.
3. Re-reading `db885261…` now returns B's slice (`receipt: "B-002"`), and `db885261…:1` returns NOT_FOUND.
4. `deleteLedgerEntrySourceSlice(db885261…, <that checksum>)` returns "Deleted entry db885261…".
5. Both entries are gone.

That is exactly what the app does when the same entry is opened twice, from Transactions and again from account detail: delete it in the second screen, go back, and Delete in the first. In the variant where B is opened first, the untouched B is reported as "changed or removed". The agent's `tsx` proof against `LedgerJournalService` shows the same, and it adds that byte-identical twins delete with the original checksum. Not tapped through natively.

## Fix

Make twin IDs stable across a sibling's removal: include metadata in the hash, or salt the hash with something that doesn't shift. Also have mobile send, and the server check, the checksum of the slice the screen *displayed*. Treat a re-read whose slice differs from the shown row as "changed".

**Acceptance:** with this fixture, the second delete is refused (or the first screen says "changed or removed"), and B survives. Editing from a stale screen never opens the other twin's text. A unit case covers metadata-only twins.

Transaction counterpart of w21/476 (done; Custom/budget entries).
