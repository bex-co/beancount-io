# Transactions and Account detail rebuild every date header on each loaded page, with an uncached date formatter

**Severity:** minor, and the least proven of this group. **Estimate:** 30 minutes. Owner: mobile.

**Root cause (A3).**
- `transaction-display-utils.ts:530` calls `formatLedgerDate` for every date section of all loaded rows, and `transactions-screen.tsx` re-runs `groupToSections` whenever `transactions` changes, which is each 20-row page. Account detail does the same at `select-account-journal.ts:472`.
- `common/date-format.ts:55` calls `date.toLocaleDateString(locale, opts)` on every call, with no cached formatter.

Not run natively; the disposable ledger is small. `tsx` proof (Node/V8, the agent's; Hermes is likely slower but not measured):
- `groupToSections` with 3 entries per day: 1,000 rows take 30 ms, 5,000 take 93 ms, 20,000 take 536 ms. The cost is paid again on each page, so a long scroll is quadratic overall.
- `toLocaleDateString` costs about 83 µs per call. A cached `Intl.DateTimeFormat` is about 14 times cheaper: 102 ms against 7.4 ms for 5,000 calls.

## Fix

Cache one `Intl.DateTimeFormat` per locale and a `Map` from ISO date to display string. Optionally, group incrementally.

**Acceptance:** `groupToSections` with 20,000 rows takes under 100 ms, with identical output for `en`, `de` and `fa`.
