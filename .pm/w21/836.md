# The account picker can't find an Arabic-spelled account from Persian typing, then offers "Create" for a look-alike duplicate

**Severity:** moderate. **Estimate:** 20 minutes. Owner: mobile. A3: `mobile/src/common/account-search.ts:48,92` (`toNfc`, `fuzzyMatch`) compares letters literally. `closedAccountNamed` and `notYetOpenAccountNamed` (`account-close-dates.ts`) don't fold either.

Not run natively. Under `tsx` (the agent's proof), with accounts `Assets:Qa20261020:بانك-ملي` and `Expenses:Qa20261020:Coffee`:
- `filterAccounts("ملی", …)` → `[]`, and `filterAccounts("بانک", …)` → `[]`.
- `visibleAccountSections` → 0 sections, and `showCreateAccountRow` → `true`.

A tester would see "No matching accounts" and a Create "ملی" row that opens Open Account for an identical-looking second account.

## Fix

Run both sides through the shared Arabic-script fold (w21/835), keeping it index-aligned like `lowerAligned`. Use it in the closed and not-yet-open exact-name checks too.

**Acceptance:** `ملی` finds the `ملي` account, and no Create row is offered for a look-alike. Unit cases are added.

## Dedupe

Not w21/060, 255, 256, 258 or 642 (İ, NFD, spaces, ranking). Searched `.pm/**` for account-search together with Persian and Arabic.
