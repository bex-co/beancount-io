# Full-width and half-width Japanese text don't match their ordinary forms in search

**Severity:** moderate for Japanese ledgers. Card and bank exports write "ＡＭＡＺＯＮ．ＣＯ．ＪＰ" and half-width "ｽﾀｰﾊﾞｯｸｽ", while the keyboard types "amazon" and "スターバックス". **Estimate:** 30 minutes. Owner: ledger and mobile. A3: no width folding (NFKC) on either side. Mobile's `plain-search-filter.ts` (`searchUnits` `:84`, `encodeUnit`) handles only NFC/NFD. The engine's `foldForSearch` (`backend-cluster/ledger/src/foundation/rustledger/directive-filter.ts:242`) folds only Turkish dotted İ and Arabic script.

Not run natively in this pass. `tsx` proof with the real helpers:
- "amazon" and "amazon.co.jp" return nothing against "ＡＭＡＺＯＮ．ＣＯ．ＪＰ".
- "スターバックス" misses "ｽﾀｰﾊﾞｯｸｽ 渋谷".
- "abc" misses "ＡＢＣ".

**Native steps:** add payee `ＡＭＡＺＯＮ．ＣＯ．ＪＰ`, then search `amazon`. Nothing is found.

## Fix

- **Engine:** in `foldForSearch`, map U+FF01–FF5E to ASCII and half-width katakana (U+FF61–FF9F) to their NFKC forms, on the text side. This is one engine shared by REST, GraphQL and MCP, so parity holds.
- **Mobile:** fold the same ranges in the search text before escaping, so a full-width "．" doesn't become an unescaped regex dot.

**Acceptance:** each pair above matches in both directions. The existing Turkish, Arabic and NFD tests stay green.

## Dedupe

Only digit-entry items (w21/192, w21/230, w21/365) and w21/333 (brand logos) came up. Searched for "half-width", "full-width", "katakana", "NFKC" and "width".
