# Internationalization (i18n) System

This document describes the architecture and usage of the i18n system in Beancount Dashboard.

## Overview

The dashboard supports **13 languages** with a feature-based translation architecture designed to work seamlessly with SSR (Server-Side Rendering) and client hydration.

## Architecture

### Language Detection Priority Chain

The system uses a cascading priority for language detection:

```
1. URL Query Parameter (?lang=xx or ?locale=xx)
         ↓ (if not found)
2. Cookie (i18nextLng)
         ↓ (if not found)
3. Accept-Language Header
         ↓ (if not found)
4. Default: English (en)
```

### SSR → Client Hydration Flow

```
┌─────────────────────────────────────────────────────────────────────┐
│                           SERVER (SSR)                               │
├─────────────────────────────────────────────────────────────────────┤
│  1. Request arrives with headers (Cookie, Accept-Language)          │
│  2. i18n-ssr.ts detects language from:                              │
│     - URL params (?lang=xx)                                         │
│     - Cookie (i18nextLng)                                           │
│     - Accept-Language header                                        │
│  3. createSSRI18n(language) initializes i18n instance               │
│  4. Render HTML with detected language                              │
│  5. server.ts injects: window.__I18N_LANGUAGE__ = "xx"              │
└─────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────┐
│                         CLIENT (Hydration)                           │
├─────────────────────────────────────────────────────────────────────┤
│  1. i18n.ts reads window.__I18N_LANGUAGE__ for initial lang         │
│  2. Before React renders: sync cookie → localStorage                 │
│  3. HydrationHandler waits for hydration to complete                │
│  4. After hydration (requestIdleCallback):                          │
│     - Check URL params for language override                        │
│     - Apply localStorage preference if different                    │
│     - persistLanguage() saves to both localStorage + cookie         │
└─────────────────────────────────────────────────────────────────────┘
```

### Dual Storage Mechanism

Language preference is stored in **both** localStorage and cookie:

| Storage      | Purpose                                     | Expiry |
| ------------ | ------------------------------------------- | ------ |
| localStorage | Client-side preference for fast access      | None   |
| Cookie       | SSR language detection (server can read it) | 1 year |

The `persistLanguage()` function writes to both:

```typescript
// src/common/lib/utils/i18n.ts
export function persistLanguage(lang: SupportedLanguage): void {
  localStorage.setItem("i18nextLng", lang);
  document.cookie = `i18nextLng=${lang}; path=/; expires=...`;
}
```

## Core Files

| File                               | Purpose                                                                           |
| ---------------------------------- | --------------------------------------------------------------------------------- |
| `src/common/lib/utils/i18n.ts`     | Client-side i18n initialization, `persistLanguage()`, language constants          |
| `src/common/lib/utils/i18n-ssr.ts` | SSR language detection functions (`createSSRI18n`, `detectLanguageFromURL`, etc.) |
| `src/entry-client.tsx`             | Client hydration with `HydrationHandler` component                                |
| `src/entry-server.tsx`             | SSR rendering with language detection                                             |
| `server.ts`                        | HTML injection of `window.__I18N_LANGUAGE__`                                      |
| `src/locales/index.ts`             | Aggregation layer (196 imports → 13 language exports)                             |

## Hooks

### `useTranslations()`

Type-safe translation hook with development-time validation.

```typescript
import { useTranslations } from "@/common/hooks/i18n/use-translations";

function MyComponent() {
  const { t, i18n } = useTranslations();

  return (
    <div>
      <h1>{t("auth.login")}</h1>
      <p>{t("common.save")}</p>

      {/* With interpolation */}
      <p>{t("common.welcome", { name: "John" })}</p>

      {/* Change language */}
      <button onClick={() => i18n.changeLanguage("zh")}>
        Switch to Chinese
      </button>
    </div>
  );
}
```

**Development Validation:**

- Warns if key doesn't use namespace prefix (e.g., `"login"` instead of `"auth.login"`)
- Warns if key doesn't exist in English translations

### `useLocaleSync()`

Syncs language preference from the user's backend profile on initial load.

```typescript
import { useLocaleSync } from "@/common/hooks/i18n/use-locale-sync";

// In __root.tsx or app layout
function RootLayout() {
  useLocaleSync(); // Loads user's locale from backend profile
  return <Outlet />;
}
```

**Behavior:**

- Only runs when user is logged in
- Only applies backend locale if no localStorage preference exists
- Respects user's explicit local choice over backend profile

## Translation Organization

### Feature-Based Structure

Translations are organized by feature, with 16 locale directories:

```
src/
├── common/locales/           # Shared translations (common.*)
├── features/
│   ├── auth/locales/         # auth.*
│   ├── ai-agent/locales/     # aiAgent.*
│   ├── bql/locales/          # bql.*
│   ├── collaboration/locales/ # collaboration.*
│   ├── journal/locales/      # journal.*
│   ├── ledger/locales/       # ledger.*
│   ├── ledger-data/locales/  # ledgerData.*
│   ├── ledger-editor/locales/ # ledgerEditor.*
│   ├── ledger-list/locales/  # ledgerList.*
│   ├── ledger-settings/locales/ # ledgerSettings.*
│   ├── reports/locales/      # reports.*
│   ├── user-profile/locales/ # userProfile.*
│   ├── user-settings/locales/ # userSettings.*
│   └── git/
│       ├── commits/locales/  # commits.*
│       └── pull-requests/locales/ # pullRequests.*
└── locales/
    └── index.ts              # Aggregation layer
```

### Namespace Prefixing Convention

**All translation keys MUST use namespace prefixes.** This is enforced at development time.

```typescript
// ✅ Correct - namespaced keys
t("auth.login");
t("common.save");
t("journal.addTransaction");

// ❌ Incorrect - unprefixed keys (will show console error in dev)
t("login");
t("save");
```

### TranslationEntry Format

Each translation is defined with a message and description for translator context:

```typescript
// src/features/auth/locales/en.ts
export interface TranslationEntry {
  message: string;
  description: string;
}

const enAuth: Record<string, TranslationEntry> = {
  "auth.login": {
    message: "Log In / Sign Up",
    description: "Button label for login or signup",
  },
  "auth.email": {
    message: "Email",
    description: "Label for email input field",
  },
  // ...
};
```

The `extractMessages()` function in `src/locales/index.ts` transforms this into the flat format i18next expects:

```typescript
// Input: { "auth.login": { message: "Log In", description: "..." } }
// Output: { "auth.login": "Log In" }
```

## Adding New Translations

### Step 1: Add to English Locale

Add your translation to the appropriate feature's English locale file:

```typescript
// src/features/[feature]/locales/en.ts
const enFeature: Record<string, TranslationEntry> = {
  // ... existing translations

  "feature.newKey": {
    message: "Your translation text",
    description: "Context for translators about when/where this is used",
  },
};
```

### Step 2: Add to Other Languages

Add the same key to all 12 other language files in the same directory:

```typescript
// src/features/[feature]/locales/zh.ts
"feature.newKey": {
  message: "您的翻译文本",
  description: "Context for translators",
},
```

### Step 3: Use in Component

```typescript
const { t } = useTranslations();
return <span>{t("feature.newKey")}</span>;
```

### Interpolation

Use single braces `{variable}` for dynamic values:

```typescript
// In locale file
"feature.greeting": {
  message: "Hello, {name}!",
  description: "Greeting with user's name",
},

// In component
t("feature.greeting", { name: user.firstName })
```

## Adding New Languages

### Step 1: Update i18n.ts Constants

Add the language code to `SUPPORTED_LANGUAGES` and `LANGUAGE_NAMES`:

```typescript
// src/common/lib/utils/i18n.ts
export const SUPPORTED_LANGUAGES = [
  "en",
  "zh",
  "es" /* ... */,
  ,
  "new", // Add new code
] as const;

export const LANGUAGE_NAMES: Record<SupportedLanguage, string> = {
  // ... existing
  new: "New Language", // Add display name
};
```

### Step 2: Update i18n-ssr.ts

Add the same language code to the SSR SUPPORTED_LANGUAGES array:

```typescript
// src/common/lib/utils/i18n-ssr.ts
const SUPPORTED_LANGUAGES = ["en", "zh", "es" /* ... */, , "new"] as const;
```

### Step 3: Create Locale Files

For each feature directory with locales, create `new.ts`:

```bash
# Example directories to update:
src/common/locales/new.ts
src/features/auth/locales/new.ts
src/features/journal/locales/new.ts
# ... (16 directories total)
```

### Step 4: Update Aggregation Layer

Add imports and exports in `src/locales/index.ts`:

```typescript
// Add imports for all feature locales
import newAuth from "@/features/auth/locales/new";
import newCommon from "@/common/locales/new";
// ... all features

// Add merged object
const new: Record<string, string> = {
  ...extractMessages(newCommon),
  ...extractMessages(newAuth),
  // ... all features
};

// Update exports
export { en, zh, /* ... */, new };
```

### Step 5: Update i18n.ts Resources

Add the new language to the i18n resources:

```typescript
// src/common/lib/utils/i18n.ts
import { en, zh, /* ... */, new } from "@/locales";

i18n.init({
  resources: {
    // ... existing
    new: { translation: new },
  },
});
```

## URL Language Override

Users can override their language preference via URL query parameters:

```
https://dashboard.beancount.io/ledger?lang=zh
https://dashboard.beancount.io/ledger?locale=fr
```

Both `?lang=` and `?locale=` are supported. The URL parameter:

- Takes highest priority over cookie and Accept-Language header
- Is persisted to localStorage and cookie when applied
- Works on both SSR and client-side navigation

## Key Design Decisions

### Why is LanguageDetector Disabled?

The i18next `LanguageDetector` plugin is intentionally **not used**. Here's why:

```typescript
// i18n.ts - Note: NO LanguageDetector
void i18n
  .use(initReactI18next) // Only react-i18next, no detector
  .init({
    lng: getInitialLanguage(), // Manual control
  });
```

**Problem with LanguageDetector:**

- It reads localStorage immediately during initialization
- This happens **before** React hydration
- SSR used a different language (from cookie/header)
- Result: Hydration mismatch error (React error #419)

**Solution:**

- Read `window.__I18N_LANGUAGE__` (injected by SSR) for initial language
- Manually sync/apply language preference **after** hydration completes
- Use `HydrationHandler` component to coordinate timing

### Why Dual Storage (localStorage + Cookie)?

| Scenario          | localStorage Only | Cookie Only | Both (Current) |
| ----------------- | ----------------- | ----------- | -------------- |
| SSR first render  | ❌ Can't read     | ✅ Works    | ✅ Works       |
| Client preference | ✅ Fast           | ⚠️ Slower   | ✅ Fast        |
| Cross-tab sync    | ❌ No             | ✅ Yes      | ✅ Yes         |
| Expiry control    | ❌ No             | ✅ Yes      | ✅ Yes         |

Using both provides the best of both worlds:

- **Cookie**: Server can detect language for SSR
- **localStorage**: Client can quickly check without parsing cookies

### Why Namespace Prefixing is Enforced

1. **Prevents key collisions**: Different features can have `save` or `cancel` keys
2. **Improves maintainability**: Easy to find where a translation is used
3. **Enables code splitting**: Future optimization for lazy-loading translations
4. **Developer experience**: IDE can autocomplete with clear context

```typescript
// Without namespacing - collision risk
t("save"); // auth.save? journal.save? common.save?

// With namespacing - clear and safe
t("auth.save");
t("journal.save");
t("common.save");
```
